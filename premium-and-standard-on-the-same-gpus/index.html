BNK and gateways

Premium and standard on the same GPUs

Tiers for inference traffic: who is served first, and who is turned away when the pool is full

Northlight Compute sells the same model, Qwen3-32B, to two kinds of caller. One is a paying customer whose users chat with an assistant and expect the first word within a second or two. The other is a batch job that summarizes documents and does not care when each summary arrives. When both land in one pool of three GPU workers and are served in order of arrival, the chat waits behind the summaries, and the most valuable traffic gets no better service than the cheapest. Tiering fixes that. Each request is put in a tier, and the tier decides which request leaves the queue first and which is turned away when the pool is full. This lesson builds that up and works one overload through with numbers.

Chapter 1 of 13

One pool, one line

A chat message waits behind summaries that came first

Start with no tiers. Three workers serve Qwen3-32B and every request is a POST to the same path. A batch job owned by the tenant docmill starts and sends sixteen documents to be summarized. A moment later a user of the tenant acme, a paying customer with an interactive assistant, sends a chat message. The data plane spreads the requests over the workers, and each worker serves its own queue in order of arrival. The chat message lands behind summaries that came first.

Nothing is broken. Every GPU is busy and every request will be answered. The capacity is being spent in the wrong order: the request whose value depends on speed is waiting for requests that would have been just as useful an hour from now. This is called head-of-line blocking. On the wire the two kinds of request differ only in size, about 1 kB for the chat message and about 40 kB for a document, and the pool has no field that says which one a person is watching.

F5's tiering slide describes the pain in three lines. Workloads differ in what they need from latency and throughput. All traffic lands in a single GPU pool. Premium capacity is spent on work that did not need it, which lowers the revenue each GPU earns. The slide stops there, and one more point follows from it. A utilization graph hides all of this, because it reads near 100 percent in the good case and in the bad one. The number to watch is the wait of each kind of request, measured separately.

Chapter 2 of 13

Which tier is this request in

Decided at the gateway, from identity, before any GPU is chosen

A tier is a label on a request, and something has to attach it. There are three common ways. By tenant or key: the API key identifies the tenant, and the tenant's contract names the tier. This is the strongest, because the caller cannot change it. By header: the caller, or a gateway in front, sets a header that names the tier, which is useful when one tenant has both interactive and batch workloads. By model alias: the caller asks for a model name such as qwen3-32b-batch, and the gateway maps that name to the same model with a lower tier.

Whichever is used, the decision belongs at the gateway. A tier header that arrives from the internet is only a claim, so the gateway removes it and writes its own. F5 words the result as traffic routed by SLA and workload type. The SLA comes from the contract behind the key. The workload type comes from the header or the alias.

The label then has to reach whatever enforces it. For separate pools it stays a header that a route can match. For one pool with priorities, the open source picker reads the header x-llm-d-inference-objective, which names an object that holds a priority. A second header, x-llm-d-inference-fairness-id, names the flow a request belongs to. Set to the tenant, it lets two tenants of the same tier share that tier's turn fairly. The gateway fills both in from the key and never copies them from the caller.

Chapter 3 of 13

First way: a pool for each tier

Hard walls, and idle capacity that stays on its own side

The simplest way to serve tiers is to give each one its own workers. In Kubernetes that is two InferencePool objects, and a route at the gateway sends each request to a pool according to its tier. An InferencePool picks its model server Pods with spec.selector, names their port in spec.targetPorts and names its endpoint picker in spec.endpointPickerRef. An HTTPRoute rule matches the tier header and lists one pool as its backend. Say gpu-1 and gpu-2 serve premium and gpu-3 serves batch.

Premium traffic is fully protected, because batch requests never reach its workers. The pools can also differ: newer GPUs or a longer context for premium. F5's picture of tiering draws this layout. A policy check sits in front of three tiers, premium on GB200 systems, standard batch and economy, and premium GPUs are kept for premium demand.

The cost shows at night. Premium uses 2 of its 8 places while ten summaries wait for the 4 places on gpu-3. Six places stand idle next to a queue. Walls protect in both directions. They keep batch out of premium capacity, and they keep idle premium capacity from doing any batch work. With requests of 6 seconds, gpu-3 frees a place every 1.5 seconds, so the tenth summary in line starts after 15 seconds. Lending a worker means changing its labels so the other pool selects it. If the pools run different models or settings, it also means a restart and the three minutes Qwen3-32B takes to load.

Chapter 4 of 13

Split by intent: a chat pool and a reasoning pool

What the request asks for decides how long it holds a GPU

Tiers answer who is calling. A second question cuts across them: what kind of work the request is. One premium tenant may send a quick chat turn and, a minute later, a question it wants the model to reason through at length. F5's deck draws this split on a slide titled Reduce latency by optimizing workloads. On the left is standard Kubernetes. Every request queues together, heavy jobs block urgent traffic, latency spikes and becomes unpredictable, and the average wait is 250 ms, marked unacceptable. On the right is BNK. A policy check classifies requests by intent and cost, chat goes to a low latency pool, reasoning goes to a high throughput pool, and the average wait is 12 ms, about 21 times shorter. Those are figures from a vendor slide, shown as an example. The slide does not say which model, what load or how the wait was measured.

The cost of a request is mostly how long it holds a place on a worker, and that is set by how many tokens it generates. Qwen3-32B has a thinking mode, and it is on by default. In that mode the model first writes its reasoning inside a <think> block and only then writes the answer. Its model card recommends allowing 32,768 output tokens for most queries and 38,912 for hard maths and programming problems. This lesson takes a chat turn with thinking switched off to be about 300 tokens, an illustrative length, since real answers vary with the question. Take an illustrative speed of 50 tokens per second for each running request. A 300 token chat answer holds its place for 6 seconds, the figure the rest of this lesson uses. A 4,000 token reasoning answer holds its place for 80 seconds.

Now mix the two. gpu-3 has four places, all held by reasoning requests that started at evenly spaced times, so a place frees every 80 ÷ 4 = 20 seconds. A chat message that arrives at a random moment waits 10 seconds on average and up to 20. On a worker that runs only chat, a place frees every 6 ÷ 4 = 1.5 seconds, so the same message waits 0.75 seconds on average and at most 1.5. The GPU is just as fast in both cases. The chat's wait is set by the length of the work in front of it, 80 seconds against 6. This is the head-of-line blocking the slide draws as a small request stuck between heavy ones.

Intent is written in the request body, and a route cannot read a body. An HTTPRoute matches on path, headers, query parameters and method. So the step that reads the body has to turn intent into a header, and in this lesson that step is the AI gateway, the policy check of F5's slide. The signals are the ones the open source picker's outlen-bucket plugin uses to guess the length of an answer, checked in order with the first match winning. chat_template_kwargs.enable_thinking set to true means a long reasoning answer. A thinking_budget above 4,000 means the same. A tool_choice of required or of a named function means a short answer, and so do tools in the request with thinking not switched on. A client cap on output tokens below 500 means short. Everything else is unknown. One more check runs after the first match and applies to its result: a cap below 2,000 turns a long guess into unknown, because a long chain of reasoning cannot fit in it. The length of the prompt is left out on purpose, because it says nothing about the length of the answer.

Qwen3 adds a trap. Its thinking mode is on unless the request turns it off, so a request that says nothing about thinking will reason at length and still classify as unknown. The gateway needs a rule for unknown. The safe one sends unknown to the reasoning pool and asks chat applications to send enable_thinking false, which also makes their answers shorter. Inside a conversation the soft switches /think and /no_think in a prompt change the mode turn by turn while enable_thinking is true. With /no_think the model still writes a <think></think> block, and leaves it empty.

The two pools are InferencePools selected by label, built the same way as the tier pools above: qwen3-chat on gpu-1 and gpu-2, qwen3-reasoning on gpu-3, and an HTTPRoute rule for each value of the workload header. Each pool can be set up for its job. Qwen3-32B reads 32,768 tokens natively, and its config allows 40,960 positions, 32,768 kept for output and 8,192 for the prompt. A reasoning worker needs that full length and the KV cache to hold it. A chat worker can run with a shorter --max-model-len and fit more requests in the same memory. Intent and tier then combine. Intent picks the pool, and an InferenceObjective whose spec.poolRefs lists both pools orders each pool's queue by tier. A premium reasoning request waits only behind other reasoning. A premium chat never waits behind an 80 second chain of thought.

Chapter 5 of 13

Second way: one pool and an order

Every worker serves every tier, and a number decides who goes first

The other way keeps one pool and gives each tier a priority. In the Gateway API Inference Extension this began as a field called criticality with three values: Critical, Standard and Sheddable. It was replaced by an object, InferenceObjective, with an integer field priority. That object is now maintained with the open source endpoint picker in the llm-d router project, as llm-d.ai/v1. A higher number is more important. An unset priority counts as 0, and negative values are allowed.

A request names its objective in the header x-llm-d-inference-objective, which the gateway sets from the tier. The picker looks the objective up and reads the priority. From then on the priority has two uses: it orders the requests that are waiting, and a negative one marks traffic that may be refused when the pool is saturated. The type's own comment gives the rule. Requests with priority 10 are always served before requests with priority 0, and requests with priority -10 always after. Fairness is tracked only between requests of the same priority.

An objective says which pools it applies to in one of two ways, and one of them must be set. spec.poolRefs lists up to 16 pools by name in the same namespace. spec.poolSelector matches pools by label and may not be empty. Once the picker has taken the object in, status.conditions holds a condition of type Accepted. Three objects with the same poolRefs are all it takes to put three tiers on the same three workers.

Chapter 6 of 13

How the picker knows the pool is full

Two readings per worker, two targets, one average

Refusing from the bottom needs a definition of full. The open source picker gets it from a saturation detector, and the default one is called utilization-detector. The picker's configuration loader fills it in when no detector is named, whether flow control is on or off. It uses two readings that the picker collects from every model server: how many requests wait in the server's own queue, and what fraction of its KV cache is in use. The KV cache is the GPU memory that holds what the model has already read for each running request. Each reading is divided by a target, 5 waiting requests and 0.8 of the cache by default. The larger of the two results is the worker's score.

The pool's saturation is the plain average of the worker scores. Take gpu-1 with 3 waiting and 0.72 of its cache in use, gpu-2 with 6 and 0.64, gpu-3 with 5 and 0.76. Their scores are 0.9, 1.2 and 1.0, and the average is 1.03. At 1.0 or above the pool counts as saturated, and in the picker's default mode that is the moment a request with a negative priority is refused. The detector can also filter the candidates for a pick. With the default headroom of 0, a worker above 5 waiting is left out, so gpu-2 is skipped until its queue drains.

The readings must be fresh. By default a worker whose metrics are older than 200 ms counts as fully saturated. If the picker loses its path to every worker's metrics, saturation reads exactly 1.0 and refusals begin. That looks like overload on a dashboard and is a monitoring fault.

Chapter 7 of 13

Inside the model server the number runs the other way

vLLM can order its own queue, with lower meaning sooner

The picker decides which request reaches a worker first. The worker has a queue of its own, and by default vLLM serves it in order of arrival. Started with --scheduling-policy priority, it orders waiting requests by a priority field in the request body, and by arrival time when two are equal. Here a lower value is handled earlier, the opposite of InferenceObjective, so whatever fills in the field has to turn the scale around. The picker can do it itself. Its configuration has a switch, requestHandler.propagatePriority, which is false by default. While it is off, the picker forwards the request body unchanged, with whatever priority the caller wrote in it. When it is on, the picker deletes any priority the caller sent and writes the objective's priority in its place. For a worker whose Pod carries the label llm-d.ai/engine-type: vllm it writes the value negated. Premium at 10 becomes -10, standard stays 0 and batch at -10 becomes 10. No gateway rule is needed for the mapping. A worker without that label gets the value as it is, and vLLM would then serve premium last, so the label belongs in the Pod template of the qwen3 Deployment. The field is a signed 32-bit integer and defaults to 0, so negative values are allowed.

Priority also decides who gives way. When the GPU runs out of KV cache blocks, vLLM pauses a running request to free memory, and in priority mode it picks the one with the highest value that arrived last. The paused request gives up its blocks and goes back to the waiting queue. Its work up to that point is done again when it is scheduled the next time, so a pause costs GPU time as well as waiting time.

Without the flag, any priority other than 0 is rejected as an error. A fleet where some workers have the flag and others do not will fail a share of its tiered requests, so the flag on the workers and propagatePriority on the picker belong to one rollout, done in that order: every worker first, then the picker. The worker's order matters most when the picker lets requests pile up in the workers' queues, which is its default behaviour.

Chapter 8 of 13

The queue inside the picker

Flow control holds requests back and releases them by priority

The picker has two ways to act on priority. The older one is on by default. It lets every request with priority 0 or above go straight to a worker, and it refuses a request with a negative priority at the moment the pool is saturated. Nothing waits in the picker. Excess requests pile up in the workers' own queues.

The newer one is flow control, switched on with the feature gate flowControl. Requests now wait in the picker and leave by priority as capacity frees. Each priority value is a band. Inside a band, requests are grouped into flows by the header x-llm-d-inference-fairness-id, and turns are shared fairly between the flows of that band. Each band has limits: maxRequests, 5000 by default, and maxBytes, with maxRequestsPerFlow and maxBytesPerFlow for a single flow. A request that finds its band full is refused at once. One that waits longer than defaultRequestTTL, 60 seconds by default, is dropped from the queue.

Sheddable requests behave differently under flow control. They are queued under the same limits and are no longer refused the instant the pool saturates. To get quick refusals back, lower the limits of the batch band, which is what this lesson does with 4 requests and 30 seconds. A caller can shorten its own wait with the header x-llm-d-inference-ttl, written as a duration such as 10s. It cannot extend a finite limit. A request that flow control admitted and sent on carries its wait back in the response header x-llm-d-flow-queue-duration-ms, as whole milliseconds, with 0 when it did not have to wait.

Chapter 9 of 13

A burst, worked through

Twenty-four requests for twelve places

All numbers here are illustrative. Each worker runs four requests at a time, so the pool has 12 places, and every request holds a place for 6 seconds. All 12 are busy and finish evenly spaced, so one place frees every half second. In one instant 24 requests arrive: 4 premium, 4 standard and 16 batch. Served in order of arrival, the last one starts after 12 seconds, and a premium chat that happens to be 21st in line waits 10.5 seconds.

With priorities the picker holds the line itself. The batch band is set to hold 4 requests, so 12 batch requests are turned away at once. The 4 premium requests start at 0.5, 1, 1.5 and 2 seconds. The standard ones follow, and the last of them starts at 4 seconds. The 4 batch requests that were kept start between 4.5 and 6 seconds.

One rule produces every figure: the request that is nth to be released starts n times 0.5 seconds after the burst. Tiering changes only the value of n for each request. The GPUs do the same amount of work either way, 12 requests started in the first 6 seconds. The 30 second limit on the batch band is never reached, because the last kept batch request waits 6 seconds. The 12 refused requests cost the pool almost nothing. They were answered in about a millisecond and never held a place.

Chapter 10 of 13

Turned away with a clear answer

A 429 that says why and when to return

Refusing a request is only useful if the caller can act on it. The open source picker answers a refused request with status 429, Too Many Requests, and the header x-llm-d-request-dropped-reason. Its value is rejected-saturated when the queue for that band is full and rejected-ttl-expired when a request waited longer than its limit. A third value, rejected-flow-limit, means the band had room and this caller's own flow was at its limit. A retry-after header gives a number of seconds when the picker has an estimate of at least one second.

The picker answers 503, Service Unavailable, when the pool has no workers at all. So 429 means capacity exists and is taken, and 503 means there is none. The same 503 covers a picker that is shutting down and a caller that hung up while its request was queued. Each has its own reason value, which is what a dashboard should count by.

A batch client treats 429 as an instruction to wait and try again. That is why shedding protects the top tier: a request refused in a millisecond takes no place on a GPU and adds nothing to anyone's wait. In this example the docmill job retries its 12 refused requests 4 at a time, at 8, 14 and 20 seconds after the burst. Each round fits the batch band of 4. The pool is quiet by then, so every round starts at once, and the last summary is running 20 seconds after the burst.

Chapter 11 of 13

Who is shed first

Callers nobody can vouch for go before batch, by an iRule and a band of their own

Refusing from the bottom leaves one decision open: what the bottom is. Batch traffic is cheap, and it is also known and paid for. Below it sits traffic nobody can vouch for: a key that matches no customer, or a caller on a watch list. The write-up says only unknown or suspect callers. Scraping, probing or sending a flood are examples of why a caller might be listed, given here as illustrations. The owner's write-up of BNK as an AI platform puts that traffic in a tier of its own, named suspect-traffic, so that it is shed first when the GPU pool saturates. The label is written by an iRule, a short Tcl program attached to the endpoint that runs in BNK's data plane for each request, before the endpoint picker sees it.

The rule runs on the HTTP_REQUEST event. It first removes the objective header x-gateway-inference-objective, so that a caller cannot set its own priority with it. If the request carries the header x-caller-key, the rule hashes the key with sha256, which returns the 32 byte SHA-256 digest, and base64 encodes the digest into a 44 character string. It removes x-caller-key so the key travels no further, and looks the hash up in a table called static::callers. A hit gives the caller's name. If there is no name, or the name is listed in a second table, static::suspect, the rule inserts the objective suspect-traffic. The tables hold hashes, so the rule never holds a raw key. Variables in the static:: namespace are meant for values that do not change while the rule runs, so the tables are written into the rule and refreshed by publishing a new version of it. In the write-up a controller fills them. On an endpoint that refuses unknown keys outright, only the watch list matters. On one that serves callers without a key, such as a free trial endpoint (an illustrative case), the rule covers both.

The rule in the write-up removes x-gateway-inference-objective, the header's older name. The open source picker reads the current name, x-llm-d-inference-objective, first, and falls back to the older one only when the current one is missing or empty. A caller who sends x-llm-d-inference-objective: premium-chat would keep it, and the picker would never look at the suspect-traffic label. Against that picker the rule has to remove both names. It can then insert either one, because with both removed the picker finds only the inserted header. The current name is the clearer choice. Two more conditions make the label work. An InferenceObjective named suspect-traffic must exist, because a request that names a missing objective is served at priority 0, the same as standard. And its priority must be the lowest of all, here -20 against -10 for batch.

What shed first means depends on the picker's mode. With flow control off, the picker refuses every request with a priority below 0 at the moment saturation reaches 1.0. Suspect traffic and batch go at the same instant, and the difference between -20 and -10 is not used. With flow control on, bands are released from the highest priority down, so suspect traffic leaves last, and three settings make it go first. The first is a small band: maxRequests 2 for priority -20, so a third suspect request waiting at once is refused. A maxRequests of 0 does not mean none. Like an omitted value, it gives the default of 5000. The second is a short wait: defaultRequestTTL 5s for that band, against 30s for batch. The third is a holdback ceiling for each priority.

The priority-holdback-policy plugin gives each priority a ceiling between 0 and 1. In every dispatch cycle the picker compares the pool's saturation with each ceiling, and a band whose ceiling the saturation has reached is held back. Its requests stay queued while higher bands still dispatch. Ceilings may not rise as priority falls. With explicit ceilings of 1.0 for premium, 0.95 for standard, 0.85 for batch and 0.6 for suspect traffic, a pool at 0.55 serves everyone. At 0.62 suspect traffic stops leaving the queue. At 0.88 batch stops too. At 0.97 only premium is released, and at 1.03 nothing is released until the saturation falls. A priority below the lowest anchor takes that anchor's ceiling, so a later band at -30 would also stop at 0.6. Holding is not refusing. Held suspect requests are refused when their band of 2 is full, with rejected-saturated, or after 5 seconds in the queue, with rejected-ttl-expired. Batch requests held at 0.88 can wait up to 30 seconds and usually start once the burst has passed.

The last setting reaches requests that are already running. With enableEviction set to true in the flowControl section, false by default, the picker may end in-flight requests with a priority below 0 when higher-priority requests are blocked by saturation. The victim is chosen lowest priority first, and among equals the one dispatched most recently, because it has the least work stored in the KV cache. A running suspect request is ended before any batch request, and premium and standard requests are never chosen. The caller sees the drop reason evicted. The whole shedding order fits in one line: unknown and suspect callers first, then batch, then standard, and premium never.

Chapter 12 of 13

What an operator watches

One object to list, three signals to graph, three ways it goes wrong

The tiers themselves are objects, so the first check is a listing. kubectl get on InferenceObjective prints the pools and the priority of each as columns, and the status of each object holds its Accepted condition. A typing mistake matters here. A request whose header names an objective that does not exist is served with priority 0, so a misspelled premium tier quietly becomes standard.

Three signals show whether tiering works. The first is the wait per tier. With flow control on, the response to every request it admitted and dispatched carries x-llm-d-flow-queue-duration-ms, 0 when there was no wait, and the gateway can record it by tier. The second is refusals, counted by the value of x-llm-d-request-dropped-reason. A steady stream of rejected-saturated on the batch band is the design at work. rejected-ttl-expired on the premium band means the pool is too small. The third is the gauge flow_control_pool_saturation next to flow_control_stale_endpoints.

Three failures are specific to this setup. If the picker cannot collect metrics from the workers, every worker counts as saturated, dispatch halts and queued requests are dropped when their limit runs out. If the queue limit is longer than the timeout of the client or the gateway, callers give up on requests that are still queued, and those show up as rejected-context-cancelled. If the picker runs as several active replicas, each has its own queue and limits, so the pool can be sent more than it has room for. The picker's documentation covers a shared counter and fixed shares per replica for that case.

Chapter 13 of 13

The same GPUs earn more

A cheap tier that can be refused turns idle headroom into work

Now the business side, with illustrative prices: a premium request earns 10 units, a standard one 3 and a batch one 1. In the six seconds after the burst the pool starts 12 requests either way. In order of arrival those are 2 premium, 2 standard and 8 batch, worth 34 units. With priorities they are 4 of each, worth 56. That is 4.67 units per request started against 2.83, on hardware that did not change. F5 calls this figure revenue efficiency, and its tiering slide shows it going from low to high.

The larger gain comes before any burst. A provider with one line has to keep places empty so that premium chats start quickly, and empty places earn nothing. With priorities those places can run batch work, because batch traffic gives way the moment premium demand arrives. Four places that were held idle can start 2,400 batch requests an hour.

Filling the headroom has a price, and it is small. A premium chat that arrives when all 12 places are busy waits for the next one to free, at most half a second here, where an empty place would have taken it at once. The premium price rests on a promise about waiting time, and tiering is what lets the provider keep that promise on full GPUs. The batch tier is sold on the opposite terms: a low price, no promise about when, and a 429 with a reason when the pool has no room.

What to keep

Label the request, order the queue, refuse from the bottom

One pool served in order of arrival treats a paying customer's chat and a batch summary alike, and under load the chat waits. Tiering starts by labelling each request at the gateway, from the key, a trusted header or a model alias. The tiers can then be served by separate pools, which isolates them and strands idle capacity, or by one pool with priorities. With priorities the picker releases waiting requests from the highest band first, the model server can order its own queue the same way, and when the pool is saturated the lowest band is refused with a 429 that says why. In the burst worked here, a premium chat waited at most 2 seconds where it would have waited 10.5, on the same three workers. Intent gives a second split: chat and reasoning in pools of their own, so a short answer never waits behind an 80 second chain of thought. At the very bottom, an iRule labels callers nobody can vouch for as suspect-traffic, and a small band, a low holdback ceiling and eviction make sure they are shed before batch.
