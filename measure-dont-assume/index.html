GPU and hardware

Measure, don't assume

Same hardware, same commands, two thirds of the speed

A GPU copy is sixty bytes of commands and one doorbell write. So it should be possible to write those bytes yourself, ring the doorbell yourself, and match CUDA's speed with no CUDA at all. Public research did exactly that, with a small library that replaces CUDA for copies. It worked, and it ran at two thirds of the speed, on the same GPU, over the same link, with almost the same commands. This lesson follows the hunt for the missing third. The cause was something nobody thought to check, and it is the same mistake a load balancer makes when it treats identical GPUs as equal.

The same habit then turns outward, to numbers other people publish. A load balancer that counts connections while the GPUs hold three million tokens of cache. A vendor slide with three percentages and no baseline. A gateway benchmark whose method sits in small type under the chart. A lab that stands a Linux tunnel in for a DPU, and a simulator that has to be shaped like a card before its numbers mean anything. Each one is read the way the copy was measured: find what was really run, do the arithmetic, and say what the number cannot carry.

Chapter 1 of 18

Three identical workers

What the spec sheet says

Three GPU workers serve one model. Each is a vLLM Pod with one H100, the same image, the same flags and the same 34.3 GB of weights: Qwen3-32B in its official FP8 build, Qwen3-32B-FP8, which stores most of its 32.8 billion parameters at 1 byte each and keeps some layers at higher precision. Their readiness probes all pass, so the pool lists three endpoints: 10.244.1.21, 10.244.2.22 and 10.244.3.23, all on port 8000. On paper there is nothing to tell them apart.

Round robin was built for a pool like this. It keeps one counter and deals requests out in turn: 1, 2, 3, 1, 2, 3. That is fair only if two things hold. Every server must clear work at the same speed, and every request must be the same amount of work. A readiness probe checks neither. It asks whether the server answers on its health endpoint. A worker answers that at full speed, at two thirds of full speed, and with a queue ten deep.

The spec sheet makes the same kind of promise one layer down. An H100 has 80 GB of memory and a PCIe Gen5 x16 link. That link runs 16 lanes at 32 gigabits a second, and 128 of every 130 bits are data, which comes to about 63 GB/s each way. Hold on to both assumptions, equal servers and hardware that runs at its rating, while we go inside gpu-2 and try something that should be simple: one copy, built by hand.

Chapter 2 of 18

A copy without CUDA

Eighteen words, by hand

Inside gpu-2 the experiment uses a small open library from public research. It allocates its own channel through the kernel module, maps the ring and the doorbell, and writes the copy command by hand. A bulk copy between host memory and GPU memory runs no program on the compute cores. The copy engine does it, hardware that streams bytes over PCIe while the cores stay free for other work. The H100 in the measurements is the PCIe card, with 114 core groups. The module drawn on this board has 132.

The name H100 covers several parts, and the differences matter when two machines are compared. NVIDIA's Hopper architecture paper gives the full GH100 die 144 SMs, the SXM module 132 and the PCIe card 114, so the products ship with some of the die switched off. Memory is 80 GB of HBM on the PCIe card and on the SXM module, and 94 GB on the H100 NVL. NVIDIA's product page gives the SXM 3.35 TB/s of memory bandwidth and the NVL 3.9 TB/s. Between the cores and that memory sits an L2 cache shared by the whole chip: 60 MB on the full die and 50 MB on the H100 products. None of those figures limits a host copy. The copy leaves the card over PCIe at about 63 GB/s each way, and the SXM's memory runs about 53 times faster than that. For the lesson's model the link sets a floor on loading. Qwen3-32B-FP8's 34.3 GB of weights need at least 0.54 s to cross a Gen5 x16 link at its full rate, and the rest of the three minutes a load takes is spent elsewhere.

The command is a list of 4-byte words in the pushbuffer. A header word names the method that comes next, says how many argument words follow, and names the subchannel they are for. CUDA's captured copy is 15 words, 60 bytes: one header over four address words, then the length, a launch, the semaphore and a second launch. The hand-built version is 18 words, 72 bytes.

The 12 extra bytes are accounted for exactly. Eight are SET_OBJECT, a header and the class number 0xC8B5, which binds the copy engine to subchannel 4. CUDA does that once when it creates the channel and never repeats it. The other four are a second address header, because the library gives the source and the destination a header each where CUDA runs all four address words under one. Each address is 57 bits wide, sent as 25 high bits and 32 low bits.

Chapter 3 of 18

Two launches and no direction

What the launch word's bits say

The word that starts the copy is LAUNCH_DMA, and its bits are public in the headers of NVIDIA's open kernel module. The first launch is 0x182. Bits 1:0 hold 2, a non-pipelined transfer that runs to completion as one unit. Bits 7 and 8 say that the source and the destination are plain linear memory. Add 0x002, 0x080 and 0x100 and the result is 0x182. The flush bit and the semaphore bits are zero, so this launch moves data and reports nothing.

The second launch is 0x00c and moves no bytes. Its transfer type is 0. Bit 2, value 0x004, is the flush: make the copy engine's earlier writes visible first. Bits 4:3 hold 1, value 0x008, which releases a one-word semaphore, the 4-byte value the CPU is polling for. CUDA sends 0x14 here, with 2 in the semaphore bits, a four-word release that also writes a timestamp. Setting the flush and semaphore bits on the copy itself gives 0x18e, one fused launch, and that form worked in the tests too.

Two limits follow from the format. LINE_LENGTH_IN is a 32-bit count of bytes, so one launch moves at most 4 GiB minus one byte and anything larger is several launches. And no bit says which way the data goes. Swap the source and destination addresses and the same 18 words copy from the host to the GPU.

Chapter 4 of 18

The first fault

A ring entry with one field in the wrong place

The ring entry is 8 bytes, two 32-bit words that point at the 72. The first word carries bits 31:2 of the pushbuffer's address in its own bits 31:2, with bit 0 left clear for an unconditional fetch. The second carries address bits 39:32 in its low byte and the length, counted in words, in bits 30:10. For a pushbuffer at 0x2_0001_0000 holding 18 words, the right entry is 0x00010000 and 0x00004802. Eighteen shifted left by 10 is 0x4800, and the high address byte is 0x02.

The first run copies nothing. NVIDIA's headers describe each field by its bit range, and the helper macro that fills a field expects the field's value and shifts it into place itself. For this field the value is the address divided by four, because commands are always 4-byte aligned. The library handed the macro the whole address. The macro kept the low 30 bits, 0x00010000, and shifted them left by two. The first word became 0x00040000. The high byte was encoded separately and stayed 0x02.

So the GPU went looking for commands at 0x2_0004_0000, which is 0x30000 or 196,608 bytes past the real pushbuffer. Nothing is mapped there. The front end's read faulted in the GPU's own memory management unit, and the driver logged Xid 31. The fix is one shift: pass the address shifted right by two bits.

Chapter 5 of 18

Xid codes are the debugger

A number that names the unit that refused

With no driver library to explain a failure, the GPU's own error reports are the debugger. NVIDIA calls them Xid messages. The kernel driver writes each one to the kernel log as a line that starts with NVRM: Xid, then the device's PCI address, then the code. Read them with dmesg or journalctl -k and search for that prefix. A memory fault's line also carries the unit that faulted, the address and the kind of access, which is often enough to tell which address was wrong.

Three codes kept coming up. Xid 32, which NVIDIA's catalog calls an invalid or corrupted push buffer stream, comes from the unit that fetches commands. Leave out SET_OBJECT and the copy engine's methods arrive on a subchannel with nothing bound to it. Skip a store fence and the write index is published before the entry is really in memory, so the front end reads garbage, some of the time. Xid 31 is a GPU memory page fault: a unit used an address the GPU's page tables cannot translate. Xid 13, a Graphics Engine Exception, is a program on the compute cores doing something illegal, typically touching memory outside its bounds.

The catalog's immediate action for all three is to restart the application, and the Kubernetes device plugin's health check skips them and leaves the GPU marked healthy. For a hand-built path that reading is right. Xid 32 sends you back to the command stream and its ordering. Xid 31 sends you to address encoding and mappings.

Chapter 6 of 18

It works. Now measure it

Two thirds of CUDA

With the address shifted the copy works. Data arrives, the semaphore fires and every byte checks out. The benchmark is built so that a silent failure cannot hide. It fills a buffer on the GPU with a known pattern, copies it to the host, verifies it, and scrambles the host buffer before the next round, so a copy that did nothing leaves visible garbage. Each run repeats copies until about 60 GiB has moved, and only the copies are timed.

A 256 MiB copy on the hand-built path sustains 38 GB/s. CUDA on the same machine runs at about 55. In time, 268,435,456 bytes take 7.06 ms at 38 GB/s and 4.91 ms at 54.7. Every obvious suspect is cleared. It is the same copy engine, the same PCIe link and the same pinned buffer. The 12 extra bytes of command cannot cost a third of the bandwidth, because commands are read once, before the engine starts moving data.

One detail does not fit a slow path. The best single iterations match CUDA exactly. Timing every iteration separately shows the latencies sitting on a few discrete steps instead of spreading out. A path that is sometimes at full speed has nothing wrong with its commands. Something outside the copy is switching between states.

Chapter 7 of 18

The clock nobody checked

345 MHz, waiting to be told

The measurement that settled it looked at the GPU and left the copy alone. Sampling the clocks during each benchmark showed the compute cores' clock, the SM clock, at 345 MHz for the whole hand-built run. That is its idle floor. During the CUDA run it sat at 1755 MHz, about five times higher. The copy engine's rate followed that clock, and at the idle floor it could not fill a Gen5 link. A workload that only copies did not raise the clock by itself on this machine.

The cause had been in the capture of CUDA's startup all along. Of the 361 resource manager ioctls CUDA made at setup in that capture, 192 were control calls, spread over 68 different commands, and among them there is one named NV2080_CTRL_CMD_PERF_BOOST, command 0x2080200a, sent to the subdevice object. NVIDIA's header describes it as a request to raise the GPU's performance state by one level or to the highest, with a duration in seconds. CUDA asked for the highest state with no expiry. The header's value for that is a duration of 0xffffffff, which holds until the boost is cleared.

Nothing in the copy path asks for the boost and no API reference mentions it. The kernel module passes the request to the firmware on the GPU, which owns power states and clocks. The header warns that other limits can still hold the state down, so the result has to be read back. Reading it needs none of this tooling: nvidia-smi --query-gpu=clocks.sm prints the SM clock, and the DCGM exporter publishes it by default as DCGM_FI_DEV_SM_CLOCK_HERTZ.

Chapter 8 of 18

Measure again

One call later, the gap is gone

With that one call added to setup, the hand-built copy at 256 MiB goes from about 38 GB/s to 54.8, against 54.7 for CUDA in the same run. The longer benchmark takes the median of three runs for each size and gives the table in the first beat below: 55.1 against 52.9 at 256 MiB, 53.9 against 53.5 at 64 MiB and 55.5 against 55.4 at 1 GiB. From 64 MiB up the two paths sit on one plateau, within the spread between runs. That plateau is about 87 percent of the link's 63 GB/s.

Small copies are slower per byte on both paths. At 4 MiB the hand-built path manages 31.3 GB/s, which is 134 microseconds for 4,194,304 bytes. About 15 of those microseconds are fixed: the flush, the semaphore write becoming visible and the CPU's polling loop noticing it. Fifteen in 134 is 11 percent. The same 15 microseconds are about 1 percent of a 64 MiB copy, which takes 1,245. The fixed cost does not explain the whole gap at 4 MiB, and CUDA falls short there too, at 35.7.

This matters for KV cache, which a model server moves in blocks of a few MiB. Take a 9,400-token prefix at about 260 KB a token, 2.44 GB. Moved as 583 separate 4 MiB copies at 134 microseconds each it takes 78 ms. Moved as one stream at 55 GB/s it takes 44 ms. A benchmark made of tiny chunks measures the fixed cost and says little about the link.

Chapter 9 of 18

The flaky one

Wrong data, sometimes, with no error

The next problem, after the clock, was harder because it only happened sometimes. The test copies 128 MiB from host to GPU and back and compares. With the same commands and the same launch words, 25 to 34 percent of runs failed. Some timed out waiting for the completion semaphore. Others finished and returned wrong data: an unexpected word, or the scramble pattern untouched. No Xid was logged. A path that fails up to one run in three with no error report looks exactly like flaky hardware.

The answer came from comparing CUDA's startup with the library's, system call by system call. Early in every CUDA process there is an mmap that reserves about 4 GiB of address space at 0x200000000 with no access rights. Mappings are then placed inside it at fixed addresses, the first at 0x200600000. CUDA creates the GPU-side mapping of each buffer at the same number, so the CPU's pointer and the GPU's pointer are equal. The library had been giving the CPU and the GPU different addresses for one buffer.

Copying that layout removed the failures: 1,000 runs out of 1,000 passed. It also put the pushbuffer below 2 to the power 40, the most a ring entry's 40 address bits can reach. An early version let the kernel place the pushbuffer at addresses like 0x76baa0e2c000, which needs an extra control entry, SET_PB_SEGMENT_EXTENDED_BASE, ahead of every submission. One limit of the finding should be stated. The layout is a fix that works, and the root cause was never isolated. Separate CPU and GPU addresses are valid elsewhere in NVIDIA's stack.

Chapter 10 of 18

Try it on your own machine

Four labs that need no patched driver, and one rule for the rest

Four of the measurements in this lesson can be repeated on any Linux machine with an NVIDIA GPU and its normal driver, with no patched module and no hand-built commands. They need a small CUDA program that allocates a pinned host buffer and a GPU buffer and calls cudaMemcpy a dozen times in a loop at a large size such as 256 MiB. The series' author did his tracing on rented H100 PCIe machines. Three of the four labs below use no offsets or class numbers specific to Hopper, so they run unchanged on other NVIDIA generations. The second uses Hopper's doorbell offset and class, and on another generation those numbers change. They read only what the kernel and the driver already publish.

The first lab counts the control plane. Run the program under strace -f -e trace=ioctl,mmap,openat -o trace.txt. strace sees every system call at the kernel boundary, so it also catches the calls libcuda makes with raw syscall instructions, the ones an LD_PRELOAD hook in front of glibc never sees. Expect a burst at start-up: openat on /dev/nvidiactl, /dev/nvidia0 and /dev/nvidia-uvm, then hundreds of ioctl calls and a run of mmap calls. In the series' traces on an H100, setup made 361 resource manager ioctls and 87 UVM ioctls. Then expect silence. During the twelve copies those traces showed zero ioctls of either kind, because a copy is only stores into memory the process mapped during setup. The kernel never hears about it. Add -tt to strace and every line carries a timestamp, so the copy loop shows up as a gap with nothing in it.

The second lab finds the doorbell. While the program sleeps between copies, read /proc/<pid>/maps and look for lines whose path is /dev/nvidia0, /dev/nvidiactl or /dev/nvidia-uvm. Each line is one mapping: start and end address, permissions, offset, device, inode and path. On an H100 the doorbell lives in a 64 KiB USERMODE aperture, so look for a /dev/nvidia0 line whose end minus start is 0x10000, 65,536 bytes. The doorbell is the 4-byte word at offset 0x90 inside it. Other generations use other classes for that aperture, so treat the size as the place to start looking.

The third lab is the one that found the missing third. In a second terminal run nvidia-smi --query-gpu=clocks.sm --format=csv -lms 100, which prints the SM clock every 100 ms, and start the copy benchmark. On the series' H100 PCIe an idle GPU read 345 MHz, and once CUDA had finished its setup the reading rose to 1755 MHz and stayed there through the copies. A workload that runs at the idle floor has its first suspect named before anything else is examined. The fourth lab reads the errors. After any failed run, sudo dmesg | grep -i xid, or journalctl -k | grep -i xid where the kernel log goes to the journal, lists every Xid the driver logged, with the GPU's PCI address and the code. A clean run adds no lines. NVIDIA's catalog gives each code an action key, such as RESTART_APP or RESET_GPU, that says what recovery it needs.

The deeper experiments belong on a machine nobody else needs. Parts 4 to 6 of the series load a patched nvidia.ko and an extra module that redirects the doorbell page and arms a CPU debug register, and bring-up triggers Xid faults on purpose. A mistake in a kernel module runs in the kernel, and it can leave the GPU wedged, refusing new work until the GPU is reset. nvidia-smi -r resets a GPU, but it needs root and refuses while any application holds the device, a monitoring agent or another nvidia-smi included. When it cannot run, the remedy is a reboot. On gpu-node-1 of the lesson's cluster a reboot stops every Pod on all four GPUs, and the qwen3 replica there, qwen3-6f7d9c8b4-x7k2p, comes back only after its three minutes of loading. So the rule in the owner's lab kit is plain: use a disposable rented H100. The author rented his from OVH and Lambda. Never use a shared machine or one that serves production traffic. Two traps come with the rented box. An x86 machine has only four debug registers, and Xorg or a running ollama can hold them, which gives an empty trace with no error, so stop both first. And the code for Parts 4 to 6 is specific to Hopper: class numbers, offsets and the QMD layout all change on another generation.

Chapter 11 of 18

Round robin trusts the spec sheet

The same wrong assumption, on every request

Back at the pool. Inside the GPU the wrong assumption was same hardware, same work, same speed. Round robin makes that assumption on every request. Requests are not equal. Two POSTs of about 1 KB each look the same on the wire. One asks for a two-line answer capped at 256 tokens. The other asks for a five-page plan of up to 8,192 tokens, 32 times the decode work. In one lab measurement on slow hardware the first held a worker for 0.8 s and the second for about 25 s. Dealt out in turn, short requests queue behind long ones. A 128K-token summary and a two-word greeting are also both one request.

Servers are not equal either, even when the hardware is. One may be decoding long answers for a dozen users while its neighbour does short prefills. One may be running hot and lowering its clocks. One may already hold the prefix this request starts with. From outside they look identical: same model, same Pod spec, same passing probe.

Least connections is a little better. It counts requests in flight and prefers the server with the fewest. It still counts requests instead of work. A connection streaming a 4,000-token answer and a connection waiting for a 10-token reply both count as one. The illustrative pool in this chapter shows the result. gpu-2 has five requests running and three waiting and needs 9 s to clear them, and the next request in turn is sent to it anyway.

Chapter 12 of 18

Three million tokens, counted as connections

What NVIDIA's Dynamo pitch puts in numbers

An F5 Tech Summit deck on the endpoint picker opens its section on NVIDIA Dynamo, NVIDIA's open framework for serving one model across many GPUs, with three lines it puts in Dynamo's mouth. The first calls recomputing the same 30,000-token prompt on eight different GPUs, at Blackwell prices, a donation. The second says that prefill is compute-bound and decode is memory-bound, and that running both on one pool is like hiring a sprinter to also do the accounting. The third says that your load balancer routes by least connections, your GPUs hold three million tokens of cache state, and the wrong one of those two is making the placement decision. Each line names something a balancer cannot see, and each can be put into numbers for the lesson's model.

Start with the prompt. Every token of a prompt leaves keys and values in every layer, and that KV cache is what a later request with the same start can reuse. Qwen3-32B has 64 layers and 8 key-value heads of 128 numbers each, and vLLM keeps them at 2 bytes each for this build unless it is told to store the cache in FP8. That is 2 × 64 × 8 × 128 × 2 = 262,144 bytes, 256 KiB, per token. A 30,000-token prompt leaves 7.86 GB. Building it costs roughly two operations per weight per token: 2 × 32.8 billion × 30,000 is about 1.97 × 10^15 operations before attention is counted. At the H100 SXM's FP8 rate without sparsity, 1,979 teraFLOPS, that is about one second of a whole GPU. Sent to eight GPUs that do not hold it, the prompt is built eight times: 15.7 × 10^15 operations and 62.9 GB of cache, seven eighths of it a copy of something that already existed.

Now the fleet. Three million tokens at 256 KiB each is 786 GB of cache. vLLM takes 90 percent of an 80 GB H100 by default, 72 GB. After 34.3 GB of FP8 weights and some working memory, about 35 GB is left for cache, room for roughly 133,000 tokens. Three million tokens is the cache of about 23 such GPUs. Least connections sees none of it. Its whole view of the pool is a few small integers, such as the 1, 8 and 2 of the chapter before, and the 786 GB that decides whether a prompt costs a second of GPU or nearly nothing is not among them.

The sprinter line is about the shape of the work. In prefill all 30,000 tokens go through each layer together, so each weight read from memory is used 30,000 times. Two operations per token over 1 byte per FP8 weight is 60,000 operations per byte read. In decode each running sequence adds one token per step, and every step reads all 34.3 GB of weights again. With one sequence that is 2 operations per byte. The H100 SXM does about 1,979 × 10^12 operations a second against 3.35 × 10^12 bytes a second of memory, about 590 operations per byte. Prefill is far above that line and waits on arithmetic. Decode is far below it and waits on memory. Reading 34.3 GB at 3.35 TB/s takes at least 10.2 ms, so one GPU runs at most about 98 decode steps a second, however small the batch. Put both phases on one GPU and the long prefill takes compute that decoding users are waiting on for their next token. Dynamo's answer is to split them: prefill workers build the cache, decode workers stream the tokens, and the cache moves between them. F5's picker lists dynamo as one of its engines, next to vllm and sglang, and reads Dynamo's KV events over NATS.

Chapter 13 of 18

Read the register

What the endpoint picker measures instead

The F5 endpoint picker is built on the lesson of the clock: read the register and do not trust the spec sheet. The data plane holds each request and asks the picker over ext_proc, a gRPC call to port 9002, before it chooses a Pod. The picker reads each worker's own metrics endpoint about every 50 ms. The three series it requires from vLLM are vllm:num_requests_running, vllm:num_requests_waiting and vllm:kv_cache_usage_perc. A dashboard that polls every 15 to 20 seconds is too slow for this job, because a queue forms and drains inside one polling gap.

Load is counted in tokens. The picker runs the prompt through its own tokenizer, so a 20,000-token prompt weighs what it costs and a 100-token lookup weighs little. Capacity is measured too. The picker tracks how many tokens a second each worker is really producing and turns the work outstanding into seconds to drain. In the illustrative pool, gpu-2 has 5,400 tokens outstanding and is producing 600 a second, so it drains in 9 s. gpu-1 has 300 outstanding at 1,000 a second and drains in 0.3 s.

A worker that is slow for any reason, an idle clock, heat or a batch of long answers, shows up in that number without a diagnosis. A worker whose KV cache is nearly full is skipped before cache affinity is considered at all. A cache hit is valued by the measured cost of fetching it from where it sits. Weights someone tuned by hand once are their own kind of spec sheet. They are right for the traffic and hardware of the day they were set.

Chapter 14 of 18

A headline with no baseline

Reading a vendor's validation slide

Vendors publish results, and a lesson about measuring has to cover how to read them. F5's deck on BNK with NVIDIA has a slide headed Validated performance with NVIDIA AI infrastructure. It gives three numbers from joint validation, for DPU-based deployments: 47 percent more efficient throughput, 60 percent lower time to first token and about 40 percent lower cost per token, all without adding more GPUs. DPU-based means that BNK's data plane, TMM, runs on an NVIDIA BlueField-3 DPU in the GPU server instead of on the host's CPUs, so traffic is routed and inspected with no hop through the host. The slide's footnote says the results were observed in joint validation with NVIDIA AI infrastructure and that actual performance varies by workload, model and deployment configuration.

That footnote is honest, and it is also a list of what is missing. The slide names no model, no prompt or answer lengths, no concurrency, no GPU type or count, and no baseline. A 47 percent increase is 47 percent over something. Round robin through a software balancer on the host, another balancer on the same DPU, or the same setup with the endpoint picker switched off would each give a different figure. The slide does not define efficient throughput either. It may mean requests served within a latency target, which some papers call goodput, or it may mean tokens a second. Under load those two can move far apart.

Put illustrative numbers under each claim to see what it would mean for the lesson's pool. If the three workers together produced 3,000 tokens a second, 47 percent more is 4,410. If the time to first token was 500 ms, 60 percent less is 200 ms. Time to first token is the wait in the queue plus the prefill, and routing changes both. A request sent to a short queue waits less, and one sent to the worker that holds its prefix skips most of its prefill. That is how a picker can cut it without new GPUs. If a million tokens cost $1.00 of GPU time, about 40 percent less is about $0.60.

Then check that the numbers agree with each other. On the same GPUs, the GPU cost of a token falls as throughput rises: 1 / 1.47 = 0.68, which is 32 percent lower. The slide says about 40. The other eight points must come from something it does not show, such as host CPU freed when the data plane moves to the DPU, a different baseline for the cost figure, or a different run. That is no proof of an error. It is the question to ask before the number is quoted: measured on which workload, against which baseline, over how many runs, and how far apart were they. A claim that cannot answer is a reason to measure your own pool with your own prompts, the way the rest of this lesson measures.

Chapter 15 of 18

A gateway race, as charted

Two charts, and what Little's law reads off them

A second deck, on F5's AI security platform, compares F5 AI Gateway, which it calls f5-aigw, with three other AI gateways: agentgateway, Bifrost and LiteLLM. An AI gateway sits between applications and model servers or hosted model APIs. It holds keys, applies policy, counts tokens and forwards each request. The first chart measures peak sustained throughput at 1,024 concurrent workers and the CPU each gateway used: f5-aigw 51,441 requests a second at 59 percent CPU, agentgateway 34,938 at 59 percent, Bifrost 7,234 at 82 percent and LiteLLM 644 at 96 percent. Its headline is 1.5 times the work of the nearest competitor on the same CPU budget. 51,441 / 34,938 = 1.47, so 1.5 is a fair rounding. The same deck claims 5 times less added latency than the nearest competitor, and prints no figures for that claim.

1,024 concurrent workers describes the load generator. In the usual meaning, which the slide does not spell out, each worker sends a request, waits for the answer and sends the next, so 1,024 requests are always in flight. Little's law ties the numbers together: requests in flight equal throughput times the time each request spends in the system. So every bar is also a latency. 1,024 / 51,441 is 19.9 ms per request through f5-aigw, 29.3 ms through agentgateway, 141.6 ms through Bifrost and 1.59 s through LiteLLM. Dividing throughput by CPU gives work per unit of CPU: 872 requests a second per percent of CPU for f5-aigw, 592 for agentgateway, 88 for Bifrost and 6.7 for LiteLLM. The slide does not say whether its percentages are of one pod's 2 vCPU or of both pods together, so these ratios compare the gateways with each other and say nothing absolute.

The second chart streams answers and compares each gateway with no gateway at all, the client talking straight to the upstream: 1,002 requests a second. f5-aigw reached 1,011, which the slide calls 100.9 percent, agentgateway 975 (97.3 percent), Bifrost 638 (63.7 percent) and LiteLLM 32 (3.2 percent). At the same 1,024 workers Little's law puts a streamed request at 1.022 s with no gateway, so this test is dominated by the upstream's stream and each gateway's cost is the difference. agentgateway adds about 28 ms, Bifrost about 0.58 s and LiteLLM about 31 s.

The slide's title says f5-aigw is the only gateway that runs faster than no gateway. Read that with care. A proxy adds work to every request, so it can beat a direct path only by changing how the upstream is reached, for example by reusing connections that the direct client opens fresh. The slide says nothing of the kind. 1,011 against 1,002 is 9 requests a second, 0.9 percent, about 9 ms on a 1.02 s request. Each bar is one number, with no spread and no count of runs. Network benchmarks commonly move by a percent or more between runs of the same setup, so the reading the data supports is that f5-aigw kept pace with the direct path. Next to 63.7 and 3.2 percent that is a strong result. The word faster is the part the data cannot carry.

Chapter 16 of 18

How the race was run

The small type under the chart

Under both charts the slide prints its method in small type, and the method changes how far the numbers reach. The vendor ran the test on its own development cluster on 29 and 30 October 2026. Each product got the same resources: 2 pods, 2 vCPU and 5 GiB of memory, one pod per node, with pinned cores. f5-aigw ran on the weaker Kubernetes QoS class and every competitor on the stronger one, each tuned per its own performance guide. LiteLLM ran at about half its recommended CPU, and the slide says to treat its result as a floor. Nothing gives the number of runs or the spread between them, the upstream that answered, the request and answer sizes, or which gateway features were switched on.

Kubernetes gives every Pod one of three QoS classes, worked out from its containers' requests and limits. A Pod is Guaranteed when every container has CPU and memory requests and limits above zero, with each limit equal to its request. It is Burstable when it misses that and at least one container has a request or a limit. It is BestEffort when none has either. The class decides who is evicted first when a node runs short: BestEffort, then Burstable, then Guaranteed. With the kubelet's static CPU manager policy it also decides pinning. Only containers in Guaranteed Pods with whole-number CPU requests get CPUs of their own, and every other container runs on the shared pool. The slide does not name the classes. With a weaker and a stronger one named, the likely reading is Burstable for f5-aigw and Guaranteed for the others.

That reading pulls against pinned cores. If the pinning came from the static CPU manager, a Burstable f5-aigw could not have had cores of its own, and sharing cores can only slow it, which makes its result conservative. If the pinning was done another way, the slide does not say how. Either way the gap in the setup leans against the vendor's own product, the right direction for a vendor's test. LiteLLM is the other case. A process given half the CPU it was sized for saturates, and once it saturates every extra worker only waits longer. 96 percent CPU at 644 requests a second is the picture of a saturated process, so its bar shows LiteLLM starved, which is why the slide itself calls it a floor.

This gives a short list to run against any benchmark, the ones in this lesson included. Who ran it, and on whose hardware. How many runs, and how far apart they were. Whether every contender had the same resources, the same QoS class, the same tuning effort and the same features on. What the load generator did: a fixed number of workers in a loop, or a fixed rate of arrivals. What sat upstream, because a mock that answers at once measures the gateway alone and a real model server measures mostly the model. And what the baseline was. The copy benchmark earlier in this lesson passes most of that list: one machine, the same buffer for both paths, a median of three runs and the code published. The gateway slide passes part of it, and says so in its own footnote.

Chapter 17 of 18

A lab DPU is a tunnel

Why simulated hardware gives no hardware results

The DPU figures three chapters back came from BlueField-3 cards. Most labs have none, so lab builds simulate the DPU. In the owner's labs, a proof of concept on F5's UDF lab platform and a KV-cache lab, a DPU is a gretap tunnel and Linux bridges. gretap is a Linux interface type that carries whole Ethernet frames inside GRE over IPv4. ip link add dpu0 type gretap local 192.0.2.10 remote 192.0.2.20 creates one end, and bridges join the tunnel to the interfaces that stand for the DPU's host side and network side. The layout matches a DPU's: a host side, a network side and a path between them. That is enough to exercise the configuration, the routes and the order in which things happen.

The real path is different hardware. A BlueField-3 is a PCIe card in the GPU server with its own Arm cores and network ports, one per chassis in BNK's DPU mode. BNK runs TMM on those Arm cores, and the host reaches the card over PCIe, with a management link over rshim and tmfifo. In the lab, every frame that would have crossed to the card is wrapped in 38 more bytes of headers, 14 of inner Ethernet, 4 of GRE and 20 of outer IPv4, and handled by the host's own kernel on the host's own CPUs. The work a DPU takes off the host is exactly the work the simulation puts back on it. On a 1,500-byte inner packet the wrapping alone is 2.5 percent more bytes on the wire, before any CPU time is counted.

So the rule in the owner's lab notes is short: never present numbers from a simulated DPU as DPU results. Throughput, latency and CPU use measured there describe a Linux tunnel on a host CPU. What a simulated DPU can show is whether things are correct: the configuration applies, routes are learned, requests reach the right Pod and a policy blocks what it should. Take the 47 percent from the validation slide. A lab that measured 47 percent through gretap tunnels would be measuring something else, and quoting it beside the slide would put two unrelated numbers side by side under one name.

Chapter 18 of 18

Shape the simulator like the card

Testing a picker for hardware you have not rented yet

The same care applies when the target is a different accelerator. The owner's lab plans to route to Qualcomm Cloud AI 100 cards running vllm-qaic, a hardware plugin under which vLLM's own scheduler, KV-cache manager and metrics run unchanged. The three gauges the picker needs are all there, and one of them behaves differently. In vllm-qaic's production mode the plugin compiles one KV block per sequence, the size of the whole context, and sizes the cache at max_num_seqs + 1 blocks. With --max-num-seqs 8 there are 9 blocks, so vllm:kv_cache_usage_perc moves in ninths and tops out at 8 / 9 = 0.889 when every slot is busy. F5's generated saturation threshold is 0.99, which that gauge never reaches. The plugin also switches prefix caching off, so it publishes no KV events and prefix affinity has nothing to work with.

Before renting a card, the plan is to make the llm-d inference simulator behave like one. llm-d-inference-sim answers OpenAI-style requests with no model behind them, with the latencies it is told to use, and publishes the same vllm: metric names the picker reads. The plan's flags were --max-model-len 2048 --max-num-seqs 8 --block-size 2048 --kv-cache-size 9 --enable-kvcache, with no KV events and --prefill-time-per-token tuned so prefill looks like the card's static 128-token chunks. One flag fails. Version 0.8.0 accepts only 8, 16, 32, 64 or 128 for --block-size, and its configuration check stops with token block size should be one of the following: 8, 16, 32, 64, 128 for anything else. The plan had listed that as a thing to verify, and reading the check in the source settles it.

The shape can still be had with arithmetic. In the simulator the gauge is blocks in use divided by --kv-cache-size, and a request holds the blocks of its prompt while it runs. With --block-size 128, a 1,920-token prompt is exactly 15 blocks and leaves 128 tokens of answer inside the 2,048 limit. Set --kv-cache-size 135, which is 9 × 15. Each running request then holds 15 / 135, one ninth of the cache, and eight running requests read 120 / 135 = 0.889, the card's steps. Three details keep it honest. The simulator shares blocks between prompts that start the same way, as a prefix cache does, so every prompt must differ, and genai-perf reuses a fixed set of synthetic prompts unless --num-dataset-entries is at least the number of requests. A chat template adds tokens to every prompt, so use the completions endpoint and confirm that one request alone reads 0.111. And --enable-kvcache publishes block events over ZMQ to tcp://127.0.0.1:5557 by default. The simulator creates that publisher only when --zmq-endpoint is set, so pass it empty to match a card that publishes none.

Then drive it and check three things. genai-perf profile with --endpoint-type completions, --synthetic-input-tokens-mean 1920, --synthetic-input-tokens-stddev 0, --output-tokens-mean 128 and --concurrency 32 puts more requests in flight than three simulated workers of 8 slots can run, so queues form. First, the picker's counter f5_epp_prefix_index_lookups_total with result no_query should stay at zero, as the plan expects for a pool with no prefix data. Second, the picker should spread requests by queue depth, the strong signal on this hardware, because vllm:num_requests_waiting is exact. Third, the saturation detector should trip at the slot threshold. With kvCacheUtilThreshold at 0.85, seven running requests read 7 / 9 = 0.778 and pass, and eight read 0.889 and trip it. Each check measures the configuration. The card's own speed is left for the card.

What to keep

The signal nobody was looking at

A copy built by hand ran a third slower than CUDA's on the same GPU, and every usual check said it should be fine. The cause was a clock left at its idle rate of 345 MHz, raised to 1755 MHz by a control call CUDA makes during setup and never mentions. Another bug failed a quarter to a third of round trips, by timing out or by returning wrong data, with no Xid logged, until both processors used one address for each buffer. Neither fix is in an API reference. Both were found by measuring what was really happening: timing every iteration, sampling the clock, comparing system calls. Routing has the same shape. Things that should behave the same don't, the reason isn't in the configuration, and the only reliable answer is to measure the thing that decides the outcome. The same rule holds for numbers other people publish. A slide with no baseline, a benchmark from one run, a tunnel standing in for a DPU and a simulator with the wrong block size each look like a measurement. Read the method, do the arithmetic, and measure your own pool before you trust any of them.
