Inference

From one request at a time to a batching vLLM server

A lab on one H100: the same model served to one user at a time, then to many in every pass

This lesson is a lab. It starts where most people start: a few lines of Python that load a model with Hugging Face transformers and call generate() on a prompt. Wrap that in a small web server and it answers questions. It also answers them one at a time. The course this track draws on ends with exactly this exercise: you are handed a model server that answers one request at a time while users wait, and you turn it into a vLLM server that serves many users at once.

The lab runs on cluster northlight-eu, on one H100 with 80 GB of memory in gpu-node-1. The model is Qwen3-32B in its official FP8 build, Qwen3-32B-FP8, whose files take 34.3 GB. First the starter server gets eight users at once and you measure what they see. Then the lesson looks at what the GPU was doing while they waited, tries the obvious fix of grouping requests into fixed batches, and shows why the batch has to be rebuilt before every pass instead. Then you swap the starter for vLLM with one change to the Deployment, read what vLLM builds before its first request, run the same benchmark against it, turn the number of users up until memory runs out, and read the server's own counters. The lesson Prefill and decode explains what one pass costs. This one is about how many users share it.

Chapter 1 of 14

The starter server: one queue and one loop

A web server in front, a single model loop behind it, and the GPU used by one request at a time

The lab hands you a server built the way the Hugging Face documentation shows for serving a model from a web server. A Starlette app, run by uvicorn, receives each POST. It does not touch the model. It puts the prompt and a reply channel on an asyncio queue and waits. One background task, the model loop, takes the next item off the queue, runs the model on it, and puts the answer on the reply channel. Then it takes the next item. The documentation explains why it is built like this. A web server is made to handle many requests at once, and the model is not, because it takes a lot of memory. So the model is loaded once and only one loop ever uses it.

Inside the loop is the code from the course: load Qwen/Qwen3-32B-FP8 with AutoModelForCausalLM, apply the chat template, call model.generate() with max_new_tokens set to 300. The starter streams each token as a server-sent event through a TextIteratorStreamer, and it answers on the path /v1/completions with just enough of the OpenAI format for a benchmark client to talk to it. That keeps the comparison fair later, because the same client and the same command can test both servers.

The loop is the part to look at. While it runs generate() for one prompt, nothing else in the process can use the GPU. A second request is accepted by the web server and sits in the queue. Python's own socketserver documentation describes its basic servers in the same terms: each request is handled synchronously and must finish before the next one starts. Here the web side is concurrent and the GPU side is strictly one at a time.

Chapter 2 of 14

Eight users in a line

Each answer takes 3.8 seconds, so the eighth user waits for seven of them

Measure one request on its own first. The prompt has 1,000 tokens and the answer 300. Prefill reads the prompt in one pass at about 0.21 ms a token, so the first token comes after about 0.21 seconds. Then 299 decode passes follow at 12 ms each, 3.59 seconds in all. The whole request takes about 3.8 seconds. That is the same speed the lesson Prefill and decode measured for one request, and to keep the comparison clean this lab gives the starter the same per-token speed vLLM gets for a single request. A plain generate() loop is usually slower per token as well, so the real gap is larger than what follows.

Now eight users send a request at the same moment. The loop takes the first and the others queue. User 1 sees a first token at 0.21 s and is done at 3.8 s. User 2's request only starts when user 1's ends, so user 2 waits 3.8 s plus 0.21 s for a first token. User 8 waits for seven full answers: 7 × 3.8 = 26.6 s, and sees a first token at about 26.8 s. The average wait for a first token is 13.5 s. Nothing is wrong in any log. Every request succeeds, the Pod is healthy, and the GPU is busy the whole time.

The server as a whole makes 300 tokens every 3.8 seconds, about 79 tokens a second, however many users there are. Add users and the line gets longer, and the throughput stays at 79. The Hugging Face page itself suggests the defence: watch the queue length and return 503 or 504 when the server is overloaded, instead of making people wait without limit.

Chapter 3 of 14

What the GPU does while they wait

Each pass reads 34.3 GB to make one token and leaves the cores almost idle

The GPU is busy the whole time, so the line looks like a capacity problem. Look inside one decode pass. To make one token, the model has to run every weight once, and every weight has to come out of the GPU's memory to the cores. With Qwen3-32B-FP8 that is 34.3 GB for every token. The H100 reads its memory at about 3,350 GB a second, so the most passes it can make is 3,350 ÷ 34.3, about 98 a second, or about 10.2 ms a pass. The 12 ms measured here sits just above that floor. The memory is close to flat out.

The arithmetic is the opposite. A common rule of thumb puts one token at about two operations per weight, a multiply and an add. Qwen3-32B has 32.8 billion weights, so one token is about 66 billion operations. Done in 12 ms, that is about 5.5 trillion a second. The lesson Prefill and decode quotes the H100 at roughly 990 trillion a second. One user's decode uses about half of one percent of the cores.

The memory is just as idle. The weights take 34.3 GB. One request's KV cache, the keys and values the model keeps for every token it has read, costs 262,144 bytes a token for this model: 64 layers × 2 × 8 heads × 128 numbers × 2 bytes. A request that ends at 1,300 tokens holds 1,300 × 262,144 bytes, about 341 MB. So the starter uses about 35 GB, and nvidia-smi shows it. The card is sold as 80 GB, which is close to 80 GiB. The driver reports about 79.2 GiB, which is about 85 GB in decimal units, so the starter leaves more than half the card empty. The read of 34.3 GB is the expensive part of every pass, and it would cost the same if it made a token for several users. That is the whole case for batching.

Chapter 4 of 14

First fix: collect a batch and run it together

Wait a moment, pad the prompts to one length, and call generate() once for all of them

The first fix most people try is in the same Hugging Face page. The loop takes one item, then keeps taking items until a short timer runs out, and passes the whole list to the model at once. This is called static batching, and the page calls its version dynamic batching. generate() then works on a batch of eight rows. Each pass reads the weights once and makes one token for each of the eight. The idea is right. The details cost a lot.

The rows of a batch must all be the same length. Prompts of 300 to 1,000 tokens are padded with filler tokens to the longest. The transformers documentation says to pad on the left for generation, because the model was never trained to continue after padding. With eight prompts of 300, 400 and so on up to 1,000 tokens, 5,200 real tokens become 8,000, and 35% of the prefill is spent on padding.

The batch also ends together. generate() keeps going until every row has stopped. Say the eight answers need 50, 80, 120, 150, 200, 240, 280 and 300 tokens. The batch takes 300 passes. The user who needed 50 tokens has their answer after 50 passes, and their row then rides along for 250 more passes filled with padding. Of 8 × 300 = 2,400 row-passes, 1,420 make a real token, 59%. And a ninth user who arrives one second in cannot join. The Orca paper, which named this problem in 2022, put it in two halves: requests that finish early cannot return, and new requests have to wait until the whole batch is done. Put times on it with this lab's speeds. The first pass reads all 8,000 padded prompt tokens, 8,000 × 0.21 ms = 1.68 s. Then 299 decode passes of eight rows follow at about 14 ms each, 4.19 s. The batch ends about 5.87 s after it starts, so the ninth user, who arrived at 1 s, waits about 4.9 s before their prompt is even read.

Chapter 5 of 14

Better fix: rebuild the batch before every pass

Continuous batching lets a request leave the moment it ends and another join the next pass

The Orca paper proposed scheduling at the level of one iteration, one pass of the model, instead of one request. Before each pass the scheduler decides which requests are in it. A request that has finished leaves at once and returns its answer. A request that arrived since the last pass joins the next one. On a GPT-3 175B model Orca reported 36.9 times the throughput of NVIDIA FasterTransformer at the same latency. The idea is now called continuous batching, and every serious model server does it. Hugging Face transformers itself now ships it, through generate_batch() and the transformers serve command.

vLLM's scheduler is written so that this is the only case. A comment at the top of its scheduling function says there is no decoding phase and no prefill phase. Each request has a count of tokens already computed and a count of tokens it should have, its prompt plus everything generated so far. Each pass, the scheduler gives tokens to requests so their computed count can catch up. A new request is behind by its whole prompt. A request in the middle of its answer is behind by one token. Both fit in the same pass, which is why prefill and decode can share one.

Replay the eight requests from the last chapter. The first pass reads all eight prompts, 5,200 real tokens with no padding, in about 5,200 × 0.21 ms = 1.09 s. User 9 arrives at 1 s, while that pass runs, and joins the very next one: pass 2 reads its 1,000-token prompt and gives each of the other eight its next token. No row carries padding, because there are no rows: vLLM lays the tokens of all requests end to end and keeps track of which belongs to whom. After pass 50 the 50-token answer is done. It returns at once, and its blocks go back to the free pool for whoever comes next. The lesson Prefill and decode shows what that mixing costs the others when a newcomer's prompt is long, and how chunked prefill limits the damage.

Chapter 6 of 14

Memory decides how many fit

Reserve for the longest possible answer and three requests fit. Hand out blocks as tokens arrive and more than a hundred do

A batch can only hold requests whose KV cache fits in the GPU. How that memory is handed out decides the batch size. A simple server reserves one stretch of memory per request, big enough for the longest request the model allows, because it cannot know in advance how long the answer will be. The vLLM authors measured earlier systems and found 60% to 80% of KV cache memory wasted this way, through over-reservation and through gaps between reservations.

Put numbers on it for this lab. In v0.11.0 vLLM may use 90% of the card's total memory as the driver reports it. An H100 sold as 80 GB reports about 79.2 GiB, about 85 GB, so the budget is 0.9 × 85 = about 76.5 GB. The weights take 34.3 GB and about 2 GB is working memory for passes, which leaves about 40.2 GB for the cache. The longest request Qwen3-32B-FP8 allows by default is 40,960 tokens, its max_position_embeddings. Reserving that for each request costs 40,960 × 262,144 bytes, exactly 10 GiB or about 10.7 GB. 40.2 GB ÷ 10.7 GB = 3.7, so only three such reservations fit. Each of this lab's requests uses 1,300 tokens of its reservation, and 97% of it sits empty.

vLLM's answer is PagedAttention, named after paging in operating systems. The cache is cut into blocks of 16 tokens, 4 MiB each for this model, and a request gets a new block only when its last one is full. A request's blocks need not sit next to each other, because a block table maps its positions to blocks. The only waste is the unfilled end of the last block, under 4% in the launch post's measurements. Here the 40.2 GB pool is 9,584 blocks. A request of 1,300 tokens needs 82 of them, so about 116 fit at once instead of 3. The vLLM paper reports 2 to 4 times the throughput of FasterTransformer and Orca at the same latency, and the launch post up to 24 times Hugging Face Transformers.

Chapter 7 of 14

Swap the server: one change to the Deployment

A new image and a command, a new ReplicaSet, and three minutes of loading

The lab's real work is small. The Deployment qwen3 in namespace inference ran the starter image. You change its container to the image vllm/vllm-openai and give it a command and arguments: vllm serve, the model Qwen/Qwen3-32B-FP8, the name qwen3-32b to answer to, 0.9 for --gpu-memory-utilization and 40960 for --max-model-len, on port 8000. The command is spelled out because the image's entrypoint has changed between releases: in v0.11.0 it runs python3 -m vllm.entrypoints.openai.api_server, and on the main branch it runs vllm serve. With an explicit command the arguments mean the same either way.

The flag values are written out too, because defaults move. In v0.11.0 --gpu-memory-utilization defaults to 0.9. On vLLM's main branch it is unset by default and sized from measured memory. Setting 0.9 keeps the arithmetic of this lab true on both. --max-model-len 40960 matches the model's own limit, so it changes nothing today and states the intent.

Applying the change makes a new revision. The Deployment controller creates a new ReplicaSet with a new pod-template hash, and its Pod is qwen3-6f7d9c8b4-x7k2p on gpu-node-1. It asks for one nvidia.com/gpu like the starter did. The image is pulled, the container starts, and vLLM spends about three minutes loading the weights and building its cache before it answers. The lesson A model server becomes ready covers the probes that hold traffic back until then. Once the new Pod is ready, the old starter Pod qwen3-7c9d5f6b8-h4j2w is stopped and its GPU is free again.

Chapter 8 of 14

What vLLM builds before the first request

Three log lines size the batch before a single user has arrived

Before vLLM answers anything it measures the card. It loads the weights, runs a test pass to see how much working memory a pass needs, and takes everything left under the 0.9 limit for the KV cache. It cuts that into blocks once and keeps them for the life of the process. This is why nvidia-smi shows an idle vLLM server using about 76.5 GB, where the starter used about 35. The memory is held on purpose, ready for the batch.

Three lines in the start-up log, in the wording of v0.11.0, say what it built. Available KV cache memory: 37.44 GiB. That is the 40.2 GB pool written in binary units. GPU KV cache size: 153,344 tokens. That is 9,584 blocks of 16. Maximum concurrency for 40,960 tokens per request: 3.74x. That third line reads like the three reservations of the last chapter, and it is easy to misread. It is the number of requests that could all reach the full 40,960 tokens at the same time: 153,344 ÷ 40,960 = 3.74. It describes a worst case. vLLM admits requests by their real size, and at 1,300 tokens each about 116 fit.

The settings that shape the batch are also fixed now. max_num_seqs, the most requests in one pass, defaults to 1,024 for the API server on a GPU of 70 GiB or more that is not an A100, in v0.11.0 and on main. max_num_batched_tokens, the token budget of one pass, defaults to 8,192 there. The policy is fcfs, first come first served. Prefix caching is on. On this card, memory will bind long before 1,024 requests do.

Chapter 9 of 14

The same client, no code change

vLLM speaks the OpenAI API, so the benchmark points at the same address with the same command

vLLM serves the OpenAI API: /v1/completions, /v1/chat/completions, /v1/models and others, on port 8000. Any program written for the OpenAI client works if its base_url points here, which is the point the course makes: tools built for OpenAI talk to your own server without changing a line. A first check is a single request through the gateway to api.northlight.example, asking for model qwen3-32b, the name given with --served-model-name. A request for any other model name gets HTTP 404.

The load test is vLLM's own benchmark, vllm bench serve, installed with the vllm[bench] extra. Its defaults matter. The backend is openai and the endpoint /v1/completions. --dataset-name defaults to random, which makes prompts of random tokens, 1,024 in and 128 out unless told otherwise. This lab sets --random-input-len 1000 and --random-output-len 300, and adds --ignore-eos so every answer runs to its full 300 tokens instead of stopping early. --num-prompts is 64 here. Its default is 1,000.

Two options decide the load. --request-rate defaults to inf, which means every request is released at time zero. --max-concurrency caps how many may be in flight at once, so with 8 the client behaves like eight users who each send a new question as soon as the last answer ends. One more detail trips people up: the served name qwen3-32b is not a Hugging Face model id, so the benchmark needs --tokenizer Qwen/Qwen3-32B-FP8 to count tokens. The starter server ran the same command, which is why the lab made it answer on /v1/completions.

Chapter 10 of 14

Reading the benchmark

Five times the tokens, a median first token in under a quarter of a second, and each user a little slower

Run the same command against the starter and against vLLM, and the result blocks look like this. The starter takes 243.2 s for 64 requests: 64 × 3.8 s. It makes 78.95 output tokens a second. Its mean time to first token is 25,150 ms, because in a closed loop of eight, every request after the first wave waits for seven full answers, 26.6 s. Its time per output token is a steady 12 ms, the speed of one user alone.

vLLM takes 46.96 s for the same work. Each pass carries all eight requests, and a pass of eight takes about 14 ms where a pass of one took 12. Over one request's life the GPU also reads the prompts of the seven others that join, at 0.21 s each. So a request lives about 299 × 14 ms + 8 × 0.21 s = 5.87 s, and eight finish every 5.87 s. That is 408.86 output tokens a second, 5.2 times the starter, on the same card and the same model.

The latency lines show who pays. The median first token is about 230 ms. The mean is higher, about 411 ms, because the first eight arrive together and their 8,000 prompt tokens fit in one pass of the 8,192-token budget, which takes about 1.68 s. Mean time per output token is 18.9 ms instead of 12. Most gaps between tokens are 14 ms, and the P99 is about 220 ms: about 7 of each request's 299 gaps include another user's whole prefill. Each user streams at about 53 tokens a second instead of 83, and nobody waits 26 seconds to start.

Chapter 11 of 14

Turn the dial: more users

Throughput climbs and flattens, each user slows, and past about 116 the memory runs out

Run the benchmark again with --max-concurrency 32, 64 and 96, and the pattern of every model server appears. A pass gets a little slower with each request in it, about 12 ms plus 0.25 ms per request in this lab, so 20 ms at 32 and 28 ms at 64. More requests also means more prompts to read: every one of them is 1,000 tokens of prefill, and those passes stall everyone. Output throughput goes from 409 tokens a second at 8 to about 756 at 32, about 880 at 64 and about 931 at 96. It flattens because prefill now takes most of the GPU's time. Each request brings 1,000 tokens to read for 300 to write.

Each user pays more as the batch grows. Time per output token rises from 18.9 ms at 8 to 41.8 ms at 32, 72.2 ms at 64 and 102.7 ms at 96. A user at 96 reads about 10 tokens a second. Whether that is acceptable is a business decision, and the benchmark can measure it. --goodput tpot:50 counts only the requests that met a 50 ms time per output token. In this lab that cuts off somewhere above 32 users.

Then memory. A request ends at 1,300 tokens and needs 82 blocks. 9,584 blocks hold about 116 such requests. vLLM admits a request when its prompt fits, 63 blocks for 1,000 tokens, so at 128 users it can admit more than will fit later. As the answers grow, the pool runs out. vLLM then preempts the request it admitted last: it frees its blocks, puts it back in the queue, and computes its prompt again later. vllm:num_preemptions counts each time. The fix is a limit that matches the card: --max-num-seqs 96 keeps 96 × 82 = 7,872 blocks under 9,584, with room to spare for longer requests, and lets the rest wait in vllm:num_requests_waiting.

Chapter 12 of 14

Reading the server's own numbers

The /metrics page shows the batch, the queue and the pool while the benchmark runs

The benchmark sees the server from outside. vLLM also reports from inside, on /metrics on port 8000, in the Prometheus text format. Scrape it during the run at eight users and four lines tell the story. vllm:num_requests_running, documented as the number of requests in model execution batches, reads 8. vllm:num_requests_waiting reads 0, because the client never sends more than eight. vllm:kv_cache_usage_perc, where 1 means 100 percent, reads about 0.060. Each request holds on average its 1,000 prompt tokens and half of its 300-token answer, 1,150 tokens or 72 blocks, and 8 × 72 = 576 of 9,584 blocks is 0.060. The KV pool that makes the card look full in nvidia-smi is 6% used by the batch.

The counters show the work. vLLM defines them as vllm:generation_tokens and vllm:prompt_tokens, and the Prometheus client adds _total to a counter's name in the scrape. vllm:generation_tokens_total, the number of generation tokens processed, rises by about 409 a second. vllm:prompt_tokens_total rises by about 1,363 a second, the 1.36 requests a second times 1,000. vllm:iteration_tokens_total is a histogram of the number of tokens in each engine step. Most steps hold 8 tokens. A few hold 1,007, a newcomer's prompt plus seven decode tokens. That histogram is the clearest picture of continuous batching there is: the step size jumps from 8 to 1,007 and back each time one request leaves and another joins, about once every 0.73 s at eight users.

On the starter the same questions have no answers. Its queue is an asyncio.Queue inside one Python process, and the only sign of it from outside is how long people wait. These vLLM gauges are also exactly what a router reads. The lessons Which GPU answers soonest and More Pods when the queue grows build on these numbers.

Chapter 13 of 14

Where the lab goes wrong

The usual failures are memory sums that do not add up, and each one has an exact message

Most first attempts fail at start, and vLLM says why in a precise sentence. The classic is the full-precision build. Point the same command at Qwen/Qwen3-32B, the BF16 build of 65.5 GB, and the sum becomes 76.5 − 65.5 − 2 = 9.0 GB for the cache, 8.38 GiB. One request at --max-model-len 40960 needs 40,960 × 262,144 bytes, 10 GiB. vLLM refuses to start. In v0.11.0 the error begins: To serve at least one request with the models's max seq len (40960), (10.00 GiB KV cache is needed, which is larger than the available KV cache memory (8.38 GiB). It then gives an estimate of the longest length that would fit and ends: Try increasing `gpu_memory_utilization` or decreasing `max_model_len` when initializing the engine. Lowering --max-model-len to 16384 would start it, with room for about 34,000 tokens in all, two requests at full length. That is why this site serves the FP8 build.

The second failure comes from sharing. --gpu-memory-utilization is a share of the whole card for this one vLLM process. Its documentation gives the example of two instances on one GPU, each set to 0.5. If something else already holds memory on the card, 0.9 may ask for more than is free, and the start fails. On Kubernetes, one GPU per Pod avoids this, and the lesson A Pod asks for a GPU explains how the card is handed out.

The third is a benchmark that measures the wrong thing. Without --ignore-eos, answers stop at random lengths and the runs are not comparable. Without --max-concurrency, --request-rate inf releases all 64 prompts at once and measures a burst. And --api-key on vLLM does not cover the whole server. In v0.11.0 the key is checked only on paths that start with /v1, and /health, for example, stays open. The current documentation lists /v1, /v2, /inference and /cohere, and warns that other paths such as /invocations are not authenticated. Either way, keep the server behind the gateway.

Chapter 14 of 14

From one server to two

A second Pod doubles the pool and the throughput, and brings the routing question with it

One vLLM server on one H100 now carries the eight users that buried the starter, and about 96 before it has to make anyone wait. Past that, the next step is a second copy. Set replicas to 2 on the Deployment and the ReplicaSet qwen3-6f7d9c8b4 adds Pod qwen3-6f7d9c8b4-m9q4t on gpu-node-2, at 10.244.2.22 on port 8000. It loads its own 34.3 GB of weights in its own three minutes and builds its own pool of 9,584 blocks. Nothing is shared between the two. The course stresses this: every replica is a full copy of the model on its own expensive GPU, slow to start and costly to copy.

With two Pods behind Service qwen3, the lab's benchmark at 16 users spreads eight to each, and the total about doubles to roughly 818 output tokens a second. That works here because the benchmark's requests are all the same size and share no prefix. Real traffic is not like that. One user sends a greeting and another a 30,000-token document, and a chat's second turn finds its cached prefix only on the Pod that served the first. A Service spreads connections and knows neither fact.

This is where the lab hands over to the rest of the track. The gauges of the last chapter, running, waiting and KV usage, are what a smarter router reads to pick a Pod. The lesson Which GPU answers soonest shows that router, and More Pods when the queue grows shows how vllm:num_requests_waiting can add Pods on its own.

What to keep

Same GPU, same model, five times the work

The starter server was correct and it was slow for one reason: a single loop gave the GPU one request at a time, so every pass read all 34.3 GB of weights to make one token while the cores sat almost idle and more than half the card stood empty. Grouping requests into fixed batches helps and wastes much of the gain on padding, on rows that ride along after they finish, and on newcomers who cannot join. vLLM rebuilds the batch before every pass and hands out KV memory in 16-token blocks as the tokens arrive, so a request leaves the moment it ends, another joins the next pass, and about 116 requests of 1,300 tokens fit where reservations for the longest case fit 3. Swapping it in was one change to the Deployment. At eight users the same H100 went from 79 to 409 output tokens a second, the median first token came in under a quarter of a second and the mean in about 0.4 s, instead of up to 27, and each user's stream slowed from 83 to about 53 tokens a second. Raising the number of users raises the total until prefill and memory set the limits, and /metrics shows the batch, the queue and the pool the whole time.
