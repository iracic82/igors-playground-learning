Kubernetes underneath

What a container is made of

From the kubelet's first call to an ordinary process in ps

The kernel has no object called a container. It has processes, and it has a few ways to restrict one: namespaces limit what a process can see, a cgroup limits what it can use, and a root filesystem of its own replaces the node's files. A container is a process started with all three. This lesson follows the model server Pod qwen3-6f7d9c8b4-x7k2p on gpu-node-1 from the moment the kubelet learns of it. The kubelet calls containerd, containerd writes the container down as a file and starts a small helper, the helper runs runc, and runc asks the kernel for each piece. The last step is one system call that starts vLLM.

After the start, the lesson keeps following the same process. It shows what an operator can see of it on the node, what the kernel does when the process reaches its CPU or memory budget, how other runtimes plug in at the same point, and how the pieces are taken apart again when the Pod is stopped. Every call, file and field named is the real one.

Chapter 1 of 13

The kubelet makes its calls in a fixed order

One call for the Pod, then two for each container

The kubelet on gpu-node-1 watches the API server for Pods bound to its node. Pod qwen3-6f7d9c8b4-x7k2p arrives. The kubelet does not create anything in the kernel itself. It talks to the container runtime, here containerd, over the Container Runtime Interface, or CRI. This is a gRPC service on a Unix socket on the node, for containerd unix:///var/run/containerd/containerd.sock.

The order of calls is fixed. First comes RunPodSandbox, once for the whole Pod. A sandbox is the part of a Pod that its containers share. Then, for each container, CreateContainer and StartContainer. Between the sandbox and the container the kubelet makes sure the image is on the node, which the lesson about image pulls covers. The first call carries the Pod's name, namespace, UID and hostname.

The kubelet's source lists its work for one Pod in nine steps: compute what changed, kill the sandbox if it must be replaced, kill containers that should not run, create the sandbox if needed, report that the sandbox is ready, resize running containers, then create ephemeral containers, init containers and finally the normal containers. Starting one container is four steps of its own: get the security profile and the image, create the container, start it, and run its postStart hook if it has one.

The request for the sandbox has a second field next to the Pod's configuration, runtime_handler. It names which runtime configuration in containerd should run this Pod. An empty string means the default, runc. A Pod sets it through spec.runtimeClassName, and a GPU Pod on some clusters names a runtime class called nvidia this way. An unknown handler makes the call fail.

Chapter 2 of 13

A pause process holds what the Pod shares

The network, IPC and hostname outlive any one container

A namespace is a kernel object that gives the processes inside it their own copy of one global resource. It exists only while something keeps it open. A Pod's containers share a network, so that shared part needs an owner that never restarts.

containerd makes a network namespace for the sandbox and has the network plugin put an interface in it, with the Pod's address 10.244.1.21. The network plugin follows CNI, the Container Network Interface. containerd looks for its programs in /opt/cni/bin and for its configuration in /etc/cni/net.d by default. Then it starts the sandbox container from the image registry.k8s.io/pause. The version in containerd's default configuration depends on the release: its configuration document gives pause:3.10 for v2.0 and v2.1, pause:3.10.1 for v2.2, and pause:3.10.2 on the main branch. containerd pins the image, which marks it as exempt from image garbage collection. Its only process sleeps. It runs in that network namespace and gets new IPC and UTS namespaces, which hold shared memory segments and the hostname. Every container added later joins these three by path. When vLLM crashes and is restarted, the Pod keeps its IP address, because pause never stopped.

The kubelet tells the runtime how each container should treat each namespace. The CRI defines four modes. POD means share the Pod's. CONTAINER means the container gets its own. NODE means use the node's own namespace, which is what hostNetwork asks for. TARGET means join another container's namespace, which a debugging container uses to see one container's processes.

Process IDs are the exception to sharing. By default each container has its own PID namespace. With shareProcessNamespace: true in the Pod, three things change. The container's process is no longer PID 1, because pause is. Every container sees the others' processes, with their arguments and environment. And each container's files are reachable from the others through /proc/<pid>/root.

Chapter 3 of 13

A root filesystem made of layers

overlayfs stacks read-only image layers under one writable directory

Now the kubelet sends CreateContainer for the vLLM container. The first thing containerd prepares is the container's files. The image is already on the node as a set of read-only layers, each one a directory, shared by every container that uses the image. containerd asks its snapshotter for one more directory on top that this container alone may write to.

The kernel filesystem overlayfs joins them. Its mount takes three options. lowerdir lists the image layers separated by colons. The kernel stacks them starting from the rightmost, so the leftmost entry is the top layer. upperdir is the writable directory. workdir is an empty directory on the same filesystem as upperdir, which overlayfs needs for its own bookkeeping. Without upperdir and workdir the whole mount would be read-only.

A read looks in upperdir first, then down the layers until a layer has the file. A file is copied up into upperdir the first time it is touched in a way that needs writing. That includes opening it for writing, changing its metadata, such as its mode or owner, and making a hard link to it. Copy-up copies the whole file, then its extended attributes. So, with overlayfs's usual settings, a chmod on a 6 GB file in an image layer writes 6 GB into the container's layer. The kernel has a feature named metacopy that changes this. When it is enabled, by a kernel build option, a module parameter or the mount option metacopy=on, a chmod or chown copies up only the metadata. The data is copied later, the first time the file is opened for writing. It is off unless one of those turns it on.

A deleted file cannot be removed from a read-only layer, so overlayfs records a whiteout in upperdir. It is either a character device with the device number 0/0 or an empty file with the extended attribute trusted.overlay.whiteout. A directory whose old contents should all be hidden is marked opaque with trusted.overlay.opaque set to y. Nothing is mounted yet. The snapshotter only hands back the mount it has prepared.

Chapter 4 of 13

The container written down as one file

config.json says everything runc will need

containerd now turns the request into a document. Its format is the runtime specification of the Open Container Initiative, or OCI, and its file name is config.json. The directory that holds it, next to a rootfs directory, is called a bundle.

The file names the process to run with its arguments, environment and user. Some of these come from the image's own configuration, which stores the entrypoint, the default arguments and the environment. containerd merges those with what the Pod's spec says. The file names the root filesystem. It lists every mount, every namespace, the cgroup path, the resource limits, the capabilities and the seccomp filter. A namespace entry with a path means join that one. An entry with no path means make a new one.

Some devices appear in every container whatever the file says. The specification requires /dev/null, /dev/zero, /dev/full, /dev/random, /dev/urandom, /dev/tty and /dev/ptmx, and /dev/console when a terminal is asked for. A GPU's device files are additions to that list, and how they arrive depends on the path. With CDI, the default of NVIDIA's GPU Operator from v25.10.0, containerd applies the edits in the CDI file while it builds the spec, so the card's device files reach config.json at this step as device entries. On the older path they do not. config.json then carries only the variable NVIDIA_VISIBLE_DEVICES that the device plugin's Allocate answer asked for, and NVIDIA's runtime adds a prestart hook that mounts the device files into the root filesystem during create. The lesson A Pod asks for a GPU follows that part.

The file can also name hooks, programs the runtime runs at fixed points. During create there are three: prestart, createRuntime and createContainer. The specification marks prestart as deprecated, in favour of createRuntime, createContainer and startContainer. Runtimes still run it. During start there is startContainer, then poststart after the program begins, and poststop after the container is deleted. NVIDIA's older GPU path still adds its work as a prestart hook. Any tool that reads this format can start the container, and runc is the usual one. Once the container is created, the specification says, changes to config.json no longer affect it.

Chapter 5 of 13

The shim stays and runc leaves

Two helpers with opposite lifetimes

The kubelet sends StartContainer. containerd does not start the process itself. It works through a shim, a small program that sits between containerd and the container. Its name comes from the runtime's name by a fixed rule. The runtime io.containerd.runc.v2 gives the binary containerd-shim-runc-v2. containerd keeps the containerd-shim- prefix on purpose, so that ps aux | grep containerd-shim lists every shim on a node. If the binary is missing, the start fails with an error that says the runtime binary is not installed.

The shim for this Pod has been running since the sandbox was made, and it serves every container in the Pod. This grouping is the runc shim's own choice. It groups by an annotation in the container's OCI spec. It first looks for io.containerd.runc.v2.group, then for io.kubernetes.cri.sandbox-id, which containerd's CRI plugin sets. The shim's code calls these keys group labels. It reads them from the spec's annotations. When containerd asks to start a shim for the vLLM container, the start command finds the existing one, returns its socket address and exits. containerd talks to the shim over ttRPC, a small version of gRPC.

The shim mounts the prepared overlayfs on the bundle's rootfs directory and then runs runc twice. runc create builds the container and stops just before the program would begin. runc start lets it begin. Each time, runc does its work and exits. The shim remains as the parent of the container's process for its whole life. It holds the process's output and collects its exit code.

Because of that, containerd can be restarted or upgraded while every container on the node keeps running. The same holds for the kubelet. The Pod lifecycle documentation says that Pods and their containers keep running while the kubelet restarts.

Chapter 6 of 13

Namespaces decide what the process can see

New ones by unshare, the Pod's own by setns

runc create starts a child process that will become the container. runc does this in three stages, named in its source STAGE_PARENT, STAGE_CHILD and STAGE_INIT. The parent clones the child. The child changes namespaces. The child then clones the last stage, which becomes the container's first process. The extra step exists because a new PID namespace applies only to children, and on older kernels the clone flags runc needs could not be combined.

Before it runs any program, the child changes its own namespaces with two system calls. setns joins an existing namespace, named by a file under /proc. The child uses it for the three that pause holds. unshare creates new namespaces, one for each flag it is given, and moves the caller into them. The flags are the same ones clone accepts when it creates a process.

Each namespace hides one thing. The PID namespace hides every process outside the container and numbers the first process inside as 1. The mount namespace gives the container its own table of mounts. The cgroup namespace makes the container's own cgroup look like the root.

A user namespace, which a Pod requests with hostUsers: false, maps user IDs so that root inside is an unprivileged user on the node. With the default of 65536 IDs for each Pod, the Pod sees IDs 0 to 65535 inside. The kubelet maps them to a range above 65535 on the node, a different range for each Pod. From v1.33 the kubelet setting userNamespaces.idsPerPod changes that count. It must be a multiple of 65536, and it applies only to containers created after the kubelet restarts with it. A custom range for the kubelet in /etc/subuid must start at a multiple of 65536 and hold that many IDs for each Pod the node may run. The documentation's example is kubelet:65536:7208960, which is 110 × 65536 for the default of 110 Pods. It needs Linux 6.3, runc 1.2 and containerd 2.0 or later.

Chapter 7 of 13

A cgroup decides what the process may use

The Pod's requests and limits become a few small files

A control group, or cgroup, is a group of processes that the kernel accounts for and limits together. With cgroup v2 every group is a directory under /sys/fs/cgroup, and each setting is a file in it. Kubernetes supports cgroup v2 on Linux 5.8 or later, with containerd 1.4 or later. To see which version a node runs, stat -fc %T /sys/fs/cgroup/ prints cgroup2fs for v2 and tmpfs for v1. From v1.35 the kubelet will not start on a cgroup v1 node by default.

Someone has to manage the tree. With the systemd cgroup driver, systemd does, and the documentation asks for it on cgroup v2. The kubelet and containerd must agree. In containerd the switch is SystemdCgroup = true in the runc options. Newer kubelets ask containerd which driver it uses through the RuntimeConfig call. The kubelet puts every Pod under a tree it owns, kubepods.slice, which is why the path has that prefix.

runc makes the directory named in config.json, puts the child process in it and writes the limits. The CPU limit of 8 becomes cpu.max, as a quota of 800000 microseconds of CPU time in every period of 100000. The CPU request of 8 becomes cpu.weight, a share that only matters when CPUs are contended. The memory limit of 64Gi becomes memory.max, in bytes. A fourth file comes from the request's unified field, which names cgroup v2 files directly. On cgroup v2 the kubelet sends memory.oom.group set to 1 by default, so an out-of-memory kill takes every process in the container together.

The kubelet's conversions have limits. Shares are clamped between 2 and 262144, so a container with no CPU request gets 2. A quota below 1000 is raised to 1000, so the smallest CPU limit is 1 ms in every 100 ms. This Pod has equal requests and limits for CPU and memory, which makes its quality of service class Guaranteed.

Chapter 8 of 13

A new root and fewer privileges

pivot_root hides the node, then capabilities and seccomp narrow the process

The child still sees the node's files. Inside its new mount namespace it mounts /proc, /dev and /sys under the bundle's rootfs, creates the device files the specification requires and bind-mounts the Pod's volumes there. Then it calls pivot_root, which makes that directory the root mount of the namespace. The old root is unmounted, and the node's filesystem is gone from view.

runc's init then works through a fixed list, read from its source in this order: set the hostname and domain name, apply the AppArmor profile, write sysctls, make the paths the spec lists read-only, mask the paths it lists, and set no_new_privs if asked. A Pod asks for no_new_privs with allowPrivilegeEscalation: false. The flag stops the process and its children from gaining privileges, for example through a setuid program.

Next it gives up privileges. Root on Linux is split into 41 capabilities, and containerd keeps 14 of them unless the Pod says otherwise. CAP_SYS_ADMIN and CAP_NET_ADMIN are not among them.

A seccomp profile, when the Pod has one, filters which system calls the process may make. containerd's default profile is a list of allowed calls with a default action of returning an error. Without no_new_privs, installing a filter is itself a privileged act, so runc installs it before dropping capabilities. With no_new_privs it installs it as late as possible. Kubernetes runs containers Unconfined unless the Pod asks for RuntimeDefault or the kubelet has seccompDefault turned on. Custom profiles live in /var/lib/kubelet/seccomp/. A profile in audit mode writes kernel lines that start audit: type=1326 and name the call by number, which is the line to search for when a filter is suspected.

Chapter 9 of 13

A pipe holds the start, then execve

runc create ends with a process waiting on a FIFO

After the privileges are dropped, the child looks up the program named in config.json. If the binary does not exist in the new root, runc create fails here, before any start is attempted. containerd runs runc create when the kubelet asks to start the container, so a typo in the command shows up as a failed StartContainer, and the kubelet records a Warning event with the reason Failed.

Then the child waits. runc keeps it on a named pipe, a FIFO, in the container's state directory. The child opens the pipe for writing. Opening a FIFO for writing blocks until some process opens it for reading, so the child stops there. That is the whole difference between created and running. Everything is in place: namespaces, cgroup, root, capabilities, seccomp. Only the program has not begun. runc create exits, and the shim reports success to containerd.

When the shim runs runc start, runc opens the pipe for reading. The child's open returns, it writes a single 0 and runc start reads it. The child then runs any startContainer hooks and calls execve with the program, its arguments and its environment from config.json. execve replaces the program in a process and keeps the process. The namespaces, the cgroup, the root and the capabilities all stay. runc's own code is gone from memory, and vLLM's is loaded. runc start exits too. The shim is now the parent of a process it did not exec itself.

The kubelet records the Started event. If the Pod has a postStart hook, the kubelet runs it now, as the fourth step of starting a container. The CRI state is CONTAINER_RUNNING and the OCI state is running. vLLM is PID 1 inside its PID namespace. That matters for signals later: PID 1 gets no default handling of signals from the kernel, so it must handle SIGTERM itself.

Chapter 10 of 13

What the node shows

ps, /proc and crictl see one ordinary process

On gpu-node-1 the model server is one more line in ps. Its PID there is 48211 and its parent is the shim, 47990. Inside its own PID namespace the same process is number 1. The file /proc/48211/status shows both numbers on the line NSpid. The link /proc/48211/ns/net points at the same namespace as the pause process's. /proc/48211/cgroup names the cgroup path.

kubectl never shows a sandbox. crictl does. It speaks the same CRI socket as the kubelet and reads its settings from /etc/crictl.yaml, where runtime-endpoint for containerd is unix:///var/run/containerd/containerd.sock. crictl pods lists the sandboxes. crictl ps -a lists containers, running and exited. crictl images lists what the CRI sees. crictl exec -i -t runs a command in a container. crictl logs reads a container's output.

That output is in files the kubelet chose. The sandbox's log directory is /var/log/pods/ followed by the namespace, the Pod's name and its UID, joined by underscores. Each container writes to its name and a restart counter, so this one writes vllm/0.log. After a restart the next file is 1.log. containerd caps one line at 16384 bytes by default and splits longer ones. kubectl logs reads these same files through the kubelet.

Nothing here is a virtual machine. There is no second kernel. Every container on the node runs on the node's kernel, which is why a kernel bug one container can reach affects all of them.

Chapter 11 of 13

When the budget runs out

CPU is throttled, memory is killed, and the whole container goes together

The limits written into the cgroup are enforced by the kernel alone. No agent watches them. What happens at each limit differs.

For CPU, cpu.max says the group may use up to its quota in each period. Once vLLM's threads have used 800000 microseconds of CPU in a 100000 microsecond period, they are paused until the next period starts. Nothing is killed. The file cpu.stat in the container's cgroup counts this. nr_periods counts the enforcement periods that have passed, nr_throttled the number in which the group hit its limit, and throttled_usec the total time it was held back. A model server whose request latency jumps while the GPU sits idle may be starving for CPU here.

For memory, memory.max is a hard limit. When the group reaches it and the kernel cannot reclaim enough, the OOM killer runs inside the cgroup. On cgroup v2 the kubelet sets memory.oom.group to 1 unless singleProcessOOMKill is set to true, and on cgroup v2 that setting defaults to false. With the flag on, the kernel kills every process in the group together, or none. The container status then carries the reason OOMKilled, and kubectl describe pod shows Last State Terminated, Reason OOMKilled and Exit Code 137. 137 is 128 plus 9, the number of SIGKILL.

Memory pressure on the whole node is another matter. The kubelet ranks processes for the node's OOM killer with oom_score_adj. A Guaranteed Pod like this one gets -997, a BestEffort Pod 1000, and the kubelet itself runs at -999. Two more files exist. memory.high throttles and reclaims hard without killing, and the kubelet writes it only when the MemoryQoS feature is on. pids.max limits the number of processes.

Chapter 12 of 13

Other runtimes at the same seam

runtimeClassName picks a handler, and the handler picks a shim

Everything after the kubelet's call can be swapped. containerd's configuration lists runtimes by name, each with a runtime_type. The default is runc with the type io.containerd.runc.v2. A Pod picks another one with spec.runtimeClassName. The RuntimeClass object maps that name to a handler, and the kubelet sends the handler in RunPodSandbox as runtime_handler.

containerd's configuration guide shows three alternatives next to runc. The type io.containerd.runsc.v1 is gVisor, which runs the container on a kernel written in user space that answers the container's system calls itself. The type io.containerd.kata.v2 is Kata Containers, which runs the Pod inside a small virtual machine with its own kernel. And crun, a runc replacement written in C, plugs in under the same runc shim by setting BinaryName to its path, for example /usr/local/bin/crun.

The shim's name follows the rule from earlier. io.containerd.kata.v2 means containerd runs containerd-shim-kata-v2. That is the reason containerd names shims after runtimes: the type is all it needs to find the binary.

This qualifies the claim made two chapters back. With runc or crun, there is one kernel on the node and every container uses it. With Kata, each Pod has a second kernel inside a virtual machine. With gVisor, a user space kernel stands between the container and the node's. The kubelet, the CRI calls and the Pod's YAML stay the same in all of them. GPU Pods use the same seam. NVIDIA's runtime can be a runtime class named nvidia, and NVIDIA's documentation says that under its CDI mode a container that asks for GPUs through NVIDIA_VISIBLE_DEVICES without a device plugin allocation must set runtimeClassName: nvidia.

Chapter 13 of 13

Stopping: the pieces in reverse

SIGTERM, a grace period, SIGKILL, then the sandbox gives its address back

Some hours later the Deployment is updated to a new revision. Its new Pods get a new pod-template-hash, such as qwen3-58b4d7f9c6-k8w3z, and qwen3-6f7d9c8b4-x7k2p is deleted. The kubelet stops the container with StopContainer and a grace period. The CRI says the runtime must kill the container forcibly once the grace period is over.

The signals come in two steps. First SIGTERM goes to the main process of each container. That is vLLM, PID 1 in its namespace, which must catch the signal itself to finish its requests and exit. The image can name a different first signal with STOPSIGNAL, and many runtimes respect it. If the process is still alive when the grace period ends, SIGKILL goes to every remaining process. The default grace period is 30 seconds, set on the Pod as terminationGracePeriodSeconds. A preStop hook still running at the end gets one extra 2 seconds. The shim, still the parent, collects the exit code and passes it to containerd. The CRI state becomes CONTAINER_EXITED.

Then the sandbox. The kubelet calls StopPodSandbox at least once before it calls RemovePodSandbox. Stopping the sandbox reclaims its network resources, which means the CNI plugin is asked to release 10.244.1.21. The pause process ends, and with it the last thing holding the Pod's network, IPC and UTS namespaces open. The kernel frees them. The cgroup directory is removed. The writable snapshot, upperdir and all, is deleted with the container, while the read-only image layers stay for the next Pod.

None of this needed the kubelet to be up the whole time, nor containerd. Each piece was owned by something that outlives a restart: the shim for the process, the pause process for the namespaces, the kernel for the cgroup.

What to keep

A container is an ordinary process

Nothing in this lesson created a thing called a container. The kubelet made three kinds of CRI call. containerd held the Pod's shared namespaces open with a pause process, stacked the image's layers with overlayfs and wrote config.json. A shim ran runc. runc went through three stages, joined and created namespaces, wrote four cgroup files, pivoted into a new root, dropped capabilities, waited on a pipe and called execve. What is left is the vLLM process with a restricted view and a budget. It appears in ps on gpu-node-1 like any other process, with the shim as its parent. The kernel enforces its budget by itself, throttling CPU and killing the whole group at its memory limit. A different runtime class can swap runc for a virtual machine without changing the calls. Stopping undoes the same pieces in reverse: SIGTERM, a grace period, SIGKILL, and a sandbox that gives its address back.
