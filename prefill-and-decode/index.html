Inference

Prefill and decode

What a GPU does with a prompt, and what limits it

A GPU is a small computer of its own: thousands of cores and a block of very fast memory, joined to the rest of the server by a much slower bus. This lesson follows a model into that memory and then follows one prompt through it. You will see the two phases every request has. Prefill reads the whole prompt in one pass and decides how long the user waits for the first word. Decode writes the answer one token per pass and decides how fast the words come. They are limited by different things, and neither limit is the one that decides how many users a GPU can serve. That one is memory.

Chapter 1 of 12

Fetch the weights

32.8 GB from object storage

A model is two things: a formula, which is the same for most models, and the weights, billions of learned numbers in a file. Qwen3-32B has 32.8 billion of them. Stored in 8 bits each, that is 32.8 GB. This lesson counts every weight at exactly one byte, which keeps the sums clean. The real Qwen3-32B-FP8 checkpoint on Hugging Face is a little larger, 34.3 GB, because about 1.56 billion weights, mainly the embedding table and the output layer, stay in 16 bits, and the 8-bit weights carry small scale factors. The official BF16 build, with 16 bits a weight, is 65.5 GB, which leaves too little of an 80 GB card for anything else. When the vLLM Pod on gpu-2 starts, it has none of it.

It downloads the weights from object storage, as seven large files. The real checkpoint has seven files of 4.88 to 4.97 GB. This lesson uses a simpler layout that adds up to its 32.8 GB: six of 5.0 GB and a seventh of 2.8 GB. Each is fetched with a signed S3 GetObject request. The requests go to BIG-IP, which stands in front of the storage nodes. It ends the TLS session, so the storage nodes spend their CPU on storage, and it picks a node for each request. The request then travels on to the node as plain HTTP on port 9000. It is 22 bytes shorter there, because the TLS record around it is gone.

In this lesson the whole download takes 9 seconds. That is 32.8 GB ÷ 9 s, about 3.6 GB or 29 gigabits every second, and it is an illustrative figure. The point is the order of events. A new worker can serve nothing until every file has landed, so the storage path decides how fast a factory can add capacity. The files land on the worker's local NVMe drive. If the Pod keeps that directory, its next start can skip the download.

Chapter 2 of 12

Into GPU memory

Across the bus, once

Zoom into gpu-2. The weights are on the local disk and the GPU can't use them there. Its cores can only work on what is in the GPU's own memory, called HBM. So the weights are read from disk into the server's memory and copied across the PCIe bus into HBM. This is the only time they cross that bus.

The CPU does not push the bytes itself. Writing into GPU memory from the CPU side tops out around 1 GB/s. The GPU's copy engines pull the data out of host memory at tens of GB/s, and the CPU only describes each copy. The bus allows about 64 GB/s each way. Large copies measured on one such machine ran at about 55 GB/s, so 32.8 GB needs about 0.6 seconds of pure copying. Reading the files from disk takes 5.9 seconds in this lesson, 32.8 GB at about 5.6 GB/s, so the load into the GPU is nearly all disk.

Then vLLM does something that surprises people: it sets aside almost all the memory that is left for the KV cache and cuts it into blocks. This worker runs with gpu_memory_utilization at 0.9, so vLLM may use 72 of the 80 GB. The weights take 32.8 GB and about 2 GB is working memory for passes. The other 37.2 GB becomes the pool. It is sized once, at start. An idle vLLM server can show a GPU that looks nearly full. That is by design.

Chapter 3 of 12

What one token costs in memory

The sum behind the 142,000

The KV cache has a fixed shape. For every token the model has read, each layer keeps one key vector and one value vector for each of its key and value heads. Qwen3-32B has 64 layers. Its attention uses 64 query heads and only 8 key and value heads, a design called grouped-query attention, and each head holds 128 numbers. Stored as 16-bit numbers, one token costs 64 × 2 × 8 × 128 × 2 bytes. That is 262,144 bytes, about 260 KB. With 64 key and value heads it would be eight times as much, about 2.1 MB.

Only the token count grows. Layers, heads and head size are fixed by the model, so the cache of a request is its length in tokens times 262,144 bytes. vLLM cuts the pool into blocks so that it never has to find one long free stretch. This worker uses blocks of 16 tokens, which makes a block exactly 4 MiB. The 37.2 GB pool holds 8,869 of them, room for 141,904 tokens. The lesson rounds that to 142,000.

Other models give other prices. A 7 billion weight model with 32 layers and 32 key and value heads of 128 numbers costs about 0.5 MB a token, so a 4,096 token conversation holds 2 GB. A vendor example for another large model lists 1,000 tokens at 0.1023 GB, about 102 KB each. At that price a user with 1,000 tokens in and 1,000 out holds 0.2046 GB, and a hundred such users hold 20.46 GB. On this worker the pool for the cache is larger than the weights.

Qwen3-30B-A3B, the mixture-of-experts sibling of this lesson's model, shows which numbers set the price. Its name says 30 billion weights with 3 billion active. The model card gives 30.5 billion in all and 3.3 billion used for each token. Each of its layers holds 128 small feed-forward networks called experts, and a router sends every token through 8 of them. The experts replace only the feed-forward part of a layer. Every token passes through the same attention weights in each layer, and the KV cache comes from attention alone, so the A3B in the name leaves the cache untouched. All 128 experts must still sit in GPU memory, because the router can pick any of them for the next token. Its config.json lists 48 layers, 32 query heads, 4 key and value heads and a head size of 128. In 16 bits one token costs 48 × 2 × 4 × 128 × 2 bytes. That is 98,304 bytes, 96 KiB, against 262,144 bytes, 256 KiB, for Qwen3-32B in the same type. The MoE model is 2.67 times cheaper a token because it has three quarters of the layers and half the key and value heads. With vLLM's cache_dtype set to fp8 it would be 49,152 bytes, 48 KiB. If the same 37.2 GB pool held its cache in blocks of 16 tokens, a block would be 1.5 MiB and the pool would hold 23,651 blocks, room for 378,416 tokens.

The README of a third-party GitHub project, synchopate/nemotron-30b-cpu-256k, ran Qwen3-30B-A3B on a CPU with a patched llama.cpp. It reports 39 KB a token and about 7 GB for the whole cache at a 256K context, which is 262,144 tokens. Nobody has reproduced those figures for this lesson, so read them as the project's own claims. Its 39 KB column is labelled Q8_0/Q4_0 EAKV, which is the project's own patch that chooses how to compress the cache. The figures are smaller than either 16-bit figure above because they use llama.cpp's compressed cache formats. Its q8_0 format packs 32 numbers into 34 bytes: one byte each plus a 2-byte scale. Its q4_0 format packs 32 numbers into 18 bytes: half a byte each plus the scale. One token of this model holds 48 × 4 × 128 = 24,576 key numbers and as many value numbers. With keys in q8_0 and values in q4_0 that is 26,112 + 13,824 = 39,936 bytes, which is 39.0 KiB, the 39 KB of the test, whose KB are units of 1,024 bytes. At 262,144 tokens that is about 10.5 GB. The same table gives 27.65 KB a token with keys and values both in q4_0, and the sum agrees: 27,648 bytes a token, about 7.2 GB at 262,144 tokens. The project's 7 GB figure is 7,078 MB, about 7.1 GB, and its table does not say which cache format that row used. It sits close to the q4_0 sum without matching it exactly, so linking the two is this lesson's inference and the source's own sums are loose. Compare like with like. Stored the same way as the 39 KB figure, Qwen3-32B would cost 106,496 bytes, 104 KiB, a token, and 27.9 GB at 262,144 tokens. A 256K context is also past what Qwen validates for either model. The model cards give 32,768 tokens natively and 131,072 with the YaRN method of stretching positions.

Chapter 4 of 12

A prompt arrives

Text becomes tokens, tokens need blocks

The worker is ready and a first request comes in: a prompt of 2,000 tokens that asks for an answer of up to 300. It arrives as one HTTP POST to /v1/chat/completions on port 8000, about 8.6 kB of JSON. The API server applies the model's chat template, which wraps each message in the role markers the model was trained on, and turns the text into token numbers. Only now does anything know the size of the request: a little over 4 bytes a token.

The request enters the waiting queue. Before every pass the scheduler looks at that queue, first come first served. It admits a request when two limits allow it: the number of running requests, capped by max_num_seqs, and free blocks in the pool. vLLM checks that the whole prompt fits before it admits anything. A 2,000 token prompt needs 2,000 ÷ 16 = 125 blocks, about 520 MB of the pool.

The scheduler also looks the prompt up in the prefix cache, block by block, in case an earlier request left the same opening text behind. This worker is new, so it finds nothing. The scheduler gives the request blocks from the KV cache pool for the tokens it will compute in the next pass, and puts it in the batch. This prompt fits in one pass, so that is enough for the whole prompt. A longer prompt gets its blocks pass by pass, as a later chapter shows. Nothing has been computed yet. The blocks are reserved space, waiting for the prefill pass to fill them. vllm:kv_cache_usage_perc moves from 0 to 0.014, which is 125 of 8,869 blocks.

Chapter 5 of 12

Prefill

The whole prompt in one pass

Now the GPU reads the prompt. All 2,000 tokens go through the model together, in one pass. In every layer, each token looks at all the tokens before it. For each token and each layer the model works out a key and a value, the two things later tokens will need from it, and stores them in the KV cache. This is prefill.

It reads the weights once and does an enormous amount of arithmetic with them, so it is limited by how fast the cores can compute. Every one of the 2,000 tokens passes through every weight matrix. Attention then compares each token with itself and every earlier one, which is 2,000 × 2,001 ÷ 2 = 2,001,000 pairs in each of the 64 layers. The longer the prompt, the longer it takes. vLLM caps the tokens one pass may carry with max_num_batched_tokens, 8,192 by default for a server on a GPU this size, so this prompt fits in a single pass.

Its last output is the first token of the answer, which is why prefill sets the time to first token. Here that is 421 ms: 2 ms to queue and schedule, 418 ms of prefill and 1 ms to sample the token and send it. vLLM records the total in vllm:time_to_first_token_seconds and the prefill share in vllm:request_prefill_time_seconds. At about 0.21 ms a token, a prompt ten times as long waits about ten times as long. Those times are illustrative.

Chapter 6 of 12

Decode

One token per pass

The rest of the answer comes one token at a time. Each pass takes the single newest token, runs it through all 64 layers, looks back at the KV cache for everything before it, and produces the next token. Then that token goes in and it starts again. A 300 token answer takes 300 passes in all: the prefill pass made token 1, and 299 decode passes make the rest.

Each pass still reads all 32.8 GB of weights, but now it does very little arithmetic with them: one token's worth. So the cores mostly wait for memory. Decode is limited by how fast the GPU can pull the weights out of its memory, and that sets the time between tokens. Here it is 12 ms. vLLM records each gap in vllm:inter_token_latency_seconds.

Add the answer up. The first token came at 421 ms. The other 299 follow 12 ms apart, 3,588 ms in all, so the answer is complete about 4.0 seconds after the request arrived. Prefill was a tenth of that. The balance shifts with the shape of the request. A 30,000 token prompt with a one line answer is nearly all prefill. A short question with a 2,000 token answer is nearly all decode. Two requests with the same total of tokens can take very different times. If saved prefill work spares 0.2 seconds of a request whose decode takes 10 seconds, the gain is 2%.

Chapter 7 of 12

The bandwidth ceiling

Bandwidth divided by the size of the weights

The limit on decode can be worked out on paper. One pass has to move every weight from memory to the cores once. So the most passes a GPU can make each second is its memory bandwidth divided by the size of the weights. The H100's HBM delivers about 3.35 TB a second and the weights are 32.8 GB. 3,350 ÷ 32.8 is about 102 passes a second, or 9.8 ms a pass. The 12 ms in this lesson sits just above that floor.

The same sum explains hardware choices. An A100 has the same 80 GB with about 2 TB/s, so its floor for this model is about 16 ms. A B200 has about 180 GB at about 8 TB/s, so about 4 ms. An H200 has the compute of an H100, roughly 990 TFLOPS, with 141 GB of memory, which buys room for KV cache. The course this track draws on makes the point with rounder numbers: 3 TB/s over a 16 GB model gives a ceiling of about 200 tokens a second, about 5 ms a token. Worked exactly, 3,000 ÷ 16 is 187.5 passes a second, 5.3 ms each.

It also explains why this model is served in 8 bits. In 16 bits, as the BF16 build, the weights are 65.5 GB. Every pass would move twice the bytes, the floor would double to about 20 ms, and the pool for KV cache would shrink from 37.2 GB to about 4.5 GB, room for about 17,200 tokens. A faster chip with the same memory would change none of this. Compute decides prefill. Bandwidth and bytes decide decode.

Chapter 8 of 12

More users, same pass

Batching is where throughput comes from

Two more requests arrive while the first is still decoding. They don't wait for it to finish. Between two passes the scheduler adds them to the batch. Now look at what a pass costs. Its expensive part is reading 32.8 GB of weights, and that is the same for one request or three. So the next decode pass produces three tokens, one for each user, in almost the time it took to produce one.

A pass with one request took 12 ms and made one token: about 83 tokens a second. A pass with three takes 13 ms and makes three: about 230. Each user's own stream slows from 83 to about 77 tokens a second, and the GPU as a whole does 2.8 times the work. This is why a GPU can serve dozens of people at once. Each of them gets tokens a little slower. Together they get far more. The course this track draws on puts it as one pass making a token for 50 users as cheaply as for one.

The batch is rebuilt before every pass. vLLM first gives each request that is already decoding its one token, then spends what is left of the pass's token budget on prefill for newcomers. So B and C are prefilled in passes that also keep A's answer moving. B needs 94 blocks for 1,500 tokens and C needs 150 for 2,400. With A's 125 that is 369 of 8,869 blocks, and vllm:kv_cache_usage_perc reads 0.042. That memory is the one thing batching cannot share.

Chapter 9 of 12

A long prompt stalls the others

The two phases take turns

There is a catch. Prefill and decode share one set of cores, so they take turns. A fourth request arrives with a very long prompt: 30,000 tokens, a whole document. Its prefill needs the cores for a long stretch. At the rate seen earlier, about 0.21 ms a token, that is about 6 seconds.

The prompt needs 1,875 blocks, about 7.9 GB, and vllm:kv_cache_usage_perc goes from 0.042 to 0.25 for a single request. Run as one pass, as this chapter shows it, the jump comes at once. With chunked prefill, vLLM's default, it climbs there over the passes of the next chapter. If the whole prompt runs as one pass, the three users who were getting a token every 13 ms see their text stop. In those 6 seconds each of them would otherwise have received about 460 tokens.

Nothing is broken. No error is returned, the Pod is healthy, and the count of running requests went from three to four. The GPU is busy reading someone else's document. The size of the request that lands next to you decides your speed, and nobody can see that size from outside without counting tokens. The long prompt was one POST of 129 kB, like any other. On the worker the stall shows only in the upper buckets of vllm:inter_token_latency_seconds. The next chapter shows what vLLM does about it by default.

Chapter 10 of 12

Cut the long prefill into chunks

What vLLM does by default

vLLM does not run a long prefill as one pass unless it is told to. Chunked prefill is on by default. Every pass has a token budget, max_num_batched_tokens, which defaults to 8,192 for an API server on a GPU of this size. Before each pass the scheduler first gives every decoding request its one token. Whatever is left of the budget goes to waiting prefills. A prompt that does not fit is cut, and the rest waits for the next pass.

Replay the 30,000 token prompt this way. The first pass carries 3 decode tokens and 8,189 tokens of the document. The document needs four passes in all. Each takes about 1.7 seconds at 0.21 ms a token, so the other three users now get a token about every 1.7 seconds. That is far better than a 6 second freeze and far worse than 13 ms. With the budget set to 2,048 the document takes 15 passes of about 0.43 seconds each. The streams stay smoother, and the document's own first token comes no sooner.

The setting is a trade. A small budget protects the time between tokens. A large one shortens the wait for the first token and raises throughput. vLLM's tuning guide suggests more than 8,192 for the best throughput, especially for smaller models on large GPUs. A second setting, long_prefill_token_threshold, caps how many tokens one long prompt may take per pass while others are in the batch. It is off by default. In every case the work is the same 30,000 tokens. Chunking only decides who waits, and for how long at a time.

Chapter 11 of 12

Give each phase its own workers

Disaggregated prefill and decode

Chunking still makes the two phases share one set of cores. The other answer is to stop sharing. In a disaggregated setup some workers only prefill and others only decode. A request first goes to a prefill worker, which reads the prompt and builds the KV cache. The cache is then sent to a decode worker, which writes the answer. A long document now delays other prefills. It no longer touches anybody's stream. In this chapter gpu-1 prefills and gpu-3 decodes. gpu-2, the worker of the earlier chapters, keeps serving its own requests and takes no part in the split.

The price is the handover. The KV cache of the 2,000 token prompt is about 520 MB and that of the 30,000 token document about 7.9 GB, and it has to cross the network between two machines before the first decode pass. vLLM does this through a KV connector, set with --kv-transfer-config. The connectors it lists include one built on NIXL, a transfer library from NVIDIA, and one from LMCache. The fabric between the workers is now part of the time to first token.

The two pools can then be built for their limits: compute for prefill, memory size and bandwidth for decode. The course this track draws on gives the example of H100s for prefill and H200s for decode, and quotes up to 70% more tokens a second for the open source llm-d project. vLLM's own documentation is more careful. It calls the feature experimental. It says the purpose is to tune time to first token and time between tokens separately and to control the worst gaps, and it states that the feature does not improve throughput.

Chapter 12 of 12

Memory is the ceiling

When the KV cache pool is full

Keep adding users and something runs out. It isn't compute: during decode most cores are idle. It is the KV cache pool. Every request in the batch holds blocks for its whole prompt and for every token it has written so far, and the pool holds about 142,000 tokens in all. A request like the first one ends at 2,300 tokens, so about 61 of them fill it: 141,904 ÷ 2,300 = 61.7.

When it is full, the scheduler can't give the next request any blocks. That request stays in the waiting queue until someone else finishes and frees theirs, and its time to first token grows by the whole wait. vLLM's queue has no length limit by default, so nothing is refused. The wait shows in vllm:num_requests_waiting and in vllm:request_queue_time_seconds. A harder case comes when requests that are already running each need one more block and none is free. vLLM then preempts the request it admitted last. It frees that request's blocks, puts it back in the queue and later computes its prompt again. vllm:num_preemptions goes up by one each time.

This is what at capacity means for a GPU: the cores have time to spare and the memory has no room. It is why the two numbers a router most needs from a worker are how full its KV cache is and how long its queue is. Both are on the worker's /metrics page, next to the count of running requests.

What to keep

One GPU, three limits

A GPU has three numbers and each one limits something else. Compute limits prefill, the one pass that reads the whole prompt, so it sets the wait for the first token. Memory bandwidth limits decode, where every pass rereads all the weights to write a single token, so it sets how fast the words come. Memory capacity limits how many requests fit at once, because each one needs its own KV cache next to the weights. Batching makes one pass serve many users, which is where throughput comes from, and a long prefill makes them all wait, which is where the trouble comes from. A worker that is full shows it in two numbers: its KV cache use and its queue.
