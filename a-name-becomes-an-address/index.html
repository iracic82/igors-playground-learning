Kubernetes underneath

A name becomes an address

What happens between the name web and the first packet to it

Pod client on node-1 wants to call the Service web. All it has is the name. Turning that name into an address takes a file, a search list and a DNS server that is itself a Service. The kubelet writes the file into every Pod. The C library in the container reads it and decides which full names to ask for and in what order. The questions go to 10.96.0.10, where CoreDNS answers from a copy of the cluster's Services that it keeps in memory. This lesson follows one lookup of a short name, with the real size of each message. Then it counts what the same rules cost for a name outside the cluster, such as the site a model server downloads its weights from.

Chapter 1 of 15

Three lines the kubelet writes

A nameserver, a search list and ndots:5

A program in a Pod does not discover the cluster's DNS server. It is told. The kubelet configures the file /etc/resolv.conf for each Pod, and with the default DNS policy, ClusterFirst, the file has three lines. The nameserver line holds the address of the cluster's DNS Service, which the kubelet was given with the flag --cluster-dns. The search line holds three suffixes built from the Pod's namespace and the cluster domain. Pod client runs in the namespace inference and the cluster domain is cluster.local, so the suffixes are inference.svc.cluster.local, svc.cluster.local and cluster.local. The options line sets ndots to 5. The C library reads this file when the program asks for a name. Everything else in this lesson follows from these three lines.

The kubelet builds the search line in a fixed order: inference.svc.cluster.local, then svc.cluster.local, then cluster.local, then the search domains of the node's own resolver file, with duplicates removed. The node's file is the one named by the kubelet flag --resolv-conf, or resolvConf in its configuration file. The nameserver line holds the cluster DNS address and nothing else. The node's own nameservers are left out on purpose, so every name a Pod asks for, inside the cluster or outside it, goes to the cluster's DNS server first. The options line comes from a constant in the kubelet's source that holds the single value ndots:5.

The manual page of resolv.conf gives ndots a default of 1, and glibc caps any value at 15. Kubernetes raises it to 5. The Kubernetes guide Debug Services, in its section on DNS, gives the reason: 5 is high enough to cover every DNS name that Kubernetes itself generates, so each of those names is completed from the search list. The cost of that choice for names outside the cluster is the subject of a later chapter.

If the kubelet was started without a cluster DNS address, a Pod with ClusterFirst still starts. The kubelet falls back to the policy Default and records a Warning event with the reason MissingClusterDNS, on the node and on the Pod. Its message reads: kubelet does not have ClusterDNS IP configured and cannot create Pod using "ClusterFirst" policy. Falling back to "Default" policy. Such a Pod gets the node's resolver file and cannot resolve any Service name.

Chapter 2 of 15

Why the short name works

Fewer than five dots means the search list goes first

The resolver counts the dots in the name. A name with fewer dots than ndots is tried with each search suffix in turn, and as written only after those. The name web has no dots, so the first full name is web.inference.svc.cluster.local. That is how every Service is named: the Service, its namespace, the label svc, then the cluster domain. The first try succeeds, and this is why a short name works from any Pod in the same namespace. A Pod in another namespace has a different first suffix. It has to ask for web.inference, which fails with its first suffix and succeeds with the second, svc.cluster.local. When a program asks for any address family, the glibc resolver sends two queries for each name it tries, in parallel: type A for an IPv4 address and type AAAA for an IPv6 address. Each query for this name is 49 bytes of DNS.

Whether the AAAA query goes out depends on the program and on the Pod. getaddrinfo asks for both families when its hints say AF_UNSPEC, and a call with no hints at all means AF_UNSPEC. For a call with no hints glibc also assumes the flag AI_ADDRCONFIG, which according to the manual page returns IPv6 addresses only if the system has an IPv6 address configured, and does not count the loopback address. In a Pod that has only an IPv4 address, such a call may send only the A query, and every count of queries in this lesson halves. A program that asks for AF_INET sends only A queries as well. This lesson counts both queries, which is what a Pod with an IPv6 address, or a program that asks for both families without AI_ADDRCONFIG, sends.

The size of a query follows from its name. A DNS query is a 12 byte header, the name written as labels, and 4 bytes for its type and class. A label is one length byte followed by its letters, and a zero byte ends the name. web.inference.svc.cluster.local has five labels with 3 + 9 + 3 + 7 + 5 = 27 letters, so the name takes 27 + 5 + 1 = 33 bytes and the query 12 + 33 + 4 = 49 bytes.

The same arithmetic prices the lookup from another namespace. A Pod in the namespace default that asks for web.inference first tries web.inference.default.svc.cluster.local. That name has six labels and 3 + 9 + 7 + 3 + 7 + 5 = 34 letters, so it takes 34 + 6 + 1 = 41 bytes and its query 12 + 41 + 4 = 57 bytes. CoreDNS answers NXDOMAIN for it and for its AAAA twin, and only then does the second suffix give web.inference.svc.cluster.local. The Pod pays two extra queries, 114 bytes, and one extra round trip. The full name with a final dot, web.inference.svc.cluster.local., is sent once as written from any namespace. Names are compared without regard to case, so WEB.Inference finds the same Service.

Chapter 3 of 15

The DNS server is a Service too

The lookup passes the same kernel rules as any other call

The query is a UDP packet to 10.96.0.10 port 53. That address is the ClusterIP of a Service named kube-dns in the namespace kube-system. The name is kept from an older DNS server. The Pods behind it run CoreDNS. So the lookup that will find the Service web first has to pass through the Service machinery itself. On node-1 the rule in KUBE-SERVICES for 10.96.0.10, UDP, port 53 matches and jumps to KUBE-SVC-TCOU7JCQXEZGVUNU. That chain picks an endpoint, and a DNAT rule rewrites the destination to the CoreDNS Pod at 10.244.1.4. Conntrack tracks UDP as well, so the answer leaves with 10.96.0.10 as its source again. The resolver expects that, because it rejects an answer from a server it did not ask. One consequence follows. A node whose kube-proxy rules are missing cannot resolve any name from its Pods, and the fault looks like a DNS problem.

The Service kube-dns that kubeadm creates has three ports, named dns for 53/UDP, dns-tcp for 53/TCP and metrics for 9153/TCP, and the selector k8s-app: kube-dns. The metrics port carries CoreDNS's Prometheus metrics, and the annotations prometheus.io/port: "9153" and prometheus.io/scrape: "true" tell a scraper to collect them. Its labels include kubernetes.io/cluster-service: "true" and kubernetes.io/name: CoreDNS. The documentation says the Service and its label keep the name kube-dns for backward compatibility with the original kube-dns server. Here the CoreDNS Pod runs on node-1, so the query is delivered across the bridge. This lesson draws one CoreDNS Pod. A real cluster runs at least two, kubeadm's Deployment spreads them across nodes, and a query that the random match sends to a second CoreDNS Pod on node-2 crosses the tunnel like any other Pod to Pod packet.

Conntrack treats UDP queries as flows. Every new combination of source address and port toward 10.96.0.10:53 needs a new entry and a new DNAT, and an entry for UDP DNS lives 30 seconds by default, the kernel setting nf_conntrack_udp_timeout. The entry sees a reply, but the current kernel gives the longer stream timeout of 120 seconds only to a flow that is still active more than 2 seconds after it began, and a query with its answer is over in milliseconds. Older kernels without that 2 second rule gave any replied entry 120 seconds, which would make the count below four times larger. The numbers add up. A Pod that makes 100 lookups a second, each from a new source port, creates at least 100 entries a second. Held for 30 seconds, that is at least 100 × 30 = 3,000 entries in the table of node-1 at any moment, from one Pod, before any connection to a model server is counted. The NodeLocal DNSCache chapter returns to this cost.

Chapter 4 of 15

CoreDNS answers from what it watches

One A record with the ClusterIP, and a time to live

CoreDNS is a DNS server built from plugins, which are listed in a file called the Corefile. The plugin named kubernetes answers for the zone cluster.local. It makes no call to the API server when a query arrives. Like kube-proxy it holds watches on Services and EndpointSlices and keeps what they deliver in memory. The query for web.inference.svc.cluster.local is answered from that memory with one A record that holds the ClusterIP, 10.96.37.204. The answer names no Pod. Choosing a Pod stays the job of the kernel rules when the client connects. The record carries a time to live, the number of seconds a client may keep it. The plugin's default is 5 seconds, and the Corefile that kubeadm installs sets 30. The AAAA query gets an answer with no records, because this Service has no IPv6 address.

CoreDNS follows a written contract, the Kubernetes DNS-Based Service Discovery specification in the kubernetes/dns repository. It defines every name in the zone and its records, and the zone even states which version of the contract it follows. A TXT query for dns-version.cluster.local returns the schema version, 1.1.0 in the specification's example. The specification also says that all comparisons between a query and the data in Kubernetes are case-insensitive.

The ttl option does more than set the time on positive answers. The kubernetes plugin accepts values from 0 to 3600 seconds, and 0 stops clients from caching at all. The same value becomes the minimum field of the zone's SOA record, and RFC 2308 tells resolvers to cache a negative answer for the smaller of that field and the SOA record's own TTL. With the kubeadm setting of 30, a caching resolver that asked for a Service before it existed may keep the NXDOMAIN for up to 30 seconds after the Service is created.

The cache plugin works differently in different versions of the default configuration. The Corefile printed on kubernetes.io ends its list with a plain cache 30, which keeps every answer for up to 30 seconds. The Corefile that kubeadm writes in its current source adds two lines inside the cache block, disable success cluster.local and disable denial cluster.local. With those, answers for Service names are never cached by CoreDNS itself and always come straight from the kubernetes plugin's memory. Only names outside the cluster are cached.

Chapter 5 of 15

Headless Services and SRV records

DNS can return Pods, and it can return ports

Some Services have no ClusterIP. Setting spec.clusterIP to None makes a headless Service. No address is allocated and kube-proxy writes no rules for it, so DNS is all it has. For a headless Service the same kind of name returns one A record for each ready Pod. If web were headless, the answer would hold 10.244.1.15 and 10.244.2.17, and the client would choose between them itself. That is one way around the limit of one Pod per connection. A gRPC client that sees every model server can open a connection to each. DNS publishes ports as well. Each named port of a Service gets an SRV record, under the port's name and protocol in front of the Service's name. For web that is _http._tcp.web.inference.svc.cluster.local, and the answer gives port 80 with the Service's own name as the target. A port with no name gets no SRV record.

An SRV record also carries a priority and a weight in front of the port. The specification leaves their values to the DNS server, and its own example answer for the API server's Service reads 30 IN SRV 10 100 443 kubernetes.default.svc.cluster.local. For a headless Service the answer holds one SRV record for each ready endpoint and each named port. With N ready Pods and M named ports there are N × M records, and each target is the Pod's own name. Each of those names has an A record of its own.

A Pod's own name comes from its hostname field, or else from an identifier that the DNS server makes up. CoreDNS uses the address with dashes, such as 10-244-1-15, or the Pod's name with the option endpoint_pod_names. A Pod gets a stable name when it sets spec.hostname and spec.subdomain and a headless Service with the subdomain's name exists in its namespace. A Pod named db-0 with hostname db-0 and subdomain db is then db-0.db.inference.svc.cluster.local. This is how StatefulSet Pods are addressed. The model server Pods come from a Deployment, have names such as qwen3-6f7d9c8b4-x7k2p that change with every new Pod, and set no hostname, so they get no stable name like this. The Pod must be ready to have a record, unless the Service sets publishNotReadyAddresses: true.

A headless Service with no ready endpoint does not return an empty list. The specification says the answer should be NXDOMAIN, as if the name did not exist, so a resolver moves on to its next search suffix. CoreDNS's option ignore empty_service does the same for ordinary Services without ready endpoints, which otherwise keep returning their ClusterIP. Order is the last detail. The loadbalance plugin in the kubeadm Corefile shuffles the order of A and AAAA records in every answer. For a headless Service that is the only spreading there is: a client that takes the first address reaches a different Pod from one lookup to the next.

Chapter 6 of 15

An outside name costs eight queries

Three suffixes fail before the real name is asked

Later the client fetches model weights from huggingface.co. That name has one dot, fewer than five, so the search list goes first. The resolver asks for huggingface.co.inference.svc.cluster.local, then huggingface.co.svc.cluster.local, then huggingface.co.cluster.local. All three lie in the zone cluster.local, so CoreDNS answers each one itself with NXDOMAIN, the code for a name that does not exist. Only then is huggingface.co asked as written. CoreDNS holds no data for it. Its forward plugin passes the query to the upstream resolvers and its cache plugin keeps the answer. Four names, each asked for A and for AAAA, make eight queries where one name was wanted. A program that asks only for IPv4, or a call that skips AAAA in a Pod with no IPv6 address, as the chapter on the short name explains, sends four. Two fixes exist. A name written with a final dot, huggingface.co., is looked up exactly as it stands. Or the Pod can lower ndots through dnsConfig in its spec.

The search list makes the cost grow with every suffix. On a cloud node whose own resolver file adds one more search domain, such as an illustrative eu-west-1.compute.internal, the kubelet appends it after the cluster's three. huggingface.co then becomes five names and ten queries, and the fourth name, huggingface.co.eu-west-1.compute.internal, lies outside cluster.local. CoreDNS cannot answer it from memory and forwards it upstream as well, so the miss costs a round trip to the upstream resolver. The model server's download waits for all of that before its first TCP packet leaves.

CoreDNS can take the walk off the client. Its autopath plugin, written as autopath @kubernetes, follows the client's search path on the server. It answers the first question with the first answer that is not NXDOMAIN, written as a CNAME from the name that was asked to the name that was found. The client would then send only its first pair of queries. autopath needs the kubernetes plugin in pods verified mode, which watches every Pod in the cluster, and the source address CoreDNS sees must be the Pod's own. The cost of the default shows in CoreDNS's metrics. The counter coredns_dns_responses_total has an rcode label, and a high share of NXDOMAIN among the answers points at names walking the search list.

Chapter 7 of 15

UDP first, TCP when the answer is too long

512 bytes, a flag named TC, and a second try

DNS tries UDP first. RFC 1035 limits a DNS message over UDP to 512 bytes. When an answer is longer, the server sends what fits and sets the TC flag, for truncated. The resolver then opens a TCP connection to the same address and asks again. Over TCP each message is prefixed with a two byte length. That is why the Service kube-dns exposes port 53 for both protocols. The limit can be worked out for a headless web. With the name written in full, an A record takes 47 bytes and nine fit. CoreDNS then turns on name compression, where a repeated name is a 2 byte pointer and a record takes 16 bytes. Now 28 records fit, in 497 bytes. A 29th Pod makes 513 bytes and sets TC. Thirty model servers behind one headless name already need TCP for every fresh lookup.

The 512 byte limit applies to a resolver that sends no EDNS option, which is the glibc default. EDNS, defined in RFC 6891, lets the client advertise a larger buffer in an OPT record of 11 bytes at the end of its query. The RFC treats any value below 512 as 512 and suggests 4096 as a starting point. In glibc the resolver option edns0 turns it on, and a Pod can set it through dnsConfig. With a 4096 byte buffer the answer for thirty Pods fits in one UDP message: 12 + 37 + 30 × 47 + 11 = 1470 bytes even with every name in full. With the log plugin turned on, CoreDNS logs the size each client advertised. The Corefile that kubeadm installs does not include log, so an operator adds it first, as the chapter on what an operator looks at shows. In the log line of a query, the field after the DO flag is the buffer size, and the value 512 there marks a client without EDNS.

RFC 1035 also fixes the limits on names. A label holds at most 63 bytes and a whole name at most 255. A Service's name, its namespace, svc and the cluster domain together must fit in that. TCP is no optional extra either. RFC 7766 says every DNS implementation must support both UDP and TCP, so a network path that carries only UDP port 53 is broken by design, even when most lookups appear to work.

Chapter 8 of 15

Other records in the zone

Reverse names, outside aliases and Pod addresses

The zone cluster.local holds more than A and SRV records. Every Service with a ClusterIP also gets a PTR record, which maps the address back to the name. The record is written under the address with its four numbers reversed and the suffix in-addr.arpa. For web that is 204.37.96.10.in-addr.arpa, which answers web.inference.svc.cluster.local. That is why the kubeadm Corefile lists the zones in-addr.arpa and ip6.arpa after cluster.local in the kubernetes line. The line fallthrough in-addr.arpa ip6.arpa below it sends reverse queries for addresses the plugin does not know on to the next plugin, forward, so a reverse lookup of an outside address still reaches the upstream resolvers.

A Service of type ExternalName has no ClusterIP, no endpoints and no rules from kube-proxy. It exists only in DNS. Its name is answered with a CNAME record that points at the name in spec.externalName, followed by that name's own address records. Suppose a Service hub in the namespace inference had externalName huggingface.co. The client could then ask for hub and be sent on to huggingface.co. The Service page warns about the catch. The HTTP Host header and the TLS server name still carry the name the client asked for, hub, and the remote server may reject a request or present a certificate for a different name. An externalName that looks like an IPv4 address is treated as a name and is not resolved.

Pods have records too. In the kubeadm Corefile the kubernetes plugin runs with pods insecure. A query for 10-244-1-12.inference.pod.cluster.local then returns the A record 10.244.1.12, taken from the name itself, without checking that such a Pod exists. The plugin's default is pods disabled, which answers NXDOMAIN to every such name. The third choice, pods verified, checks the Pod first and for that has to watch every Pod in the cluster, which costs memory in CoreDNS.

Chapter 9 of 15

The resolver's clock

Five seconds, two attempts and options per Pod

The C library in the container decides how long a lookup may take. glibc waits for an answer for the timeout given in resolv.conf, which defaults to 5 seconds and is capped at 30. It sends each query up to attempts times, 2 by default and at most 5. It uses at most 3 nameservers, tries them in the order listed and moves to the next one only after a timeout. The option rotate spreads queries over them in turn. A Pod with ClusterFirst has a single nameserver, 10.96.0.10. If one of its queries is lost, the resolver waits the full 5 seconds before it sends that query again. A single lost packet therefore turns a lookup of a millisecond into one of about 5 seconds.

The NodeLocal DNSCache page names one way such packets get lost: races in conntrack, tracked as Kubernetes issue 56903. glibc sends the A and AAAA queries in parallel, and both need conntrack entries and a DNAT on the way to a CoreDNS Pod. The same page quotes DNS timeouts of up to 30 seconds in the worst cases. The resolver's own options offer workarounds that a Pod can set through dnsConfig. single-request, since glibc 2.10, sends the A and AAAA queries one after the other. single-request-reopen, since glibc 2.9, deals with network equipment that sends back only one of the two replies. The resolver normally sends the A and AAAA queries from the same socket. With this option, when two requests from the same port are not handled correctly, it closes that socket and opens a new one before it sends the second request. use-vc, since glibc 2.14, forces TCP. no-aaaa, since glibc 2.36, stops AAAA queries altogether.

Alpine and other images built on the musl C library behave differently in four ways. musl sends a query to all nameservers in parallel and takes whichever answer comes first. A name with at least ndots dots is tried only as written, never with the search list, where glibc falls back to the search list if the name is not found. musl ignores a search line longer than 256 characters. And it had no DNS over TCP until version 1.2.4, which is the reason for the Kubernetes advice to use Alpine 3.18 or later.

Chapter 10 of 15

Four policies and the limits of the file

dnsPolicy, dnsConfig and what the kubelet refuses to write

ClusterFirst is one of four values of spec.dnsPolicy. Default, despite its name, is not the default. It makes the Pod inherit the resolver configuration of its node, so the Pod can resolve outside names but no Service names. ClusterFirst is what a Pod gets when it names no policy, and it gives the file this lesson started with. ClusterFirstWithHostNet is for Pods that run in the node's network namespace with hostNetwork: true. Such a Pod with plain ClusterFirst falls back to the behaviour of Default and loses Service names, and the kubelet's code makes the same choice. None ignores the cluster's settings, and the whole file then comes from spec.dnsConfig, which must hold at least one nameserver.

dnsConfig has three lists. nameservers, at most 3, are added to those of the policy. searches are merged into the policy's search list. options, each a name with an optional value, are merged with the policy's options. The documentation's example sets ndots to 2 and adds edns0, and the Pod's file ends with the line options ndots:2 edns0. For a model server that mostly calls names outside the cluster, a lower ndots saves the failed suffix queries on every lookup.

The kubelet enforces limits on what it writes: at most 3 nameservers, at most 32 search domains and at most 2048 characters in the search line. The 32 and 2048 limits are stable since Kubernetes 1.28. When the merged list is longer, the kubelet cuts it and records a Warning event with the reason DNSConfigForming, with a message that begins Search Line limits were exceeded, some search paths have been omitted. For the node's own file the reason is CheckLimitsForResolvConf. Older software has smaller limits. glibc 2.25 and earlier used only six search domains with 256 characters in total. The resolv.conf manual page records that limit and says the search list has had no limit since glibc 2.26, so the old limit matters only in images built on an older glibc. containerd 1.5.5 or earlier and CRI-O 1.21 or earlier left Pods with too many search domains pending.

Chapter 11 of 15

The Corefile that kubeadm installs

Ten plugins, a Deployment and the right to watch

CoreDNS reads its configuration from a ConfigMap named coredns in kube-system, under the key Corefile. The file that kubeadm writes has one server block, .:53, which serves every zone on port 53. Its plugins in order are errors, health with lameduck 5s, ready, kubernetes, prometheus on :9153, forward, cache, loop, reload and loadbalance. The kubernetes plugin serves cluster.local, in-addr.arpa and ip6.arpa with pods insecure, fallthrough for the reverse zones and ttl 30. forward sends everything else to the servers in /etc/resolv.conf, with max_concurrent 1000. cache 30 caches for at most 30 seconds, and in the current kubeadm source it is told not to cache successes and denials for cluster.local. The other plugins are covered in the chapters that follow.

The Deployment carries the label k8s-app: kube-dns, which is what the Service selects, and runs with priorityClassName: system-cluster-critical, so the scheduler favours it over ordinary Pods. Each Pod requests 100m of CPU and 70Mi of memory, with a memory limit of 170Mi. A preferred anti-affinity on kubernetes.io/hostname spreads the Pods across nodes. The container exposes 53/UDP, 53/TCP and 9153/TCP for metrics. Its liveness probe asks /health on port 8080, starting after 60 seconds and failing after 5 misses. Its readiness probe asks /ready on port 8181.

Two settings matter more than they look. The CoreDNS Pods run with dnsPolicy: Default, so their own /etc/resolv.conf is the node's file, and forward . /etc/resolv.conf sends outside names to the node's upstream resolvers. And the ClusterRole system:coredns grants list and watch on endpoints, services, pods and namespaces, and on endpointslices in the group discovery.k8s.io. Without the rule for EndpointSlices the watches fail, and the debugging guide shows the result: every query ends in SERVFAIL.

Chapter 12 of 15

Outside names: forward and cache

Random upstreams, two second timeouts and a cap of 30 seconds

For huggingface.co the forward plugin does the work. It reads its upstream servers from /etc/resolv.conf, at most 15 of them, and by default picks among them at random. It keeps connections to them open and expires them after 10 seconds. It waits 2 seconds for an answer, the setting read_timeout, before it tries another upstream. When an upstream returns an error, forward starts probing it every 0.5 seconds with a query for the root zone's NS records. Two failed probes in a row, the setting max_fails, mark it down. If all upstreams are down, forward assumes its health checks have failed and sends to a random upstream anyway.

The kubeadm Corefile sets max_concurrent 1000. A query that would push the number of queries in flight to the upstreams above 1000 gets an immediate REFUSED, counted in coredns_forward_max_concurrent_rejects_total. The plugin's documentation estimates about 2 kB of memory for each query in flight, so the cap holds that memory near 1000 × 2 kB = 2 MB, well inside the Pod's 170Mi limit. forward keeps the client's protocol, UDP for UDP and TCP for TCP, unless force_tcp or prefer_udp says otherwise.

The cache plugin keeps the answer. The 30 in cache 30 caps the time at 30 seconds, and that cap never extends a record's own TTL. If huggingface.co came back with an illustrative TTL of 300, CoreDNS keeps it for 30 seconds and tells clients 30. An answer with a TTL of 10 is kept 10 seconds. A separate floor does extend short records. The minimum cache duration, MINTTL, defaults to 5 seconds, so an answer with a TTL of 2 seconds is still kept for 5. It can be set apart for answers and for denials, as the last value of the success and denial lines inside the cache block. A SERVFAIL is cached for 5 seconds. Without a cap the maximum would be 3600 seconds for answers and 1800 for denials. The cache holds 256 shards of 39 items, 9984 entries for each type of answer, and evicts at random when full. A zone can also be sent to its own servers with an extra server block, a stub domain, such as consul.local:53 with its own forward line.

Chapter 13 of 15

How CoreDNS starts, stops and loops

Five seconds to sync, five seconds of lame duck, and a loop that kills it

CoreDNS needs its watches before it can answer for the cluster. When it starts, the kubernetes plugin delays serving for up to 5 seconds while it connects to the API server and synchronises its watches, the option startup_timeout. If that takes longer, CoreDNS starts serving anyway and answers SERVFAIL for any record it has not received yet. The ready plugin keeps the Pod out of the Service meanwhile. /ready on port 8181 returns 503 with the list of plugins that are not ready, the kubernetes plugin among them until its sync is done, so the Pod's readiness probe fails and its endpoint stays out of the kube-dns EndpointSlice.

Shutdown runs the other way round. lameduck 5s delays the end of the process by 5 seconds. During that time /health still answers 200, so the liveness probe passes, but the ready plugin stops answering OK. The Pod leaves the Service's endpoints while it can still answer queries that are already on their way.

Changes to the Corefile are picked up by the reload plugin. It checks the file every 30 seconds with up to 15 seconds of random jitter and compares a checksum, SHA512 in the current source and MD5 in the log line the debugging guide shows from an older release. A file with an error is rejected, CoreDNS keeps its old configuration and logs the error. The Kubernetes page says to allow two minutes for an edit to take effect.

The best known failure is a loop. CoreDNS forwards outside names to the servers in the node's resolver file. If that file names a resolver on the loopback address, as systemd-resolved does with 127.0.0.53, CoreDNS forwards its queries to itself. The loop plugin catches this. At start it sends itself a query of type HINFO for a random name, and if it sees that query more than twice, it halts the process. The Pod then sits in CrashLoopBackOff. The fix is to give the kubelet the real file with --resolv-conf, for systemd-resolved /run/systemd/resolve/resolv.conf. kubeadm detects systemd-resolved and sets that flag itself.

Chapter 14 of 15

A DNS cache on every node

NodeLocal DNSCache skips the DNAT and the conntrack entry

NodeLocal DNSCache moves a caching DNS server onto every node. It runs as a DaemonSet named node-local-dns in kube-system, built from CoreDNS. Pods reach it on a link-local address, which the documentation recommends taking from 169.254.0.0/16, and it runs on the same node as the Pod. The query therefore needs no DNAT rule and no conntrack entry. The documentation lists the reasons. It avoids the conntrack races of issue 56903 and UDP entries for DNS that fill the table while they wait 30 seconds to expire. The documentation says the connections from the cache to CoreDNS can be upgraded to TCP, whose conntrack entries are removed when the connection closes. The published manifest does that. Its Corefile sets force_tcp on the forward for the zones cluster.local, in-addr.arpa and ip6.arpa, so misses for those names always go over TCP. They do not go to the kube-dns Service itself, because in iptables mode the cache has taken over that address. The manifest adds a second Service, kube-dns-upstream, with the same selector k8s-app: kube-dns, and starts the cache with -upstreamsvc kube-dns-upstream. Misses go to that Service's ClusterIP and from there to the CoreDNS Pods. Names outside the cluster go to the upstream servers that the node-local-dns Pod fills in for the placeholder __PILLAR__UPSTREAM__SERVERS__, and that forward has no force_tcp. And it cuts the DNS timeouts of up to 30 seconds, three retries with a 10 second timeout in the page's words, that follow a lost UDP packet.

How Pods find it depends on the kube-proxy mode. In iptables mode the node-local Pods listen on both the link-local address and the kube-dns ClusterIP, 10.96.0.10, so the kubelet's --cluster-dns can stay as it is and every Pod's resolv.conf is unchanged. In ipvs mode they can listen only on the link-local address, and --cluster-dns must be changed to that address. A model server Pod on gpu-node-1 then resolves names from a cache on its own node, and CoreDNS sees only the misses from each node.

For the numbers in this lesson this removes the per-lookup conntrack entries on the client's node. The 3,000 entries held by a Pod making 100 lookups a second disappear from node-1's table, and the misses that still go to CoreDNS share a few TCP connections. The scene in this lesson has no place for the node-local cache. In the beats below it is drawn at the kernel of node-1, where it intercepts the query.

Chapter 15 of 15

What an operator looks at

Three kubectl commands, a log line and port 9153

The debugging guide starts with three checks. kubectl get pods --namespace=kube-system -l k8s-app=kube-dns shows whether the CoreDNS Pods run. kubectl get svc --namespace=kube-system shows the Service, in the guide's example the line kube-dns ClusterIP 10.0.0.10 <none> 53/UDP,53/TCP. A cluster built with kubeadm lists a third port as well, 9153/TCP for metrics. kubectl get endpointslice -l kubernetes.io/service-name=kube-dns --namespace=kube-system shows whether the Service has ready endpoints. Then a test Pod runs nslookup kubernetes.default. A working cluster prints the server 10.96.0.10 and the address of the kubernetes Service. A broken one prints nslookup: can't resolve 'kubernetes.default'.

To see the queries themselves, add the log plugin to the Corefile with kubectl -n kube-system edit configmap coredns. Each query then produces one line in a fixed format: the client's address and port, the query ID, then in quotes the type, class, name, protocol, size, DO flag and buffer size, then the response code, the response flags, the response size and the time taken. A tc among the flags marks a truncated answer, the case from the chapter on UDP and TCP. The guide's sample, from 2018, reads 172.17.0.18:41675 - [07/Sep/2018:15:29:11 +0000] 59925 "A IN kubernetes.default.svc.cluster.local. udp 54 false 512" NOERROR qr,aa,rd,ra 106 0.000066649s. It is older than the format the log plugin's README gives today, which has no timestamp between the dash and the query ID. Its flags also include ra, recursion available. The kubernetes plugin's answers in this lesson carry qr, aa and rd, and the flags a current CoreDNS prints are the ones its answer actually carries.

The prometheus plugin serves metrics on port 9153 at /metrics. coredns_dns_requests_total counts queries by server, zone, protocol, family and type. coredns_dns_responses_total counts answers by response code and plugin, and the share of NXDOMAIN there shows what the search list costs. coredns_dns_request_duration_seconds gives latency, coredns_cache_hits_total and coredns_cache_misses_total the cache's work, and coredns_forward_requests_total and coredns_forward_healthcheck_broken_total the state of the upstreams. A rise in coredns_health_request_duration_seconds is, in the health plugin's words, a sign that CoreDNS is having trouble keeping up with its query load.

What to keep

A file, a list, a watch and a record

A name becomes an address in four steps. The kubelet gives each Pod a resolver file with the DNS Service's address, three search suffixes and ndots:5. The resolver tries the suffixes first for any name with fewer than five dots, which makes web work and makes huggingface.co cost eight queries when A and AAAA are both asked. The questions travel to 10.96.0.10 through the same kernel rules as every Service. CoreDNS answers from what it watches: the ClusterIP for an ordinary Service, the Pod addresses for a headless one, and ports through SRV records. Answers over 512 bytes come back truncated and are fetched again over TCP. Around that path sit the parts that decide how it behaves under load: the resolver's 5 second timeout, the dnsPolicy and its limits, a Corefile with ten plugins, forward and cache for outside names, a loop check that can stop CoreDNS cold, and a node-local cache that takes DNAT and conntrack out of the way.
