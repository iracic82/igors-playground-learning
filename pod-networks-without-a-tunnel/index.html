Kubernetes underneath

Pod networks without a tunnel

How Calico routes a Pod's packet with BGP, and what the network must know in return

The lesson "A packet between two nodes" sent a SYN from Pod client at 10.244.1.12 to Pod web-2 at 10.244.2.17 inside a VXLAN tunnel, at a cost of 50 bytes in every packet. This lesson sends the same SYN with no tunnel. The cluster now runs Calico as its network plugin, with encapsulation turned off. Each node runs a routing daemon that tells the other nodes which block of Pod addresses it holds, one route for the whole block and none for single Pods. It uses BGP, the protocol that routers on the internet use. The packet then crosses the switch exactly as the Pod built it. You will see what is announced, the route that appears in the kernel, the 74 byte frame on the wire, and what this design demands from the network between the nodes.

Chapter 1 of 16

A routing daemon instead of a tunnel

A pool that wraps nothing, and BIRD to announce each node's block

Calico keeps Pod addresses in a resource called an IPPool. This cluster's pool is 10.244.0.0/16 with ipipMode Never and vxlanMode Never, the default of both fields, so nothing is encapsulated. Calico gives each node a block from the pool: 10.244.1.0/24 to node-1 and 10.244.2.0/24 to node-2. The default block is a /26, and this pool was created with blockSize 24 to match the earlier lessons. On every node the calico-node Pod runs BIRD, an open source routing daemon, and confd, which writes BIRD's configuration from Calico's datastore. For node-1 that configuration holds a blackhole route for the block and a filter that announces the block and nothing beneath it. Peers learn one fact: 10.244.1.0/24 is behind 10.0.1.11. Calico uses no bridge. Each Pod's cable ends in a routed interface on the node, with one route for each Pod.

The word default needs care. Never is the default of the IPPool resource's ipipMode and vxlanMode fields. A typical install does not leave it there. The operator's Installation resource defaults a pool's encapsulation to IPIP, and Calico's stock manifest sets CALICO_IPV4POOL_IPIP to Always and CALICO_IPV4POOL_VXLAN to Never. So a cluster without a tunnel is one where someone asked for it, by creating the pool with both modes set to Never or by setting encapsulation to None in the Installation.

The blackhole route is the node's claim on its whole block. confd turns each block that belongs to the node into a line route 10.244.1.0/24 blackhole in BIRD's static protocol, and BIRD exports the block from there. The export filter has three parts. It accepts the block itself. It accepts a more specific route inside the block only if its metric is below the normal route priority, which Calico uses for live migration of workloads. And it rejects every other route inside the block, so the per Pod routes never leave the node. Inside the node, the more specific /32 route for each Pod wins over the blackhole by longest prefix. An address in the block that no Pod holds matches only the blackhole and is dropped on the spot, instead of bouncing to the default route.

Chapter 2 of 16

Blocks, borrowing and the IPAM records

How Calico hands out Pod addresses without a range per node

Calico does its own address management and ignores the per node podCIDR that Kubernetes assigns. Its CNI plugin uses Calico IPAM by default. The host-local plugin from the previous lessons is possible too, and Calico's documentation says it is generally used only where the Kubernetes route controller has to be integrated. Calico IPAM keeps its state in the datastore as objects, one per block.

Each block is an IPAMBlock named after its range with dots and the slash replaced, so 10.244.1.0/24 becomes 10-244-1-0-24. Its affinity field says host:node-1. Its allocations list has one entry per address, and null means free. Its unallocated list holds the free positions. Calico assigns from the front of that list and returns freed positions to the end, so a freed address is not reused at once. The documentation warns not to edit these objects, and calicoctl get does not show them.

A node can run out of addresses in its block. It then claims another block from the pool. If the pool has no free blocks left, the node borrows addresses from a block that belongs to another node. That works, and it costs routes: a borrowed address needs its own /32 route announced from the borrowing node, because the block's owner announces the whole block. The documentation therefore recommends at least as many blocks in the pool as there are nodes. IPAMConfiguration controls this behaviour. strictAffinity, false by default, forbids borrowing when set to true. maxBlocksPerHost caps how many blocks one node may hold. Calico's sources disagree on its default. The IPAMConfiguration reference page lists 20. The v3 API source defaults the field to 0 and says the cap applies only when it is not zero, which means no limit. An operator who relies on a cap should set the field explicitly and read it back with kubectl get ipamconfigurations -o yaml.

The pool reports on itself in current releases. Since Calico 3.32 an IPPool has status conditions. Allocatable is True with the reason OK in normal operation, and False with CIDROverlap, PoolDisabled or Terminating when something is wrong. AddressSpaceNearlyFull turns True with the reason ThresholdExceeded when at least 80 percent of the pool's addresses are in use or reserved. calicoctl ipam show prints the totals per pool and, with --show-blocks, per block.

Chapter 3 of 16

The Pod's side of the cable

A fake gateway, a fixed MAC address and one route per Pod

Calico's CNI plugin builds the cable differently from the bridge plugin. Inside the Pod it first adds a route to 169.254.1.1/32 with link scope on eth0. The source code calls that address a dummy next hop: a link scope route makes it directly reachable, so the plugin can then add the default route via 169.254.1.1. No device anywhere holds that address. It exists only as a next hop for the Pod's routing table.

On the node side the cable gets a name and a MAC address that never change. The name is the interface prefix cali, followed by the first 11 hex characters of the SHA-1 hash of the Pod's namespace and name joined by a dot. The same Pod name in the same namespace always gives the same interface name. The MAC address of every node side end is ee:ee:ee:ee:ee:ee. The plugin sets it on purpose and retries for up to 5 seconds. If that fails it keeps the kernel's address and logs a warning. Because the address is the same for every Pod's cable, the neighbour entry inside each Pod for 169.254.1.1 always reads ee:ee:ee:ee:ee:ee.

Four settings make the node side work. proxy_arp is 1, so the node answers the Pod's ARP request for 169.254.1.1 with its own MAC address. proxy_delay is 0, because the kernel normally waits a little before it answers proxy ARP. forwarding is 1 on that interface, so packets from the Pod may be routed. route_localnet is 1. Then the plugin adds one route on the node for the Pod's address, 10.244.1.12 dev followed by the cali name, with link scope. If such a route already exists on another interface, the plugin fails with an error that says the route already exists for an interface other than the one it expected.

Other software can get in the way. Calico's troubleshooting page asks NetworkManager hosts to mark cali*, tunl* and vxlan.calico interfaces as unmanaged in /etc/NetworkManager/conf.d/calico.conf, because NetworkManager can interfere with Calico's routing.

Chapter 4 of 16

Two nodes become BGP peers

A TCP connection to port 179 inside one autonomous system

BGP runs between two routers over a TCP connection to port 179. Each side sends an OPEN message with its autonomous system number, and KEEPALIVE messages confirm the session. An autonomous system, or AS, is a set of routers under one administration. Calico puts every node in AS 64512 unless you configure another number. 64512 is the first AS number that RFC 6996 reserves for private use. Two peers in the same AS speak internal BGP. Once the session is established, each BIRD sends UPDATE messages. One UPDATE from node-2 carries the prefix 10.244.2.0/24 and the attribute NEXT_HOP with the value 10.0.1.12. Nobody configured this session. Calico's default is a full mesh, in which every node peers with every other node. With two nodes that is one session.

Which node dials matters when a session will not come up. Calico makes every mesh session one directional to avoid a race in which both sides connect at the same moment. On each node, confd marks a mesh peer as passive when the peer's address is greater than the node's own, and a passive BIRD never opens the connection itself. node-1 at 10.0.1.11 is passive towards 10.0.1.12, so node-2 opens the TCP connection to node-1's port 179. A capture on node-1 shows the SYN arriving from 10.0.1.12.

After the OPEN messages both sides confirm with a KEEPALIVE and the session enters the state Established. Calico does not set the hold time for mesh sessions, so BIRD's defaults apply. BIRD prefers a hold time of 240 seconds and sends keepalives at one third of it, every 80 seconds between two BIRDs. RFC 4271 suggests 90 seconds and requires a hold time of zero or at least three seconds. If no message arrives within the hold time, the session drops with a NOTIFICATION and the routes learned over it are withdrawn.

Chapter 5 of 16

Inside BIRD's configuration

What confd writes and why each line is there

BIRD reads a configuration file that confd generates from templates every time something relevant changes in the datastore. Three parts of it shape this lesson. The kernel protocol connects BIRD to the node's routing table. It has learn, so BIRD sees routes other programs wrote. It has persist, which the template comments as do not remove routes on BIRD shutdown. It has scan time 2, so BIRD rereads the kernel table every 2 seconds, graceful restart, and merge paths on, which allows routes with several next hops. The device protocol also scans interfaces every 2 seconds.

The direct protocol takes addresses from interfaces, and its pattern is -"cali*", -"kube-ipvs*", "*". The cali interfaces are excluded, because their routes are handled per Pod. kube-ipvs0 is excluded because, in the template's words, that interface gets an address for every cluster IP in use, which would flood BGP with Service addresses.

Every BGP session uses the same template. local as sets 64512. gateway recursive tells BIRD to resolve the next hop through the routing table. add paths on lets a peer send more than one path for a prefix. connect delay time 2, connect retry time 5 and error wait time 5,30 make reconnects fast. BIRD's own defaults are 5 seconds, 120 seconds and 60 to 300 seconds, so Calico cuts the wait after a failure from minutes to seconds.

The router id defaults to the node's IPv4 address, 10.0.1.11 on node-1. The variable CALICO_ROUTER_ID can set another address, or hash to derive one from the node's name. Mesh sessions are named after the peer's address with underscores, so node-1's session to node-2 is Mesh_10_0_1_12. Sessions from BGPPeer resources are named Node_ or Global_ followed by the address, which is how calicoctl node status tells the kinds apart.

Chapter 6 of 16

The route lands in the kernel

One line of ip route, marked proto bird

BIRD writes each route it accepts into the kernel's routing table. On node-1 the new entry reads 10.244.2.0/24 via 10.0.1.12 dev eth0 proto bird. Compare it with the route flannel wrote in the VXLAN lesson: 10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink. That route pointed at a tunnel device, and it needed a neighbour entry and a forwarding entry to find node-2. This route names node-2's real address and the real network card. Nothing else is needed, because 10.0.1.12 is in the node's own subnet and ordinary ARP finds it. The words proto bird record which program installed the route. If BIRD stops, the route stays. Calico's configuration tells BIRD to leave its routes in place on shutdown, so traffic keeps flowing while the daemon restarts.

The label proto bird is a number in the kernel. Each route carries a protocol field, and iproute2's table rt_protos gives names to the numbers: 3 is boot, 4 is static and 12 is bird. Felix writes the per Pod routes on the node with protocol 3, its DeviceRouteProtocol default. BIRD's routes carry 12. That is how each program recognises its own routes and leaves the others alone.

The route on node-1 points at 10.0.1.12 directly, and gateway recursive is why that works. BIRD resolves the next hop from the UPDATE through the routing table, finds that 10.0.1.12 is on eth0's own subnet and writes the route with eth0 as the device. If node-2 were behind a router, recursive resolution would find the router instead, which is the situation a later chapter returns to. The route is an ordinary kernel route in every other way. It appears in ip route, and any process on node-1 can use it, the kubelet's health checks included.

Chapter 7 of 16

Who owns which route

BIRD, Felix and the kernel each write some of the table

Three programs write routes on a Calico node, and the table only makes sense once you know which wrote what. ip route on node-1 shows four kinds. The node's own subnet, 10.0.1.0/24 dev eth0 proto kernel, comes from the kernel when the address was configured. 10.244.1.12 dev followed by a cali name, with link scope, is a Pod route that Felix and the CNI plugin keep. blackhole 10.244.1.0/24 proto bird is the block claim from BIRD's static protocol. 10.244.2.0/24 via 10.0.1.12 dev eth0 proto bird is the route learned from node-2.

Felix watches its routes and repairs them. RouteRefreshInterval, 90 seconds by default, sets how often it rereads the table to check. RemoveExternalRoutes, true by default, lets it delete routes on its interfaces that it did not write. RouteSource, CalicoIPAM by default, says that Felix takes the list of local Pod addresses from Calico's IPAM. IPForwarding, Enabled by default, makes Felix turn on forwarding for the node.

Who programs the routes to other nodes depends on configuration and version. BGPConfiguration has a field programClusterRoutes with the values Disabled, EnabledNoEncapOnly, EnabledIPIPOnly and Enabled, and its default, EnabledNoEncapOnly, keeps BIRD responsible for pools without encapsulation, which is this lesson's case. The operator calls the same choice clusterRoutingMode, BIRD by default or Felix. With Felix programming the routes, BGP is no longer needed for routing inside the cluster, and Calico still uses it to announce routes to external peers. For IP in IP pools the picture is in motion. The overlay page says BGP distributes those routes. Current source makes Felix's ProgramClusterRoutes default EnabledIPIPOnly, and confd marks BIRD's handling of IP in IP routes as deprecated since version 3.33.

BIRD's own view is available through birdcl inside the calico-node container, which talks to the socket /var/run/calico/bird.ctl. show route lists the blackhole from static1, each Pod's /32 from the kernel protocol, and the remote block with the session it came from, Mesh_10_0_1_12.

Chapter 8 of 16

The packet is routed once and leaves as it is

No bridge, no tunnel device, one routing decision

A minute later the client connects to 10.244.2.17 port 8080. Inside a Calico Pod the routing table has one exit: default via 169.254.1.1 dev eth0. No interface holds that link-local address. Calico sets the proxy_arp flag on the node end of the Pod's cable, so the node answers the Pod's ARP request for 169.254.1.1 itself. The 74 byte SYN arrives in node-1's network namespace, and the node routes it. The longest matching prefix is 10.244.2.0/24 via 10.0.1.12 dev eth0. Routing lowers the time to live from 64 to 63. The node finds the MAC address of 10.0.1.12 with ARP and writes a new Ethernet header, from its own network card to node-2's card. It adds no other header.

The ARP exchange inside the Pod is short because of the settings on the node end. The client asks who has 169.254.1.1. proxy_arp makes the node answer for an address it does not hold, and proxy_delay 0 removes the kernel's usual pause before such an answer. The reply carries ee:ee:ee:ee:ee:ee, so the SYN leaves the Pod addressed to that MAC address. That address belongs to the node end of the client's own cable, so the frame goes straight up into node-1's IP layer, with no bridge and no forwarding table in between.

On node-1 the packet arrives on the client's cali interface, where forwarding is 1. The route lookup has two candidates, the blackhole for 10.244.1.0/24 and the learned 10.244.2.0/24, and only the second covers 10.244.2.17. The node's ARP entry for 10.0.1.12 is the same entry it uses for any traffic to node-2, such as the BGP session itself, so it is almost always present already.

Chapter 9 of 16

What the switch sees now

Pod addresses in the only IP header, node MAC addresses around it

The frame on the wire is 74 bytes. In the VXLAN lesson the same SYN was 124 bytes, because 50 bytes of outer headers went around it. Here the Ethernet header carries the MAC addresses of the two nodes' network cards, and the single IP header carries 10.244.1.12 and 10.244.2.17. The switch forwards on the destination MAC address as before, and its table still holds node addresses only. Everything that reads the IP header now sees Pods. A firewall on the path can filter on Pod addresses and on the real port, 8080. A capture on the switch shows the connection with no tunnel to decode. Calico's documentation puts it this way: the packet that leaves your workload is the packet that goes on the wire. Node-2 routes the packet to web-2's interface, and web-2 sees 10.244.1.12.

Node-2's side mirrors node-1's. The packet arrives on eth0 with destination 10.244.2.17. The route 10.244.2.17 dev followed by web-2's cali name, with link scope, matches with all 32 bits and beats the blackhole of node-2's own block. node-2 lowers the time to live to 62, writes an Ethernet header from ee:ee:ee:ee:ee:ee to web-2's MAC address and sends the frame into web-2's cable.

For anyone who has to debug, this is the biggest difference from the tunnel. tcpdump on node-1's eth0 with the filter host 10.244.2.17 and port 8080 shows the SYN, the SYN-ACK and every data packet without any decoding. A mirror port on the switch shows the same. Flow records from the network, such as sFlow or NetFlow exports, list Pod addresses, so a network team can see which Pods talk to which model servers. With VXLAN the same records show only the two node addresses and UDP port 8472.

Chapter 10 of 16

What the network must do in return

The nodes must be neighbours, or the routers must know the Pod routes

The route on node-1 works because 10.0.1.12 is a neighbour on the same layer 2 segment. Node-1 can put node-2's MAC address on the frame, and no device in between reads the IP header to make a decision. Place a router between the nodes and that changes. The router receives a packet for 10.244.2.17, and it can forward the packet only if it holds a route for that address. So a routed network needs the Pod routes too. A cloud network adds a second obstacle. On AWS every instance performs a source and destination check by default: the instance must be the source or destination of any traffic it sends or receives. A packet from 10.244.1.12 fails that check and is dropped until the check is disabled on each node. Calico's agent Felix can disable it for you.

The documentation gives the cloud details. On AWS the check can be turned off in the console under Actions, Networking, Change source/destination check, by choosing Stop. Calico's AWS page says that disabling the check is enough within one VPC subnet. Across subnets, availability zones or peered VPCs, the nodes are no longer one layer 2 segment, and Calico points to IP in IP in CrossSubnet mode with outgoing NAT. Calico also notes that it avoids the AWS limit of 50 entries in a route table, because it does not need one route per node in the VPC's table.

The same problem has a general form. Kubernetes' own alternative to BGP is the cloud route controller, which the cloud controller manager runs and which writes a route for each node's Pod range into the cloud's routing table. Either the nodes' network learns the routes, from BGP or from a controller, or the Pods' packets have to be wrapped. The Kubernetes network model only requires that every Pod has a unique cluster wide address and that Pods reach each other without NAT. It leaves the choice of mechanism to the network plugin.

Chapter 11 of 16

What an operator checks

Node status, readiness and BIRD's own answers

calicoctl node status is the first command, and it must run on the node itself, because it asks the local calico-node. It shows Calico process is running and a table of IPv4 BGP peers with the columns PEER ADDRESS, PEER TYPE, STATE, SINCE and INFO. On node-1 a healthy mesh prints one row: 10.0.1.12, node-to-node mesh, up, the time the session started, Established. Any other value in INFO, such as Active or Connect, means the session is not up.

The same information is available through the API as a CalicoNodeStatus resource. Its spec names a node, the classes to report, Agent, BGP and Routes, and updatePeriodSeconds, between 0 and 86400. Its status shows agent.birdV4.state Ready, bgp.numberEstablishedV4 and numberNotEstablishedV4, and a list peersV4 with peerIP, state, since and type NodeMesh. It works on Linux nodes only.

The calico-node Pod checks BIRD for Kubernetes. Its liveness probe runs calico-node -felix-live -bird-live every 10 seconds, after an initial 10, and allows 6 failures. Its readiness probe runs calico-node -felix-ready -bird-ready every 10 seconds. The readiness check talks to BIRD over /var/run/calico/bird.ctl, and the probe gives the whole check 10 seconds, its timeoutSeconds in the manifest. The current manifest on Calico's main branch spells the same probe calico component node health --felix-ready --bird-ready. A node with no peers is ready. Right after start, every peer must be Established, which stops a rolling update from moving on before BGP is back. After that one Established peer is enough. When it fails, kubectl describe shows a message of the form calico/node is not ready: BIRD is not ready: BGP not established with 10.0.1.12.

Calico's troubleshooting page names the pattern to look for. If Pods can reach each other on one host and can reach the internet, but cannot reach Pods on other hosts, the problem is probably in the BGP configuration. Check calicoctl node status on each host, check IP connectivity between the hosts, and check that TCP port 179 is open.

Chapter 12 of 16

When a session fails

The BGP state machine, its error codes and what happens to the routes

RFC 4271 describes a BGP session as a state machine with six states. Idle refuses connections. Connect waits for the TCP connection to complete. Active retries after a failed attempt. OpenSent has sent an OPEN and waits for the peer's. OpenConfirm has received it and waits for a KEEPALIVE. Established is the only state in which UPDATE messages may be exchanged. calicoctl node status and CalicoNodeStatus print these names, so a session stuck in Active or Connect points at TCP. A session that sits in OpenSent has sent its OPEN and never received the peer's, so the TCP connection works and the peer is not answering at the BGP level. A mismatched AS number looks different. The peer that receives the wrong AS in the OPEN sends a NOTIFICATION with error code 2, subcode 2, Bad Peer AS, and closes the connection. The session falls back to Idle or Active and tries again, and BIRD shows the received error next to the state.

When something goes wrong after the session is up, the side that notices sends a NOTIFICATION and closes the connection. Its error code says why. 1 is a message header error, 2 an OPEN message error, 3 an UPDATE message error, 4 hold timer expired, 5 a state machine error and 6 cease, which covers administrative shutdowns. The smallest messages are 19 bytes for a KEEPALIVE, 23 for an UPDATE and 29 for an OPEN.

What happens to the routes depends on how the session ends. Graceful restart, RFC 4724, covers a session that drops without a Cease NOTIFICATION, as when BIRD's process is killed or restarted without closing its sessions. Then node-1 keeps node-2's routes marked as stale for up to the restart time, 120 seconds by BIRD's default, and BIRD's persist option leaves node-2's own routes in its kernel, so traffic keeps flowing while node-2's BIRD comes back. A shutdown that does send a Cease is different. Under RFC 4724 node-1 then deletes node-2's routes at once, unless both sides support RFC 8538, which keeps graceful restart in force for most NOTIFICATIONs. Calico's BIRD template switches graceful restart on for every session, where BIRD's own default is aware, the receiving role only. A comment in the same template warns that with a full mesh graceful restart is not guaranteed to work. Whether an upgrade of calico-node keeps the routes therefore depends on how the old BIRD stops, and it is worth testing on one node before a rollout. If node-2 dies, node-1 waits out the hold time, 240 seconds with BIRD's preferred value, before it gives up on the session and withdraws the route. During that time packets to node-2's Pods keep going to 10.0.1.12 and are lost.

That wait is the one number in this design that an operator may want to change. Calico exposes keepaliveTime and maxRestartTime on BGPPeer and nodeMeshMaxRestartTime in BGPConfiguration. The documentation warns that changing the restart time may break networking in the cluster.

Chapter 13 of 16

Mesh, route reflectors and the top-of-rack switch

Three ways to arrange the BGP sessions

A full mesh needs a session between every pair of nodes. The reason is a rule of BGP: a speaker does not pass a route learned from one internal peer on to another internal peer. For n nodes that is n(n-1)/2 sessions, which is 1 for this cluster and 4,950 for 100 nodes. Calico's documentation recommends the mesh up to about 100 nodes and route reflectors beyond that. A route reflector is a BGP speaker that is allowed to pass routes between internal peers. A few nodes take that role and peer with each other, and every other node peers with a subset of them, typically two. On your own hardware there is a third arrangement. Each node peers with its top-of-rack switch, the mesh is turned off, and the physical network learns the Pod routes. That also solves the router problem of the last chapter.

Reflection needs extra bookkeeping to avoid loops, which RFC 4456 defines. A reflector adds an ORIGINATOR_ID attribute, type code 9, holding the router id of the node that first announced the route, and prepends its cluster ID to a CLUSTER_LIST attribute, type code 10. A reflector that sees its own cluster ID in that list drops the route. RFC 4456 allows, and does not require, several reflectors that serve the same clients to share one cluster ID. With a shared ID a reflector discards routes that another reflector of its own cluster already reflected, which saves duplicate copies. Calico's documentation takes that choice and uses one unused address, such as 244.0.0.1, for all of them.

The change has a cost the documentation spells out. Giving a node a cluster ID removes it from the node to node mesh immediately, with a disruption of about 2 seconds. The guide therefore recommends dedicated reflector nodes that do not run workloads, set up before anything else. Turning off nodeToNodeMeshEnabled breaks Pod networking until replacement peerings exist, so the BGPPeer resources have to be in place first.

Chapter 14 of 16

Filters and AS numbers

Controlling what each peer hears and who speaks for whom

Once nodes peer with real routers, what they announce needs control. A BGPFilter resource holds rules in four lists, exportV4, importV4, exportV6 and importV6. Each rule matches on keys such as cidr with a matchOperator of In, NotIn or Equal, the source RemotePeers, or an interface, and names an action. Rules apply in order and the first match wins. When no rule matches, the action is Accept. A BGPPeer refers to filters by name, and they apply in the order listed.

AS numbers decide whether a session is internal or external. The private ranges from RFC 6996 are 64512 to 65534 for 2 byte numbers and 4200000000 to 4294967294 for 4 byte numbers, so Calico's default 64512 is the first private number. The AS can be changed for the whole cluster, calicoctl patch bgpconfiguration default with asNumber 64513, or for one node, calicoctl patch node node-1 with spec.bgp.asNumber 64514. A design common in data centres gives every rack its own AS, so the nodes of a rack and their top-of-rack switch form one AS and the switches speak external BGP to the spine.

BGPPeer has more fields for real networks. password or secretKeyRef sets the TCP MD5 password. ttlSecurity enables the generalized TTL security mechanism, which accepts packets only from a given number of hops away. reachableBy adds a static route to the peer's gateway so the session does not flap when routes change. nextHopMode replaces the older keepOriginalNextHop. With a filter, a node can announce its blocks to the switch while keeping Service addresses to itself, or accept only a default route from the rack.

BGPConfiguration can also announce Service addresses. serviceClusterIPs, serviceExternalIPs and serviceLoadBalancerIPs are empty lists by default. Filling them makes every node announce those ranges, so the physical network can reach a model server's Service without a separate load balancer in front.

Chapter 15 of 16

The MTU, and the modes in between

1500 with no wrapping, 1480 with IP in IP, 1450 with VXLAN

With no outer headers, a Pod's packet can be as large as the node network allows. Calico detects the MTU from the nodes and the enabled modes, and on a 1500 byte network every Pod's eth0 gets 1500. Under VXLAN it was 1450. A full TCP segment now carries 1448 bytes of data, where the VXLAN lesson carried 1398. Calico also offers two encapsulations for networks that cannot learn Pod routes. IP in IP puts one extra 20 byte IP header in front of the packet. VXLAN costs 50 bytes. Each has a mode named CrossSubnet, which wraps a packet only when the destination node is in a different subnet. Neighbours on one segment keep exchanging plain packets. Azure's network blocks IP in IP, so Calico's documentation points to VXLAN there.

Calico's MTU table gives the numbers for other networks. On a 1500 byte network a Pod gets 1500 with no encapsulation, 1480 with IP in IP, 1450 with VXLAN over IPv4, 1430 with VXLAN over IPv6, and 1440 or 1420 with WireGuard over IPv4 or IPv6. On AWS with jumbo frames of 9001 bytes the first three are 9001, 8981 and 8951. On Google Compute Engine, whose network MTU is 1460, they are 1460, 1440 and 1410. The overheads behind the table are 20 bytes for IP in IP, 50 and 70 for VXLAN over IPv4 and IPv6, and 60 and 80 for WireGuard.

Auto detection depends on Felix knowing which encapsulations are on, so the documentation asks to disable unused ones, vxlanEnabled, ipipEnabled, wireguardEnabled and wireguardEnabledV6. Felix finds the node's interfaces with the pattern in MTUIfacePattern, which matches names such as eth0 and ens5. A changed MTU applies only to new Pods. Manifest installs set veth_mtu in the calico-config ConfigMap, where 0 means detect, and restart the calico-node DaemonSet. Switching encapsulation modes on a running cluster can also disrupt connections that are in progress.

Chapter 16 of 16

Node addresses and the cloud

Which address BIRD uses, and what each cloud demands

Everything in this lesson assumed that Calico knows each node's address, 10.0.1.11 and 10.0.1.12. It finds them by autodetection. The default method is first-found, which takes the first valid IP address on the first interface and skips local interfaces such as the docker bridge. On machines with several networks that can pick the wrong one. The other methods are kubernetes-internal-ip, which uses the Node's internal address, can-reach followed by an address or name, interface with a pattern, skip-interface, and cidrs with a list of ranges.

The detected address goes into the Calico Node resource as spec.bgp.ipv4Address, with its prefix length, 10.0.1.11/24 on node-1. Two decisions use it. BIRD peers from that address, and CrossSubnet compares the destination node's address with this subnet to decide whether to wrap. A node detected with the wrong address peers from the wrong place, and its CrossSubnet decisions are made against the wrong subnet.

IP in IP, the lighter of the two wrappings, comes from RFC 2003. The outer IPv4 header carries protocol number 4. Its time to live is set for the trip to the tunnel's far end, its type of service is copied from the inner header, and if the inner header has Don't Fragment set, the outer one must have it too. Calico's IP in IP supports IPv4 only. Azure blocks IP in IP, so Calico's documentation points to VXLAN there.

With either encapsulation the documentation recommends natOutgoing on the pool. Without it, traffic between workloads and hosts running Calico is routed asymmetrically and may be dropped by reverse path checks. On AWS the advice combines all of this: within one subnet disable the source and destination check, and across subnets or availability zones use IP in IP in CrossSubnet mode with outgoing NAT. For a GPU cluster that keeps all nodes in one subnet, the plain routed design of this lesson needs nothing but the disabled check.

What to keep

The Pod's packet, and nothing around it

The tunnel hid Pod addresses from the network and paid 50 bytes a packet for it. Native routing does the opposite. BIRD on each node announces the node's block over BGP, one route for each other node lands in the kernel marked proto bird, and the Pod's packet crosses the switch as a 74 byte frame with Pod addresses in its only IP header. Pods get the full MTU of 1500, and firewalls and captures see real addresses and ports. In return the network has to cooperate. The nodes must share a layer 2 segment, or the routers between them must learn the Pod routes, and a cloud must be told to let those addresses pass. Where that is not possible, CrossSubnet modes wrap only the packets that need it. For model servers that move tens of gigabytes of weights between nodes, the larger packets add up.
