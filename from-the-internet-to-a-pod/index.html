Kubernetes underneath

From the internet to a Pod

A Service of type LoadBalancer, hop by hop, and where the client's address is lost

An outside client at 198.51.100.7 opens a connection to 203.0.113.80, the public address of the Service web. Its packets pass a load balancer, a node and sometimes a second node before they reach a Pod. At some of those hops an address in the IP header is rewritten. This lesson shows the headers at every hop, so you can see exactly where the client's address survives and where a node's address replaces it. It covers what type LoadBalancer adds to a Service, the health check that decides which nodes receive traffic, the two values of externalTrafficPolicy, and how MetalLB gives a cluster on your own hardware such an address. It ends with two ways to carry the client's address inside the connection.

Chapter 1 of 17

What type LoadBalancer adds

A ClusterIP, a node port, and one address from outside the cluster

The lesson "A service is a set of rules" ended at the node port. This lesson starts there. The Service types are nested, and each adds to the one before. Change web to type LoadBalancer and it keeps its ClusterIP 10.96.37.204 and its node port 31080. The new part is a request to something outside Kubernetes, because Kubernetes has no load balancer of its own. A controller in the cloud-controller-manager watches Services, asks the provider for a load balancer and configures it to forward to the node port on the nodes. This happens asynchronously. When the provider has allocated an address, the controller writes it into the Service's status, in the field status.loadBalancer.ingress. Until then that list is empty. The same controller sets up the load balancer's health checks.

The status has a second field that decides how packets look when they arrive. status.loadBalancer.ingress[].ipMode takes two values. VIP, the default, means traffic reaches the node with the load balancer's address and port still as its destination. Proxy means it arrives with the node's address and node port as its destination, or with a Pod's address and port when the load balancer sends straight to Pods. The packet forwarder in this lesson rewrites the destination to the node port, so its controller writes Proxy. MetalLB, later in the lesson, is the VIP case. kube-proxy reads the field. It writes rules that catch the load balancer's address only for addresses in VIP mode.

A Service can name the implementation that should serve it in spec.loadBalancerClass, stable since Kubernetes 1.24. The cloud provider's own controller ignores every Service that has the field set. The field can be set only on type LoadBalancer and never changed afterwards. That is how a second controller, such as MetalLB beside a cloud provider, can serve some Services without a fight over them. The ports of one load balanced Service may mix TCP and UDP since the feature gate MixedProtocolLBService was turned on by default in the API server in 1.24, although a provider may still refuse. And switching an existing Service to allocateLoadBalancerNodePorts: false does not free its node ports. They stay until you remove the nodePort entry from every port yourself.

Chapter 2 of 17

While the address is pending

What kubectl shows, the events the controller writes and the finalizer that guards deletion

Between the change of type and the moment the provider hands out an address, the Service exists but cannot be reached from outside. kubectl get svc prints <pending> in the EXTERNAL-IP column as long as status.loadBalancer.ingress is empty and the Service has no external IPs. kubectl describe service web shows the address on the line LoadBalancer Ingress once it exists, next to the lines NodePort and External Traffic Policy.

The service controller reports its progress as events on the Service. It records Normal EnsuringLoadBalancer, with the message Ensuring load balancer, when it starts, and Normal EnsuredLoadBalancer, Ensured load balancer, when the provider has finished. A failure gives Warning SyncLoadBalancerFailed with the message Error syncing load balancer followed by the provider's error. The controller retries a failed Service with a delay that starts at 5 seconds and doubles each time up to 300 seconds: 5, 10, 20, 40, 80, 160, then 300 seconds between tries. A quota problem at the provider therefore shows as a slowing series of the same warning.

Before it creates anything at the provider, the controller adds the finalizer service.kubernetes.io/load-balancer-cleanup to the Service. Deleting the Service then runs in steps. The Service gets a deletion timestamp and shows as Terminating. The controller records DeletingLoadBalancer, removes the load balancer at the provider, records DeletedLoadBalancer and only then removes the finalizer, and the Service disappears. A Service that stays Terminating for a long time usually means the provider refuses to delete its load balancer, and the Warning DeleteLoadBalancerFailed says why. This protection has been stable since Kubernetes 1.17. Without it a deleted Service could leave a load balancer at the provider, still running and still billed.

Chapter 3 of 17

The load balancer picks a healthy node

A health check on every node, then two hops with the client's address intact

A load balancer sends connections only to nodes that pass its health check. Kubernetes leaves the details to each provider and recommends one target: the health port of kube-proxy. With the default policy, Cluster, that is port 10256 and the path /healthz on each node. kube-proxy answers 200 when it is keeping the node's rules up to date and the node is eligible, and 503 otherwise. Eligible means, above all, that the node is not being deleted. The chapter on health endpoints lists the other conditions in the current source. Both nodes pass, so both are targets. Now the outside client at 198.51.100.7 opens a connection to 203.0.113.80 port 80. The load balancer in this lesson forwards packets and does not end the TCP connection. It picks node-1, rewrites the destination to 10.0.1.11 port 31080 and leaves the source alone. The SYN arrives at node-1 still carrying the client's address.

Which nodes become targets at all is the service controller's decision, made before any health check runs. In the current source a node is included when it has no deletion timestamp, when it does not carry the label node.kubernetes.io/exclude-from-external-load-balancers, and when it does not carry the cluster autoscaler's taint ToBeDeletedByClusterAutoscaler. The controller does not look at the node's Ready condition. The source still defines a list of checks that includes Ready, but nothing uses it. A node that is NotReady stays a target, and only the load balancer's own health check keeps connections away from it. The documented way to take a node out, for example before maintenance, is kubectl label nodes node-2 node.kubernetes.io/exclude-from-external-load-balancers=true. The controller compares the set of nodes every 100 seconds and updates the load balancer when it has changed, with the event UpdatedLoadBalancer and the message Updated load balancer with new hosts. If no node qualifies, it records the Warning UnAvailableLoadBalancer with the message There are no available nodes for LoadBalancer.

The health check then filters that set from moment to moment, and healthy has an exact meaning. kube-proxy counts as healthy while it is starting, while it has nothing waiting to be written to the kernel, and while a pending update has waited less than its health timeout. The documentation gives that timeout as 2 × syncPeriod, which is 2 × 30 = 60 seconds with the default. A kube-proxy that has had an update queued for longer than 60 seconds answers 503, and a load balancer that checks port 10256 stops sending it new connections.

Chapter 4 of 17

Cluster policy: a second hop and a new source

Any Pod in the cluster may be chosen, so the node must stay on the return path

The Service has externalTrafficPolicy: Cluster, the default. Node-1 may choose any ready Pod of web in the cluster, and this time the random match picks web-2 on node-2. The destination is rewritten to 10.244.2.17 port 8080, as in the Service lesson. The source is rewritten too. If web-2 saw 198.51.100.7, it would answer straight to that address through node-2. The reply would miss node-1, which holds the conntrack entry that can undo the rewrite. So node-1 replaces the source with one of its own addresses before it sends the packet through the tunnel. Web-2 answers to node-1, node-1 restores both addresses, and the load balancer restores its own. The connection works. The cost is that web-2's logs show a node address for every outside caller.

The source port changes as well. KUBE-POSTROUTING applies MASQUERADE with the option --random-fully, so the kernel picks the new source port at random. Here the client's port 40222 becomes 61734, an illustrative value, on the way to web-2. The conntrack entry holds both pairs, so node-1 can map 61734 back to 40222 when the reply comes. The KUBE-EXT chain under the Cluster policy is short. It has one rule that marks the packet, with the comment masquerade traffic for inference/web:http external destinations, and one jump to the KUBE-SVC chain.

The Kubernetes tutorial Using Source IP shows the effect from the server's side. A test server that prints the address it sees is called through the node port of each node in turn, and every answer reports an internal address: client_address=10.180.1.1, 10.240.0.5 and 10.240.0.3 in the tutorial's run. The tutorial lists the same steps as this chapter. The node replaces the source with its own address and the destination with the Pod's address, the reply returns to that node, and the node answers the client. For a model API this means every outside caller appears in the Pod's logs as one of a handful of node addresses. Limits per caller and audit trails cannot be built on the source address at this hop.

Chapter 5 of 17

Local policy: the client's address survives

Only Pods on the receiving node, and a health check that knows about them

Set spec.externalTrafficPolicy to Local and node-1 changes its behaviour in two ways. For traffic from outside it uses only the Pods of web that run on node-1, through a chain named KUBE-SVL in place of KUBE-SVC. And it stops marking those packets for masquerade, because a packet that never leaves the node needs no detour on the way back. The SYN for the node port is rewritten to web-1 at 10.244.1.15 port 8080, and its source stays 198.51.100.7. Web-1 sees the real client. Kubernetes also allocates a second port for the Service, spec.healthCheckNodePort. On that port kube-proxy on every node answers 200 if the node has a local endpoint of this Service and 503 if it has none. The load balancer's health check moves to that port, so nodes without a Pod drop out of the target list.

The KUBE-EXT chain under Local holds up to four rules. Traffic from a Pod in the cluster goes to the cluster chain, KUBE-SVC, with the comment pod traffic for inference/web:http external destinations. Traffic that the node itself sends is first marked, with the comment masquerade LOCAL traffic for inference/web:http external destinations, and then sent to the same cluster chain with the comment route LOCAL traffic for inference/web:http external destinations. Everything else, which means traffic from outside, falls through to KUBE-SVL. The node also opens the health check node port in its filter table. kube-proxy keeps a chain named KUBE-NODEPORTS in both tables: the one in the nat table rewrites node port traffic, and the one in the filter table accepts it. The rule is -A KUBE-NODEPORTS -m tcp -p tcp --dport 32205 -j ACCEPT and the comment inference/web:http health check node port. kube-proxy writes that rule whether or not the node has a local endpoint, because the load balancer must be able to hear the 503 as well as the 200.

The tutorial Using Source IP proves the effect with the loop from the last chapter, after the command kubectl patch svc nodeport -p '{"spec":{"externalTrafficPolicy":"Local"}}'. Now only one node answers, the one that runs the endpoint Pod, and it reports the real caller, client_address=198.51.100.79 in the tutorial. The other nodes drop the packet, so the loop needs --connect-timeout 1 to move on. With a cloud load balancer in front, the tutorial waits about 10 seconds for the nodes without endpoints to fail their health checks. That delay comes from the tutorial's provider and its settings. Kubernetes defines no such number.

Chapter 6 of 17

Two health endpoints, read exactly

One answers for kube-proxy and the node, the other for one Service

Each node has two kinds of health endpoint, and they answer different questions. Port 10256 belongs to kube-proxy as a whole. Its /healthz answer is JSON with the fields lastUpdated, currentTime, nodeEligible and healthy, and a status for each IP family, sent with the header Content-Type: application/json. The status code is 200 only when kube-proxy is healthy and the node is eligible. In the current source a node is not eligible when its Node object has a deletion timestamp, when it carries the cluster autoscaler's taint ToBeDeletedByClusterAutoscaler, or when kube-proxy has no Node object at all. The documentation mentions only the first.

The same port serves /livez, which ignores whether the node is being deleted. The documentation warns against using /healthz as kube-proxy's own liveness probe. On a node that is being deleted /healthz answers 503, the kubelet would restart kube-proxy again and again, and the node would lose its rule updates while it drains. /livez is the path for liveness. Both paths are counted, in kubeproxy_proxy_healthz_total and kubeproxy_proxy_livez_total, each with one series for 200 and one for 503.

The health check node port, 32205 here, answers for one Service. Its body is JSON with the Service's namespace and name, localEndpoints and serviceProxyHealthy. The tutorial on kubernetes.io still prints older plain text bodies, 1 Service Endpoints found and No Service Endpoints Found, so the format depends on the release. kube-proxy opens the port on the node's addresses. If it cannot, because another process holds the port, it records a Warning event on the Service with the reason FailedToStartServiceHealthcheck. That node then fails the load balancer's check although it runs a Pod of the Service.

The order of steps when a node is removed protects open connections, and the documentation describes it for the Cluster policy, where the load balancer checks port 10256. While the node is being deleted it fails that check, so a load balancer with connection draining lets existing connections end and sends no new ones. In the documentation's account the service controller removes the node from the targets once it is deleted, and removing a target ends all of its connections at once. That is why the health check fails first. In the current source the controller leaves out a node with a deletion timestamp whenever it computes the set of targets, so the removal can come before the Node object is gone.

Under the Local policy the load balancer checks the healthCheckNodePort, 32205 here, and port 10256 plays no part in its decision. A node that is being deleted keeps answering 200 on that port while it has a local endpoint of the Service. It goes on receiving new connections until its Pods of the Service stop being endpoints or the controller removes the node from the targets.

Chapter 7 of 17

Even across nodes, uneven across Pods

The load balancer counts nodes, and the Pods live with the result

Local has a price. The load balancer spreads connections across nodes and does not know how many Pods each node holds. Scale web to three replicas and suppose the new Pod, web-3, lands on node-2. Out of 1,200 new connections each node receives 600. Node-1 gives all 600 to web-1. Node-2 splits its 600 between web-2 and web-3, 300 each. Web-1 carries half the load and the other two a quarter each. With Cluster every Pod would receive about 400. For model servers this means one GPU at twice the load of its neighbours. The remedy is to control where Pods land, for example with anti-affinity rules, so that each node holds the same number. The opposite case is harsher. If web-1 goes away, node-1 has no local endpoint. Its health port answers 503, and packets that still arrive are dropped.

The documentation names the cases where Local spreads load evenly with no help. When there are many more nodes than Pods, or many more Pods than nodes, the distribution comes close to equal. Two nodes with three Pods sit between those extremes, which is where the imbalance is largest. Traffic from inside the cluster is not affected. Pods that call the Service by its ClusterIP are spread with equal probability over all Pods, because their path never passes the load balancer.

The weight header points at a fix. kube-proxy puts the number of local endpoints into X-Load-Balancing-Endpoint-Weight on every health response, 1 from node-1 and 2 from node-2 in this example. A load balancer that reads it and weights its targets 1 to 2 sends node-1 1,200 × 1/3 = 400 connections and node-2 1,200 × 2/3 = 800. Node-2 splits its 800 between web-2 and web-3, so every Pod again receives 400. Whether a provider reads the header is its own choice. Where it does not, keeping the same number of Pods on every node is the remedy that always works, and for GPU servers that usually means one model server Pod for each GPU on every node that serves the model.

Chapter 8 of 17

Rules for the public address

A rule for the address itself, a firewall for source ranges, and drop against reject

kube-proxy also writes rules for the load balancer's address itself, for addresses in VIP mode. A rule in KUBE-SERVICES with the comment inference/web:http loadbalancer IP matches the address and port and jumps on toward the KUBE-EXT chain. With this lesson's forwarder the status says Proxy, so kube-proxy writes no such rule, and the packets that arrive are addressed to the node port. With MetalLB, in the next chapters, the status says VIP and that rule receives the traffic. The rule has a side effect. A Pod or a process on a node that calls 203.0.113.80 never reaches the load balancer. Its packet matches the rule on its own node and goes straight to a Pod.

spec.loadBalancerSourceRanges limits who may connect, and kube-proxy enforces it on the node in two parts. A chain named KUBE-FW-OSVKZ2AR6ZI2SYOS in the nat table has one rule for each allowed range that sends matching sources on to the KUBE-EXT chain. A rule in the filter chain KUBE-PROXY-FIREWALL then drops whatever was not sent on, with the comment inference/web:http traffic not accepted by KUBE-FW-OSVKZ2AR6ZI2SYOS. A comment in kube-proxy's source states the limit. This works only for load balancers of the VIP kind that keep the client's address. For load balancers that send traffic to the node port, the firewall rules do not apply.

The filter table also tells a missing Pod from a missing local Pod. A Service with no endpoints anywhere gets a REJECT rule with the comment has no endpoints, for its node port, its external addresses and its load balancer address. A Local Service with no endpoint on this node gets a DROP with the comment has no local endpoints, in the chain KUBE-EXTERNAL-SERVICES. From outside, a refusal therefore means no Pod at all, and a timeout means no Pod on that node. kube-proxy counts Services in the second state on each node in the gauge kubeproxy_sync_proxy_rules_no_local_endpoints_total, with the label value external.

Chapter 9 of 17

Bare metal, layer 2: one node answers ARP

MetalLB hands out the address and one node claims it on the local network

On your own hardware no provider answers, and a Service of type LoadBalancer stays pending. MetalLB fills the gap. Its controller assigns the Service an address from a pool you define, an IPAddressPool. A speaker on every node then makes the network deliver that address. In layer 2 mode the speakers agree on one node for each address. That node answers ARP requests for 203.0.113.80 with the MAC address of its own network card. No load balancer stands in front, so the packet reaches the node with the public address still in its destination field, and all traffic for the address enters through that one node. If the node fails, the others notice through a membership protocol. A new node takes over and sends unsolicited ARP messages so that neighbours update their tables, usually within a few seconds.

With the Local policy, layer 2 mode is harsher than a provider's load balancer. MetalLB's documentation says it directly: Pods that are not on the current leader node receive no traffic and are there only as replicas in case of a failover. With Cluster the leader's kube-proxy spreads connections over all Pods, and the Pods see the leader node's address as the source. The choice of leader keeps no state. Each speaker builds the list of nodes that could announce the address from the active speakers, the traffic policy, the active endpoints and the node selectors. It sorts a hash of node name and address and announces if it comes first. Removing a node that is not the leader does not move the address. Adding a node moves it only if the new node sorts first.

Two things can go wrong with that design. If one speaker wrongly believes other nodes are gone, it computes a different list, and two speakers, or none, announce the same address. The membership comes from the memberlist library. MetalLB does not use VRRP, so it has no VRRP limit of 255 load balancers on a network, and it cannot work together with routers that run VRRP. For IPv6, NDP takes the place of ARP. Unsolicited announcements are sent only at failover by default, and the flag --gratuitous-arp-interval repeats them for networks where switches forget MAC addresses sooner than routers forget ARP entries. MetalLB asks for a bug report when a failover takes more than about 10 seconds.

Chapter 10 of 17

Running MetalLB in layer 2

What must exist before a speaker answers, and how to check it

Several conditions must hold before a speaker announces anything. In layer 2 mode MetalLB announces an address only when an L2Advertisement exists. One with an empty spec covers every pool. Its nodeSelectors are a hard filter: nodes outside the selector cannot announce at all. Its interfaces list limits which network interfaces are used. All of MetalLB's resources live in the namespace it runs in, metallb-system. A speaker also stays silent for a Service with no active endpoints, for a Local Service with no endpoint on its own node, and on a node labelled node.kubernetes.io/exclude-from-external-load-balancers. That label is the usual reason a single node or control plane only cluster announces nothing, and the speaker's flag --ignore-exclude-lb overrides it.

A Service can ask for an address. The annotation metallb.io/loadBalancerIPs requests specific addresses, comma separated for dual stack, and metallb.io/address-pool requests a pool by name. An address outside every pool or already in use makes the assignment fail with a warning event on the Service. Two Services can share one address with the annotation metallb.io/allow-shared-ip and the same sharing key, as long as their ports differ and both use the Cluster policy or select exactly the same Pods. The older prefix metallb.universe.tf/ is deprecated. A configuration that does not parse is not applied. MetalLB keeps the last valid one, logs a line that starts with failed to parse the configuration, and sets the metric metallb_k8s_client_config_stale_bool.

One setting outside MetalLB matters. If kube-proxy runs in ipvs mode, MetalLB's installation guide requires strictARP: true in kube-proxy's configuration, since Kubernetes 1.14.2. Lab notes that compare an Envoy based gateway with BIG-IP Next for Kubernetes list what MetalLB added to give that gateway an address on premises: a Helm chart, a controller, a DaemonSet on every worker node, custom resources and the strictARP change to kube-proxy. Checking the result needs care. MetalLB's troubleshooting page warns that pinging the service address does not work, and that reaching it from a node proves nothing, because the node's own rules answer. The check is arping from another host on the same segment. Every reply should carry the same MAC address. Several different MAC addresses mean two speakers announcing, a duplicate address on the segment, or the network plugin answering as well.

Chapter 11 of 17

Bare metal, BGP: every node announces the address

The router spreads connections with ECMP, and reshuffles them when a node leaves

MetalLB's other mode uses BGP, the protocol from the lesson "Pod networks without a tunnel". Each speaker opens a session with a router you own and announces the Service address as a /32 route with its own node as the next hop. The router now holds two equal routes to 203.0.113.80. With multipath enabled it uses both, which is called ECMP, equal-cost multipath. It picks a next hop for each packet by hashing header fields, so all packets of one connection reach the same node. With Local, only nodes that run a Pod of the Service announce the address. The weakness shows when the set of nodes changes. The hash is usually not stable, so most open connections move to a node that has never seen them, and they break. MetalLB's documentation describes a one-time burst of connection resets.

The hash on the router decides how far the spread goes. With a 3-tuple hash of protocol, source address and destination address, every connection from one client lands on the same node. A gateway that sends all its connections from one address then reaches a single node, however many connections it opens. A 5-tuple hash adds both ports and spreads those connections. MetalLB's documentation lists the remedies for the reset burst: resilient ECMP on the router, pinning the Service to specific nodes, changing deployments when traffic is low, two Services with different addresses and a migration through DNS, client retries, or an ingress controller between BGP and the Services.

The configuration has three required parts. A BGPPeer names the router and the two AS numbers, an IPAddressPool gives the addresses, and a BGPAdvertisement says that the pool is announced over BGP. Without the BGPAdvertisement nothing is announced at all. MetalLB's default BGP backend is now FRR-K8s, and the earlier FRR mode is deprecated. The FRR based modes add BFD, a fast liveness protocol between the node and the router, and IPv6 sessions. With BFD the router can drop a dead node's route after a few missed BFD packets, set by receiveInterval and transmitInterval in a BFDProfile, without waiting for the BGP session to time out.

Chapter 12 of 17

BGP in practice

Aggregates and communities, the return path, and what to read

The default announcement is one /32 route for each Service address, with the BGP local preference set to zero and no communities. A BGPAdvertisement can change all three with aggregationLength, localPref and communities. MetalLB's documentation works through a common case. A transit provider that carries your public addresses rejects routes more specific than a /24, so you announce the whole /24 to it with a second advertisement with aggregationLength: 24. The /32 routes stay for your own routers, marked with the well known community no-advertise, 65535:65282, so that they are not passed any further. For this lesson's pool, 203.0.113.80 to 203.0.113.89, the aggregate is 203.0.113.0/24.

The return path needs a check of its own. With BGP a client's packets can arrive on a network interface that is not the node's default route. Linux reverse path filtering, the sysctl rp_filter, can then drop them, because the reply would leave through a different interface. MetalLB's troubleshooting page lists static routes, routes learned from the fabric through FRR-K8s, or routing by source address as the fixes.

What an operator reads is short. Every speaker records an event on the Service of the form announcing from node "node-1" with protocol "bgp", so kubectl describe service web shows one such event for each announcing node. In layer 2 mode there is only one. The state of each session is the metric metallb_bgp_session_up, or frrk8s_bgp_session_up with FRR-K8s. With FRR, the command show bgp neighbor 10.0.1.1 inside vtysh should report the session as Established. The native mode logs BGP session established, BGP session down and failed to send BGP update.

Chapter 13 of 17

Two other ways to carry the client's address

When the load balancer ends the connection, the address must travel inside it

Some load balancers end the client's TCP connection and open a new one to a node. The source address of that second connection is the load balancer's. No traffic policy can bring the client's address back, because it is no longer in any IP header. Such a load balancer has to pass the address along inside the connection. The PROXY protocol does that for any TCP service. The load balancer sends one short header before the first byte of data, with the original addresses and ports. The receiver must be configured to expect it. For HTTP there is the header X-Forwarded-For, to which each proxy adds the address it received the request from. Both are claims made by the sender, so a server must accept them only from proxies it trusts.

The Kubernetes tutorial Using Source IP names three ways for a proxying load balancer to pass the address on: the standard HTTP header Forwarded, the header X-Forwarded-For, and the PROXY protocol. Which one applies depends on the load balancer and on the server behind it. A model server such as vLLM serves HTTP, so the headers are the usual route there. A TCP service that does not speak HTTP can only use the PROXY protocol. Whatever the method, the Pod's own TCP connection still comes from the load balancer or from a node. Every decision per client, a rate limit, a quota or a bill, has to read the carried address in place of the socket's peer address, and has to know which hops it can trust.

Chapter 14 of 17

Inside the PROXY header and the Forwarded header

Twelve bytes of signature, a LOCAL command for health checks, and RFC 7239

Version 2 of the PROXY protocol is binary. It starts with a 12 byte signature, the bytes 0D 0A 0D 0A 00 0D 0A 51 55 49 54 0A. The 13th byte holds the version in its high four bits, always 2, and the command in its low four bits: 0 for LOCAL and 1 for PROXY. The 14th byte holds the address family and the protocol. Two bytes of length follow, and then the addresses and ports: 12 bytes for IPv4, 36 for IPv6 and 216 for UNIX sockets. For TCP over IPv4 the whole header is 16 + 12 = 28 bytes. After the addresses, version 2 can carry extra fields as records of type, length and value, such as PP2_TYPE_ALPN (0x01), PP2_TYPE_AUTHORITY (0x02, the host name the client asked for), PP2_TYPE_CRC32C (0x03), PP2_TYPE_UNIQUE_ID (0x05) and PP2_TYPE_SSL (0x20).

The LOCAL command exists for the load balancer's own connections, such as its health checks. The receiver must accept such a connection and use its real endpoints. Both versions are designed to fit in one TCP segment of 536 bytes, the smallest every host must accept, so the header arrives whole. A version 1 line is at most 107 characters, which is why a 108 byte buffer always suffices. The receiver must not start processing a connection before it has a complete and valid header. It may close the connection if the header has not arrived within a few seconds, at least 3, and it must drop a connection whose header does not match the protocol. That strictness has a practical consequence. Turn the protocol on at the load balancer and not at the server, or the other way round, and every connection fails, health checks included, so every backend can drop out at the same moment.

For HTTP the standard header is Forwarded, from RFC 7239, with parameters such as for, by, host and proto. Several hops are written as a list separated by commas. IPv6 addresses are quoted and written in brackets. The last proxy does not add itself to the for list, because its address is already the source of the connection the server sees.

Chapter 15 of 17

Where an AI factory puts this hop

The address and the node port are two of several layers in front of a GPU

Everything in this lesson is one layer of a longer path for AI traffic. F5's material on BIG-IP Next for Kubernetes draws an inference cluster as a stack of separate layers. An external load balancer gives the cluster an address. kube-proxy with a node port carries traffic from the node to Pods. An L7 gateway handles routes, policy and health checks. An AI gateway handles API access and model routing. Endpoint selection picks a Pod by prefix and by GPU load. F5's argument is that each layer adds a hop, a configuration and a team, and that one data path can do the work of all of them.

F5's deck on its AI gateway names the first two layers as stages. Stage 1 is layer 4 ingress, with three options: bring your own layer 4 appliance, an NVIDIA BlueField DPU, or BIG-IP Next for Kubernetes acting as the external layer 4 balancer itself, with BGP and its own custom resources. Stage 2 is the Kubernetes routing layer, described as node port and CNI routing that maps node traffic to Pods, and the deck claims to replace the iptables hops of kube-proxy with its own data path. The owner's notes comparing BNK with the open source project llm-d, hop by hop against that slide, draw the same line: llm-d brings an endpoint picker, uses a cloud load balancer or MetalLB for the address, and does not replace the kube-proxy and node port step into the cluster.

The mechanics in this lesson show what those layers cost a model server. Each hop is a place where the client's address can be replaced, where a connection is balanced once and then pinned, and where a health check knows about nodes and not about GPUs. Under the Cluster policy a single SYN has its destination rewritten twice, by the load balancer and by the node, and its source once, before it reaches a Pod. A path that delivers straight to a Pod address skips the node port and the second hop between nodes.

Chapter 16 of 17

Five hops, five failure domains

The ingress chain without BNK, drawn as one picture and counted

F5's deck on BIG-IP Next for Kubernetes and NVIDIA draws the ingress path of an inference cluster without BNK as one column, under the title 5 Hops, 5 Failure Domains, Multiple Components, No Single Vendor. A client's request passes five boxes before it reaches an AI workload Pod. Hop 1 is the external load balancer. Hop 2 is kube-proxy with a node port. Hop 3 is an L7 gateway that does HTTP and gRPC routing and has no GPU awareness. Hop 4 is an AI gateway that processes AI requests and handles tokens. Hop 5 is an inference endpoint picker that selects a Pod from GPU metrics. Only then does the request reach the box the deck labels AI Workload Pod (LLM / Inference). In this site's example cluster that would be a vLLM Pod such as qwen3-6f7d9c8b4-x7k2p at 10.244.1.21 port 8000, on the node this lesson calls node-1 and the site's other lessons call gpu-node-1. The deck names no Pod, so that name and address are this site's example. This lesson has so far walked hops 1 and 2 packet by packet. The other three are lessons of their own. Here the point is the chain as a whole.

The deck lists four problems under the column. The first is hairpinning, traffic that crosses nodes when it did not need to. That is the second hop of the Cluster policy in this lesson. Take the three Pods of web from the chapter on uneven load, web-1 on node-1 and web-2 and web-3 on node-2, and 1,200 new connections that the load balancer spreads evenly. Node-1 receives 600 and its random match sends a third of them to each Pod, so 400 leave node-1 through the tunnel. Node-2 receives 600 and sends 200 of them to web-1 on node-1. That makes 600 of 1,200 connections, half of them, that cross between nodes. Every packet of those connections carries 50 extra bytes of VXLAN wrapping, an outer Ethernet header of 14 bytes, an outer IPv4 header of 20, UDP of 8 and VXLAN of 8, and is rewritten by a node that is not the one running the Pod. The SYN of this lesson grew from 74 bytes to 124 on that hop.

The second problem is 5 independent failure domains. Each box can fail on its own, and a request needs all five to be up. A worked example with an illustrative figure shows what that does. If each layer is available 99.9% of the time and they fail independently, the chain is available 0.999 × 0.999 × 0.999 × 0.999 × 0.999 = 0.99501, or 99.50%. Over a 30 day month of 43,200 minutes, one layer at 99.9% is down about 43 minutes. The chain of five is down 43,200 × 0.00499 = about 216 minutes, five times as long. Each box also has its own logs, its own metrics and its own idea of health, so a failed request has to be traced through five places.

The third problem is multiple components with different release cycles. Kubernetes itself keeps release branches for the three most recent minor versions and gives each about one year of patches. kube-proxy may run up to three minor versions behind the API server and must never be newer. The load balancer, the L7 gateway, the AI gateway and the endpoint picker each ship on their own schedule, from their own project or vendor, and an upgrade of one has to be tested against the other four. The fourth problem is no single vendor support, and the deck pairs it with the sharpest technical point of the four: the external load balancer is blind to Pod and GPU state. The earlier chapters show exactly what it can see. Under Cluster it reads kube-proxy's /healthz on port 10256, which says whether kube-proxy has programmed the node. Under Local it reads the healthCheckNodePort, which says how many Pods of the Service run on the node. Neither says how full a GPU's KV cache is, how many requests wait in vLLM's queue, or whether a Pod is still loading its 34.3 GB of FP8 weights. F5's other deck, on its AI gateway workflow, puts the same contrast in one row of a comparison table: a traditional L7 load balancer chooses by round robin, least connections or IP hash, and the workflow-driven AI gateway by KV cache prefix affinity, GPU memory telemetry and queue depth.

Chapter 17 of 17

BNK's data path in place of the node port hop

TMM gets its own network interfaces, learns the Pod addresses and sends to them directly

F5's deck on its AI gateway workflow names stage 2 of the pipeline Kube Routing, NodePort and CNI routing that maps inbound traffic to Pod endpoints. Its slide on stages 1 and 2 makes three claims: BNK replaces the iptables hops of kube-proxy with its own data path, it is configured with custom resources, and it supports static routing, BGP peering and multi-network interfaces. This chapter shows the mechanism behind each claim, using F5's documentation, and compares it with the kube-proxy hop of this lesson. The data plane of BNK is TMM, the Traffic Management Microkernel, which runs as a Pod on the host CPU or on an NVIDIA BlueField DPU. A controller called the CNE controller watches the Kubernetes API and pushes configuration to TMM over gRPC.

Multi-network interfaces come first, because TMM cannot deliver traffic without its own wires. A Pod normally has one interface, eth0, on the cluster's Pod network. Multus is a CNI plugin that adds more. An administrator defines each extra network as a NetworkAttachmentDefinition object, and a Pod that names it in the annotation k8s.v1.cni.cncf.io/networks receives an extra interface, net1 for the first one, while eth0 stays. Multus then writes what it attached into the annotation k8s.v1.cni.cncf.io/network-status. For TMM those extra networks are SR-IOV virtual functions on a host, or scalable functions on a DPU. TMM numbers them in the order they are attached, 1.1, 1.2 and so on. Its control traffic still uses eth0: the CNE controller reaches TMM's routing container by the TMM Pod's own address over gRPC with mutual TLS.

The interfaces then become VLANs with self IPs, the addresses TMM itself owns on each network. In the older custom resource F5SPKVlan, an external VLAN on interface 1.1 faces the clients and an internal VLAN on 1.2 faces the Pods. The self IPs are a list, and each TMM replica takes the next one, the first address to the first TMM Pod. The field internal: true may be set on one VLAN only, and F5's guide requires the internal self IPs to share a subnet with the nodes. In this lesson's world that could be 10.0.1.90 on the nodes' network 10.0.1.0/24, an illustrative address. In the BNK 2.3 documentation, with the Gateway API model, one resource called Infra holds the same things for the whole installation: ipams for address pools, networkAttachments that name NetworkAttachmentDefinitions, networks of type vlan or vxlan, vrfs, and staticRoutes. F5's 2.3 reference page for Infra describes it as a singleton in the BNK namespace that holds at most 64 networks and 64 attachment groups, and says that when it changes the controller sends only the difference to TMM. These limits come from that release's reference and can change between releases, so check the page for the version you run.

Next TMM learns where the Pods are. The controller watches the Endpoints of the Service a route points to and keeps TMM's load balancing pool equal to them. For web that pool is 10.244.1.15:8080, 10.244.2.17:8080 and web-3's address. A Gateway listener with an L4Route, or an HTTPRoute for HTTP, names the Service in backendRefs with its port. TMM chooses a Pod and sends the connection to that Pod's address. The packet never carries the node port 31080 and never enters the KUBE-EXT, KUBE-SVC or KUBE-SEP chains, because those rules match only the ClusterIP, the node port and the load balancer address. When the SYN reaches node-2 on its way to 10.244.2.17, the node's kernel finds no Service rule for that destination and simply routes it to the Pod. There is no random match on node-1, no second hop to another node and no MASQUERADE by a node. The source the Pod sees is set by TMM. F5's ingress guide for BlueField-3 shows TMM translating the source to its own self IP on the way to the backends, the behaviour F5 calls SNAT Automap, so the Pod sees TMM's address and its reply returns to TMM. The field sourceNATConfig in a GatewaySettings resource belongs to egress: it sits under egressConfigs, for traffic that leaves the cluster, and needs a type, Automap in the owner's lab. A setup that keeps the client's address toward the Pod must still route the Pod's reply back through TMM, which F5's OpenShift guide does by making TMM's internal self IP the gateway for the Pods' namespace.

Static routing and BGP connect TMM to the rest of the network. A static route tells TMM where a prefix lives. F5's own example of the older F5SPKStaticRoute sends 10.10.1.100/32 through the gateway 10.146.134.1, its status reads CR config sent to all grpc endpoints, and ip route inside the TMM container then shows 10.10.1.100 via 10.146.134.1 dev external. In Infra, each entry of staticRoutes has destinations and exactly one of nextHop or networkRef. BGP makes the outside world learn TMM's virtual addresses. GlobalRoutingConfig sets the cluster-wide BGP settings, with startASN, an optional endASN from which the controller hands one AS number to each TMM slot, and routerIdSource %POD_IP% to use each TMM's Pod address as its router ID. RoutingConfig, the resource F5's deck names under stage 2, is the per-tenant part. It links a RoutingTemplate with a VRF or a VXLAN, BGP neighbors given by address or interface with a remoteAs between 1 and 4294967295, and integrated routing and bridging interfaces, and renders them as configuration for OcNOS, the routing software in TMM's routing container. It cannot be edited after creation, so a change means delete and create. The owner's lab notes add what an operator meets. BNK 2.4.2 advertises the virtual addresses as /32 routes, the BGP route for a new Gateway's address came up about 10 seconds after the Gateway was Ready in one lab and 11.5 seconds in another, and turning dynamic routing on after install needs ZEBOS_STATE=ocnos in the TMM environment. F5's older guide adds a condition that surprises people: the Service behind a route needs at least one endpoint before TMM creates and advertises the virtual address.

What to keep

Where the source address changes

Type LoadBalancer adds one address from outside the cluster to a Service that already has a node port and a ClusterIP. A controller allocates that address, writes it into the Service status and points a load balancer at the nodes. From there the client's address has three fates. With externalTrafficPolicy: Cluster the receiving node may send the packet on to another node and puts its own address in the source. With Local the node uses only its own Pods and the source stays 198.51.100.7, at the price of load that follows the placement of Pods. A load balancer that ends the connection removes the address from the IP header altogether, and it returns only through the PROXY protocol or X-Forwarded-For. On bare metal MetalLB supplies the address, through one node with ARP or through all of them with BGP. If a model API limits or bills callers by address, choose with these hops in mind. Around those paths sit the parts an operator meets: <pending> and the controller's events while the address is allocated, a finalizer that holds deletion until the provider has cleaned up, two health endpoints with exact meanings, a firewall for source ranges that only works for addresses in VIP mode, and MetalLB resources that must all exist before a single ARP reply or BGP route appears.
