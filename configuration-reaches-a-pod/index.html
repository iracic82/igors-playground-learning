Kubernetes underneath

Configuration reaches a Pod

Two ways in for a ConfigMap or a Secret, and what happens when one changes

A model server needs settings that do not belong in its image: the name it serves the model under, the default sampling values, a token to download the weights and a key that callers must present. Kubernetes keeps these in two kinds of object, the ConfigMap and the Secret. Both reach a container in one of two ways, as environment variables or as files. The two ways behave differently when the object changes later. A variable keeps the value it had when the process started. A file is rewritten on the node, within about a minute under the kubelet's default settings.

This lesson follows both ways into one vLLM Pod. It shows how the kubelet builds the environment and what happens when a reference is wrong, how a volume of files is laid out behind a hidden link, how a change travels from the API server to the node and is swapped in with one rename, and how teams restart Pods on purpose. It ends with what actually protects a Secret: encryption at rest, the Node authorizer, RBAC and key rotation.

Chapter 1 of 11

Two objects beside the Deployment

Plain settings in one, sensitive ones in the other

The model server needs two kinds of settings. Some are plain: the name the model is served under and the default sampling values, such as temperature. Some are sensitive: a Hugging Face token to download the weights and an API key that callers must present. Kubernetes has one object for each kind. A ConfigMap holds plain keys and values. A Secret holds the same shape of data, with each value written in base64, an encoding that turns bytes into text.

Both live in the namespace, beside the Deployment and outside the image, so one image can run with different settings. A Pod can only use ConfigMaps and Secrets in its own namespace, so a setting shared by two namespaces needs a copy in each. Static Pods, the ones a kubelet runs from files on its own disk, cannot use them at all. Each object is limited to 1 MiB, which is plenty for settings and far too small for weights.

Key names follow one rule for both kinds: letters, digits, the hyphen, the underscore and the dot. A ConfigMap's data and binaryData must not share a key. A Secret also has a type. Opaque is the general one and is what an empty type means. Others carry a fixed set of keys that the API server checks, such as kubernetes.io/tls for a certificate and its key and kubernetes.io/dockerconfigjson for registry credentials. You apply both objects, and the API server stores them in etcd. Nothing reads them until a Pod refers to them.

Chapter 2 of 11

Making the objects with kubectl

From files, from literals, from env files, and back again

Few people write these objects by hand. kubectl create configmap builds one from local files or values. With --from-file=generation_config.json the file name becomes the key and the content becomes the value. With --from-file=<key>=<path> you choose the key. A directory given to --from-file adds one key for every regular file in it whose name is a valid key. --from-literal=SERVED_MODEL_NAME=qwen3-32b adds a single key. --from-env-file reads lines of NAME=value, and since v1.23 it may be given several times. kubectl checks every key it is about to add, a single --from-file and each file found in a directory alike. A key may hold only letters, digits, dashes, underscores and dots. When a file name breaks that rule, kubectl stops with an error such as "my file.json" is not a valid key name for a ConfigMap, and creates nothing. The task page on kubernetes.io still has an older sentence saying such files are skipped, but kubectl's source returns the error. Kustomize's configMapGenerator builds the same object from a kustomization file.

kubectl create secret generic makes an Opaque Secret with the same flags and does the base64 encoding for you. kubectl create secret tls and kubectl create secret docker-registry make the typed ones.

Reading them back is just as easy, which is the point of the next chapters. kubectl get secret qwen3-secrets -o jsonpath='{.data.HF_TOKEN}' prints the encoded value, and piping it through base64 -d prints the token. kubectl get configmap -o jsonpath='{.binaryData}' shows binary keys.

In a manifest, stringData lets you write plain values and the API server encodes them into data. The documentation warns that stringData does not work well with server-side apply. Teams that apply manifests that way write data in base64 instead.

Chapter 3 of 11

The first way in: environment variables

Copied into the process once, when it starts

The first way in is the environment. The container's spec names a key in the ConfigMap or the Secret, and the kubelet turns it into an environment variable. This happens once. The kubelet reads both objects from the API server, builds the list of variables and hands it to containerd with the request to create the container. The kernel copies the list into the new process when it starts. Nothing can change it from outside after that. The documentation states the rule in one sentence: ConfigMaps consumed as environment variables are not updated automatically and require a Pod restart.

The kubelet builds the list in a fixed order. First it computes the variables for the namespace's Services. Then it reads every envFrom source in order. An envFrom entry may carry a prefix, which is put in front of every key. Then it processes env in the order written, and a name set in env replaces the same name from envFrom. While it does this it expands references of the form $(NAME) in values, in commands and in args.

That expansion has rules people trip on. Inside an env value, a name counts as defined if it came from a Service variable, from any envFrom source, or from an env entry earlier in the list. An env entry further down does not count yet. In command and args the order does not matter, because the kubelet expands them against the container's complete, final environment. A reference to an undefined name is left as plain text and does not stop the container. $(NAME) is an escape that is never expanded. vLLM gets its served model name, its token and its API key this way, and its args use $(SERVED_MODEL_NAME) and $(API_KEY). A misspelt name would start vLLM with the literal text $(API_KEY) as its key.

Chapter 4 of 11

When a reference is wrong

A missing key stops the container, an odd envFrom key now passes straight through

A reference can point at nothing. By default every ConfigMap and Secret a Pod names is required, and none of the Pod's containers start until they exist. If the object exists but the named key does not, the kubelet fails with couldn't find key API_KEY in Secret inference/qwen3-secrets. The container stays in the waiting state with the reason CreateContainerConfigError, and the Pod gets a Warning event with the reason Failed and a message that starts with Error:. The kubelet keeps retrying, so creating the key later lets the container start. Marking the reference optional: true changes all of this. A missing object or key then leaves the variable out and the container starts.

envFrom behaves differently, and its behaviour changed in v1.30. Each key of the object becomes a variable. Up to v1.29 the kubelet checked each key against the rules for variable names, skipped the keys that failed, started the Pod anyway and recorded a Warning event with the reason InvalidEnvironmentVariableNames that listed them. In v1.30 that check and that event were removed from the kubelet. Every key now goes into the environment exactly as it is, and no event is recorded. The task page on kubernetes.io still shows the old event, so it is stale on this point. On every supported cluster a key such as generation_config.json becomes a variable with a dot in its name. A separate check lives in the API server and covers only names you write yourself, the env[].name fields and an envFrom prefix. The feature gate RelaxedEnvironmentVariableValidation, alpha in v1.30, beta from v1.32 and locked on from v1.34, lets those names use almost every printable ASCII character.

Some variables arrive uninvited. KUBERNETES_SERVICE_HOST is always injected, and with enableServiceLinks, true by default, every Service in the namespace adds its own host and port variables. Newer versions add a third source, env[].valueFrom.fileKeyRef, which reads a key from an env file in a volume, usually written by an init container. Its feature gate, EnvFiles, is beta and on by default from v1.35.

Chapter 5 of 11

The second way in: mounted files

One file for each key, behind a hidden link

The second way in is a volume. The Pod lists the ConfigMap as a volume and the container mounts it at /etc/vllm. The kubelet creates a directory on the node and writes one file for each key, with the key as the file name and the value as the content. With configMap.items you pick only some keys and give each a path. Files get mode 0644 unless defaultMode or an item's mode says otherwise. A mode is octal in YAML, 0400 for example, and must be written as the decimal 256 in JSON.

The files are not written directly into that directory. They go into a hidden directory named after the time in UTC with a random suffix, a hidden link called ..data points at it, and each visible file name is a link through ..data. That detour is what makes updates safe later. Names that start with two dots are reserved for this.

Under the hood both volume types are an emptyDir. A ConfigMap volume wraps a plain one on the node's disk. A Secret volume wraps one with medium Memory, which is tmpfs, a filesystem held in memory, so the kubelet does not write a Secret's values to durable storage on the node. A projected volume puts several sources in one directory: secret, configMap, downwardAPI, serviceAccountToken and others, all from the Pod's namespace.

An items entry that names a key the ConfigMap lacks fails the mount, unless the volume is optional. An optional volume whose ConfigMap does not exist is mounted empty, and fills in if the ConfigMap appears later. vLLM is started with --generation-config /etc/vllm and reads its sampling defaults from the file.

Chapter 6 of 11

A value changes

The object is new at once. The Pods are not

Ten minutes later you lower the default temperature from 0.7 to 0.6 by editing the ConfigMap. The API server stores the new version. Two things do not happen. No controller reacts, because the Deployment's Pod template has not changed, so no Pod is replaced. And no environment variable changes anywhere.

What does happen is on the nodes. Each kubelet keeps a local cache of the ConfigMaps and Secrets its Pods use. How it fills that cache is the KubeletConfiguration field configMapAndSecretChangeDetectionStrategy. Watch, the default, opens one watch for each object its Pods refer to, so the new version arrives within moments. It closes the watch on an object that became immutable, and on one that no Pod has asked for in a while. Cache keeps each object for a time to live. The task page says one minute by default, but in the source that minute is only a fallback. The TTL controller in kube-controller-manager writes the annotation node.alpha.kubernetes.io/ttl on every Node, and the kubelet uses that value whenever it is there. It is 0 seconds for clusters of up to 100 nodes, then 15, 30, 60 and 300 seconds as the cluster grows. On northlight-eu, with two nodes, it is 0, and the cache fetches the object again on every read. Get fetches the object from the API server every time.

The kubelet only rewrites the files when it next syncs the Pod, and it syncs every minute by default, set by syncFrequency. The documented worst case is the kubelet sync period plus the delay of the cache. With Watch that is about one minute. With Cache the task page gives about two, one minute of sync plus one minute of cache. That sum holds only where the TTL annotation is 60 seconds, which the TTL controller sets for clusters of roughly 900 to 2,000 nodes. On a small cluster the cache adds next to nothing, and on a very large one with 300 seconds it adds up to five minutes. Updating one of the Pod's annotations triggers a refresh at once.

Secrets follow the same path. A mounted Secret is updated the same way, eventually, and a Secret in an environment variable stays as it was. A file mounted with subPath gets no update at all, which a later chapter shows.

Chapter 7 of 11

The files are swapped in one step

A new directory, then one rename

On its next sync the kubelet hands the new content to a writer in its source called the atomic writer. The writer reads ..data to find the current directory and compares its files with the new content. If nothing differs it stops there, so the timestamp in the directory name is the time of the last real change and not of the last sync. Here the temperature differs. It creates a fresh directory named after the current UTC time, writes the files, sets their modes, creates a link called ..data_tmp that points at the new directory, and renames ..data_tmp to ..data. A rename is atomic. A reader sees all the old files or all the new ones and never a mixture. Then the old directory is removed.

One detail of the order matters. The links for new keys are created, and the links for removed keys deleted, after the rename. So a change to an existing key is fully atomic, while a key that is added or removed appears or disappears a moment later. The writer also enforces limits: 255 characters for a file name and 4,096 for a path.

Two limits remain for programs. A file mounted with subPath, which mounts a single file instead of the directory, was resolved to the old file when the container started and never changes. The same holds for subPathExpr, its sibling built from environment variables. And new bytes on disk do nothing by themselves. The program has to read the file again. The kubelet's source suggests watching the ..data link with inotify to learn of updates. vLLM read its generation config at startup, so it still answers with 0.7.

Chapter 8 of 11

Restarting the Pods on purpose

Change the Pod template, and the Deployment does the rest

Since nothing restarts Pods for a ConfigMap, teams arrange it themselves. The direct way is kubectl rollout restart. It writes the current time into the annotation kubectl.kubernetes.io/restartedAt on the Deployment's Pod template. The template has now changed, so the Deployment controller creates a new ReplicaSet and starts an ordinary rolling update. Each new Pod resolves its environment variables again and reads the new file at startup.

The lasting way is to put a hash of the configuration into the same place. Helm charts commonly carry an annotation such as checksum/config with the SHA-256 of the rendered ConfigMap. Any change of settings then changes the hash, the template and the Pods, in the same apply. Kustomize's configMapGenerator reaches the same goal differently: it appends a hash of the content to the ConfigMap's name and rewrites the references, so a change produces a new name.

A third way is an immutable ConfigMap. Set immutable: true, give each version a new name, and point the Deployment at it. The field arrived as alpha in v1.18, has been on by default since v1.19 and is stable since v1.21. A mutable ConfigMap or Secret can be made immutable later, and the step cannot be undone. The data can no longer change, and the kubelet stops watching the object, which takes load off the API server in a large cluster.

Every one of these replaces model servers, and each new one needs about three minutes to load the 34.3 GB of weights of the FP8 build Qwen3-32B-FP8. A rolling update with the Deployment's default of 25% maxUnavailable and 25% maxSurge on two replicas adds one new Pod at a time, so the change takes at least two loads.

Chapter 9 of 11

Encryption at rest

The encoding protects nothing, so the API server can encrypt before etcd

A Secret is a separate kind so that it can be treated more carefully. The encoding adds nothing to that. Base64 can be reversed by anyone, and by default the API server writes Secrets to etcd unencrypted. The default provider is called identity, which writes data as it is.

Encryption at rest is a setting of the API server: a file named by the flag --encryption-provider-config lists which resources to encrypt and with which providers. The first provider in the list encrypts everything written from then on. When reading, each provider is tried in order until one can decrypt. If none can, the client gets an error and cannot read the object. Secrets written before the change stay as they were until they are written again.

The documentation rates the providers. aescbc, common in older examples, is rated weak and not recommended because of CBC's padding oracle weakness. aesgcm must have its key rotated every 200,000 writes and is recommended only with automated rotation. secretbox, XSalsa20 with Poly1305 and a 32 byte key, is rated strong. For all three the key sits in the file on the control plane host. kms v2 is rated strongest. Each object is encrypted with a data key, those data keys are derived from a seed, and the seed is encrypted with a key that never leaves an external key management service. kms v2 is stable from v1.29. kms v1 is deprecated since v1.28 and off by default since v1.29.

Resources can be named one by one, by group such as '*.apps', or as '*.*' for everything, from v1.27. ConfigMaps are encrypted only if listed.

Chapter 10 of 11

Who may read a Secret

RBAC for people, the Node authorizer for kubelets

The rest is access control. Whoever may get a Secret can read it. Whoever may list Secrets receives every Secret in the namespace with its values, so list is as strong as get on all of them, and the documentation says watch is too. The good practice page asks for list and watch on Secrets to be kept to the most privileged system components. And whoever may create a Pod in the namespace can mount any Secret in it, so that right also opens them.

Kubelets are limited by a special authorizer. A kubelet authenticates as system:node:<node name> in the group system:nodes. The Node authorizer lets it read Secrets, ConfigMaps, PersistentVolumeClaims and PersistentVolumes only when they relate to Pods bound to its own node. That is how the rule that a Secret is only sent to a node that needs it is enforced. A stolen kubelet credential opens the Secrets of that node's Pods and no others. The NodeRestriction admission plugin limits what a kubelet may change.

On the node itself the boundaries are weaker. One Pod cannot read another Pod's Secrets through Kubernetes. A container running with privileged: true can read every Secret used on that node, and anyone with root on the node can read a process's environment in /proc. That is one reason to prefer mounted files in tmpfs over environment variables for a token.

The good practice page adds more. Let only administrators reach etcd, read-only access included. Prefer short-lived credentials. Or keep values outside the cluster with the Secrets Store CSI Driver, a DaemonSet that fetches them from an external store and mounts them as a volume.

Chapter 11 of 11

Rotating the encryption key

Add the new key, promote it, rewrite, then remove the old one

An encryption key, like any key, has to be replaced from time to time, and the replacement must never leave a Secret that no API server can decrypt. The documentation describes four moves. Each provider holds a list of keys. When reading, the keys are tried in order. When writing, the first key of the first provider is used.

First, add the new key as the second entry in the keys list and restart every API server, so each one can decrypt with it. Second, move the new key to the first position, so it is used for encryption, and restart every API server again. Third, rewrite every Secret, for example with kubectl get secrets --all-namespaces -o json | kubectl replace -f -, so each one is encrypted with the new key. Fourth, remove the old key from the file. The order matters in a cluster with several API servers. If one server encrypted with a key that another did not know yet, the second could not read that Secret.

The flag --encryption-provider-config-automatic-reload=true lets the API server pick up changes to the file without a restart. The file must be the same on every API server. It also holds the keys themselves, so its permissions matter as much as etcd's.

With kms v2 the routine is different. The key encryption key lives in the external service. The API server reaches it through a KMS plugin, which it talks to with gRPC over a Unix domain socket. Rotating it there rotates the seed from which data keys are derived, and the Secrets are rewritten the same way afterwards.

What to keep

Fixed at start, or rewritten on disk

A ConfigMap and a Secret are stored objects, and they reach a container in two ways. As environment variables they are copied into the process when it starts and stay as they were. A wrong reference stops the container, unless it is optional. As a mounted directory they are files that the kubelet rewrites after a change, within the sync period plus the cache delay, about a minute with the default Watch strategy, by writing a new directory and renaming one link. A subPath mount is left out of that, and so is any program that does not read its files again. Nothing restarts Pods when configuration changes, so a rollout restart, a checksum in the Pod template or a new immutable ConfigMap has to do it, and each restart costs a model load. A Secret is only as private as etcd encryption, the Node authorizer, RBAC and the people with root on the nodes make it.
