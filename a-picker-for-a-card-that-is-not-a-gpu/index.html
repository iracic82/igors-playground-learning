Inference

A picker for a card that is not a GPU

Qualcomm Cloud AI 100 cards behind vLLM and the F5 endpoint picker: what the picker can read, and what to change

Every earlier lesson on the picker assumed NVIDIA GPUs under vLLM. This one puts a different accelerator under the same model server: Qualcomm's Cloud AI 100, an inference card that vLLM drives through a separate package called vllm-qaic. The F5 endpoint picker never talks to the card. It reads the Prometheus page that vLLM serves on port 8000 and scores workers from it. So the question is how much of that page still means what it means on a GPU.

The answer has three parts. The queue and the count of running requests are exact, because vLLM's own scheduler produces them on any hardware. The KV cache gauge is present but coarse: in the production mode each sequence gets one block the size of the whole context, so the gauge counts seats and moves in steps of one eighth. Prefix caching does not exist on this hardware yet, so the picker's cache affinity has nothing to aim at.

The lesson follows the plugin from its entry point to the numbers on /metrics, works through the block geometry and the gauge with real values, then turns that into six changes to an F5EPP resource. It ends with where such a pool can be tested, because the plugin has no simulator path, and with what is changing upstream.

In this lesson a node with Cloud AI 100 cards joins cluster northlight-eu, and a second pool, llama-qaic, runs next to the qwen3 GPU pool. The three workers on the scene stand for its three Pods, one card each.

Chapter 1 of 11

The picker reads a page, not a card

The F5 endpoint picker scores workers from vLLM's Prometheus page, whatever runs underneath

The F5 endpoint picker, the EPP, is the program that answers BNK's question of which worker should take a request. The lesson Which GPU answers soonest showed how it decides. It keeps a fresh copy of a few numbers from every worker and scores each one. Those numbers come from one place: an HTTP GET to /metrics on the worker's metrics port, which is spec.server.modelServerMetricsPort in the F5EPP resource and 8000 for vLLM. The owner's notes give F5's default refresh as every 50 milliseconds.

The picker reads the numbers through a plugin called core-metrics-extractor. Its settings name one Prometheus series for each signal. queuedRequestsSpec is vllm:num_requests_waiting, the requests accepted but not yet started. runningRequestsSpec is vllm:num_requests_running, the requests in the running batch. kvUsageSpec is vllm:kv_cache_usage_perc, the share of KV cache blocks in use, from 0 to 1. Two optional ones follow: cacheInfoSpec is vllm:cache_config_info, read for its block_size label, and loraSpec is vllm:lora_requests_info. These are the same three required signals that the Gateway API Inference Extension's model server protocol asks of any model server.

Nothing in that list mentions a GPU. A worker qualifies if it serves those series with their meanings intact. That is the whole contract between the picker and the hardware. Qualcomm's Cloud AI 100 is an inference accelerator on a PCIe card. A Cloud AI 100 Ultra holds 64 compute cores, called NSPs, split into four groups of 16 that the software addresses as QIDs. The card has no CUDA, so the vLLM that NVIDIA users install cannot drive it. vllm-qaic fills that gap. If the gap is filled below the code that writes /metrics, the picker can route to the card without knowing what it is.

The rest of this lesson checks where that line falls, series by series.

Chapter 2 of 11

What the plugin swaps out and what it leaves alone

vllm-qaic supplies a worker, a model runner and an attention backend, and vLLM's scheduler runs above them unchanged

vLLM has a hardware plugin system. A separate Python package declares an entry point in the group vllm.platform_plugins, and vLLM loads it at start-up. vllm-qaic declares qaic = "vllm_qaic:QaicPlugin". The plugin registers a platform class, QaicPlatform, and through it the classes vLLM should use for the parts that touch the hardware. The release examined here is v1.23.4. Its own README calls it not a stable release and points production users to the main branch or release/v0.15.0, a line built on vLLM 0.15.0. Main's README now names release/v0.15.0, release/v1.23.4 and release/v0.30.0 as the stable branches. The gauge result of this lesson holds on all of them, because every vLLM from 0.10.2 on leaves the null block out of the gauge. The v1.23.4 Dockerfiles pin vLLM 0.23.0, QEfficient release/v1.23.4 and the Cloud AI SDK 1.22 or later on Python 3.12.

The parts it replaces sit at the bottom. QaicWorker starts the device, opens a session on it and sets up communication between cards, with the collective backend qccl in place of NVIDIA's NCCL. QaicModelRunner prepares inputs in the fixed shapes the card expects, schedules prefill and decode on it, loads the compiled program and holds the attention backend, which manages the KV cache on the card. The platform class also names the environment variable that picks visible devices, QAIC_VISIBLE_DEVICES, where a GPU uses CUDA_VISIBLE_DEVICES.

The parts it keeps sit at the top. The OpenAI-compatible API server, the waiting queue, the scheduler that decides which requests run in each step, the KV cache manager that hands out blocks, and the Prometheus logger are all vLLM's own code from vllm.v1. The plugin's model runner consumes the same SchedulerOutput a GPU runner consumes. That is why the queue and running counts on a QAIC worker are exact. They are counted by the scheduler before any work reaches the card. The KV gauge is also computed by vLLM's own KV cache manager. Its meaning, though, depends on the block size and block count that the plugin chooses, and those are the next two chapters.

Chapter 3 of 11

Two ways to run on the card

AOT runs a program compiled ahead of time and carries every production feature, eager mode is for development

vllm-qaic has two execution modes. In AOT mode, short for ahead of time, Qualcomm's QEfficient library takes a Hugging Face model, exports it, quantises it if asked, and compiles it into a QPC, a program for the card. The plugin's runner then loads the QPC and feeds it. In eager mode, which the plugin's documents also call PYT, vLLM's own model code runs through a PyTorch backend for the card called torch_qaic, with kernels sent to the hardware one by one.

The mode is not a command-line switch. The platform class checks whether the torch_qaic package is installed. If it is missing, the plugin runs AOT, uses the worker class QaicWorkerAoT, and logs a warning and turns --enforce-eager off if someone passed it. If torch_qaic is installed, it runs eager with QaicWorkerPyt and turns enforce_eager on.

The feature matrix for v1.23.4 decides which mode a production pool uses. Only AOT has mxfp6, the card's 6-bit microscaling number format for weights, and the mxint8 KV cache set with --kv-cache-dtype mxint8. Only AOT has speculative decoding by n-gram, suffix, draft model or DFlash, LoRA adapters, disaggregated serving with separate encode, prefill and decode workers, embedding models and pipeline parallelism. Both modes have text generation, continuous batching and tensor parallelism across QIDs.

Compilation has a cost an operator sees. The plugin's serving guide says the first start takes 3 to 10 minutes for the download and the QPC build, and that later starts reuse the cached QPC when $HOME/.cache is mounted and QEFF_HOME points into it. The QPC is built for a context length equal to --max-model-len and a batch of --max-num-seqs sequences. Those two numbers are baked into the program, and they set the block geometry of the next chapter. Eager mode keeps vLLM's usual geometry, 16-token blocks counted by memory profiling, and so a finer KV gauge. It is still a development mode, because a pool there gives up quantisation, LoRA and speculative decoding.

Chapter 4 of 11

One block for each seat

In AOT mode a KV block is as long as the whole context, and there are max_num_seqs plus one of them

On a GPU, vLLM cuts the KV cache into small blocks, 16 tokens each by default in vLLM 0.23.0 and every version up to 0.33 (0.34 raised the default to 64), and gives a sequence one more block each time it grows by that many tokens. The lesson How the picker hears about the cache relies on those small blocks: each full block gets a hash that a later prompt can match.

The AOT QPC has no such pages. It reserves a fixed region of context for each sequence it can hold. The plugin makes vLLM's bookkeeping agree with that. In platform_base.py it sets cache_config.block_size = model_config.max_model_len, with the comment ctx_len. A sequence of any length up to the context limit therefore needs exactly one block. In worker.py the AOT worker's determine_available_memory reports room for max_num_seqs + 1 blocks, or for num_gpu_blocks_override + 1 when an override is set. vLLM then takes the override itself, when there is one, as the block count. initialize_cache asserts that the count is exactly max_num_seqs + 1, so the only override a v1.23.4 worker starts with is max_num_seqs + 1 itself. Any other value stops it at the assert.

The extra block is for vLLM. vLLM's V1 block pool, already at 0.8.5 and still at 0.23.0, takes block 0 out of the free list when it starts and keeps it as a null block, a placeholder that is never given to a request. Of the nine blocks with --max-num-seqs 8, eight can hold sequences. So the cache has exactly one block for each seat in the compiled batch.

The sizes follow from the model. The plugin's own examples serve Llama-3.1-8B-Instruct: 32 layers, 8 KV heads, 128 values per head. One token needs a key and a value in each head of each layer, 2 x 32 x 8 x 128 = 65,536 values. With an mxint8 cache at about one byte a value, that is 64 KiB a token, and one block of 2,048 tokens is 128 MiB. Nine blocks take 1,152 MiB of the card's memory, and 128 MiB of it is the null block.

The block_size label in vllm:cache_config_info shows this from outside. On the qwen3 GPU Pods it says 16. On the llama-qaic Pods it says 2048.

Chapter 5 of 11

A KV gauge that counts seats

With eight seats, vllm:kv_cache_usage_perc moves in eighths and reads 1.0 only when every seat is taken

vLLM computes vllm:kv_cache_usage_perc in its block pool. In vLLM 0.23.0, the version the plugin pins, the function get_usage subtracts one block for the null block and returns 1 - free / (num_gpu_blocks - 1). With nine blocks the denominator is eight. Each running sequence holds one block, so the gauge is the number of running sequences divided by max_num_seqs.

With --max-num-seqs 8 the gauge can take nine values only: 0, 0.125, 0.25, 0.375, 0.5, 0.625, 0.75, 0.875 and 1.0. It says nothing about how long the prompts are. A worker running one 50-token chat and a worker running one 2,000-token document both read 0.125. On the qwen3 GPU Pods the same gauge has thousands of 16-token blocks behind it, so it rises with every prompt's length and gives the picker a sense of memory pressure. On QAIC it duplicates vllm:num_requests_running.

That matters for the saturation backstop. The picker's utilization-detector plugin counts a worker as saturated when its KV use crosses kvCacheUtilThreshold, and the owner's notes record F5's generated value for it as 0.99. On a QAIC worker the gauge crosses 0.99 only at 1.0, when all eight seats are taken. That is the same moment the ninth request has to wait, so the KV threshold gives no warning ahead of the queue. A threshold of 0.85 sits between 0.75 and 0.875 and trips with one seat left. Pick a value between two steps, so the result does not depend on whether the comparison counts equality.

Older vLLM divided by all blocks. Up to vLLM 0.10.1, get_usage returned 1 - free / num_gpu_blocks, the null block counted as free capacity, and eight seats in nine blocks topped out at 8/9, 0.889. On that formula F5's 0.99 could never fire. With the pinned vLLM 0.23.0 the ceiling is 1.0. Read the vLLM version in the image before deciding which of the two a pool shows.

Chapter 6 of 11

Prompts in fixed pieces, and where the queue forms

The card prefills in 128-token chunks, and a ninth request waits until a seat frees

Prefill is the first pass over the prompt, the step that fills the KV cache before the first output token. The lesson Prefill and decode covers it on a GPU, where vLLM can split a long prompt into chunks of any size and mix them with decode steps of other requests.

The AOT QPC is compiled for fixed shapes, so the card takes a prompt in pieces of a fixed length called prefill_seq_len. The plugin reads it from override_qaic_config in --additional-config. If it is not set, the plugin uses min(128, max_model_len), which is 128 for a 2,048-token context. A 1,900-token prompt goes through as 15 pieces: fourteen full ones cover 1,792 tokens and the fifteenth carries the last 108.

The plugin also caps how many tokens vLLM's scheduler may hand over in one step: max_num_batched_tokens becomes the smaller of max_num_seqs x prefill_seq_len and vLLM's own value. With 8 seats and 128-token pieces that cap is at most 1,024 tokens a step, and exactly 1,024 when vLLM's own value is larger. In release v1.23.4 the plugin turns vLLM's chunked prefill off only for embedding models and vision encoders. For text generation vLLM's scheduler may still split a prompt across steps, and the card cuts each part into 128-token pieces. When chunked prefill is off, the plugin raises the step budget to at least max_model_len so a whole prompt still fits.

The queue forms at a hard edge. The compiled batch has eight decode lanes and the cache has eight usable blocks. While eight sequences run, the scheduler cannot admit a ninth however short it is, and vllm:num_requests_waiting goes from 0 to 1. On a GPU worker the edge is soft: a short request can often fit in the blocks left by long ones. That makes queue depth the strong signal on this hardware. A worker with a queue is full, and a worker without one has a free seat. The utilization-detector's queueDepthThreshold can say so directly, where the owner's lab sets it to 200000 for a demonstration that should never trip.

Chapter 7 of 11

No prefix cache to aim at

The plugin turns prefix caching off in both modes, so there are no events, no hits and nothing for affinity to gain

Prefix caching lets vLLM reuse the KV blocks of a prompt opening it has seen before. The picker's prefix scorer exists to send a prompt to the worker that holds its opening. On QAIC there is nothing to hold.

The plugin closes the door in four places. platform.py sets the command-line default of enable_prefix_caching to False. If someone passes --enable-prefix-caching anyway, platform_base.py in AOT mode switches it back off and logs "Prefix caching is not yet supported on v1 Engine. Will automatically disable it." In eager mode it is forced off with a comment that waits for paged attention. And the AOT worker's initialize_cache raises NotImplementedError("prefix caching is not supported on QAIC in V1") if the flag ever reaches it set. The feature matrix lists prefix caching as planned for both modes.

Three things follow at the metrics port. vllm:cache_config_info carries enable_prefix_caching="False". vLLM publishes KV cache events only for blocks it caches, so the ZeroMQ stream that the lesson How the picker hears about the cache follows stays silent. And vllm:prefix_cache_queries and vllm:prefix_cache_hits are registered but both stay at 0, because vLLM 0.23.0 returns from its cache lookup before it records a query when caching is off.

The picker does not know this on its own. With no events arriving, F5's picker falls back to speculative cache tracking: it remembers where it sent each prefix and believes that worker now holds it. On QAIC that belief is always false. If the prefix scorer keeps its weight, it steers every prompt with a shared system prompt to the same Pod. That Pod fills its eight seats first and queues while its neighbours sit idle, and the steering gains nothing, because the Pod reads the prompt again from the start anyway. Comparing f5_epp_prefix_index_lookups_total{result="hit"} on the picker with vllm:prefix_cache_hits on the workers shows the gap: the picker counts hits that never happen.

Chapter 8 of 11

Six changes to the F5EPP

The pool keeps engine vllm and gets a picker tuned for seats, queues and no cache affinity

The llama-qaic pool gets its own F5EPP, because each pool has exactly one picker, as the lesson Wiring a pool to its picker showed. Most of the generated configuration fits the card as it is. Six settings need attention.

First, spec.engine stays vllm. The QAIC workers are vLLM, and vllm selects the series names above and ZeroMQ for events. spec.server.modelServerMetricsPort stays 8000. The five extractor specs keep their generated values. That includes cacheInfoSpec. The owner's notes say its block_size label feeds only prefix matching, which the next two changes switch off, so on this pool it does no harm and needs no change.

Second, remove the zmq-wire plugin, the picker's ZeroMQ subscriber. The owner's lab removes it with a $patch: delete entry for pools of simulated workers, which publish no matching events either. A QAIC pool publishes none at all.

Third, set the weight of f5-prefix-cache-scorer to 0 in the scheduling profile under spec.eppConfig.config.schedulingProfiles. Until Qualcomm ships prefix caching, affinity can only concentrate load. The load scorers then decide alone.

Fourth, set kvCacheUtilThreshold in seat terms. With --max-num-seqs 8, 0.85 trips with one seat left. Or lean on queueDepthThreshold, which the last chapter showed is the honest signal here. Both live in the utilization-detector plugin's parameters.

Fifth, spec.tokenizer.name must equal the model name the QPC serves, here meta-llama/Llama-3.1-8B-Instruct. A mismatch makes epp_tokenizer_guard_events_total{event="encode_failed"} count every request, and the token-weighted scorer runs blind.

Sixth, set loraSpec only if the pool serves adapters. LoRA works in AOT mode only, cannot be combined with speculative decoding or disaggregated serving, and max_loras defaults to 1. vllm:lora_requests_info then lists the running and waiting adapters for the picker's LoRA affinity.

Chapter 9 of 11

No simulator under the plugin

The workers need real devices at start-up, and the free hosted options have no /metrics

A pool on new hardware would ideally be tested first on a laptop. vllm-qaic offers no path for that. Both workers count real devices before they do anything else. The AOT worker's init_device imports qaicrt, Qualcomm's runtime library, and calls Util().getDeviceIds() to learn which cards exist. A device_group in the configuration that names an ID not in that set logs "Device id ... not available!!". The eager worker asserts that its local rank is below torch.qaic.device_count() and that the cards it needs are visible. No card means no worker, and no worker means no /metrics.

Qualcomm's SDK does have a simulator, at a lower layer. The owner's notes record that the qaic-exec tool, which runs a compiled QPC directly, runs in a simulator mode on an ordinary x86 machine unless told to use hardware, and that Qualcomm calls it significantly slower for larger models. It runs a program on a simulated card. It does not create a device that qaicrt would enumerate, and the plugin contains no simulator or emulator path. It helps a compiler engineer. It does not help a picker test.

The free Cloud AI 100 Ultra Developer Playground is an API in front of hosted models. It has no virtual machine and no /metrics page for the picker to scrape.

What can be tested without a card is the picker's side. The llm-d inference simulator already in the owner's lab speaks vLLM's metrics. It can be set to --max-num-seqs 8 and --max-model-len 2048, run with no KV event publishing, and given a prefill time per token that resembles the card. Pointed at by an F5EPP with the six changes, it shows whether f5_epp_prefix_index_lookups_total stops counting, whether the picker spreads by queue, and whether the saturation detector trips. It cannot copy the block geometry. In version 0.8.0 --block-size accepts 8, 16, 32, 64 or 128, so a 2,048-token block is out of reach, and its KV gauge will be finer than a card's. Test the gauge threshold on a card.

Chapter 10 of 11

Where a real card can be rented

An AWS dl2q.24xlarge or bare metal from Cirrascale, then the same /metrics check

Two routes give a machine with Cloud AI cards and root access, which the plugin needs.

The self-serve one is AWS EC2 DL2q. One size exists, dl2q.24xlarge. AWS's product page lists 8 Qualcomm AI 100 accelerators with 16 GiB of memory each, which the page totals as 128 GB (8 × 16 GiB is 128 GiB, about 137 GB), 96 vCPUs on second-generation Intel Xeon Scalable processors, 768 GiB of system memory, 100 Gbps of network bandwidth and EBS storage only. The on-demand price on that page is $8.919 an hour, with $5.352 and $3.568 for one-year and three-year reservations. The Qualcomm SDKs come with AWS's Deep Learning AMIs. The cards in DL2q are the Cloud AI 100 Standard model.

The other route is Cirrascale. Its inference cloud with Qualcomm cards deploys models behind an API with one click, which hides /metrics like the Playground. Cirrascale also offers Cloud AI 100 Ultra cards as bare metal on request, and bare metal is what a picker test needs.

The card size shapes what such a test can serve. Qwen3-32B, the model of the GPU pool, needs 34.3 GB for its FP8 build and 65.5 GB in BF16. The FP8 files are larger than one byte a weight because the input embedding and the separate output layer, each 151,936 × 5,120 values, stay in BF16 at two bytes a value, about 3.1 GB of the total. Neither fits a 16 GiB card. Even in mxfp6, at about 6.25 bits a weight once the shared scales are counted, its 32.8 billion weights take about 25.6 GB. It would have to be split across cards with tensor parallelism, and dense Qwen3 is not on QEfficient's validated model list for release v1.23.4. Llama-3.1-8B-Instruct, which the plugin's guides use, has 8.03 billion weights: about 6.3 GB in mxfp6, which leaves room on one card for the 1.1 GiB cache of the earlier chapter.

On the machine the check is short. Start vllm serve with the plugin, run curl localhost:8000/metrics, and confirm the five series, a block_size label equal to --max-model-len, and nine possible values of the gauge. Then point the same F5EPP at the real Pods.

Chapter 11 of 11

What is moving upstream

The plugin's main branch already has paged attention for AOT, and the picker settings should be checked again on each upgrade

Everything above is release v1.23.4, the line whose Dockerfiles pin vLLM 0.23.0. The plugin is moving fast. In the week after that release, its main branch took a merge of the development branch on 18 November 2026 and a change named Paged Attention AOT on 24 November 2026.

The main branch on 25 November shows where that leads. Its platform code now has a path for AOT with prefix caching switched on, where the block size comes from a user-set --block-size or from prefill_seq_len, and the block count becomes ceil(max_model_len / block_size) x max_num_seqs + 1. With prefix caching off the formula still gives a block size of max_model_len and nine blocks for eight seats, the geometry of this lesson. The AOT worker on main still raises NotImplementedError when prefix caching reaches it, the command-line default is still off, and the feature matrix still lists prefix caching as planned. So the picker settings above still hold on main. Qualcomm's roadmap, last updated June 2026, lists LMCache integration and llm-d orchestration as ongoing for AOT. llm-d routes through the same Gateway API Inference Extension contract the F5 picker implements. Main's README also says the branch is being rebased onto vLLM v0.30.0, so its code changes from day to day.

When the plugin is upgraded, four lines of /metrics tell the operator whether to change the F5EPP. If the block_size label drops from the context length to 128, the KV gauge has become a memory gauge, and kvCacheUtilThreshold can move back toward F5's default. If enable_prefix_caching turns "True" and vllm:prefix_cache_hits starts rising, the prefix scorer can get its weight back. If the image publishes KV events, the zmq-wire plugin can return, with spec.blockSize set to the workers' block size. And the vLLM version in the image decides whether the gauge ends at 1.0 or at 8/9.

What to keep

The page decides, so read the page

The F5 picker routes to a Qualcomm Cloud AI 100 card through the same vLLM metrics it reads from an H100, because vllm-qaic replaces only the worker, the model runner and the attention backend, and leaves vLLM's scheduler, KV cache manager and Prometheus logger in charge of the numbers. Queue and running counts are exact. The KV gauge is exact too, but in AOT mode it counts seats: one block of max_model_len per sequence, max_num_seqs + 1 blocks with block 0 held back, so with eight seats it moves in steps of 0.125 and reaches 1.0 at the same moment the queue starts. Prefix caching is off on the card, so the picker should not chase it. For a QAIC pool, keep engine vllm, remove zmq-wire, set the prefix scorer's weight to 0, put the saturation threshold between two seat steps or lean on the queue, match the tokenizer name, and set loraSpec only with adapters. Test the picker's side on a simulator, test the gauge on a rented card, and read /metrics again on every plugin upgrade.
