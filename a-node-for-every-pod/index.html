Kubernetes underneath

A node for every Pod

How the scheduler filters, scores, binds and sometimes evicts

Every Pod starts without a node. One program, kube-scheduler, gives it one, and it does so by writing a single field. Its decision is made by a chain of small plugins that run at named steps: some rule nodes out, some rank what is left, one writes the result. This lesson follows that chain on the cluster northlight-eu, where two GPU nodes are shared by the model servers of the Deployment qwen3 and by a batch Job that evaluates models overnight. Both want the same eight GPUs. You will see a model server placed by filtering and scoring, with every score worked out, and what would change if the cluster packed GPUs instead of spreading them. Then a later model server takes a GPU from the batch Job by priority, a waiting Pod is explained from its message and brought back by the queue, and the lesson ends where plain priority stops being enough for a shared GPU pool, and what an operator watches.

Chapter 1 of 15

A Pod with no node joins a queue

Three places to wait: active, backoff and unschedulable

The Deployment qwen3 is scaled from two model servers to three. The new Pod, qwen3-6f7d9c8b4-r8n5w, is stored with an empty spec.nodeName. The scheduler, kube-scheduler, watches for exactly such Pods and keeps them in a scheduling queue with three parts. The active queue holds Pods ready for an attempt, ordered by priority and then by arrival time. The scheduler takes one Pod from its head at a time. A Pod that could not be placed moves to the unschedulable pool and stays there until something in the cluster changes that might help it, such as a Pod being deleted or a node being added. It then passes through the backoff queue before it is tried again.

The backoff grows with every failed attempt. The first wait is podInitialBackoffSeconds, 1 second by default, and each further failure doubles it, up to podMaxBackoffSeconds, 10 seconds by default. So the waits run 1, 2, 4 and 8 seconds, and 10 seconds for every attempt after that. A Pod that sits in the unschedulable pool for 5 minutes without any helpful event is moved back anyway. A sweep that checks for such Pods runs every 30 seconds, so in practice the retry comes between 5 and 5.5 minutes after the last attempt.

Before a Pod enters the active queue at all, PreEnqueue plugins must all agree. The plugin SchedulingGates is one of them. A Pod created with entries in spec.schedulingGates is held back with the status SchedulingGated until another controller removes the gates. Gates can only be removed, never added after creation. A gated Pod is not eligible for any attempt, so the metric scheduler_pending_pods counts it under a fourth label of its own, gated, apart from the Pods that are active, in backoff or unschedulable. Priority orders the queue, but it does not block it. If the Pod at the head cannot be placed, the scheduler moves on and tries Pods of lower priority.

Chapter 2 of 15

The plugins that make up the default scheduler

One profile, twenty plugins, each at the steps it implements

kube-scheduler has no fixed algorithm. It runs a profile, a named list of plugins, and every plugin implements one or more extension points: the named steps of a scheduling attempt. The default profile is called default-scheduler. In release 1.37 its list, in order, is SchedulingGates, PrioritySort, NodeName, NodeUnschedulable, TaintToleration, NodeAffinity, NodePorts, NodeResourcesFit, VolumeRestrictions, NodeVolumeLimits, VolumeBinding, VolumeZone, PodTopologySpread, InterPodAffinity, DefaultPreemption, NodeResourcesBalancedAllocation, ImageLocality and DefaultBinder. Each plugin is enabled at every step it implements, which the configuration calls MultiPoint.

Some plugins join when a feature is on. Dynamic resource allocation has been stable and on since 1.34, so DynamicResources is added before DefaultPreemption with a score weight of 2. It handles Pods that ask for devices through ResourceClaims. Since 1.37 the gate DRAExtendedResource is stable, so a DeviceClass may also declare extendedResourceName: nvidia.com/gpu, and then DynamicResources serves ordinary nvidia.com/gpu requests from DRA devices too. This cluster has no such DeviceClass, so DynamicResources does nothing for qwen3-6f7d9c8b4-r8n5w, whose nvidia.com/gpu comes from the device plugin. The gate NodeDeclaredFeatures is stable and locked on in 1.37, so the plugin NodeDeclaredFeatures is appended to the list as well. It lets nodes report the features they support in their status and rejects a node that lacks a feature the Pod needs. With the 18 plugins above, that makes 20 in a default 1.37 profile. Gang scheduling, which places a group of Pods all at once or not at all, is behind the gate GenericWorkload, beta and off by default in 1.37.

A few of the simple filters matter for every Pod. NodeName rejects every node but the one named, if spec.nodeName was set by hand. NodeUnschedulable rejects a cordoned node. NodePorts rejects a node where a requested host port is taken. The filters for one Pod run on many nodes at the same time, in up to 16 goroutines by default, set by parallelism. Only one QueueSort plugin may be enabled, and all profiles must use the same one, because there is only one queue.

Chapter 3 of 15

The scheduler counts requests, never usage

The first filter that matters: NodeResourcesFit

One attempt to place a Pod is a scheduling cycle. It starts with the PreFilter and Filter extension points. An extension point is a named step where plugins run. Filter plugins rule out nodes that cannot run the Pod, and the first plugin to say no ends the checks for that node. NodeResourcesFit is the one that does capacity. It adds up the requests of the Pods already assigned to a node, adds the new Pod's requests and compares the sum with the node's allocatable amount. It never looks at what the Pods use. A batch Pod that requested a GPU and 32 Gi holds them in the scheduler's books while it sits idle. A container with no requests adds nothing to the sum, however much it later uses. Both GPU nodes pass for qwen3-6f7d9c8b4-r8n5w.

A GPU is an extended resource, and extended resources follow stricter rules than CPU and memory. A container may give a GPU limit without a request, and then the request equals the limit. If it gives both, they must be equal. A request without a limit is invalid. Extended resources cannot be overcommitted, and a GPU cannot be split: the count is a whole number. So the sum on a node can never exceed 4 here, and one Pod that asks for one GPU holds one whole H100 in the books whether vLLM keeps it busy or not.

When this filter rejects a node, it says why in words that end up in the Pod's events: Too many pods, Insufficient cpu, Insufficient memory, Insufficient ephemeral-storage, or Insufficient followed by the resource name, such as Insufficient nvidia.com/gpu. A Pod created with spec.nodeName already set skips the scheduler entirely. If the node has no room, its kubelet then refuses the Pod with a reason such as OutOfcpu.

Chapter 4 of 15

How a GPU node describes itself

A count from the device plugin, labels from GPU feature discovery

The scheduler knows nothing about a GPU beyond what the Node object says. Two programs on each node put that there. The NVIDIA device plugin talks to the kubelet over the kubelet's device plugin API. It registers the resource name nvidia.com/gpu and keeps a stream open, called ListAndWatch, on which it reports each GPU and whether it is healthy. The kubelet writes the count into the Node's status as capacity and allocatable. If a GPU goes unhealthy, allocatable drops and the scheduler stops placing new Pods on it.

A count cannot tell an H100 from a smaller card. That is the job of GPU feature discovery, which publishes labels on the node. nvidia.com/gpu.product names the model, such as NVIDIA-H100-80GB-HBM3. nvidia.com/gpu.count gives the number of GPUs, nvidia.com/gpu.memory the memory of one GPU in MiB, and nvidia.com/gpu.family the architecture. When a GPU is split with MIG, the product label is changed to show the slice, in the form A100-SXM4-40GB-MIG-1g.5gb. When a sharing strategy is used, nvidia.com/gpu.replicas shows how many shares each GPU is counted as, and the product label may be changed too.

Labels drive placement, so who may write them matters. A kubelet can label its own Node object. A compromised node could therefore relabel itself to attract GPU workloads, and with them model weights and prompts. Labels under the prefix node-restriction.kubernetes.io/ cannot be set by the kubelet when the NodeRestriction admission plugin is on, so selecting on such labels closes that path. The two nodes here also carry topology.kubernetes.io/zone, which the spreading rule later uses.

Chapter 5 of 15

Labels, affinity and taints say where a Pod may go

NodeAffinity selects nodes by label, and taints keep Pods away

Capacity is one question. The other filters ask whether this Pod may use this node at all. The simple form of selection is nodeSelector, a map of labels the node must carry. Node affinity is the fuller form. A rule under requiredDuringSchedulingIgnoredDuringExecution is a filter. It holds a list of nodeSelectorTerms: a node passes if it matches any one term, and within one term every expression must match. The operators are In, NotIn, Exists, DoesNotExist, Gt and Lt. A rule under preferredDuringSchedulingIgnoredDuringExecution only adds to a node's score, with a weight from 1 to 100, and the weights of the matching rules are summed for each node. The NodeAffinity plugin handles both.

Taints work the other way round. A taint on a node keeps away every Pod that does not carry a matching toleration, and the TaintToleration plugin enforces it. A toleration with operator Equal matches a key and a value. One with Exists matches the key with any value, and an empty key with Exists matches every taint. A toleration lets a Pod onto a tainted node. It does not steer it there, so GPU workloads usually need both a selector and a toleration. The documentation suggests tainting GPU nodes with the resource name and turning on the ExtendedResourceToleration admission plugin, which adds the matching toleration to any Pod that requests that resource.

Some taints are added by Kubernetes itself. The node lifecycle controller turns bad node conditions into NoSchedule taints such as node.kubernetes.io/memory-pressure, disk-pressure, pid-pressure and network-unavailable, kubectl cordon sets spec.unschedulable to true on the Node, and the node lifecycle controller then adds the taint node.kubernetes.io/unschedulable with effect NoSchedule. The scheduler never reads the node conditions themselves. It reads the taints through TaintToleration. A cordon it reads from spec.unschedulable, through its filter NodeUnschedulable, which rejects the node with node(s) were unschedulable unless the Pod tolerates the unschedulable taint. Every Pod also receives tolerations for not-ready and unreachable with tolerationSeconds 300, so it stays bound for 5 minutes after its node goes bad.

Chapter 6 of 15

Spreading model servers across zones

PodTopologySpread counts the matching Pods in each zone

Two model servers on one node share that node's fate. A topology spread constraint tells the scheduler to keep matching Pods even across a set of domains. A domain is the group of nodes that share one value of a label, named by topologyKey. With the key topology.kubernetes.io/zone every zone is a domain. maxSkew is the largest allowed difference between the domain with the most matching Pods and the domain with the fewest. whenUnsatisfiable says what to do when a node would break that limit. DoNotSchedule, the default, makes the constraint a filter. ScheduleAnyway makes it a score. The Deployment qwen3 uses maxSkew 1 across zones with DoNotSchedule. There is one qwen3 Pod in each zone now, so a third may go to either. A fourth will have only one zone open to it.

Three optional fields change the counting. minDomains, only with DoNotSchedule, says how many domains there should be. If fewer eligible domains exist, the smallest count is treated as 0, which pushes Pods into new domains, useful when an autoscaler can add nodes. nodeAffinityPolicy decides whether nodes the Pod's own selector rules out are counted, and its default Honor leaves them out. nodeTaintsPolicy does the same for taints, and its default Ignore counts tainted nodes anyway. So a tainted node in an empty zone can still count as a domain with 0 Pods and block placement elsewhere. A node that lacks the topologyKey label is rejected with the reason node(s) didn't match pod topology spread constraints (missing required label).

Only one constraint is allowed for each pair of topologyKey and whenUnsatisfiable. The built-in soft spread applies only to a Pod that sets no constraint of its own and belongs to a Service, ReplicaSet, StatefulSet or ReplicationController, because its selectors are computed from those owners. qwen3-6f7d9c8b4-r8n5w qualifies through its ReplicaSet and the Service qwen3. The documentation advises defining your own constraints when nodes do not carry both kubernetes.io/hostname and topology.kubernetes.io/zone, and says nodes missing a key are not scored. The 1.37 source is more lenient for these built-in defaults: it requires every key only when the Pod sets its own constraints or a cluster default is configured, so a node without a zone label is still scored for the hostname spread.

Chapter 7 of 15

Scores rank the nodes that are left

Each plugin gives 0 to 100, and weights add them up

Two nodes passed every filter, so the cycle moves to PreScore and Score. Each score plugin gives every remaining node a number from 0 to 100. The scheduler multiplies each number by the plugin's weight and adds them up. The default weights are 3 for TaintToleration, 2 for NodeAffinity, PodTopologySpread and InterPodAffinity, and 1 for NodeResourcesFit, NodeResourcesBalancedAllocation and ImageLocality.

NodeResourcesFit scores too. Its default strategy, LeastAllocated, favours the node with the larger share of unrequested CPU and memory. For each resource it computes the free part times 100 divided by the allocatable amount, rounded down, and then averages the resources by weight. It does not count GPUs unless you add them to its list of resources. NodeResourcesBalancedAllocation favours a node whose CPU and memory would be used in the same proportion. With two resources it takes half the difference of their two fractions as the spread, and scores 100 times one minus that spread. In 1.37 it scores how much the new Pod improves that balance, which gives 75 when nothing changes. ImageLocality favours a node that already holds the Pod's images, by their size, counted from 23 MiB and capped at 1000 MiB for each container. A model server image of many gigabytes scores no higher than a 1 GB one.

Here every plugin ties except NodeResourcesFit, and gpu-node-2 has more room. The highest total wins, and a tie is broken at random. In a large cluster the scheduler stops searching once it has enough feasible nodes, a limit set by percentageOfNodesToScore.

Chapter 8 of 15

Packing GPUs instead of spreading them

MostAllocated, with GPUs added to the resources it scores

Spreading is the right default for web servers. For GPUs it has a cost. LeastAllocated put qwen3-6f7d9c8b4-r8n5w on gpu-node-2, which now has one GPU free, and gpu-node-1 also has one free. Two free GPUs, but on different nodes. A later Pod that needs two GPUs on one node cannot run anywhere, although the cluster has two free. Packing does the opposite. It fills one node before it starts the next, so free GPUs gather in one place.

The scheduler supports this through the scoringStrategy of NodeResourcesFit in its configuration. With type MostAllocated a node scores higher the more of it is requested: requested times 100 divided by allocatable, rounded down, for each resource. The list of resources is cpu and memory with weight 1 each unless you change it. Adding nvidia.com/gpu with weight 3 makes the GPU count three times as much as either of the others, which is the example the documentation uses for extended resources.

Worked through for qwen3-6f7d9c8b4-r8n5w: on gpu-node-1, GPUs 4 of 4 give 100, cpu 24 of 64 gives 37, memory 192 of 512 gives 37. The weighted average is (100 × 3 + 37 + 37) / 5 = 374 / 5, which is 74. On gpu-node-2, GPUs 3 of 4 give 75, cpu 20 of 64 gives 31 and memory 160 of 512 gives 31. That is (75 × 3 + 31 + 31) / 5 = 287 / 5, which is 57. MostAllocated would choose gpu-node-1 and fill it, leaving gpu-node-2 with two free GPUs side by side. A third strategy, RequestedToCapacityRatio, takes a shape: a list of points that map utilization to score, so any curve between spreading and packing can be drawn.

Chapter 9 of 15

Reserve, permit, then bind

The scheduling cycle ends and the binding cycle starts

The scheduler has chosen gpu-node-2. Before it tells anyone, it books the choice in its own cache, so that the next Pod it considers already sees one GPU fewer on that node. Reserve plugins are told at the same moment, and Permit plugins may approve, deny or delay the Pod. A delay has a timeout, and the framework caps it at 15 minutes. When a wait times out it becomes a denial. Whenever a Pod fails after Reserve, every Reserve plugin's Unreserve runs and the Pod goes back to the queue. That ends the scheduling cycle. Scheduling cycles run one at a time, which is why two Pods are never given the same last GPU.

The binding cycle runs separately, and several may run at once. PreBind plugins do work that must finish first, such as preparing a volume. VolumeBinding waits up to bindTimeoutSeconds, 600 by default, for volumes to be bound. An error in PreBind sends the Pod back to the queue. Bind plugins are then tried in order, and the first that chooses to handle the Pod does it, so the others are skipped. The default one, DefaultBinder, posts a Binding object to the API server, which sets spec.nodeName on the Pod. PostBind plugins are told afterwards, for their own bookkeeping.

The scheduler records the success as a Normal event with reason Scheduled, reported by default-scheduler, with the message Successfully assigned inference/qwen3-6f7d9c8b4-r8n5w to gpu-node-2. It contacts no node. The kubelet on gpu-node-2 learns of the Pod through its own watch, and the scheduler's part is done until the Pod is deleted and its GPU returns to the books.

Chapter 10 of 15

A model server takes a GPU from a batch job

When no node passes the filters, PostFilter runs preemption

Later the batch team raises the parallelism of the Job nightly-eval from three to five, and its two new Pods take the last free GPUs. Then traffic grows and a fourth model server, qwen3-6f7d9c8b4-h4zj6, is created. Every node fails the filters, so the PostFilter extension point runs. Its default plugin is DefaultPreemption. Each Pod has a priority, an integer copied from its PriorityClass. The model servers have 1000 and the batch Pods 100.

The plugin asks, for each node, whether qwen3-6f7d9c8b4-h4zj6 would fit if Pods of lower priority were removed. It does not try every node in a large cluster. It looks at a sample of at least 10 percent of the nodes and at least 100, or all of them when there are fewer. A node that failed a filter with UnschedulableAndUnresolvable, such as a missing label or an untolerated taint, is skipped, because removing Pods cannot fix that. A node is also skipped if the Pod has inter-pod affinity to the low-priority Pods there. There is no preemption across nodes: the victims must all be on the node where the Pod will run.

On gpu-node-1 qwen3-6f7d9c8b4-h4zj6 would fit by removing one batch Pod, and the zones would hold two qwen3 Pods each. On gpu-node-2 a third qwen3 Pod would break the zone spread whatever is removed. When several nodes qualify, the scheduler prefers the one where preemption breaks the fewest PodDisruptionBudgets, then the one whose victims have the lowest priority, and so on. A PriorityClass value can be anything from −2147483648 to 1000000000. Larger values are reserved for the built-in classes system-cluster-critical, 2000000000, and system-node-critical, 2000001000.

Chapter 11 of 15

The victim leaves, and the GPU is handed over

A condition, an event, a grace period, then the bind

Before it deletes a victim, the scheduler marks it. It adds the condition DisruptionTarget with status True, reason PreemptionByScheduler and the message default-scheduler: preempting to accommodate a higher priority pod. Then it deletes the Pod and records on it a Normal event with reason Preempted and the message Preempted by pod, followed by the preemptor's UID and on node gpu-node-1. A workload controller or a person reading the victim later can tell from these that it was pushed out on purpose and did not crash.

The victim is not killed at once. It gets its normal graceful termination, terminationGracePeriodSeconds, 30 seconds by default. During that time its GPU is still in use, and qwen3-6f7d9c8b4-h4zj6 waits with status.nominatedNodeName set to gpu-node-1. That field is only a note. If another node frees up first the Pod may go there, and a Pod of still higher priority may take the freed GPU, in which case the field is cleared. The documentation suggests giving low-priority Pods a short grace period, even zero, to close this gap. For a batch evaluation that checkpoints its work, a short grace period loses little.

Here the batch Pod exits after 11.5 seconds, illustrative. The kubelet on gpu-node-1 removes the Pod object. The scheduler sees the deletion, tries qwen3-6f7d9c8b4-h4zj6 again with the nominated node first, finds one free GPU on gpu-node-1 and binds it there. The new model server now needs its three minutes to load the weights. From the moment traffic called for a fourth model server to the moment it can answer, about three minutes and twelve seconds pass, and only the first twelve were spent on scheduling.

Chapter 12 of 15

Reading why a Pod is Pending

One event, one condition, and a count for each reason

The Job controller replaces the Pod it lost, and the replacement finds no free GPU. Its priority is 100 and nothing on either node is lower, so preemption cannot help. The scheduler records the outcome in two places. The Pod's PodScheduled condition becomes False with reason Unschedulable. An event of type Warning with reason FailedScheduling carries the same message, and kubectl describe pod shows it at the bottom. If the scheduler itself failed, the reason is SchedulerError instead.

The message has a fixed shape. It starts with 0/N nodes are available, then a colon, then a count and a reason for each kind of failure, sorted as text and joined by commas, ending with a full stop. Each node is counted once, under the first filter that rejected it. If a PreFilter plugin rejected the Pod before any node was looked at, its message replaces the whole list. A second part that starts with the word preemption says why evicting other Pods would not help either. The event's message can be cut short to fit the event size limit, and the condition's message is not, so the condition is the place to read a long one. Some pages of the documentation still show an older form without the count before each reason.

The Pod then waits in the unschedulable pool until a GPU is released. Nothing is broken. The batch work waits because the cluster's owner ranked serving above it. A Pod that never gets a FailedScheduling event at all was never tried: check that spec.schedulerName names a scheduler that runs, and that spec.schedulingGates is empty.

Chapter 13 of 15

How a waiting Pod gets another chance

Cluster events, queueing hints, backoff and the 5 minute sweep

A Pod in the unschedulable pool is not retried on a timer. It waits for an event in the cluster that might help it. Each plugin that can reject a Pod also says which events could change its mind, and registers a small function called a queueing hint for each. NodeResourcesFit cares about Pods being deleted and nodes gaining allocatable resources. DefaultPreemption registers for the deletion of an assigned Pod. When such an event arrives, the hint looks at it and answers whether the parked Pod might now fit. Only then does the Pod move on, through the backoff queue, to the active queue.

The batch Pod has failed once, so its next attempt waits 1 second after it is woken. If it fails again, 2 seconds, then 4, then 8, and 10 for every attempt after that. A Pod with preemptionPolicy Never is placed in the queue by its priority like any other, so it still jumps ahead of lower-priority Pods, but it never evicts anyone and it is subject to the same backoff. That suits a batch job that should start before others but must not disturb what is running.

If no helpful event comes, the 5 minute rule applies. Five minutes after its last attempt, at the next 30-second sweep, the Pod is moved back and tried again. Here that happens at about 1212.5 seconds. The cluster is still full, so it fails with the same message and goes back to the pool. The cost of all this waiting is small. A parked Pod uses no GPU and only a little of the scheduler's memory, and the queue's state is visible as the metric scheduler_pending_pods with the labels active, backoff, unschedulable and gated.

Chapter 14 of 15

Where priority alone stops being enough

One shared GPU pool needs guarantees, and stock Kubernetes has priority

PriorityClass and preemption let serving win over batch, as this lesson showed. Used alone across a large shared pool, they have a known flaw. The owner's notes on a KubeCon talk by the team behind Nebius Token Factory describe it. They ran every inference workload of a region on one GPU node pool: dedicated endpoints with capacity promised to a customer, public endpoints, non-production and batch. With plain priority in that order, one dedicated customer scaling up could take nearly the whole pool and push a public endpoint down. A tier that ought to give up only its spare GPUs ended up giving up all of them.

What they wanted was a quota for each workload, a number of GPUs that stays available to it, and priority only for demand above the quota. They tried an Excel sheet and an on-call engineer evicting Pods by hand, and two Deployments per workload, before choosing a specialised scheduler. Of those they compared, only KAI Scheduler and Kueue could preempt above-quota Pods in order of priority. They picked KAI, NVIDIA's open-source GPU scheduler, because it is a scheduler and Kueue only admits work and needs one, because it places GPUs and CPUs with NUMA in mind, and because its preemption delay gives the cluster autoscaler time to add nodes before anything is evicted. Their example: a dedicated endpoint with a quota of 4 GPUs and 2 GPUs per Pod has two replicas guaranteed, and a third runs above quota and can be preempted.

Two more limits apply to model servers. The owner's deck notes that a model spread over several nodes is a group of Pods that must start together, which stock Kubernetes does not schedule. Release 1.37 has gang scheduling behind a feature gate that is off by default. And a preempted replica gets only its grace period, 30 seconds by default, to finish the answers it is streaming.

Chapter 15 of 15

What an operator watches

Events, metrics and the scheduler's own configuration

Most scheduling questions are answered by the Pod itself: its PodScheduled condition, its nominatedNodeName and its events. Across a cluster, kubectl get events -A --field-selector reason=FailedScheduling lists every Pod that could not be placed recently. Every scheduling event carries the scheduler's name, from the Pod's spec.schedulerName, as the reporting controller, which tells events of two schedulers apart.

kube-scheduler serves metrics on its secure port, 10259 by default. scheduler_schedule_attempts_total counts attempts by result: scheduled, unschedulable and error. scheduler_pending_pods shows the queue by part: active, backoff, unschedulable and gated. scheduler_unschedulable_pods counts waiting Pods by the plugin that rejected them, which turns a cluster-wide shortage of GPUs into one rising line labelled NodeResourcesFit. scheduler_preemption_attempts_total and scheduler_preemption_victims show how often serving pushes out batch and how many Pods it costs each time. scheduler_pod_scheduling_sli_duration_seconds measures the time from a Pod entering the queue to being bound, and scheduler_plugin_execution_duration_seconds shows which plugin is slow.

The configuration lives in a file passed with kube-scheduler --config, with apiVersion kubescheduler.config.k8s.io/v1. The older v1beta3 was removed in 1.29. A file can define several profiles, each with its own plugins and weights, and a Pod picks one by its spec.schedulerName. Setting disabled with the name '*' at an extension point turns all default plugins there off. In a cluster with several control plane nodes, only one scheduler is active at a time. Leader election is on by default with a lease named kube-scheduler, held for 15 seconds and renewed within 10. The scheduler's own client may send 50 requests per second to the API server, with bursts of 100.

What to keep

Filter, score, bind, and sometimes evict

The scheduler takes one Pod at a time from a queue ordered by priority. Filter plugins remove the nodes that cannot run it: too little unrequested capacity, the wrong labels, a taint, a spread rule. Score plugins rank the rest, by default spreading Pods out, or packing GPUs when the configuration says so, and the binding cycle writes the winner into spec.nodeName. When no node passes, preemption may delete Pods of lower priority to make room, which is how model servers and batch work can share GPUs without an operator deciding each time. A Pod that still cannot be placed waits for an event that might help it, or for the 5 minute sweep. Priority alone cannot promise any workload a share of the pool, which is where quota-aware GPU schedulers come in. Everything the scheduler did is written on the Pod and in its metrics, so a Pending Pod can always be explained.
