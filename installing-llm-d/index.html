Inference

Installing llm-d

Two charts, one values file, three recipes

llm-d is an open source project that puts a smart router in front of a fleet of vLLM model servers on Kubernetes. Red Hat, Google, IBM, CoreWeave and NVIDIA are among the companies that founded it, and it reached version 1.0.0 on 20 October 2026. Other lessons on this site take its pieces apart: how a picker chooses a GPU, how it hears about the cache, why prefill and decode are split. This lesson is about putting it on a cluster.

The owner's course frames the install as two Helm commands and a values file that says what the fleet looks like. In the course, helm install router installs the llm-d router and sets up the vLLM servers, and helm install model installs the model. In the charts llm-d ships, the split is cleaner: the router chart installs the router and its InferencePool, and the model chart (or, in the v1.0 guides, a Kustomize overlay) creates the vLLM servers. Behind those commands sits a problem that takes weeks to solve by hand: every behaviour of the router has a knob, and the right setting depends on the model, the GPU and the traffic. llm-d answers it with well-lit paths, ready-made configurations with every knob already set and measured on real hardware. The course calls them recipes, and this lesson does too in that everyday sense.

The lesson follows northlight-eu, where the Deployment qwen3 already serves Qwen3-32B in its FP8 build (34.3 GB of weights) from two Pods, one H100 each. It installs the router in front of them, hands the fleet to the model chart, swaps the values file to change the fleet's shape, checks that routing really follows the cache, then walks the three recipes most teams choose from: the optimized baseline, the prefill and decode split and wide serving for giant models.

Chapter 1 of 13

Four knobs, and weeks to set them by hand

Everything the router does has a setting behind it, and the settings depend on each other.

The course names four knobs. The first is how much the router should favour a server that already holds a request's saved work, its KV cache, over a server that is simply less busy. The second is whether to split the servers that read prompts (prefill) from the servers that write answers (decode), and how many of each to run. The third is how many GPUs one copy of the model spans. The fourth is how many requests each server takes into one batch before it starts to fall behind. Each one moves both speed and cost.

In llm-d 1.0 the first knob is a set of real parameters. The prefix-cache-affinity-filter keeps only the workers whose estimated cache match for this prompt is at least affinityThreshold, 0.80 by default. It lets go of them when their estimated time to first token is worse than the best other worker by more than maxTTFTPenaltyMs, 18000 milliseconds by default. It estimates that time from peakPrefillThroughput, 15,928 tokens a second by default. After the filter, the token-load-scorer scores each worker by the tokens it has in flight, falling to zero at queueThresholdTokens, 4,194,304 tokens by default, which the documentation equates to 128 requests of 32K tokens. Older and other configurations weight scorers by hand instead: the wide serving recipe gives prefix-cache-scorer a weight of 3 and queue-scorer and active-request-scorer 2 each. The lesson Which GPU answers soonest explains why such weights exist.

The second knob is a ratio. llm-d's documentation gives 8 prefill Pods with one GPU each and 2 decode Pods with four GPUs each, 16 GPUs, as the fit for prompts of about 5,000 tokens and answers of about 250 on gpt-oss-120b. The lesson Prefill and decode explains the split itself.

The third knob is tensor parallelism. Qwen3-32B in BF16 is 65.5 GB, which leaves too little of an 80 GB H100 for the cache. llm-d's reference setup serves Qwen/Qwen3-32B, the BF16 build, with each copy spread over two GPUs, 32.75 GB of weights on each. The FP8 build northlight runs, 34.3 GB, fits one GPU. The fourth knob lives in vLLM: --max-num-batched-tokens and --max-num-seqs. vllm serve v0.34.0 sets them to 8192 and 1024 on an H100.

The knobs are not independent. The 15,928 default was measured on two H100s per copy with a batch chunk of 8192 tokens. Change the third or fourth knob and the first is wrong. That is why tuning by hand can take weeks and still leave several settings wrong.

Chapter 2 of 13

A recipe somebody has already measured

A well-lit path changes what runs and how it is wired, and comes with proof that it works.

llm-d's answer to the tuning problem is the well-lit path. The project's own policy defines it as an opinionated, curated way to run one inference pattern on llm-d, chosen as a working example on specific infrastructure. The guide is the artifact that makes the path runnable: a directory under guides/ with documentation, deployable manifests and machine-readable steps in a file called guide.yaml. A recipe, in llm-d's vocabulary, is smaller: a reusable building block under guides/recipes/ that does nothing on its own. When this lesson follows the course and calls the three well-lit paths recipes, it uses the word in its everyday sense, a ready-made configuration.

The policy draws a sharp line between a guide and a knob. Its rule is: if the answer is a parameter, it is a knob. Serving another model with the same topology is the MODEL variable of an existing guide. One flag, one replica count or one scheduler weight belongs in a guide's tuning section. A new guide has to change topology or composition: the number and role of model server groups, which router plugins are active, which cache tiers exist, which services sit in the request path.

Each guide carries a tier that says how much evidence stands behind it. Tier 0 is planned. Tier 1 is experimental, documentation only. Tier 2 is deployable, with Kustomize overlays checked by a dry run in CI. Tier 3 is validated: its guide.yaml is machine-checked and an end-to-end job runs it every night. Tier 4 is benchmarked under load with reviewed results. Tier 5 is proven, with a published write-up that shows an improvement over a baseline. Foundation guides, one mechanism each, aim for tiers 1 to 3. Model guides, such as DeepSeek-V4 on GB200 NVL72 or GLM-5.2 in FP8 on H200, compose several mechanisms for one model on one accelerator and aim for tiers 4 and 5.

The v1.0 menu is long: optimized baseline, predicted-latency routing, precise prefix cache routing, tiered prefix cache, P2P KV cache sharing, prefill and decode, wide expert parallelism, multimodal and omni serving, and operations guides for autoscaling, fast startup, rollouts, flow control and batch. The project also says plainly that guides are a starting point for your own configuration, not a supported product. Every guide starts the same way: clone the repository at the release branch, load the shared variables and install the custom resource definitions the router needs.

Chapter 3 of 13

Three fleets behind one router

The optimized baseline, the prefill and decode split and wide serving share the router and differ in what stands behind it.

Of all the paths on the menu, the course picks three that carry almost the whole story. The first is the optimized baseline: one pool of identical model servers, with cache-aware and load-aware routing switched on and nothing else changed. In llm-d's reference setup that is two copies of Qwen3-32B, each on two H100s, four GPUs in all. Every request is scheduled once, onto one Pod.

The second path splits the work in two. One pool of servers reads prompts and another writes answers, and the cache made by the first is handed to the second over a fast link. You size each pool for your own traffic, which makes it the path for long, heavy prompts. In llm-d 1.0 both pools sit in one InferencePool, told apart by the label llm-d.ai/role, and the router schedules each request twice: once onto a prefill Pod and once onto a decode Pod. The smallest version in the guide is one prefill Pod on one GPU and one decode Pod on four, five GPUs, serving gpt-oss-120b.

The third path spreads one model across a group of GPUs that act as a single server, which is what the largest mixture-of-experts models need. The guide serves DeepSeek-R1-0528 on 32 H200s: a prefill group and a decode group, each 16 GPUs over two nodes. Every GPU in a group runs its own copy of the attention layers and its own server port, so the router picks a rank, one port on one Pod, and not only a Pod.

The router is the same program in all three: the llm-d router's endpoint picker, installed by the same chart. What changes is its plugin configuration and the shape of the fleet. The course's advice is that most teams start with the first path, because it is the smallest change with the biggest payoff. Its claim for cache-aware routing over spreading requests evenly is about three times the throughput and a first token twice as fast on the same hardware, and for the split, up to 70% more tokens a second. Those are the project's own figures. The lesson Prefill and decode shows why vLLM's documentation is more careful about the split.

Chapter 4 of 13

The first command installs the router

helm install puts the endpoint picker and the InferencePool in the namespace, and in standalone mode an Envoy proxy beside the picker.

The router comes as two Helm charts that share one library chart, routerlib. llm-d-router-standalone is the default in every guide: it runs the endpoint picker (EPP) with an Envoy proxy as a sidecar in the same Pod, so the router is reachable without any Gateway. llm-d-router-gateway is for a cluster that already has a Gateway: it deploys the picker and the InferencePool and can create an HTTPRoute that sends the Gateway's traffic to the pool. Each guide picks its values by layering files: the shared guides/recipes/router/base.values.yaml first, then the guide's own file, then optional monitoring or accelerator files.

northlight already runs a Gateway, northlight at 203.0.113.80, so gateway mode fits. The release is called qwen3-llmd here. From that name the chart makes an InferencePool named qwen3-llmd and a Deployment and Service for the picker named qwen3-llmd-epp. The InferencePool selects model server Pods by the labels in router.modelServers.matchLabels and sends to router.modelServers.targetPorts, 8000 by default. Its endpointPickerRef names qwen3-llmd-epp on port 9002, the gRPC port of the ext_proc protocol a proxy uses to ask the picker. Its failureMode is FailOpen, so if the picker cannot be reached, the proxy still sends the request to some Pod in the pool.

base.values.yaml sets one picker replica with 4 CPUs and 8 GiB requested and a 16 GiB memory limit, the same for an Envoy sidecar when the standalone chart runs one, and Envoy flags that override the chart's own defaults: --log-level warn instead of trace, and --concurrency 8 so Envoy does not start a worker thread for every CPU of the node. It samples 10% of traces. The guide's file adds the plugin configuration and a Service port 80 that forwards to 8081, Envoy's listener in standalone mode. The proxy settings belong to llm-d-router-standalone only. In gateway mode, which northlight uses, the chart runs no Envoy, nothing in the picker's Pod listens on 8081, and the Gateway's own data plane is the proxy.

One detail matters for northlight. The optimized baseline's values file selects Pods with the label llm-d.ai/guide: optimized-baseline. Helm merges maps from several values files key by key, so adding app: qwen3 in a later file leaves both labels in the selector, and the existing Pods, which carry only app: qwen3, match nothing. Helm's documentation says a key set to null is deleted, but that rule is about keys in the chart's own values.yaml, and the router chart's default matchLabels is empty. Checked with helm template in Helm 4.1.4, a null in a later file over a label that came from an earlier file renders llm-d.ai/guide with no value instead of removing it. The reliable fix is to copy the guide's file to qwen3-llmd.values.yaml, replace its matchLabels with app: qwen3 and pass the copy in place of the original. The lesson Wiring a pool to its picker follows the same objects when F5's picker is the one behind the pool.

Chapter 5 of 13

The second command installs the model

A values file names the model and the size of each pool, and the chart turns it into Deployments.

The course's second command is helm install for the model. The Helm chart for that is llm-d-modelservice, kept in llm-d's incubation organisation and at version 0.5.6 at the time of writing. Its values file describes the model servers. modelArtifacts.name is the model as clients will name it in the OpenAI model field, and the chart passes it to vLLM as --served-model-name. modelArtifacts.uri says where the weights come from: hf:// for Hugging Face, pvc:// for a volume already in the cluster, or oci:// for weights packed in an image. modelArtifacts.size sizes the emptyDir volume the weights are downloaded into, mounted at /model-cache. modelArtifacts.authSecretName names the Secret that holds HF_TOKEN.

Then come the pools. decode and prefill each have create, replicas, containers and parallelism. The chart's defaults are decode.replicas 1 and prefill.replicas 0, so a file that only sets decode gives one ordinary pool of servers that do both halves of the work. parallelism.tensor sets vLLM's --tensor-parallel-size, and unless the container sets its own GPU limit, the chart sets nvidia.com/gpu to tensor times dataLocal. multinode: false makes Deployments, and true makes LeaderWorkerSets.

For northlight, the file names Qwen/Qwen3-32B-FP8, downloads it from Hugging Face into a 40Gi volume (42.9 GB, room for the 34.3 GB of files), and asks for two decode replicas with tensor 1. With fullnameOverride: qwen3 the chart makes a Deployment named qwen3-decode, whose Pods get names such as qwen3-decode-5f6b8c7d9-h4r2n. Each Pod carries the labels in modelArtifacts.labels plus llm-d.ai/role: decode. Setting app: qwen3 there puts the new Pods in the pool the router already watches.

llm-d's own v1.0 guides do this step with Kustomize instead: kubectl apply -k on an overlay such as guides/optimized-baseline/modelserver/gpu/vllm/base. The overlay holds the same decisions in a patch: a Deployment named decode with replicas 2, the arguments Qwen/Qwen3-32B and --tensor-parallel-size=2, nvidia.com/gpu: 2, labels such as llm-d.ai/guide: optimized-baseline, and graceful shutdown settings. Helm chart or overlay, the second step is a description of the fleet.

Chapter 6 of 13

One values file is the whole fleet

Swap the file and the same command builds a different set of Pods.

The course makes the point that the values file is the fleet. In the course it holds the model's address and how many Pods serve prefill and how many serve decode. The chart's file also says how many GPUs each Pod spans, in parallelism.tensor. Pass a different file to the same chart and Kubernetes builds a different fleet. Apply it and llm-d's pieces line up: the model chart creates the prefill and decode Pods, the router chart has already put the gateway route and the picker in front, and labels join them.

northlight has eight H100s, four per node. The first file asks for two decode Pods with one GPU each, two GPUs in use and six free. A second file for a split fleet could ask for prefill.replicas 2 with tensor 1 and decode.replicas 1 with tensor 2: two plus two, four GPUs. Its containers must also carry vLLM's KV transfer setting, --kv-transfer-config with the NixlConnector, and the NIXL side channel port 5600, as the chart's own P/D example does. A third file could ask for four decode Pods with tensor 2 for the BF16 build, eight GPUs, the whole cluster. helm upgrade qwen3 with the new file is all it takes to move between them, because Helm compares the rendered objects with the release and changes only what differs.

The values change more than counts. Turning prefill on makes the chart create a second Deployment, qwen3-prefill, with the label llm-d.ai/role: prefill. Its Pods are separate from the decode Pods, so the two pools are scaled separately: more decode Pods when answers back up, more prefill Pods when prompts get heavy. The router's side has to change too. A split fleet needs the P/D plugin configuration, with prefill and decode profiles, so the router chart is upgraded with the P/D values file at the same time. A fleet behind the baseline configuration would send whole requests to prefill Pods.

The split also asks something of the network. NIXL moves the KV cache from the prefill GPU to the decode GPU. llm-d's documentation says it falls back to TCP without RDMA and that TCP is only for testing. On northlight, a prefill Pod on gpu-node-1 and a decode Pod on gpu-node-2 would move every prompt's cache, 262,144 bytes per token in Qwen3-32B with a 16-bit cache, across the node network.

Chapter 7 of 13

A label and a port join the two releases

The router and the model servers are installed separately and never name each other.

The two Helm releases do not reference each other by name. The router's InferencePool selects Pods by labels, and the model chart puts labels on Pods. If the two sets of labels match and the port is right, every model server Pod that becomes Ready is in the pool. The chart documents this relationship: modelArtifacts.labels must match the pool's matchLabels, and routing.servicePort must be one of the pool's target ports.

This chapter steps back to the first values file, before the split upgrade of the previous chapter, when qwen3-decode still ran two Pods with one GPU each. This is also what makes the smallest step possible. Before the model chart was ever installed, the router's selector app: qwen3 already matched the two Pods of the hand-made Deployment qwen3, qwen3-6f7d9c8b4-x7k2p at 10.244.1.21 and qwen3-6f7d9c8b4-m9q4t at 10.244.2.22, both on port 8000. The router chart alone turned northlight's existing fleet into an optimized baseline. When the model chart's Pods arrived with the same label, they joined the same pool. Scaling the old Deployment to zero then hands the pool over without a gap, because the old Pods leave only once the new ones serve.

The same mechanism makes mistakes quiet. A selector with a label no Pod carries gives a pool with no endpoints. The chart installs, the route is accepted and every request fails. A target port that does not match where the server listens gives endpoints that refuse connections. The model chart's decode Pods can listen in two places: the routing sidecar on routing.servicePort, 8000 by default, and vLLM behind it on routing.proxy.targetPort, 8200. The pool must target 8000. Targeting 8200 skips the sidecar, which a split fleet needs for its two-step request.

Labels can also select too much. The Service qwen3, which selects app: qwen3, now includes the new Pods too. In a split fleet, the pool also contains prefill Pods, and only the router's role filters keep whole requests away from them. That is why the role label exists: the prefill-filter and decode-filter plugins keep llm-d.ai/role prefill and decode apart, and a Pod labelled prefill-decode can do both. The lesson A model server becomes ready shows the other half of membership: a Pod is only an endpoint while its readiness probe passes.

Chapter 8 of 13

Once it is up: proving it routes by cache

A Pod list shows the fleet is up. A burst of shared prompts shows the router is doing its job.

The course describes the moment after the install: a minute later you ask the cluster what is running and a few lines of text tell you the whole inference system. kubectl get pods -n inference lists the picker's Pod and the model server Pods. A minute is enough to see them listed. A model server Pod is Running long before it is useful, because loading takes about three minutes, so the test in this chapter waits until every Pod shows Ready. The v1.0 overlay gives vLLM a startup probe with initialDelaySeconds 15, periodSeconds 30 and failureThreshold 120. That allows 15 + 30 × 120 = 3,615 seconds, about an hour, for a slow download. With northlight's three-minute load, the probes run at 15, 45, 75, 105, 135, 165 and 195 seconds, and the seventh one passes. After that the readiness probe runs every 5 seconds and takes the Pod out of the pool after 3 failures.

One answer from the model only proves the stack is up. llm-d's guide adds a test of the mechanism. It sends 10 requests that share a prompt of about 2,000 tokens, built from one sentence repeated 100 times, and differ only in a final question. Each asks for 16 tokens. Then it reads each Pod's counters through the API server proxy, with kubectl get --raw on /api/v1/namespaces/<namespace>/pods/<pod>:8000/proxy/metrics, so no port forwarding is needed.

What it should show is one Pod with most of the 10 requests in vllm:request_success_total, and on that Pod vllm:prefix_cache_hits_total as a large fraction of vllm:prefix_cache_queries_total. Every request after the first reuses the cached opening. The other Pods show few or none. If the requests are spread evenly and the hit rate stays near zero, prefix affinity is not working.

The guide is careful about what this proves. Ten requests are a smoke test, with no steady load and no saturation. Under real load the signals to watch are the per-Pod load (llm_d_epp_request_total and vllm:num_requests_running), the hit rate, each Pod's cache use and queue (vllm:kv_cache_usage_perc and vllm:num_requests_waiting), the picker's own decision time (llm_d_epp_plugin_duration_seconds), and time to first token and between tokens. Load balance and hit rate pull against each other, so they are read together.

Chapter 9 of 13

Inside the optimized baseline

Two producers, one filter and one scorer, with a load gate that lets go of the cache when the cache becomes the bottleneck.

The baseline's whole router configuration is a short EndpointPickerConfig, apiVersion llm-d.ai/v1. It lists four plugins. approx-prefix-cache-producer estimates, for each worker, how much of the incoming prompt it holds, from the picker's own record of where it sent earlier prompts. inflight-load-producer counts the tokens each worker has in flight. prefix-cache-affinity-filter and token-load-scorer then make the decision in the one scheduling profile, default.

The filter works before any scoring. It keeps only the sticky workers, those with a cache score of at least 0.80 for this prompt. If none qualifies, it keeps them all and does nothing. It then checks the load gate. It estimates each worker's time to first token as tokens in flight ÷ peakPrefillThroughput × 1000 milliseconds. If the best sticky worker is slower than the best other worker by more than 18,000 milliseconds, it keeps all workers and lets the scorer decide.

A worked example with the default 15,928 tokens a second. gpu-1 holds the prompt's opening and has 240,000 uncached tokens in flight: 240,000 ÷ 15,928 = 15.07 seconds, 15,068 milliseconds. gpu-2 has 8,000: 502 milliseconds. The difference, 14,566 milliseconds, is under 18,000, so the filter keeps only gpu-1. Later gpu-1 has 300,000 tokens in flight: 18,835 milliseconds. The difference is now 18,333, over the limit, so the filter keeps both. The token-load-scorer then scores gpu-1 at 1 − 300,000 ÷ 4,194,304 = 0.928 and gpu-2 at 1 − 8,000 ÷ 4,194,304 = 0.998, and the request moves to gpu-2. llm-d calls the strategy sticky until saturated.

Two rules keep this working. Scorers after the filter must not include a separately weighted prefix scorer, because its weight would pull the request back to the warm worker after the gate let go. And the recommended load scorers count uncached tokens, so a warm worker's cache still lowers its cost in the same units as the load. The guide says no tuning is needed for its reference setup, Qwen3-32B on H100s with two GPUs per copy. On other hardware the common failure is uneven load: some Pods hot, some idle, because a wrong peakPrefillThroughput makes the gate fire too late or never.

Chapter 10 of 13

The prefill and decode recipe

Two profiles in one pool, a decider, and a sidecar that runs the request in two steps.

The second recipe keeps the router program and changes its configuration. The disagg-profile-handler replaces the single profile. For each request it first runs the decode profile, decode-filter and then active-request-scorer, which picks the decode Pod with the fewest requests in flight, because pure decoding is limited by how many requests run at once. It then asks a decider whether the part of the prompt the decode Pod has not cached is large enough to split off. The guide uses always-disagg-pd-decider, which always says yes. With vLLM a prefix-based-pd-decider can say no, and the request then runs whole on the decode Pod. If the answer is yes, the handler runs the prefill profile: prefill-filter, the same prefix-cache-affinity-filter as the baseline and token-load-scorer, and returns both addresses to the proxy.

The guide's affinity filter here sets peakPrefillThroughput to 33,821 tokens a second. The values file says it was measured through the whole split path on a reference fleet of 8 prefill Pods with one H200 each, including the NIXL transfer and the sidecar. That measuring fleet is larger than the fleet the guide deploys by default, described below. It also caps maxPrefixTokensToMatch at 131,072. And it keeps the picker at one replica, because the in-flight token counts live in each picker process, and two replicas would each see only part of the load.

The request then moves in two steps, run by the routing sidecar inside the decode Pod. The proxy sends the request to the decode Pod with the prefill Pod's address in the header x-llm-d-prefiller-host-port. The sidecar sends the prompt to the prefill Pod with max_tokens 1 and remote decode parameters, receives KV transfer parameters back, and passes them to its own vLLM. The decode vLLM pulls the cache from the prefill GPU over NIXL, the prefill Pod frees it, and decoding begins. If the prefill Pod answers with a server error, the sidecar falls back to decoding alone.

The guide's default fleet serves gpt-oss-120b on H200s with one prefill Pod at tensor parallel 1 and one decode Pod at tensor parallel 4, five GPUs, the smallest shape that runs the whole path. In the v1.0 guide's Kustomize overlays, both roles are deployed as one DisaggregatedSet, a LeaderWorkerSet API that rolls prefill and decode out as one version. The llm-d-modelservice chart used earlier in this lesson takes a different route to the same split: with multinode: false it makes two plain Deployments, qwen3-prefill and qwen3-decode, and that is the shape northlight runs in the rest of the lesson. The documentation's tuning advice is fewer GPUs and more replicas for prefill, more GPUs and fewer replicas for decode, and a ratio chosen for the traffic's prompt and answer lengths.

Chapter 11 of 13

Wide serving for the giant models

When one copy of a model needs more than one machine, Kubernetes needs a group it can treat as one server.

The third recipe is for models too big for one machine, such as DeepSeek-R1-0528, a mixture-of-experts model. llm-d's wide expert parallelism guide serves it on 32 H200s. Prefill and decode each get one group of 16 GPUs spread over two nodes. Inside a group, data parallelism gives each GPU its own copy of the attention layers and its own API server port, and expert parallelism spreads the experts across all 16 GPUs, so tokens travel to the GPU holding their expert in an all-to-all exchange. The guide uses DeepEP for that exchange and NIXL for the cache between prefill and decode, and it requires RDMA where every network card can reach every other. A rail-only network, where card 1 only reaches card 1 on other hosts, fails.

The course asks why a StatefulSet would not do. A StatefulSet gives each Pod a stable name and starts them in order, 0, 1, 2, 3, which suits a database. But it still treats every Pod as a separate replica. Here the Pods of one group are one server cut into pieces. Scaling must add a whole group. If one piece fails, the whole group has to restart, because a model missing a piece answers nothing. The Kubernetes community built the LeaderWorkerSet for this, an add-on API from the kubernetes-sigs/lws project with its own controller: a leader Pod and its workers, created, scaled and healed as one unit. In the guide, two LeaderWorkerSets, one per role, are managed as a DisaggregatedSet so both roles roll out as one version. It needs the LeaderWorkerSet controller v0.11.1 or newer with the DisaggregatedSet API turned on.

The router changes in two ways. Its pool lists eight target ports, 8000 to 8007, one per rank on each Pod, and without them only rank 0 gets traffic. And its configuration adds a disaggregatedset-rollout-screener, an alpha plugin, that keeps each request's prefill and decode inside one revision during a rollout, so a new prefill group never hands its cache to an old decode group. Its prefill profile weights prefix-cache-scorer 3, queue-scorer 2 and active-request-scorer 2.

northlight cannot run this recipe. It has eight H100s on two nodes. The lesson A model bigger than one GPU explains the cuts inside and between layers that such groups rely on, and the lesson Dynamo on a validated cluster shows another stack doing the same with its own resources.

Chapter 12 of 13

The one number you must measure

Most of the baseline is portable. peakPrefillThroughput is not.

The baseline guide says no tuning is needed on its reference setup, and points at one exception for everything else. The load gate in the affinity filter turns tokens in flight into milliseconds with peakPrefillThroughput. The default 15,928 was measured for Qwen3-32B on two H100s per copy with vLLM, as the prefill speed of one unloaded chunk of 8,192 tokens. northlight runs the FP8 build on one H100 per copy, so its number is different, and if it is wrong the gate fires too early, spreading requests that should have stayed with their cache, or never, leaving one Pod hot while the others idle.

llm-d ships a calibration recipe in guides/recipes/router/calibration. calibrate.sh runs a short Kubernetes Job against the deployed stack. The Job sends requests of exactly CHUNK_SIZE random token ids, so every request misses the prefix cache and measures a true prefill. It sends 5 warm-up requests and 20 measured ones, records the time to first token of each and computes peakPrefillThroughput = CHUNK_SIZE ÷ median time to first token. CHUNK_SIZE must equal vLLM's --max-num-batched-tokens, 8,192 on an H100 by vLLM's default, because a longer request would be cut into several steps and measure something else. The script only prints the number and changes nothing.

An illustrative run on northlight: the median time to first token for 8,192 random tokens comes back as 0.73 seconds. 8,192 ÷ 0.73 = 11,222 tokens a second. That goes into the router's values as a parameter of prefix-cache-affinity-filter. Then helm upgrade the router release and restart the picker with kubectl rollout restart deployment/qwen3-llmd-epp, because the picker reads its plugin file at start.

The number changes the decision. With 11,222 in place of 15,928, the 240,000 tokens in flight from the baseline chapter become 21,387 milliseconds instead of 15,068, and with 8,000 tokens on the other worker the gate opens at about 210,000 tokens in flight instead of about 295,000. A model guide carries its own measured value, and the P/D guide's 33,821 was measured through the whole split path. llm-d also keeps a configuration matrix of pre-measured values, and a second calibration script for minCachedTokenDelta in the P2P cache-sharing guide, where the crossover between pulling a cache and recomputing it depends on the model, the GPU and the network.

Chapter 13 of 13

Keeping the fleet alive

Every server is a Pod, so the Kubernetes loop the operations team already trusts looks after them.

The course's last point about llm-d is that the hard part of running it is already solved. Every model server is a Pod. If a Pod crashes, the kubelet restarts its container. If a whole machine dies, the Deployment controller replaces its Pods and the scheduler places them on a node with free GPUs. Because the model chart made prefill and decode separate Deployments on northlight, each pool grows on its own: kubectl scale deployment qwen3-decode adds decode Pods when answers back up, and qwen3-prefill grows when prompts get heavy. llm-d's workload autoscaling guide automates this on signals such as queue depth, requests in flight and cache pressure. Kubernetes keeps the servers alive and llm-d keeps them smart, in the course's words.

Replacing a model server has a cost the readiness probe alone does not cover: requests in the middle of an answer. The v1.0 vLLM overlays add a graceful shutdown component. vLLM gets --shutdown-timeout=45, the container a preStop hook that sleeps 15 seconds, and the Pod a termination grace period of 75 seconds. The 15 seconds give the pool time to stop sending new requests. vLLM then has 45 seconds to finish the ones it holds. 15 + 45 = 60 seconds, inside the 75, leaving 15 seconds before the kubelet kills the process. Raise one and the other has to follow. Some vendor overlays do not drain yet. The lesson A Pod is asked to stop follows the signals in that order.

The picker is a single point too. base.values.yaml runs one replica. With more replicas the chart turns on leader election by default, so one picker routes and the others wait as warm standbys. All replicas can route at once with router.epp.haMode: all-active, but the approximate prefix record stays local to each replica, so cache routing becomes less consistent. The P/D guide keeps one replica on purpose. While the picker is down, FailOpen keeps requests flowing to some Pod in the pool, without cache routing.

The guide's list of failure modes is the operator's checklist. Uneven load means the gate is not spreading work, usually a miscalibrated peakPrefillThroughput. A low hit rate with cold Pods means the prompts do not share openings. Slow first tokens with balanced load and healthy caches point at the model servers' queues, and llm_d_epp_plugin_duration_seconds shows whether the picker itself is the slow part.

What to keep

The router stays, the fleet changes

Installing llm-d is two decisions written as two commands. The router chart puts the endpoint picker and an InferencePool in the namespace, with an Envoy proxy beside the picker in standalone mode, and its values file says how to choose. The model step, a Helm values file in the course and earlier releases or a Kustomize overlay in the v1.0 guides, says what the fleet is: the model's address, how many prefill and decode Pods, how many GPUs each spans. A label and a port are the only things that join them, which is why the router alone can front a Deployment you already run, and why one wrong label empties the pool without an error. The well-lit paths save the weeks of tuning by setting every knob and measuring the result on real hardware, and the validated ones are run end to end every night. Most teams start with the optimized baseline, add the prefill and decode split when prompts are long, and reach for wide serving only when a model outgrows a machine. One number travels badly between clusters, the prefill throughput behind the load gate, and it takes one short Job to measure.
