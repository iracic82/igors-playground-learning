Running a GPU cloud

A server nobody has to trust

How NVIDIA Infra Controller takes in a bare-metal host, lends it to a tenant and proves it clean again

Renting out bare metal means giving a stranger root on a whole machine, and then giving the same machine to another stranger next week. The lesson From an order to a server and back followed the steps of provisioning with OpenStack Ironic. This one asks a harder question about the same server: on what grounds can anyone trust it. NVIDIA Infra Controller, NICo for short, is open source software built around one answer. The host is never believed. Its network is enforced on a DPU that the host cannot configure, its firmware is measured before it joins the pool, and after each tenant it must be shown clean before it is offered again. We follow gpu-srv-2 through one full cycle. The last three chapters move to the factory's gateway: how BNK turns away known bad addresses, unproven callers and floods, how its events leave by high speed logging, and how it serves a tenant that sells inference to enterprises of its own.

Chapter 1 of 14

Three things that cannot be taken on trust

The machine, the tenant, and whatever the last tenant left

A provider of bare metal has three problems that a provider of virtual machines does not. The first is trust in the machine. A host that a stranger ran as root cannot vouch for itself. Its firmware is an attack surface, and so is its management controller: a tenant who can reach the server's own BMC from inside has stepped out of the tenant's role and into the infrastructure. The second is movement sideways. Tenants share one physical fabric, so each tenant's servers must sit in a private network that still looks like an ordinary local connection to the host, and that separation has to fail closed. The third is reuse. No data may remain between rentals, tenants coming and going must not disturb the shared fabric, and tenants should serve themselves through an API without holding more rights than they need.

NICo answers with five principles, and the rest of this lesson is those principles at work. The machine is untrustworthy, so no security decision rests on software inside the host. No requirement is placed on the host's operating system. A racked machine must become ready with no human step. All monitoring is done out of band. And the network fabric stays static while tenants change. The third principle is about the work after racking. A person still registers each machine's identifying facts and approves trust material, such as a TPM manufacturer's CA certificate, as later chapters show. Discovery, validation, assignment and cleanup then run with no one stepping in.

The aim, in the words engineers use for it, is the look and feel of a public cloud with the performance of bare metal built for AI.

Chapter 2 of 14

A controller that lives in the site it manages

One service owns the state, and everything else talks to it

NICo is a set of microservices that runs on a Kubernetes cluster placed in the same data center as the machines it manages. NVIDIA calls this control plane the site controller. It needs at least three nodes to stay available, and its services speak to each other over gRPC with certificates on both sides.

The centre is the API service, also called NICo Core. It is the single source of truth. It alone reads and writes the PostgreSQL database, and it holds a state machine for every managed thing: hosts, network segments, InfiniBand and NVLink partitions. Around it sit a DHCP service, a PXE service that serves boot scripts and images over HTTP, a hardware health service, a console service that keeps serial connections to every BMC, and DNS. Certificates and secrets come from Vault, with cert-manager issuing and rotating the certificates the services use.

Two agents work on the machines. Scout is temporary. It runs on the host only while the provider controls it, during discovery and cleanup, and never while a tenant does. The DPU agent is permanent and runs on the card. Above all this is NICo REST, a JSON API that can sit in the site or centrally and serve several sites, each connected through its site agent. NICo itself stops there. Scheduling, tenancy policy, prices and the customer's portal belong to the provider's own control plane, which calls NICo.

Chapter 3 of 14

Ingestion: found from outside

An operator supplies four facts, and the machine is discovered without its cooperation

A server enters the pool through ingestion. The operator registers it as an expected machine with four facts: the MAC address of its BMC, its chassis serial number, and the BMC's user name and password, usually the factory defaults. DHCP requests from the management networks are relayed to NICo, so when the BMC asks for an address, NICo recognises it.

From there the work is automatic. NICo talks to the BMC over Redfish, the HTTPS management API from the earlier lesson, and takes over its credentials. It pairs each host with its DPUs by comparing LLDP neighbour data and serial numbers, so nobody types in which card sits in which server. The DPU is prepared first, because it provides the host's network: its operating system is installed, its firmware components brought to the site's versions and its network software configured. Then the host is prepared. NICo inventories the UEFI and BMC firmware and brings a host that is off the baseline into line before it can become available.

The host then boots a discovery image from the network. In it runs Scout. Its first call proves what booted, which the next chapter follows, and only once that check has passed does Scout report the inventory that cannot be read from outside. NICo then sets a UEFI password and locks the host down, and validation follows. One check compares the machine's parts with what its model should contain, so a server with a missing GPU or DIMM is flagged. Others are tests from a catalogue, and a site can add its own as containers. In lifecycle runs only tests that are both enabled and verified are used.

Chapter 4 of 14

Measured before it is believed

The server proves what it booted, with a chip the tenant cannot rewrite

Validation can show that a machine works. It cannot show that the machine is honest, and NICo asks that question first, before it accepts any inventory from the host. For that NICo uses measured boot. While a server starts, each stage of firmware hashes the next thing it loads and extends the hash into a register of the TPM, a security chip on the motherboard. These registers are called PCRs. A register cannot be set to a chosen value. It can only be extended, so its final content depends on everything that was measured, in order.

In the discovery image, Scout reads the registers and calls the API service to register the machine. The call is DiscoverMachine. With attestation enabled the API service replies with a challenge that only this TPM can solve. Scout returns the solution, the register values and the TPM's endorsement key certificate. NICo checks that certificate against a CA certificate of the TPM's manufacturer, which an administrator installed, so a software imitation of a TPM is rejected. Then it compares the values with golden values for this kind of machine.

The golden values are trust on first use. NICo groups machines into profiles by vendor, BIOS version and product name. The measurements of a first machine of a profile become the reference bundle once approved, and later boots are compared with it. A host that passes receives the mTLS certificates Scout needs for every further call, and only then does it report its inventory, take its UEFI password and lockdown, and run validation. A host that fails receives none. Scout then repeats DiscoverMachine once a minute. Without the certificates only the calls that need no mutual authentication succeed, such as DiscoverMachine itself and Version, so the host cannot report anything else. That is the enforcing behaviour. A site can also run measured boot in a permissive mode, and then the measurements are evidence to weigh under the site's own policy.

Chapter 5 of 14

The wall is a card in the server

The DPU fetches its orders every 30 seconds, and the host has no say

Tenants are kept apart on the DPU. The lesson A computer in the network slot showed the card: a small computer with its own processor, whose embedded switch every packet of the host must cross. NICo calls it the trust anchor. It works independently of the host, and nothing running on the host can influence it.

NICo runs a DPU agent on the card's own cores. About every 30 seconds the agent asks the API service for this host's desired network configuration. It applies the answer to HBN, a containerized Cumulus Linux on the card that does the routing, through that system's configuration interface NVUE. Then it reports back which version it applied and whether the card is healthy. The model is declarative. NICo never pushes a command at a card. It changes the desired state, and a state that depends on the network does not advance until the card reports that it has caught up.

The card also takes over services the host expects from a network. A DHCP server on the card answers the host's requests, so they never reach the physical underlay. A metadata service on the host-facing interface gives the tenant's system its machine ID and boot information. Two more locks complete the wall. The host's in-band path to its own BMC is disabled, and on SuperNICs the firmware is locked with keys the DPU holds, so a tenant cannot reflash a network card to escape.

Chapter 6 of 14

A tenant's network is a routing table on the card

A VPC, a prefix, and a pair of addresses for every interface

What a tenant asks for is a VPC, a virtual private cloud, and one or more prefixes attached to it, each a VpcPrefix. Tenants create both through the REST API. On the DPU of every host in that VPC, the VPC becomes a Linux VRF, a separate routing table. A route announced in one VPC does not appear in another VPC's table.

The host's connection is routed, with no shared layer 2. For each host interface NICo carves a /31, a network of exactly two addresses, out of the VPC's prefix. The even address goes to the card's interface in that VPC's VRF and is the host's gateway. The odd address goes to the instance. The card is therefore the host's next hop, and the host sees an ordinary local link. Across the fabric the card redistributes that connected /31 into BGP and announces it as a BGP EVPN type-5 route, an IP prefix route, tagged with a route target built from the site's ASN and the VPC's VNI. The prefix announced is the /31 itself. NICo does not announce a /32 route per host. Other cards that import this target learn the route into the same VPC. NICo stretches no tenant layer 2 segment across the fabric.

NICo describes Ethernet isolation as three independent layers. Routing isolation is the VRF, with reachability between VPCs only by explicit peering or route leaking. Default isolation is the admin overlay: a host carries no tenant traffic unless a configuration places it in a VPC. Filtering is the Network Security Group, stateful or stateless rules at layers 3 and 4, attached to a VPC or to one instance.

Chapter 7 of 14

Assignment: the order waits for the card

Nothing is handed over until the DPU reports the new network in place

Tenant A orders a server through the provider's portal, and the provider's control plane asks NICo for an instance. In NICo an instance is a managed host assigned to a tenant: validated hardware with tenant-isolated networking and DHCP and DNS available. The host leaves Ready and enters Assigned, which has inner states of its own.

The order of those states is the point. First NICo waits until the network segments are ready. Then it publishes a new desired configuration that moves the host's interfaces from the admin overlay into the tenant's VPC, and waits in WaitingForNetworkConfig until every required observation matches its desired version and no health alert blocks the change. That includes the card's report. Only then does it restart the host through its BMC, and the host boots the tenant's operating system. NICo sets no requirement on that system. Anything that installs over iPXE will do, and NICo does not enter the host again while the tenant holds it.

While the host is in use, its firmware is locked. UEFI lockdown prevents changes to BIOS settings, NICo holds the BMC credentials, and the in-band path to the BMC stays closed. The tenant has root on the host and no route to the layers beneath it. The provider's metering starts when its own order turns active, as in the earlier lesson. NICo reports the instance's status, and money is none of its business.

Chapter 8 of 14

Release: platform first, then the network

The platform is reset and the tenant's system stopped, then the host leaves the tenant's network before any disk is wiped

Tenant A ends the rental. The release is accepted at once and the work runs in the background. NICo first takes the platform back. In a phase called HostPlatformConfiguration it resets the BMC to factory settings, unless the site has turned that step off, power-cycles the host, disables lockdown, restarts it, checks the BIOS settings and boot order, locks the host again and waits for the DPUs to come up. Only then does it boot the host into the discovery image, so the tenant's system is no longer running. Then it removes the tenant from the network path. It sets a flag named use_admin_network on the host's configuration and raises the version. On its next poll the card renders its configuration again without the tenant's parts: the membership in the VPC's VRF, the card's own interface and addresses in it, the VNI, the tenant's prefixes and any security group rules.

With the VRF gone, the card stops announcing the tenant's host routes, the fabric withdraws them, and every other card that imported that route target drops them from its copy of the VPC. The card's DHCP server now offers the admin network's parameters, and the metadata service no longer serves the old tenant's identity, so the next tenant cannot read it. The host sits on the admin overlay, a VPC of NICo's own that is separate from every tenant.

The ordering protects the records. NICo returns the tenant's addresses to their pools and deletes the instance record only after the card has confirmed the switch to the admin network. A health alert does not count as that confirmation. And if a card ever has no configuration at all, because NICo does not know the host, it detaches every interface from every overlay. That is the fail-closed case. On a transient error the card keeps its last known configuration.

Chapter 9 of 14

Wiping what a tenant can leave behind

Disks, memory and firmware settings, each with a result that is recorded

With the network gone, the host itself is cleaned. If attestation is enabled, the boot of the discovery image is measured again first. The cleaning tool is Scout, and a tenant who had tampered with the boot path could otherwise hand NICo a Scout that lies about what it erased.

Scout then works through the machine and reports each step with a result and a message. NVMe drives are formatted with the drive's own secure erase, namespace by namespace, and where the drive supports namespace management Scout deletes the namespaces and creates a fresh one sized to the drive. HDD and SAS devices have a step of their own. For memory, Scout checks a UEFI variable named MemoryOverwriteRequestControl. When it is 1, the firmware has been asked to overwrite RAM on the next boot, and the step passes. InfiniBand settings on the host are cleaned in a further step. Some hardware needs more: on Dell servers with a BOSS storage controller, NICo lifts the lockdown, decommissions the controller over Redfish, cleans, recreates the virtual disk and locks the host again.

Platform controls follow. NICo restarts the host with a Redfish ForceRestart, which is also what applies pending BIOS settings. It can clear the TPM over Redfish on supported vendors, and it checks that firmware is at the site's default version. The management controller was already handled at the start of the release: the FactoryResetBmc step reset the BMC to factory settings before the discovery image booted, unless the site has turned that step off. A last state validates the inventory again, in case a part was removed or swapped, and machine validation then runs with the Cleanup context. Then the host passes HostInit/Discovered, or HostInit/WaitingForPlatformConfiguration when its NICs must be qualified, and is Ready.

Chapter 10 of 14

When clean cannot be proven

The safe outcome is a server that earns nothing

The whole design leans one way: a host that cannot be shown clean is not offered. gpu-srv-3 shows it. Tenant B rented it in the hours this lesson skipped. Tenant B releases it, the network is removed, and one NVMe drive refuses the erase. Scout reports the step as failed, the host enters the failure state NVMECleanFailed and it never reaches Ready. An operator has to repair it or replace the drive. NICo has repair workflows for that, and a decommissioning flow that resets the device and deletes its credentials when hardware leaves service.

The same bias appears in smaller ways. The alert IbCleanupPending lets a release finish and blocks new allocations while it is present, and NVIDIA warns that the alert clearing is not proof that the InfiniBand membership was removed. A host stuck in SwitchToAdminNetwork or WaitingForNetworkReconfig has a card that has not converged, and it stays there. NICo counts how long each host has sat in each state and compares it with an allowance per state, so the stuck machines of a whole fleet show up as one metric.

The cost is real, and it is the theme of the earlier lesson seen from the other side. Four GPUs can sit idle because of one drive, and every minute between release and Ready is capacity paid for and unsold. A provider can shorten that time with faster drives and fewer reboots. Shortening it by skipping a confirmation is a bet made with a tenant's data.

Chapter 11 of 14

What else runs on the card

Services placed on DPUs through the controller, and what F5 puts there

A DPU that stands between a host and the fabric is also a place to run network services. NICo has a mechanism for it, DPU extension services. A service is defined once, through the REST API, and then deployed to DPUs, either following instances or to every DPU at once. There are two types. A KubernetesPod service is a Pod manifest that the DPU agent runs. A DpfHelmChart service is a Helm chart deployed by DPF, the DOCA Platform Framework, which NICo can also use to provision the cards. NICo follows DPF's zero-trust mode. Chart services have a deployment policy. DemandDriven follows instances and needs a target: the primary DPU, all DPUs used by the instance's networking, or every attached DPU. Baseline deploys to all DPUs managed by DPF, with no instance attached.

F5 builds on this. In its design for a NICo-run factory, BNK's parts run on the DPUs in front of every tenant host: TMM, the traffic engine, with its companions. Beside the tenant hosts stands a border services tier, hosts whose DPUs carry layer 4 to 7 services for each tenant. And beside the infrastructure management cluster, which holds NICo's own API, DNS, telemetry and PXE services, F5's slide lists a load balancer for NICo's own endpoints and a catalogue of services a provider can offer: border firewall, application load balancer, web application firewall, inference gateway and AI guardrails. The slide places these in a column between the management cluster and the border services tier, and does not say plainly which of the two runs them.

The effect is that tenant separation and tenant services share one enforcement point, on the provider's side of the line, where a tenant with root cannot touch either.

Chapter 12 of 14

Known bad addresses and unproven callers

IP intelligence drops a packet by its address, and access policy refuses a request without a valid identity

The card keeps tenants away from the factory. The same traffic engine, TMM, also faces the internet, and there the threats arrive by address. Every refusal is cheaper the earlier it happens. For the Qwen3-32B Pods behind api.northlight.example at 203.0.113.80, BNK checks in this order. First the network firewall looks at addresses and ports. Its F5BigFwPolicy is compiled by the AFM pod into a binary blob that TMM loads, and a rule can also match source countries through its geos field. Next IP intelligence looks up the source or destination address. Only the traffic left after that gets a TLS handshake, an HTTP parse and an identity check. A packet dropped in the first two steps costs no handshake, no key lookup and no GPU time at all.

IP intelligence, IPI for short, compares each address with lists of addresses that have a known record. The lists come from two places. The first is the IP Reputation database, a curated list from Webroot BrightCloud that needs an F5 add-on licence. A pod named f5-downloader fetches it from the internet, as an F5BigCneDownloader object tells it to, with a component of type ipi, mode online and a pollInterval of at least 1m. It pushes each new copy to the TMM pods, and TMM's reputation library answers whether an address falls in a denied category. F5's overview says the database can be updated automatically as often as every five minutes, and the downloader object itself accepts a pollInterval as short as 1m. The second source is a feed list of the provider's own. An F5BigIpiFeedlist object names an http or https URL, how often to poll it and which category to give entries that carry none. A pod named dwbld encodes the addresses into a prefix tree and TMM applies it as a blob.

The policy says what to do with each category. A singleton object, F5BigIpiCategorylist named ipi-category-default-list, holds the predefined categories, among them botnets, scanners, spam_sources, tor_proxy, phishing, denial_of_service and web_attacks. Up to 62 categories are allowed, counting the predefined ones. An F5BigIpiPolicy then gives each category an action, drop or accept or the policy default, and says whether to match the source address, the destination or both. The default action is Drop. An allowlist match always wins over a category match, so an address the provider trusts is let through even when a feed lists it. Logging has a price. With logCategoryMatch set to yes every matching packet is logged and the policy gives up hardware acceleration. With no it logs nothing and runs at full speed. The counter src_ip_blacklist in the TMM table ip_intelligence_stat counts the drops per category.

A worked case. A host at 198.51.100.23 is listed in botnets and sends 1,000 TCP SYN packets to 203.0.113.80 port 443 in one minute. The policy matches the source and drops all 1,000. The counter for botnets rises by 1,000, no TLS session starts and vLLM sees nothing. If the category is logged, 1,000 log lines leave TMM, one per packet. The log profile can cap all IPI messages together with aggregateRate, and a cap of 5,000 per second leaves this case untouched.

Access policy asks a different question: who is calling. An address says where a packet came from. A key or a token says who sent the request. BNK answers in TMM before the request leaves the gateway. The provider's API key is checked by a policy iRule, a short program the provider sets up in TMM. In the owner's design the iRule calls a URL the provider configures, once per request, and gets back whether the key is active and who owns it. A missing or unknown key gets 401. With nothing cached, a revoked key stops on the next request. A short cache can be added if the round trip costs too much, and then a revoked key works until its cached answer expires. The token counting settings name the header that carries the identity, Authorization with a Bearer token by default or a header such as x-api-key. With fallback_to_ip set to false, a request without one is refused with 401 user_identity_missing. From BNK 2.4.0 the gateway also validates OIDC identities and JWTs for agent traffic, so identity claims are checked at the traffic layer before anything reaches an MCP server, an A2A agent or a tool. F5 calls this an IAM enforcement point at ingress.

A JWT is three base64url parts joined by dots: a header, a set of claims and a signature. A validator checks the signature with the identity provider's public key. The provider publishes its keys as a JWKS document, and OIDC discovery finds its address under jwks_uri in /.well-known/openid-configuration. Then the claims are checked: iss must be the expected issuer, aud must name this API, exp must lie in the future and nbf in the past. A token that fails any check stops at the gateway.

The two checks cover different failures. IP intelligence is cheap and coarse and works on single packets. It stops addresses already known to be bad. Access policy is exact and needs a parsed request. A stolen key used from a clean home address passes IP intelligence, and only revoking the key stops it. A botnet without a key never gets as far as the key check.

Chapter 13 of 14

Floods it learns and logs it must not lose

Behavioural DDoS, high speed logging and the Analyzer

BNK keeps its DDoS settings in one object for the whole instance, F5BigDdosGlobal, with the short name ddos. A SecPolicy attaches it, and for this kind it may target only a GatewayClass, so it covers every gateway of the class. Most of the object is a list of fixed attack vectors such as synFlood, udpFlood, ipv4IcmpFlood or dnsAQuery. Each vector has a state, detection-only by default or mitigation, a detection threshold in packets per second, a rate limit, and per-source and per-destination thresholds. Every threshold defaults to 4294967295, the largest 32-bit number, so a vector does nothing until someone writes a number into it. F5's own example puts ipv4IcmpFlood in mitigation with perSrcIpDetectionEps 4000 and rateLimit 5000. A source sending 6,000 ICMP packets a second crosses 4,000 and is marked a bad actor, and everything above 5,000 a second on the vector is dropped.

Fixed thresholds need someone who knows the right number. Behavioural DoS learns it. Under spec.behavioralDos.dynamicSignatures the field dynSigDetection is disabled by default. learn-only keeps statistics without thresholds or logs, and enabled acts. For a learning period, 120 minutes by default and anywhere from 15 to 7,200, the system learns what normal traffic looks like. Every anomalyDetectFreq seconds, 10 by default, it compares the traffic with that baseline. 120 minutes is 7,200 seconds, so learning spans 720 comparisons. When traffic departs from the baseline the system writes a dynamic signature: a description of the attack packets, built from predicates on packet fields. networkFamily limits the predicates to layers 3 and 4 and dnsFamily adds DNS fields. A signature needs at least bdosMinPredicates of them, 7 by default and between 3 and 8.

mitigationSensitivity decides what happens to a signature. none, the default, only detects. low, medium and high drop, each with its own pair of numbers: the share of throughput a signature must carry to qualify for hardware mitigation, and the mitigation threshold applied to it. high uses 10 and 95, medium 12 and 90, low 15 and 80. A signature counts as transient until it has lasted transSigMergePeriods correlation periods, 2 by default, and it is switched off after sigDisableNoStatsPeriods periods without traffic, 5 by default. Up to 32 custom signatures cover attacks the built-in ones miss. An allow list of up to eight entries, plus an address list of single /32 or /128 addresses, keeps known sources out of detection.

On a BlueField card some vectors and the address list run in hardware. Setting dosGlobalOptions.common.forceSwDos to false turns the offload on, and all supported vectors move together, with no way to pick a subset. synFlood can be offloaded and ipv4FragFlood cannot. Behavioural DDoS accelerated in hardware is part of BNK on the DPU. When several TMM pods see one attack, the first stores an attack ID in the dSSM database and the others reuse it, so one attack is reported once.

All of these features write events: firewall decisions, IP intelligence matches, DoS attacks, token usage. TMM sends them itself, straight from the data plane to a pool of collectors, with high speed logging, HSL. No file on a disk sits in between. An F5BigLogHslpub object, API version k8s.f5net.com/v2, defines the pool. Its endpoints are written as IP:PORT, such as 192.0.2.100:514. It can instead list members with priority groups and a minActiveMembers floor, and it can watch them with ICMP or TCP monitors that probe every 5 seconds with a 16 second timeout. Its syslog destinations use rfc5424 by default, or rfc3164 or legacy-bigip, over udp by default or tcp. distribution is adaptive by default and adds connections as bandwidth needs them. balanced sends each message to the next member. replicate sends every message to every member, so two collectors double the logging traffic. IPFIX destinations use netflow-9 by default and resend their templates every 30 seconds. An F5BigLogProfile, short name logprof, decides which events go out: nat, firewall with its ipIntelligence part, dns, protocolInspection, algLogging and pe.

The Analyzer is the part that reads the GPUs. Setting spec.intelligentLB.enabled to true on the CNEInstance makes the controller deploy the Analyzer pod. An F5BigAnalyzer object names the HTTPRoute or L4Route to watch and a script: the built-in LLMLoadMonitor, or a Python script of the provider's own in a ConfigMap. It writes its weights for each backend as the annotation k8s.f5.com/service-settings on the HTTPRoute, and the ingress controller passes them to TMM. From BNK 2.4 the Analyzer also hosts F5's endpoint picker as an ext_proc server with its own tokenizer. TMM calls it over gRPC for each request. It reads KV cache events that Dynamo workers publish over NATS, or ZMQ from 2.4, and GPU metrics from DCGM and vLLM through Prometheus. For security it matters as the last decision before a GPU. An InferencePool with failureMode FailClose fails a request when the picker is unreachable and never falls back to blind round robin. The owner's design adds a trusted label to the pool's selector. A controller fed by runtime audit removes the label from a worker that misbehaves, the picker stops choosing it within seconds, and the Pod stays up for forensics.

Chapter 14 of 14

When the tenant sells inference itself

BNK as a shared service plane in front of a provider's own router and pods

Tenant B in this lesson rents whole servers. Some tenants like it are inference providers themselves. They sell tokens of open models to enterprises through an API. In this chapter the provider is that tenant, and the enterprises it sells to are its customers, A and C. A provider of this kind runs its own model router and its own pools of model servers, some of them set aside for one customer. The pitch calls those sovereign pods. For such a provider the buyers' first question has changed. Speed and price still matter. F5's pitch to one provider of this kind puts the question this way: if another tenant is compromised, what happens to my data. Isolation now comes first.

The picture has four layers. Enterprise customers are at the top. Under them sits the BNK service plane, with three jobs: isolation, policy and metering. Under that is the provider's own router with its sovereign pods, and at the bottom the GPUs that run inference. BNK stands in front of the router and leaves it in place. The router keeps choosing models and pods, as before. F5 sums up what BNK adds in three foundations. Multi-tenancy means each customer is isolated at the network layer, even on shared GPUs. Zero trust means nothing is trusted by default and every connection is checked against policy. Authorization means every request is tied to a tenant and metered, and access can be revoked at once.

Each foundation is a mechanism from the earlier chapters. F5's pitch says only that each customer is isolated at the network layer. BNK 2.4 has the parts to do it: a VRF, a separate routing table, and VXLAN-based EVPN over BGP. This lesson gives each customer a VRF of its own, so one customer's routes cannot reach another's. That is a design choice. The owner's deck for another provider drew one VRF per environment, and warns that VRF and EVPN need a network underneath that supports them, which differs from one provider to the next. Each customer endpoint is a Gateway, an HTTPRoute and an F5BigFwPolicy carrying the endpoint's label, and deleting the endpoint removes exactly its objects. A sovereign pod pool is reachable only through its own customer's routes. Zero trust is the firewall policy for each endpoint, IP intelligence and a key check on every request. Authorization is the key check again, plus token counting. With user_id_source set to api_key, TMM ties each request to a key. It reads usage.prompt_tokens and usage.completion_tokens from the model's own answer and stores the counts in dSSM. It sends a usage record by high speed logging to the provider's metering and billing. Revoking is one change in the key service. The policy iRule asks that service about every request, so with nothing cached the next request with that key gets 401 at the gateway, and the provider's router never sees it. If the provider adds a short cache to save the round trip, the key keeps working until its cached answer expires.

A worked case with numbers. Customer A has a per_user limit of 100,000 tokens in a window of 3,600 seconds and rate_limit_action set to drop. Each of its calls to Qwen3-32B sends 2,000 prompt tokens and gets 500 completion tokens back, 2,500 in all. Forty calls use 40 × 2,500 = 100,000 tokens, and the forty-first inside the hour gets 429 Too Many Requests without reaching the router. Customer C's key is stolen. BNK cannot tell the thief from C, because the key is valid. What the thief holds is C's routes, C's VRF and C's budget of 100,000 tokens an hour, and no route to A's sovereign pods. When C revokes the key, the thief's next request fails, as long as no cached answer still vouches for it. The harm is bounded by C's budget and by the time it takes to revoke.

F5 is plain about the limits. BNK does not stop a credential from being stolen. It limits the blast radius, speeds up containment and gives the provider a stronger answer for enterprise buyers. The plane grows without being rebuilt: AI Guardrails, a firewall, a WAF and DDoS protection attach to the same gateways. The same TMM runs in host mode on the provider's own nodes, or on BlueField DPUs where the provider's hosts cannot reach it. Sovereign AI factories already run BNK on BlueField DPUs, and GSLB across sites keeps a service up when one site fails.

What to keep

Believe the card and the chip, never the host

NICo makes bare metal rentable by moving every guarantee off the host. Tenant separation is a routing table on a DPU that fetches its configuration from the site controller and that the host cannot reach. Trust in the firmware comes from TPM measurements checked against golden values, at ingestion and again after each tenant. Reuse is a fixed sequence: reset the platform and boot the discovery image, take the host out of the tenant's network and wait for the card to confirm, then erase drives, request a memory overwrite, restart and recount. Each step leaves a result, and a host missing one stays out of the pool. Ironic's cleaning, from the earlier lesson, erases disks and can move a node to a cleaning network and apply firmware settings. This design adds a card that confirms the network change and a TPM that proves the boot.
