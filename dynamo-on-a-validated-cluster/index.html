Inference

Dynamo on a validated cluster

The runtime under NVIDIA Dynamo, the graph that deploys it, and a request whose prompt and answer run on different GPUs

NVIDIA Dynamo is a serving framework that sits around a model engine such as vLLM and makes many GPU workers act as one service. It routes each request to the worker that already holds its prefix, it can run the reading of a prompt and the writing of an answer on separate workers, and it scales each group by its own pressure. All of that assumes a cluster where drivers, GPU allocation, scheduling, networking and metrics already work together. This lesson builds from the bottom. It first assembles and checks that runtime with NVIDIA's AI Cluster Runtime, then deploys a Dynamo graph on it, and then follows one request and its KV cache from the front door to two different GPUs.

Chapter 1 of 13

What one model server on one GPU cannot do

Three groups of problems, and a list of questions about the cluster

A Deployment of vLLM Pods, one GPU each, serves a model. It stops being enough as the pool grows, and the reasons fall into three groups. The first is the shape of the work. Reading a prompt, prefill, is bound by compute. Writing the answer, decode, is bound by memory capacity and memory bandwidth. One worker doing both serves neither well, and splitting them needs something that moves the KV cache between workers at close to the speed of memory. The second is elasticity. Autoscaling on CPU or requests per second says little about the two numbers users feel, the time to the first token and the time between tokens. KV cache memory is a hard ceiling that long contexts and many users reach quickly, and a large model replica takes minutes to start. The third is orchestration. A serving graph that spans nodes cannot be scheduled as a unit by stock Kubernetes, operators want this without being tied to one engine, and a failing GPU strands the requests that were running on it.

Dynamo addresses these with disaggregated serving, routing that knows the KV cache, and autoscaling driven by latency targets, in front of vLLM, SGLang or TensorRT-LLM.

Underneath, a cluster has questions to answer first. Is the GPU Operator installed with a driver stack that matches the nodes? Are GPU nodes labelled and discoverable? Are GPUs exposed through the expected allocation driver? Can the scheduler place workers together with the required topology? Are node health signals available before work lands on a degraded node? Is Prometheus reachable? Is the Gateway path configured?

Chapter 2 of 13

The runtime under Dynamo, piece by piece

Eight prerequisites, and the component that meets each

NVIDIA's DSX AI Factory Platform contains a tool for this layer, the AI Cluster Runtime, AICR. It does not serve models. It packages Dynamo together with the cluster components Dynamo depends on into a recipe: a configuration for one environment and one kind of workload, with pinned versions, compatibility constraints and checks.

The components are worth knowing one by one, because each answers one of the questions. The NVIDIA GPU Operator installs the driver and GPU software stack on the nodes. Node Feature Discovery labels nodes so GPU nodes can be found. The GPU Operator also runs the device plugin, and in AICR's stock recipes that device plugin is what hands whole GPUs to Pods as nvidia.com/gpu. The DRA Driver for NVIDIA GPUs is installed beside it. It works through Dynamic Resource Allocation, the newer Kubernetes way for a Pod to claim a device, and in the stock recipes it serves ComputeDomain and IMEX channels, the resources that let GPUs in different nodes of a rack share memory. Its whole-GPU allocation ships switched off, as resources.gpus.enabled: false, and turning it on is an experimental opt-in. KAI Scheduler places GPU workers with topology in mind and with gang scheduling, which means a group of Pods is placed all together or not at all. Grove orchestrates serving graphs of several components, so they start, are placed and scale as coordinated groups. NVSentinel and Nodewright provide node health signals where the chosen recipe supports them. The Prometheus stack collects cluster, accelerator and Dynamo metrics. For ingress the recipe installs agentgateway, a Gateway API implementation, with Gateway API resources.

Dynamo itself arrives as the dynamo-platform chart, version 1.4.2 in this recipe. It contains the Dynamo operator, the runtime images and the custom resource definitions, among them DynamoGraphDeployment at API version nvidia.com/v1beta1, which replaces the earlier v1alpha1.

Chapter 3 of 13

A recipe from a snapshot

The cluster is described first, and the versions are chosen to fit it

AICR separates setting up the runtime from deploying an application, and it works in five steps. The first two produce the recipe.

Step one takes a snapshot. The command captures the state of the cluster that recipe selection and later validation need. With no placement flags it targets nodes labelled nvidia.com/gpu.present=true and tolerates the taints of GPU nodes. Step two generates the recipe. From the snapshot AICR identifies the Kubernetes distribution, the GPU accelerator and the operating system of the GPU nodes. The command adds two statements of intent: the workload is inference and the platform is dynamo. The output records pinned component versions, configuration for this environment, node selectors, tolerations, checksums, compatibility constraints and the checks to run later.

Pinning is the substance of it. For the Amazon EKS inference recipe for GB200 NVL72 and GB300 NVL72 systems, AICR v1.0.0 selects seventeen Helm charts at exact versions, from the GPU Operator at v26.7.1 to Dynamo Platform at 1.4.2. NVIDIA's AICR team tested those versions together on that platform and hardware, and that is what the word validated refers to at this stage: a combination that was tried, as opposed to the newest release of each part. Those seventeen are the list NVIDIA published for the GB200 and GB300 recipe. The RTX PRO 6000 leaf this lesson follows later, rtx-pro-6000-eks-ubuntu-inference-dynamo, is a different recipe on the same Amazon EKS base, and its exact list of charts can differ, so read it from the recipe AICR writes for your own snapshot.

A recipe can also be checked without touching a cluster, against a snapshot captured elsewhere. That offline run evaluates the declarative constraints and reports the behavioural checks as skipped.

Chapter 4 of 13

Which Kubernetes the whole stack agrees on

Every layer names the minor versions it was qualified on, and the cluster has to sit where those lists overlap

A Kubernetes version has three numbers, such as 1.35.2: the major 1, the minor 35 and the patch 2. New features and API graduations arrive with a new minor. The Kubernetes project keeps release branches for the three newest minors only, which at the time of writing are 1.35, 1.36 and 1.37, and each minor receives about one year of patch releases. Every product that runs on a cluster is tested on some minors and not on others. That testing is called qualification. A vendor that has qualified a release on a minor has run its own test suite there and supports it there. Outside that list nothing has been proven, even when an install appears to work.

AICR writes qualification into the recipe as constraints. A constraint has a name and a comparison. The one that matters here is named K8s.server.version, and it is compared with the server version the snapshot recorded. Recipes are overlays that inherit from each other through spec.base, from general to specific. base.yaml sets the floor at >= 1.32. For RTX PRO 6000 servers on Amazon EKS the chain runs base, eks, eks-inference, rtx-pro-6000-eks-inference and rtx-pro-6000-eks-ubuntu-inference, and the two RTX PRO overlays raise the floor to >= 1.32.4. The last overlay of the chain, the leaf, is the one a query for --platform dynamo resolves to, and it sets >= 1.34. Constraints merge by name, and a later overlay wins over an earlier one with the same name, so the leaf's 1.34 replaces every floor above it in the chain.

The leaf states its reason in a comment: DRA requires Kubernetes 1.34, where it went GA. Kubernetes 1.34 moved the Dynamic Resource Allocation API group, resource.k8s.io/v1, to stable and turned it on by default. The recipe installs the DRA Driver for NVIDIA GPUs, so on an older minor the stable API that driver depends on does not exist. In the stock recipes the driver serves ComputeDomain and IMEX channels, and whole GPUs still reach Pods through the GPU Operator's device plugin, but the floor applies all the same. Every Dynamo recipe in AICR's catalogue ends up with a floor of 1.34 or higher. Most leaves state >= 1.34 themselves. Two inherit it instead: the B300 leaf on mk8s takes >= 1.34 from mk8s.yaml, and the VR200 leaf on RKE2 takes >= 1.34.1 < 1.36.0 from its RKE2 chain. That upper bound shuts out 1.36 and 1.37, two of the three maintained minors. The GKE GB300 Dynamo leaf is stricter and names patch builds of two minors: >= 1.34.3-gke.1318000 < 1.35 || >= 1.35.0-gke.2745000. A 1.34 build older than that patch fails it, and so does any 1.35 build older than its own patch.

The constraint is checked twice. An offline run with --no-cluster needs a snapshot, and the owner found that the snapshot must report 1.34 or later before the Dynamo leaf passes readiness. On a live run AICR evaluates the readiness constraints before any validation phase starts. A failure stops the run before a single validator Job is created, prints the expected and the actual value, and exits with code 2. The fix is to upgrade the cluster or to pick a recipe whose constraints match it.

The data plane in front of the graph has its own list. In the owner's lab notes, one BNK release was qualified on Kubernetes 1.30, and later releases ran on 1.35 on kind, kubeadm and OpenShift clusters. The DPU shows how literal qualification is. The BlueField image that a DPU is flashed with brings Kubernetes 1.34. The DPU guide for the release qualified on 1.30 had the engineer remove that Kubernetes and install 1.30 for arm64 before the DPU joined the cluster. The version skew policy explains why the order matters. A DPU node runs its own kubelet, and a kubelet must never be newer than the API server it talks to. It may be up to three minors older. A 1.34 kubelet under a 1.30 API server breaks the first rule.

Put together, the arithmetic decides the minor. A cluster on 1.30 satisfies the data plane release qualified there and fails the Dynamo leaf, because 30 is below 34. A cluster on 1.35 passes the leaf and needs a data plane release that runs on 1.35. The owner's notes record releases that ran there, which is a weaker statement than qualified, so confirm the qualification list for the release before choosing. With the API server on 1.35, any kubelet in the cluster, on a GPU node or on a DPU, may run 1.32, 1.33, 1.34 or 1.35, because 35 minus 3 is 32. So the order of work is fixed: list the qualified minors of every layer, take the minors they share, choose one, and only then take the snapshot that the recipe is generated from.

Chapter 5 of 13

Render, deploy, then prove it

A bundle in dependency order, and checks that run on the live cluster

Step three renders the recipe into a bundle: Helm values and manifests ready to deploy. Placement is decided here. Flags give the node selector and tolerations for accelerated nodes and, separately, for system nodes, so the GPU workloads and the supporting services land where they should. One setting restricts which source ranges may reach agentgateway. If the cluster has no default StorageClass, the command also needs one named.

Step four deploys. For a local run AICR writes a Helmfile. Components depend on each other, a CRD chart before the chart that uses it, and AICR encodes that as tiers. Helmfile works through the tiers in order and applies independent components inside a tier at the same time. Running apply again reconciles the installed releases with the bundle. Without Helmfile, the default Helm deployer writes a deploy.sh. For production AICR renders GitOps bundles for Argo CD or Flux.

Step five is what makes the runtime validated in the second sense. AICR has three validation phases: deployment, conformance and performance. Step five runs validator Jobs on the live cluster in the first two, deployment and conformance, and writes a report. They check the cluster baseline, down to a working nvidia-smi on the accelerator nodes, the health and version of the GPU Operator and of the Dynamo platform, DRA support, gang scheduling and autoscaling, Prometheus-backed metrics and the readiness of the Gateway. Only when they pass is the application's DynamoGraphDeployment installed. The performance phase is a separate run, because it deploys a temporary serving workload and occupies the GPUs under test.

Chapter 6 of 13

A validated design on RTX PRO Servers

NVIDIA's Enterprise AI Factory fixes the servers, the network and the software, and BNK holds the north-south slot

The word validated has a third meaning, one level above a recipe. The NVIDIA Enterprise AI Factory is a full-stack validated design for an enterprise that builds its own AI factory on premises. It combines Blackwell GPUs, Spectrum-X Ethernet, BlueField, NVIDIA AI Enterprise software and products from partners, tested together and built to run on recommended configurations from NVIDIA's Enterprise Reference Architectures. A reference architecture describes hardware: which servers, how many GPUs and network cards each one has, and how they are connected. The validated design adds the software and the partner products that run on that hardware. A runtime recipe such as AICR's is then installed on the cluster that results.

The hardware comes from the RTX PRO AI Factory reference architecture. Its building block is a 2-8-5-200 server: 2 CPUs, 8 GPUs and 5 network cards at 200 Gb/s each. The 200 is the base rate. NVIDIA's pages also describe a Spectrum-X variant whose east-west interfaces run at 400 Gb/s, and the B3240 recommended for north-south has 400 GbE ports.Each NVIDIA-Certified RTX PRO Server carries eight RTX PRO 6000 Blackwell Server Edition GPUs. Each GPU has 96 GB of GDDR7 memory with up to 1.6 TB/s of memory bandwidth, so one server holds 8 × 96 = 768 GB of GPU memory with up to 8 × 1.6 = 12.8 TB/s in aggregate. Every GPU gets at least one PCIe Gen5 x16 link. The host is sized per GPU: at least 7 physical CPU cores and 128 GB of system memory for each GPU, and 2 more cores per GPU for the operating system kernel or virtualisation. For eight GPUs that is 8 × (7 + 2) = 72 cores and 8 × 128 = 1,024 GB of memory. Servers are grouped in scalable units of four. The guide gives layouts for 16 servers with 128 GPUs and for 32 servers with 256 GPUs, which are 4 and 8 scalable units. Up to eight more nodes run the control plane. NVIDIA's example uses seven of them: 2 for Base Command Manager, 2 Slurm head nodes and 3 Kubernetes control plane nodes.

The five network cards split by direction. Four BlueField-3 SuperNICs carry east-west traffic between GPU servers, with RDMA over RoCE and GPUDirect. That is the network a disaggregated graph moves its KV cache over. Four cards for eight GPUs is two GPUs per card, the highest ratio NVIDIA recommends. The fifth card is a BlueField-3 DPU on the north-south network, the side that faces users, storage and management. NVIDIA recommends the B3220, with two 200 GbE ports, or the B3240, with two 400 GbE ports, for that slot. A DPU there has its own Arm cores and can stand in front of the host. In Embedded Function mode, ECPF, traffic passes a virtual switch on the DPU before it reaches the server. The design targets many users inside one enterprise, a single tenant with consolidated accounting and access control, and it is built for Kubernetes and the tools that depend on it.

That north-south DPU is where BNK sits. F5 validated BIG-IP Next for Kubernetes on RTX PRO Servers with BlueField-3 DPUs, and it is included in the Enterprise AI Factory validated design. On RTX PRO 6000 Blackwell Server Edition it is generally available and is ordered through NVIDIA's channel and OEM partners. F5's announcement of that availability does not say where the data plane runs, and F5 lists RTX PRO 6000 and BlueField DPUs as separate deployment options. In the validated design, which pairs RTX PRO Servers with BlueField-3 DPUs, its data plane, TMM, runs on the DPU, the same B3220 and B3240 models on which BNK's DPU support has been generally available since April 2025. It takes four jobs away from the host CPU and onto the DPU's Arm cores and acceleration engines: load balancing and traffic steering, TLS termination and encryption, firewall and security policy enforcement, and API protection and intrusion detection. In F5's own lab testing that gave more than 30% more token generation throughput and up to 60% lower time to first token. The same data plane counts tokens per tenant, per user or per model, enforces token rate limits, and routes requests between models served by NVIDIA NIM.

The lesson's model fits this hardware with room to spare. The FP8 build of Qwen3-32B, 34.3 GB, fits on one 96 GB GPU and leaves 96 − 34.3 = 61.7 GB. With the KV cache kept in BF16 at 256 KiB, 262,144 bytes, per token, that is 61.7 billion ÷ 262,144 ≈ 235,000 tokens of cache before the engine's memory limit, activations and the CUDA context take their share. A 20,000-token prompt needs 5.2 GB, so about 11 of them fit at once. The BF16 build, 65.5 GB, also fits and leaves 30.5 GB, about 116,000 tokens. Decode reads every weight once per step. At 1.6 TB/s one step over 34.3 GB takes at least 34.3 ÷ 1,600 ≈ 21 ms, a ceiling near 47 tokens per second for a single sequence. Batching many sequences shares that one read, which is why throughput is measured with hundreds of requests in flight.

AICR's catalogue has recipes for this GPU as well. Its Dynamo leaf for RTX PRO 6000 on Amazon EKS carries a performance gate measured on one 8-GPU node serving Qwen/Qwen3-8B with 256 concurrent requests per GPU: about 59,260 tokens per second for the node and a p99 time to first token of about 445 ms. The gate passes at 50,000 tokens per second or more and a p99 of 2,000 ms or less, set below and above the measured values so that run-to-run variation does not fail a healthy cluster.

Chapter 7 of 13

A graph where a Deployment used to be

One resource lists the frontend, the workers and their roles

On the validated runtime, a model is deployed as a DynamoGraphDeployment, DGD for short. It is the description of one running inference graph. Under spec.components it lists the parts by name and type. The types are frontend, worker, prefill, decode, planner and epp. A graph may hold up to 25 components, types may repeat, and only epp is limited to one. spec.backendFramework names the engine, and the operator uses it to inject the right defaults into each component's main container.

The Dynamo operator reconciles the graph, and what it creates depends on the pathway. On the Grove pathway, the one the AICR recipe sets up, the operator builds one PodCliqueSet straight from the graph and creates no DynamoComponentDeployment at all. Only on the path without Grove does it create a DynamoComponentDeployment for each component, and from those the Deployments or LeaderWorkerSets, the Pods and the Services. The status reports a componentKind per component: a plain Deployment, a LeaderWorkerSet, or with Grove a PodClique or PodCliqueScalingGroup. With Grove the whole graph is one PodCliqueSet, and KAI Scheduler can place the cliques as gangs and by network topology. That is the answer to the scheduling problem from the first chapter.

The component's type also becomes a Pod label, nvidia.com/dynamo-component-type, which routing later selects on. An aggregated graph has a frontend and workers that do both phases. A disaggregated graph replaces the workers with two components, one of type prefill and one of type decode. Each starts the same engine with --disaggregation-mode set to its role. Both must load the same model with the same block size and KV layout, or the cache one produces cannot be read by the other.

Chapter 8 of 13

Three planes: who is there, requests, and cache news

No etcd and no NATS in the default path

The parts of a graph talk on three separate planes. The discovery plane answers who is there. Outside Kubernetes Dynamo uses etcd for it, with a lease per runtime that expires ten seconds after the heartbeats stop. On Kubernetes the operator sets DYN_DISCOVERY_BACKEND to kubernetes, and discovery uses the cluster's own resources. Each worker writes a DynamoWorkerMetadata resource describing its endpoints, EndpointSlices signal which Pods are ready, and frontends watch both. No extra store is needed, and a Pod that disappears is cleaned up with it.

The request plane carries the requests from a frontend to a worker. In Dynamo 1.4.2 it runs over TCP by default.

The event plane carries news: KV cache changes, worker load and sequence tracking between router replicas. Its default transport is ZMQ, a messaging library without a broker. Each worker binds a publishing socket and advertises it through discovery, and subscribers connect to every publisher and adjust as workers come and go. NATS, a broker, remains an option, selected with DYN_EVENT_PLANE=nats. AICR's default path no longer uses it, and the dynamo-platform chart no longer installs it by default.

One detail is easy to miss. The vLLM engine inside a worker publishes raw cache events on a local ZMQ socket. The Dynamo worker runtime subscribes to that local source, normalises the events into Dynamo's own form and publishes them again on the event plane. Routers listen to Dynamo's stream, never to vLLM directly. Without events a router can only predict the cache from its own decisions, and prediction cannot see evictions.

Chapter 9 of 13

Path one: the Frontend chooses the worker

The smallest topology, and the one with the longest record in production

Dynamo has two routing paths on Kubernetes, and the runtime is validated for both. In the first, clients reach a Dynamo Frontend behind an ordinary Service. The Frontend is an OpenAI-compatible HTTP server with a router inside. Run with --router-mode kv, or the environment variable DYN_ROUTER_MODE=kv, it tokenizes each request, scores the eligible workers by how much of the prompt's prefix they hold and by their present load, picks one and sends the request over the request plane.

The score is a cost, and lower is better. For each worker the router takes the prefill blocks the request would need, reduces them by the blocks already cached there, scales the result and adds the worker's decode blocks. Two settings shift the balance. The overlap credit, a finite number of 0 or more with a default of 1, says how much a cached prefix counts. Values above 1 give a cached prefix extra credit, but the adjusted prefill cost is clamped at zero and never goes negative. At 0 the router ignores caches and does not even build its index. The prefill load scale, default 1, says how much prompt work counts against decode load.

This path suits a team that owns a model-specific endpoint, or an edge proxy that only needs to pass traffic on. It needs nothing beyond the frontend and the workers. NVIDIA calls it the smallest topology and the most production-proven. Agentic workloads are where it pays most. An agent's turns keep extending one long prefix of system prompt, tool definitions, history and tool results. A turn that lands on a worker without that prefix makes the GPU read all of it again.

Chapter 10 of 13

Path two: a Gateway and an endpoint picker

The same routing logic, with the Gateway carrying the traffic

The second path fits a platform team that runs shared ingress through the Gateway API and wants timeouts, retries and fallback handled there. A Gateway, agentgateway in the AICR example, resolves an HTTPRoute to an InferencePool, the resource of the Gateway API Inference Extension that stands for a set of model servers with an endpoint picker in front.

Nobody writes that pool by hand. Adding one component of type epp to the graph makes the Dynamo operator create the picker's Deployment and Service and an InferencePool named after the graph with the suffix pool. The pool's selector matches the worker Pods and its endpointPickerRef points at the picker. For each request the Gateway asks the picker, which tokenizes the prompt and runs Dynamo's KV router to choose an endpoint. The picker returns the choice and some routing metadata, and the Gateway, which is the real HTTP proxy here, forwards the request.

It does not forward to the engine. Each routable worker Pod carries a Frontend as a sidecar, named in the component's frontendSidecar field and run with --router-mode direct. The sidecar accepts the request, applies the picker's choice without choosing again, and hands it to the worker container over the request plane. In Dynamo 1.4 the picker is the extension's Go framework with Dynamo's Rust router embedded through CGO and configured through eppConfig. From Dynamo 1.5 a native Rust picker replaces that bridge and is configured with DYN_ environment variables. The topology around it stays the same.

Chapter 11 of 13

Prefill here, decode there

One request, two workers, and a hand-off in between

In a disaggregated graph one request is served by two workers in sequence. Execution has three steps: a prefill engine computes the prefill phase and produces the KV cache, the cache is transferred to a decode engine, and the decode engine generates the tokens.

A router stage called the PrefillRouter orchestrates it. The Frontend activates it by itself when it discovers a decode worker and a prefill worker registered for the same model. The stage first selects a prefill worker, with KV-aware routing, since this is where a cached prefix saves work. It sends the request there. The prefill worker computes the cache and returns a small result, disaggregated_params, with the metadata a decode worker needs to fetch it. For vLLM that is kv_transfer_params: block IDs and how to reach the prefill worker. The router then selects a decode worker and sends it the request with that metadata. The decode worker pulls the cache, generates, and streams the answer back through the Frontend.

The decode choice follows different rules. Overlap scoring is switched off there, because decode routing should not chase prefix reuse, and prompt tokens are not counted as its load. With vLLM, prefill runs to completion before decode starts. SGLang lets decode begin while the transfer proceeds. A failure after the request has been sent to prefill is returned to the caller. The router does not fall back to serving it as an aggregated request.

Chapter 12 of 13

The cache crosses the fabric

From one GPU's memory to another's, and why the transport decides everything

The decode worker now has to get the KV cache out of the prefill worker's GPU memory and into its own. Dynamo's transfer layer for this is NIXL. It moves the cache directly from the memory of one GPU to the memory of the other, and the transfer does not block either engine: forward passes for other requests continue meanwhile. NIXL itself sits on a lower communication library, UCX or libfabric, which drives the actual transport.

Which transport is available decides whether disaggregation helps or hurts. Between two Pods the fast in-server link, NVLink, cannot be used, even on one node. Pods are separate processes with separate GPUs assigned, and NVLink peer access needs both GPUs inside one process. That leaves the network. With RDMA, over InfiniBand, RoCE or on AWS the EFA adapter, the network card reads and writes memory directly. With GPUDirect RDMA it reads and writes GPU memory, so the cache never passes through host memory or the kernel. Without RDMA the transfer falls back to TCP: out of the GPU into host memory, through the kernel's network stack, and back up on the other side.

Dynamo's documentation puts numbers on the difference: 200 to 500 times slower, with an observed time to first token of about 98 seconds over TCP against 200 to 500 milliseconds with RDMA. A cluster without an RDMA fabric should serve aggregated.

Chapter 13 of 13

Scaling each pool, and losing a worker

Replica counts owned by an autoscaler that thinks in token latency

Two pools can be sized separately, and that is the point of splitting them. Prefill replicas follow input length and prompt reuse. Decode replicas follow concurrency, output length and KV memory in use. Disaggregation supports any mix of x prefill and y decode workers and changes at run time. A new worker registers through discovery and publishes its configuration, including its KV capacity. A worker being removed drains its requests and deregisters.

In the graph, a component opts into autoscaling with a scalingAdapter field, even an empty one. The operator then creates a DynamoGraphDeploymentScalingAdapter that owns the replica count and implements the Kubernetes Scale subresource, so HPA, KEDA or Dynamo's Planner can drive it. The Planner is the autoscaler built for this. It has four optimisation targets. throughput is the default and scales on queue depth and KV cache utilisation. latency scales earlier. load uses thresholds you set for the prefill queue and decode KV utilisation. sla aims at stated values for first-token and inter-token time. It plans capacity on a long interval, 180 seconds by default, and corrects for bursts on a short one, 5 seconds.

Workers also fail. Request migration, configured on the Frontend and off by default, moves a generation in progress to a healthy worker and continues from the exact token where it stopped. One limit to know: scaling a worker pool to zero is not fully supported. With no worker left the Frontend removes the model from its list and answers 404.

What to keep

Check the ground, then build the graph on it

Dynamo on Kubernetes is two layers. The lower one is a runtime of ordinary cluster components, the GPU Operator, a DRA driver, KAI Scheduler, Grove, health and metrics, a Gateway, that AICR selects as a recipe of pinned versions, deploys in dependency order and then checks on the live cluster. The upper one is a DynamoGraphDeployment that names a frontend, the workers and their roles. Requests enter through Dynamo's Frontend or through a Gateway with an endpoint picker, and both route on the cache state that workers publish. In a disaggregated graph one worker reads the prompt, NIXL moves the KV cache to another over RDMA, and that one writes the answer. Each pool then scales by the pressure it feels. Under all of it sits one Kubernetes minor that every layer is qualified on, 1.34 or later for the Dynamo recipes, and above it a validated design such as NVIDIA's Enterprise AI Factory can fix the servers, the two networks and the place of BNK on the north-south DPU.
