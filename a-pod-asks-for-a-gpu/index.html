Kubernetes underneath

A Pod asks for a GPU

How a card in a server becomes a number Kubernetes can schedule

Kubernetes was built to hand out CPU and memory. It has no idea what a GPU is. A GPU reaches a Pod through a chain of four small agreements. A program on the node tells the kubelet that GPUs exist. The kubelet turns that into a number on the node. The scheduler does arithmetic on that number and nothing more. And when a Pod lands, the container runtime puts the real device inside the container. This lesson follows one model server through all four, and then shows what the arrangement cannot do.

The story runs on cluster northlight-eu, with two GPU nodes of four cards each. gpu-node-2 already runs four model servers. gpu-node-1 runs three and has one card free. A new vLLM Pod of the Deployment qwen3, qwen3-6f7d9c8b4-x7k2p, asks for one GPU. After it starts, the lesson keeps going: a card fails, the kubelet restarts, a ninth model server finds no room, and the cluster's owners look at sharing a card and at the newer way of asking for devices. Every name, field and message is the one an operator meets on a real cluster.

Chapter 1 of 13

The plugin opens its socket, then registers

A fixed directory, a fixed order, and a request with four fields

A GPU node boots. On it runs a small program from NVIDIA called a device plugin. It is usually started as a DaemonSet, so one copy runs on every GPU node like any other Pod. The kubelet and the plugin talk over gRPC on Unix sockets, which are files on the node that two programs can connect through. All of these sockets live in one directory, /var/lib/kubelet/device-plugins/. The Kubernetes documentation calls this path hardcoded. It does not move when the kubelet's root directory is changed. Writing a socket there needs privileges, so the plugin runs in a privileged security context and mounts that directory from the node.

The order of the first steps is fixed. The plugin first starts its own gRPC server on its own socket in that directory. Only then does it call Register on the kubelet's socket, kubelet.sock. The documentation says a plugin must be serving before it registers, because the kubelet connects back to it at once. Registering first would point the kubelet at a socket that nobody answers.

The Register request carries four fields. version is the device plugin API version, and the only one the kubelet accepts is v1beta1. endpoint is the file name of the plugin's socket, which the kubelet joins to the directory. resource_name is the name the plugin will answer for, here nvidia.com/gpu. options says which optional calls the plugin supports. The kubelet can refuse. It does so when the version is not supported or when another active plugin already holds the same resource name. A refused plugin is expected to exit.

Chapter 2 of 13

The kubelet counts and publishes

A stream of devices on one side, two numbers on the node on the other

After registration the kubelet opens ListAndWatch on the plugin. This is a stream that stays open for as long as both are alive. The plugin sends the full list of its devices at once, and sends the whole list again whenever anything changes. Each device has three fields. ID is a string of at most 63 characters. NVIDIA's plugin uses the card's UUID by default, a string that begins with GPU-. health is exactly one of two strings, Healthy or Unhealthy. topology lists the NUMA nodes the card is close to, which matters later for CPU placement.

The kubelet does not pass the list on. It writes two numbers into the node's status in the API server. allocatable is the count of healthy devices. capacity is healthy plus unhealthy. With four healthy cards both read 4. From now on, as far as the rest of the cluster knows, this node has four of something called nvidia.com/gpu. Which cards they are, what model, how much memory: none of it is in those numbers.

A resource with a name like this is an extended resource. Its name is fully qualified, with a domain prefix. Any domain except kubernetes.io may be used, and a device plugin's name takes the form vendor-domain/resourcetype. Kubernetes needs no plugin to learn such a number. An administrator can add one by hand with a JSON patch to the node's status, at the path /status/capacity/example.com~1dongle, where ~1 stands for the slash. The documentation's own words: Kubernetes does not need to know what a dongle is. That is the whole idea. The API server holds a count and nothing else.

Chapter 3 of 13

The Pod asks for one

One line in the Pod, and it has to be a whole number

Now someone applies a Pod for a model server. Asking for a GPU is one line under the container's resources: a limit of one nvidia.com/gpu. Two rules apply to it that do not apply to CPU. It has to be a whole number, so there is no asking for half a card. And it cannot be overcommitted. For CPU a Pod may request less than its limit and share. For an extended resource the request always equals the limit, so a GPU that is given out is gone.

The GPU documentation spells out three cases. A limit alone is enough, because Kubernetes uses the limit as the request. A limit and a request may both be given, but they must be equal. A request without a limit is not allowed. Whole number is checked on the value, not on how it is written. 3 and 3000m are valid and mean the same count, 3. 3Ki is valid too, but it means 3 × 1024, so it asks for 3072 devices, not 3. 0.5 is not valid, and neither is 1500m, because that is 1.5.

NVIDIA's README carries a warning that surprises people. A container that asks for no GPU at all can be given every GPU on the machine. The README does not say why. The usual cause is an environment variable. NVIDIA's CUDA base images set NVIDIA_VISIBLE_DEVICES to all, and NVIDIA's runtime, when it is the node's default runtime, obeys it. So a Pod that forgets the line may not fail. It may quietly use cards that other Pods were given. The GPU Operator's documentation narrows this for its CDI default from v25.10.0: there a container that gets GPUs through NVIDIA_VISIBLE_DEVICES, instead of through the device plugin, must set runtimeClassName: nvidia, unless the Operator's NRI plugin is on.

A namespace can be held to a budget of GPUs with a ResourceQuota. For an extended resource only items that start with requests. are allowed, for example requests.nvidia.com/gpu. The inference namespace here has a quota of 10, and 7 are in use, so this Pod fits and the count becomes 8. The API server stores the Pod. It has no node yet, and it sits in Pending until something chooses one.

Chapter 4 of 13

The scheduler filters by subtraction

It counts GPUs. It never sees one

The scheduler watches for Pods with no node. Each attempt to place one has two halves. The scheduling cycle picks a node. The binding cycle writes that choice into the cluster. Scheduling cycles run one Pod at a time. Binding cycles may run side by side.

The scheduling cycle first rules nodes out, in a phase called Filter, then ranks what is left. A node goes through a series of filter plugins, and the first one that says no ends that node's chance, so the rest are not asked. The GPU count is used in the plugin that checks resources. For every extended resource the Pod asks for, it takes the node's allocatable number and subtracts what the Pods already bound there have requested. If the Pod's request is larger than what is left, the reason it records is the text Insufficient followed by the resource name. Its neighbours are fixed texts: Insufficient cpu, Insufficient memory, Insufficient ephemeral-storage and Too many pods.

The subtraction uses requests, never live use. A model server that has been idle for a week still holds its GPU on paper. gpu-node-2 has four GPUs and four model servers, so 4 minus 4 leaves 0 and it is ruled out. gpu-node-1 has three in use and one free, so 4 minus 3 leaves 1 and it passes.

A GPU node usually also carries a taint, a mark that keeps ordinary Pods away, and this Pod carries the matching toleration. The Kubernetes documentation recommends naming the taint after the extended resource and turning on the ExtendedResourceToleration admission controller. It adds the toleration to every Pod that asks for that resource. It is off by default.

Chapter 5 of 13

Score, reserve, bind

The node is chosen in one cycle and written down in another

After Filter, the scheduler scores the nodes that passed. Here only gpu-node-1 is left, so it wins whatever the scores are. With several candidates the default scoring does not try to pack GPU nodes full. Packing is something an operator turns on. The NodeResourcesFit plugin has a scoring strategy, and two of its strategies favour nodes that are already busy: MostAllocated and RequestedToCapacityRatio. Each resource can be given a weight there, so nvidia.com/gpu can count for more than CPU. On a GPU cluster that keeps whole nodes free for a job that needs all four cards of one machine.

Between choosing and binding comes a phase called Reserve. The scheduler marks the GPU as taken in its own memory before it has told anyone. This closes a race. Without it, two Pods scheduled one after the other could both see gpu-node-1 with one free card, because the first binding has not landed yet. With it, the second Pod sees 0 free at once.

Then the binding cycle writes the choice. It posts a Binding object for the Pod, whose target is the Node gpu-node-1. The API server sets spec.nodeName on the Pod. The scheduler's part is done. It chose a node. It did not choose a card, and it could not, because it has never seen one. If no node had passed Filter, a phase named PostFilter would run instead. Its usual job is preemption, which the chapter on running out shows.

Chapter 6 of 13

The kubelet admits the Pod and picks the card

Only the node knows which GPUs are free

The kubelet on gpu-node-1 has been watching for Pods bound to its node, and this one arrives. Before it starts anything it runs its own admission. It checks the request again against its own books, because it alone knows which of the four cards are taken. Devices are handed out here, at admission, before any container exists. The device plugin API says why: a container that cannot get its device would make the Pod fail to start, so the failure should come early.

The kubelet's part that keeps the books is called the device manager. It writes every assignment to a checkpoint file next to the sockets, /var/lib/kubelet/device-plugins/kubelet_internal_checkpoint. That file survives a kubelet restart, so the kubelet still knows after a restart which card belongs to which container.

If the plugin said get_preferred_allocation_available, the kubelet first asks it which cards it would prefer. It sends the IDs that are free, the IDs that must be included and how many are needed. A plugin can use this to keep cards that share a fast link together. The answer is advice. The device manager makes the final choice. Here one card is free and the kubelet assigns it.

Then comes Allocate. This call asks the plugin what a container needs in order to use this device. The answer has five parts: environment variables, mounts, device files, annotations and CDI device names. With the standalone plugin's default, DEVICE_LIST_STRATEGY=envvar, only the first is used, one variable naming the card. The GPU Operator from v25.10.0 turns CDI on and sets the strategy to cdi-annotations,cdi-cri. The answer then names the card as a CDI device instead, in an annotation with the prefix cdi.k8s.io/ and in cdi_devices. If the node cannot satisfy the Pod after all, the kubelet rejects it with the reason UnexpectedAdmissionError and a message that wraps the cause: Allocate failed due to, then the error, then which is unexpected.

Chapter 7 of 13

The runtime puts the GPU in the container

A container sees only what is put inside it

A container is a process with a restricted view of the machine. Left alone it would see no GPU at all, because the card's device files are not in its view. The kubelet asks containerd to create the container and passes along what the plugin said. Here NVIDIA's container toolkit takes over, as a step in creating the container.

There are two ways it does that. In the older way, containerd's runtime for the node is the NVIDIA Container Runtime, a thin wrapper around runc. It takes the container's specification, adds a prestart hook to it and calls the real runc. The hook reads the container's config.json and runs nvidia-container-cli, from the libnvidia-container library, which does the mounting. An administrator points containerd at this runtime with nvidia-ctk runtime configure --runtime=containerd, which writes a drop-in file /etc/containerd/conf.d/99-nvidia.toml. In the newer way, CDI, the Container Device Interface, a file describes each device ahead of time. Since toolkit v1.18.0 a service named nvidia-cdi-refresh writes it to /var/run/cdi/nvidia.yaml. From GPU Operator v25.10.0, CDI is the default on Kubernetes.

Either way, three kinds of thing are added. The device file of the one card, which keeps its node name. The free card here is the node's /dev/nvidia3. The driver's control devices, /dev/nvidiactl and /dev/nvidia-uvm. And the driver's user libraries from the node, chosen by NVIDIA_DRIVER_CAPABILITIES. Unset, it means utility and compute: the management library behind nvidia-smi and the CUDA library. They come from the node, not the image, so they match the kernel driver exactly. Then the process starts. Inside, CUDA numbers the one card it can see as device 0.

Chapter 8 of 13

Which container holds which card

The kubelet answers on a second socket, and counts what it does

The API server never learns which card qwen3-6f7d9c8b4-x7k2p got. An operator who wants to know, or a program that exports GPU metrics, asks the kubelet directly. It serves a second gRPC API for this, the PodResources API, on the socket /var/lib/kubelet/pod-resources/kubelet.sock. Its service is called PodResourcesLister. List returns every Pod and container on the node with the devices each one holds. Each entry gives a resource_name, the device_ids and their topology. GetAllocatableResources returns everything the node could hand out. Get returns one Pod. List and GetAllocatableResources are stable since Kubernetes v1.28. Get has its own feature gate, KubeletPodResourcesGet: alpha from v1.27, beta and on in v1.34 and v1.35, stable from v1.36. A GPU monitoring agent uses this to label a card's temperature and memory use with the Pod that owns it.

The kubelet also exports metrics about the plugin. kubelet_device_plugin_registration_total counts registrations for each resource name. kubelet_device_plugin_alloc_duration_seconds is a histogram of how long Allocate calls take. kubelet_device_plugin_devices reports the number of devices for each resource name and each health state, healthy or unhealthy. All three are marked alpha.

Newer clusters also put device health on the Pod itself. With the feature gate ResourceHealthStatus, beta and on by default since v1.36, each container's status gains a field allocatedResourcesStatus. It lists the devices the container was given and the health of each one. Before v1.31 the only way to tie a Pod to a failed device was the PodResources API.

Finally there is topology. Each device carries the NUMA nodes it sits near. The kubelet's Topology Manager can use that to keep a GPU and the Pod's CPUs on the same socket. Its policies are none, the default, best-effort, restricted and single-numa-node.

Chapter 9 of 13

When the cluster runs out

One message on a Pending Pod, then preemption if priorities allow

Both nodes are now full: four model servers on each, eight GPUs given out. Someone scales the Deployment and a ninth model server, qwen3-6f7d9c8b4-r5h8w, is created. It comes from the same revision, so it keeps the pod-template-hash 6f7d9c8b4 and gets new random characters. The namespace's quota still allows it, 9 of 10, so the API server stores the Pod. The scheduler runs Filter on both nodes. Each has 4 allocatable and 4 requested, so each is ruled out with Insufficient nvidia.com/gpu. No node passes.

Then PostFilter runs. Its usual job is preemption. If the new Pod has a higher priority than some Pod already on a node, the scheduler can evict that Pod to make room. A GPU it frees becomes free on paper once the evicted Pod is gone. Here all nine model servers have the same priority, so nobody is evicted.

The Pod stays Pending. The scheduler records why on the Pod, in the condition PodScheduled with the status False and the reason Unschedulable. The message is built from the same reason text each node produced, counted and ended with a full stop. The preemption step then adds its own verdict, which starts with the word preemption and a colon. Here the whole message reads 0/2 nodes are available: 2 Insufficient nvidia.com/gpu. preemption: 0/2 nodes are available: 2 No preemption victims found for incoming pod. kubectl describe pod shows it under Events with the reason FailedScheduling. That message means the request is fine and the cluster is full. A real error in the Pod looks different.

Nothing in Kubernetes itself queues GPU jobs fairly between teams. The owner's infrastructure notes list batch schedulers that add that on top: Volcano, Kueue and Slurm, and the owner's own lab runs NVIDIA's KAI Scheduler with a queue per tenant. A Pod that waits on them still shows the same Pending state underneath. The way out is always one of three things: free a card, add a node, or share cards. Sharing comes in a later chapter.

Chapter 10 of 13

When a card fails

Allocatable drops, capacity stays, and the Pod is not moved

Some weeks later, the card held by qwen3-6f7d9c8b4-x7k2p reports a serious fault. NVIDIA's plugin learns of it from the driver. It registers with NVML, NVIDIA's management library, for three kinds of event: critical Xid errors, double-bit ECC errors and single-bit ECC errors. Only the first kind can change a card's health. The plugin's health loop skips every event that is not a critical Xid, with the log line Skipping non-nvmlEventTypeXidCriticalError event, so an ECC event on its own never marks a card unhealthy. An Xid is a numbered error report from the driver. Not every Xid means a broken card. The plugin ignores seven that are usually the application's own fault: 13, 31, 32, 43, 45, 68 and 69. Number 31, for example, is a GPU memory page fault. Any other critical Xid marks the device unhealthy, and the plugin logs XidCriticalError with the number and the device. The variable DP_DISABLE_HEALTHCHECKS can turn these checks off, with all or xids, or add more numbers to ignore. DP_ENABLE_HEALTHCHECKS names Xids to check even so, and it wins over the disabled list, so an operator can switch all Xids off and a few back on. One more case marks cards unhealthy without any Xid: if waiting for events fails with an NVML error other than a timeout, the plugin marks every device it watches unhealthy. NVIDIA's README is frank that the plugin still lacks comprehensive health checking.

The plugin sends its device list again on the ListAndWatch stream, with that card now Unhealthy. The kubelet lowers allocatable from 4 to 3. capacity stays at 4, because it counts healthy and unhealthy cards together. The difference of one is how an operator spots a broken card from the node object alone.

qwen3-6f7d9c8b4-x7k2p is not moved. The documentation says Pods assigned to a failed device stay assigned to it. Code that uses the card will start failing. With restartPolicy Always, which a Deployment's Pods have, the container goes into a crash loop on the same broken card. The kubelet will not hand it another one. Someone has to delete the Pod so its replacement can be scheduled anew. Then the scheduler sees 3 allocatable and 3 requested on gpu-node-1 and the replacement waits for a card elsewhere.

Chapter 11 of 13

When the kubelet or the plugin restarts

Sockets are wiped, the count can read zero, and a five-minute grace

The kubelet is upgraded on gpu-node-1. A new kubelet deletes every Unix socket in /var/lib/kubelet/device-plugins when it starts. The plugin is expected to notice that its socket is gone and register again. NVIDIA's plugin does.

In the gap, the count can read zero. The kubelet source says so in a comment. After a restart, device plugin capacities can drop to zero until the plugins register again. Running Pods are safe, because admission adjusts the node's numbers for Pods that already hold devices, and the assignments come back from the checkpoint file. New Pods that need a GPU are not scheduled until the plugin is back. On a busy cluster that shows up as a few seconds of Insufficient nvidia.com/gpu on a node with free cards.

The other direction is the plugin going away. If its endpoint stops, the kubelet keeps it for a grace period of five minutes, so a quick restart of the plugin does not erase the resource. During that time every healthy device of that resource is moved to the unhealthy set. allocatable falls to 0 at once and capacity still counts the cards. If the plugin has not come back after five minutes, the kubelet sets capacity to 0 and logs Set capacity for removed resource to 0 on device removal. That line is logged at verbosity 2, so it shows only when the kubelet runs with --v=2 or higher. It keeps the resource name on the node with a 0 instead of deleting it, to show that a plugin managed it before.

Right after a reboot, a container can also ask for a device before the plugin has registered. The kubelet then rejects the Pod with UnexpectedAdmissionError, and the message wraps the cause: Allocate failed due to cannot allocate unregistered device nvidia.com/gpu, which is unexpected.

Chapter 12 of 13

Sharing a card: time-slicing, MPS and MIG

Each one makes the node report a larger number

A whole 80 GB card for a notebook that uses a twentieth of it is waste, and the scheduler counts the node as full all the same. NVIDIA's plugin can share cards in three ways. Each has to be set up on the node, and each ends the same way: the node reports a larger number.

Time-slicing is set in the plugin's configuration as sharing.timeSlicing.resources with a number of replicas. The README's example: with 10 replicas on a node with 8 GPUs, the plugin advertises 80 nvidia.com/gpu. It simply makes 10 references to each card and hands them to anyone who asks. On gpu-node-1, 4 replicas would turn 4 cards into 16. Nothing is isolated. Every workload can reach all of the card's memory, and they share one fault domain, so if one crashes they all do. Asking for two replicas buys no more compute, because CUDA gives an equal share of time to every process on the card. The option renameByDefault advertises nvidia.com/gpu.shared instead, so nobody mistakes a slice for a card. failRequestsGreaterThanOne makes a request for more than one fail at admission.

MPS is set the same way, as sharing.mps.resources with a number of replicas, and the node again reports the larger number. The README's example is the same arithmetic: 10 replicas on a node with 8 GPUs advertise 80 nvidia.com/gpu. The difference is enforcement. A control daemon divides memory and compute and limits each client to an equal fraction, so with 10 replicas each Pod gets a tenth of the card: 8 GB of an 80 GB card. It cannot be combined with time-slicing, does not work with MIG, and the README still marks it experimental. Both apply to every GPU on a node alike.

MIG, Multi-Instance GPU, splits a card in hardware. With the strategy single, each slice is an nvidia.com/gpu. With mixed, each slice gets a name from its profile, such as nvidia.com/mig-1g.10gb or nvidia.com/mig-3g.40gb on an 80 GB A100. The strategy does not switch MIG on. That is done on the card. Labels tell cards apart: GPU Feature Discovery writes nvidia.com/gpu.product, nvidia.com/gpu.memory in MiB, nvidia.com/gpu.count and nvidia.com/gpu.replicas.

Chapter 13 of 13

What replaces the count: dynamic resource allocation

Devices described by attributes and claimed by name

Everything so far rests on one integer per node. The Kubernetes documentation lists what that cannot do. Device plugins need a request for each container, cannot share a device between containers and cannot filter devices by an expression. Dynamic Resource Allocation, DRA, is the answer the project built.

With DRA a driver on each node publishes ResourceSlices. Each one lists real devices with their attributes, such as model, memory and driver version, instead of a bare count. An administrator defines DeviceClasses, a named kind of device with a selector. A Pod refers to a ResourceClaim, or a ResourceClaimTemplate that makes one claim per Pod. The claim selects devices with CEL expressions on their attributes, for example a GPU with at least 80 GB of memory. The scheduler now sees attributes and allocates specific devices. The device reaches the container through CDI, the same file-based mechanism the newer NVIDIA path already uses. Two containers can share one claim, and so one device.

DRA's feature gate was alpha in 1.30 and 1.31, beta and off by default in 1.32 and 1.33, stable and on by default from 1.34, and locked on from 1.35.

The one-line request does not have to go away. A DeviceClass can name an extendedResourceName, and then a Pod that asks for nvidia.com/gpu: 1 is served by a DRA driver. That gate, DRAExtendedResource, is beta and on by default in 1.36 and stable from 1.37. For qwen3-6f7d9c8b4-x7k2p nothing in its manifest would change. Underneath, the scheduler would pick a particular card on a particular node, which is the step this lesson showed the kubelet doing.

What to keep

A count, a node, a card, a device file

A GPU reaches a Pod in four steps, each owned by someone else. A device plugin serves a socket, registers, and streams a list of devices with their health. The kubelet publishes that as two numbers on the node, allocatable and capacity. The scheduler subtracts requests from allocatable, reserves, and binds the Pod to a node. The kubelet admits it, picks the card, records the choice in its checkpoint and asks the plugin how to expose it. The container runtime, through NVIDIA's hook or a CDI file, puts the device files and the driver's libraries inside. Because the cluster only ever holds a count, GPUs come whole unless a node is set up to share them, cards look alike unless labels say otherwise, a failed card lowers allocatable and leaves its Pod in place, and running out shows up as one message on a Pending Pod. Dynamic resource allocation replaces the count with real devices and attributes.
