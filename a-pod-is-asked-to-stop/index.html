Kubernetes underneath

A Pod is asked to stop

Thirty seconds of grace, and an answer that takes a minute

Pods are deleted all the time: by a rolling update, by a node being emptied for repair, by a scheduler that needs the GPU for something more important, by someone with kubectl. Kubernetes does not pull the plug. It writes down a deadline, asks the processes to stop, and waits. Two parts of the cluster react to that request at the same moment and neither waits for the other. One stops the server. The other stops sending it traffic. If the first is quicker, requests arrive at a server that is already shutting down. A model server adds a second problem. One streamed answer can run for a minute, and the default deadline is thirty seconds. A third problem sits inside the server itself, because what it does when the signal arrives is a setting of its own. This lesson follows the Pod qwen3-6f7d9c8b4-m9q4t on gpu-node-2 through all three, step by step, with the fields, events and log lines an operator sees along the way.

Chapter 1 of 12

A delete sets a deadline

The Pod is marked, and it is still there

You delete the Pod qwen3-6f7d9c8b4-m9q4t. The API server does not remove the object. It writes two fields into the Pod's metadata. deletionGracePeriodSeconds is how long the Pod has. deletionTimestamp is the moment that time runs out. Neither can be undone. From now on kubectl shows the Pod as Terminating. Terminating is not one of the Pod phases. kubectl prints it for any Pod that has a deletionTimestamp and has not yet reached a terminal phase. The phase underneath is still Running. Its container is still running, its GPU is still in use and it is still answering requests.

The API server picks the grace period by a fixed rule. If the delete request carries a period, that one is used. If not, the Pod's own spec.terminationGracePeriodSeconds is used, and that field defaults to 30. Two cases skip the wait entirely. A Pod that was never bound to a node has no process to stop, so it is deleted at once. A Pod that has already finished, in phase Succeeded or Failed, is also deleted at once. That is why a surge Pod that sits Pending for lack of a GPU vanishes the instant it is deleted.

A second delete of a Pod that is already terminating can only shorten the time. The timestamp may be brought forward and never pushed back. Everything that follows is other components noticing those two fields. Nobody is told directly. Each one watches the API server and reacts when it sees the mark.

Chapter 2 of 12

Two watchers start at once

One stops the server. One stops the traffic. Neither waits

Two components were watching this Pod and both see the mark within moments. The kubelet on gpu-node-2 runs the Pod. It begins the local shutdown: first a preStop hook if the container has one, then a signal to the process. Meanwhile the EndpointSlice controller in the control plane keeps the EndpointSlices, the objects that list the addresses behind each Service. It marks this Pod's address as terminating so that nothing new is sent to it.

The two paths share no lock and no message. The kubelet does not ask whether traffic has stopped. The controller does not ask whether the server is still up. Each reacts to the same field in the same object, and each has its own queue, its own delays and its own work to do. Which one finishes first is a race. The rest of this lesson is about what happens when the wrong one wins.

A third watcher acts as well. The ReplicaSet that owns qwen3-6f7d9c8b4-m9q4t stops counting a Pod that carries a deletion timestamp. It sees seven of eight and creates a replacement straight away. On a fleet where every GPU has an owner, that replacement has nowhere to go. The only free card will be the one qwen3-6f7d9c8b4-m9q4t still holds, so the new Pod stays Pending with the scheduler message Insufficient nvidia.com/gpu until this shutdown is complete. Every second the shutdown takes is a second the replacement waits.

Chapter 3 of 12

One endpoint, three conditions

The address stays in the list with new flags

The Pod's address is not deleted from the EndpointSlice. It stays, and its conditions change. There are three, and the controller computes them in three lines. serving is whether the Pod's Ready condition is true. terminating is whether the Pod has a deletion timestamp. ready is serving and not terminating, unless the Service has spec.publishNotReadyAddresses set to true, in which case ready is always true. So for a Pod that is shutting down, ready is false, even while serving is still true.

The EndpointSlices page says only that ready is essentially a shortcut for checking serving and not terminating. The reason it is forced to false comes from the controller's source, whose comment says that for compatibility reasons ready should never be true for a Pod that is terminating, unless publishNotReadyAddresses is set. Consumers that predate the two newer conditions read only ready, and forcing it to false keeps them from sending regular traffic to a Pod that is going away. serving and terminating let a load balancer that wants more detail see the difference between a Pod that is broken and one that is finishing its work. The documentation marks both as stable since Kubernetes 1.26.

The endpoint leaves the slice when the Pod reaches a terminal phase, Succeeded or Failed, or when the Pod object is deleted, whichever comes first. The controller's rule for which Pods belong in a slice leaves out terminal Pods. Until then a slice for a Service of this size holds both the terminating address and, once it is Ready, the replacement's. A slice holds up to 100 endpoints by default, a limit set with the kube-controller-manager flag --max-endpoints-per-slice, up to 1000. Here the gateway's controller reads the slice and reprograms the gateway, which sends requests straight to Pod addresses. kube-proxy reads the same slice to program Service rules on each node.

Chapter 4 of 12

Inside the kubelet, in order

Probes stop, an event is written, and the runtime is told how long it has

The kubelet stops each container in a fixed order of steps. First it stops the container's liveness and startup probes, so that a server that slows down while shutting down is not restarted in the middle of it. The readiness probe keeps running, on purpose. A draining server that starts to fail it is marked not Ready, and serving on its endpoint turns false. Next it works out the time the container has, from the Pod's deletion grace period. Then it writes an event on the Pod: type Normal, reason Killing, message Stopping container vllm. That is the first line an operator sees in kubectl describe pod.

Then comes the preStop hook, if the container has one and the grace period is above zero. The seconds the hook takes are subtracted from what the container gets afterwards. Whatever is left is raised to at least 2 seconds, a constant in the kubelet with the comment that it avoids needless SIGKILLs. Finally the kubelet calls the container runtime, containerd here, with StopContainer and that number of seconds as the timeout.

The containers of one Pod are stopped without an order between them. The documentation says the runtime handles the requests asynchronously and each container gets TERM at a different moment. Sidecar containers, the init containers with restartPolicy Always, are the exception. They get TERM only after the last main container has stopped, in the reverse of the order they are listed. If the kubelet or the runtime restarts in the middle of all this, the shutdown starts again with the full original grace period.

Chapter 5 of 12

The request that arrives after the signal

With no preStop hook, the server usually stops first

This Pod has no preStop hook, so the kubelet goes straight to the signal. containerd sends TERM to process 1 in the container. The signal is TERM because the image sets no other with STOPSIGNAL, and TERM is the default of both containerd and CRI-O. TERM arrives a tenth of a second after the delete, and from that moment the server is shutting down. A plain web server that handles the signal stops accepting connections. vLLM works in two stages, as a later chapter shows in detail. Its handler first stops the engine that runs the model, and only after that tells its HTTP server to exit. Until the second stage the port still accepts connections, but the engine behind it is stopping or already gone.

The traffic path is slower, and each part of it has its own delay. The EndpointSlice controller can be told to batch Pod changes with the flag --endpointslice-updates-batch-period, trading latency for fewer updates. kube-proxy rewrites its iptables rules at most once a second by default, the flag --iptables-min-sync-period with a default of 1s. A gateway controller has to see the slice, compute new configuration and push it to the gateway. Say all of that takes two seconds here. In between, the gateway still believes 10.244.2.22 is a good backend.

A request that arrives at 0.8 seconds is sent there and is not served. What the caller sees depends on how far the shutdown has got. If vLLM has already closed its HTTP server, the connection is refused. If not, the connection is accepted by a server whose engine is stopping, and the request ends in an error or an answer cut short. Which of these happens was not measured here. Kubernetes gives no bound for this gap. It is short, and on a busy service something always lands in it. Imagine the fleet serving 40 requests a second across eight Pods, five per Pod. In 1.9 seconds, from 0.1 to 2.0, about nine or ten requests are aimed at this one server after it began to shut down. That arithmetic is illustrative, and it repeats for every Pod a rolling update replaces.

Chapter 6 of 12

Holding the signal back for ten seconds

A preStop sleep keeps the server open while the traffic moves away

The fix is to make the kubelet's side slower on purpose. A container can define a preStop hook, an action the kubelet runs before it stops the container. The hook has to finish before TERM may be sent. There are three kinds of handler. exec runs a command inside the container, in its cgroups and namespaces, so its CPU and memory count against the container. httpGet sends a request to the container. sleep simply waits. httpGet and sleep are run by the kubelet process itself. The sleep handler is written as lifecycle.preStop.sleep.seconds, so the image needs no sleep program. It arrived as alpha in 1.29, was on by default from 1.30 and is stable since 1.34.

Run the same delete again with a sleep of 10. For ten seconds nothing happens to the server. It keeps its port open and answers as usual. The request at 0.8 seconds is served. At 2 seconds the gateway stops choosing this Pod. At 10 seconds TERM arrives at a server that has received nothing new for eight seconds.

A few rules about hooks matter here. A hook runs at least once, and may in rare cases run twice, so it must be safe to repeat. Its output does not appear in Pod events. When it fails, the kubelet writes a Warning event with reason FailedPreStopHook and the fixed message PreStopHook failed, leaving out the error so that secrets do not leak into events. And it runs only when the grace period is above zero.

Chapter 7 of 12

Thirty seconds against a one minute answer

New requests have stopped. The work already inside has not

The request that arrived at 0.8 seconds asked for a long answer. The model streams it token by token and it will take 60 seconds, so it is due to finish 60.8 seconds after the delete. The gateway has stopped sending new requests, and this one is already inside.

Say this server drains on TERM: it stops taking new work and keeps streaming what it has. vLLM does that only when it is told to, as the next chapter shows. TERM arrives at 10 seconds and the stream carries on. The deadline does not move. At 30 seconds the grace period is over, and containerd sends KILL to every process still running in the Pod. KILL cannot be caught or delayed. The stream stops in the middle of a sentence after 29.2 seconds of a 60 second answer, because 30 minus 0.8 is 29.2.

The caller already received status 200 when the stream began, so it gets no error code, only an answer that ends early with no final message. A client library may report it as a dropped connection or as a normal end, depending on how it reads the stream. Either way the 29.2 seconds of GPU time spent on it are lost, and so is the caller's patience. This is the case the owner's notes raise for preempted replicas on a shared GPU pool: once the Pod is terminating it gets no new requests, but a long agent turn already in flight has only the grace period, 30 seconds by default.

Chapter 8 of 12

What vLLM does when TERM arrives

It aborts or it drains, and the default is to abort

Everything so far assumed a server that keeps streaming after TERM. What vLLM actually does is a setting. Its API server installs its own handlers for SIGTERM and SIGINT and tells uvicorn, the web server underneath, not to install its own. When the signal arrives it logs [shutdown] API server: shutdown triggered. It then reads shutdown_timeout from its configuration and picks a mode: abort if the value is 0, drain if it is above 0. It logs the choice, stops the engine, and then shuts the HTTP server down.

The value comes from the command line flag --shutdown-timeout, an integer in seconds, default 0. Its help text says 0 means abort and a positive number means wait. The configuration describes it as a grace period for in-flight requests: shutdown is delayed for up to that many seconds so running requests can complete, and whatever is still running when it runs out is aborted.

So with the default, a third run with the second run's settings, a 10 second sleep and 30 seconds of grace, goes differently. TERM arrives at 10 seconds. vLLM aborts the open request at once, 9.2 seconds into the 60 second answer, and exits. The Pod is gone within moments, well before its 30 seconds. The preStop sleep still did its job for requests arriving late. It did nothing for the one already inside. To keep it, start vLLM with --shutdown-timeout set to at least the longest answer, and give the Pod a grace period that covers the sleep and that drain. This was read from vLLM's current main branch. Check the release you run.

Chapter 9 of 12

When the hook runs past the deadline

The kubelet stops waiting, sends TERM, and allows two more seconds

The preStop hook and the container share one grace period, and a hook can be longer than that period. Say someone, wanting more margin, sets the sleep to 35 seconds and leaves the grace period at 30. The kubelet runs the hook with the whole 30 seconds as its limit. At 30 seconds it stops waiting for the hook and logs PreStop hook not completed in grace period. The time left for the container is now 30 minus 30, which is zero. The kubelet raises that to its floor of 2 seconds and calls containerd with a 2 second timeout. containerd sends TERM at 30 seconds and KILL at 32. The server had two seconds of warning after keeping its port open the whole time.

The documentation gives its own example of the same trap. With terminationGracePeriodSeconds 60, a hook that takes 55 seconds, and a container that needs 10 seconds to stop after TERM, the container is killed before it can finish, because 55 plus 10 is 65, more than 60.

The 2 seconds are a one-off extension, granted once. They are not a second grace period. The documentation calls it a small, one-off grace period extension of 2 seconds. The lesson for a model server is plain. The hook must be well under the grace period, and the time after TERM must fit what the server needs to drain. Sleep plus drain must be less than the grace period, with a margin.

Chapter 10 of 12

A grace period sized to the longest answer

Add up the sleep, the longest answer and a margin

The grace period has to cover everything that happens after the delete. Add it up from the worst case. A request may arrive at any time until the sleep ends at 10 seconds. The longest answer you allow takes 60 seconds, so the last one could finish at 70. Add 20 seconds of margin and set terminationGracePeriodSeconds to 90.

The server has to agree. Start vLLM with --shutdown-timeout 60. TERM arrives at 10 seconds, and vLLM may drain until 10 plus 60, which is 70 seconds. That fits under 90 with the same 20 seconds to spare. The numbers line up in one chain: sleep 10, drain at most 60, KILL no earlier than 90.

These values go into the Deployment's Pod template, and that has a consequence. A running Pod keeps the terminationGracePeriodSeconds it was created with, because the API server rejects a change to that field of an existing Pod. Its only exception sets a negative value to 1. The qwen3-6f7d9c8b4-m9q4t of the earlier runs still has 30. A change under spec.template starts a rollout, as the lesson on replacing a model server shows, and only the Pods that rollout creates carry 90 and the new argument. The fifth run below deletes the replacement that now serves on gpu-node-2. It is a new Pod, so it has a new name. The new template got a new pod-template-hash, and the Pod is called qwen3-58b4d7f9c6-h3v6z. To keep the story readable it has the same address as before, 10.244.2.22. A delete request can also name its own period, kubectl delete --grace-period=90, which is used in place of the Pod's, but a value typed by hand is easy to forget on the next delete.

This is a ceiling. It is not a wait. The Pod goes as soon as its processes exit. Here the last stream ends at 60.8 seconds, vLLM has nothing left to drain and exits, and the kubelet does not wait for 90. It moves the Pod to a terminal phase, Succeeded or Failed depending on how the containers ended. That write is the moment that matters. The scheduler watches only Pods whose phase is neither Succeeded nor Failed, so from then on it stops counting the Pod's GPU, and the card is free for the replacement that has been Pending all along. The EndpointSlice controller leaves terminal Pods out of the slice, so the address goes at the same point. Last, the kubelet deletes the object by sending a delete with grace period 0. On this full fleet the replacement waited 61 seconds for that card, the cost the rolling update lesson counts as one step.

Chapter 11 of 12

Drains and evictions ask the same way

kubectl drain uses the Eviction API, which may answer no

A Pod is often stopped by someone who never names it. kubectl drain gpu-node-2 empties a node for repair. It marks the node unschedulable, then asks for each Pod to be evicted. An eviction is a POST to the Pod's eviction subresource. If no PodDisruptionBudget covers the Pod, the API server always answers 200 OK, and the Pod is deleted exactly as if you had sent a DELETE. Everything in the chapters above then happens in the same order with the same grace period.

A PodDisruptionBudget, PDB for short, can make the answer no. Say a PDB for app qwen3 has minAvailable 7. If one of the eight Pods were already terminating elsewhere, evicting another would leave six. The API server answers 429 Too Many Requests and the Pod is left alone. kubectl drain keeps retrying until the budget allows it or its --timeout runs out. A 500 Internal Server Error means a misconfiguration, such as two budgets selecting the same Pod.

The drain flags touch termination directly. --grace-period overrides the Pod's own period, and a negative value, the default, keeps the Pod's. --disable-eviction switches to plain deletes and skips the budgets. --skip-wait-for-delete-timeout stops waiting for Pods whose deletion timestamp is older than that many seconds. A Pod evicted this way also gets the condition DisruptionTarget, with reason EvictionByEvictionAPI, so the server can see why it is going. A rolling update is different again. The Deployment controller only lowers the size of the old ReplicaSet, and the ReplicaSet controller deletes the Pods. Neither goes through the Eviction API, so neither is held back by a PDB, though the Pods they remove still count against the budget.

Chapter 12 of 12

Force, and a node that shuts down

Two ways the grace period is cut short

kubectl delete --grace-period=0 --force removes the Pod from the API at once. The API server does not wait for the kubelet to confirm that anything stopped. kubectl prints a warning that the resource may continue to run on the cluster indefinitely. On the node, the kubelet still gives the process a short grace period before killing it. For a GPU Pod this has a specific risk. The API object is gone, so the ReplicaSet creates a replacement, and the scheduler counts the card as free because no Pod object claims it. If the old process is still alive, the replacement starts on a GPU whose memory is still full of the old model's weights. Use force only when the node is truly gone.

A node that shuts down cuts the grace period from the other side. Graceful node shutdown lets the kubelet notice the machine is going down and stop Pods first. It is configured with two kubelet settings, shutdownGracePeriod and shutdownGracePeriodCriticalPods, and both default to zero, which leaves the feature switched off. With shutdownGracePeriod 30s and shutdownGracePeriodCriticalPods 10s, ordinary Pods get the first 30 minus 10, which is 20 seconds, and critical Pods get the last 10. The model server's 90 seconds do not apply. It has 20.

A Pod stopped this way shows the status Terminated, with the message Pod was terminated in response to imminent node shutdown. The node turns NotReady with the reason node is shutting down. If your answers run for a minute, a planned shutdown should be a drain first, so the full 90 seconds apply.

What to keep

Stopping is two jobs with one deadline

A delete writes a deadline and starts two jobs that do not talk to each other. The kubelet stops the server: probes, an event, the preStop hook, then TERM through containerd with whatever time is left, and KILL when it runs out. The control plane marks the endpoint ready false and terminating true, and the gateway moves new requests elsewhere after its own delays. A preStop sleep delays the first job so the second can finish. That deals with requests that arrive late. It does nothing for work already in progress, and a model server's work is long. vLLM aborts that work on TERM unless --shutdown-timeout tells it to drain, and even a draining server is cut by KILL when the grace period ends. So size the sleep, the drain and terminationGracePeriodSeconds together, and remember that a drain, an eviction, a forced delete or a node shutdown can each change the time you get. A stopping Pod holds its GPU until it reaches a terminal phase, so every replacement waits for it.
