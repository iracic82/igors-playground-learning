Models

Which token comes next

One forward pass through a transformer, stop by stop

Every lesson about the factory ends at a GPU that reads a prompt and writes an answer. This one goes inside that GPU's work. A language model does one thing: given everything so far, it scores every token it knows for how likely it is to come next. One is picked, added to the end, and the question is asked again. That is all generation is. The model that answers in the factory is Qwen3-32B, and the numbers here are its real shape. The ideas are the same ones a tiny teaching model uses to write bad Shakespeare, a model whose embedding table holds just 520 weights. Follow five words through it and watch a sixth come out.

Chapter 1 of 12

Text becomes numbers

The tokenizer cuts and looks up

A model can't read letters. The first stop is a tokenizer, which cuts the text into pieces it has an entry for and replaces each piece with that entry's number. A teaching model can use one token per character, which gives a vocabulary of about 65 different tokens for the works of Shakespeare. Real tokenizers merge pieces that often appear together, so a common word is one token and a rare one is several: Qwen3's tokenizer cuts unbelievably at the very start of a text into un, belie and vably, and in the middle of a sentence, with a space in front, into two pieces, unbelie with its space and vably. This model's vocabulary has 151,936 entries. The tokenizer is built before training and learns nothing afterwards. Everything from here on is arithmetic on numbers.

On average a token is about three quarters of an English word. Some words are one token, some are several, and spaces and punctuation ride along inside tokens. The rule works in both directions: 100 tokens hold about 75 words, and 1,000 words need about 1,333 tokens. The exact count depends on the tokenizer. The sentence Serving LLMs is not like serving web apps has 8 words, and the talk this example comes from counts about 9 tokens for it. Qwen3's tokenizer makes 11: S, erving, L, LM, s, is, not, like, serving, web, apps. The capital S at the very start has no space before it, so it does not match the common token for serving with a space, and an abbreviation like LLMs falls apart into pieces. On two spoken lecture transcripts of 8,695 and 9,386 words, Qwen3's tokenizer made 10,167 and 11,552 tokens, which is 0.86 and 0.81 words a token.

Everything about serving a model is counted in tokens. The context limit is a number of tokens: this model takes at most 40,960 at once, prompt and answer together. Price is a number of tokens: hosted model APIs price input tokens and output tokens separately, per million, and a gateway that meters usage counts the same two numbers. Speed is a number of tokens: the time until the first token appears, and how many tokens a second follow it. So a page count has to become a token count before anything can be planned. A page of plain prose holds about 500 words, which is about 670 tokens. A 100-page contract is then about 50,000 words, about 67,000 tokens by the rule of thumb and about 62,000 at Qwen3's measured 0.81 words a token. Either way it is more than 40,960, so the whole contract does not fit in one request to this model as it is served here.

Chapter 2 of 12

Counting what comes next

Why a table of counts can't be the model

The simplest model of what comes next is a table of counts. Take the works of Shakespeare cut into its 65 characters. Walk through the text and, for every character, add one to the count of the character that follows it. The words cat, car and can put three counts in the row for c, all of them for a, and three in the row for a, one each for t, r and n. Divide each row by its total and the counts become shares: after c, a is 100%, and after a, each of t, r and n is a third. If q was followed by u 90 times in 100, the row for q says u 90%. To generate, draw from the row of the last character like a weighted dice roll, add what came out to the text, look up the row of the new last character and draw again. That is already a language model. Its output is gibberish with a little structure: th and he show up, spaces land in plausible places, and now and then a real word appears.

Its weakness is that it sees one character back. A t at the start of the, at the end of cat and inside computer all read the same row. The obvious repair is a longer history, and that is where counting breaks. With two characters of history there are 65 × 65 = 4,225 histories, each with its own row of 65 counts. With three there are 65 × 65 × 65 = 274,625. With ten there are 65 to the power 10, about 1.35 quintillion (1,346,274,334,462,890,625). Storage is only half the problem. Each row needs enough examples in the text to estimate its shares, and most long histories never appear in the text even once. A history that was never seen gives the table nothing to say.

With real tokens the explosion starts sooner. This model knows 151,936 tokens. A table with just one token of history already has 151,936 × 151,936 = 23,084,548,096 cells, about 30 times the 778 million weights of the embedding table in the next chapter. Two tokens of history make about 3.5 quadrillion cells. And every row is learned on its own: whatever was counted after happy teaches nothing about glad. The way out is to stop storing histories at all. A learned model keeps a short list of numbers for each token, so what it learns about one token carries over to tokens used in the same way. Then it computes the prediction from the tokens actually in front of it, however long the history is. The next chapters build exactly that: embeddings for the first part and attention for the second.

Chapter 3 of 12

A number becomes a meaning

The embedding table

A token number says nothing about the token. So the model keeps a table with one row per entry of the vocabulary, and each token number picks its row. A row is a list of 5,120 numbers, a point in a space with 5,120 directions. Nobody chose what the directions mean. Training moved the rows until tokens that are used alike ended up close together, which is how something learned about happy helps with glad. This table alone holds 778 million weights. The teaching model's table is 65 rows of 8 numbers, 520 weights in all, and it works the same way.

Chapter 4 of 12

Order has to be added

Attention alone can't tell first from last

The next stop compares tokens with each other, and that comparison has no sense of order built in. Left alone, dog bites man and man bites dog would look the same to it. So position has to be worked into the numbers. The classic way adds a second list of numbers to each row, one that depends only on where the token sits. This model does it differently and rotates each token's query and key by an angle that grows with its position, so that two tokens compare according to how far apart they are. Either way the result is the same kind of thing: five lists of numbers that now carry both what the token is and where it is.

Chapter 5 of 12

Every token asks a question

Query, key and value

Now the tokens look at each other, and this is the only place in the model where they do. From its own numbers each token makes three shorter lists. A query: what am I looking for. A key: what do I have. A value: what I will pass on if I am asked. To build the new meaning of is, the model multiplies its query with the key of every token up to and including itself. A high product means a good match. The products are turned into shares that add up to one, and the token takes in the values of the others in those shares. A token is never allowed to look at what comes after it, because during training that would be reading the answer.

The match is a dot product: take two lists of the same length, multiply the numbers in the same positions and add the products. A worked example with lists of 2 numbers can be traced by hand. Take the sentence the animal was tired, treat each word as one token, and build the new meaning of tired. Say the query of tired is (1, 1). The keys are (1, -1) for the, (1, 1) for animal, (1, 0) for was and (-1, 1) for tired itself. The dot products are 1×1 + 1×(-1) = 0 for the, 1×1 + 1×1 = 2 for animal, 1×1 + 1×0 = 1 for was and 1×(-1) + 1×1 = 0 for tired. These are the attention scores. Animal matches best.

Softmax turns the scores 0, 2, 1 and 0 into shares. e to the power 0 is 1, e squared is 7.39 and e is 2.72, so the sum is 1 + 7.39 + 2.72 + 1 = 12.11. The shares are 8.3% for the, 61.0% for animal, 22.5% for was and 8.3% for tired. Rounded to 10%, 60%, 20% and 10%, they are easy to use. Now the values. Say they are (2, 0) for the, (1, 5) for animal, (4, 1) for was and (0, 2) for tired. Each value is scaled by its share and the four are added: 0.1×(2, 0) + 0.6×(1, 5) + 0.2×(4, 1) + 0.1×(0, 2) = (0.2 + 0.6 + 0.8 + 0, 0 + 3.0 + 0.2 + 0.2) = (1.6, 3.4). With the exact shares it comes to (1.67, 3.44). That pair is the output of attention for tired. It started from the same embedding tired always has, and now it carries mostly what animal handed over. In another sentence the keys around it differ, so the scores, the shares and the output differ too.

In this model each query and key is 128 numbers, so one score is 128 multiplications and 127 additions. The real formula also divides every score by the square root of that length before softmax, √128 ≈ 11.3 here. Sums of 128 products grow large, and large scores push softmax towards handing almost the whole share to one token, where training learns very little. vLLM's attention layer for Qwen3 sets this factor as head_dim to the power -0.5. In the two-number example the divisor would be √2 ≈ 1.41, and the shares would soften to 12.3%, 50.5%, 24.9% and 12.3%. Blocking the later tokens is called causal masking, and attention among the tokens of one text is called self-attention.

Chapter 6 of 12

Keys and values are kept

Where the KV cache comes from

Look at what that step left behind. Every token made a key and a value in this layer, and a later token will need exactly those to ask its own question. They do not change when more text is added, because a token never looks forward. So the model keeps them. That store is the KV cache from the other lessons, and now its size can be worked out. A query is used once and thrown away. A key and a value are kept for each token, in each of 64 layers, in each of 8 key and value heads, as 128 numbers of 2 bytes. That is 262,144 bytes for every token of every conversation, held in GPU memory for as long as the conversation is served.

Chapter 7 of 12

Each token is worked on alone

The feed-forward layer, and then the next block

After attention has mixed in what the other tokens had to say, each token goes through a second stage by itself. Its 5,120 numbers are stretched to 25,600, pushed through a simple curve, and brought back to 5,120. This is where the model keeps most of what it knows: about three quarters of its 32.8 billion weights are in these layers. Two things hold the whole arrangement together. The result of each stage is added to what went in, so nothing learned earlier is overwritten. And the numbers are rescaled before each stage so they stay in a workable range. Attention plus feed-forward is one block. This model runs 64 of them in a row, each with weights of its own.

The same recipe runs at very different sizes. The teaching model that writes bad Shakespeare has a few blocks, lists of 8 numbers and 2 attention heads. GPT-3, published in 2020, has 96 blocks, lists of 12,288 numbers, 96 heads of 128 numbers each, a feed-forward layer four times as wide at 49,152, and 175 billion weights. Qwen3-32B sits between them with 64 blocks, 5,120 numbers, 64 query heads and 32.8 billion weights. Size changes how many numbers there are, and the steps stay the same. Two differences matter for serving. GPT-3 gives every query head its own key and value head, so it keeps 96 × 2 × 96 × 128 numbers per token. At 2 bytes a number that is 4,718,592 bytes, 18 times the 262,144 bytes of this model. And GPT-3 reads at most 2,048 tokens at once, where this model takes 40,960.

Chapter 8 of 12

A score for every token

The output head

After 64 blocks the model holds five finished lists of numbers, one per position. To predict what follows the prompt it needs only the last one. That list goes through one more table, which turns its 5,120 numbers into 151,936 scores, one for every token in the vocabulary. The scores can be any size and can be negative. A formula called softmax turns them into shares that add up to one: each score becomes e to its power, divided by the sum over all of them. A score that is one higher than another gets about 2.7 times its share.

Chapter 9 of 12

One token is drawn

Sampling and temperature

The model has not chosen anything yet. It has produced a table of shares, and the last stop draws from it like a weighted dice roll. Paris will come up most of the time and London some of the time. That is why the same prompt can give different answers. Temperature is the one dial on this stop. Every score is divided by it before softmax. A temperature below one stretches the scores apart, so the favourite wins almost always. Above one squeezes them together and the long shots get a real chance. Nothing in the model changes. Only the draw does.

Always taking the top token is called greedy decoding. It looks safe and goes wrong in a particular way. In the counting model, u is the top pick after q, so every q becomes qu. The top pick after u is fixed as well, and the one after that, so the text keeps settling into the same few paths. If the top pick after a space is t, after t is h, after h is e and after e is a space, a greedy model writes the the the the and never stops. A large model does the same at the scale of phrases and sentences: once a line has appeared, repeating it becomes the most likely continuation. Qwen's model card for this model says it plainly: DO NOT use greedy decoding, as it can lead to performance degradation and endless repetitions.

In vLLM, temperature 0 is greedy: the parameter's own description ends with Zero means greedy sampling. vLLM's default temperature is 1.0, but it loads the model's generation_config.json unless told otherwise, and the file for Qwen3-32B sets temperature 0.6, top_k 20 and top_p 0.95. So a request to this server that sends no temperature is drawn at 0.6, from the 20 highest scores, and among those from the smallest set whose shares reach 95%. The card suggests temperature 0.7 and top_p 0.8 when the model's thinking mode is turned off. Where repetition still appears, presence_penalty between 0 and 2 lowers the score of every token that already appears in the answer, at some risk of the model mixing languages.

Chapter 10 of 12

Add it and go again

The loop, and why the second pass is cheap

Paris is added to the end of the text, and the question is asked again for the token after it. This is the whole of generation: one token per pass, each pass a full trip through 64 blocks. Here the cache pays for itself. The five old tokens are not read again, because their keys and values are already stored. Only the new token goes through the model. It makes its query, key and value, adds its key and value to the five that are stored, and compares its query with all six, its own included. That is the difference between the two phases of serving. Reading the prompt is one wide pass over many tokens. Writing the answer is many narrow passes over one token each, and every one of them reads the whole cache.

Chapter 11 of 12

What fills the context window

Three different limits that are all called context

The context window is how many tokens the model can work with at once when it predicts the next one. Everything that shapes the answer has to be inside it: the system prompt, every earlier message of the conversation, any document pasted in or retrieved, and every token the model has written so far in this answer, its thinking included. The chat API keeps no memory between calls. The client sends the whole conversation again with each new message, so turn ten carries the text of turns one to nine. Every one of those tokens takes a position, a key and a value in each of the 64 layers, and a place in the KV cache.

Three numbers get called the context, and they are different things. The first is what the model was built and trained for. Qwen3-32B's card gives 32,768 tokens natively. Its config sets max_position_embeddings to 40,960, which the card explains as 32,768 tokens reserved for output plus 8,192 for a typical prompt, and vLLM takes 40,960 as the longest request it serves. With YaRN, a change to how positions are rotated, the card validates up to 131,072 tokens, started with vllm serve and --rope-scaling '{"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":32768}' --max-model-len 131072. The second number is the one in advertisements, 128K or 1M, and 131,072 is what gets called 128K. The third is what the GPU can hold. On one 80 GB H100 serving the FP8 build, the lesson Prefill and decode finds room for about 142,000 tokens of KV cache, shared by every request on that GPU.

The numbers combine. One request at the full 40,960 tokens holds 40,960 × 262,144 bytes = 10,737,418,240 bytes of cache, 10 GiB, and the 142,000-token pool fits three of those at once. A YaRN window of 131,072 tokens needs 34,359,738,368 bytes, 32 GiB, for a single request, which is 92% of the pool. The attention work grows faster still. The token at position n compares its query with n keys, so a full 40,960-token text makes 40,960 × 40,961 ÷ 2 = 838,881,280 query and key pairs in each head of each layer. A prompt longer than the limit is refused before it reaches the GPU, with an error that begins This model's maximum context length is 40960 tokens.

Chapter 12 of 12

Looking at fewer tokens

Sparse attention cuts the comparing

Full attention lets every token compare its query with every key before it. The work grows with the square of the length: 1,000 tokens make 500,500 pairs per head and layer, 2,000 make 2,001,000, and 40,960 make 838,881,280. Sparse attention is the family of designs that let each token look at a chosen subset of the earlier tokens instead of all of them. In the designs here the subset is fixed by the architecture before training, and the model learns to work within it.

The simplest subset is a sliding window: each token looks only at the last W tokens. Mistral 7B in its first release, v0.1, uses W = 4,096. Its later versions, the v0.2 Instruct model and v0.3, set sliding_window to null and use full attention. At 40,960 tokens that cuts the pairs per head and layer from 838,881,280 to 4,096 × 4,097 ÷ 2 + 36,864 × 4,096 = 159,385,600, about 5.3 times fewer, and the saving grows with length because each token's work stops growing at W. Older tokens still count. Layer 2 reads what layer 1 gathered, which already reached W back, so information can move W positions further with every layer. Mistral's paper gives 32 layers × 4,096 as a theoretical span of about 131K tokens. The KV cache shrinks as well. Only the last W tokens' keys and values are ever read, so the cache becomes a rolling buffer of W slots, and the keys and values of position i go into slot i mod W. Mistral reports 8 times less cache memory at 32K tokens.

The Sparse Transformer paper from 2019 split the work between heads. One head looks at the previous l positions and another at every l-th position, with l close to the square root of the length. At 40,960 tokens l is about 202, so a token looks at about 400 positions instead of up to 40,960, and the total grows as n times √n. Any position can still reach any other in two steps. The paper found that this strided pattern routes information poorly for text, and used a fixed pattern for it, where the last few positions of each block are visible to every later token: with a stride of 128 and 8 such positions, everything after position 128 can see the last 8 positions of the first block, 121 to 128 when counting from 1. The paper writes this range as 120 to 128. GPT-3 alternated dense layers with locally banded sparse ones.

The price is a model that can miss things, because a fact outside the window has to be carried forward layer by layer. Qwen3-32B uses none of this. Its config sets use_sliding_window to false and sliding_window to null, so all 64 layers use full attention, and the cost of a long context here is the full square. Sparse attention is part of what the model computes, so it is decided when the model is designed and trained. Switching a dense model like this one to a window at serving time would make it compute something it was never trained on.

What to keep

One question, asked again and again

A language model answers one question: given everything so far, which token comes next. Text is cut into tokens, each token becomes a list of numbers, and position is worked in. Then 64 blocks repeat the same two moves. Attention lets each token take in what earlier tokens offer, by matching its query against their keys and blending their values. Feed-forward reworks each token by itself. The last position is turned into a score for every token, one is drawn, and the loop runs again. The keys and values are kept between passes, which is why the first token of an answer is slow, the rest are quick, and GPU memory fills up with conversations.
