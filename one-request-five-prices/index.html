Inference

One request, five prices

Where a cache hit lives decides what it costs

A request arrives at a pool of GPU workers. They run the same model, from the same image, on the same hardware. Any of them can answer, so routing looks like the easy part. It isn't, because each worker remembers different things. One has most of this request's work already done and sitting in GPU memory. Another has it on a local SSD. A third has never seen anything like it. Sending the request to the right one is the difference between a first token in a fraction of a second and a first token about two seconds later. This lesson prices the same request five ways.

On the way it weighs the prefix in bytes and chunks, follows the KV cache as a cache engine moves it out of GPU memory, shows how vLLM finds a hit that is not in GPU memory and waits for it, and reads the counters that report all four kinds of hit. Then it goes back to the front door and shows two ways a router gets it wrong, and what an endpoint picker has to know to get it right. The worker numbers come from public measurements. Where a value is illustrative, the lesson says so.

Chapter 1 of 14

Three workers that look the same

And one request that could go to any

An agent sends the next step of its loop. Like every step before it, the request starts with the same instructions and tool definitions, and ends with a few hundred new tokens. Here the prompt is 9,400 tokens. The first 9,000 are the shared opening and the last 400 are new: the result of the last tool call and the next question.

The model answers in two passes. Prefill reads the whole prompt at once and sets the time to the first token. Decode then writes the answer one token at a time. Prefill leaves something behind, the KV cache, and if that is kept, the next request that starts the same way can skip most of its prefill. So the question is not only who is free. It is who still has this prefix, and where.

From the outside nothing shows it. All three workers answer their readiness probe. All three sit behind the same Service on port 8000. Their Pod IPs, 10.244.1.21, 10.244.2.22 and 10.244.3.23, say which node they run on and nothing about what they remember. A load balancer that sees only addresses and health has nothing to choose with. So the BNK data plane asks the endpoint picker. It sends the request headers and body to the picker over ext_proc, a gRPC stream, and waits for one address back.

Chapter 2 of 14

What 9,000 tokens weigh

The prefix in bytes, blocks and chunks

Before pricing the trips, weigh the cargo. For Qwen3-32B one token of KV cache is 64 layers × 2 × 8 heads × 128 numbers × 2 bytes, which is 262,144 bytes. The prefix is 9,000 tokens, so its cache is 9,000 × 262,144 = 2,359,296,000 bytes, about 2.36 GB. That is the amount that must be in GPU memory before decode can use it, wherever it is now.

vLLM keeps it in blocks of 16 tokens, 4 MiB each. 9,000 tokens is 562 full blocks and 8 tokens over. Only full blocks are labelled and reused, so a precise count finds 8,992 tokens and reads 408. This lesson keeps the round numbers of 9,000 and 400.

The cache engine below vLLM works in larger units. LMCache gathers many blocks into one chunk, and its chunk size is counted in tokens, 256 by default, set with --chunk-size. At 262,144 bytes a token, a 256 token chunk is 64 MiB. This lesson's LMCache server is started with --chunk-size 80, which makes a chunk exactly 20 MiB, in the middle of the 10 to 30 MiB that a public benchmark calls typical. The prefix is then 9,000 ÷ 80 = 112.5 chunks, about 113. The chunk size matters because it is the size of every read and write the storage below will see.

Chapter 3 of 14

Why the cache leaves the GPU

GPU memory fills, so cache moves down

Go inside gpu-2 to see where a KV cache can end up. Every request has its own, and it grows with the length of the context. It shares GPU memory with the model weights. On this worker that leaves a pool of 8,869 blocks, about 142,000 tokens. This one prefix takes 562 of them. When the pool fills, the server either throws cache away and recomputes it later, or pushes it down into memory that is bigger, cheaper and slower. The second is now common.

A cache engine such as LMCache sits under vLLM. vLLM loads it as a KV connector, set with --kv-transfer-config and the connector name LMCacheMPConnector. In LMCache's current multiprocess mode the cache lives in a separate LMCache server process on the same machine. When vLLM wants to keep blocks, the transfer channel, CUDA IPC or POSIX shared memory, gathers a batch of them out of GPU memory and packs them into one chunk in host DRAM. That is the L1 tier. The server's --l1-size-gb sets its size and has no default. This worker gives it 5 GB, which holds only two prefixes this size.

When L1 is under memory pressure, or a policy says to spill through, it hands chunks down to an L2 backend. L2 is pluggable: a directory on local NVMe, optionally opened with O_DIRECT, a raw block device, NIXL, a remote key value store or S3. Each backend implements the same interface, keyed on chunk keys. It takes store tasks, lookup tasks that also lock the chunks they find, load tasks and unlocks, and it deletes. Below L1, every tier is slower, and that is where the prices come from.

Chapter 4 of 14

Finding a hit below the GPU

Ask GPU memory first, then the connector

When a request arrives, vLLM looks for its prefix in two places, in a fixed order. First the scheduler hashes the prompt into blocks and looks them up in its own table of blocks in GPU memory. That gives a local hit, counted in tokens. Then it asks the connector how many more tokens, past the local hit, the connector can supply. LMCache answers from its own index of chunks in L1 and L2.

If the connector can supply tokens, the request does not run yet. vLLM gives it GPU blocks for the whole prefix and moves it into a waiting state called WAITING_FOR_REMOTE_KVS. The connector starts the load in the background. Other requests keep running. When the load reports finished, the request is scheduled like any other, its prefix already in place, and prefill runs over the new tokens only. The gauge vllm:num_requests_kv_fetch_by_stage shows how many requests are in each stage of that load.

This is why a lower tier costs time and not GPU work. The GPU computes nothing for the 9,000 tokens. The request simply waits while bytes move. Its time to first token grows by the length of the wait, and that extra time is the price this lesson measures. Because the load runs in the background, the other requests on the worker keep running while this one waits.

Chapter 5 of 14

Price one: already there

A hit in GPU memory

Start with the best case. The prefix's KV cache never left GPU memory. The scheduler looks the prefix up, finds its 562 blocks, and attaches them to the new request by raising their reference count. Nothing is copied and nothing is computed for those 9,000 tokens. The connector is asked too, and has nothing to add, because the local hit already covers the prefix.

Prefill runs over the 400 new tokens only. At the illustrative rate of about 0.21 ms a prefill token used in the lesson Prefill and decode, that is about 84 ms. The same rate makes a full prefill of all 9,400 tokens about 2 seconds, which is the miss at the end of this lesson. Decode starts as soon as the 400 are done.

This price has a condition. The blocks are in GPU memory only while nothing has needed their space. A cached block that no running request uses sits on the free queue and is evicted when a new request needs room, oldest first. On a busy worker the best case lasts minutes, sometimes less. That is the reason the tiers below exist.

Chapter 6 of 14

Price two: host DRAM

A copy across PCIe

Now the same prefix is one tier down, in host DRAM, in LMCache's L1. It has to come back to the GPU before decode can read it. The GPU's copy engine pulls each chunk across PCIe by direct memory access. The CPU only describes each copy and the GPU fetches the bytes itself.

The prefix is 9,000 tokens at 262,144 bytes each. That is 2.36 GB, or about 113 chunks of 20 MiB. Large copies from host memory into GPU memory were measured at about 55 GB/s on one such machine, so one chunk takes about 0.38 ms and all of it is back in about 43 milliseconds. Then prefill reads the 400 new tokens as before. The request spent about 43 ms in WAITING_FOR_REMOTE_KVS, and no GPU core worked on the prefix.

It is a real cost and a small one. 43 ms is about a fiftieth of the 2 seconds a miss would cost, and it scales with the size of the prefix, not with the size of the model's compute. The catch is room. L1 on this worker holds 5 GB, about two prefixes this size, and it is shared by every conversation the worker serves. Most hits will not stay here long either.

Chapter 7 of 14

Price three: local NVMe

The drive sets the speed

One tier further down the chunks are on the server's SSD, in LMCache's L2. Each one has to be read into host memory first, and only then copied across PCIe. A public benchmark of LMCache's L2 on one NVMe drive measured about 1.6 GiB/s for reads and about 0.75 GiB/s for writes at chunk sizes of 10 to 30 MiB. Reading a 20 MiB chunk at 1.6 GiB/s takes about 12 milliseconds, and the prefix is about 113 of them. That is about 1.4 seconds, then the same 43 ms of PCIe copies as price two.

Better software might make the drive faster, and the same benchmark tested that, driving the NVMe from user space with SPDK instead of through the kernel. For small requests of 256 KiB it helped a little, 2 to 10 percent, with better tail latency on writes. At the chunk sizes the cache really uses, both ways hit the same wall: what one drive can do.

Writing costs too. To get here the chunks were written at about 0.75 GiB/s, about 2.9 seconds for this prefix, while the drive also serves reads for other requests. LMCache has no disk tier until someone configures one with an --l2-adapter on its server, so the disk tier exists only when someone gives it room. Every number here is for one drive. Several drives behind one adapter can add up, which the benchmark leaves for later work.

Chapter 8 of 14

Price four: a remote store

Across the fabric first

The cache can also live off the server altogether, in a key value store shared by many workers. LMCache reaches it through an L2 adapter, such as NIXL, a store that speaks the Redis protocol, Mooncake or S3. The older in-process engine used a remote_url setting, written as protocol://host:port. That makes a prefix reachable from any worker, which is attractive. A prefix made on gpu-2 can save prefill on gpu-1.

The read now crosses the network fabric first, competes with everything else on that fabric, and comes off whatever drive the store uses. Then it crosses PCIe like the others. The network alone sets a floor. At 100 Gbit/s, 12.5 GB/s, moving 2.36 GB takes at least 0.19 s. At 25 Gbit/s it takes at least 0.75 s. If the store reads from a single NVMe like the local one, the drive sets a floor of about 1.4 s again. These are illustrative floors. Real reads add protocol overhead and queueing behind other traffic.

It is still called a hit. It also has a cost a router cannot read from GPU metrics. The fabric it uses is shared with inference traffic, with weight downloads and with other tenants, so the same read can be fast at night and slow at noon. And one tenant's prefix is now data on a shared network and a shared store, which is a question for whoever decides who may read it.

Chapter 9 of 14

Price five: a miss

The GPU does all the work again

Last, the worker that has never seen this prefix. There is nothing to fetch from anywhere. The GPU runs prefill over all 9,400 tokens. Here that is about 2 seconds of compute, 9,400 × 0.21 ms, and during that time everyone else on that GPU slows down too, because every pass carries part of this prefill. vLLM splits it into chunks of at most 8,192 tokens a pass, two passes, so other streams keep moving more slowly. The miss also writes a fresh 2.46 GB of cache into this worker's pool, all 9,400 tokens in 588 new blocks.

Line the five up and something stands out. Four of them count as a cache hit. The hit in GPU memory costs nothing. The hit in host DRAM costs about 43 ms. The hit on local NVMe costs about 1.4 seconds, which is about 70 percent of what the miss costs. The gap between the best hit and the NVMe hit is far larger than the gap between that hit and the miss.

There is one more difference. A miss uses the GPU's cores and slows the other requests on that worker. A hit in any tier waits on memory, drives or the network and leaves the cores free. So the NVMe hit is cheaper for the pool even when it is only a little faster for the request. Whether it is cached is the wrong question. Where it is cached, and what it costs to get back, is the right one.

Chapter 10 of 14

What the dashboards count

Four kinds of hit, one hit rate

An operator looking at this worker sees hit rates, and a hit rate hides the price. vLLM counts a hit in GPU memory in vllm:prefix_cache_hits, in tokens. It counts tokens the connector supplied in vllm:external_prefix_cache_hits. Both have a matching queries counter. A dashboard that adds the two shows one cache hit rate for all four kinds of hit.

Newer vLLM versions split the hits by where they came from. vllm:prompt_tokens_cached_by_source has a source label with the values device for GPU memory, host for memory offloaded to DRAM, disk, p2p for another vLLM instance, and external_unspecified for a connector that does not say. The label values add up to the two hit counters. A request priced at three adds 9,000 tokens to the disk series. A request priced at two adds 9,000 to the host series. Their hit rates are the same and their wait differs by more than a second.

Two more signals help. vllm:num_requests_kv_fetch_by_stage shows requests waiting on a load, which grows when a slow tier is busy. The request's own queue time is in vllm:request_queue_time_seconds. Watching the hit rate alone, an operator would see a healthy cache on a worker whose first tokens are getting slower.

Chapter 11 of 14

Tier blindness

Prefix affinity counts every hit the same

Back at the front door. Round robin ignores all of this and is as likely to send the request to the miss as to the hit. With three workers it reaches the worker that holds the prefix in GPU memory one time in three.

The natural fix is prefix affinity: send a prefix to a worker that has it. That is a real improvement with a blind spot. A picker that only asks whether a worker has the prefix counts an SSD hit the same as a GPU memory hit. Here gpu-1 holds the prefix on its SSD and gpu-2 holds it in GPU memory. Asked a yes or no question, both say yes, and the request may get 1.4 seconds of reading when it could have had none.

The fix is to know the tier and give it a weight. KV cache events carry a medium for each stored block, so a router can learn where a block lives as well as which worker holds it. The open source llm-d indexer does this. It scores a worker by its longest matching run of blocks and weights each block by tier, 1.0 for GPU memory and 0.8 for CPU memory by default. Those weights are a choice. The price gap in this lesson, nothing against 43 ms against 1.4 seconds, suggests that a disk hit deserves much less weight than either.

Chapter 12 of 14

Hot spot

Cache awareness without load awareness

Fix the blind spot the simple way and always choose the worker with the prefix in GPU memory. Now a different thing goes wrong. Popular prefixes are popular. Every step of every agent that shares these instructions goes to gpu-2, the one worker that cached them first. The other workers never get a copy, because they never get the requests.

gpu-2's queue grows until waiting in it costs more than the prefill it saves. In this illustrative snapshot it runs 12 requests, has 28 waiting and its KV cache is 97 percent full. A new request saves about 2 seconds of prefill there and spends several seconds in line. Worse, a nearly full pool starts to evict cached blocks, so the hottest worker begins losing the very cache it was chosen for. One GPU is overloaded, two are idle, and the cache made it worse.

The owner's course states it in one line: cache awareness without load awareness is worse than neither. Its slides show the same shape, with one warm GPU holding the queue while the others sit idle. The course also lists the first attempt at load awareness, reading queue and memory metrics from Prometheus, and its two flaws: polling every 15 to 20 seconds is too slow, and the metrics say nothing about the prompt.

Chapter 13 of 14

Signals, and how fresh they are

What the picker must know at the moment it picks

To weigh tier against queue, a picker needs three things about every worker, and it needs them now. What is cached where. How long the line is. How big this request is.

What is cached comes from KV cache events. Each vLLM worker publishes BlockStored and BlockRemoved messages over ZMQ the moment its table changes, with the hashes of the blocks and the medium they sit on. A picker that subscribes keeps an index of every worker's blocks that is at most a moment old. How long the line is comes from the workers' own counters of waiting and running requests and from the picker's own record of what it has sent where. Polling a metrics endpoint every 15 to 20 seconds is too slow for this, because a burst of agent steps arrives in less time than that.

How big the request is needs a tokenizer. A POST body of about 40 kB says only roughly how much work is inside it. The F5 endpoint picker has its own tokenizer, so it counts load in tokens and knows that a 20,000 token prompt and a 100 token lookup are different jobs. The owner's course describes two more parts. A drain estimate tracks each GPU's live tokens per second to predict how long its queue takes to clear. An overload gate skips saturated GPUs before warm cache is even considered.

Chapter 14 of 14

Weigh both, on every request

What the endpoint picker does with this

Getting it right means weighing two things against each other each time: how much prefill a worker can save, and how long the request would wait behind the work that worker already has. The F5 endpoint picker runs inline on every request and doesn't guess. It learns from KV cache events which worker holds which prefix, and reads each worker's own metrics. Load is counted in tokens, so a long prompt weighs what it costs. A worker's speed is measured as how fast it is draining its queue. A hit is valued by what it costs to fetch from the tier it is in.

With gpu-2 buried, the picker compares the two idle workers. The SSD hit on gpu-1 takes about 1.4 seconds to fetch, plus 43 ms of PCIe and about 84 ms of prefill. A full prefill on gpu-3 takes about 2 seconds of GPU work. The SSD hit is the cheapest way to a first token, by a small margin, and it leaves gpu-3's cores free.

The answer changes with the moment. A minute later gpu-2's queue has drained, and the same request goes to gpu-2 for nothing at all. The picker also has to fail safely. With FailClose, a request that cannot get an answer from the picker is refused rather than spread blindly across the pool.

What to keep

The price is set at the front door

KV cache doesn't stay in GPU memory. It spills to host DRAM, to a local SSD, to a store across the network, and each step down makes it slower to bring back. So one request has five possible prices, and four of them are called a cache hit. Here the hit in DRAM costs about 43 ms, the hit on a local SSD about 1.4 seconds and the miss about 2. The worker's own hit rate is the same for all four hits. A router that counts requests sees none of it. One that only asks who has the prefix sends work to slow tiers and piles everything onto whoever cached it first. The price is decided when the worker is chosen, before any GPU sees the request, and the model server can't fix a bad choice afterwards. That is the job of the endpoint picker: know where each prefix is, what it costs to reach, and how long the line in front of it is.
