Kubernetes underneath

From a Gateway to a Pod

Three objects, one controller, and the path a request takes into the cluster

Pods have addresses that only mean something inside the cluster, and they change every time a Pod is replaced. A caller outside needs one stable address and a set of rules for what goes where. In Kubernetes today that is written as three objects of the Gateway API. One says who implements gateways. One says where to listen. One says which requests go to which backend. None of them carries a single packet. A controller reads them and programs a data plane that does. This lesson builds the three, watches them take effect, and follows a request through. It then looks at what the objects say when something is wrong: the status conditions and their reasons, and the HTTP codes a caller gets back. The AI gateway lessons on this site all stand on this.

Chapter 1 of 14

Who builds gateways here

A GatewayClass ties a name to one controller

The first object is made once, by the platform team, before any Gateway exists. A GatewayClass is cluster-scoped, so it lives in no namespace, and kubectl also knows it by the short name gc. Its one required field is spec.controllerName. It names the controller that will build every Gateway of this class. The value must be a path with a domain in front, like example.net/gateway-controller, and it cannot be changed once the object exists. F5's BIG-IP Next for Kubernetes, which the AI factory lessons on this site use, writes f5.com/ followed by the namespace its CNE controller is installed in and -f5-cne-controller. Two installs in two namespaces therefore own two different classes.

The API server gives a new GatewayClass a status before any controller has seen it. It holds one condition: Accepted, with status Unknown, reason Pending and the message Waiting for controller. A running controller that finds its own name in controllerName replaces this with Accepted: True. If the condition stays Unknown with reason Pending, no controller has decided about the class yet. The API defines Pending only that way. The usual cause is that no running controller claims that name: a typo in the name, or a controller that was never installed. A controller that crashes, or that lacks the permission to write the class's status, looks exactly the same. Accepted: False comes with a reason. InvalidParameters means spec.parametersRef points at an object that does not exist or is of the wrong kind. Unsupported and UnsupportedVersion mean the controller cannot serve this class or the installed version of the Gateway API definitions.

kubectl get gatewayclass prints the columns Controller, Accepted and Age, so this one condition is visible at a glance. Once a Gateway uses the class, the implementation should add the finalizer gateway-exists-finalizer.gateway.networking.k8s.io to it. That keeps the class from being deleted while a Gateway still needs it. The API also recommends that a Gateway keeps the class settings it was created with, so a later edit of the class does not reach Gateways that already exist.

The F5 value is a pattern, and it changes from one install to the next. BIG-IP Next for Kubernetes, BNK for short, builds it from three parts: f5.com/, then the namespace the CNE controller is installed in, then -f5-cne-controller. The owner's lab notes find that namespace as the namespace of the CNEInstance, the object that installs the controller, so the two names mean the same slot in this lesson. F5's 2.4 reference writes it as f5.com/<namespaceofcontroller>-f5-cne-controller and shows f5.com/default-f5-cne-controller for an install in the namespace default. The owner's labs have found the namespaces f5-bnk, default and f5-operator in that slot on different clusters, so by the pattern f5.com/f5-bnk-f5-cne-controller on one and f5.com/f5-operator-f5-cne-controller on another. F5's own sample GatewayClass and L4Route manifests, and the owner's 2.3 audit, print f5.com/f5-bnk-instance-f5-cne-controller instead. By the same pattern that is an install in a namespace named f5-bnk-instance, so it is one more value to check against the cluster, not one to copy. Some F5 pages for releases 2.0 and 2.1 print an older form, f5.com/default-f5-gateway-controller, while other pages of the same 2.1 release already use -f5-cne-controller. One F5 slide deck on the AI gateway workflow prints f5.io/bnk-gateway, a value no BNK controller answers to.

The value is checked only for its shape, so the API server stores any of these without complaint. A copied name breaks a demo quietly. The class sits at Accepted: Unknown with reason Pending, every Gateway of the class stays Pending with it, and nothing listens on the address. An edit cannot repair it, because controllerName is immutable. The class has to be deleted and created again. The safe way is to build the string from the cluster: find the namespace of the CNEInstance with kubectl get cneinstance -A and put it in the middle. The same string comes back later in this lesson, as the controllerName that the controller writes into the status of routes and pools.

Chapter 2 of 14

Where to listen

A Gateway is a request for an entry point

Someone applies a Gateway. It is short. It names a class, which says which product should build it. It lists one listener: HTTPS on port 443, for the name api.northlight.example, with a certificate kept in a Secret. That is a wish, and nothing is listening yet. The API server stores the object, and the gateway's controller, which has been watching for objects of its class, sees it arrive. Being split into objects this way is deliberate. The team that runs the platform owns the Gateway. Application teams never touch it. They attach routes to it.

Each listener is a combination of protocol, port and, where the protocol carries one, a host name. The protocol is one of HTTP, HTTPS, TLS, TCP and UDP. Every implementation has to support two combinations for HTTP routes: port 80 with HTTP, and port 443 with HTTPS and a certificate. For HTTPS the tls block is required. Its mode defaults to Terminate, which means the gateway ends the TLS session itself, and then certificateRefs must name at least one certificate. The supported form is one reference to a Secret of type kubernetes.io/tls. A Gateway can hold between 1 and 64 listeners, and no two of them may share the same port, protocol and host name.

The listener also says which routes may attach to it. The field allowedRoutes defaults to namespaces from: Same. Only routes in the Gateway's own namespace can attach until the platform team writes All or a label Selector there. That default comes back later in this lesson, when a team in another namespace tries to attach a route.

The new object starts with a status nobody has written yet. The API server fills in two conditions, Accepted and Programmed, both Unknown with reason Pending and the message Waiting for controller.

Chapter 3 of 14

The controller makes it real

Objects in, configuration out, status back

The controller turns the object into configuration for the data plane, the part that will hold the address and handle packets. It loads the certificate, opens the listener and gets the address announced to the network. Then it does the thing that makes this system workable to operate: it writes back what happened. Every Gateway carries a status, and the controller sets two conditions on it. Accepted means the object made sense. Programmed means the data plane is really configured for it. It also writes the address it obtained. Anyone can now read from the object itself whether the wish came true.

The words of the API are careful about Programmed. It says the Gateway has generated configuration that is assumed to be ready soon in the data plane. It is a claim about configuration, written by the controller. A first request sent the same millisecond can still fail. In the owner's lab, F5's BNK took about 3 seconds from applying a Gateway to Programmed: True. The address can come from spec.addresses, where a Gateway may ask for up to 16, or from the implementation's own pool. Its type is IPAddress unless Hostname or NamedAddress is written.

Every listener gets its own entry in status.listeners, with a name, the kinds of route it supports, a count of attached routes and up to 8 conditions of its own. A listener can be broken while the Gateway as a whole is accepted, so both levels have to be read. Each condition also carries observedGeneration, the generation of the object it describes. When observedGeneration is lower than metadata.generation, the controller has not caught up with the latest edit yet.

kubectl get gateway, short name gtw, prints Class, Address, Programmed and Age. Accepted is no column. It takes kubectl describe or -o yaml to read it.

Chapter 4 of 14

What the class says it can do

Conformance is counted per feature, and the class lists its own

Every implementation of the Gateway API supports a different slice of it, and the API has a way to say which slice. The project ships a conformance test suite. Its tests are grouped into profiles: GATEWAY-HTTP, GATEWAY-TLS, GATEWAY-TCP, GATEWAY-UDP, GATEWAY-GRPC, MESH-HTTP and MESH-GRPC. Inside each profile, core tests cover what every implementation of that profile must do, and extended tests cover optional features that an implementation chooses to claim. Each level gets one result. It is success when no test failed or was skipped, partial when some were skipped, and failure when any failed. An implementation that wants to appear on the project's list uploads the report exactly as the suite wrote it, into conformance/reports/<Gateway API version>/<project>/, under a name of the form <API channel>-<its version>-<mode>-report.yaml, such as experimental-2.8.0-default-report.yaml, together with the steps to reproduce it. NGINX Gateway Fabric, F5's other Kubernetes gateway, is one example: its v2.8.0 report against Gateway API v1.6.3 shows the GATEWAY-GRPC profile with 14 core tests passed and 11 extended tests passed, none failed.

The cluster can also say it directly. A GatewayClass has status.supportedFeatures, a list of up to 64 feature names. The BNK controller fills it when it starts, before or at the moment it accepts the class, sorted alphabetically as GEP-2162 asks. F5's 2.4 reference lists 27 names, from BackendTLSPolicy to TLSRoute. Among them are GRPCRoute, ReferenceGrant, HTTPRouteTimeoutRequest, HTTPRouteBackendProtocolH2C and GatewayStaticAddresses. Mesh features are not in it. F5 states that BNK 2.4 supports Gateway API features from v1.4.0. kubectl get gatewayclass northlight-edge -o yaml prints the list, and it is the first thing to check before a design depends on a feature.

One F5 deck says BNK adheres 100% to the CNCF Gateway API standards. The Gateway API defines no percentage. Its measures are the profile, the level and the feature list. F5's own published table, the same page in its documentation for BNK 2.0.0 and 2.1.0, marked 21 of 39 core tests Successful and 18 Not supported, among them every ReferenceGrant test and the three gRPC tests, and 5 of 22 extended tests Successful. The 2.4 feature list adds GRPCRoute, ReferenceGrant, timeouts, redirects and rewrites, so the gap has closed a long way. When this lesson was checked, the upstream reports folder held reports for NGINX Gateway Fabric and none for BNK. The fair reading of the slide is this: BNK uses the standard objects with their standard meaning, extends them through objects of its own that attach to them, and its class says which features it serves.

The same deck lists the Gateway's protocols as HTTP, HTTPS and gRPC. A listener's protocol field has five core values: HTTP, HTTPS, TLS, TCP and UDP. Other values must carry a domain prefix and are implementation-specific. gRPC is no listener protocol. It runs over HTTP/2, so it arrives on an HTTPS listener, where the gateway must accept HTTP/2 chosen during the TLS handshake through ALPN, or on an HTTP listener with h2c, cleartext HTTP/2 spoken from the first byte. A GRPCRoute attaches to that listener and matches on service and method. Each gRPC call is an HTTP/2 POST to the path /<service>/<method>. A listener that cannot serve HTTP/2 in the required way reports Accepted: False with reason UnsupportedProtocol. vLLM's OpenAI-compatible server on port 8000 speaks plain HTTP, so the chat route in this lesson stays an HTTPRoute. gRPC appears elsewhere in the stack: the gateway talks to the endpoint picker over a gRPC stream, and in the owner's lab the picker took the gateway's requests on port 9002 and answered gRPC health checks on a second port, 9003. The owner's 2.4 lab found the GRPCRoute definition installed and did not exercise it.

Chapter 5 of 14

Which requests go where

A route attaches itself to the Gateway

The Gateway listens and sends nothing anywhere, because it has no routes. An application team adds one. An HTTPRoute names the Gateway it wants to attach to, the host names it is for, and a list of rules. Each rule has a match and a destination. This one says: requests whose path starts with /v1 go to the Service called qwen3 on port 8000. The controller checks it and answers on the route's own status, once for each Gateway it tried to attach to. Accepted means the Gateway took it. ResolvedRefs means everything it points at, such as that Service, really exists.

A parentRef needs only a name. Its group defaults to gateway.networking.k8s.io, its kind to Gateway and its namespace to the route's own. A route can list up to 32 parents. sectionName narrows the attachment to one listener by its name. Left out, the route offers itself to every listener of that Gateway, and it counts as attached if at least one listener accepts it.

The host names of route and listener must overlap. The listener here serves api.northlight.example, and so does the route. Had the route named only another host, it would get Accepted: False with the reason NoMatchingListenerHostname. A route may list up to 16 host names. IP addresses are not allowed there, and a port in the Host header is ignored when names are compared.

Once the route is accepted, the listener's attachedRoutes goes from 0 to 1. That counter includes only routes whose Accepted condition is True, so it is a quick check from the Gateway side. Neither Accepted nor ResolvedRefs is a column of kubectl get httproute, which prints only Hostnames and Age. Each entry in status.parents also carries controllerName, so a route attached to Gateways of two products shows which controller wrote which verdict.

Chapter 6 of 14

A Service is a list of Pods

The gateway skips the Service's own address

The route points at a Service, and a Service is not a thing that handles traffic. It is a name for the set of Pods that carry a certain label. The current members of that set are kept in EndpointSlices: the address of each Pod and whether it is ready. A Service also has a virtual address of its own that Pods inside the cluster can use, and the nodes spread connections made to it. A gateway often does not use that. It reads the EndpointSlices and keeps the Pod addresses itself, because it wants to make the choice of Pod for every single request. For a model server that choice is the whole point, as the lessons on picking a GPU show.

EndpointSlices belong to the API group discovery.k8s.io/v1. A slice is tied to its Service by the label kubernetes.io/service-name and by an owner reference, so kubectl get endpointslices -l kubernetes.io/service-name=qwen3 lists them. The slices the control plane makes carry the label endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io. By default a slice holds at most 100 endpoints. The flag --max-endpoints-per-slice of kube-controller-manager raises that to at most 1000. A Service with 250 Pods therefore has at least three slices, and one slice holds only one address family, IPv4 or IPv6.

Each endpoint carries three conditions. serving follows the Pod's Ready condition. terminating is set once the Pod has a deletion timestamp. ready is a shortcut for serving and not terminating. The endpoint also names its node and zone. The port the route names is the Service port. The slice holds the Pod's own port, its targetPort. Here both are 8000, which is what Kubernetes does when targetPort is left out. A Service port can also carry appProtocol, which tells a gateway what to speak to the Pods. The standard value kubernetes.io/h2c means HTTP/2 without TLS.

Chapter 7 of 14

How a rule is chosen

The API fixes the order, whatever order things were written in

The team adds a second rule to the route chat. GET requests for the exact path /v1/models, the list of models the server offers, also go to Service qwen3. Both rules now fit a request for /v1/models, and the gateway must pick one. The Gateway API does not leave that to the order of the YAML or the time of the edit. It ranks matches. An Exact path match wins first. Next comes a PathPrefix match, the longer prefix first. Then a match on the method, then the match with more header conditions, then the one with more query parameter conditions. If two routes still tie, the older route by creation time wins, and then the one first in alphabetical order of namespace and name. Inside one route the first matching rule in the list wins.

A rule can hold up to 64 matches and a route up to 16 rules. The conditions inside one match must all be true. The matches of one rule are alternatives, and any one of them is enough. A path match is Exact, PathPrefix or RegularExpression, and PathPrefix is the default. How regular expressions rank is left to each implementation. Header and query parameter matches are Exact by default. The method is one of GET, HEAD, POST, PUT, DELETE, CONNECT, OPTIONS, TRACE and PATCH.

A rule written with no matches at all gets one by default: PathPrefix /, which fits every request. That is a common way to send everything for a host name to one backend, and an easy way to catch more traffic than intended.

A rule can also carry filters, up to 16. The types include RequestHeaderModifier, ResponseHeaderModifier, RequestMirror, RequestRedirect, URLRewrite and ExtensionRef. A redirect answers the caller itself, with 302 unless statusCode says otherwise. A rule with a redirect may not also have backendRefs, and a redirect and a URLRewrite may not be combined.

Chapter 8 of 14

A request comes in

Host, then path, then a Pod

A caller outside opens a connection to the Gateway's address. The data plane ends the TLS session with the certificate it was given and reads the request. Matching goes from the outside in. Which listener: the one for this host name. Which route: the one attached to it whose path match fits, and /v1/chat/completions starts with /v1. Which backend: the route's only one. Which Pod: one of the two targets. The request goes straight from the gateway to that Pod's address. No Service address is involved and no other proxy is in between.

The Kubernetes page on the Gateway API describes the same order. The caller first resolves api.northlight.example to the Gateway's address. The data plane receives the request and uses the Host header to find the configuration made from the Gateway and its routes. Then it checks path, method and headers. For HTTPS the listener's host name should match both the name in the TLS handshake, SNI, and the Host header, though the two need not be the same string.

Two answers exist for a request that arrives at the wrong listener. If another listener has an exact or more specific match for its Host, the gateway should answer 421 Misdirected Request. If no listener matches the Host at all, it must answer 404. A wildcard such as *.northlight.example matches any name ending in .northlight.example, also with several labels in front, and never northlight.example itself.

The answer streams back the way the request came, from the Pod to the gateway and from the gateway to the caller, on the connections already open. A chat completion from a model server can stream tokens for many seconds, so the connection to the Pod stays open the whole time.

Chapter 9 of 14

Pods come and go behind the route

The EndpointSlice changes first, then the gateway's list

gpu-node-2 is drained for maintenance, so Pod qwen3-6f7d9c8b4-m9q4t is deleted and its Deployment starts a replacement elsewhere. The replacement belongs to the same revision, so its name keeps the hash and gets new random characters: qwen3-6f7d9c8b4-r5w8z. The moment the Pod gets its deletion timestamp, the control plane rewrites the EndpointSlice. The endpoint 10.244.2.22 now reads serving: true, terminating: true and ready: false. The Pod still answers, because vLLM is finishing the requests it holds, but it should get no new ones.

The gateway controller watches the slice, sees the change and gives the data plane a shorter list. From now on every new request goes to 10.244.1.21. The Kubernetes page on EndpointSlices describes the choice that Service proxies make here. They normally skip terminating endpoints. If every endpoint is terminating, they may still use the ones that are both serving and terminating, so that a Service does not go dark during a rollout. A gateway that reads slices itself has to make the same choice, and the Gateway API leaves the details to the implementation.

The replacement Pod is not added the moment it starts. A model server is ready only once its weights are in GPU memory. Qwen3-32B has 32.8 billion parameters. This site serves the official FP8 build, Qwen3-32B-FP8, whose files take 34.3 GB, and loading them takes about three minutes here. The full-precision BF16 build would be 65.5 GB. Until its readiness probe passes, its endpoint has serving: false, and the gateway sends it nothing. If there were no ready endpoint at all, the route would still be valid, and the API says the gateway should answer 503 for requests to that backend.

The gateway only learns of all this through the watch. Between the deletion and the new list reaching the data plane, a request can still be sent to the old Pod. This is one reason a model server should keep answering for a while after it is told to stop.

Chapter 10 of 14

What the caller gets when a piece is missing

404, 500 and 503 each point at a different object

The Gateway API fixes the status code for each kind of gap, which makes the code a caller sees a clue to where to look. When no rule attached to the listener fits a request, the gateway must answer 404. A request for /admin on this host gets that, because no rule matches the path /admin.

When a rule fits and its backend reference is invalid, the gateway must answer 500 for the requests that would have gone there. Invalid means a Service that does not exist, a kind the gateway does not support, or a reference to another namespace that no ReferenceGrant allows. The route then shows ResolvedRefs: False with one of the reasons BackendNotFound, InvalidKind, RefNotPermitted or UnsupportedProtocol.

When the Service exists but has no ready endpoint, the gateway should answer 503. The route is fine and the Pods are missing or still loading.

A rule can split traffic between backends by weight. weight defaults to 1 and goes from 0 to 1000000. Each backend gets its weight divided by the sum of all weights in the list. The numbers are no percentages and need not add up to 100. Weight 0 sends nothing. If two backends have equal weight and one is invalid, half the requests get a 500. A rule that is partly broken can also show the condition PartiallyInvalid, with a message that starts with Dropped Rule or Fall Back.

Model answers need one more setting. rules[].timeouts.request covers the whole request, and timeouts.backendRequest covers one call from the gateway to a Pod. When they are not set, the timeout is up to the implementation. A streamed answer of several minutes can be cut by a default meant for web pages. Setting a timeout to 0s should turn it off, and backendRequest may not be longer than request.

Chapter 11 of 14

A listener that cannot start

The certificate is renamed, and the listener says so

Some weeks later the certificate is renewed. Someone edits the Gateway to point at a new Secret, northlight-tls-2027, and forgets to create that Secret. The Gateway as an object is still valid, and the API server stores it. The controller cannot load a certificate that does not exist. It reports the problem where it lies, on the listener: ResolvedRefs: False with the reason InvalidCertificateRef. The listener's own Programmed condition can turn False as well. The Gateway's top-level conditions may still read True, so a look at kubectl get gateway alone can miss it.

The listener has more ways to report trouble. ResolvedRefs: False with RefNotPermitted means the Secret is in another namespace and no ReferenceGrant there allows the Gateway to read it. Accepted: False with PortUnavailable means the port is in use or not supported. UnsupportedProtocol means the implementation does not offer that protocol. Conflicted: True means the listener clashes with another on the same port. The reason ProtocolConflict means the two ask for conflicting protocols on that port, and HostnameConflict means they use the same host name there. An exact duplicate of port, protocol and host name never gets a condition, because the API server refuses the Gateway when it is written.

On the Gateway itself, Accepted: False comes with the reasons Invalid, InvalidParameters, NotReconciled, UnsupportedAddress or ListenersNotValid. ListenersNotValid can also come with Accepted: True, when some listeners work and some do not. Programmed: False comes with Invalid, Pending, NoResources, AddressNotAssigned or AddressNotUsable. The API's own examples for AddressNotAssigned are an address pool that has run out and an address not yet allocated. For AddressNotUsable they are a named address that cannot be found and an address already in use.

The fix is to create the Secret. The controller sees it, loads the certificate, and the listener's conditions turn True again. The edit raised metadata.generation from 1 to 2, and observedGeneration shows 2 once the controller has caught up.

Chapter 12 of 14

A route from another namespace

Attachment is allowed by the listener, references by a ReferenceGrant

A second team runs an evaluation service in the namespace evals and wants its own route on the same host, for the path /v1/evals. They write an HTTPRoute in evals with parentRefs naming Gateway northlight in namespace inference. The controller refuses it. The listener's allowedRoutes is still the default, from: Same, so only routes from the Gateway's own namespace may attach. The route's status shows Accepted: False with the reason NotAllowedByListeners, and attachedRoutes on the Gateway stays at 1.

The decision about who may attach belongs to the owner of the Gateway. The platform team changes the listener to from: Selector with a label that marks namespaces allowed to publish routes, and labels evals with it. The route is accepted on the next pass, and attachedRoutes becomes 2.

Other reasons a route is turned away are NoMatchingListenerHostname, when no listener serves its host names, and NoMatchingParent, when its sectionName or port matches no listener. A route can also get no status at all. The API says this happens when the parent does not exist, when the controller does not support the route's kind, or when the controller cannot see the route's namespace. An empty status.parents usually means a misspelled Gateway name or namespace.

References in the other direction work differently. If a route in evals named the Service qwen3 in inference as its backend, the owner of inference would have to allow it with a ReferenceGrant in inference. The grant lists who may refer, in from with group, kind and namespace, and to what, in to with group, kind and an optional name. Each list holds 1 to 16 entries. Without it the route gets ResolvedRefs: False with RefNotPermitted. Removing the grant must withdraw the access again.

Chapter 13 of 14

When the backend is a model

The same route, pointing at a pool

Picking one of two Pods at random or in turn is fine for a web server. For model servers it throws away most of what a GPU can do, because which Pod already holds a conversation's cache matters enormously. The Gateway API was extended for this. In place of a Service, a route can point at an InferencePool: a set of model server Pods, usually with a reference to an endpoint picker that the gateway asks before it sends each request. Nothing else in this lesson changes. Same Gateway, same route, same status conditions. Only the last step, which Pod, is handed to something that knows about models. That is where the lessons on BNK and the endpoint picker begin.

The pool is its own object in inference.networking.k8s.io/v1, short name infpool. selector picks the model server Pods by matchLabels, in the pool's own namespace only. targetPorts lists from 1 to 8 ports, and each Pod address with each port counts as one endpoint for the picker. appProtocol is http, meaning HTTP/1.1, by default, or kubernetes.io/h2c. endpointPickerRef names the picker, by default a Service, and its port is the Service port. In the owner's BNK lab the picker listened on port 9002 for the gateway's requests, and answered gRPC health checks on a separate port, 9003.

failureMode decides what happens when the picker does not answer. The default is FailClose, and the gateway drops the request. FailOpen lets it go to a Pod without the picker's advice. Up to release v1.5.0 of the extension, endpointPickerRef was required. The API now allows it to be left out, and the API itself notes that most implementations still require it.

The pool gets its own status, written per Gateway in status.parents. Accepted: False comes with NotSupportedByParent, HTTPRouteNotAccepted or EndpointPickerRefMissing. ResolvedRefs: False comes with InvalidExtensionRef. After the switch there are four conditions to read: two on the route and two on the pool. In the owner's lab, BNK showed the route Accepted and ResolvedRefs with an InferencePool backend, and 20 of 20 test requests got HTTP 200.

Each entry in status.parents holds up to 8 conditions, and the list holds up to 32 entries. An entry may also carry controllerName, the name of the controller that wrote it. For a Gateway parent that is the GatewayClass controllerName, so on BNK it is the f5.com/<namespace>-f5-cne-controller string from the first chapter, and it tells you which install wrote the status.

A third condition type, Exported, belongs to pools shared between clusters. It comes from the extension's multi-cluster design. A platform owner asks for it by putting the annotation inference.networking.x-k8s.io/export: ClusterSet on the pool. ClusterSet means every member of the current ClusterSet, a group of clusters that trust each other in the Kubernetes multi-cluster services model, and it is the only value defined so far. The controller then adds a separate entry to status.parents. Its parentRef is of kind InferencePoolImport, with the pool's own namespace and name, and Exported is set on that entry. True, with reason Exported, means the pool reached every member cluster. False comes with NotSupported when the export was asked for and this implementation cannot do it. The reason NotRequested marks a deliberate non-action with no error. When the annotation is removed, the controller must remove the condition. In each importing cluster a controller then keeps an InferencePoolImport of the same name, and a route there can name it as a backend, so requests reach model server Pods in another cluster. The northlight-eu pool asks for no export, so its status shows Accepted and ResolvedRefs only.

Chapter 14 of 14

Policies that hang off the class

Firewall, DDoS and layer 4 objects attach to the Gateway API objects

The Gateway API covers routing. Firewall rules, DDoS protection and logging are left to each implementation, through a pattern called direct policy attachment, written down in GEP-2648. A separate object names its target in a field called targetRefs, and the controller applies it there. BNK's object for security is SecPolicy, in the group gateway.k8s.f5.com/v1alpha1 in F5's 2.4 reference. Release 2.1 called it BNKSecPolicy, in gateway.k8s.f5net.com/v1alpha1, and the owner's 2.3 audit and older research notes use that older name. Its spec holds two lists. extensionRefs names what to apply: at most three objects, each kind at most once, chosen from F5BigFwPolicy, F5BigLogProfile and F5BigDdosGlobal, with the group k8s.f5net.com by default. targetRefs names where: 1 to 16 targets of kind Gateway, GatewayClass or EgressGateway. It is immutable once created. On a Gateway target, sectionName narrows the policy to one listener.

The target decides where the rules land in TMM, the Traffic Management Microkernel that is BNK's data plane. A GatewayClass target puts them in the global context of every TMM in the cluster. A Gateway target puts them on the ingress and egress virtual servers of that Gateway. A listener target puts them only on that listener's ingress virtual server, and they override the Gateway-wide rules there. Each target takes one SecPolicy. When two name the same target, the oldest by creation time wins, as GEP-2648 says. The policy and its extensions must sit in one namespace. A GatewayClass target is valid only when all of them sit in the controller's namespace, the same namespace that appears inside the controllerName. A Gateway in another namespace can be targeted once it, or its namespace, carries the label secpolicy.gateway.k8s.f5.com/allowed-cross-namespace with the policy's namespace as the value. This is how security chains off the GatewayClass: the protection of every TMM hangs from the one class.

F5BigFwPolicy, in k8s.f5net.com/v1, holds firewall rules. Each rule has a name, ipProtocol, source and destination addresses and ports, an action such as accept or drop, and logging. When it is applied, the rules go first to the AFM Pod, which compiles them into one binary blob, and the blob goes to TMM, which filters packets with it. AFM is F5's Advanced Firewall Manager. For northlight the rule can be narrow: drop TCP from a scanner range to 203.0.113.80 port 443, attached to the listener https. A dropped packet never reaches the GPU nodes, so no model server spends a cycle on it.

F5BigDdosGlobal, in k8s.f5net.com/v1 with the short name ddos, sets DDoS protection for all TMMs at once. Under spec.vectors each attack type gets a state such as mitigation, a rateLimit and a detectionThresholdEps, events per second, and some get perDstIpLimitEps. F5 notes that the numbers count per Pod. forceSwDos, false by default, forces software DoS handling on hardware that could offload it. hslPublisher names where logs go, and an allow list can name an F5BigCneAddresslist of sources to leave alone. Because it is global, a SecPolicy that carries F5BigDdosGlobal may target only GatewayClass objects. In releases 2.0 and 2.1 the DDoS object named the class itself, in its own targetRef field. Its status shows Accepted and Programmed. Programmed: True carries the message CR config sent to all grpc endpoints, and a failure shows Programmed: False, reason Failed, Failure in sending CR config to grpc endpoints.

Traffic that is not HTTP needs a layer 4 route. BNK's is L4Route, in gateway.k8s.f5.com/v1, modelled on the experimental TCPRoute and UDPRoute. It holds 1 to 16 rules for TCP, UDP and SCTP, up to 32 parentRefs, and 1 to 16 backendRefs per rule, with weight 1 by default. The owner's 2.3 audit lists RoutingConfig as the layer 4 object. F5's 2.4 reference describes RoutingConfig as something else: per-tenant routing in k8s.f5net.com/v1alpha1. It links a RoutingTemplate with either a VRF or a VXLAN, never both, BGP neighbors with a remoteAs from 1 to 4294967295, neighbor secrets and IRB interfaces, and renders them into OcNOS command line configuration. It cannot be edited, only deleted and created again. So in 2.4 L4Route carries layer 4 connections and RoutingConfig, with the cluster-wide GlobalRoutingConfig, announces addresses to the network. In the owner's lab the route to a Gateway address reached the border router about 10 seconds after the Gateway showed Programmed.

What to keep

Objects say what, a controller makes it so

Traffic gets into a cluster through three objects and one loop. A GatewayClass names the implementation. A Gateway asks for a place to listen. An HTTPRoute attaches to it and maps requests to a backend. A controller reads all three, programs a data plane, and writes back on each object whether it worked: Accepted on the class, Accepted and Programmed on the Gateway and on each listener, Accepted and ResolvedRefs on the route. The API fixes which rule wins and which code a caller gets: 404 when no rule fits, 500 when a backend reference is broken, 503 when no Pod is ready. The backend is a list of Pod addresses that the gateway keeps itself, read from EndpointSlices, so a request takes one hop from gateway to Pod. Swap the Service for an InferencePool and the choice of Pod is handed to something that understands model servers.
