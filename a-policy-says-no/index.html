Kubernetes underneath

A policy says no

How Kyverno checks, changes and adds objects before the cluster stores them

Access control in Kubernetes answers one question: may this user create a Pod in this namespace. It never opens the Pod to see what is inside. A Pod that asks for a GPU and runs as root passes, as long as its author may create Pods. Admission control is the step that reads the object itself. The API server runs it on every write, after it knows who is asking and before anything is stored. Kyverno is a policy engine that plugs into that step. This lesson follows one test Pod for the model server through it, with three policies: one that refuses, one that fills in a default and one that creates a second object. On the way it shows what the API server already does on its own, how Kyverno keeps its webhooks registered and trusted, how to roll a rule out without breaking anything, what an operator sees in metrics and events, what happens when the policy engine is down, and how the built-in policy objects of Kubernetes do the same job with no webhook at all. It describes Kyverno 1.20 on Kubernetes 1.37.

Chapter 1 of 14

Six stops before etcd

Every write takes the same road, and nothing on it reads the Pod yet

Someone wants to try a new build of the model server and applies a Pod by hand. It asks for one GPU and has no toleration for the taint that keeps ordinary Pods off the GPU nodes. Both GPU nodes carry the taint nvidia.com/gpu=present with the effect NoSchedule, so the scheduler places no Pod there unless the Pod says it tolerates that key.

Whether the Pod gets that toleration without asking depends on one admission plugin. ExtendedResourceToleration, when it is turned on, adds a toleration to any Pod that requests an extended resource such as nvidia.com/gpu, for the taint whose key is that resource name. It is off by default in upstream Kubernetes, and this cluster's API server runs the default set, so it does not run here. GKE does run it, and GKE taints its GPU nodes with exactly nvidia.com/gpu=present:NoSchedule, so on GKE this Pod would arrive with the toleration and be scheduled. Where that plugin can be turned on, it is the simpler fix. This lesson's cluster writes the rule as a policy, which also lets it check other things about the Pod.

The API server takes the request through six stops. Authentication works out who is asking, from a client certificate or a bearer token. Authorization checks that this user may create Pods in the namespace inference. Mutating admission may change the object. Schema validation checks the finished object against the rules of its kind, such as required fields and allowed values. Validating admission may refuse the object. The last stop writes it to etcd, the key value store that holds the state of the cluster.

The order has consequences. A request that fails authorization is answered with 403 Forbidden at stop 2, so no admission plugin and no policy engine ever sees it. Admission only runs for requests that change something: create, update and delete, plus connect, the operation behind kubectl exec and port-forward. Reads with get, list and watch skip admission entirely, so a policy cannot hide objects from someone who may read them.

In this cluster no policy is installed yet, so both admission stops wave the Pod through. It is stored. The scheduler then finds no node that accepts it, records a FailedScheduling event and tries again later. The Pod sits in Pending, and nobody told its author why at the moment they applied it.

Chapter 2 of 14

The API server's own admission plugins

Before any policy engine is asked, built-in code has already changed the Pod

Admission is not empty in a cluster with no policy engine. The API server has admission plugins compiled into it, and the Kubernetes reference lists the set that is on by default: CertificateApproval, CertificateSigning, CertificateSubjectRestriction, DefaultIngressClass, DefaultStorageClass, DefaultTolerationSeconds, LimitRanger, MutatingAdmissionPolicy, MutatingAdmissionWebhook, NamespaceLifecycle, PersistentVolumeClaimResize, PodSecurity, Priority, ResourceQuota, RuntimeClass, ServiceAccount, StorageObjectInUseProtection, TaintNodesByCondition, ValidatingAdmissionPolicy and ValidatingAdmissionWebhook. That is twenty plugins. The flag --enable-admission-plugins adds to the set, and the reference says the order of names in that flag does not matter, because the API server runs its plugins in a fixed order of its own.

Four names on that list are the doors that policy uses. MutatingAdmissionWebhook and ValidatingAdmissionWebhook are the plugins that call webhooks such as Kyverno's. MutatingAdmissionPolicy and ValidatingAdmissionPolicy evaluate the built-in CEL policies of the last two chapters. Every plugin is mutating, validating or both.

Three plugins change the test Pod before anything else sees it: ServiceAccount, DefaultTolerationSeconds and Priority. ServiceAccount sets serviceAccountName to default when it is missing, refuses the Pod if that ServiceAccount does not exist, and adds a projected volume named kube-api-access- with a random suffix. That volume carries a token that expires after 3607 seconds, and it is mounted in every container at /var/run/secrets/kubernetes.io/serviceaccount. DefaultTolerationSeconds adds two tolerations, for node.kubernetes.io/not-ready and node.kubernetes.io/unreachable with the effect NoExecute, each for 300 seconds, the default of five minutes. Priority both changes and checks. It reads priorityClassName, and because this Pod names no PriorityClass and none is marked as the global default, it writes spec.priority 0. A Pod that names a class that does not exist is refused. LimitRanger, also on by default, would add default requests and limits if the namespace had a LimitRange, and inference has none. PodSecurity then checks the Pod against the Pod Security Standard set for its namespace. It is a validating plugin and changes nothing.

So the Pod that later reaches Kyverno already has two tolerations its author never wrote. Neither of them has the key nvidia.com/gpu, because ExtendedResourceToleration, the plugin that would add one, is not turned on. That is why this lesson's rule tests for that key and does not just count tolerations.

Chapter 3 of 14

Kyverno asks to be asked

A policy is an object, and a webhook configuration is how the API server learns to call out

Kyverno runs as ordinary Deployments in its own namespace: an admission controller, a background controller, a reports controller and a cleanup controller. A default installation runs each with a single replica. The control plane is left as it is.

You write a policy as a Kubernetes object. In Kyverno 1.20 the kinds used here are ValidatingPolicy, MutatingPolicy and GeneratingPolicy, with the apiVersion policies.kyverno.io/v1, and their rules are written in CEL, the expression language Kubernetes uses for its own validation. Each kind also has a namespaced form, such as NamespacedValidatingPolicy, that applies only to resources in its own namespace. The older ClusterPolicy kind is no longer executed in 1.20.

When a policy is stored, a controller inside Kyverno's admission controller watches it appear and rewrites a ValidatingWebhookConfiguration. That object tells the API server which requests to send, to which Service, how long to wait and what to do if no answer comes. Kyverno puts policies that fail closed into one webhook whose name ends in -fail and policies that fail open into one ending in -ignore. Policies that share the same selectors share one webhook, and the URL path is built from their names, sorted and joined. With one validating policy the path is /vpol/gpu-pod-rules. A second policy named a-later-rule would make it /vpol/a-later-rule/gpu-pod-rules.

The webhook entry also carries sideEffects NoneOnDryRun, admissionReviewVersions v1 and a namespaceSelector that leaves out kube-system and kyverno. The Kubernetes documentation warns that the API server takes a few seconds to honour a new webhook configuration, so a Pod created in the same second as the policy can slip through.

Chapter 4 of 14

A certificate and a heartbeat

The API server only talks to a webhook it can trust, and Kyverno checks that the road still works

The API server calls a webhook over HTTPS and checks the server's certificate like any client. The Kubernetes documentation sets the rule: for a webhook reached through a Service, the certificate must be valid for the name service.namespace.svc, here kyverno-svc.kyverno.svc. The caBundle field in the webhook entry holds the certificate authority that the API server should trust for that name. If the two do not match, every call fails the TLS handshake, and with failurePolicy Fail every covered write is refused.

Kyverno runs its own small certificate authority so that nobody has to manage this by hand. By default the CA certificate is valid for one year and the serving certificate for 150 days. Both live in Secrets in the namespace kyverno, named kyverno-svc.kyverno.svc.kyverno-tls-ca and kyverno-svc.kyverno.svc.kyverno-tls-pair. Kyverno checks their validity at least every 12 hours, and also whenever one of those Secrets changes, renews them before they expire and writes the new CA into caBundle.

The Service listens on port 443 and forwards to the container's webhook port, 9443 by default. That second number matters on clusters where the control plane reaches the nodes through a firewall, because the firewall has to allow 9443 to the nodes.

Kyverno also tests the road end to end. Every 10 seconds its webhook controller updates a Lease named kyverno-health with the annotation kyverno.io/last-request-time. That update passes through one of Kyverno's own mutating webhooks, whose handler stamps the current time. If the stamp is more than 100 seconds old, ten intervals, Kyverno concludes its webhooks are not being called and keeps the webhook configuration it already has. The source says why: rebuilding at that moment would publish an empty configuration and drop every rule.

Chapter 5 of 14

Audit first: a report on what already runs

Before a rule refuses anything, find out what it would refuse

The policy was applied with validationActions set to Audit. In that mode Kyverno lets every request through and records each failure. The other values are Deny, which refuses the request, and Warn, which lets it through with a warning to the client. In the old ClusterPolicy the same choice was the field validationFailureAction with the values Audit and Enforce.

Admission only sees objects as they arrive, so Kyverno's reports controller also runs the policy over what exists already. That is a background scan. It runs when a policy appears and again every hour by default, set by the flag backgroundScanInterval, with two scan workers. Admission results and scan results first land in intermediate objects called EphemeralReport and ClusterEphemeralReport. The reports controller merges them into PolicyReport objects, one for each resource checked, in that resource's namespace. A result is one of five values: pass, fail, warn, skip when an exception bypassed the policy, or error when evaluation itself broke.

Two details trip people up. The background scan ignores the webhook's namespaceSelector, so objects in a namespace that admission never sees can still show up in reports. A label reports.kyverno.io/disabled on a policy turns its reports off. Here the two model servers pass. A forgotten benchmark Pod that holds a GPU and never declared runAsNonRoot fails.

The point of the order is safety. A rule that would refuse a Pod every running model server depends on, such as the replacement after a crash, is found in a report and not in an outage.

Chapter 6 of 14

The policy says no

One HTTPS request out, one answer back, and nothing reaches etcd

The same test Pod is applied again. It passes authentication and authorization as before, the built-in plugins add their token volume and tolerations, and schema validation finds nothing wrong. At validating admission the API server now has a webhook that matches Pods.

It wraps the request in an object of kind AdmissionReview and posts it to Kyverno over HTTPS. The request part carries a unique ID, the kind and resource, the namespace, the operation, the user and the whole Pod as it would be stored, built-in additions included. The URL carries ?timeout=10s. The API server computes that value from the time it has left and rounds it up to a whole second, so a client with a nearer deadline of its own can see a smaller number there. Validating webhooks are called in parallel, one goroutine each, and the API server waits for all of them.

Kyverno evaluates both expressions against that Pod. The first comes out false, because the Pod asks for a GPU and has no toleration for that key. Kyverno sends the AdmissionReview back with a response part: the same ID, allowed set to false and a status message it builds as Policy, the policy name, failed, and the message of the rule.

The API server stops there. It prefixes the message with admission webhook, the webhook name and denied the request. The webhook set no HTTP code, so the API server uses 400. Had the webhook set a code below 400, the API server would also have raised it to 400. Nothing is written, so the scheduler and the kubelet never hear of this Pod.

Chapter 7 of 14

Warn, dry run and exceptions

Three ways to learn what a rule thinks without being blocked by it

Deny is not the only answer a strict rule can give. With validationActions set to Warn, a failing Pod is stored and the client receives the failure as a warning. The API server sends warnings in HTTP Warning headers with the code 299, and kubectl prints each one on its own line. Kyverno uses the same text as for a denial, Policy, the name, failed, and the message. The Kubernetes documentation asks webhooks to keep a warning under 120 characters if they can. It says the API server may cut a single warning longer than 256 characters and ignores further warnings once 4096 characters have been added from all sources. For the built-in policy objects, Deny and Warn may not be set together, because the failure would then be reported twice.

A server side dry run asks the full question without storing anything. kubectl apply --dry-run=server sends the request with dryRun set, and the API server runs every stop up to the write. A webhook only receives such a request if it declares that it has no side effects on a dry run, with sideEffects None or NoneOnDryRun. Otherwise the API server fails the request and says the webhook does not support dry run. Kyverno's webhooks declare NoneOnDryRun, so a dry run shows exactly the denial the real request would get.

Some objects need to be let through on purpose. A PolicyException in policies.kyverno.io/v1 names the policies it relaxes in policyRefs and the objects it covers in matchConditions, written in CEL. Exceptions are disabled by default. They are enabled with the flag enablePolicyException, together with exceptionNamespace, which names the only namespace where exceptions may be created. A Pod that an exception covers is admitted and shows up in its report with the result skip.

Chapter 8 of 14

A default filled in on the way

A mutating policy changes the object, and the checks see the changed version

Some rules are easier to apply than to demand. A MutatingPolicy adds the label cluster: northlight-eu to every new Pod, so that every log line and alert about a model server says where it ran. Its mutation is a CEL expression that returns a partial object, and Kyverno merges that into the Pod. When this policy is stored, Kyverno registers a second webhook, in a MutatingWebhookConfiguration.

The author now adds the missing toleration to the test Pod and applies it. Mutating webhooks are called first, one at a time. The API server sorts the mutating webhook configurations by name and calls them in that order, so that the result is the same every time. Kyverno answers allowed, and adds a patch in JSON Patch format, the only patch type a webhook may return. The API server applies the patch itself. If a mutating webhook changes the object, the built-in mutating plugins run again so they can see the change.

A webhook can ask to be called again too. With reinvocationPolicy IfNeeded, a webhook is called a second time when a later webhook changed the object. The documentation promises nothing more: the number of extra calls is not guaranteed to be exactly one, and webhooks may be reordered. Mutating webhooks therefore have to be idempotent, able to see an object they already changed and leave it right. Inside Kyverno, mutations of one policy apply in the order written, and the order across several MutatingPolicies is not guaranteed.

The changed Pod then goes through schema validation and on to validating admission, so the Deny policy judges the Pod as it will be stored. An audit log at level Request or above records each patch under a key such as patch.webhook.admission.k8s.io/round_0_index_0.

Chapter 9 of 14

A NetworkPolicy for every new namespace

A generating policy answers yes, and then creates something of its own

The third kind of policy creates objects. A GeneratingPolicy watches for a trigger, here the creation of a Namespace, and produces a downstream object, here a NetworkPolicy that blocks all incoming traffic to the Pods in that namespace. A team that wants to reach a model server then has to open the path on purpose.

When someone creates the namespace training, the API server asks Kyverno through a webhook as before. Kyverno answers allowed and writes a note for itself, an object of kind UpdateRequest. The background controller picks the note up and creates the NetworkPolicy through the API server, like any other client and under its own service account, system:serviceaccount:kyverno:kyverno-background-controller. Kyverno checks that this account has the permissions it needs when a generating policy is created, and refuses the policy if they are missing. The documented test is kubectl auth can-i create networkpolicies with --as and that service account.

With evaluation.synchronize.enabled set to true, Kyverno keeps watching what it generated. A NetworkPolicy that someone deletes is created again, and one that someone edits is set back. A change to the policy is copied to every downstream object. Deleting the trigger deletes the downstream, and so does a change to the trigger. Deleting the policy deletes the downstream too, unless evaluation.orphanDownstreamOnPolicyDelete.enabled is true. Without synchronize, a deleted downstream stays deleted.

When generation stalls, the notes pile up. The troubleshooting guide says to list them with kubectl -n kyverno get updaterequests, and reads many in the Pending state as a sign of a permissions problem.

Chapter 10 of 14

When Kyverno cannot answer

failurePolicy decides whether an unreachable webhook means no or yes

A webhook puts another program on the path of every write it covers. The field failurePolicy says what the API server does when the call itself fails. The documentation lists what counts: a network error, a timeout or a connection failure, a reply that is not 2xx or cannot be read, a request the API server could not serialize or send, and for mutating webhooks a patch type it cannot decode. Fail refuses the request. Ignore lets it through unchecked. Fail is the default in Kubernetes and in Kyverno, and a policy can choose Ignore in spec.failurePolicy.

An explicit no is a different thing. The documentation says a rejection that arrives correctly always denies the request, whatever failurePolicy says.

Here the node that runs Kyverno's only admission controller Pod loses its network. Seconds later the model server qwen3-6f7d9c8b4-m9q4t crashes and the ReplicaSet controller asks for a replacement. Mutating webhooks come first, so the API server calls Kyverno's mutating webhook, waits ten seconds and refuses the Pod. Its log says Failed calling webhook, failing closed. The ReplicaSet controller records a FailedCreate event and retries.

Everything that already runs keeps running, and qwen3-6f7d9c8b4-x7k2p goes on answering alone. No new Pod can start in any namespace the webhook covers until Kyverno is back. Kyverno's own namespace and kube-system are left out of the webhook, so a replacement Kyverno Pod can be created and started without asking Kyverno. That makes recovery possible, and it does not make it quick. The Kyverno Pod on the cut-off node is replaced only after the node controller marks the node NotReady, once node-monitor-grace-period has passed, and then after the 300 second unreachable toleration that DefaultTolerationSeconds gave the Kyverno Pod runs out. Left alone, the outage lasts more than five minutes. Once the node is NotReady the Kyverno Pod is no longer a ready endpoint of its Service, so later calls most likely fail at once with a connection error instead of waiting ten seconds. failurePolicy Fail refuses them either way. When Kyverno answers again, the next retry succeeds and the replacement model server needs about three minutes to load the 34.3 GB of its FP8 weight files before it is Ready.

Chapter 11 of 14

Keeping the webhook up, and getting out of trouble

Replicas spread the load, leader election guards the bookkeeping, and two commands open the door

The admission controller does not use leader election for webhook calls. Every replica answers AdmissionReviews, and the Service spreads them across all of them, so more replicas give both availability and throughput. Certificate renewal and webhook management do use leader election, so only one replica does that work at a time. Kyverno's leader election renews every 2 seconds by default, with a lease of six retry periods, 12 seconds. The reports and background controllers also elect a leader and only the leader works, so extra replicas of those two give availability and nothing more.

The Kyverno documentation gives two numbers. The high availability guide calls three the minimum supported replica count for the admission controller. The installation page says at least two, and its example sets three replicas for the admission controller and two for each of the other three. Three is the safer reading, and it is what the scaling guide measured: with three replicas every load test stayed below 650 ms at the 99th percentile with 500 virtual users, each a concurrent client creating Pods, while a single replica under the same 500 went above one second.

Some outages look like timeouts and are really network paths. On a private GKE cluster the control plane must be allowed to reach the nodes on the webhook port, 9443 by default. On EKS with a custom network plugin the API server cannot reach Pod addresses, and the documented fix is to run the admission controller with hostNetwork true. On AKS an admissions enforcer rewrites the webhooks unless they carry an annotation that tells it not to.

When nothing else works, the troubleshooting guide gives the way out. Delete the two resource webhook configurations, and the API server stops calling Kyverno at once. Then scale the admission controller to zero and back to three. Kyverno writes the configurations again when it starts.

Chapter 12 of 14

What an operator sees

A refused request leaves no report, so look at metrics and events

A PolicyReport describes objects that exist. A Pod that admission refused never existed, so it has no report. The Kyverno documentation says to use metrics and Kubernetes events to investigate blocked requests. Both sides of the call publish metrics.

The API server counts every webhook call. The histogram apiserver_admission_webhook_admission_duration_seconds is labelled with the webhook name, the type, the operation and whether the request was rejected, with buckets at 0.005, 0.025, 0.1, 0.5, 1, 2.5, 10 and 25 seconds. Healthy calls sit in the lowest buckets, and a call cut off by the ten second timeout lands far above them. apiserver_admission_webhook_rejection_count has the label error_type. Its value is no_error when the webhook answered allowed false, calling_webhook_error when the call failed and failurePolicy was Fail, and apiserver_internal_error for faults in the API server itself. apiserver_admission_webhook_fail_open_count counts calls that failed and were let through because failurePolicy was Ignore. A rising fail open count means requests are entering the cluster unchecked.

Kyverno exposes its own metrics on port 8000, through the Service kyverno-svc-metrics. kyverno_admission_requests_total counts the AdmissionReviews it received, kyverno_admission_review_duration_seconds times them, and kyverno_validating_policy_results_total counts results per policy. Kyverno's scaling guide names an alert, KyvernoAdmissionHighLatency, that fires when the 99th percentile stays above one second for five minutes.

Kyverno also writes Kubernetes events. Their reasons are PolicyViolation, PolicyApplied, PolicyError and PolicySkipped. By default the flag omitEvents suppresses PolicyApplied and PolicySkipped, so the events that remain are the ones that need a person.

Chapter 13 of 14

The same rule with no webhook

ValidatingAdmissionPolicy runs CEL inside the API server

Kubernetes has a built-in way to write a validation rule, stable since version 1.30. A ValidatingAdmissionPolicy holds CEL expressions, the same language Kyverno's policies use. A second object, a ValidatingAdmissionPolicyBinding, switches the policy on, says where it applies and sets validationActions to Deny, Warn or Audit. Audit here includes the failure in the audit event the API server records for the request.

The API server evaluates the expressions in its own process during validating admission, before it calls any validating webhook. No Service is called and no Pod has to be up, so the outage of the last chapters cannot happen to this rule. failurePolicy still exists on the policy, and here it covers a different failure: a policy that is misconfigured or an expression that ends in an error. Failures of that kind are enforced through the binding's validationActions only when failurePolicy is Fail or unset. With Ignore they are ignored.

What the built-in policy leaves out is everything around the rule. It creates no reports, does not scan existing objects and cannot generate objects. Kyverno can also produce these objects for you. A ValidatingPolicy with autogen.validatingAdmissionPolicy.enabled set to true is turned into a ValidatingAdmissionPolicy that the API server runs. The documentation adds a condition: generating a ValidatingAdmissionPolicy and generating rules for Pod controllers exclude each other. The documentation states the condition this way: when spec.autogen.podControllers is configured, Kyverno skips the ValidatingAdmissionPolicy and says why in the policy's status. That is a different switch from podControllers.enabled: false, which only turns the controller rules off, and the documentation does not say whether a podControllers block with enabled false also counts as configured.

The mutating counterpart, MutatingAdmissionPolicy, is listed as alpha from 1.30, but its feature gate had no effect in 1.30 and 1.31, so it first worked as alpha in 1.32. It went to beta in 1.34 and became stable in 1.36, enabled by default from then on.

Chapter 14 of 14

Messages, parameters and cost limits

A built-in policy can explain itself, read settings from another object, and is stopped if it thinks too long

The bare denial in the last chapter quoted a CEL expression. A policy can say more. Each validation may carry a static message, or a messageExpression that builds the text in CEL from the object, the old object, the request, the parameters and the namespace. messageExpression wins when both are set. If it fails to evaluate or returns several lines, the static message is used. A validation may also set reason, one of Unauthorized, Forbidden, Invalid or RequestEntityTooLarge. Without one the client gets Invalid. When several validations fail, the reason and code of the first one in the list are used.

One policy can serve several namespaces with different settings. The policy names a paramKind, any kind such as a ConfigMap or a custom resource. Each binding then points at one parameter object through paramRef, by name or by selector, never both. The field parameterNotFoundAction is required and takes Allow or Deny. With Deny, a missing parameter is treated as a failure under the policy's failurePolicy. A binding for inference could set a maximum of one GPU per test Pod, and a binding for training a maximum of four, both on the same policy.

CEL runs inside the API server, so every expression has a budget. The source sets a cost limit of 1,000,000 units for each expression call, which it describes as roughly 0.1 seconds, and 10,000,000 units for all the expressions of one binding together, roughly one second. Match conditions on webhooks and bindings get 2,500,000 units, roughly a quarter of a second. The largest string a messageExpression may produce is 5 × 1024 = 5120 bytes. An expression that runs out of budget is an error, so failurePolicy decides what happens to the request.

The API server also checks types. When it can work out the types of the matched resources, it writes problems into status.typeChecking.expressionWarnings. That check only warns. It never changes what the policy does.

What to keep

Asked before it is stored

Admission is the one place where the cluster reads an object before accepting it. It comes after authentication and authorization and before etcd, and inside it changes come first and checks last. Built-in plugins already add a token volume, two tolerations and a priority before any policy engine is asked. Kyverno joins the step from outside: it registers webhooks, keeps their certificates and a heartbeat, and the API server posts each matching object to it in an AdmissionReview and waits. A ValidatingPolicy answers yes or no. A MutatingPolicy answers yes with a patch. A GeneratingPolicy answers yes and creates a second object afterwards. Audit, Warn, a server side dry run and the background scan show what a rule would refuse before it refuses anything. The price of a webhook is that every covered write depends on it, so failurePolicy, replicas, excluded namespaces and the API server's own metrics matter. The built-in ValidatingAdmissionPolicy runs CEL with no network call and a fixed cost budget. All of this judges what a Pod declares. What a container does once it runs is a different question, for a different tool.
