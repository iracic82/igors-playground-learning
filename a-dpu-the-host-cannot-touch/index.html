BNK and gateways

A DPU the host cannot touch

BNK on BlueField-3 in zero-trust mode, the leaf and spine fabric, and what each VNI is for

The lesson A computer in the network slot showed that a DPU can keep the network's rules away from whoever is root on the host. This lesson opens that claim up. It shows which five things NVIDIA's zero-trust mode can take from the host, how TMM gets two ports of its own on the card, and which Kubernetes cluster the card belongs to. Then it follows packets. One comes from the leaf switch in a tenant's fabric tunnel and ends at the Pod qwen3-6f7d9c8b4-m9q4t. One leaves that Pod through a second, shorter tunnel, one PCIe slot long, between the host and the card, and its answer comes back the same way. Each tunnel has a VXLAN number, a VNI, and each number answers a different question.

The lesson keeps three kinds of statement apart. Some things the owner's public lab repository configures, field by field: the VNIs 100 and 200, the scalable functions, the Open vSwitch bridges and the Calico settings. Some things F5's and NVIDIA's documentation and the owner's decks describe: zero-trust mode, DPF, EVPN with one VNI per tenant. A few things are this lesson's inference, and each one is labelled where it appears.

Chapter 1 of 30

The host belongs to the tenant

So nothing that enforces tenancy may live on it

Northlight rents gpu-node-2 to tenant A as bare metal. Tenant A installs an operating system and is root. From that moment the provider can believe nothing the host says about itself. Its kernel, its drivers and its network settings are the tenant's. If the firewall or the tenant's network boundary ran on the host, the tenant could switch it off. A host that can reach the card's management interfaces could also climb from being a tenant into the provider's infrastructure.

The owner's grid deck lists the problems this creates for a provider. The host cannot vouch for itself. Firmware is an attack surface. A host with access to the BMC turns the tenant role into an infrastructure role. Tenant resources must be placed in a private network of their own while looking to the host like a local network connection. Isolation must fail closed. No data may survive from one rental to the next, and tenant churn must not shake the shared fabric.

The host needs only a network interface from the card. In the lab guide's layout that is a virtual function, VF, a slice of the card's second physical port that appears on the host's PCIe bus as an ordinary network card. The lab guide creates it with netplan: virtual-function-count 1 on the second port, then a static address on the new VF, named after the port with np1 replaced by v0. The host also sees both physical functions, and root decides how many VFs exist. Each function arrives on the card at a twin port called a representor, pf1vf0 for this VF, which the provider's software on the card controls.

Chapter 2 of 30

What zero-trust mode switches off

Five operations, each restricted on its own

A BlueField-3 ships in DPU mode. NVIDIA also calls this ECPF mode, the embedded CPU function ownership mode. In it the card's Arm cores own the network chip and its embedded switch, and every packet to or from the host passes a virtual switch that the Arm side controls. NVIDIA's documentation still treats the card in plain DPU mode as managed by the data center and host administrator together, and lists their shared tasks: loading drivers, resetting an interface, updating the firmware and changing the card's mode.

Zero trust, which the same page also calls Restricted Mode, is DPU mode with that door closed. The page lists five operations that can be restricted one by one. The host cannot make itself owner of a port. It cannot read the hardware counters. The tracer is blocked. The RShim interface, the host's console and install path into the card, is disabled. Firmware cannot be flashed from the host. From then on the card is managed from its Arm cores or through its BMC.

The mode is visible from the host. mlxconfig queried for INTERNAL_CPU_OFFLOAD_ENGINE answers ENABLED(0) for DPU mode and DISABLED(1) for NIC mode. When the line is marked RO, read only, the card is in DPU mode with zero trust. The BMC reports the same through Redfish under Systems/Bluefield/Oem/Nvidia as "Mode": "DpuMode". Leaving zero trust takes the provider's path. A card cannot go from zero trust straight to NIC mode. It must first return to plain DPU mode with a system level reset, and NVIDIA warns that NIC mode with zero-trust settings still in place is undefined behaviour.

Chapter 3 of 30

Turning zero trust on, and what it leaves out

mlxprivhost on the Arm side or a Redfish PATCH on the BMC

The provider switches zero trust on from one of the two sides the host cannot use. On the card's Arm side the tool is mlxprivhost. NVIDIA's example is mlxprivhost -d /dev/mst/<device> r --disable_rshim --disable_tracer --disable_counter_rd --disable_port_owner. The letter r restricts the host, and each of the four flags closes one operation. NVIDIA's list has a fifth restriction, firmware flash, and the example names no flag for it. The same tool with p returns the card to privileged DPU mode. From the BMC the step is a Redfish PATCH that sets "PrivilegeMode": "Restricted" under the card's HostPrivilegeConfig settings, and NVIDIA says a power cycle is needed before it applies.

Each restriction is set on its own, so a card can be restricted with only some flags in force. The RO marking on INTERNAL_CPU_OFFLOAD_ENGINE and the Redfish Mode field say that zero trust is on. They do not say which flags are set. A provider has to check each one after every change and between rentals.

Zero trust also leaves a lot to the provider. NVIDIA's list says nothing about the host's PCIe functions, how many VFs root creates, or the data plane. As with any PCIe card, the host keeps its own resets, power and server BMC, and can flood its functions with traffic. Trust runs the other way too: the provider's card sits on the tenant's PCIe bus and can reach host memory by DMA, so the tenant relies on its own IOMMU. NVIDIA's public NICo overview names what a provider builds around the card: attestation and firmware checks over Redfish, network isolation, and tenant sanitization between rentals.

Chapter 4 of 30

Every host packet passes a switch the Arm side programs

Representors, the slow path and the fast path

In DPU mode the card has two kinds of port. Physical ports, p0 and p1, face the leaf switch. Functions face the host and the Arm cores: physical functions, virtual functions and scalable functions. Each function has a representor on the Arm side. A representor is a network device on the card's Linux that stands for the function. Whatever the function sends arrives on its representor, and whatever is sent to the representor reaches the function. A switch on the card, usually Open vSwitch, joins representors and physical ports into bridges.

NVIDIA's documentation describes two paths through this switch. On the slow path a packet goes up to the Arm cores, through the representor, and the software switch decides where it goes. On the fast path the embedded switch in the network chip already holds a rule for the flow and forwards the packet itself at line rate. A virtual switch usually lets only the first packet of a new flow take the slow path. It classifies that packet and then installs a rule in the embedded switch for the rest of the flow.

Two details matter for a provider. At power on, network access to the host is blocked until the switch on the Arm side has loaded its default rules. The host's driver can only load after the card's own driver has finished configuring the network chip, and the chip's configuration memory lives in the card's memory. So the card decides when the host has a network, and every embedded switch rule comes from the Arm side. In the lab's plain DPU mode the host can still log in there over RShim and tmfifo_net0.

Chapter 5 of 30

The lab guide installs the card from the host

The exact path that zero-trust mode closes

The lab guide runs the card in plain DPU mode, and its install path shows what zero trust takes away. On the host it installs NVIDIA's rshim package and starts the service. RShim gives the host a device directory, /dev/rshim0, with a console, a boot channel and a small network link to the card called tmfifo_net0 on a /30 subnet. The host then writes the whole operating system image, the BlueField bundle or BFB, into the card with bfb-install --rshim rshim0 --config <file> --bfb <bundle>. Progress is read from /dev/rshim0/misc, which ends with the lines Linux up and DPU is ready. The same file prints SECURE_NIC_MODE 0. In rshim's README, 1 means most rshim functions are off over PCIe, with USB unaffected: a lock on one path, related to zero trust.

The config file that dpu-config.sh generates runs inside the card's installer. It sets the hostname, writes network settings for tmfifo_net0 and the out of band management port oob_net0 with DHCP, loads the kernel modules overlay, br_netfilter and vfio_pci, and reserves hugepages for TMM. The documented script asks the boot loader for 12544 pages of 2 MiB, which is 25,088 MiB or 24.5 GiB. Its comment asks 1.5 GB per TMM thread for 16 threads. The Ansible template reserves 8192 pages, 16 GiB, though its comment says 14 GB. Its post install step runs mlxconfig inside the card to size SFs, VFs and the LAG, and sets INTERNAL_CPU_OFFLOAD_ENGINE=0.

In zero-trust mode the first step already fails. RShim is disabled from the host, so bfb-install has no channel, and firmware flashing from the host is restricted. That is why DPF provisions zero-trust cards through the BMC instead.

Chapter 6 of 30

TMM will not start without hugepages

On a host in host mode as much as on the card

TMM moves packets with DPDK, a library that reads and writes network buffers straight from user space. DPDK keeps those buffers in hugepages, blocks of memory far larger than the normal 4 KiB page. A 2 MiB hugepage covers what 512 normal pages cover, so the processor needs one address translation entry where it would need 512, and the memory is pinned so it is never swapped out. The card's numbers come from the previous chapter: 12544 pages in the documented script, 8192 pages, 16 GiB, in the Ansible template. The owner's pipeline plan turns that second number into a check, HugePages_Total 8192 on the card.

The same rule holds when TMM runs on a host in host mode, as a software Pod on the host's own CPUs with no BlueField at all. TMM will not start without 2 MiB hugepages. The owner's lab notes record 4 to 6 GiB of them in labs. At 2 MiB a page, 4 GiB is 2048 pages and 6 GiB is 3072 pages. Measured on a BNK 2.4.0 install at deploymentSize Small, the f5-tmm Pod asks for 4.6 vCPU, 8 GiB of memory and 4 Gi of hugepages-2Mi. 4 Gi is exactly 2048 pages, so 2048 pages is the floor for one TMM. The notes do not say what the extra 1024 pages of a 6 GiB lab were used for.

Kubernetes does not create hugepages. The kernel reserves them, and the kubelet then reports them in the node's Capacity and Allocatable as the resource hugepages-2Mi. The owner's install repository reserves them with sudo sysctl -w vm.nr_hugepages=2048, which takes effect at once, and writes vm.nr_hugepages = 2048 into /etc/sysctl.d/90-bnk.conf so they come back after a reboot. Kubernetes' Manage HugePages page warns that for pages allocated after boot the kubelet must be restarted before it reports them. Until it does, the scheduler still sees zero. The check is kubectl get node gpu-node-1 -o jsonpath='{.status.allocatable.hugepages-2Mi}', which should print 4Gi.

Hugepages cannot be overcommitted. A Pod that asks for 4Gi of hugepages-2Mi fits only on a node with 4Gi still free, and a request for hugepages must come with a memory or CPU request too. A node without them never gets the TMM Pod. The scheduler leaves it Pending with Insufficient hugepages-2Mi, and the owner's notes say no override removes the requirement. On a GPU node the reservation comes out of the host's own memory. 4 GiB reserved on gpu-node-1 is 4 GiB that vLLM's process for Pod qwen3-6f7d9c8b4-x7k2p cannot use on the host side. The model's weights, 34.3 GB in the FP8 build, sit in the H100's own memory and are not touched.

Chapter 7 of 30

TMM gets two ports of its own

Scalable functions, their representors and two bridges

TMM, the data plane of BIG-IP Next for Kubernetes, runs as a Pod on the card's Arm cores and drives its ports itself with DPDK. The ports it gets are scalable functions. An SF is a light network function cut from one of the card's physical ports, with its own queues. Each SF has a representor, the end that plugs into a bridge.

The documented script empties /etc/mellanox/mlnx-sf.conf, which normally holds the card's default SFs without trust, and writes two lines per port: mlnx-sf --action create --enable-trust with --sfnum 0 and --sfnum 1, each with a random locally administered MAC address that starts with 02. Number 1 on each port is TMM's. Then it renames the two default bridges in /etc/mellanox/mlnx-ovs.conf. Bridge sf_external joins the uplink p0 and en3f0pf0sf1, the representor of SF 1 on port 0. Bridge sf_internal joins p1, en3f1pf1sf1 and pf1vf0, the representor of the host's VF. These are plain Open vSwitch bridges. The repository adds no flow rules, and a bridge without its own rules forwards with the NORMAL action, as a learning switch. On sf_internal the host's VF is one layer 2 hop from the uplink p1, so TMM is not forced into its path.

The Ansible template builds a different card. It creates SFs 0, 1 and 2 on each port, bonds p0 and p1 into bond0 with LACP, and puts bond0, pf0hpf (the representor of the host's first physical function) and both TMM SF representors on one bridge, br-lag. Its README shows both 200 Gb/s links active in one aggregator with hash policy layer3+4.

Chapter 8 of 30

One bond, two links, one leaf

What LACP rate and hash policy do in the Ansible layout

The Ansible layout's bond is the lab's only link redundancy, and its settings decide how flows spread. netplan sets mode 802.3ad, which is LACP, the Link Aggregation Control Protocol. lacp-rate fast asks the partner to send an LACPDU every second. The slow rate is one every 30 seconds, so fast notices a dead partner far sooner. mii-monitor-interval 100 checks each link's carrier every 100 ms.

transmit-hash-policy layer3+4 picks a member link from the IP addresses and the TCP or UDP ports of each packet, so one flow stays on one link and different flows spread. The Linux bonding documentation calls this policy not fully 802.3ad compliant. For fragments it leaves the ports out of the hash, so a flow that mixes fragments and whole packets can be striped over both links and arrive out of order. Each end hashes only what it sends. The leaf picks the link for the return direction with its own policy, and the two need not match. The template also sets LAG_HASH_MODE="yes" and does not explain it.

A switch that reads only outer headers cannot see the flow inside a tunnel. That is why RFC 7348 asks the sender to fill the outer UDP source port from a hash of the inner packet. layer3+4 on the bond, and equal cost hashing on the spines, then spread tunnel traffic by inner flow.

Both links go to one leaf, as the README states, so that leaf is a single point of failure. Homing a card to two leaves needs MLAG on the switches or EVPN multihoming, with an Ethernet Segment Identifier and EVPN route types 1 and 4.

Chapter 9 of 30

From scalable function to interface 1.1

Device plugin, network attachments and the sf CNI

An SF on the card is only a network device until Kubernetes hands it to the TMM Pod. Four pieces do that, and the lab guide configures each one.

The SR-IOV network device plugin advertises SFs as countable node resources. Its ConfigMap sriovdp-config defines two resources. bf3_p0_sf with prefix nvidia.com selects devices of vendor 15b3 and device a2dc, the BlueField-3, on the PCI address of port 0, with pfNames p0#1 and auxTypes sf. bf3_p1_sf does the same for port 1. deviceType is auxNetDevice, because an SF sits on the auxiliary bus. The selector #1 picks SF number 1 only, which is why the script made SF 1 the TMM port. The DaemonSet is patched to tolerate every NoSchedule taint so it also runs on the tainted DPU nodes.

Multus then attaches extra networks to a Pod. Two NetworkAttachmentDefinitions in the default namespace, sf-external and sf-internal, each carry the annotation k8s.v1.cni.cncf.io/resourceName for one resource and a CNI config of type sf. That sf binary is F5's. It is copied by hand to /opt/cni/bin on every DPU node, and when Multus delegates to it, it moves the SF's network and RDMA devices into the TMM container.

The SPKInfrastructure resource bnk-dpu-infra lists the attachments in order, default/sf-external first and default/sf-internal second, and asks for one of each resource. Order is the interface number: the first becomes 1.1, the second 1.2. The SPKInstance pins TMM to Arm cores 8 to 15 with palCPUSet, limits it to 8 CPUs, 13Gi of 2 MB hugepages and 2Gi of memory, and names the two auxiliary devices DPDK may open, mlx5_core.sf.4 and mlx5_core.sf.5, each with dv_flow_en=2.

Chapter 10 of 30

F5SPKVlan gives TMM its addresses

The internal and external networks, one self IP per TMM

Interfaces 1.1 and 1.2 have no addresses yet. The F5SPKVlan resource gives them a VLAN, self IPs and settings. The lab guide applies two. external sits on interface 1.1 and internal on 1.2. Both use tag 0. The reference says frames of a VLAN with tag 0 leave without an 802.1Q tag, and any tag from 1 to 4094 adds one.

The address lists are per TMM. selfip_v4s and selfip_v6s hold one address for each TMM replica, handed out in list order, so the list needs at least as many entries as there are DPU nodes. The lab guide has three TMMs and lists three addresses of each family, with prefixlen_v4 24 and prefixlen_v6 112. In this lesson's world there are two cards. TMM on gpu-node-2's card is 10.0.20.201 on internal and 10.0.10.201 on external, and the other TMM has .202 on both.

Two more fields matter. internal: true marks the VLAN that faces the application Pods, and the reference allows it on one VLAN only. auto_lasthop: AUTO_LASTHOP_ENABLED makes TMM send return traffic to the MAC address that sent the request. Neither file sets mtu, and the current reference gives that field a default of 1500.

The host needs a matching annotation. F5's reference says each host node must carry k8s.ovn.org/node-primary-ifaddr with its address on the internal network, so that static routes toward the TMM on the DPU can be built. The install script loops over the nodes right after kubeadm init, when the control-plane host is the only one, and writes the fixed address 192.168.20.41. A working VLAN shows in kubectl get f5-spk-vlan with READY True and the message CR config sent to all grpc endpoints.

Chapter 11 of 30

The 2.4.1 form of the same networks

Infra, GatewaySettings and EgressGateway, and what has to be true first

The lab guide's README is at its own version, v2.1.0. That is the guide's version, not BNK's: its install pages link F5's 2.0.0 documentation and pull the f5-eowyn chart at 2.0.0-LA. It builds its networks with F5SPKVlan, F5SPKVxlan, F5SPKSnatpool and F5SPKEgress. F5's current references mark all four deprecated as of 2.4.0. From 2.4 the same ideas are split across three Gateway API style resources in the group gateway.k8s.f5.com, version v1alpha1. The owner's notes on BNK 2.4.1 list what the new form needs: a switch named USE_GATEWAY_SETTINGS, the Infra resource, one GatewaySettings per Gateway, TMM's internal leg on its own network card and NetworkAttachmentDefinition, a restart of the controller once TMM is stable, and Multus in its thick form. The notes do not record where USE_GATEWAY_SETTINGS is set, and the F5 pages this lesson read do not name it, so treat it as the owner's lab knowledge for that release.

Infra describes the underlay, the networks TMM itself stands on. F5's page asks for it before any GatewaySettings, Gateway or EgressGateway. It has five lists. ipams holds named address pools, each with ipPools given as a cidr or as a rangeStart and rangeEnd, never both in one entry. These pools supply self IPs, SNAT addresses and listener addresses. networkAttachments maps a logical name to one or more Kubernetes NetworkAttachmentDefinitions, so networks never point at a NetworkAttachmentDefinition directly. vrfs lists routing domains, and strictIsolation defaults to true, which forbids route leaking and shared interfaces between them. networks lists VLANs and VXLANs. A VLAN has tag, mtu, networkAttachmentRef, ipamRefs and an optional vrfRef, and tag 0 or no tag means untagged, as with F5SPKVlan. A VXLAN has vni, mtu, port, ipamRefs for its self IPs and vtepIpamRefs for its tunnel endpoint addresses. staticRoutes gives each route a destination and either a nextHop or a reference to a directly connected network, never both. F5's pages spell that reference two ways: networkRef in the API reference, networkRefs in the how-to's example. Each network name must be unique in the whole resource.

GatewaySettings carries what a tenant's traffic uses: which network, which VRF and how to translate the source address. Its egressConfigs list holds named entries. Each has a sourceNATConfig with a type, Automap to use TMM's own self IP, or Pool with a sourceNATPoolRef to a pool from Infra, and a vrfRef. In the owner's 2.4 lab the admission webhook refused an entry without sourceNATConfig and its type. An EgressGateway names one entry by infrastructure.parametersRef, with name and sectionName, and both are immutable. It must live in the same namespace as the GatewaySettings. It selects Pods with sourceSelector, in mode NamespaceSelector, PodSelector or Combined, and each one creates a wildcard virtual server on TMM, 0.0.0.0:0 for IPv4 and [::]:0 for IPv6. That is the replacement for F5SPKEgress that later chapters show in its older form.

The last three items are about order and plumbing. In host mode TMM's internal leg, the side that faces the Pods, gets its own network card and its own NetworkAttachmentDefinition, apart from the external leg. Multus attaches those extra interfaces. In its thick form Multus is two parts: a small shim binary on each node that the container runtime calls as a CNI plugin, and a multus-daemon that the shim calls over a Unix socket, by default in /run/multus. The daemon reads the NetworkAttachmentDefinition, computes the runtime configuration and calls the real plugin. The owner hit two related traps: the NetworkAttachmentDefinition CRD must exist before the lifecycle operator starts, even in host mode, and Multus needed a 512Mi memory limit or Pods hung in ContainerCreating. Once TMM is up and stable, the controller is restarted. The notes give the step and not the reason.

Chapter 12 of 30

One cluster in the lab, two in zero trust

Which Kubernetes the card is a node of

The lab guide builds one Kubernetes cluster. The hosts and the DPUs are all worker nodes of it, and each DPU joins with kubeadm join. Each DPU node then gets the taint dpu=true:NoSchedule so ordinary Pods stay off it, and the label app=f5-tmm so the TMM DaemonSet lands on it. BNK's control plane runs on a host, and the SPKInstance tells it to watch the tenant namespaces red and blue, which must exist before the install. The host sits inside the cluster that configures the card.

The label app=f5-tmm is easy to forget, and forgetting it gives one of the worst errors in the install. The lifecycle operator, FLO, builds the TMM DaemonSet from the nodes that carry the label. With no labelled node it panics with assignment to entry in nil map at f5tmm_daemonset.go:186. That sentence is the Go runtime's own message for a program that writes a key into a map that was never created. The operator recovers, puts the work back on its queue, tries again and panics again, round after round, while every other component reports healthy. The message names neither TMM nor the label. The quick test is kubectl get nodes -l app=f5-tmm. If it prints No resources found, no TMM can exist. In the owner's install repository the nodes are declared in the cluster file, and its phase 05 applies or verifies the label from that file. The fix is one command per card, kubectl label node gpu-node-2-dpu app=f5-tmm, and the operator's next round builds the DaemonSet. A second count trap sits beside it. On BNK 2.3.0 the operator also panicked building the DaemonSet when two nodes carried the label, and this lesson's world has two cards. The owner's install repository guards that case with BNK_TMM_ALLOW_MULTI=true, and two TMMs worked on 2.4.1 and 2.4.2 in two of the owner's labs. A third, a kind cluster on 2.4.x, still looped with a second TMM node, and that case is unresolved.

NVIDIA's DOCA Platform Framework, DPF, has a model close to this called Host Trusted: the host is a worker of the cluster that manages the DPUs, and the card is managed in band. The match is loose, because DPF still keeps the DPUs in a DPU cluster of their own. DPF's other model is Zero Trust. There a DPF management cluster provisions the cards through each BMC with Redfish, and the host stays outside both clusters. DPF Zero Trust is a deployment model. The card's restricted privilege mode is a separate setting, and the two are normally used together.

F5's product material places BNK in that DPU cluster as a DPF service. The owner's notes on F5's 2.4 feature deck describe it as deployed in the role of f5-ingress, with tenants isolated by per-tenant fabric VRFs, and managed out of band through DPF and Argo. The grid deck draws the same picture: a DPF DPU configuration virtual cluster holding f5-tmm and f5-coremod beside NVIDIA's HBN on every card, below a line labelled the zero trust customer boundary. The tenant's own Kubernetes, if it runs one, is a third cluster the provider never enters.

Chapter 13 of 30

Every F5 piece on the NICo slide

What runs on each card, what runs in the management cluster, and what runs once per tenant

Slide 12 of the owner's grid deck draws a whole factory run by NICo, NVIDIA Infra Controller, and puts F5 components in three places. This chapter reads the slide box by box, so that each name has a location and a job. Where F5's or NVIDIA's public pages describe a component, the chapter says what they say. Where only the slide names it, the chapter says that too.

The first place is the card in front of every tenant host. The slide draws four tenant hosts, in VPC A, VPC B, VPC C and VPC D, each with a DPU on top and a question mark below a black bar labelled Zero Trust Customer Boundary. The question mark is the tenant's workload, which the provider does not see. Every one of those DPUs carries NVIDIA's HBN, the routing container that NICo's DPU agent configures, and two F5 boxes, f5-tmm and f5-coremod. The DPUs of VPC A, B and C also carry a third box, f5-dssm. The DPU of VPC D carries only f5-tmm and f5-coremod. TMM is the traffic engine this lesson has followed from the start. dSSM, distributed Session State Management, is described on F5's dSSM Database page: Redis data stores that give the TMM Pods central, persistent storage for application traffic data, bound to persistent volumes so the data survives a container restart. TMM reaches them through a Service named f5-dssm-sentinel on TCP port 26379, and the database Pods are placed with affinity_type preferred, which tries to put each one on a different node and lets two share a node when no other node can take one. Other lessons on this site show what TMM keeps there: the DoS attack ID that lets several TMMs report one attack once, and the token counts of a tenant's requests. f5-coremod is drawn on every card. F5's public pages do not describe a component of that name, so this lesson gives it no job beyond its place on the slide.

The second place is NICo's Infrastructure Management Cluster, drawn in the middle. NVIDIA's page on NICo describes this cluster. NICo runs as a set of microservices, called the site controller, on a Kubernetes cluster in the data centre it manages, and the cluster needs at least three nodes for high availability. Its services include the API service that holds the state of every host, a DHCP server, a PXE service that serves iPXE scripts and OS images, a Hardware Health service that scrapes host and DPU BMCs over Redfish, and an authoritative DNS service. The slide draws them as API, DNS, Telemetry and PXE / iPXE / DHCP. Beside them it adds three grey F5 boxes: f5-downloader, f5-ingress and f5-cne-core. Each name is known from BNK. f5-downloader is the Pod that fetches the IP reputation database, as an F5BigCneDownloader object tells it, and pushes each copy to the TMM Pods. f5-cne-core is the namespace where BNK's core runs: the Cluster-Wide Controller for licensing and usage reports, the dSSM database and sentinel Pods, three of each in F5's install guide, and RabbitMQ for messages between controllers. f5-ingress is the role F5's 2.4 feature deck gives BNK in a zero-trust DPF deployment: the provider's fabric ingress at layers 4 to 7. Read together, the slide puts the shared F5 control pieces once in the management cluster and the data plane on every card.

The same cluster holds a box labelled Community LB, with F5's logo and one entry, nico-lb-provider-tmm. NVIDIA's page lists MetalLB, an open source load balancer, as a prerequisite that gives NICo's services load-balanced virtual IPs reachable from the underlay network. The slide's box reads as TMM taking that load-balancer role for the provider's own NICo endpoints. That reading is the slide's. NVIDIA's page names MetalLB only.

The third place is the Border Services Tier on the right. It is drawn as two hosts, each with its own DPU carrying HBN, f5-tmm and f5-coremod, and on each host three separate boxes: Tenant A L4-L7, Tenant B L4-L7 and Tenant C L4-L7. Each tenant gets its own instance of the layer 4 to 7 services, and each instance appears on both hosts. A tenant's border firewall or load balancer therefore has a second copy on a second machine, and tenant A's configuration never lives in the same instance as tenant B's. An arrow from the provider's network on the far right enters this tier. Chapter 16 of 30

Many hosts, one cluster: a /30 per link

Why every card's tmfifo address collides, and how a pool fixes it

RShim's network link, tmfifo_net0, is a point-to-point /30 between one host and its card. A /30 holds four addresses: the network address, two usable ones and the broadcast address. NVIDIA's BFB images preset the card's side to 192.168.100.2/30, and the host takes 192.168.100.1. In the owner's tooling the card joins Kubernetes over that link, with kubeadm join and the kubelet's --node-ip set to the tmfifo address. With one host that is fine.

With two hosts it breaks. gpu-node-1's card and gpu-node-2's card both come up as 192.168.100.2, and both hosts call themselves 192.168.100.1. With --node-ip set to that address, two nodes in one cluster would report the same InternalIP. The control-plane host cannot route to the card behind another host, because 192.168.100.0/30 is a local link on every host and points only at that host's own card. NVIDIA's own page says that with more than one card the default address must be changed. The Forge project's decision record ADR-424, accepted on 2026-07-23, settles it for one cluster across many hosts and cards.

The unit stays a /30 per host and card link, with the host on .1 and the card on .2 of its block. The blocks come from one pool for the whole cluster, for example 192.168.100.0/22. A /22 holds 1024 addresses, which is 256 blocks of four, so 256 links. In this lesson's world gpu-node-1's link takes 192.168.100.0/30, host .1 and card .2, and gpu-node-2's link takes 192.168.100.4/30, host .5 and card .6. Each allocation is stored with the card's record, so a second deployment hands out the same addresses again.

Routing is hub and spoke. One host runs the API server and etcd, here gpu-node-1. The API server is advertised on that host's management address, 10.0.1.11 in this world, and its certificate lists the management and tmfifo addresses. A card reaches it through its own host, which rewrites the source with NAT MASQUERADE. The other direction needs a route: the API server reaches a card's kubelet on port 10250 for logs and exec, so the control-plane host installs 192.168.100.6/32 via 10.0.1.12, and gpu-node-2 turns on ip_forward to pass the packet over its tmfifo link. Teardown runs in reverse: remove BNK, reset the cards and their routes and NAT, reset the worker hosts, reset the control-plane host, then release the blocks.

Chapter 17 of 30

Leaf and spine carry a number per tenant

VNI 10001 crosses the fabric and the spines never read it

Between the cards lies the fabric: leaf switches that servers plug into, and spine switches that join the leaves. It has two layers of routes. The underlay is plain IP. Every leaf and spine announces its loopback address with BGP, and in F5's EVPN design OcNOS in TMM's Pod announces TMM's VTEP address, so each tunnel endpoint can reach every other. The owner's nv deck calls loopback addressing a stable identity for routing. The overlay is BGP EVPN, which carries each tenant's prefixes with a route target and a VNI.

A tenant's packet crosses the fabric wrapped in VXLAN between two tunnel endpoints, VTEPs. The wrapping is four headers: outer Ethernet 14 bytes, outer IPv4 20, UDP 8 to port 4789, and VXLAN 8. The VXLAN header holds a flags byte with the I bit set to say a VNI is present, 24 reserved bits, the 24-bit VNI and 8 more reserved bits. 24 bits give 16,777,216 values, against 4,094 usable VLAN IDs. RFC 7348 recommends an outer UDP source port hashed from the inner packet, in the range 49152 to 65535, so that equal cost paths spread flows. It says the outer UDP checksum SHOULD be sent as zero, and receivers must accept zero.

A spine routes on the outer addresses only. The VNI selects the tenant's VRF at the far end. Tenant A uses VNI 10001 and tenant B 10002, as in the lesson Two tenants, one factory. The nv deck sums up the idea: compute nodes join the EVPN-VXLAN fabric directly, with no static VLANs and no separate routing tier. The lab guide stops short of this layer, and no BGP runs in it.

Chapter 18 of 30

How tenant A's prefix reaches the fabric

EVPN route type 5, route targets and the CRDs behind them

F5 documents how BNK joins an EVPN fabric. Each tenant gets a VRF, its own routing table inside TMM, and each VRF maps one to one to an L3 VNI. The L3 VNI carries routed traffic for the tenant, between subnets and to the outside. F5 requires the mapping to be the same on every VTEP, so if one maps 10001 to tenant-a, all must, and its page calls BGP EVPN the source of truth for that. The protocol itself does not check it. EVPN imports routes by route target, and RFC 8365 even allows VNIs that the receiving endpoint assigns. One L3 VNI everywhere is F5's and OcNOS's rule. F5 says isolation holds at three levels: a tenant's routes stay in its VRF, a VNI carries one tenant, and route targets decide which VRF imports which routes.

The route F5 documents is type 5, the IP prefix route of RFC 9136. Its NLRI holds a route distinguisher, an Ethernet Segment Identifier, an Ethernet tag, the prefix length and the prefix, such as a virtual server or SNAT address, a gateway address, and a label field that carries the L3 VNI. The address of the VTEP that sent it is the BGP next hop, outside the NLRI. It travels with address family 25 and subsequent address family 70, L2VPN EVPN. Extended communities ride along: the route target, the encapsulation type and the router's MAC.

A received route lands in the leaf's EVPN table. A VRF copies it in only if one of its import route targets matches. That step keeps tenant A's prefix out of tenant B's table.

Chapter 19 of 30

The resources and the router's MAC behind the route

BNK's CRDs, route distinguishers and symmetric IRB

Inside BNK the chain is declared with resources. A Vrf creates the tenant's routing domain, with strictIsolation true by default. A Vxlan sets the local endpoint: vni, port 4789, mtu with a default of 1430, the vrf, a subnet for tunnel addresses, and evpn: true, which only one Vxlan may carry. A GlobalRoutingConfig holds the fabric BGP neighbours, a RoutingConfig ties a tenant to its Vxlan, and a RoutingTemplate renders configuration for OcNOS, the routing software in TMM's Pod. OcNOS speaks BGP, and tmrouted passes what it learns into TMM's tables.

A route distinguisher and a route target do different jobs. The distinguisher is put in front of the prefix so that two tenants may use the same prefix and both routes survive in BGP. The target is a tag that decides import. The encapsulation extended community tells the receiver which tunnel to build, and VXLAN is tunnel type 8.

The router's MAC comes from RFC 9135, symmetric integrated routing and bridging. In that model both ends route: the sending VTEP routes into the tenant's L3 VNI, and the receiving VTEP routes out of it. The inner frame needs an Ethernet header, so the sender writes the receiver's router MAC as the inner destination MAC. F5 says OcNOS sets the router MAC on the VRF to the MAC of the VNI interface. A type 2 route in this model can carry two labels, the subnet's L2 VNI and the tenant's L3 VNI.

The owner's clab lab used a second placement: the leaf is the VTEP, and TMM reaches each tenant over its own VLAN leg, 101 for tenant A, 102 for B, with BGP in every tenant VRF.

Chapter 20 of 30

From the leaf through the card to the Pod

Four decisions, all made before the host sees a byte

The wrapped packet arrives on the card's fabric port. The first decision is the tunnel's: the outer header is removed and VNI 10001 selects tenant A's VRF. F5's EVPN page describes exactly this order for inbound traffic: TMM on the destination removes the VXLAN header, looks up the VRF and forwards.

The second decision is TMM's. The packet enters on interface 1.1, and in tenant A's table the address 203.0.113.80 belongs to tenant A's Gateway. The lab guide's ingress example has the same shape: a GatewayClass whose controllerName is f5.com/f5-gateway-controller, a Gateway with an address of type IPAddress and a TCP listener, and an L4Route that names a Service as its backend. The SPKInstance switches AFM, F5's network firewall, on, but the lab applies no firewall policy, so where a policy would run in this order is not shown.

The third decision picks a Pod and a way to it. TMM chooses qwen3-6f7d9c8b4-m9q4t and sends the packet out of interface 1.2. Its source is TMM's own internal self IP 10.0.20.201, which the lab guide calls SNAT automap: the client's address is replaced by TMM's own address, and no SNAT pool is used. The ephemeral port, 42776 here, is illustrative. F5's architecture page names this leg: TMM reaches the application Pods through the internal VLAN and the host's virtual functions. The fourth decision is the bridge's. sf_internal forwards the frame to pf1vf0, and the host receives it on its VF. The host's kernel delivers it to the Pod. Every decision so far was made on the card, and the host never learns the caller's address.

Chapter 21 of 30

VNI 100 and VNI 200: the tunnels to the host

A second VXLAN, one PCIe slot long, built by F5SPKVxlan

The lab guide has VNIs of its own, and they sit on the other side of the card. Each tenant namespace gets an F5SPKVxlan: red with key 100, blue with key 200, both on UDP port 4789. key is the VNI. F5's 2.0 reference describes the resource as a tunnel between TMM and the Kubernetes worker nodes. TMM builds its end from the resource, and a host side component called CSRC, Calico Static Route Configuration, builds the other end on each host.

The tunnel's underlay is the internal network, with fixed addresses and no routing protocol. local_ips lists TMM's end: the self IPs of the internal F5SPKVlan, one per TMM, so 10.0.20.201 and 10.0.20.202 here. remote_interface_name names the host device the tunnel rides on, the VF on port 1. Each remote_nodes entry is one host: node_name as Kubernetes knows it, node_ip its address on that VF, and three values for the overlay, which is the network inside the tunnel. peer_mac is the MAC address of the VXLAN device on the host, and peerip_v4 and peerip_v6 are its addresses. selfip_v4s and selfip_v6s give each TMM its overlay address, with prefixlen_v4 24 and prefixlen_v6 112. red's overlay in this lesson is 172.16.100.0/24 and blue's is 172.16.200.0/24.

The repository's comments explain two choices. remote_nodes lists hosts only, because tenant workloads never run on the DPU nodes. And the VF name must be changed everywhere to the real one. F5's 2.0 page adds rules: peer and self addresses in one subnet, unique peer addresses and MACs per tunnel, both peer IP families set or no static route is created, and no updates. A change means delete and apply again.

Chapter 22 of 30

F5SPKEgress steers a namespace into its tunnel

pseudoCNIConfig, CSRC's policy rules and the SNAT pool

A tunnel alone carries nothing. The F5SPKEgress resource decides which Pods use it. The lab guide applies two, red-egress and blue-egress, with apiVersion k8s.f5net.com/v3. Each sets dualStackEnabled true, snatType SRC_TRANS_SNATPOOL and egressSnatpool, red-snat or blue-snat. Its pseudoCNIConfig names the namespaces it covers, red, the Pod's interface appPodInterface eth0, the host's tunnel device appNodeInterface red, and the TMM tunnel vlanName red.

F5 calls this mechanism pseudo CNI. A controller reads the egress resource, works out which TMM serves which host, and sends those mappings over gRPC to CSRC. CSRC is a privileged DaemonSet in the host's network namespace, listening on port 8751 by default. It writes policy rules and routes on each host that runs Pods of the namespace, so packets from those Pods leave through the tunnel. F5 says the TMM on the DPU local to the host gets the highest priority. Traffic to other Pods and to the cluster's own networks is not steered. The SPKInfrastructure's egress section names two of the cluster's ranges, the internal subnet and the Pod pool 10.244.0.0/16, and the lab guide does not explain them further.

F5SPKSnatpool supplies the outside address. addressList is a list of lists: one inner list per TMM, applied in replica order. In the lab guide each inner list holds four addresses, IPv4 and IPv6 on the external network and on the internal network, and TMM picks the one closest to the next hop for the destination. snatType has two other values. SRC_TRANS_AUTOMAP uses TMM's own external self IP, and SRC_TRANS_NONE keeps the Pod's address and needs secureSPKIngressPort. Felix must also accept the tunnel, so the lab patches FelixConfiguration default with externalNodesList set to TMM's internal self IPs.

Chapter 23 of 30

Out through VNI 100, byte by byte

qwen3-6f7d9c8b4-m9q4t fetches its weights from tenant A's store

qwen3-6f7d9c8b4-m9q4t needs its weights, 65.5 GB in BF16 for 32.8 billion parameters, and tenant A keeps them in an object store outside the factory at 192.0.2.50. The store accepts one address only, 203.0.113.201. Here is the first packet of that download, hop by hop.

vLLM in qwen3-6f7d9c8b4-m9q4t opens a TCP connection to 192.0.2.50:443 from port 38412. The SYN leaves eth0 as 74 bytes: Ethernet 14, IPv4 20, TCP with options 40. The host's kernel matches CSRC's rule for the Pod's source address and routes the packet into the device red.

The device red wraps it with VNI 100. The outer IPv4 header runs from the VF's address 10.0.20.12 to TMM's internal self IP 10.0.20.201, UDP to port 4789. The inner Ethernet header carries the host device's MAC, peer_mac, as its source. The frame is now 124 bytes. It leaves the VF, crosses the PCIe slot, arrives on pf1vf0, and the bridge sf_internal delivers it to TMM's SF on port 1, interface 1.2. No leaf switch is involved.

TMM checks the outer destination and port, sees VNI 100, and knows the packet came from tunnel red, so from namespace red. It removes 50 bytes. The egress listener of red-egress takes the connection, and the source becomes 203.0.113.201 from red-snat, with a port TMM picks, 20114 here. The new SYN is 74 bytes and leaves interface 1.1 through en3f0pf0sf1 and p0. In the lab guide it goes out untagged. In an EVPN fabric with TMM as the VTEP, TMM wraps it once more with tenant A's L3 VNI 10001, and it crosses the fabric as 124 bytes again.

Chapter 24 of 30

The answer comes back through the tunnel

The store's SYN-ACK, reversed by TMM and wrapped with VNI 100

The store answers to the only address it saw, 203.0.113.201 port 20114. Routing brings that address to the card that owns it. In the lab guide the external network is one flat subnet, and the next hop finds TMM's MAC by ARP. In an EVPN fabric the type 5 route for 203.0.113.201 in tenant A's VRF points at the DPU's VTEP, so the leaf wraps the SYN-ACK with VNI 10001 and sends it to 10.0.0.5. That is one reason each TMM needs its own SNAT address: an answer has to come back to the TMM that holds the connection. F5's shared SNAT mode exists for the opposite case, with a flow forwarding VLAN between TMMs so that an answer which reaches the wrong TMM is passed to the right one.

TMM finds the connection in its table. It writes back the original destination, 10.244.2.22 port 38412, and keeps the store as the source. The connection belongs to tunnel red, so TMM wraps the answer with VNI 100, from its own underlay address 10.0.20.201 to gpu-node-2's node_ip 10.0.20.12, and sends it out of interface 1.2. The bridge sf_internal hands it to pf1vf0 and across the slot to the VF.

On the host, Felix's rules check the outer source against externalNodesList before the VXLAN device may accept it. The device red removes 50 bytes and passes a 74-byte SYN-ACK to the Pod. vLLM in qwen3-6f7d9c8b4-m9q4t sees an answer from 192.0.2.50 and never learns that its address was replaced. The connection is now open, and the 65.5 GB of weights follow the same two tunnels in the same order.

Chapter 25 of 30

Three VXLANs on one host

Calico's VNI 4096, the namespace tunnels and the fabric VNI, and their MTUs

A host in this design can meet three VXLANs. The first is Calico's own. The install script sets up Calico through the Tigera operator with one IP pool, 10.244.0.0/16, blockSize 26, encapsulation VXLANCrossSubnet, natOutgoing Enabled, bgp Disabled, and node addresses detected only inside the management network. With VXLAN pools Felix programs the routes to other nodes' blocks itself, so BGP is not needed. Calico's tunnel uses the FelixConfiguration defaults: VNI 4096 on UDP port 4789, on a device called vxlan.calico. CrossSubnet means Calico wraps a Pod packet only when the two nodes are on different IP subnets. Between gpu-node-1 and gpu-node-2 on one management subnet, the Pod packet travels unwrapped.

The second is the namespace tunnel, VNI 100 or 200, on the VF over the internal network, built by TMM and CSRC. The third is the fabric's L3 VNI, 10001 or 10002, which the host never sees. All three use port 4789 and the same 8-byte header. Only the VNI and the device tell them apart.

Felix guards the host against tunnels it did not build. Its externalNodesList is a list of addresses of non-Calico nodes from which VXLAN and IP in IP traffic is accepted. By default such traffic is blocked to reduce the attack surface. That is why TMM's internal self IPs must be listed.

Each wrapping costs 50 bytes of IP MTU over IPv4: outer IPv4 20, UDP 8, VXLAN 8 and the inner Ethernet header 14. Calico's tunnel rides the management network, so its MTU follows that network, not the card's ports. A namespace tunnel on a 1500-byte VF carries inner packets of at most 1450. The next chapter works through these numbers.

Chapter 26 of 30

When a wrapped packet does not fit

MTU, MSS and the rule that VTEPs never fragment

Three MTUs meet in this design, and the lab sets only some of them. The Ansible inventory, a separate kubespray build, sets dpu_mtu 9000 on the card's p0, p1 and bond0 and calico_mtu 8900. Its Calico file leaves kubespray's defaults commented out as backend vxlan and mode Always, which read as defaults would wrap every Pod packet. The documented install-host.sh build sets no MTU at all. Calico rides the management network, so 8900 says nothing about the card's ports.

RFC 7348 sets the rules for a packet that does not fit. A VTEP must not fragment VXLAN packets. A router in the middle may fragment them, and the receiving VTEP may silently discard the fragments. So the underlay MTU has to be raised to carry the wrapped packet. Over IPv4 the wrapping costs 50 bytes and over IPv6 it costs 70. An 802.1Q tag on the outer frame adds 4 bytes on the wire and nothing to the IP MTU.

On a VF left at 1500, device red carries inner IP packets up to 1450. TCP over it uses an MSS of 1410, which is 1450 minus 20 for IPv4 and 20 for TCP. With 12 bytes of timestamps each segment carries 1398 bytes of data. If the Pod's own interface is 1500, the Pod builds packets that red cannot carry whole. The host answers with ICMP fragmentation needed and relies on path MTU discovery. If that message is lost, the connection stalls on its first large segment. F5's current Vxlan and egress tunnel default of 1430 is 1500 minus 70, so it fits an IPv6 underlay too.

Chapter 27 of 30

A bridge is not yet a wall

What the lab's bridges allow, and what a provider must add

The chapter on TMM's ports showed what the lab's bridges hold. sf_internal joins p1, TMM's SF and the host's pf1vf0. br-lag joins bond0, pf0hpf and both TMM SFs. Neither file adds a flow rule, so Open vSwitch runs its default NORMAL action: it learns MAC addresses and forwards like an ordinary switch. Root on the host can address any machine on the uplink's segment directly. TMM, its VRF and its policy are never in that path.

A representor only tells the card where a frame came from. It becomes a wall when the switch acts on that knowledge. A provider has two ways to do that. One is a bridge whose only ports are the host's representor and TMM's SF, with no uplink on it. The other is explicit OpenFlow rules in place of NORMAL, keyed to the representor, so that frames from pf1vf0 go to TMM's SF and nowhere else. The owner's decks place NVIDIA's HBN on the card beside BNK, and it could own that forwarding instead. The decks do not say how.

The rules have to cover every function the host can use. Root sees PF 0 and PF 1, with representors pf0hpf and pf1hpf, and can create VFs whose representors appear as pfXvfN. Each needs a rule from the moment it exists, so that isolation fails closed. The same rules can pin each representor to its own MAC and IP addresses against spoofing, and meters can cap what a host may send, so one tenant cannot flood the shared fabric. None of this is in the lab guide, which runs on trusted hosts.

Chapter 28 of 30

What the tenant can reach

And why VNI 100 is not the wall

VNI 100 and 200 are added by the host. They keep two namespaces apart on a host the provider runs. There CSRC, Felix and the kernel are the provider's software. On a rented host they are the tenant's. Root could remove CSRC's rules, add a device with any VNI, and write any address into a frame, so these numbers cannot be the boundary there.

The boundary has to be the host's port on the card. DPU mode already sends every host frame through a representor into a switch the Arm side controls, and zero trust stops the host from taking management back or reflashing the card. F5 documents a vrf field on F5SPKVlan, and one on the current egress tunnel, pseudoCNIConfig.vxlan.vrf, that place TMM's side in one tenant's routing domain. F5's Vrf turns on strict isolation by default. A design that ties every host representor to TMM alone and puts that VLAN or tunnel in tenant A's VRF, gives the host tenant A's network, the services published into it, and no route to tenant B. That combination is this lesson's inference. The owner's clab lab came close: its egress tunnel worked only once its underlay was a tenant VLAN with internal: true in the tenant's VRF.

The grid deck asks for isolation that fails closed. Zero-trust mode removes the host's RShim console, counters, tracer, port ownership and firmware flash. The provider must design the rest: no host port on the BMC network, no route to the API of the cluster that configures the card, and no address of the Arm OS that the host can reach through the bridges.

Chapter 29 of 30

What an operator sees when it breaks

Status lines, error messages and the failures the owner hit

Every resource in this lesson reports itself the same way. kubectl get f5-spk-vlan, f5-spk-vxlan and f5-spk-snatpools show READY True and the message CR config sent to all grpc endpoints once every TMM has the configuration. That message means the controller delivered it. It does not prove that packets flow.

Some failures are documented by F5. CSRC runs in the host's network namespace and listens on port 8751. If another program holds that port, CSRC logs ERROR: Failed to listen: listen tcp :8751: bind: address already in use, and no host gets its rules. The fix is to move the port in two places, the Service f5-csrc-grpc-svc and PSEUDOCNI_GRPC_PORT in the DaemonSet. F5SPKVxlan cannot be updated, and F5 recommends deleting and applying F5SPKEgress again for any change. F5's current egress page also asks for one egress resource per namespace and one VLAN per egress resource, and says one VLAN cannot be named by two egress resources.

To see which SNAT address a TMM holds, run tmctl -w 120 -d blade pool_member_stat -s pool_name,addr in TMM's debug container. The address appears as an IPv4 mapped IPv6 value in hex. For red-snat's first address, 203.0.113.201, the four IPv4 bytes are cb 00 71 c9. Inside the same container, tcpdump -nnei 0.0 shows what TMM really sends and receives on all its interfaces, and tmctl -d blade -i virtual_server_stat shows whether a virtual server counts any connections at all.

Chapter 30 of 30

Failures the owner hit in the lab

Lost tunnels, a deleted neighbour and checksums left to hardware

Some failures come from the owner's labs, on specific builds. After a TMM restart the egress tunnel was not rebuilt by itself, and the fix was to apply the egress again and restart CSRC. Deleting and recreating an egress on a running cluster was worse. The new object counted its Pods from zero, at zero the controller sent CSRC a delete with an empty tunnel name, and CSRC removed another tenant's tunnel device on every node. The lab then kept its egress objects and switched the firewall policy they name.

Separate egress resources with separate SNAT pools did not work together on one build. The lab guide itself applies exactly that, red-egress with red-snat and blue-egress with blue-snat, and F5's note asks for one egress resource per namespace. The two fit if the failure belonged to that build or to how its resources were combined. The lab notes do not settle which, so test it on the release in use.

TMM dropped SYNs whose checksum the sender had left to hardware. With checksum offload, the kernel leaves the TCP checksum for the network device to fill in. Through a VXLAN device that inner checksum can stay unfilled, and the packet reaches TMM with a wrong one. F5's 2.0.0 page states that TCP offloading with VXLAN for egress traffic is not supported on that release.

Each of these looked like silence: no error, no counter, just no connection. The checks that found them were CSRC's log, tcpdump in TMM's debug container and TMM's virtual server statistics.

What to keep

Two tunnels, two questions

Zero-trust mode is DPU mode with up to five host management rights restricted: port ownership, counters, tracer, RShim and firmware flash, which also closes the lab guide's own install path over RShim. On the card TMM owns two scalable functions, 1.1 toward the fabric and 1.2 toward the host. Two bridges join an uplink, TMM and the host's VF, and as the lab builds them they do not force host traffic through TMM. F5SPKVlan gives TMM its addresses, one per TMM. Across the leaf and spine fabric a VXLAN number says which tenant a packet belongs to, EVPN type 5 routes carry it, and spines forward it without reading it. Between host and card the lab guide's VNI 100 and 200, made by F5SPKVxlan, steered by F5SPKEgress and CSRC and translated with F5SPKSnatpool, say which namespace a Pod's packet came from. Calico's VNI 4096 is a third tunnel that this traffic never uses. Every wrapping costs the same 50 bytes around a 74-byte SYN over IPv4, and 70 over IPv6. This lesson infers that the wall for a rented host can be its ports on the card, once the provider's bridges or flow rules tie every host-facing representor to TMM alone and that side of TMM sits in one tenant's VRF.
