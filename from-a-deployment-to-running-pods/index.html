Kubernetes underneath

From a Deployment to running Pods

One object goes in. Five components each do one thing about it

You apply a Deployment called qwen3 that asks for two model servers. About three minutes later two Pods answer on port 8000. In between, nothing was ordered to do anything. The API server checked the request and stored one object. A controller saw that object and stored a second one. Another controller saw the second and stored two Pods. The scheduler gave each Pod a node, and the kubelet on each node started it. Every step is a component reading an object and writing another. This lesson follows the chain down, follows the status back up and reads it the way an operator does. Then it deletes a Pod by hand to show why it comes back, runs into a GPU quota, scales back down to show which Pod a ReplicaSet gives up, and finally deletes the Deployment to show how owners take their dependents with them.

Chapter 1 of 18

Who is asking

Authentication turns a certificate or a token into a user name and groups

kubectl turns the file into one HTTPS request to the API server. Three stages look at it in a fixed order: authentication, authorization and admission. Authentication works out who is asking. The API server can have several authenticators switched on at once, such as client certificates, bearer tokens and OpenID Connect. It tries them in turn, and the first one that succeeds decides. The rest are not asked.

With a client certificate, the user name is the certificate's common name and the groups are its organization fields. Here the certificate says CN=mira and O=ml-platform, so the request comes from user mira in group ml-platform. The API server adds the group system:authenticated to every request that passed authentication. Kubernetes keeps no object for a human user. The name is whatever the credential says, and it only matters because rules refer to it.

A request that cannot be authenticated gets 401 Unauthorized. There is one exception. When anonymous access is turned on, a request with no credentials at all is let through as the user system:anonymous in the group system:unauthenticated, and it is then up to authorization to refuse it. A request with credentials that are wrong, such as an expired certificate, is still refused with 401. The result of this stage is a user name, a list of groups and sometimes extra fields. The next stage reads only those, never the certificate itself.

Chapter 2 of 18

May this user do this

Authorizers are asked in order, and silence means no

Authorization asks whether this user may do this: the verb create, on the resource deployments, in the API group apps, in the namespace inference. The API server is started with a list of authorization modes, for example --authorization-mode=Node,RBAC,Webhook. The available modes are Node, RBAC, ABAC, Webhook, AlwaysAllow and AlwaysDeny. The API server asks the ones you turned on in the order you list them in --authorization-mode, or in the authorization configuration file. In this example that is Node first, then RBAC, then Webhook. Each one can allow, deny or have no opinion. The first to allow or deny decides. If every one has no opinion, the request is refused with 403 Forbidden.

The Node authorizer only judges requests from kubelets, whose user names have the form system:node:<name>. For mira it has no opinion, so RBAC is asked next. RBAC, role-based access control, looks for RoleBindings in the namespace and ClusterRoleBindings that name this user or one of its groups, and for a rule in the bound Role that lists the verb and the resource. In this cluster a RoleBinding in inference gives the group ml-platform a Role whose rules include create on deployments in the group apps. That allows the request.

There is one group to know about. system:masters is built in and grants unrestricted access. A certificate with O=system:masters is allowed everything, whatever the RBAC rules say, which is why such certificates are kept to a few administrators. Anyone can test a rule before using it. kubectl auth can-i create deployments --namespace inference answers yes or no for the current user, and an administrator can add --as=mira to ask on someone's behalf.

Chapter 3 of 18

Is the object acceptable

Admission runs plugins and webhooks, first mutating, then validating

Admission comes last and is the only stage that reads the object itself. It runs in two phases. Mutating plugins may change the object. Validating plugins may only accept or reject it. One rejection in either phase ends the request. Some plugins are compiled into the API server. In release 1.37 the ones on by default include NamespaceLifecycle, LimitRanger, ServiceAccount, DefaultStorageClass, DefaultTolerationSeconds, MutatingAdmissionWebhook, ValidatingAdmissionWebhook, ResourceQuota, Priority, TaintNodesByCondition, RuntimeClass, DefaultIngressClass and PodSecurity. Two more run policies written as API objects inside the API server: MutatingAdmissionPolicy and ValidatingAdmissionPolicy, which check or change an object with CEL expressions and need no webhook. The documented default set is completed by plugins for certificates (CertificateApproval, CertificateSigning, CertificateSubjectRestriction) and storage (PersistentVolumeClaimResize, StorageObjectInUseProtection), 20 in all. The order you list them in --enable-admission-plugins does not matter. The API server runs them in its own fixed order.

Two of those plugins call out to programs the cluster's owners add. In this cluster the policy engine Kyverno is registered as an admission webhook. The API server sends it an AdmissionReview with the object, the operation and the user, and waits for an answer. A webhook has 10 seconds by default, and the value can be set from 1 to 30. Its failurePolicy decides what happens if it does not answer. Fail, the default, rejects the request. Ignore lets it through. Validating webhooks are called in parallel, and any one rejection fails the request. A mutating webhook is not called again after a later change unless its reinvocationPolicy is IfNeeded. The default is Never.

Admission can also have side effects. ResourceQuota is the usual example: it counts usage as it admits, and because a request may still fail after admission, a controller recounts later. All of this runs again for every Pod created later. The Deployment is admitted now, and a quota on GPUs can still reject its Pods, as a later chapter shows.

Chapter 4 of 18

A record, and nothing running

The API server fills in defaults, stores the object and answers

The Deployment is now written to etcd, the database that only the API server talks to. Fields you left out have received their defaults on the way. The rollout strategy is RollingUpdate, with maxSurge and maxUnavailable both at 25%. maxSurge is rounded up and maxUnavailable rounded down, so for two replicas they come out as 1 and 0. revisionHistoryLimit is 10 and progressDeadlineSeconds is 600. minReadySeconds is 0, which means a Pod counts as available the moment it is ready. Had you left out replicas, it would have been 1.

The API server also sets the fields a client cannot choose: a UID, a creation time, a resourceVersion and a generation of 1. The generation counts changes to the spec. It goes up when you change the replicas or the template, and stays the same when only the status changes. The selector is fixed from now on. A Deployment's spec.selector cannot be changed after it is created, so app: qwen3 is what this Deployment will always use to find its Pods.

Then the API server answers kubectl with 201 Created, and kubectl exits. At this moment the cluster holds one stored description of what you want. No ReplicaSet exists, no Pod exists and no GPU is in use. The API server's part is finished. It will not create anything from this object. Others have to notice it, and they do so by watching.

Chapter 5 of 18

The Deployment controller makes a ReplicaSet

One ReplicaSet for each version of the Pod template

Inside kube-controller-manager runs the Deployment controller. It watches Deployments, and the new one reaches it as an event. Its answer is to create a ReplicaSet, an object whose only job is to keep a given number of identical Pods. The controller computes a hash of the Deployment's Pod template and uses it three times. The ReplicaSet is named after the Deployment and the hash. The label pod-template-hash, with the hash as its value, is added to the ReplicaSet's selector and to the labels of its Pod template. A later change to the template gives a different hash and so a second ReplicaSet, and a rollout is the new one growing while the old one shrinks. The label keeps the two from claiming each other's Pods.

The hash is a 32-bit FNV-1a hash of the Pod template, printed as a decimal number and then re-encoded with a reduced alphabet so that no real words appear in names. If the Deployment's status.collisionCount is set, its value is fed into the hash as well: the controller writes the count into the hasher as 8 more bytes, the number in little-endian order, so each new count gives a different hash. That field exists for a rare case. If a ReplicaSet with the computed name already exists but has a different template, the controller raises collisionCount, logs Found a hash collision for deployment, and tries again with the new hash.

The controller also numbers revisions. The new ReplicaSet gets the annotation deployment.kubernetes.io/revision with the highest old revision plus one, here 1, and the Deployment gets the same annotation. kubectl rollout history and kubectl rollout undo --to-revision read these numbers. The controller runs 5 workers by default, set by --concurrent-deployment-syncs. A Deployment whose sync keeps failing is retried 15 times and then dropped from the queue until its next change.

Chapter 6 of 18

The ReplicaSet controller makes two Pods

It counts what it owns and creates what is missing

A second controller in the same program watches ReplicaSets and Pods. It sees a ReplicaSet that wants two Pods and finds none that match its selector. So it creates two, each a copy of the ReplicaSet's Pod template. It does not choose their names. It sets generateName to the ReplicaSet's name and a hyphen, and the API server appends five random characters. The characters come from an alphabet of 27: bcdfghjklmnpqrstvwxz2456789. It has no vowels and no 0, 1 or 3, so no generated name spells a word. The name generator keeps every generated name within 63 characters, the length its source calls a standard Kubernetes name, so the prefix is cut to 58 before the suffix is added. The name of a Pod may itself be longer, up to 253 characters as a DNS subdomain. The 63 is a limit of the generator. If the generated name is already taken, the API server tries again, up to 8 attempts in all, since the RetryGenerateName feature became stable in 1.32.

The controller creates Pods in growing batches: 1, then 2, then 4, and so on, at most 500 in one pass. The reason is quota. If the first Pod is refused, the rest would be refused too, and sending them all would only produce errors. Here the first batch is one Pod. It succeeds, so the next batch may be two, but only one is left to create.

Each Pod gets an entry in metadata.ownerReferences that points at the ReplicaSet by name and UID. That entry is how the ReplicaSet knows which Pods are its own, and it is what lets the garbage collector delete the Pods when their owner is deleted. After sending the creates, the controller records that it expects two Pods to appear on its watch. Until they do, or until 5 minutes pass, it does not count again, so a cache that is a moment behind cannot make it create the same Pods twice. Both Pods are stored with an empty spec.nodeName and the phase Pending.

Chapter 7 of 18

A node for each Pod

The scheduler writes a name into the Pod. It starts nothing

The scheduler watches Pods that have not finished, and acts on the ones with no node. Two arrive. For each it first rules out the nodes that cannot run it, and here that means nodes without a free GPU. GPUs are counted as nvidia.com/gpu, a resource the NVIDIA device plugin advertises on each node, four per node here. Then it scores the nodes that are left and takes the best. When the cluster sets no rule of its own, the scoring leans towards spreading Pods over nodes, so the second Pod goes to the other node. This is a preference and no guarantee.

The scheduler records each choice by creating a Binding, a small object posted to the Pod's binding subresource, which fills in the Pod's spec.nodeName. The Pod's condition PodScheduled becomes True, and the scheduler records an event with reason Scheduled. It does not contact the node. A Pod that fits nowhere stays Pending, and the reason is written into its status and into a FailedScheduling event.

The lesson on scheduling, A node for every Pod, takes this step apart: the queue, the filter and score plugins, and preemption. What matters here is where the step sits in the chain. Before it, the Pod exists and nothing runs. After it, the Pod names a node and still nothing runs. The only change is one field in one object, and the kubelet on that node is the only component that cares.

Chapter 8 of 18

The kubelet starts what it was given

It hears of the Pod through its own watch

Each node runs a kubelet, and each kubelet watches only the Pods whose spec.nodeName is its own node. The Binding changed that field, so the Pod now appears on the watch of the kubelet on gpu-node-1. From here the work is local. The kubelet asks containerd, the container runtime, through the Container Runtime Interface, a gRPC API. First it asks for a sandbox, which is the Pod's own network environment with its IP address. When that is ready, the kubelet sets the condition PodReadyToStartContainers to True. Image pulls and container creation only happen after that.

Next comes the image. Whether the kubelet pulls it depends on imagePullPolicy. Its default is set when the object is created: Always when the image has the tag latest or no tag at all, and IfNotPresent for any other tag or a digest. The template here names vllm/vllm-openai with no tag, so the default is Always. With Always the kubelet still asks the registry, but it only downloads layers it does not have. A pull that fails is retried with a growing delay up to 300 seconds, and the Pod shows ImagePullBackOff meanwhile.

Then the kubelet creates the container, with one GPU made visible inside, and starts it. The process is now running, and the Pod's phase becomes Running. A model server is not useful yet at that point. vLLM first has to read 34.3 GB of weights, the size of the FP8 build Qwen3-32B-FP8, onto the GPU. If the process crashes, the kubelet restarts it after 10, 20, 40 seconds and so on, at most 300 seconds, and resets that delay once a container has run for 10 minutes. CrashLoopBackOff is the name kubectl shows for that waiting. It is the container's waiting reason, and the Pod's phase stays Running.

Chapter 9 of 18

Status travels back up

Pod, then ReplicaSet, then Deployment, each written by its own keeper

What you asked for travelled down through spec fields. What happened travels up through status fields, by the same watching. The kubelet writes the Pod's status: Running after about three seconds, and the conditions ContainersReady and Ready once the readiness check passes, three minutes later. The ReplicaSet controller watches Pods, counts the ready ones and writes the count into the ReplicaSet's status. The Deployment controller watches ReplicaSets, adds their counts up and writes the Deployment's status and its conditions.

The Deployment's status holds several counts that are easy to confuse. replicas is every Pod its ReplicaSets own that is not terminating. updatedReplicas is the ones made from the current template. readyReplicas is the ones whose Ready condition is True. availableReplicas is the ones that have been ready for at least minReadySeconds, which is 0 here, so ready and available are the same. unavailableReplicas is what is still missing. From 1.35 a further count, terminatingReplicas, is on by default and counts Pods that are shutting down.

Each status also records observedGeneration, the generation of the spec it was computed from. If that is lower than metadata.generation, the controller has not yet seen your latest change, and nothing else in the status is about that change yet. The Available condition follows one rule: True when availableReplicas is at least spec.replicas minus maxUnavailable. Here that is 2 minus 0, so both Pods must be available. kubectl rollout status only reads these fields.

Chapter 10 of 18

Reading a rollout, and its deadline

kubectl rollout status prints what the status fields say

kubectl rollout status deployment/qwen3 watches the Deployment and prints one line each time its status changes. It first compares metadata.generation with status.observedGeneration. While the controller has not yet seen the latest spec, it prints Waiting for deployment spec update to be observed. Then it prints, as each count changes, lines such as Waiting for deployment "qwen3" rollout to finish: 0 of 2 updated replicas are available. When every Pod is updated and available, it prints deployment "qwen3" successfully rolled out and exits with code 0.

The Deployment controller also keeps a clock. progressDeadlineSeconds, 600 by default, is the time a rollout may go without progress before the controller marks it as stalled. Progress means a ReplicaSet being created or scaled, or a new Pod becoming ready or available. If nothing like that happens for 600 seconds, the Progressing condition turns False with reason ProgressDeadlineExceeded and the message ReplicaSet "qwen3-6f7d9c8b4" has timed out progressing. kubectl rollout status then prints deployment "qwen3" exceeded its progress deadline and exits with code 1. Kubernetes takes no other action. It does not roll back. The documentation lists the usual causes: insufficient quota, failing readiness probes, image pull errors, missing permissions, limit ranges and a misconfigured application.

The owner's material on serving large models says it plainly: large model replicas start very slowly. Here a model server needs about 180 seconds from start to ready, well inside 600. A larger model, a first image pull of many gigabytes or weights fetched over a slow link can take longer than ten minutes. Such a Deployment needs a larger progressDeadlineSeconds, or every first rollout is reported as failed while it is in fact still loading.

Chapter 11 of 18

What kubectl describe shows

Events from each component, in the order they happened

Every component in the chain leaves events behind. An event is a small object that names the object it is about, a type of Normal or Warning, a short reason in one word and a message. kubectl describe pod prints the ones about that Pod at the bottom of its output, oldest first. For qwen3-6f7d9c8b4-x7k2p the list reads like a summary of this lesson. The scheduler, reporting as default-scheduler, wrote Scheduled with the message Successfully assigned inference/qwen3-6f7d9c8b4-x7k2p to gpu-node-1. The kubelet wrote Pulling, Pulled, Created and Started.

The two image events tell you about the pull. The image has no tag, so its pull policy is Always and the kubelet asks the registry every time. It writes Pulling with Pulling image "vllm/vllm-openai", and afterwards Pulled with the time taken, the time including waiting for other pulls, and the image size in bytes. When every layer is already on the node, as here, the time is short. With imagePullPolicy IfNotPresent and the image on the node, the kubelet writes only Pulled. Since 1.35 the gate KubeletEnsureSecretPulledImages is beta and on, so the kubelet first checks that this Pod may use the image it already has. Under the default policy, NeverVerifyPreloadedImages, an image that the kubelet pulled before with the same credentials, or with none as for the public vllm/vllm-openai, is confirmed from the kubelet's own records without asking the registry. The message is then Container image "vllm/vllm-openai" already present on machine and can be accessed by the pod. If the Pod brings credentials that have never pulled that image, the kubelet pulls it again to prove them, and Pulling appears. With the gate off, the message is the older Container image "vllm/vllm-openai" already present on machine. On a GPU node these lines show exactly how much of a slow start was the image and how much the model.

The Warning reasons are the ones to look for when a Pod does not come up. Failed and BackOff cover image pulls that do not work. ErrImageNeverPull means imagePullPolicy is Never and the image is missing. FailedCreatePodSandBox and NetworkNotReady point at the network plugin. FailedMount points at a volume. Unhealthy means a probe failed, which during the three minutes of loading can be expected, depending on how the readiness probe is set. Killing means the kubelet is stopping a container. Events on the ReplicaSet and the Deployment are separate. A Pod that was never created leaves no Pod to describe, and its error is only on the ReplicaSet.

Chapter 12 of 18

Delete a Pod, and a new one appears

To reconcile is to compare what is wanted with what exists, and close the gap

Ten minutes in, you delete the Pod on gpu-node-1 by hand. The API server does not remove it at once. It marks it with a deletionTimestamp and a grace period of 30 seconds, and the kubelet begins to stop the container. The ReplicaSet controller receives this change like any other. It does what it always does. It counts its Pods, leaving out any that are being deleted, finds one and wants two. So it creates one.

The rule for counting is exact. A Pod is active, and counts, when its phase is neither Succeeded nor Failed and it has no deletionTimestamp. So a Pod that failed, for example because the kubelet evicted it, is replaced in the same way as a deleted one. This is what reconcile means: compare the wanted state with the state that exists, and act on the difference. The controller never learns who deleted the Pod or why. It does not need to.

The replacement does not wait for the old Pod to be gone. For a short time both exist: one shutting down, one starting. For a model server that matters, because the new Pod needs a GPU. On gpu-node-1 three GPUs were free before the delete, so the new Pod fits even while the old one still holds its GPU. On a full node it would wait. The new Pod has a new name, a new UID and a new address, and it has to load the weights from the start. Nothing it inherits from the old Pod helps it start faster.

Chapter 13 of 18

The old Pod shuts down

TERM, a grace period, then KILL, and the address leaves the Service first

While the replacement is being scheduled, the old Pod goes through its shutdown on gpu-node-1. The kubelet hears of the deletionTimestamp on its watch. If the container had a preStop hook, the kubelet would run it first. Then it asks containerd to stop the container, with a timeout equal to what is left of the grace period. The runtime sends the stop signal to the main process of each container. That is TERM unless the image names another one with STOPSIGNAL. If a preStop hook is still running when the grace period ends, the kubelet grants a one-off extension of 2 seconds. When time is up, the runtime sends KILL to anything still running.

At the same moment the Pod leaves the Service. The EndpointSlice controller sees the deletionTimestamp and marks the address 10.244.1.21 with ready: false and terminating: true. A separate condition, serving, keeps saying whether the Pod still passes its readiness check, so a load balancer that drains connections can tell a Pod that is ending but still answering from one that is gone. New requests stop arriving through the gateway, while requests already in flight have until the grace period ends. For a model server streaming a long answer, 30 seconds may be too short.

Here vLLM stops its server and exits after 12 seconds, illustrative. The kubelet then removes the Pod object by deleting it with a grace period of 0, and the GPU is free again. Deleting with kubectl delete pod --grace-period=0 --force skips all of this: the API server removes the object without waiting for the kubelet to confirm, while the process may still be running on the node.

Chapter 14 of 18

Two of two again

Available returns. Progressing never changed

About three minutes after the delete, the replacement has loaded its weights and its readiness check passes. The kubelet writes Ready: True. The ReplicaSet controller counts two ready Pods. The Deployment controller sees availableReplicas 2, which is at least 2 minus 0, and sets Available back to True with reason MinimumReplicasAvailable.

The Progressing condition did not move during any of this. The documentation says it keeps True with reason NewReplicaSetAvailable until a new rollout starts, whatever happens to availability in between. Losing a Pod and getting it back is not a rollout, because the template did not change and no new ReplicaSet was made. So the two conditions answer two different questions. Available asks whether the Deployment has as many Pods as it promised. Progressing asks whether the latest template has been rolled out. An alert on a model service should watch the first one.

No person decided to recreate the Pod, and no component was told to. The same idea runs through the controllers that products add on top of Kubernetes. In the owner's OpenShift lab, running F5 BNK 2.4.2, BNK keeps a Deployment of the endpoint picker for each F5EPP resource, owned by that resource, and asks for two replicas: one serving and one standby. When that Deployment was scaled to zero by hand, BNK saw the difference between what it wanted and what existed, and put it back to one replica before any picker Pod had gone away. It is the ReplicaSet controller's loop again, one level higher, with a custom resource in the place of the Deployment.

Chapter 15 of 18

When an operator owns the Deployment

A Deployment that a product renders takes its spec from a custom resource, and a hand edit is put back

You wrote the Deployment qwen3 yourself, so its spec is yours to change. Many Deployments in a GPU cluster are not written by a person. An operator writes them. The Kubernetes documentation describes an operator as a client of the API that uses custom resources to manage an application, following the same control loop as the built-in controllers. You give it one custom resource that describes what you want. It renders the Deployments, DaemonSets, Services and Secrets that make it real, and from then on it keeps them equal to what it rendered. F5 BIG-IP Next for Kubernetes (BNK) works this way. Its lifecycle operator, installed with Helm into the namespace f5-operators, reads one custom resource of kind CNEInstance (apiVersion k8s.f5.com/v1) and builds the data plane from it: the TMM traffic Pods, the controllers and the datastore. When spec.intelligentLB is on, BNK also runs an endpoint picker for each F5EPP resource, as a Deployment owned by that F5EPP. The owner's notes say BNK keeps that Deployment, without naming which of its controllers does the work, so this lesson says BNK.

The mechanism is the one from the last chapters, one level higher. A generated object carries an entry in metadata.ownerReferences with controller: true that points at the object it was made for. In controller-runtime, the library most operators are built on, a controller declares the kind it reconciles with For() and the kinds it generates with Owns(). The documentation of Owns() says the controller then responds to create, delete and update events of the generated objects by reconciling the owner object. So when you change a generated Deployment, the watch delivers an update event, the operator is woken for its custom resource, it computes the Deployment it wants from that resource's spec and writes it back over your change. Nothing in the operator compares your change with its own and asks which is better. Its spec is the only source. As a backstop, controller-runtime also replays every cached object as an update on a resync period, 10 hours by default, so even a missed event is corrected in the end.

The owner saw this on two labs. On an OpenShift lab running BNK 2.4.2, scaling the endpoint picker Deployment to zero by hand was undone at once. BNK put it back to one replica before any picker Pod had gone away, so the picker never stopped. On a BNK 2.4.0 lab on Google Cloud, patching other Deployments that BNK rendered was reverted by the operator within a minute. Your kubectl command succeeds each time, because a plain update never fails on a field conflict. The server-side apply documentation says a change made with update to a field that another manager owns does not provoke a conflict. The field changes, the managedFields entry for it moves to kubectl, and a moment later the operator's write moves it back. kubectl get deployment -o yaml --show-managed-fields shows which manager last wrote each field, and that is the quickest way to see whether a Deployment has an owner other than you.

The second trap is that only what the custom resource exposes can be changed at all. CNEInstance has spec.deploymentSize, and the owner's installs ran at Small, the smallest size. Small is the floor. On the BNK 2.4.0 install at Small on Google Cloud, with one TMM Pod, the owner measured 22.58 vCPU of CPU requests and 31.4 GiB of memory requests across the cluster. The owner's note breaks out two groups: 19,958 millicores in the f5-* namespaces and 950 millicores in Kubernetes, Calico and Multus. Those two add up to 20,908 millicores, so the note leaves 1,672 millicores of the total in neither group. The single largest Pod was f5-tmm at 4,600 millicores, with 8 GiB of memory and 4 GiB of hugepages, made of the TMM container plus five sidecars. The six DSSM datastore Pods asked for 850 millicores each, 5,100 millicores together. What the cluster actually used was 0.45 vCPU and 2.5 GiB. 22.58 divided by 0.45 is about 50, so CPU was reserved about fifty times over. The owner's note gives 48 times, a figure these two totals do not quite produce. Memory at 31.4 GiB against 2.5 GiB is about twelve times over.

The scheduler places Pods by their requests. What a Pod really uses plays no part, so those reservations must fit on the nodes. The resource override the CNEInstance exposes for TMM is spec.advanced.tmm.resources, and it governs the main TMM container only. The five sidecars keep their own requests. The owner set cpu: 1 there and the TMM Pod still requested 2. spec.advanced.dssm exposes only env, with no replica count, so the six DSSM Pods stay at 850 millicores each. Patching the rendered Deployments to lower a request is the hand edit from above, and it is reverted within a minute. On a GPU node this matters directly. The vLLM Pod for qwen3 needs CPU and memory requests too, and if TMM and its sidecars have already reserved the node's CPU, the next model server waits Pending with the scheduler message Insufficient cpu, while the node's real CPU sits nearly idle. The owner's lab ran on machines without GPUs, so this is the mechanism applied to a GPU node, and no measurement of one.

So the rule for a Deployment an operator owns is to change the custom resource, never the Deployment. The endpoint picker's replica count is spec.replicas on its F5EPP resource (apiVersion inference.k8s.f5.com/v1alpha1), where 2 means one serving picker and one standby. TMM's main container is sized in spec.advanced.tmm.resources. What the resource does not expose cannot be changed by you, only traded. The owner's figure for the one trade left comes from the same Google Cloud lab. The 22.58 vCPU above was measured with one TMM Pod. Counting a second TMM Pod and the lab's own Pods (simulated workers, Prometheus and Grafana) the lab committed 27.6 vCPU. Running TMM on one labelled node instead of two lowers that to 23.0 vCPU. The difference is 4.6 vCPU, the size of one f5-tmm Pod, and the cost is having one TMM and no redundancy.

Chapter 16 of 18

A quota says no

The Deployment and the ReplicaSet accept the change. The Pod is refused

The namespace inference has a ResourceQuota called gpu-quota that allows 3 GPUs in requests: requests.nvidia.com/gpu: 3. Two are in use. Now you scale the Deployment to four model servers. The Deployment's spec changes, so its generation goes to 2. The Deployment controller sets the ReplicaSet's spec.replicas to 4 and records the event Scaled up replica set qwen3-6f7d9c8b4 from 2 to 4. Neither write uses a GPU, so the quota does not look at them.

The ReplicaSet controller needs two more Pods. Its first batch is one Pod. The ResourceQuota admission plugin adds that Pod's request to the namespace's usage: 2 plus 1 is 3, which is within 3, so it is admitted and the usage becomes 3. The next batch may be two, but only one is needed. That Pod would bring usage to 4. The plugin refuses it with 403 Forbidden and the message exceeded quota: gpu-quota, requested: requests.nvidia.com/gpu=1, used: requests.nvidia.com/gpu=3, limited: requests.nvidia.com/gpu=3.

The refusal lands on the ReplicaSet controller, because it sent the request. It records a Warning event with reason FailedCreate and the message Error creating: followed by that text. The ReplicaSet gets a condition ReplicaFailure with reason FailedCreate, and the Deployment shows the same. No Pod exists for the refused one, so kubectl get pods shows three Pods and nothing about the fourth. kubectl describe rs, or the conditions in kubectl describe deployment, is where the reason is. The controller keeps trying with a growing delay, and the fourth Pod appears by itself once the quota is raised or a GPU is released.

Chapter 17 of 18

Scaling down: which Pod goes

The ReplicaSet removes the Pod that costs least to lose

A minute and a half later you change your mind and scale back to two. The ReplicaSet now owns three active Pods and wants two, so it deletes one. It does not pick at random. It sorts its Pods so that the cheapest to lose comes first, and the rules are applied in order until one tells two Pods apart. A Pod not yet bound to a node goes before one that is. A Pending Pod goes before an Unknown one, and an Unknown one before a Running one. A Pod that is not ready goes before a ready one. Then a lower value of the annotation controller.kubernetes.io/pod-deletion-cost goes first. Then a Pod that shares its node with more Pods of the same ReplicaSet. Then a Pod that has been ready for less time. Then one whose containers restarted more often. Last, a newer Pod goes before an older one.

Here the third rule decides. qwen3-6f7d9c8b4-w7njs was created 90 seconds ago and is still loading its weights, so it is not ready. The other two are ready and serving. The controller deletes qwen3-6f7d9c8b4-w7njs, and the 90 seconds of loading are lost, which is the cheapest outcome available. Losing a ready Pod would have cut capacity at once.

The annotation lets you steer this when you know better. It takes a whole number from −2147483648 to 2147483647, and a Pod with a lower cost goes first. A controller that knows which model server is least busy could set it. The documentation calls it best effort, and it is no guarantee. Writing the annotation often on many Pods also costs API server load. With the scale-down the quota usage drops to 2, and the fourth Pod is no longer wanted at all.

Chapter 18 of 18

Owners take their dependents with them

Deleting the Deployment, and the garbage collector that finishes the job

At the end of the day you delete the Deployment. You do not delete the ReplicaSet or the Pods. The garbage collector in kube-controller-manager does that, by following ownerReferences. Each Pod names the ReplicaSet as its owner, and the ReplicaSet names the Deployment. When an owner is gone, its dependents are deleted too. The garbage collector runs 20 workers by default.

The default is background cascading deletion. The API server removes the Deployment at once and answers you, and the garbage collector then deletes the ReplicaSet, and after it the Pods, as it finds them without an owner. In foreground deletion the API server keeps the owner, sets its deletionTimestamp and adds the finalizer foregroundDeletion, and removes the owner only after the dependents with blockOwnerDeletion: true are gone. kubectl delete --cascade=foreground asks for that. kubectl delete --cascade=orphan removes only the owner and leaves the dependents running without one. Owner references never cross namespaces. An invalid one produces a Warning event with reason OwnerRefInvalidNamespace.

Ownership also works the other way. A ReplicaSet adopts any Pod that matches its selector and has no controller owner. If you started a Pod by hand with the labels app: qwen3 and pod-template-hash: 6f7d9c8b4, the ReplicaSet would take it over at once and might then delete it as one too many. Orphaned ReplicaSets and Pods left by --cascade=orphan are adopted the same way when a new Deployment with the same selector appears. Each Pod shuts down as before, with TERM and a grace period, and the GPUs it held are free again once its containers have stopped.

What to keep

A chain of owners, each watching one thing

A Deployment becomes running Pods through five components that never call each other. The API server authenticates, authorizes and admits the request and stores the object. The Deployment controller creates a ReplicaSet named after a hash of the Pod template. The ReplicaSet controller creates Pods in growing batches and marks them as its own. The scheduler writes a node into each Pod. The kubelet on that node starts the container and reports what happened, and the counts climb back up into the Deployment's status and conditions, where kubectl rollout status and kubectl describe read them. Every one of them compares what is wanted with what exists and acts on the difference. That is why a deleted Pod returns, why a quota refusal shows up on the ReplicaSet and not on a Pod, why a scale-down removes the Pod still loading, and why deleting the owner removes everything below it. For a model server each return costs about three minutes.
