Kubernetes underneath

Killed for memory

What a memory limit covers, who enforces it, and why it says nothing about the GPU

A model server can run out of two kinds of memory, and Kubernetes knows about one of them. The memory limit in a Pod is a limit on the host's RAM. The kubelet hands it to the Linux kernel as a number in a file, and the kernel enforces it by killing the process that goes over. The GPU's memory is on the card. The memory cgroup that enforces the Pod's limit does not count it, and Kubernetes sets no limit on it, so running out of it is an error inside the program. Both failures end in the same restart loop and the same word in kubectl. This lesson takes one Pod through each. It shows what the kernel writes down when it kills, how to size a limit from a measurement, the softer ceiling that Kubernetes leaves off by default, how the node defends itself when it runs short as a whole, and where to look to tell the cases apart. The Deployment's two Pods are qwen3-6f7d9c8b4-x7k2p on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t on gpu-node-2, and the lesson follows the one on gpu-node-1. A Deployment names each Pod from its own name, the pod-template-hash of its template and a random suffix, so when the template changes later in the lesson the new Pods get new names. Numbered names like db-0 are how a StatefulSet names its Pods.

Chapter 1 of 14

A request and a limit have different readers

The scheduler reads one, the kernel enforces the other

A container can state two numbers for memory. The request is what it expects to need. The scheduler reads it, adds it to the requests already on each node and places the Pod only where the total fits. The limit is the most the container may use. The scheduler ignores it. It goes to the node, where the kernel enforces it. Both numbers are about the host's RAM. Someone on the team reasons that the weights of Qwen3-32B live on the GPU, so the server needs little RAM, and sets both to 16Gi. Equal requests and limits for CPU and memory put the Pod in the Guaranteed class, which matters later. The scheduler finds room for 16Gi on gpu-node-1 and binds the Pod there.

The units are easy to get wrong. Gi is a power of two, so 16Gi is 16 × 1024³ = 17,179,869,184 bytes. G is a power of ten, so 16G is 16,000,000,000 bytes, about 7% less. A lowercase m means one thousandth, so a memory request of 400m asks for 0.4 bytes. When a container states a limit and no request, Kubernetes copies the limit into the request, unless a LimitRange in the namespace has already filled in a default request at admission.

The room the scheduler counts is the node's Allocatable memory. That is the node's total memory minus what is set aside for the system and for the kubelet, and minus the hard eviction threshold. On gpu-node-1 Allocatable is 480Gi in this example. Pods already there request 96Gi, so 16Gi more brings the total to 112Gi, which fits.

Chapter 2 of 14

The limit becomes one file

The kubelet passes a number down and the kernel keeps it

On the node, the limit stops being a Kubernetes field. The kubelet turns 16Gi into bytes and gives the number to the container runtime when it asks for the container to be created. The runtime creates a cgroup for the container. A cgroup, or control group, is the kernel's way of putting a set of processes under shared accounting and limits. With cgroup v2, each one is a directory under /sys/fs/cgroup, and the limit is a file in it called memory.max. The runtime writes 17179869184 there. Next to it the kernel keeps memory.current, the bytes charged to the group right now. From here on Kubernetes does not watch the container's memory to enforce anything. The kernel checks the limit itself, each time it charges memory to the group.

To see which version a node runs, run stat -fc %T /sys/fs/cgroup/. It prints cgroup2fs for v2 and tmpfs for v1. Kubernetes supports v2 as stable since 1.25, on Linux 5.8 or later with the systemd cgroup driver, and v1 is deprecated.

The cgroups form a tree. With the systemd driver every Pod sits under kubepods.slice. Burstable and BestEffort Pods sit one level deeper, under kubepods-burstable.slice or kubepods-besteffort.slice. Each Pod gets its own slice and each container a cgroup below it. A Pod's slice also gets a memory limit of its own whenever every container in the Pod declares a memory limit. That is always true of a Guaranteed Pod, and also true of a Burstable Pod whose containers all set one. The kubelet works it out as the sum of the containers' limits, raised to an init container's limit if that is larger, plus any Pod overhead from the RuntimeClass. qwen3-6f7d9c8b4-x7k2p has one container and no overhead, so its slice gets 16Gi too, and the ceiling exists twice: for the container and for the Pod. The kubelet passes two more settings with the limit. oom_score_adj is -997 for a Guaranteed Pod. memory.oom.group is 1.

Chapter 3 of 14

Memory cannot be throttled

Past a CPU limit a process waits, past a memory limit it dies

A CPU limit is enforced by making the process wait. Nothing like that happens at memory.max, because a page that holds data cannot be handed out late. People call memory incompressible for this reason. The kernel charges the cgroup for the process's own memory, called anonymous memory, and for file data it has cached. Files written to a memory backed volume such as vLLM's /dev/shm are charged too. When the total reaches memory.max, the kernel first frees what it can, which is cached file data. Anonymous memory has nowhere to go on a node without swap. If the usage cannot be reduced, the kernel's out of memory killer runs inside the cgroup and kills its processes with SIGKILL. Here vLLM needs about 20 GiB while it starts. The container starts 2 seconds after the Pod is created. It is killed at 95 seconds, which is 93 seconds into the load.

The process gets no warning. The kernel's documentation says that in the default setup ordinary allocations always succeed unless the out of memory killer picks the allocating task as its victim. There is no failed malloc to catch and no error to log. Each time the cgroup is about to go over the limit, the kernel counts one more max event and tries to reclaim. Only when reclaim fails does the cgroup go into the out of memory state.

The killer picks a victim by a score: its resident memory, swap entries and page tables in pages, plus oom_score_adj × the cgroup's limit in pages / 1000. Every process in one container starts with the same oom_score_adj, because a child inherits it from its parent. A process may raise its own value but needs privilege to lower it. While none of them changes it, the largest one scores highest. With memory.oom.group set to 1, the choice hardly matters, because every process in the cgroup is killed together.

Chapter 4 of 14

What the kernel writes down

A block in the kernel log, counters in the cgroup, and a signal to the runtime

A kill for memory leaves a record in three places, and each is read by someone different. The first is the node's kernel log, read with dmesg or journalctl -k. The block opens with a line naming the process that tried to allocate: <name> invoked oom-killer, followed by the allocation flags and order and that process's oom_score_adj. Next comes a table headed Tasks state (memory values in pages), with one row for each process in the cgroup and its pid, total_vm, rss and oom_score_adj. A line starting oom-kill:constraint=CONSTRAINT_MEMCG says this was a cgroup limit and the whole node is fine. Then comes the first kill line, for the process with the highest score: Memory cgroup out of memory: Killed process <pid> (<name>), followed by its total-vm, anon-rss, file-rss and shmem-rss in kB, its UID, pgtables and its oom_score_adj, here -997. The kernel kills that victim first. Only after it, with memory.oom.group set, does the kernel print Tasks in <cgroup path> are going to be killed due to memory.oom.group set, and then one more Killed process line for each other process in the group that it kills.

The second record is the cgroup's memory.events file. max counts how many times the usage was about to cross memory.max. oom counts how many times it reached the limit with an allocation about to fail. oom_kill counts processes killed. oom_group_kill counts group kills. A max count that rises while oom_kill stays 0 is the early warning: the container touched its ceiling and was saved by dropping cache.

The third record goes to containerd. Its shim watches the cgroup for out of memory events, and containerd marks the container when one arrives. Those events are handled one at a time, so the exit can be seen before the event. For that case containerd has a second check in its current source. If the container exits with 137 and is not yet marked, containerd asks the shim for the cgroup's counters and marks it if oom_kill is above 0. Either way, that is how the reason OOMKilled is chosen.

Chapter 5 of 14

Exit code 137, reason OOMKilled

How a kill in the kernel becomes a word in kubectl

The runtime sees the container's process end. A process ended by a signal is reported with an exit code of 128 plus the signal's number, and SIGKILL is 9, so the code is 137. containerd has also been told by the kernel that an out of memory kill happened in this cgroup, and it labels the exit with the reason OOMKilled. The kubelet copies both into the Pod's status. Then it applies the Pod's restartPolicy, which is Always for a Deployment, and starts the container again in the same Pod. The first restart is immediate. After that the kubelet waits 10 seconds, then 20, then 40, up to five minutes. While it waits, kubectl shows CrashLoopBackOff. Every attempt dies at the same point, so the Pod never becomes ready.

The STATUS column of kubectl get pods shows this in two steps. Right after the kill it prints OOMKilled, taken from the container's state.terminated.reason. Once the kubelet is waiting to restart, it prints CrashLoopBackOff from state.waiting.reason. kubectl describe pod keeps the earlier death under Last State: Terminated, with Reason OOMKilled, Exit Code 137, the Started and Finished times, and Restart Count. containerd uses a small set of reasons. OOMKilled for a memory kill. Completed for exit code 0. Error for any other non-zero exit. StartError when the process could not start at all.

The fix in this case is in the Pod's spec. The limit has to cover what the server really holds in host RAM at its peak. Raising it to 64Gi gives a new container a memory.max of 68719476736 bytes, and the server, which needs about 20 GiB, now starts.

Chapter 6 of 14

Sizing the limit from a measurement

Read the peak once the server runs, and know what else lives in host RAM

A limit should come from a measurement. Once the server has started with 64Gi, the kernel can say how much it ever used. The file memory.peak in the container's cgroup holds the highest usage since the cgroup was created. Here it reads about 20 GiB. memory.current shows the usage right now, and memory.stat breaks it down. The same numbers reach Prometheus through cAdvisor in the kubelet: container_memory_working_set_bytes, container_memory_rss, container_memory_cache and container_oom_events_total.

A model server holds more in host RAM than people expect. The weights pass through the page cache as they are read from disk, and that cache is charged to the cgroup. vLLM's documentation mounts a memory backed volume at /dev/shm, because the server uses the host's shared memory for tensor parallel inference. Its example is an emptyDir with medium: Memory and sizeLimit: 2Gi. That is a tmpfs, and the kubelet counts it as the container's memory. Without a sizeLimit it may grow up to the Pod's memory limit. Unlike page cache, data in it cannot be dropped, because there is no file behind it to drop it to. In memory.stat it appears under file and again under shmem. A KV cache layer can hold much more. LMCache in its multiprocess mode runs as its own server, started with lmcache server, and keeps its first tier, L1, in pinned host DRAM sized with --l1-size-gb, for example 50. That memory is charged to the cgroup of whichever container runs the LMCache server. If it runs as a separate container, it needs its own limit and does not count against vLLM's. If it runs inside the vLLM container, the vLLM limit must cover it too.

So the limit needs the measured peak plus headroom for cache and growth. In this example LMCache, where it is used, runs in a container of its own, so 64Gi leaves 44 GiB above a 20 GiB peak. If its 50 GB L1 ran inside the vLLM container instead, the same limit would have to hold about 20 + 50 = 70 GiB and would be too small. A limit can be changed on a running Pod by a resize, kubectl patch pod with --subresource resize. Lowering a memory limit is best effort and is skipped while usage is above the new value, and the QoS class never changes.

Chapter 7 of 14

A KV cache tier below the GPU

LMCache moves the cache out of the card in chunks, into DRAM and then onto storage

vLLM keeps the KV cache in the GPU's memory. The KV cache holds the keys and values the model has already computed for every token it has read, so the next token does not have to read the whole prompt again. When vLLM needs the room, it frees those blocks and the work that made them is lost. LMCache copies them out first, so a later request that starts with the same text can load them back instead of computing them again. In its multiprocess mode LMCache runs as its own server, started with lmcache server, and keeps two tiers. L1 is the server's own memory: pinned host DRAM by default, sized with --l1-size-gb, which is required. It can instead be an NVMe slab reached through GPUDirect Storage when --gds-l1-path is set. L2 is one or more storage backends behind L1, each chosen with its own --l2-adapter flag that takes a JSON object.

The unit LMCache moves is a chunk. The server's --chunk-size is 256 tokens by default, and vLLM keeps its cache in blocks of 16 tokens, so one chunk is 16 vLLM blocks. Qwen3-32B has 64 layers, 8 KV heads and 128 values per head. With the cache kept in 16-bit numbers, which is what vLLM does for the FP8 build unless --kv-cache-dtype says otherwise, one token costs 64 × 2 (key and value) × 8 × 128 × 2 bytes = 262,144 bytes, or 256 KiB. A chunk of 256 tokens is then 256 × 256 KiB = 64 MiB. Those bytes are not next to each other on the card. vLLM keeps one tensor per layer, and inside it each 16 token block holds 16 × 8 × 128 × 2 bytes = 32 KiB of keys and 32 KiB of values. One chunk is therefore 16 blocks × 64 layers × 2 = 2,048 pieces of 32 KiB spread across the card. On a STORE call the transfer channel, CUDA IPC or POSIX shared memory, gathers all 2,048 pieces into one contiguous 64 MiB chunk in L1. On a RETRIEVE it scatters them back into whatever blocks vLLM has free. LMCache's quickstart runs both containers with --ipc host because CUDA IPC needs it. The chunk size also fixes the size of every request L2 will ever see, so the storage below works in 64 MiB pieces for this model.

L1 lives in the host's RAM, which ties it to everything earlier in this lesson. Pinned memory is locked in place for the GPU's copy engines, so the kernel can neither reclaim it nor swap it. With --l1-size-gb 50, taking the gigabyte as 2³⁰ bytes, L1 holds 50 × 1,024 ÷ 64 = 800 chunks, or 800 × 256 = 204,800 tokens of prefix for Qwen3-32B. All of it is charged to the cgroup of the container that runs lmcache server. L1 has its own eviction. --eviction-policy is required and takes LRU, ARC, IsolatedLRU or noop. ARC balances keys used recently against keys used often, and IsolatedLRU keeps one LRU list per cache_salt, with quotas set through the server's HTTP API. This example uses LRU. --eviction-trigger-watermark is 0.8 by default and --eviction-ratio 0.2. With 50 GB, a background thread starts evicting once usage passes 40 GB and drops 20% of the allocated memory per cycle, about 8 GB or 128 chunks, least recently used first. That keeps L1 inside its own size. It does nothing for the container limit if the limit was set below the L1 size in the first place.

The hand-down from L1 to L2 is asynchronous. When vLLM stores a chunk into L1, a StoreController thread notices the new object through an eventfd and submits a store task to every configured L2 adapter. What happens to the L1 copy depends on --l2-store-policy. The default policy stores every key to every adapter and never deletes from L1, so each chunk spills through to storage as soon as it arrives and stays in DRAM until L1's own eviction drops it under pressure. The skip_l1 policy is buffer-only mode: each key is deleted from L1 right after L2 has stored it, and the docs pair it with --eviction-policy noop because there is nothing left for LRU to track. The way back starts with a LOOKUP call, which checks L1 for the prefix. For keys L1 does not have, a PrefetchController asks the L2 adapters in the order they were given. A key found in L2 is loaded into L1 and read-locked until the RETRIEVE that wanted it has copied it to the GPU. --l2-prefetch-policy default takes each key from the first adapter that has it and keeps the loaded copy in L1, so later requests for the same prefix, such as a long system prompt, hit L1. skip_l1 loads the same way and makes the copy temporary, deleted once the reader is done. retain is now only a deprecated name for default. Prefetches are limited by L1 memory, not by a count. A queued prefetch starts only when the L1 memory being written by prefetches and stores in flight is below --l2-prefetch-inflight-watermark, 0.5 of L1's capacity by default, and L1 has room for it. With a 50 GB L1 that is 25 GB, or 400 chunks of 64 MiB. The older flag --l2-prefetch-max-in-flight is still accepted, has no default and is ignored with a warning. Buffer-only mode pairs skip_l1 for stores and prefetches with --eviction-policy noop.

Every L2 backend sits behind one contract, the class L2AdapterInterface in lmcache/v1/distributed/l2_adapters/base.py. It has three non-blocking operations and a delete. submit_store_task takes a list of keys and the matching memory objects and returns a task id. submit_lookup_and_lock_task takes keys, finds which exist and locks them so that L2 eviction cannot remove them before they are loaded. submit_load_task takes keys and buffers that the caller owns and writes the data straight into them. delete removes keys and is what L2 eviction calls. Each submit returns at once and signals completion through an eventfd. A store that fails is reported for the whole task, and lookups and loads answer with a bitmap, one bit per key. Keys are chunk keys. The Hugging Face adapter shows their shape in its object names: model, KV rank and chunk hash joined by @. Two threads call an adapter, the store controller and the prefetch controller, so an adapter must be thread safe. A new backend implements the interface and registers a config class. Code kept outside LMCache's tree is loaded at runtime through the adapter type plugin.

The built-in adapters, by their type names, include these. nixl_store is the primary production adapter. It runs on NVIDIA's NIXL library with a backend of POSIX, GDS, GDS_MT, HF3FS, OBJ or AZURE_BLOB and a pool_size of storage descriptors allocated up front. nixl_store_dynamic opens files per operation and keeps its data across restarts. fs is plain files written with async I/O under base_path, with use_odirect false by default. fs_native does the same from a C++ thread pool of num_workers, 4 by default. raw_block writes fixed size slots straight onto a block device such as /dev/nvme0n1, with use_odirect true, block_align 4096, a 4096 byte header per slot and a 256 MiB metadata region by default, and can use io_uring. dax maps Device-DAX memory such as CXL. mooncake_store and aerospike are native connectors. s3 uses the AWS Common Runtime with 64 I/O threads by default. hfbucket writes to Hugging Face Buckets, and mock simulates a size and a bandwidth for tests. The source registers more: bigtable, valkey, resp, nixl_native, p2p, sagemaker-hyperpod, hf3fs, fault_inject for tests, and plugin and native_plugin for code kept outside the tree. Repeating --l2-adapter makes a cascade: stores go to all of them, and lookups ask them in order. L2 eviction is per adapter and off unless the adapter's JSON has an eviction object, with trigger_watermark 0.8 and eviction_ratio 0.2 as defaults. fs has none, so its directory grows until the disk is full.

The adapter choice touches host memory too. fs and fs_native without use_odirect write through the page cache, and those pages are charged to the cgroup of the container running the server, as file memory the kernel can reclaim. raw_block with O_DIRECT bypasses the page cache. Its slot_bytes has to hold one whole chunk, so for this model a slot is at least 64 MiB. Below raw_block there is a further step, which the owner's sources cover through a write-up in the AI Infrastructure series that built two out-of-tree adapters on SPDK, a kernel bypass storage library. The bdev adapter keeps a map from chunk keys to device blocks in host memory and allocates variable sized extents, because engines sharing one server can have different KV block shapes. Its connector threads, connector_worker_cpus, and SPDK's polling threads, spdk_reactor_cpus, must sit on different CPUs. On one NVMe drive with 4 KiB blocks it was 2 to 10% faster than LMCache's fs_native adapter with O_DIRECT, fs_native_odirect in the benchmark, for 256 KiB requests, and at 10 to 30 MiB both reached the drive's ceiling of about 1.6 GiB/s read and 0.75 GiB/s write. At those rates one 64 MiB chunk of Qwen3-32B takes 64 ÷ 1,638 ≈ 39 ms to read and 64 ÷ 768 ≈ 83 ms to write. The NVMe-KV adapter moves the key map onto the drive itself, hashing each key with SHA-256 to a 16 byte device key, and gives each worker its own queue pair. It was tested only in QEMU, because KV drives are hard to buy.

Chapter 8 of 14

A data plane that reserves more than it uses

F5 BIG-IP Next for Kubernetes asks for far more than it uses, and the scheduler counts the asking

The rule from the first chapter, that the scheduler counts requests and never usage, decides where infrastructure Pods fit as much as it decides where model servers fit. F5 BIG-IP Next for Kubernetes, BNK for short, puts F5's data plane into the cluster as Pods. Its packet engine is TMM, the Traffic Management Microkernel, which runs in the Pod f5-tmm. An operator installs everything from one custom resource, and its deploymentSize field picks a size class. Small is the smallest. Version 2.4.0 pulls 81 images from repo.f5.com. Besides f5-tmm, the install runs a session state store called DSSM as six Pods, a CSRC Pod on every node that installs the routing rules steering Pod traffic to TMM, and a set of controllers.

The owner measured one licensed 2.4.0 install at Small. The requests across the whole cluster came to 22.58 vCPU and 31.4 GiB of memory. The f5-* namespaces asked for 19,958m of CPU and Kubernetes itself, with Calico and Multus, for 950m. Those two parts make 20.9 vCPU. The notes do not say what the other 1.67 vCPU of the 22.58 belongs to. The largest single Pod was f5-tmm at 4.6 vCPU and 8.0 GiB, plus 4Gi of hugepages-2Mi. The six DSSM Pods asked for 850m each, 6 × 850m = 5.1 vCPU. Measured usage on the same install was 0.45 vCPU and 2.5 GiB. Dividing, 22.58 ÷ 0.45 ≈ 50 and 31.4 ÷ 2.5 ≈ 12.6, so CPU was reserved about 50 times over and memory about 12 times over. The owner's notes give the CPU figure as 48 times without showing the division, which is the same order. The scheduler cannot know this. It places every one of those Pods as if it used what it asks for.

The requests cannot be lowered from outside. Small is the floor. The only resource knob for TMM, advanced.tmm.resources, sets the main container and leaves the five sidecars that make up the rest of f5-tmm's 4.6 vCPU as they are. advanced.dssm takes only environment variables, so there is no replica count to turn down from six. A patch to the Deployments the operator generated is put back by the operator within a minute. The requests are a fixed cost of running BNK, to be planned for like a model server's.

TMM will not start without huge pages. A huge page is a 2 MiB page in place of the normal 4 KiB one, so one entry in the CPU's address cache covers 512 times more memory. Labs reserve 4 to 6 GiB of them, and a DPU install expects 8192 pages, which is 8192 × 2 MiB = 16 GiB. Kubernetes treats huge pages as their own resource. They must be set aside on the node before use, for example with hugepages=3072 on the kernel command line for 6 GiB of 2 MiB pages, and the node then reports hugepages-2Mi in its Capacity and Allocatable. They cannot be overcommitted. A container's huge page request must equal its limit, and it must also request memory or CPU. The kubelet subtracts every huge page reservation from the node's Allocatable memory, so a 24 GB worker with 6 GiB of huge pages offers at most 24 GB − 6.44 GB ≈ 17.6 GB of ordinary memory before system reservations. The kubelet gives each container its own hugetlb limit, separate from memory.max, so huge pages never count toward the memory limit that ends in OOMKilled. In 2.4.2 with the ocnos routing engine turned on, TMM's memory went from 8 to 9.5 GiB.

The owner's OpenShift lab shows what happens when the sum does not fit. It had one control plane and two workers of 8 vCPU and 24 GB each, with 6 GiB of each worker held as huge pages. Two workers give 16 vCPU. The measured install above asked for 22.58 vCPU across its cluster, and the owner's install guide puts BNK alone at roughly 20 vCPU of requests. The OpenShift lab differs from that install in its TMM count and in OpenShift's own Pods, so its exact total is not known. The third DSSM replica and one CSRC Pod stayed Pending, and the BNK instance timed out waiting for them. The lab notes record the Pending Pods and not the scheduler's reason. The install guide says that below its CPU floor Pods sit Pending with Insufficient cpu. Each VM was shut down and resized: the control plane from 48 to 40 GB and each worker from 8 to 12 vCPU and from 24 to 28 GB. The total memory stayed the same, 48 + 24 + 24 = 40 + 28 + 28 = 96 GB, so nothing else on the host lost memory. After that the instance reported Available, with all 14 components up and the licence Active.

A second lab, on three cloud hosts built with kubeadm, shows the arithmetic in full. kubeadm reserves no CPU by default, and on the running cluster Allocatable equalled Capacity. On one host the whole 22.58 vCPU must fit on that host, which needs a 32 vCPU machine. Spread over three hosts of 16, 8 and 8 vCPU, the binding limit becomes the largest single Pod, and f5-tmm's 4.6 vCPU fits an 8 vCPU worker. With a second TMM and the lab's own Pods the committed total was 27.6 vCPU against 32 allocatable. On a real install the per node spread of requests was 6.2, 10.8 and 5.6 vCPU, 22.6 in all, so uneven placement is the normal case. Dropping to one TMM takes 27.6 − 4.6 = 23.0 vCPU. On a GPU node the same requests compete with the model server. Every GiB BNK reserves on gpu-node-1 comes out of the 480Gi of Allocatable that qwen3-5d4b9c7f8-r2v6n is placed against, whether or not BNK ever touches it.

Chapter 9 of 14

A softer ceiling, off by default

The kernel can throttle memory, and Kubernetes only asks it to when told

The kernel has a second memory setting, memory.high. Above it the processes in the cgroup are slowed down and put under heavy reclaim pressure, and the out of memory killer is never called for it. Its default is max, which means no throttle. Kubernetes leaves it at max unless a feature called Memory QoS is turned on in the kubelet. Whether that alone is enough depends on the setting memoryThrottlingFactor. How it behaves when the setting is left out depends on the version. In the current Kubernetes source, on the main branch after release 1.36, the default is empty, and empty means the kubelet does not set memory.high at all. Up to and including 1.36 the kubelet filled in 0.9 whenever the setting was unset, so on those clusters turning on the MemoryQoS feature gate alone was enough to set memory.high.

When it is set, the kubelet computes memory.high = request + memoryThrottlingFactor × (limit − request). The documentation's example uses 0.9 with a 256 MiB request and a 1 GiB limit: 256 + 0.9 × (1024 − 256) = 947.2 MiB. A Guaranteed container gets no memory.high, because its request equals its limit and there is no room between them. So qwen3-5d4b9c7f8-r2v6n would be killed at memory.max exactly as before, with or without the feature. Memory QoS needs cgroup v2, and the documentation recommends kernel 5.9 or later. A second setting, memoryReservationPolicy, first appears in the 1.36 source with the values None, the default, and TieredReservation. TieredReservation protects requested memory with memory.min for Guaranteed Pods and memory.low for Burstable Pods. The main branch adds two more values, Soft and Hard, behind their own feature gate, NodeMemoryReservationPolicy. The documentation warns that memory.min then equals memory.max, and a server that reads a lot of files may be killed before enough cache is reclaimed.

Swap is the other way memory could stretch. The kubelet refuses to start on a node with swap unless failSwapOn is false. Even then the default behaviour is NoSwap, and with LimitedSwap only Burstable Pods may swap. A Guaranteed model server never does.

Chapter 10 of 14

An eviction is a different event

The kernel kills a container, the kubelet removes a Pod

There is a second way to lose a Pod to memory, and it is often confused with the first. Here no container passed its own limit. The node as a whole is running short. The kubelet watches a signal called memory.available, and by default it acts when that falls below 100Mi. It picks Pods to evict. Pods that use more memory than they requested go first, ordered by their priority and then by how far over they are. Pods that stay within their request go last. The three classes give a fair guess at that order: BestEffort, then Burstable, then Guaranteed. An evicted Pod is not restarted. Its phase becomes Failed with the reason Evicted, and its controller has to create a new Pod.

memory.available is the node's memory capacity minus its working set, read from the cgroup files and never from free. The working set leaves out inactive_file, file cache on the inactive list, because the kernel can reclaim it. It counts active_file as in use. A server that reads its 34.3 GB of FP8 weights often can leave much of that cache on the active list and push the node toward pressure with cache alone.

The kubelet checks every 10 seconds, the housekeeping interval, and evicts at most one Pod each time. At a hard threshold it asks for a grace period of 1 second and ignores PodDisruptionBudgets and the Pod's own terminationGracePeriodSeconds. The container runtime manager then raises any grace period below 2 seconds to 2, so in practice the container gets 2 seconds. The message on the Pod names the starved resource, the threshold, what was available, and each container that used more than it requested.

Chapter 11 of 14

When the kubelet is too slow

Ten seconds is long enough for the kernel to act first

The kubelet sees memory through a poll, every 10 seconds by default. A process that allocates fast can take the node from comfortable to empty inside one interval. The documentation says plainly that the kubelet may then not see the pressure in time, and the kernel's own out of memory killer runs for the whole node. The kubelet can be told to use the kernel's memory cgroup notifications with kernelMemcgNotification, which is off by default, so it hears of a crossed threshold at once.

A node-wide kill follows the same scoring as a cgroup kill, with the node's memory as the scale. Here oom_score_adj decides almost everything. Every process of a BestEffort Pod has 1000 and goes first. A Guaranteed Pod's processes have -997. The kubelet itself runs at -999. A Burstable container gets 1000 − 1000 × request / node memory, kept between the ends. The kernel log line then starts Out of memory: Killed process, without the words Memory cgroup. The kubelet watches for these too. When the victim sat in the node's root cgroup, outside every container, it records a Warning event on the Node with the reason SystemOOM.

The best defence is room that Pods cannot touch. kubeReserved and systemReserved set memory aside for the kubelet and the operating system. Allocatable is the node's capacity minus both and minus the hard eviction threshold, and the kubelet keeps all Pods together under that total in the kubepods cgroup. On gpu-node-1 the scheduler sees 480Gi of Allocatable, so the system, the kubelet and the 100Mi threshold have their memory outside it.

Chapter 12 of 14

The cgroup cannot see the GPU

GPU memory is on the card, and no limit in the Pod covers it

Now the other memory. The kernel's memory controller tracks RAM: a process's own pages, cached files and some kernel structures. Memory on a GPU is handed out by the card's driver and is in none of those counts. The Pod has no field for it. Kubernetes counts whole cards and nothing inside them. Suppose gpu-node-1 shares its cards by time-slicing, which lets two Pods use one card and does not divide its memory. Someone scales the Deployment from two replicas to three. Scaling does not change the template, so the third Pod, qwen3-5d4b9c7f8-c4w8n, carries the same hash and the same 64Gi, and it is given the card that qwen3-5d4b9c7f8-r2v6n uses. qwen3-5d4b9c7f8-r2v6n took 0.9 of the card's 80 GB, so 72 GB are held and 8 GB are free. qwen3-5d4b9c7f8-c4w8n wants 72 GB too. vLLM checks the free memory before it loads the model, finds 8 GB and exits with an error. A process that runs out of GPU memory while working gets PyTorch's CUDA out of memory error, which is likewise an error inside the process.

vLLM's check is plain arithmetic. It takes the card's total memory in bytes, multiplies by --gpu-memory-utilization and rounds up to a whole byte. In round numbers that is requested = ceil(80 × 0.9) = 72 GB. The real figures are a little different, because a card sold as 80 GB reports somewhere around 79 to 80 GiB of total memory, and vLLM prints its sizes in GiB. If the free memory it measures at start-up is less than that, it raises a ValueError with the free, total and requested sizes filled in and suggests lowering the setting or freeing the card. A newer option in vLLM that lets the KV cache grow later skips this check.

PyTorch's error starts with the words CUDA out of memory. Tried to allocate, followed by the size. It is an exception in Python. A server that catches it can keep running, and one that does not exits with an ordinary error code. Neither path involves the kernel's killer.

Chapter 13 of 14

Sharing a card with a wall in it

Time-slicing shares memory freely, MPS and MIG divide it

Time-slicing is set in the NVIDIA device plugin's configuration under sharing.timeSlicing.resources, with a number of replicas for each card. With 2 replicas each of the node's 4 cards is advertised twice, so the node reports 8 of nvidia.com/gpu. The option renameByDefault advertises them as nvidia.com/gpu.shared instead, so a Pod has to ask for the shared kind on purpose. The option failRequestsGreaterThanOne makes a Pod that asks for more than one shared GPU fail with UnexpectedAdmissionError. It is recommended and is false by default. The plugin's documentation is blunt about the rest. Each workload has access to all of the card's memory and runs in the same fault domain as the others, so if one crashes, they all do.

Two other ways of sharing do divide memory. With MPS the plugin starts a control daemon and gives each client an equal fraction of the card's memory, enforced per workload. Its documentation calls MPS support experimental as of version 0.15.0, and MPS cannot be combined with time-slicing or used on cards with MIG enabled. MIG splits a card in hardware into instances with their own memory, advertised under names such as nvidia.com/mig-1g.10gb.

Sharing a card halves what each server can use. The owner's notes put it simply: free GPU memory, more than compute, caps how many users a GPU serves. Take the FP8 build of Qwen3-32B, whose weights are 34.3 GB. One server at 0.9 holds 72 GB, which leaves 72 − 34.3 = 37.7 GB for the KV cache and the engine's working memory. Two servers at 0.45 each hold 36 GB, which leaves 36 − 34.3 = 1.7 GB each. That 1.7 GB must also cover the engine's working memory, so each server would hold almost no KV cache, and vLLM may refuse to start for lack of room for it. The full BF16 build, at about 65.5 GB, would not even load at 0.45.

Chapter 14 of 14

Two failures, side by side

The same word in kubectl, and four places where they differ

Both Pods end up showing CrashLoopBackOff, so that word decides nothing. The last state of the container does. A host memory kill reads OOMKilled with exit code 137, and the container's log simply stops, because a killed process cannot write a last line. A GPU memory failure reads Error with exit code 1, and the log ends with the program's own error, here vLLM's message about free memory on the device. The fixes are in different places too. For the first, raise limits.memory or make the process use less RAM. For the second, no field in the Pod helps. Raising limits.memory changes nothing on the card. Free memory on the card, load a smaller model, or lower the share of the card each server takes. An eviction is a third case, with its reason on the Pod.

The order to read things in is short. First kubectl describe pod, and the Last State block of each container: reason and exit code. Then kubectl logs with --previous, which shows the log of the container that died. Then, for a kill, the cgroup's memory.events or the node's kernel log for the Memory cgroup out of memory line. For the GPU, nvidia-smi on the node or the DCGM metrics. kubectl top pod reads only CPU and host memory.

Three checks catch the edge cases. Exit code 137 with the reason Error can still be a memory kill, when containerd could not read the cgroup in time, so check memory.events. Exit code 137 with no memory event can be the kubelet's own kill after a grace period. A healthy Pod with failing requests can be a server that caught PyTorch's error and kept running.

What to keep

One limit, one kind of memory

A memory limit is a number the kubelet passes to the kernel, which keeps it in memory.max for the container's cgroup. Past memory.max nothing waits, so a container that goes over and cannot be trimmed is killed with SIGKILL. The kernel writes the kill into its log and its counters, the runtime reports exit code 137 and the reason OOMKilled, and the kubelet restarts the container with a growing delay. A softer ceiling, memory.high, exists in the kernel and is left unset by Kubernetes unless Memory QoS is configured. A node that runs short as a whole is handled by the kubelet, which evicts entire Pods and starts with those over their requests, and by the kernel itself when the kubelet's poll is too slow. None of this reaches the GPU. Memory on the card is not counted by the memory cgroup and Kubernetes sets no limit on it, so exhausting it is an error the program reports itself. For a model server, size the RAM limit from memory.peak and plan GPU memory separately.
