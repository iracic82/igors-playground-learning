GPU and hardware

The network is part of the computer

RDMA, RoCEv2 and GPUDirect between two GPUs

The public story of AI infrastructure is told through accelerators. It is accurate and incomplete. The moment a job spans more than one server, the network starts deciding how much of that accelerator capacity turns into work. GPUs in a training job exchange gradients, activations and parameters in synchronized phases, and a slow participant delays the whole group. This lesson follows one such exchange from the memory of GPU 0 in one server to the memory of GPU 1 in another. First the ordinary way, through both hosts. Then the way AI clusters do it, where the network card reaches into GPU memory and the hosts stand aside.

Chapter 1 of 12

Everyone waits for everyone

A training step ends with a conversation

Two GPUs in two servers train one model. Each has worked through its share of the data and now holds numbers the other needs before either can take the next step. Frameworks don't ask the network to move arbitrary buffers for this. They use collective operations. AllReduce ends every data-parallel training step. It combines values from every GPU and gives the result back to all of them, so every GPU applies the same update to its copy of the model.

NVIDIA's library for this, NCCL, discovers how the GPUs and network cards are connected and turns the collective into a concrete schedule of transfers. A common schedule is a ring. Each rank sends to the next one and receives from the one before, in 2 × (N − 1) steps. The first N − 1 steps add the parts together, and the last N − 1 hand the finished parts around. Each step carries 1/N of the buffer, so every rank sends 2 × (N − 1)/N of the buffer in all.

With two ranks and a 128 MiB buffer, each rank sends 2 × 1/2 × 128 = 128 MiB, in two steps of 64 MiB. This lesson follows one of those steps: 64 MiB from GPU 0 to GPU 1. With eight ranks the same formula gives 2 × 7/8 = 1.75 times the buffer per rank, so the traffic per GPU barely grows as the job gets wider. The number of steps does grow, and each step waits for its slowest link.

Until those transfers finish, the GPUs do nothing. The step ends when the slowest participant finishes. One slow link, one throttled card or one bad cable sets the pace for every GPU in the job. That is the sense in which the network is part of the computer.

Chapter 2 of 12

The ordinary way: sockets

Every byte through both hosts

A socket connection is built for generality. The tensor starts in GPU memory, so first it is copied into host memory across PCIe. The application hands it to the operating system with a write call. The kernel copies it into socket buffers, runs the transport protocol and feeds the network card. On the other side the card interrupts the CPU, the kernel copies the data up to the application, and the application copies it into its GPU.

Count the work for this 64 MiB. On host A the payload is written into host memory once by the GPU copy, then read and written again by the kernel's copy into socket buffers, then read once more by the card as it sends. Host B does the same in reverse. Each host's memory carries the payload several times, and the CPU runs the transport state, the checksums and the copies for every segment.

TCP also cuts the tensor into segments. With a 9,000-byte MTU, each segment carries at most 8,948 bytes of data after 20 bytes of IP header and 32 bytes of TCP header with timestamps. So 64 MiB, which is 67,108,864 bytes, becomes 7,500 segments. Every one of them is handled by software on both sides, even when the card and the kernel batch them together.

Modern kernels do all this well. The CPU still takes part in every flow, and nothing on this path knows that the data started and ended in GPU memory.

Chapter 3 of 12

Register memory, build queues

Pay the cost once, before any data moves

RDMA changes the steady state. Before any transfer the application registers the memory it will use. Ordinary memory moves around and gets paged out, and a device that reads it directly needs addresses that stay put, so registration pins the pages and gives the card the translation it needs. It also produces keys, and a remote side may only touch the memory it holds the right key for.

In the verbs API that RDMA programs use, registration is one call, ibv_reg_mr. It takes a protection domain, a start address, a length and a set of access flags. On node B, the buffer in GPU 1 is registered with IBV_ACCESS_LOCAL_WRITE and IBV_ACCESS_REMOTE_WRITE, which let the card write into it on behalf of a remote peer. On node A the 64 MiB in GPU 0 only needs local access, because node A's own card reads it. Each call returns a memory region with two keys: the lkey for this side's own requests, and the rkey that a peer must quote.

Then the application creates a completion queue with ibv_create_cq and a queue pair with ibv_create_qp. The queue pair carries work requests, and the completion queue reports finished work. This queue pair is reliable connected, type IBV_QPT_RC, which means the cards acknowledge, order and retransmit in hardware. Node B then sends its buffer address, its rkey and its queue pair number to node A over an ordinary connection. NCCL uses its own bootstrap connection for this.

People describe the result as kernel bypass, zero copy and CPU offload. Each phrase needs care. The kernel still allocates, pins and enforces permissions. It just isn't in the path of every packet.

Chapter 4 of 12

Connect the queue pairs

Four states before the first byte

A new queue pair can do nothing. It starts in the RESET state, and the application walks it through three more with ibv_modify_qp before any data moves. INIT binds it to a port of the card and sets which remote operations it will accept. RTR, ready to receive, is where it learns about its peer: the peer's queue pair number, the first packet sequence number to expect, the path MTU and the peer's address. RTS, ready to send, sets this side's own starting sequence number and its rules for retrying.

On RoCE the peer's address is a GID, a 128-bit identifier, which for RoCEv2 carries the peer's IP address. Node A's queue pair 0x1a moves to RTR with destination queue pair 0x2c and the GID for 10.10.0.2. Its path MTU is 4096 bytes, the largest RDMA allows. That is why each data packet in this lesson carries 4096 bytes.

Moving to RTS sets the send sequence number to 1000 and two retry settings. The timeout is an exponent. The card waits 4.096 µs × 2 to that power for an acknowledgment before it tries again. A value of 14 gives 4.096 µs × 16,384, which is 67 ms. The retry count, 7 at most, is how many times it tries again before it gives up. Node B makes the same moves with the roles swapped, and its receive side expects sequence number 1000 first.

When both queue pairs are in RTS the connection exists, held entirely inside the two cards. No kernel is in the data path from here on. A queue pair that hits a fatal error moves to the ERROR state, and the application has to reset it and walk it through the states again.

Chapter 5 of 12

Post the work

A queue and a doorbell, again

To send, the application builds a work request. Its scatter-gather list names local memory as an address, a length and an lkey, here the 64 MiB in GPU 0. The opcode is IBV_WR_RDMA_WRITE. The remote address and the rkey name the destination in GPU 1. The flag IBV_SEND_SIGNALED asks the card to write a completion entry when the request is done. ibv_post_send places the request in the send queue as a work queue element, in memory the card can read.

Then the application tells the card there is work. That is a doorbell, a small write to a register on the card. The register's page was mapped into the process at setup, so no system call is made. The card reads the work queue element and takes the transfer from there, and the application goes back to what it was doing. One work request moves all 64 MiB. The card cuts it into 16,384 packets of 4096 bytes on its own.

The application and the device coordinate through shared structures. The CPU does not treat every packet as a software event of its own. If you have seen how a CPU asks a GPU for a copy, this is the same pattern with a transport engine where the GPU has a copy engine. A queue in memory, a doorbell, and later a completion.

Because this is an RDMA WRITE, the operation is one-sided. Node B posted no receive and runs no code for it. Its card does the whole job on the far end.

Chapter 6 of 12

Straight out of GPU memory

GPUDirect RDMA skips the host

Plain RDMA removes most of the host's network stack from the path. Accelerator work adds one more boundary, because the data starts in GPU memory. Without a direct path it would still be staged through host memory first. GPUDirect RDMA lets the network card reach GPU memory over PCIe as a peer. The card reads the tensor straight from GPU 0's memory and puts it on the wire. The host set the transfer up and controls it. It no longer carries the payload, so its memory bandwidth and its CPU are left alone.

A network card can read GPU memory because the GPU exposes it on PCIe. NVIDIA's GPUDirect RDMA documentation describes how: the GPU's driver maps the memory through a BAR window, and the third-party device reads and writes those bus addresses just as it would host memory. nvidia-smi -q shows how much of that BAR1 window is in use.

Registering GPU memory with the card needs a bridge between the two drivers. For NVIDIA GPUs and Mellanox cards that bridge is the nvidia-peermem kernel module, introduced with CUDA 11.4. It must be loaded by hand. Newer setups can use the Linux dma-buf mechanism instead, when CUDA reports dma-buf support for the device.

The documentation also sets rules for the path. Both devices must share the same PCIe root complex. A path through PCIe switches only performs best. A path through the CPU, inside that one root complex, works, and peer reads may be severely limited. A path across the link between two CPU sockets leaves the root complex, and it may be very slow or unreliable. The IOMMU must be off or in pass-through mode, because the card has to use the same physical addresses the GPU driver hands out. lspci -t shows the PCIe tree.

Chapter 7 of 12

On the wire: RoCEv2

RDMA inside UDP inside IP

RDMA needs a transport under it. InfiniBand is a fabric built for the purpose. RoCEv2 carries the same InfiniBand transport over ordinary routed Ethernet: an IP packet, a UDP header with destination port 4791, and then the base transport header that names the destination queue pair and the packet's sequence number. Because it is IP, operators can build the leaf and spine fabrics they already know and spread traffic over equal paths.

A 64 MiB write becomes 16,384 packets of 4096 bytes. The first is an RDMA WRITE First, which adds the RDMA extended header with the remote address, the key and the total length. The 16,382 in between are RDMA WRITE Middle and carry only the base transport header and data. The last is RDMA WRITE Last. Their sequence numbers run from 1000 to 17383. The field is 24 bits, so it wraps after 16,777,216 packets.

The overhead is small. A middle packet as drawn here is 4,158 bytes: 18 of Ethernet header with its VLAN tag, 20 of IPv4, 8 of UDP, 12 of base transport header, 4,096 of data and a 4-byte invariant CRC. The Ethernet frame check sequence, FCS, adds 4 more bytes on the wire, which the drawing leaves out. That is 4,096 ÷ 4,158 = 98.5 percent data, or 4,096 ÷ 4,162 = 98.4 percent counting the FCS. A 4096-byte payload does not fit the default Ethernet MTU of 1500, so every hop needs jumbo frames.

The UDP source port has a job too. Switches spread flows over equal-cost paths by hashing header fields, and the destination port is always 4791. The card picks a source port per queue pair, so different queue pairs can take different paths through the spine. The IP header's ECN field is set to 10, ECT(0), which tells switches they may mark this packet instead of dropping it.

Chapter 8 of 12

Placed, acknowledged, completed

The far host's CPU never ran

The receiving card checks the key against the memory it was registered for and writes each packet's data straight into GPU 1's memory at the address the first header named. It also checks the sequence number, and it expects them in order. No receive call ran on host B, and no interrupt fired per packet.

Time it. The 16,384 packets put 16,384 × 4,158 bytes on the wire, plus 16 for the first packet's extended header: 68,124,688 bytes. At 400 Gb/s, which is 50 GB/s, that takes about 1.36 ms. Each frame also costs 24 more bytes of wire time: a 4-byte FCS, 8 bytes of preamble and 12 of gap between frames. That is 16,384 × 24 = 393,216 more, 68,517,904 byte times in all, about 1.37 ms. Host B's CPU was idle for all of it.

The receiving card does not need to acknowledge every packet. It may cover a range with one acknowledgment, and the last one covers sequence number 17383. Only then does node A's card know the write is complete, and it writes one entry into the completion queue. The application on host A finds it with ibv_poll_cq, which reads the queue in host A's own memory without a system call.

The entry carries a status. IBV_WC_SUCCESS means the write landed. Anything else names what failed. A bad key or a missing permission shows as IBV_WC_REM_ACCESS_ERR. A peer that stopped answering shows as IBV_WC_RETRY_EXC_ERR. On node B nothing is reported at all, because an RDMA WRITE uses no receive request. If node B must know the data has arrived, the sender adds a message for it, such as an RDMA WRITE with immediate data, which does consume a receive request and does produce a completion on node B.

Chapter 9 of 12

When a packet goes missing

Go back and send it all again

RoCEv2 keeps the InfiniBand transport, and that transport was designed for a fabric that does not drop packets. Its recovery is simple. Each packet carries its sequence number, and the receiver accepts them only in order. Suppose packet 5000 is dropped in the switch. Packet 5001 reaches node B's card, which sees the gap. It answers with a negative acknowledgment, a NAK for a sequence error, that names 5000 as the packet it expected. Node A's card goes back to 5000 and sends everything from there again: 5000, 5001, 5002 and on. This is go-back-N. Packets that arrived after the gap are discarded and sent again.

If no answer comes at all, the timeout from the RTS step applies. After 67 ms without an acknowledgment, the card retries. After 7 retries it gives up. The queue pair moves to the ERROR state, and the application gets a completion with IBV_WC_RETRY_EXC_ERR.

One drop costs far more than one packet. A 4,158-byte packet takes 4,158 × 8 ÷ 400 = 83 ns on a 400 Gb/s wire. Learning about the gap takes a round trip of several microseconds, and everything sent in that time is sent twice. A timeout is much worse, because the flow stalls for 67 ms, and in a collective every GPU waits for the slowest flow.

So RoCE fabrics work hard to avoid loss in the first place. The next two chapters show the two tools: marking packets so senders slow down early, and pausing a sender outright when a buffer is about to overflow.

Chapter 10 of 12

When everyone sends at once

Congestion control is part of compute performance

AI collectives make brutal traffic. Many endpoints start sending at nearly the same instant and many flows aim at the same switch port. Its queue fills. If the switch drops packets, the go-back-N recovery from the last chapter makes tail latency spike. If the network overreacts, links sit idle. So the switch marks packets instead: when a queue grows past a threshold it sets the two-bit ECN field in the IP header to 11, congestion experienced. Nothing is dropped. The receiver sees the mark and sends a congestion notification packet back, and the sender cuts its rate. The control loop widely used for this on RoCEv2 fabrics is called DCQCN.

The switch side is a curve with three settings. Below a queue depth called Kmin nothing is marked. Between Kmin and Kmax the chance of marking rises in a straight line up to Pmax. Above Kmax every packet is marked. The DCQCN paper, from Microsoft and Mellanox at SIGCOMM 2015, marks on the egress queue, the queue a packet waits in before it leaves the switch.

The receiving card is the notification point. When a marked packet arrives for a flow and no notification has gone out for that flow in the last N microseconds, it sends one at once. After that it sends at most one every N microseconds while marks keep coming. The paper's deployment used N = 50 µs, and sent notifications at high priority so they are not lost in the congestion they report.

The sending card is the reaction point. On a notification it cuts its current rate RC to RC × (1 − α/2), where α is its running estimate of how congested the path is. With α at 0.5 the rate drops by a quarter. α rises with each notification and decays while none arrive, on a timer of K = 55 µs in the paper. The rate then climbs back in phases: five steps of fast recovery towards the rate before the cut, then additive increase, then hyper increase, driven by a timer and a byte counter.

Chapter 11 of 12

Pause frames

Priority flow control stops one class, one hop at a time

Priority flow control, PFC, is the blunter tool. It is defined in IEEE 802.1Qbb and works one link at a time. A link carries eight priorities, and RDMA traffic is given one of them, here priority 3. When the switch's ingress buffer for priority 3 on a port fills past a threshold, the switch sends a pause frame back to the sender on that link. The frame names the priorities to stop and how long to stop them, in quanta of 512 bit times. At 400 Gb/s one quantum is 1.28 ns, so the largest value, 65,535, is about 84 µs. The sender stops that priority only. Other traffic on the same link keeps flowing. A frame with a time of 0 lets it resume early.

The switch has to keep headroom: buffer space above the threshold for the bytes already in flight on the cable when the pause goes out, plus what the sender transmits before it reacts. That reserved space is the price of a lossless class.

Pause frames have side effects. A paused port's own queues fill, so the switch behind it may pause too, and congestion spreads backwards through the fabric to flows that never went near the hot port. A flow can wait behind another that is stuck. A loop of pause dependencies can deadlock part of the fabric. A host that stops reading its receive buffers can make its card send pauses without end, a pause storm.

So the usual design is ECN and DCQCN to keep queues short, with PFC as a backstop that should rarely fire. The DCQCN paper notes that marking works on the egress queue while pause frames are sent from the ingress queue, so the marking threshold has to be low enough that senders slow down before any pause is needed.

Chapter 12 of 12

Locality, from process to port

The path starts inside the server

Network diagrams start at the server's edge. The real path starts inside the box. A GPU may share a PCIe switch with the network card, one hop away with full peer bandwidth. Or it may sit under one CPU socket while the card sits under the other, so every transfer crosses between sockets. Nothing fails when you get the slow one.

nvidia-smi topo -m prints a matrix of how every GPU and network card in the server are joined, in short codes. PIX means at most one PCIe bridge between them. PXB means several PCIe bridges, without going through the CPU's host bridge. PHB means the path goes through a PCIe host bridge, usually the CPU. NODE means it crosses between host bridges inside one NUMA node. SYS means it crosses the link between NUMA nodes, such as QPI or UPI. NV with a number means the GPUs are joined by that many NVLinks.

NCCL reads the same topology and decides whether to use GPUDirect RDMA for each GPU and card pair. NCCL_NET_GDR_LEVEL sets the farthest distance it accepts, with the same names. LOC never uses it. PIX uses it only on the same PCI switch, PXB through PCI switches, PHB within one NUMA node with traffic through the CPU, and SYS even across NUMA nodes. Left unset, NCCL picks a value for the platform. NCCL_DEBUG=INFO prints what it chose. When it decides the path is too far, it stages data through host memory, and nothing reports an error.

A network problem can then look exactly like a training problem: collective phases get longer, GPUs wait at their synchronization points, utilization drops, and every individual program is fast. So measure in layers: PCIe peer access, host to device bandwidth, RDMA bandwidth, GPUDirect bandwidth, the collective, the application.

What to keep

Where the state lives, the network reaches

Distributed AI is a communication system as much as a compute system. The ordinary socket path sends every byte through both hosts, with four copies and CPU work per packet. RDMA has the application register memory and post work to queues, and the network card does the transport in hardware. GPUDirect RDMA lets that card read and write GPU memory directly, so the path matches where the valuable state lives. RoCEv2 carries it over routed Ethernet in UDP port 4791. From there on the fabric's behavior under bursts is compute performance: marks, notifications and rate cuts decide how much of a link is usable, and the wiring inside each server decides how fast the first and last hop are. The layers can be designed apart. They can't be measured apart.
