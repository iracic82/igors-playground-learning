BNK and gateways

Inside the LLM gateway

An agent's calls, byte by byte

An agent is a program that calls a model in a loop. It sends a task, the model asks for a tool, the agent runs the tool and sends the result back, and so on until the job is done. One task can be ten calls or a thousand, and nobody is watching each one. The LLM gateway is what stands between that loop and the models. This lesson follows one agent through nine turns of its loop and opens every message of turns 1, 2, 3, 4 and 9. You will see the gateway swap the agent's key for a real one, hold back budget before each call, send one turn to a GPU in this factory and the next to another company's model, rewrite the request into that provider's format and the answer back again, survive the provider failing, and finally stop the agent when its budget is gone. In this factory the gateway is the BNK LLM Gateway, BNK's own gateway. Its product name is not settled. F5's engineers avoid calling it an AI gateway because F5 already sells a different product, F5 AI Gateway, under that name, yet the switch that turns it on and the profile it attaches are still called AI Gateway. The factory scene labels its place with that older name. This lesson calls it the LLM gateway, or just the gateway. The same jobs can also run in the BNK data plane as policy, which the guardrails lesson shows. A last group of three chapters brings a second client to the same address: a developer's coding assistant that speaks Anthropic's Messages format, which the gateway translates for the model on our own GPUs and back.

Chapter 1 of 15

The agent's first turn

A task, and the tools it may use

An agent is a program that calls a model in a loop, and one click by a person can start many calls. F5's own example is a travel planner in which an orchestrator and five specialist agents turn one trip search into 5 to 12 model prompts. Here one agent has been asked to find out why a customer was charged twice. It sends its first request to the factory at api.northlight.example, the same address and the same path a chat app would use: POST /v1/chat/completions.

The body is a chat request with one addition, a list of tools. Each tool is a function name, a description and a JSON schema of its arguments. The model can't run a tool. It can only answer with a request to run one, and the agent does the running. Here the list has one entry, lookup_invoice, which takes a customer id and a month. The whole body is 8,890 bytes: about 2,000 tokens of instructions, a one-line task and the tool definition, 2,140 tokens once counted.

The agent identifies itself with a bearer key, nl-agent-…c21d, issued for this agent alone. TMM ends the TLS session at 203.0.113.80, adds the caller's address as x-forwarded-for and passes the request to the gateway Pod at 10.244.4.31:8080. From here on every decision about this call is the gateway's: who is calling, what they may use, what it may cost and which model answers.

Chapter 2 of 15

A virtual key, or a token

Who is calling, settled before anything else

The gateway starts with the key. It is a virtual key: a name the gateway invented, which stands for this agent and is worth nothing at any model provider. Behind it is a small tree of four levels: the organization northlight-labs, the team billing-team, the user svc-invoice-agent and the key itself. A user can hold several keys, for example one per tool or per agent, so that each can be limited and revoked alone. An unknown or revoked key gets 401. Revoking this key stops this one agent and nothing else.

A caller can also present a JSON Web Token from the company's identity provider in place of a key. The gateway validates it before anything else. It finds the signing key in a named JWK configuration by the kid field in the token's header, checks the issuer against a list and allows a clock skew set in seconds, 30 in the build the owner was shown. Keys and tokens work side by side on one gateway.

In that build of BNK's own gateway a token proves who the caller is and nothing more. Its claims are not used to decide which models the caller may use. A user who arrives by token lands in a default organization and a default team, and an administrator scopes models there. The console has three roles: admin, team admin and member. A member sees only their own usage and manages only their own keys. Mapping groups from the identity provider to models was a request from the field and had not been built.

Chapter 3 of 15

Scope, then a reservation

Two checks before any model is called

With the caller known, the gateway checks the scope: the list of model names this key may ask for. The key is scoped to northlight-chat and northlight-frontier, and it asked for northlight-chat, so it passes. A model outside the scope gets 403 with the code model_not_allowed. The same scope decides what GET /v1/models lists for this key, so an agent can't even see a model it may not use. An administrator can also pause a model in the catalog, and a paused model answers model not found to every caller.

Then comes the budget, and here the gateway is careful. It doesn't know yet what the call will cost, because the answer isn't written. So it holds back the most the call could cost: the 2,140 prompt tokens plus the 512 that max_tokens allows, 2,652 in all. The key has a monthly budget of 200,000 tokens and has used 172,400. With the reservation that becomes 175,052, which fits. If it didn't fit, the call would be refused with 429 and the code budget_exceeded before any model spent anything.

Budgets exist at every level of the tree: organization, team, user and key. Each can be counted in tokens or in money, over an hour or a month, and every level must have room. Reserving first is what makes the limit hold when calls overlap. Ten calls in flight at once have each reserved their worst case, so together they can't overrun the budget. The price of that safety is headroom held for the length of each call, 474 tokens too many for this one.

Chapter 4 of 15

A model on our own gpus

The request never leaves the factory

The name northlight-chat is an alias. The gateway's catalog says it means qwen3-32b, and that this model is served here, behind BNK. To the gateway a provider is a URL with a format and a key. So the factory's own inference listener, inference.northlight.internal, is registered as one more provider. That listener is an internal address on the same BNK, so the request doesn't leave the cluster and come back in.

The gateway rewrites the model field, which shortens the body from 8,890 to 8,884 bytes, drops the agent's Authorization header and sends the request to BNK. No key goes with it, and the agent's key never reaches a model server. The division of work is fixed at this point. The LLM gateway chose the model. Which GPU serves it is BNK's decision, and the gateway has no say in it.

TMM holds the request, asks the endpoint picker over gRPC ext_proc and gets one Pod address back: 10.244.2.22:8000, gpu-2. The picker chose it because gpu-2 already holds this agent's instructions in its KV cache. Every agent of this kind starts with the same 2,000 tokens, so once one worker has read them the picker keeps sending these agents there while it has room. An alias can also be left open, so that a router chooses the model for each request. In BNK that router is an external service called over the same ext_proc protocol. It is given the request and the models the caller may use, and it answers with one of them.

Chapter 5 of 15

The model asks for a tool

Not an answer, a request

The model reads the task and decides it needs the invoices. It doesn't write text. It writes a tool call: the id call_8f2k, the name lookup_invoice and the arguments as a JSON string. In the stream this arrives as chunks whose delta holds tool_calls where a chat answer would hold content. The first chunk carries the id and the name. The following ones carry pieces of the arguments string, which the agent joins before it parses them.

The chunk that ends the call carries finish_reason tool_calls. One more chunk follows with an empty choices list and the usage object, because the agent asked for include_usage, and the stream closes with data: [DONE]. The gateway passes all of it through unchanged, because the agent already speaks this format. It does read it on the way. The tool's name and arguments are in plain sight, which makes the gateway a natural place to log tool use and to refuse a tool an agent shouldn't have.

Then the gateway settles the turn. It held back 2,652 tokens. The usage object says 2,140 prompt tokens and 38 completion tokens, 2,178 in all. The difference, 474, goes back into the budget, and the key's month stands at 174,578 of 200,000. The whole turn took about 500 ms: about 40 ms of prefill for the 140 tokens gpu-2 had not seen, then 37 decode passes at about 12.4 ms each for the rest of the 38 tokens. The agent now parses the arguments, runs its own lookup_invoice for customer 4471 and October 2026, and gets two invoices for the same plan.

Chapter 6 of 15

The second turn is bigger

Every turn resends everything

The agent has run the tool. Now it calls again, and it has to send the whole story: its instructions, the task, the model's tool call as an assistant message and the tool's result as a message with the role tool. That last message carries tool_call_id call_8f2k, which is how a result is matched to its call when several tools run at once. The API keeps no memory between calls, so each turn of the loop is longer than the last: 4 messages and 2,410 tokens now, up from 2 messages and 2,140.

The gateway reserves again, for a bigger prompt this time: 2,410 + 512 = 2,922 tokens, which takes the key from 174,578 to 177,500. Growth like this is why agents need budgets more than people do. If every turn adds about 270 tokens, the tenth turn alone carries about 4,570 prompt tokens, and the ten prompts together come to 33,550 tokens for a job whose useful content was a few hundred.

Now look at what the GPU sees. The first 2,176 tokens of this prompt are what gpu-2 read and wrote a moment ago: 136 blocks of 16 tokens, about 570 MB of keys and values still in its KV cache. The picker sends the turn to gpu-2 again, and prefill only has to read the 234 new tokens. On gpu-1 it would have read all 2,410. Round robin over three workers would have sent this turn elsewhere two times out of three. An agent loop is the best case for cache-aware routing. The 2,176 assumes the chat template renders the assistant's tool call back into exactly the tokens the model generated. Templates often reformat a tool call, for example the spacing of its JSON arguments. Then reuse stops where the two differ, at the latest at block 133, which is 2,128 tokens, and prefill reads 282 tokens in place of 234.

Chapter 7 of 15

A harder question, another company's model

The gateway translates the request

The invoices show two charges for one plan, and the agent wants a stronger model to reason about refunds. For its third turn it asks for northlight-frontier. That alias points outside the factory, at a model hosted by another company, and that company's API is a different format. The request goes to POST /v1/messages. The instructions move out of the message list into a top-level system field. A tool call becomes a content block of type tool_use inside an assistant message, and a tool result becomes a tool_result block inside a user message.

Smaller differences matter as much. Tool arguments are a JSON string in the OpenAI format and a JSON object, called input, in this one. A tool's schema is called parameters in one and input_schema in the other. max_tokens is optional in one and required in the other. The provider also wants a version header, anthropic-version, on every call. The agent knows none of this and doesn't change a line. One place translates, and every agent behind it is spared the work.

The gateway also swaps keys. The agent's virtual key stays inside the gateway. The provider's real key, which only the gateway's secret store holds, goes out in its place. The call leaves the factory over TLS from 203.0.113.91, an egress address that belongs to this tenant alone, so the provider can allow that one address and its logs show which tenant called. Before sending, the gateway held back 2,655 + 512 = 3,167 tokens.

Chapter 8 of 15

Translate the stream back

Different events in, the same chunks out

The provider streams its answer in its own event format, and every event has a name. message_start opens the message and already carries the input token count, 2,655. content_block_start opens a block. content_block_delta events carry the text piece by piece. content_block_stop closes the block. message_delta carries the stop reason and the output token count, and message_stop ends the stream. Ping events can appear anywhere in between and carry nothing.

The agent expects chat.completion.chunk lines ending in [DONE]. So the gateway translates in the other direction too, event by event, as they arrive. It can't wait for the whole answer, because the agent is reading a stream. A text_delta becomes a chunk with delta.content. A tool_use block becomes delta.tool_calls, and its input_json_delta pieces become pieces of the arguments string. The stop reason end_turn becomes finish_reason stop, and message_stop becomes data: [DONE]. The provider's event is 118 bytes on the wire and the chunk the agent receives is 152.

At the end the gateway has the provider's counts from two events: 2,655 input tokens and 164 output tokens, 2,819 in total. It turns them into money with its price list. The list holds a price per million input tokens and per million output tokens for every model, and an administrator can replace any of them with the company's negotiated price. At the illustrative prices of $3 and $15 per million, this turn cost 2,655 × 3 ÷ 1,000,000 + 164 × 15 ÷ 1,000,000 = $0.0104. The key's month stands at 180,037 tokens.

Chapter 9 of 15

The provider fails, the agent doesn't notice

Two deployments behind one alias

The agent's fourth turn goes to the same hosted model, and this time the provider is overloaded. It answers 529 with the error type overloaded_error, 180 ms after the request left. In the gateway's catalog the alias has more than one deployment: the same model reached a second way, for example through another region or another cloud. Each deployment has a priority and a weight. Priority decides which one is tried first. Weight splits traffic among deployments of equal priority, so an operator can send most calls to the provider with the better contract.

The gateway doesn't pass the error on. It marks deployment 1 as failing for now and sends the same request to deployment 2 at 192.0.2.61, in whatever format that one needs. The agent sees one request and one answer that came 180 ms later than usual. Nobody had to teach the agent about retries, regions or a second set of keys.

This works cleanly only before the first token has gone out. A stream that has started can still fail, because the provider can send an error event with overloaded_error in the middle of it. By then the gateway has forwarded part of an answer and can't take it back, so the failure reaches the agent as a broken stream. The safe pattern for agents follows from that. Retry the whole turn, and make every tool safe to call twice.

Chapter 10 of 15

What every call leaves behind

A record for the budget, a log line for the operator

Every call ends with a record: which key, which user and team, which model and deployment, how many prompt and completion tokens and what it cost. This chapter opens the record for turn 3, which is 300 bytes of JSON. The gateway did not wait until now to send it. It went to the usage service at 10.96.40.12, where the budget counters live, when turn 3 settled at about 5,200 ms, so turn 4's reservation at 8,000 ms was already checked against it, and so is every reservation after. The record appears here at 11,000 ms only because the lesson stops to look at it after the failover. For a provider that sells tokens these records are the raw material of the invoice, counted per key, per team and per organization.

The gateway's console reads the same data. Its pages follow the questions an operator asks: a dashboard, logs, analytics, spend per team and per organization, and usage per model. A member sees only their own usage and keys. The console sits on a REST API, so a service provider can build its own branded portal on the same data.

The gateway is not built to be the archive. It streams its log lines out over HSL, BIG-IP's high-speed logging, to a store the operator runs, such as an Elasticsearch stack or a ClickHouse database. The operator decides how long the data lives. Prices come from a built-in sheet of public prices per model, in dollars per million input and output tokens, and an administrator can override any of them. That is why two tenants can pay different amounts for the same 2,819 tokens.

Chapter 11 of 15

The loop runs out of budget

A hard stop before any model is called

The records add up. The agent keeps looping. Turns 4 to 8 use 18,033 tokens, and the key's month stands at 198,070 of 200,000. The ninth turn carries 18 messages and a prompt of 4,358 tokens, twice the size of the first, in a body of 17,509 bytes that needs two HTTP/2 DATA frames.

The gateway does what it did every time. It counts the prompt, adds max_tokens and tries to hold back 4,358 + 512 = 4,870 tokens. Only 1,930 are left. The reservation fails, and the gateway answers 429 with the code budget_exceeded one millisecond after the request arrived. No model was called, no GPU read the 4,358 tokens and no provider charged for them. The check uses the amount held back and never the amount spent so far, so calls in flight at the same moment can't slip past it together.

This is the guard that matters most for agents. A person stops asking at some point. A loop with a bug does not. A limit on requests per minute would not catch it, because nine turns in thirty seconds is a modest request rate. Counted in tokens the same loop used 25,670 tokens in half a minute. F5's material states the change of unit plainly: tokens per minute and tokens per day in place of requests per minute. Without a token budget the loop runs until someone reads the bill.

Chapter 12 of 15

Three kinds of gateway, and how this one is switched on

Where the gateway sits among the others

The word gateway covers three different products, and F5's field material separates them by where they started. An API-native gateway is an API management product that learned about tokens. It suits a company whose AI use is mostly hosted models behind API management it already runs. An AI-native gateway was built for model traffic: one API across providers, budgets and chargeback, fallback, guardrails and caching. An inference-native gateway is the Kubernetes Gateway API with the inference extension. It knows queues and KV caches and decides which model server gets a request.

The three stack. A company that only buys hosted models needs the first two at most. A factory that runs its own GPUs puts the inference-native gateway under the AI-native gateway, and a hybrid one has a single AI-native gateway in front of hosted and self-hosted models alike. This lesson's factory is the hybrid case. The BNK LLM Gateway played the AI-native part in every chapter, and BNK with its endpoint picker played the inference-native part in the two turns that stayed on gpu-2.

In BNK the gateway is switched on in the CNEInstance, the platform's top-level object, with spec.aiGateway.enabled set to true. That starts the console and its admin API. Each Gateway object can then carry one AI Gateway profile, the engineers' name for it, the way a virtual server carries a profile. The profile is a list of switches: rate limits, budget enforcement, observability, model routing, prompt caching, parameter governance and provider translation. Tenancy follows from that shape. One tenant is one Gateway with its own profile, its own provider keys and its own token issuer, so a token issued for one tenant is refused at another tenant's gateway.

Chapter 13 of 15

A second client speaks Anthropic's format

One address, two request formats

The agent's loop has stopped, and a developer on the same team sets out to find the bug that drained its budget. She works in Claude Code, Anthropic's coding assistant. It runs on her laptop and calls a model in a loop much like the agent did. Claude Code speaks Anthropic's Messages API. It posts to /v1/messages, puts its instructions in a top-level system field and expects named events back. The gateway takes that format on the same address as the agent's. api.northlight.example at 203.0.113.80 answers POST /v1/chat/completions in the OpenAI format and POST /v1/messages in Anthropic's format, behind the same keys, budgets and catalog. F5's blog post on the platform says the Anthropic Messages API works too. In the engineering preview of release 2.4.1, OpenAI Chat Completions and Anthropic Messages are the two formats the gateway speaks, and it translates between them in both directions. Providers in the formats of Bedrock, Gemini, Azure and Vertex are planned for 2.5, because each new format adds a row and a column to the translation table. The OpenAI Responses API, which a client calls in place of Chat Completions, is also planned for 2.5.

A few settings on the laptop point Claude Code at the gateway. ANTHROPIC_BASE_URL is https://api.northlight.example. ANTHROPIC_AUTH_TOKEN holds her virtual key, nl-dev-…7b0e, and Claude Code sends it as Authorization: Bearer, the same header the agent used. The other variable, ANTHROPIC_API_KEY, sends the key in an x-api-key header instead. A key in the variable whose header the gateway doesn't read arrives where nobody looks, and the answer is 401. ANTHROPIC_MODEL is northlight-chat, the alias the agent used. CLAUDE_CODE_MAX_OUTPUT_TOKENS=8192 sets max_tokens on most requests. Without it, Claude Code's default for a model ID it doesn't know is 32,000, and its cap is 128,000. Claude Code's documentation suggests a one-token test before the first session: a POST to $ANTHROPIC_BASE_URL/v1/messages with the header anthropic-version: 2023-06-01 and a body asking for max_tokens 1. The documentation's example body names a Claude model, so here the body must say model northlight-chat instead. A 200 then proves the address, the key and the alias together. With ANTHROPIC_AUTH_TOKEN set, Claude Code also runs its background tasks on the main model, so every call of the session asks for northlight-chat.

The key sits in the same tree as the agent's: northlight-labs, billing-team, the user dev-ana and a key named claude-code. A user can hold one key per tool, so this one can be limited and revoked without touching her others. It is scoped to northlight-chat only, and its budget is counted in money: $5.00 a month. A key over a money budget gets the same 429 as a key over a token budget. The reservation works the same way, converted with the price list. At illustrative internal prices of $0.40 per million input tokens and $1.20 per million output tokens for northlight-chat, the 19,840-token prompt and the 8,192 tokens max_tokens allows cost at most 19,840 × 0.40 ÷ 1,000,000 + 8,192 × 1.20 ÷ 1,000,000 = $0.0178. The key has spent $3.12 this month, so the reservation brings it to $3.1378.

Claude Code knows the names of Anthropic's models, and northlight-chat isn't one of them. Two things follow, and both matter on a GPU. First, Claude Code assumes a context window of one million tokens for a name it doesn't know, and compacts the conversation only as it nears that size. qwen3 is served with --max-model-len 40960, the max_position_embeddings in Qwen3-32B's config.json. Setting CLAUDE_CODE_MAX_CONTEXT_TOKENS=40960 gives Claude Code the real window, so it compacts the conversation before vLLM has to refuse it. A prompt longer than 40,960 tokens gets a 400 from vLLM whose message names the 40,960-token limit. When only the prompt plus max_tokens is too long, current vLLM lowers max_tokens to what is left of the window. This first request needs 19,840 + 8,192 = 28,032 of the 40,960. Second, for a name it doesn't know Claude Code sends every request field that current Claude models accept, such as thinking, effort and context management, and it sends some reminders as messages with role system in the middle of the conversation. None of these exist in the format the GPU speaks, so the translation has to drop them or map them.

Before the first request Claude Code sends HEAD /api/hello to warm the connection. The gateway may refuse it, and nothing breaks. Inference requests arrive as POST /v1/messages?beta=true, so a gateway matches on the path and ignores the query. Each carries anthropic-version: 2023-06-01, an anthropic-beta header listing the capabilities the request uses, and x-claude-code-session-id, one id for the whole session, which a gateway can use to group a session's calls without reading their bodies. Claude Code can also post to /v1/messages/count_tokens for an exact count of its context. That endpoint is optional. Without it Claude Code estimates from the number of characters, and its /context view shows approximate counts.

Chapter 14 of 15

Anthropic in, OpenAI out to our GPU

The translation of turn 3, run backwards

The model behind northlight-chat is qwen3-32b on vLLM, registered with the gateway as an OpenAI-format provider at inference.northlight.internal. So this time the gateway translates the other way from turn 3. Its input is an Anthropic request and its output is a Chat Completions request. Every field has a place. The top-level system field, a string or a list of text blocks, becomes the first message of the list, with role system. A text block becomes message content. An assistant message's tool_use block becomes an entry in tool_calls, with type function, the block's name, and its input object written out as a JSON string in function.arguments. A tool_result block in a user message becomes a message of its own with role tool, and its tool_use_id becomes tool_call_id. Two results in one user message become two tool messages.

The tools and the controls map just as directly. Each tool's input_schema becomes function.parameters inside an entry of type function. stop_sequences becomes stop. tool_choice of type auto stays auto, any becomes required, none stays none, and a named tool becomes a named function. disable_parallel_tool_use: true becomes parallel_tool_calls: false. max_tokens, which Anthropic's format requires, carries over as max_tokens 8,192. stream: true stays, and the translator adds stream_options with include_usage: true, so that vLLM reports the token counts in a last chunk. The model field becomes qwen3-32b. These are the rules vLLM's own Anthropic endpoint applies in its source, vllm/entrypoints/anthropic/serving.py. The gateway's own translation table was promised to the field and hasn't been published, so the rows in the beats are the two public formats.

Some of what Claude Code sends has no counterpart. anthropic-version and anthropic-beta are instructions to Anthropic's API, and vLLM has no use for them. They are forwarded unchanged only when the upstream speaks Anthropic's format. cache_control markers ask Anthropic to cache a prefix. vLLM does that without being asked: with prefix caching on, a prompt that starts with blocks already in GPU memory skips their prefill. thinking, output_config.effort and context_management have no Chat Completions fields. A translator drops them or maps them onto the model's own switches, which is what vLLM's endpoint does with thinking for Qwen3. Which of these the BNK build drops and which it maps was not shown to the owner. A field that does slip through to vLLM is ignored, and vLLM names it only in a debug log line, so a translation gap shows up as a setting that silently has no effect.

With two formats in and two out there are four routes, and this lesson has now taken three of them. OpenAI in, OpenAI out: the agent's turns 1 and 2 to qwen3, where the gateway only rewrites the model and drops the key. OpenAI in, Anthropic out: turn 3, translated in the two chapters about the hosted model. Anthropic in, OpenAI out: this request. The fourth is Anthropic in, Anthropic out. Had dev-ana's key been scoped to northlight-frontier, her requests would go to the hosted model with nothing translated. The gateway would swap the key and pass anthropic-version and anthropic-beta exactly as they came. Claude Code's documentation tells gateway builders to forward anthropic-beta verbatim and never to allowlist its values, because the set changes with Claude Code releases.

From here the path is the agent's path. The gateway sends the Chat Completions request to inference.northlight.internal, TMM asks the endpoint picker, and the picker answers 10.244.1.21:8000, Pod qwen3-6f7d9c8b4-x7k2p on gpu-1. No worker holds Claude Code's 19,840-token prefix yet, so there is no cache hit to follow, and the picker goes by load. gpu-1 has the most free KV cache. The next turn of this session starts with the same instructions and tool list, so it will find them on gpu-1. Qwen3 writes a tool call as text in the Hermes style. vLLM turns that text into tool_calls only when it runs with --enable-auto-tool-choice and --tool-call-parser hermes, the flags Qwen's documentation gives for vLLM. Without them the tool call would reach Claude Code as plain text, and no tool would run.

Chapter 15 of 15

The stream goes back as Anthropic events

Chunks in, named events out

vLLM answers the way it answered the agent: server-sent events, each a data: line holding a chat.completion.chunk. The first chunk carries delta.role assistant. Then pieces of text arrive in delta.content. The model decides to search the code, so later chunks carry delta.tool_calls, first with the call's id and the function name Grep, then with pieces of the arguments string. The last choice chunk has finish_reason tool_calls. Because the gateway asked for include_usage, one more chunk follows with an empty choices list and usage: prompt_tokens 19,840, completion_tokens 610 and total_tokens 20,450. Then comes data: [DONE].

Claude Code expects the same event sequence the hosted provider sent in the agent's turn 3, and the gateway builds it as the chunks arrive. The first chunk becomes event: message_start, with a message of type message, role assistant, empty content, stop_reason null and the input token count, which the gateway knows from its own count of the prompt. The first text piece opens a block: content_block_start at index 0 with type text. Each piece after it becomes a content_block_delta with a text_delta. When the first tool_calls piece arrives, the text block closes with content_block_stop, and content_block_start opens index 1 with type tool_use, the call's id, the name Grep and an empty input. Each piece of the arguments string becomes an input_json_delta with partial_json, so Claude Code assembles {"pattern": "max_tokens", "path": "agent/loop.py"} from the pieces. finish_reason tool_calls becomes stop_reason tool_use in a message_delta, which also carries output_tokens 610. data: [DONE] becomes event: message_stop. An Anthropic stream has no [DONE] line.

The other stop reasons map the same way. finish_reason stop becomes end_turn. length, which means max_tokens ran out, becomes max_tokens, and Claude Code then knows the answer was cut short. If one of the request's stop_sequences matched, stop_reason is stop_sequence and the field stop_sequence names the string that matched. vLLM's own converter adds one rule worth copying: when max_tokens cut the answer short, the stop reason is max_tokens even if a tool call had begun, so the client never runs a half-written call.

The translation has to keep pace with the stream. Claude Code reads each event as it arrives, so a gateway that buffers the answer until it is complete makes Claude Code stall. It also needs the whole sequence through message_delta and message_stop. A stream that ends cleanly after a block has started and before message_delta counts as a dropped connection, and Claude Code reports that the response above may be incomplete. Long silences are the third trap. Claude Code abandons a stream when no bytes reach it for longer than its idle timeout. From an Anthropic upstream, ping events fill those silences, and a gateway that strips them can trip that timeout. A Chat Completions stream has no ping event, so a translator that wants to fill a long prefill on a busy GPU with bytes has to send ping events of its own.

When the stream ends the gateway settles in dollars. The actual cost is 19,840 × 0.40 ÷ 1,000,000 + 610 × 1.20 ÷ 1,000,000 = $0.0087. It releases the other $0.0091 of the reservation, and the key's month stands at $3.1287 of $5.00. Claude Code runs Grep on the laptop and sends the result back as a tool_result block in its next request. On the way to the GPU that block becomes a message with role tool, and the prompt starts with the 19,840 tokens gpu-1 already holds in its KV cache. The record for this call names the key, the user, billing-team, the model qwen3-32b and the tokens, like the agent's records. In the console the developer's spend and the agent's spend sit side by side under billing-team, one counted in dollars and one in tokens.

What to keep

One format in, any model out

The agent spoke one format to one address with one key, and behind that the gateway did everything else. It turned a virtual key into an identity with budgets at four levels. It held budget back before each call and settled it after. It sent one alias to a GPU in this factory, where the growing conversation kept hitting the KV cache, and another alias to a hosted model, translating the request and the stream in both directions and using a key the agent never saw. It hid a provider failure behind a second deployment. And it stopped the loop when the budget ran out. For a person these are conveniences. For an agent, which never gets tired and never reads the bill, they are the controls. A coding assistant that spoke Anthropic's format used the same address, the same tree of keys and the same GPUs, with the translation run the other way.
