GPU and hardware

Seeing without slowing down

Where you watch from decides what it costs

Everything known about how CUDA drives a GPU came from one ability: catching each doorbell write and reading the command it points at. That sounds easy. The doorbell is one 4-byte store to a known address. In practice the obvious way of watching it slows copies from 55 GB/s to 0.02 GB/s, and the next most obvious way is fast and sees an empty ring. The method that works diverts the store into ordinary memory, traps it with a CPU debug register, reads the ring before the GPU has been told, and only then passes the store on. It caught 174 doorbells out of 174 with no change in copy speed. Teams that run inference want the same thing from their stack, and they face the same two ways of getting it wrong. This lesson follows the doorbell work step by step on gpu-2, then carries its rule to the front of the factory.

Chapter 1 of 13

The thing to watch

One store, to one address

Inside gpu-2 the model server asks the GPU for a copy with four writes to memory. First it writes the commands into a pushbuffer, a block of ordinary host memory. For a 256 MiB copy the whole command is ten methods in 15 words, 60 bytes: a source address and a destination address, each written as an upper and a lower half, a length, a launch, a semaphore address in two halves, a semaphore value and a second launch that only releases the semaphore. Second it writes an 8-byte entry into the GPFIFO ring that points at that pushbuffer. In this setup the ring sits in the GPU's own memory, its HBM, and the CPU writes it through a BAR1 mapping, a window that exposes GPU memory to the CPU. Only the pushbuffer stays in host memory. Third it moves the ring's write index, GPPut, forward by one. GPPut lives in a small per-channel page called USERD, at offset 0x8c. USERD also sits in HBM and is written through BAR1. Fourth it stores a 32-bit value, the channel's work-submit token, to the doorbell. On Hopper the doorbell is the 4 bytes at offset 0x90 of a 64 KiB register window, the HOPPER_USERMODE_A aperture, that the driver mapped into the process.

The first three writes are silent. The GPU does not look at the ring until the fourth one arrives. The doorbell itself carries no work. It names the channel that has some, and the GPU's front end, the PBDMA unit, then reads the ring entry from its own memory and fetches the pushbuffer from host memory over PCIe, all by itself.

So an observer who wants to know what CUDA really sends needs to hear about that one store, and then read the ring entry and the 60 bytes behind it while they are still in place. The store is the whole event. Everything interesting hangs off it. With nobody watching, a large device-to-host copy on the H100 PCIe used for these measurements runs at about 55 GB/s.

Chapter 2 of 13

The kernel never sees a copy

Zero system calls on the hot path

The first idea for watching what a program does is to watch its calls into the kernel. For a copy that finds nothing. On an H100 PCIe a test program did one 256 MiB host-to-device copy to fill a buffer and then 11 timed device-to-host copies, 12 copies in all. Setup took 361 calls into the resource manager, the main part of nvidia.ko, 87 calls into nvidia-uvm.ko and 237 messages to the GSP firmware on the GPU. The 12 copies took zero of each. They took 12 doorbells and 12 pushbuffer submissions. Teardown took 3 resource manager calls, 2 UVM calls and 183 firmware messages.

During the copies only the top and the bottom layers work. The library writes bytes to memory it shares with the GPU and pokes one register, and the GPU does the rest. The driver has no record that a copy happened. Over the whole run the library made 192 control calls of 68 kinds. They ask for the chip's name, its copy engines and its memory layout, and not one of them is about a transfer.

Watching the library from inside its own process is harder than it looks too. A shim loaded with LD_PRELOAD can wrap the C library's open and mmap. libcuda opens and maps /dev/nvidia0 with raw system call instructions that never pass through those wrappers, so the hook never fires for the most important file. The shim has to find the doorbell another way, by scanning /proc/self/maps for a writable 64 KiB mapping backed by /dev/nvidia0. Kernel tracing and strace can both be left aside. The doorbell store is the only place a copy shows up at all.

Chapter 3 of 13

What the firmware is told

420 messages, and not one of them is a copy

On Hopper most of the resource manager runs on the GPU itself. GSP, the GPU System Processor, is a RISC-V core on the die, and it runs a closed, signed firmware called GSP-RM. nvidia.ko keeps a thinner CPU side of the resource manager. When that CPU side needs the firmware, it writes a message, an RPC (remote procedure call), into a queue in host memory that both sides can read, then moves the queue's head register on the GPU so the firmware picks it up. Every message carries a function number. The numbers are public in the open kernel module, in rpc_global_enums.h: FREE is 10, DUP_OBJECT is 21, GSP_RM_CONTROL is 76 and GSP_RM_ALLOC is 103.

To count those messages, the series rebuilt the open kernel module with one extra trace call, nv_trace_printf, which hands its text to the kernel's ftrace_vprintk. It sits at three choke points: where the driver allocates an object, where it runs a control command and where it sends an RPC. Each event becomes one line with a fixed shape: a version tag mc1, a category, an event name, then key=value pairs. The line rm/alloc id=2012 hclass=0xc86f root=0xc1d00051 parent=0x5c000015 new=0x5c00001c records a new object of class 0xc86f, HOPPER_CHANNEL_GPFIFO_A, the channel that copies are later submitted on. It sits under the client handle 0xc1d00051, its parent is 0x5c000015, and the driver hands back the new handle 0x5c00001c. The line gsp/rpc_tx mode=sync func=103 name=GSP_RM_ALLOC len=64 records a 64-byte message to the firmware, function 103, sent in sync mode, where the driver waits for the firmware's reply before it returns to the library.

One whole run of the 12-copy test sent 420 RPCs. That is the 237 of setup plus the 183 of teardown, with none during the copies. By kind they were 151 FREE, 122 GSP_RM_ALLOC, 118 GSP_RM_CONTROL and 29 DUP_OBJECT, and 151 + 122 + 118 + 29 = 420. GSP_RM_ALLOC forwards an object the library created when the firmware needs its own record of it, as it does for the channel above. Not every resource manager call becomes a message. Setup made 361 resource manager calls and sent 122 GSP_RM_ALLOC messages. DUP_OBJECT gives an object that already exists a second handle under another client session. The driver's NV_ESC_RM_DUP_OBJECT call takes a source client and object and a destination client and parent for exactly this. FREE removes one object from the firmware's records. 122 allocations plus 29 duplicates is 151, exactly the number of FREE messages. That is what you would see if every object the firmware learned about was freed once at the end. Equal totals alone do not prove each free matched one of those objects. The 151 frees are teardown work, and the 183 teardown messages leave room for 32 others.

Control commands are where the library asks questions and sets options. It issued 192 RM_CONTROL ioctls, the driver's control call, spread over 68 different command numbers. A command number packs three fields, as ctrlxxxx.h defines them: the class in bits 31 to 16, a category in bits 13 to 8 and an index in bits 7 to 0. Take the traced line rm/control cmd=0x20800110 hclient=0xc1d00051 hobject=0x5c000003 params_size=68. Class 0x2080 is NV20_SUBDEVICE_0, the object that stands for one GPU. Category 0x01 is the GPU group. Index 0x10 picks NV2080_CTRL_CMD_GPU_GET_NAME_STRING in ctrl2080gpu.h, which returns the GPU's name. Its parameter block is a 4-byte flags word and a 64-byte ASCII buffer, 4 + 64 = 68 bytes, which is the params_size on the line. The other commands ask about the copy engines, the memory layout and the graphics topology. Not one of the 68 command numbers has anything to do with moving data. A copy has no control command at all.

192 control calls from the library and 118 control messages to the firmware do not match, because the driver forwards only some controls. In the resource manager source, a control marked RMCTRL_FLAGS_ROUTE_TO_PHYSICAL is, in the source's words, directly forwarded to the physical object when it is called on the CPU side, and the physical object lives in GSP-RM. A control without that flag is answered inside nvidia.ko from state it already holds. The two counts are not a one-to-one map, since the driver also sends controls of its own while it builds objects, so the gap of 192 - 118 = 74 is only a rough sign of how many were answered on the host.

The counts come from a small test program, and a real model server allocates far more objects, so its numbers are larger. The shape stays the same. When vLLM in Pod qwen3-6f7d9c8b4-x7k2p starts and builds its CUDA context, and while it allocates the memory for 34.3 GB of FP8 weights and the KV cache, the firmware gets a burst of allocations and controls. When the process exits it gets a burst of frees. In between, through hours of streaming tokens, the firmware hears nothing about copies from that process unless it allocates new memory. A monitor placed on the RPC queue sees startup and shutdown, and it shows the same picture whether the server moved 1 GB or 1 TB.

Chapter 4 of 13

The obvious way: protect the page

Correct, and 2,750 times slower

The standard tool for being told when memory is written is page protection. The shim marks the doorbell mapping read-only with mprotect. When the library stores to it, the CPU faults and the kernel sends the process a SIGSEGV signal, which runs a handler inside the shim. At that moment the store has not happened. The GPU has been told nothing, so the pushbuffers, the ring and USERD are exactly as the library left them. A snapshot taken here is complete and correct.

Then the store has to be let through. The handler makes the page writable again with PROT_READ | PROT_WRITE and sets the CPU's trap flag, the bit 0x100 of the saved EFLAGS register. When the handler returns, the CPU runs the faulting store and then traps after that one instruction. A second handler, for the trap, takes write permission away again so the next doorbell faults too.

Every copy now goes through a page fault, a signal, a permission change, a single-step trap, a second signal and another permission change. Worse, the snapshot has to walk every GPU-backed mapping, because nothing yet says where the pushbuffer is. The GPU waits through all of it, since the doorbell is held back until the end. Large copies fell from 55 GB/s to 0.02 GB/s. That is 55 divided by 0.02, a factor of 2,750. The observer sees everything, and what it sees is no longer the system it set out to study.

Chapter 5 of 13

The cheap way: look afterwards

Full speed, and nothing left to see

So do almost nothing in the SIGSEGV handler and take the snapshot in the trap handler, after the store. Most of the overhead goes away and copies run at full speed again. Now the observer is racing the GPU, and it loses. Writing the doorbell wakes the GPU's command processor almost at once. By the time the trap handler starts, the PBDMA has already read the ring entry and moved its read index.

The ring indices show it. GPPut is the producer index that the CPU advances. GPGet, at USERD offset 0x88, is the consumer index that the GPU advances. The gap between them is the work still outstanding. Sampled inside the handler across three runs, the pair read 83 and 83, then 93 and 93, then 1 and 1. Pending was zero every time. The state the observer wanted did exist, and it was gone before the observer could read it.

The doorbell register is no help either. Reading the BAR address back returns zero, never the token that was written. So the late observer also cannot tell which channel rang, because that is what the token encodes. And it still cannot find the pushbuffer without searching snapshots for something shaped like a method stream. Add those up across both variants, the snapshot before the store and the snapshot after it, and the page-protection approach failed in four ways: no token, no channel, no pushbuffer, and either the race or the bandwidth. One approach is correct and too slow. The other is fast and too late. That isn't a tuning problem. Both watch from the wrong place.

Chapter 6 of 13

What a debug register can and cannot do

A free alarm that rings one instruction late

Racing in software cannot be won, so the next tool is hardware. Every x86 CPU has four debug address registers, DR0 to DR3, and a control register, DR7, that says for each of them what to watch and how wide. The condition can be instruction execution, data writes, or data reads and writes. The width can be 1, 2, 4 or 8 bytes. The comparison runs in the CPU's own circuitry on every access, and it costs nothing until one matches. When one does, the CPU raises a debug exception, #DB, and the status register DR6 records which of the four fired.

The timing matters more than anything else here. An execute breakpoint fires before the instruction runs. A data breakpoint fires as a trap, after the instruction that touched the address has completed. For a store to the doorbell that means the store has already happened when the handler runs. Pointed at the real doorbell register, a hardware breakpoint would be exactly as late as the trap-flag handler of the last chapter.

Linux shares these registers out through its hardware breakpoint interface. A breakpoint is described by a type such as HW_BREAKPOINT_W, for writes, and a length such as HW_BREAKPOINT_LEN_4. A breakpoint on user code belongs to one task, which in Linux means one thread, and is registered with register_user_hw_breakpoint. So the hardware gives an exact alarm that costs nothing while it waits, and it rings after the store. The fix cannot make it ring sooner. It has to change where the store lands.

Chapter 7 of 13

Divert and arm

Choose where the store lands

The method that works comes from published research by Y. Yan and colleagues in 2026, the paper Revealing NVIDIA Closed-Source Driver Command Streams for CPU-GPU Runtime Behavior Insight (arXiv 2604.26889), and the series Under the Endpoint Picker used a port of it into the open NVIDIA kernel module. It moves the observer from the application into the kernel and gives the debug register a different target. The observer cannot beat the store, so it chooses where the store lands.

First, divert. When the driver sees a process map the doorbell page, it can recognise it, because it is a single-range 64 KiB mapping of the HOPPER_USERMODE_A object. Instead of the GPU register, it backs that mapping with a private shadow page of ordinary write-back RAM that the kernel controls. The process notices nothing. Its pointer to the doorbell has the same value as before. From now on its doorbell store lands in memory the GPU never reads, and the module keeps the address of the real register for later.

Second, arm. The module sets DR0 to the doorbell dword, the 4 bytes at offset 0x90 of the shadow page, and watches it for writes. A hardware breakpoint belongs to one thread and libcuda runs worker threads, so the arming walks every thread in the process. In these traces libcuda made two doorbell mappings per context, one over BAR0 and one over BAR1, and both were armed. Nothing else about the process changes. No copy is slowed by any of this, because a breakpoint that does not match costs nothing.

Chapter 8 of 13

Trap and inspect

Read the ring before the GPU does

Now the library rings the doorbell. The store lands in the shadow page, and the CPU raises #DB right after it, into the driver's handler, with interrupts off. Because the store went to RAM and not to the register, nothing has reached the GPU. The ring is exactly as the library left it, with GPPut one ahead of GPGet.

The handler first reads the value the process wrote, out of the shadow page. That value is the work-submit token. Its bits 11:0 hold a vector that names the channel, and its bits 22:16 hold the runlist the channel belongs to. With the channel known, the handler reads that channel's GPPut from USERD at offset 0x8c. GPPut counts the entries the CPU has published, so the submission this doorbell announces sits one slot behind it. The ring size is fixed when the channel is made and is always a power of two, so the index is GPPut minus one, masked with the number of entries minus one. With GPPut at 84, the entry is 83.

Each entry is two little-endian 32-bit words. The first holds bits 31:2 of the pushbuffer address already in place, so clearing its two low bits gives the low half. The second holds address bits 39:32 in its bits 7:0 and the length, counted in 4-byte words, in its bits 30:10. In the worked example the words read 0x00600000 and 0x00003C02. That gives the address 0x200600000 and a length of 15 words, which is 60 bytes, the size of one copy command. libcuda's pushbuffers really did sit that low, around 0x200600000, in these traces.

Chapter 9 of 13

Forward, and count

174 doorbells in, 174 decoded

Only now does the handler make the real register write, writel of the token to the real doorbell. The GPU wakes, fetches the entry and the pushbuffer, and runs the copy as if nothing had happened. The whole path, in order, is: the process writes the doorbell, #DB, decode the token into channel and runlist, read GPPut, read the ring entry, write one trace line, write the real register. Only the doorbell write is delayed. The copy itself is untouched.

On a CUDA device-to-host round trip the module's own counters for one run read: 2 mappings armed, 20 channels resolved with none failed, GPPut read 174 times, a ring entry decoded 174 times and 0 lookup misses. That is 174 doorbells in and 174 decoded submissions out. Each trap costs a few microseconds. On a bulk copy that is invisible, and copy speed matched a run without the module, where page protection had cost a factor of 2,750. It would show up in a measurement of how long it takes to submit small pieces of work.

The trace also showed two things that no public header says. Every doorbell write went to the BAR1 window, and none to the BAR0 one. And libcuda packs its channels into BAR1 at a fixed stride of 12 KiB each: an 8 KiB GPFIFO ring, which at 8 bytes an entry holds 1,024 entries, plus a 4 KiB USERD page. That layout is libcuda's own choice. All four failures of the page-protection approach, counted across both of its variants, are gone: the token is read from RAM, the token names the channel, the entry points at the pushbuffer, and nothing waits.

Chapter 10 of 13

Safe in a trap, and fast to look up

What a handler with interrupts off may do

Writing anything from a #DB handler with interrupts off is the kind of thing that deadlocks a kernel. The trace line here goes through ftrace_vprintk, which writes into ftrace's per-CPU ring buffer. The series describes that path as taking only a raw, IRQ-saving spinlock, a lock that spins with interrupts off and never sleeps. The exact locking inside the ftrace ring buffer has changed between kernel versions, and none of the versions takes a lock that can sleep. The path allocates no memory, so nothing in it can block or schedule. That is the argument from the code. In practice it held up under heavy capture, with hundreds of decode events per run and no kernel warnings.

Its one limit is size. The file buffer_size_kb sets how many kilobytes each CPU's buffer holds, and with the default overwrite setting of 1 the oldest events are thrown away when a buffer fills. A buffer sized too small quietly loses the start of a run. Merging this trace with other logs also needs trace_clock set to mono, the monotonic clock, or the streams drift apart by seconds.

The handler also has to know where each channel's ring lives, and it cannot take locks in trap context to find out. Two early versions read it from RAMFC, the per-channel block the hardware itself reads, by mapping it. Mapping it on every lookup broke a device-to-host copy with a timeout in the series' hand-built copy library. Falling back to that mapping then broke libcuda, because on Hopper with the GSP firmware the host never maps RAMFC, and the fallback freed a pointer it had never allocated. That printed two warnings for each of twenty channels on every run. The working version records the values the client hands in when it creates a channel, in a small table keyed on GPU, runlist and channel id, and removes them first thing at teardown. On a miss the handler skips the decode and still forwards the doorbell.

Chapter 11 of 13

The sharp edges

A research tool, with limits worth knowing

The method has limits, and they teach as much as its success. A CPU has four breakpoint slots, DR0 to DR3, shared by everything on the machine. A debugger uses them. In these tests so did the display server Xorg and an ollama model server that happened to be running. If the slots are taken when the process starts, arming fails and the watchpoint falls back to plain pass-through. lsmod shows the module loaded, the copies run normally, and the trace holds zero doorbell events. There is no error. Before each test the author had to run sudo systemctl stop lightdm ollama. On a GPU server that also runs other model servers this is a real conflict.

Breakpoints belong to threads. Arming walks the threads that exist at that moment, and threads created later do not inherit the breakpoint, so their doorbells slip past. libcuda's worker threads exist before the first copy, so it works today. Nothing guarantees it will tomorrow.

The faster lookup table also exposed an older bug. The cache held kernel addresses inside a BAR1 mapping, and teardown unmapped that region without clearing them. A doorbell arriving late, while a process was exiting, read memory that had just been freed. The crash address ended in 0x208c. The offset 0x8c is where GPPut sits in USERD, and GPPut is the first thing the handler reads from that mapping, since the token comes from the shadow page, so the address named the read that died. The fix clears every cached address that points into a region before unmapping it. The old slow path had hidden the bug all along. Even the debugger needed debugging.

Chapter 12 of 13

Bolted on from the side

The same two mistakes, in an inference stack

Teams that run inference want the same kind of sight into their requests. For each one they want to know which tenant sent it and with which key, how many tokens went in and came out, how long the first token took, which model and which GPU served it, whether its prefix was already cached there and why the router picked that worker. The common ways of getting this bolt an observer on from the side: a sidecar in each model server Pod that intercepts traffic, a tap or mirror port on the fabric, scraping the model server's logs and metrics after the fact, or a separate tracing proxy chained into the path. Each repeats one of the two failed doorbell methods.

A sidecar, or one more proxy in the chain, is the page-protection method. It sees every request, and every request pays for it with an extra hop, an extra copy and an extra queue, on the path where time to first token is measured.

Scraping logs and metrics, or tapping the fabric, is the look-afterwards method. It costs the request nothing and it arrives after the routing decision was made. vLLM on gpu-2 exports good numbers about itself, such as vllm:time_to_first_token_seconds, vllm:prompt_tokens_total and vllm:prefix_cache_hits_total. They describe the worker. The worker is not told the tenant unless something in front of it adds that, and it never sees the other two workers or the scores they got. A log at the worker can say which GPU served a request. It cannot say why, or what else was possible. Joining it to a gateway log afterwards needs the same request id on both sides and clocks that agree, the problem the doorbell trace solved with trace_clock.

Chapter 13 of 13

In the path, at the decision

Record where the request already is

BNK, F5 BIG-IP Next for Kubernetes, the data plane drawn as the border of the factory, is on the path of every inference request, because it is the path. TMM, its traffic engine, ends the client's connection at 203.0.113.80, the gateway address, and opens its own connections onward from its internal address 10.20.0.5, so it knows the source address and the credentials. Its policy rules call the key service at 10.96.40.12:8443 on the side to check the key and record usage, so it knows the tenant. It applies the firewall and the token budget. For the GPU it asks the F5 endpoint picker, over ext_proc on port 9002. The picker scores every candidate on how long its queue would take to drain and on whether the prompt's prefix is already in its KV cache. Its reply to TMM names the chosen endpoint. The per-candidate scores stay inside the picker. On the board, gpu-2 is drawn with a block that holds a cached prefix, which is why the picker sends this request there. It forwards to the chosen Pod and carries the streamed tokens back, so it sees the time to first token and both token counts.

Recording there adds no hop, because the request is already there. The record is written once, with the tenant, the tokens and the chosen worker together, and it needs no join afterwards. Billing by tenant and finding which worker served a slow request read the same line. The picker's reasons are the part this record does not hold. Joining them in needs the picker to log its scores against the same request id. The owner's planning notes list carrying callout metadata into the per-request decision record as a target, and note that the logs carry no per-request custom fields from a callout yet. In the owner's material, a deck for the telemetry format and the engineering preview notes for the log path, BNK uses OpenTelemetry as its telemetry format and its logs are shipped to the operator's own sink, so the record lands where the team already looks.

That is the debug-register trap again. It sits exactly where the event happens, reads the state before anything acts on it, and touches nothing on any other path. This is no argument against the model server's own metrics. The picker depends on them: vllm:num_requests_waiting, vllm:num_requests_running and vllm:kv_cache_usage_perc are what it reads to score a worker. It is about where the view of one request gets put together.

What to keep

Watch at the event, before the action

The same observation cost 2,750 times the bandwidth from one place and nothing from another. Protecting the doorbell page saw everything and wrecked the thing being watched. Looking afterwards was free and found an empty ring. What worked was to stand exactly where the event happens: divert the store, trap it in hardware, read the state before the GPU has been told, then pass it on. An inference stack offers the same choice. Sidecars and extra proxies see requests and slow them all. Logs and taps are cheap and arrive after the routing decision. The router is the only place that saw all the options, and the gateway is the only place that knows both the tenant and the tokens.
