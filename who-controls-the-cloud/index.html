Running a GPU cloud

Who controls the cloud

Sovereign AI: six things to control, and location is only one of them

A customer asks Northlight Compute for a sovereign AI cloud. The first answer people reach for is a location: the servers stand in the right country. Location answers one question out of three. This lesson uses three working definitions, set by no law or standard. Data residency is where data is stored and processed. Data sovereignty is which law applies to it and which authorities can demand it. Operational sovereignty is who runs the system: who logs in, who holds the keys, who ships the updates.

This lesson walks through six things a customer may need to control, each with the mechanism that enforces it and the limits of that mechanism as its own documentation states them. Data is held in place by egress policy, placement labels and defined network edges. Access is bounded by short-lived credentials and an audit log the administrators cannot change. Keys are held by the customer through envelope encryption, and the lesson shows how to prove it on disk and why the key service sits on the control plane's start-up path. It then covers the hardware answer for data in use on GPUs, attestation step by step, the management plane, models and artefacts, jurisdiction, and the forms a sovereign cloud takes, with the four words on premises, private, air-gapped and sovereign kept apart. The last chapters set a level of control per workload in three worked tiers, look at the telcos, regional operators and neoclouds that offer sovereign AI, and treat the software platform that runs a cloud as a dependency with its own exit plan. Nothing here is legal advice.

Chapter 1 of 18

Data: where it rests, where it runs, what leaves

A dataset has more copies than the one that was uploaded

Tenant A uploads a dataset to Northlight's storage and trains on gpu-srv-1. Residency for that dataset means every copy stays in the agreed place, and there are more copies than the upload. Storage replicates it. Backups copy it again. Logs and traces can quote pieces of it. A support bundle, the archive of diagnostics sent to a vendor, can contain it. Processing has a location too: a prompt sent to a hosted model API is processed wherever that API runs.

On an AI platform the list grows. Prompts and model outputs are data, and they appear in request logs, traces and caches. Embeddings are numbers computed from documents, and a vector index built from them can be searched to recover what the documents said. Checkpoints and adapters are trained from the data. The owner's AI Grid deck puts the requirement in one line: regulated tenants need data, models and logs kept in jurisdiction. Logs are named on purpose, because they are the copy most often shipped elsewhere.

So the control is a list of every place the data can flow to, with a rule for each. In a Kubernetes cluster two mechanisms help. A NetworkPolicy that denies all egress stops Pods from sending anything out. Node labels such as topology.kubernetes.io/region let a workload be pinned to a place. Both have limits that the next chapter sets out, and neither reaches storage replication or backups, which are configured in the storage system itself.

Chapter 2 of 18

What egress policy and placement labels can and cannot do

Both are allow lists with documented gaps

By default a Pod is not isolated for egress, and every outbound connection is allowed. A Pod becomes isolated for egress only when some NetworkPolicy selects it and lists Egress in policyTypes. Policies never conflict. They add up, and for a Pod that is isolated the model is deny by default with allow rules added on top: only connections that some policy allows get out. There is no deny rule to write. To let tenant A's Pods reach only the site's own storage, the namespace gets the default deny policy from the last chapter and a second policy that allows that one destination.

The Kubernetes documentation lists what NetworkPolicy cannot do. It cannot do anything TLS related, cannot target Services by name, cannot set node-wide policies, and cannot apply default policies to all namespaces at once. It cannot log network security events, so a blocked attempt to send data out leaves no record from this API. Pods on the host network are a gap of their own: their behaviour is undefined, and a plugin may simply ignore them. A NetworkPolicy created in a cluster whose plugin does not enforce it is accepted and has no effect, with no error. The ipBlock field is meant for addresses outside the cluster, and traffic to a Service address that gets rewritten may or may not be matched.

Placement has a weak point too. topology.kubernetes.io/region is filled in by the kubelet or the cloud controller manager from the cloud provider, and only when a cloud provider is in use. On bare metal an administrator writes it, and so can anyone with that permission. The NodeRestriction admission plugin reserves the prefix node-restriction.kubernetes.io/ for administrators, and a kubelet cannot change labels with that prefix on its own Node. A placement rule for residency belongs on such a label.

Software inside the Pods has outbound habits of its own. Hugging Face libraries send usage data by default until HF_HUB_DISABLE_TELEMETRY=1 is set, and a model load asks the Hub for updates unless HF_HUB_OFFLINE=1 is set.

Chapter 3 of 18

Defined edges: residency enforced in the network

One controlled point where flows in and out can be seen and stopped

Rules inside the cluster cover Pods. A regulator usually asks a wider question: where are the edges of this environment, and what crosses them. The owner's deck for F5 and NVIDIA states it in one line: regulations and certifications require defined edges, with observability and control. It then describes how such an edge is built for a multi-tenant GPU cloud.

The edge is defined in one place, either on the DPU, the data processing unit in each server that runs network functions beside the host, or as a BGP endpoint that the data plane controls. BGP is the routing protocol the site's network uses to learn which addresses live where. A layer 4 firewall with IP, DNS and DDoS profiles protects that edge. Service access in every direction passes through it, so it is also the point that records what crossed. Telemetry leaves it in OpenTelemetry format, OTEL, a vendor-neutral standard for metrics, logs and traces. Each tenant's namespace maps to its own network, so tenant A's servers and tenant B's servers are separated in the network itself.

The same deck shows sovereignty as a routing rule. A request tagged EU-only cannot leave EU infrastructure, whatever the latency or the cost. An inference router that would normally send a request to the least loaded GPU anywhere treats that tag as a hard constraint and picks only among EU sites.

This kind of edge can fill some of the gaps the last chapter listed, within limits set by where it sits. An edge on a GPU server's DPU sits outside the host's own network stack, so traffic that a Pod on the host network sends off the server passes it like any other. It can record what it blocks. The deck requires tenant traffic to cross the zero-trust layer both north-south, in and out of the site, and east-west, between workloads. Meeting the east-west half depends on how Pods are attached. If the cluster's network plugin joins two Pods on the same host through a bridge in the host's own kernel, their traffic never leaves the server, so the design has to send it through the DPU on purpose. And storage arrays and their replication links do not normally pass through a GPU server's DPU at all. For storage replication to another site to be seen and stopped, the storage network's own exit has to be a defined edge as well. The deck states the requirement. Covering every path is a design task for the site.

Chapter 4 of 18

Administrative access: who can log in

The people with root matter more than the building

Someone has to operate the control plane and the servers, and whoever can log in can read. So the second control is the list of administrators and the conditions on each session. Four questions define it. Who is the person, by name. Who employs them, because an employer can instruct its staff. Where they connect from, since a session opened from another country is access from that country. And which law that employer answers to.

The mechanisms are ordinary ones, applied strictly: accounts in an identity service the customer can inspect, roles with the least access the job needs, access that expires and that a second person approves, and an audit log the administrators cannot edit. The Kubernetes audit log records for each request who made it, from which address, and what it touched.

The list of paths to a server is longer than the list of logins. The operating system has its accounts. The cluster API has users and roles. And every server has a baseboard management controller, the BMC, a small computer on the board that controls power, boot device and firmware, reachable on a management network with its own password. NVIDIA's threat model for confidential computing says that host management access through the BIOS or the BMC does not make those interfaces trusted recipients of workload data. They are administrative paths all the same, and they belong on the list.

One group in Kubernetes deserves its own line. A credential in the group system:masters is bound to the cluster-admin super-user role by the default bindings, and the list of who holds such a credential is the shortest and most important list of all.

Chapter 5 of 18

Access that ends by itself

Kubernetes cannot revoke a certificate, so access has to be issued short

The access request in the last chapter expires after 2 hours. In Kubernetes the way that expiry is enforced matters, because some credentials cannot be withdrawn once issued. The authentication documentation says it directly: Kubernetes does not support certificate revocation, and any certificate that is issued stays valid until it expires. A client certificate made for an operator with a one-year lifetime keeps proving who that operator is for a year, whatever happens to the operator's job in the meantime. What the operator can do with it is decided separately, by RBAC. Removing the operator's RoleBindings and ClusterRoleBindings withdraws the rights, even though the certificate still authenticates. A certificate becomes a one-year pass when the rights come from a group nobody can unbind, and a paragraph further on names that group.

Other credentials follow the same rule. An OpenID Connect id_token, the token an identity provider issues after a login, cannot be revoked either, and the documentation advises keeping it short-lived, only a few minutes. Service account tokens can be made short on purpose. kubectl create token myapp --duration 10m issues a token that lasts ten minutes, and --bound-object-kind with --bound-object-name ties it to one object, so it stops working when that object is deleted. A Pod's own projected token is invalidated when the Pod is deleted. Its stated lifespan is 1 hour by default, but that is not the whole story. kube-apiserver has a flag, --service-account-extend-token-expiration, that is true by default, and with it the tokens injected by admission are extended up to 1 year, to ease the move away from legacy tokens. The kubelet still refreshes the token on its own schedule, but a copy taken from a running Pod can stay usable long after an hour. Deleting the Pod is the reliable end.

The second half of the control is that a person cannot widen their own access. RBAC, role-based access control, blocks escalation: creating or changing a role with more rights than the creator holds requires the escalate verb on roles or clusterroles. And membership of system:masters is outside RBAC's reach entirely. A member of that group bypasses every RBAC check, and any authorization webhook too, so removing RoleBindings or ClusterRoleBindings cannot take its access away. A certificate in that group is a pass until it expires. Credentials in that group are kept offline, counted and used only in an emergency.

Put together, the 2 hour session becomes concrete: an identity provider issues the operator an OIDC id_token that lasts minutes and issues new ones only until the 2 hour window closes, with a role that cannot grant itself more.

Chapter 6 of 18

An audit log that can be trusted

No policy means no log, and only the last address in sourceIPs is evidence

The audit log is the evidence behind every claim about access, so its own configuration deserves the same care. The first fact surprises people. The API server writes audit events only when it is given a policy with --audit-policy-file, and if the flag is left out, no events are logged. The policy is a list of rules, and the first rule that matches a request sets its level: None, Metadata, Request or RequestResponse. Each request produces events at stages: RequestReceived, ResponseStarted, ResponseComplete, and Panic if the server panicked.

Each event has named fields: auditID, stage, verb, user, impersonatedUser, sourceIPs, userAgent, objectRef, responseStatus, requestReceivedTimestamp and annotations. sourceIPs needs a careful reading. It is built from the X-Forwarded-For header, then the X-Real-Ip header, then the remote address of the connection. The reference adds that all but the last address can be set to anything by the client. Only the last entry is evidence of where a request came from, and behind a proxy that entry is the proxy.

Where the events go decides whether administrators can change them. The log backend writes JSON lines to a file named by --audit-log-path, with rotation set by --audit-log-maxage in days, --audit-log-maxbackup in files and --audit-log-maxsize in megabytes. A file on the control plane host can be edited by whoever runs that host. The webhook backend sends events to another system, one the customer can run. It has three modes. batch, the default, buffers events and sends them asynchronously. blocking waits for each event. blocking-strict also fails the request itself if the event cannot be written at the RequestReceived stage.

Batch mode has numbers worth knowing: a buffer of 10,000 events, after which events are dropped, at most 400 events in a batch, a 30 second maximum wait, and throttling at 10 batches per second with a burst of 15. Auditing also costs the API server memory.

Chapter 7 of 18

Keys: what it takes for the provider to be unable to read

Encryption moves the question to whoever can use the key

Encrypting stored data is common. For sovereignty the question is who can use the key. The usual design is envelope encryption. Data is encrypted with a data encryption key, the DEK. The DEK is encrypted with a key encryption key, the KEK, and stored beside the data. With customer-managed keys the KEK stays in a key service the customer controls, ideally in a hardware security module, an HSM: a physical device that safeguards keys and does the cryptography inside itself.

The provider's storage has to ask that service to unwrap each DEK. The customer sees every request and can refuse. That gives the customer a switch and a log. The switch has limits that the documentation states plainly. In Kubernetes with KMS v2, once the API server has unwrapped the DEKs through the KMS, they are cached in the clear, and they can be used to decrypt indefinitely with no further call. Refusing new unwrap requests stops a server that restarts. It does not stop one that is already running. The customer's key log also shows far fewer requests than there are reads, because most reads use the cache.

Data in use is a separate matter. While a workload runs, the unwrapped DEK and the plaintext sit in memory on the provider's machines. Three things have to hold for the provider to be unable to read: the KEK is outside its control, the unwrapped DEK is never visible to its staff, and the plaintext is never in memory it can read. Customer-managed keys give the first. Confidential computing, three chapters on, addresses the other two.

Chapter 8 of 18

Proving the data at rest is encrypted

Read the raw bytes from etcd and look for the prefix

A sovereignty claim about keys is worth as much as the evidence behind it, and Kubernetes documents how to produce that evidence for its own store. The API server encrypts resources in etcd according to a file named by --encryption-provider-config. Without that file nothing is encrypted. The default provider is called identity, and the documentation says it provides no confidentiality protection.

The order of providers in the file is the rule. The first provider encrypts everything written. When reading, each provider that matches the stored data tries to decrypt it in order. Putting kms first and identity after it means new writes are encrypted and old plaintext is still readable. Putting identity first means new writes are plaintext again. Only the resource types listed are encrypted, and the documented example deliberately lists Events under identity, so they are left in the clear while everything else is covered.

The proof is to read a Secret directly from etcd, bypassing the API server, and print the raw bytes: ETCDCTL_API=3 etcdctl get /registry/secrets/default/secret1 piped to hexdump -C. An encrypted value starts with a prefix that names the provider: k8s:enc:aescbc:v1: for aescbc, k8s:enc:kms:v1: for KMS v1 and k8s:enc:kms:v2: for KMS v2. A value without a prefix is plaintext.

Two traps follow. Turning encryption on does not touch data already stored. The documented step is to rewrite every Secret, with kubectl get secrets --all-namespaces -o json piped to kubectl replace -f -, run as a privileged user and run again after every key rotation. And turning encryption off does not decrypt anything either: existing encrypted resources are not overwritten with plaintext automatically. The documentation's comparison table rates aescbc as weak and both KMS versions as strongest, with v2 fast and v1 slow.

Chapter 9 of 18

The key service is on the control plane's start-up path

KMS v2 in detail: three calls, a socket, a timeout and a latency budget

Customer-managed keys put the customer's key service into the control plane's critical path, and the KMS v2 protocol shows exactly how. KMS v1 is deprecated since Kubernetes v1.28 and disabled by default since v1.29. KMS v2 is the stable version. Its provider entry names the plugin, an endpoint that is a UNIX domain socket, and a timeout, 3 seconds by default. The plugin is a gRPC server on the same host as the API server, and it talks onward to the customer's key service.

Three calls make up the protocol. Status returns the plugin's version, the word ok as its health and a key_id, the public name of the KEK in use. EncryptRequest wraps a key. DecryptRequest unwraps one. The API server calls Status about every minute while things are healthy and every 10 seconds when they are not. With KMS v2 providers only, the API server exposes one health check for all of them, /healthz/kms-providers, whether or not automatic reload of the configuration is on. Separate endpoints per provider, /healthz/kms-provider-0 and onward, exist only for KMS v1 providers when automatic reload is off.

The latency budget is where distance matters. The documentation asks for encryption under 100 milliseconds and decryption under 10 milliseconds, because the API server may make thousands of DecryptRequest calls at start-up to fill its watch cache. A key service in another building, or another country, sits on that path every time the control plane restarts.

KMS v2 makes DEKs differently from v1. v1 made a new DEK for each encryption and asked the KMS every time. v2 derives single-use DEKs from a secret seed with a key derivation function, and rotates the seed whenever the KEK rotates. If an EncryptRequest returns a key_id that differs from what Status reported, the response is thrown away and the plugin is marked unhealthy, and plugins must never reuse a key_id. A plugin can also return annotations, such as the remote KMS's own audit ID, which links the API server's request to the customer's key log.

Chapter 10 of 18

Data in use: confidential computing on GPUs

Hardware that keeps the host's administrator out of the workload's memory

Data in use is plaintext in memory. Confidential computing is the hardware answer: the processor isolates a workload's memory from the host's operating system and its administrators. NVIDIA documents three ways to use it with GPUs: confidential bare metal, confidential virtual machines and confidential containers. In a confidential virtual machine the CPU feature is AMD SEV-SNP or Intel TDX, and a Hopper or Blackwell GPU passed through to the machine brings the GPU inside the machine's trust boundary: GPU memory is guarded by hardware access controls, and data moving between CPU and GPU is encrypted. The H100 is a Hopper GPU.

The mechanism has several parts. Each GPU is assigned whole to one confidential VM. Inside GPU memory, NVIDIA's threat model says hardware access controls protect plaintext, and GPU memory encryption is not the mechanism. Between CPU and GPU, data travels through a bounce buffer: shared CPU memory that carries only ciphertext, while the VM's private memory stays protected by the CPU. That traffic uses authenticated encryption, session counters detect replay, and keys rotate before the counters run out.

What each mode encrypts differs. A single GPU in CC mode encrypts CPU to GPU. Several Blackwell GPUs in multi-GPU CC mode also encrypt GPU to GPU over NVLink. Several Hopper GPUs use Protected PCIe mode, PPCIe, which encrypts CPU to GPU and leaves NVLink unencrypted. NVIDIA's page says the assessment must then also account for the fabric, NVSwitch included, and for physical access.

Before it releases a key, the tenant checks attestation: signed evidence from the CPU and from every GPU about the hardware, firmware and mode in use. The operator still controls power, network and scheduling, so it can stop the workload. Reading it is what the hardware prevents, within documented limits.

Chapter 11 of 18

Attestation, step by step

The operator sets the mode, the tenant checks it, and the ready flag proves nothing by itself

NVIDIA's deployment guide splits the work between two people, and the split is the sovereignty point. The cloud provider configures the host and puts the GPUs in a mode. The tenant sets up the guest, attests the GPUs and runs the workload. In NVIDIA's words for its example, the provider does not decide how often the tenant attests, and the tenant does not configure the GPU's mode.

The three mode values mean different things. on enables every supported GPU security feature, bus encryption included, with performance counters off. devtools is the same, except that the blocks on profiling and debugging tools are lifted. off is the GPU's default mode. The host sets the mode for each GPU with nvidia_gpu_tools.py and --reset-after-cc-mode-switch, in a loop over the GPUs it finds. The tenant's policy accepts on and rejects the other two for production data, because the evidence reports which mode is set.

Inside the guest, nvidia-persistenced has to be running. Attestation then works like this: the GPU collects measurements of its firmware and configuration and signs them, and a verifier compares them with known-good reference measurements. The GPU does not turn itself ready. Software in the guest sets the GPU ready state through the driver, and that needs root. NVIDIA's Local GPU Verifier does it for the tenant: when attestation succeeds, and the verifier is not running in user mode, it sets the ready state to READY on its own. The PPCIe verifier's instructions ask for root for the same reason. The ready state is still not evidence that the tenant's release policy was met. In the Local GPU Verifier's code, when attestation fails on a GPU in devtools mode, the ready state is set to READY anyway. A flag that a failed attestation can also set proves only that something in the guest set it. nvidia-smi conf-compute -q shows it in a block headed NVSMI CONF-COMPUTE LOG, with a line such as CC GPUs Ready State : Not Ready.

The tools are moving. NVIDIA's nvtrust repository marks its Python SDK and the Local GPU Verifier as deprecated in favour of a C++ SDK and a command line tool, and it carries a separate PPCIe verifier for multi-GPU setups in that mode. The trust list also reaches past the hardware: the verifier, its reference values and policies, and the services that hold or release secrets are trusted even when they run outside the VM. Whoever runs the key release service is inside the boundary.

Chapter 12 of 18

The infrastructure and its management plane

Whoever can update, observe and reach the machines controls them

Below the customer's workload sits the machinery that runs the site: the control plane that provisions servers, the management controller in each server, the firmware, and the tools that update and monitor all of it. Together they are the management plane. Three flows decide who controls it. Updates: who chooses which versions are installed, and when. Telemetry: what the equipment and the platform report, and to whom. Support access: who can open a session to diagnose a fault.

Then there is the location of the management plane itself. A site whose servers stand in one country and whose control plane runs in another can be changed, observed or switched off from that other country. NVIDIA's confidential computing pages say the same about any operator: it keeps power, networking and scheduling, and with them availability. Its threat model lists the infrastructure owner's controls as host OS, hypervisor, GPU assignment, platform management, power and scheduling, and treats host administration as potentially malicious.

A useful test is to imagine the link to the provider's headquarters cut for a week, and to list what stops: provisioning and repairing servers, renewing certificates, adding users, licences that need to check in. Each item on that list is a dependency on someone outside the country.

Telemetry deserves a list of its own. Equipment and software often report to their vendor by default: serial numbers, error logs, usage, sometimes names of jobs and files. Each flow is either switched off, or passed through a point the local operator controls, such as the defined edge from earlier, where its contents can be seen.

Chapter 13 of 18

Models and artefacts

A model is data that behaves like software

An AI platform holds assets that an ordinary cloud does not: model weights, fine-tuned adapters, datasets, checkpoints, embeddings and the indexes built from them. Two questions apply to each. Where it came from, and who can change it. Weights usually start at a public model hub, so the origin and the exact revision are recorded when they enter. After that the platform refers to each artefact by its content, never by a name that can be moved.

Kubernetes shows the pattern for images: a tag can be moved to point at a different image, while a digest is fixed. When an image name carries both a tag and a digest, only the digest is used for the pull. A model revision pinned by its commit hash works the same way: Transformers uses the cached files for that commit without asking the Hub again, while a branch name is first resolved to a commit and can change.

Who may say what a name means is a control in itself. containerd calls resolving, turning a name into a digest, a trusted operation, to be done only by a trusted host. A mirror allowed only to pull cannot change what a tag means. The site's own registry gets that trust, and a mirror run by someone else does not.

What the customer creates is an artefact too. A checkpoint or an adapter trained on confidential data can reveal parts of that data, so it needs the same residency and the same keys. Embeddings and vector indexes follow the documents they came from, and prompts and outputs in logs follow the conversation.

Chapter 14 of 18

Operations and jurisdiction

The operator is a company, and a company answers to courts

The last control is one that no configuration can set. The operator of the cloud is a legal entity. A court or authority with power over that entity can order it to act: to hand over data, to grant access or to stop a service. The location of the servers does not by itself settle which authorities those are. It can also matter where the operating company is established, who owns it, and where the people with access work. Depending on the laws involved, a provider owned from another country may be reachable through its owner. This is why the three terms from the start are kept apart. Residency can be met while sovereignty is still open.

Technical controls shape what an order can produce. An operator that holds only ciphertext can hand over only ciphertext. With keys it manages itself it can produce plaintext. With the customer's KEK in the customer's HSM it can produce ciphertext and an unwrap request the customer sees, keeping in mind that a running service already holds unwrapped DEKs in its cache. With the workload in an attested confidential VM it has no view into memory, within the documented limits. In every case it keeps the ability to stop the service.

Exit belongs here too. A customer that cannot move its data, keys and models elsewhere within a known time is bound to this operator, whatever the contract says about ownership. An exit plan names the formats, the volume, the transfer time and who carries it out. For any real case, ask a lawyer.

Chapter 15 of 18

The forms it takes, and what each gives up

Four designs, from most convenient to most closed

Four designs cover most offers. A public cloud region in the country gives residency and the full service catalogue. The operator, the management plane and the jurisdiction stay the provider's. Customer-managed keys and confidential computing can be added where offered.

A sovereign region is run by a local company with local staff, often on a large provider's technology. It adds operational control and often trails the public regions in services and updates. The questions to ask are who owns the local operator and what still depends on the technology vendor, such as updates, licences or a central control plane.

A private cloud is dedicated to one organisation. NIST's definition lets it be operated by the organisation or a third party, on or off premises, so the word private says nothing about who runs it. On the customer's premises it gives up elasticity and adds capacity planning: Northlight's 12 GPUs stay 12 until more are bought, and the customer pays for idle time in full.

An air-gapped site removes the outside connection completely and pays with late updates and no remote help. Telemetry and remote sessions are impossible by construction, and insiders, what is carried in and who the operator answers to remain open.

Northlight's three servers could be the hardware in any of the four. The label sovereign is not a defined standard, so two offers with that name can differ in each of the six controls, and the only reliable comparison is to ask for the answers one by one.

The four words used to describe these designs answer four different questions, and mixing them up is the most common source of confusion. On premises names a location: the hardware stands in a building the organisation controls. Private cloud names an operating model: resources dedicated to one organisation and delivered the way a cloud delivers them. NIST SP 800-145 lists five essential characteristics of cloud computing: on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service. Air-gapped names a connectivity boundary: no network path to the outside. Sovereign names a control requirement: which of the six controls must stay under the customer's or the jurisdiction's authority. The terms overlap without being equivalent. Two examples show the gap. A rack of GPU servers in a company's own data centre, where an engineer installs vLLM by hand on each server when a team sends an email, is on premises and is not a private cloud, because nothing about it is self-service, pooled or metered. Dedicated servers hosted in a third party's data centre, ordered through a portal, scheduled from a pool and metered per tenant, are off premises and can be a private cloud. An air-gapped private cloud is possible, and most private clouds are not air-gapped. None of the three settles sovereignty, because the operator, the supply chain, the keys and the jurisdiction still have to be checked one by one.

The private design has a full list of costs, and the elasticity line is only the first. Capacity planning comes first: GPUs must be forecast, ordered and installed before they can be used, and the order sits in a queue of its own at the hardware vendor. Infrastructure cost comes next: the servers, the network, the storage, and the power and cooling for all of them. NVIDIA rates the H100 SXM at a maximum thermal design power of up to 700 W, so Northlight's 12 GPUs alone can draw 8.4 kW (12 × 700 W) before a single CPU, memory module, network switch or cooling fan is counted, and every watt drawn must also be removed as heat. Operations need people with skills in clusters, GPU drivers, container runtimes, security, monitoring, upgrades and failure recovery, on call. Elasticity has a hard ceiling. NIST describes rapid elasticity as capacity that often appears unlimited to the consumer. On Northlight's floor it is 12 GPUs. The Deployment qwen3 runs one Pod per GPU with the FP8 build, whose 34.3 GB of weights fit one 80 GB H100 with room for the KV cache, so qwen3 can reach at most 12 replicas. If demand needs 16, four replicas stay Pending until servers are bought, delivered and racked, while in a large public region the same request is often met within minutes, subject to the provider's available capacity. The last cost is the technology lifecycle. GPU generations and the serving software around them change quickly, so servers bought today for several years of use will run beside newer, faster hardware well before they are paid off, and the upgrade path has to be planned from the start. More control comes with more responsibility.

Sovereignty is also not the same thing as using only domestic technology. Some national strategies put the weight on domestic technology or domestic ownership of the companies involved. Others put it on control of the data, the operations, the keys, the jurisdiction or the ability to keep running in a crisis, and accept foreign technology that is operated locally. A sovereign region run by a local company on a large provider's technology meets the second kind of strategy and may fail the first. Neither is the correct reading in general. The right architecture follows from the actual requirement of the country, the sector and the workload, and there is no universal formula.

Chapter 16 of 18

One level of control per workload

Sovereignty is a spectrum, set by what the workload holds

A single organisation rarely needs one level of sovereignty for everything it runs. The useful question for each workload is which controls must stay under the organisation's or the jurisdiction's authority for that workload. Asked that way, sovereignty becomes a spectrum with settings, where a yes or no label gives none. Three tiers show how the answer changes as the workload changes.

The first tier is a workload built on public information. Tenant A runs an assistant that answers questions from its published product manuals. Nothing in its prompts is confidential, the documents are on the public website already, and a leak would cost little. Such a workload can tolerate dependencies on a global cloud: a hosted model API abroad, a provider-managed key, a management plane in another region. The controls that still matter are basic ones, such as an egress rule so the assistant cannot be used to reach internal systems.

The second tier is a sensitive enterprise system that retrieves answers from internal documents, known as RAG, retrieval-augmented generation. Tenant A's contracts and HR files are split into chunks, turned into embeddings and stored in a vector index. Each question pulls matching chunks into the prompt sent to the model. Here three controls tighten. Data: the documents, the embeddings, the index, the prompts and the logs all stay in the agreed place, because each of them can reveal the source text. Identity: every user and every service that queries the index is a named account, and a user sees only the chunks their own permissions allow. Model endpoints: the prompts go to the qwen3 Deployment in tenant A's own namespace, reached at Service qwen3 on port 8000, and never to a hosted API outside the boundary. The management plane and the operator can still be the provider's.

The third tier is a critical or highly regulated workload, such as a health record system or a government service. Here the infrastructure, administrative and operational boundaries become strict. The administrators are a local operating company's named staff, the KEK sits in the customer's HSM, the workload can run in an attested confidential VM, requests are tagged EU-only, updates are pulled by the local operator, and an exit plan is written down. Some workloads at this tier go to an air-gapped site.

One customer can have all three on Northlight's floor at once. The tier of a workload is set by the most sensitive thing it touches. A public assistant that is later connected to the HR index has moved to the second tier, and its controls have to move with it.

Chapter 17 of 18

Who offers it: regional operators, telcos and neoclouds

A category of provider and a model of control are different things

As sovereignty moves beyond data residency to control over data, operations, infrastructure, administration and jurisdiction, operators who already run regional infrastructure gain a role in it. Telecom operators are the clearest case. Many already own or run data centres, national networks, regional and edge sites and relationships with enterprise customers, and some now own GPUs as well. The owner's AI Grid deck puts the scale in one line: telcos and CDNs operate about 100,000 distributed network data centres. The same deck lists sovereignty and residency among the problems such distributed capacity addresses, in the words regulated tenants use: data, models and logs kept in jurisdiction. A telco can place inference close to its customers and inside the country's borders.

Local hosting by itself does not establish sovereignty. A telco's regional site answers the location question. The six controls still need their own answers: who the administrators are, who holds the keys, where the management plane runs, which vendor sends updates and telemetry, and who owns the operating company. A site in the country whose GPU platform is provisioned from a control plane abroad has residency and lacks operational independence. Owning GPUs also does not make an operator a cloud. The same deck lists what a telco needs to sell inference and not just run it: hard multi-tenancy, RBAC, token metering and a marketplace. Even when every customer receives dedicated servers, the operator still needs separate identities, credentials, network segments, storage, quotas, service records and billing records for each one. Dedicated hardware and multi-tenant operations are separate problems.

Neocloud is the second term that meets sovereignty. It is an industry term, not one of NIST's formal cloud service or deployment models, for cloud providers built mainly around GPUs and AI workloads. A general-purpose hyperscaler offers breadth: databases, analytics, identity, serverless, and hundreds of managed services. A neocloud offers depth in AI compute: high-end GPUs, bare-metal servers, GPU clusters with fast interconnect, AI-optimised storage, and training and inference platforms. One way to describe such a provider, used in this lesson, has three layers: AI-optimised infrastructure, a cloud operations layer that provisions, schedules, meters and exposes APIs, and the AI workloads on top. Northlight's floor is that model in small: three GPU servers, a control plane of six modules, and tenants' training and inference above.

Some neoclouds offer more than GPU access: data centres in a given region, flexible deployment such as dedicated or reserved clusters, and options sold as sovereign. An offer like that does not make every neocloud sovereign. Neocloud describes a category of provider. Sovereignty describes a control model that some providers support for some workloads. A neocloud with data centres in the country, run from a parent company abroad with a central control plane, is a regional AI cloud whose operations, and depending on the laws involved its data, may stay within reach of the parent's jurisdiction. The way to tell is the same as for any offer: the six questions, asked one by one.

Chapter 18 of 18

Depending on the platform: APIs, portability and exit

The software that runs the cloud can bind its owner too

Exit came up earlier as the customer's question about its operator. The same question applies one level down, to the operator and the software it runs the cloud on. Northlight's control plane has six modules: identity, catalogue and orders, scheduler, provisioner, metering and billing. Northlight can build them itself from open source, or buy an integrated cloud operations platform that provides them as one layer. Both work. Open source can carry a real GPU cloud: OpenStack with Ironic provisions bare-metal servers, Kubernetes schedules GPUs exposed through device plugins, and Prometheus with Grafana and NVIDIA's DCGM exporter show GPU telemetry. What open source leaves to the operator is the workflow that ties them together, from an order to a server and back to the free pool.

An integrated platform takes that workflow on, and with it creates a dependency on its vendor. Four things decide how strong that dependency is. APIs: whether every step a customer and an operator take, from ordering to metering, can be driven and read through documented, versioned APIs, so that Northlight's own tools and its tenants' automation do not depend on the vendor's console. Portability: which layers speak standard interfaces that another implementation also speaks, and which use the vendor's own formats. Customisation: whether Northlight can add a new GPU model, a new product, a new site or a new rule without waiting for the vendor's release. Exit strategy: whether all the state the platform holds can be exported in a documented format, and what keeps running if the contract ends.

Portability can be checked against public standards. The Certified Kubernetes program run by the CNCF tests that every vendor's Kubernetes supports the required APIs, with the stated aim of interoperability from one installation to the next. Vendors must provide a current Kubernetes version at least once a year to stay certified, and anyone can rerun the same tests with the standard open source tools, Sonobuoy or Hydrophone. The Deployment qwen3 with its Service and its image pinned by digest moves between certified clusters unchanged. Gateway API, the Kubernetes standard for routing traffic in, makes the same split explicit with three support levels. Core features are portable and expected of all implementations. Extended features are portable and optional, and an implementation lists the ones it supports in its GatewayClass under status.supportedFeatures. Implementation-specific features are not portable, have no API types of their own and are not covered by the conformance tests. The owner's decks describe BNK the same way: it adheres to CNCF Gateway API standards while embedding AI filters, configured with Gateway API resources plus F5's own custom resources for the endpoint picker. An HTTPRoute moves to another implementation. The F5 resources have to be expressed again in whatever the next platform offers.

The failure cases show where the integration cost really sits. Suppose a reservation for gpu-srv-3 succeeds and the network step fails. Something must retry the network step or release the server, clean up what was half created, show the customer the correct state, keep billing from starting, return the GPUs to the pool and record the failure. Whoever owns that code owns a large part of the cloud. A licence fee is not the total cost either: engineering, integration, upgrades, security patches, incident response and support cost money whichever way the platform is built, so the comparison is over three to five years.

An exit plan turns all of this into numbers. It lists what must move: tenants, orders, usage and billing records, audit logs, keys, images, models and datasets, and the format of each. It estimates the transfer time. The FP8 build of Qwen3-32B is 34.3 GB, which crosses a 10 Gb/s link in about 27 seconds. A 200 TB dataset takes about 44 hours over the same link and about 4.4 hours at 100 Gb/s. And it names who carries the move out. Sovereignty includes this kind of dependency management: knowing whether models, data, keys and workloads can move if a provider, a contract, a jurisdiction or a business condition changes.

What to keep

Ask who, then ask where

A location is easy to state and easy to check, which is why sovereignty is so often reduced to it. The fuller question is who controls each of six things. Data: every copy and every place it is processed, held in by egress rules, placement labels and a defined edge. Administrative access: the named people, their employer and where they connect from, with credentials that expire by themselves and an audit log the administrators cannot edit. Keys: who can use them, how that is proven on disk, and whether the plaintext is ever in memory the operator can read. The management plane: who updates, observes and reaches the machines. Models and artefacts: where they came from and who can change them. Jurisdiction: which authorities the operating company answers to. Confidential computing narrows what an operator can see, within documented limits, and leaves availability with the operator. The right amount of control differs per workload, and each added control costs convenience. A public-information assistant can live with global dependencies, a sensitive RAG system needs its data, identities and model endpoint held in place, and a regulated workload needs strict boundaries around infrastructure, administrators and operations. On premises, private, air-gapped and sovereign answer four different questions, and a telco site or a neocloud in the country answers only the first of the six. The software that runs the cloud is a dependency as well, so its APIs, its standard interfaces and an exit plan with real transfer times belong in the same review.
