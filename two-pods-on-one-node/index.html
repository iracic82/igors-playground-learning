Kubernetes underneath

Two Pods on one node

A namespace, a virtual cable and a bridge that learns

Two Pods on the same node are the shortest trip a packet can take in Kubernetes, and it already uses most of the parts. Each Pod lives in its own network namespace, a private copy of the Linux network stack. A CNI plugin joins that namespace to the node with a virtual cable called a veth pair, and plugs the node end into a bridge, which is a switch made of software. This lesson follows one TCP SYN from Pod client at 10.244.1.12 to Pod web-1 at 10.244.1.15. It shows the routing decision, the ARP exchange, the bridge's forwarding table and every header with its size in bytes.

Chapter 1 of 14

A Pod is a network namespace

A private network stack that starts out empty

A Pod's network identity is a Linux network namespace. A network namespace is a separate copy of the kernel's network stack: its own devices, its own IPv4 and IPv6 stacks, its own routing tables, its own firewall rules and its own port numbers. All containers of one Pod share one namespace, which is why they reach each other on localhost and cannot both listen on the same port. The container runtime creates the namespace when it sets up the Pod, before any application container starts. At that moment it holds a single device, the loopback interface lo. The Pod has no address and no way out. The node itself runs in the first namespace of the machine, called the host namespace, where the real network card lives.

The runtime does not leave the namespace floating. containerd creates it with a random name and pins it as a file under /var/run/netns, its default directory. The option netns_mounts_under_state_dir moves these files under containerd's state directory, in StateDir/netns, and this lesson assumes the default. The name is built from 16 random bytes in the shape cni-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx, so a real path looks like /var/run/netns/cni-5f0c2a1e-8b3d-7e41-a9c6-0d27f4b18e53. That file is the handle every later step uses. The CNI plugin gets it as CNI_NETNS and enters the namespace through it. Kubernetes also needs a process to hold the Pod together while application containers come and go. containerd starts a small sandbox container from the pause image for that, registry.k8s.io/pause:3.10.2 in the default configuration on containerd's main branch. Released versions of containerd may default to another tag.

The namespace lives as long as the Pod's sandbox. When the sandbox is removed and the namespace is freed, the kernel destroys every veth device inside it, and a physical device would be moved back to the host namespace. This is why the Pod's address is stable while its containers restart. If the container in Pod client crashes and starts again, the Pod keeps 10.244.1.12, because the namespace and its eth0 survive the restart. Only a new Pod gets a new namespace and, usually, a new address.

Chapter 2 of 14

The runtime finds the plugin

One configuration file and one directory of programs decide the Pod network

The container runtime does not know about flannel. It knows a directory of network configuration files and a directory of plugin programs. containerd's CRI plugin reads its configuration from conf_dir, which defaults to /etc/cni/net.d, and looks for executables in bin_dirs, which defaults to /opt/cni/bin. By default it loads only one configuration file, because max_conf_num is 1. Whatever network that file describes becomes the Pod network of the node.

Flannel puts both halves in place with init containers in its DaemonSet. The container install-cni-plugin copies the flannel binary to /opt/cni/bin/flannel. The container install-cni copies the configuration to /etc/cni/net.d/10-flannel.conflist. That file is a list of two plugins under one network name, cbr0, with cniVersion 1.0.0. The first entry is type flannel, with a delegate block that sets hairpinMode and isDefaultGateway to true. The second is type portmap with the capability portMappings, which only matters for Pods that ask for a hostPort.

The CNI specification calls the first kind an interface plugin, because it creates an interface inside the container and gives it connectivity. It calls the second kind a chained plugin, because it adjusts an interface that already exists. The runtime runs them in order for ADD and in reverse order for DEL, and it passes each one the result of the previous one. The current specification is version 1.1.0. Kubernetes requires a plugin that supports version 0.4.0 or later and recommends 1.0.0.

The contract has strict rules for the runtime. It must create the namespace before it runs any plugin. It must never run two operations for the same container at the same time, but it may run them for different containers in parallel. Every ADD must eventually be followed by a DEL, even when the ADD failed. Plugins must therefore lock shared state themselves, and host-local does that with a lock file, as a later chapter shows.

Chapter 3 of 14

The CNI plugin plugs the Pod in

One call creates the cable, the address and the routes

The runtime now runs a CNI plugin. CNI, the Container Network Interface, is a small contract: the runtime starts a program, passes the request in environment variables, and sends the network configuration as JSON on standard input. The command is ADD. On a flannel node the plugin named flannel reads the node's Pod range from /run/flannel/subnet.env and hands the work to the bridge plugin. The bridge plugin does four things. It creates the bridge cni0 if it is missing. It creates a veth pair, a virtual Ethernet cable with two ends. It moves one end into the Pod's namespace and names it eth0, and it attaches the other end to the bridge. Then an address plugin called host-local picks a free address from 10.244.1.0/24, and the plugin sets the Pod's routes.

The flannel plugin itself does little work. It reads FLANNEL_NETWORK, FLANNEL_SUBNET, FLANNEL_MTU and FLANNEL_IPMASQ from /run/flannel/subnet.env, which flanneld wrote when it started, and builds a configuration for the bridge plugin from them. It adds the route to the whole flannel network, 10.244.0.0/16, to the routes that host-local will report. It also saves the generated configuration under /var/lib/cni/flannel, in a file named after the container ID, so that DEL can later undo exactly what ADD did.

The names in this chapter can be checked on the node. The node end of the cable gets a random name, veth followed by eight hex digits from 4 random bytes, such as veth3f2a91c4. If that name is taken, the plugin tries again, up to 10 times. To find which node end belongs to which Pod, ethtool -S on the node end prints peer_ifindex, the interface number of the other end inside the Pod. The setup takes a few milliseconds of kernel calls. On a GPU node this happens for every model server Pod before its container starts, so a broken CNI plugin stops model servers before they ever load a weight.

Chapter 4 of 14

What the bridge plugin also sets

Forwarding, hairpin, a waiting loop and an announcement

The bridge plugin does more than make a cable. Because flannel asks for isGateway, the plugin puts 10.244.1.1/24 on cni0 and switches on IPv4 forwarding for the node with net.ipv4.ip_forward. The kernel's default for that setting is 0, which means a Linux machine drops packets that are not addressed to itself. Without forwarding, Pods on this node could still reach each other through the bridge, but nothing could leave for another node.

Because flannel also sets isDefaultGateway, the plugin adds a default route, 0.0.0.0/0 via 10.244.1.1, inside the Pod. The flannel plugin's README states what happens without it: only Pod to Pod traffic works. The route to 10.244.0.0/16 comes from the flannel plugin, which adds it to the address plugin's result.

Hairpin mode is set per port, on the node end of each cable. A bridge normally never sends a frame back out of the port it came in on. Kubernetes needs that rule turned off. A Pod that calls a Service address can be load balanced to itself, and after the address is rewritten the frame has to leave by the port it entered. The Kubernetes page on debugging Services names this exact failure: a Pod cannot reach itself through its Service when kube-proxy runs in iptables mode and Pods hang off a bridge. The plugin refuses to combine hairpinMode with promiscMode and fails with the message cannot set hairpin mode and promiscuous mode at the same time.

Two smaller steps finish the job. Inside the Pod the plugin writes 1 to arp_notify for eth0 before it adds the address. The kernel then sends a gratuitous ARP when the device comes up, an unasked announcement of the Pod's own IP and MAC addresses, so neighbours with old entries update them. Then ADD waits for the node end of the cable to come up. It checks the port after 0, 50, 500, 1000 and 1000 milliseconds, about 2.5 seconds in total, and fails with bridge port in error state if the port never reaches the up state.

Chapter 5 of 14

host-local keeps the books

Every Pod address is a small file on the node

host-local is the address plugin, called IPAM in CNI terms, for IP address management. It has no server and no database. It keeps one directory per network, /var/lib/cni/networks/cbr0 on a flannel node, and writes one file per address it has handed out. The file for the client is named 10.244.1.12. It holds two lines, the container ID and the interface name eth0, separated by a carriage return and a line feed, and it is written with mode 0600 so only root can read it. Beside the address files sit a file named last_reserved_ip.0, which remembers the last address handed out in range 0, and a file named lock.

The lock matters because CNI allows the runtime to set up two Pods at the same time. Both ADD calls would read the same directory and could pick the same free address. host-local takes the lock first, picks an address and writes the file, then releases it.

The range comes from the node's Pod range. By default the gateway is the .1 address, the first address given out is .2, and the last is .254, because the broadcast address .255 is left out. In the code the default rangeStart is .1 itself, the address right after the subnet address. A comment in range.go admits that this clashes with the gateway, and the iterator skips the gateway, so .2 is the first address a Pod receives. That leaves .2 to .254, which is 254 minus 2 plus 1, or 253 addresses for Pods on each node. The kubelet's maxPods defaults to 110, so a /24 per node has room to spare. Kubernetes picks the /24 itself, because kube-controller-manager's --node-cidr-mask-size defaults to 24 for IPv4.

host-local does not always give out the lowest free address. Its allocator is round robin. It starts after the address in last_reserved_ip.0 and walks the range, so the address of a Pod that was just deleted is not handed out again at once. That is why the client in this lesson has .12 and web-1 has .15 and not .2 and .3. When every address is taken, ADD fails with no IP addresses available in range set, and the Pod stays in ContainerCreating. The files live on disk, so the bookkeeping survives a reboot. The documentation suggests a directory on tmpfs, such as /var/run/cni, for setups where every container is gone after a reboot.

Chapter 6 of 14

Neighbour or gateway

The Pod's own routing table decides who gets the frame

The application in Pod client calls connect() for 10.244.1.15 port 8080. The kernel inside the Pod builds a TCP SYN and has to decide where to send it. It looks in the Pod's routing table and takes the most specific match. The address 10.244.1.15 falls inside 10.244.1.0/24, a route with no gateway, which means the destination is on the same Ethernet segment and can be reached directly. A destination outside that range, such as a Pod on another node, would match a route through 10.244.1.1 and go to the bridge first. IP now knows the next hop. Ethernet needs something else: a MAC address, the 6 byte hardware address that every frame carries. The Pod does not know web-1's MAC address yet, so the SYN waits.

The decision uses the routes the CNI plugin wrote a moment earlier. The kernel compares the destination with every route and takes the one with the longest prefix that matches. Here three routes are candidates: the default route 0.0.0.0/0 matches with 0 bits, 10.244.0.0/16 matches with 16 bits and 10.244.1.0/24 matches with 24 bits. The /24 wins. The CNI result reported only two routes, and this third one appeared by itself. The kernel adds a route for the subnet whenever an address with a prefix length is put on a device, which is what scope link and src 10.244.1.12 in the routing table record.

The same rule decides the source address. The packet leaves with 10.244.1.12, the address the route names in src. For an application this choice is invisible, and it matters later: web-1 will see this exact address. For a model server behind a Service the path has one more step. The Service address is outside the /24, so this lookup picks the default route via 10.244.1.1 and the packet goes to cni0's own MAC address. The node rewrites the destination to a Pod address with kube-proxy's rules and routes the packet back onto the bridge, so a client on the same node as a vLLM Pod still reaches the model server without the packet ever touching the node's network card.

Chapter 7 of 14

ARP finds the neighbour

A broadcast question and a private answer, 42 bytes each

ARP, the Address Resolution Protocol, turns an IPv4 address into a MAC address. The Pod sends an ARP request to the broadcast address ff:ff:ff:ff:ff:ff. It asks who has 10.244.1.15 and gives its own addresses so the owner can answer. The request is 42 bytes: a 14 byte Ethernet header and a 28 byte ARP message. It leaves eth0, comes out of the node end of the cable and enters the bridge, which sends a broadcast out of every other port. Every Pod on the node receives it. Only web-1 owns the address, so only web-1 replies, straight to the client's MAC address. Had the destination been on another node, the Pod would have sent the same question for 10.244.1.1, and the bridge itself would have answered.

The ARP message has a fixed layout of 28 bytes for IPv4 over Ethernet. It starts with the hardware type 1 for Ethernet and the protocol type 0x0800 for IPv4, followed by the lengths 6 and 4 of those addresses. Then come the operation code, 1 for a request and 2 for a reply, and four addresses: the sender's MAC and IP addresses and the target's MAC and IP addresses. In the request the target MAC is all zeros, because that is the unknown. In the reply web-1 fills in its own MAC address as the sender and puts the client's addresses in the target fields.

The reply teaches both sides at once. The client learns web-1's MAC address from the reply. web-1 learns the client's MAC address from the request it answered, so when it sends its SYN-ACK a moment later it does not need to ask. The broadcast also reaches the node itself through cni0, and every other Pod on the node. Each of them reads the target address, sees that it is not its own and ignores the request. On a GPU node with dozens of Pods every new conversation starts with one such broadcast to all of them, which is cheap at this size.

Chapter 8 of 14

The neighbour table keeps the answer

ARP answers are cached, aged and checked again

The answer goes into the Pod's neighbour table, which ip neigh shows inside the Pod. The entry for 10.244.1.15 now reads lladdr d6:3f:71:a8:44:0f REACHABLE. The kernel keeps every entry in one of a few states. INCOMPLETE means a request was sent and no answer has come yet. REACHABLE means the address was confirmed recently. STALE means the entry still works but has not been confirmed for a while. DELAY and PROBE are the steps of checking it again, and FAILED means no answer came. PERMANENT is for entries an administrator or a program wrote, and they never expire.

A REACHABLE entry stays that way for a random time between half and one and a half times base_reachable_time. The default is 30000 milliseconds, so the entry is trusted for 15 to 45 seconds. The random part keeps many hosts from checking at the same moment. Every TCP acknowledgement from web-1 counts as proof that the neighbour is still there and resets the clock. When the time runs out with no proof, the entry turns STALE. The next packet still goes out at once, and the kernel waits delay_first_probe_time, 5 seconds by default, before it probes the address again with a unicast ARP request.

If the owner of an address is gone, the probes fail. The kernel sends ARP requests 1000 milliseconds apart, retrans_time_ms, up to mcast_solicit, 3 by default, for an unknown address. After three unanswered requests, about three seconds, the entry is FAILED and the application's connect() call ends with an error that says the host is unreachable. This is what a client sees when it calls the address of a Pod that was just deleted on the same node.

The table has limits too. The garbage collector leaves the table alone below gc_thresh1, 128 entries by default. gc_thresh2, 512, is a soft maximum that the table may exceed only briefly, and gc_thresh3, 1024, is the hard maximum. What those limits count depends on the kernel. On the released long term kernels that GPU nodes usually run, the ARP table is one table for the whole machine, so the entries of every Pod namespace and of the node itself count together against the same 1024. The current mainline source gives each network namespace its own table and copies the limits from the host namespace when the namespace is created. A single Pod talks to few neighbours. The risk is the sum across all Pods and the node's own entries for each Pod it forwards to, and that sum can reach the hard maximum on very dense nodes.

Chapter 9 of 14

The bridge learns as it listens

A table of MAC addresses and the ports they were seen on

The bridge cni0 behaves like an Ethernet switch. It keeps a forwarding table, called the FDB, that maps a MAC address to the port where that address was last seen. It fills the table by reading the source address of every frame that arrives, which is called learning and is on by default for every port. A frame for a known address goes out of one port. A frame for an unknown address, or a broadcast, is flooded to every other port. The ARP exchange taught the bridge both addresses. The request carried the client's MAC address in through the client's port. The reply carried web-1's MAC address in through web-1's port. Everything after this is forwarded to exactly one port.

Learned entries do not last forever. An entry the bridge learned is dynamic and ages out after ageing_time, the number of seconds a MAC address is kept after the last frame from it. The kernel's default is 300 seconds. If web-1 stays silent for five minutes its entry disappears, and the next frame for it is flooded again until web-1 answers and is learned once more. A Pod that moves away leaves no stale entry for longer than that, because a deleted Pod's cable and port are removed with it.

The table also holds entries the bridge did not learn. bridge fdb show lists the MAC address of each port device marked permanent, and the bridge's own MAC address on cni0. The bridge(8) man page explains what permanent and local mean: a frame for such an address is not forwarded to any port and is handed to the node itself. That is the mechanism the next lesson needs. A frame addressed to cni0's MAC address goes up into the node's IP layer, where the node routes it like any router.

Chapter 10 of 14

The SYN crosses the bridge

74 bytes, three hops, and nothing changed on the way

The Pod now has web-1's MAC address and sends the waiting SYN. The frame is 74 bytes: 14 bytes of Ethernet header, 20 bytes of IPv4 header and 40 bytes of TCP, which is a 20 byte header plus 20 bytes of options. It goes down the client's cable into the bridge. The bridge reads the destination MAC address, finds it in the FDB and sends the frame out of web-1's port. The cable delivers it to eth0 inside web-1. The bridge changed nothing. A switch forwards frames by MAC address and does not touch the IP header, so the time to live field is still 64 and both MAC addresses are the ones the client wrote. No router took part, because both Pods share one subnet.

The options are what make the TCP header 40 bytes long. The maximum segment size option takes 4 bytes and says 1410, the largest payload this Pod wants to receive in one segment. SACK permitted takes 2 bytes, the timestamp option 10 bytes, the window scale option 3 bytes, and one no-operation byte pads the list to a multiple of four: 4 + 2 + 10 + 3 + 1 = 20. The segment size is 1410 because eth0 has an MTU of 1450, minus 20 bytes of IPv4 header and 20 bytes of TCP header. That MTU was chosen for the tunnel between nodes, and it applies here as well, although these two Pods never use the tunnel.

On the bridge the forwarding step is cheap. One lookup in a hash table finds web-1's port, and the kernel hands the frame to that port's veth device, which delivers it into web-1's namespace. No copy goes to the node's network card, and the switch outside never sees this packet. A capture on the node's eth0 shows nothing. A capture on cni0 or on either node end of the cables shows the frame.

Chapter 11 of 14

Bridged frames still pass the firewall

A switch inside Linux can call iptables

A hardware switch never looks at IP headers. A Linux bridge can. When the kernel module br_netfilter is loaded, the setting net.bridge.bridge-nf-call-iptables decides whether frames that cross a bridge are also passed to the iptables chains. Its default is 1, enabled. On a node where the module is loaded, the SYN from the client to web-1 passes the node's FORWARD chain on its way from one port of cni0 to another, although no router took part.

This is not a detour for nothing. It is what lets the rules of kube-proxy and of network policy act on traffic between two Pods on the same bridge. Service traffic shows why. A Service address is outside the Pod's /24, so the client sends that packet to its gateway, the MAC address of cni0 itself. The node receives it as a router would, and kube-proxy's rules in the nat PREROUTING chain rewrite the destination to the chosen Pod whether or not br_netfilter is loaded. The trouble is the reply. If the chosen Pod sits two ports away on the same bridge, it answers the client's own address, which is on its /24, so the bridge switches the reply straight across. Without bridge-nf-call-iptables no rule and no connection tracking sees that reply, the rewrite is never undone, and the client receives an answer from the Pod's address when it expected one from the Service address. It does not match the connection, and the connection fails. A Pod that reaches itself through its Service, the hairpin case, breaks the same way.

Flannel adds rules of its own to the FORWARD chain, because Docker 1.13 and later set the chain's default policy to DROP, which once broke Pod traffic between hosts. flanneld adds a jump with the comment flanneld forward to a chain named FLANNEL-FWD. That chain accepts any packet whose source is in 10.244.0.0/16 and any packet whose destination is in 10.244.0.0/16. The flag --iptables-forward-rules turns this on and defaults to true, and flanneld checks the rules again every 5 seconds, the default of --iptables-resync. The SYN to web-1 matches the first accept rule and goes on.

Chapter 12 of 14

No address was rewritten

web-1 sees the client's own address

web-1 accepts the connection and sees the caller as 10.244.1.12, the client's real address. This is a rule of the Kubernetes network model: every Pod gets its own address that is unique in the cluster, and Pods talk to each other directly, without proxies or network address translation. NAT appears in two other places. A Service address is rewritten to a Pod address, and traffic that leaves the cluster takes the node's address. This packet was addressed to a Pod, so neither applied. The bridge plugin runs with ipMasq set to false, and flannel's own masquerade chain returns early for traffic from the Pod range to the Pod range. The SYN-ACK goes back through the same two cables, and the client's ACK completes the handshake.

The rule that proves it is flannel's masquerade chain, FLANNEL-POSTRTG, which flanneld writes because the DaemonSet runs it with --ip-masq. Its rules are checked in order. A packet that kube-proxy marked for masquerade returns at once. A packet from this node's Pod range to the cluster's range, 10.244.1.0/24 to 10.244.0.0/16, returns, and so does a packet from the cluster range to this node's range. A packet from outside the cluster to a local Pod returns too. Only after those does a rule masquerade the remaining traffic from 10.244.0.0/16, except traffic to the multicast range 224.0.0.0/4, with --random-fully where the kernel supports it. A last rule masquerades traffic from outside the cluster to other Pod ranges. The SYN to web-1 matches the second rule and keeps its source address.

The network model page adds a third rule to the two this chapter quotes: agents on a node, such as the kubelet, can reach every Pod on that node. The cluster networking page defines which address is the Pod's: only the addresses listed in the Pod's status count. That page writes the field as pod.status.ips, while the field in the Pod API is status.podIPs, with status.podIP holding the first address, so kubectl get pod client -o jsonpath='{.status.podIPs}' is the command that prints it. kubectl get pod -o wide shows 10.244.1.12 for the client, the same address web-1 sees on its socket. For a model server this matters for logs, rate limits and network policy, which all key on the caller's real Pod address.

Chapter 13 of 14

When the network is not ready

What the kubelet, containerd and kubectl show when CNI fails

Every step so far depended on the CNI plugin being installed and working. When it is not, the failure shows up in three places. containerd reports a runtime condition named NetworkReady to the kubelet. With no usable CNI configuration the condition is false with the reason NetworkPluginNotReady and a message that starts with Network plugin returns error. The kubelet turns that into a node level error, container runtime network not ready, and stops starting Pods that need the Pod network. It records a Warning event with the reason NetworkNotReady.

Pods that use the host network still start. flannel's own DaemonSet runs with hostNetwork set to true, which is how the network plugin can be installed on a node that has no Pod network yet. kubeadm documents the visible symptom: after kubeadm init, CoreDNS stays Pending until a Pod network is installed, and that is expected.

A second kind of failure happens when CNI is installed but an ADD fails. The kubelet then reports an event with the reason FailedCreatePodSandBox on the Pod, and the Pod stays in ContainerCreating while the kubelet retries. The most common message from the flannel plugin is failed to load flannel subnet.env file, followed by Check the flannel pod log for this node. It means flanneld on this node has not written /run/flannel/subnet.env, often because it cannot reach the API server or the node has no Pod range.

The Pod's conditions tell the same story. PodReadyToStartContainers turns true only after the sandbox exists and its network is configured. Image pulls and container creation happen after that point, so a model server Pod that never gets this condition never starts pulling its image. CNI errors themselves carry numbers. Codes 0 to 99 are reserved by the specification, for example 7 for an invalid network configuration and 11 for try again later, and plugins may use 100 and above for their own errors.

Chapter 14 of 14

Taking it apart again

DEL undoes ADD, and GC cleans up what DEL missed

When the client Pod is deleted, the runtime runs the plugins again with CNI_COMMAND set to DEL, in reverse order, portmap first and flannel last. The specification requires the runtime to pass prevResult, the result the plugin printed during ADD, so the plugin knows what it created. The flannel plugin reads the configuration it saved under /var/lib/cni/flannel for this container ID, passes it to the bridge plugin, and deletes the saved file.

The bridge plugin releases the address through host-local, which removes the file 10.244.1.12 from /var/lib/cni/networks/cbr0. If the namespace still exists, it also deletes eth0 inside it, which removes both ends of the veth pair and the bridge port with them. The bridge cni0 stays, because other Pods use it. If the namespace is already gone, the kernel has destroyed the veth pair, and the plugin only releases the address.

DEL must be safe to repeat. The specification allows a DEL to be followed by more DELs, and the runtime must run DEL even after a failed ADD. The bridge plugin's source says so in a comment: delete can be called multiple times, so it does not return an error if the device is already removed. A plugin that failed on a missing device would block cleanup forever.

Nodes still leak addresses when a runtime crashes between steps. The GC command, added in the CNI 1.1 specification, handles this. The runtime passes the list of attachments that should exist, and the plugin removes everything else. host-local implements GC by deleting the address files whose container ID is not on the list. After DEL, the address .12 is free, but host-local's round robin moves on, so the next Pod most likely gets .16 or later and not .12.

What to keep

One subnet, one bridge, no translation

The whole exchange stayed inside node-1. The CNI plugin had prepared everything when each Pod started: a namespace, a veth pair, an address from the node's range and three routes. The packet itself needed one routing decision in the Pod, one ARP exchange and one lookup in the bridge's forwarding table. The node's network card and the tunnel device carried nothing. A client Pod that calls a model server on the same GPU node takes exactly this path. When the model server is on another node, the Pod sends the packet to its gateway instead, and the next lesson follows it there.
