BNK and gateways

A sandbox and its gateway

The sandbox fences one agent's process. The tenant's gateway owns everything that agent sends.

An agent is a program that decides for itself what to call next. Put one in a GPU cloud and two different jobs appear. The first is to fence the agent's process, so it can only open the connections its owner allowed and never sees the secrets it uses. That is the sandbox's job. The second is to own the tenant's whole path to the models: which address the traffic leaves from, which network it travels in, which key and budget it spends, and which GPU answers. That is the tenant gateway's job.

This lesson follows the design the owner's blog recommends. A sandbox, NVIDIA OpenShell or Agent Substrate, sits in front. BIG-IP Next for Kubernetes (BNK) sits behind it as the tenant's AI Gateway. You will see how OpenShell, in its default layout, builds a sandbox from two Pods and three NetworkPolicies, why that fence holds only when the cluster's network plugin enforces NetworkPolicy, what its supervisor checks on HTTP, GraphQL and MCP, how it injects a key the agent never holds and how it writes every decision down in OCSF. Then the same slice with Agent Substrate: its egress gateway puts a signed token, minted by Substrate's API server ateapi, on each actor's request, and BNK checks that token before the request reaches Qwen3-32B on gpu-node-1.

Where the agent's traffic fits

One slice of the platform: a sandboxed agent calling a model

Michael Levan opens his post on agentic infrastructure with the line that networking is 90% of what you need to get right. The owner's blog agrees and takes it one step further. If the network is 90% of the job, the network should be the platform the AI factory runs on, from picking the site down to picking the GPU. Levan's post, "Agent Substrate + Agentgateway: Your Secure Egress Path to Models", walks one slice of that platform: getting a sandboxed agent's traffic to a model. The owner's post zooms out to the platform that slice sits in.

In the owner's tiers, agent traffic lives in tier 3, the tenant gateway, and tier 4, inference. In tier 3 BNK is the VXLAN tunnel endpoint on a BGP EVPN fabric. Each tenant is a VRF, a separate routing table with its own VXLAN network identifier (VNI), and VRFs can be set to strict isolation. Each tenant gets its own egress and its own pool of source addresses for SNAT, and the AI Gateway runs on the same tenant gateway. In tier 4 the traffic engine TMM asks the F5 Endpoint Picker over gRPC ext_proc which GPU worker should take the request.

The owner's recommendation splits the work in two. Isolating the agent's process is the sandbox's job, with Agent Substrate or NVIDIA OpenShell. BNK is the tenant gateway behind it. The sandbox's allowed destination for model calls is the tenant's AI Gateway, named by its fully qualified domain name (FQDN).

In this lesson the cluster is northlight-eu. A tenant's agent called triage runs in a sandbox in the namespace agents. It calls the model at api.northlight.example, which resolves to the BNK address 203.0.113.80. Behind that address the Deployment qwen3 serves Qwen3-32B from its FP8 build, 34.3 GB of weights, on one H100 per Pod: qwen3-6f7d9c8b4-x7k2p at 10.244.1.21 on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t at 10.244.2.22 on gpu-node-2, both on port 8000. Chapter 2 of 15

An OpenShell sandbox is two Pods

The agent runs in one Pod, its supervisor in another, joined by a label

OpenShell has a gateway that stores platform state and hands sandbox creation to a Kubernetes compute driver. The driver creates a Sandbox resource. The Agent Sandbox controller, from the Kubernetes SIG project at agent-sandbox.sigs.k8s.io, creates the workload Pod from that resource. The driver creates the supervisor Pod itself, as a separate Pod named os-supervisor-<id>, where <id> is the sandbox's ID in lower case. The supervisor Pod carries an owner reference to the Sandbox, so it is deleted with it, without fighting the Agent Sandbox controller over the workload Pod. A PersistentVolumeClaim keeps /sandbox across Pod restarts.

That is the default layout, and the one this lesson follows. The driver's README also documents a shared supervisor topology: with supervisor_topology = "gateway", each new sandbox generation becomes an instance on one supervisor process that Helm deploys in the gateway namespace, with no supervisor Pod or boundary Service of its own.

Two labels pair the Pods. openshell.ai/boundary-pair holds one value that the workload Pod and its supervisor Pod share, and no other Pod has. openshell.ai/boundary-role says which side each Pod is: workload or supervisor. Per sandbox the driver also creates a Service os-boundary-<id>, which always selects the workload Pod, a Service os-supervisor-<id>, which always selects the supervisor Pod, and bootstrap Secrets.

The two Pods split the work. The sandbox side owns the agent's process. It applies Landlock, the kernel's file access sandbox, and seccomp filters on system calls. It identifies the binary behind each network system call and relays the connection to the supervisor. The supervisor authenticates to the OpenShell gateway with a JWT, loads the sandbox's policy and provider state, decides each destination and each request, and opens the approved connections to the outside. The workload receives no gateway credential, no provider identity and no proxy credential. Both Pods run as a non-root user with allowPrivilegeEscalation set to false, all Linux capabilities dropped and the runtime's default seccomp profile.

The Kubernetes setup page lists what has to be there first: a cluster with RBAC (the current docs name 1.33 as the oldest version tested, while the setup page for 0.1.0 asked for Kubernetes 1.29 or later), a CNI that enforces ingress and egress NetworkPolicy in sandbox namespaces, Helm 3, and the Agent Sandbox controller with its CRDs. On the scene, the Pod called client at 10.244.1.12 stands for the workload Pod and the Pod called web-1 at 10.244.1.15 stands for its supervisor, both on gpu-node-1 at 10.0.1.11.

Chapter 3 of 15

The fence is NetworkPolicy

The workload Pod may not open a connection of its own

Before it releases any workload Pod, the OpenShell driver creates a namespace-wide NetworkPolicy called openshell-sandbox-workloads. It selects every Pod labelled openshell.ai/boundary-role: workload and lists both Ingress and Egress in policyTypes. Its one ingress rule admits TCP on the boundary port, 5500 by default, from Pods labelled as supervisors. Its egress list is empty. In Kubernetes an empty egress list on a Pod that is isolated for egress, with no other policy adding to it, allows no new connection at all. That includes DNS to CoreDNS at 10.96.0.10 and the Kubernetes API. The agent cannot even look up a name by itself.

Replies still flow. The Kubernetes documentation says reply traffic for an allowed connection is implicitly allowed. So in the direction the 0.1.x setup page describes, the supervisor opens the boundary connection, the workload answers on it, and the agent's requests travel back to the supervisor over that channel. The supervisor evaluates each one and opens the approved connection upstream.

A second namespace-wide policy, openshell-sandbox-supervisors, selects only supervisor Pods and gives them one empty egress rule, which allows all egress. The comment in the driver's source says why: other default-deny policies in the namespace would otherwise block the supervisors' DNS and approved upstream connections, and policies add up.

The driver's source on main has moved new sandboxes to a mode it calls runtime-initiated control, where the workload dials its own supervisor. A third policy per sandbox, os-control-<id>, admits exactly one flow: from this pair's workload Pod to this pair's supervisor Pod on the boundary port, as workload egress and supervisor ingress. The policy's UID and resourceVersion are recorded with the sandbox. If the policy disappears or changes, reconciliation suspends the workload. The setup page for 0.1.x still describes the supervisor dialling the workload. Only the dial direction differs.

The supervisor Pod has a tcpSocket readiness probe on port 5501, which accepts connections only while its gateway session is ready. If you add a default-deny ingress policy to a sandbox namespace, allow TCP 5501 from the node, or kubelet cannot mark the supervisor ready. The lesson "Who may talk to whom" covers NetworkPolicy itself.

Chapter 4 of 15

No path except the supervisor, if the CNI enforces it

Kubernetes accepts a NetworkPolicy that nothing enforces

OpenShell's promise that the agent has no network path except through its supervisor rests on one condition, and NVIDIA's setup page states it as a warning. The cluster must use a CNI that enforces NetworkPolicy for both ingress and egress in every sandbox namespace. OpenShell creates the policies, but Kubernetes accepts them even when no plugin enforces them. Without enforcement, sandbox workloads may reach the network directly and bypass supervisor policy. The Kubernetes documentation says the same thing in its own words: posting a NetworkPolicy has no effect unless your networking solution supports network policy.

The scene shows exactly the case to worry about. Its tunnel devices are flannel.1, and flannel on its own does not implement NetworkPolicy. On a cluster like that, kubectl get networkpolicy -n agents lists openshell-sandbox-workloads, the YAML looks right, and the workload Pod can still open a TCP connection to 203.0.113.80 or to any address on the internet. Nothing in the API tells you. So test it: from inside the workload, try a direct connection to an outside address and to CoreDNS, and expect both to fail. Run the test again after every CNI upgrade.

The NetworkPolicy does one job: it removes the direct path. It does not decide which supervisor talks to which sandbox. TLS, the Sandbox Protocol JWT, the sandbox generation and the recorded Pod UIDs bind a supervisor to its exact sandbox. Any supervisor in the namespace may reach any workload's boundary port at the network layer, and the protocol refuses the wrong pairing.

Policies are additive, and that cuts both ways. An extra policy in the sandbox namespace that allows egress for all Pods, say a team's allow-egress-all written for something else, adds to the workload's empty egress list and opens it. The OpenShell driver's README says only the driver and its trusted Agent Sandbox controller may administer the sandbox namespace, its Sandbox resources, its Pods and its ServiceAccount. In operator mode, where the platform team brings its own namespaces, adding a namespace to the allowlist grants that trust.

Chapter 5 of 15

What the supervisor decides

Each binary gets the destinations its rules name, and nothing else

A sandbox policy is a YAML file with version: 1 and up to five sections. filesystem_policy says which paths can be read or written, enforced by Landlock at startup. landlock says whether the sandbox may still start when those rules cannot be applied. process sets the user and group. network_policies lists the destinations each binary may reach and the requests it may send. network_middlewares adds further inspection. Filesystem and process settings are fixed once the sandbox starts. Network rules reload while it runs, with openshell policy update and --wait.

The policy in force comes from the first source that applies: a global policy from the gateway administrator, then the sandbox's saved policy, then a policy inside the image, then OpenShell's restrictive default. Attached providers add their own network rules on top, unless a global policy is active, which suppresses them. That combination is the effective policy.

Every outbound connection is denied unless a rule allows it. A rule pairs a list of endpoints with a list of binaries, and allows every listed binary to reach every listed endpoint. Binaries are matched by the real path the kernel reports, so /usr/bin/python3 on Ubuntu 24.04 has to be listed as /usr/bin/python3.12. A rule also covers processes a listed binary starts. OpenShell records a hash of each executable the first time it connects and denies later connections if the file changes. A rule with an empty binaries list allows nothing.

Rules are not an ordered firewall list. Every matching rule adds access, and a matching deny wins over any allow. Private addresses are blocked by default against server-side request forgery, and loopback, link-local and 169.254.169.254 are never authorized. An exact hostname may still reach the private addresses it resolves to, and allowed_ips pins the addresses a name may resolve to.

Under the YAML sits a policy engine. The supervisor's network crate implements the YAML backend as OpaEngine and compares Rego endpoint rules when the policy reloads. The deny log names it: engine:opa. A Cedar backend exists in a separate crate.

Chapter 6 of 15

Rules per request: REST, GraphQL and MCP

With a protocol set, the supervisor reads every request on the connection

A connection check answers only which binary may reach which host and port. Set protocol on an endpoint and OpenShell adds a second stage: it terminates TLS and checks each request against the endpoint's rules. rest checks the method, path and query. graphql checks the operation type, the operation name and the top-level fields. mcp checks the MCP method and the tool name. websocket checks the upgrade and each text message. json-rpc checks the method name. tcp has no request rules.

enforcement decides what a broken rule does. enforce blocks the request with an OpenShell policy_denied response. audit, the default, lets it through and logs the violation. Write a new rule in audit, read the log, then switch to enforce, because an endpoint left in audit blocks nothing. If an allowed request meets an upstream failure before its answer starts, OpenShell returns 502 Bad Gateway with Connection: close and does not retry.

For the gateway, a rest endpoint allows POST /v1/chat/completions and GET /v1/models and nothing else. In paths, * matches within one segment and ** as a whole segment matches across segments. deny_rules carve exceptions out of allows.

GraphQL hides everything behind POST /graphql, so a REST rule cannot tell a query from a mutation. A graphql endpoint on path /graphql can allow operation_type: query and only the mutation fields you name. Every top-level field must match an allow, and one bad operation denies a whole batched request. A request with an Upgrade header gets 403 on a GraphQL, MCP or JSON-RPC endpoint.

For the workspace MCP server, an mcp endpoint allows initialize, notifications/initialized, tools/list and tools/call for read_status, and denies tools/call for delete_resource. Tool arguments are not matched, so an allowed tool accepts any arguments the server accepts. Server responses are relayed without MCP parsing. Without mcp.versions only revision 2025-11-25 is allowed. The sessionless revision 2026-07-28 has to be listed, and its requests must carry MCP-Protocol-Version, Mcp-Method and Mcp-Name headers that match the body. The lesson "An agent keeps its session" covers those revisions.

Chapter 7 of 15

A key the agent never holds

The supervisor swaps a placeholder for the tenant's virtual key

Step 1 at the tenant's gateway checks the caller's key, a virtual key issued by the AI Gateway, against the provider's key service. Putting that key in the agent's environment would let a prompt-injected agent print it, write it to a file or send it anywhere it can reach. OpenShell keeps it in the supervisor.

A provider profile defines a kind of credential. It says which credentials it accepts and in which environment variables, how each is placed (auth_style: bearer in the Authorization header), which endpoints may receive it and which binaries may use it. The profile holds no secret. A provider instance stores the value, created with openshell provider create --type and --credential. A new gateway starts with an empty profile catalog, so the profile is imported first with openshell profile import.

Inside the sandbox the agent sees a placeholder, an opaque handle such as openshell:resolve:env:... in NORTHLIGHT_VIRTUAL_KEY. The supervisor resolves it just before forwarding, and only if three things are true. Network policy allows the binary and the destination. The request's host, port and path match the credential's binding, which the profile sets. And the placeholder sits where the credential is declared, here the Authorization header.

If the agent sends the placeholder to any other host, the proxy rejects it with 403 and credential_endpoint_mismatch, even when network policy allows that host. It logs the reason without the secret or the placeholder. Unknown, expired or malformed placeholders fail the same way. Resolution needs HTTP inspection, so a credential cannot ride a tls: skip endpoint or a raw tunnel. Attaching a provider is refused if a current rule lets uninspected traffic reach a credentialed endpoint, unless allow_uninspected_credentials: true marks it as intended.

A profile also contributes network rules, and the effective policy combines them with the base policy. A global policy replaces the sandbox's own and suppresses provider rules while it is active. The owner's lab chose this for its sanctioned agents: inside a sandbox there is an injected key. Outside one, a developer has to copy a key, and a copied key scoped to another principal is refused and logged at the AI Gateway.

Chapter 8 of 15

Every decision on the record

Each sandbox writes its own OCSF audit trail

OCSF, the Open Cybersecurity Schema Framework, is a shared JSON schema for security events that tools such as Amazon Security Lake read natively. OpenShell emits OCSF v1.8.0 only. The supervisor writes a record for every connection and request it decides, and each record names its sandbox under device.container, with uid and name. Records from the gateway itself carry unmapped.sandbox_id instead.

class_uid says what kind of event a record is. 4001 is Network Activity, with the shorthand prefix NET:. 4002 is HTTP Activity, for inspected requests. 2004 is a Detection Finding. 1007 is Process Activity, 3002 Authentication, 5019 a configuration state change, 6002 Application Lifecycle and 6003 API Activity. An allowed connection has action Allowed and a firewall_rule with the rule's name and type opa. A refusal always has action Denied, and on Network and HTTP Activity disposition Blocked. So jq select(.action == "Denied") counts every refusal, including malformed requests and fail-closed middleware.

With ocsf_json_enabled=true the supervisor writes full JSON to stderr on lines that start with a UTC time and the token OCSF-JSON. Collect them with kubectl -n agents logs os-supervisor-<id> -c supervisor --follow and decode everything after that token. Where /var/log is writable, the supervisor also writes /var/log/openshell-ocsf.YYYY-MM-DD.jsonl in its own filesystem, out of the workload's reach. On Kubernetes that is the supervisor Pod's emptyDir. Files rotate daily and three are kept. The console writer shares a queue of 1,024 lines and drops new lines when it is full, so enforcement never waits for logging. Ship the records before the Pod goes away.

Each inspected HTTP request gets one UUID, carried in metadata.correlation_uid and returned to the client in the x-openshell-request-id header. It is a join key, never proof of identity.

The owner's blog uses this trail as an input. A controller fed by Tetragon's eBPF events and the sandbox's audit trail can relabel a GPU worker that misbehaves, so the Endpoint Picker stops choosing it within seconds while the Pod stays up for forensics. The same controller can have BNK answer a compromised caller with 403 and add its address to the firewall.

Chapter 9 of 15

One sandbox at a time, so the tenant needs a gateway

A supervisor fences its own agent and nothing else

The owner's blog is precise about scope. OpenShell works per sandbox, at the level of one agent's process. It is not a shared egress point for many Pods or for a tenant. In the default topology every supervisor connects from its own Pod address, applies its own sandbox's policy and writes its own audit trail. The shared supervisor topology puts many sandbox instances on one supervisor process in the gateway namespace, but that shares the supervision, not a tenant's address range, routing table, firewall or budget. The openshell-sandbox-supervisors policy gives supervisors all egress, so where a supervisor's approved connection lands is up to the network after it.

A tenant needs things that no single sandbox can give. All of tenant A's traffic should leave from one source address range, so a partner can allowlist it. One routing table should carry it, so it cannot reach tenant B. One firewall should apply to every Pod in the namespace, including the ones nobody put in a sandbox. One token budget should count the requests of five sandboxes that share a key. And one record should hold everything the tenant sent. The tenant gateway provides each of these. In the owner's tier 3, BNK is the VTEP on the BGP EVPN-VXLAN fabric. Tenant A is VRF tenant-a with VNI 10001, it has its own egress and SNAT pool, and the AI Gateway runs on that same gateway. The lesson "What leaves the factory" shows how F5SPKEgress steers a namespace into that path.

The owner's lab storyline sets out to test each control alone and then together, against an agent nobody approved. It is a real agent with an ordinary task whose sequence of permitted calls exfiltrates data to an outside webhook. In the storyline that agent belongs to a different tenant from this lesson's tenant A: Cobalt Labs, in VRF tenant-c, posting to hooks.cobalt-labs.example. Identity alone fails once the developer borrows a sanctioned agent's key. Content checks in the data path catch the records in the prompt, until a clean prompt sends them. Reachability is the last line. The sandboxed agent cannot open the connection at all, because its policy lists the AI Gateway and the tenant's MCP server and nothing else. The unsandboxed agent gets its socket, and the packet is meant to die in BNK: the namespace is steered into VRF tenant-c, the firewall has no rule for the webhook, and tcpdump on the border shows nothing leaving.

So the design uses both layers. The sandbox keeps each agent's process honest. BNK owns the tenant's single way out.

Chapter 10 of 15

Agent Substrate: actors behind one egress gateway

Every byte an actor sends goes through atenet-egress

Agent Substrate runs agents as actors. An actor runs in a gVisor sandbox inside a worker Pod, and several actors can share one pre-warmed worker. The runtime can snapshot an actor and resume it later. The owner's note on agent identity points out what follows from that: the worker Pod's own identity says nothing about which actor is running in it, so each actor needs an identity of its own.

Substrate gives it one. ateapi mints each actor a certificate from the actor-identity certificate authority, with an ActorIdentity X.509 extension that names the actor's atespace, its name and its UID. An atespace is Substrate's group of actors, close to a namespace.

Inside the worker, nftables redirects the actor's outbound TCP into atunnel. atunnel carries it to the egress gateway over mutual TLS with the actor's own certificate and a bare HTTP CONNECT. The actor believes it is dialling its destination directly and has no say in what identity the gateway sees. The gateway is the atenet-egress Deployment in the ate-system namespace. ate-api-server is started with --default-egress-gateway-address=atenet-egress.ate-system.svc:443, which turns tunnelled egress on for the whole cluster.

The gateway refuses any client certificate that the actor-identity CA did not sign. It reads the UID from the certificate and checks with ateapi that it is a real actor in the RUNNING state. A certificate does not survive its actor being deleted and recreated under the same name. Then it checks the request against the actor's EgressPolicy. The gateway denies by default. Rules are read in order and the first match wins. An actor with no policy gets no tunnel. A missing policy is cached as a deny for 10 seconds (--egress-policy-cache-ttl), so a fetch tried just before the policy exists keeps failing for up to that long.

The gateway's data plane is chosen at install. Envoy is the default, with a co-located atenet ext_proc container deciding identity. --atenet-dataplane=agentgateway uses agentgateway's built-in substrateEgress policy instead. On the scene, the worker Pod is the one at 10.244.1.12 on gpu-node-1 and atenet-egress is the Pod at 10.244.2.17 on gpu-node-2.

Chapter 11 of 15

atenet-egress puts a signed token on the request

An actorJwt entry replaces a header with a JWT that names the actor

To send a credential, atenet-egress has to read the request. It can do that for cleartext HTTP that an http rule allows, and for HTTPS that an https rule allows. An https rule makes the gateway terminate the actor's TLS for the names it lists and re-originate TLS to the destination. The actor trusts the gateway's certificate authority through a projected trust bundle. Those rules list hostnames, and that is why the owner's post says to point the sandbox at the tenant's AI Gateway by FQDN for Substrate. Substrate's current source has no egress rule for an IP range. One appears only in a design document.

The rule's effects carry replaceHeaders. Each entry names a header and a prefix, and sets exactly one of credentialUri or actorJwt. credentialUri fetches a stored secret from a credential provider, with a URI of the form ate-secret://<provider-class>/<path>. actorJwt asks ateapi to mint a JWT for the actor making the request. It needs no credential provider at all.

The header is replaced only if the actor sends it. A request without the header is forwarded unchanged and gets no token. So the agent opts in by sending Authorization with any placeholder value, which the gateway throws away. The agent never sees the token and cannot choose the value that leaves the cluster.

audiences becomes the token's aud claim: 1 to 16 values of up to 512 characters, set to what the receiver checks. expirationSeconds is the lifetime, from 300 to 3600 seconds, with no default. This lesson uses 900. The gateway reuses a token for the same actor, audiences and lifetime until a third of its lifetime is left. With 900 seconds, it mints a new one 600 seconds after the last, and the receiver always gets at least 300 seconds. Concurrent requests that need the same token share one mint.

Failures fail closed. If the actor no longer exists, 403. If ateapi is unreachable or times out, 503, which a client may retry. Any other mint failure gives 500 on the Envoy data plane and 403 on agentgateway.

Chapter 12 of 15

BNK checks the actor's JWT

The tenant's AI Gateway trusts Substrate's issuer and nothing else

The owner's post says it plainly: with Substrate, atenet-egress injects the actor JWT, and since the AI Gateway validates JWTs from your issuer, that JWT is checked at BNK. The lesson "An agent keeps its session" explains JWT access tokens in general. This chapter is about the actor token in particular.

Substrate's documentation lists what a relying party checks. iss must equal the trusted issuer, https://idp.ate-system.svc by default, which is https://idp.<namespace>.svc for the system namespace. The issuer's discovery document sits at /.well-known/openid-configuration and names jwks_uri, https://idp.ate-system.svc/openid/v1/jwks. The key whose kid matches the token header verifies the signature with its alg. aud must contain the expected audience, here https://api.northlight.example. exp and nbf must hold. sub must start with actor/. The same keys sign worker-for-actor tokens, used by a worker acting for an actor, and a receiver that wants the actor itself must reject them.

F5's own sources disagree on discovery. The BNK 2.4.0 release notes list OIDC and JWT validation as new, and the notes on the NVIDIA deck say OIDC discovery and JWT validation are available now, but slide 20 of the BNK 2.4 PM deck marks OIDC Discovery as future. Until that is settled for your release, give the validator the issuer, the audience, the JWKS URI and the allowed algorithm directly, which works whether or not discovery does. The installer creates one ES256 key. Set actorJWT.algorithm to RS256 for a 4096-bit RSA key if a receiver cannot handle ES256.

The validator also has to reach the keys. ate-idp-server sits behind the idp Service on port 443 with a certificate from Substrate's servicedns signer, which only verifiers inside the cluster trust by default. A receiver outside the cluster needs the issuer published through an Ingress with a publicly trusted certificate on a host you own, and the issuer set to that host. ate-idp-server rereads the key pool at most once a minute. On an unknown kid, refetch the key set, at a limited rate.

Two limits matter at the gateway. There is no revocation: a token stays valid until exp, at most an hour, even after its actor is deleted. And the subject names the actor and stays the same when the actor is recreated. To tell a recreated actor apart, compare actorUID in actor.ate.dev. Even that is not exact right after a recreation: Substrate's documentation (issue 2208) warns that the gateway caches tokens by actor name, so for up to two thirds of a token's lifetime it can inject a token whose actorUID still names the old actor.

Chapter 13 of 15

After the check, the path is the tenant's

Seven decisions in one engine, then a GPU that already holds the prefix

From the gateway on, the owner's post lists seven decisions for each request at one address, and all of them run in TMM, the traffic engine BNK takes from BIG-IP. Step 0 is the F5 network firewall, which checks source and port before any HTTP is parsed. Step 1 is the identity check: the virtual key against the key service for an OpenShell agent, or the actor JWT for a Substrate actor. Step 2 sends the prompt to F5 AI Guardrails. Step 3 is the token budget per user, which can move an over-budget caller to a cheaper model or answer 429. Step 4 is model choice, including an off-peak model on a schedule or a frontier model from another provider behind the same address. Step 5 asks the F5 Endpoint Picker which GPU should answer. Step 6 counts tokens from the model's own answer, per user.

Steps 0 to 3 can stop the request, and anything they stop never reaches a GPU. A sandboxed agent that sends a harmful prompt or has spent its budget costs the provider no GPU time. Steps 1 to 6 are one policy iRule per endpoint, which makes sideband calls to the key service, F5 AI Guardrails and the usage store, and asks the picker over gRPC ext_proc. The picker's InferencePool uses failureMode: FailClose, so if the picker is down the request fails instead of falling back to round robin.

The picker sends this request to gpu-node-1. Pod qwen3-6f7d9c8b4-x7k2p at 10.244.1.21:8000 already holds the agent's system prompt and tool descriptions in its KV cache from the previous turn, so it skips the prefill for that prefix. The FP8 build's 34.3 GB of weights leave the rest of the H100's 80 GB for that cache. The answer streams back, and BNK counts its tokens from the usage the model reports, so the bill matches what the agent's SDK saw.

None of this is in the sandbox. The sandbox decided that the agent may call this address with this method and path. The tenant gateway decided everything that happened after.

Chapter 14 of 15

One slice, two layouts

Levan splits egress and model concerns across components, BNK runs them in one engine

Levan's post walks one path through the tenant tier: a sandboxed agent calling a hosted model. In Agent Substrate all of an actor's outbound traffic goes through atenet-egress. For model concerns his layout adds a dedicated agentgateway instance as the LLM gateway. The chain is actor, then atunnel, then atenet-egress, which applies policy and injects the actor JWT, then the agentgateway LLM gateway, then OpenAI or Anthropic. The owner's post describes agentgateway in that role as doing model routing and failover, budgets, rate limits and prompt guarding, and implementing the endpoint picker protocol too. Substrate can also use agentgateway as the egress gateway itself, with --atenet-dataplane=agentgateway.

The owner's post calls the split between egress and model concerns the layout his article chose. On BNK the same slice runs through one engine inside the tiers. The sandbox, Substrate or OpenShell, still isolates the process and still decides which destinations it may reach. Its one allowed model destination is the tenant's AI Gateway. From there the tenant's VRF, SNAT range and gateway are BNK's, and the same TMM runs the firewall, the identity check, the guardrail callout, the budget, the model choice, the picker call and metering. A hosted model is one more choice at step 4. The AI Gateway reaches it on the tenant's behalf, so the provider's real key stays in the gateway and never in a sandbox.

The owner's lab made one more decision for the same reason. The lab is a smaller setup than this lesson's cluster, and its agent's model is not Qwen3-32B but a small model on CPU, reached through the AI Gateway, because a provider key would put a real key in a sandbox.

The post closes with where the owner would take the platform. Agent identity and per-task authorization belong in policy, with a declarative layer next to iRules: CEL evaluated over an ext_authz callout. Egress should follow the task, open only to what the task may reach and closed when it is done. Every decision should land in a signed record per tenant. And a quarantine should come with a provable stop, so an operator can show a workload sent nothing after it was stopped.

Chapter 15 of 15

What an operator sees when it fails

Most failures are refusals by design, and each one says where it happened

When something does not work, the first question is which layer refused, and each layer answers in its own words.

At the OpenShell supervisor, a connection no rule allows shows up in curl as error 56, Received HTTP code 403 from proxy after CONNECT, and in the sandbox log as NET:OPEN DENIED with the binary's real path and reason network connections not allowed by policy. If the binary named in the log is /usr/bin/python3.12 and the rule lists /usr/bin/python3, fix the rule. A request an enforced rule blocks gets a policy_denied response. A key sent to a host outside its binding gets 403 credential_endpoint_mismatch. A connection that worked yesterday and fails today after an image update may be the binary hash check. When a rule seems to have no effect at all, check that its endpoint is not still in audit.

At the network layer, the dangerous failure is the quiet one: a sandbox that reaches the network directly because the CNI does not enforce egress policy, or because another policy in the namespace allows egress. Neither leaves an OCSF record, so test for it.

At atenet-egress, an actor with no EgressPolicy gets no tunnel, and the deny stays cached for 10 seconds after the policy appears. A request without the Authorization header goes out with no token, and BNK then answers 401. A deleted actor gets 403, an unreachable ateapi 503. After an actor is recreated under the same name, the gateway can keep injecting a token with the old actorUID for up to two thirds of the token's lifetime, 600 seconds at 900, because it caches tokens by actor name.

At BNK, a JWT with the wrong aud, an expired exp, an unknown kid or a worker-for-actor subject is refused at step 1. If every token fails, check that BNK can reach and trust https://idp.ate-system.svc/openid/v1/jwks. After a key rotation, a validator that never refetches the key set fails every token signed by the new key. Rotation is three steps with kubectl ate admin: add-jwt-key, then activate-jwt-key once relying parties have the new key set, then remove-jwt-key once every old token has expired.

What to keep

Two layers on one path

A sandbox and a tenant gateway answer different questions. OpenShell answers what one agent's process may do: by default it runs a supervisor Pod per sandbox, paired by openshell.ai/boundary-pair, fences the workload with NetworkPolicy that the CNI must enforce, checks each HTTP, GraphQL and MCP request with OPA, puts a credential only where its profile allows and writes every decision to its own OCSF trail. Agent Substrate answers the same question for actors, and its atenet-egress adds an identity: a short-lived JWT that names the actor, which the tenant's AI Gateway validates against Substrate's published keys. Neither one is a shared way out for a tenant. That is BNK's job in tier 3: one VRF, one SNAT pool, one firewall, one set of keys and budgets, and then the seven decisions that end at the GPU already holding the agent's prefix. Point the sandbox at the gateway by name, and the slice comes with the platform.
