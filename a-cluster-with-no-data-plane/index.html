BNK and gateways

A cluster with no data plane

The traps of installing BNK: a licence that gates TMM, trial keys, install order, and versions that do not exist

BIG-IP Next for Kubernetes (BNK) is installed in layers. A few open source pieces come first: Multus, cert-manager and a certificate authority. Then F5's Lifecycle Operator (FLO), a Kubernetes operator that reads one resource, the CNEInstance, and builds everything else from it: the shared CNE core with its licensing controller, and the instance with its controller and the Traffic Management Microkernel (TMM), the data plane that carries traffic. Last comes the licence. Each layer depends on the one before, and several of those dependencies fail without a useful message.

The worst case looks like success. Every control plane Pod is Running, nothing restarts, no event names the licence, and the gateway address 203.0.113.80 answers nothing. The two vLLM Pods qwen3-6f7d9c8b4-x7k2p and qwen3-6f7d9c8b4-m9q4t are healthy, each holding the 34.3 GB of the Qwen3-32B-FP8 build on its H100, and no request can reach them through BNK, because no TMM Pod exists. This lesson follows a host-mode install on the cluster northlight-eu step by step, shows the licence that brings the data plane into being, the trial licences and the certificate inside older builds that expired on 2026-10-11, and the install traps the owner hit in labs on 2.2 to 2.4.2. Each trap comes with its symptom, its cause and the check that finds it.

Chapter 1 of 13

What an install puts in the cluster, layer by layer

Prerequisites, the operator, the CNE core, the instance, then the licence

F5's install guide for BNK on hosts with FLO runs in a fixed order, and the owner's installers number the same steps as phases 00 to 70. Phase 00 is preflight: tools, the API server, the Kubernetes version, the CNI, a StorageClass, hugepages and the CPU floor. Phase 05 labels the nodes that may run TMM with app=f5-tmm. Phase 10 installs Multus, cert-manager and a three object certificate authority chain. Phase 20 logs in to F5's registry repo.f5.com with the service account key cne_pull_64.json and creates the pull secret far-pull-secret. Phase 30 installs FLO with Helm into the namespace f5-cne-core. Phase 40 creates the CWC and OpenTelemetry certificates. Phase 50 applies the CNEInstance. Phase 60 applies the licence, and phase 70 verifies.

The CNEInstance is the one resource FLO acts on. F5's page says that before FLO installs an instance it installs the CNE core and the custom resource definitions (CRDs) if they are missing. The core lands in f5-cne-core: f5-spk-cwc, the Cluster-Wide Controller that handles licensing and usage reports, three f5-dssm-db and three f5-dssm-sentinel Pods for session state, f5-rabbit for messages between controllers, the observers, Fluentd, an OpenTelemetry collector and a crd-installer job. The instance lands in its own namespace, f5-bnk-instance in this lesson: the Deployment f5-cne-controller, which turns F5 and Gateway API resources into TMM configuration, f5-afm for the firewall, f5-downloader, and f5-tmm.

TMM is what this site's other BNK lessons draw as the border of the AI factory. It holds the address 203.0.113.80, takes requests for api.northlight.example and forwards them to the vLLM Pods on port 8000. Everything else in the list exists to configure, license, observe or store state for it. That is why an install that stops short of TMM is useless, however green the rest looks.

Chapter 2 of 13

The licence is a resource of its own

From 2.3 a License object in f5-cne-core replaces the operator's Helm values

A BNK licence key is a JSON Web Token (JWT), a signed string of three base64url parts separated by dots: a header, a payload of claims and a signature. It comes from MyF5, under My Products & Plans, Subscriptions, as a file such as SFA-1515255-F5-subscription-2.jwt in F5's example. Alongside it comes the registry key cne_pull_64.json. The two are separate. The registry key only lets images be pulled. The JWT decides whether the cluster may process traffic.

Before 2.3 the JWT went into FLO's Helm values. F5's UDF lab blueprint, which the owner studied, shows that older path: it installs FLO v2.9.27-0.2.10 into the namespace f5-operators, sets license.operationMode to connected and license.jwt to the token in the FLO values, and checks the result by searching the log of deployment/f5-spk-cwc in f5-operators for ResponseCM20LicenseVerified. From 2.3 that path no longer licenses the cluster. The licence is its own resource: apiVersion k8s.f5net.com/v1, kind License, name f5-cne-cluster-license, applied in f5-cne-core. Its spec has two fields in F5's example, operationMode, connected or disconnected, and jwt, the token in quotation marks. The owner's notes found the same rule in F5's Forge tooling for 2.3.1, where the FLO values alone stopped licensing the cluster.

The CWC reads the object. Inside it a module called CPCL, Common Product Component and Libraries, activates the licence and later builds the monthly usage reports. In connected mode the CWC reaches F5's licensing service over the internet by itself. kubectl get license.k8s.f5net.com shows a STATE column: PendingVerification while the cluster is not yet licensed, then Active. The owner's tooling also waits on a status condition named LicenseActive. F5's guide says to watch until STATE is Active and to contact support if it never gets there.

Chapter 3 of 13

No active licence, no TMM

The controller skips its resource controllers and the gateway never appears

The f5-cne-controller asks the CWC over RabbitMQ whether the cluster is licensed. When the answer is no, the owner's labs on 2.3 and 2.4 saw one line in the controller's log: License is not enabled.. skip Resource controllers. The resource controllers are the loops that turn F5SPKVlan, Gateway, HTTPRoute and the other F5 resources into TMM configuration, and with them skipped no TMM is ever created. Everything else keeps running. The dSSM Pods, RabbitMQ, the CWC, the observers and the controller itself all report Running. Nothing crashes, nothing restarts, and no event names the licence.

For the cluster northlight-eu that means the gateway place on the scene stays empty. A caller at 198.51.100.7 sends a request to 203.0.113.80 on port 443 and gets no answer, because no process holds that address. Behind it the two qwen3 Pods are Ready. Each has loaded the 34.3 GB FP8 build in about three minutes and is listening on port 8000. kubectl port-forward to either Pod gets a reply. The model is fine and the GPUs are idle. Only the path through BNK is missing.

The owner's training lab turns this into the install order. It installs BNK unlicensed on purpose, shows the learner the full control plane with no TMM, then applies the licence. Within a short time the controller starts its resource controllers and the f5-tmm Pods appear on the nodes labelled app=f5-tmm. The DaemonSet that runs them is built by FLO, which is why the panic in the chapter on the node label comes from FLO's code. The licence is what brings the data plane into being. The owner's installer treats an unlicensed install as an expected state in its verification and reports it as such, so nobody reads it as a fault.

Chapter 4 of 13

An expired key looks like a healthy install

The token is checked when the licence is applied, after the install has finished

Nothing in phases 00 to 50 reads the licence. FLO pulls images, creates the core and the instance, and every component reports healthy. The JWT is validated against F5 only when the License object is applied and the CWC tries to activate it. An expired or wrong token therefore produces the state of the previous chapter, a full control plane and no TMM, after half an hour of installing, and the cause is a file that was out of date before the install began.

The owner's installer moves the question to the front. Its preflight, phase 00, resolves the licence question before anything else runs, and its README tells the platform team to check that the licence is current before planning any work around it. Outside lab environments it refuses the --skip-license flag, so nobody ships an unlicensed demo by accident.

Checking a token needs no tool from F5. The payload is the middle part of the JWT, base64url encoded JSON. RFC 7519 defines two time claims used here: iat, the time the token was issued, and exp, the time after which it must not be accepted, both as seconds since 1970-01-01 UTC. A worked example: a payload with exp 1793404800 decodes to 2026-10-31 00:00 UTC. Applied on 2026-11-26, which is 1795651200, the token is 2,246,400 seconds past its end, exactly 26 days. Decoding the payload only reads it. It proves nothing about the signature, which only F5 can check, but it catches the commonest mistake in a minute.

Chapter 5 of 13

Trial licences and a certificate that expired on 2026-10-11

TST keys work on 2.4.1 and newer, and a cluster takes only one

F5 also issues trial licences. Their order type is TST, and inside the JWT f5_order_type is eval. A trial token has no exp claim. Its end is the claim f5_sat, again in seconds since 1970. iat is when it was issued, and sub names the F5 account that issued it. Trial periods are fixed choices: 1 week, 1 month, 3 months, 6 months or 1 year.

A worked example: a 1 month trial issued with iat 1793577600, 2026-11-02 00:00 UTC, has f5_sat 1796169600, 2026-12-02 00:00 UTC. The difference is 2,592,000 seconds, which is 30 days. Anyone checking a trial for expiry with a tool that only reads exp finds nothing and may wrongly conclude the token never expires.

Trials only work on BNK 2.4.1 or newer. BNK 2.4.0 and every earlier release carry a built-in test certificate that is used when a trial is verified, and that certificate expired on 2026-10-11. From that day those releases refuse every trial with an error that begins x509: certificate has expired. That prefix is the start of the message Go's crypto/x509 package returns, x509: certificate has expired or is not yet valid: followed by the times. The fault is in the cluster, so issuing another trial does not help. The cluster has to be upgraded.

A cluster that already holds a trial also refuses a second one. F5's troubleshooting table lists the same rule as License switch rejected, with the cause Cannot switch eval to eval. When a trial runs out on a lab cluster, the way to a new trial is a fresh install. Plan lab clusters so that the trial outlives the work, and pick the period with that in mind.

Chapter 6 of 13

Licensing a cluster that cannot reach F5

Disconnected mode carries a report out and a manifest back by hand

In disconnected mode the CWC never talks to F5. The License object is applied with operationMode disconnected and stays in PendingVerification until a person completes the exchange. F5's guide does it over the CWC's own API. A port-forward to service/f5-spk-cwc on 38081 opens a tunnel from the engineer's machine. Every call uses mutual TLS with three files extracted earlier from the secret cwc-license-client-certs: f5-cwc-api-client.key, f5-cwc-api-client.crt and f5-cwc-api-root.crt, plus a bearer token read from the secret cwc-auth-token.

Three calls follow. GET /status returns JSON from which jq reads .InitialRegistrationStatus.LicenseDetails.DigitalAssetID, the cluster's identity. GET /report returns the configuration report. On a machine with internet access, the report is posted to https://product.apis.f5.com/ee/v1/entitlements/telemetry with the headers F5-DigitalAssetId, User-Agent: SPK and Authorization: Bearer with the JWT. F5 answers with license-manifest.json. In the owner's offline procedure for BlueField-3 that file was about 16 KB. Back inside, POST /receipt sends the manifest field of that file to the CWC. F5's guide warns that this call only succeeds the first time, and anything other than HTTP 200 means calling support.

Then the state moves to Active. The owner's procedure adds one step: if the TMM Pods do not reach their two readiness gates, restart the TMM DaemonSet with kubectl rollout restart and wait for its rollout. The lesson A cloud with no way out places this receipt exchange among the other ways a closed site gets its licences.

Chapter 7 of 13

Multus has to exist before the operator starts

A missing CRD makes FLO crash-loop even when nothing uses an attachment

Multus is a CNI plugin that lets a Pod have more than one network interface. Its extra interfaces are described by NetworkAttachmentDefinition objects, and the type is a CRD named network-attachment-definitions.k8s.cni.cncf.io. Installing Multus installs that CRD. A host install that gives TMM no extra interfaces does not need any NetworkAttachmentDefinition object at all. FLO still needs the CRD to exist.

The reason is how operators built on the controller-runtime library start. Each controller watches a list of kinds, and for each kind it asks the API server for an informer, a cached watch. If the API server does not serve that kind, the library logs if kind is a CRD, it should be installed before calling Start, with the missing group and kind, and tries again every 10 seconds. After the cache sync timeout, 2 minutes by default, the controller gives up, the operator process exits, and Kubernetes restarts it. The Pod cycles through CrashLoopBackOff with growing back-off delays. The message is the library's, and FLO's logs show it in exactly this situation, which is how the owner tied the crash loop to the CRD.

The order matters even after the fact. Installing Multus later creates the CRD, but a FLO Pod sitting in back-off may wait minutes before its next try. The owner's installer installs Multus in phase 10, installs FLO in phase 30, and in phase 30 restarts FLO if it finds it looping. The same preflight in phase 00 that resolves the licence also checks for the CRD, so both are known before the cluster is changed.

Chapter 8 of 13

Multus runs out of memory once BNK arrives

Pods stay in ContainerCreating because the network plugin itself was killed

Multus in its thick form runs as a daemon on every node, the kube-multus-ds DaemonSet in kube-system. When kubelet creates a Pod, the container runtime calls the CNI plugins to give the Pod its network. The small multus-shim binary on the node passes that call to the Multus daemon, and the daemon calls the real plugin, Calico here. Every Pod on the node goes through it, including the qwen3 Pods.

The upstream manifest for the thick daemon sets a memory request and limit of 50Mi. A BNK install creates a large number of Pods at once, and the owner found that this exhausts Multus at its default limit. A container that passes its memory limit is killed by the kernel and shown as OOMKilled. While the daemon is down, no new Pod on that node gets a network, and kubelet reports the sandbox could not be created. The Pods stay in ContainerCreating, and from the outside it looks like BNK is slow.

F5's troubleshooting page shows the state: one kube-multus-ds Pod at 0/1 OOMKilled with 8 restarts among others that are Running, and the fix as a patch to the DaemonSet raising the memory request and limit to 256Mi. If the Pod still fails, F5 removes /opt/cni/bin/multus-shim on that node and deletes the failing Multus Pod so it reinstalls the shim. The owner's installer raises the limit to 512Mi in phase 10, before BNK arrives. That is 512 ÷ 50, about ten times the upstream value, and twice F5's figure. For a GPU node that also restarts model server Pods, the margin is cheap. A Multus outage on gpu-node-1 also blocks a new qwen3 Pod from starting there.

Chapter 9 of 13

Certificates: a CA with its own name, and make on the machine

Two traps that leave the licensing component unable to talk

BNK's components talk to each other over TLS with certificates signed by a cluster issuer from cert-manager. F5's guide builds the chain in three objects. A ClusterIssuer named selfsigned-cluster-issuer signs one CA Certificate, isCA true, commonName f5-cne-internal-signing-cert, stored in the secret f5-cne-internal-signing-cert. A second ClusterIssuer, f5-cne-internal-ca, uses that secret to sign everything else. The leaf certificates have other names: the two OpenTelemetry certificates use commonName otel.cluster.local, and the CWC's server certificate is made for f5-spk-cwc.f5-cne-core.svc.cluster.local.

The owner's first trap came from a home-made chain where the CA's CommonName equalled a leaf's. The licensing component then crash-looped on an x509 error that did not explain why. A verifier finds a certificate's issuer by its name. When a leaf carries the same name as its CA, the subject and issuer of the leaf look identical and the leaf can be taken for a self-signed certificate, so the chain does not build. Using F5's own names avoids it, and the owner's installer asserts after phase 10 that the issuer really is a CA.

The second trap is in phase 40. F5's chart f5-cert-gen contains cert-gen/gen_cert.sh, run as sh cert-gen/gen_cert.sh -s=api-server -a=f5-spk-cwc.f5-cne-core.svc.cluster.local -n=1. It writes cwc-license-certs.yaml and cwc-license-client-certs.yaml. F5's list of tools for the installing machine includes make. Without it, the script still wrote the two files, with empty certificate data, and kubectl create accepted them because a Secret with empty values is valid. The CWC then has nothing to serve TLS with, the licence API on 38081 cannot work, and the cluster can never be licensed. The owner's installer now refuses empty certificates.

Chapter 10 of 13

Where TMM may run: the node label and hugepages

No label means no TMM, and on some builds a panic that names neither

TMM runs only on nodes labelled app=f5-tmm. F5's page is plain about the daemon-set mode, where BNK runs one TMM per node: if no node carries the label, Kubernetes schedules no TMM Pod. For northlight-eu the command is kubectl label node gpu-node-1 app=f5-tmm and the same for gpu-node-2, then kubectl get nodes -l app=f5-tmm to confirm.

The owner's labs saw something worse than an empty DaemonSet. With no labelled node, FLO panicked with assignment to entry in nil map at f5tmm_daemonset.go:186. That text is Go's runtime error for writing into a map that was never created. The error names neither TMM nor the label. controller-runtime recovers panics inside a reconcile by default, turns them into an error ending in [recovered], counts them in the metric controller_runtime_reconcile_panics_total, and requeues the object. So the operator does not even restart. It panics, recovers, requeues and repeats, while every other component reports healthy.

A labelled node still needs hugepages. TMM uses DPDK, which keeps packet buffers in 2 MiB pages, and without allocatable hugepages-2Mi the TMM Pod is never scheduled. The owner's labs gave 4 to 6 GiB. sysctl -w vm.nr_hugepages=2048 reserves 2048 × 2 MiB = 4096 MiB, 4 GiB, and a file in /etc/sysctl.d keeps it across reboots. A running kubelet does not notice the new pages until it restarts, so restart it and check kubectl get node gpu-node-1 -o jsonpath='{.status.allocatable.hugepages-2Mi}'.

One build added its own trap. The 2.3.0 lifecycle operator panicked while building the TMM DaemonSet when two nodes carried the label. The owner's installer refuses a second TMM node unless BNK_TMM_ALLOW_MULTI=true is set. Two TMMs worked on 2.4.1 and 2.4.2, and the owner's 2.4.2 lab had to set that variable to get them, because the guard does not check the version. The picture is not fully clean on 2.4.x either: a containerlab run on a kind cluster still saw a panic loop with a second TMM node on 2.4.x, and its cause was never resolved.

Chapter 11 of 13

A webhook and a CRD that must exist first

Some objects can only be applied once the controller is up

BNK checks its own resources with a validating admission webhook named f5validate.f5net.com. A validating webhook is a call the API server makes to a service before it stores an object. The service lives in the CNE controller. Right after the CNEInstance is applied, that service has no ready endpoint yet. An F5SPKVlan applied in that window, the object that gives TMM a VLAN and self IP addresses, cannot be validated. A webhook's failurePolicy decides what happens when the call cannot be made: Fail refuses the object with a message that the API server failed calling the webhook, Ignore stores it unchecked. F5 does not document the policy of f5validate.f5net.com, and the owner's labs had to wait for the controller before VLANs would apply, so read the live value with kubectl get validatingwebhookconfigurations -o yaml. The fix is order: wait until the f5-cne-controller Pod is Ready, then apply VLANs. The owner's host installer applies its network phase 55 with retries for exactly this reason.

A related trap ties the gateway to the GPUs. A CNEInstance may name eppNamespaces, the namespaces where BNK's endpoint picker serves inference pools. Then f5-cne-controller watches InferencePool objects, a kind from the Gateway API Inference Extension that BNK does not install. If that CRD is missing, the controller exits at boot. Install the Inference Extension CRDs before setting eppNamespaces. The lesson Wiring a pool to its picker shows what the picker does once it runs.

One more object stays behind in one namespace. The image pull secret far-pull-secret is created only where the installer puts it. A picker in the namespace inference, next to the qwen3 Pods, pulls from repo.f5.com as well and needs its own copy, or its Pod sits in ImagePullBackOff.

Chapter 12 of 13

A manifest version that does not exist is accepted

Versions come from the release manifest, and the operator does not check them

Every BNK release has a release manifest, a YAML bill of materials that names each Helm chart and image with its version. It is packaged as a chart, f5-bigip-k8s-manifest, pulled with helm pull oci://repo.f5.com/release/f5-bigip-k8s-manifest --version followed by the release-manifest version. For 2.3 F5 lists four: 2.3.0-3.2598.3-0.0.170, 2.3.1-3.2598.3-0.0.304, 2.3.2-3.2598.3-0.0.392 and 2.3.3-3.2598.3-0.0.509. The owner's notes add 2.2.0-3.2226.0-0.0.385, 2.2.1-3.2226.0-0.0.511 and 2.4.0-3.3175.0-0.0.380 with 86 components.

Component versions are not published as a table. F5 gives a script, get-cne-chart-version.sh, that uses yq to read one chart's version out of the manifest. The owner's installers resolve them once and pin them in versions.env: for 2.3.0, f5-lifecycle-operator v2.21.13-0.0.28 and f5-cert-gen 0.9.3. For 2.4.0 FLO is v2.30.0-0.5.2, for 2.4.2 v2.30.0-0.11.4. Unpinned installs read the manifest at install time, so two runs a month apart can differ.

The trap is in the CNEInstance field spec.manifestVersion. FLO's reference says its CRD Installer job validates the manifest version. In the owner's upgrade tests an unresolvable value was accepted without complaint. It was recorded, Available stayed True, nothing degraded, and the upgrade appeared to succeed while changing nothing, because no component had new charts to pull. The guard is outside FLO: resolve the version against the registry first, which fails at once if the chart version does not exist.

Upgrades carry two more traps. Going from 2.2.1 to 2.3.0 converts cpcl-config-cm and cpcl-key-cm from ConfigMaps to Secrets, because the new CWC needs Secrets. That is one way, so rolling the operator back afterwards leaves components looking for objects that no longer exist. And Helm can race cert-manager over external-otelsvr-secret, rendered by the chart and rotated with rotationPolicy Always, failing with no Secret with the name … found. A retry succeeds.

Chapter 13 of 13

Proving the data plane exists

A check that ends at a model answer, and what the install costs

Verification should end where traffic ends. The owner's installers finish with assertions that go past Running Pods: the licence Active, the CNEInstance Available, TMM present and configured, then an answer through the gateway. For northlight-eu that is five checks in order. kubectl get license.k8s.f5net.com -n f5-cne-core shows Active. kubectl get cneinstance shows Available True. kubectl get pods -l app=f5-tmm -A shows one Pod per labelled node, two here. The controller log no longer carries the not-licensed line. And a request to https://api.northlight.example at 203.0.113.80 returns a completion from Qwen3-32B served by qwen3-6f7d9c8b4-x7k2p or qwen3-6f7d9c8b4-m9q4t.

The install also has a size to plan for. On 2.4.0 at deploymentSize Small the owner measured about 20 vCPU of requests in the f5-* namespaces, 19,958 millicores, plus 950 millicores for Kubernetes, Calico and Multus. The largest single Pod is f5-tmm at 4,600 millicores, its main container and five sidecars, with 8 GiB of memory and 4 Gi of hugepages. Actual use was 0.45 vCPU and 2.5 GiB. Kubernetes schedules on requests, so the reservation is what must fit. The requests cannot be lowered much: Small is the floor, advanced.tmm.resources covers only the main container, and the operator reverts patches to the Deployments it generates within a minute. On OpenShift, 8 vCPU and 24 GB workers left dSSM and CSRC Pending, and 12 vCPU and 28 GB worked.

Time counts too. A cold install pulled 81 images from repo.f5.com. In the owner's training lab it took 29 minutes to a full control plane, 5 of them up to the CNEInstance and the remaining 24 spent pulling the release manifest and what it names. With the images already in the cache, those 24 minutes are what pre-pulling removes. A trap found at minute 29 costs the whole run, which is why every check in this lesson belongs in preflight.

What to keep

Install the prerequisites in order, check the licence first

A BNK install is a chain: Multus and its CRD, cert-manager and a CA with its own name, the registry key, FLO pinned from the release manifest, certificates generated with make on the machine, the CNEInstance, the webhook and CRDs its objects need, labelled nodes with hugepages, and a licence that is current and of a kind the build accepts. Most links fail quietly. The licence fails most quietly of all, because without it the controller skips the work that creates TMM and leaves a cluster with a perfect control plane and no data plane. The defence is to move every check forward: read the JWT's exp or f5_sat before starting, confirm a trial against the build, verify the manifest version against the registry, and end verification with a model answer through the gateway.
