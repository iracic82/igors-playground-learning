Inference

How the picker hears about the cache

KV cache events from the model server to the endpoint picker, over ZeroMQ or NATS

A picker that sends each prompt to the GPU already holding its opening needs a map of what every worker has in memory. That map changes every second, as workers store new blocks and push old ones out. This lesson follows the news of one such change from the inside of a vLLM worker to the endpoint picker.

It covers what the worker says and how it hashes each block, the ZeroMQ sockets that carry the news, why a quiet socket proves nothing, how a lost message is noticed and repaired, what happens when one Pod runs two engines, and what the picker builds from the stream. Then it does the same for NATS, the broker NVIDIA Dynamo can use, and its limits.

The last chapters cover the F5EPP resource that selects the transport, why the cache map is only one score among several, the faults that leave the map empty, model servers outside the cluster, and the commands an operator runs to check each link by hand.

Chapter 1 of 17

Guessing, or being told

A picker can remember where it sent a prefix, or the worker can report what it holds

The lesson Which GPU answers soonest showed why the picker wants a map from prompt openings to workers. A worker that already holds the KV cache for the first 2,048 tokens of a prompt can skip reading them again. The time to the first token then depends on the 52 new tokens, and the GPU is free sooner for the next request. To use that, the picker has to know which worker holds which opening. There are two ways to fill the map.

The first is to remember. Each time the picker sends a prompt to a worker, it records that the worker now holds that prompt's blocks. F5 calls this speculative cache tracking. It needs nothing from the workers and works with any model server that speaks HTTP. It is a guess. A worker with full memory hands its oldest unused blocks to new requests, and a worker that restarts comes back empty. Neither tells the picker, so its record stays as it was until it ages out. F5's prefix cache scorer has its own time-to-live parameters for that, set through spec.eppConfig.

The second way is for the worker to report every block it stores and every block it drops. That is precise tracking. It costs a stream of messages from every worker and a little memory in the picker, and it removes the guess. The rest of this lesson is about how those reports are made, how they travel, and what breaks them.

Chapter 2 of 17

What a worker says when its cache changes

Three event types, collected into one batch per scheduler step

vLLM can publish an event whenever prefix caching changes which blocks it holds. The option is --kv-events-config, a JSON object, and events are off by default. Setting enable_kv_cache_events to true is enough to turn them on. When publisher is left out it becomes "zmq", and the other fields keep their defaults.

There are three event types. BlockStored says that full blocks were hashed and added to the cache. It carries their hashes, the hash of the block before them, the token ids they cover and the block size. BlockRemoved says that a cached block was taken for another request and names its hash. AllBlocksCleared says the whole prefix cache was reset. Each event is encoded as a map with a "type" key naming the event. Fields that hold their default value, such as an empty session_id or lookahead_token_ids, are left out of the message to save bytes.

The block pool queues events as they happen. At the end of a scheduler step, the scheduler takes the queue and wraps it in a KVEventBatch with a timestamp. A step with no events produces no batch, so an idle worker sends nothing at all. The batch goes into a queue that holds up to max_queue_size batches, 100,000 by default. If that queue is ever full, the call that hands over the batch waits for room.

A publisher thread takes batches from that queue. It encodes each one with msgpack, a compact binary form of JSON-like data, and gives it a sequence number that starts at 0 and rises by one per batch.

Chapter 3 of 17

ZeroMQ: a publishing socket and no broker

The worker binds a port and each subscriber connects to it

ZeroMQ is a messaging library that applications link in. No server process sits in the middle. A PUB socket sends every message to all subscribers connected to it. A SUB socket receives them and filters by topic, which is a prefix match on the first bytes of the message. A SUB socket can hold several filters and accepts a message that matches any one of them.

vLLM decides from the endpoint string whether to bind or to connect. An address with a wildcard, such as tcp://*:5557, or an ipc or inproc address, is bound, and the worker waits for subscribers. Any other address, such as tcp://10.244.0.40:5557, is connected to, and the worker dials out to a subscriber that has bound that port. llm-d's indexer supports both layouts. In one, each Pod binds its own socket and the indexer finds the Pods by label and connects to all of them. In the other, the indexer binds one port and every Pod connects to it. The special address tcp://*:0 makes vLLM bind the node's own address on a port the kernel picks.

In this lesson vLLM binds its PUB socket on port 5557 of the Pod. With three workers there are three ports to reach, so the picker opens one connection to each Pod address. A Service address would not do, because a connection to it lands on one worker only. PUB never waits for anyone. A message published before a subscriber connected is gone, and a subscriber that reads too slowly loses messages once the publisher's queue for it reaches the high-water mark.

Chapter 4 of 17

A quiet socket proves nothing

Silence can mean an idle worker, a lost connection or a worker that moved

A vLLM worker publishes only in a step that changed its cache. A worker with no traffic sends nothing for minutes, and that is normal. The subscriber therefore cannot treat silence as a fault, and it has no message that tells it the worker is still there.

ZeroMQ does not add one by default. ZMQ_HEARTBEAT_IVL is 0, so the library sends no heartbeat of its own, and ZMQ_TCP_KEEPALIVE is -1, which leaves TCP keepalive to the operating system. vLLM sets neither on its PUB socket. If a worker's node loses power, no FIN or RST reaches the picker. Its SUB socket keeps a TCP connection to a peer that is gone and waits, exactly as it waits for an idle worker.

A connecting socket also never gives up. When a connection drops, ZeroMQ tries again after ZMQ_RECONNECT_IVL, 100 milliseconds by default. ZMQ_RECONNECT_IVL_MAX is 0, which keeps the interval at 100 milliseconds, so the subscriber dials ten times a second for as long as the connect stays in place. When gpu-3's Pod is replaced, the new Pod gets a new address. The old connect keeps dialling the old one, and nothing reaches the new one until the subscriber learns the address and connects again.

The practical rule follows from this. The list of addresses to subscribe to has to come from Kubernetes, from the Pods the InferencePool selects, and it has to be refreshed when Pods change. The health of a worker has to come from somewhere other than its event stream, such as its readiness and its /metrics endpoint.

Chapter 5 of 17

A gap in the numbers, and a replay

The sequence number shows a loss and a second socket repairs it

Since PUB may drop, the subscriber has to notice. Every message carries the publisher's sequence number, so a jump from 4,211 to 4,213 means batch 4,212 never arrived. vLLM offers a repair when replay_endpoint is set.

The publisher keeps its last 10,000 encoded batches in memory and opens a ROUTER socket, a ZeroMQ type that can serve many requesters and send several replies to one request. The subscriber sends the first sequence number it lacks. The worker sends back every buffered batch from that number on and then an end marker. The same publisher thread handles both jobs. Before it takes the next batch from its queue, it checks the replay socket and answers any request that is waiting.

The buffer has a cost. Each entry is a whole encoded batch, so 10,000 batches the size of the one in this lesson would hold 10,000 × 9,986 B, about 100 MB, in the worker's own memory. The replay socket's send high-water mark is set to 2 × (10,000 + 1) = 20,002 messages, enough for a full replay and its end marker even when ZeroMQ is slow to acknowledge.

On the subscriber the request goes out on a REQ socket. REQ must receive a reply before it may send again. vLLM's example subscriber waits 200 milliseconds at a time for replies. Its launch script sets no replay_endpoint, so in that pairing a replay request is never answered.

A restart is different. The new process starts counting at 0 with an empty buffer and an empty cache, so everything the picker knew about that worker has to go.

Chapter 6 of 17

One Pod, two engines, two streams

With data parallelism each engine publishes on its own port

A vLLM server can run several copies of the model in one process tree, each on its own GPUs, with --data-parallel-size. Each copy is a data parallel rank with its own scheduler and its own KV cache. A block stored by rank 0 is of no use to a request that rank 1 serves. The picker therefore has to know which rank holds what.

vLLM gives each rank its own publisher. Rank 0 uses the endpoint as written. Every other rank adds its rank number to the port. With the default tcp://*:5557, rank 0 binds 5557 and rank 1 binds 5558. The replay endpoint gets the same treatment, so tcp://*:5558 becomes 5558 for rank 0 and 5559 for rank 1. Each publisher has its own sequence counter starting at 0 and its own replay buffer. Each batch also says where it came from in its data_parallel_rank field.

The two offsets can collide. In the configuration used earlier in this lesson, events on 5557 and replay on 5558, rank 1's event port and rank 0's replay port are both 5558 in the same Pod. Whichever socket binds second fails with address already in use. The fix is to leave a gap, for example replay on 5567, which gives 5567 and 5568. An inproc endpoint gets the rank as a suffix, _dp1, instead of a port change. An ipc endpoint gets neither: at rank 1 or higher vLLM v0.34.0 stops with ValueError("Invalid endpoint: must contain 'inproc' or 'tcp'"), so data parallel events need a tcp or inproc address.

For the subscriber, two ranks are two publishers. It connects to both ports of the Pod, tracks a sequence number for each connection, and keeps their blocks apart in the index.

Chapter 7 of 17

What the picker builds: an index of block hashes

From each block's key to the set of workers that hold it

The picker turns the stream into an index. Its key is a block hash and its value is the set of workers holding that block. BlockStored adds a worker to the sets, BlockRemoved takes it out, and AllBlocksCleared takes it out everywhere. Events from one worker must be applied in the order they were sent. llm-d's indexer, a public design of the same kind, does this by giving each Pod's events to one worker queue, chosen by an FNV-1a hash of the Pod's id. Events from different Pods run in parallel and each Pod's own events stay in order.

For a new prompt the picker has only text. It must turn the text into the same token ids the worker would, cut them into blocks of the same size and chain the hashes in the same way, or its keys will never equal the ones in the index. Then it walks the blocks in order and stops at the first one a worker lacks, because a block is usable only when every block before it is there too. A worker that holds blocks 1 to 4 and not block 5 scores 4. A worker that holds blocks 1 and 2, misses block 3 and holds later ones scores 2.

The index has to fit in memory. llm-d's in-memory index is a two-level LRU sized by entries, by default 100 million keys with up to 10 Pod entries each. It can also weigh where a block lives, 1.0 for GPU memory and 0.8 for CPU memory by default. The F5 picker has spec.blockSize and spec.tokenizer for the settings that must match the workers.

Chapter 8 of 17

Keys that match across processes

The hash algorithm and its seed decide whether two workers agree

Each block hash is computed from three things: the hash of the block before it, the token ids of this block and its extra keys. The first block of a prompt has no parent, so vLLM uses a fixed starting value called NONE_HASH in its place. The 130 blocks of the 2,085-token prompt take 130 hash calls, each one feeding the next.

--prefix-caching-hash-algo takes four values in vLLM v0.34.0. sha256, the default, serializes the input with Python's pickle and hashes it with SHA-256. sha256_cbor serializes it with canonical CBOR instead, a format with one exact byte layout, so a program in another language can compute the same hash. xxhash and xxhash_cbor use the faster, non-cryptographic xxHash with 128 bits. vLLM warns that a weaker hash raises the chance of collisions, which matters when tenants share a server.

The starting value is where workers can disagree. If PYTHONHASHSEED is set, NONE_HASH is derived from it. If not, the two SHA-256 forms derive it from the fixed string vllm-none-hash, so every worker computes the same keys. The two xxHash forms draw 32 random bytes per process instead, and vLLM logs a warning that block hashes are then not reproducible across processes. Two workers serving the same prompt then report different hashes for identical blocks.

The event carries a shortened hash. By default VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES is 1 and vLLM sends the low 64 bits as an integer. Set to 0, it sends the full hash as bytes, 32 of them for SHA-256. The 130 hashes in the batch then take 130 × 34 + 3 = 4,423 B where the integers took 1,173 B.

Chapter 9 of 17

Resets, offloading and other news

AllBlocksCleared, refused resets and blocks kept outside GPU memory

AllBlocksCleared is sent when a running server drops its whole prefix cache. vLLM does that on request. The block pool's comments name two reasons: invalidating the cache after the model's weights were updated, as in reinforcement learning, and starting a benchmark from a cold cache. The HTTP route for it is POST /reset_prefix_cache, and it exists only when the server runs with VLLM_SERVER_DEV_MODE=1. It answers with JSON, {"success": true} or {"success": false}.

A reset can be refused. vLLM clears the cache only when no block is in use except its one reserved null block. If running requests still hold blocks, it logs a warning that names how many, returns false and sends no event. The caller can try again later. A successful reset logs Successfully reset prefix cache, removes every hash and queues one AllBlocksCleared. A batch holding only that event is 35 B.

The medium field matters once blocks live outside GPU memory. A KV offloading connector can copy blocks to CPU memory or to storage. vLLM collects the connector's events with its own and publishes them in the same batch, with medium set to "CPU" or "STORAGE". A picker that reads medium can prefer a worker that holds a block in GPU memory over one that would have to load it back first. llm-d does this with its tier weights.

Every one of these events reaches the picker on the same stream as BlockStored and BlockRemoved. A subscriber that ignores AllBlocksCleared keeps every entry the reset just made false.

Chapter 10 of 17

NATS: the same news through a broker

Workers and picker each connect to one server and never to each other

NATS is a message broker. A server process, nats-server, listens on port 4222 by default, and publishers and subscribers both connect to it. Messages are addressed to subjects, which are names made of words joined by dots. The server passes each message to whoever subscribed to that subject. A subscriber can use wildcards: * stands for one word and > for one or more words at the end.

Core NATS stores nothing. It delivers at most once. A subscriber that is away when a message is published never gets it, and nothing numbers the messages for it. JetStream is the layer of NATS that stores messages in numbered streams and lets a consumer read them again later.

NVIDIA Dynamo can carry its KV cache events on NATS. In recent Dynamo releases that is a setting, DYN_EVENT_PLANE, since Dynamo's documentation from v1.3.0 on gives ZeroMQ as the default event plane. With NATS chosen, the events travel on core NATS without JetStream. vLLM itself only speaks ZeroMQ, so under Dynamo the vLLM worker still publishes on a ZeroMQ socket inside its Pod and Dynamo relays each event to NATS. Dynamo's events have their own shape. Each one names the worker, carries an event_id that rises by one per worker, and lists blocks with a block_hash and a tokens_hash in place of raw token ids.

The owner's lab ran the F5 picker with engine dynamo on Dynamo 1.5.1 and BNK 2.4. Twenty prompts that shared a 1.8 KB opening all went to one worker. Twenty prompts with nothing in common split 10 and 10 across two workers.

Chapter 11 of 17

What a broker adds, and what it limits

Message size, slow readers and dead clients are the server's business now

Moving the stream through a broker moves some decisions into the broker's configuration. Three of them matter for KV events.

The first is message size. max_payload is 1 MB by default, and a message larger than that is refused. A batch for a very long prompt carries thousands of block entries, so the size of the largest batch has to be compared with this limit when contexts grow.

The second is a reader that falls behind. The server writes to each client under a per-client write deadline, 10 seconds by default. When a client reads too slowly, the server gives up on it and closes the whole connection. It does the same when the data queued for one client passes max_pending, 64 MB by default, even before the deadline runs out. It counts the event in the slow_consumers figure on its /varz monitoring page. The client sees a disconnect with a read error and starts to reconnect. Client libraries also cap the messages they hold for one subscription. The Go client allows 500,000 messages or 64 MB, whichever comes first, and then drops new messages and reports a slow consumer error while the subscription stays open. ZeroMQ dropped messages for a slow subscriber silently. Here the drop is visible, and core NATS still has no replay.

The third is a client that vanished. The server pings each client every ping_interval, 2 minutes by default, and closes the connection after ping_max unanswered pings, 2 by default. A dead subscriber can therefore hold its place for several minutes.

The broker is also one process that every worker's events depend on. F5 documents that the picker falls back to speculative tracking when it receives no KV events, and keeps routing traffic. F5's pages do not describe a NATS outage during operation as a case of its own. A picker cut off from NATS receives no events, which is the input the documented fallback covers.

Chapter 12 of 17

Telling the F5 picker which transport to use

One field, spec.engine, selects it

On BIG-IP Next for Kubernetes the picker is described by an F5EPP resource, and one field decides the transport. spec.engine is vllm, sglang or dynamo. For vllm and sglang the picker takes KV cache events over ZeroMQ from the model server Pods. For dynamo it takes them from NATS, and spec.natsURL must give the address of the NATS server. Validation enforces the pairing: natsURL is required with dynamo and rejected with any other engine.

The same resource holds the two values that have to agree with the workers, spec.blockSize and the tokenizer. Only spec.poolRef.name and spec.engine are required. The controller generates the rest of the picker's configuration from the engine, and status.resolved shows what it settled on. In the generated configuration of the owner's lab, the ZeroMQ subscriber is a plugin named zmq-wire. The lab removes that plugin for simulated workers, which cannot publish vLLM's events.

There is one picker per pool. F5's own material gives the reason: each model may need a different tokenizer and different picker parameters. spec.replicas set to 2 gives one serving picker and a standby. BNK's data plane reaches the picker for ext_proc on port 9002, and its gRPC health check answers on 9003. In the lab, BNK put the picker back when its Deployment was scaled to 0. With a NetworkPolicy that let only BNK's namespace reach 9002, all 20 test requests still went through.

Chapter 13 of 17

The cache map is one score among several

Chasing every cache hit piles requests onto one GPU

The index tells the picker where a prompt's opening is cached. It does not tell it whether that worker can start soon. F5's picker weighs several signals for each candidate: how many requests wait in its queue, how many run, how full its KV cache is, the prefix match and other engine metrics. It reads the load signals from each worker's /metrics endpoint, about every 50 milliseconds in the owner's lab, and it skips a worker whose KV cache is above a saturation threshold, 0.99 in the generated configuration. The weights of the scorers sit in spec.eppConfig, under its scheduling profiles.

F5's benchmark shows why. Qwen3-32B ran on 8 H100 GPUs with a workload whose prompts shared an opening, and only the router changed. A router that sent every prompt to the GPU holding its prefix reached 81.5 % cache hits. More than 100 requests queued on the one warm GPU while 7 sat idle, and the median time to the first token was 29 seconds. The F5 picker reached 76.7 % hits. It moved the overflow to idle GPUs once the warm one filled, and its median time to the first token was 1.2 seconds. 29 ÷ 1.2 is about 24 times slower for the router that chased hits.

The owner's decks put this in one line: cache awareness without load awareness is worse than neither. The event stream makes the prefix score accurate. The load signals keep that score from sending everything to one place.

Chapter 14 of 17

Tuning the prefix scorer: its weight and its memory

Two knobs sit in spec.eppConfig.config, one in the scheduling profile and one on the scorer itself

F5's prefix scorer is a plugin called f5-prefix-cache-scorer. Two things about it can be changed. The first is its weight, which decides how much a cache match counts against the load of a worker. The second is how long and how much the scorer remembers, which F5 calls its cache TTL and entry management. TTL means time to live, the age after which an entry is dropped. Neither knob has a field of its own on the F5EPP. F5's tuning page says that the relative weighting of the scoring signals is tuned by F5 for each engine and cannot be set directly. That reads like a contradiction of the first knob, and it is one only on the surface. It means the F5EPP has no field of its own for the weights. The same page then lists scorer weighting under spec.eppConfig.config.schedulingProfiles, and the CR reference says one weight can be set there while everything else stays generated. So the weights can be changed, only through the merge. Both knobs are reached through spec.eppConfig.config, the field that merges settings over the configuration the controller generates.

That generated configuration is the place to start. For a pool called qwen3 the controller writes it into the ConfigMap qwen3-epp-config, which status.refs.configMap on the F5EPP names. The key pool.yaml holds the plugins with their parameters and the scheduling profiles. The key epp.yaml holds the settings of the picker process. A plugin entry has a type, an optional name that defaults to the type, and a parameters map. A scheduling profile has a name and a list of entries, each a pluginRef with an optional weight. In the upstream Gateway API Inference Extension, which F5's picker implements, a scorer with no weight counts with weight 1. F5's pages do not print the names of the scorer's TTL parameters or of the generated profile, so the operator reads both from pool.yaml before writing an override.

Here is how weights combine, in the upstream extension at v1.4.0. Every scorer gives every candidate a number. Anything below 0 counts as 0 and anything above 1 counts as 1. Each number is multiplied by the scorer's weight and the products are added up, one total per Pod. The picker then takes the Pod with the highest total, and breaks ties at random. The upstream prefix scorer's number is the share of the prompt's blocks that a Pod is believed to hold. The queue scorer gives 1 to the shortest queue in the pool, 0 to the longest and a straight line in between. The KV cache utilisation scorer gives 1 minus the share of the cache in use. F5's own scorers and its hcl-picker, which also sets aside hot Pods, are not documented to that level, so the arithmetic below uses the upstream formulas as an illustration. It also uses only three scorers. In the owner's lab with engine dynamo, the generated profile held five: queue-scorer, f5-prefix-cache-scorer, f5-prefill-load-scorer, f5-predictive-load-scorer and kv-cache-utilization-scorer. Every extra scorer adds to every total, so the exact flip point worked out below does not carry over to F5's picker. Only the method does.

Take the 2,100-token prompt from the first chapter. In blocks of 16 tokens it has 131 full blocks, and gpu-2 holds the first 128 of them. gpu-2 also has 6 requests waiting and 85 % of its cache in use. gpu-1 has an empty queue and 10 % in use. gpu-3 has 2 waiting and 40 % in use. With every weight at 1, gpu-2 scores 128 ÷ 131 = 0.977 for the prefix, 0 for the queue and 0.15 for the cache, 1.127 in all. gpu-1 scores 0 + 1 + 0.90 = 1.900. gpu-3 scores 0 + 4 ÷ 6 + 0.60 = 1.267. gpu-1 wins. Raise the prefix weight to 3 and gpu-2 reaches 2.931 + 0.15 = 3.081, so the prompt joins a queue of six. The two totals meet where 0.977 × w + 0.15 = 1.900, at a weight of about 1.79. Only the ratio between weights matters. Doubling every weight doubles every total and changes no choice. A weight of 0 takes the scorer out of the choice. The owner's notes use that for Qualcomm cards, whose vLLM plugin turns prefix caching off, so affinity could only concentrate load.

The memory knob matters most when the picker is guessing. With events flowing, a BlockRemoved deletes an entry as soon as vLLM evicts the block. Without events, nothing ever says a block is gone, so an age limit is one of the few ways an entry leaves the index. Too long and the picker keeps steering prompts at blocks that were reused minutes ago, as in the first chapter. Too short and it forgets blocks the worker still holds, and spreads prompts that could have hit. The upstream scorer limits its index by count instead, and its guide gives the rule behind any such limit: the index should be about as large as the cache it describes. At v1.4.0 it follows that rule by itself. autoTune is true by default, and then the capacity for each Pod is taken from the num_gpu_blocks label that the Pod's vLLM reports in vllm:cache_config_info. lruCapacityPerServer, 31,250 entries per Pod by default, is used only when that metric is missing or autoTune is switched off. For a sense of scale, one token of Qwen3-32B's KV cache takes 262,144 bytes: 64 layers × 8 KV heads × 128 values per head × 2 for key and value × 2 bytes. One H100 running the FP8 build holds 34.3 GB of weights. The card has 80 GiB, about 85.5 GB as the driver reports it, and with vLLM taking 0.9 of that, roughly 42.7 GB is left. That is about 160,000 tokens, or about 10,000 blocks of 16, before activations and CUDA graphs take their share, so the real number is somewhat lower. The 31,250 fallback is about three times that. vLLM reports the real count in num_gpu_blocks, and it logs the cache size in tokens at start-up.

The override carries only what changes. Plugins merge by name. Profiles merge by name, and the entries inside them by pluginRef. Setting one parameter or one weight leaves everything else generated and on F5's upgrade path. A config block must hold at least one of plugins, schedulingProfiles, featureGates or flowControl, and data or saturationDetector at its top are rejected. The other route, spec.eppConfig.configMapRef, replaces both keys with a ConfigMap of your own. It cannot be combined with config, and since the picker reads its configuration once at start-up, an edit to that ConfigMap does nothing until the qwen3-epp Deployment is restarted.

Chapter 15 of 17

What goes wrong in practice

Requests are still served. Only the cache hits go

None of these faults stops traffic. The picker keeps choosing workers by load, and what disappears is the cache hit. That makes them easy to miss, because every request still gets an answer, only slower.

First, the event port is blocked. The subscriber dials each worker on 5557, so a firewall or NetworkPolicy that only allows port 8000 into the model Pods cuts the stream. ZeroMQ connects in the background and raises no error for this.

Second, the keys do not match. Events arrive and the index fills, and no prompt ever finds its blocks, because the block size or the tokenizer differs between picker and worker. vLLM 0.34.0 changed the default block size from 16 to 64, so an upgrade that leaves --block-size unset produces exactly this. A worker that hashes with xxHash and no shared seed has the same effect for a picker that repeats the worker's hash.

Third, events are enabled on a worker whose prefix caching is off, so it has nothing to report. Prefix caching is on by default in vLLM 0.34.0, so this only happens when someone switched it off on purpose.

Fourth, the topic does not have the form the reader expects. llm-d's reader treats a topic without exactly three @-separated parts as one Pod id with no model name.

When no KV events reach it, the F5 picker falls back to speculative tracking, the guess from the first chapter. A mismatch is quieter still. F5 describes it as silent degradation of cache-hit accuracy.

Chapter 16 of 17

A model server outside the cluster

The picker only hears from Pods, so a relay Pod has to stand in

The F5 picker finds its workers as Pods. It reads the InferencePool's selector and watches the Pods with those labels in its own cluster. BNK can still send plain traffic to a vLLM server on a virtual machine or another cluster, through a Service with no selector and endpoints written by hand. The picker ignores those endpoints. It never scrapes that server's metrics, never subscribes to its events and never checks its health, so the server gets no prefix-aware routing at all. The owner's notes record that supporting this would take new code in the picker for discovery, metrics, events and health, which no setting can replace.

The owner's Lambda proof of concept worked around it with relay Pods. Each relay is a Deployment running socat, a program that copies bytes between two TCP connections. There is one relay per model on each GPU virtual machine. It listens on 8000 for the API and /metrics, on 20080 for the ZeroMQ event stream and on 20081 for replay, and forwards each to the same port on the machine. The relay Pods carry the pool's label, so the picker discovers them as workers. Because the copy is byte for byte, the metrics and events the picker sees are the machine's own, and with one relay per machine and model the index stays accurate.

The notes also list what the relay does not solve. Its readiness probe checks the relay, so the picker can route to a dead machine until something else removes the relay. All traffic passes through relay Pods pinned to one node. The link to the machine is plain TCP. F5 does not support the pattern, and a change to how the picker discovers Pods could break it.

Chapter 17 of 17

Checking the stream by hand

Four commands, from the resource to the socket

When prefix-aware routing seems not to work, each link in the chain can be checked on its own, from the configuration to the bytes on the socket.

Start with the picker's resource. kubectl get on the F5EPP with -o yaml shows status.resolved: the engine in use, the model and where its name came from, the block size and whether the configuration was generated or merged. If the engine is wrong, nothing further will help.

Then ask a worker what it is doing. vLLM publishes its cache settings as a metric, vllm:cache_config_info, a gauge fixed at 1 whose labels hold every cache setting as text. The labels block_size, enable_prefix_caching and prefix_caching_hash_algo answer three of the questions in this lesson in one line. The counters vllm:prefix_cache_queries and vllm:prefix_cache_hits count tokens looked up and tokens found. That is how vLLM registers them. The Prometheus client adds _total when it exposes a counter, so the series on /metrics and in PromQL are vllm:prefix_cache_queries_total and vllm:prefix_cache_hits_total. Hits divided by queries is the share of prompt tokens served from the cache. The request in the index chapter alone would add about 2,100 queried tokens and 2,048 hits, close to 97.5 %.

Next, listen to the stream yourself. A short script with pyzmq, run from a Pod that the NetworkPolicy lets in, connects a SUB socket to the worker's port 5557, subscribes to kv@ and prints each message. Three frames that arrive mean the worker publishes and the path is open. Nothing at all, while requests flow, points at the port or the configuration.

Last, read the picker's own metrics. In the owner's lab, f5_epp_prefix_index_lookups_total with result no_query and epp_tokenizer_guard_events_total with event encode_failed rose together when the tokenizer name was wrong.

What to keep

A map is only as good as its news

The picker's map of cached prefixes can come from its own memory of past decisions or from the workers. vLLM reports each stored and removed block as events in a msgpack batch, with hashes that only match when the algorithm, the seed, the block size and the tokenizer agree. ZeroMQ carries the batches straight from each worker with no broker, drops them for a slow or absent subscriber, sends nothing when a worker is idle, and leaves the repair to sequence numbers and a replay socket. Data parallel ranks add one stream per rank. NATS puts a broker in the middle, which means one connection for the picker, visible slow consumers and one more thing to keep running. The map then feeds one score among several, beside the load of each worker. Its weight in the scheduling profile and the age limits of f5-prefix-cache-scorer are set by override in spec.eppConfig.config, after reading the generated pool.yaml. When the news stops, routing continues on guesses.
