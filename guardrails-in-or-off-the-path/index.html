BNK and gateways

Guardrails: in the path or beside it

A policy iRule in TMM, or a gateway every byte crosses

A guardrail reads a prompt and says whether it may go on. Where it stands decides what it can see and what it costs. This lesson shows both places. First the guardrail stands beside the path: a policy iRule in TMM holds the request, sends a copy of the prompt to the guardrail's API and waits for a verdict. Then it stands in the path: the request goes through an AI gateway, and so does every token of the answer. You will see a prompt with a trick in it get refused, a clean one pass both ways, and what happens when the guardrail doesn't answer.

Chapter 1 of 15

A prompt with a trick in it

It looks like any other request

Someone sends the support bot a message that tries to make it give away its instructions. To the network this is an ordinary request: a valid TLS session, a well-formed POST, a real API key. The firewall lets it in, because the firewall looks at addresses and ports. Only something that reads the words can tell that this prompt is an attack.

Follow what the border does with it. TMM completes the TLS 1.3 handshake for api.northlight.example, so from here on it can read the HTTP/2 request. The firewall rule on the listener allows TCP port 443 from any address, and this packet matches it. The route for /v1/chat/completions matches too. The body is 8,260 bytes of JSON with two messages in it, and it asks for a stream with the token counts at the end. The first is the system prompt, which the provider of the bot wrote. The second is the user's line.

A request in this factory passes seven decisions in a fixed order: the firewall, the API key, the prompt check, the budget, the choice of model, the choice of GPU and the meter. A request that is refused at any of the first four never costs GPU time. The budget can also act without refusing, by sending the request to a smaller model, and that request does use a GPU, as the last chapter shows. The firewall is the first, and it has just said yes. This lesson is about the third decision, and about the two places where the thing that makes it can stand.

Chapter 2 of 15

One iRule holds the request

Policy that runs inside the data plane

In this design there is no separate gateway in front of the GPUs. The policy runs in TMM itself, as an iRule attached to the Gateway's listener. An iRule is a small program that TMM runs at fixed moments of every connection. When the request headers arrive, the iRule tells TMM to keep the request and collect its body instead of forwarding it. When the body is in, it reads the JSON. Its first job is the key. It opens a side connection to the key service, asks about the key and gets back the team that owns it. The user's request has not moved. It is parked in TMM while the iRule asks around.

The iRule is stored as a Kubernetes resource and bound to the listener through a policy object, so it is deployed like any other manifest. Two details decide whether it works. HTTP::collect takes a byte count, and here the iRule passes the Content-Length of 8,260. When that many bytes are in, TMM fires HTTP_REQUEST_DATA and HTTP::payload returns them. This factory's iRule refuses bodies above 1,048,576 bytes before it collects, so that a huge upload cannot be parked in memory.

The side call uses three sideband commands: connect, send and recv. In the lab build this lesson follows, the connect only reached a ClusterIP with -protocol TCP written out. It leaves from the TMM Pod's own address, 10.244.0.14, and a NetworkPolicy on the key service has to allow that address. The answer comes back 1.6 ms later.

Chapter 3 of 15

Beside the path: ask the guardrail

A copy of the prompt goes out, a verdict comes back

The second side call goes to F5 AI Guardrails. The iRule sends the text of the prompt to the guardrail's scan API and waits. The call leaves TMM over TLS, through a bridge that the next chapter opens up. The guardrail is not in the path here. The request itself never passes through it. It only sees the copy that TMM chose to send, and it answers with a verdict. This time the verdict is block: the last message is an attempt to override the system prompt. The iRule doesn't forward anything. It writes the refusal itself. No picker was asked, no GPU was touched.

F5 AI Guardrails offers this as a scan API. The caller posts to /backend/v1/scans with a bearer token. The body names the text in input, a project that holds the guardrail settings, and a scanDirection of request for a prompt. One more field matters for this design. With flagOnly left out or set to true, a guardrail that is set to block only reports flagged. With flagOnly set to false, the outcome in the result says blocked. F5 added the field for setups where the scanner stands beside the path and another system enforces. Here that system is the iRule, so it sends false and acts on the outcome.

Add up the time. The key check ended at 2.4 ms. The scan left at 2.6 ms and its verdict arrived at 108 ms, which is 105.4 ms of waiting. The 403 was on its way 0.3 ms later. All of it was spent in TMM and in the guardrail.

Chapter 4 of 15

The side call needs a bridge for TLS

Sideband commands speak plain TCP

Look again at that side call. The sideband commands of an iRule, connect, send and recv, speak plain TCP. They cannot start a TLS session. F5 AI Guardrails is reached over HTTPS, and it is often a hosted service outside the cluster, so something has to add the TLS. A small proxy Pod in between would work. It would also add a hop and one more thing to run. The lab build this lesson follows does it inside TMM.

The iRule connects to a virtual server that exists only inside TMM, here 10.20.0.9:8087, and sends plain HTTP to it. That virtual server has a pool with one member, the guardrail's real address and port, and a server-side TLS setting that allows TLS 1.2 and 1.3. TMM opens the TLS session toward the guardrail itself. In the lab these are six resources: an F5VirtualServer, an F5BigCnePool, an F5BigServersslSetting, an F5BigHttpSetting, an F5BigTcpSetting and an F5BigCneIrule.

The last one closes a gap. Neither the virtual server nor the TLS setting has a field for the server name to send in the TLS handshake. The hosted guardrail in the lab sits behind a shared front end that routes on that name and on the HTTP Host header, so both have to name the guardrail for the request to reach it. So a second small iRule on the bridge sets the name and rewrites the Host header. One of the other resources is easy to leave out because it looks like a default. The lab marked the TCP setting, F5BigTcpSetting, as required: without it the connection was reset. The lab proved the path with a bare request through the bridge. It came back as a 422 from the real service: wrong body, right destination.

Chapter 5 of 15

Five objects in a row, three iRules and three libraries

The lab chain from the Gateway to the model server

The bridge is one part of a longer chain. The lab build this lesson follows drew the whole inference path with AI Security as five objects in a row. A client posts to /v1/chat/completions. The first object it meets is a Gateway named guardrails-gw, which gives TMM a virtual address that listens on port 8000. The second is an HTTPRoute named guardrails-route in the namespace dynamo-system. It matches the path and names the backend. The third is a BNKNetPolicy named guardrails-policy, which attaches three iRules to the traffic of that route. The fourth is the egress bridge of the last chapter, which only the side calls use. The fifth is the model server. In the lab it was the frontend of an NVIDIA Dynamo deployment with vLLM workers behind it, llm-vllm-agg-llmfrontend on port 8000, also in dynamo-system. In this factory the endpoint picker and the two qwen3 Pods take that place, on the same port.

The policy object is the piece people miss. An iRule on its own does nothing. It is stored as an F5BigCneIrule resource, and TMM runs it only on the traffic of a listener that a policy object binds it to. F5's deck draws this object as BNKNetPolicy. The guardrails chain ran on a test cluster whose BNK version the deck does not give. In a separate BNK 2.4.2 lab the policy kind is NetPolicy, in the API group gateway.k8s.f5.com, and iRules are attached through it. The deck shows the policy as the object that attaches the three iRules to the route. It does not show what happens when that object is removed. What follows from the attachment is this: an iRule that nothing attaches to traffic is a stored resource and checks no prompt.

There is one iRule for each moment of the exchange. The request iRule, guardrails-request-irule, runs on HTTP_REQUEST_DATA. It scans the prompt and takes one of the three outcomes of the next chapter. The lab also had a response iRule and a stream iRule. The deck gives them no more detail than their names and one rule about errors. By their names, one acts on an answer that comes back whole and the other on an answer that is streamed, but the lab material does not describe what they check. Only the request iRule blocks on a flagged verdict. The response and stream iRules fail open when a scan errors, so in this build blocking on a verdict happens on the request side only. All of this is the lab build. This factory's iRule scans prompts only, as the later chapters show.

Code that all three need lives once, in three shared libraries: common-lib, json-lib and redaction-lib, whose full name in the lab is guardrails-redaction-lib. A library is an iRule that holds only procedures and is attached to no listener. F5's iRule reference says a proc must be defined outside any event, and that another iRule calls it by putting the name of the iRule that defines it in front: call other_rule::my_proc $args. The redaction library holds the span replacement shown in the next chapter. Settings such as the block body are set once in RULE_INIT. That event fires when an iRule is saved, when the device starts and when the software restarts, and the static variables it sets are read by every request after that. So a change to the block body is a change to one resource, applied once, and the next request already uses it.

Chapter 6 of 15

Three outcomes, and one changes the prompt

Cleared, flagged or redacted

A verdict is more than yes or no. The lab build behind this lesson sorts every scan into one of three outcomes. Cleared means no rule was broken. The request goes on unchanged, and the iRule adds the header X-Guardrails-Request-Action: pass so that later hops and logs can see it was checked. Flagged means a guardrail fired. The request iRule answers at once with a block body that the operator configures. The lab's default is status 200 with a JSON body that says Blocked by policy. This factory chose 403, as you saw.

The third outcome is redacted. Here a customer writes that their account is locked and includes an email address and a social security number. Nothing is wrong with the request, yet those two strings should never reach a GPU. The scan result lists each match with its character offsets. A redaction library in the iRule replaces each span with <redacted>. The simple way is to work from the last match to the first, so that a replacement does not shift the offsets still to be used. HTTP::payload replace changes the held body and corrects Content-Length. The request goes on with the header set to redact.

So a guardrail beside the path can still change a prompt, because TMM is holding the whole body when the verdict arrives. Count the bytes. The address is 16 characters and the number is 11. Each becomes 10. The body shrinks by 7 bytes, from 8,276 to 8,269.

Chapter 7 of 15

A clean prompt, the same road

Allowed, then picked, then served

Now an honest question arrives on the same listener. The iRule does the same things in the same order: collect the body, check the key, send a copy of the prompt to the guardrail. This verdict is allow. Only now does the iRule let the request go. TMM asks the endpoint picker which worker should take it and forwards it to gpu-2. Count the cost of the check: one extra round trip, about a tenth of a second, before the first hop toward a GPU. The answer will stream back through TMM alone.

During that wait the guardrail is running a model of its own. The injection check is a small classifier. One of the open ones, Llama Prompt Guard 2, is measured by its makers at 92.4 ms for a 512 token input on an A100 GPU. That is the scale of the number here. A pattern check for card numbers costs a few milliseconds at most. So the delay of a guardrail beside the path is set almost entirely by which checks are switched on. The extra round trip inside the cluster is a small part of it.

The user feels this as a later first token, which is the delay people notice most in a chat. Take a model that sends its first token 70 ms after the request reaches it, an illustrative figure. The user now waits about 170 ms for it. Once the stream is running, no guardrail reads it in this design. The iRule only watches for the last chunk, to count the tokens.

Chapter 8 of 15

Released to the picker

Allowed, then picked, then forwarded

Only an allowed request reaches this point. The iRule lets go of it and TMM carries on with its normal work in a fixed order: the firewall first, then the iRule's key and guardrail checks, then the endpoint picker, then the forward. The picker is asked over ext_proc. That is a gRPC protocol in which the data plane streams a request's headers and body to an outside service and gets instructions back. TMM sends two messages, 8,554 bytes of protobuf in all, to the picker on port 9002.

The picker answers 0.7 ms later with one header to set: x-gateway-destination-endpoint, with the value 10.244.2.22:8000. That is gpu-2, chosen because it already holds this bot's system prompt in its KV cache. TMM then sends the request to that Pod address directly. No Service address and no kube-proxy rule sits in between.

One change was made on the way. The caller asked for northlight-chat, which is an alias. The iRule rewrote it to qwen3-32b, the name the model server knows. The alias is 15 characters and the real name is 9, so the body is 6 bytes shorter: 8,234 came in and 8,228 go out. With no AI gateway in front, the choice of model lives in the same iRule as the key check and the guardrail call. From the first byte at the border to the forward, this request spent 101.3 ms, and all but about 4 of them were the guardrail.

Chapter 9 of 15

In the path: the AI gateway

Every byte crosses it, in both directions

Here is the other design, with the same clean prompt. TMM does not hold the request. Its route sends the whole request to F5 AI Gateway, a proxy that stands in the path. The gateway has the guardrail as one stage of its own pipeline, next to keys, budgets and model choice. The prompt check looks the same. The difference shows on the way back. The answer streams through the gateway too, so the guardrail can read what the model says, and here it finds an email address in the answer and masks it before the user sees it. The price is that every token now takes one more hop each way.

The gateway is one endpoint that applications call, and it works through fixed checkpoints: who is calling, which models that key may use, what budget is left, then inspection, then the route to a model. Guardrails are called at two of those checkpoints, once for the prompt and once for the response. The request now crosses TMM twice, on the way to the gateway and on the way from it to a GPU. An AI gateway in a Pod only governs the traffic that is sent to it. So the border still has to make sure nothing reaches a GPU by another road. In this factory the route on the listener is that guarantee.

The gateway earns its hop in a second way. It can send the same request to a hosted model outside the factory, with the provider's key kept inside the gateway, and the same prompt check applies. A company with no GPUs of its own runs only this half.

Chapter 10 of 15

The answer crosses the gateway too

A window of tokens is scanned before it is released

Here is the difference. In the iRule design the answer streamed from gpu-2 through TMM to the user, and no guardrail read it. The iRule looked only at the last chunk, for the token counts. Now every chunk of the stream goes to the gateway first. A chunk is one server-sent event: a line that starts with data: and holds a small JSON object with the next few characters of the answer. This one is 166 bytes and carries the text billing@. The rest of the address comes in the chunks after it.

A scanner cannot judge that fragment alone. Half an email address is not yet an email address. So the gateway keeps a short window of the newest tokens to itself, 40 in this example, and has the guardrail scan the window as one text. The verdict takes 4 ms. It says that characters 9 to 35 of the window are an email address and gives the text to put in their place. The gateway rewrites the held text and releases it to the user as one event of 150 bytes. The address was 26 characters and [email removed] is 15, so the user gets 11 bytes less text than the model wrote.

Two costs follow. Each window waits for a scan, so the delay is paid all along the stream, and the first token is held until the first window fills. The gateway also holds two long-lived connections for every answer. In return the model's output is covered, and an email address the model should not hand out never leaves the factory. F5's own raw scan endpoint is stricter still when it is called without stream=true. By default it scans the full answer before it returns it, so a caller that waits for it shows the user nothing until the end.

Chapter 11 of 15

The same check as a declared policy

A policy object on the route replaces the script

Both designs so far needed something written: an iRule, or a gateway pipeline. BNK's own design for this check is a third form. The check is declared as a policy resource, an EgressPolicy, and attached to the HTTPRoute that carries the chat traffic. It is managed like any other Kubernetes object, with kubectl or from Git. TMM hands the prompt to F5 AI Guardrails and enforces what comes back inside the data plane. There is no script to maintain.

The policy knows three verdicts. Pass means the prompt is clean, and it moves straight on to the semantic cache and the model. Fail means an injection or a jailbreak was found, and TMM answers 403. Obfuscate means personal data or a secret was found, and it is masked in place before the prompt reaches a model. Those are the three outcomes the lab iRules produced by hand: cleared, flagged and redacted.

The order of stages stays the same. Traffic comes in at layer 4, is routed to a TMM Pod, meets the guardrail policy, then the AI gateway functions such as the semantic cache and token limits counted per minute and per day, then the endpoint picker, and behind it workers that may be split into prefill and decode pools. Every blocked prompt and every masking is logged in one place. The check protects a hosted model and a self-hosted one in the same way, because it runs before the request knows where it is going.

Chapter 12 of 15

When the guardrail doesn't answer

Fail closed or fail open is your choice

Back to the iRule design. A guardrail is one more thing that can be down. Suppose the side call gets no answer. The iRule has to decide, and whoever wrote the policy decided for it in advance. Fail closed means: no verdict, no GPU. The user gets an error and nothing unchecked goes through. Fail open means the request continues without a verdict. This factory fails closed on the prompt. The same question exists in the gateway design. There it is a setting of the gateway. Here it is a few lines of the iRule.

The sideband commands report failure in two ways, and an iRule has to handle both. Given -timeout 2000, connect waits two seconds. If nothing answers, it returns an empty string where a connection id should be, and the variable named with -status holds timeout. The other values are connected and failed. Some failures raise a Tcl error instead, for example when TMM has no route to the address. An error that is not caught aborts the iRule, and the user's connection is reset.

With the TLS bridge in between, the silence shows up one command later. The iRule's connect goes to the bridge at 10.20.0.9:8087, which is inside TMM and accepts it. It is the bridge's own connection to the guardrail that gets no answer. So the wait happens in recv. Given -timeout 2000, recv waits two seconds and its -status variable holds timeout. Its other values are received, closed and failed. recv has a trap of its own. F5's reference for recv says that without -timeout the default is an immediate timeout, so it returns at once, usually with nothing.

The choice can differ by direction. The lab build behind this lesson also scanned answers, with separate response and stream iRules. Its request iRule blocks on a flagged verdict. Its response and stream iRules fail open when a scan errors, so a slow guardrail never cuts off an answer that is already streaming. This factory's iRule does not scan answers at all, so its only choice is the one on the prompt. The endpoint picker has the same kind of switch. In the standard picker protocol it is a field named failureMode, and FailClose is its default.

Chapter 13 of 15

Count what the model said

The same iRule meters the answer

One job is left for the iRule, on the way back. When gpu-2 finishes the clean request about the billing address, the last chunk of its stream carries the token counts. The request asked for that with stream_options.include_usage. The iRule reads them from the response and reports them to the usage service with one more side call. That is where budgets come from. When a team runs out, the same policy can answer 429, or quietly send that team's next requests to a smaller model. So in this design one iRule on one address holds the key check, the guardrail, the model choice and the meter, and the picker still chooses the GPU.

The numbers come from the model server. With stream_options.include_usage set, the server adds one extra event before data: [DONE]. Its choices list is empty, and its usage object holds prompt_tokens 1,904, completion_tokens 186 and total_tokens 2,090. The iRule collects the response data, finds that object and posts it to the usage service on the same kind of side call as before. The team had 8,800,000 tokens left this month. It now has 8,797,910. The iRule also adds the same 2,090 to the team's running total in TMM's session table. That copy lives in TMM's memory, so the budget check can read it before the next request without a side call. The usage service holds the month's budget, and the session table holds the fast running total that the next chapter and the lab chapter use. The balance is illustrative. To keep the arithmetic on one request, it leaves out the tokens of the other requests in this lesson, such as the redacted one sent to gpu-1.

An AI gateway meters the same way and adds more. It keeps budgets in layers, for a member, a group, a model and a provider. It also reserves up front: it sets aside the prompt's tokens plus max_tokens before the request runs, and answers 429 if that would break the budget. One huge request cannot overspend a team that way. The iRule shown here counts after the fact.

Chapter 14 of 15

Three habits that keep an iRule alive

Catch every error, apply from a file, capture on any

The lab that built these iRules wrote down three rules after each one cost time. Each failure they prevent gives no useful message, which is why they are worth learning before the first iRule goes in.

The first rule: every connect and every table command goes inside catch. table is the iRule command for TMM's session table, a store of keys and values in TMM's memory that every connection through that TMM can read. The lab's meter parks each user's token counts there, with commands such as table incr, whose syntax is table incr [-notouch] [-subtable name] [-mustexist] key [delta]. connect opens the side calls. Both can raise a Tcl error at run time. When an error is not caught, TMM stops the iRule at that line and resets the client's connection. The user sees a broken connection with no status code and no body. catch runs a script, returns 0 if it finished normally and 1 if it raised an error, and puts the result or the error text in a variable. F5's own example for connect tests both ways a side call can fail: if {[catch {connect -timeout 1000 -idle 30 -status conn_status sideband_virtual_server} conn_id] == 0 && $conn_id ne ""}. An error gives 1. A connection that never opened gives 0 and an empty conn_id.

The second rule: apply an iRule from a YAML file, with kubectl apply -f and the file name. The Tcl of the iRule sits inside an F5BigCneIrule resource as a string. Pasting it into a terminal as a here-document, the shell's << form that feeds the lines after it to a command, changes it. The Bash manual says that when the word after << is not quoted, the lines are treated like a double-quoted string and go through parameter expansion, command substitution and arithmetic expansion. Tcl writes every variable with $, and the shell reaches them first. The line log local0. "key $key team $team" arrives as log local0. "key team " when the shell has no variables of those names. The line set status $static::block_status arrives as set status ::block_status, because the shell takes $static as a variable name, finds it empty and keeps the rest. The resource is still valid YAML, so the cluster accepts it, and TMM loads an iRule that does something else. A quoted word, <<'EOF', turns expansion off. A file is safer still, and it can be reviewed and kept in Git.

The third rule is about seeing the traffic. In the lab, traffic of an L4Route, the route kind for plain TCP and UDP listeners, showed up in a packet capture only on the interface named any, and only in the TMM that owns the virtual address. The lab ran two TMMs, each on its own node. In a TMM's debug container the named interfaces are external-vlan for client-side traffic and internal-vlan for server-side traffic. The L4Route traffic did not show on either of them, and it did not show in the TMM that did not own the address. An empty capture tells you where you looked. It tells you nothing about whether traffic arrived.

Chapter 15 of 15

The whole chain, run in a lab

Firewall to meter in one TMM, with results

The decisions this lesson took one at a time were also run together, in one TMM, in a lab. The owner's write-up numbers them from 0 to 6: 0 the network firewall, 1 the API key, 2 the guardrail scan, 3 the token budget, 4 the choice of model, 5 the endpoint picker and 6 the meter. They are the seven decisions of the first chapter, counted from zero. Step 0 works at the network layer, before any HTTP is parsed. Steps 1 to 6 are one policy iRule per endpoint, built from the policies the provider switched on. It makes side calls to the key service, the guardrail and the usage store, and asks the picker over gRPC ext_proc. Steps 0 to 2 stopped requests in the lab, and a request stopped there costs no GPU time. Step 3 did not stop anyone in the lab. It sent the request on to a smaller model, which still spends GPU time.

The lab was BNK 2.4.2 in host mode on OpenShift 4.22.22, with two TMMs. A controller turned the inference endpoint profile of one GPU cloud into BNK resources, and the endpoint went active in 2.1 s on the virtual address 10.210.100.20, advertised to the fabric by both TMMs. There were no real GPUs. The workers were simulators that answer like a model server, and the guardrail was a mock of the scanner. So the results show the order of the steps and that each one is enforced. They show nothing about GPU speed.

Every step passed. With no key or a bad key the gateway answered 401, and a valid key got 200 and was metered as its user. Usage rows per user and model appeared within seconds. The iRule parks the counts in TMM's session table, one leader flushes them, and the side call leaves from TMM's Pod address. A harmless prompt was served and a prompt about ransomware was blocked before any model. Then the scanner was taken away under a live policy. The iRule was rendered again with its side call pointed at an address where nothing answers, every request was blocked, and the policy's status said error. That is fail closed, shown end to end. The model schedule sent requests to a 1.5B model off peak and a 7B model at peak.

The budget step was tested with a quota of 50 tokens. The meter adds each answer's usage.total_tokens to the user's total in the session table. Before the next request is forwarded, the iRule reads that total. Below 50 the request goes on as asked. At 50 or more the iRule rewrites the model field of the held body to the 1.5B model and sends it to the fallback workers. Nothing is refused. The user still gets an answer, from a smaller model. A reset clears TMM's totals. In this factory the same rule would rewrite qwen3-32b to a smaller model once team support-bot ran low.

Step 0 used a SecPolicy and an F5BigFwPolicy with the address and port lists written inline. Separate F5BigCneAddresslist and F5BigCnePortlist objects resolve only in the CNE namespace, and in the endpoint's own namespace the firewall policy waited for them forever. The blocked client was dropped, TMM sent 8 drop events over syslog, and the rule hits were counted. The log publisher F5BigLogHslpub takes an address and port, so the syslog receiver is given as ip:port. Finally the picker: 288 requests per mode, 0 errors, and a median time to first token of 80.7 ms in round robin against 63.3 ms cache aware. That is 17.4 ms less, about 22 percent, on simulated workers.

What to keep

Checked before the GPU

Both designs stop a bad prompt before it costs a GPU anything. Beside the path, the request waits in TMM while a policy iRule asks the key service and the guardrail on the side. That adds one round trip before the first token and nothing after it, and it needs no extra proxy. In the path, the request and the whole answer cross an AI gateway. That costs a hop for every token, and in return the answer can be read and changed as it streams, and the same gateway can front models that are not in this factory at all. Either way, decide in advance what happens when the guardrail is silent. The same check can also be declared as a policy on the route, with pass, fail and obfuscate as its verdicts, and a verdict beside the path can redact a prompt as well as refuse it, because TMM still holds the body. A lab ran the whole chain, firewall to meter, in one TMM, and every step held, including a quota that sends a team to a smaller model instead of refusing it.
