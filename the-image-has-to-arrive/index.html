Kubernetes underneath

The image has to arrive

What a node does between getting a Pod and starting its container, when the image is ten gigabytes

The scheduler has given a model server to gpu-node-1. The node has a free GPU. Its other three cards run model servers on an older vLLM release, so this Pod's tag, v0.33.0, is not on its disk yet. Before anything can run, the software has to get there. A container image is a description plus a stack of compressed archives, kept on a server called a registry. The node reads the description, downloads each archive, checks it, and unpacks it into a filesystem. For a web server that takes a second or two. A vLLM image carries the CUDA libraries and PyTorch and is about ten gigabytes. This lesson follows that pull from the name in the Pod to a running container, through one failure on the way, and then adds up what a cold start costs.

After the container runs, the lesson stays on the node. It shows why a second Pod's image waited in line, how mirrors and rate limits change where the bytes come from, and how the kubelet decides when a ten gigabyte image is deleted again. Every request, header, field, event and setting shown is the real one.

Chapter 1 of 13

The name on the Pod

Registry, repository, and a tag that can move or a digest that cannot

The Pod's container names its image in one string: registry.northlight.example/vllm/vllm-openai:v0.33.0. It has three parts. The host before the first slash is the registry, the server that stores images. The path after it is the repository, which holds every version of one image. The part after the colon is the tag, a label for one version.

Leave the registry out and Kubernetes uses Docker's public registry. The documentation's example is busybox, which means docker.io/library/busybox:latest. A one-word name gains the library/ prefix as well. A cluster can change the default registry in the container runtime's configuration. Leave the tag out and it assumes latest.

Each part has rules. A repository name is lower case only: letters, digits and single separators such as a dot, a dash or an underscore, in parts joined by slashes. Many clients cap the registry host, the slash and the repository together at 255 characters. A tag is at most 128 characters. It starts with a letter, a digit or an underscore, and may then hold dots and dashes too. A name that breaks the rules never reaches the registry. The kubelet stops with the waiting reason InvalidImageName.

A tag is a pointer, and its owner can move it to different content tomorrow. In the registry's own words, one manifest can have zero, one or many tags. A digest cannot move. It is written after an @ sign, as an algorithm and a hash, and is the hash of the image's own description. The image specification registers sha256, sha512 and blake3, and sha256 is the one in common use. A client should check the size of the content before it hashes it. If a reference carries both a tag and a digest, only the digest is used for the pull.

Chapter 2 of 13

Pull, or use what is on the node

imagePullPolicy decides, and its default depends on the tag

Each container has a field named imagePullPolicy with three possible values. IfNotPresent pulls only when the node does not have the image. Always asks the registry every time a container starts. Never refuses to pull at all.

Always does not mean download everything again. The documentation is exact here. The runtime contacts the registry, resolves the tag to a digest and downloads only the layers it does not already hold. If it holds them all, it downloads nothing. The kubelet itself does not check the node's cache when the policy is Always. It hands the question to the runtime every time. So Always costs one round trip to the registry, and the registry must be reachable for the container to start.

Never means the kubelet does not try. If the image is somehow on the node, the container starts. If not, the container waits with the reason ErrImageNeverPull and the message Container image "…" is not present with pull policy of Never.

When the field is left out, the API server fills it in once, when the object is created. There are four cases. A digest gives IfNotPresent. A tag of latest gives Always. No tag gives Always. Any other tag gives IfNotPresent. A cluster can also force Always on every Pod with the AlwaysPullImages admission controller, which stops one tenant from using an image another tenant's credentials pulled.

This Pod says v0.33.0, so it gets IfNotPresent. The kubelet asks the container runtime containerd whether it holds the image. gpu-node-1 has never pulled this tag, so the answer is no. The container waits with the reason ContainerCreating, and the Pod's phase stays Pending.

Chapter 3 of 13

The kubelet asks containerd

One call named PullImage, and this first time it carries no credentials

The kubelet downloads nothing itself. It talks to containerd through the CRI, the Container Runtime Interface, a gRPC API on a socket on the node. One call does the work: PullImage. It carries the image name and, when there are any, the credentials for the registry.

The Pod lists a pull secret named registry-pull under imagePullSecrets. Nobody has created that Secret in the inference namespace yet. The kubelet logs Unable to retrieve pull secret, the image pull may not succeed, and goes on with no credentials. It records an event with the reason Pulling. If the pull then fails, the kubelet also records a Warning event with the reason FailedToRetrieveImagePullSecret. Its message names the missing Secret, registry-pull, and warns that the pull may not succeed. Of all the events this Pod gets, that one names the cause. By default a kubelet pulls one image at a time, so another Pod's pull on this node would wait in line. A later chapter shows that queue.

PullImage can take a long time, and the kubelet allows for that. Its setting runtimeRequestTimeout, 2 minutes by default, applies to every runtime call except the long-running ones: pull, logs, exec and attach. The guard against a pull that hangs is in containerd instead. Its setting image_pull_progress_timeout, 5 minutes by default, cancels a pull that has made no progress for that long.

containerd now speaks HTTP to the registry. Its first question is what the tag v0.33.0 points to. It sends a HEAD request for the manifest, which asks for the headers only. The request has no Authorization header. The repository is private, and the registry answers 401 Unauthorized. With the 401 comes a WWW-Authenticate header that says where to get a token and for which scope. A registry may also answer a wrong name this way, so as not to reveal which private repositories exist.

Chapter 4 of 13

A failed pull waits longer each time

ErrImagePull is the failure, ImagePullBackOff is the wait before the next try

containerd returns the error to the kubelet. The kubelet sets the container's waiting reason to ErrImagePull and records an event with the reason Failed. It will try again, with a growing pause called a back-off. The first pause is 10 seconds and each failure doubles it, up to a fixed limit of 300 seconds. While a pause runs, the kubelet's next sync of the Pod skips the pull and the reason reads ImagePullBackOff. That is true of the first pause too. So ImagePullBackOff means the kubelet is waiting before its next attempt, and it will keep trying.

The kubelet keeps one back-off timer for each Pod and image pair. Its key is the Pod's UID joined to the image name. A second Pod with the same broken image has its own timer. A Pod deleted and made again by its controller has a new UID, so it starts again at 10 seconds.

During a pause the kubelet records an event of type Normal with the reason BackOff and the message Back-off pulling image followed by the name. The container's waiting message adds the last error after it, so the cause stays visible while the reason says BackOff.

Here the attempts fall at about 0, 10 and 30 seconds. Someone creates the missing Secret at 15 seconds. Nothing happens then, because the second pause still has 15 seconds to run. The same two reasons appear for a tag that does not exist and for a registry that is rate limiting. The registry's error body names the case. It is JSON with a list named errors, and each entry has a code of upper case letters and underscores, with an optional message and detail. Two other reasons come from the runtime's own text. An error that starts with RegistryUnavailable or SignatureValidationFailed becomes that reason instead of ErrImagePull.

Chapter 5 of 13

Where the credentials come from

The kubelet collects them and containerd presents them

A private registry wants to know who is asking, and the kubelet can learn that in several ways. The Pod can list Secrets under imagePullSecrets. They must be in the Pod's own namespace and of the type kubernetes.io/dockerconfigjson, or the older kubernetes.io/dockercfg. A ServiceAccount can carry the same list, and Pods that use it inherit the list. A node can hold a registry login in its own configuration, and then every Pod on that node can use it. Or the kubelet can run a credential provider.

A credential provider is a small plugin program that fetches short-lived credentials when a pull needs them. The kubelet finds it through two flags, --image-credential-provider-config and --image-credential-provider-bin-dir. The configuration, of kind CredentialProviderConfig, lists each provider with matchImages, the image patterns it serves, and defaultCacheDuration, how long its answer may be reused. The feature is stable since v1.26. Static Pods, which the kubelet runs from files, cannot refer to Secrets at all, so for them a provider or a pre-pulled image is the way.

The kubelet matches a Secret's entries more loosely than Docker does. A key can be a glob, so *.kubernetes.io matches abc.kubernetes.io and does not match kubernetes.io itself. A key can carry a path, so registry.northlight.example/vllm would match every image under that path. If several entries match, the kubelet tries them one after the other until one works.

At 30 seconds the back-off ends. The kubelet reads the Secret, finds the entry that matches the registry's host, and puts it in the auth part of PullImage.

One gap remains. With IfNotPresent, a Pod with no credentials could use an image another Pod pulled with credentials. The feature KubeletEnsureSecretPulledImages, beta and on by default from v1.35, closes it. The kubelet setting imagePullCredentialsVerificationPolicy chooses how strict it is: NeverVerify, NeverVerifyPreloadedImages (the default), NeverVerifyAllowlistedImages or AlwaysVerify. The Images page on kubernetes.io prints the third with a capital L. The kubelet's own constant has a lower-case l, so write it that way in the configuration.

Chapter 6 of 13

A password buys a token

The registry never sees the password, only a short-lived token

containerd now has a username and a password. It does not send them to the registry. It follows the token scheme that the 401 described.

The WWW-Authenticate header named three things. realm is the address of a token service. service names the registry the token is for. scope names what is asked: the repository vllm/vllm-openai and the action pull. Because it holds a username and a password, containerd first sends a POST to the realm. Its body is an OAuth2 form with grant_type=password, client_id=containerd-client, the username, the password, service and scope. Some token services do not accept that POST. When the answer is 404, 401 or 400, or 405 with a username set, containerd falls back to a GET to the realm with service and scope as query parameters and the login in a Basic Authorization header. With no credentials at all it would send that GET without a login. Either way the password goes to the token service alone.

The token service checks the login and what that user may do. It answers with JSON that holds a token, under the name token or access_token, with expires_in in seconds and issued_at. If expires_in is left out, the token is good for 60 seconds. The token only allows what the scope said, pull on one repository.

containerd then repeats its request to the registry with the header Authorization: Bearer and the token. The registry checks the token's signature and scope and answers. A pull of ten gigabytes can take longer than a token lives, and a client then fetches a new one the same way.

This split is why a registry can sit behind one company login system while the registry itself stores no passwords. Docker Hub works this way. Its realm is https://auth.docker.io/token and its service is registry.docker.io. In this lesson the realm is the private registry's own token endpoint. A login that the token service rejects ends the pull there, and the Pod shows ErrImagePull as before.

Chapter 7 of 13

One manifest, then one request for each layer

The registry is an HTTP server and every object has a hash for a name

The registry's API comes from the OCI distribution specification. For a pull it has only two endpoints: /v2/<name>/manifests/<tag or digest> and /v2/<name>/blobs/<digest>, each answering GET or HEAD with 200 when the object exists, 404 when it does not, and 401 when a token is needed first, as the earlier chapters showed. A GET of /v2/ alone tells a client whether the server speaks this API at all.

A pull begins with HEAD /v2/vllm/vllm-openai/manifests/v0.33.0, now with the token. The answer is headers only: the digest the tag points to, in Docker-Content-Digest, and a media type in Content-Type. The client says which manifest types it understands with an Accept header, and the registry says which it returned. If the manifest's own mediaType field disagrees with Content-Type, the client should reject it.

containerd then sends a GET for that digest. The answer here is an image index, a short list with one entry for each platform. Each entry's platform names architecture and os, and may add a variant. containerd picks linux/amd64 and fetches that entry by its digest. This third answer is the manifest. It names one config blob and the layers in order, each with a media type, a digest and a size. The base layer must be at index 0 and the rest follow in stack order. Layers are tar archives, plain, gzip compressed or zstd compressed, each with its own media type.

A blob is any stored file whose name is the hash of its bytes. containerd then sends one GET /v2/vllm/vllm-openai/blobs/<digest> for each layer, three at a time by default. It hashes the bytes as they arrive and keeps a blob only if the hash matches its name. A registry should support HTTP Range requests, so a client can resume a broken download from the bytes it already holds. Five layers, 10.6 GB, 53 seconds at 0.2 GB each second.

Chapter 8 of 13

The config blob and the second hash

One layer has two digests, and a stack of layers has a third name

One blob in the manifest is not a layer. The config blob, here sha256:0d17…b9e4, is a small JSON document about the image as a whole. It records the architecture and the os, both required, the creation date, and the settings a container starts with: the entrypoint, the default arguments, the environment, the working directory and the user. containerd merges these with the Pod's own fields when it writes the container's runtime specification. A Pod's command replaces the entrypoint, and its args replace the default arguments.

The config also lists the layers again, under rootfs.diff_ids, and these hashes are different. The manifest's digest is the hash of a layer as stored, which is compressed. A DiffID is the hash of the same layer's uncompressed tar. The image specification warns readers not to confuse the two. containerd records the link between them as a label on each layer blob, containerd.io/uncompressed with the DiffID as its value. Its documentation shows the check by hand: decompress the blob and hash it, and the result must equal the label.

The unpacked filesystem needs a third kind of name, because a layer only has a meaning on top of the layers beneath it. A ChainID names a whole stack. The ChainID of the base layer is its DiffID. Each further ChainID is the hash of the previous ChainID, a space and the next layer's DiffID. So two images share an unpacked layer on the node only if every layer below it is identical too. Two vLLM images that share the same CUDA base share those snapshots. Two images with the same PyTorch layer on different bases do not, even though the blob on disk is shared.

Chapter 9 of 13

Blobs become a filesystem

Each layer is unpacked into a snapshot and overlayfs stacks them

A layer blob is a gzip compressed tar archive of file changes. Nothing can run from it. containerd unpacks the layers in the manifest's order. For each one, a component called a snapshotter prepares a directory on top of the previous layer's, the tar is extracted into it, and the result is committed as a read-only snapshot. The default snapshotter is overlayfs, named after the Linux filesystem that shows several directories as one.

A layer is applied, which is more than extracted. Where an entry's path already exists below, and is not a directory on both sides, the old path is removed and made again from the entry. A file removed by a later layer is recorded as a whiteout, an empty file whose name starts with .wh. and hides the file below. A whiteout only applies to layers below it, and it is hidden itself once applied, so no real file can have a name starting with .wh. A whole directory's old contents are hidden by one opaque whiteout, a file named .wh..wh..opq inside it.

Those tar entries are not what lands on disk. The overlayfs snapshotter converts them while it applies the layer. A .wh.<name> entry becomes a character device with the device number 0/0 at <name>. An opaque whiteout becomes the extended attribute trusted.overlay.opaque set to y on its directory. Those are the forms overlayfs itself reads, and the lesson What a container is made of shows them from the kernel's side.

When the last snapshot is committed, PullImage returns. With containerd's default, discard_unpacked_layers false, the compressed blobs stay in the content store after unpacking. The node holds the image twice.

Since containerd v2.1, the CRI plugin pulls through containerd's Transfer Service by default. The older path is chosen with use_local_image_pull = true. In the newer path max_concurrent_downloads is set in the transfer plugin's section, and discard_unpacked_layers is not supported. containerd 2.1 falls back to the older path by itself, with a warning, when it finds settings only the older path understands. To start the container, containerd adds one empty writable snapshot on top and mounts the stack as the root filesystem. Nothing is copied, so the start takes about 2 seconds.

Chapter 10 of 13

One pull at a time on a node

A ten gigabyte pull holds up every other image on the node

While qwen3-58b4d7f9c6-p2w4n's image was downloading, a second Pod was scheduled to gpu-node-1: a small embedding server with an image of its own. Its kubelet sync ran, found its image missing and asked for a pull. It got none for a while.

By default the kubelet sends only one image pull request to the image service at a time. That is serializeImagePulls, true by default. Other requests wait in a queue inside the kubelet, a channel with room for 10 requests. An eleventh request is not refused. The sync that asked for it waits until there is room. So the small image waited behind the big one. Its Pulled event shows this. The message carries two durations: the first is the pull itself, the second includes the time spent waiting. For the embedding server it read in 6s (1m4s including waiting).

The kubelet can pull in parallel. Set serializeImagePulls to false, and maxParallelImagePulls caps how many run at once. Its default is no limit. The kubelet refuses to start if the value is below 1, or above 1 while pulls are serialized. Even then the kubelet never pulls several images in parallel for one Pod. Two more settings limit the rate. registryPullQPS is the number of pulls each second the kubelet allows, 5 by default, with 0 meaning no limit. registryBurst lets 10 go at once.

The kubelet also measures pulls. kubelet_image_pull_duration_seconds is a histogram labelled by image size, in bands such as 1GB-5GB, 5GB-10GB and 10GB-20GB, up to GT100GB. Its time buckets run from 1 second to 3600. The value includes waiting. A dashboard of that metric for GPU nodes shows at once whether cold starts are spent on the network or in the queue.

Chapter 11 of 13

The image was the short part

The weights are not in the image, and loading them takes longer than the pull

The vLLM process is running and cannot answer one request. The image holds the server and its libraries. It does not hold the model. The weights usually stay out of the image. One image can then serve any model, and a new vLLM version does not move the weights again. Inside a layer they would also sit on the node's disk twice. Qwen3-32B has 32.8 billion parameters, and the official FP8 build this site serves, Qwen3-32B-FP8, is 34.3 GB of files. The full-precision BF16 build would be 65.5 GB. The server reads the FP8 files when it starts, from object storage or from a mounted volume, and that takes about three minutes.

Now add it up. On a node without the image: 90 seconds of image pull, 2 to start, 180 to load, so 272 seconds. On a node that has the image: 2 plus 180, so 182 seconds. Holding the image saves the pull and nothing more. This Pod took 302 seconds, because 30 more went to the missing Secret.

Kubernetes has a newer way to ship weights as OCI content without baking them into the server's image. A Pod can mount an image as a volume, with volumes[].image naming a reference. The volume is read-only. The weights can then be pushed to the same registry as an artifact of their own, versioned by digest, and pulled with the same credentials and the same caching as any image. The feature gate ImageVolume was alpha in 1.31 and 1.32, beta and off in 1.33 and 1.34, beta and on in 1.35, and stable from 1.36. It does not make loading faster by itself. The 34.3 GB of the FP8 build still have to arrive and be read into the GPU.

A replacement Pod that lands on gpu-node-1 later finds the image there and starts without a single request to the registry.

Chapter 12 of 13

Mirrors, rate limits and where the bytes come from

A file per registry decides which hosts containerd tries first

The private registry in this story is one choice. Many clusters also pull from Docker Hub, and Docker Hub limits pulls. Its documentation gives 100 pulls every 6 hours for unauthenticated users, counted per IPv4 address or per IPv6 /64 subnet, and 200 for a signed-in personal account. Paid plans have no limit. Over the limit, Docker Hub answers 429 Too Many Requests when the manifest is requested. Its answers carry headers that show the state, ratelimit-limit and ratelimit-remaining, each with a window of 21600 seconds, which is 6 hours. A whole node pool behind one NAT address shares one unauthenticated limit. A rollout of 120 Pods that each pull a public image can use it up.

A mirror solves both the limit and the distance. containerd reads per-registry settings from a directory when config_path is set to /etc/containerd/certs.d. Each registry gets a folder named after its host with a file hosts.toml inside. A folder named _default applies to every registry that has none of its own. In the file, server names the upstream, and each host entry lists its capabilities: pull, resolve and push. A mirror trusted only to pull cannot turn a tag into a digest, so tags are still resolved upstream. containerd tries the listed hosts in order and falls back to the upstream registry after all of them. The same file is where a private certificate authority is named. The older mirrors settings in containerd's CRI configuration are deprecated.

Docker Hub's name and its API host differ. containerd's example for docker.io sets server to https://docker.io and the host to https://registry-1.docker.io. When a pull goes through a proxy, the specification says the Host header names the proxy, and the proxy may use an ns query parameter to learn which upstream registry the image came from.

Chapter 13 of 13

The image stays until the disk fills

The kubelet deletes the least recently used images, and the next Pod pays again

The vLLM image now occupies about 10.6 GB compressed in the content store and more again unpacked. It stays after its Pod is gone. The kubelet decides when images are removed, on a check that runs every 5 minutes.

Two thresholds govern it. imageGCHighThresholdPercent, 85 by default, is the disk use above which garbage collection always runs. imageGCLowThresholdPercent, 80 by default, is the level it cleans down to. Above the high mark, the kubelet deletes images that no container uses, starting with the one used longest ago, until use falls to the low mark. imageMinimumGCAge, 2 minutes by default, protects an image that was only just pulled. imageMaximumGCAge removes images unused for longer than its value regardless of disk use. It defaults to 0s, which turns it off, and it forgets its tracking when the kubelet restarts. The pause image is pinned and is never chosen.

On a GPU node this matters more than on most. An unused ten gigabyte vLLM image is the first candidate when the disk fills. The next model server that lands there pays the full 90 second pull again, and the cold start goes from 182 seconds back to 272. Sizing the disk well and setting the thresholds is cheaper than a slow restart.

The kubelet records what happened. The metric kubelet_image_garbage_collected_total counts removals, labelled by whether disk use or image age was the reason. The events ImageGCFailed and FreeDiskSpaceFailed tell an operator it could not free enough. The node's status lists its images in status.images, capped at 50 entries by nodeStatusMaxImages.

What to keep

A name, a manifest, some blobs, and then the model

An image reference names a registry, a repository and a tag or digest. The kubelet decides whether to pull from imagePullPolicy, gathers credentials and makes one CRI call. containerd does the rest: it trades the login for a short-lived token, makes three requests to reach the manifest and one for each layer blob, checks a hash on each, reads the config and its uncompressed hashes, and unpacks the layers into stacked snapshots that overlayfs presents as one filesystem. When a pull fails the Pod shows ErrImagePull, then ImagePullBackOff while the kubelet waits up to 300 seconds between attempts, on a timer kept for each Pod. On a node, pulls run one at a time by default, so a ten gigabyte image delays every other. Mirrors and hosts.toml decide where the bytes come from, and the kubelet's garbage collection decides how long they stay. A node that already has the layers starts a container in seconds. A model server is the exception to that comfort, because its largest part is the weights and they load after the container starts.
