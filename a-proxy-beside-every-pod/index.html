Kubernetes underneath

A proxy beside every Pod

How a service mesh decides who may call a service

Inside a cluster, any Pod that can reach 10.244.2.17:8080 can send requests to the Pod web-2, and web-2 knows its caller only by an IP address that will belong to another Pod tomorrow. For a model server on a GPU, which is expensive to run and easy to misuse, that is too little. A service mesh changes what a caller is. It puts a proxy beside every application, sends all of the application's traffic through it, and gives each proxy a certificate that names the workload. This lesson uses Istio. It follows one request from the Pod client to web-2, a Pod of the Service web: how the proxy got into the Pod, how probes and start-up are changed by it, how it learned its configuration, what it can read of a connection, how the two proxies prove who they are, how a rule about callers is written and checked, what happens to open connections when the Pod stops, and what all of it costs. It ends with ambient mode, which does the same work without a proxy in each Pod.

Chapter 1 of 13

A Pod gains two containers on its way in

The API server asks istiod before it stores the Pod

Istio's control plane is one program, istiod. It registers a mutating admission webhook with the API server. A webhook of that kind is a service the API server calls before it stores an object, and the service may change the object. The registration is a MutatingWebhookConfiguration named istio-sidecar-injector. Its entry namespace.sidecar-injector.istio.io sends each new Pod to istiod's Service on port 443, path /inject, with a 10 second timeout. Port 443 on that Service is forwarded to port 15017 on the istiod container.

You opt in by namespace, with the label istio-injection=enabled. The full rule has three steps. If the namespace label istio-injection or the Pod label sidecar.istio.io/inject says disabled, the Pod is left alone. If either says enabled, or the namespace names a control plane revision with istio.io/rev, the Pod is injected. With no label at all the Pod is left alone, because the install setting enableNamespacesByDefault is off by default. When a namespace carries both istio-injection and istio.io/rev, istio-injection wins.

The Deployment web asks for a Pod with one container, web. istiod fills in a template kept in the ConfigMap istio-sidecar-injector in the namespace istio-system and returns a patch that adds two more. istio-init is an init container: it runs once before the others, sets up the Pod's network and exits. istio-proxy is the sidecar: an Envoy proxy with a small agent, running beside the application for the life of the Pod. Where it goes in the Pod depends on the version. Since Istio 1.27 the setting ENABLE_NATIVE_SIDECARS is on by default for eligible Pods, and the upgrade notes say this changes istio-proxy from a container to an init container. It is then a Kubernetes native sidecar: an entry in initContainers with restartPolicy Always, which keeps running after it starts. In the current source the setting's default is auto, which turns it on when the kubelet of the Pod's node, or of every node if the Pod has none yet, is version 1.33 or later. With the setting off, on Istio 1.26 and earlier, or on older nodes, istio-proxy is a second ordinary container next to web. The Deployment mentions neither. istioctl kube-inject -f applies the same template to a file by hand, which is a quick way to read the patch.

The webhook is in the path of every Pod that is created. If istiod cannot be reached, injection fails and the Pod is not created at all. For a model server that means an istiod outage blocks every restart and every scale up in the namespace.

Chapter 2 of 13

Rules inside the Pod send traffic to the proxy

The application listens on 8080 and never learns about ports 15001 and 15006

The application knows nothing about the proxy, so something has to put the proxy in the path. That is the job of istio-init. A Pod has its own network namespace, a private copy of the network stack with its own interfaces and its own iptables rules. istio-init writes rules into the NAT table of that namespace and exits. TCP connections that the application opens are redirected to port 15001, where Envoy listens for outbound traffic. TCP connections that arrive from outside are redirected to port 15006, where Envoy listens for inbound traffic. The same rules are written in the client's Pod.

One exception prevents a loop. Envoy runs as user ID 1337, and traffic from that user leaves the Pod untouched. The source adds the same exemption for the proxy's group ID, and notes that the user rule covers every protocol so that no packet from Envoy is ever sent back to Envoy. A few cases on the loopback interface are handled with care. An application calling its own Pod address over loopback is left alone. When the proxy sends a call back into its own Pod through a Service address, the call is sent through the inbound path, so it is treated like any other caller.

Only TCP is proxied. UDP and other protocols pass through as before. DNS is not captured unless the agent option ISTIO_META_DNS_CAPTURE is set, in which case UDP port 53 is redirected to the agent's DNS listener on port 15053. Pods can opt ports out with annotations. traffic.sidecar.istio.io/excludeOutboundPorts lists outbound ports to leave alone, for example a port a model server uses to fetch weights from storage. Istio's port table lists the ones the sidecar uses: 15000, 15001, 15002, 15004, 15006, 15008, 15020, 15021, 15053 and 15090. Istio's application requirements say applications should not use any of the ports Envoy uses, to avoid conflicts. That is a list of ports, and the numbers between them are not reserved.

Chapter 3 of 13

Probes and start-up change too

The kubelet has no certificate, so its probes go through the agent

The kubelet checks a container's health with probes. An HTTP probe sends a request to a port. A TCP probe only checks that something is listening. Both have a problem in a mesh. With mutual TLS required, the kubelet's plain request would be refused, since the kubelet holds no Istio certificate. And a TCP probe would always pass, because the redirect rules send every incoming connection to Envoy, so every port looks open as long as the sidecar runs.

Istio fixes both at injection time. It rewrites the HTTP, TCP and gRPC probes in the Pod so that they point at the Istio agent on port 15020, at a path of the form /app-health/<container>/livez or readyz. The original probe is kept as JSON in an environment variable of the sidecar. When the kubelet probes 15020, the agent performs the original check against the application itself, outside the redirection, and returns only the status code, dropping the body. exec probes run a command in the container and need no change. A Pod can opt out with the annotation sidecar.istio.io/rewriteAppHTTPProbers set to "false".

Start-up order is the other trap, and how it is handled depends on how the sidecar was injected. As a native sidecar, the default since Istio 1.27 on nodes whose kubelet is 1.33 or later, istio-proxy is an init container, and the kubelet starts the next container only once a sidecar has started. Istio gives the sidecar a startup probe on port 15021 at /healthz/ready, checked every second with up to 600 failures, which is ten minutes. So web starts only after the proxy reports ready, with no setting needed.

With native sidecars off, istio-proxy is an ordinary container, and the application can start before the proxy is ready. Its first outbound calls then fail. For a model server whose first act is to fetch weights or register itself, that is a failed start. The setting holdApplicationUntilProxyStarts, false by default, fixes this case. It puts the sidecar first in the container list and adds a postStart hook, pilot-agent wait, that holds the other containers back until the proxy is ready. It can be set for the whole mesh, or for one Pod with the annotation proxy.istio.io/config. Istio's injection template ignores it when the sidecar is native, because the init container order already does the job.

Chapter 4 of 13

Each proxy gets a name in a certificate

The identity is the Pod's ServiceAccount, signed by istiod

Before it carries traffic, the proxy needs a way to prove which workload it stands for. Istio takes that identity from the Pod's Kubernetes ServiceAccount and writes it as a SPIFFE ID, a URI of the form spiffe://trust-domain/ns/namespace/sa/serviceaccount. The owner's notes put the same idea in one line: when one workload runs in one Deployment, the Deployment is the binding, and the workload identity is the identity of what runs there.

The Istio agent in the sidecar creates a private key and a certificate signing request. It sends the request to istiod together with the Pod's ServiceAccount token. The token must carry the audience istio-ca, the default of istiod's TOKEN_AUDIENCES. istiod acts as the certificate authority. It validates the token and signs a certificate that carries the SPIFFE ID in its Subject Alternative Name, with the uses TLS Web Server Authentication and TLS Web Client Authentication, so the same certificate serves both ends of a connection. The agent hands the certificate and key to Envoy over a local API called the secret discovery service. The private key never leaves the Pod.

The agent asks for 24 hours, its SECRET_TTL. It renews at about half the lifetime, the ratio SECRET_GRACE_PERIOD_RATIO 0.5, moved up or down by 0.01 so that thousands of proxies do not all renew in the same minute. One hundredth of 24 hours is 14.4 minutes. When istiod generates its own root, that root lasts ten years and is checked every hour.

Chapter 5 of 13

istiod pushes the map to every proxy

Four kinds of configuration over one stream called xDS

An Envoy proxy starts empty. It opens a gRPC stream to istiod on port 15012 and keeps it open. istiod watches the API server for Services, their endpoints and Istio's own objects, converts them into Envoy configuration and sends it down that stream. The protocol is xDS, a family of discovery services. Listeners say which ports to accept and what to do with a connection. Routes match an HTTP request, by host and path, to a destination. Clusters are the destinations, one for each Service port. Endpoints are the Pod addresses behind each cluster. No request ever passes through istiod. It only describes the network to the proxies that carry the traffic.

The listener on port 15001 is called virtualOutbound. It accepts everything the rules redirect and hands each connection to a more specific listener: one on 0.0.0.0 for each HTTP port, and one for each Service address for plain TCP. Traffic to a destination the mesh does not know falls through to PassthroughCluster.

istiod does not push on every change at once. It waits at least PILOT_DEBOUNCE_AFTER, 100 ms by default, for more changes to arrive, and keeps waiting while they do, up to PILOT_DEBOUNCE_MAX, 10 seconds. So a new endpoint reaches a proxy after at least 100 ms plus the push itself. The metric pilot_proxy_convergence_time measures that delay. By default every proxy is told about every workload in the mesh. In a large cluster that costs proxy memory, and the Sidecar resource limits what each proxy receives.

Chapter 6 of 13

What the proxy can read decides what rules can do

A port named http gets HTTP routing and HTTP rules. Anything else is bytes

Envoy can route by URL and check a method or a path only if it knows the connection carries HTTP. Istio learns the protocol of a Service port in one of two ways. The port's name can start with the protocol, in the form protocol-suffix, such as http or http-web. Or the port can set appProtocol. If both are present, appProtocol wins. Values include http, http2, https, tcp, tls, grpc and grpc-web. With neither, Istio tries to detect HTTP and HTTP/2 from the first bytes, and treats anything else as plain TCP. Here the Service web names its port http.

The protocol changes routing. For HTTP, Istio routes by the Host header, so a request to any address with Host web.inference is sent to the Service web. For plain TCP, it routes by the destination Service address. A direct call to a Pod address on a TCP port is not matched to any Service, and passes through without mTLS, routing or telemetry.

It also changes policy, and silently. On a port treated as TCP, HTTP-only fields in an authorization rule cannot be checked. In an ALLOW policy they never match, so the request is denied. In a DENY or CUSTOM policy they always match, so the policy is broader than you wrote. The documentation's remedy is to name the port with the http prefix. The lesson's rule about GET /api/orders works only because the port is named http. Some protocols send the first bytes from the server, such as MySQL on 3306 or SMTP on 25. Detection and the PERMISSIVE mode both read the first bytes, so these ports are treated as TCP.

Chapter 7 of 13

The two proxies prove who they are

Mutual TLS: both sides show a certificate

Sixty seconds in, the client calls web. It opens a TCP connection to the Service name web.inference.svc.cluster.local on port 80 and sends plain HTTP. The rules in its Pod hand the connection to its own proxy on port 15001. That proxy matches the request to a route, picks one of the two endpoints itself and opens a connection straight to the Pod web-2, 10.244.2.17 port 8080. On that connection the proxies run a TLS handshake in which both sides present a certificate. This is mutual TLS, or mTLS. The client's proxy checks that the server's identity is one allowed to run the Service web, a check Istio calls secure naming. The server's proxy learns the caller's SPIFFE ID. Everything between the two Pods is now encrypted.

Nobody told the client's proxy to use mTLS. Istio calls this auto mTLS. When no DestinationRule sets TLS for a destination, the proxy decides on its own whether the other end can take Istio mTLS, and between two sidecars it always can. The MeshConfig field enableAutoMtls is true by default. If it was turned off at install, a DestinationRule without TLS settings makes the client send plain HTTP to a server that expects TLS, and callers get 503 until the rule sets trafficPolicy.tls.mode ISTIO_MUTUAL.

The TLS settings between sidecars are fixed by Istio. The minimum version is TLS 1.2 on both sides. The cipher suites are ECDHE-ECDSA and ECDHE-RSA with AES-256-GCM and SHA-384 or AES-128-GCM and SHA-256, plus AES256-GCM-SHA384 and AES128-GCM-SHA256.

Chapter 8 of 13

What the application sees and what it costs

Plain HTTP on port 8080, and two extra proxies on every request

The encrypted connection arrives at the Pod web-2 for port 8080. The rules there redirect it to Envoy on port 15006. Envoy ends the TLS session and passes the request to the application as plain HTTP. The application sees an ordinary request. The one trace of the mesh is a header, X-Forwarded-Client-Cert, that carries the caller's identity. When a server has no sidecar, that header is missing, which is the documentation's own way to tell that a request arrived in plain text. Neither application holds a certificate or links a TLS library for this.

The price is that every request now crosses two proxies it did not cross before, one in each Pod, in both directions. Each sidecar also uses CPU and memory. Istio's benchmark for version 1.24 measured about 0.20 vCPU and 60 MB for one sidecar handling 1000 requests a second, with 2 worker threads and a 1 KB payload. The number of worker threads is the ProxyConfig setting concurrency. Left unset, it follows the container's CPU request or limit. Set to 0, it uses every core of the machine, and with a CPU limit in place that can make the proxy much slower. Proxy memory also grows with the number of listeners, clusters and routes it is told about. Beside a model server on a GPU these costs are small, and it is still a second container to run and upgrade in every Pod.

Each proxy reports standard metrics. istio_requests_total counts every request it handles, with labels such as source_principal, the caller's identity, response_code and connection_security_policy. istio_request_duration_milliseconds records how long each took. Together they count, per caller identity, how many requests were mutual TLS and how many were refused.

Chapter 9 of 13

Who may call web

A rule about identities, enforced by the server's own proxy

So far the mesh encrypts and identifies, and it refuses nobody. Two objects change that. A PeerAuthentication with mode STRICT makes the proxies of the web Pods accept only mutual TLS. There are four modes. UNSET inherits from the parent, or else acts as PERMISSIVE. DISABLE turns mutual TLS off, so the connection is plain text. PERMISSIVE accepts plain text and mTLS, so that workloads can join the mesh one at a time. STRICT accepts only mTLS. A portLevelMtls map can set a different mode for one port. When several apply, the narrowest wins: a policy for the workload, then one for the namespace, then the mesh-wide one in the root namespace. There may be one mesh-wide policy and one per namespace. If more exist, the newer ones are ignored. Change modes through PERMISSIVE, because proxies do not all receive a new policy at the same moment.

An AuthorizationPolicy then says which identities may do what. This one selects the web Pods and allows the ServiceAccount client in namespace inference to GET /api/orders. The trigger for deny by default is precise. It applies only when the workload has at least one ALLOW policy. From then on, a request that matches none of them is denied. Several policies on one workload add up. The documented way to start is an allow-nothing policy, an ALLOW policy with no rules, and then add ALLOW policies one at a time.

Identity fields such as principals and namespaces need mutual TLS, and the documentation strongly recommends STRICT with them. In PERMISSIVE mode a plain text request has no identity to check. istiod pushes both objects to the proxies in the web Pods, and each proxy enforces them before the application sees anything. The rule never mentions an address, so it holds when Pods move.

Chapter 10 of 13

Watching one decision

Turn up the proxy's RBAC log, then read the access log

Proxies enforce policies eventually, so the first question when a caller is refused is whether the proxy has the policy at all and what it decided. The proxy can be asked to log every authorization decision. istioctl proxy-config log deploy/web --level rbac:debug raises the log level of Envoy's RBAC filter in the web Pods. Then kubectl logs on the istio-proxy container shows one line per request. An allowed request logs enforced allowed. A refused one logs enforced denied, and when a policy matched, it is named in the form ns[inference]-policy[name]-rule[0]. A policy can be tried first in dry run, and then the log shows shadow denied for what it would have refused, without refusing it.

The access log tells you what happened to the request after that. The documentation calls it the best way to understand why requests are rejected. It is switched on with the Telemetry API or with meshConfig.accessLogFile set to /dev/stdout, and each line starts with the time, the method, the path, the protocol, the response code and the response flags. Three flags come up most. NR means no route was configured for the request. UO means the upstream overflowed and a circuit breaker turned it away. UF means the proxy failed to connect to the upstream, and with Istio authentication the documentation says to check for a mutual TLS conflict first.

For a model server, these two logs separate the three common cases cleanly: a caller with the wrong identity gets 403 from RBAC, a caller with no certificate never reaches HTTP at all, and a client proxy sending plain text to a STRICT server shows UF or 503.

Chapter 11 of 13

When the Pod stops, the proxy stops too

As a native sidecar it stops last. As an ordinary container it drains for 5 seconds

The Istio agent in the sidecar handles TERM in its own way. It tells Envoy to start draining, which discourages new connections and lets existing ones complete. Then it sleeps for terminationDrainDuration and kills whatever Envoy processes remain. If the setting is not given, the sleep is 5 seconds. When that TERM arrives depends on how the sidecar was injected.

As a native sidecar, the default since Istio 1.27 on nodes whose kubelet is 1.33 or later, istio-proxy is an init container with restartPolicy Always. Kubernetes postpones stopping sidecar containers until the main containers have fully stopped, and then stops them in the reverse of their order in the Pod. Istio's template also gives the native sidecar a preStop hook, pilot-agent request POST drain, which asks the agent to start draining. The template's own comment says the hook runs when the Pod starts to shut down, and that the proxy gets TERM once the applications are torn down. Say web were a model server streaming a 60 second answer, with a Pod grace period of 90 seconds sized for it. web gets TERM first. The proxy is still running, so the 5 second clock has not started, and the answer can finish at 60 seconds. Only then does istio-proxy get TERM, sleep its 5 seconds and exit, at about 65 seconds, inside the 90. How Envoy's early drain treats a stream that is already open was not confirmed here. The one limit is the shared deadline. The Kubernetes page on sidecars warns that when the main containers use up the whole grace period, a sidecar gets TERM and KILL almost together.

With native sidecars off, as on Istio 1.26 and earlier, on older nodes, or with the Pod annotation sidecar.istio.io/nativeSidecar set to "false", istio-proxy is an ordinary container. Then every container gets TERM at about the same time, the sidecar included, with no order between them. The same 60 second answer goes wrong. The application may keep streaming for the whole minute, but its traffic leaves the Pod through Envoy. Five seconds after TERM, Envoy is gone and the stream is cut. The grace period of the Pod did not help, because the proxy has its own, shorter clock. This follows from the documented behaviour, and it is the reason to check how the sidecar was injected whenever a mesh carries streamed model answers.

Two settings fix the second case. terminationDrainDuration can be raised for the Pod, through the annotation proxy.istio.io/config, to cover the longest answer. Or the agent option EXIT_ON_ZERO_ACTIVE_CONNECTIONS, false by default, makes the proxy exit as soon as its active connections drop to zero during the drain, after a minimum of MINIMUM_DRAIN_DURATION, also 5 seconds. Either way the Pod's terminationGracePeriodSeconds must be longer still, because the kubelet kills everything when it runs out.

Chapter 12 of 13

Ambient mode: the mesh without sidecars

One ztunnel on each node, and the tunnel still starts inside the Pod

A sidecar in every Pod means restarting Pods to add or upgrade it. For a model server that takes three minutes to load the 34.3 GB of weights in its FP8 build, Qwen3-32B-FP8, a restart is not free. Istio's ambient mode moves the proxy out of the Pod. istiod must have ambient support switched on with PILOT_ENABLE_AMBIENT. You label the namespace istio.io/dataplane-mode=ambient and running Pods join without a restart. Each node runs one ztunnel, a small proxy written in Rust.

Enrolment works like this. The istio-cni agent on the node enters the Pod's network namespace and writes redirect rules there, in chains named ISTIO_PRERT and ISTIO_OUTPUT. It then tells ztunnel over a Unix domain socket to open listening ports inside that namespace, and hands it a file descriptor for the namespace. ztunnel starts a separate logical proxy for that Pod within its one process, listening on 15001, 15006 and 15008. The Pod gets the annotation ambient.istio.io/redirection to show it is enrolled, and the ztunnel log says received netns, starting proxy.

Between Pods, ztunnels carry connections in HBONE, an HTTP/2 CONNECT tunnel inside mutual TLS on port 15008. The drawings show the tunnel between two ztunnels, and the documentation is careful to say that it really starts and ends inside the two Pods' network namespaces. Traffic between two Pods on the same node also passes through ztunnel. The identities are the same SPIFFE IDs, one for each ServiceAccount, and the owner's notes record that agent platforms already use exactly this to give each agent Deployment its identity. By default a Pod accepts both HBONE and plain text. Plain text arrives with no identity, so a policy that requires any identity blocks it.

Chapter 13 of 13

ztunnel's rules and the waypoint

HTTP rules on ztunnel fail in two directions. A waypoint reads HTTP

ztunnel enforces AuthorizationPolicy at the level of connections. When a policy names HTTP attributes such as methods or paths, ztunnel cannot check them, and what it does instead depends on the action. The documentation gives a table. An ALLOW rule with HTTP attributes is skipped, so no ALLOW rule ever matches and traffic is denied. A DENY rule with only HTTP attributes is skipped, so it never matches and traffic is allowed. A DENY rule that mixes connection and HTTP attributes in the same entry enforces only the connection part, so it denies more than intended. A DENY rule with the two kinds in different entries is skipped, and traffic is allowed. Two of the four rows fail open. A DENY rule meant to block a path on a model server, written for a sidecar and moved to ambient, blocks nothing.

The answer is a waypoint, an Envoy proxy that runs as its own Deployment and reads HTTP. istioctl waypoint apply -n inference creates one as a Gateway with the class istio-waypoint, listening on 15008 for HBONE. The label istio.io/use-waypoint on a namespace, Service or Pod tells ztunnels to send traffic for it through the waypoint. Waypoints receive only HBONE.

Only ambient callers use the waypoint. A caller outside the mesh knows nothing of waypoints and goes straight to the destination. The ambient data plane page says traffic from sidecars also skips the waypoint today. Traffic from an Istio ingress gateway skips it by default too, but it can opt in. The label istio.io/ingress-use-waypoint=true on the Service, or on its namespace, sends ingress traffic through the same waypoint, so the request is processed at Layer 7 twice, at the gateway and at the waypoint. The waypoint page calls this a two-tier gateway pattern. A policy for a waypoint must be attached with targetRefs, and one that uses selector is ignored by the waypoint. Benchmarked for 1.24 at 1000 requests a second, a ztunnel used about 0.06 vCPU and 12 MB, a waypoint about 0.25 vCPU and 60 MB.

What to keep

An identity that travels with the workload

A service mesh has two parts. Proxies carry every call, so they can encrypt it and attach a proven identity to it. A control plane, istiod, injects those proxies, rewrites their probes, signs their certificates and pushes their configuration after a short debounce, and it stays out of the traffic. For a model server this turns the question of who may send prompts into a rule about ServiceAccounts, checked from a certificate that lasts one day. That rule works only where the proxy can read HTTP, so name ports for their protocol, start in PERMISSIVE and move to STRICT, and read the RBAC and access logs when a call is refused. The applications do not change. In return you run a proxy beside every Pod, which since Istio 1.27 is a native sidecar that stops after the application on 1.33 or later nodes, and which elsewhere has its own 5 second drain that must be raised for long answers, or one ztunnel per node in ambient mode, where HTTP rules need a waypoint and DENY rules on ztunnel can fail open. Either way it is one more system that must be configured correctly.
