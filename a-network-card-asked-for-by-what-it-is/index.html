Kubernetes underneath

A network card, asked for by what it is

How DRA lets a Pod claim an EFA by its attributes, and how to run it on EKS today

On 9 November 2026 AWS announced that EKS Auto Mode and Karpenter support Dynamic Resource Allocation, DRA, for two kinds of device: NVIDIA GPUs and Elastic Fabric Adapter network devices. A LinkedIn post about the launch, the post this lesson answers, put it under the headline Kubernetes can now schedule a network interface like a GPU. That is the post's wording, not AWS's. The launch built on an earlier one. On 22 July 2026 AWS let Auto Mode and Karpenter node pools choose an EC2 placement group, with the cluster, spread or partition strategy, and lay out EFA interfaces as efa-only or as standard interfaces. EFA-only interfaces use no IP address. This lesson takes that sentence apart and puts it back together with the real objects, fields, commands and version numbers.

It starts with how a special network card used to reach a workload: an OpenStack port with vnic-type direct and a flavor that asked for hugepages, then a Kubernetes device plugin that turned SR-IOV virtual functions into a count, and Multus that plugged the second interface into the Pod. It shows what that chain could not say. Then it follows DRA for a network device step by step: the driver publishes ResourceSlices with attributes, a DeviceClass names the kind of card, a ResourceClaim asks with a CEL expression, the scheduler allocates, and the kubelet and driver move the interface into the Pod. A GPU and an EFA on the same PCIe root get their own chapter, because that is where DRA pays for itself.

The second half is practical. It lists what must be true before you start, installs the drivers, teaches Karpenter and Auto Mode to launch a node for a claim, runs a worked example on the site's cluster northlight-eu, reads the claim when something breaks, and moves a workload off the device plugin. The lesson builds on A Pod asks for a GPU, which already explains the device plugin and DRA for GPUs, and does not repeat it.

Chapter 1 of 20

Before Kubernetes, the flavor and the port asked for the card

OpenStack split the request between a port, a flavor and a scheduler filter

Telecom network functions met fast network cards first on OpenStack, so the old request shapes are worth knowing exactly. SR-IOV, single root I/O virtualization, lets one physical network card, the physical function or PF, present many lightweight PCI devices called virtual functions or VFs. An operator creates them by writing a number into sysfs, for example echo '8' > /sys/class/net/eth3/device/sriov_numvfs, and the Neutron SR-IOV agent is told which interface carries which physical network with physical_device_mappings = physnet2:eth3.

The request for a VF lives on a port. A user runs openstack port create --network $net_id --vnic-type direct sriov-port and then boots with openstack server create --flavor m1.large --nic port-id=$port_id. Other vnic types are normal, direct-physical and macvtap. Nova's scheduler only lands that server on a host with a free VF when PciPassthroughFilter is in [filter_scheduler] enabled_filters. A whole PCI device can instead be asked for through the flavor, with pci_passthrough:alias set to an alias such as a1:2, two devices of alias a1.

The OVS-DPDK path asks differently. A DPDK-backed vhost-user interface needs the guest's memory in huge pages, so the flavor carries hw:mem_page_size=large. A telco operator therefore built a flavor per shape of network need. The request named an alias, a physical network and a page size. It never named a property of the card such as its PCIe position relative to another device in the same server.

Chapter 2 of 20

The device plugin turns virtual functions into a count

intel.com/sriov_net_A: 8 on the node, a PCI address in an environment variable

On Kubernetes the same VFs reached Pods through the SR-IOV Network Device Plugin. It is a device plugin, the mechanism A Pod asks for a GPU walks through, so this chapter only adds what is specific to network cards. The plugin discovers SR-IOV VFs, whole PCI physical functions and auxiliary devices such as BlueField subfunctions. It does not create VFs and does not bind drivers. Its README is explicit that VFs are usually created at boot time when the kernel module loads.

An operator writes a ConfigMap with a resourceList. Each entry has a resourceName, an optional resourcePrefix, and selectors: vendors such as 8086 or 15b3, devices such as 154c, drivers such as vfio-pci or iavf, pfNames such as enp2s2f0, rootDevices by PCI address, linkTypes, isRdma and needVhostNet. A pfNames value can pick a range of VFs, so netpf0#0,2-7,9 takes VF 0, VFs 2 to 7 and VF 9. If one device matches two selector objects it goes only to the first.

What Kubernetes then sees is a number. Each pool becomes a resource named prefix/resourceName, so the README's pool intel_sriov_dpdk with prefix intel.com appears as intel.com/intel_sriov_dpdk. The README's sample node output, from a configuration with pools sriov_net_A and sriov_net_B, shows allocatable entries intel.com/sriov_net_A: 8 and intel.com/sriov_net_B: 8 next to hugepages-2Mi: 8Gi. A Pod asks for intel.com/sriov_net_A: 1, and when the kubelet picks a VF the plugin tells the container which one through an environment variable. Its name is PCIDEVICE_ followed by the full resource name in capitals, with dots and slashes turned into underscores, so this Pod would read PCIDEVICE_INTEL_COM_SRIOV_NET_A. The README's own example, for a resource called intel.com/sriov, is PCIDEVICE_INTEL_COM_SRIOV=0000:03:02.1,0000:03:04.3 for two VFs. A JSON variant ending in _INFO lists vfio mounts for DPDK pools. The selectors are rich. They are evaluated once, on the node, when the pool is built. A workload cannot say anything about the device beyond the pool's name. A DPU the host cannot touch showed the same VFs and subfunctions from the card's side.

Chapter 3 of 20

Multus plugs in the second interface

A NetworkAttachmentDefinition per network, named in an annotation

A VF handed to a container through an environment variable is still only a PCI address. Something has to configure it as an interface inside the Pod's network namespace. Kubernetes gives each Pod one network, from the cluster's CNI plugin. Multus is a CNI meta plugin that calls further CNI plugins to attach more interfaces.

Each extra network is a NetworkAttachmentDefinition in the API group k8s.cni.cncf.io/v1. Its spec.config holds a CNI configuration in JSON. A macvlan example sets type macvlan, master eth1, mode bridge and an IPAM range from 10.10.1.20 to 10.10.3.50 in 10.10.0.0/16. The SR-IOV device plugin's own example network, sriov-net1, uses type sriov with host-local IPAM in 10.56.217.0/24 and gateway 10.56.217.1, and carries the annotation k8s.v1.cni.cncf.io/resourceName: intel.com/intel_sriov_netdevice. That pool name comes from the plugin's deployment examples, not from the README pools in the previous chapter. That annotation is the glue. It tells Multus which device plugin resource holds the VF for this network.

A Pod asks for networks with the annotation k8s.v1.cni.cncf.io/networks, as text (macvlan-conf-1, macvlan-conf-2) or as JSON with an interface name. The plugin's test Pod, testpod1, names sriov-net1 and asks for intel.com/intel_sriov_netdevice: 1 in its requests and limits. Inside the Pod, ip -d address shows eth0 from the default network, then one interface per extra network, netN by default (the Multus guide shows net1, net2) or the names asked for. In that example testpod1 has eth0 at 192.168.74.177/24 and net0 at 10.56.217.179/24, an address from the NAD's subnet, with a route to 10.56.217.0/24. The chain is now three parts: the plugin counts, the NAD names the resource and the CNI config, and the Pod annotation names the NAD. A typo in any of the three strings breaks it.

Chapter 4 of 20

What the count and the label could not say

No attributes, no sharing, no relation between two kinds of device

The EKS user guide lists the limits of device plugins in four lines. Devices are requested as opaque integer counts with no attribute-based filtering. Devices cannot be shared between containers or Pods. There is no expressive topology-aware allocation across device types. Custom scheduler extensions are often needed for smart placement. Kubernetes' own DRA page says the same in other words: device plugins need a request per container, do not share, and do not filter by expression.

On EKS the two counts in play are nvidia.com/gpu from the NVIDIA device plugin and vpc.amazonaws.com/efa from the EFA device plugin. A Pod could ask for nvidia.com/gpu: 1 and vpc.amazonaws.com/efa: 4, and nothing in that request says the four EFAs should sit next to the GPU. AWS does give the device plugin path some topology help, which it calls automatic topology-awareness, only on the EKS-optimized AL2023 AMIs.

The workaround was labels. GPU Feature Discovery writes labels such as nvidia.com/gpu.product=NVIDIA-A100-SXM4-40GB and nvidia.com/gpu.memory in MiB. The EKS guide is careful about what a label means: labels are informational and used for node targeting, and a GPU is obtained by requesting the resource. A label picks a node. It cannot pick which device on the node, and it cannot pair a GPU with a NIC. The far side of the motherboard showed the kubelet's Topology Manager lining up CPUs and devices inside one node. That works only after the scheduler has already chosen the node from counts. A network card asked for by what it is needs the scheduler itself to see the card's attributes.

Chapter 5 of 20

The driver publishes every card with its attributes

DRANET writes a ResourceSlice for the node, one entry per interface

With DRA a driver on the node replaces the device plugin. For network devices on EKS that driver is DRANET, the Kubernetes Network Driver from kubernetes-sigs/dranet. AWS calls it the EFA DRA driver and says the two names mean the same tool. Its driver name in the API is dra.net. It runs as a DaemonSet, discovers devices, and writes ResourceSlice objects in the API group resource.k8s.io/v1.

A ResourceSlice has a spec.driver, a spec.pool with a name, a generation and a resourceSliceCount, the node it belongs to, and a list of devices. Each device has a name and attributes, typed as string, int, bool or version. In the live slice DRANET published from a p4d.24xlarge node, the EFA device pci-0000-10-1b-0 carries dra.net/pciDevice: Elastic Fabric Adapter (EFA), dra.net/pciVendor: Amazon.com, Inc., dra.net/pciSubsystem: efa0, dra.net/rdma: true, dra.net/rdmaDevice: rdmap16s27, dra.net/numaNode: 0, dra.net/pciAddress: 0000:10:1b.0, and the standard resource.kubernetes.io/pcieRoot: pci0000:10.

The same slice also lists the node's ENA interfaces, for example ens65 with dra.net/pciDevice: Elastic Network Adapter (ENA), dra.net/rdma: false, dra.net/mtu: 9001 and an IPv4 address. AWS states this directly: the driver advertises every network interface on the node, so the EFA DeviceClass must filter. The slice belongs to the driver. A controller in the driver overwrites any manual change. The scheduler reads these slices, and the order it walks them in is the lexicographic order of slice and pool names, first fit.

Chapter 6 of 20

A DeviceClass names the kind of card

efa.networking.k8s.aws keeps only devices whose pciDevice is EFA

A DeviceClass is a cluster-scoped object that names a category of devices and holds the CEL expression that selects them. CEL is the Common Expression Language that Kubernetes already uses in validation rules. Every ResourceClaim refers to a class by name, so the class is the vocabulary that workload owners use.

For EFA the class is efa.networking.k8s.aws, and its selector is device.driver == "dra.net" && device.attributes["dra.net"].pciDevice == 'Elastic Fabric Adapter (EFA)'. Without the second half, AWS warns, a claim could be given an ordinary network interface. For GPUs the class is gpu.nvidia.com with device.driver == 'gpu.nvidia.com' && device.attributes['gpu.nvidia.com'].type == 'gpu'.

Who creates them depends on how the driver arrived. Installed with Helm, each driver's chart creates its class. On EKS Auto Mode the drivers run from the node runtime with no chart, so you create both classes yourself, with the same names and selectors, so claims stay portable between Auto Mode and clusters where you manage the drivers. A claim that names a class that does not exist is never allocated and its Pod stays Pending. The scheduler's message for that case, from its DRA plugin source, is request <name>: device class <name> does not exist.

A class can also carry extendedResourceName. AWS's NVIDIA DRA page says the driver's chart sets extendedResourceName: nvidia.com/gpu on Kubernetes 1.34 and later, so plain nvidia.com/gpu requests are served by DRA. The field depends on the DRAExtendedResource gate, which was alpha and off in 1.34 and 1.35, is beta and on in 1.36 and stable in 1.37. On 1.34 and 1.35 it only takes effect where that gate has been switched on. AWS leaves it out of its Auto Mode definition because it turns every GPU Pod in the cluster into a DRA Pod at once.

Chapter 7 of 20

The claim asks by attribute

A ResourceClaimTemplate, a CEL selector, and a Pod that refers to it

A ResourceClaim is the request. It has spec.devices.requests, each with a name and, under exactly, a deviceClassName, an allocationMode that is ExactCount (the default, with a count) or All, and optional selectors written in CEL. A request can instead hold firstAvailable, a prioritized list of alternatives, stable from Kubernetes 1.36. Claims can also hold constraints across requests, which the PCIe chapter uses.

There are two ways to make one. A ResourceClaim you create by hand lives until you delete it and can be shared by every Pod that names it with resourceClaimName. A ResourceClaimTemplate is a pattern: the resourceclaim-controller in kube-controller-manager makes one claim per Pod, named after the Pod and the Pod's claim name plus a random suffix, and deletes it with the Pod. EFA uses templates, because AWS documents that an EFA device is allocated to one Pod at a time.

The Pod lists the template under spec.resourceClaims with a local name, and each container that should see the device lists that name under resources.claims. A container that leaves it out gets nothing even though the Pod holds the claim. A selector can use any attribute in the slice. Karpenter's page lists the EFA attributes it can evaluate before a node exists: pciDevice, pciVendor, pciSubsystem, rdma and numaNode as selectors, and resource.kubernetes.io/pcieRoot for matching only. So device.attributes["dra.net"].numaNode == 0 is a valid selector, while a selector on a pcieRoot value is not one Karpenter can plan for. The Pod also keeps requesting hugepages-2Mi directly, because hugepages remain an ordinary resource.

Chapter 8 of 20

The scheduler allocates devices, then a node

First fit over slices, a result per request, a node selector in the claim

With DRA the scheduler does the device choice that the kubelet used to do. For every Pod with claims it looks through the ResourceSlices for devices that match each request's class and selectors, that are not already allocated, and that sit on a node the Pod may use. It walks pools and slices in lexicographic order of their names and takes the first fit, so a driver can give a pool priority by naming it. The DRA API page adds that pools without binding conditions are always evaluated before those with binding conditions, whatever their names.

When it finds devices for all the claim's requests it writes the result into the claim's status. status.allocation.devices.results has one entry per device, with request, driver, pool and device. status.allocation.nodeSelector pins the claim to the node that owns the devices. status.reservedFor records which Pod may use the claim. Then the Pod is bound to that node. kubectl get resourceclaims then shows the state allocated,reserved.

If no node can satisfy every claim, the DRA plugin reports cannot allocate all claims and the Pod stays Pending. Two limits come from the Kubernetes documentation. A ResourceClaim's reservedFor list holds at most 256 entries, so at most 256 Pods share one claim. The DRA API page adds that a PodGroup from the Workload API can be recorded there instead of its Pods, so many more can share. That needs the DRAWorkloadResourceClaims gate, alpha in 1.36 and beta but still off by default in 1.37. And the scheduler does not preempt for DRA resources: a high-priority Pod waiting for a device stays Pending until the Pod holding it ends. A node for every Pod explained preemption for ordinary resources. It does not reach devices held through claims. On Auto Mode and Karpenter a Pending DRA Pod is also the signal that makes them launch a node, which later chapters cover.

Chapter 9 of 20

The kubelet and the driver move the interface into the Pod

NodePrepareResources over gRPC, then NRI when the network namespace exists

Once the Pod is bound, the kubelet on that node reads the claim's allocation and calls the driver for each driver in the claim over gRPC, NodePrepareResources before the containers start and NodeUnprepareResources when the Pod ends. That is the DRA kubelet plugin API. A GPU driver answers with CDI device names, as A Pod asks for a GPU described. A network driver has a different problem: the interface must end up inside the Pod's network namespace, and that namespace does not exist yet when prepare runs.

DRANET solves this with NRI, the Node Resource Interface of containerd. Its documentation says that once the Pod's network namespace has been created, the container runtime makes a gRPC call to DRANET through NRI, and DRANET then performs the configuration. Because it works beside the cluster's CNI, it is compatible with whatever CNI the cluster runs. The Pod keeps eth0 from the CNI and gains the allocated interface. That is the case for an ordinary network device. An RDMA device such as an EFA is handled differently, and DRANET's RDMA modes page explains how. DRANET moves the RDMA character devices, such as /dev/infiniband/uverbsN, into the Pod. It moves the RDMA link device as well only when the host's RDMA subsystem runs in exclusive mode. In shared mode the link stays in the host namespace. An efa-only EFA has no IP address, so what its Pod receives is device files for libfabric to open, not an interface with an address. DRANET keeps prepared state in a bbolt database at /var/run/dranet/dranet.db so it can finish after a restart.

DRANET then writes what it did into the claim's status.devices, a field defined by Kubernetes for drivers. Conditions are Ready with reason NetworkDeviceReady when the device is in the namespace, NetworkReady when addresses and routes are set, and RDMALinkReady when an RDMA link device was moved in exclusive mode. networkData holds interfaceName, hardwareAddress and ips. In DRANET's EFA example the EFA device reports Ready with reason RDMAOnlyDeviceReady. When the Pod is deleted the interface goes back to the host, and Linux may rename it if its old name is taken.

Chapter 10 of 20

A GPU and an EFA on the same PCIe root

matchAttribute: resource.kubernetes.io/pcieRoot

Inside a GPU server, GPUs and network cards hang off PCIe root complexes. A GPU and a NIC under the same root can move data directly, which NVIDIA calls GPUDirect RDMA and AWS calls Accelerator Data Transfer. A NIC under another root makes the data cross the CPU's interconnect. The far side of the motherboard showed the cost of crossing between sockets. This is the same idea one level down, and DRA can express it in the claim.

Kubernetes defines standard attributes under resource.kubernetes.io so that drivers from different vendors can be compared. resource.kubernetes.io/pcieRoot is the root complex in the form pci<domain>:<bus>, and devices with the same value sit in the same PCIe switch hierarchy. resource.kubernetes.io/numaNode is the device's NUMA node from sysfs. resource.kubernetes.io/pciBusID is the full address. Both the NVIDIA driver and DRANET publish pcieRoot.

A claim with two requests, one GPU from gpu.nvidia.com and one EFA from efa.networking.k8s.aws, adds constraints: - requests: ["1-gpu", "1-efa"] with matchAttribute: "resource.kubernetes.io/pcieRoot". The scheduler then only allocates pairs with the same value. On a p4d.24xlarge DRANET measured four roots, pci0000:10, 20, 90 and a0, each with two A100s and one EFA. For a p5.48xlarge, Karpenter's table gives only totals: eight H100s and 32 EFAs. Spread evenly that is four EFAs per GPU. None of the sources read publishes the p5 layout root by root, so the four per root is derived from the totals. Check the pcieRoot values in a live slice before you rely on it. If it holds, ask for the EFAs with allocationMode: ExactCount and count: 4 under the same constraint to get one H100 with its four EFAs.

Here the sources conflict. The EKS EFA guide offers a template, aligned-all-efa-one-nvidia, that asks for the EFAs with allocationMode: All and one GPU with ExactCount, for when you do not know the count. The Kubernetes API defines All as all of the matching devices in a pool, and says allocation fails if some of them are already allocated. A matchAttribute constraint does not narrow that set. It only requires every chosen device to carry the same value, and the scheduler's allocator returns an error when the constraint rules out one of the devices All must take. If the 32 EFAs of a p5.48xlarge sit on several roots, this lesson's reading of the upstream rules is that such a claim cannot succeed, and a second such Pod on the node would fail too. That is an inference from the API definition and the allocator, not a documented result: none of the sources reports running the template, and it contradicts a template AWS publishes. This lesson follows the API and uses ExactCount. On a type with fewer EFAs per GPU, such as p5en.48xlarge with 16 EFAs for 8 GPUs, four on one root may not exist, and a firstAvailable list can fall back to a smaller count. Two newer tools help when drivers disagree on names: list-type attributes, alpha from 1.36, and derivedAttributes, alpha from 1.37, which computes a common value per request in CEL.

Chapter 11 of 20

What alignment is worth on the wire

11.35 GB/s with GPUDirect RDMA, 6.04 GB/s without

DRANET's EKS example measured the difference on two p4d.24xlarge nodes, one GPU per worker, with NCCL's all_reduce_perf and the aws-ofi-nccl 1.16.3 plugin carrying NCCL over EFA through libfabric. With the aligned template the worker got gpu-0 on pci0000:10 and the EFA pci-0000-10-1b-0, RDMA device rdmap16s27, on pci0000:10. NCCL logged the transport NET/Libfabric/GDRDMA with GDR 1, and average bus bandwidth was about 11.35 GB/s. With the unaligned template the same GPU was paired with the EFA pci-0000-a0-1b-0, RDMA device rdmap160s27, on pci0000:a0. NCCL fell back to NET/Libfabric with GDR 0, and bandwidth was about 6.04 GB/s. That is 11.35 / 6.04 ≈ 1.9 times, from placement alone.

Two penalties stack. Without a direct PCIe path the EFA cannot read GPU memory, so data is staged through host memory. And each transfer crosses between root complexes through the CPU. DRANET's paper reports up to 59.6 percent more bus bandwidth for all_gather and 58.1 percent for all_reduce from topology-aware scheduling.

EFA itself is an OS-bypass device. The application talks to libfabric, which talks to the EFA directly, and EFA uses AWS's Scalable Reliable Datagram protocol. It supports NCCL, NIXL for moving KV cache in disaggregated inference, and MPI. For the site's qwen3 servers this is not yet needed: Qwen3-32B-FP8 is 34.3 GB and fits one 80 GB H100, so one Pod talks to nobody. EFA matters when a model spans nodes, or when prefill and decode Pods pass KV cache between nodes.

Chapter 12 of 20

Sharing a device, splitting it, and looking at one in use

Consumable capacity, partitionable devices and admin access

Three DRA features go beyond one whole device per request. Kubernetes documents all three, and its own example for the first is a network card.

Consumable capacity, gate DRAConsumableCapacity, alpha in 1.34 and 1.35 and beta and on from 1.36, lets several claims take parts of one device. The driver marks the device allowMultipleAllocations: true and gives it a capacity with a requestPolicy. Kubernetes' example is eth1 with bandwidth value 10G, a default of 1M per allocation and a valid range starting at 1M in steps of 8. A claim asks with exactly.capacity.requests.bandwidth: 1G. The allocation result records consumedCapacity bandwidth: 1G and a shareID, and the scheduler keeps the sum under 10G. The CEL test device.allowMultipleAllocations == true forces a shareable device. The distinctAttribute constraint makes several devices in one claim differ, for example across NUMA nodes. Karpenter uses consumable capacity for GPU time-slicing. It takes three settings. The NVIDIA DRA driver's chart needs featureGates.ConsumableShares: true and consumableShares 4. Karpenter cannot read the driver's configuration, so the EC2NodeClass carries the same mode in the annotation karpenter.k8s.aws/nvidia-consumable-capacity: "4", whose values are disabled, a positive integer N, memory or unlimited. Without the annotation Karpenter models each GPU as not shared. With all three, Karpenter packs up to four claims onto each GPU, so eight replicas fit on two GPUs. Karpenter's page warns that shares only affect scheduling and do not limit memory a process uses.

Partitionable devices, gate DRAPartitionableDevices, beta and on from 1.36, describe overlapping devices. A slice declares sharedCounters, for example memory 8Gi, and each device declares consumesCounters. Two devices that each consume 6Gi of that counter can never both be allocated.

Admin access, gate DRAAdminAccess, stable from 1.36, lets a request set adminAccess: true to reach devices that are already in use, for monitoring or troubleshooting. Only claims in namespaces labelled resource.kubernetes.io/admin-access: "true" may use it. None of the AWS pages offers bandwidth sharing or partitioning for EFA. AWS says EFA devices are not shared.

Chapter 13 of 20

What must be true before you start

Versions, API, gates, instance types, AMIs, permissions, and what to switch off

The version numbers come from several pages and they differ in a way that matters. The EKS guide says DRA is available on EKS from Kubernetes 1.33 but recommended from 1.34, because of upstream issue 133920. Both DRA driver install pages list Kubernetes 1.34 or later as a prerequisite, and DRANET's EKS example says the same. Karpenter's DRA page says DRA requires Kubernetes 1.34 or later and GPU time-slicing through DRA requires 1.36. EKS Auto Mode supports DRA only on 1.36 or later. On older Auto Mode clusters you use device plugins.

For Karpenter, AWS's device-management page contradicts itself. One passage says static capacity provisioning works with DRA on any Karpenter version that supports static NodePools, because Karpenter never simulates the claim. Two other passages on the same page, and the EKS EFA guide, say Karpenter supports DRA with both dynamic and static capacity provisioning as of Karpenter 1.15. Treat 1.15 as the safe floor for both. Dynamic provisioning, launching a node because a claim is pending, needs Karpenter 1.15 in every version of the text and is alpha and off by default. The 9 November What's New says DRA support is available for all Kubernetes versions in Karpenter, and for 1.36 and newer in Auto Mode. That is about Kubernetes versions, not Karpenter versions. Read it together with the 1.34 floor for the drivers.

The API is resource.k8s.io/v1. The DynamicResourceAllocation gate is stable and on from 1.34 and locked on from 1.35, so there is nothing to switch on in the core. Optional features have their own stages, listed in the beat. Drivers work on the EKS-optimized AL2023 and Bottlerocket AMIs, and those AMIs ship the EFA host software, though not the DRA drivers. EFA needs hugepages, reserved at boot by the EFA installer. The EKS EFA guide gives roughly 15 GiB on a c5n.18xlarge and roughly 41 GiB on a p5.48xlarge, says the amount grows with vCPUs, and warns not to assume a fixed amount. Karpenter's chart grants it read access to DeviceClasses, ResourceClaims and ResourceSlices. None of the pages read lists extra IAM permissions for DRA. Finally, a DRA driver and a device plugin must never manage the same device type on one node.

Chapter 14 of 20

Installing the drivers on Karpenter or node groups

aws-dranet and dra-driver-nvidia-gpu from Helm, then three checks

On Karpenter, managed node groups and self-managed nodes you install both drivers yourself. Auto Mode includes them and you skip this chapter.

The EFA driver comes from the EKS charts repository: helm repo add eks https://aws.github.io/eks-charts, helm repo update, then helm install aws-dranet eks/aws-dranet --namespace kube-system. It detects that it runs on EC2 through the instance metadata service and enables EFA discovery. It runs as a DaemonSet called aws-dranet in kube-system. The chart creates the efa.networking.k8s.aws class. For Karpenter, add one Helm value: tolerations [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}], because the DaemonSet does not tolerate the GPU taint by default and would never run on tainted GPU nodes.

The GPU driver comes from the Kubernetes SIG registry: helm install dra-driver-nvidia-gpu oci://registry.k8s.io/dra-driver-nvidia/charts/dra-driver-nvidia-gpu with --version 0.4.1 in AWS's example, --namespace nvidia, --set resources.computeDomains.enabled=false and --set gpuResourcesEnabledOverride=true. Karpenter's page explains both values: the second is required for GPU allocation and defaults to false, and ComputeDomains are a feature Karpenter cannot provision for. The kubelet plugin only runs on nodes labelled nvidia.com/gpu.present=true. The EKS AL2023 NVIDIA AMI sets that label. On another AMI add it to the NodePool or the driver never starts and DRA Pods stay Pending.

Then check three things in order: the DaemonSet is ready on every node, the DeviceClasses exist, and ResourceSlices appear for each node and driver. If slices are missing, the driver's logs come first.

Chapter 15 of 20

Teaching Karpenter to launch a node for a claim

Device metadata per instance type, settings.enableDRA, and separate NodePools

Drivers publish slices only once a node is running, but Karpenter must choose an instance type before the node exists. So Karpenter ships metadata for each supported instance type describing the devices the NVIDIA and EFA drivers would publish there. When a Pod with claims is Pending, Karpenter evaluates the claims against that metadata and against the slices of existing nodes. If no existing node fits, it launches the cheapest instance type that can. This works from zero GPU nodes, and NodePools and EC2NodeClasses need no DRA-specific fields.

You turn it on with settings.enableDRA: true in Karpenter's Helm values. That enables the DRANVIDIAGPU and DRAEFA feature gates and sets settings.ignoreDRARequests to false. enableDRA assumes both drivers run on your DRA nodes. If you run only one, set settings.awsFeatureGates.draNVIDIAGPU or settings.awsFeatureGates.draEFA instead, and never combine the two forms or the chart fails to render. Upgrading with --reuse-values fails because older charts default ignoreDRARequests to true. Use --reset-then-reuse-values.

Karpenter can only plan on attributes it knows before launch. For GPUs that includes productName, architecture, cudaComputeCapability, type and memory capacity. For EFA it is the list in the claim chapter. Its table of instance counts includes p4d.24xlarge 8 A100 and 4 EFA, p5.4xlarge 1 H100 and 1 EFA, p5.48xlarge 8 H100 and 32 EFA, p5e.48xlarge 8 H200 and 32 EFA, p5en.48xlarge 8 H200 and 16 EFA, p6-b200.48xlarge 8 B200 and 8 EFA, p6-b300.48xlarge 8 B300 and 16 EFA, and g6e.48xlarge 8 L40S and 4 EFA. A new instance type needs a new Karpenter release. For dynamic provisioning, leave spec.networkInterfaces unset on the EC2NodeClass: Karpenter's metadata assumes an EFA on every EFA-capable card, and a custom list with alignment is undefined there.

That rule meets the July 2026 launch. Since 22 July an EC2NodeClass can name a placement group in spec.placementGroupSelector, by name or ID, and Karpenter supports the cluster, spread and partition strategies. A cluster placement group keeps the nodes of one distributed job on one low-latency network segment in one Availability Zone, which is what EFA wants, and it is not part of the warning. The same launch lets spec.networkInterfaces, a field since Karpenter 1.11, lay out each card as efa-only or as a standard interface, and efa-only interfaces take no IP address, which AWS recommends for every card but the primary one. Here the pages pull in opposite directions. The EKS guide says not to combine dynamic provisioning, a custom networkInterfaces list and topology-aligned GPU and EFA allocation. The behaviour is undefined: Karpenter launches a node, and the Pod can stay Pending with no error at provisioning time. So an efa-only layout with aligned claims belongs on static capacity, where nodes exist first and the drivers publish what is really there. Karpenter's example of a selector for a GPU of compute capability 9.0 or newer with at least 100Gi only matches H200 and Blackwell types.

Chapter 16 of 20

The same request on EKS Auto Mode

Drivers built in, classes by hand, and a node role that never changes

Auto Mode runs Karpenter's logic as a managed service and includes the NVIDIA DRA driver and DRANET in the node runtime, beside the NVIDIA, EFA and Neuron device plugins. You install nothing. You create the two DeviceClasses, then the claims, then the workload. Auto Mode launches an instance whose devices satisfy the claim and enables the matching DRA driver on it.

Auto Mode decides for each device type, when it launches a node, whether that node is a DRA node or a device plugin node, from the Pods it launched the node for. The node keeps that role for life, even when empty. It records the choice in labels: eks.amazonaws.com/device-manager-nvidia and eks.amazonaws.com/device-manager-efa, each set to dra or device-plugin, present only for device families the instance has. A node can use DRA for GPUs and the device plugin for EFA. GPU and EFA alignment needs DRA for both, because the EFA device plugin does not publish PCIe attributes. With dynamic provisioning you need not set these labels. A static NodePool, with a fixed spec.replicas, needs them, or it uses the device plugin.

The limits are documented. Auto Mode has no GPU sharing through DRA, no time-slicing or MIG, because those are alpha in the NVIDIA driver. It does not support ComputeDomains. Its metadata assumes an EFA on every EFA-capable card, so with dynamic provisioning leave advancedNetworking.networkInterfaces unset. The interfaces Auto Mode attaches itself are of type efa, each taking a private IP, so size subnets for one address per EFA card, 32 on a p5.48xlarge. That count applies only to interfaces Auto Mode attaches. A node with several interfaces gets no public IP, so in a public subnet it reports Ready and then fails to pull images. Use private subnets with NAT.

The July 2026 launch adds two NodeClass fields. placementGroupSelector puts the nodes in an EC2 placement group, and for the EFA nodes of one job a cluster group is the natural choice. advancedNetworking.networkInterfaces lists each card with an interfaceType of interface or efa-only, and efa-only interfaces take no IP address. The EKS guide draws the same line as for Karpenter: dynamic provisioning, a custom interface list and topology-aligned GPU and EFA allocation together are undefined behaviour, with a node launched and a Pod left Pending and no error. For an efa-only layout with aligned claims, use a static NodePool with the device manager labels.

One stage label belongs to Karpenter alone. The alpha tag is on the open-source Karpenter's dynamic provisioning. AWS's pages give Auto Mode's DRA support no alpha or preview label, only the 1.36 floor and the limits above.

Chapter 17 of 20

Worked example: two training workers on northlight-eu

From Pending to an allocated claim and the interface inside the Pod

Imagine northlight-eu running on EKS with Karpenter 1.15 and settings.enableDRA on, both drivers installed, and no p5 node yet. The two qwen3 model servers keep running as before, one H100 each through the device plugin path on gpu-node-1 and gpu-node-2. Because device plugin Pods and DRA Pods now share the cluster, the nodes are kept apart first, as the migration chapter describes. NodePool gpu-dra labels its nodes example.com/device-manager: dra. The NVIDIA and EFA device plugin charts select example.com/device-manager: device-plugin, the label on the model servers' nodes, and the two DRA driver charts select dra. Without that step the device plugins would also run on the new p5 nodes and hand out the same devices as the DRA drivers, the silent oversubscription of the troubleshooting chapter. A new job fine-tunes a model across two nodes and needs EFA. Its workers use the template from AWS's NCCL test: nccl-efa-gpus asks for every EFA and every GPU with allocationMode: All and no constraint, because each worker takes a whole node.

The MPIJob creates worker Pods with nodeSelector node.kubernetes.io/instance-type: p5.48xlarge, to which this example adds example.com/device-manager: dra, resources.claims efa-gpus, and limits of hugepages-2Mi: 5120Mi and memory: 32000Mi. The resourceclaim-controller makes one claim per worker. The scheduler cannot allocate them, so the Pods are Pending. Karpenter reads the claims, finds that p5.48xlarge satisfies All of gpu.nvidia.com and All of efa.networking.k8s.aws, and launches two, each with 32 EFAs attached and 2 MiB hugepages reserved at boot, roughly 41 GiB on this type by AWS's guide. Size the Pod's request against what the node reports, not against that figure.

When each node joins, the drivers publish slices: 8 GPUs and 32 EFAs per node, plus the ENA interfaces. The scheduler allocates and kubectl get resourceclaims shows allocated,reserved. The kubelet prepares the devices, DRANET marks each EFA Ready, and the workers run. In the launcher log NCCL_DEBUG=INFO should show the ofi transport, libfabric, and no TCP fallback. When the job ends, the generated claims are deleted with their Pods and the devices return to the pool. A worker that only needed one GPU and its own EFAs would switch to a template like aligned-four-efa-one-nvidia, one GPU and four EFAs by ExactCount under the pcieRoot constraint, so up to eight such Pods could share a node if each root does hold four EFAs. AWS's aligned-all-efa-one-nvidia, with All for the EFAs, would not do that, as the PCIe chapter explains.

Chapter 18 of 20

Reading a claim when something goes wrong

Pending, ContainerCreating and silent oversubscription each have their own sign

The Kubernetes task page gives the method: drill down from the Job to the Pods to the ResourceClaims and run kubectl describe at each level, reading status fields and events. Each failure below is documented by AWS, Karpenter or Kubernetes.

The claim names a class that does not exist. This is the usual mistake on Auto Mode, where nobody created the classes. The claim is never allocated, and the scheduler's DRA plugin reports request <request>: device class <class> does not exist. Fix: create efa.networking.k8s.aws and gpu.nvidia.com.

No node can satisfy the claim. The Pod is Pending with cannot allocate all claims. On Karpenter, check that the instance types the NodePool allows are in Karpenter's DRA table and that the selector only uses attributes Karpenter knows before launch.

The driver is missing on the launched node. With enableDRA but only one driver installed, Karpenter launches nodes for claims that can never be served. The NVIDIA plugin does not start without nvidia.com/gpu.present=true. DRANET does not start on GPU nodes without the nvidia.com/gpu toleration. In each case no slices appear for that node, the Pod stays Pending, and kubectl get resourceslices shows the gap.

A custom interface list with dynamic provisioning and alignment. The node launches, the Pod stays Pending, and there is no error at provisioning time.

Two Pods share one EFA claim. Both are scheduled to the node, the kubelet reports FailedPrepareDynamicResources with driver only supports one pod per claim, and every Pod stays ContainerCreating.

A device plugin and a DRA driver on one node. Nothing fails. Both hand out the same device, and the only symptom is two workloads on one card. Auto Mode prevents it. Elsewhere it is your job.

Chapter 19 of 20

Moving a workload from the device plugin to a claim

Separate nodes, change the Pod, replace the nodes

Migration is mostly about not letting two managers own one card. The steps below put AWS's and Karpenter's rules in order.

First, decide where DRA runs. On Karpenter, managed node groups or self-managed nodes, give DRA nodes and device plugin nodes different labels, for example example.com/device-manager: dra and device-plugin, and set nodeSelectors in each chart: kubeletPlugin.nodeSelector for the NVIDIA DRA driver, nodeSelector for DRANET, nodeSelector for each device plugin. On Auto Mode this is automatic per node, though you may pin it with eks.amazonaws.com/device-manager-* labels on a NodePool.

Second, change the Pod. Remove vpc.amazonaws.com/efa and nvidia.com/gpu from resources.limits. Requesting them makes the Pod a device plugin Pod. Add a ResourceClaimTemplate, spec.resourceClaims and resources.claims in each container. Keep hugepages-2Mi. Keep the toleration for the GPU taint. Add a nodeSelector to the DRA label so the Pod cannot land on a plugin node. There is a shortcut for GPUs, extendedResourceName: nvidia.com/gpu on the class, which serves old requests through DRA without editing Pods. It applies to every GPU Pod at once, and Karpenter does not treat a Pod that requests nvidia.com/gpu as a DRA Pod, even when a DeviceClass serves that resource through DRA.

Third, replace nodes. A node's role cannot change in place. On Capacity Reservations or Capacity Blocks that means scaling down before scaling up.

For SR-IOV with Multus there is a DRA path too. dra-driver-sriov from k8snetworkplumbingwg needs Kubernetes 1.34 and runs in STANDALONE mode through NRI or MULTUS mode. Multus reads ResourceClaims when the driver publishes k8s.cni.cncf.io/resourceName and k8s.cni.cncf.io/deviceID, and the NAD keeps its resourceName annotation, which must exactly equal the driver's k8s.cni.cncf.io/resourceName. The Multus guide's DRA example uses intel.com/sriov_vf on both, with a NAD named sriov-net. AWS's pages do not cover this path. The project publishes no tagged release yet.

Chapter 20 of 20

What it cannot do yet

Alpha in Karpenter, EFA is a fabric for collectives, and 5G user planes stay where they are

The post said it is early. The pages agree, and they are specific about where.

Karpenter's DRA support is labelled Feature State: Alpha and is off by default. It plans only for instance types in its table and only for attributes it knows before launch. It does not launch nodes for MIG claims on mig.nvidia.com, because its metadata describes whole GPUs, and it does not launch for ComputeDomains used by multi-node NVLink. Those still need static capacity, managed node groups or self-managed nodes. GPU time-slicing through consumable capacity is alpha and needs Kubernetes 1.36. Auto Mode has no DRA GPU sharing beyond several Pods naming one ResourceClaim. And the two 2026 launches do not yet fit together: the efa-only interface layout from July, which saves an IP address per card, has undefined behaviour with dynamic provisioning and GPU and EFA alignment, so that combination still needs static capacity.

EFA has its own shape. It is an OS-bypass fabric for NCCL, NIXL and MPI, reached through libfabric. Its traffic is not routable and cannot cross an Availability Zone or a VPC. An efa-only interface has no IP address at all. EFA devices cannot be shared between Pods. AWS's pages say nothing about 5G or telco user planes. The post's author concludes that EFA is not a 5G user-plane NIC and that DRA here is no SR-IOV replacement yet. That is his judgement, and the documented limits fit it: a user plane function forwards routable IP traffic, often VLAN-tagged, and SR-IOV VFs with the sriov CNI provide exactly that.

In the core, the scheduler still does not preempt for DRA devices, and features that help networking, such as list-type and derived attributes, are alpha. What is stable is the pattern itself. A driver describes the card, a class names it, a claim asks by attribute, and the scheduler finds a node where the answer is true.

What to keep

Ask for the network you need, and let the scheduler find it

A special network card used to reach a workload through a chain of names: an OpenStack port and flavor, then a device plugin's count, a NetworkAttachmentDefinition's resourceName and a Pod annotation. None of them could say which card relative to which GPU. With DRA the driver, DRANET for EFA on EKS, publishes every interface with attributes such as dra.net/pciDevice, dra.net/rdma, numaNode and resource.kubernetes.io/pcieRoot. A DeviceClass names the EFAs, a ResourceClaimTemplate asks for one or all of them with CEL and a matchAttribute constraint, the scheduler writes the chosen devices and node into the claim, and the kubelet and DRANET move the interface into the Pod through NRI and report it in status.devices. On EKS that runs from Kubernetes 1.34 with drivers you install, on Auto Mode from 1.36 with drivers built in and classes you create, and under Karpenter 1.15 with an alpha switch that lets a pending claim launch the right instance from zero. Keep device plugins and DRA drivers on separate nodes, keep efa interfaces off public subnets, put the EFA nodes of one job in a cluster placement group, keep an efa-only layout with aligned claims on static capacity, and keep routable user-plane traffic on SR-IOV until a DRA driver for it is released and proven.
