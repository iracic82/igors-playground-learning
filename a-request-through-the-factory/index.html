BNK and gateways

A request through the factory

From a chat message to a GPU and back

A user types a question into a chat app. Follow that one request from the browser to a GPU and back. Four parts of the factory each make a decision on the way. The BNK data plane decides whether the packet may enter. The AI gateway decides who is asking, what they may spend and which model answers. The guardrail decides whether the prompt is safe. The endpoint picker decides which GPU does the work. Only then does a GPU spend any time on it.

Chapter 1 of 15

The call

The chat app opens a connection

The chat app talks to the factory through one address: api.northlight.example, which resolves to 203.0.113.80. That address is a virtual IP that BNK announces to the network with BGP as a single /32 route. No server owns it. The BNK data plane, TMM, answers for it. The browser first completes a TCP handshake with port 443 and then starts TLS 1.3. Its ClientHello carries the server name in the SNI field, so TMM knows which certificate to present. It also carries an ALPN list that offers h2, so both sides settle on HTTP/2 inside the same handshake.

Inside the encrypted connection the app sends one HTTP/2 request on stream 1: a HEADERS frame of 148 bytes and a DATA frame that carries 8,210 bytes of JSON in the OpenAI chat format. The body names the model northlight-chat, sets stream to true, caps the answer at 256 tokens with max_tokens and lists five messages. The first message is the support bot's system prompt, about 1,800 tokens that every user of this bot sends unchanged. Once tokenized the whole prompt is 1,912 tokens, a little over 4 bytes of JSON per token.

Chat APIs keep no memory between calls, so each turn resends the whole conversation. Two things follow. The size of a request says almost nothing about the work behind it, because an 8 kB POST can ask for 20 tokens or for 2,000. And the repeated start of every prompt is something a GPU that has read it before can skip. Both facts shape every decision further in.

Chapter 2 of 15

The border

Firewall, TLS and the first route

TMM is the only way in. Before it reads any HTTP it runs the packet through the firewall policy, a list of rules read in order. Rule allow-https accepts TCP from anywhere to 203.0.113.80 on port 443. The last rule drops everything else and logs the drop. A packet refused here is never decrypted, never parsed and never counted as a request. In BNK the firewall is an object of its own kind, F5BigFwPolicy, so each endpoint can carry its own rules.

Then TMM ends the TLS session, so everything behind it sees plain HTTP. It reads the host name and looks for a route. The Gateway object named northlight declares the listener: HTTPS on port 443, TLS terminated here, address 203.0.113.80 handed out by F5 IPAM. Its status condition Programmed says the data plane has loaded it. The HTTPRoute chat-edge attaches to that Gateway through parentRefs, matches the host api.northlight.example and the path prefix /v1, and names the Service ai-gateway on port 8080 as its backend. A route reports Accepted when the Gateway took it and ResolvedRefs when its backend exists.

TMM is a full proxy. The browser's connection ends at TMM, and a second connection starts from TMM's own address, 10.20.0.5, to the AI gateway Pod at 10.244.4.31. The caller's address would be lost at that point, so TMM writes it into the x-forwarded-for header. The body passes through unchanged, all 8,210 bytes of it.

Chapter 3 of 15

Who is asking

A key becomes a team, and the prompt is scanned

The AI gateway is where the factory learns who sent this. The Authorization header carries a bearer key, nl-key-…7f3a. The gateway looks it up and finds an active key that belongs to the team support-bot in the organization northlight-labs. It is a virtual key: the gateway issued it, it means nothing outside this factory, and it can be revoked without touching any other caller. The key's record also lists the model names it may ask for, here northlight-chat and northlight-code. An unknown or revoked key ends the request with 401, and a model outside the list ends it with 403.

Next the text of the prompt goes to F5 AI Guardrails for a scan, and the request waits. F5's sources differ on which component makes this call. One deck attaches the guardrail to the HTTPRoute in BNK, so that BNK itself drops a failed request with a 403, and in the owner's lab a BNK iRule made the call. The BNK LLM Gateway build showed its own guardrails as unavailable. This lesson draws the call from the gateway's place in the path. The scan request carries 7,790 bytes of JSON for 7,640 characters of prompt in five messages. Guardrails checks for prompt injection, personal data and restricted topics and answers 95 ms later. F5's material names three verdicts. Pass sends the prompt on untouched. Fail ends the request, and the caller gets a 403. Obfuscate masks the sensitive part, such as a card number, and lets the rest continue.

Those 95 ms are the largest single cost in front of the GPU, about three times the 31 ms that the TLS handshake and the border took together. The scan is paid before the first token, so it adds to the time to first token one for one. That is the price of inspecting in the path. The lesson on guardrails follows a blocked prompt and shows the alternative of scanning beside the path.

Chapter 4 of 15

Budget and model

What the call may cost, and what will answer it

A budget is a counter with a limit and a window. Team support-bot may use 50,000,000 tokens a month and has used 41,200,000, which leaves 8,800,000. The gateway can't know yet what this call will cost, because the answer hasn't been written. So it takes the worst case: the 1,912 prompt tokens it can count now plus the 256 output tokens that max_tokens allows, 2,168 in all. That fits 4,059 times over, so the request goes on. Over the limit the caller would get a 429 before any model is called.

The same counters work on short windows, and F5's material names the two usual ones: tokens per minute and tokens per day. A limit on requests per minute can't do this job. One agent that sends ten requests a minute can burn more tokens than a hundred people chatting. Limits can be set for an organization, a team, a user and a key, in tokens or in money, and every level has to have room.

Last, the gateway turns the name the caller asked for into a real model. Its catalog says that the alias northlight-chat means qwen3-32b, served in this factory at inference.northlight.internal. The gateway rewrites the model field in the JSON, which shortens the body by 6 bytes to 8,204, and sends the request back to BNK. The caller never names a GPU, a Pod or the real model. Tomorrow the alias can point at a different model, or at a hosted one, and no app changes.

Chapter 5 of 15

Other models behind the same name

A spent budget, the clock or a hosted model can change what answers

The alias is where the gateway can change its mind. The catalog entry for northlight-chat can hold more than one target, each with a condition, and the gateway tests the conditions on every request. The owner's design names three: the token budget is spent, the clock says off-peak, or policy sends this kind of call to a frontier model that another company hosts. The owner's design keeps that budget per user. This lesson keeps it per team, on the counter for support-bot, and the rule works the same way. In every case the caller still sends model northlight-chat to 203.0.113.80, and only the target changes.

Past the budget, the request can go to a cheaper model before anyone refuses it. Move to a later day than this lesson's request, which found 41,200,000 used. Take the month end from the refusal chapter: by then support-bot has used 49,999,000 of its 50,000,000 tokens, 1,000 are left, and this call could cost 2,168. With a downgrade rule the gateway does not answer 429 straight away. It checks a second counter, an overflow allowance of 5,000,000 tokens a month that may only be spent on qwen3-8b. 1,250,000 of it are used, so 3,750,000 are left and 2,168 fits. The gateway rewrites the model field to qwen3-8b, which makes the body 7 bytes shorter at 8,203, and charges the overflow counter. Only when the overflow is spent as well does the caller get 429. All Qwen3 models share one tokenizer of 151,669 tokens. Their model configs set vocab_size to 151,936, which counts the rows of the padded embedding table, not tokens. So the prompt is still 1,912 tokens and the worst case is still 2,168.

Cheaper here is a fact about the GPU. Qwen3-8B has 8,190,735,360 weights. Its FP8 build, Qwen3-8B-FP8, is 9.4 GB of files against 34.3 GB for Qwen3-32B-FP8. A decode step reads every weight matrix once, with one exception. The input embedding table is only looked up, one row for the new token, so its bytes are not read in full. Both builds keep that table at 2 bytes a weight: 622,329,856 weights for Qwen3-8B and 777,912,320 for Qwen3-32B. Leave it out and a step reads about 8.2 GB on Qwen3-8B against 32.8 GB on Qwen3-32B, so each output token moves about 4 times fewer weight bytes out of GPU memory. The KV cache reads come on top of that, and they shrink too. It has 36 layers where Qwen3-32B has 64, with the same 8 KV heads of 128 numbers, so its KV cache costs 36 × 2 × 8 × 128 × 2 = 147,456 bytes a token. This prompt then holds about 282 MB of KV memory where Qwen3-32B holds about 501 MB. The small model runs in its own InferencePool with its own picker, which this scene does not draw. Its answers are usually weaker. A team that must never spend past its limit keeps the plain 429 and turns the downgrade off.

A schedule changes the target by the clock. In the illustrative rule here, northlight-chat means qwen3-32b from 07:00 to 22:00 Berlin time and qwen3-8b from 22:00 to 07:00, so that gpu-2 and gpu-3 can run the factory's batch work at night. The gateway reads the clock when the request arrives. A request at 23:10 Berlin time on 26 November is 22:10 UTC, because Germany is on UTC+1 in winter, and it gets qwen3-8b. In summer the same 22:00 is 20:00 UTC, so a rule written in UTC would be an hour off for half the year. A stream admitted at 21:59 finishes on qwen3-32b, because the choice is made once per request. A conversation that crosses 22:00 keeps working, since every turn resends the whole history. It does lose the warm cache. KV blocks belong to one model, so the first night-time turn pays the prefill for all 1,912 tokens on the small model. The same kind of rule can point the other way and give night traffic a larger model while the GPUs are idle.

A frontier provider fits behind the same address in the same way. Amazon Bedrock accepts the OpenAI Chat Completions format at https://bedrock-runtime.<region>.amazonaws.com/openai/v1/chat/completions and takes a Bedrock API key as a bearer token. A catalog entry can point there, at a model such as openai.gpt-oss-120b-1:0. The gateway changes the model name, takes the caller's nl-key out of the Authorization header, puts the factory's Bedrock key in, and sends the call out to AWS. The Bedrock key stays in the gateway and no caller ever sees it. The prompt does leave the factory, which is why the key check, the model list and the guardrail scan all run before this hop. Bedrock's runtime endpoint does not implement GET /models, so clients see the gateway's own model list. Bedrock's native Converse API, POST /model/{modelId}/converse, wants each message's content as a list of text blocks, so a gateway that uses it has to translate the body.

Chapter 6 of 15

Which GPU

The data plane asks the endpoint picker

The AI gateway knows the model. It doesn't know the GPUs. So it sends the request back to BNK, on an internal listener for the host inference.northlight.internal. This time TMM finds a route whose backend is an InferencePool where the first route had a Service. A Service would mean that any Pod will do. An InferencePool means: ask its endpoint picker first. The pool selects its members by label, here app: vllm-qwen3-32b, names the port they serve on, 8000, and points at the picker with endpointPickerRef, here qwen3-epp on port 9002.

TMM holds the request and opens a gRPC stream to the picker. The protocol is ext_proc, the external processing protocol that Envoy defined, and the Gateway API inference extension requires every endpoint picker to speak it. TMM sends two messages on the stream. The first is a ProcessingRequest with the request headers. The second carries the body, all 8,204 bytes, with end_of_stream set. The picker needs the body because the model name, the prompt and max_tokens are all inside the JSON.

Two settings on this hop decide what happens on a bad day. failureMode is FailClose by default, so a picker that can't be reached means a refused request and never a GPU chosen at random. And BNK connects to the picker without TLS, so a NetworkPolicy that admits only the BNK namespace to port 9002 is what keeps prompts private on this hop. In BNK the picker itself is declared with an F5EPP object that points at the pool. Two replicas give one serving picker and one standby.

How much of the body TMM sends, and when, is a setting of the ext_proc protocol called the body mode. Envoy defines it in ProcessingMode as BodySendMode, with six values. NONE sends no body at all and is the default. STREAMED sends the body in pieces as they arrive. BUFFERED holds the whole body in memory and sends it in one message, and a body larger than the buffer limit gets the caller an error. BUFFERED_PARTIAL also sends one message, but only the part of the body that fits the buffer limit. FULL_DUPLEX_STREAMED streams the pieces both ways: the picker may hold as many pieces as it likes, must send the body back as StreamedBodyResponse messages, and the trailer mode has to be SEND. GRPC is a planned mode that would split a gRPC body into its separate messages, and Envoy has not implemented it. Headers have their own setting, request_header_mode, which defaults to SEND, and trailers default to SKIP.

The endpoint picker protocol says a picker must support the streaming mode. The light reference picker that the Gateway API inference extension keeps for its conformance tests shows what that means in practice. It collects every chunk of the body until one arrives with end_of_stream set, because it cannot choose a worker from half a JSON document. Then it picks, sends the headers answer with the chosen address, and streams the body back in chunks of at most 62,000 bytes. It refuses a body over 10 MB, 10,485,760 bytes, with the gRPC status ResourceExhausted. This request's 8,204 bytes arrive as one chunk and go back as one. Which body mode TMM itself uses was not seen in the owner's lab, so the beats here follow the reference picker.

Chapter 7 of 15

The picker decides

Tokens counted, three workers compared

The picker reads the body and counts the prompt with a tokenizer of its own: 1,912 tokens in, at most 256 out. Tokens are the unit a GPU works in. Two requests of about 1 kB each look the same to a balancer that counts connections. If one asks for 256 tokens and the other for 8,192, then at this factory's pace of about 12.4 ms a token the first holds a place in the batch for about 3 seconds and the second for about 101 seconds, 32 times longer. Round robin would give every worker the same number of requests and very different amounts of work.

Then it compares the three workers. From each worker's /metrics page it has three gauges: vllm:num_requests_waiting, vllm:num_requests_running and vllm:kv_cache_usage_perc. From the KV event stream it knows which prompt prefixes each worker holds. gpu-1 is quiet and has never seen this prompt. gpu-3 holds the first 1,808 tokens, but it has 6 requests waiting and its cache is 97% full. gpu-2 holds the same 1,808 tokens, has nothing waiting and is at 58%. The picker skips a saturated worker first and only then looks for a warm cache, so gpu-2 wins.

The answer comes back on the same stream as a ProcessingResponse. It sets the header x-gateway-destination-endpoint to 10.244.2.22:8000 and repeats the value as metadata under the key envoy.lb. The protocol requires at least one of the two, and when a picker sets both they must not differ, because a data plane may read either one. The whole exchange took about 1 ms. A picker that only chased the cache had two candidates and could have chosen gpu-3, behind six others. Cache awareness without load awareness can end up worse than neither, because it piles requests onto the one worker that is already busy.

Chapter 8 of 15

When something says no

Five places can end the request, and none of them is a GPU

Five places can end a request, and the order they come in is the point. The firewall drops a packet that matches no allow rule before any TLS work, and logs the drop. The AI gateway answers 401 for an unknown or revoked key and 403 for a model the key may not use. Guardrails returns the verdict fail and the caller gets a 403. The budget check answers 429. None of these four has touched the picker or a GPU. The rule this factory is built around says that no GPU time is spent on a request that fails one of the first four checks.

The fifth refusal is the picker's. If no worker in the pool is ready, the protocol tells the picker to answer with an ImmediateResponse that carries status 503. If the pool is saturated and the request is marked sheddable, it answers 429. TMM sends that status to the caller and forwards nothing. If the picker can't be reached, FailClose applies. In a lab run with the picker scaled to zero, no request reached a worker, and after 4 to 5 seconds TMM answered 503 with the message inference endpoint picker unavailable.

For an operator the status code says which layer refused. Silence and a timeout point at the firewall. 401 and 403 point at the key, its scope or the content of the prompt. 429 points at a budget or at a shed request. 503 points at the pool or the picker. Each refusal costs the factory a few milliseconds of proxy time. The same request served costs 2.6 seconds of a place in a GPU's batch.

Chapter 9 of 15

Two orders for the same checks

Why one picture meters tokens before it knows the caller

This lesson walks the checks in the order of the owner's design: firewall, key, the key's model list, guardrail, budget, then model and picker. F5's workflow diagram for the BNK AI gateway draws another order. After the L4 ingress comes the Gateway listener, which ends TLS and reads the SNI. Next is a gateway token meter that enforces tokens per minute and tokens per day and drops an exceeded caller with 429. Then the HTTPRoute matches the path and the MCP session, an identity step checks OIDC and JWT and drops an invalid caller with 401, and the EgressPolicy sends the prompt to F5 AI Guardrails, where fail gives 403. A semantic cache answers a match at once, and only a miss goes on to the endpoint picker and the prefill and decode GPUs.

The deck's own slides do not quite agree here. Its slide on token control says the meter limits clients and service accounts by tokens per minute and per day, which is a limit per caller. Its diagram puts that meter before the identity step. A meter in front of identity can only use what the listener already knows: the listener itself, the host from SNI, the client address, or a header that nobody has checked yet. So at that position a meter either counts a caller name that nobody has proven yet, or it counts something coarser. The example below is the coarser kind, and it is this lesson's illustration, not F5's design: a ceiling for the whole factory or for one entry point, whose job is to stop new work when the pool is already full. The two kinds of meter answer different questions, and that is why both orders can work. Say the listener allows 6,000,000 tokens a minute, an illustrative figure for what three workers can serve, and 6,010,000 have been charged this minute. Every new request gets 429 for the price of one counter read. Nothing calls the key service, nothing waits 95 ms for a guardrail scan, and no picker is asked. When the factory is full the answer is the same for every caller, so there is nothing to gain by finding out who it is.

A team's budget is a different question, and it needs a proven caller. A counter keyed on an unchecked value can be abused. If a meter counted against the sub claim of a JWT before the signature was verified, anyone could write sub support-bot into a forged token and use up that team's minute. So any meter that charges a person, a team or a key has to sit after the step that proves who that is. Envoy Gateway, an open source Gateway API implementation, orders its HTTP filters that way by default: jwt_authn at position 10, each ext_proc filter at 100 plus its index, the local rate limit at 302 and the global rate limit at 303. External authorization, ext_authz, runs earlier still, at position 6, and API key auth at 7.

How a meter charges matters as much as where it sits. Envoy AI Gateway checks only the usage already charged when a request arrives, and charges the real tokens from the response when the stream ends. A request refused with 401 has no response and is never charged, so moving that kind of meter earlier only changes who hears 429 first. This lesson's budget reserves the worst case up front, 1,912 + 256 = 2,168 tokens. A reservation taken before the guardrail would have to be handed back every time a scan fails, and that is why the budget here runs after the scan. F5's deck says its tokenizers count usage before the call and again after the stream. A factory can run both meters: a ceiling at the listener and a per-team budget after identity.

Chapter 10 of 15

To the worker

Straight to the Pod the picker chose

TMM now knows the Pod. It takes the address from the picker's answer and opens a connection straight to 10.244.2.22 on port 8000. There is no Service in between and no second load balancer. That matters because a ClusterIP would hand the connection to kube-proxy's rules, which choose a Pod at random, and the picker's choice would be undone. The picker may also return several addresses separated by commas. TMM would then try them in order, and later it reports which one served the request.

On gpu-2 the request will find most of its work already done. The first 1,808 tokens of the prompt are the support bot's system prompt, and gpu-2 holds them as 113 blocks of 16 tokens in its KV cache. The KV cache stores the keys and values that attention computed, for every token and every layer. For Qwen3-32B that is 64 layers times 2 tensors times 8 heads times 128 numbers times 2 bytes, which is 262,144 bytes per token. The cached prefix alone occupies 1,808 × 262,144 bytes, about 474 MB of GPU memory.

That memory is why the choice of worker matters. The Pod took 72 GB of the card's 80 GB at start, about 34.3 GB of it for the weights of the FP8 build, Qwen3-32B-FP8. What is left holds KV blocks for every running request and every cached prefix. Sending this request to gpu-1 would have worked. But gpu-1 would have computed all 1,912 tokens and stored another 474 MB that already exists one machine over.

Chapter 11 of 15

Into the batch

Tokenize, queue, and join the requests already running

Zoom into gpu-2. The vLLM API server receives the POST on port 8000. It applies the model's chat template, which joins the five messages into one string with role markers, and runs the tokenizer over it. The result is 1,912 token ids. This is the count the bill will later carry as prompt_tokens, and it matches what the picker counted a millisecond ago.

The request then joins the waiting queue, and the gauge vllm:num_requests_waiting goes from 0 to 1. Three other requests are already running as one batch. vLLM does continuous batching: the scheduler looks at the queue between two passes of the model and can add a request to the running batch without waiting for the others to finish. Here the request waits 5 ms for the pass in progress to end. Then the gauges read 0 waiting and 4 running, and vLLM records the wait in the histogram vllm:request_queue_time_seconds.

Those two gauges are exactly what the picker scrapes. A worker with a long waiting queue is one where the scheduler has no room, because the batch is at its limit or the KV cache has no free blocks for another prompt. gpu-3 is in that state, with 6 waiting and its cache 97% full. When the cache runs out entirely, vLLM preempts a running request, frees its blocks and computes it again later. It counts each such event in vllm:num_preemptions, a number an operator wants to see stay at zero.

Chapter 12 of 15

Prefill

Read the prompt, reuse what is cached

The scheduler looks in the KV cache before it computes anything. These workers are set to cut the cache into blocks of 16 tokens. Each block is found by a hash of its own tokens and of the block before it, so a block's hash covers every token from the start of the prompt. The lookup walks the chain. Block 0, block 1 and on to block 112 are hits, and block 113 is a miss. That is 113 blocks, or 1,808 tokens, already computed. vLLM adds 1,912 to vllm:prefix_cache_queries and 1,808 to vllm:prefix_cache_hits.

That leaves 104 new tokens. The GPU reads them in one pass, all at once, and each of them attends to the 1,808 cached tokens before it. This pass is called prefill. It is limited by compute, because many tokens share one read of the weights, and it is why the first token takes longer than the ones after it. Here it takes 38 ms. If prefill time grew in step with the token count, the full 1,912 tokens would have taken about 700 ms. That figure is illustrative, and it shows the size of what the cache saved.

The pass leaves new keys and values behind: 104 tokens × 262,144 bytes, about 27 MB. They fill six more blocks, 113 to 118, and half of block 119. The worker publishes a BlockStored event for the six full blocks, with their hashes, the hash of the parent block and the block size. The picker listens to that stream. It is how it knew a moment ago that gpu-2 held the system prompt, and how it will know that gpu-2 now holds this conversation too.

Chapter 13 of 15

Decode

One token per pass, streamed as it comes

The end of the prefill pass gives the first token of the answer, 44 ms after the request reached gpu-2. From here the model works one token at a time. Each pass takes the last token, reads all the weights again, looks back at the KV cache and produces the next token. That is decode. A 212-token answer needs the prefill pass and 211 decode passes after it.

Decode is limited by memory bandwidth. The cores do little arithmetic for one token, but every pass has to pull about 32.8 GB of weights out of the GPU's memory. That is the 34.3 GB FP8 build less its input embedding table, which a pass only looks up. An H100 moves about 3.35 TB a second, so 3,350 ÷ 32.8 gives at most about 102 passes a second, or 9.8 ms a token at the very best. This worker delivers a token about every 12 ms: 211 passes in 2,609 ms. A pass costs about the same for one request as for four, because the weights are read once for the whole batch. So all four requests get their next token from the same pass, and that sharing is where a worker's throughput comes from.

Each new token's keys and values are appended to the cache, another 262,144 bytes, and block 119 goes from 8 to 9 of its 16 tokens. The API server writes the token to the open response at once as a server-sent event, one data line holding a chat.completion.chunk object. Streaming is a side effect of the decode loop. vLLM records the first token in vllm:time_to_first_token_seconds and every gap in vllm:inter_token_latency_seconds, the two numbers a user feels.

Chapter 14 of 15

The answer goes back

The same proxies, in reverse

Back in the factory view. Each chunk leaves gpu-2 as a small packet of 238 bytes and returns through the proxies it came in by. When the response headers arrive, TMM tells the picker over the ext_proc stream, which is still open, which worker served the request. It does so in the metadata field x-gateway-destination-endpoint-served. The picker may have offered a list of workers, so this report keeps its picture of each worker's load true.

The stream then passes the AI gateway, which puts the alias back so the caller sees northlight-chat in every chunk. Because the app asked for stream_options.include_usage, the model server sends one extra chunk before [DONE] with an empty choices list and a usage object: 1,912 prompt tokens and 212 completion tokens, 2,124 in total. The gateway charges those to team support-bot, whose counter moves from 41,200,000 to 41,202,124. It had allowed for 2,168, so 44 tokens of headroom are released. Metering from the model's own count means the bill matches what the app's SDK reports.

TMM encrypts each chunk again and sends it on HTTP/2 stream 1. The first word, "You", left gpu-2 as soon as prefill produced it at about 175 ms, and the user saw it about 177 ms after the first packet. The beats here follow the second chunk, " were", which leaves gpu-2 at 185.3 ms and reaches TMM at 186 ms. The first chunk took the same path about 10 ms earlier, carrying the status line and the response headers with it. The last word arrived at 2,784 ms. Of that time 31 ms went to TLS and the border, 97 ms to the AI gateway and its guardrail call, about 1 ms to the picker, 5 ms to the queue, 38 ms to prefill and 2,609 ms to decode. Those add up to 2,781 ms. The other 3 ms or so went to the short hops between the steps: TMM to the gateway, the gateway back to TMM, TMM to gpu-2 and the tokenizer on the worker. The conversation's KV blocks stay on gpu-2. A follow-up question that the picker sends there again will find almost its whole prompt cached.

Chapter 15 of 15

Six layers, one hop

What BNK takes out of a typical inference stack, and what one place costs

F5's deck for BNK with NVIDIA draws a typical inference stack as six layers above the runtime. An external load balancer gives the world a way into the cluster. kube-proxy on a NodePort spreads that traffic over Pods. An L7 gateway does service routing, policy and health checks. An AI gateway does API access, policy and model routing. An AI-aware scheduler, the endpoint picker, chooses a worker by prefix and load. A prefill and decode orchestrator places the two phases of a request on different GPUs. Under all six sit the inference runtime, which runs the model, and the GPUs. In the BNK picture the six layers become one. BNK holds API access, policy and security, prefix-aware routing, endpoint selection and prefill-decode orchestration, and the runtime and the GPUs stay as they were.

Each removed layer had a cost this lesson can name. The external load balancer was a second VIP and a second team's configuration in front of the cluster. Here BNK announces 203.0.113.80 as a /32 with BGP itself. A NodePort, a port from 30000 to 32767 by default on every node, hands the packet to kube-proxy's rules, and in iptables mode they pick a backend at random, which is the very choice the picker exists to make. Sidecars put a proxy beside each Pod, so every hop passes through two more proxies. A separate AI gateway adds a Pod, a connection and a set of keys. This lesson draws the AI gateway as its own Pod, so the request uses four TCP connections: browser to TMM, TMM to the gateway at 10.244.4.31, the gateway back to TMM, and TMM to gpu-2. The owner's design runs the key, guardrail, budget and model steps as one policy in TMM for each endpoint, with side calls to the key service and the guardrail, next to the call to the picker that TMM makes in both designs. Then the count drops to two, and the body makes two fewer trips across the cluster network, 8,210 + 8,204 = 16,414 bytes a request.

One control point means one place to configure and one place to read. For each endpoint the objects are a Gateway, an HTTPRoute, an InferencePool with its F5EPP, the policy and an F5BigFwPolicy, and deleting the endpoint deletes exactly those. Policy, security, failover and logs come from the same data plane, so every status code in the refusal chapter shows up in one log. Open at both ends means standard interfaces on both sides. Northbound the factory is configured with the Gateway API and the inference extension resources, plus F5's own CRDs for the picker. Southbound the workers here run vLLM, and the deck names NVIDIA Dynamo and Triton as other runtimes. The picker needs only what a runtime publishes: queue and KV cache gauges on /metrics and, for prefix scoring, KV events. F5's workflow deck calls BNK an extensible collection of tools, from L4 ingress to the picker, each switched on by a CRD.

One place is also one dependency. When the picker was scaled to zero in the owner's lab, every request for that pool got 503, because FailClose refuses and never guesses. With every check in one data plane, a fault or a bad change there reaches every endpoint at once, so the TMM replicas and the standby picker carry more weight. Separate tools still fit some factories. A team may already run an AI gateway that its billing reads from, a cloud may already provide the external load balancer, or two groups may own the gateway and the network. The deck allows for that at the front. Option A keeps a customer's own L4 load balancer and hands traffic to BNK's VIPs. Option B runs BNK on NVIDIA BlueField DPUs. Option C makes BNK the L4 balancer itself with BGP, which is what this factory does. The trade is fewer hops and one policy place against the freedom to replace each piece on its own.

One request, four decisions, one GPU. The firewall in TMM let the packet in. The AI gateway found the team behind the key, had the prompt checked, confirmed the budget and chose the model. The endpoint picker chose gpu-2 because it already held 1,808 of the prompt's 1,912 tokens and had room. On the GPU, prefill read only the 104 new tokens in 38 ms, and decode produced the answer one token per pass in 2.6 seconds. Had any check failed, the request would have ended with a drop, a 401, a 403, a 429 or a 503 before a GPU spent a single pass on it.
