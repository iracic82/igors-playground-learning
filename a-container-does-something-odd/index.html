Kubernetes underneath

A container does something odd

How Falco watches system calls and turns one of them into an alert

Admission control reads what a Pod declares before it is stored. It has no view of what the container does once it runs. A model server that passed every policy can still have a shell opened inside it an hour later, by someone whose credentials allow that. Falco covers that part. It is an agent on every node that watches the system calls containers make, compares each one with a list of rules and raises an alert when a rule matches. This lesson follows one event from the kernel to a chat channel: someone opens a shell in the model server qwen3-6f7d9c8b4-x7k2p and reads the token that Kubernetes mounted into it. Around that one event it shows how Falco gets onto a tainted GPU node, what its kernel probe costs in memory, which system calls it chooses to see, how it names the Pod, how a rule is read and written, where an alert goes, what responds to it, what gets lost on a busy node, and how to watch, tune and test Falco itself. It describes Falco 0.45 with its default rules.

Chapter 1 of 14

Falco on every node

A DaemonSet puts one Falco Pod on each node, if the node lets it in

Falco can only watch the kernel it runs on, so it has to run on every node. The Falco Helm chart, version 9.2.2 here, installs it as a DaemonSet, the controller kind that keeps one Pod on each matching node. That is the value controller.kind: daemonset.

The GPU nodes of this cluster carry the taint nvidia.com/gpu=present:NoSchedule, which keeps ordinary Pods off them. A DaemonSet Pod is subject to taints too. The chart's default tolerations cover only the taints node-role.kubernetes.io/master and node-role.kubernetes.io/control-plane, both NoSchedule. With those defaults the scheduler places no Falco Pod on gpu-node-1 or gpu-node-2, and the two nodes that run the model servers are the two nodes nobody watches. The fix is a toleration for nvidia.com/gpu in the chart's tolerations value.

Falco needs a lot of the host. The chart's driver.kind defaults to auto, and with auto, or with the modern eBPF probe when leastPrivileged is false, the chart makes the container privileged. With leastPrivileged true it adds four capabilities instead: BPF, PERFMON, SYS_RESOURCE and SYS_PTRACE. SYS_RESOURCE lets Falco raise the limit on locked memory so its eBPF maps can be pinned in RAM, and SYS_PTRACE lets it read /proc/<pid>/environ of other processes. Falco also needs parts of the host's file system, mounted under /host. Falco's own page on running in a container mounts /proc and /etc, plus the container runtime's socket, for the modern eBPF probe, and adds /dev for the kernel module. The chart decides by driver.kind. With auto, its default, the Falco container gets /proc, /etc and /dev under /host, and the driver loader, an init container that runs first, gets /boot, /lib/modules and /usr as well, which it needs to find or build a kernel module for the running kernel.

The chart requests 100m CPU and 512Mi of memory and caps the container at 1 CPU and 1024Mi. Falco serves /healthz on port 8765. The startup probe waits 3 seconds and then checks every 5 seconds up to 20 times, so Falco has the 3 second delay plus 20 × 5 = 100 seconds, about 103 seconds in all, to load its probe and rules before the kubelet restarts it.

Chapter 2 of 14

A shell is a system call

Everything a container does to the outside world, it asks the kernel to do

Someone runs kubectl exec against the Pod qwen3-6f7d9c8b4-x7k2p and asks for a shell. The API server checks who they are and that they may use exec on Pods in the namespace inference. Exec is the subresource pods/exec, and admission sees it as the operation CONNECT. They may, so the API server passes the connection to the kubelet on gpu-node-1. From then on the session is a stream of bytes. The commands typed into it are never API requests, so nothing in the API server sees them.

The kubelet asks containerd over the Container Runtime Interface, the CRI, to start a process in the running container. containerd's shim runs runc, and runc makes the new process join the namespaces and the cgroup of the container. Namespaces give it the container's view of process IDs, network, mounts, host name and inter-process communication. The cgroup puts it under the container's limits on CPU and memory. Because kubectl was called with -t, the process also gets a pseudo-terminal.

Then comes the step that matters here. To become a shell, the new process asks the kernel to replace its program with /bin/sh. That request is a system call, the only way a program can ask the kernel for anything: start a program, open a file, make a connection. On x86-64 the call is execve, number 59.

A container is an ordinary process, and all containers on a node share one kernel. The model server's Python process, its GPU driver calls and this new shell all go through the same kernel of gpu-node-1. Whoever watches system calls on the node sees what every container does.

Chapter 3 of 14

A probe in the kernel, a ring buffer out

Falco's kernel half copies the event and gets out of the way

Falco's kernel half is called a driver. Falco 0.45 has two: the modern eBPF probe, the default in falco.yaml, and a kernel module. The older eBPF probe was removed from the whole stack in Falco 0.44. The modern probe is a set of small programs that the Falco binary carries inside itself and loads into the kernel when it starts, with no kernel module to build. It can do that on many kernel releases because of CO-RE, compile once run everywhere: the kernel describes its own data structures in a format called BTF, and the probe adjusts to them when it loads. The documentation names two kernel features it needs, BPF ring buffers and BTF, and says that kernels from 5.8 usually have both. bpftool feature probe kernel tells you whether a node has them. Since 0.45 the probe also uses BPF atomic instructions, added in Linux 5.12, where the kernel has them, and logs a warning containing no BPF atomics on this kernel where it does not.

The kernel runs the programs at tracepoints, fixed hooks it offers for system calls entering and returning. When the execve returns, the probe runs. It collects the arguments, the IDs of the process and the result, and writes one event into a ring buffer, a block of memory shared between the kernel and Falco. Then it returns, and the shell carries on. The probe never waits for Falco.

The memory adds up. buf_size_preset 4 means 8 MB per buffer, and cpus_for_each_buffer 2 means one buffer for every two online CPUs. On a node with 64 CPUs that is 32 buffers and 32 × 8 MB = 256 MB. Each buffer is mapped twice into Falco's virtual memory, so the 256 MB show up as 512 MB of address space. Separately, since 0.45 the probe keeps two auxiliary map segments of 128 KiB for every possible CPU, where it assembles events of variable size: 64 × 256 KiB = 16 MiB more.

Chapter 4 of 14

Which system calls are traced

Falco only collects what its rules and its own bookkeeping need

Tracing every system call on a busy node would cost more than it is worth. A model server writes to sockets and files all the time, and most of those calls say nothing about security. So Falco works out a set. It starts with the system calls the loaded rules mention, then adds the ones its state engine needs to keep its process and file tables right, such as clone, fork, execve, setuid and chdir. Very frequent calls such as write are left out unless a rule asks for them, and falco -i lists the events ignored by default.

The documentation shows the set being computed. Load a rules file whose only rule looks at execve and start Falco with --dry-run and debug logging. The log line says two system calls come from the rules, execve and execveat, and sixteen more come from the state engine: capset, chdir, chroot, clone, clone3, fchdir, fork, prctl, procexit, setgid, setpgid, setresgid, setresuid, setsid, setuid and vfork. Eighteen in total. That is the list the probe is told to watch.

Three settings under base_syscalls in falco.yaml change it. custom_set lists calls to add, and a name written with a leading ! removes one. repair: true, which the documentation recommends for most cases, picks the smallest set that keeps the state engine correct. all: true traces everything, write included. The defaults are an empty custom_set, repair false and all false.

Two more settings trim what each event carries. snaplen, 80 by default, is how many bytes of an I/O buffer Falco copies for each read or write. engine.modern_ebpf.drop_failed_exit, false by default, would drop the exit events of failed system calls in the kernel, saving work at the price of not seeing failed attempts.

Chapter 5 of 14

From a thread ID to a Pod name

The kernel has never heard of Pods, so Falco adds the names itself

The event that comes out of the buffer holds numbers: a thread ID, a result, a file name, a terminal. A rule that says shell in a container needs more than that. Falco keeps a table of every thread on the node, and updates it from the clone, fork, execve and exit events it traces. Rules talk about processes, and Falco treats the thread leader of each group as the process. Looking the thread up gives the process name, its parent and its ancestors. At start the modern probe fills the table with BPF iterators, which read the kernel's state directly and are faster than walking /proc. They also heal the table after drops, and they are switched off automatically when Falco does not run in the host's own process ID namespace.

The table holds at most 262144 threads by default. Every 300 seconds Falco purges threads that have not been seen for 300 seconds, so a stale entry can linger for up to 300 + 300 = 600 seconds. Stale entries come from dropped exit events or events that arrive out of order.

The container comes from the process's cgroup. The path of that cgroup contains the container ID, and Falco takes the first 12 characters of it. That happens inside the kernel, so container.id is always there. A plugin that ships with Falco, called container, turns the ID into names. It is switched on by a small file in /etc/falco/config.d that sets load_plugins to container. A worker inside the plugin listens on the container runtime's socket, by default /run/containerd/containerd.sock for containerd through the CRI. It learns of each container at the create hook, which comes before the first process in it starts, and keeps the image, the Pod name, the namespace and the Pod's labels in memory. No request goes to the API server for an event.

Chapter 6 of 14

When the names are missing

container.id is always there. The Pod name can arrive late

The two halves of enrichment are not equally reliable. container.id is cut from the cgroup path inside the kernel, so it is on every event of a container from the first one. Everything else comes from the runtime socket, and the plugin's documentation says plainly that in cases of lookup delays a field such as container.name may not be available yet. Metadata can also be missing when an event arrives before the lookup of its container has finished. The troubleshooting page concludes that Falco's logs can never be perfect and that empty values occur.

A missing value does not look the same everywhere. It can be an empty string, the text <NA> or a numeric default. In an alert it shows up as k8s_pod_name=<NA> or with nothing after the equals sign.

The plugin talks to each runtime with a timeout. engine_timeout is 10 seconds by default, and 0 turns it off. An engine that does not answer in time is skipped with a warning for the rest of the run, and the containers it runs have no metadata until Falco restarts. For containerd the documentation recommends the CRI engine over the plain containerd one, because CRI carries richer metadata, container names included.

This matters for rules. The rule this cluster wrote for its token tests k8s.ns.name = "inference". If the first events of a brand new container arrive before its namespace is known, that test is false and the rule stays silent for those events. A shell opened hours after the container started, as here, is not affected. An attack in the first instant of a container would be. A rule that must never miss can test a field the kernel supplies, such as container.id != host, and use the Kubernetes names only in its output.

Chapter 7 of 14

A rule is a condition, an output and a priority

The default rule for a shell in a container, read line by line

Falco's rules are YAML. A rule has a name, a description, a condition, an output and a priority. The condition is an expression over the event's fields that is true or false. The output is the text of the alert, with field names that Falco fills in. The priority says how serious a match is, from debug up to emergency. Optional keys have defaults: enabled is true, and a rule with enabled false is neither loaded nor matched.

Two helpers keep conditions readable. A macro is a named piece of a condition that many rules share. A list is a named set of values. The default rules file, falco-rules 5.2.0, opens with required_engine_version 0.57.0. Falco 0.45 has engine version 0.65.0, so the file loads. It ships 25 stable rules, and one of them is Terminal shell in container.

Its condition is six parts joined with and, five of them macros. spawned_process is true for execve and execveat. Since Falco 0.42 an event has no direction any more, entry or exit, so the macro no longer needs to say which side it wants. container is true when container.id is not host. shell_procs tests the process name against the list shell_binaries. proc.tty != 0 means a terminal is attached. container_entrypoint is true when the parent is missing or is one of the runtime's own processes, runc, containerd-shim, conmon and others. The last part is the placeholder macro user_expected_terminal_shell_in_container_conditions, negated. The default rules define it as never_true, so it matches nothing until a cluster gives it a condition of its own.

The event from the shell in qwen3-6f7d9c8b4-x7k2p makes all six true. The rule's priority is Notice, because people open shells in containers for honest reasons every day. Its description says so: the rule is common when using kubectl exec, and it advises matching the alert with the Kubernetes audit log of the exec to find which user or token opened the shell.

Chapter 8 of 14

The token read, and a rule of your own

The default rules know /etc/shadow. They do not know your secrets

Nine seconds later the person in the shell types cat and the path of a file. Every Pod has a token for its service account mounted at a fixed path, put there by the ServiceAccount admission plugin when the Pod was created, and with it a program can call the Kubernetes API as that Pod. Reading it is one more system call, openat, number 257 on x86-64, and it reaches Falco by the same road.

This time the default rules stay silent. The rule Read sensitive file untrusted, priority Warning, looks for a short list of files: /etc/shadow, /etc/sudoers, /etc/pam.conf and /etc/security/pwquality.conf, plus anything under /etc/sudoers.d and /etc/pam.d. The token is not on it. Falco's own documentation says to write rules for the credentials that matter in your environment.

The owners of this cluster did. Their rule reuses the default macro open_read, which is true for open, openat and openat2 when the file is opened for reading, is a regular file and the call succeeded. It adds container, the namespace inference and a path test with the operator pmatch. pmatch compares a path with a set of directory prefixes by whole path components: pmatch (/tmp/hello) is true for /tmp/hello and /tmp/hello/world and false for /tmp/hello_world. A glob would have to match the whole path. The model server never reads its token, so every match deserves a look.

Since Falco 0.45 conditions compare the original bytes of a field. A file name with a newline or an invalid UTF-8 byte in it can be matched exactly, and in the output such characters are escaped, so a crafted file name cannot forge a second line of alert.

Chapter 9 of 14

What an alert looks like and where it goes

One line of JSON on the node, then a forwarder that knows many destinations

An alert is one line. falco.yaml ships with json_output false, and with it set to true the line is a JSON object. Its keys are hostname, output, priority, rule, source, which is syscall for kernel events, tags, time and output_fields. output_fields carries every field the output used, with evt.time as an integer in nanoseconds. Switches with the prefix json_include_ decide which of these keys appear. The container and Pod fields at the end of the text come from append_output with suggested_output: true, which lets a plugin add the fields it suggests to every alert of its source.

Falco writes that line to the channels switched on in falco.yaml. Standard output and syslog are on by default. Syslog messages use the facility LOG_USER, with the rule's priority as the syslog priority. A file, a program and an HTTP endpoint are available and off. Falco neither rotates nor truncates its output file, and reopens it on the signal SIGUSR1 so a log rotation tool can work. Standard output is enough to land the alert in whatever collects the logs of your Pods.

To reach people, most clusters add Falcosidekick. It is a small service that receives the alerts of every node's Falco over HTTP on port 2801 and forwards them to chat, to log stores and to alerting systems. Each destination has its own minimum priority, so a Notice can go to the log store while only a Warning reaches the chat channel. Falcosidekick answers 200 on /healthz, serves Prometheus metrics on /metrics, and sends a test event to every enabled output when it receives a POST on /test. customfields adds fixed fields, such as the cluster name, to every alert it forwards.

Chapter 10 of 14

Falco detects. Something else responds

The system call had already returned when the rule matched

By the time the alert exists, cat has printed the token. Falco could not have stopped it. The probe only copies, and rules are evaluated afterwards in user space, in a separate process that reads the buffer when it can. Every event has to cross from the kernel to user space before any rule sees it. So a response is a separate step, taken by a person or by a program that reads the alerts.

Falco Talon is such a program. Its rules link alerts to actions: each rule can run several actions in order, each action uses an actionner that says what to do, and a notifier reports the result. Falcosidekick forwards alerts to it once talon.address points at http://falco-talon:2803.

A careful first action is to label the Pod. A NetworkPolicy that already exists selects that label and allows no traffic in or out, so the Pod is cut off while its processes and files stay in place for inspection. The action needs the alert to carry k8s.ns.name and k8s.pod.name, and Talon's service account needs permission to patch Pods.

Deleting the Pod is the other common action. The Deployment replaces it, the shell and the token die with it, and so does the evidence in the container's writable layer. The token itself is bound to the Pod. Once the Pod is gone the API server rejects it, so the copy that was read becomes useless. The credentials used for kubectl exec are a different matter and stay valid until someone revokes them. The replacement, a new Pod of the same revision such as qwen3-6f7d9c8b4-r5n8w, needs about three minutes to load the 34.3 GB of its FP8 weight files, and qwen3-6f7d9c8b4-m9q4t on gpu-node-2 serves alone until then.

Chapter 11 of 14

The cost of watching, and what gets lost

Busy nodes fill buffers, and a full buffer drops the event

The probe runs on every traced system call of every process on the node, and each event is then decoded and tested in user space. Falco's documentation states two facts about the cost. It is not constant: it follows the workload, so the more system calls the containers make, the more CPU Falco uses. And Falco's hot path is single threaded, so its process should not be able to use more than one full CPU. On a 64 CPU GPU node that keeps Falco's own process to about 1 of 64 CPUs, and it is also the ceiling on how many events per second Falco can process.

That ceiling covers Falco's process in user space only. The probe does its work inside each traced system call, on the CPU where the calling program runs, so that time is spent in the workloads, the model server included, and it is not counted in the Falco Pod's CPU. The whole cost of watching is therefore not capped at one CPU, and Falco's own CPU metric shows only part of it.

When events arrive faster than Falco reads them, a ring buffer fills up. The probe does not wait for room, because that would slow down every program on the node. It drops the event and counts it. A dropped execve is a shell Falco never saw. A dropped exit can leave a dead process in the table. Since 0.45 there are also counters for drops in the auxiliary maps, and the documentation points out that a bigger buf_size_preset does not enlarge those maps.

Once a second Falco compares dropped events with all events. Above the threshold of 0.1, ten percent, it takes the actions in syscall_event_drops, log and alert by default. A token bucket with rate .03333 and max_burst 1 lets at most one message through every 30 seconds. The alert is the rule Falco internal: syscall event drop at priority Debug, with counters for each kind of event lost. falco.yaml 0.45.2 and its source say the log line is Debug too. The documentation page on dropped events still says CRITICAL and shows an example at that level, which is older text.

The documentation's advice for the modern probe is to try buf_size_preset 6 or 7 with cpus_for_each_buffer 4 or 6, to trace fewer system calls and to drop rules nobody acts on.

Bigger buffers have a cost inside Falco's own Pod. Since Linux 5.11 the kernel charges the memory of eBPF maps to the memory cgroup of the process that created them, and the ring buffers are eBPF maps that Falco creates. The 256 MB of default buffers on this node already count against the chart's limit of 1024Mi. Preset 6 with cpus_for_each_buffer 4 makes it 16 × 32 MB = 512 MB, half the limit before Falco's own process memory or its output queue. A buffer change and the memory limit have to move together.

Chapter 12 of 14

Watching the watcher

Falco can report on itself, once you switch that on

Drops, CPU and rule matches are visible only if Falco publishes them, and by default it does not. metrics.enabled is false in falco.yaml. Turned on, Falco gathers its counters every metrics.interval, one hour by default. The comments recommend intervals such as 15m, 30m, 1h, 4h or 6h and enforce at least 100 ms. With output_rule true, the default, each sample is written as an alert named Falco internal: metrics snapshot, which needs the rules priority at info or lower to appear.

For Prometheus a second switch is needed. webserver.prometheus_metrics_enabled is false by default and works only when metrics.enabled is true. Then the webserver on port 8765 serves the counters as Prometheus series.

A few series answer most questions. falcosecurity_scap_n_evts_total and falcosecurity_scap_n_drops_total give the drop rate. falcosecurity_scap_n_drops_buffer_total, labelled with dir="exit" and drop="execve", says whether lost events were process starts. falcosecurity_falco_cpu_usage_ratio and falcosecurity_falco_memory_rss_bytes show the cost. falcosecurity_falco_rules_matches_total counts matches per rule. falcosecurity_scap_n_drops_full_threadtable_total rises when the process table is too small. The troubleshooting page shows a sample with average times of 194 nanoseconds at the system call entry tracepoint and 205 at the exit tracepoint.

Alerts can also be lost after the rules. outputs_queue.capacity is 0, which means unbounded, and the comments warn that Falco could then be killed for running out of memory. With a capacity set, an alert that finds the queue full is dropped and counted in falcosecurity_falco_outputs_queue_num_drops_total. And when the kernel sends nothing at all, syscall_event_timeouts raises an alert after 1000 consecutive reads that time out with no event.

Chapter 13 of 14

Quieting noise without editing the rules

A later file overrides one macro, one list or one rule, and the rest stays as shipped

The other running cost is noise. A rule that fires many times a day on normal work trains people to ignore the channel, so it has to be tuned. You tune it without editing the default file, because the default file is replaced on every update. Falco loads rules files in the order of rules_files in falco.yaml: /etc/falco/falco_rules.yaml, then /etc/falco/falco_rules.local.yaml, then the files in /etc/falco/rules.d. A later file can change what an earlier one defined, and when two macros have the same name the last one wins.

The tool for that is override. For a list it may touch items. For a macro it may touch condition. For a rule, append may touch condition, output, desc, tags and exceptions, and replace may touch those plus priority, enabled, warn_evttypes and skip-if-unknown-filter. append and replace cannot be used on the same key together. append is plain text concatenation: the new text is added to the end of the old condition, so an old condition containing or needs parentheses or the result means something else.

The shell rule was built for this. Notebook Pods in the namespace training open shells all day. A rules file of this cluster's own replaces the placeholder macro user_expected_terminal_shell_in_container_conditions, which is never_true by default, with a condition that matches those Pods by namespace and image. The rule itself is untouched, and shells everywhere else still raise a Notice.

Exceptions are the structured way to do the same on a rule. An exception has a name, a list of fields, a list of comparison operators and a list of value tuples. A rule can also be switched off whole with enabled: false and override.enabled: replace, or from falco.yaml with a rules list of enable and disable entries by name pattern or tag, evaluated in order.

Chapter 14 of 14

Testing and shipping a rule

Validate the file, check what is loaded, and know what updates the rules for you

A rules file with a mistake can stop Falco from starting, and a DaemonSet that crashes on every node watches nothing. So a rule is tested before it ships. falco -V with the file validates the rules and exits. falco -L lists every loaded rule, and falco -l with a rule name shows that one rule. falco --list prints the fields a condition can use, and --list-events the events. falco --dry-run loads the configuration and the rules and stops before processing any event, which is the same run that printed the system call set earlier. falco --support prints the version, the rules files in use and the loaded configuration, the first thing to collect when asking for help.

Two checks happen at load time. A file that declares a required_engine_version higher than the running engine is loaded and returns an error. A rule that uses a field this Falco does not know makes Falco report an error and exit, unless the rule sets skip-if-unknown-filter: true, in which case it is accepted and never runs.

The order of rules also matters. rule_matching is first by default, so only the first rule that matches an event fires, and a broad rule early in the files can shadow a precise one later. Setting it to all fires every matching rule in the order they are defined, at some cost in speed.

Under the Helm chart the rules are not static. A falcoctl sidecar follows the artifact falco-rules:5 and checks for a new version every 168 hours, one week, asking Falco on localhost:8765/versions whether the new rules suit the running engine. falco.yaml has watch_config_files true, so Falco reloads when its configuration or rules files change. A local rules file that depends on a default macro should be tested again after each such update.

What to keep

Seen from below

Containers on a node share its kernel, and everything they do to the world passes through it as system calls. Falco runs on every node it tolerates and puts a probe in that kernel. The probe copies each traced call into a ring buffer and never holds the caller up. In user space Falco gives the event a process from its table, a container from the cgroup and a Pod from the runtime, and tests it against rules made of a condition, an output and a priority. A match becomes one line of JSON, and Falcosidekick takes it to people. The shell in qwen3-6f7d9c8b4-x7k2p was allowed by every check the API server has. It was noticed because starting a program and opening a file cannot be done without the kernel. Falco only notices, and only what its rules ask about, on events it did not drop. Its metrics show what it missed, overrides keep the noise down, and validation keeps a bad rule from blinding a node. Stopping the shell at the door is the work of admission, network policy and a Pod that mounts no token it does not need.
