Running a GPU cloud

From an order to a server and back

What a GPU cloud does between the click and the login, and after the customer leaves

A customer of Northlight Compute orders one bare-metal server with four H100 GPUs. Bare metal means the customer gets the whole physical machine, with no hypervisor in between. Minutes later they log in and see four GPUs. Between those two moments the provider reserves a server, powers it on through its management controller, boots it from the network, writes an operating system to its disk, moves it into the customer's network segment and checks that it works. This lesson follows that one order through every state, using OpenStack Ironic as the worked example of the bare-metal steps. It shows how a server enters the pool in the first place, the deploy steps in the order Ironic runs them, the agent that calls back from the network boot, the image and config drive it writes, and what Ironic does while the customer uses the machine. Then it follows the server back to the pool through cleaning, shows what an operator reads when a step fails, and follows an order that fails halfway. Before any of that it shows what is being sold: the catalogue item that turns three GPU servers into products, what one item holds, and why a provider that builds every server by hand cannot grow. Along the way it separates provisioning from scheduling, builds the same order as a GPU virtual machine, and lets a training pipeline order, change and end a server through the API with no person involved. At the end it follows an order the customer cancels halfway, an order where only part of the servers become ready, the open-source parts and the gaps they leave, who owns the whole workflow, how the SLA is tracked on every order, how tenant isolation is tested, and how a new GPU model is added without a new way of working.

Chapter 1 of 28

The catalogue turns servers into products

Before anyone can order, the provider has to decide what it sells

Northlight's inventory knows every machine it owns. gpu-srv-1, gpu-srv-2 and gpu-srv-3 each have four H100 GPUs, a BMC address such as 10.9.0.12, a rack position and a state such as available, active or in maintenance. Inventory answers four questions: what hardware exists, what is free, what is in use and what is being repaired. A customer has no use for an asset ID or a BMC address. A customer wants a product it can understand, such as a dedicated four-GPU server, a GPU virtual machine, a block of GPU capacity held for one week, or a bundle of compute with a given network and storage. The service catalogue is the layer that turns infrastructure facts into things a customer can select and order. Each entry says what can be consumed, under which conditions, and how it is built behind the scenes.

Three lists are easily confused. Inventory describes what physically or logically exists. A price list describes what things cost. The catalogue describes what a customer may order and on which terms. A catalogue item points at inventory and at prices, and it is identical to neither. OpenStack uses the words service catalogue for a fourth thing. Keystone, its identity service, keeps a catalogue of service endpoints, and openstack catalog list prints entries such as compute, image and network, each with its URLs. That catalogue lets an API client find the compute service. The commercial catalogue in this lesson lets a customer find a product. A cloud built on OpenStack has both, and they never replace each other.

A SKU, short for stock keeping unit, is one orderable product code. A GPU provider usually sells a handful of kinds. Dedicated bare metal is a whole physical server for one tenant, the product this lesson's order buys. Reserved capacity is an agreed amount of GPUs held for one customer for a period and paid whether it is used or not. A GPU virtual machine runs on a hypervisor, with a whole GPU passed through to it or a slice of one. On-demand GPU service is capacity started and stopped at will and paid for the hours it is held. Bundles add specific network or storage options to any of these. The names a customer sees are things like an H200 server with eight GPUs, a four-GPU training node, a reserved GPU cluster or an on-demand GPU instance. A provider does not have to expose every GPU model it owns as an item.

A hosting business often starts from one customer's requirement. Sales negotiates, an engineer designs a configuration, someone builds the server by hand, and billing gets a custom contract. That works for a few long contracts. It stops working when orders arrive every day, because every custom solution needs its own way to build, its own billing rule and its own way back. Turning capacity into repeatable products is the first step to scale. Each product maps to a known server shape, a known pool of capacity and a known way to build and wipe it. The same hardware can serve both models. The difference is the layer of products and automation around it.

The catalogue must stay tied to what the pool can really deliver. An item can be listed while no server can fill it. The provider then needs a rule: show live availability, take a reservation for a later start, put the order in a waiting state, send it for approval, or offer another item. The catalogue must also agree with billing. If the item says seven-day dedicated reservation while metering counts GPU utilization and billing charges VM runtime, the service has three definitions of what was sold, and none of them can be defended to the customer.

Chapter 2 of 28

An order is a record with a state

Nothing touches a server yet

Tenant A picks a product in the portal: one bare-metal server with four H100 GPUs. A tenant is one customer, with its own users, quota, network and bill. The portal sends the request to the order service. The order service asks identity two things: who the caller is, and whether tenant A may order this product. Then it writes an order record in the state ordered.

From here on every part of the cloud reads and updates that record. The state is what the customer sees, what support looks at and, later, what billing trusts. Nine states cover this lesson: ordered, reserved, provisioning, ready, active, terminating, completed, failed and cancelled. They are this provider's own names. Failed means the provider could not deliver. Cancelled means the customer withdrew the order before it became active. The two end the same way on the hardware, and they mean different things to the SLA and to the bill, so the record keeps them apart. The bare-metal software underneath has its own, finer set, and the order service maps one onto the other.

The record carries more than a state. It names the tenant, the product, the image the customer chose and the SSH public key that will let them in. It is written before any hardware is chosen, so a crash anywhere later leaves a trace of what was asked for. Each later step changes the state in one direction, and each change is a moment that someone can point to: when the customer was told, when billing began, when it stopped. An order that sits in one state for too long is the first sign that a step below it is stuck.

Chapter 3 of 28

What the customer sees and what the operator runs

Five simple steps in front, a dozen systems behind

From tenant A's side the service has five steps. Select a product. Order it. Use it. Monitor it. Terminate it. Each step is one screen in the portal or one API call. Behind each step the operator runs a different part of the cloud. Select is served by the service catalogue. Order is served by ordering: identity, entitlement, quota and the order record. Use is served by provisioning and scheduling: the reservation, the deploy steps, the network move and the readiness check. Monitor is served by metering, observability and the SLA, which tell the customer what it holds, for how long and whether the promise was kept. Terminate is served by billing, which closes the charge, and by recovery and reuse, which wipe the server and put it back in the pool.

The two lanes are very different in size. For ord-1042 the customer makes two calls: one to order and one, a day later, to end the order. In between, the operator's side runs an identity check, an order record, a quota check, an Ironic allocation, six core deploy steps, two power-ons through the BMC, a network boot, an agent lookup and its heartbeats, an image write, a config drive, a switch port binding, a readiness check and a metering record. On the way back it runs a teardown, a port unbinding, a cleaning pass with two erase steps, the closing of the metering record and the release of the claim. Customers see simple self-service. Operators need all of that working behind it, every time.

The customer's view depends on the operator's states being honest. The portal shows the order state, which moves through ordered, reserved, provisioning, ready and active. During the twelve minutes of provisioning, Ironic underneath passes through deploying, wait call-back, deploying again and active, and the order service maps all of it to the single word provisioning. When a step fails and a retry runs, the customer should see provisioning with a retry noted, and billing must not start. When the provider gives up, the customer should see failed and a zero charge. A view that says active while the server still sits on the provisioning network is the most damaging error the front lane can show, because the customer cannot use what it is told it has, and billing believes it.

Chapter 4 of 28

Why the order runs without a person

Manual fulfilment works for a few servers and breaks with growth

Imagine ord-1042 handled by hand. A ticket arrives. An engineer finds a free server in a spreadsheet, logs in to its BMC, mounts an installer, waits, configures the switch port for the customer's network, creates a storage account, pastes the customer's SSH key, checks the GPUs, and emails the customer. When the customer leaves, another engineer revokes the access, wipes the disks, moves the port back and marks the server free. Each of those tasks is reasonable. Done by a person for every request, delivery becomes slow and inconsistent. Take an illustrative 3 engineer-hours to build and 2 to take back, 5 hours per order. At 40 orders a week that is 200 engineer-hours, five people doing nothing else for a 40-hour week. Double the customers and the people double. Automated, ord-1042 went from order to active in twelve minutes with no person involved.

Speed is half of the argument. The other half is consistency. A person who builds forty servers a week will one day forget a VLAN, paste the wrong key, skip a disk or leave a server on the provisioning network. Each such slip is a security problem or a broken service, and none of them is written down anywhere a second person can find. An automated workflow runs the same steps in the same order every time and records each one as a state, so a failure lands in a named place, deploy failed with last_error filled in, instead of in someone's memory. That makes provisioning automation a core capability of delivering cloud service, and the same holds for the way back: cleaning has to be just as repeatable.

NIST SP 800-145 lists on-demand self-service as one of the five essential characteristics of cloud computing: a consumer can provision computing capabilities, such as server time and network storage, as needed and automatically, without requiring human interaction with each service provider. A portal can look like self-service and still hide a team working tickets behind it. The test is whether a request flows through policy, capacity, provisioning, service state, usage and recovery without an employee rebuilding the workflow each time. Self-service is a way of operating. It is also a scaling mechanism: as the number of customers grows, handling every request by hand stops scaling, and self-service lets customers request directly while the platform applies the policies.

Self-service sits beside enterprise sales. Large customers still negotiate reservations, network designs and SLAs with people. Tenant B's hold on gpu-srv-1 came from such a contract. What self-service takes over is the repeatable part: choosing a product, ordering, reading the status, consuming and terminating. Self-service does not mean every request is approved either. Quota, entitlement, eligibility and capacity still apply. It does not remove the operations team. It moves the team to the policies, the exceptions, the capacity plan and the incidents. Self-service and on demand are related and different. Self-service is about how a customer asks and controls. On demand is about whether capacity can be started and released as needed. A reserved server can be ordered self-service, and an on-demand request can still wait for approval.

Chapter 5 of 28

Before the pool: enrolling and proving a server

A server can be sold only after Ironic knows how to reach it and has checked it

gpu-srv-2 entered the pool months before this order. An operator enrolled it with baremetal node create, giving a driver and the details needed to reach its management controller. Enrolling only records that the node exists. The verb manage then makes Ironic check those credentials, and the node passes through verifying to manageable. The verb provide runs a cleaning pass and makes it available. Both verbs answer at once and finish in the background, so success is read afterwards from the node's provision_state, and failure from its last_error field.

Before a node goes further, baremetal node validate prints a table with one row for each of the node's interfaces except vendor. On current Ironic that is twelve rows. Five interfaces are required of every driver: boot, deploy, management, network and power. Seven are optional: bios, console, firmware, inspect, raid, rescue and storage. Older examples in Ironic's own guide show fewer rows, because some of these interfaces did not exist yet. A failing row says what is missing, such as an absent ipmi_address in driver_info. A row that reads not supported is not a failure. The manageable state is where a node is repaired. Ironic's documentation names it as the state for changing driver_info or port details, and as the only stable state reachable from clean failed, inspect failed and adopt failed.

The product a customer orders maps to hardware through a resource class. Ironic's own docs give the example of a class named large-gpu for nodes with powerful GPUs. Northlight's class is gpu-4xh100, an illustrative name. Traits add yes or no properties, such as CUSTOM_ names the provider invents. Ironic can also test GPUs during cleaning. The burn-in framework arrived in the Xena release with steps for CPU, memory, disk and network. A GPU step came much later: the step named burnin_gpu first appears in the 2025.1 release, in both Ironic's burn-in guide and the agent's code. It checks that the expected number of GPUs is visible and then loads them with gpu-burn. The count check is off by default, with agent_burnin_gpu_count at 0, so a provider has to set it to 4 for a four-GPU server.

Chapter 6 of 28

Inside one catalogue item

A product definition carries its own recipe for building and ending it

A catalogue item is a record with many fields, and each one answers a question someone will ask later. Depending on the service it can hold: a product code or SKU, the GPU type and count, the form (bare metal, VM or a workload on a shared cluster), the compute shape, the network options, the storage options, the rules for reservation or duration, the region or site, who is eligible and against which quota, the price or contract it maps to, a provisioning template, a termination and recovery policy, and the scope of support or SLA. Not every item needs every field. What matters is that the fields connect the product the customer sees to the operating model behind it.

Northlight's bm.h100x4 fills them in this way, all illustrative. GPU: H100, four. Form: bare metal. Shape: one gpu-4xh100 server. Network: one segment in the tenant's VRF. Storage: access to the tenant's storage, with a read rate of at least 1 GB/s. Duration: on demand, by the held hour, from active to terminating. Site: northlight-eu. Eligible: any tenant with a verified account, counted against GPU quota. Price: 5,000 units per GPU-hour from the price list, so 20,000 units for each hour the server is held. Termination: automated cleaning before the server returns to the pool. SLA: active within 30 minutes of the order, 99.5% availability per month.

The provisioning template is the part that makes the item repeatable. It tells the platform how to create this product: which servers may be chosen, which images may be written, which network to bind, which storage to reach, which credentials to issue, and which checks must pass before the order may be called ready. Without it, ordering bm.h100x4 would still need an engineer to decide what that means. For bm.h100x4 the template says: resource class gpu-4xh100 and the trait CUSTOM_NVLINK, an image from the approved list, the tenant's VNI, the config drive with the customer's key, and the readiness check that counts four GPUs.

Where OpenStack Nova sits in front of Ironic, server selection is written as a flavor. Ironic's guide gives the rule for the name. The node's resource class is upper-cased, prefixed with CUSTOM_, and every punctuation mark becomes an underscore. gpu-4xh100 becomes CUSTOM_GPU_4XH100, just as the guide's baremetal.with-GPU becomes CUSTOM_BAREMETAL_WITH_GPU. The flavor asks for exactly one of that class with resources:CUSTOM_GPU_4XH100=1. It also sets resources:VCPU=0, resources:MEMORY_MB=0 and resources:DISK_GB=0, which turns off scheduling on the standard counts, because a bare-metal server is taken whole. The flavor's disk value is still used for the root partition size. Required traits are written as trait:CUSTOM_NVLINK=required, and nodes have carried traits since Bare Metal API version 1.37. A flavor can request exactly one instance of a bare-metal resource class. Ironic warns that a resource class can be added to an active node and cannot be replaced on one, so changing what a product maps to is done on nodes that are not rented.

Chapter 7 of 28

Reserving a server

The scheduler claims one machine so nobody else can

The scheduler checks tenant A's quota and looks for a free server of the right kind. In Ironic, a server that can be handed out is in the provision state available. To claim one, Ironic offers an allocation: a request for a node of a given resource class, sent as POST /v1/allocations from API version 1.52. A node is eligible only when six things hold. Its provision_state is available, its power_state is known, maintenance is false, instance_uuid is empty, its resource class matches, and its traits include every trait asked for. A list of candidate_nodes can narrow the search further.

The call is asynchronous. It returns 201 with the new allocation in the state allocating, and Ironic finishes the work in the background. When it succeeds the allocation becomes active and Ironic sets the node's instance_uuid to the allocation's UUID. That field is what stops a second allocation from taking the same node. The command line waits for the result with --wait. If no node fits, the allocation fails and its last_error says why.

The order moves to reserved. gpu-srv-2 now belongs to this order, and it still has no operating system. An allocation is deleted automatically when its node is later unprovisioned. If a node is claimed and never deployed, deleting the allocation is the caller's job. A provider that forgets this leaves servers claimed by orders that no longer exist, which shows up as capacity nobody can find.

Chapter 8 of 28

The deploy steps and their order

Ironic turns deploy into a list of steps, each with a fixed priority

The order moves to provisioning, and the order service asks Ironic to take the node to active. Ironic does not run one long script. It runs deploy steps, ordered from the highest priority number to the lowest. The core list has six. deploy.deploy at 100 boots the node into the provisioning image. deploy.write_image at 80 writes the customer's image. deploy.prepare_instance_boot at 60 sets the boot device and installs the bootloader, for the direct deploy interface. deploy.tear_down_agent at 40 shuts the provisioning image down. deploy.switch_to_tenant_network at 30 moves the server's ports to the customer's network. deploy.boot_instance at 20 starts the customer's system.

The gaps between those numbers are left for the provider. A step above 100 runs out of band before anything else, through the BMC. A step from 81 to 99 runs inside the ramdisk before the image is written. From 61 to 79 it runs after the write and before the bootloader, and from 41 to 59 after the bootloader. From 21 to 39 it runs out of band once the ramdisk is gone, and from 1 to 19 when the customer's system is already up. When two interfaces use the same priority, the order is power, management, deploy, BIOS and RAID.

From API version 1.69 a caller can add steps to a single deployment with --deploy-steps. Ironic's example applies a BIOS setting at priority 150, so it runs through the BMC before the node is booted. A provider could use the same slot to set the firmware options its GPU servers need. Before the first step, the boot interface prepares the network boot files, the management interface switches the next boot to the network, and the power interface turns the server on.

Chapter 9 of 28

Reaching the server out of band

A powered-off machine still has one small computer that listens

gpu-srv-2 is powered off and has an empty disk. The provisioner reaches it through its baseboard management controller, the BMC. A BMC is a small computer on the motherboard with its own network port and its own address, here 10.9.0.12. It runs whenever the server has power at the plug, and it can switch the main system on and off and choose what it boots from. Talking to it is called out of band, because it does not go through the server's operating system.

Two protocols are common. Redfish is an HTTPS and JSON API defined by the DMTF. IPMI is the older one, and Ironic's ipmitool driver uses port 623 by default. For Redfish, Ironic reads the BMC's details from the node's driver_info. redfish_address must include the host part of the URL and may also include the scheme, as https://10.9.0.12 does here. https is assumed when the scheme is left out. redfish_system_id is needed only when the BMC manages more than one system. By default Ironic checks the BMC's TLS certificate, and redfish_verify_ca can point to a CA file or turn the check off. redfish_auth_type is basic, session or auto, and auto tries a session first and falls back to basic.

Ironic first tells the BMC to boot from the network once. Then it powers the server on. A power change that has not taken effect within power_state_change_timeout, 60 seconds by default, counts as a failure. The BMC network is the provider's alone. A tenant who could reach a BMC could change the boot device or the power of a server, which would make the tenant an administrator of the infrastructure.

Chapter 10 of 28

Network boot and the agent's call back

A small temporary system starts, finds out who it is and reports in

The server starts, and its firmware does what the BMC told it: boot from the network. Ironic's default boot mode on current releases is UEFI, and older releases defaulted to BIOS. With PXE, the firmware asks DHCP for an address and for the name of a boot program, then fetches that program over TFTP. UEFI HTTP boot fetches it over HTTP. What arrives is the deploy ramdisk, a small Linux system that runs from memory. All of this happens on the provisioning network, which keeps a machine being built away from machines that customers control.

Inside the ramdisk runs the ironic-python-agent. It does not know which node it is on, so it asks Ironic's lookup endpoint. The call is GET /v1/lookup, with the MAC addresses of its network cards joined by commas in the query parameter addresses, and the node UUID in node_uuid when the agent already knows it. Ironic matches the addresses against the ports it has on record and answers with the node's UUID and a block of configuration for the agent. Some older agent documentation describes this as sending a hardware profile. The current code sends only those query parameters. On that first lookup Ironic also hands over an agent token, a random string of 43 characters by default. The agent sends the token with every heartbeat, and the conductor includes it in its commands. Since the Victoria release every agent must use one. The token is not a substitute for TLS, and Ironic requires https callback URLs unless agent.require_tls is set to False.

Then the agent heartbeats to /v1/heartbeat/{node}. The agent learns its maximum interval from the lookup reply, in the field heartbeat_timeout. Ironic fills that field from the API option api.ramdisk_heartbeat_timeout, which defaults to 300 seconds. The agent multiplies it by a random number between 0.3 and 0.6, so by default it heartbeats every 300 × 0.3 = 90 to 300 × 0.6 = 180 seconds. The random factor is jitter, so that many agents do not call at the same moment. A heartbeat that fails is retried after 5 to 10 seconds. A different option, conductor.heartbeat_timeout with a default of 60 seconds, is about the conductor's own liveness and does not set the agent's interval. Some older agent documentation quotes 20 to 36 seconds for a timeout of 60. That figure is out of date. The work is driven by those heartbeats. Each time one arrives, the conductor does whatever is due next. While Ironic waits for the first call the node is in wait call-back. If none arrives within deploy_callback_timeout, 1800 seconds by default, the node goes to deploy failed. A PXE retry exists, pxe.boot_retry_timeout, and it is off by default.

Chapter 11 of 28

Writing the image and the config drive

The agent writes the customer's system to disk, then the server is turned off

With the direct deploy interface the agent downloads the customer's image itself and writes it to the local disk. instance_info.image_source tells it where. It takes http://, https:// and file:// URLs, and a value with no scheme is read as an image ID in the Glance image service. A partition image needs root_gb as well. By default the agent fetches the image straight from its source. With image_download_source set to local, the conductor caches the image, converts it to raw and serves it from its own web server.

The download is checked. image_checksum holds an MD5 sum and is required only for http:// images with direct deploy. Other algorithms go in image_os_hash_algo and image_os_hash_value, for example sha256. A host in FIPS 140-2 mode has no MD5 and must use SHA-256. Size has a trap. A compressed file of 2.4 GB can unpack to a disk of 20 or 100 GB, and the agent writes the unpacked size, which stretches the time in deploying and wait call-back.

Next to the image goes the config drive. Ironic expects a gzipped, base64-encoded ISO 9660 image with the label config-2, up to 64 MB, or it builds one from JSON with the keys meta_data, user_data and network_data. The customer's SSH key travels in meta_data. A first-boot service such as cloud-init must be in the image, or nothing reads the drive. User data is a string, and a cloud-init file starts with #cloud-config. instance_info is cleared when the node is torn down. Then Ironic sets the boot device to disk and the agent powers the server off. A deployment boots the server twice: power on into the ramdisk, power off after the image is written, and power on again into the written image.

Chapter 12 of 28

The tenant's network, storage and keys

A server with an operating system is still not the customer's server

So far the server has lived on the provisioning network. Before the customer gets it, it must sit in tenant A's own segment, where it can reach tenant A's other machines and nobody else's. With Ironic's neutron network interface, the step switch_to_tenant_network, priority 30, removes the provisioning ports and binds the tenant's ports. Binding means the switch port the server is cabled to is reconfigured for the tenant's network. In the owner's designs that network is a VRF with its own VNI on an EVPN-VXLAN fabric, here VNI 10001 for tenant A, an illustrative number.

To program the right switch port, the networking service needs to know where each cable lands. Each Ironic port carries local_link_connection with switch_id, a MAC address or OpenFlow datapath ID, and port_id, such as Gig0/1. These are usually filled during inspection from LLDP messages sent by the switches, so the switches must have LLDP on. When a cable moves or a switch is replaced, they have to be corrected by hand. The networking service also needs a driver for the switch model that supports the baremetal port type. The neutron interface needs a provisioning_network and a cleaning_network configured, and either network may be given by UUID or by name. Ironic's configuration reference says a name given there must be unique among all networks, or the deployment or cleaning that uses it fails. InfiniBand ports skip local_link_connection, because the subnet manager discovers the topology.

Then boot_instance, priority 20, powers the server on and it boots from its disk. On first boot cloud-init reads the config drive and installs the customer's SSH key. Storage is reached over the tenant's segment with credentials that belong to tenant A. The NVIDIA driver and CUDA came with the image. Moving the ports must not disturb anyone else on the fabric. The owner's material lists that as a rule of its own: tenant churn must not destabilize the shared network.

A server with working GPUs is still useless if the workload cannot reach its data at the rate it needs. AI work moves large files all the time: training data, checkpoints, model artifacts, container images and results. So provisioning has to coordinate four things around the GPUs: the network path, the storage, the security policy between them, and the data access rights. Each is a precondition of the order, and the template of bm.h100x4 names a floor for it, 1 GB/s of read rate from the tenant's storage, an illustrative figure.

The arithmetic shows why. Tenant A plans to serve Qwen3-32B from its storage. The FP8 build, Qwen3-32B-FP8, is 34.3 GB of files. Over a path that delivers 10 Gb/s, which is 1.25 GB/s, loading takes 34.3 ÷ 1.25 = 27.4 seconds. Over 1 Gb/s, 0.125 GB/s, it takes 34.3 ÷ 0.125 = 274 seconds, about 4.6 minutes, while four GPUs that are billed by the hour sit idle. The BF16 build of 65.5 GB takes 52.4 seconds at 1.25 GB/s and 524 seconds, about 8.7 minutes, at 0.125 GB/s. A training job that saves a 65.5 GB BF16 copy of the weights every hour waits 52.4 seconds per save at 1.25 GB/s, which is 24 × 52.4 = 1,257.6 seconds, about 21 minutes of a 24-hour day. Container images and datasets add their own transfers on top.

The failures here are quiet. The server's main port can be in tenant A's segment while a second port meant for storage was never bound, because its local_link_connection was missing. The MTU, the largest packet a link carries, can be 9000 bytes on the storage network and 1500 on one hop, which cuts the rate or stalls large transfers. A security policy can block the storage port. The storage keys can point at the wrong bucket. A closed site may have no route to a public registry, so images must come from the internal registry. None of these stops Ironic from reaching active, and only a check that moves real data at the needed rate finds them.

Chapter 13 of 28

Done means the customer can log in

A finished task and a usable server are different things

Ironic now reports the node as active. That says the deployment steps ran. It does not say the customer can use the machine. A cable to one GPU can be loose, a driver can fail to load, the address can be wrong. Ironic knows nothing about GPUs, so a server with three working GPUs out of four reaches active just the same.

So the provisioner runs a readiness check from the customer's point of view: reach the server on its tenant address, log in with the issued key, count the GPUs the driver sees, and reach storage. The burn-in during cleaning proved the cards before the server was sold. This check proves the customer's view of this deployment. Only when it passes does the order move to ready, and then to active. The customer is told right after, twelve minutes after the order in this lesson's illustrative clock.

Ironic also records who uses the node. Its lessee field names a project, OpenStack's word for a tenant, here tenant A's, that uses the hardware and may be a completely untrusted customer. Default policies let a lessee use the node and hide sensitive fields, such as the BMC credentials, from it. The owner field names a delegated administrator, who may change those credentials. With conductor.automatic_lessee_source, Ironic can set the lessee during deployment. The start of active is also the moment metering opens an allocation record, so billing starts at the same instant the service does. On a Kubernetes service the NVIDIA GPU Operator would manage the driver and the monitoring instead.

Chapter 14 of 28

Provisioning prepares, scheduling places

Two words that are used for each other, and three different jobs

Provisioning prepares a usable resource. Creating a GPU VM, writing an image to a bare-metal server, configuring its network and storage, and issuing its access are all provisioning. Scheduling decides where a workload runs among resources that already exist. Choosing the GPU node for a training job, matching the GPU type it asks for, and applying queues, priorities, quotas or topology are all scheduling. In one line: provisioning prepares the resource, scheduling places the workload. A third word sits between them. Allocation assigns a resource to a tenant, a user or a workload. Provisioning can include an allocation, and it continues until the environment can be used.

This lesson shows the gap between allocation and provisioning in numbers. The Ironic allocation made gpu-srv-2 tenant A's at 1,500 ms on the clock, and the order became reserved. The server was useless for the next 718.5 seconds: no system on the disk, no tenant network, no credentials, no storage. Provisioning closed that gap, and only at 720,000 ms did the order become active. A server can be allocated and still unusable because the network is incomplete, the image is not installed, the credentials are missing or the storage is not attached. The box on the board labelled Scheduler does allocation in this sense: it places orders on servers. It does not place programs on GPUs.

Scheduling in the workload sense starts once a server exists. Suppose tenant A joins gpu-srv-2 to its own Kubernetes cluster. The NVIDIA GPU Operator installs the driver if needed, the container toolkit and the device plugin, labels the node and runs monitoring. The device plugin advertises the extended resource nvidia.com/gpu, so the node reports a capacity of 4 and an allocatable count of 4. From then on, every Pod that asks for nvidia.com/gpu: 1 goes through kube-scheduler. It filters out nodes without enough free GPUs, scores the rest, and binds the Pod by writing the node's name into spec.nodeName. That takes milliseconds to seconds and happens for every Pod. Provisioning the node took twelve minutes and happens once per order.

The site's own cluster shows the same split. In northlight-eu, the nodes gpu-node-1 and gpu-node-2 were provisioned long ago. When the Deployment qwen3 asked for two Pods with one GPU each, kube-scheduler placed qwen3-6f7d9c8b4-x7k2p on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t on gpu-node-2, and no server was built. A new revision of the Deployment gets new Pods with a new hash, and they are scheduled again, still with no provisioning. If every GPU were taken, a new Pod would stay Pending with a FailedScheduling event saying 0/2 nodes are available and Insufficient nvidia.com/gpu. That is a scheduling result. The remedy may be provisioning, a new order for a new server, and that is a separate job with its own minutes and states. In Kubernetes, GPU provisioning mostly means keeping a GPU-ready cluster healthy and exposing it, because each workload does not need a new machine.

Chapter 15 of 28

The same order as a GPU VM

A hypervisor replaces the BMC and the disk wipe, and the ready check changes

Some customers order vm.h100x1, a virtual machine with one GPU. Bare metal means the host operating system uses the GPUs directly, with no provider hypervisor. A GPU VM runs on a hypervisor and reaches its GPU in one of two ways. With passthrough, a whole physical GPU is assigned to one VM. The hypervisor is there, and the GPU is still not shared, so a virtualized GPU does not automatically mean a shared one. With vGPU, vendor software on the host exposes slices of a GPU to several VMs, which raises use when a customer needs less than a whole card. The steps of a VM order are different from those of ord-1042: create the VM, attach a passed-through GPU or a vGPU profile, configure network and storage, apply the image and runtime, and set up user access. There is no BMC, no network boot and no write to a physical disk, because the hypervisor host is already running.

With OpenStack Nova, passthrough needs a prepared host. Nova's guide lists VT-d enabled in the firmware, the IOMMU enabled in the host kernel with intel_iommu=on or amd_iommu=on, and assignable PCIe devices. nova-compute is told which devices may pass through with [pci] device_spec, for example by PCI address or by vendor_id and product_id, and an alias gives them a name, such as alias = { "vendor_id": "10de", "product_id": "<the H100's ID>", "name": "h100" }, 10de being NVIDIA's PCI vendor ID. A flavor then asks for devices by alias. Nova's own example is openstack flavor set m1.large --property "pci_passthrough:alias"="a1:2", two devices of alias a1. The scheduler needs the PciPassthroughFilter to place such flavors.

vGPU needs the vendor's vGPU manager on the host. For NVIDIA GPUs that support SR-IOV, the virtual functions are enabled first, for example with /usr/lib/nvidia/sriov-manage -e and the slot address. Then [devices] enabled_mdev_types names the vGPU type the host offers, nvidia-35 in the guide's example. Each type can get its own section listing which physical GPUs carry it and, since Xena, an mdev_class that sets its resource class in Placement, VGPU by default. A flavor asks with resources:VGPU=1, and the scheduler asks Placement for a host with that resource free. Nova's guide says that, as of the Queens release, all hypervisors accept only a single vGPU per instance. A newer part of the same guide, marked as changed in version 33.0.0, asks for more than one through separate request groups, resources1:VGPU=1 and resources2:VGPU=1. Nova warns that changing a host's type while instances of the old type exist leads to NoValidHost, so a new type goes on new hosts.

The ready check changes with the form. Nova reports the server status as ACTIVE when the VM is running. That says the hypervisor's work is done, just as Ironic's active did. The customer's view is checked inside the guest. With passthrough, nvidia-smi in the guest lists one whole H100 with its full 80 GB, and the guest image must carry the driver. With vGPU, the guest sees a vGPU with its share of the memory, and it needs NVIDIA's vGPU guest driver and licence. The size of the slice decides what fits. The FP8 build of Qwen3-32B, 34.3 GB, fits one passed-through 80 GB H100 with room for the KV cache. A slice with 20 GB of memory, an illustrative size, cannot even hold the weights. The way back is shorter too: the VM is deleted, its device returns to Placement, and the host stays up.

Chapter 16 of 28

Watching a server while it is rented

Ironic keeps checking power and the BMC while the customer works

Active does not mean Ironic stops looking. Each conductor periodically compares the power state in its database with the power state the BMC reports. With force_power_state_during_sync set to True, the default, the database wins and the hardware is made to match it. A customer who shuts the server down from inside the operating system, without telling the API, would therefore find it switched back on at a later sync. The supported way to power a rented server off is through the provider's API, which updates the database first. The sync retries a failed reading up to power_state_sync_max_retries, 3 by default.

If the BMC stops answering, the node goes into maintenance, its fault field is set to power failure, and the reason is stored in maintenance_reason. A node in maintenance is never handed out by an allocation. Every power_failure_recovery_interval, 300 seconds by default, the conductor tries the BMC again and clears the fault when it answers. Maintenance that an operator set by hand is never left automatically. Ironic does not rotate BMC passwords, because of the risk of locking everyone out. After a password is changed on the BMC, the node sits in maintenance until driver_info is updated and maintenance is unset.

An active node also accepts other verbs. rebuild writes the image again and returns to active. rescue boots a ramdisk with a password for a user named rescue, so the customer can repair a system that no longer boots. Servicing runs steps, such as firmware updates, on an active node and returns it to active. Retiring marks a node to leave the pool: when its instance is deleted it is cleaned and goes to manageable, and provide is refused.

Chapter 17 of 28

A pipeline orders through the API

GPU capacity is often consumed by other programs, so the API is the product's real front door

Much GPU capacity is ordered by software. MLOps platforms, training pipelines, job schedulers, internal developer platforms and CI/CD systems need to create a server, inspect its state, change it and end it without a person clicking. The portal is one client of the same API. Everything tenant A did in the portal for ord-1042, a program must be able to do with calls, and with the same checks of identity, entitlement and quota.

A pipeline should not log in with an engineer's password. OpenStack's identity service offers application credentials for this. One is created by a user for one project and carries a subset of that user's roles. Keystone generates a secret, or accepts one, and stores only a hash of it, so a lost secret cannot be read back and a new credential has to be made. By default an application credential may not create or delete other application credentials, a guard that stops a stolen one from renewing itself, and --unrestricted lifts that guard. It can carry an expiry with --expiration. Access rules narrow it further, for example to POST on /v2.1/servers of the compute service only. Northlight's order API accepts such a credential the same way the portal accepts a user's token, which is an illustrative design.

Tenant B runs a nightly fine-tuning pipeline. At 10,000,000 ms on the lesson's clock it orders bm.h100x4. Its quota allows it: tenant B holds 4 GPUs of a quota of 10, and 4 + 4 = 8. Had the same call come from tenant A, it would be refused, because tenant A holds 4 of a quota of 6 and 4 + 4 = 8 is over 6. The call is asynchronous. With Nova in front of Ironic, a create is POST /v2.1/servers and answers 202 with the server in BUILD. The pipeline then inspects it with GET /v2.1/servers/{id} until the status is ACTIVE or ERROR. A program that times out and simply calls create again can end up with two servers. It should give the server a unique name and look for it with GET /v2.1/servers?name=… before trying again.

Modify and terminate are calls too. At 30,000,000 ms the pipeline rebuilds the server with a newer image, POST /v2.1/servers/{id}/action with a rebuild body. Nova shows REBUILD, and underneath Ironic runs its rebuild verb, from active through deploying back to active. The order stays active and the server stays tenant B's, so those minutes are held time. At 46,000,000 ms the pipeline ends the order with DELETE /v2.1/servers/{id}, which answers 204, and the server goes through deleting and cleaning like any other. A locked server answers 409. Metering counts from active at 10,720,000 ms to terminating at 46,000,000 ms: 35,280,000 ms, which is 9.8 hours, times 4 GPUs is 39.2 GPU-hours, and at 5,000 units a GPU-hour the charge is 196,000 units. Cleaning ends at 49,600,000 ms and gpu-srv-3 is available again.

Chapter 18 of 28

The way back

Taking a server back is as much work as handing it out

A day later tenant A ends the order. It moves to terminating, and metering closes the allocation record at that moment. The provisioner asks Ironic for the target deleted. The node goes to deleting, where Ironic removes what it set up, then into cleaning. Automated cleaning is on by default, through conductor.automated_clean. It runs at two moments: when an active node is given back, and when a manageable node is first made available, before its first customer.

Which steps run is chosen by conductor.automated_cleaning_step_source. The default, autogenerated, collects the clean steps of the node's interfaces and orders them by priority. runbook runs the steps of a runbook assigned to the node, and a node with none assigned fails to clean. hybrid uses a runbook when one is assigned and the generated list otherwise. While cleaning runs, nobody may change the node's power through the API, because a step such as a firmware update must not be cut off.

The owner's rule for renting bare metal applies here: no data can remain between rentals. Ironic's default set concentrates on the disks. Returning many servers at once has a limit too. conductor.max_concurrent_clean, 50 by default, caps the nodes that may be deleting, cleaning or in clean wait at the same time. A request over the cap is rejected with ConcurrentActionLimit, and it is not queued, because the cap is a safety mechanism. A provider whose large customer leaves at once has to pace the returns itself. Deployments have their own cap, max_concurrent_deploy, 250 by default.

Chapter 19 of 28

Inside the wipe

The agent erases the disks, and every minute of it is capacity that cannot be sold

Cleaning has two kinds of step. In-band steps are run by the agent in the ramdisk, at Ironic's request. Out-of-band steps are run by the BMC through the power or management interface. While the conductor runs an out-of-band step or prepares the ramdisk, the node is in cleaning. While it waits for the ramdisk, the node is in clean wait. If the ramdisk does not report back within clean_callback_timeout, 1800 seconds by default, the node goes to clean failed.

The agent's default steps erase disks. erase_devices_metadata, priority 99, removes partition tables and file system signatures first, so the node can never boot back into the old tenant's system. erase_devices, priority 10, then wipes each disk, with ATA or NVMe secure erase where the drive supports it. Both priorities come from the ramdisk's generic hardware manager. Two different cases follow when secure erase is not the answer. If a drive does not support secure erase at all, the agent's code moves on to shred by default, which overwrites the disk once with random data and then with zeros. That is why a disk without secure erase can take hours or days. If a secure erase is attempted and fails with an error, cleaning fails, to protect the data. Only with continue_if_disk_secure_erase_fails set to True, False by default, does the agent fall back to shred in that second case. Ironic's cleaning page describes the fallback as if it applied to both cases, and the agent's code is the more precise source. Recent agent code also has an opt-in discard erase for drives whose firmware has locked secure erase, off by default. Up to 4 disks are erased at once by default. A third step, erase_devices_express, added in Yoga, uses hardware erase on NVMe drives and metadata erase elsewhere. It is off until the other two are set to 0 and it is given a priority such as 95.

Much is off by default: RAID reset, the CPU, memory, disk, network and GPU burn-in steps, and erasing pstore, where the kernel keeps crash records. When a step fails, the node goes to clean failed and into maintenance. Recovery takes three commands: manage, then maintenance unset, then provide, and cleaning starts again from the beginning.

Chapter 20 of 28

When the network step fails

The GPUs are reserved, and the customer has nothing

Tenant A places a second order, ord-1043. The scheduler reserves gpu-srv-3. The image is written. Then binding the tenant's switch port fails. Because neutron.fail_on_port_binding_failure is true by default, Ironic aborts the deployment and the node lands in deploy failed. The order is now in the most expensive place it can be: four GPUs are taken out of the pool and nobody can use them. Ironic aborts on purpose. The other outcome would be a server reported as active while it still sits on the provisioning network.

The state names tell an operator where to look. A state ending in ing, such as deploying or cleaning, means the conductor is working and holds a lock on the node. A state containing wait means Ironic is waiting for another component, usually the agent. A second change sent while a lock is held gets HTTP 409 with a message that the node is locked by a named host, which is normally safe to retry after a few seconds. A failed state such as deploy failed means the work has stopped and needs a decision.

The reason is in last_error. Every time that field is set, Ironic also adds an entry to the node's history, which baremetal node history list shows, up to 300 entries per node. When a deployment fails, Ironic fetches the ramdisk's logs by default and stores them under /var/log/ironic/deploy as a tar.gz archive named after the node and the time, holding the journal and the output of ps, df, ip addr and iptables. For a binding failure the usual suspects are a local_link_connection that no longer matches the cabling, a switch the networking service has no driver for, or a misnamed network.

Chapter 21 of 28

Retry, undeploy and release

Each part has a duty, and the server is free only when Ironic says available

The provisioner owns the retry, and Ironic allows a new deploy from deploy failed with the target active, deploy or rebuild. In this lesson it retries three times, four attempts in all, and every attempt fails. After the last one the provisioner must undeploy, which sends the node through deleting and cleaning back to available. The server is cleaned even though no customer ever logged in. Its disk holds a written image and a config drive with the customer's key, and it may sit on the wrong network. A failed server goes through cleaning before it counts as free.

The allocation goes away by itself when the node is unprovisioned, so the undeploy also releases the claim. The scheduler then counts the four GPUs as free again. Had the order been abandoned before any deploy, the allocation would have stayed until someone deleted it. If the operator wants to fix the cabling record first, the node is moved to manageable, the port's local_link_connection is corrected, and provide runs cleaning again before the node returns.

The order service sets the state to failed and tells the customer. Metering never opened an allocation record, because the order never reached active, so there is nothing to bill. The provider carries the whole cost: from reservation at 93,600,000 ms to available at 98,000,000 ms is 4,400,000 ms, about 73 minutes, so 4 GPUs × 73 ÷ 60 is about 4.9 GPU-hours that could not be sold.

Chapter 22 of 28

Cancelled while it is being built

The customer changes its mind, and the half-built server still has to be wiped

Tenant A orders bm.h100x4 again, ord-1045, at 98,200,000 ms. The scheduler reserves gpu-srv-2, which came back to the pool at 90,000,000 ms, and the deployment starts. Five minutes later, at 98,500,000 ms, tenant A cancels. Nothing about the server changes because of a click. The order service has to bring the node back to available by a path Ironic allows, from whatever state the node is in at that moment.

Ironic's state machine decides the path. In wait call-back, where the conductor waits for the ramdisk to boot or to finish writing, the deployment can be interrupted with the deleted or undeploy verb, and the node goes through deleting and cleaning to available. In deploying the conductor is working and holds a lock on the node, so a second change answers HTTP 409 with a message that the node is locked by a host. The order service then keeps the cancel request in its own record and sends it again once the node reaches a state that accepts it: wait call-back, deploy failed or active. If the deploy finishes before the cancel lands, the node is active and undeploy works from there. Every path ends in cleaning, because the disk may already hold the customer's image and the config drive with its key.

The order ends in a state of its own, cancelled. Failed would say the provider could not deliver, and that would count against the provider's SLA. Cancelled says the customer withdrew. The catalogue's cancellation rule decides the money. Northlight's on-demand item charges nothing for an order cancelled before active, because billing only starts at active, and no metering record was ever opened. A reservation item such as bm.h100x4.r7d could carry a cancellation fee in its contract. The provider still pays in capacity: from the reservation at 98,200,000 ms to available at 101,800,000 ms is 3,600,000 ms, one hour, so 4 GPUs × 1 hour = 4 GPU-hours could not be sold. The allocation goes away with the undeploy, as it did for ord-1043.

Chapter 23 of 28

Six of eight: when part of an order is ready

A multi-server order needs a state per server and a rule for the whole

Distributed training needs several servers at once. A customer that orders eight bm.h100x4 servers, 32 GPUs, may find six of them ready and two failing their checks: 24 GPUs usable, 8 missing. The order cannot be described by a single state any more. It needs a line for each server with its own state, and a rule that rolls the lines up into the state the customer sees.

The catalogue item sets the rule, and three are common. All or nothing: the order stays in provisioning until every server is ready, which suits a training job that cannot start on fewer GPUs. The provider then holds the ready servers unbilled. With six ready servers waiting four hours for two replacements, that is 24 GPUs × 4 hours = 96 GPU-hours that can be neither sold nor billed. Partial acceptance: the customer is asked, and if it accepts, the ready servers become active and are billed while the missing ones are replaced or dropped. Replace: the provider swaps the failing servers for spares, if any are free, and the order waits for them. Whichever rule applies, billing follows each server's line. Metering opens a record for a server only when that server is active for the customer.

On the board the order is smaller. Tenant A's account team has raised its quota to 8 GPUs under a negotiated contract, an illustrative change, and tenant A orders two servers for one job, ord-1046, at 102,000,000 ms. gpu-srv-2 passes its readiness check. gpu-srv-3 reaches Ironic's active, and its readiness check finds three GPUs where four were expected. Ironic knows nothing about GPUs, so only the check catches it. Northlight's rule for this item is all or nothing with an offer of partial acceptance. Tenant A accepts one server. ord-1046 becomes active with one line, the metering record covers 4 GPUs on gpu-srv-2, and gpu-srv-3 is undeployed, cleaned and moved to manageable with maintenance set, out of sale until a technician replaces the card and burn-in counts four GPUs again. The ready server waited from 102,720,000 ms to 103,000,000 ms, 280 seconds, unbilled: 4 GPUs × 280 ÷ 3,600 = 0.31 GPU-hours.

Chapter 24 of 28

What open source gives, and what it leaves

Every part of this lesson exists as open source, except the parts that sell

Everything that moved a server in this lesson is open source. OpenStack provides infrastructure services: Keystone for identity, projects and roles, and the endpoint catalogue, Neutron for networks and switch ports, Glance for images, and Nova for compute, both virtual machines and bare metal through its Ironic driver. Ironic is the bare-metal provisioning project. It enrolls nodes, deploys them, cleans them, watches their power and keeps their history. It is a bare-metal lifecycle manager, and it is not a complete commercial GPU service by itself: it has no products, no prices, no orders, no customers' bills, and apart from burn-in it knows nothing about GPUs.

Kubernetes orchestrates containers and schedules GPUs that a vendor device plugin exposes. It offers namespaces, role-based access control (RBAC) and quotas, which help several teams share a cluster. A ResourceQuota can cap a namespace's GPUs with requests.nvidia.com/gpu: 4, and for extended resources only requests. entries are allowed, because they cannot be overcommitted. Kubernetes is still not a product catalogue, a contract system, a pricing engine, an invoice or a settlement platform.

For observability, the NVIDIA DCGM exporter exposes GPU telemetry from the Data Center GPU Manager in the Prometheus text format, on port 9400 by default, with series such as DCGM_FI_DEV_GPU_UTIL. Prometheus scrapes and stores those series and answers queries over them. Grafana draws dashboards from them, and the exporter's repository ships a Grafana dashboard. That stack shows how busy and how healthy each GPU is. It does not say which customer held a GPU under which contract, so its numbers are telemetry and never a billing record by themselves.

Add up what is left. The catalogue of products, the order record and its states, contracts, pricing and rating, invoices, settlement and SLA tracking come from none of these projects. A provider builds them, buys them, or already has some of them, such as a billing system. Licence cost is not the full cost either: open source removes the licence fee and leaves engineering, integration, testing, upgrades, security patches, incident response, billing integration and support, which a fair comparison counts over three to five years.

Chapter 25 of 28

Who owns the order from end to end

Each step lives in a different system, and someone must own the whole and keep the records in agreement

Follow one order across systems. Choose a product: the catalogue and the portal. Check identity and entitlement: Keystone and the order service's policy. Create the order or reservation: the order service. Reserve capacity: the scheduler and Ironic's allocation. Provision: Ironic, Neutron, Glance and the storage system. Create access: the config drive, storage keys and the lessee field. Measure: metering. Rate and bill: billing. Terminate: the order service and Ironic. Clean and return: Ironic's cleaning and the scheduler. That is ten steps, and each may be a different system with its own database.

Someone has to own the workflow that calls them in order, records each result and decides what to do when one fails. In this lesson that owner is the order service with the provisioner. For ord-1043 it decided to retry three times, to undeploy, to release the claim, to set failed, to tell the customer and to keep billing closed. For ord-1045 it kept a cancel that Ironic refused with 409 and sent it again. A provider either writes that owner itself around the open-source parts, or uses an integrated operations platform that provides more of it. Building it is rational when the service is internal only, the organization has strong platform engineers, deep customization matters, or a portal, identity, ordering and billing already exist. An integrated platform is worth evaluating when the service is external and multi-customer, self-service and on demand are required, platform engineering is scarce, and the list of products keeps growing. Neither wins by default.

Owning the workflow includes reconciliation, because records drift. A crash between two calls, a timeout or a manual fix leaves systems disagreeing. A reconciliation job compares them on a schedule, every 10 minutes at Northlight as an illustrative interval. Four mismatches it looks for: an order completed or failed while an Ironic allocation still exists, a claim that hides capacity, so the allocation is deleted. An order active while its node is in maintenance with a power failure fault, so an incident is opened and the SLA clock starts. A metering record still open while the order is terminating or completed, so it is closed at the time terminating began. A node available in Ironic while the order service still counts it as held, so the scheduler's count is corrected. Each fix is written to an audit log, so that usage and billing can be traced back to a customer, a resource, a time, a contract and a rate.

Chapter 26 of 28

The SLA is tracked on every order

A promise needs a clock, a record that starts and stops it, and a settlement

An SLA, a service level agreement, puts commitments in the contract: resource availability, provisioning time, support response, failure recovery and maintenance notice. Monitoring shows numbers. An SLA is an operating function that ties each promise to a definition, a record that measures it, a report and a remedy. The catalogue item says which SLA applies. For bm.h100x4 Northlight promises, as illustrative values, an order active within 30 minutes of being placed and 99.5% availability per server per month.

The provisioning promise is measured from the order record, which is one reason the record keeps a time for every state. ord-1042 went from ordered at 400 ms to active at 720,000 ms: 719.6 seconds, about 12 minutes, within 30. ord-1044, the pipeline's order, went from 10,000,000 to 10,720,000 ms, 12 minutes. ord-1046 went from 102,000,000 to 103,000,000 ms, 16 minutes 40 seconds, and the 280 seconds spent waiting for the customer's answer count against the provider unless the SLA's definition says otherwise. ord-1043 never reached active: it was reserved at 93,600,000 ms and closed as failed at 98,000,000 ms, after four attempts, and Northlight's definition counts a failed order as a miss. ord-1045 was cancelled by the customer and is excluded. So the definitions decide the result as much as the clock does.

Availability is measured from different records: Ironic's power failure faults, the fabric's port state and the reachability checks. A 30-day month has 43,200 minutes, and 0.5% of them is 216 minutes. For ord-1042's single day of 1,428 minutes, 0.5% would be about 7.1 minutes. Observability for the SLA means dashboards and alerts tied to those definitions: an order in provisioning for more than 20 minutes pages an operator before the 30-minute promise is broken, and a node that enters maintenance under an active order starts a clock.

Settlement closes the period. Billing rates the usage, applies credits as negative lines and produces the invoice before it is final. Northlight's illustrative remedy for a missed provisioning promise is one hour of the item's price, 4 × 5,000 = 20,000 units, credited to the next bill. Tenant A's lines for the period are ord-1042, 4 GPUs for 23.8 hours, (86,400,000 − 720,000) ÷ 3,600,000 = 23.8, which is 95.2 GPU-hours or 476,000 units, ord-1045 at zero, the 20,000-unit credit for ord-1043, and ord-1046, still open and billed at the period's end. Where no invoice is sent, as between departments or members of a consortium, settlement is the transfer of the same amounts between the parties.

Chapter 27 of 28

Testing the walls between tenants

Before a server returns to sale, the walls between tenants are tried from the inside

A design that separates tenants is a claim until someone tests it. The boundaries are identity, network, storage and workload access, and each can fail through one wrong setting: a role with too wide a scope, a switch port left in the wrong segment, a storage key with too broad a policy, an SSH key that was never removed. A provider that scores ten out of twelve on a readiness list can still be unsafe if one of the two missing items is tenant isolation, customer data handling, billing correctness, access revocation or failure recovery. Those critical controls are validated first, and the rest of the workflow is then tested for repeatability.

Northlight runs an isolation test before a repaired server returns to sale, after any change to switch software, and before a new item goes on sale. gpu-srv-3 has its new card and has passed burn-in with agent_burnin_gpu_count set to 4. It is deployed into a test project in its own segment, and from there the test tries each wall it can reach: network, management, storage and identity. It sends traffic to tenant B's server gpu-srv-1, which must find no route. It tries the BMC network, 10.9.0.11 to 10.9.0.13, which must not answer. It presents test-tenant storage keys for tenant B's bucket, which must be refused. It asks the order API for tenant B's orders with a test-tenant token, which must answer 403. It reads Ironic's node record as a lessee, where the BMC password must come back masked. It checks the record of the cleaning that ran before this deployment, where erase_devices_metadata and erase_devices must both have completed. The disk itself can no longer show this, because writing the test image has just created a new partition table on it.

Each test expects a refusal, and a test that succeeds is a failure of isolation. The results go into the node's record and the change log, so the next audit can see what was proven and when. When every check refuses, the test deployment is undeployed and cleaned like any other, and gpu-srv-3 becomes available.

Chapter 28 of 28

Adding a GPU model without a new way of working

New hardware should arrive as new data, while the order machine stays the same

A provider grows by adding GPU models, servers, sites and items. The test of its operating model is whether each addition is new data or new engineering. Northlight adds servers with eight H200 GPUs, each H200 with 141 GB of memory, 8 × 141 = 1,128 GB per server. What changes is a list of records. Ironic gets new nodes, enrolled with create, checked with manage and validate, given a resource class gpu-8xh200 and the trait CUSTOM_NVLINK, burned in with agent_burnin_gpu_count set to 8, and made available with provide. A new site would be a new conductor group, set on each node with baremetal node set --conductor-group, so conductors near the hardware drive it. A flavor asks for resources:CUSTOM_GPU_8XH200=1 with the standard counts at 0. The catalogue gets bm.h200x8 with its own price, eligibility and template, whose readiness check expects 8 GPUs. The approved images must carry a driver that supports the H200.

What must not change is the machine around them. The nine order states, the allocation call, the deploy steps and their priorities, cleaning, the readiness check's structure, the metering record, the billing rules, the SLA tracker and the reconciliation job all work for the new item as they are. If adding the H200 needed a new order state, a new billing code path or a special cleaning script written by hand, the operating model would be rebuilt for each model, and the provider would be back to custom solutions.

The new hardware also changes what fits. Qwen3-32B's BF16 build, 65.5 GB, fits one H200 with 141 − 65.5 = 75.5 GB left for the KV cache, so a customer can serve the full-precision build on a single GPU. On an 80 GB H100 the same build leaves 14.5 GB, which is why this lesson's world serves the FP8 build, 34.3 GB, on H100s. A new item therefore needs its own description in the catalogue, so customers can pick by what they want to run.

What to keep

A state machine with money attached

Provisioning a bare-metal GPU server is a chain of small, checkable steps: reserve, reach the BMC, boot from the network, write the image, move the network, issue credentials, check. Ironic gives each step a state on the server and a priority in its list, and it records every failure where an operator can read it. The provider's order adds the states a customer and a bill care about. The two points to keep are these. An order is active when the customer can log in and see their GPUs, and billing starts at that moment and stops when terminating begins. And a server that is being built, wiped or stuck in a failed state is capacity the provider has paid for and cannot sell. Around that chain sits the commercial layer that turns it into a business: a catalogue whose items carry their own provisioning template, self-service and an API so that people and pipelines can order without a ticket, order states that keep cancelled apart from failed and track each server of a multi-server order, a workflow owner that reconciles every system's record, an SLA measured from those records, isolation that is tested before a server returns to sale, and new GPU models added as data while the order machine stays the same.
