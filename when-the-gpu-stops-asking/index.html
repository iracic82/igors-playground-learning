GPU and hardware

When the GPU stops asking the CPU

A GPU thread rings its own doorbell

In every GPU workload you have seen so far the CPU does the asking. It writes the commands, adds the ring entry, moves the write index and rings the doorbell. The GPU answers and never starts anything by itself. That puts the host CPU in a convenient place: it sees every transfer being requested, so the host is where you would enforce a rule about what data moves where. Now take the CPU out of that position. Let it prepare a copy on an H100 PCIe card but leave the doorbell alone, and have a thread on the GPU ring it. This lesson follows the experiment from the owner's series Under the Endpoint Picker, built on Maxime Peim's series that rebuilds CUDA's copy path from raw bytes: the launch descriptor, the six instructions, the two faults, the test on plain memory, the doorbell mapping, the store and the copy. Then it follows the same idea into products that ship today, and ends with the hard question it raises: where policy has to live when the host no longer sees the data move. The code is public: the tracing tools are in github.com/maxime-peim/libcuda-research, the CUDA-free library in github.com/maxime-peim/libmc, and the doorbell-catching method comes from Yan, Karlin and Grant, arXiv:2604.26889. All of it was written for Hopper, and a chapter shows what changes on a Blackwell card.

Chapter 1 of 15

The CPU does the asking

How every copy starts today

Start with the ordinary path, because the experiment only changes its last step. A model server such as vLLM wants 4 MiB of KV cache moved from GPU memory to host memory. The CPU never moves those bytes itself. It writes a short list of commands, called methods, into a pushbuffer in ordinary memory. It writes an 8-byte entry into a ring called the GPFIFO that points at that pushbuffer and gives its length in 4-byte words. Then it moves the ring's write index, GPPut, forward by one. GPPut lives in a small per-channel page called USERD, at offset 0x8c.

None of that wakes the GPU. The GPU's front end is not polling host memory. So the CPU rings a doorbell: one 32-bit store of the channel's token to a register at offset 0x90 in the GPU's 64 KiB user-mode aperture. The token names the channel: bits 11 to 0 carry its number and bits 22 to 16 carry its runlist. The front end reads the ring entry, fetches the commands, and hands them to the copy engine.

Order matters. The CPU's mappings of these regions are write-combined, so stores can leave the processor in a different order than they were written. If the doorbell overtook the ring entry, the GPU would fetch a half-written entry and report Xid 32, a bad command stream. So the CPU puts a store fence, sfence on x86, between the steps.

Measured on an H100 PCIe card in the series this lesson follows, the whole submission, command, entry, index and doorbell, takes about 350 nanoseconds for a 4 MiB copy, against about 130 microseconds for the copy itself. No system call and no firmware call happen per copy. All the expensive work was done once, at setup. That is the position this lesson takes apart: the CPU decides when every transfer starts.

Chapter 2 of 15

Prepared, and not sent

Channel A is ready and silent

Now the experiment. The CPU starts as it always does, on one channel, call it A. A channel is one of the GPU's independent work queues, with its own pushbuffer, ring and USERD page. It writes a copy-engine command into the pushbuffer. In the library used for this experiment, libmc, that command is 18 words, 72 bytes. It binds the copy engine's class, 0xC8B5, to subchannel 4, gives the source and destination addresses and a byte count, and launches the copy with the value 0x182: run it as one unit, linear memory on both sides, no flush and no semaphore. A second launch, 0x00c, moves no data. It flushes the copy's writes and then writes a 4-byte completion value to a semaphore the CPU can watch.

Then it adds the ring entry and moves GPPut forward, with the same fences as always. And then it stops. It does not ring the doorbell.

From the GPU's point of view nothing has happened. Its front end is not watching host memory, and nobody has told it to look. A complete request for a 4 MiB copy from GPU memory to host memory sits ready, with GPPut one ahead of GPGet, waiting for a signal that the CPU is not going to send.

Nothing in those 18 words says which way the data goes. Swap the two addresses and the same command copies in the other direction. In this test the source is a 4 MiB pattern in GPU memory, staged there earlier, and the destination is pinned host memory that was zeroed first, so a successful copy is easy to check.

Chapter 3 of 15

A program for the GPU, by hand

Three things CUDA normally builds for you

On a second channel, B, the CPU will launch a tiny program on the GPU's compute cores, the streaming multiprocessors or SMs. Writing the program is trivial. Launching it without CUDA is the hard part, because three things have to be built by hand that the CUDA driver normally builds in the background.

The first is a launch descriptor. NVIDIA calls it a QMD, queue meta data. On Hopper, the H100's generation, the format is version 4 and 384 bytes long, 96 words of 4 bytes. It describes the program's address, the grid of blocks and the threads in each block, how many registers each thread uses, and which constant buffers to bind. For this launch it says one block of one thread, eight registers, and constant buffer 0.

The second is that constant buffer, called CB0. The compiled program reads its arguments from fixed offsets in it, so the arguments are laid out where the machine code expects them. There is no calling convention as on a CPU.

The third is the program itself, the GPU's native machine code, called SASS. It is compiled ahead of time for this one GPU generation and embedded in the library as a 256-byte image. No compiler runs at launch.

Channel B is bound to a different class than channel A: HOPPER_COMPUTE_A, class 0xCBC0, on subchannel 1. Two methods start the launch. SEND_PCAS_A carries the QMD's address shifted right by 8 bits, which is why the QMD must sit on a 256-byte boundary. SEND_SIGNALING_PCAS2_B with the value 0x0a tells the scheduler to invalidate, prefetch, copy and schedule it. The QMD, CB0 and program do not have to be in GPU memory. They live in host memory, mapped into channel B's GPU address space, where the GPU can read them.

Chapter 4 of 15

Six instructions

What the one-line kernel becomes

The program's source is one line inside a function that takes two arguments, a pointer dst and a 32-bit token: *dst = token. Store the token at that address. One block with one thread runs it. On the hardware that thread still runs inside a warp, the group of 32 threads an SM schedules together, with only one of them active.

Compiled for Hopper it becomes six instructions on the way to the end. Three LDC instructions load constants into registers: a stack value from offset 0x28 of CB0, the token from offset 0x218, and the 64-bit destination address from offset 0x210. A ULDC.64 loads a 64-bit descriptor from offset 0x208 into a uniform register. Then STG.E.STRONG.SYS stores the token at the destination. EXIT ends the thread.

So CB0 needs three things filled in. At 0x208, 8 bytes of zero. In the ABI this kernel was tested with, a zero descriptor lets the store use dst as a plain GPU virtual address. At 0x210, the destination address, written as two 32-bit halves. At 0x218, the token. Everything else in CB0 is zeroed. These offsets come from the compiled machine code, and the QMD has no say in them.

STG is a global store. STRONG marks it as a strong operation in NVIDIA's memory model, one that takes part in ordering between threads and devices, unlike an ordinary weak store. SYS is the scope: the store must become visible system-wide. Scope names who must be able to see the write. It does not say which wires the write travels on. That difference matters when the destination becomes a doorbell.

The image in the library is 256 bytes, longer than six instructions, because it ends with a branch to itself and padding.

Chapter 5 of 15

Two faults on the way

The Xid codes said which layer was wrong

It did not run the first time, and how it failed is half the lesson. NVIDIA GPUs report faults as Xid codes in the kernel log, which dmesg shows. Each code names the part of the GPU that gave up, and that was the debugger for this whole series.

The tempting shortcut was to capture a launch descriptor from a real CUDA launch, patch the program and argument addresses, and submit it. The result was Xid 31, an MMU fault: HUBCLIENT_SKED faulted at address 0x0. SKED is the GPU's scheduler. It had tried to read virtual address zero. The report named the client and the address but not the field. The captured descriptor carried state that only made sense inside the CUDA process it came from, and patching a few known pointers did not make it valid elsewhere.

So the descriptor was built from nothing, with the open-source Mesa NVK driver as the guide to what each field means: version and launch defaults, the program address, a one-block grid, a one-thread block, eight registers and the CB0 binding. Only 13 of its 96 words ended up non-zero, all of them written on purpose, and the scheduler fault went away.

The next error was Xid 13, reported as an SM warp exception with an invalid address space. The failure had moved from the scheduler into the SM, which meant the launch now worked and the program itself hit something. The setup had borrowed NVK's base for the shared-memory window, 0x100000000, chosen to meet that window's 4 GiB alignment. The scratch address the test wrote to, 0x120c00040, sat in the region that choice covered. Moving the window base to 0x400000000, 16 GiB, removed the exception.

Read together, the two codes split the problem in layers. Xid 31 sends you to addresses and mappings. Xid 32 sends you to the command stream. Xid 13 inside an SM sends you to what the program touched.

Chapter 6 of 15

Test the store on plain memory first

Prove the thread wrote before pointing it at a register

Before the program is given a doorbell, it is given something harmless: one cell of ordinary GPU memory. If the store goes to the wrong place there, nothing else breaks.

The library maps that scratch allocation twice. Channel B gets a GPU virtual address for it, which is what the program will store to. The CPU gets an alias through BAR1, a window in the GPU's PCIe address range that exposes GPU memory to the host. With the two mappings, the CPU can set the cell, the GPU can write it, and the CPU can read the result.

The test does four things. It asks the library for the scratch cell's CPU pointer and GPU address. It writes 0xcafebabe into the cell and different sentinel values into the cells around it, then issues an sfence so those writes are out before anything else happens. It launches the one-store kernel with the cell's GPU address as dst and 0xdeadbeef as the token, and waits for the launch's completion semaphore. Then it reads back through the CPU alias.

The pass condition is the value, not the completion. A kernel can finish and leave the cell untouched, and a semaphore would still say done. So the test checks that the cell now holds 0xdeadbeef and prints the neighbouring cells as well, so a store that landed one word off would show up as a changed sentinel.

It passed. That proves three things at once: the hand-built launch works, the arguments are where the code reads them, and the store reaches the address it was given. Only the destination changes in the next step.

Chapter 7 of 15

A doorbell the GPU can reach

The register has to exist in the GPU's own address space

Now the real destination. A GPU thread can only store to addresses in its channel's GPU virtual address space. The CPU's pointer to the doorbell is a CPU virtual address. Passing it to the kernel would be meaningless, because the SM translates addresses through the GPU's own page tables, which know nothing about the process's CPU mappings.

So the doorbell's region gets a second mapping. The region is the user-mode aperture object, HOPPER_USERMODE_A on Hopper, the same 64 KiB page whose offset 0x90 is the doorbell. The library allocates it with the flag bBar1Mapping set to true. It then asks the kernel driver to map it into an address space the driver manages for channel B, through the call NV_ESC_RM_MAP_MEMORY_DMA. The driver returns a GPU virtual address. That address plus 0x90 is what goes into CB0 as dst.

Channel A is set up differently. Its copy runs in a separate address space managed by the unified-memory driver, nvidia-uvm, the same one the earlier copies used. Channel A's source and destination buffers do not need to be mapped into channel B's space at all. The thread never touches the data. All it writes is the 32-bit token that identifies channel A.

The token itself follows the same layout the CPU uses: channel number in bits 11 to 0, runlist in bits 22 to 16. In this lesson it is shown as 0x0000_0e03. That value is illustrative.

Chapter 8 of 15

One thread, one store

The GPU rings the doorbell

The CPU now does the last thing it will do for this copy. It rings the doorbell once, for channel B, to start the little program. It does not ring channel A's.

The front end reads channel B's ring entry and the launch methods. The scheduler reads the QMD and starts one thread on one SM. The thread loads its constants and executes its single store: the token for channel A goes to the doorbell's address. The doorbell register cannot tell who wrote it. The front end sees a token for channel A and goes to fetch the work the CPU left there, exactly as if the CPU had rung.

The name of the allocation flag, bBar1Mapping, suggests the store might leave the card and come back over PCIe. NVIDIA's open driver source describes the flag as enabling both BAR1 use and internal MMIO, and on Hopper the GPU-side mapping points at hardware registers with caching disabled. What the experiment shows is narrower: the store reached the doorbell and the prepared copy ran. No PCIe transaction for that store was captured, and the owner's write-up of the run reports none seen leaving the card, so the experiment does not prove the route either way.

The test also does not show that the copy engine sat idle until the store. It shows a side effect: work that only a doorbell write could start did start. And the SM did not copy anything. It wrote 4 bytes. The 4 MiB is still moved by the copy engine.

Chapter 9 of 15

The copy runs

Started by the GPU, checked twice

The rest is the ordinary path. The front end reads channel A's ring entry and the 72 bytes of commands it points at, and the copy engine moves the 4 MiB pattern from GPU memory into pinned host memory. Then the second launch in the command flushes the writes and releases channel A's semaphore.

There are now two completions, and they belong to different things. The compute launch on channel B has its own report semaphore. The copy on channel A has the copy engine's semaphore. The CPU waits for the first, then separately polls the second. Seeing the first is no substitute for the second: the thread can be done long before the 4 MiB has landed. The order the CPU checks them in also says nothing about which finished first on the GPU. Only after both does the test compare the bytes.

The chain test sets itself up with an ordinary copy. A known pattern is staged into 4 MiB of GPU memory by a normal host-submitted copy, which does use a CPU doorbell, and the host destination is zeroed. Then the device-to-host copy under test runs, rung by the SM. The pattern arrived intact and no Xid was reported.

The test did not time the copy. The earlier parts give the scale. A 4 MiB device-to-host copy on this H100 PCIe card measured about 31.3 GB a second, about 130 microseconds, of which an estimated 15 were submission and completion overhead. That is more than the 350 nanoseconds of the first chapter, which counts only the CPU's writes. The 15 microseconds also hold a few microseconds from doorbell to dispatch, then the flush, the semaphore becoming visible and the CPU's poll. Larger copies reach about 55 GB a second. The overhead explains only part of that gap, and the series leaves the rest open.

The CPU still did a lot: it wrote channel A's command, ring entry and GPPut, and it launched the kernel. The SM only did the last write. The next step in the series moves the rest onto the GPU: the SM writes the commands, the ring entry, GPPut and the doorbell itself, with those structures in GPU memory. That brings back the ordering problem from the first chapter, now between an SM and the GPU's own command fetcher.

Chapter 10 of 15

What carries over to another GPU

The ideas move to any NVIDIA GPU. The bytes of Parts 4 to 6 do not.

Everything in the experiment so far was measured on one card, an H100 PCIe, which belongs to NVIDIA's Hopper generation. Much of what it wrote was a number that only Hopper understands. That matters the moment you try to repeat it on something else, such as an RTX PRO 5000, which is a Blackwell card. The owner's own lab machine has one, and the code from Parts 4 to 6 of the series will not run on it as it stands. The observations from Parts 1 to 3 mostly will.

Start with what changes. Every object the driver creates has a class, a 16-bit number that names the hardware interface and its generation. The values in this lesson are Hopper's: HOPPER_USERMODE_A is 0xC661, HOPPER_CHANNEL_GPFIFO_A is 0xC86F, HOPPER_DMA_COPY_A is 0xC8B5 and HOPPER_COMPUTE_A is 0xCBC0. NVIDIA's open kernel module headers give Blackwell its own: BLACKWELL_USERMODE_A is 0xC761, the channel classes are 0xC96F and 0xCA6F, the copy classes are 0xC9B5 and 0xCAB5, and the compute classes are 0xCDC0 and 0xCEC0. Which of the A and B classes a card uses depends on the chip. The SET_OBJECT method in the copy command of the second chapter names 0xC8B5, and the launch in the third names 0xCBC0. On a Blackwell card both have to change, together with the allocation calls that created the objects.

The launch descriptor changes more. NVIDIA's published class headers define QMD versions 3.0 and 4.0 for HOPPER_COMPUTE_A. The two Blackwell compute classes define 4.1, 5.0 and 5.1. All of them are 3,072 bits, the same 384 bytes, and the fields sit in different places. In version 4.0 the grid width is bits 1055 to 1024, word 32. In version 5.0 those same bits hold the low part of the program address, stored shifted right by 4, and the grid width has moved to bits 1279 to 1248, word 39. The register count moves from bits 1208 to 1200 to bits 1136 to 1128. The bits that say a constant buffer is valid move from bit 416 to bit 1856 for CB0. The version field itself moves from bits 583 to 580 to bits 471 to 468. So the 13 words that were set by hand for Hopper would land on the wrong fields of a version 5 descriptor. The chapter Two faults on the way showed what the scheduler does with a descriptor it cannot make sense of.

The program changes too. The 256-byte image is SASS for compute capability 9.0, which is the H100. NVIDIA lists the B200 at 10.0 and the RTX PRO 5000 Blackwell at 12.0. The CUDA programming guide is explicit that a compiled binary for compute capability X.y runs only on devices of capability X.z with z at least y. A 9.0 image is never valid on a 10.0 or 12.0 part. Recompiling it needs nvcc and cuobjdump, and the CB0 offsets 0x208, 0x210 and 0x218 then have to be read again from the new machine code, because they came from the compiled code and not from any rule.

Some values do stay. In the Blackwell channel headers, clc96f.h and clca6f.h, GPPut is still at USERD offset 0x8c, as in Hopper's clc86f.h. The doorbell offset 0x90 has been the same since Volta's usermode class, and the GB202 register manual still places the doorbell at 0x30090 with the channel in bits 11 to 0 and the runlist in bits 22 to 16. The library hard-codes these too, so a port checks every one of them against the headers for the new chip before trusting it. The fact that they matched once is no promise for the next generation.

Then there is the driver itself. libmc talks to the driver's private interfaces, which NVIDIA does not keep stable between releases. Each revision of the library pins one driver release, 610.43.02 at the time of writing, and builds against that release's source. At start, mc_init checks the loaded driver and returns MC_EVERSION on a mismatch. It then identifies the GPU and returns MC_EARCH for a chip it has no backend for. Its README lists backends for Hopper, Ampere GA100, Ampere GA10x and Ada.

The GPU-rung doorbell has one more condition. A thread can only store to the doorbell if the usermode aperture can be mapped through BAR1 and given an entry in the GPU's own page tables. HOPPER_USERMODE_A accepts the parameter that asks for that mapping, and the experiment used it. The libmc README says BLACKWELL_USERMODE_A accepts it too. NVIDIA's published header for that class, clc761.h, defines only the class number 0xC761 and no parameter struct, so this lesson could not confirm the Blackwell half. AMPERE_USERMODE_A takes no parameters at all, so on Ampere and Ada a GPU thread has no doorbell to write. The library reports this through mc_feature_supported with MC_FEAT_XFER_SM and returns MC_EUNSUPPORTED where the feature is missing. Its README says the feature is implemented and verified on H100, and that Blackwell has the aperture but no backend yet. The two repositories disagree here. The libcuda-research README calls SM-authored submission Hopper-only, because it needs a GPU-mappable doorbell page that other architectures do not expose. Until someone runs it on a Blackwell card, treat the GPU-rung doorbell as Hopper-only.

What does carry over is everything you can watch from outside. The owner's lab notes list four exercises that run on the Blackwell machine unchanged. strace -f -e trace=ioctl,mmap,openat around a CUDA program doing one big copy in a loop shows a burst of driver calls at start and silence during the copies. /proc/<pid>/maps shows the /dev/nvidia mappings, including the 64 KiB doorbell aperture. nvidia-smi --query-gpu=clocks.sm --format=csv -lms 100 shows the SM clock idling until the context warms up. sudo dmesg | grep -i xid reads the fault codes after any experiment. Parts 4 to 6 need a Hopper card, root and an out-of-tree kernel module. They were run on the H100 only. The owner's notes also name the H200, which is a Hopper card as well, but no run on one has been reported. The owner's advice is to rent a disposable cloud H100 for them, because patched GPU modules and deliberate Xid faults can wedge a GPU until it is reset, and that is not something to do on a machine that also serves models.

Chapter 11 of 15

Where the code and the method come from

Two public repositories and one paper

Everything in the first nine chapters can be reproduced, and the tools to do it are public on GitHub under the account maxime-peim. There are two repositories, and they do different jobs.

The first is libcuda-research, at github.com/maxime-peim/libcuda-research. It is a fork of NVIDIA's open GPU kernel modules, pinned at release 610.43.02, with tracing added. It answers one question: what libcuda asks the driver to do during a cudaMemcpy. Its parts are an instrumented driver that writes every resource-manager allocation and control call and every GSP message as ftrace lines, an LD_PRELOAD shim, a decoder and a tool that merges all the streams onto one clock. The kernel-side doorbell watchpoint from Part 4 lives in kernel-open/nvidia/nv-doorbell-watch.c. It is armed by default and diverts the user-space doorbell mapping to a shadow page, so the driver does not behave exactly like a stock one. The module parameter nv_dbell_disable_intercept=1 turns it off. A sample capture is checked in under reverse/traces/cuda_reference, so the decoder runs without a GPU. python3 tools/trace_section.py --trace traces/cuda_reference --section cudaMemcpy prints every kernel and system call event inside one copy. tools/phase_census.py splits a run into setup, transfer and teardown and counts the driver calls in each, which is how the copies turn out to cost none.

The second is libmc, at github.com/maxime-peim/libmc. It is the CUDA-free library this lesson calls the vLLM process's copy path: allocation, address spaces, channels, copy commands, compute launches and the GPU-rung doorbell, written against the raw RM and UVM interfaces with no libcuda underneath. Its README lists runs on H100 SXM5, A100 SXM4, L4 and A2, all on driver 610.43.02. Its H100 is the SXM board, not the PCIe card the series used, and each board has its own transfer ceiling. Its demos include mc_demo for host-submitted copies and mc_compute_dbell_demo and mc_compute_dbell_chain_demo for the experiment in this lesson. Its document docs/compute_kernel_launch.md describes the Hopper compute launch and the chain the SM starts. Running the integration demos needs root access to /dev/nvidia0, /dev/nvidiactl and /dev/nvidia-uvm and the matching kernel modules.

The method for catching doorbells comes from a paper. Yuang Yan, Ian Karlin and Ryan Grant, Revealing NVIDIA Closed-Source Driver Command Streams for CPU-GPU Runtime Behavior Insight, arXiv:2604.26889, April 2026. Its sections 5.1 and 5.2 give the four steps that Part 4 ports: divert the 64 KiB usermode mapping to ordinary memory, arm an x86 debug register on the doorbell word at offset 0x90, let the trap fire when the store lands in the shadow page, then decode the token, GPPut and the ring entry, log them and forward the token to the real doorbell. The numbers that follow are from that port, not from the paper. On the H100, Part 4 caught 174 doorbells out of 174 with no change in bandwidth and a few microseconds per trap.

The owner's series Under the Endpoint Picker tells the same story for platform engineers. The original series, Rebuilding CUDA From Scratch by Maxime Peim, is on Medium under AI Infrastructure. Read the repositories' own READMEs for the exact driver release they pin, because that changes with each revision.

Chapter 12 of 15

Not just a lab trick

Products already point the same way

Nobody will ship hand-written machine code and hand-built launch descriptors, and this exact code runs on one GPU generation only. As an experiment it is narrow. The direction is real, and some of it is already in products.

GPUDirect RDMA lets a network card read and write GPU memory directly over PCIe, without staging the data in host memory. NVIDIA introduced it with Kepler GPUs and CUDA 5.0, and since CUDA 11.4 the kernel module nvidia-peermem gives InfiniBand adapters that peer access. The host still sets up each transfer. GPUDirect Storage does the same for NVMe drives, so weights or a KV cache tier can go from a drive to GPU memory without a bounce buffer in host memory.

The step after that has the GPU start network transfers too. NVSHMEM, NVIDIA's library for one GPU writing into another's memory, gained a transport called IBGDA, InfiniBand GPUDirect Async, in version 2.6.0. With it a thread on an SM writes the network card's work request into a queue in GPU memory, updates a doorbell record, and then writes the card's doorbell register. It is this lesson's experiment, aimed at a network card. NVIDIA's published comparison shows why: with a CPU proxy thread ringing doorbells on the GPU's behalf, puts top out near 1.7 million operations a second. With IBGDA they reached 180 million, close to the card's limit of 215 million.

Mixture-of-experts models push hardest. Their tokens are sent to whichever GPU holds the right expert in the middle of a forward pass. DeepEP, a library for that dispatch and combine traffic, now does its RDMA through the GPU-initiated networking backend of NCCL, called Gin.

Follow that line and the host CPU stops being where data movement is decided. It sets things up and then watches.

Chapter 13 of 15

Why mixture-of-experts tokens travel

Many experts in memory, a few used per token

The previous chapter said that mixture-of-experts models push GPU-initiated networking hardest. To see why, look at what such a model is. Every transformer block has two halves: attention, where a token looks at the others, and a feed-forward network, a pair of large matrix multiplies applied to each token on its own. In a dense model like Qwen3-32B every token goes through the same feed-forward network in every one of its 64 layers. Every token uses all 32.8 billion weights.

A mixture-of-experts model, MoE for short, replaces that one feed-forward network with several separate ones, called experts, and adds a small router in front of them. The router is one more matrix. For each token it gives every expert a score, keeps the best few, and sends the token only to those. The layer's output is the sum of the chosen experts' outputs, each weighted by its share of the router's score. A token's choice is made again in every layer, so the same token can use different experts at different depths.

The classic example is Mixtral 8x7B, which has 8 experts per layer and uses 2 per token. Its config gives the shapes: 32 layers, a hidden size of 4,096 and an expert size of 14,336. Each expert has three matrices of 4,096 by 14,336, which is 176,160,768 weights. Eight experts in 32 layers make 45,097,156,608 expert weights. The attention weights add 41,943,040 per layer, 1,342,177,280 in all, and the input and output embeddings add 2 × 32,000 × 4,096 = 262,144,000. That comes to about 46.7 billion weights, which is the total Mistral publishes. A token uses only 2 of the 8 experts, so it touches 11,274,289,152 expert weights plus the same attention and embeddings, about 12.9 billion. Mistral's own words are that it runs at the speed and cost of a 12.9B model.

Newer models use many more, smaller experts. Qwen3-30B-A3B has 48 layers with 128 experts each and activates 8 per token. Each expert is three matrices of 2,048 by 768, 4,718,592 weights. All 128 in 48 layers come to about 29.0 billion, and the 8 a token uses come to about 1.8 billion. The model card gives 30.5 billion in total and 3.3 billion activated. The A3B in the name means about 3 billion active. The owner's own lab model, Qwen3.6-35B-A3B, goes further: 40 layers of 256 experts, 8 routed plus 1 shared expert per token, 35 billion total and 3 billion activated per its card.

Total and active parameters measure different costs. Memory follows the total. The router can pick any expert for the next token, so every expert of every layer has to sit in GPU memory all the time. Qwen3-30B-A3B in BF16 is 61.1 GB of files, close to Qwen3-32B's 65.5 GB BF16 build, and it needs the same one 80 GB H100. The FP8 build of Qwen3.6-35B-A3B is 37.5 GB of files. Compute per token follows the active count, about 2 floating-point operations per active weight, so a 3.3 billion active model does roughly a tenth of the arithmetic of the 32.8 billion dense one.

Memory bandwidth sits in between, and it depends on the batch. Generating one token at a time, a decode step reads only the weights it uses: about 3.3 billion weights, 6.6 GB in BF16, for Qwen3-30B-A3B, against all 34.3 GB of the Qwen3-32B FP8 build. With a full batch that saving fades. If 64 tokens in one step each pick 2 of Mixtral's 8 experts, and the picks were spread evenly and independently, the chance that a given expert is picked by none of them is (6/8) to the power 64, about 1 in 100 million. So in practice every expert's weights are read on every step, and a large batch of an MoE model reads as many bytes per step as a dense model of its total size.

Now spread the model over GPUs. With expert parallelism each GPU holds a share of the experts. vLLM turns it on with --enable-expert-parallel, sets the number of expert-parallel GPUs to the tensor-parallel size times the data-parallel size, and moves tokens with the backend chosen by --all2all-backend. On 4 GPUs, Qwen3-30B-A3B's 128 experts per layer become 32 per GPU. Each token's 8 chosen experts can be on any of the 4. So in every MoE layer the token's hidden state, 2,048 values or 4,096 bytes in BF16, is sent to the GPUs that hold its experts. This is called dispatch. The results come back and are added up. This is called combine. If a token's experts sit on all three other GPUs, that is 3 × 4,096 = 12,288 bytes out and the same back in one layer, and 589,824 bytes each way over 48 layers, for one token. Each MoE layer runs one dispatch and one combine, two all-to-all exchanges, on the critical path of every forward pass, with many small messages to many peers. That is the pattern where a CPU proxy ringing doorbells becomes the limit, and why libraries such as DeepEP have GPU threads drive the transfers themselves.

Chapter 14 of 15

What the host stops seeing

An assumption many security designs rest on

Security for servers has long assumed one thing quietly: the host sees the traffic. An agent on the host, a host firewall, an eBPF program attached to the kernel's network stack, a packet capture on the host's interface. Each of them works because the bytes pass through the host's memory and kernel on their way in or out.

If the GPU and the network card exchange data directly, none of them sees it. The data does not touch the host's memory or its kernel. The host prepared the path, registered the memory and created the queues, and then the path stopped needing it. Once the GPU rings the card's doorbell itself, the host does not even see when a transfer starts.

For a single team's training cluster that may be fine. Everyone on it is trusted, and the traffic is one job talking to itself.

For an AI factory serving many tenants on shared GPUs it is not. Tenant isolation, egress control, and the record of who talked to what all need an enforcement point the data really passes through.

The KV cache makes this concrete. Once the cache tier moves off the node, onto NVMe over fabrics or a remote KV store, cache traffic shares the fabric with inference traffic, across tenants. One tenant's prompt prefix becomes data on a shared network. For Qwen3-32B that is 262,144 bytes of keys and values per token, so a 24,000-token conversation is 6.3 GB of one tenant's state crossing the fabric. It is exactly the kind of traffic that will increasingly move between GPU and network card without the host in between.

Chapter 15 of 15

Where policy has to live

Two decisions that keep getting merged

The owner splits this into two decisions, because teams building AI platforms tend to merge them.

The first: is there a network boundary in the AI platform at all, one layer that owns tenancy, ingress, egress, policy and inference-aware routing? That is a choice for day zero. It does not depend on hardware, and it gets made whether or not anyone makes it on purpose. If nobody owns it, it ends up spread across a cloud load balancer, kube-proxy, an ingress controller, a service mesh and some scripts.

The second: where does that boundary run? On the host CPU, or on a DPU such as BlueField, a network card with its own Arm cores, sitting beside the GPUs on the same PCIe complex.

BNK, BIG-IP Next for Kubernetes, is built for both answers, with the same traffic engine, TMM, in each. In host mode it runs on the server's own CPU and needs no DPU, so it can be added to a running cluster later. In DPU mode it runs on BlueField, where it sees traffic that never touches the host. The two have different timelines. Host mode is the retrofit path. A DPU has to be in the bill of materials, because you cannot fit one into every node of a running fleet after the fact.

GPU-initiated I/O makes the second decision matter more over time. The more the data path moves off the host CPU, the more the DPU becomes the last point in the node where a tenant boundary can still be enforced on that traffic. In this factory, a request reaches qwen3 on gpu-2 through the BNK data plane, which takes it in at 203.0.113.80 and opens its own connection to the Pod from its address 10.20.0.5, and that is the boundary the data still crosses, whichever of the two places it runs in.

What to keep

The host steps out of the path

A thread on a GPU stored four bytes to a doorbell and started a data transfer the CPU had only prepared. Building it took a 384-byte launch descriptor with 13 of its 96 words set, a constant buffer with three arguments at fixed offsets, 256 bytes of machine code, a second mapping of the doorbell, a test on plain memory, and two Xids along the way. As an experiment it is narrow. As a direction it is where GPUDirect RDMA, GPUDirect Storage and GPU-initiated networking such as NVSHMEM's IBGDA are already going: the host sets things up and the devices talk to each other. That breaks an assumption many security designs rest on, that the host sees the traffic. So decide early that the AI platform has a network boundary, and decide where it runs. The more the data path leaves the host CPU, the more that boundary belongs where the data still goes.
