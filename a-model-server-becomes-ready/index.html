Kubernetes underneath

A model server becomes ready

Running is not ready: probes, and the three minutes a model takes to load

A web server is ready a second after it starts. A model server is not. Its process starts at once and then spends minutes reading tens of gigabytes of weights into GPU memory, and for all of that time it cannot answer a single request. Kubernetes has to be told about that gap, or one of two bad things happens. Either traffic is sent to a server that cannot answer yet, or the server is judged dead and restarted before it ever finishes loading. This lesson follows one Pod from started to ready. It shows who is asking the Pod what, exactly what the kubelet sends and how it counts the answers, how the news of readiness travels to the gateway, how a Deployment waits for it, and then the restart loop that the wrong setting produces and how to read it from outside. The two Pods are qwen3-6f7d9c8b4-x7k2p on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t on gpu-node-2. A Deployment names each Pod from its own name, the pod-template-hash of its template and a random suffix. Numbered names like db-0 are how a StatefulSet names its Pods.

Chapter 1 of 11

Running, and no use to anyone

The process is up and the port is closed

The container has started. Kubernetes marks the Pod as Running, which means only that its process exists. Inside, the model server has begun pulling 34.3 GB of weights into GPU memory. That is the FP8 build of Qwen3-32B, published as Qwen/Qwen3-32B-FP8, which stores most weights in one byte each. The full BF16 build is about 65.5 GB. Until that is done it cannot answer on its port. A request sent now would fail. The Pod has a second, separate status for exactly this: a condition called Ready. It starts out false. Everything that sends traffic in a cluster looks at Ready and never at Running, so for now this Pod is invisible to callers. That is what we want.

The Pod carries a short list of conditions, each True or False, written by the kubelet. PodScheduled is True because the scheduler placed it on gpu-node-1. PodReadyToStartContainers is True because the Pod's sandbox and network exist. Initialized is True because there are no init containers left to run. ContainersReady and Ready are both False, with the reason ContainersNotReady and the message containers with unready status: [vllm]. Each condition also records lastTransitionTime, the moment it last changed.

The three minutes are mostly not the copy. Copying 34.3 GB across a PCIe Gen5 x16 link at about 64 GB/s takes about half a second, since 34.3 / 64 ≈ 0.54 s. The copy onto the card is the short part. Most of the time goes to reading the files from wherever they are stored and to the engine's own preparation before it serves. vLLM reserves its port as soon as it starts and only begins to listen on it once the engine is built. Until then a connection to port 8000 is refused. The log line Starting vLLM server on http://0.0.0.0:8000 marks the moment it begins to listen.

Chapter 2 of 11

The kubelet keeps asking

A startup probe gives a slow start room

Nobody tells Kubernetes when the server is done. The kubelet has to find out by asking, over and over. The Pod's definition says how: an HTTP request to the server's health address every ten seconds. A request that gets no answer is a failure. For the slow first part of a container's life there is a probe made for the purpose, the startup probe. It comes with a generous allowance: here up to sixty failures in a row, which is ten minutes. While the startup probe has not yet succeeded, the kubelet runs no other probe at all. So the failures pile up harmlessly. Each one means not yet.

Inside the kubelet each probe of each container has its own worker, a small loop with a timer set to periodSeconds. The first run happens as soon as the worker starts, then one on every tick. A tick does nothing while the container has no ID or is not running yet, so the first real probe lands on the first tick after the container starts. That can be anywhere from 0 to 10 seconds after the start. This lesson draws it at 10 s.

The liveness and readiness workers tick too, from the start. Each time, they first check whether the container has started. Until it has, they return without probing. Before any probe has run, readiness counts as a failure and liveness counts as a success, so the container is not ready and is not killed. The field status.containerStatuses[0].started stays false until the startup probe passes. Without a startup probe it is true as soon as the container runs.

Chapter 3 of 11

What a probe sends and what counts as yes

A short request from the node, judged by its status code alone

A probe is one of four kinds, and each probe names exactly one. An exec probe runs a command in the container and succeeds on exit status 0. A grpc probe calls the gRPC health service and succeeds on SERVING. A tcpSocket probe succeeds if the port accepts a connection. An httpGet probe, the one used here, succeeds on any status code from 200 up to 399. Anything else is a failure, and so is a refused connection or no reply within timeoutSeconds, which defaults to 1 second.

The request comes from the kubelet's own network stack on the node. For that reason a Service name cannot be used as the host. It sends two headers besides Host: User-Agent, which defaults to kube-probe followed by the kubelet's version, and Accept: */*. Keep-alives are off, so every probe is a new TCP connection. With scheme HTTPS the kubelet skips certificate checks. It reads at most 10 KiB of the body. A larger body makes it close the connection early, which can show up in the server's log as connection reset by peer or broken pipe. Redirects to the same host are followed. A redirect to another host is not followed: the probe counts it as a success and records a Warning event with the reason ProbeWarning. The client follows at most 9 redirects. At the 10th it stops with the error stopped after 10 redirects, and that counts as a failure, so a redirect loop fails the probe.

A probe that errors inside the kubelet is tried up to 3 times in total within the same tick, which is at most 2 retries. Then the result is counted. The kubelet counts a run of equal results. The stored result changes only when a run of failures reaches failureThreshold or a run of successes reaches successThreshold. Every failure is also written as a Warning event with the reason Unhealthy.

Chapter 4 of 11

Not ready means not listed

How a Pod that cannot answer stays out of the way

While this goes on, look at what callers can see. A Service in Kubernetes is a name for a changing set of Pods, and that set is kept as a list in objects called EndpointSlices. A controller in the control plane maintains them. For every Pod that matches the Service it writes an entry with the Pod's address and a flag: ready, or not. Our Pod is on the list with ready set to false. Anything that sends traffic reads that list and skips entries that are not ready. So the second model server, which has been ready all along, gets every request, and the one still loading gets none.

An entry carries three conditions. serving copies the Pod's Ready condition. terminating is true once the Pod has been asked to stop. ready is the shortcut: serving and not terminating. The controller computes ready = publishNotReadyAddresses or (serving and not terminating). So a Service with publishNotReadyAddresses: true lists a loading server as ready, which is meant for things like peer discovery and is wrong for a model server's traffic.

A slice holds up to 100 endpoints by default, set by the kube-controller-manager flag --max-endpoints-per-slice, up to 1000. Slices this controller writes carry the label endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io. The kubelet's own probes never use this list. The owner's lab notes add a lesson from a real gateway that routes on Pod readiness: workers that turned ready before they had registered their model answered 404 for a few seconds. Ready has to mean ready for the model.

Chapter 5 of 11

Choosing the startup allowance

Longer than the slowest load, and what an operator sees while it runs

The allowance is failureThreshold × periodSeconds, plus initialDelaySeconds if one is set. The documentation's rule is plain. If a container usually takes longer than initialDelaySeconds + failureThreshold × periodSeconds to start, give it a startup probe that checks the same address as the liveness probe. Its own example allows 30 × 10 = 300 s. vLLM's example for its Rust frontend, a separate server started with VLLM_USE_RUST_FRONTEND=1 or vllm-rs that answers gRPC health checks, uses failureThreshold 120 with periodSeconds 10, which is 1200 s, with the comment Allow for model loading.

Here the load takes about 190 s and the allowance is 600 s, a little over three times the load. That margin covers a cold node whose storage is slower, or a larger model later. Too small an allowance kills the server in a loop. Too large only delays the restart of a server that truly hangs at start. Keep periodSeconds at 10 and change failureThreshold. A shorter period makes the server ready sooner after it opens its port, at the cost of more requests to it. vLLM's troubleshooting note suggests measuring the real start time first, by removing the probes and timing how long the server takes until it is ready to serve.

kubectl describe pod prints each probe on one line, for this Pod http-get http://:8000/health delay=0s timeout=1s period=10s successThreshold=1 failureThreshold=60. The empty host means the Pod's IP. Under Events the failures appear as one folded line, a Warning with the reason Unhealthy and a count. The kubelet also counts every probe in the metric prober_probe_total, with labels for probe_type and result.

Chapter 6 of 11

The answer comes

One success, and a chain of updates follows

Three minutes in, the weights are loaded and the server starts listening on its port. The next probe gets an answer: 200. One success is enough for a startup probe, and it does not run again. The kubelet sets started to true on the container. Now the readiness probe takes over and passes too. While a container is not ready, the kubelet triggers a readiness probe at once on each status update, outside the normal ten second rhythm, to make the Pod ready faster.

Now watch the news travel, because no component tells another directly. The kubelet writes Ready: True on the Pod. The controller that keeps the EndpointSlices is watching Pods, sees the change and flips the entry to ready. The gateway is watching EndpointSlices, sees that, and adds the address to the set it sends traffic to. This is a plain gateway that reads EndpointSlices and acts the moment its watch fires. An inference gateway's endpoint picker reads Pods instead, and a gateway with a data plane of its own adds time to reprogram it, as a later chapter shows. Each step is a write to the API server and a watcher reacting to it.

The numbers on this clock add up as follows. Probe 1 ran at 10 s and probe 19 at 190 s, so 18 probes failed and the 19th passed. That used 18 of the 60 failures allowed. The first request reached the new Pod at 191 s, three minutes and eleven seconds after it started. The second between the 200 OK and that request is spent on three writes and three watch notifications. On a quiet cluster each hop takes milliseconds. A busy API server can stretch them.

Chapter 7 of 11

The rollout waits for ready

A Deployment counts a Pod as available only once it is ready

The Pod belongs to the Deployment qwen3, and the Deployment controller also watches for Ready. It counts a Pod as available once the Pod has been ready for minReadySeconds, which defaults to 0. So qwen3-6f7d9c8b4-x7k2p became available at 190 s, the moment it turned ready.

This matters most during a rollout. A rolling update has two limits, maxSurge and maxUnavailable, and both default to 25%. With 2 replicas, maxSurge is 25% of 2 = 0.5, rounded up to 1 extra Pod. maxUnavailable is 0.5 rounded down to 0. So the controller may add one new Pod and may not take an old one away until a new one is available. With a model server that means the old Pod keeps serving for the whole three minute load, and is removed only after its replacement is ready. A readiness signal that came too early would let the controller remove a working server while the new one still cannot answer.

The Deployment also has a clock. progressDeadlineSeconds defaults to 600. If a rollout makes no progress for that long, the Deployment gets the condition Progressing with status False and the reason ProgressDeadlineExceeded. The controller keeps retrying. Nothing is rolled back by itself. A model server that needs an image pull of several minutes plus a three minute load can come close to ten minutes on a cold node. Raise the deadline for such servers so that a slow start is not reported as a failed rollout.

Chapter 8 of 11

Readiness keeps watching after the start

A server that stops working leaves the list without being restarted

The startup probe is done for good once it passes. The readiness and liveness probes keep running every period for the life of the container. They answer different questions. Readiness asks whether to send traffic. Liveness asks whether to restart. A readiness failure only takes the Pod out of the EndpointSlices, and the Pod keeps running.

vLLM's documentation points out that /health only checks that the server's processes are alive. It returns 200 while the engine works and 503 once the engine is dead. A server whose engine is stuck, for example in a hung collective call or after a GPU fault, can still answer 200 there. vLLM offers a second address, /health_generate, which checks that the engine can actually run the model. It answers 503 with a JSON body when the engine cannot, and the body's reason says why. engine_dead means an engine process has died. sleeping means an engine rank is paused, for example during a weight sync. probe_timeout means an engine rank did not answer in time, because its busy loop is blocked in a hung collective or one step is taking longer than the limit. probe_failed means the test pass on an idle rank raised an error. Its query parameter timeout_s sets how long vLLM waits for each engine rank before it gives up with probe_timeout, and it defaults to 20 seconds. So the probe's timeoutSeconds must be longer, for example 30, so that vLLM's own 503 arrives before the kubelet gives up. The Kubernetes default of 1 s is too short.

vLLM's advice is to use /health_generate for readiness and to keep /health for liveness. /health_generate also returns 503 while the engine sleeps for a weight update, and a liveness probe on it would restart the container in the middle of that. In this example the engine hangs at 300 s in a stuck collective call. Each readiness probe now waits the 20 s of timeout_s, and then vLLM answers 503 with the reason probe_timeout. That is inside the kubelet's 30 s, so each probe is a clean failure with a status code. The kubelet's probe worker runs one probe at a time, so the next one starts as soon as the last returns. The three failures in a row land at about 320, 340 and 360 s. At about 360 s the Pod is marked not ready and is not restarted. The gateway stops sending it requests once its own data path has caught up, which the next chapter follows.

Chapter 9 of 11

Ready on the Pod, seconds later on the data path

A gateway with its own data plane hears the news late, and Ready must mean the model is served

Everything so far stopped at the EndpointSlice and treated the gateway as if it acted the moment the list changed. A gateway with a data plane of its own adds a step. BNK, F5's gateway for Kubernetes, has a controller that watches the API server and reprograms TMM, the traffic engine that carries the requests. Next to it an endpoint picker chooses the Pod for each inference request. The picker keeps its own list of Pods. In the reference picker of the Gateway API Inference Extension, a Pod enters that list only when its labels match the InferencePool's selector and its Ready condition is True. It is dropped as soon as either stops being true, or as soon as the Pod gets a deletion timestamp. The picker watches Pods directly, so it reacts to the same Ready condition the kubelet writes, and an InferencePool whose selector changes makes the picker list the matching Pods again and remove every one that is not Ready. That rule is the reference picker's. The owner's sources do not show whether F5's picker follows it. They show that F5's picker answers gRPC health checks on port 9003 of its Service, and that it runs 1 or 2 replicas, of which one serves and the other stands by.

The owner measured how long the data path takes to follow one kind of change. In a lab, a pool's selector was pointed at no Pods by mistake, and a controller put it back within 0.1 s. Requests still failed for another 5 to 6 seconds. That is the time BNK and the picker needed to reprogram after a pool change. Putting a bad edit right quickly shortens the outage it causes and cannot remove it. At 5 requests a second, a window of 5 to 6 s holds 25 to 30 requests, and after that pool change every one of them failed, because the pool had no Pods at all.

A single Pod leaving the ready set is a different change, and its lag was not measured. When our Pod failed readiness at about 360 s, the kubelet's write and the EndpointSlice change took milliseconds. The data path learns of it some time later, and requests sent into that gap can still reach the server whose engine is stuck. Only the share sent to that Pod is at risk. With two Pods that is roughly half. If the lag were as long as after the pool change, roughly half of 25 to 30, about 12 to 15 requests, would go to the stuck Pod. The lab's nearest measurement points to a shorter gap. When a worker was killed under a load of 5 requests a second, one or two of about 250 requests failed, each with HTTP 400, a success rate of 99.2 to 99.6%. BNK stops routing to a Pod once it leaves the ready set, and requests already on their way to it fail. A killed worker is not a stuck engine, so the lab did not show how requests to a hung engine fail. A hung engine is more likely to leave them waiting until they time out than to answer at once with 400. Clients should retry requests that are safe to repeat. On the way in, the same reprogramming delays a new Pod's first request by however long it takes, as long as Ready really means the model can be served.

That condition is where a split server goes wrong. NVIDIA Dynamo divides serving into a frontend, which takes the OpenAI-style HTTP requests, and workers, which run the engine. A worker registers its model with the frontend once its engine is up, and the frontend keeps a catalog of registered models. A request for a model that is not in the catalog gets 404 with the message Model not found. In the owner's lab, Dynamo decode workers were scaled from 0 to 2. Their Pods turned Ready and BNK routed to them before the workers had registered the model with the frontend sidecar, the frontend container running in the same Pod. Requests got 404 for a few seconds. BNK did what it does by design, which is to route on Pod readiness. The Pod's readiness promised less than the gateway assumed.

The fix is to make Ready mean served. Dynamo's documentation lists the endpoints. On the frontend, /live reports whether the HTTP service is running, and /health reports frontend health plus the endpoints and instances it has discovered. Neither depends on whether a model is ready. Dynamo 1.6.1 documents a third path, GET /v1/models/<model>/ready. It answers 200 when the model is ready to serve, 503 when the model is known but its workers, engine or routes are not ready, and 404 when the model is not in the frontend's catalog. The 1.6.1 page notes that the path used to answer 200 with ready: false for a known model that was not ready, and the 1.5.0 health check page does not list the path at all. The owner's lab ran Dynamo 1.5.1. So this probe needs Dynamo 1.6.1 or later. Operators opt in to model readiness by making that path the frontend's readiness probe. Workers serve /health and /live on a separate system port set by DYN_SYSTEM_PORT, which is disabled by default. Both answer 503 with the status notready until the worker's endpoints are ready. DYN_SYSTEM_STARTING_HEALTH_STATUS sets the status a worker starts with. An older variable, DYN_SYSTEM_USE_ENDPOINT_HEALTH_STATUS, is deprecated and no longer chooses which endpoints count. An httpGet probe judges only the status code, so a probe aimed at /v1/models would pass whatever the list held. The owner's controller reads the body instead and counts a worker only when /v1/models lists the model. Plain vLLM, as this lesson's Pods run it, has no such gap. It starts listening only after the engine is built with the model it was started with, so its first answer on port 8000 already lists Qwen/Qwen3-32B-FP8 under /v1/models.

Chapter 10 of 11

The same Pod with the wrong probe

Killed at thirty seconds, every time

Now take the startup probe away and give the Pod the kind of liveness probe a web server would have: ask every ten seconds, and after three failures in a row decide the container is dead and restart it. The model needs 190 seconds. The probe allows thirty. So at thirty seconds the kubelet kills a healthy server that was a sixth of the way through loading. It starts again from nothing and is killed again at the same point. The first restart is immediate. After each later death the kubelet waits longer before the next try, doubling from ten seconds up to five minutes. The Pod's status reads CrashLoopBackOff. The model never loads, a GPU is held the whole time, and nothing is wrong with the server at all.

The kill is graceful at first. The kubelet records a Normal event with the reason Killing and the message Container vllm failed liveness probe, will be restarted. It has the runtime send SIGTERM and waits for the grace period before SIGKILL. The grace period is the probe's own terminationGracePeriodSeconds if set, otherwise the Pod's, which defaults to 30 seconds. vLLM's documentation notes that a container stopped this way leaves the line KeyboardInterrupt: terminated in its log.

The back-off is measured from the moment the last container finished, and it resets once a container runs for 10 minutes without trouble. The same loop happens with a startup probe whose allowance is too short. Then the event reads failed startup probe instead.

Chapter 11 of 11

Reading the loop from outside

Where the status, the events and the numbers come from

The STATUS column of kubectl get pods is stored nowhere. kubectl asks the API server for a table, and the API server's Pod printer works the column out from the Pod's status on every request. kubectl only draws the table. It starts from the Pod's phase and is replaced by a container's state.waiting.reason, such as CrashLoopBackOff, or its state.terminated.reason. With no reason it prints Signal:<n> or ExitCode:<n>. So a Pod in this loop shows 0/1 in READY, CrashLoopBackOff in STATUS and a climbing number in RESTARTS. Running with 0/1 READY is the healthy slow start. CrashLoopBackOff with a growing restart count is the loop.

kubectl describe pod gives the cause. Each container shows Ready, Restart Count, and a State and a Last State with Reason, Exit Code, Started and Finished. The events show the warning with the reason BackOff and the message Back-off restarting failed container vllm in pod qwen3-6f7d9c8b4-x7k2p_inference(<uid>), next to the Unhealthy and Killing lines.

The kubelet publishes the probes as metrics. They are served on the kubelet's own path /metrics/probes, apart from its main /metrics. prober_probe_total counts every probe, with the labels probe_type, result, container, pod, namespace and pod_uid. prober_probe_duration_seconds is a histogram of how long probes took to answer, and the kubelet's source describes it as the duration of a successful probe lifecycle. A liveness probe whose failed count climbs in steps of three is the pattern of this loop. Two newer kubelet settings change the back-off itself. crashLoopBackOff.maxContainerRestartPeriod can lower the cap anywhere from 1 s to 300 s. A feature gate named ReduceDefaultCrashLoopBackOffDecay starts the wait at 1 s and caps it at 60 s. Both are behind feature gates. The fix for this Pod is simpler: add a startup probe with an allowance longer than the load.

What to keep

Tell Kubernetes how long a start takes

A Pod that is Running may still be minutes from being able to answer. The kubelet finds out by probing, and three probes do three jobs. The startup probe covers the slow beginning and holds the others back. The readiness probe decides whether the Pod is listed as a target for traffic, for the whole life of the container. The liveness probe decides whether to restart it. A probe is a short request from the node judged by its status code, and the kubelet counts runs of results against the thresholds. News of a Pod turning ready travels by writes and watches: kubelet to Pod status, controller to EndpointSlice, gateway to its targets, and the Deployment waits for the same signal before it removes an old Pod. For a model server the startup allowance has to be longer than the longest model load, or the cluster will keep killing a healthy server.
