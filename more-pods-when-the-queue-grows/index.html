Kubernetes underneath

More Pods when the queue grows

How the HorizontalPodAutoscaler counts, and why a model server makes it wait

Two model servers handle the usual load. Then a burst arrives and requests start to wait. Kubernetes can add Pods on its own with an object called the HorizontalPodAutoscaler. It is a loop that reads one measurement every 15 seconds, does one division, and writes a replica count. Two things decide whether that helps a GPU workload. The first is the measurement. CPU use says almost nothing about a model server, so this lesson takes the queue length from vLLM itself and carries it to the autoscaler. The second is time. A new replica needs a free GPU and three minutes to load its model.

The lesson follows one burst from the first waiting request to the moment the cluster shrinks again. It shows the metric path hop by hop, the HPA object field by field, the arithmetic of every loop, the two code paths that limit how fast a count may grow, the rule for Pods that are still loading, the node autoscaler that has to find a third GPU node for the ninth and tenth replicas, and the conditions and events an operator reads when something in the chain breaks. Then it follows the night: taking the model servers to zero when traffic stops, the queue at the gateway that wakes them, what the first caller of the morning waits for, and the ways to make that wait shorter.

Chapter 1 of 16

Two Pods and a queue that grows

A burst fills the servers in seconds and the rest of the requests wait

The Deployment qwen3 runs two Pods, each with one GPU and one copy of Qwen3-32B. A model server works on many requests at once by batching them on the GPU. Each step of the engine moves every request in the batch forward, usually by one token. When more requests arrive than the batch can hold, the extra ones wait in a queue inside the server. vLLM counts both groups. The gauge vllm:num_requests_running is the number of requests in model execution batches. The gauge vllm:num_requests_waiting is the number of requests waiting to be processed.

At noon a batch job in another team starts calling the API. Within 15 seconds qwen3-6f7d9c8b4-x7k2p has 16 requests waiting and qwen3-6f7d9c8b4-m9q4t has 14. Every waiting request is a caller watching nothing happen, because a request in the queue has not produced its first token yet. The waiting time adds directly to the time to first token that the caller sees.

The fix is more Pods, and Kubernetes has an object that adds them: the HorizontalPodAutoscaler, or HPA. It changes the replica count of a Deployment to keep a measurement near a target. It does not create Pods itself. It writes one number, and the Deployment and ReplicaSet controllers do the rest. Everything depends on which measurement it is given, and on how long a new Pod takes to be useful. A gateway can only spread requests over the Pods that exist, so until the count changes the two servers carry everything.

Chapter 2 of 16

CPU is the wrong thing to watch

The usual signal barely moves while the queue keeps growing

The usual HPA watches CPU. It reads each Pod's CPU use from the resource metrics API, metrics.k8s.io, which an add-on named Metrics Server fills. Metrics Server does no arithmetic of its own. It asks the kubelet on every node for GET /metrics/resource and keeps the latest figures in memory. CPU is a rate taken over a cumulative counter that the kernel keeps. Memory is the working set at the moment of collection. The README says Metrics Server collects every 15 seconds. Its FAQ gives the default of the --metric-resolution flag as 60 seconds and advises against going below 15. So the interval depends on how it was installed. The HPA calls the API at version v1beta1, which is the version it supports.

That API carries CPU and memory and nothing else. Utilization is computed by the client, here the HPA: use divided by the container's CPU request. When a Pod has several containers their use and requests are summed. The type ContainerResource looks at one named container instead. The HPA compares the average utilization with a target such as 60%.

For a web server this works, because requests cost CPU. A model server does its work on the GPU. Its Python process keeps a few cores busy whether 2 requests are waiting or 30. Here each Pod requests 8 cores and uses 2.4 before the burst and 2.56 during it. Utilization goes from 30% to 32%. An HPA watching CPU would see nothing to do.

Chapter 3 of 16

The server counts its own queue

From vLLM to Prometheus to an adapter to the API the HPA can read

vLLM publishes its own measurements at /metrics on port 8000, in the text format Prometheus reads. Every series carries a model_name label. One of them is the gauge vllm:num_requests_waiting, which is the queue itself. There are others that could serve as a second signal later: vllm:kv_cache_usage_perc, where 1 means the KV cache is full, and the histogram vllm:request_queue_time_seconds, the time requests spent waiting. vLLM binds its port early and starts answering HTTP requests only after its engine has loaded the model. A Pod that is still loading answers no scrape at all, and that detail decides the arithmetic later in this lesson.

The same gauge already steers requests in some clusters. An endpoint picker, such as F5's, reads vllm:num_requests_waiting from each model server and uses it, with other signals, to choose the Pod for each new request. Routing uses the number to share load between Pods that exist. The HPA uses it to decide how many Pods should exist.

The HPA cannot read Prometheus. It can only call three Kubernetes APIs: metrics.k8s.io for CPU and memory, custom.metrics.k8s.io for metrics that describe Kubernetes objects, and external.metrics.k8s.io for metrics from outside the cluster. The last two are empty until an adapter serves them, and the API aggregation layer must be enabled. So the path has three hops. Prometheus scrapes each Pod, here every 30 seconds. An adapter, registered with the API server as an APIService, turns a custom metrics request into a Prometheus query. The HPA asks the API server and never learns that Prometheus exists.

Chapter 4 of 16

The adapter turns a name into a query

Four parts of a rule, a cache of names, and a request you can make by hand

The adapter's documentation splits a rule into four parts. Discovery says which Prometheus series to look at, with seriesQuery and optional seriesFilters. Association says which labels name Kubernetes objects, here namespace and pod, through resources.overrides. Naming says what the metric is called in the API. A name with a colon is awkward in a URL path, so this rule exposes it as vllm_num_requests_waiting with name.as. Querying is a Go template, metricsQuery, that becomes the PromQL query. A counter such as a token total would need rate() inside it. A gauge such as a queue length is used as it is.

The adapter does not ask Prometheus which series exist on every request. It keeps a list and refreshes it every --metrics-relist-interval, which is 10 minutes by default. A metric that first appears after the adapter started can be missing from the custom metrics API for up to that long. The flag --metrics-max-age should be at least the Prometheus scrape interval, or values occasionally vanish. Its default is the relist interval.

The HPA's request carries the Deployment's label selector. The adapter turns the Pods it matches into label matchers, so the query that reaches Prometheus names both Pods with pod=~"qwen3-6f7d9c8b4-x7k2p|qwen3-6f7d9c8b4-m9q4t" and the namespace inference, and groups by pod. One adapter can also serve the resource and external metrics APIs. The HPA walkthrough prefers custom metrics to external ones where both work, because the custom metrics API is easier for administrators to secure.

Chapter 5 of 16

The object that states the target

What to scale, between which bounds, on which metric, toward which value

The HPA object is short. scaleTargetRef names what to scale: the Deployment qwen3. The controller reads and writes the Deployment through its scale subresource, and it selects the Pods with the labels the scale reports. minReplicas and maxReplicas bound the answer, here 2 and 10. Left out, minReplicas defaults to 1. A metrics list left empty is filled by the API server with one CPU metric at 80% utilization.

The metrics list says what to watch. Its type is Pods, which means one value for each Pod, averaged. A Pods metric supports only the target type AverageValue, and the value is 5. Read together: keep the average number of waiting requests for each Pod near 5. A metric may also carry metric.selector, a label selector passed down to the metrics pipeline, which could pick one model_name if a Pod served several. The other metric types are Resource for CPU and memory, ContainerResource for one container's share, Object for a value that describes one other object, and External.

A target of 5 is a judgement. A target near 0 would add Pods for every brief queue. A high target lets callers wait long before anything happens. If the list has several metrics, the HPA computes a count for each and takes the largest.

This HPA also carries a behavior block with the scale-up rules written out. The next chapters show why that block changes the arithmetic. One more habit belongs with an HPA. Remove spec.replicas from the Deployment's manifest, or every kubectl apply sets the count back.

Chapter 6 of 16

One division every 15 seconds

desired = ceil(current replicas × current value ÷ target)

The HPA controller runs inside kube-controller-manager. It does not react to events. It runs intermittently, every 15 seconds by default, set by --horizontal-pod-autoscaler-sync-period. Up to 5 HPA objects are processed at the same time, set by --concurrent-horizontal-pod-autoscaler-syncs. Each run reads the metric and computes: desired = ceil(current replicas × current value ÷ target).

At 30 seconds it reads 16 and 14. The average is 15 and the target is 5, so the ratio is 3. Two replicas times 3 is 6. Three checks follow. First the tolerance. If the ratio is within 10% of 1.0, which here means an average between 4.5 and 5.5, nothing changes. The flag is --horizontal-pod-autoscaler-tolerance with a default of 0.1, and newer versions add a field for each direction, spec.behavior.scaleUp.tolerance and scaleDown.tolerance, behind the feature gate HPAConfigurableTolerance, stable from v1.37. Second, the result is kept between minReplicas and maxReplicas. Third, the scale-up policies allow adding 4 Pods or doubling in 15 seconds, whichever is more. From 2 that permits 6.

The controller writes 6 into the Deployment's scale and records an event. It also writes status: the current and desired replicas, the metric value it read, and three conditions. AbleToScale says whether it could read and write the scale. ScalingActive says whether a metric produced a count. ScalingLimited says whether a bound or a rate limit cut the answer.

Chapter 7 of 16

Two code paths for the speed limit

Without a behavior block the first step from 2 replicas is 4, not 6

The controller limits how fast a count may grow, and it has two ways of doing it. The choice depends on one thing: whether spec.behavior is present in the object. The API server fills in default rules only when the block is there. If it is, even with a single field, the missing fields of both directions are filled with the defaults, with one exception: the scale-down stabilization window stays unset, for a reason the chapter on shrinking explains. If it is absent, the field stays empty and the controller takes an older code path.

The older path allows, in one run, at most twice the current replicas or 4, whichever is larger. From 2 that is max(4, 4) = 4. The newer path applies the policies: add 4 Pods, or add 100%, in a period of 15 seconds, and pick the larger. From 2 that is max(6, 4) = 6. The documentation says the default values match the older algorithm. That is true from 4 replicas upward, where both give double. Below 4 they differ: from 3 the old path allows 6 and the new one 7, from 2 it is 4 against 6, from 1 it is 4 against 5. When a limit cuts the answer, ScalingLimited becomes True with the reason ScaleUpLimit.

The newer path also remembers its own changes. It counts the Pods it added inside each policy's period and measures the next step from the count at the start of that period. The older path forgets after every run. Policies have bounds of their own. periodSeconds must be above 0 and at most 1,800. A Percent policy rounds up: with 10% a minute, 72 replicas may lose 8, because 7.2 rounds up to 8. selectPolicy is Max by default, Min picks the policy that allows the smallest change, and Disabled switches that direction off. stabilizationWindowSeconds may be from 0 to 3,600.

Chapter 8 of 16

New Pods count as zero

Four Pods exist within a second and serve nothing for three minutes

The Deployment's controller creates four Pods and the scheduler finds each a GPU. Six of the cluster's eight were free, so two remain. The images are on both nodes, and the containers start in 2 seconds. Then each Pod loads 34.3 GB of FP8 weights for three minutes. During that time vLLM has not started its HTTP server, so Prometheus gets no answer from it and the Pod has no value in the custom metrics API.

Before any arithmetic the controller sorts the Pods into groups. A Pod being deleted or already finished is ignored. A Pod in phase Pending goes into the unready group: it is left out of the first computation and, on the way up, counted as 0. A Pod with no value in the answer is called missing. For CPU there is one more test, whether the Pod is Ready and how long ago it started, governed by --horizontal-pod-autoscaler-initial-readiness-delay (30s) and --horizontal-pod-autoscaler-cpu-initialization-period (5m0s). A custom Pods metric skips that test. A Running Pod that reports a value counts, Ready or not, which is why it matters that a loading vLLM reports nothing.

At 45 seconds the HPA runs again. A naive average over the two old Pods would still say 15 and ask for 18. The rule is more careful. The controller first sees a ratio above 1, a scale up. It then counts every missing Pod as 0 and computes again. The sum is still 30, now over six Pods, so the average is 5 and nothing changes. If the second ratio had flipped direction, it would also do nothing. The status still shows the average of 15 from the reporting Pods, because the documentation says the original value is reported without the missing Pods. At 60 seconds Prometheus has newer numbers: 25 and 23. The sum is 48, the average over six is 8, and ceil(6 × 8 ÷ 5) is 10.

Chapter 9 of 16

Ten replicas, eight GPUs

The HPA counts replicas and knows nothing about hardware

The Deployment now wants ten Pods. Four more are created. Two take the last free GPUs. The other two stay Pending, and the scheduler's event says why. Its message begins 0/2 nodes are available: 2 Insufficient nvidia.com/gpu. and goes on with a part from the default preemption step, which starts preemption: and says why evicting other Pods would not help. With every qwen3 Pod at the same priority there is nothing to evict, so that part reads 0/2 nodes are available: 2 No preemption victims found for incoming pod. The scheduler also sets the Pod's PodScheduled condition to False with the reason Unschedulable, and that condition is what a node autoscaler looks for.

The HPA has done its part. It counts replicas and knows nothing about hardware. Right after the scale its status reads 10 desired replicas and reports no problem, because from its point of view the scale was written successfully. The ScalingLimited condition stays at DesiredWithinRange while the formula asks for 10 or fewer. In any later loop where the queue is still long enough for the formula to ask for more than maxReplicas of 10, ScalingLimited turns True with the reason TooManyReplicas. Even then the HPA reports a limit of its own. It never says that GPUs are missing.

The Pending Pods count in the HPA's next loops as well. A Pending Pod is set aside before the arithmetic and, on the way up, counted as 0, just like a Pod that is loading. So the two Pods that cannot run hold the average down a little until they start. The numbers in the lesson's later loops stay at 10, the maximum, so nothing changes in practice.

The operator who looks only at kubectl get hpa sees REPLICAS 10 and a target being chased. The shortage is visible in kubectl get pods, where two Pods show Pending, and in their events. This is why an alert on GPU capacity belongs beside an HPA on a GPU workload. Pods 7 and 8 load their model and are Ready at 62 + 180 = 242 seconds.

Chapter 10 of 16

A node autoscaler has its own clock

Ten seconds to notice, minutes to boot, and a cold start after that

Only a node autoscaler helps now. Kubernetes describes the job as provisioning: adding nodes for Pods that cannot be scheduled. The Cluster Autoscaler, one such tool, checks for unschedulable Pods every 10 seconds, set by --scan-interval. It recognizes them by the PodScheduled condition. Its own objective is no more than 30 seconds from a Pod marked unschedulable to the request for a node on a small cluster, about 5 seconds on average. The machine's boot time comes on top.

Before it asks, the autoscaler simulates. It checks whether one more node of a given group would let the Pod schedule, using the Pod's requests and not its real use. When several groups would fit, an expander chooses. least-waste, which the FAQ calls the default, picks the group that leaves the least idle CPU. A Pod that would not fit even on a new node gets the event NotTriggerScaleUp. Here it fits, and each Pending Pod gets TriggeredScaleUp with the group, its old and new size and its maximum. The FAQ still shows an older wording of both events, so trust what the code prints.

The cloud then creates and boots a GPU machine. The node joins, its driver loads and the device plugin reports 4 GPUs as allocatable. Here that takes until 360 seconds. A node that is not ready in --max-node-provision-time, 15 minutes by default, is given up on. A node that joins but whose GPUs are not reported counts as resourceUnready in the autoscaler's status.

Then it is a fresh node, so the image pull costs 90 seconds, the start 2 and the weights 180. The last two Pods are Ready 632 seconds after the burst began. The first four new Pods were Ready at 212 seconds, and until then two Pods carried everything.

Chapter 11 of 16

Slow to shrink, on purpose

For scaling down, the highest recommendation of the last 300 seconds wins

At 15 minutes the batch job ends and the queues empty. The next scrape is at 915.4 seconds, so the loop at 930 seconds is the first to read 0. The formula then gives 0, raised to minReplicas, so the recommendation is 2. The HPA does not act on it at once. For scaling down it keeps every recommendation from the last 300 seconds and uses the highest. This is the stabilization window. While it holds the count, the HPA's AbleToScale condition carries the reason ScaleDownStabilized.

This HPA's behavior block sets only scale-up rules, so the API server filled scaleDown with defaults: a policy of 100% in 15 seconds and selectPolicy Max. It leaves the window itself unset on purpose. The controller then uses its own flag, --horizontal-pod-autoscaler-downscale-stabilization, whose default is 5m0s. An administrator can change that flag for the whole cluster, and an HPA can set scaleDown.stabilizationWindowSeconds for itself.

A lull of one minute removes nothing, which matters when each removed Pod costs three minutes to bring back. The last 10 came at 915 seconds. At 1,215 seconds, 300 later, the default rule allows all the extra Pods to go in one step, and ten become two. The event on the HPA gives the new size, 2, and the reason All metrics below target.

A model server needs a gentler rule. A policy of type Pods with value 1 and periodSeconds 60 removes one Pod a minute, so a renewed burst finds most of the servers still loaded.

Chapter 12 of 16

The GPU node outlives the burst

Nodes shrink on a slower clock than Pods

Ten Pods became two at 1,215 seconds. Which eight go is the ReplicaSet controller's choice, so gpu-node-3 may keep a model server or lose both of its Pods. Suppose it keeps none. The node is now a machine with 4 GPUs and nothing on them, and in a cloud it is billed by the hour.

The Cluster Autoscaler removes nodes on a much slower clock than the HPA removes Pods. A node becomes a candidate when the sum of the requests of its Pods, divided by what it can allocate, is below a threshold. For an accelerator node only the GPU counts: --scale-down-gpu-utilization-threshold has a default of 0.5, and CPU and memory are ignored. Here the node has 0 of 4 GPUs requested, a utilization of 0, so it is a candidate. The autoscaler also checks that the Pods left on it could move elsewhere. A node with only DaemonSet Pods passes.

The candidate must stay unneeded for --scale-down-unneeded-time, 10 minutes by default. And no scale down is considered within --scale-down-delay-after-add of a scale up, also 10 minutes. The scale up was requested at about 70 seconds, so that delay ended long ago. The node became unneeded at about 1,225 seconds and is removed at about 1,825.

Add it up. The node was asked for at 70 seconds, served from 632 to 1,215, and existed until 1,825. For about 20 of its 29 minutes it did no useful work, most of it loading or waiting to be removed. Faster settings shorten the second part, at the price of a node that is gone when the next burst arrives.

Chapter 13 of 16

When the metric path breaks

The conditions and events an operator reads

Every hop in the metric path can fail, and the HPA reports each failure in its conditions and events. If the adapter is down, the API server cannot reach the Service behind the APIService, and the HPA's request fails. ScalingActive becomes False with the reason FailedGetPodsMetric and the message the HPA was unable to compute the replica count, followed by the error. A Warning event FailedComputeMetricsReplicas appears. If the request works but no Pod has a value, the error reads did not receive metrics for targeted pods (pods might be unready). If the selector matches nothing, it reads no pods returned by selector while calculating replica count.

While the metric fails the HPA keeps the current count. With several metrics the rule is asymmetric. If one metric fails and the others suggest a scale down, the HPA skips scaling. If any metric that works asks for more replicas than now, it still scales up. A broken adapter can freeze a cluster at its burst size, so it deserves an alert.

Scaling the Deployment to 0 by hand switches the HPA off. When the target's replicas are 0 and minReplicas is above 0, the HPA stops adjusting it and sets ScalingActive to False with the reason ScalingDisabled. It resumes when the replicas are raised again. Scaling to zero on purpose is a separate feature: minReplicas: 0 is accepted only with an Object or External metric, behind the feature gate HPAScaleToZero, which is beta and on by default from v1.37. A Pods metric cannot do it, because a Deployment with no Pods has no queue to report. The documentation names dedicated hardware such as GPUs as the reason to want it.

Chapter 14 of 16

Down to zero when traffic stops

Only a queue that lives outside the model servers can bring them back

The burst is long over. After the maintenance in the last chapter the Deployment runs two replicas again. They are new Pods, so they carry the same template hash and new suffixes: qwen3-6f7d9c8b4-r4h6d on gpu-node-1 and qwen3-6f7d9c8b4-t8v2c on gpu-node-2. In the evening the callers go home. A model server with nothing to do still holds its GPU. Kubernetes gives a Pod its nvidia.com/gpu for the whole life of the Pod, so two idle replicas keep two H100s away from every other workload all night. Scaling to zero gives them back. The next caller pays for it, and the next chapter measures how much.

The HPA built in this lesson cannot do it. Its signal is a Pods metric, vllm:num_requests_waiting, read from each model server. With no Pods there is no series at all, so nothing could ever report that one replica is needed again. The Kubernetes documentation states the rule: minReplicas: 0 is accepted only when the HPA has at least one Object or External metric, and the API server rejects the object otherwise. Resource metrics such as CPU are excluded for the same reason, because they can only be measured on running Pods. The signal has to come from something that keeps running at zero. In front of the model servers that is the gateway, and in particular its endpoint picker. The endpoint picker, or EPP, is the part of the Gateway API Inference Extension that chooses a model server for each request, and llm-d builds on it. F5's endpoint picker, met earlier in this lesson, implements the same contract. The queue and the metric names in these chapters are those of llm-d's EPP. With its flowControl feature gate on, the EPP holds requests in queues of its own when no model server can take them. It publishes the length of those queues as llm_d_epp_flow_control_queue_size.

Kubernetes gives two ways to write the rule. The first is a plain HPA with minReplicas: 0 and an External metric. This is the HPAScaleToZero feature, beta and on by default since v1.37. It must be on in both the kube-apiserver, which accepts the 0, and the kube-controller-manager, which does the scaling. When the HPA itself takes a workload to zero it sets a condition ScaledToZero to True with the message the HPA controller scaled the workload to zero. That condition is how it tells its own zero apart from a Deployment that someone scaled to 0 by hand, which stays switched off as the last chapter showed. The second way is KEDA, and it is the path llm-d recommends. KEDA is an operator that evaluates triggers, such as a Prometheus query, publishes each value through the external metrics API and creates an HPA for the target. It needs no feature gate, because KEDA moves the Deployment between 0 and 1 itself and leaves 1 to N to the HPA it generated. When minReplicaCount is 0, that HPA gets minReplicas 1.

KEDA's own clocks decide when zero arrives. It polls each trigger every pollingInterval, 30 seconds by default and 15 in llm-d's guide. A trigger is active when its value is above its activationThreshold, which defaults to 0. Above means strictly above, so a queue of 1 is active and a queue of 0 is not. Each poll that finds a trigger active records the time as LastActiveTime. When no trigger is active and LastActiveTime is older than cooldownPeriod, 300 seconds by default, KEDA writes the replica count straight to 0. The generated HPA cannot take that step. It can only bring two replicas to one, and in practice it does that first. Its running-requests trigger has an AverageValue target of 16, so two replicas are justified only while more than about 16 requests are running across the pool.

Here the evening tails off well below that. Once the HPA's 300 second scale-down window has passed with every recommendation at 1, keda-hpa-qwen3 takes the Deployment from two replicas to one, and the ReplicaSet removes qwen3-6f7d9c8b4-t8v2c on gpu-node-2. One replica carries the last callers. The last request finishes at 22:00, which is 36,000 seconds after the burst at noon. The poll at 36,015 seconds is the last whose Prometheus reading still shows a running request, so LastActiveTime is 36,015. Add 300 and the cooldown ends at 36,315. The first poll after that runs at 36,330, finds both triggers at 0 and scales qwen3 from 1 to 0. The last Pod stops and its GPU goes back to gpu-node-1.

The nodes stay unless something removes them. With no GPU requested, gpu-node-1 and gpu-node-2 both fall below the Cluster Autoscaler's GPU threshold of 0.5. After 10 minutes unneeded they are candidates for removal, as gpu-node-3 was. Whether they go depends on the minimum size of their node group. Here that minimum is two, so the machines stay and only the Pods are gone.

Chapter 15 of 16

The first request after zero

Every slow step of a new replica now sits in front of a caller

At 07:30 the next morning, 70,200 seconds after the burst, a caller sends the first request of the day. The gateway takes the connection and asks the EPP for an endpoint. There is none. With flow control on, the EPP parks the request in the queue for its flow and the handler waits. The request has no fairness header and no objective header, so it goes to the single global queue at priority 0. The pool's queue size goes from 0 to 1. Nothing else happens until the metric path carries that 1 to KEDA.

The path has the same shape as the one the HPA used during the burst, with KEDA in place of the adapter. Prometheus scrapes the EPP, here every 30 seconds, and KEDA queries Prometheus on its own poll. In this run the scrape lands at 70,220 seconds and KEDA's poll at 70,230. The value 1 is above the activation threshold of 0, so the trigger is active. KEDA sets the Deployment's replicas from 0 to 1. From zero it always goes to minReplicaCount, or to 1 when that is 0. Anything more is the HPA's job afterwards. A plain HPA works differently at this step. From zero there is no current ratio to compare, so it skips the tolerance check and proposes ceil(value ÷ target) directly, so a queue of 3 with an AverageValue target of 1 would ask for 3 replicas at once.

Now every slow step of a new replica runs in series, with a caller waiting at the start of the chain. The ReplicaSet creates a Pod with the same template hash and a new suffix, qwen3-6f7d9c8b4-p5n8w. The scheduler binds it to gpu-node-1, which has four free GPUs, in about a second. The image is still in the node's cache, so the container starts in 2 seconds. vLLM then spends three minutes loading the 34.3 GB of the FP8 build, and it serves no HTTP until the engine is ready. Only when the Pod turns Ready does the EPP see an endpoint and release the parked request to it. Add the steps: 30 seconds of metric path, 1 to schedule, 2 to start and 180 to load. The first token arrives about 213 seconds after the request, plus the prefill of the prompt. A replica that was already running would have sent the request straight to its GPU.

llm-d measured a cold replica on real hardware. Its benchmark of Qwen/Qwen3-32B, the BF16 build, with one H100 80 GB per replica, reports a mean Pod startup of 155 seconds under its saturation trigger and 149 seconds under its queue trigger, for a new decode Pod that loads the model. Those runs scaled up from one replica, so they show the cost of a cold replica without the extra seconds of activation from zero.

The EPP's queue has a clock of its own, and its default would end this story early. While the pool has no endpoints, a queued request waits at most noEndpointRequestTTL. Left unset, that budget follows defaultRequestTTL, and in the router's code both default to 60 seconds. Some of llm-d's configuration pages still give defaultRequestTTL a default of 0s, but the router changed it to 60s in July 2026. At the defaults this request would expire at 70,260 seconds, more than two and a half minutes before the Pod is Ready. The caller would get HTTP 503 with the header x-llm-d-request-dropped-reason: rejected-no-endpoints, and the EPP would count it as EvictedNoEndpoints. The router's notes say to size noEndpointRequestTTL above the expected Pod startup. So this lesson's EndpointPickerConfig sets noEndpointRequestTTL to 300s, above the 213 second cold start, and the gateway's request timeout is at least as long, because a long budget only helps if the caller is still waiting. An explicit 0s would let the request wait without limit. Once the pool has an endpoint, the request moves onto defaultRequestTTL with a fresh budget. The llm-d documentation says it directly: model cold-start time becomes request latency, and clients must allow enough time for the model to load. The queue also lives only in the EPP's memory. If the EPP restarts while the pool is at zero, the parked request is lost.

Two other setups do worse. Without flow control there is no queue to hold the request. The in-flight metric, llm_d_epp_inflight_requests, has no endpoints to count and stays absent, so it can never wake the Deployment. llm-d's guide therefore requires the queue or the saturation signal for scale to zero. If the GPU nodes were removed overnight, the same request also waits for a machine. With this lesson's assumptions of 360 seconds for a new GPU node and 90 seconds for the image pull, the sum is 30 + 360 + 90 + 2 + 180 = 662 seconds, eleven minutes for the first answer. That is longer than this lesson's noEndpointRequestTTL of 300s, so the request would be dropped with a 503 at 70,500 seconds unless the budget and the gateway timeout were raised above 662 seconds.

Chapter 16 of 16

Shorter ways back

A warm floor, a sleeping engine, or a launcher that is already running

Scale to zero trades GPU hours against the first caller's wait, so measure both. Here the Deployment sat at zero from 36,330 to 70,230 seconds. That is 33,900 seconds, about 9.4 hours. The HPA from the first part of this lesson, with minReplicas 2, would have kept two replicas idle for that long: 2 × 9.4 = 18.8 GPU-hours. One replica kept as a floor holds 9.4 GPU-hours and answers the 07:30 request at once. The floor is minReplicaCount in KEDA or minReplicas in an HPA. llm-d calls it the warm floor that keeps a keep-warm replica up and damps flap. Its guide advises turning on scale to zero only after scaling from one replica to N has been validated.

The next way back keeps the server process and empties the GPU. vLLM has a sleep mode. Started with --enable-sleep-mode and the environment variable VLLM_SERVER_DEV_MODE=1, the server answers POST /sleep?level=1 and POST /wake_up. Level 1 copies the weights to the CPU's memory and throws away the KV cache. Waking copies the weights back, with no file read and no new process. Level 2 throws the weights away as well. It is meant for replacing them, as a training loop does, and the weights must be reloaded after waking. For the FP8 build, level 1 needs at least 34.3 GB of free host memory for each sleeping server. The sleep endpoints are development endpoints, and vLLM's documentation says they should not be exposed to users.

Sleep on its own does not give the GPU back to Kubernetes. Once a Pod has been allocated a GPU it keeps that allocation for its whole life. A sleeping vLLM in an ordinary Pod frees the GPU's memory and still holds nvidia.com/gpu: 1, so the scheduler will not place another Pod on that GPU. llm-d's Fast Model Actuation, or FMA, works around this with two kinds of Pod. A server-requesting Pod asks for the GPU through the scheduler, which keeps the cluster's accounting right, and runs no inference. A launcher Pod runs vLLM without requesting GPUs and is pointed at the reserved GPU with CUDA_VISIBLE_DEVICES. When the requesting Pod is deleted its GPU allocation goes with it, and the FMA controller puts that vLLM instance to sleep. The instance keeps its CUDA context in a small amount of GPU memory until the controller deletes it.

FMA's benchmark names four ways back: a cold start without FMA, a cold start that first creates a launcher Pod, a warm start and a hot start. llm-d's results for Qwen3-32B on H100 report hot, warm and cold. A hot start wakes a sleeping instance and took 4.0 seconds. A warm start creates a new vLLM in a launcher that has already loaded its Python modules and took about 85 seconds. A cold start loads everything and took 149 to 155 seconds. In the queue-triggered runs the hot path cut the 95th percentile time to first token from 74.2 to 24.1 seconds, and it completed all 1,860 requests in every run where the cold path averaged 80 failures. A hot start happens only when the scheduler places the new requesting Pod on the node and GPU where the instance sleeps. The controller also keeps only a configured number of sleeping instances per GPU and removes the least recently used beyond that.

Smaller savings add up. An image kept on the node removes the 90 second pull. A GPU node group whose minimum stays above zero removes the wait for a machine. And the HPA's scale-up stabilization window should sit near the measured cold start. llm-d's guide sets it to 300 seconds, validated against a cold start of about 240 seconds for Qwen3-8B, so a replica that is still loading is not answered with yet another one.

What to keep

Minutes against seconds

The HorizontalPodAutoscaler is a division that runs every 15 seconds. Give it a measurement that follows the load. For a model server that is the queue inside the server, carried through Prometheus and an adapter to the custom metrics API. CPU does not follow it. Write a behavior block, because without one the first step from two replicas is capped at four. Pods that are loading count as zero on the way up, which keeps the HPA from asking for far too many. The loop decided correctly within a minute here, and it still took 212 seconds before the first four new Pods answered requests, and 632 before all ten did. A replica needs a GPU, perhaps a new node, perhaps an image, and always three minutes of loading. Shrinking is slow on purpose: the extra node stayed ten minutes after its Pods had gone, about fifteen after the burst ended. So autoscaling handles the hour that is busier than the last one. It does not handle the burst that arrives in ten seconds. That burst is met by replicas that are already running, or by a queue that callers are willing to wait in. Scaling to zero stretches the same trade over a night. Against the two replicas the first HPA kept as its minimum, it gave back 18.8 GPU-hours here. It cost the first caller of the morning about 213 seconds, and only because the EPP's empty-pool budget was raised to 300 seconds. At the 60 second default that caller would have got a 503 instead.
