Kubernetes underneath

Who is asking the API

ServiceAccounts, the token in every Pod, and the RBAC rules that answer yes or 403

The API server is the only door to the cluster. It settles two things about every request before it acts: who sent it, and whether that sender may do what it asks. The first is authentication and the second is authorization. People prove who they are with certificates or with tokens from an identity provider. Programs in Pods use a ServiceAccount and a short-lived token that the kubelet places in the Pod. Permissions come from RBAC, role-based access control. A Role lists what may be done, and a binding gives a Role to someone.

This lesson sets up two identities in northlight-eu. The model server gets one that can read nothing. A deploy pipeline gets one that can change Deployments in the namespace inference and nothing else. On the way it looks at every way into the API server, the kubelet's own identity, how a token is checked and how it is taken back after an intruder uses it, the fine print of RBAC rules, impersonation, and the default roles every cluster starts with.

Chapter 1 of 16

Two checks on every request

First who you are, then what you may do

Someone on the platform team runs kubectl to create a ServiceAccount. The request reaches the API server over TLS with a client certificate. Authentication comes first. The API server has several authenticators: client certificates, bearer tokens, an authenticating proxy. The first one that succeeds settles the matter, and the documentation says the order in which they run is not guaranteed. A successful authenticator yields four things: a username, a UID, a list of groups, and extra fields, a map of strings to lists of strings that authorizers may use. To the authentication system all of these are opaque strings.

For a certificate, the common name becomes the username and the organization fields become groups. Kubernetes keeps no objects for human users. It trusts what the authenticator says. A request with an invalid bearer token gets 401 Unauthorized. A request with no credential at all is treated as anonymous, when anonymous access is on, which is the default with any authorization mode other than AlwaysAllow.

Authorization comes second. It looks at the username, the groups, the verb, the resource and the namespace, and answers allow or deny. A deny is 403 Forbidden. Only after both steps do admission controllers, such as the policy engine on this cluster, look at the object itself. A certificate has one weakness worth knowing from the start: Kubernetes cannot revoke it. Every certificate that was issued stays valid until it expires, which is why people are usually given short-lived certificates or tokens from an identity provider instead.

Chapter 2 of 16

The ways in, and what each one cannot do

Certificates, tokens of four kinds, a proxy, or nobody at all

The Authenticating page lists the methods the API server knows: X.509 client certificates, bootstrap tokens, ServiceAccount tokens, a static token file, and external ones: JSON Web Tokens, OpenID Connect tokens, a webhook that checks tokens, and an authenticating reverse proxy. It advises at least two: ServiceAccount tokens for programs and at least one other method for people.

Each method has a limit to remember. Client certificates are trusted when they chain to a CA given with --client-ca-file, and they cannot be revoked. The cluster can issue them itself through a CertificateSigningRequest to the signer kubernetes.io/kube-apiserver-client. Such a request may ask for a lifetime in spec.expirationSeconds, at least 600 seconds, and the built-in signers use the smaller of that and --cluster-signing-duration. The admission plugin CertificateSubjectRestriction, on by default, refuses requests that ask for the group system:masters. OpenID Connect ID tokens cannot be revoked either, so the page says they should live only a few minutes. A webhook that checks tokens has its answers cached for two minutes by default, so a token revoked at the provider can keep working that long. The static token file holds tokens that never expire, and changing it needs a restart of the API server.

Bootstrap tokens are how a new node first gets in. They look like six characters, a dot, and sixteen characters, live as Secrets in kube-system, and authenticate as system:bootstrap followed by the token ID, in the group system:bootstrappers. Anonymous access can be narrowed to a few paths, such as /livez, /readyz and /healthz, with an AuthenticationConfiguration file, stable since 1.34. Any credential's result can be checked with kubectl auth whoami.

Chapter 3 of 16

Which authorizer answers

A chain of authorizers, a verb taken from the HTTP method, and one group above them all

Authorization is a chain. kube-apiserver is started with a list such as --authorization-mode=Node,RBAC,Webhook, or with a structured file given by --authorization-config, stable since 1.32. The two cannot be used together. The modes are AlwaysAllow, AlwaysDeny, ABAC, RBAC, Node and Webhook. Each authorizer in turn may allow, deny or have no opinion. The first one that allows or denies decides, and an earlier one has priority over a later one. If none decides, the request is denied. Because RBAC has no deny rules, putting AlwaysAllow in front of it makes RBAC pointless. A configuration file is reloaded when it changes and every 60 seconds, and a reload may not add or remove the Node or RBAC authorizer.

The verb the authorizer sees is taken from the HTTP request. POST is create. GET and HEAD are get for one object, list for a collection and watch for a watch. PUT is update and PATCH is patch. DELETE is delete for one object and deletecollection for a collection. A request outside the resource paths, such as /healthz, uses the lower-cased HTTP method as its verb. A few verbs are checked in addition to the normal ones: impersonate, approve on certificate signing requests, bind and escalate on roles, and unsafe-delete-ignore-read-errors.

One group stands above the chain. A user in system:masters has full administrator rights and bypasses RBAC and webhook authorization entirely. Removing the cluster-admin binding does not take that away. Every decision is counted in the API server's metric authorization_attempts_total, whose result label is allowed, denied, no-opinion, conditional or error, and recorded in the audit log with the annotation authorization.k8s.io/decision set to allow or forbid.

Chapter 4 of 16

An identity for a program

A ServiceAccount lives in a namespace, and every Pod runs as one

A ServiceAccount is an identity for software. It lives in a namespace, and a controller makes sure that every active namespace has one named default. When a Pod is created without spec.serviceAccountName, an admission controller in the API server fills in default. So every Pod runs as some ServiceAccount. To the API server the account is a username of the form system:serviceaccount:namespace:name. It belongs to two groups, system:serviceaccounts and system:serviceaccounts:namespace.

The model servers now get their own account, qwen3. Sharing default would mean that a permission given to it reaches every Pod in the namespace that did not choose an account. A new ServiceAccount can do almost nothing. The default RBAC rules give accounts outside kube-system no permissions beyond API discovery and a few read-only facts about themselves and the cluster.

The same admission controller does more to each Pod. If the Pod lists no imagePullSecrets, it copies them from the ServiceAccount, which is a convenient way to give every Pod of an account access to a private registry. And it adds a projected volume named kube-api-access followed by a random suffix, mounted at /var/run/secrets/kubernetes.io/serviceaccount in every container that does not already mount something there. Its files get mode 0644, written in the spec as the decimal 420. That volume will hold the token. A Pod spec that sets automountServiceAccountToken to false, or an account that does, skips the volume.

Chapter 5 of 16

The kubelet is a user too

system:node:gpu-node-1, held to its own node by the Node authorizer

Before a token can reach the Pod, the kubelet on gpu-node-1 has to ask for it, and the kubelet is itself a client of the API server. It authenticates with a client certificate whose subject puts it in the group system:nodes with the username system:node:gpu-node-1. That identity is created when the kubelet joins the cluster through TLS bootstrapping, and the node name in it must match the name the node registered with.

A kubelet could do a lot of harm with broad rights, so a dedicated authorizer, Node, limits it. The Node authorizer lets a kubelet read Services, Endpoints, Nodes and Pods, and read the Secrets, ConfigMaps, PersistentVolumeClaims and PersistentVolumes that belong to Pods bound to its own node. With AuthorizeNodeWithSelectors, stable since 1.34, it may read only its own Node object and only Pods bound to its node. It may write Node and Pod status and events, take part in certificate signing for its own TLS bootstrap, and create TokenReviews and SubjectAccessReviews to check callers of its own API. The admission plugin NodeRestriction then narrows the writes to its own Node and its own Pods.

One more restriction concerns tokens. With ServiceAccountNodeAudienceRestriction, beta and on by default since 1.33, and NodeRestriction active, a kubelet may only request ServiceAccount tokens for audiences that Pods on its node already use: the API server's own audience, audiences named in projected token volumes, and audiences that CSI drivers of those Pods ask for. A compromised node cannot mint tokens for any audience it likes.

Chapter 6 of 16

The kubelet fetches a token for the Pod

Requested for one Pod, good for about an hour, written to a file

The Pod is bound to gpu-node-1, and the kubelet there prepares its volumes. For the token it calls the TokenRequest API. That is a subresource of the ServiceAccount, reached with a POST to serviceaccounts/qwen3/token. The request carries three things. audiences says who the token is meant for, and when it is empty the API server's own audience is used. expirationSeconds asks for a lifetime, here 3607 seconds. The API refuses anything below 10 minutes. boundObjectRef names the Pod and its UID, which ties the token to this one Pod.

The API server signs a JSON Web Token, a JWT, and returns it. The kubelet writes it to a file named token inside the Pod, next to the cluster's CA certificate and the name of the namespace. No Secret is involved. The kubelet asks for a fresh token once the old one is past 80 percent of its lifetime or older than 24 hours.

The files are readable by any process in the container, with mode 0644. There is one exception. When every container in the Pod runs as the same user, set with runAsUser, the kubelet makes that user the owner of the token file and sets its mode to 0600. A debug container added later with a different user then cannot read the token. A Pod that writes its own projected token volume chooses the audience and the lifetime itself. The lifetime there defaults to one hour and must be at least 600 seconds, and the API server's --service-account-max-token-expiration caps what any request can get.

Chapter 7 of 16

What the token says

Signed claims that name the account, the Pod and the node

A JWT has three parts separated by dots: a header, a payload and a signature. The payload is a set of claims that anyone holding the token can decode. The signature is made with the API server's signing key, so a changed claim no longer verifies. That key comes from --service-account-signing-key-file, which is read once at start. --service-account-key-file lists the keys that verify tokens and may be given several times, which is how a key is rotated without breaking tokens already issued.

The claim sub is the username, system:serviceaccount:inference:qwen3. iss is the issuer, set by --service-account-issuer, which should be an https URL. aud is the audience. iat and nbf give the time of issue, and exp gives the expiry. jti is a unique ID for this token. Under the key kubernetes.io are the namespace, the ServiceAccount's name and UID, the Pod's name and UID, and the node's name and UID. The Pod entry is the binding. Each time the token is used, the API server checks that this Pod still exists with this UID. The node entry is only information, and the API server does not verify it.

The application has to read the file again from time to time, because the kubelet replaces it. The source of the kubelet's token manager gives the exact rule. A token needs a refresh when it is older than 24 hours minus a random jitter of 0 to 9 whole seconds, or when the time left before expiry falls below 20 percent of the lifetime asked for plus that jitter. 20 percent of 3607 seconds, in whole seconds, is 721. So a new token becomes due between 2,877 and 2,886 seconds after issue, about 48 minutes, whatever exp says. The kubelet applies this rule when it next sets up the Pod's projected volume again, which happens on its periodic sync of the Pod, so the actual fetch can come somewhat later than the moment the token becomes due.

Chapter 8 of 16

Tokens made by hand, and the old Secret tokens

kubectl create token, and why a token stored in a Secret is a last resort

The deploy pipeline runs outside the cluster, so no kubelet fetches a token for it. Its account, deployer in the namespace ci, gets one from kubectl create token, which calls the same TokenRequest API by hand and prints the JWT. --duration asks for a lifetime, and the documentation warns that the token issued may be shorter or even longer. Since kubectl 1.31 a token can also be bound to a Node with --bound-object-kind Node and the node's name and UID, so that it dies with the node. The right to do this is a privilege of its own: anyone allowed to create serviceaccounts/token can issue tokens for every existing account in the namespace.

Before Kubernetes 1.24, every ServiceAccount automatically got a token stored in a Secret. Those tokens never expired and were not bound to any Pod. A long-lived token can still be made on purpose, by creating a Secret of type kubernetes.io/service-account-token with an annotation that names the account. The control plane then writes a token into it. The documentation says to do that only when TokenRequest cannot be used. Anyone who can read such a Secret can act as the account, and anyone who can write Secrets can ask for one.

Old auto-generated tokens are cleaned up. A controller checks every 24 hours. A legacy token Secret that no Pod mounts and that has not been used for a year gets the label kubernetes.io/legacy-token-invalid-since with the date, and the token stops working. If it stays unused for another year, the Secret is deleted. The period is set by --legacy-service-account-token-clean-up-period. The API server counts legacy token use in metrics, so an operator can see who still relies on them. serviceaccount_legacy_tokens_total counts every use of a Secret-based token. serviceaccount_legacy_auto_token_uses_total counts the auto-generated ones and serviceaccount_legacy_manual_token_uses_total the ones made by hand. serviceaccount_invalid_legacy_auto_token_uses_total counts attempts with an auto-generated token already marked invalid.

Chapter 9 of 16

No rule, no access

RBAC only adds permissions. With none, the answer is 403

Suppose someone breaks into the model server through a bad dependency. They find the token file and use it to ask for every Secret in the namespace. Authentication passes. The signature is good, the token has not expired, the audience is the API server and Pod qwen3-58b4d7f9c6-h2n6w exists. The request now comes from system:serviceaccount:inference:qwen3. Authorization is next. RBAC looks at every RoleBinding in the namespace and every ClusterRoleBinding that names this user or one of its groups, and at the rules of the roles they point to.

Permissions in RBAC are purely additive. There are no deny rules and there is no order among rules. If one rule anywhere allows the request, it is allowed. Here nothing does, because nobody has bound anything to this account. The only bindings that reach it are the defaults for every authenticated user. system:basic-user lets a user read basic facts about itself. system:discovery opens the discovery endpoints. system:public-info-viewer shows harmless facts about the cluster and is bound to unauthenticated users too. RBAC therefore has no opinion. In this cluster's chain, Node,RBAC,Webhook, the request then goes on to the webhook, which is the last authorizer. When no authorizer allows the request, the API server answers 403 Forbidden with a message that names the user, the verb and the resource.

The refusal is quiet for the intruder and loud for anyone who watches. The audit log records the request with the decision forbid. The metric authorization_attempts_total counts it under the result no-opinion, because nothing decided. The result denied is kept for requests that an authorizer refuses outright. A runtime sensor can catch the step before. The site owner's research notes record that Tetragon, with a kprobe on the kernel function security_file_open and a path filter, can report a process that opens the token file, with its Pod and process ancestry. A model server has no reason to read that file at all.

Chapter 10 of 16

Taking a token back

No list of tokens to revoke, so you delete what the token is bound to

The platform team sees the forbidden request in the audit log. The entry names the user, the verb, the resource, and in the user's extra fields the Pod qwen3-58b4d7f9c6-h2n6w. The intruder failed this time, but the token is still valid and may have been copied out of the Pod. It has to stop working.

Kubernetes keeps no central record of the tokens it issued, so a single token cannot be revoked. What can be removed is what the token is bound to. Every use of a ServiceAccount token goes through five checks, in this order: the signature, the expiry, whether the objects named in its claims still exist, whether the token is currently valid, and the audience. The third check is the lever. Deleting Pod qwen3-58b4d7f9c6-h2n6w makes every token bound to it fail. While a bound object, or the ServiceAccount itself, is still being deleted, for example held by a finalizer, the token keeps working until 60 seconds after its deletionTimestamp, and then fails. For a Pod, deletionTimestamp is the time of the delete plus the grace period. Once the Pod object is gone, the token fails at once.

The heavier option is to delete the ServiceAccount and create it again. The new account has a new UID, and every token ever issued for the old one stops working, including tokens for Pods that did nothing wrong. Here deleting one Pod is enough. The Deployment creates a replacement, qwen3-58b4d7f9c6-p6d4j, with a new UID and a new token, and the model server is back after its three minutes of loading. Services outside the cluster that accept these tokens should check them with the TokenReview API instead of only the signature, so that this kind of revocation reaches them too, and should insist on their own audience.

Chapter 11 of 16

Roles say what, bindings say who

One Role and one RoleBinding hold the pipeline's only permission

The deploy pipeline runs as the ServiceAccount deployer in the namespace ci. It has to roll out new versions of the model server and should be able to do nothing else. Two objects grant that. A Role is a list of rules inside one namespace. Each rule has three lists: apiGroups, resources and verbs. Deployments are in the API group apps.

A RoleBinding gives a Role to subjects, which can be users, groups or ServiceAccounts, and it grants only inside its own namespace. Here the Role and the RoleBinding are both created in inference, and the subject is the account from ci. A ClusterRole is the same idea without a namespace. It is used for cluster-wide resources such as nodes, and for rules meant to be reused. A ClusterRoleBinding grants a ClusterRole everywhere. A RoleBinding may also point at a ClusterRole, and then grants it in one namespace only.

The RBAC page ranks the ways of giving a program permissions, from the most secure to the least. First comes a role granted to an account made for that one application, which is what this chapter does. Further down come grants to the default account of a namespace, to all ServiceAccounts of a namespace, and to all ServiceAccounts in the cluster. The same binding could be written in one command: kubectl create rolebinding with --role and --serviceaccount ci:deployer in the namespace inference. A binding's roleRef cannot be changed, so a binding that should point elsewhere is deleted and created again.

Chapter 12 of 16

Rules in detail: subresources, names and wildcards

A permission on deployments says nothing about deployments/scale

A rule's resources list is matched exactly, and a subresource is a resource of its own, written with a slash. Permission on pods does not include pods/log, pods/exec or pods/portforward. Permission on deployments does not include deployments/scale. So when a request goes to the scale subresource of the Deployment qwen3 to change its replica count, the pipeline's Role does not cover it, although the same change made by patching spec.replicas on the Deployment itself is allowed.

resourceNames narrows a rule to named objects. It cannot narrow create, because the name of a new object may not be known when the request is authorized, and it cannot narrow deletecollection. A list or watch is matched by a name-restricted rule only when the client asks with a field selector on metadata.name, such as kubectl get configmaps --field-selector=metadata.name=my-configmap. An empty resourceNames means every name.

The asterisk stands for all apiGroups, all resources or all verbs, and for nonResourceURLs it matches as a suffix. The RBAC page warns about what that means later: when a new resource type, a new subresource or a new custom verb appears, a wildcard grants it automatically. Some permissions are also larger than they look. get on nodes/proxy reaches the kubelet's own API, which can run commands in containers, so the good practices page states plainly that it is not a read-only permission. And anyone who can create a Pod, or a Deployment, Job or CronJob that creates Pods, in a namespace can mount that namespace's Secrets, use any of its ServiceAccounts and mount volumes meant for other workloads.

Chapter 13 of 16

Check before you grant, and be careful with list

kubectl auth can-i asks the authorizer without touching anything

A permission can be tested without being used. kubectl auth can-i sends the API server a SelfSubjectAccessReview, an object that asks whether the caller may do one thing, and prints yes or no. It works with any authorizer. The review's status carries two booleans, allowed and denied, because an authorizer may also say nothing. Three relatives exist in the same API group, authorization.k8s.io. SubjectAccessReview asks about any user, and the kubelet and extension API servers use it to check callers of their own APIs. LocalSubjectAccessReview asks about one namespace. SelfSubjectRulesReview returns the set of actions a user can take in a namespace.

With --as an administrator asks on behalf of another identity. That uses impersonation, which is a permission of its own. kubectl auth can-i --list shows what an identity may do in a namespace.

One check deserves extra care. Everyone sees that get on Secrets reveals their contents. list and watch reveal them too, because a list response holds every Secret in full, data included. The good practices page gives the plain example of kubectl get secrets -A -o yaml. A Role that grants only list on Secrets grants reading all of them. The same care applies to creating Pods. Whoever can create a Pod in a namespace can mount that namespace's Secrets into it. The same page also advises reviewing every binding for the group system:unauthenticated and removing it where possible.

Chapter 14 of 16

Asking as someone else

Impersonation swaps the identity after authentication, and it is a privilege in itself

kubectl --as is impersonation, and it works on every request, not only on can-i. The caller sends its own credential plus headers that name another identity. The API server first authenticates the caller. Then it checks that the caller may impersonate. Then it replaces the request's user information with the impersonated values, and authorization runs against those. The headers are Impersonate-User, Impersonate-Uid, Impersonate-Group, which may be repeated, and Impersonate-Extra- followed by a key. All of them except Impersonate-User require Impersonate-User to be present. kubectl sets them with --as, --as-uid and --as-group.

The classic permission is the verb impersonate on users, groups or serviceaccounts in the core API group, and on userextras and uids in authentication.k8s.io. Every named identity is checked on its own, so a request that names a user and two groups needs impersonate on the user and on each group. It can be narrowed with resourceNames to particular identities. It cannot be narrowed to particular actions: once granted, the impersonator can do anything the target can, in every namespace. The good practices page counts it among the escalation paths, because it lets a user take on the rights of other users. Granting impersonate on serviceaccounts in a namespace is close to granting everything those accounts can do.

ConstrainedImpersonation, alpha in 1.35 and beta and on by default since 1.36, adds a finer kind. It needs two separate permissions. The first, granted in the API group authentication.k8s.io, says whom the caller may impersonate, with verbs such as impersonate:serviceaccount, impersonate:user-info for ordinary users, groups, UIDs and extra fields, and impersonate:arbitrary-node or impersonate:associated-node for nodes. The second says what the caller may do while impersonating, with verbs of the form impersonate-on:serviceaccount:list on the resource being acted on. The API server checks the constrained permissions first and falls back to the plain impersonate verb if they fail, so existing rules keep working. The audit event then carries authenticationMetadata.impersonationConstraint with the verb that was used, and apiserver_impersonation_attempts_total counts attempts by mode and decision.

This matters for AI agents that operate a cluster. The site owner's notes on agent identity describe the choice. An agent that impersonates the user it works for, as a Kubernetes debugging agent might, is held to that user's RBAC, and the audit log shows the user doing everything. An agent that acts by delegation keeps its own identity and records that it acted for someone. Kubernetes impersonation is the first kind. Constrained impersonation lets an operator hold such an agent to a short list of actions, for example only get and list on Deployments while it acts as the pipeline. The audit log does record the original caller next to the impersonated user, so an operator can still tell an agent's requests apart if the agent has an identity of its own.

Chapter 15 of 16

Roles that grow, and the limit on granting

Aggregation adds rules to a role. escalate and bind limit who can hand rules out

A ClusterRole can be assembled from others. An aggregated ClusterRole has an aggregationRule with a label selector and no rules of its own. A controller finds every ClusterRole whose labels match and copies their rules in. The built-in roles admin, edit and view work this way, through the labels rbac.authorization.k8s.io/aggregate-to-admin, aggregate-to-edit and aggregate-to-view, each set to true. When an operator for model serving is installed and brings a ClusterRole with the label rbac.authorization.k8s.io/aggregate-to-edit set to true, everyone bound to edit gains those rules. A role can grow without anyone editing it.

Handing out permissions is guarded. The API refuses to create or update a Role that holds a permission its author lacks, unless the author has the verb escalate on roles. The author must hold each permission at the same scope as the object: across the cluster for a ClusterRole, and in the same namespace or across the cluster for a Role. The API refuses a RoleBinding to a role whose permissions the author lacks, unless the author has the verb bind on that role.

bind can itself be narrowed. The RBAC page's example lets a user create RoleBindings but bind only the ClusterRoles admin, edit and view, with a rule for the verb bind on clusterroles and resourceNames admin, edit and view. Write access to RBAC objects cannot be turned into more access than the writer already has.

Chapter 16 of 16

The roles every cluster starts with, and RBAC kept in files

Default roles are repaired at every start. kubectl auth reconcile applies RBAC safely

Every cluster starts with a set of ClusterRoles and ClusterRoleBindings, all labelled kubernetes.io/bootstrapping=rbac-defaults. At each start the API server adds back any permission missing from a default ClusterRole and any subject missing from a default binding. A default object marked with the annotation rbac.authorization.kubernetes.io/autoupdate set to false is left alone, which also means it no longer receives fixes in later releases.

Four of the defaults are meant for people. cluster-admin can do anything. Bound with a ClusterRoleBinding it covers the whole cluster. Bound with a RoleBinding it gives full control over that one namespace, including the namespace object itself. admin gives broad rights within a namespace, including Roles and RoleBindings, and does not allow writing resource quotas or the namespace. edit allows changing most objects and does not allow viewing or changing Roles and RoleBindings. The RBAC page warns that edit still allows reading Secrets and running Pods as any ServiceAccount in the namespace, so it can reach the API rights of every account there. view allows reading most objects and leaves out Secrets, because their contents include ServiceAccount credentials.

RBAC objects kept in files are best applied with kubectl auth reconcile -f. It creates what is missing, adds permissions to existing roles and subjects to existing bindings, and removes extra ones only when given --remove-extra-permissions or --remove-extra-subjects. When a binding's roleRef changes, it deletes the binding and creates it again, which plain apply cannot do because the field is immutable. --dry-run=client shows the changes first. For this cluster the file would hold the Role deployment-editor and its binding, and nothing at all for the account qwen3.

What to keep

An identity, a token, a rule, an answer

Every request to the API server is authenticated and then authorized. People arrive with certificates that cannot be revoked or tokens from a provider, kubelets with their own node identity held in check by the Node authorizer, and Pods with a ServiceAccount and a signed token that the kubelet requests for that one Pod, writes to a file and keeps replacing. A token cannot be revoked on its own, so it is taken back by deleting what it is bound to. RBAC answers the second check from Roles, which list verbs on resources and subresources, and bindings, which give a Role to a subject. Rules only add. An account with no binding gets 403 Forbidden, and the message says which user, verb and resource were involved. The model server ended with no permissions, and the pipeline with five verbs on one resource in one namespace. The limits on escalate, bind and impersonate keep either of them from granting itself more.
