Kubernetes underneath

A packet between two nodes

How flannel wraps a Pod's packet in VXLAN, and what the 50 bytes cost

Pod client on node-1 sends a TCP SYN to Pod web-2 at 10.244.2.17 on node-2. The network between the nodes knows the node addresses 10.0.1.11 and 10.0.1.12 and has never heard of 10.244.2.17. Flannel solves this with an overlay: node-1 wraps the Pod's packet inside a UDP packet addressed to node-2, and node-2 unwraps it. The wrapping format is VXLAN, defined in RFC 7348. This lesson follows the packet through the routing decision on node-1, the three kernel entries flannel wrote in advance, the four headers that are added, the 50 bytes they cost, what the switch sees, and the delivery on node-2. It also explains what a VNI is, how several VNIs keep networks apart on one underlay, the forwarding database and ARP entries a VXLAN device needs, and what an operator sees when the tunnel works and when it breaks.

Chapter 1 of 18

The Pod sends it to the gateway

The destination is outside the Pod's subnet

The kernel inside Pod client looks up 10.244.2.17 in the Pod's routing table. The address is outside the Pod's own subnet 10.244.1.0/24, so the direct route does not match. The route that matches is 10.244.0.0/16 through 10.244.1.1, which is the address of the bridge cni0 on node-1. The Pod needs the gateway's MAC address and sends an ARP request for 10.244.1.1. The bridge device answers for itself. The Pod then sends the SYN with a combination that is normal for routed traffic: the IP header names web-2 as the destination, and the Ethernet header names the bridge. The frame is 74 bytes, made of a 14 byte Ethernet header, a 20 byte IPv4 header and 40 bytes of TCP.

The SYN is the same 74 byte frame that crossed the bridge in the previous lesson, with one difference: its Ethernet destination. Because the frame is addressed to cni0's own MAC address, the bridge finds that address in its forwarding table marked local and hands the frame to the node instead of switching it to a port. That entry is how a Linux bridge also acts as the gateway of the Pods behind it.

The TCP options are those of any Linux client: a maximum segment size of 1410, SACK permitted, timestamps and window scaling, 20 bytes in all. The 1410 already contains the cost of the tunnel. eth0 in the Pod has an MTU of 1450, and 1450 minus 20 bytes of IPv4 header and 20 bytes of TCP header is 1410. The client has no idea a tunnel is involved. It only knows its own MTU, and flannel chose that MTU so that the wrapped packet fits the network between the nodes. The ARP answer for 10.244.1.1 stays in the Pod's neighbour table, so the next connection to any other node skips this step.

Chapter 2 of 18

Node-1 acts as a router

One route for each node's Pod range

The frame is addressed to the bridge's own MAC address, so the bridge does not switch it to another port. It passes the packet up to the IP layer of the node, and the node now acts as a router. Its routing table has one entry for each node's Pod range. The entry for this node points at cni0. The entry for node-2 reads 10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink. The device flannel.1 is a VXLAN device that flannel created, and 10.244.2.0 is the address of the same device on node-2. The word onlink tells the kernel to treat that next hop as directly attached to flannel.1, even though no address on the device covers it. Routing costs the packet one hop, so its time to live drops from 64 to 63.

ip route on node-1 shows the candidates side by side. 10.244.1.0/24 dev cni0 proto kernel scope link src 10.244.1.1 covers the node's own Pods, and the kernel added it when cni0 got its address. 10.244.2.0/24 via 10.244.2.0 dev flannel.1 onlink covers node-2's Pods, and flanneld added it. The destination 10.244.2.17 matches only the second, with 24 bits, which beats the node's default route with 0 bits. The next chapter shows the checks the packet passes before the kernel hands it to flannel.1.

The routing table on node-1 holds one such entry per remote node, so a cluster of 100 nodes has 99 of them. The address 10.244.2.0 is odd for a next hop, because it is the first address of node-2's range. flannel gives it to flannel.1 on node-2 as a /32, a single address, so that the kernel creates no broadcast routes for it. flannel's source explains why the device needs an address at all: the node uses it as the source of traffic it sends to Pods itself, so the reply has an address on the flannel network to come back to. onlink is a flag on the route. The kernel would normally refuse a gateway that no local address covers, and the flag tells it to accept the gateway as reachable on flannel.1 anyway.

Chapter 3 of 18

The node must be allowed to forward

Three checks the packet passes before it reaches flannel.1

Between the packet's arrival on cni0 and the tunnel device the kernel runs three checks, and each one has stopped real clusters. Two of them are part of the routing decision itself. When the kernel looks up the route for a packet that came in on an interface, it first checks that forwarding is enabled on that interface, and then it validates the packet's source address. Only after the lookup has produced a route does the packet reach the firewall's FORWARD hook.

The first check is the forwarding switch itself. net.ipv4.ip_forward must be 1, and the kernel's documentation gives its default as 0, disabled. Writing it sets forwarding on every interface, and the route lookup tests the incoming interface's own setting. On a node where it is 0, the node still answers ping on its own address and still reaches its own Pods through the bridge, but every packet from a Pod to another node is dropped silently, because the lookup ends with no route. The Kubernetes container runtime page tells you to set it and to check it with sysctl net.ipv4.ip_forward.

The second check is reverse path filtering, set by rp_filter per interface and run inside the same route lookup. With the value 1, strict mode, the kernel drops a packet if the route back to its source would leave by a different interface than the one it arrived on. With 2, loose mode, the source only has to be reachable by some interface, and the kernel documentation recommends loose mode for asymmetric routing. In this cluster the checks pass even in strict mode. On node-1 the SYN arrived on cni0, and the route to 10.244.1.12 leads to cni0. On node-2 the unwrapped packet will arrive on flannel.1, and the route back to 10.244.1.0/24 leads to flannel.1 as well.

The third check is the firewall's FORWARD chain, which the kernel runs once the route is chosen and the packet is about to be forwarded. A routed packet passes it, and on many hosts the default policy of that chain is DROP. flannel's troubleshooting page explains the history: Docker 1.13 changed the policy to DROP, and the symptom was that containers on different hosts could not reach each other. flanneld therefore installs its own accept rules, a jump with the comment flanneld forward to the chain FLANNEL-FWD, which accepts any source or destination inside 10.244.0.0/16. The flag --iptables-forward-rules controls this and defaults to true. flanneld puts the rules back every 5 seconds, the default of --iptables-resync, in case another program removed them. A packet that fails this check was already routed, so the drop happens after the two checks of the route lookup have passed.

Chapter 4 of 18

How node-1 knows where node-2 is

Static entries that flannel wrote from what it watches in the API server

Nothing in that route says 10.0.1.12. The link between the Pod range and the node address was written earlier by flanneld, the flannel agent that runs on every node. When flanneld starts on node-2 and once node-2's range and address are known, as the next chapter shows, it creates flannel.1 and records three facts as annotations on its own Node object in the API server: the backend type, the node's address and the MAC address of its flannel.1. Every other flanneld watches Node objects. When node-1 sees node-2, it writes three entries into its kernel, in this order. A permanent neighbour entry says 10.244.2.0 has node-2's flannel.1 MAC address. A forwarding entry on flannel.1 says that MAC address lives behind 10.0.1.12. The route comes last. Because all three are static, node-1 never sends an ARP request through the tunnel.

The order matters because the route is what attracts packets. If the route existed first, packets would reach flannel.1 before the device knew where to send them, and they would be dropped. flannel's code writes the neighbour entry, then the forwarding entry, then the route, and it wraps each step in a retry. If the route cannot be added, it removes the two entries it already wrote, so no half finished state stays behind.

The watch is how flannel learns of changes. Its Kubernetes subnet manager keeps a watch open on Node objects and processes every Node again every 5 minutes, the resyncPeriod in its source. Because the three entries are static, the packets themselves never wait for flanneld. Earlier versions of flannel worked differently. The kernel asked flanneld for the missing pieces with L2 miss and L3 miss messages, the first time a Pod talked to a remote container, and flanneld answered. The current design removed both callouts. flannel's source notes that this improves reliability, because a crash or restart of flanneld no longer causes timeouts. The forwarding keeps working while flanneld is down, and only changes to the set of nodes wait until it comes back.

Chapter 5 of 18

Where node-2's range and address come from

Kubernetes assigns the range, flannel picks the address

flannel does not invent node-2's range. Its Kubernetes subnet manager relies on each Node already having spec.podCIDR set, and the troubleshooting page says so in those words. The range is set by kube-controller-manager when it runs with --allocate-node-cidrs=true and --cluster-cidr=10.244.0.0/16, or by the kubelet's --pod-cidr flag. With kubeadm, kubeadm init --pod-network-cidr=10.244.0.0/16 sets the controller manager flags. The size of each node's range comes from --node-cidr-mask-size, which defaults to 24 for IPv4. That is how node-1 got 10.244.1.0/24 and node-2 got 10.244.2.0/24.

flannel's own configuration must agree. The DaemonSet mounts net-conf.json with Network 10.244.0.0/16 and Backend Type vxlan. If a Node's range lies outside that Network, flanneld refuses to start and says that the subnet in the flannel net config does not contain the node's PodCIDR. If the Node has no range at all, it exits with node node-2 pod cidr not assigned.

The address that goes into the forwarding entry is node-2's public IP, flannel's name for the address other nodes use to reach it. flanneld chooses it at start. By default it takes the interface of the machine's default route and that interface's address. The flags --iface, --iface-regex and --iface-can-reach choose another interface, and --public-ip sets the address directly. A Node annotation, flannel.alpha.coreos.com/public-ip-overwrite, does the same per node. The choice appears in flanneld's log, in lines such as Using interface with name eth0 and address 10.0.1.12. Because the lease is tied to that address, flannel must be restarted if it changes.

Only after both are known does flanneld publish the annotations the previous chapter described, write /run/flannel/subnet.env and mark the node ready. It patches the Node's condition NetworkUnavailable to False with the reason FlannelIsUp and the message Flannel is running on this node.

Chapter 6 of 18

flanneld builds flannel.1

One VXLAN device per node, sized and named from the backend options

flannel.1 is a kernel VXLAN device that flanneld creates when the vxlan backend starts. Its name comes from the VNI, flannel. followed by the number, and the default VNI on Linux is 1. flanneld logs the options it uses in one line: VXLAN config: VNI=1, then the port, then GBP=false, Learning=false and DirectRouting=false. GBP is the group based policy extension, which flannel leaves off.

The device gets a handful of attributes. VxlanId is the VNI. SrcAddr is node-2's public IP, 10.0.1.12, which becomes the outer source address. Port is the UDP destination port. When the backend option Port is not set, the kernel default applies, which is 8472 on Linux. The kernel documentation explains why that differs from 4789, the number IANA assigned. Linux shipped VXLAN before IANA chose the standard port and kept its own value to stay compatible. On Windows flannel must use 4789 and a VNI of at least 4096. Learning is false, so the device does not learn addresses from the packets it receives.

The MTU is the external interface's MTU minus 50, 1500 minus 50 = 1450 here. If the interface is a jumbo frame link of 9000 bytes, flannel.1 gets 8950 and so do the Pods. The backend option MTU replaces the external interface's MTU in that sum, and flannel still subtracts 50 from it. A backend configuration with MTU set to 1500 therefore still gives flannel.1 and the Pods 1450, and setting the Pods to 1500 takes an MTU of 1550 there and a network that carries it.

The MAC address of flannel.1 is part of what other nodes store, so flannel keeps it stable. When flanneld restarts, it reads the MAC address back from its own Node annotation and sets it on the device, and logs Interface flannel.1 mac address set to the address. Only a node that never had one gets a new random MAC address. If a device named flannel.1 already exists with different settings, for example another VNI, flanneld logs that it exists with incompatible configuration and recreates it.

Chapter 7 of 18

What a VNI is

A 24 bit network number that keeps overlays apart on one wire

VNI stands for VXLAN Network Identifier. RFC 7348 calls each overlay a VXLAN segment and gives every segment a 24 bit number. 24 bits allow 2 to the power of 24, or 16,777,216, segments. The kernel documentation names the reason this mattered: an IEEE 802.1Q VLAN tag has a 12 bit ID, so a network can hold at most 4096 VLANs. A cloud with thousands of tenants runs out of VLANs. It does not run out of VNIs.

The VNI is the only field in the VXLAN header that carries meaning. The header is 8 bytes. The first byte holds the flags, and only the I bit, value 0x08, is set, to say the VNI is valid. Three reserved bytes follow, then three bytes of VNI, then one more reserved byte. The RFC requires the reserved bits to be zero on transmission and ignored on receipt. For flannel the three VNI bytes are 00 00 01.

The RFC states what the number does. Only endpoints in the same segment can talk to each other, and because the VNI scopes the inner frame, two segments may use the same MAC addresses without their traffic ever crossing over. The same holds for IP addresses inside the frame. Two tenants can both number their Pods out of 10.244.0.0/16, and the VNI tells the receiving node which network a frame belongs to.

Linux implements this with one device per VNI. All VXLAN devices on a node that use the same UDP port share one socket. When a packet arrives on port 8472, the kernel reads the VNI from the header and looks for the device that owns it. flannel.1 owns VNI 1. If no device owns the VNI in the packet, the kernel drops the packet and counts it with the reason that no tunnel was found. That is the isolation, enforced at the receiving node.

The VNI is a label and no proof of anything. Nothing in the header authenticates the sender, so any machine that can send UDP to port 8472 on a node can write any VNI into a packet. The separation holds only as long as the underlay keeps strangers away from the tunnel endpoints, which is one reason to block the VXLAN port at the edge of the node network.

Chapter 8 of 18

The forwarding database and the ARP entries

What a VXLAN device must know before it can send one frame

A VXLAN device carries Ethernet frames, so it needs two answers for every frame it sends. The first is a MAC address for the next hop, to write the inner Ethernet header. The kernel gets that from the neighbour table, the same table ARP fills on any Ethernet device. The second is the address of the remote tunnel endpoint, to write the outer IP header. The device gets that from its own forwarding database, the FDB, which maps an inner destination MAC address to a remote IP address. bridge fdb show dev flannel.1 lists it. An FDB entry can also name a VNI and a UDP port for that destination, and when it names none, the device's own values are used.

The kernel's transmit code shows what happens when the FDB has no answer. It looks for the destination MAC address. If that is missing, it looks for the all zeros address 00:00:00:00:00:00, the default destination. A default destination can be a multicast group, as in the kernel's example ip link add vxlan0 type vxlan id 42 group 239.1.1.1, or a list of remote addresses, in which case the device sends one copy to each. If there is no default destination either, the frame is dropped and counted as a transmit drop.

There are three ways to fill the FDB. The first is the one RFC 7348 describes, flood and learn. Unknown and broadcast frames go to a multicast group that belongs to the VNI, and each endpoint learns from what it receives that the inner source MAC address sits behind the outer source IP. The kernel does this when learning is on, and learned entries age out after 300 seconds. The second is to let a program write static entries, which is what flannel does. The third is a control protocol. In EVPN, BGP carries the MAC and IP addresses behind each endpoint, so every endpoint can program its tables without flooding. The owner's F5 deck describes exactly this for GPU clusters: EVPN-VXLAN replaces static VLAN configuration, each tenant gets isolation and routing like a cloud VPC, and compute nodes with DPUs join the EVPN fabric and exchange routes themselves.

flannel needs no flooding at all, because a static neighbour entry answers the ARP question before it is asked. The entry for 10.244.2.0 is permanent, so the kernel never sends an ARP request into flannel.1. The FDB entry for node-2's VTEP MAC address is permanent too, marked self so the VXLAN driver handles it directly. With 100 nodes each node holds 99 routes, 99 neighbour entries and 99 FDB entries, which flannel's source sums up as one of each per host.

Chapter 9 of 18

Four headers go around the packet

Ethernet 14, IPv4 20, UDP 8, VXLAN 8

flannel.1 first gives the routed packet a new Ethernet header. Its destination is the MAC address of flannel.1 on node-2, taken from the neighbour entry. That inner frame is 74 bytes. Then the VXLAN code in the kernel wraps it. An 8 byte VXLAN header carries a flags byte of 0x08 and the 24 bit VXLAN Network Identifier, or VNI, which is 1 in flannel. An 8 byte UDP header carries destination port 8472 and a source port computed from a hash of the inner headers. A 20 byte IPv4 header goes from 10.0.1.11 to 10.0.1.12, the address the forwarding entry gave. A 14 byte Ethernet header carries the MAC addresses of the two real network cards. That is 50 new bytes in front of 74, a frame of 124 bytes.

The lengths in the new headers can be computed. The outer IPv4 header's total length counts everything after the Ethernet header: 20 + 8 + 8 + 74 = 110 bytes. The UDP length field counts the UDP header and what follows: 8 + 8 + 74 = 90 bytes. The outer protocol number is 17, UDP. The inner frame keeps its own 74 bytes untouched, including the inner IPv4 header with TTL 63 and the TCP options.

The inner Ethernet header is not the one the Pod wrote. The Pod addressed its frame to cni0. Routing removed that header, and flannel.1 wrote a fresh one from its own MAC address to node-2's flannel.1 MAC address. Those two MAC addresses exist only on virtual devices and mean something only inside the tunnel. The outer Ethernet header carries the MAC addresses of the real network cards, the only ones the switch has ever seen.

Chapter 10 of 18

The outer headers in detail

Source port, checksum and the Don't Fragment bit

The UDP source port is chosen per flow. The kernel takes the flow hash of the inner packet, computed from its addresses and ports, and maps it into a port range. If no flow hash is available, it hashes the two inner MAC addresses instead. The range matters. RFC 7348 recommends the dynamic range 49152 to 65535. Linux uses the device's own source port range when one is configured with the srcport option. flannel does not configure one, so the kernel falls back to net.ipv4.ip_local_port_range, whose defaults are 32768 and 60999. That gives 60999 − 32768 + 1 = 28,232 possible source ports. The 41873 in this lesson is inside that range.

The outer UDP checksum may be zero. RFC 7348 says it should be sent as zero and must be accepted as zero, because the inner packet carries its own checksums. Linux makes it a device option, udpcsum. flannel's troubleshooting page records a real failure tied to it: when a node's public address is behind NAT, the checksum fields of VXLAN packets can be corrupted, and the documented fix is ethtool -K flannel.1 tx-checksum-ip-generic off, made permanent with a udev rule.

The outer IPv4 header has a Don't Fragment bit. iproute2 documents the df option of a VXLAN device and says the bit is not set by default. flannel does not set that option. So when an outer packet is larger than a link on the way, a router may fragment it instead of dropping it. RFC 7348 adds that the receiving endpoint may silently discard such fragments. Fragmented tunnel traffic is therefore something to avoid, which is why flannel lowers the Pod MTU instead.

Network cards have learned this format. The kernel documentation lists offload features that point to VXLAN support: tx-udp_tnl-segmentation and tx-udp_tnl-csum-segmentation let the card cut a large TCP send into packets after encapsulation, and rx-udp_tunnel-port-offload lets it parse received tunnel packets. ethtool --show-tunnels eth0 lists the UDP ports the card has been told about. On a GPU node that pushes model traffic at high rates, these offloads decide how much CPU the tunnel costs.

Chapter 11 of 18

Fifty bytes and the MTU

Why every Pod's eth0 says 1450

The network between the nodes has an MTU of 1500 bytes. MTU, the maximum transmission unit, is the largest IP packet a link carries, counted without the Ethernet header. The outer IP packet holds 20 bytes of IPv4 header, 8 of UDP, 8 of VXLAN and the 14 byte inner Ethernet header before the Pod's packet begins. That leaves 1500 minus 50, or 1450 bytes, for the Pod. flanneld does this subtraction when it creates flannel.1 and writes FLANNEL_MTU=1450 to /run/flannel/subnet.env. The CNI plugin passes the value on as the bridge plugin's mtu, so every Pod's eth0 has an MTU of 1450. TCP then offers a maximum segment size of 1410, and a full packet from a Pod fills the outer packet to exactly 1500. RFC 7348 says tunnel endpoints must not fragment VXLAN packets, so the sizes have to fit in advance.

The numbers move together on other networks. On a jumbo frame network with an MTU of 9000, flannel.1 and every Pod get 9000 − 50 = 8950, and TCP offers a segment size of 8950 − 40 = 8910. flannel's troubleshooting page advises a network with a large MTU for the most raw bandwidth, because the 50 bytes then cost 50 of 9000 bytes, about 0.6 percent, instead of 50 of 1500, about 3.3 percent.

The value reaches the Pods only once. A Pod's eth0 gets its MTU when the CNI plugin creates it. If the node network's MTU changes later, or if flannel.1 was created with a wrong value, existing Pods keep the old one until they are recreated. A mismatch is easy to miss, because small packets fit either way. A connection opens and short requests work. Only full sized packets exceed what the path can carry, and if they are dropped on the way, bulk transfers stall. For a model server that streams long answers or loads the 34.3 GB of weights of the FP8 build Qwen3-32B-FP8 from a peer, the large packets are the traffic that matters.

Chapter 12 of 18

What the switch sees

Two nodes exchanging UDP, and no Pod address anywhere it looks

The frame leaves node-1's network card and reaches the switch. The switch reads the outer Ethernet header and forwards by the MAC address of node-2's network card. Its table holds the addresses of the nodes and nothing else. A router on the way would read the outer IP header and see 10.0.1.11 sending UDP to 10.0.1.12 on port 8472. No device between the nodes needs a route to 10.244.0.0/16, which is the point of an overlay. Two things do matter to the physical network. It must carry 1500 byte packets between nodes and allow UDP port 8472. And the UDP source port changes from one Pod connection to the next, so equipment that spreads load by hashing the outer headers can still tell flows apart. VXLAN does not encrypt, so a capture on the switch shows the inner packet in clear.

The UDP source port is what keeps load balancing working. Switches and routers that spread traffic over several equal links hash the outer headers to pick a link. If every packet between two nodes had the same five values, source and destination address, protocol, and the two ports, all of them would take one link. Because the source port comes from the inner connection, two Pod connections between the same two nodes usually take different ports and can take different links. The RFC recommends this for exactly that reason.

A capture shows how readable the tunnel is. A tool such as tcpdump on node-1's eth0 shows UDP packets to port 8472. Once a decoder is told to read that port as VXLAN, the inner Ethernet header, the Pod addresses and the TCP ports are all visible. flannel offers a wireguard backend for clusters that need encryption between nodes. It listens on UDP port 51820 by default.

Chapter 13 of 18

When the tunnel breaks

Four failures and what each one looks like

The first failure is a blocked port. flannel's documentation is direct: with the vxlan backend the kernel uses UDP port 8472, and the firewall must allow it between all hosts in the overlay. With firewalld the command is firewall-cmd --permanent --zone=public --add-port=8472/udp. The symptom has a clear shape. Pods on the same node reach each other, because that traffic never enters the tunnel. Pods on different nodes do not, and nothing reports an error. The SYN simply never arrives, and the client times out.

The second is a wrong public address. flannel's troubleshooting page uses Vagrant as its example. Vagrant gives every virtual machine a first interface with the same address, 10.0.2.15, for traffic to the outside. flanneld picks the default route's interface, so every node announces 10.0.2.15 as its public IP. Every FDB entry on every node then points at 10.0.2.15, and the tunnel goes nowhere. The fix is --iface=eth1, the interface that really connects the nodes.

The third is a missing range. If kube-controller-manager does not allocate Pod ranges, the Node has no spec.podCIDR, and flanneld exits with node node-2 pod cidr not assigned. The Pod of the flannel DaemonSet on that node restarts again and again, and Pods there wait in ContainerCreating because the CNI plugin finds no subnet.env.

The fourth is missing permissions. flanneld runs with the capabilities NET_ADMIN and NET_RAW and with hostNetwork true. Without them it cannot create the device or write the entries, and its log shows errors such as Error registering network: operation not permitted, Add L2 failed or Failed to set up IP Masquerade. The flannel Pods' logs are where to look in all four cases: kubectl logs --namespace kube-flannel with the Pod name and -c kube-flannel, after kubectl get pod --namespace kube-flannel -l app=flannel finds the Pods.

Chapter 14 of 18

Node-2 unwraps it

Port 8472, VNI 1, then an ordinary route to the bridge

node-2's network card receives a UDP packet for its own address on port 8472. The kernel's VXLAN code is listening on that port. It reads the VNI, finds the device for VNI 1, which is flannel.1, and removes the outer Ethernet, IPv4, UDP and VXLAN headers. Fifty bytes are gone and the 74 byte inner frame is left. Its destination MAC address is flannel.1's own, so the node keeps it and routes the packet inside. The destination 10.244.2.17 matches 10.244.2.0/24 on cni0. The node finds web-2's MAC address with ARP on the bridge, writes a third Ethernet header and lowers the time to live to 62. The bridge sends the frame out of web-2's port and the cable delivers it. web-2 sees a SYN from 10.244.1.12, the client's real address.

The VNI check is the moment the VNI chapter described. The kernel's socket on port 8472 serves every VXLAN device on node-2. It reads the three VNI bytes, finds flannel.1 as the owner of VNI 1 and hands the inner frame to that device as if it had arrived on an Ethernet port. Because learning is off, the device writes nothing into its FDB from this packet. A learning device would have noted that the inner source MAC address sits behind 10.0.1.11.

The packet then passes the same checks node-1 applied. ip_forward must be 1 on node-2, the FORWARD chain must accept it, and the reverse path check passes, because the route back to 10.244.1.0/24 leads out of flannel.1, the interface the packet came in on. The node then needs web-2's MAC address. Its neighbour table on cni0 usually has it from earlier traffic. If not, node-2 sends one ARP request for 10.244.2.17 on its bridge, exactly as a Pod did in the previous lesson.

Chapter 15 of 18

What a healthy node shows

Logs, a readiness endpoint and the Node condition

An operator who wants to confirm the tunnel without capturing packets has three places to look. The first is flanneld's log. flannel uses the klog library and writes only to standard error, so kubectl logs on the flannel Pod shows everything, and -v raises the detail. A healthy start prints Created subnet manager, then Found network config - Backend type: vxlan, then the VXLAN config line with VNI=1, then Wrote subnet file to /run/flannel/subnet.env, Running backend. and watching for new subnet leases. At verbosity 2 each remote node appears as a line that starts with adding subnet. In node-1's log, node-2 shows up as adding subnet: 10.244.2.0/24 PublicIP: 10.0.1.12 VtepMAC: followed by node-2's MAC address. node-2's log has the mirror line for node-1, adding subnet: 10.244.1.0/24 PublicIP: 10.0.1.11, which is the line the beat below shows.

The second is flanneld's health server. The flag --healthz-port defaults to 0, disabled, and flannel's manifest sets it to 8081. /healthz returns HTTP 200 whenever the process is running and serves as the liveness probe, checked every 30 seconds after an initial 10. /readyz returns 503 until startup is complete, which means the masquerade and forward rules are installed and subnet.env is written, and 200 after that. The readiness probe checks it every 10 seconds after an initial 5.

The third is the Node object. flanneld sets NetworkUnavailable to False with the reason FlannelIsUp. kubectl describe node node-2 shows it among the conditions, and the annotations flannel.alpha.coreos.com/public-ip and backend-data show the address and VTEP MAC address the other nodes use.

On the node itself the three entries per remote node can be listed. ip route shows 10.244.1.0/24 via 10.244.1.0 dev flannel.1 onlink on node-2. ip neigh show dev flannel.1 shows the permanent neighbour entry, and bridge fdb show dev flannel.1 shows the forwarding entry with the destination 10.0.1.11. ip -d link show flannel.1 prints the device's VXLAN settings, including its VNI.

Chapter 16 of 18

The reply, and clusters without a tunnel

The same wrap in reverse, and what other designs do

web-2 answers with a SYN-ACK and everything runs in reverse. node-2 has its own three entries for node-1, wraps the reply and sends it as UDP from 10.0.1.12 to 10.0.1.11. The tunnel is one design among several. Flannel has another backend called host-gw that adds a plain route to each remote Pod range through the other node's address and wraps nothing. It needs the nodes to share a layer 2 network. Flannel's VXLAN backend has an option, DirectRouting, that does the same for nodes on one subnet and keeps the tunnel for the rest. Calico can run without an overlay and announce Pod ranges with BGP, and Cilium has a native routing mode. Without a tunnel there is no 50 byte cost, and either the nodes or the network between them must hold a route to each Pod range.

flannel has more backends than these two, and its documentation ranks them. VXLAN is the recommended choice. host-gw is for experienced users whose infrastructure supports it, because it needs direct layer 2 connectivity between hosts. wireguard encrypts traffic between nodes and listens on UDP 51820, and 51821 for IPv6, on interfaces named flannel-wg and flannel-wg-v6. The old udp backend, on port 8285, is for debugging only. flannel's performance advice is short: with encapsulation, vxlan always beats udp, and for the best data plane performance avoid encapsulation.

DirectRouting shows that the choice can be made per node pair. With it turned on, flanneld writes a plain route through the other node's address when that node is in the same subnet, and logs Adding direct route to subnet. For a node in another subnet it writes the three VXLAN entries as before. The backend has to be chosen once. flannel's documentation says it should not be changed at runtime, and flanneld ignores lease events from nodes that run a different backend.

These designs are Kubernetes networking in general. A cluster that runs F5 BIG-IP Next for Kubernetes has a shorter list to choose from, and Cilium is not on it. The next chapter gives that list and what each entry does to the packet in this lesson.

Chapter 17 of 18

Which pod networks BNK accepts

BNK sends traffic straight to Pod addresses, so its operator checks the CNI first

The program that gives each Pod its address and builds the paths in this lesson is the CNI plugin, short for Container Network Interface plugin. The container runtime runs it, on the kubelet's request, every time a Pod starts. Flannel is one CNI plugin among many, and each one moves a Pod's packet between nodes in its own way. That choice matters when F5 BIG-IP Next for Kubernetes (BNK) runs in the cluster. BNK's data plane, TMM (the Traffic Management Microkernel), forwards a client's request to the address of a model server Pod. In this site's cluster that is a Pod such as qwen3-6f7d9c8b4-m9q4t at 10.244.2.22 port 8000 on gpu-node-2, the node with the address 10.0.1.12 that this lesson calls node-2. Its address lies in node-2's range 10.244.2.0/24, next to web-2 at 10.244.2.17, and its sister Pod qwen3-6f7d9c8b4-x7k2p at 10.244.1.21 lies in node-1's range. BNK builds its pool of targets from the Service's EndpointSlice, the Kubernetes object that lists the ready Pod addresses behind a Service. Every one of those addresses has to be reachable from TMM over the pod network that the CNI built.

BNK's operator therefore checks which CNI the cluster runs. Calico is the primary supported CNI. Four others are recognised, the word the owner's install notes use. The notes do not say what that word promises beyond the operator not refusing them, so treat it as weaker than supported. The four are Flannel, the Amazon VPC CNI on EKS, the OCI VCN-Native Pod Networking CNI (OCI-CNI) on Oracle Cloud, and OVN-Kubernetes (OVN-K) on OpenShift. Cilium is not supported, and the operator refuses it. The owner's install notes record the refusal and do not give a reason. The owner's notes say BNK 2.3 is qualified against Kubernetes 1.30. BNK 2.3's DPU install guide also pins Calico 3.29.1, Multus 4.2.0 and SR-IOV device plugin 3.10.0. Those pins come from the guide for DPU installs, and the notes give no qualification matrix for other installs such as host mode. The note on Cilium's native routing in the previous chapter describes Kubernetes in general. On a BNK cluster, a design that relies on Cilium has to be rebuilt on Calico or one of the four recognised CNIs.

Calico gives each IP pool two settings, ipipMode and vxlanMode, each Always, CrossSubnet or Never, with Never as the default and the two never on together. With VXLAN, Calico uses the same 50 bytes of headers as flannel on different numbers: UDP port 4789 where flannel uses 8472, VNI 4096 where flannel uses VNI 1, and a device named vxlan.calico in place of flannel.1. With IP in IP, IP protocol 4, it adds only an outer IPv4 header of 20 bytes through a device named tunl0. Calico's MTU table for a 1500 byte network gives 1480 for IP in IP, 1450 for VXLAN and 1440 for WireGuard. CrossSubnet wraps only the traffic whose destination node is in another subnet, the same idea as flannel's DirectRouting. With Never and BGP, Calico announces Pod routes to the network and the SYN of this lesson crosses the switch as the plain 74 byte frame. Calico also hands out Pod addresses differently. It takes blocks of /26, 64 addresses, from the pool on demand, where flannel gives every node one /24.

The other three move the packet in two more ways. OVN-Kubernetes is the default network plugin of OpenShift and OKD. It builds its overlay with Geneve (Generic Network Virtualization Encapsulation) on UDP port 6081, and OpenShift reserves 100 bytes of overhead for it, so on a 1500 byte network the cluster network MTU is 1400. The Amazon VPC CNI attaches elastic network interfaces to each EC2 node and gives every Pod a private address from the VPC itself. OCI-CNI does the same on Oracle Cloud with secondary VNICs and addresses from the VCN's CIDR block. With these two there is no tunnel at all. The cloud network already knows every Pod address, and the frame on the wire is the Pod's own 74 bytes.

The owner's labs show where a recognised CNI still breaks BNK. On a kind cluster with Calico, the interface setting for Calico's address detection was the regular expression eth0. Calico's default method, first-found, takes the first valid address on the first interface, and interface=<regex> limits it to interfaces whose names match. The lab added VLAN sub-interfaces for tenant traffic, and a sub-interface named eth0.203 also matches the pattern eth0. Calico moved its own VXLAN endpoint onto the tenant leg. The fix was to name the sub-interfaces int-a, int-b and int-c. In the same lab, Felix, Calico's per-node agent, dropped VXLAN arriving from TMM until TMM's self IP addresses were listed in the FelixConfiguration field externalNodesList. Calico blocks tunnelled traffic from non-Calico nodes by default to reduce the attack surface. On OpenShift with BNK 2.4.2 in host mode, Pods on an OVN-K primary user-defined network (UDN) were unreachable. BNK read their addresses from the default network's EndpointSlice, and under a primary UDN those addresses admit only infrastructure traffic. Every request timed out. Tenant isolation for BNK traffic there comes from BNK's own VRFs and VLANs on TMM's interfaces.

The CNI also decides whether a NetworkPolicy does anything. Kubernetes says network policies are implemented by the network plugin, and a NetworkPolicy without a controller that implements it has no effect. flanneld does not enforce Network Policies itself. Calico does. The owner's BNK design notes put default deny egress on the CNI, because BNK does not set it. Any default deny NetworkPolicy, for egress or between tenant namespaces, does nothing on plain flannel, so such a cluster needs a policy controller added before that promise holds.

Chapter 18 of 18

When a node joins or leaves

flanneld adds and removes three entries, and repairs the device

Clusters change while the tunnel runs. When a third GPU node joins, flanneld on node-1 sees a new lease in its watch of Node objects and runs the same three steps it ran for node-2: the neighbour entry, the forwarding entry and the route. Each step is retried on failure. If the route fails after the other two succeeded, flannel removes the neighbour and forwarding entries again and logs failed to add vxlanRoute with the subnet and the device.

When a node leaves, flanneld removes the same three things in the same order it added them. On a lease removed event it deletes the neighbour entry, then the forwarding entry, then the route. For the short time between the first delete and the last, the route to the leaving node's range still exists while its neighbour entry is already gone, which is the state that writing the route last avoids on the way in. Packets sent in that moment find no neighbour entry on flannel.1 and are dropped, and they would have had nowhere to go anyway. At verbosity 2 it logs removing subnet with the range, the public IP and the VTEP MAC address. Packets still addressed to that node's Pods no longer match a route through flannel.1. They follow node-1's default route out of the cluster network instead, where nothing knows the Pod range.

flanneld itself is not on the data path, so its restarts are cheap. Existing entries stay in the kernel while it is down, and Pods keep talking. What waits is change: a node that joins while flanneld is down on node-1 is not reachable from node-1's Pods until flanneld comes back and catches up.

Current flannel also guards the device. It watches flannel.1, and if something deletes it, it logs Interface flannel.1 deleted and vxlan device missing, attempting to recreate, builds the device again, logs that it was recreated successfully and then re-applies all known leases, writing every node's three entries back. Releases from before the watcher was added leave a deleted device gone until flanneld restarts.

The same mechanism serves a cluster of model servers. When a new GPU node joins with fresh vLLM Pods, every existing node gets its three entries within the time it takes the Node event to reach each flanneld, and the gateway on node-1 can reach the new Pods without any change to the switch.

What to keep

A Pod packet inside a node packet

The Pod's IP header crossed two nodes without a change to its addresses. Around it, the Ethernet header was replaced twice, and for the stretch between the nodes the whole frame became the payload of a UDP packet. Flannel made that work with one route, one neighbour entry and one forwarding entry for each other node, all written from Node objects before any packet was sent. The price is 50 bytes in every packet and an MTU of 1450 in every Pod. Requests between a gateway on one GPU node and a model server on another ride this tunnel in both directions.
