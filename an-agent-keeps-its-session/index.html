BNK and gateways

An agent keeps its session

MCP sessions and A2A tasks have to land on the replica that knows them, and the caller is not a person

An agent is a program that calls a model in a loop and acts through tools. Its traffic looks like ordinary HTTP. Behind the POSTs are conversations that live on one backend: a session with a tool server, a task handed to another agent. Put several replicas behind a load balancer and the second request can land where nobody knows the first. This lesson follows Northlight's status agent through the factory's border. It shows what a Model Context Protocol session is on the wire, the event streams that hang off it, why round robin breaks it and why its ID must never be treated as a password. Then it shows how BNK's persistence keyed on the session repairs it, field by field, and where that repair ends: a replica that dies. The current MCP revision removes the session altogether and moves state into handles. The Agent2Agent protocol has the same problem with tasks, with its own streams and callbacks. The last chapters look at how a caller with no person behind it gets a token for one server, how that token is checked at the border, and how the same identity is used to limit what the agent can spend. Five more chapters go further. The model call has a session too, held in one GPU's KV cache, and the endpoint picker weighs session affinity against prefix affinity and load. An agent that must remember beyond a session keeps long-term and short-term memory in on-premises object storage. Then the token governance annotation field by field, where the JWT check attaches in BNK 2.4.0 and where it does not yet, and what a firewall for tool calls reads.

Chapter 1 of 19

A session on the wire

One POST to start, one header to keep, one GET to listen

Northlight's status agent uses a tool server for pages and messages. The two speak the Model Context Protocol (MCP) over its Streamable HTTP transport: every message from the client is a new HTTP POST with one JSON-RPC message in the body, sent to one URL that the specification calls the MCP endpoint. The POST must carry an Accept header that lists both application/json and text/event-stream, because the server may answer either way. Chapters one to seven describe protocol revision 2025-11-25, in which a conversation is a session. The current revision, 2026-07-28, removed sessions, and chapters eight and nine show what changed.

The client's first POST is initialize, with the protocol version it wants, its capabilities and its name. The server answers with the version it agrees to, its own capabilities and its name, and it may add a response header, MCP-Session-Id. If it does, the client must send that header on every later request. The client then confirms with notifications/initialized. A notification expects no answer, so the server returns 202 Accepted with no body. From here on the client also sends MCP-Protocol-Version with the agreed version on every request. A server that gets no such header, and has no other way to tell, assumes 2025-03-26. One that gets a version it does not support answers 400 Bad Request.

The client may also send a GET to the same URL. The server answers with a stream of server-sent events for its own messages, such as a notice that its tool list changed, or with 405 Method Not Allowed if it offers no such stream. Every server must check the Origin header on incoming connections and answer 403 Forbidden when it is present and wrong. That stops a web page in someone's browser from reaching a tool server through DNS rebinding.

Chapter 2 of 19

Streams hang off the session

Answers can arrive as event streams, and a broken stream is resumed by ID

A tool call can take a while, and the server may want to say something before its answer is ready. So the answer to a POST can itself be a stream. The server replies with Content-Type: text/event-stream, sends any progress notices that belong to this call, then the JSON-RPC response, and then it should end the stream. A quick call can be answered with plain application/json instead. The client must handle both.

When the server opens such a stream, it should first send a priming event: an event ID with an empty data field. That ID gives the client somewhere to resume from. The server may then close the connection at any time without ending the stream, to avoid holding many long connections open. Before it does, it should send an event with a retry field, a number of milliseconds, and the client must wait that long before it reconnects. A dropped connection never means the client gave up. To cancel a call, the client sends an explicit cancellation notification.

The client reconnects with a GET to the MCP endpoint and a Last-Event-ID header naming the last event it received. Resumption always uses GET, whether the stream began on a POST or a GET. The server may then replay what it would have sent after that event, on that stream only. It must never replay messages that belonged to a different stream, and it must never send one message on two streams. Event IDs must be unique across all the streams of the session, and should encode which stream they came from, so the server can find the right place from the ID alone.

All of that state lives where the stream was opened. The buffer of events after evt-3, the stream it belongs to, the call still running: tools-1 holds them. A resume GET that lands on another replica finds no stream and no events. So persistence has to cover POSTs, the long GET and every reconnection, all by the same session ID.

Chapter 3 of 19

The next request meets a stranger

Round robin sends it to a replica that never saw the initialize

The tool server keeps each session in memory: what was agreed, which streams are open, which events are buffered, what the agent has in progress. Three replicas run behind the BNK data plane, tools-0, tools-1 and tools-2, and BNK hands requests to them in turn with no persistence. In chapters one and two every request of this agent happened to land on tools-1, the replica that holds its session, because other agents' requests filled the turns in between. Up to now the agent was lucky. In this chapter it is not.

The initialize went to tools-1. The agent's next tools/call carries the session ID and goes to tools-2, which has never heard of it. The specification says a server answers 404 Not Found for a session it has ended. It does not define an answer for an ID the server never issued, and the official TypeScript SDK gives 404 for that too, with the JSON-RPC error -32001 and the message Session not found. A client that gets 404 on a request with a session ID must begin again with a new initialize that carries no session ID. Whatever tools-1 held for the old session is orphaned: the half-done work, the open GET stream, the buffered events. It stays in memory until tools-1 ends the session, if it ever does.

With three replicas taking turns, two requests in every three go to a replica that does not hold the session. If this agent were the only caller, the four requests after its initialize would go to tools-2, tools-0, tools-1 and tools-2, and one of the four would work. Other agents' requests take turns in between, so which of an agent's requests land on tools-1 changes from minute to minute. Retrying does not help in a predictable way either. About one retry in three works, which makes the fault look random in logs and dashboards, and a team can spend days on it before anyone looks at the balancer.

The same table explains two other status codes. A request without the session ID, to a server that requires one, gets 400 Bad Request. A client that is done sends DELETE with the ID to end the session, and a server that does not let clients end sessions answers 405.

Chapter 4 of 19

A session ID is a label, never a password

It says where a request belongs and nothing about who sent it

The session ID is about to become the key that BNK routes on, so it matters what it is and what it is not. The specification asks that it be globally unique and cryptographically secure, for example a securely generated UUID, a JWT or a cryptographic hash. It may only contain visible ASCII characters, the bytes 0x21 to 0x7E, which rules out spaces and anything that needs escaping in a header. The client must keep it as carefully as any other secret.

It must still never be used to decide who the caller is. The MCP security guidance is plain about this: servers that implement authorization must verify every inbound request, and must not use sessions for authentication. Two attacks show why. In session hijack impersonation, an attacker who learns or guesses an ID sends requests with it, and a server that checks nothing else treats the attacker as the agent. In session hijack prompt injection, several stateful replicas share a queue of events keyed by session. An attacker sends a crafted event to replica B with someone else's session ID. B puts it in the shared queue, replica A picks it up for that session and delivers it to the real client as if it came from the server. One such event is a notice that the tool list changed, which can leave a client using tools it never agreed to.

The guidance gives three defences. IDs must be random and never sequential, and rotating or expiring them helps. Every request is authenticated on its own, with a token. And anything stored per session is stored under a key that includes the authenticated user, in the form <user_id>:<session_id>. The user part comes from the validated token, never from the client, so a guessed session ID alone opens nothing.

For a load balancer the consequence is simple. It may route on the session ID. It must not let the session ID stand in for identity. Identity is the token, which a later chapter checks at the border.

Chapter 5 of 19

Keep the session on the replica that owns it

Persistence keyed on the session ID, and why the address is the wrong key

Persistence means the load balancer remembers a choice. The first request of a conversation is balanced as usual, and the balancer writes down where it went. Later requests that carry the same key go to the same place. The question is what to use as the key.

BNK's persistence profile defaults to the source address, SRC_ADDR: one client address, one backend. That is a poor fit for agents. Forty agents behind one NAT address, 198.51.100.9 in this example, all look like one client and all land on one replica, while the other two sit idle. And a single agent's address can change in the middle of a session, when its Pod restarts or its egress moves, and then its requests start landing somewhere new. The other address type, DST_ADDR, keys on the destination address and does not separate conversations at all.

The session ID is the better key, because it names exactly the thing that must stay together. BNK has a persistence type for it, MODEL_CONTEXT_PROTOCOL. The 2.4.0 release notes describe it as protocol-aware persistence for stateful agentic workloads, which keeps sessions, streams, task state and long-running workflows continuous as MCP servers, A2A agents and tool services scale out. F5's session on agents says it is keyed on the MCP session identifier. The initialize is balanced like any new request. The replica that answers it owns the session, and every later request with that ID goes back there: POSTs, the long GET and every resume with Last-Event-ID alike.

This also decides what happens when the pool grows. Replicas added later take new sessions. Old sessions stay where they are, so a new replica fills up only as new conversations start. A pool that was scaled out for a burst of load does not relieve the busy replicas at once, because their sessions cannot move.

Chapter 6 of 19

The profile, field by field

A secret, an F5BigPersistenceProfile and a NetPolicy that ties it to a Gateway

Three Kubernetes objects switch this on, all in the same namespace as the Gateway. The first is a Secret holding a passphrase. The MCP and A2A types both require one: mcpEncryptionPassphrase for MODEL_CONTEXT_PROTOCOL and a2aEncryptionPassphrase for AGENT2AGENT. Each points at its Secret with secretRef.name, and passphraseField names the key inside the Secret, passphrase by default. A profile may set one of the two passphrase fields and never both. The reference page does not say what BNK encrypts with the passphrase, and the owner's lab notes say only that BNK tracks the MCP session itself, with its own passphrase.

The second object is the F5BigPersistenceProfile, apiVersion k8s.f5net.com/v1. Its spec.persistenceType takes SRC_ADDR, DST_ADDR, MODEL_CONTEXT_PROTOCOL or AGENT2AGENT, with SRC_ADDR as the default. The other fields belong to address persistence. timeout is 180 seconds by default, and applies only to the DEFAULT hash algorithm. addressAffinity.hashAlgorithm is CARP by default, which is stateless and keeps each client on the same server when the pool size changes. DEFAULT keeps a record per client, which can move a client when its record times out. ipv4PrefixLength (default 32) and ipv6PrefixLength (default 128) set how much of the address counts.

The third is a NetPolicy, apiVersion gateway.k8s.f5.com/v1alpha1. Its extensionRefs list from 1 to 8 objects of the kinds F5BigCneIrule, F5BigPersistenceProfile and F5BigTcpSetting, each persistence profile and TCP setting once. Its targetRefs hold exactly one Gateway, and cannot be changed later. An optional sectionName narrows it to one listener of that Gateway. That is the way to give one listener MCP persistence and another A2A persistence, since one NetPolicy carries one persistence profile.

F5's agents material adds one property: a misconfiguration fails closed, so traffic is never routed unvalidated. The owner's lab verified MCP persistence on a live 2.4.0 cluster.

Chapter 7 of 19

When that replica dies

Persistence keeps a session in place and cannot keep the place alive

Persistence keeps a session on its replica. It cannot keep the replica running. Suppose the node under tools-1 is drained for maintenance and the Pod is deleted. Kubernetes takes the Pod out of the Service's endpoints and sends its process a TERM signal. The process has a grace period to finish, 30 seconds unless the Pod sets terminationGracePeriodSeconds, and is then killed. The open event stream breaks with it.

The agent's next POST still carries the old session ID, and the replica that owned it is gone, so the request has to go to a live one. That replica does not know the session and answers 404. The agent begins again with initialize and gets a new session on another replica. Anything the old replica held only in memory is lost: the agreed capabilities, the event buffers that a Last-Event-ID could have resumed from, and any half-finished work. Here the agent was in the middle of update_page, and that update has to be worked out again from the conversation. Every rolling update of the tool server deletes replicas in the same way, so with sessions held in memory a deploy in working hours restarts every agent conversation that is open.

Two things soften this. A server can keep its session state in a shared store, so that any replica can pick a session up. The security guidance applies there too: it says the server should key the store in a form like <user_id>:<session_id>, and a shared queue of events is exactly what the injection attack in chapter four uses. And a rollout can let old replicas finish the sessions they have before they stop, with a grace period long enough for the typical session. Neither is something the load balancer can do on its own. Persistence moves the problem from the balancer to the replica, and the replica has to solve the rest.

Chapter 8 of 19

The current revision removes the session

Since 2026-07-28 every MCP request stands alone

The MCP specification changed all of this in revision 2026-07-28, which is the current one. The initialize handshake is gone, and so are the session header, the GET stream and stream resumption. Every request now stands alone. It carries its protocol version and the client's capabilities in the _meta field of the body, under io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities, and the client should name itself there too. Lists such as tools/list no longer vary by connection. A client that wants to know a server's versions and capabilities before it starts can call the new server/discover, which every server must implement.

Every POST also repeats facts from the body in HTTP headers. MCP-Protocol-Version must match the version in _meta, Mcp-Method carries the method, and Mcp-Name carries the tool or prompt name for tools/call and prompts/get, taken from params.name, and the resource URI for resources/read, taken from params.uri. A name that is not plain ASCII is sent in a Base64 form. The point is that a gateway can route or check a call without parsing JSON. Header names are compared without regard to case, and header values with it.

Servers answer mismatches precisely. A header that disagrees with the body gets 400 Bad Request with a HeaderMismatch error, code -32020. A version the server does not support gets 400 with UnsupportedProtocolVersionError, code -32022, listing the versions it does support. A method the server does not implement gets 404 with -32601, Method not found, which a client can tell apart from the plain 404 of a server built for the old HTTP+SSE transport.

Server-to-client notices that used to arrive on the GET stream now come on the response to subscriptions/listen, a long-lived POST in which the client names the kinds of change it wants. A broken response stream loses the call in flight, and the client must send it again as a new request with a new ID. Session persistence still serves the servers and clients that speak the earlier revisions.

Chapter 9 of 19

State moves into handles

A name the server hands out, and the model hands back

Some tools still need state across calls: a draft being built, a browser that stays open, a database transaction. Without a session, the specification's guidance is to make that state explicit. A creation tool returns a handle, an opaque string that names the state, and later calls take it as an ordinary argument. The model carries it forward from one call to the next. On the wire a handle is nothing special, just a string in a result and in later arguments.

The guidance names four things to get right. Authorization: for a server that authenticates its callers, a handle is a name and never a capability, so the server checks on every call that this caller may use it. For a server without authentication a handle is all there is, so it needs enough randomness, such as a UUIDv4, and a bounded lifetime. Opacity: a handle that reveals internal structure invites guessing. Lifetime: the creation tool's description should say how long the state is kept, so the model knows before it creates any. Expiry: a call with an unknown or expired handle should get a tool execution error that says so, and the model can then create a new one.

The old problem can come back through a handle. If the state behind it lives in one replica's memory, a call with that handle must reach that replica, and there is no session header for a balancer to key on. A server can help with x-mcp-header. That property in a tool's input schema marks a parameter to be copied into an HTTP header named Mcp-Param- and the given name, so a handle argument can travel as Mcp-Param-Draft. Clients must support it for primitive values. Servers must reject a request whose header and body disagree, because a balancer could route on the header while the server acts on the body.

The better answer is the one from chapter seven: keep the state behind the handle in a shared store, and let any replica serve any call.

Chapter 10 of 19

A2A has the same problem with tasks

The key is a task ID, and it is in the body

MCP connects an agent to tools. The Agent2Agent (A2A) protocol connects an agent to another agent, and its unit of work is a task. Northlight's status agent asks a research agent for a summary with SendMessage, which is POST /message:send in the REST binding. By default SendMessage blocks until the task reaches a final state or one where it waits for input. With returnImmediately set to true it returns as soon as the task exists, which suits work that takes minutes. historyLength in the same configuration caps how many past messages come back, and 0 means none.

The answer is a Task object with an id, a contextId and a status. The contextId groups related tasks and messages into one conversation. The agent may generate it when the message has none, and must then return it. A client should send its own only if it knows how the server treats it. Task states are TASK_STATE_SUBMITTED, TASK_STATE_WORKING, two interrupted states, TASK_STATE_INPUT_REQUIRED and TASK_STATE_AUTH_REQUIRED, and four final ones: TASK_STATE_COMPLETED, TASK_STATE_FAILED, TASK_STATE_CANCELED and TASK_STATE_REJECTED.

The caller then polls with GetTask, which is GET /tasks/{id} in REST, or opens a stream with SubscribeToTask. When tasks live in a replica's memory, both must reach the replica doing the work, or the answer is TaskNotFoundError, JSON-RPC code -32001 or 404 Not Found in REST. Here the key is in the JSON body, or in the URL path with REST. No header carries it. BNK's persistence type for this is AGENT2AGENT, which F5's session describes as keyed on context and task identifiers. It needs a2aEncryptionPassphrase in place of the MCP one.

Every request also carries an A2A-Version header. An empty value means version 0.3, and a version the server does not support gets VersionNotSupportedError, code -32009.

Chapter 11 of 19

Streams, pauses and callbacks for a task

Every way of following a task has to reach the replica doing it

Polling is the simplest way to follow a task, and also the most wasteful. A2A offers two others, and both bring their own routing questions.

SubscribeToTask opens a stream of updates for one task, POST /tasks/{id}:subscribe in REST. Each update arrives as a server-sent event: a change of state, or an artifact the task produced. The stream ends when the task reaches a final state. Like the MCP GET stream it is long-lived, and it has to stay on the replica doing the work for its whole length. A subscription to a task that has already finished fails with UnsupportedOperationError, code -32004, 400 in REST, so a client that reconnects late should poll with GetTask instead.

A task can also stop and wait. TASK_STATE_INPUT_REQUIRED means the other agent needs something from the caller, and TASK_STATE_AUTH_REQUIRED means it needs credentials. The caller answers with another SendMessage that carries the task's id and contextId. That message has to reach the same replica as everything before it, which is the case F5's description of AGENT2AGENT persistence names: context and task identifiers.

The third way turns the direction round. With push notifications, the caller registers a webhook: a url, which is required, an optional token and optional authentication details. The serving agent then POSTs updates to that URL. It must declare pushNotifications as true in its Agent Card, the JSON description every A2A agent publishes at /.well-known/agent-card.json. An agent that does not support them answers PushNotificationNotSupportedError, -32003. The callback travels from the serving agent to the caller, so it needs a route into the caller and an authentication check of its own there.

A caller can also give up. CancelTask, POST /tasks/{id}:cancel, ends the work, and a task that can no longer be cancelled answers TaskNotCancelableError, -32002.

Chapter 12 of 19

A token for one server

The caller has no person at a login page, so it proves itself with OAuth

A session ID says which conversation a request belongs to. It says nothing about who may have that conversation, and chapter four showed why it must never be used for that. An agent has no person at a login page, so it proves itself with an OAuth access token.

The first request without a token shows the agent where to get one. The server answers 401 Unauthorized with a WWW-Authenticate header. Its resource_metadata parameter points to the server's protected resource metadata, a JSON document at a well-known URL that names the authorization servers this server trusts and the scopes it supports. The header should also carry a scope parameter with the scopes this request needs, and a client takes those first. Without them it asks for the scopes_supported in the metadata.

Then the agent asks the authorization server for a token. It names the server it wants to call in the resource parameter defined by RFC 8707, using that server's canonical URI, as specific as it can be. An agent that acts for a person uses the authorization code flow. One with no user behind it, such as a scheduled job, uses the optional client credentials extension: grant_type=client_credentials, with the client proving itself either by a client_id and client_secret or by a JWT it signs with its own private key, per RFC 7523. The second avoids a shared secret. The assertion's aud is the authorization server's issuer identifier.

The token comes back good for that one resource. The agent sends it on every request in the Authorization header as Bearer, and never in the URL's query string. An MCP server must check that the token was issued for it. It must also never pass a token it received on to another API. That pattern, called token passthrough, is forbidden because the downstream API would lose track of which client called it and could no longer limit or audit by client.

Chapter 13 of 19

Checked at the border, scoped to tools

BNK validates the token before any replica is reached

The token arrives with every tool call. The BNK 2.4.0 release notes say it adds OIDC and JWT validation for agentic traffic: it validates identity claims at the traffic layer, before the traffic reaches MCP servers, A2A agents or other services. F5's product deck for the same release words it the other way round, OAuth and JWT validation with OIDC planned, so JWT validation is the part both sources agree on. F5's slide for BNK agents puts the order the same way as the release notes: identity validated at ingress, then protocol-aware persistence keeps sessions on the right backend. The release notes say OAuth-based flows at BNK itself are planned for a later release, so the token in this lesson comes from Northlight's own authorization server and BNK checks it.

A JWT access token, in the profile of RFC 9068, carries claims that make the check possible. iss names the authorization server that issued it, and the signature has to verify with that server's keys. aud names the resource it was issued for. exp says when it stops being valid. client_id names the client, and scope lists what it may do. The audience is the claim that ties this to the resource parameter: a token issued for another server has a different aud and must be refused here, even with a good signature. A gateway that only checks the signature has missed the point of the resource parameter.

An invalid or expired token gets 401 Unauthorized with WWW-Authenticate. A valid token without the needed scope gets 403 Forbidden, with error="insufficient_scope", the scope the operation needs and the resource_metadata link. The client can then ask for the larger scope, adding it to the ones it already has so it loses nothing.

Which tool needs which scope is not in the specification. The server's owner decides. In this lesson update_page needs pages:write and the check runs at the AI gateway. The owner's lab notes record that BNK 2.4.0 has no MCP tool-level authorization object of its own, so a tool rule needs another component. With revision 2026-07-28 that component can read the tool's name from the Mcp-Name header. With earlier revisions it has to read params.name from the JSON body.

Chapter 14 of 19

A limit per agent

Counted by the identity in the token, whatever the address or the session

The last control is a count. A person clicks a few times a minute. An agent in a loop can call a tool hundreds of times while nobody watches, and every tool result goes back into a prompt that a GPU has to read. A limit per source address does little, because many agents share one address and one agent may use several. A limit per session does nothing, because a looping agent can open a new session for every call. The token already names the caller. Its client_id claim is the same on every request this agent sends, whichever session or task the request belongs to.

So the count is kept at the border, per client_id. This is the general pattern of a rate limiter in a gateway, shown here with illustrative numbers, and the lab notes below say what BNK itself was seen to count. Northlight allows this agent 60 tool calls a minute. Call 61 in the same minute is answered with 429 Too Many Requests, which RFC 6585 defines for a client that sent too many requests in a given time. The answer may carry a Retry-After header with the seconds to wait, here 12, the time left in the minute. No replica sees the call. Other agents on the same address are not touched.

A count of calls is the plain version. What an agent costs is the tokens the model reads and writes for it, and the same counter can hold those. The owner's lab on BNK 2.4 sets token limits per identity and per model with a Gateway annotation, k8s.f5.com/ai-token-counting, and its manifest expects a 429 when a limit is passed. The MCP security guidance gives one more reason to count at the right place. A server that forwarded the agent's token to another API, the forbidden token passthrough, would let the agent reach that API with no limit tied to it, because the API's own limits depend on the token being issued for it.

The IDs of this lesson end up in two groups. Session, task and context IDs say where to send a request. The client_id says whom to count and whom to refuse.

Chapter 15 of 19

The model call has a session too

Session affinity is one signal the endpoint picker weighs against prefix affinity and load

Every chapter so far kept a session on a tool server. The agent's other traffic goes to the model, and it has the same shape. Each turn of the loop is a POST to /v1/chat/completions for the model qwen3, and each one resends the whole conversation so far. For every such request BNK asks the endpoint picker, over the ext_proc protocol on port 9002, which GPU worker should serve it. The worker that served the last turn still holds the conversation's KV cache, the keys and values the model computed for every token it read. For Qwen3-32B that is 64 layers × 8 KV heads × 128 values × 2 (one key and one value) × 2 bytes = 262,144 bytes, or 256 KiB, per token, with the cache kept in 16-bit values. A conversation of 7,200 tokens therefore holds 7,200 × 262,144 = 1,887,436,800 bytes, about 1.89 GB, on one GPU. Send turn eight to another worker and that worker has to read all 7,200 tokens again before it can write the first new one.

So the model side has a session as well, and it lives in GPU memory. F5's two-tier control plane slide names what BNK weighs at Tier 2, the local inference routing that decides which GPU, model or Pod handles a request: per-Pod GPU utilisation, queue depth, KV-cache locality, model affinity and priority class. Tier 1 above it is F5 DNS and GSLB choosing the region, cluster or cloud. The AI gateway deck describes the picker's composite score the same way: prefix match, GPU utilisation from NVIDIA DCGM or Prometheus, and the tokens waiting in the vLLM queue, with traffic spilling to a cold replica when a warm one passes its memory threshold. F5's slide for BNK agents draws the agent half of the picture: the MCP-Session-Id gives session affinity at the MCP servers, and A2A traffic gets task and stream affinity. A session ID on the model call is one more input beside the others, and it is weighed against them.

The upstream llm-d inference scheduler, an endpoint picker built on the Gateway API Inference Extension, shows how such an input is scored. Its session-affinity-scorer gives 1.0 to the Pod that served the session last and 0.0 to every other candidate. It has two strategies. encoded_endpoint_header, the default, keeps no state: the picker writes a response header, x-session-token by default, holding the base64 of the chosen Pod's namespace/name, and the client sends it back on its next request. session_id keeps state in the picker: the client sends an opaque ID, read by default from the header x-session-id, and the picker binds it to the Pod that served it. A binding is dropped after evictionTtlSeconds without use, 300 by default, and expired bindings are swept every evictionSweepSeconds, 10 by default. Sources are tried in order, so an agent-identity attribute can follow the header as a fallback. An unbound session expresses no preference. A bound session whose Pod has left the candidate set scores zero everywhere and is bound again to wherever the request lands.

Each scorer returns a number from 0 to 1 for each candidate. The picker multiplies each score by its scorer's weight, which is 1.0 when none is set, adds them up and takes the highest, rotating round robin among ties. prefix-cache-scorer gives the share of the prompt's blocks already cached on that worker. kv-cache-utilization-scorer gives 1 minus the share of KV cache in use. queue-scorer scales the waiting queue so the shortest queue gets 1.0 and the longest 0.0. The beats work one choice through with illustrative weights, and then show the trap. Prefix affinity and session affinity nearly always point at the same worker, so weighting both counts one fact twice and can hold a conversation on a worker that is already full. llm-d also offers session-affinity-filter, a hard pin. Its documentation says to place it after any filter that can return an empty set, because a request whose pinned Pod is removed by a later filter ends with 503.

The MCP session and the model session are two keys on two kinds of traffic. The MCP-Session-Id rides on POSTs to the tool server, and BNK's MODEL_CONTEXT_PROTOCOL persistence acts on those. A chat completion carries no session header unless the agent or a gateway adds one. F5's own picker takes its scorers and weights in spec.eppConfig.config.schedulingProfiles. The session scorer and its defaults in this chapter are the llm-d ones.

Chapter 16 of 19

What the agent remembers, and where

Long-term and short-term memory, kept in on-premises S3 object storage and reached through MCP tools

Nothing in this lesson so far lasts. The model remembers nothing between requests, which is why each turn resends the conversation. The KV cache sits in one GPU's memory and is evicted when the space is needed. An MCP session lives in one replica's memory and dies with it, as chapter seven showed. An agent that should know tomorrow what it learned today needs a store that outlives all three. F5's Distributed Inference session draws that store with a travel agent. A person asks for a ten-day trip to Japan for a family of five, with three daughters aged 11 to 15, museums, vegetarian restaurants and good weather for cycling. A central agent orchestrates, plans and reasons. Beside it sits grounded context: enterprise knowledge and customer data, long-term memory such as country regulations and visa requirements, and short-term memory such as major events and exchange rates. All of it is kept in on-premises S3-compatible secure object storage, and the agent reaches it through MCP tools that give safe and controlled access. Flights, hotels, activities and weather are further tools behind them, and an AI gateway with security sits in front of the whole flow.

The two kinds of memory differ in how fast they go stale. Long-term memory changes rarely and is shared by many users: the visa rule for one passport holds for months. Short-term memory changes by the hour and is often wrong by tomorrow: an exchange rate, a festival that closes a district. In object storage that difference becomes a key layout and a lifecycle rule. Long-term facts sit under one prefix and stay. Short-term facts sit under another prefix with an expiration rule, which S3 counts in whole days, so the store deletes them on its own. Anything that belongs to one person sits under a prefix that starts with the user, the same <user_id> first rule that chapter four applied to session state.

Access goes through a tool, and the tool's own access goes through a gate. The Distributed Inference deck lists the credential models for S3: an access key and secret key, federated identity with SAML or OIDC, and short-lived credentials from STS by role assumption. AWS's STS reference gives a role session from 900 seconds up to the role's maximum, which is set between 1 and 12 hours. Pre-signed URLs are to be treated as bearer tokens, scoped and expired. With Signature Version 4 an IAM user can sign one for at most 7 days. The deck's advice is never to expose a bucket anonymously or publicly by default.

The gate has to understand S3, because the HTTP method says little. The deck counts 21 S3 actions behind GET, 17 behind PUT and 15 behind POST in MinIO. GET can be GetObject, ListObjectsV2, which returns up to 1,000 keys a call, or GetBucketPolicy, which reads the security configuration. POST can be CreateMultipartUpload or DeleteObjects, which removes up to 1,000 objects in one request. So a rule that allows POST for a memory writer also allows a mass delete, unless the gate maps method, query string, headers and body to the S3 action. The deck's BIG-IP demo does that with an S3-aware iRule in front of the storage, and the 2.5 roadmap adds secure S3 AI data storage access to BNK.

Memory ends up in a prompt, and a prompt ends up on a GPU. Put the long-term facts early, in the same order every time, and they form a prefix that the KV cache and the picker of the last chapter can reuse across turns and across users. Put the short-term facts after them, where a change costs only the tokens that follow. Four thousand tokens of visa and customs rules hold 4,000 × 262,144 = 1,048,576,000 bytes, about 1.05 GB, of KV cache on Qwen3-32B. Read once and reused, they cost one prefill. Placed after a changing exchange rate, they are read again on every turn.

Chapter 17 of 19

Token limits, field by field

The k8s.f5.com/ai-token-counting annotation: who is counted, which model, how much, and what happens over

Chapter fourteen counted calls and pointed at the real control for model traffic: token governance in the BNK data plane, switched on with one annotation on the Gateway, k8s.f5.com/ai-token-counting. The BNK 2.3 documentation shows its value as a list of settings. token_counting=enabled turns counting on. enforcement=enabled makes the limits bite, so it is more than a meter. user_id_source says whom to count. It takes api_key, so each key is one user, or ip, so each source address is one user. rate_limit_policy says how to group the counts, and the documented example uses per_user_per_model. The owner's comparison of BNK 2.4.0 lists the scopes it supports as per user, per model, per user per model and global, all counted in the data path.

rate_limits is a list of rules, each with a model pattern, a number of tokens and a window in seconds. The documented example has three. Models matching gpt-4* get 10,000 tokens per 3,600 seconds. gpt-3.5* gets 100,000 per 3,600 seconds. Any model, *, gets 500,000 per 86,400 seconds, a day. The patterns are globs, so one rule covers every version of a model family. concurrent_sessions_limit=5 caps concurrency, rate_limit_action=drop names what happens to a request over a limit, and hsl_pool=usage-logging-pool sends a usage record for each request to a pool of high speed logging collectors. The owner's 2.4 lab manifest for this annotation expects a 429 once a limit is passed. F5's AI gateway deck describes the same control as tokens per minute and tokens per day, counted with fast tokenizers before the request goes out and again after the answer has streamed.

For Northlight the model family is qwen3. A rule of 200,000 tokens per hour for qwen3* gives the status agent room for 31 turns of 6,400 tokens, 6,000 read and 400 written: 31 × 6,400 = 198,400. Turn 32 would bring the hour to 204,800, over the limit. The choice of user_id_source matters as much as the number. With api_key each of the 40 agents behind 198.51.100.9 has its own 200,000. With ip they share one, 200,000 / 40 = 5,000 tokens each, less than a single turn.

The owner's notes leave a few things open. They do not say whether a request for a model that matches two patterns, such as gpt-4o against gpt-4* and *, counts against both rules or only the first. They do not define what concurrent_sessions_limit counts as a session. And they record the value drop without listing the other actions. Test those three on your own release before you rely on them.

Chapter 18 of 19

Where the token check attaches

JWT validation at ingress is promised, and the way to bind it to a Gateway is still open

Chapter thirteen checked the agent's token at the border. This chapter looks at what that check needs and how far BNK gets with it. A JWT check has four inputs: the issuer it trusts, that issuer's signing keys, the audience it expects and a clock. OpenID Connect Discovery supplies the first two. The issuer publishes a JSON document at /.well-known/openid-configuration with its issuer value and a jwks_uri, the address of its JSON Web Key Set. The validator fetches that set, picks the key whose kid matches the kid in the token's header, checks the signature with it, and then checks iss, aud and exp. Without discovery the issuer and the key set are configured by hand.

F5's sources agree that JWT validation happens at ingress and disagree on the rest. The BNK 2.4.0 release notes add OIDC and JWT validation at the traffic layer, before traffic reaches MCP servers, A2A agents or other services, and plan OAuth-based flows for a later release. F5's product deck for the same release says OAuth and JWT validation, with OIDC planned, and marks OIDC Discovery as future. The NVIDIA deck's slide for BNK agents draws OAuth flows, JWT validation and OIDC Discovery inside one identity and access box, and it too tags OIDC Discovery as FUTURE, in a dashed grey box, with an external OIDC or enterprise identity provider below it. The AI gateway deck puts native OAuth 2.0, OIDC and JWT validation on the HTTPRoute. Which of OIDC and OAuth ships first is unresolved in the sources, and the owner has recorded it as a question for the product team.

The owner's lab on a live 2.4.0 cluster found the objects. F5BigAccessJwtConfig exists for JWT validation and F5BigAccessOauthProvider for OIDC. What it did not find is a way to attach them. Security objects reach a Gateway through SecPolicy.extensionRefs, and on 2.4.0 that list accepts firewall, log and DDoS objects only. The lab notes rank accepting the access objects there as the cheapest real change on the list, because the CRDs already exist. Until that binding is verified, the border check of chapter thirteen is the design, and a deployment that needs it today validates tokens in a component behind BNK, such as the tool server or an AI gateway.

Whatever does the check, the order on the BNK agents slide stays: identity first, then persistence. A request that fails validation is never balanced, so it never creates a persistence entry and never reaches a replica.

Chapter 19 of 19

Firewalling the tool call

A tool firewall reads JSON-RPC: which tool, with which arguments, from a list that must not change underneath

The NVIDIA deck's slide for BNK agents draws agent tool firewalling in red inside the agentic traffic delivery box, under the MCP and A2A persistence profiles, and gives it no date. The whole slide carries an EA/PoC label, and the caption under that box ends with the word JSON-RPC. Everything this lesson has done to MCP traffic so far, persistence and token checks, works without knowing which tool is being called. A tool firewall is the part that does know. It reads the JSON-RPC body of each request. tools/call carries params.name, the tool, and params.arguments, the input. It also reads the server's answers. A tools/list result describes each tool with a name, a description, an inputSchema in JSON Schema and optional annotations such as readOnlyHint and destructiveHint. A server that declared listChanged can send notifications/tools/list_changed at any time to say the list has moved.

From those fields a firewall can enforce three kinds of rule. Per tool: this agent may call read_page and search_pages and never delete_page. Per argument: update_page only for pages under status/, checked against the arguments before the call reaches the server. And per list: the tool definitions an operator approved are pinned, so a later tools/list in which a description has changed, or a new tool has appeared, is flagged before the model ever reads it. That last rule matters because a description is text the model reads and trusts. The specification says clients must treat annotations as untrusted unless they come from a trusted server, and the session hijack attack of chapter four ended with exactly such a list_changed notice.

The MCP specification gives a server two ways to say no, and a firewall faces the same choice. A protocol error is a JSON-RPC error, -32602 for an unknown tool. A tool execution error is a normal result with isError set to true and text the model can act on. The current revision 2026-07-28 makes the firewall cheaper: Mcp-Method and Mcp-Name carry the method and tool name as headers, and the server must refuse a request whose headers disagree with its body, so a check on the header is a check on the call.

F5's roadmap puts this in two steps. 2.4 lists MCP Security with Agentic IAM as early access, next to the A2A and MCP persistence profiles. 2.5, BNK as LLM gateway and AI Grid, lists MCP Security again with Agentic IAM, agentic application delivery and agentic firewall policies as early access. The F5 AI Security deck describes the same direction for its MCP gateway: server and tool authorization, tool-level access by group, approving or disabling tools per server, an audit of tool calls, and on-behalf-of identity as a direction. On the owner's 2.4.0 cluster there was no object for MCP authentication, per-tool authorization or tool-call inspection, and the owner's notes conclude that Agentic IAM in 2.4 means the persistence profiles. Per-tool rules need an MCP parser first. Until then the rule runs elsewhere, as chapter thirteen placed it at the AI gateway.

What to keep

Two kinds of ID, and they do different jobs

Agent traffic through a gateway carries two kinds of identifier. One kind says where a request belongs: the MCP session ID in a header, the event ID that resumes a stream, the A2A task and context IDs in the body, and in the current MCP revision a handle in a tool argument. A load balancer that reads them keeps a conversation on the replica that holds it, POSTs, streams and resumes alike, and that is all it does. If the replica dies the conversation dies too, unless its state was stored somewhere shared under the user and the session. The current MCP revision takes this route to its end and has no session at all. The other kind says who is calling: an access token issued for one server, checked at the border for its issuer, audience and expiry, with scopes that bound what the agent may do and a client_id to count by. Mixing the two up is the mistake to avoid. A session ID is not a credential, and a token is not a routing key.
