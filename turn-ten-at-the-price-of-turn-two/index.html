Inference

Turn ten at the price of turn two

Prefix caching, and how a load balancer throws it away

A model keeps nothing between two messages. So a chat application sends the whole conversation again on every turn: the instructions, every question, every answer, and the new message at the end. The GPU has to read all of it before it can write a word, and that reading is prefill, the expensive pass that sets the wait for the first token. Left alone, a conversation gets slower with every turn. This lesson follows one chat through ten turns, shows the trick that keeps the wait flat, and then shows how an ordinary load balancer undoes it.

Along the way it opens up the parts that decide whether the trick works: how a thread becomes tokens, how vLLM labels each block of saved work with a hash, why a freed block is not yet forgotten, which small changes in the text quietly break the match, what the worker reports on its metrics page, and how a router can learn where each prefix lives. The model is Qwen3-32B on three identical vLLM workers. Every token of its KV cache costs 262,144 bytes, and each worker has a pool of 8,869 blocks of 16 tokens.

Chapter 1 of 16

A chat API remembers nothing

Every turn carries the whole thread

The user asks a first question. The request holds the assistant's instructions, 1,200 tokens of them, and the question, 48 tokens. The data plane sends it to gpu-2. Nothing about this is special yet. The point to hold on to is what the request contains, because the next one will contain all of it again.

The OpenAI chat completions API is stateless. The body of each POST to /v1/chat/completions carries a messages array, and that array is the whole conversation as far as the server is concerned. The server keeps no session for this user. It does not know this is turn one, and it will not know that the next request is turn two. The application proves it by resending everything each time: the system message, every earlier user message and every earlier assistant answer, in order, with the new question last.

That is why the size of a chat request grows on its own. Turn one is about 5.4 kB of JSON. Each later turn adds the previous answer, 192 tokens, and a new question, 48 tokens, so every turn is 240 tokens longer than the one before. By turn ten the request is 3,408 tokens and by turn eleven 3,648, about 15.7 kB on the wire. The new text in each of them is still one short question. Everything else is a copy of what the server has already seen, and whether the server can recognise that copy is the subject of this lesson.

Chapter 2 of 16

The thread, written out as tokens

A chat template turns messages into one long line

The model never sees a messages array. The vLLM API server turns it into one string with the model's chat template, a small Jinja program shipped with the model, and then into token numbers with the model's tokenizer. For Qwen3 each message is wrapped in markers: <|im_start|>system, the text, <|im_end|>, then <|im_start|>user and so on. With the generation prompt switched on, the template ends with <|im_start|>assistant, which tells the model that its own turn starts here.

The tokens are what the GPU and the cache care about. The scheduler cuts the token line into blocks of 16, the block size this worker is started with. Turn one is 1,248 tokens, so it fills exactly 78 blocks. The 1,200 tokens of instructions fill the first 75 of them, and the question with its markers fills the last 3. In this lesson every message is counted with its markers, which keeps the arithmetic whole.

Two consequences follow. First, a block is a unit of exact text. Change one token anywhere and every block from that point on describes a different line. Second, the template decides what the earlier turns look like when they are sent again. If it writes a past answer in a different way from how the model produced it, the tokens differ even though the conversation is the same. A later chapter shows that this happens with this very model, and what it costs.

Chapter 3 of 16

Prefill once, then write

The KV cache is what makes streaming possible

Go inside gpu-2. Prefill reads all 1,248 tokens in one pass and leaves its work in GPU memory: a key and a value for every token at every layer. That is the KV cache. For Qwen3-32B one token costs 64 layers × 2 × 8 heads × 128 numbers × 2 bytes, which is 262,144 bytes. The 1,248 tokens of this prompt therefore hold about 327 MB.

Decode then writes the answer one token at a time. Each decode pass reads the whole cache, adds one entry for the newest token and picks the next one. Without the cache every word would need the whole prompt read again, with a pause before each word. With it the pause is paid once, before the first word, and that pause is the time to first token. The answer here is 192 tokens long, so when it ends the thread is 1,440 tokens, 90 blocks of 16. The cache holds one token less, 1,439, because the very last answer token is never fed back in, so the 90th block has 15 tokens. That is about 377 MB. Until the chapter When the same text is not the same tokens, this lesson keeps the round figures of 1,440 tokens and 90 blocks.

While this happens vLLM is already labelling the work. Each time a block fills up, prompt or answer, it gets a hash and is entered into the worker's table of cached blocks. Only full blocks are labelled. A block that is half written has no label yet, because its text is not final. This is the moment the saving for the next turn is made, and it costs nothing extra: the keys and values had to be computed anyway to write the answer.

Chapter 4 of 16

Throw it away and pay again

The longer you talk, the longer you wait

Suppose the server forgets those blocks the moment the answer ends. In vLLM that is what happens when prefix caching is switched off with --no-enable-prefix-caching. It is on by default in current versions, so a server only behaves like this when someone turns it off, or on an engine that has no such cache. The request is over, its blocks go back to the pool and nothing marks what was in them.

Now the user sends a second message. The application resends the thread: instructions, first question, first answer, new question. That is 1,488 tokens, and as far as the GPU knows it has never seen any of them. It reads them all. Turn three brings 1,728. By turn ten the prompt is 3,408 tokens, and the user waits for every one of them before the first word appears.

Add it up. Turn n carries 1,248 + 240 × (n − 1) tokens, so ten turns carry 10 × 1,248 + 240 × 45 = 23,280 tokens of prefill. The new text in all of that is 480 tokens of questions. About 98 percent of the work repeats work already done. At the illustrative rate of about 0.21 ms per prefill token used in the lesson Prefill and decode, turn ten's 3,408 tokens take about 0.72 s before the first word, against about 0.26 s for turn one. The wait grows with the length of the conversation, and the length of the new message hardly matters.

Chapter 5 of 16

Keep the blocks, label them by their text

Prefix caching

Now keep the blocks when the request ends, and give each one a label worked out from the exact tokens it covers and everything before them. vLLM builds the label as a hash of three things: the hash of the block before it, the token ids in the block, and extra keys such as a LoRA adapter id, an image hash or a cache salt. Because each label folds in the one before, a label stands for the whole line of text up to the end of that block. Since vLLM v0.11 the default hash is SHA-256, set with --prefix-caching-hash-algo, so two different texts do not end up with the same label.

When a request arrives the scheduler hashes its prompt block by block and looks the labels up, from the first block on. For as long as they match, the work is already done. At the first block that is not found, it stops. Turn two arrives with 1,488 tokens, which is 93 blocks. The first 90 are the thread so far, and their blocks are still there. Only the new question, 3 blocks of 48 tokens, has to be read.

This is prefix caching. It works only from the start of a prompt, because a token's key and value depend on every token before it. The same paragraph placed after a different opening is different work, and its blocks get different labels. A match in the middle of a prompt is worth nothing.

Chapter 6 of 16

Freed is not forgotten

A cached block stays until its space is needed

Between two turns the conversation's blocks are not in use. Nobody is running. vLLM keeps a reference count on every block, the number of running requests that use it. When the first answer ends, the count on all 90 blocks drops to zero and they go onto the free queue. The free queue is the list from which new blocks are handed out. The blocks keep their labels while they wait there, so a request that arrives with the same text can take them back.

The order matters. A finished request's blocks are added to the tail of the queue in reverse order, last block first. New blocks are taken from the head. So the oldest freed blocks are reused first, which makes the queue a least recently used list, and within one request the end of the text goes before its opening. The end of a long text is the part least likely to be shared, so it is the part to give up first.

When turn two finds its 90 blocks, the scheduler touches them: it raises their count back to one and pulls them out of the free queue so nothing can reuse them. Only when a new request needs space and the head of the queue is a labelled block is that block evicted. Its label is removed and its memory is written over. An operator should know one more thing. vllm:kv_cache_usage_perc counts free blocks as free, labelled or not. A worker can show 2 percent usage while holding thousands of cached prefixes.

Chapter 7 of 16

Turn ten costs what turn two cost

The wait stops growing

Follow the chat to its tenth turn. The prompt is now 3,408 tokens in 213 blocks. With the blocks kept, the first 210 are found, 3,360 tokens, and the last 3, the new question, are read. The wait before the first word is the same as on turn two. Every turn from the second on reads 48 tokens.

Over ten turns the GPU prefilled 1,248 + 9 × 48 = 1,680 tokens where it would have prefilled 23,280. The worker's counters show it plainly. vllm:prefix_cache_queries grows by every prompt token looked up, 23,280 in all, and vllm:prefix_cache_hits by the tokens found, 21,600. The hit rate is 21,600 ÷ 23,280, about 93 percent, and the worker's log prints it as Prefix cache hit rate.

The price is memory. After the tenth answer the conversation covers 3,600 tokens, 225 blocks, about 944 MB. Those blocks sit in the same pool of 8,869 blocks that limits how many requests the GPU can run at once. Thirty-nine idle conversations this size would fill it. Kept blocks are given up first when room is needed, so the saving lasts as long as the memory does. A chat that pauses for an hour on a busy worker will usually find its blocks gone and pay the full prefill once more, after which the saving starts again.

Chapter 8 of 16

What a hit cannot shorten

Kept blocks save the reading, and the answer is still written one pass at a time

A prefix hit removes work from one phase of a request. Prefill reads the prompt, and that is the work the kept blocks replace. Decode writes the answer one token per pass. Every pass moves all 32.8 GB of weights from memory to the cores and reads this conversation's keys and values. That figure counts each of Qwen3-32B's 32.8 billion weights at one byte, as the lesson Prefill and decode does. The published Qwen3-32B-FP8 files are a little larger, 34.3 GB, because about 1.56 billion weights, mainly the embedding table and the output layer, stay in 16 bits and the 8-bit weights carry small scale factors. A kept block holds keys and values for text the GPU has already read. It holds nothing for text that has yet to be written, so every answer token still costs one full pass. vLLM's own documentation states the limit in its page on automatic prefix caching: it only reduces the time of the prefilling phase and does not reduce the time of generating new tokens, so it brings no gain when the server spends most of its time writing long answers.

Put prices on turn ten. This lesson costs prefill at the illustrative 0.21 ms a token and a decode pass at 12 ms, the figure the lesson Prefill and decode uses for Qwen3-32B on one H100. That sits just above the floor of 32.8 GB ÷ 3.35 TB/s, about 9.8 ms a pass. With nothing kept, turn ten reads 3,408 tokens, 3,408 × 0.21 ms = about 716 ms, then writes 192 tokens, 192 × 12 ms = 2,304 ms. The user waits 3,020 ms for the whole answer. With the blocks kept, prefill reads 48 tokens, about 10 ms, and decode still takes 2,304 ms, so the whole answer takes 2,314 ms. The first word arrives about 70 times sooner, 716 ms against 10 ms. The whole answer arrives 706 ms sooner, which is 23 percent.

The saving is a fixed 706 ms, and the length of the answer decides what share of the request it is. A classifier that answers with a 4-token label decodes for 4 × 12 ms = 48 ms. Its request drops from 764 ms to 58 ms, 92 percent less. A report of 2,000 tokens decodes for 24,000 ms. Its request drops from 24,716 ms to 24,010 ms, about 3 percent less. The owner's notes on F5's endpoint picker make the same point with rounder numbers: 0.2 s saved on a 10 s decode is 2 percent. F5's own H100 benchmark of that picker found the same trend: the gain grows with shorter outputs, more requests at once and longer shared prefixes.

The ten-turn chat shows how a high hit rate can hide this. Without kept blocks the GPU prefilled 23,280 tokens, about 4.89 s at 0.21 ms a token. With them it prefilled 1,680 tokens, about 0.35 s. Both versions wrote ten answers of 192 tokens, 1,920 passes at 12 ms, 23.04 s. The user's total wait over ten turns falls from 27.93 s to 23.39 s, about 16 percent, while the hit rate reads 93 percent. The hit rate counts prompt tokens found. It has no term for the answer.

A hit doesn't make decode lighter either. Each decode pass for this request reads its whole cache, and at the end of turn ten that is 3,600 tokens × 262,144 bytes, about 944 MB. At 3.35 TB/s that adds about 0.28 ms to the request's pass. The blocks found by the prefix lookup are the same blocks decode reads, so the memory moved per answer token is the same whether they were kept or computed again a moment earlier.

vLLM shows the split per request. vllm:request_prefill_time_seconds is a histogram of the time spent in the PREFILL phase and vllm:request_decode_time_seconds the time spent in the DECODE phase. vllm:time_to_first_token_seconds, vllm:inter_token_latency_seconds and vllm:e2e_request_latency_seconds give the wait for the first token, the gap between tokens and the whole request. If decode time is many times prefill time, a better hit rate moves time to first token and little else. On a busy GPU a hit is still worth more than this one request's sum. A long prefill makes every running decode on that GPU wait, as the chapter Two requests that look the same shows, so the prefill a hit avoids also stops slowing thirty other answers.

Chapter 9 of 16

One set of instructions, every user

The cache doesn't know whose text it is

Something else comes with this for free. The saved work for a stretch of text depends only on that text and what came before it. It has no idea whose conversation it belongs to. A second user opens the same assistant. Their request starts with the same 1,200 tokens of instructions, so the first 75 blocks are found, and only their own question is read.

The blocks are shared. Nobody copies them. Their reference count rises to two and both requests read the same memory. The 75 blocks are about 315 MB. A hundred users who start with these instructions hold them once, where a hundred private copies would take about 31.5 GB, most of this worker's 37.2 GB pool. An assistant with a long system prompt, or an agent with a long list of tools, pays for that text once per worker and then never again, in compute and in memory.

This is also why the same cache is a question for tenancy. A hit is faster than a miss, and the difference can be measured from outside. A caller who can guess another tenant's text could time requests to learn whether that text was recently sent. vLLM lets a request carry a cache_salt. The salt is mixed into the label of the first block, so only requests with the same salt can share blocks. Requests from one trust group still share among themselves.

Chapter 10 of 16

When the same text is not the same tokens

Small differences that quietly break the match

The counts so far assume the thread comes back as exactly the tokens the worker saw. Two details make the real match smaller, and one of them can make it much smaller.

The first is the last token of every answer. Decode feeds each new token back in to make the next one. The final token is never fed back, because the answer stops there, so its key and value are never computed. After turn one the cache really holds 1,439 tokens. Block 90 has only 15 tokens of work in it, so it is not full and gets no label. Turn two then finds 89 blocks, 1,424 tokens, and reads 64. Every later turn loses one block the same way. That is a small cost: 64 tokens a turn instead of 48.

The second is the chat template. Qwen3's template writes earlier assistant turns without their thinking section. When the model answered turn one, the prompt it continued from ended with an empty <think></think> block if thinking was off, or the answer began with its reasoning if thinking was on. On turn two the same answer is written out without that part. The tokens of the thread differ from that point, so the match ends where the previous answer starts. Each turn then reads that answer and the new question again, about 240 tokens where 48 would do. Over ten turns that is about 1,248 + 9 × 240 = 3,408 tokens of prefill. That is still far below 23,280, and about twice the clean case. A chat template passed with --chat-template that writes earlier turns the way they were produced lets the match run on. That has a price. Qwen3's model card asks for earlier answers without their reasoning, and the stock template follows it. With thinking on, keeping the reasoning makes the thread longer by every reasoning token and shows the model text its makers advise leaving out. With thinking off, the only difference is the empty <think></think> pair, a few tokens a turn. So the choice trades the model card's advice for cache hits, and it is cheapest when thinking is off. Timestamps inside a system prompt and tool lists in a changing order break the match in the same way.

Chapter 11 of 16

What the worker tells the outside

Counters for people, events for routers

A prefix cache is invisible from outside unless the worker says what it holds. vLLM says it in two ways, for two kinds of reader.

For people and dashboards there are counters on GET /metrics at port 8000. vllm:prefix_cache_queries counts prompt tokens looked up and vllm:prefix_cache_hits counts the tokens found. Their ratio over a window is the hit rate. vllm:kv_cache_usage_perc shows how much of the pool is held by running requests, and vllm:num_requests_waiting how long the queue is. A Prometheus server scrapes these every 15 or 30 seconds, which is fine for a graph and slow for a routing decision.

For routers there are KV cache events. Started with --kv-events-config and enable_kv_cache_events set to true, the worker publishes a message over ZMQ, by default on tcp://*:5557, each time it labels or evicts blocks. A BlockStored event carries the new block hashes, the hash of the parent block, the token ids, the block size and the medium the blocks are on. A BlockRemoved event carries the hashes that were evicted. AllBlocksCleared says the whole cache was dropped. A subscriber that keeps up with these knows, block by block, what each worker holds, without scraping anything. An optional replay endpoint lets a subscriber that missed messages catch up on the last 10,000 steps by default.

Chapter 12 of 16

Round robin sends turn eleven elsewhere

Good work thrown away on the most expensive hardware

Back out to the factory, and put an ordinary load balancer in front of the workers. Its job is to spread requests evenly, one to each worker in turn. That has balanced web traffic for decades, because web servers are interchangeable. Any of them can answer any request at the same cost, so the only thing worth spreading is the number of requests.

These workers are not interchangeable. They run the same model from the same image, and every health check passes on all three. The difference is in memory. gpu-2 holds 225 blocks of this conversation. gpu-1 and gpu-3 hold none of it. The first user's eleventh turn comes in, 3,648 tokens, and the rotation points at gpu-3. Nothing of this conversation is there. gpu-3 reads the whole thread from the first token, while the blocks that would have saved the work sit unused on gpu-2.

The cost is easy to work out. On gpu-2 the turn would read 48 tokens. On gpu-3 it reads 3,648, seventy-six times as much, about 0.77 s at the illustrative rate of 0.21 ms a token. gpu-3 also now holds a second copy of the thread, 228 blocks it did not need. With three workers in a rotation, a conversation lands back on its own worker only one turn in three. No error is raised, no log line is written, and the hit rate on each worker simply drops.

Chapter 13 of 16

Two requests that look the same

The second thing a load balancer can't see

There is a second reason, and it has nothing to do with caches. Spreading requests evenly spreads work evenly only if requests are about the same size. A short greeting and a request to summarize fifty pages are both one POST to the same path. The balancer can't tell them apart. The owner's F5 deck on distributed inference makes the same point with two agent calls, each a POST of about 1 KB. One asks for a two-line pick and writes 256 tokens. The other asks for a five-day plan and writes 8,192. On its illustrative timings the first takes about 0.8 s and the second about 25 s, about 30 times longer. Those timings come from the deck's own setup. At this lesson's 12 ms a decode pass the two answers would take about 3 s and about 98 s. The ratio is the point, and it is the same either way.

In this factory the fifty pages are about 40,000 tokens. Their KV cache is 2,500 blocks, about 10.5 GB, more than a quarter of one worker's pool. Their prefill at the illustrative 0.21 ms a token is about 8.4 s of GPU work. vLLM splits it into chunks of at most 8,192 tokens a pass, five passes, so streams on the same worker keep moving. Every one of those passes is still slower for them.

So the fifty pages can land on a worker that is streaming answers to thirty people, and its long prefill makes all thirty wait. Everything the balancer would need is inside the workers: how full each one's memory is, whose saved work sits where, and how long each queue is.

Chapter 14 of 16

How a router learns where the blocks are

A copy of every worker's table, kept by events

A router that wants to send a turn back to its cache needs to know which worker holds which blocks. It cannot ask every worker on every request. That would add a round trip to each worker before each decision. Instead it keeps its own copy of the answer, fed by the KV events each worker publishes.

The open source llm-d project shows how such an index works. Its KV cache indexer subscribes to BlockStored, BlockRemoved and AllBlocksCleared from every vLLM Pod and keeps a map from block keys to the Pods that hold them. When a request arrives, it tokenizes the prompt, cuts it into chunks of 16 tokens, and computes a chain of keys from them in the same way the workers do. Then it scores each Pod by its longest run of matching blocks from the first block on. A Pod that holds blocks 3 and 4 but not block 1 scores zero, because those blocks are unusable without the ones before them.

The indexer also weighs where a block is. A block in GPU memory counts 1.0 and one offloaded to CPU memory counts 0.8 by default. For turn eleven the answer is easy. gpu-2 matches 225 blocks, gpu-1 and gpu-3 match none. The F5 endpoint picker in this factory learns prefixes from the same kind of events, and it has its own tokenizer, so it knows the size of a prompt in tokens before it picks.

Chapter 15 of 16

A router that can see inside

Send the turn back to its cache, unless the line is too long

The fix is a router that knows what the workers know. In the factory that is the endpoint picker. The data plane asks it before every request, over the ext_proc protocol, and it answers with one worker address. For each request it weighs three things: which worker already holds this request's opening text, how much memory each has free, and how long each queue is.

Replay the last two chapters with this router in front of the workers. The first user's eleventh turn, the one round robin sent to gpu-3, now goes back to gpu-2, so gpu-3 never writes a second copy of the thread. There, in this lesson's round figures, 3,600 of its 3,648 tokens are found and prefill reads 48. The fifty pages go to the worker with the most room and the shortest queue, because their own prefill will cost the same everywhere and only the line in front of them differs.

Prefix alone is not enough. A router that always follows the prefix piles a popular prompt onto the one worker that cached it first. The owner's F5 deck puts it in one line: cache awareness without load awareness is worse than neither. It also notes that polling queue metrics every 15 to 20 seconds, the interval in its example, is too slow for a decision made per request. So the picker counts load in tokens, with its own tokenizer, and skips a saturated worker before it looks for a warm cache. KodeKloud's course on llm-d, a separate source this lesson also draws on, quotes about three times the throughput and a first response twice as fast for cache-aware routing like this, against spreading requests evenly on the same hardware. The next chapter says who builds llm-d and what else it runs besides the router. The AI gateway picks the model. BNK picks the GPU.

Chapter 16 of 16

The project behind the router

Who builds llm-d, and the fleet jobs it does beyond routing

The router in the last chapter is one part of an open source project called llm-d. Red Hat announced it at Red Hat Summit on 20 May 2025, with CoreWeave, Google Cloud, IBM Research and NVIDIA as founding contributors, AMD, Cisco, Hugging Face, Intel, Lambda and Mistral AI as partners, and the University of California, Berkeley and the University of Chicago as supporters. In March 2026 it joined the CNCF, the foundation that also hosts Kubernetes, as a Sandbox project. KodeKloud's course on llm-d names Red Hat, Google, IBM and NVIDIA and gives the project's job in one sentence: run the whole fleet of servers, routing every request to the right server, moving caches around, sharing the GPUs fairly and scaling them down when traffic stops. It runs on Kubernetes with vLLM as the model server, and its router is an endpoint picker built on the Gateway API Inference Extension, the same pattern this factory uses.

Routing is what this lesson has shown so far: a score for the cached prefix, the free KV cache memory and the queue of each server. llm-d ships it inside tested recipes it calls well-lit paths. The first, the optimized baseline, is one pool of identical vLLM servers with cache-aware routing switched on and nothing else changed. KodeKloud's course gives its figures of about three times the throughput and a first response twice as fast for cache-aware routing like this, against spreading requests evenly. It does not say which recipe they were measured on. Several of llm-d's guides serve Qwen/Qwen3-32B by default, the model of this lesson, as two replicas at tensor parallelism 2, four GPUs in all.

Moving caches happens in two ways. The tiered prefix cache path stops a server from throwing away evicted blocks. Each vLLM server offloads them to CPU memory, and optionally on to a shared filesystem, and loads them back when a later turn reuses the prefix, instead of computing its prefill again. The router adds a second prefix scorer that tracks what each server holds in its CPU tier, which is where the tier weights of GPU 1.0 and CPU 0.8 from the chapter How a router learns where the blocks are come in. On NVIDIA GPUs the recommended setting is vLLM's own OffloadingConnector with a 300 GiB CPU tier per replica, set by cpu_bytes_to_use. vLLM keeps that tier in /dev/shm, so it counts toward the Pod's memory limit. The chat from the chapter Turn ten costs what turn two cost, which lost its 225 blocks after an hour's pause, could find its 944 MB in host memory and copy it back over PCIe instead of prefilling 3,648 tokens, about 766 ms. At the roughly 64 GB/s of a PCIe Gen5 x16 link that copy takes about 15 ms. The second way is the prefill and decode split: one server reads the prompt and hands its KV cache across a fast link to another that writes the answer. KodeKloud's course quotes up to 70 percent more tokens a second for it.

Sharing the GPUs fairly is a feature of the endpoint picker called flow control. Requests arrive with headers that carry a tenant ID and a priority. The picker files each request under a FlowKey, the pair of fairness ID and priority, keeps a separate queue for each flow and places each flow in a priority band. Several tenants can share a band. In each cycle it serves the highest band first, takes turns between the tenants inside a band as its fairness policy decides, and orders the requests inside a flow as its ordering policy decides, first come first served or by SLO. While it sees the servers saturated it holds requests in its own queues instead of committing them to one server's local queue, where they would be stuck. The defaults copy the old behaviour: global-strict-fairness-policy, fcfs-ordering-policy and the utilization-detector. The documentation advises the concurrency-detector in production because telemetry lags. The system is work-conserving: when the GPUs have spare capacity it holds nothing back.

Scaling down starts from a different signal. GPU and CPU utilization move only after the servers are already saturated, so llm-d scales on queue depth, requests in flight, token backlog, KV cache pressure or predicted latency, read from the picker's metrics by KEDA, the Kubernetes event-driven autoscaler. KEDA can scale a Deployment to zero. llm-d's scale-from-zero guide is one of its Fast Model Actuation guides. It has KEDA watch llm_d_epp_flow_control_queue_size with a threshold of 1 and an activation of 0, between 0 and 2 replicas, with a cooldownPeriod of 30 and a 30 s stabilization window that the guide shortens on purpose. The Deployment it scales is fma-requester. Its Pod reserves a GPU, and vLLM itself runs in a separate launcher Pod. When the requester goes to zero the GPU is released and the vLLM instance is put to sleep, while the launcher keeps running. Flow control is what makes it work: with no server ready, a new request waits in the picker's queue instead of failing, and that queue is the metric that wakes the pool. The guide serves the small Qwen/Qwen3-0.6B, but the start matters most for a large model. In this site's world a Qwen3-32B Pod loading its 34.3 GB FP8 files from scratch takes about three minutes. The guide's own benchmark of Qwen/Qwen3-32B on H100 measures a mean Pod startup of 4.0 s for a hot start, which wakes the sleeping vLLM, against 85.3 s for a warm start. Which path a request gets depends on which GPU is assigned. llm-d's earlier Workload Variant Autoscaler is deprecated, with v0.9.0 as its last release.

In this factory BNK's endpoint picker sits in the router's seat. It answers the data plane over ext_proc, reads the same vLLM metrics and KV events, and weighs the same prefix, memory and queue. The owner ran F5's picker and llm-d's side by side on the same Envoy, which is why llm-d's public documentation is a fair guide to what any such router has to weigh.

What to keep

Keep the work, then route to it

A chat resends its whole thread on every turn, and the GPU must read a prompt before it can answer. If the work of reading is thrown away, a conversation gets slower with every message. Prefix caching keeps the KV cache blocks and finds them again by a hash of the text that produced them, so only new text is read: turn ten costs what turn two cost, and a shared system prompt is paid for once. The saving needs the thread to come back as the same tokens, so check the hit counters and the chat template. All of it lives in one worker's memory. A load balancer that spreads requests evenly sends the next turn somewhere else and the saving is gone. It also can't tell a greeting from fifty pages. Serving a model well needs a router that sees prefixes, memory and queues.
