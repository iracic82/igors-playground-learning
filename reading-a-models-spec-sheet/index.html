Models

Reading a model's spec sheet

Parameters, active parameters, context window and precision, worked out from config.json

A model is sold in one line. "A sparse attention MoE model with a 1M context window, quantised to 4 bits." "Qwen3-30B-A3B." "117B parameters, 5.1B active, 128k context, MXFP4." Each word in such a line names a real part of the transformer built in the lesson Which token comes next, and each one turns into gigabytes, GPUs and tokens a second on the machine that serves it. This lesson reads those lines end to end. It counts the 32,762,123,264 parameters of this site's model Qwen3-32B one matrix at a time, shows why its FP8 build is 34.3 GB and its BF16 build 65.5 GB, and explains what FP8, FP4, MXFP4 and NVFP4 store in each byte. It then takes apart a mixture of experts model, where the count that sets memory and the count that sets speed are different numbers. It shows what a context window limits, what it costs per token in memory and in work, and how vLLM checks it when the Pods qwen3-6f7d9c8b4-x7k2p and qwen3-6f7d9c8b4-m9q4t start. It ends by decoding real spec sheets, gpt-oss-120b and DeepSeek-V3.2-Exp, field by field from their config.json.

Chapter 1 of 14

One sentence, four claims

A spec line is a summary of config.json

The owner's tiny GPT video ends with a sentence that would have meant nothing at its start: a sparse attention MoE model with a 1 million context window quantised to 4 bits. Every part of it is a claim about something already built. Sparse attention means the model skips some of the token to token comparisons that attention normally makes. MoE, mixture of experts, means each block holds several feed-forward networks and only a few of them work on any one token. A 1 million context window means one request may hold up to about a million tokens of prompt, history and answer. Quantised to 4 bits means each stored weight takes about half a byte.

A model card prints the same facts as a short list. For this site's model, Qwen3-32B, the card says: 32.8B parameters, 31.2B of them non-embedding, 64 layers, 64 attention heads for queries and 8 for keys and values, and a context length of 32,768 tokens natively and 131,072 tokens with YaRN. The FP8 build's card adds one more line: fine-grained FP8 quantisation with a block size of 128.

The card is a summary. The exact numbers sit in config.json, the small file shipped beside the weights that the model server reads before it loads anything. For Qwen3-32B the fields that matter here are hidden_size 5,120, intermediate_size 25,600, num_hidden_layers 64, num_attention_heads 64, num_key_value_heads 8, head_dim 128, vocab_size 151,936, max_position_embeddings 40,960, use_sliding_window false and tie_word_embeddings false. The FP8 build adds a quantization_config block. There are no expert fields, because Qwen3-32B is a dense model: every weight works on every token.

That gives four questions to ask of any spec sheet. How many parameters, and so how many bytes at the stored precision. How many of them each token uses. How many tokens one request may hold, and what each one costs. And how many bits each number takes. The chapters answer them in that order, first for Qwen3-32B and then for models built differently.

Chapter 2 of 14

Counting 32,762,123,264 parameters

Multiply out every matrix and the card's number appears

A parameter is one learned number. The embeddings, the matrices that make queries, keys and values, the feed-forward matrices and the small scaling vectors of the norms are all parameters. The count on the card is the sum of the sizes of those arrays, and config.json gives every size.

Start at the bottom. The embedding table has one row per vocabulary entry and one column per hidden number: 151,936 × 5,120 = 777,912,320. The output head, which scores every vocabulary entry at the end, has the same shape and its own 777,912,320, because tie_word_embeddings is false and the two tables are stored separately.

Each of the 64 blocks then holds an attention part and a feed-forward part. The query projection maps 5,120 numbers to 64 heads × 128 = 8,192 numbers: 41,943,040 weights. The key and value projections map 5,120 to 8 heads × 128 = 1,024 numbers each: 5,242,880 apiece. The output projection maps 8,192 back to 5,120: 41,943,040. That is 94,371,840 for attention, plus 256 for two small norms on the queries and keys. The feed-forward part has three matrices of 5,120 × 25,600 (gate, up and down): 393,216,000. Two layer norms add 10,240. One block holds 487,598,336 parameters, and 64 blocks hold 31,206,293,504.

Add the final norm of 5,120 and the two tables and the total is 32,762,123,264, exactly what Hugging Face reports for the files. The card's 31.2B non-embedding figure is the same sum without the two tables. The split also shows where the weight is: about 25.2 billion in the feed-forward layers, about 6.0 billion in attention and 1.6 billion in the two tables. The lesson Which token comes next shows the same split from the other side, as the stops of one forward pass.

This sum is the first thing to do with any new model. If it lands on the card's figure, the config has been read correctly, and every later number in this lesson follows from the same fields.

Chapter 3 of 14

From parameters to gigabytes

Bytes per parameter, and the parts that stay wide

Memory is the parameter count times the bytes each parameter takes. The tiny GPT video gives the rule: 16 bits is 2 bytes, so a 7 billion parameter model needs about 14 GB and a 70 billion one about 140 GB, the same 140 GB the AI infrastructure video gives for a large model's file. At 8 bits the 7 billion model drops to about 7 GB and at 4 bits to about 3.5 GB. That is the weights alone. The KV cache and the server's working memory come on top.

For Qwen3-32B the rule is exact. The BF16 build stores every one of the 32,762,123,264 parameters in 2 bytes, and its tensor data comes to 65,524,246,528 bytes, 65.5 GB. That is too much for comfort on one 80 GB H100: 14.5 GB would be left for everything else.

The FP8 build's files add up to 34,322,567,640 bytes, 34.3 GB. One byte per parameter would give 32.8 GB, so the extra 1.56 GB needs explaining, and the Hugging Face file listing does it. 31,205,621,760 parameters are stored as F8_E4M3, one byte each: all the projection matrices of the 64 blocks. The other 1,556,501,504 stay in BF16 at 2 bytes: the embedding table, the output head and the norms. That is 3,113,003,008 bytes. Weights and tables together make 34,318,624,768 bytes. The remaining 3,942,872 bytes, about 4 MB, are mostly the scale factors that turn the 8-bit numbers back into real values: the projection matrices hold 1,904,640 tiles of 128 by 128, one 2-byte scale each, about 3.8 MB. The rest is the headers of the files. The index file's total_size field says 34,335,541,248, a little more than the files hold, so add up the files when the exact figure matters. The lesson Three numbers on a GPU card uses 32.8 GB, one byte for every weight, as a round figure. The file on disk is 34.3 GB.

One more trap: GB and GiB. Model hubs count in GB, 10^9 bytes. nvidia-smi and most memory tools count in MiB and GiB, 2^30 bytes. The same 34,322,567,640 bytes are 34.3 GB and 32.0 GiB, and the BF16 build's 65.5 GB is 61.0 GiB. Mixing the two units makes a model look 7 percent smaller than it is.

When the Pod qwen3-6f7d9c8b4-x7k2p starts, all 34.3 GB come from object storage onto the GPU once, in about three minutes, and stay there for as long as the Pod runs.

Chapter 4 of 14

What fits in eight bits

Sign, exponent, mantissa, and a scale per block

Precision is how many bits each number takes, and how those bits are split. A floating-point number has a sign bit, some exponent bits that set how large it is, and some mantissa bits that set how finely it is placed between two powers of two. More exponent bits give range. More mantissa bits give resolution.

BF16, the format Qwen3-32B is released in, has 1 sign bit, 8 exponent bits and 7 mantissa bits. It has the same range as a 32-bit float with less resolution. FP8 comes in two encodings defined in the FP8 Formats paper. E4M3 has 4 exponent bits and 3 mantissa bits, gives up infinities to stretch its range, and reaches 448 at most. E5M2 has 5 and 2, more range and less resolution. Qwen3-32B-FP8 stores its weights as E4M3, which its config.json names as fmt e4m3.

With 3 mantissa bits there are only 8 steps between two powers of two. Between 256 and 512 the representable values are 256, 288, 320 and so on, 32 apart. So a weight cannot be stored as itself. It is divided by a scale first, rounded to the nearest E4M3 value, and multiplied by the scale again when used. The scale is chosen so that the largest value in a group lands near 448.

The group is what fine-grained means. Qwen3-32B-FP8 has weight_block_size [128, 128]: every 128 by 128 tile of a matrix gets its own scale, stored beside it as weight_scale_inv. One big outlier then spoils only its own tile. That is why the files hold about 4 MB of scales next to 31.2 GB of weights. activation_scheme dynamic means the numbers flowing through the model, the activations, get their scales worked out on the fly for each pass instead of fixed at quantisation time.

The H100 has tensor cores that multiply FP8 directly, at about twice its BF16 rate. So on this cluster FP8 halves the bytes and also speeds up the arithmetic, which is why the FP8 build is the one the Deployment qwen3 serves.

Chapter 5 of 14

Four bits and the scale that rides along

Why 4-bit is a little more than half a byte

At 4 bits the problem gets sharper. FP4 in the E2M1 layout has 1 sign bit, 2 exponent bits and 1 mantissa bit, so it can say only 0, 0.5, 1, 1.5, 2, 3, 4 and 6, and the same values negative. Fifteen distinct numbers. Without a scale for each small group of weights almost every weight would round to one of a handful of values, so every 4-bit format is defined together with its scales.

MXFP4 groups 32 values and gives the group one shared scale that is a power of two, stored in 8 bits. That costs 8 bits per 32 values, a quarter of a bit each, so a weight takes 4.25 bits. NVFP4, NVIDIA's format, groups only 16 values and stores their scale as an FP8 E4M3 number, which can also take values between powers of two, plus one 32-bit scale for the whole tensor. That is 4.5 bits a value. NVIDIA puts NVFP4 at about 3.5 times smaller than FP16 and 1.8 times smaller than FP8. The smaller blocks and finer scales are why it loses less accuracy than MXFP4 at almost the same size.

So 4 bits is about half a byte plus a little. gpt-oss-120b shows it exactly. Its 114,661,785,600 expert weights are MXFP4: 114,661,785,600 × 4.25 ÷ 8 = 60,914,073,600 bytes. Its other 2,167,371,072 parameters, attention, router, tables, are kept in BF16: 4,334,742,144 bytes. The two add up to 65,248,815,744 bytes, to the byte the tensor data its index file lists. The files themselves add up to 65,248,893,184 bytes, and the extra 77,440 bytes are their headers. 117 billion parameters in 65.2 GB, about the size of Qwen3-32B in BF16.

Applied to this site's model as an illustration, NVFP4 projection matrices with the tables left in BF16 would take 31,205,621,760 × 4.5 ÷ 8 + 3,113,003,008 bytes, about 20.7 GB. The hardware decides whether that is also faster. NVIDIA lists FP4 among the formats Blackwell's tensor cores multiply, and the BNK and NVIDIA deck uses about 4 times the throughput of full precision on the same hardware as a planning figure. The H100 has no FP4 tensor cores, so on this cluster a 4-bit model saves memory and the bytes read each pass, while its kernels widen the weights before multiplying. The lesson A detour beside the weights uses a third 4-bit format, NF4, to hold frozen weights while training adapters.

Chapter 6 of 14

Total parameters and active parameters

A router picks 8 of 128 experts for each token

In Qwen3-32B every token goes through the same feed-forward layer in each block. A mixture of experts model replaces that single layer with many smaller ones, the experts, and a router. The router is one small matrix. For each token it gives every expert a score, keeps the top few, and sends the token only to those. Their outputs are added together, weighted by the router's scores. The video's example has 8 experts with 2 used per token. Qwen3's MoE models have 128 experts and use 8.

Qwen3-30B-A3B shows the effect. Its name reads as 30 billion total, 3 billion active. config.json gives hidden_size 2,048, 48 layers, num_experts 128, num_experts_per_tok 8 and moe_intermediate_size 768. One expert is three matrices of 2,048 × 768: 4,718,592 parameters. 128 of them make 603,979,776 per layer, against an attention part of only 18,874,368 and a router of 2,048 × 128 = 262,144. One layer is 623,120,640, 48 layers are 29,909,790,720, and with the two tables of 151,936 × 2,048 the total is 30,532,122,624. That is the card's 30.5B.

Now count what one token uses: the attention, the router, the norms, 8 experts instead of 128, and the tables. Per layer that is 56,889,600, so 2,730,700,800 for 48 layers, and with the tables 3,353,032,704. That is the card's 3.3B activated. Only 8 ÷ 128, 6.25 percent, of the expert weights work on any one token.

Vendors do not all count active parameters the same way. Qwen's 3.3B includes both tables even though the embedding table is a lookup of one row. Without the embedding table the figure is 3.04 billion, and without both tables 2.73 billion. The same sum for gpt-oss-120b, counting the biases of only the 4 experts in use, gives about 5.71 billion with both tables and 5.13 billion without the embedding table. That second figure matches the 5.1B OpenAI states, so OpenAI appears to leave out the embedding table, while Qwen keeps it in. Treat active parameter counts as good to about a tenth.

The largest Qwen3, Qwen3-235B-A22B, is built the same way with 94 layers and the same 128 and 8: 235 billion total, 22 billion active.

Chapter 7 of 14

Memory follows the total, speed follows the active

Every expert must be on the card, few are read per token

The router can pick any expert for the next token, so all of them must already be in GPU memory. Memory therefore follows the total count. Qwen3-30B-A3B in BF16 is 61,064,245,248 bytes, 61.1 GB, and its FP8 build is 32,444,792,832 bytes, 32.4 GB. On disk and in GPU memory it is about the same size as Qwen3-32B: 32.4 GB against 34.3 GB in FP8, and 61.1 GB against 65.5 GB in BF16.

Work follows the active count. A common rule of thumb puts a forward pass at about 2 floating-point operations per weight used per token, one multiply and one add. Qwen3-32B then costs about 65.5 billion operations a token and Qwen3-30B-A3B about 6.7 billion, ten times less.

Reading follows the active count too, for one request. The lessons Three numbers on a GPU card and Prefill and decode show that decoding reads every weight once per pass, and that the H100's 3,350 GB/s divided by the bytes read caps the passes per second. For Qwen3-32B FP8 that is 3,350 ÷ 34.3, about 98 passes a second. A lone request to Qwen3-30B-A3B FP8 reads only the active weights, about 3.4 GB, so the same arithmetic allows about 1,000. That is the appeal of MoE: the knowledge of a 30 billion parameter model at the speed of a 3 billion one.

Batching takes some of that back. Each token in a batch picks its own 8 experts, and the pass must read every expert that any token picked. If the router spread tokens evenly at random, a batch of 16 tokens would touch about 82 of the 128 experts in each layer, and a batch of 64 about 126. A busy MoE server reads close to all of its weights every pass, like a dense one, and keeps only its compute saving. Real routers are not uniform, so treat these counts as a sketch.

The KV cache follows neither count. It depends only on the attention: 48 layers × 2 × 4 key and value heads × 128 × 2 bytes = 98,304 bytes a token for Qwen3-30B-A3B, little more than a third of Qwen3-32B's 262,144.

Chapter 8 of 14

When the experts do not fit one GPU

Expert parallelism sends tokens to where their expert lives

Qwen3-235B-A22B has 235,093,634,560 parameters. Its BF16 files are 470,187,269,120 bytes, 470.2 GB, and at one byte a weight it would still be about 235 GB. Three 80 GB cards hold 240 GB, which would leave nothing for the KV cache, so a model this size is spread over a server of several GPUs or more. The lesson A model bigger than one GPU shows the two dense ways to split a model: by layers, and inside every layer. An MoE model has a third.

Expert parallelism gives each GPU a share of the experts of every layer. With 8 GPUs and 128 experts, each holds 16 experts per layer. Attention is shared out as in a dense model, split inside each layer or copied to every GPU for its own requests. When the router has chosen a token's 8 experts, the token's vector is sent to the GPUs that hold them, they each apply their expert, and the results are sent back and summed. Every GPU talks to every other in each MoE layer, an exchange called all-to-all. In vLLM it is switched on with --enable-expert-parallel.

The traffic is the price. For each token and each MoE layer, the hidden vector goes out to up to 8 places and comes back. Qwen3-235B-A22B has a hidden size of 4,096, so one copy is 8 KB in BF16, and it makes that trip in 94 layers. Inside one server this rides NVLink. Spread across servers it rides the RDMA fabric, which is why the wide expert parallelism guide in the lesson Installing llm-d, serving DeepSeek-R1-0528 on 32 H200s, requires RDMA.

The spec sheet tells you which of these you are in for. A dense 32 billion model fits one card in FP8. A 30 billion MoE fits one card and runs fast. A 235 billion MoE needs a server and a fast interconnect before it answers its first token, however few parameters each token uses.

Chapter 9 of 14

The context window is a budget of tokens

Prompt, history and answer share one limit

The context window is the most tokens one request may hold at once: the system prompt, every earlier message, any documents pasted in, and every token the model writes back. The answer counts. A request with a 30,000 token prompt to a model with a 32,768 token window has room for 2,768 tokens of reply.

Qwen3-32B gives two numbers and a third in its config. Natively it handles 32,768 tokens. Its config.json sets max_position_embeddings to 40,960, and the card explains why: 32,768 tokens reserved for output and 8,192 for a typical prompt, because a reasoning model can think for a long time before it answers. With YaRN it has been tested up to 131,072 tokens.

YaRN is a way to stretch the position encoding. Positions in Qwen3 are worked into attention as rotations of the query and key vectors, RoPE, and the model only learned the rotations of the positions it saw in training. YaRN rescales them so that a longer sequence maps onto the range the model knows. The card shows how to switch it on in vLLM: --rope-scaling '{"rope_type":"yarn","factor":4.0,"original_max_position_embeddings":32768}' --max-model-len 131072. The factor is 131,072 ÷ 32,768 = 4. The card also warns that the open-source servers apply YaRN statically, the same factor whatever the length of the text, which can hurt quality on short texts. It recommends a factor of 2.0 if requests are usually around 65,536 tokens, and no YaRN at all if they stay under 32,768.

vLLM turns all of this into one setting, max_model_len. Without --max-model-len it takes the value from config.json, so the Pods of the Deployment qwen3 run with 40,960 and log Using max model len 40960. A value above what it derives from config.json is refused with User-specified max_model_len ... is greater than the derived max_model_len unless VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 is set, and vLLM warns that for a RoPE model positions past the derived length lead to nan, numbers that are no longer numbers. That is why the card's YaRN settings and the longer limit are given together. --max-model-len -1 asks vLLM to fit the length to the memory it finds. A request longer than the limit is rejected with a client error before it reaches the GPU.

Chapter 10 of 14

What each token of context costs in memory

262,144 bytes a token, held for the whole request

Every token a request holds keeps one key and one value per key and value head in every layer. The lessons Three numbers on a GPU card and Prefill and decode work out the figure for Qwen3-32B: 64 layers × 2 × 8 heads × 128 numbers × 2 bytes = 262,144 bytes a token. Multiplied by a context length, that becomes the memory one full request can take.

At the native 32,768 tokens one request holds 8,589,934,592 bytes, 8.6 GB, exactly 8 GiB. At the 40,960 vLLM uses by default it is 10.7 GB. At 131,072 with YaRN it is 34.4 GB, as much as all the FP8 weights. At a million tokens it would be 262.1 GB, more than three H100s hold, for one conversation. A long context window on the card is a promise about the model's skill. Whether a server can afford it is a separate sum.

vLLM makes that sum when it starts. It measures what memory is left after the weights and its own working space, divides it into blocks, and checks that at least one request of max_model_len fits. If not, it refuses to start with To serve at least one request with the model's max seq len (131072), ... GiB KV cache is needed, which is larger than the available KV cache memory, and suggests a length that would fit. If it does fit, it logs GPU KV cache size: N tokens, Maximum concurrency for 40,960 tokens per request: X.

For the FP8 build on one 80 GB card, before vLLM's own reserve, 45.7 GB is left: about 174,000 tokens. That is 4.25 requests of 40,960 tokens, or 1.33 of 131,072. Prefill and decode works the same figure out at about 142,000 once vLLM's memory setting and working space are taken off. The BF16 build would leave 14.5 GB, about 55,000 tokens, barely one long request.

Two levers shrink it. --kv-cache-dtype fp8 stores keys and values in one byte, 131,072 bytes a token, and doubles every count above. A smaller max_model_len does not change the cost of a token. It only lowers the worst case one request can claim.

Chapter 11 of 14

What long context costs in work

Every new token compares itself with every token before it

Attention is the one place where tokens look at each other. Each token's query is compared with the key of every token before it. For a prompt of n tokens that is n × (n + 1) ÷ 2 comparisons in each head of each layer. The tiny GPT video puts it simply: going from 1,000 tokens to 2,000 makes about four times as much attention work. The exact counts are 500,500 and 2,001,000.

The square grows fast. At 32,768 tokens one head of one layer makes 536,887,296 comparisons. At 131,072 it makes 8,590,000,128, sixteen times more for four times the length. Qwen3-32B does this in 64 heads of 64 layers. At short lengths the feed-forward matrices dominate the work of prefill. At long lengths attention takes over, which is why the first token of a 100,000 token prompt arrives much later than that of a 10,000 token one, more than ten times later.

Decode has its own version of the cost. Each new token is compared with every stored key and blends every stored value, so each pass reads the whole KV cache of the request. At 131,072 tokens that is 34.4 GB, as much as the FP8 weights. The lesson Three numbers on a GPU card shows decode as a race to read the weights once per pass. With long contexts the cache becomes a second load of the same size, read for each request separately, so the passes per second fall as the conversation grows.

The owner's distributed inference deck measured eight Qwen3-32B FP8 Pods with 20,000 token prompts. At that length prefill is a large share of the work. Long prompts like these are the case the lesson Prefill and decode has in mind when it gives each phase its own workers.

These costs make a model card's context window a ceiling to stay well under. Sparse attention attacks exactly this square.

Chapter 12 of 14

Sparse attention compares fewer pairs

Windows, alternating layers and chosen tokens

In the attention built so far each token may look at every token before it. Sparse attention is any design where it looks at only a chosen subset, so the work and, for some designs, the cache stop growing with the square of the length. Qwen3-32B has none of it: use_sliding_window is false and every layer is full attention. Two real designs show what the word on a spec sheet can mean.

The first is a sliding window. A layer with a window of w tokens lets each token see only the last w. Its comparisons grow as n × w instead of n squared, and its cache never holds more than w tokens. gpt-oss-120b uses this in half of its layers. Its config.json lists layer_types alternating sliding_attention and full_attention through all 36 layers, with sliding_window 128. OpenAI describes it as alternating dense and locally banded sparse attention patterns, similar to GPT-3. The full layers keep long-range recall. The banded ones are cheap. At 131,072 tokens a banded layer makes about 16.8 million comparisons per head against 8.59 billion for a full one, 512 times fewer.

The cache follows. gpt-oss-120b has 8 key and value heads of width 64, so a layer stores 2 × 8 × 64 × 2 = 2,048 bytes per token. The 18 full layers store 36,864 bytes for every token of the request. The 18 banded layers store at most 128 tokens each, 4,718,592 bytes per request whatever its length. At 131,072 tokens that is 4.8 GB instead of the 9.7 GB that 36 full layers would need. vLLM's hybrid KV cache manager allocates exactly that, keeping only the last window for the sliding layers. Older releases, or --disable-hybrid-kv-cache-manager, give every layer the full length.

The second design picks tokens by content. DeepSeek-V3.2-Exp adds DeepSeek Sparse Attention: a small, fast indexer scores the earlier tokens for each new one, and attention runs only over the top 2,048 of them, index_topk in its config. The main attention then works on a fixed 2,048 tokens however long the context grows. The indexer still scores every earlier token, so its work over a whole sequence still grows with the square of the length, but each of its scores costs far less than a full attention comparison. Its cache still holds every token, because any of them might be picked next.

Chapter 13 of 14

Decoding real spec sheets

gpt-oss-120b and DeepSeek-V3.2-Exp, field by field

gpt-oss-120b is close to the sentence the video decoded. OpenAI's announcement says 117B total parameters, 5.1B active per token, 128 experts with 4 active, 36 layers, alternating dense and banded sparse attention, grouped multi-query attention with a group size of 8, a 128k context, and MoE weights natively in MXFP4 so that it runs within 80 GB. Each claim is in config.json. num_local_experts 128 and num_experts_per_tok 4. layer_types and sliding_window 128. num_attention_heads 64 and num_key_value_heads 8, which is the group of 8. max_position_embeddings 131,072, reached with rope_scaling of type yarn and factor 32 from an initial_context_length of 4,096. quantization_config with quant_method mxfp4 and a modules_to_not_convert list.

Now the arithmetic. 65.2 GB of weights on an 80 GB H100 leaves 14.8 GB. At 36,864 bytes a token for the full layers, plus the fixed 4.7 MB per request for the banded ones, that holds about 400,000 tokens of context. Qwen3-32B in BF16 is about the same size on disk and leaves 14.5 GB, which holds about 55,000. A model with more than three times as many parameters fits seven times more context beside it, because of three choices on its spec sheet: 4-bit experts, half its layers banded, and narrow key and value heads. Its decode reads only the active weights for a lone request, about 5 billion parameters, most of them 4-bit experts.

DeepSeek-V3.2-Exp is the other shape. 685 billion parameters stored in FP8 with block size 128, 256 routed experts plus one shared expert that every token uses, 8 routed experts per token, 61 layers, a context of 163,840 positions, and DeepSeek Sparse Attention with top 2,048. It is a sparse attention MoE model, quantised to 8 bits, that needs a multi-GPU server before anything else.

And the video's sentence on this site's model, as an exercise. Qwen3-32B in 4 bits would take about 20.7 GB. A 1 million token window would need 262.1 GB of KV cache for one request. At that length the weights are the small part. Sparse attention and a narrower cache matter more than the bits.

Chapter 14 of 14

From the spec sheet to the Pod

Which line of the card becomes which flag

Before a model is ordered for the cluster northlight-eu, the four questions of this lesson decide where it can run and how its Pods are started.

Parameters and precision give the size of the weights. Sum the safetensors files, or multiply the count by the bytes per weight and add the parts kept wide. If that is more than about half of one GPU's memory, the KV cache will be cramped. If it is more than one GPU, the Deployment needs several GPUs per Pod with --tensor-parallel-size, or for an MoE model --enable-expert-parallel, and the GPUs need NVLink between them. Qwen3-32B-FP8 at 34.3 GB passes on one H100, which is why each Pod of the Deployment qwen3 asks for one GPU.

Precision also says which hardware helps. vLLM reads quantization_config from config.json and picks its kernels without a flag. FP8 weights run on the H100's FP8 tensor cores. 4-bit weights fit on an H100 and save bandwidth there, and they run their arithmetic in 4 bits only on Blackwell.

The context window gives max_model_len. Leave it at the config's 40,960, or raise it with the YaRN settings from the card, and check the startup lines Using max model len and GPU KV cache size. The KV cache per token, worked out from num_hidden_layers, num_key_value_heads and head_dim, says how many requests of that length one Pod holds, and so how many Pods a given load needs.

Active parameters give speed. A dense model decodes at roughly the memory bandwidth divided by its weight bytes. An MoE model decodes faster for a few users and loses much of that lead under heavy batching, while still saving compute. When the gateway's endpoint picker in front of qwen3-6f7d9c8b4-x7k2p and qwen3-6f7d9c8b4-m9q4t routes by queue length and KV cache use, those are the same quantities, measured live.

What to keep

Four numbers, read from the files

A spec sheet is a summary of config.json and the size of the weight files. Parameters are learned numbers, and their count times the bytes each takes is the memory the weights need: 32,762,123,264 parameters make 65.5 GB in BF16 and 34.3 GB in the FP8 build, where the tables stay two bytes wide and small scales ride along. Precision is a choice of bits and of how many numbers share a scale: E4M3 with 128 by 128 tiles here, MXFP4 at 4.25 bits and NVFP4 at 4.5 bits for the 4-bit formats. A mixture of experts keeps every expert in memory and uses a few per token, so memory follows the total and work follows the active count, until a large batch touches most experts anyway. The context window caps what one request may hold, and each token of it costs 262,144 bytes of cache on this model and a comparison with every earlier token. Sparse attention, through windows or chosen tokens, is how a long window becomes affordable.
