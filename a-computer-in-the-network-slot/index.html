GPU and hardware

A computer in the network slot

The motherboard of a GPU server, and what a DPU changes on it

Take the lid off gpu-2. On one motherboard there are three computers. The host is the one you log in to: CPUs, memory in slots, an operating system. The GPU is a card with its own cores and its own memory. The third is the network card, and in this server it is a DPU: a network card with processors, memory and an operating system of its own. This lesson follows one request across the board, from the cable to the GPU's memory and back. Then it asks the question a DPU exists to answer. If someone else is root on the host, where can the provider still enforce anything? Along the way it shows the modes the card can run in, how it joins the cluster, the exact switches that lock a tenant out, and the road the provider uses instead. Later chapters count the cable in packets, follow the prompt from CPU memory into the GPU's registers, compare the BlueField models and host mode side by side, add a firewall and DDoS protection to a running gateway, and set F5's releases beside NVIDIA's.

Chapter 1 of 20

Three computers on one board

And roads of very different width between them

Start with the layout. The fabric cable does not plug into the host. It plugs into the DPU. Inside the DPU is a switch that every packet has to cross, and beside it a set of Arm cores running their own Linux. The DPU sits in a PCIe slot, and so does the GPU. The host's CPUs and their memory are in the middle, and everything that passes between a card and the host passes through a slot.

Now look at how wide each road is. The cable carries 400 gigabits a second, and 400 divided by 8 bits per byte is 50 GB a second. A PCIe Gen5 slot with 16 lanes runs each lane at 32 gigatransfers a second, which comes to about 64 GB a second in each direction. Host memory feeds the CPUs at 307 GB a second. That figure is eight DDR5 channels, each moving 8 bytes per transfer at 4,800 million transfers a second: 8 × 8 × 4.8 = 307.2. On the GPU card, memory feeds the cores at about 3,350 GB a second.

So the widest road in the building never leaves the GPU card. It is more than fifty times wider than the slot that joins the card to the host, and 3,350 ÷ 64 is 52. The layout of every AI server follows from that one ratio. Whatever must move for every token stays on the GPU card. Whatever crosses a slot has to be small.

The DPU is a whole computer of its own. NVIDIA sells BlueField-3 with 8 or 16 Arm Cortex-A78 cores and 16 or 32 GB of its own DDR5 memory. The card in this server has 16 cores. It also carries a 128 GB SSD for its operating system and logs, a 40 GB eMMC for its boot firmware, and a 1 gigabit RJ45 port that is used only for management. Behind its edge connector sits a PCIe switch of its own, so the card can present several devices to the host at once.

Chapter 2 of 20

The packet meets the DPU first

Policy runs before the host has seen a byte

In DPU mode the switch does not hand the packet to the host. NVIDIA's documentation describes this mode as the one where the card's Arm side owns the network resources and the data path. The Arm side configures the embedded switch, and traffic to and from the host always lands on the Arm side first. A packet reaches the host only through a rule that the Arm side has installed.

On the Arm cores runs TMM, the data plane of BIG-IP Next for Kubernetes. All the work that other lessons show at the border happens here, on the card: the firewall, the TLS session, the routes, the policy, the choice of GPU worker. The request in this lesson is 8.5 kB on the wire, a POST to /v1/chat/completions from 198.51.100.7 to 203.0.113.80 on port 443. TMM ends the TLS session on the card, checks the request against the policy for api.northlight.example, takes gpu-2 as the worker the endpoint picker chose and sends it on as plain HTTP to the vLLM Pod at 10.244.2.22:8000.

Only what passes comes back down to the switch and is sent across the PCIe slot to the host, about 8.4 kB once the TLS framing is gone. The host's CPUs spent nothing on any of it. Up to this point the host has not seen one packet.

Some rules do not need the Arm cores for every packet. F5's roadmap for BNK on NVIDIA DPUs lists access control lists and DDoS protection as offloaded through NVIDIA's DOCA libraries. Such a rule is written into the switch hardware once, and the switch then applies it to each packet as it passes. F5's own material sums up the effect as security and routing without a CPU hop. The host's cores are left for the thing the server was bought for, which is feeding the GPU.

Chapter 3 of 20

Line rate when the traffic bursts

A rule in the switch costs the same at any packet rate

F5's deck on BNK with NVIDIA lists three gains for a deployment on DPUs. The first is higher throughput at scale, which the deck spells out as line-rate processing even under bursty load. The second is efficient inline processing, where security and routing happen without a CPU hop. The third is better use of the hardware, more inference per dollar. The chapter before this one showed the second. This one works through the other two.

Line rate means the card keeps up with everything the cable can deliver. Count it in packets, because rules are applied per packet. The smallest Ethernet frame is 64 bytes. On the wire each frame also carries an 8-byte preamble and a 12-byte gap before the next one, so it takes 84 bytes, which is 672 bits. A 400 Gb/s cable can therefore deliver 400,000,000,000 ÷ 672 = 595 million of the smallest frames a second.

Now put that against processors. The BlueField-3 in this server has 16 Arm cores at up to 2,133 MHz, which is 16 × 2.133 = 34.1 billion clock cycles a second in total. Spread over 595 million packets, that leaves 34.1 ÷ 0.595 = 57 cycles per packet, with every core doing nothing else. A table lookup in memory alone can cost more than that. So a core cannot be the thing that looks at every packet at full rate. The embedded switch can. NVIDIA's DOCA Flow library programs it with pipes: each pipe has match criteria on the packet headers, monitoring actions such as a counter or a policer, and a forwarding target, which can be a port, another pipe, software, or a drop. A rule in such a pipe is applied by the switch hardware as the packet passes, and its cost does not grow with the packet rate.

Bursty load is where this matters. Suppose, as an illustration, a flood of 100 million SYN packets a second arrives for 203.0.113.80. That is 100,000,000 × 672 = 67.2 Gb/s, about a sixth of the cable. If the Arm cores had to look at each one, they would have 34.1 billion ÷ 100 million = 341 cycles per packet for everything, and the TLS sessions of real users would be starved. With a drop or policer rule in the switch, the flood is counted and cut in hardware, and the cores keep their cycles for the 8.5 kB requests that pass. In host mode the same flood would land on the host's cores, the ones vLLM needs.

The third gain is in the money. F5 reports these results from joint validation with NVIDIA: 47% more throughput, 60% lower time to first token, and about 40% lower cost per token, with the note that results vary by workload, model and configuration. The arithmetic of cost per token is simple. A server costs the same per hour whatever it produces, so cost per token is the cost per hour divided by tokens per hour. If throughput rises by 47%, the same hour buys 1.47 times as many tokens, and each one costs 1 ÷ 1.47 = 0.68 of what it did, 32% less. That 32% is only what throughput alone would explain. F5's figure of about 40% is a separate result of the same validation, larger than the 32%, and the deck does not say what makes up the difference, so the two numbers cannot be derived from each other. Either way the GPU, the most expensive part of the server, is the part that gains.

Chapter 4 of 20

Down the other slot to the GPU

A narrow road for commands, a wide one for the work

vLLM now drives the GPU, and the second card comes into play. The prompt's 1,912 tokens and the commands for the pass cross the GPU's PCIe slot. Each token ID is a small integer, and the commands are a few dozen bytes each, so the whole crossing is kilobytes. At about 64 GB a second the slot moves 16 kB in a fraction of a microsecond.

The work itself never crosses a slot. The weights are already in GPU memory, loaded once when the Pod started. For every token of the answer all of them stream from that memory through the cores, on the one road built for it. The factory serves the official FP8 build, Qwen3-32B-FP8, whose 32.8 billion weights take 34.3 GB, because some layers stay at higher precision. At 3,350 GB a second that takes 34.3 ÷ 3,350 = 0.0102 seconds, or 10.2 ms. So one stream of answers can get at most 1,000 ÷ 10.2 = 98 tokens a second. Batching lets one pass of the weights produce a token for many requests at once, which is how a server answers more than one user at that speed.

Now suppose the weights sat in host DRAM and had to cross the slot for every token. The slot would be the limit: 34.3 ÷ 64 = 0.54 seconds per token, about two tokens a second. This is why the layout looks the way it does. Small things travel between the computers. Big things stay on the card where the wide road is.

The answer goes back the way the request came. Each streamed chunk of the answer is small, around 180 bytes in this illustration. It crosses the host's slot to the DPU, goes up to TMM on the Arm cores, which encrypts it and counts its tokens, and leaves through the fabric port. In this whole exchange the PCIe slots carried kilobytes, while the road inside the GPU card carried 34.3 GB for every token.

Chapter 5 of 20

Text becomes numbers on the host

The road from CPU memory to the GPU's registers and back

F5's deck has a slide titled CPU is the gateway for GPU, and it draws the path every request takes. Text arrives in CPU RAM. The CPU turns it into tokens. The tokens go into GPU HBM, where they become embeddings. From HBM the numbers go through registers and shared memory into the GPU's cores, the cores produce output, and the output goes back to CPU RAM. Every arrow on that slide crosses a road on this board.

The first step is tokenizing, and it runs on the host's CPUs. The slide's example is the sentence Hello what is the weather today. A tokenizer splits it into pieces and gives each piece the number it has in the model's vocabulary, drawn on the slide as id_100 to id_600. Those numbers are made up for the drawing. Qwen3-32B has a vocabulary of 151,936 entries, so every token ID is a whole number below 151,936. That needs 18 bits, because 2 to the power 17 is 131,072 and 2 to the power 18 is 262,144. The request in this lesson becomes 1,912 IDs. Held as 64-bit integers, as index tensors usually are, they take 1,912 × 8 = 15,296 bytes. That is the ≈16 kB that crossed the GPU's slot in the previous chapter.

The second step is the embedding, and it happens on the GPU. The model keeps a table with one row for every token in the vocabulary. In Qwen3-32B a row holds 5,120 numbers, and in the FP8 build that table is one of the parts kept at higher precision: it is stored in BF16, two bytes a number. So one row is 5,120 × 2 = 10,240 bytes, and the whole table is 151,936 × 10,240 = 1.56 GB of the 34.3 GB build. For the prompt the GPU reads 1,912 rows, 1,912 × 10,240 = 19.6 MB, out of its own memory. At 3,350 GB/s that takes about 6 microseconds. Had the host looked the rows up itself and sent them over, 19.6 MB would have crossed a 64 GB/s slot in 0.31 ms, and the slot would have carried 1,280 times more bytes than the IDs. This is why the slide draws the embeddings inside the GPU's HBM.

The third step is the climb into the chip. HBM is the GPU's large memory, but the cores do not compute on it directly. Data comes in through a 50 MB L2 cache and lands in two small, very fast stores inside each of the 132 streaming multiprocessors. Each SM has 65,536 registers of 32 bits, 256 KB, and up to 228 KB of shared memory. Across the chip that is about 34.6 MB of registers and 30.8 MB of shared memory. Set that against 34.3 GB of weights and the shape of the work is clear. The weights cannot sit next to the cores. They stream up from HBM through these stores for every pass, a tile at a time, and that stream is the 10.2 ms per token computed before.

The last step comes back down. What the GPU produces at the end of each pass is one chosen token ID per request in the batch. It crosses the slot to CPU RAM, a few bytes, and the host turns it back into text. So the host stands at both ends of every request: it makes the IDs going in and the text going out, and in between it builds each batch and launches each pass. F5's second slide on this, titled F5 DPU deployment, names what goes wrong when the same CPU also does network work. It sorts the CPU's jobs into non-AI tasks, which are model routing, tenant isolation, TLS termination and intelligent load balancing, and AI tasks, which are token processing, padding and batching. In its words, non-AI tasks consume CPU cycles on the path to the GPU, reducing utilization, increasing latency and driving up cost. Moving the first group onto the DPU leaves the host's cores for the second.

Chapter 6 of 20

Who the card answers to

The card's mode decides who owns it

A BlueField card can run in more than one mode, and the mode decides who is in charge of it. NVIDIA documents three. DPU mode is the default for BlueField DPUs. The Arm side owns the network resources and the data path, configures the embedded switch, and decides what reaches the host. The host's network driver loads only after the card's own software has finished setting up the network side.

Zero-trust mode is a stricter form of DPU mode. The data path is the same, and on top of that the host loses its management rights over the card. A later chapter shows exactly which rights. The third mode is NIC mode. In NIC mode the card behaves like an ordinary network adapter from the host's point of view, and on BlueField-3 the Arm operating system does not boot at all.

The mode is a firmware setting. On BlueField-3 one parameter switches between DPU mode and NIC mode, INTERNAL_CPU_OFFLOAD_ENGINE, set with NVIDIA's mlxconfig tool. A value of 1 means NIC mode and 0 means DPU mode. The change takes effect only after a system-level reset, so changing mode is planned work, done before the server goes into service.

F5's deck shows four places the BNK data plane can run: a host with standard CPUs, NVIDIA RTX PRO 6000 servers, ConnectX-7 and ConnectX-8 SmartNICs, and BlueField-3 and BlueField-4 cards in SmartNIC or DPU mode. For this lesson the card is in DPU mode. TMM runs on the Arm cores, and on BlueField-3 those cores only run an operating system when the card is in DPU mode.

Chapter 7 of 20

Which BlueField, and the one after it

Two BlueField-3 models, two ports bonded on the card, and BlueField-4

F5's partnership timeline puts BNK general availability with BlueField-3 support in March 2025. Another F5 slide lists the BlueField-3 cards it runs on as generally available since April 2025: two NVIDIA models, the B3220 and the B3240. They share the same chip: a BlueField-3 with 16 Arm cores running at up to 2,133 MHz, 32 GB of DDR5 with ECC on the card, a 40 GB eMMC and a 128 GB SSD, and a PCIe Gen5 x16 connection to the host. Both carry an integrated BMC, the management controller the zero-trust chapters rely on. They differ in the network and the size. The B3220 has two QSFP112 ports at up to 200 Gb/s each, its memory runs at 5,200 million transfers a second, and it fits in a single slot. The B3240 has two ports at up to 400 Gb/s each, memory at 5,600 million transfers a second, and a heatsink 29.3 mm tall that takes two slots. NVIDIA's guide lists both as needing a supplementary 8-pin power connector beside the PCIe slot. The card on this board, with 16 cores, 32 GB and a 400 Gb/s fabric cable, matches a B3240.

F5's documentation adds one rule about how many. BNK on BlueField-3 can be deployed on one DPU per chassis. Other DPUs in the same server are used to speed up GPU-to-GPU or GPU-to-storage traffic. So in a server like this, one card in one slot is the BNK node, and it is the one the fabric cable comes in through.

Two ports raise a question: one cable or two. F5's timeline lists BNK with hardware LAG for the NVIDIA Cloud Partner reference architecture in October 2025, and link aggregation is a 2.1 roadmap item. LAG, link aggregation, bonds two ports into one logical link, for more bandwidth and so that traffic keeps flowing when one link fails. On BlueField the bond is built on the Arm side, in a way the host does not see: the host gets a single network function. NVIDIA documents two modes, chosen with mlxconfig and a reboot of the card. LAG_RESOURCE_ALLOCATION=1 is hash mode, which spreads packets over the two ports by a hash of their headers. LAG_RESOURCE_ALLOCATION=0 is queue affinity mode, which spreads them by queue. The bond itself is an ordinary Linux bond on the Arm side, mode 4 with the layer3+4 hash policy. Mode 4 is 802.3ad, the LACP standard, so the leaf switch must be configured for it too. While the bond is being built, no traffic passes through the physical ports.

Worked through for a B3240: two 400 Gb/s ports make 800 Gb/s of bond, 100 GB a second. A hash on addresses and ports keeps each connection on one port, so one connection still tops out at 400 Gb/s. Many clients spread over both. If one cable is pulled, everything rides on the other at 400 Gb/s, and the host never sees a link go down.

The next card was announced in October 2025. NVIDIA describes BlueField-4 as a 64-core NVIDIA Grace CPU combined with ConnectX-9 networking, with 800 Gb/s of throughput, six times the compute of BlueField-3, and support for AI factories up to four times larger. NVIDIA expects it in early availability as part of its Vera Rubin platforms in 2026. On F5's side BlueField-4 support is a 2.5 roadmap item. For this lesson the change in numbers is the point. Four times the cores and twice the cable on the card means the same per-packet budget arithmetic of the line-rate chapter starts from a larger base, and the same BNK data plane runs on it.

Chapter 8 of 20

The card joins the cluster

Two Kubernetes nodes in one server

A DPU running TMM is a Kubernetes node in its own right. F5's deployment tooling for bare-metal servers treats the server and its card as two members of one cluster. The host joins over its management address. With one server, the host is also the cluster's control plane. With several, one host is the control plane and the others join as workers. The hosts carry the GPU workloads, such as the vLLM Pod, and BNK's own control-plane workloads. The DPU joins as a worker in its own right, beside whatever role the host has, and carries the BNK data plane: TMM and the components that run beside it.

The card joins over a link that never touches the fabric. Each BlueField offers the host a management interface called RShim over PCIe, and on top of it a small point-to-point network device called tmfifo. The tooling gives each host and card pair a /30 subnet on that link. The host takes the .1 address and the card the .2, for example 192.168.100.1 and 192.168.100.2. The card's kubelet registers with the .2 address as its node IP. Its traffic to the Kubernetes API server leaves through the host, which translates it to the host's own management address.

Getting the card that far takes time. The card's operating system arrives as a BFB file, NVIDIA's bootstream image, written onto the card from outside. F5's specification for the tooling plans 15 to 40 minutes for a BFB flash and 2 to 5 minutes for a connection to come back after each reboot. All of that is setup. Once the card is a node, TMM is placed on it the same way any Pod is placed on any node.

This path has one weakness, and it matters for the rest of the lesson. RShim is a road from the host into the card. A host that can use RShim can flash the card and reach its Arm side. That is fine when the provider runs the host. The chapters on zero trust close that road and use the card's own management port instead.

Chapter 9 of 20

The same work without a DPU

Host mode runs TMM on the host's CPUs

None of this needs a DPU to function. With an ordinary network card, TMM runs as a process on the host's CPUs, and that is called host mode. It is the same data plane, configured by the same Kubernetes resources. F5's deck lists a host with standard CPUs as one place BNK can run, beside SmartNICs and BlueField DPUs, and the same TMM runs on ordinary nodes or on BlueField DPUs. A SmartNIC such as a ConnectX-7 or ConnectX-8 sits in between. It speeds up network work in hardware, and TMM still runs on the host.

Two things differ. The first is cost. The cores TMM uses are the host's, taken from whatever else the server does. On a GPU server those cores already have a job. vLLM's API server turns prompts into tokens, its scheduler builds a batch for every step, and the host launches the GPU's work for each pass. A core that ends TLS sessions or checks policy is a core that is not feeding the GPU. F5's deck puts it in six words: CPU is the gateway for GPU.

The second matters more. TMM is now inside the host. Whoever controls the host's operating system controls the place where the rules are enforced. When the provider runs the host, that is fine. When the host is rented out as bare metal to a customer, it is not.

F5's deck matches each option to a place. Host mode fits edge and regional sites and controlled, sovereign environments. A SmartNIC keeps host CPU for AI work in regional sites and factories. A DPU is the column for large AI factories, with dedicated infrastructure processing and strong isolation between tenants.

Chapter 10 of 20

DOCA on a plain network card

The switch in a ConnectX can hold the rules too

The chapter on host mode put a SmartNIC in between the host and the DPU. This chapter shows exactly what that middle option does, because the mechanism is the same one the DPU uses. A ConnectX-7 or ConnectX-8 has no Arm cores and runs no operating system of its own. It does have the same kind of embedded switch, with the same match and action hardware. NVIDIA's DOCA Flow library is written for that hardware, and its documentation says a DOCA Flow application can run either on the host machine or on a BlueField. DOCA is not a BlueField-only toolkit.

So on a ConnectX, TMM runs on the host's CPUs as in host mode, and it uses DOCA Flow to write rules into the card. F5's BNK 2.4 material lists what goes there: L4 and L7 traffic handling, ACLs, DDoS protection and CGNAT, carrier-grade NAT, the translation of many private addresses onto a few public ones. It works with the card in its regular NIC mode or in SuperNIC mode, and on x86 hosts and, from 2.4, on Arm hosts. The roadmap lists ConnectX-7 on x86 from 2.2, ConnectX-8 on x86 from 2.3, and ConnectX-7 and ConnectX-8 on Arm from 2.4.

The way DOCA Flow spends the switch explains why this helps the host. NVIDIA describes the default path in its VNF mode: the first packet of a flow misses every rule and is sent up to software through RSS, the hashing that spreads packets across the host's receive queues. The application looks at it, decides, and creates an entry in a pipe. The second packet of that flow hits the entry and the switch does the action itself: forward, rewrite, count or drop. In TMM's terms, the first packet of a connection is a decision on a host core, and the rest of the connection is handled in the card. A drop rule from an ACL never needs the first-packet trip at all.

What the ConnectX does not change is ownership. TMM is still a process on the host, and whoever is root on the host is root over TMM and over what it writes into the card. That is the line F5's deck draws between the columns. A ConnectX keeps host CPU for AI work in regional sites and factories. Only a DPU puts the data plane where a tenant with root cannot reach it.

Chapter 11 of 20

Host mode and DPU mode, side by side

Exactly two deployment models, and what differs between them

F5's documentation describes exactly two deployment models for BNK. F5's comparison table lines up their features row by row. In BNK on the host, which used to be called SPK, TMM runs on the host's CPUs as a software Pod. There is no hardware offload. The target workloads are 5G and communication service providers, and the protocols listed are SCTP, NGAP, Diameter and GTP. The lifecycle is managed with Helm or with FLO, the F5 Lifecycle Operator. In BNK on the DPU, TMM runs on the DPU. Packet processing and enforcement are accelerated with DOCA. The target workloads are AI and cloud native, with TCP, UDP, HTTP/2 and gRPC. The lifecycle is FLO only.

The protocol row tells you where each model came from. SCTP is a transport protocol used for signalling in mobile networks. NGAP is the 5G protocol between a radio base station and the core's access function, and it runs over SCTP. Diameter is the protocol mobile cores use for authentication and charging. GTP carries subscriber traffic in tunnels through the mobile core. These are carrier protocols, and host mode is the product that grew up handling them inside telco Kubernetes clusters. The DPU model's list is the traffic of an inference service: HTTP/2 and gRPC between clients, gateways and model servers.

The costs differ in concrete ways. In the owner's lab, BNK 2.4.0 in host mode at the Small size asked for about 20 to 22.6 vCPU and 31.4 GiB of memory across its Pods, of which the f5-tmm Pod alone asked for 4.6 vCPU, 8 GiB and 4 GiB of hugepages. TMM will not start without hugepages, the 2 MiB memory pages it uses for packet buffers. Every one of those requests comes out of a GPU server's host. In DPU mode the CNEInstance sets dpu.enabled, deploymentSize Large and TMM_DEFAULT_MTU 9000, uses the card's scalable functions nvidia.com/bf3_p0_sf and nvidia.com/bf3_p1_sf as its ports, and expects 8,192 hugepages on the card, 8,192 × 2 MiB = 16 GiB of its 32 GB. The memory and cores TMM uses are the card's. The two sets of figures are not a like-for-like size comparison: the host-mode numbers are for the Small profile and the DPU example uses the Large profile. What they show is whose resources pay for TMM, the GPU server's host or the card.

Where you can run each also differs. No public cloud offers BlueField-3 to its customers, so a BNK lab in a cloud is a host-mode lab. OpenShift is supported for host mode, and the 2.4.1 release notes list OpenShift 4.16, 4.18, 4.20 and 4.22. OpenShift adds one detail that catches people. By default a Pod gets the restricted-v2 security context constraint, which assigns each Pod a user ID from a range set on its namespace. BNK's endpoint picker runs as user ID 2000 under its own service account, one per endpoint, so it needs the nonroot-v2 constraint, which accepts any user ID except 0. Without it the picker's Pod is refused at admission.

Chapter 12 of 20

One feature list, two homes

The docs promise the same capabilities on both, and the examples all point one way

The two deployment models come with one claim that carries a lot of weight. F5's documentation says they share a unified capability set, and the list explicitly includes AI traffic handling with intelligent load balancing and token governance. Read on and the picture tilts. The target workload row puts AI on the DPU. The AI inference use case is written against the DPU. Every AI example in the material assumes a card. So the documents assert parity in the capability list, while every worked AI case points at the DPU. A reader is left to decide which to believe.

The owner's own labs give part of the answer. On OpenShift, in host mode, BNK 2.4.2 ran the full intelligent load balancing path: an InferencePool, F5's endpoint picker, and twenty out of twenty requests through TMM with a NetworkPolicy fencing the picker. The same TMM does the same work, because it is the same software. What it does not get in host mode is a hardware counter. TMM keeps firewall offload statistics that tmctl reads by the name fw_hw_offload_stats and prints under the heading "fw_rule_stat table", so the same data shows up under both names. That table has a counter column for rule hits in software and an hw_counter column for hits counted in the switch hardware. With no DOCA offload, the second column has nothing to count.

So the honest reading is this. The functions are the same in both models. Three things differ. The first is where the CPU time comes from: the host's cores in host mode, the card's in DPU mode. The second is what can be cut in hardware: ACLs and DDoS rules in the switch on a DPU or a ConnectX, everything in software on a plain host. The third is who can reach the enforcement point: in host mode, whoever is root on the host. The owner's lab notes put the last one in one line: host mode enforces, and a DPU removes host root from the trust base.

For anyone choosing, that turns the parity question into three plain checks. The first is whether the host's CPU time is cheap enough to spend on network work. The second is whether the traffic rate is high enough that per-packet rules must be in hardware. The third is whether someone other than the provider will be root on the host. When all three come out no, host mode fits. When the third comes out yes, the answer is a DPU, whatever the first two say.

Chapter 13 of 20

Handing root to a stranger

What renting bare metal demands of the provider

Some providers rent whole servers. The tenant gets bare metal: no hypervisor, an operating system of their own choice, and root on the host. F5's deck on NVIDIA's zero-trust work puts the business plainly. The provider hands root on a machine worth about $400,000 to a stranger, and does it again for the next tenant a week later.

The deck lists what that demands. The host cannot vouch for itself, because the tenant controls everything it reports. The enforcement of tenancy cannot live where the tenant lives. Firmware is an attack surface, so a tenant who can flash a card can leave something behind for the next one. If the host can reach the management controller, a tenant can climb from their own server into the provider's infrastructure. Isolation has to fail closed, so that when something breaks, traffic stops.

There are rules for reuse too. No data can remain between rentals. One tenant leaving must not disturb the shared fabric that every other tenant uses. Tenants must not hold more rights than they need, and they still expect to serve themselves through an API, the way they would in a public cloud.

Every item on that list points at the same place. There has to be a computer in the server that the tenant cannot log in to, cannot reconfigure and cannot reflash, standing between the host and the network. On this board that computer is the DPU. Its Arm cores run the provider's software, its embedded switch carries every packet, and its management controller answers only on the provider's network.

Chapter 14 of 20

Root on the host, and still locked out

Zero-trust mode takes the card away from the host

Now rent this server to a stranger as bare metal. On most servers the tenant's root would be the end of the provider's control. A DPU can be put in a mode that NVIDIA calls zero trust. In that mode the host is only a guest of the card. It gets a network device and can send and receive on it, through the rules on the card.

NVIDIA's documentation lists what the host loses. It cannot make itself the port owner, so it cannot change how the ports are set up. It cannot read the hardware counters. Its use of the tracer is blocked, so it cannot trace the card's traffic. Its RShim interface, the road from the host into the card's Arm side, is gone. Firmware flashing from the host is restricted.

The restriction is switched on from the Arm side with NVIDIA's mlxprivhost tool. The command is mlxprivhost -d /dev/mst/mt41692_pciconf0 r, with four flags: --disable_rshim, --disable_tracer, --disable_counter_rd and --disable_port_owner. The r sets every external host to restricted, except the one that ran the command. Here that is the card's own Arm side, so the server's host is the one restricted. Three of the flags need a firmware reset to take effect, and the RShim flag needs a power cycle. Run from the Arm side, mlxprivhost with q --full then shows the host at level RESTRICTED with all four flags TRUE.

So the tenant asks, and the card refuses. The firewall, the tenant's own slice of the fabric and the record of who talked to whom all stay where the tenant cannot touch them. Only the Arm side can lift the restriction, with the same tool and p for privileged.

Chapter 15 of 20

The provider's own door

The card is managed without going through the host

If the host cannot manage the card, something else has to. The DPU has a management controller with a network port of its own, a 1 gigabit RJ45 port wired to a network the tenant is not on. The provider's tooling reaches the card there. NVIDIA's DOCA Platform Framework, DPF, does this in its zero-trust deployments. Its control plane talks to each card's BMC with Redfish, the standard HTTP API for server management, over that out-of-band network.

DPF describes the cards as Kubernetes objects. A DPUDevice records one card and its BMC address. A BFB object points at the operating system image to install. A DPUFlavor carries the card's settings, including dpuMode: zero-trust. A DPUSet ties them together and starts provisioning. Creating a DPUDevice on its own changes nothing. NVIDIA's guides add operator details: the card's BMC firmware must be version 24.10 or later, every managed BMC needs the same root password, and some releases need a manual power cycle when a card reaches its rebooting phase.

Once a card is up, the same road carries policy. A new firewall rule for this tenant arrives at the card, and TMM on the Arm cores applies it a moment later. Every packet to and from the host already passes through TMM, so the next one meets the rule. The host was never asked and never told. F5's roadmap lists this kind of deployment as zero-trust DPF, with a trusted-mode DPF deployment before it.

That is the point of the whole arrangement. One server, two owners, and a line between them that is drawn in hardware.

Chapter 16 of 20

Tenant after tenant

Clean handovers and a fabric that does not notice

A rental ends and the next one starts. On a shared GPU cloud this happens over and over, and each handover has to be clean. F5's deck states the two rules that matter here: no data can remain between rentals, and tenant churn must not destabilize the shared network fabric. The tenant's operating system on the host is wiped. The card can be provisioned again from the provider's side, over the BMC road, from a known image, so nothing the last tenant did carries over.

The fabric side is where the DPU earns its place a second time. F5's material shows servers with a DPU joining the fabric directly. BNK on the card speaks BGP and takes part in EVPN-VXLAN, so each tenant gets its own routed network, much like a VPC in a public cloud. When a tenant arrives, the card announces that tenant's prefixes. In BGP, a route that is no longer wanted is withdrawn, and a withdrawal names only those prefixes. So when the tenant leaves, its routes can go without anyone editing static VLANs on the leaf switches, and the other tenants' routes stay as they were. F5's grid material sets that as a requirement: tenant churn must not destabilize the shared fabric. Each node also gets a loopback address, a stable identity for routing that does not change from tenant to tenant.

Traffic in every direction passes through BNK on the card, north and south to the outside world and east and west between servers. The deck lists layer 4 firewall rules with IP and DNS profiles, DDoS profiles at the edge, and telemetry exported in the OpenTelemetry format. Each of these runs on a computer the tenant never had access to.

The result is a server that can change hands every week. The host belongs to the tenant. The card belongs to the provider. The line between them holds for every packet, whoever is root.

Chapter 17 of 20

A firewall added to a running gateway

One more object, attached to the Gateway that already carries traffic

F5's material for shared AI infrastructure has a slide titled Start here, grow from here. The BNK foundation is multi-tenancy, zero trust and authorization, and on top of it sit AI Guardrails, the firewall, WAF and DDoS, added on the same service plane with no re-architecture. Here is what adding one looks like on a gateway that is already serving api.northlight.example. Nothing about the routes changes. The HTTPRoute that sends chat requests to the qwen3 Pods stays exactly as it is. The firewall arrives as new objects that point at the Gateway.

The rule itself is an F5BigFwPolicy, in API group k8s.f5net.com/v1. Each rule has a name, an ipProtocol, an action such as accept or drop, a source and destination with addresses and ports, and logging. Rules can also live in an F5BigFwRulelist that the policy refers to by ruleList. For this tenant, accept TCP to ports 443 and 8000 from 198.51.100.0/24, and drop everything else with logging on. In later releases a separate security policy object binds the firewall policy to its target. F5's community lab and the owner's lab use it as SecPolicy, in API group gateway.k8s.f5.com/v1alpha1, and F5's CRD reference lists it as BNKSecPolicy in gateway.k8s.f5net.com. Which name and group your cluster has depends on the release, so check with kubectl api-resources. Its targetRefs names the Gateway, and its extensionRefs names the F5BigFwPolicy and an F5BigLogProfile for the record. BNK 2.0.0 put targetRefs on the F5BigFwPolicy itself. F5's 2.0.0 documentation says that attachment follows the Gateway API pattern called direct policy attachment, GEP 2648, and that the F5BigFwPolicy must be applied in the same namespace as the resource its targetRefs names.

The scope follows the target. A policy on the GatewayClass goes into TMM's global context and applies to every Gateway of that class on every TMM. A policy on a Gateway becomes that Gateway's default, and a policy on one listener, named with sectionName, applies only to the virtual server TMM built for that listener. Each listener on a Gateway is one virtual server in TMM. This is the firewall's place in the packet order. On BIG-IP, AFM, the Advanced Firewall Manager, evaluates its contexts from global to route domain to virtual server, so a GatewayClass rule meets a packet before a Gateway rule does.

The policy reaches TMM in two steps. F5's 2.0.0 documentation describes them. The rules go first to the AFM Pod, which compiles them into a binary large object, a BLOB, that is quick to search. The BLOB is then sent to the TMM Proxy Pod, which starts filtering packets with it. The status on the F5BigFwPolicy tells you when that has happened. In F5's sample a condition of type Accepted says the controller took the object, and a condition of type Programmed with the message CR config sent to all grpc endpoints says every TMM has it. In the DPU model, the next packet to cross the card meets the rule, and the host was never touched. Removing the firewall is deleting the objects, and the route still was never edited.

Chapter 18 of 20

DDoS and the sovereign edge

A defined edge, with a layer 4 firewall and DDoS profiles in front of it

F5's slide on sovereignty and regulation starts from one sentence: regulations and certifications require defined edges, with observability and control. It then says where the edge is. Either it is on the DPU, or it is a BGP endpoint that BNK controls access through. In the first case the edge is the card in this server, in front of a host that may belong to a tenant. In the second, BGP runs directly on BNK. The slide says BNK-enabled compute nodes exchange multi-tenant IP prefixes directly, with no static VLANs and no separate routing tier between the leaf or top-of-rack switch and the compute. The slide lists what protects that edge: a layer 4 firewall with IP and DNS profiles, and DDoS profiles. The previous chapter showed the IP side, rules on addresses, protocols and ports. The slide does not spell out what its DNS profile contains. The closest documented mechanism is in F5's CNF Edge Firewall, a sibling product built on the same TMM and the same F5BigFwPolicy kind: there a rule can list destinations by domain name in destination.fqdns, and TMM resolves them through a DNS resolver set up as an F5BigDnsCache object named security-fqdn-dns-resolver, with cacheType net-resolver. F5 documents that for the CNF Edge Firewall, not for BNK's F5BigFwPolicy, so check the CRD reference of your BNK release before relying on it.

DDoS protection is its own object, an F5BigDdosGlobal, in API group k8s.f5net.com/v1. It holds attack vectors, each with a state and thresholds. F5's sample sets arpFlood to mitigation with a rate limit of 20 and a detection threshold of 20 events a second. It sets ipv4IcmpFlood and ipv6IcmpFlood to mitigation with a rate limit of 20, detection at 30 events a second and a limit of 10 a second per destination address. It sets a detection threshold of 20 for ipv4BadSrc, packets with an invalid source address. An F5 community lab adds synFlood in mitigation with a rate limit of 10,000. The object names an hslPublisher, so every detection and mitigation is logged off the box.

The DDoS policy has one strict rule about where it attaches. It goes to the global context, so it can target only a GatewayClass, and it applies to the whole cluster. If one SecPolicy lists an F5BigDdosGlobal together with a firewall policy that targets a Gateway, the admission webhook refuses it with this message: When extensionRefs includes F5BigDdosGlobal, all targetRefs.kind must be GatewayClass. Gateway and EgressGateway are not allowed. So a working edge has two SecPolicy objects, one on the Gateway for the firewall and the log profile, one on the GatewayClass for DDoS.

On a DPU these vectors are the kind of per-packet work the line-rate chapter showed belongs in the switch. F5's roadmap lists DDoS protection among the DOCA-offloaded features since the first release on BlueField, and hardware-accelerated behavioral DDoS as a later item. F5's own sample sets dosGlobalOptions.common.forceSwDos to true, which makes TMM run these vectors in software on the Arm cores. With that setting the flood is still stopped on the card, before the host, but by TMM and not by the embedded switch. The rest of the slide fills in the sovereign picture. Service access in every direction passes through BNK, and OpenTelemetry is the telemetry format, so the audit trail comes from the same place as the enforcement. The slide draws each tenant with its own network and its own BNK in front of it, labels the layer below namespace to network isolation over rows of shared servers, and says tenant traffic must cross the zero-trust layer both north and south and east and west.

Chapter 19 of 20

Grow the plane without moving it

Guardrails and WAF ride the same Gateway

The firewall and the DDoS policy show the pattern every added service follows. The traffic path is built once: the cable into the card, TMM on the Arm cores, the Gateway and its listeners, the HTTPRoute to the qwen3 Pods. Every new protection is an object attached to something on that path. The path itself is not rebuilt, and the model server is not redeployed. That is what F5's slide means by no re-architecture.

AI Guardrails, the service that inspects prompts and answers for things like personal data or attempts to subvert the model, attaches the same way. In the path F5 has built and documented in its deck, a NetPolicy, which the deck calls BNKNetPolicy, in API group gateway.k8s.f5.com/v1alpha1, attaches three iRules to the Gateway's listener. An iRule is a small TCL program that TMM runs on events in a connection. These read the request and response bodies and send them to the guardrails service on the side. TMM's side-call primitives speak only plain TCP, so the TLS to the service is made by an egress bridge inside BNK: an F5VirtualServer with an F5BigCnePool behind it, an F5BigServersslSetting for TLS 1.2 or 1.3, and one more iRule that sets the server name the service expects. No extra proxy sits in the traffic path.

The verdict decides one of three outcomes. Cleared means no violation: the request passes unmodified and TMM adds the header X-Guardrails-Request-Action: pass. Flagged means a policy violation: the request iRule blocks at once and answers with the configured block body, by default a 200 response in JSON saying Blocked by policy. Redacted means a pattern such as a social security number or an email address matched: a redaction library replaces the matched spans with <redacted> by character offset, adds X-Guardrails-Request-Action: redact, and forwards the changed request to the model. The route to the model is the same route as before.

WAF, the web application firewall, is the third of the four services on the slide, after AI Guardrails and the firewall and before DDoS. It inspects HTTP requests for attacks on the application, and on BNK it joins the plane the same way: one more policy on the same Gateway. F5's roadmap places WAF support on BNK in CY27 or later, after the AI services, together with hardware-accelerated behavioral DDoS and hardware-accelerated IPS.

On the DPU model, all of these run on the card. Each one adds work for TMM on the Arm cores, and each one is applied without the tenant's host being asked or told. The order on F5's slide is a sensible order to grow in. Start with the foundation: isolation, zero trust and authorization. Add the firewall and DDoS at the edge. Add guardrails for what the model is asked and what it answers, and the WAF for the application around it.

What to keep

The line is drawn in hardware

A GPU server is three computers on one board. Small things move between them over PCIe slots: packets, commands, token IDs. The heavy work stays on the GPU card, where memory feeds the cores fifty times faster than any slot could. A DPU puts the network's rules on a computer of its own, in front of the host. That frees the host's CPUs, and it means the rules still hold when the host belongs to someone else. The same BNK data plane runs in host mode without one. What the DPU adds is a place to enforce that the tenant cannot reach, and that has to be decided when the server is ordered.
