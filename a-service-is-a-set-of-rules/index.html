Kubernetes underneath

A Service is a set of rules

How an address that nobody owns reaches a Pod

A Service gives a group of Pods one stable address. Pod client on node-1 is about to open a connection to the Service web. Its address is 10.96.37.204 and it has two Pods behind it: web-1 on the same node and web-2 on node-2. That address is on no network interface anywhere in the cluster, and no process listens on it. It works because a program called kube-proxy has written rules into the kernel of every node. Those rules rewrite the destination of the first packet to a real Pod, and the kernel remembers the choice for the rest of the connection. This lesson follows one packet through the rules by their real names. Then it shows what that design means for long connections to model servers.

Chapter 1 of 14

An address that no machine has

The API server hands out a number and nothing more

Someone creates a Service named web in the namespace inference. Its type is ClusterIP, which is the default. The API server picks a free address from the Service range, 10.96.0.0/12, and stores it in the field spec.clusterIP. Kubernetes calls this a virtual IP. Nothing else happens to it. No node adds it to an interface and no route points at it. You can list the addresses of both nodes and of every Pod and never find 10.96.37.204. A Pod address always leads to one fixed place. A Service address leads nowhere until something rewrites it. The Service also carries a selector, app: web, and a port mapping: port 80 on the Service goes to port 8080 on the Pods. Had targetPort been left out, it would default to the value of port. It can also be the name of a container port, so Pods behind one Service may use different numbers for the same name. A Service with more than one port must name every port.

The address is not drawn from the whole range at random. The API server splits the range into two bands with the formula min(max(16, size / 16), 256). The range 10.96.0.0/12 holds 2^20 = 1,048,576 addresses. Divided by 16 that is 65,536, and the formula caps it at 256. So the lower band runs from 10.96.0.1 to 10.96.1.0 and is kept for addresses that people choose by hand. Automatic allocation takes from the upper band first and touches the lower band only when the upper one is full. 10.96.37.204 lies above 10.96.1.0, so it came from the upper band. A Service can ask for a fixed address in spec.clusterIP. An address outside the range is refused with HTTP status 422, and an address already in use is refused as well. Many installers give the cluster's DNS Service the tenth address of the range, 10.96.0.10 here. That is a convention. Nothing reserves the address, so a Service created earlier can take it.

With the allocator that the documentation calls MultiCIDRServiceAllocator, each allocated address is also an object of its own. The API server writes an IPAddress named 10.96.37.204 whose parent reference points at the Service web, and the range itself is a ServiceCIDR object. The default ServiceCIDR is named kubernetes and is built from the API server flag --service-cluster-ip-range. More ranges can be added by creating more ServiceCIDR objects. The older allocator kept one allocation map in etcd and limited IPv6 ranges to a /108. The new one accepts a /64 or smaller.

Kubernetes could have published Pod addresses through DNS and skipped the virtual address. The documentation gives three reasons it does not. Some DNS clients ignore the time to live of a record. Some applications look a name up once and keep the result forever. And very short times to live would put a heavy load on the DNS servers. An address that never changes avoids all three. The Pods behind it come and go while every client keeps the same number. A client can also learn the address without DNS. When a Pod starts, the kubelet adds environment variables for the Services that exist at that moment, such as WEB_SERVICE_HOST and WEB_SERVICE_PORT. A Service created after the Pod started is missing from them.

Chapter 2 of 14

kube-proxy writes the rules and steps aside

Two watches in, a set of chains out

On every node runs kube-proxy. It holds two watches on the API server. A watch is a request that stays open and delivers each change as it happens. One watch is on Services. The other is on EndpointSlices, the objects that list the Pods behind each Service with their addresses, ports and readiness. A controller in the control plane fills them from the selector. When web appears, kube-proxy on node-1 and on node-2 each receive the Service and one EndpointSlice with two endpoints. Each turns them into iptables rules in the kernel of its own node, loaded in one call to iptables-restore. Then kube-proxy goes back to waiting. It carries no packets. If it stops, the rules stay and traffic keeps flowing. Only changes stop arriving.

The rules are loaded as one block of text. kube-proxy builds an input for iptables-restore with a *filter section and a *nat section, each closed by the word COMMIT, and the kernel applies each table as a single change. Chains that belong to other programs in the same tables are left alone, because kube-proxy runs the restore without flushing the tables. Two timers shape the loads. minSyncPeriod, 1 second by default, is the shortest gap between two loads, so a burst of changes is batched into one. syncPeriod, 30 seconds by default, does two other jobs. It is how long kube-proxy waits before it retries a load that failed. It is also how often kube-proxy checks its canary chains, empty chains named KUBE-PROXY-CANARY that it creates in the mangle, nat and filter tables. If another program has flushed one of those tables, the canary is gone, and kube-proxy writes all its rules again. The documentation describes syncPeriod as controlling how quickly kube-proxy notices that an outside component has interfered with its rules. The longest gap between two loads is a separate constant in the source, FullSyncPeriod, which is 1 hour. Since Kubernetes 1.28 a normal load writes only the chains of Services whose Service object or EndpointSlices changed. The chains of every other Service stay in the kernel untouched.

The chain names are computed, so they agree on every node without any coordination. The name of a Service chain is KUBE-SVC- followed by the first 16 characters of a SHA-256 hash of inference/web:http and tcp, written in base32. kube-proxy on node-1 and kube-proxy on node-2 compute the same names from the same objects. When a load fails, kube-proxy logs Failed to execute iptables-restore and counts the failure in the metric kubeproxy_sync_proxy_rules_iptables_restore_failures_total. The old rules stay in force until a later load succeeds. kube-proxy also does not promise to clean up after itself. The documentation warns that the kernel rules it creates may stay behind, in some cases until the node reboots.

Chapter 3 of 14

EndpointSlices hold the list

Up to 100 endpoints in a slice, three conditions on each

An EndpointSlice is the list that kube-proxy turns into KUBE-SEP chains. The EndpointSlice controller in kube-controller-manager writes it from the Service's selector. It links the slice to its Service with the label kubernetes.io/service-name: web, and marks the slice as its own with the label endpointslice.kubernetes.io/managed-by: endpointslice-controller.k8s.io. One slice holds at most 100 endpoints by default. The flag --max-endpoints-per-slice on kube-controller-manager raises that, up to a maximum of 1000. Slices are grouped by IP family, protocol, port number and Service name. Each slice has a single addressType, IPv4 or IPv6, so a Service with both families has at least two slices.

The controller fills slices and does not rebalance them. Given 10 new endpoints and two slices with room for 5 each, it creates one new slice rather than updating two. The documentation gives the reason: every change to a slice is sent to kube-proxy on every node, so one creation costs less than two updates. An endpoint can appear in two slices for a short time, so kube-proxy reads all the slices of a Service and removes duplicates before it writes any rule. The older Endpoints object, deprecated since Kubernetes 1.33, stopped at 1000 addresses and then set the annotation endpoints.kubernetes.io/over-capacity: truncated. Slices have no such limit in total.

Each endpoint carries three conditions. serving follows the Pod's Ready condition. terminating is set once the Pod has a deletion timestamp. ready is a short form for serving and not terminating. A Service with spec.publishNotReadyAddresses: true has ready set to true on every endpoint. In the normal case only ready endpoints get rules. A Service with no selector gets no slices at all, and you write them yourself with the service-name label. Their addresses may not be loopback or link-local, and they may not be the ClusterIP of another Service, because kube-proxy does not send traffic to a virtual address.

Chapter 4 of 14

Three chains and a coin toss

KUBE-SERVICES, then KUBE-SVC, then KUBE-SEP

A minute later the client connects to 10.96.37.204 port 80. Its kernel builds a SYN, the first packet of a TCP connection. The Pod's default route sends it across the virtual cable to the bridge, and so into the network namespace of node-1. Before the node routes the packet, the PREROUTING chain of the nat table runs and jumps to KUBE-SERVICES. One rule there matches the address and port of web and jumps to the chain for that Service. That chain has a rule for each endpoint. iptables has no rule that says choose one from a list, so kube-proxy gives every rule except the last a probability. With two endpoints the first rule matches half the time. A packet that it lets pass meets the second rule, which has no condition. This time the first rule passes, and the second sends the packet to the chain for web-2.

Two hooks of the nat table lead into KUBE-SERVICES, and both rules carry the comment kubernetes service portals. Packets that arrive from a Pod or from another machine pass PREROUTING. Packets that a process on the node itself sends pass OUTPUT. In front of the endpoint rules of a KUBE-SVC chain there can be one more rule. It sends any packet for the ClusterIP whose source lies outside the Pod range to KUBE-MARK-MASQ. kube-proxy's source explains the case. Someone can route the whole Service range to a node from outside the cluster, and that node will then forward into the Service. The reply has to come back through the same node, so the source is rewritten. With the option masqueradeAll every packet to a ClusterIP is marked this way.

The probabilities come from one line of Go that formats 1/n with ten digits after the point, where n is the number of endpoints still to choose from. A Service with four Pods gets rules with 0.2500000000, 0.3333333333 and 0.5000000000, then a last rule with no condition. Each Pod then receives a quarter of new connections. The first gets 1/4 at rule one. The second gets 3/4 × 1/3 = 1/4. The third gets 3/4 × 2/3 × 1/2 = 1/4. The fourth gets the 1/4 that is left. The sample output on kubernetes.io still shows an older format with eleven digits, such as 0.33332999982, because it was captured from an older release. In a cluster with more than 1000 endpoints in total, kube-proxy leaves the comments off the endpoint rules to make the rule set smaller, so the comments shown in this lesson are missing there.

Chapter 5 of 14

The first packet is rewritten, the rest are remembered

DNAT once, then conntrack for both directions

The chain for web-2 ends in a rule with the target DNAT, destination network address translation. It rewrites the destination of the packet from 10.96.37.204 port 80 to 10.244.2.17 port 8080. The source stays the client's own address. At the same moment conntrack, the kernel's connection tracker, records the connection with both pairs of addresses. From here it is an ordinary Pod to Pod packet. Node-1 sends it through the tunnel and node-2 delivers it to web-2. Web-2 answers to 10.244.1.12, so the reply comes back to node-1. Conntrack recognises it there and puts 10.96.37.204 port 80 back as the source. The client sees an answer from the address it called. The nat table is consulted only for the packet that creates a connection. Every later packet is translated from the conntrack entry.

The translation can be undone only where the conntrack entry lives. Here that is node-1. Web-2's reply is addressed to 10.244.1.12, a Pod on node-1, so node-2 routes it back through the tunnel to node-1 by its ordinary route, and the entry is there to meet it. Nothing in this case had to be arranged. When the caller is outside the Pod network, the reply would not find its way back to the node that made the entry on its own. That is why the node port path later in this lesson rewrites the source as well.

The first rule of every KUBE-SEP chain handles a Pod that reaches itself through its own Service. If web-2 called 10.96.37.204 and the random match picked web-2, the packet would go back down the same virtual cable with source and destination both 10.244.2.17. Web-2 would then answer itself directly, and the reply would skip the translation. So a packet whose source is the endpoint's own address is marked, and the node replaces the source with an address of its own. This hairpin case also needs the bridge to send a frame back out of the port it arrived on. On this lesson's nodes the bridge cni0 belongs to the CNI bridge plugin, which flannel calls. That plugin has an option hairpinMode, false by default, and flannel's manifest sets it to true. The plugin then turns on hairpin for the host end of each Pod's veth. On the node, cat /sys/devices/virtual/net/cni0/brif/*/hairpin_mode should print 1 for each port of the bridge. The kubelet's own setting hairpin-mode, with the values hairpin-veth and promiscuous-bridge, comes from the debugging guide's example of kubenet's bridge cbr0. The guide checks hairpin_mode = 1 only when the effective mode is hairpin-veth. For promiscuous-bridge it checks that the bridge shows the PROMISC flag instead.

Chapter 6 of 14

A mark now, a new source later

KUBE-MARK-MASQ sets a bit, and KUBE-POSTROUTING acts on it

kube-proxy never rewrites a source address in the chains that choose an endpoint. It only marks the packet. The chain KUBE-MARK-MASQ holds a single rule, -j MARK --or-mark 0x4000. The value comes from the setting masqueradeBit, which is 14 by default. One shifted left by 14 places is 0x4000, or 16,384. The mark is a number the kernel keeps beside the packet while it decides where to send it. It is never written into a header.

The rewrite happens at the very end, after routing, in the nat POSTROUTING hook. That hook jumps to KUBE-POSTROUTING with the comment kubernetes postrouting rules. The chain holds three rules. The first returns at once for any packet that does not carry the mark. The second clears the mark with --xor-mark 0x4000, so that a packet passing through the network stack a second time is not rewritten twice. The third applies MASQUERADE --random-fully, with the comment kubernetes service traffic requiring SNAT. MASQUERADE replaces the source with an address of the interface the packet leaves through, and --random-fully chooses the new source port fully at random.

The client's SYN from the last chapter came from a Pod address, so nothing marked it, and the first rule of KUBE-POSTROUTING let it go unchanged. The hairpin case is different. If web-1 calls the Service and the random match picks web-1 itself, the first rule of its KUBE-SEP chain marks the packet. It leaves through the bridge cni0, so its new source is the bridge's address, 10.244.1.1. Web-1 answers 10.244.1.1, the reply passes the node, and conntrack undoes both rewrites.

kube-proxy also writes rules in the filter table. FORWARD and OUTPUT jump to KUBE-SERVICES in that table, for new connections only. That is where the REJECT for a Service without endpoints sits. FORWARD also jumps to KUBE-FORWARD. Its rules accept packets that carry the mark, with the comment kubernetes forwarding rules, and packets of connections that are already RELATED or ESTABLISHED, with the comment kubernetes forwarding conntrack rule. So node port traffic gets through even when the node's default FORWARD policy is DROP.

Chapter 7 of 14

One choice per connection

The rules balance connections and never see a request

The coin is tossed when a connection opens and never again. That suits a client that opens a new connection for each request. It matters for a client that keeps one connection open. HTTP/2 and gRPC send many requests over a single TCP connection, and a gateway may hold that connection for hours. Every request on it goes to the Pod that was chosen at the SYN. Picture the Service qwen3 in front of two model servers. A gateway with one gRPC connection sends all of its prompts to one GPU while the other sits idle. A Pod added later receives nothing from connections that already exist. The kernel rules work on packets and connections. They cannot see where one request ends and the next begins. Spreading requests takes something that reads them: a proxy that speaks HTTP, or a client that opens a connection to each Pod.

A Service port has a field that looks as if it could help, spec.ports[].appProtocol. It accepts values such as kubernetes.io/h2c for HTTP/2 without TLS, kubernetes.io/ws and kubernetes.io/wss for WebSocket, IANA service names, or names with a domain prefix. The documentation calls it a hint for implementations. kube-proxy's rules do not read it, whatever its value. It is read by proxies, gateways and cloud load balancers that work on requests. The other kube-proxy modes do not change the picture either. In ipvs mode a least connection scheduler counts connections, so it sees the gateway's one connection as one unit of load, however many prompts travel on it.

Numbers make the effect concrete. Suppose a gateway holds one HTTP/2 connection to the Service qwen3, which has two model servers, and sends 100 prompts a minute on it. The SYN of that connection was matched once and picked one Pod. All 100 prompts a minute land on that Pod's GPU, and the other model server receives none. If the gateway opened 10 connections, each would be matched on its own with a probability of 1/2, and the split would be even only on average. The chance that one given Pod receives exactly 7 of the 10 is C(10,7) / 2^10 = 120 / 1024, about 11.7%. Counting both directions, a split of 7 to 3 or worse in either direction happens (2 × (120 + 45 + 10 + 1)) / 1024 = 352 / 1024 of the time, about 34%. A deliberate choice for each request needs a component that sees requests.

Chapter 8 of 14

Conntrack has a size and a clock

A limit on entries, and timers that kube-proxy shortens

Every connection through a Service holds an entry in the conntrack table, and the table has a limit. kube-proxy computes it when it starts. It multiplies 32,768 entries for each CPU core, from the setting conntrack.maxPerCore, by the number of cores. Since version 1.36 that product is capped at 1,048,576 entries, so that machines with many cores do not reserve too much memory. The limit is then the larger of that capped product and 131,072, from conntrack.min. A node with 4 cores gets 131,072, because 4 × 32,768 is exactly 131,072. A node with 32 cores gets 32 × 32,768 = 1,048,576, exactly the cap. A GPU node with 64 cores would get 64 × 32,768 = 2,097,152, and the cap brings it down to 1,048,576. Version 1.35 and older had no cap and wrote 2,097,152. Version 1.36 writes the computed value every time it starts. Newer source writes it only when the kernel's current value is smaller, so a limit an operator has raised by hand is left alone. The kernel shows the limit as the sysctl nf_conntrack_max and the current number of entries as nf_conntrack_count, which is read only. When the count reaches the limit, the kernel cannot track new connections and drops their packets.

Entries also expire. The kernel's own default for an established TCP connection that carries no traffic is 432,000 seconds, which is five days. kube-proxy lowers it to 24 hours, and its source marks that value as one fifth of the default. It also sets the time for a connection in the CLOSE_WAIT state to 1 hour, where the kernel's default is 60 seconds. A UDP entry lasts 30 seconds after its last packet. In the current kernel source it moves to the longer stream timeout of 120 seconds only when a reply has been seen and the flow is still sending packets more than 2 seconds after it began. A DNS query and its answer, a few milliseconds apart, therefore keep the 30 second timeout. Kernels without that 2 second rule gave any entry that had seen a reply the 120 second timeout at once. So a gRPC connection from a gateway to a model server that stays silent for more than 24 hours loses its entry. Packets after that are no longer translated from the old entry, and the connection usually breaks. Keepalive packets at intervals well below 24 hours prevent that.

One more rule protects long connections. Linux kernels before 6.1 have a bug that can close long-lived TCP connections to Service addresses with the error Connection reset by peer. The iptables mode works around it by dropping packets that conntrack classifies as INVALID, the first rule of KUBE-FORWARD. If the sysctl nf_conntrack_tcp_be_liberal is set, kube-proxy leaves that rule out and logs nf_conntrack_tcp_be_liberal set, not installing DROP rules for INVALID packets. The nftables mode has no such workaround and offers the option --conntrack-tcp-be-liberal instead. The metric kubeproxy_iptables_ct_state_invalid_dropped_packets_total shows whether a cluster depends on the workaround.

Chapter 9 of 14

A ClusterIP between a picker and a GPU

A second random choice undoes a deliberate one

The site's model servers are where the last two chapters matter most. An inference gateway that knows which GPU already holds a prompt's prefix in its cache, or which one has the shortest queue, asks an endpoint picker. The picker returns one Pod address, such as 10.244.1.15:8080 for web-1, and the gateway should send the request to exactly that Pod. If the gateway sends it to the Service address instead, the SYN meets the KUBE-SVC chain on the gateway's node. The random match runs again and may pick web-2. The picker's choice is thrown away, and nothing reports that it was.

A packet addressed to a Pod passes the same PREROUTING hook and the same KUBE-SERVICES chain. No rule there matches a Pod address, so it leaves that chain unchanged and is routed like any other packet. That is why gateways that use a picker connect to Pod addresses directly. They may still use the Service, or its EndpointSlices, to find out which Pods exist.

Material on F5 BIG-IP Next for Kubernetes states the rule plainly. Once an endpoint has been selected, it must not be load balanced again downstream, and a ClusterIP in the path makes kube-proxy discard the choice. F5's discovery material for distributed inference tells its field teams to listen for clusters that rely on standard Kubernetes Services through kube-proxy, on Ingress or on round robin, because those spray prompts that share a prefix across different GPUs. Its picture of an inference cluster lists an external load balancer, kube-proxy with a node port, an L7 gateway, an AI gateway and endpoint selection as separate layers, and argues for one data path that delivers straight to Pod addresses. kube-proxy balances connections well. It has no view of prompts, caches or GPU queues.

Chapter 10 of 14

Sticky clients and local traffic

sessionAffinity, internalTrafficPolicy and trafficDistribution

Three fields on the Service change how the random match behaves. The first is spec.sessionAffinity, whose default is None. Set to ClientIP, it sends every new connection from one client address to the endpoint that address used last. The memory lasts spec.sessionAffinityConfig.clientIP.timeoutSeconds, which defaults to 10800 seconds, three hours. In iptables mode it is built from the recent match, a small list of source addresses that the kernel keeps for a rule. When a KUBE-SEP chain rewrites a packet, it also adds the client's address to a list named after that chain. The KUBE-SVC chain gets one extra rule for each endpoint, ahead of the random rules. Each checks whether the source is on that endpoint's list and was seen within the timeout, and if so jumps straight to that endpoint.

The second is spec.internalTrafficPolicy, stable since Kubernetes 1.26. Cluster, the default, uses every endpoint. Local uses only endpoints on the same node as the client. On node-1 the ClusterIP rule then jumps to a chain named KUBE-SVL in place of KUBE-SVC, and that chain lists only web-1. If node-1 had no Pod of web, traffic from Pod client would be dropped by a rule with the comment has no local endpoints. The gauge kubeproxy_sync_proxy_rules_no_local_endpoints_total counts, on each node, the Services in that state.

The third is spec.trafficDistribution, which expresses a preference and makes no promise. PreferSameZone asks for endpoints in the client's zone, and PreferSameNode for endpoints on its node. PreferClose is the older name for PreferSameZone and is deprecated. The EndpointSlice controller writes hints into the slice. kube-proxy uses them only when every ready endpoint has a hint and at least one hint matches its own node or zone. Otherwise it falls back to all endpoints and logs that it is ignoring the hints. A Local traffic policy takes precedence over this field. For model servers, ClientIP affinity is a coarse tool: every request from one gateway address lands on one GPU for three hours.

Chapter 11 of 14

When a Pod goes away

New connections move at once, old ones keep their entry

Now web-2 is deleted. While it shuts down, its endpoint stays in the EndpointSlice with new conditions: ready is false and terminating is true. kube-proxy on each node receives the change and rewrites the chains. The chain for web-2 is removed. The chain for web now holds a single endpoint rule with no probability, pointing at web-1. Every new connection goes there. The client's old connection is a different matter. Its conntrack entry still names 10.244.2.17, and kube-proxy removes stale entries only for UDP. The TCP connection lasts until web-2 closes it or stops answering. That is why a server should finish its requests and close its connections when it is asked to stop. If the last endpoint goes as well, kube-proxy replaces the Service's rules with one that rejects, and a connection attempt fails at once.

The change to the rules and the signal to the Pod race each other. The control plane takes the endpoint out of the slice at the same moment as the kubelet starts the graceful shutdown of the Pod. On a busy cluster the new rules can reach node-1 after web-2 has received SIGTERM. A server that stops accepting connections the instant it gets SIGTERM can still receive a few SYNs in that window and refuse them. That is why many servers keep accepting for a few seconds after the signal and only then close their listener.

kube-proxy has one more fallback. In the normal case only ready endpoints get rules. If a Service has no ready endpoint left but has endpoints that are both serving and terminating, kube-proxy uses those, under the Cluster policy and under Local alike. Only when neither kind exists does the REJECT rule appear. This matters for a Service with a single replica whenever the old Pod is still draining and the new one is not ready yet. A Deployment with the default rolling update does not get there. Its maxSurge of 25% rounds up to 1 and its maxUnavailable of 25% rounds down to 0, so the new Pod must be ready before the old one is stopped. A rolling update with maxSurge: 0 and maxUnavailable: 1 gets there, and so does an eviction or a deletion of the only Pod, which starts its replacement only after the old Pod begins to terminate. With the fallback, new connections still reach the old Pod for as long as it passes its readiness probe.

The cleanup of UDP entries is more careful than the word stale suggests. kube-proxy lists conntrack entries and deletes the UDP ones that point at a Service address, a node port or a load balancer address but are not translated to an endpoint that is still serving. It has to. An established flow is translated before the REJECT rule is ever evaluated, and a one-way UDP stream, such as metrics sent to statsd, refreshes its entry with every packet and would never expire. The metric kubeproxy_conntrack_reconciler_deleted_entries_total counts the deletions. For TCP, kube-proxy leaves the entries alone and relies on the server to end its connections.

Chapter 12 of 14

From outside the cluster

A NodePort is one more way into the same chain

A ClusterIP works only where the rules are, on the nodes and in their Pods. For callers outside, a Service of type NodePort adds a port from the range 30000 to 32767, the same number on every node. Here web gets 31080. A packet to 10.0.1.11 port 31080 enters node-1. The last rule of KUBE-SERVICES sends packets for the node's own addresses to the chain KUBE-NODEPORTS. From there the packet passes a KUBE-EXT chain, which marks it, and then joins the same KUBE-SVC chain as before. Because of the mark, the node also replaces the source with an address of its own. The reply then returns through the node that holds the conntrack entry. Type LoadBalancer builds on this. A load balancer outside the cluster gets a public address and typically forwards to the node port.

The node port range is split into two bands, like the Service range. With the default range the lower band is 30000 to 30085 and the upper band is 30086 to 32767. Automatic allocation uses the upper band first, which leaves the lower band for ports people choose by hand. A Service that asks for a node port another Service already holds is refused. In iptables mode a node port answers on every address of the node, because the jump to KUBE-NODEPORTS matches any local destination with --dst-type LOCAL. That jump is the last rule of KUBE-SERVICES on purpose, and its comment says so. With the option --nodeport-addresses set to address ranges, kube-proxy writes one jump for each matching node address in place of that match. In nftables mode only the node's primary addresses answer by default.

In iptables mode a node port even works on 127.0.0.1. That needs the sysctl net/ipv4/conf/all/route_localnet set to 1, which kube-proxy sets and reports with the log line Setting route_localnet=1 to allow node-ports on localhost. The option --iptables-localhost-nodeports false turns it off. A Service can also list addresses in spec.externalIPs, and each gets a rule in KUBE-SERVICES with the comment external IP that jumps to the same KUBE-EXT chain. That field has been deprecated since Kubernetes 1.36, and the documentation asks every user to migrate away from it. The marked packet from the load balancer is accepted by KUBE-FORWARD on its way to node-2, which is why the node port path works even with a strict firewall policy on the node. The rest of the outside path, the load balancer, its health checks and the fate of the client's address, is the subject of the lesson From the internet to a Pod.

Chapter 13 of 14

What an operator checks on a node

iptables-save, two ports and a handful of metrics

When a Service misbehaves, the documented check on a node is to dump the rules and search for the Service: iptables-save | grep web. The guide states what a healthy result looks like. For each port of each Service there is one rule in KUBE-SERVICES and one KUBE-SVC chain. For each endpoint there are a small number of rules in that KUBE-SVC chain and one KUBE-SEP chain. For web on node-1 that means one KUBE-SERVICES rule, the chain KUBE-SVC-OSVKZ2AR6ZI2SYOS with two rules, and the two KUBE-SEP chains. A Service with no endpoints shows only the REJECT rule in the filter table.

kube-proxy listens on two ports of its own. Its health server listens on 0.0.0.0:10256 by default, which is also the port that load balancers ask. Its metrics are served on 127.0.0.1:10249, so they are visible from the node only. All its metric names start with kubeproxy_. kubeproxy_sync_proxy_rules_duration_seconds is how long a load takes, with separate versions for full and partial loads. kubeproxy_network_programming_duration_seconds is the time from a change in the API to the rules in the kernel. kubeproxy_sync_proxy_rules_endpoint_changes_pending and kubeproxy_sync_proxy_rules_service_changes_pending show changes waiting for the next load. kubeproxy_sync_proxy_rules_iptables_total gives the number of rules in each table. The documentation's tuning advice is to raise minSyncPeriod only if a load takes much longer than 1 second on average.

The log tells the same story in words. At verbosity 2 each load writes the line Reloading service iptables data, with the counts numServices, numEndpoints, numFilterChains, numFilterRules, numNATChains and numNATRules. If kube-proxy runs in ipvs mode, the check is ipvsadm -ln, which lists each virtual server with its scheduler and each real server behind it with its forwarding method, weight and counts of active and inactive connections.

Chapter 14 of 14

Other ways to write the same rules

ipvs, nftables and eBPF follow the same model

iptables is one of three modes that kube-proxy has on Linux. In ipvs mode it programs IPVS, a load balancer inside the kernel. IPVS looks a Service up in a hash table and offers several schedulers, such as round robin and least connection. This mode has been deprecated since Kubernetes 1.35. In nftables mode kube-proxy writes the same logic through nftables, the successor to iptables. It needs kernel 5.13 or later and processes changes to Services and endpoints faster. It also handles packets more efficiently, which shows only in clusters with tens of thousands of Services. The default is still iptables, and the documentation says a future release will change it to nftables. Some network plugins, Cilium for one, replace kube-proxy with eBPF programs. The model stays the one in this lesson: watch Services and EndpointSlices, pick a backend when a connection opens, and remember the choice.

The ipvs mode has a fixed end. It is deprecated since Kubernetes 1.35, it will be disabled by default from 1.40 behind the feature gate KubeProxyIPVS, and it will be removed in 1.43. The documentation gives the reason in one line: the kernel's IPVS interface turned out to be a bad match for the Kubernetes Services API. A cluster that runs it can be read with ipvsadm -ln, which prints each Service address with its scheduler, such as rr for round robin, and each Pod behind it with the forwarding method Masq, a weight and counts of active and inactive connections.

The nftables mode differs from iptables mode in three documented ways. A node port answers only on the node's primary addresses by default, where iptables mode answers on all of them. kube-proxy adds no rules to open node ports through a local firewall. And it installs no workaround for the conntrack bug in kernels before 6.1. Node ports on 127.0.0.1 need the feature gate KubeProxyNFTablesLocalhostNodePorts and --nodeport-addresses primary,localhost, and they are served by a small proxy in user space. Rules written by one mode are not guaranteed to disappear when the mode changes. The documentation warns that kernel rules created by kube-proxy may not be cleaned up, in some cases until the node reboots, and that the cleanup function in the binary is not an official feature.

What to keep

An address made of rules

A ClusterIP is a number in the API server and a match in the kernel of every node. kube-proxy watches Services and EndpointSlices and writes three kinds of chain: KUBE-SERVICES to find the Service, a KUBE-SVC chain to choose an endpoint with random matches, and a KUBE-SEP chain to rewrite the destination. The choice is made on the first packet. Conntrack applies it to every later packet and reverses it on the replies. That makes the Service a balancer of connections. For a model server behind HTTP/2 or gRPC, one long connection means one Pod and one GPU, however many replicas exist. Around the three chains sit the pieces that keep them honest: EndpointSlices that say which Pods are ready, a mark that asks POSTROUTING for a new source, a conntrack table with a size and a clock, and fields that make the choice sticky or local. A gateway that has picked a GPU on purpose must send to the Pod address, because a ClusterIP in between makes the choice again at random.
