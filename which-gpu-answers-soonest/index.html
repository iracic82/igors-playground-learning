BNK and gateways

Which GPU answers soonest

From round robin to a picker that weighs warm cache against the line in front of it

Every request to a pool of model servers ends in one decision: which GPU gets it. For a web server the answer hardly matters, because requests are alike and servers are alike. For a model server it decides almost everything. Two requests of the same size can differ thirty times in how long they hold a GPU, and one worker may already hold most of a prompt in memory while the next would have to read it from scratch. This lesson walks through four ways of making the choice, each fixing what the one before got wrong, and ends at what the F5 endpoint picker does. It starts with a single click in an app.

Chapter 1 of 14

One click, a storm

A travel planner turns one request into three kinds of work

A user asks a travel app to plan a trip. Behind the app is a team of agents, and one click sets all of them off. In F5's demonstration the team is an orchestrator and five specialists, for flights, hotels, activities, weather and travel. One trip search makes between 5 and 12 calls to the model. A full run is twelve: the orchestrator calls four times, the flight, hotel and activity agents twice each, and the travel and weather agents once each.

The calls come in three shapes. First a retrieval step looks up the destination in a document store and pastes five passages of about 900 characters each into the prompts. That is 4,500 characters, roughly 1,100 tokens, and every agent's prompt starts with the same text. Then the five specialists run at the same instant, and run again if the plan comes out over budget. F5 counts these as bursts of 5 to 10 or more requests at once. Finally the orchestrator writes the whole itinerary, a single answer several pages long.

The passages come from a store built for the demonstration. F5's deck says travel documents land in S3 storage, served by MinIO in F5's lab, and are then chunked and embedded into a vector database, pgvector in the lab. Its source note gives the chunks injected into the prompts as five of 900 characters, so this lesson takes the chunks to be about 900 characters. Each chunk is turned into an embedding, a list of numbers that places texts with similar meaning close together, and kept as a row in PostgreSQL with the pgvector extension. pgvector adds a column type, vector(n) for n numbers, and distance operators: <-> for straight-line distance, <=> for cosine distance and <#> for the negative inner product. F5's slide on the retrieval process shows the query being embedded the same way before the search, without naming which component does it. In this lesson's reading, the small service in the lab, rag-service, embeds the lookup, asks the database for the five nearest chunks with ORDER BY embedding <=> the lookup's vector LIMIT 5, and pastes them into the prompt. An HNSW or IVFFlat index keeps that search fast when the table is large. F5's deck calls this tier Data and Grounding Storage: S3 or MinIO for the documents, pgvector for the search.

This store is where the shared prefix comes from. The deck says rag-service injects five destination documents into the agents' prompts. When every agent planning one trip gets the same five passages in the same order, the first 4,500 characters of all their prompts are the same, and a router that can see it can send them to the GPU that has already read those tokens. If each agent searched with its own wording, the five could differ or arrive in another order, and the shared part would shrink to whatever text comes before them.

So one click produces prompts that are heavy going in and share a prefix, a burst of many at the same moment, and one long piece of writing. To the network all of them look alike. Each is a small HTTP POST to the same path, /v1/chat/completions. A balancer that counts connections has nothing to tell them apart.

Chapter 2 of 14

A model request is not a web request

The cost is in the tokens, and it comes in two phases

Round robin was built for web and API traffic, and there it works. F5's engineers describe that traffic as requests of 50 to 200 milliseconds and 0.5 to 2 kB, each costing a server about the same, served first in, first out. Taking turns then gives near-perfect balance. For inference they give 50 to 800 milliseconds, a spread of 16 times, and prompts from 100 bytes to more than 5 kB, a spread of 50 times. Another F5 deck compares a ten-word question with a prompt of 64,000 tokens and puts the gap in compute and GPU memory at up to 1,000 times.

The cost also comes in two phases. In prefill the model reads the whole prompt in one pass. That phase is bound by compute and sets the time to first token, TTFT. Then the decode loop writes one token per pass. It is bound by how fast memory can be read and sets the gap between tokens, the inter-token latency. What prefill computed stays in GPU memory as the KV cache. For Qwen3-32B that is about 260 kB per token, so a prompt of 20,000 tokens holds about 5.2 GB.

Two things follow. The unit of work is the token. And a cached prompt saves prefill only. If a hit saves 0.2 seconds on a request that decodes for 10 seconds, the gain is 2%. Agent workloads are heavy in prefill, so there the cache matters most.

Chapter 3 of 14

Round robin sees two equal requests

They differ thirty times in what they cost a GPU

Start with the simplest balancer. Round robin hands each new request to the next worker in turn. Look at two requests from this app the way it sees them. One asks an agent to pick the best flight. One asks the coordinator to write a five-day itinerary. Both are a post of about a kilobyte to the same address. The first makes the GPU write two lines, about 256 tokens, and is done in under a second. The second makes it write 8,192 tokens and takes about 25 seconds. Both times were measured in F5's session on a test machine running on CPUs, so read them as illustrative. On a GPU each request runs faster, but the long one still costs about 30 times the short one, because decode time grows with the number of tokens written.

Nothing in the size or shape of the request gave it away. The difference is in a field of the JSON body, max_tokens, and in what the question asks for. A balancer that works on connections never opens the body. It splits the two kinds evenly across the workers.

The result has a name, head-of-line blocking. A lookup that needs 0.8 seconds is sent to a worker that is busy with an itinerary and waits for a place. If it has to wait for the whole 25 seconds it finishes after 25.8 seconds, 32 times later than on an idle worker, while the worker beside it was free. Averaged over an hour the load looks even. Request by request it is not.

Chapter 4 of 14

First fix: ask the workers how busy they are

Better, late, and blind to the prompt

The obvious repair is to stop guessing and ask. Each model server publishes numbers about itself: how many requests are running, how many are waiting, how full its cache memory is. A router can collect these and send each request to the worker with the shortest queue. F5's first AI balancer worked this way. It set a weight for each pool member from requests running, requests waiting and GPU memory in use, on a schedule.

This is a real improvement, and it has two flaws. The numbers are collected on a timer, typically every 15 to 20 seconds. A burst of five agents arrives inside one such interval, so all five are placed using the same stale picture and can land on the same worker. And the numbers describe the worker only. They say nothing about the request, so the router still cannot tell which worker already holds this prompt.

There is a third, quieter problem. A queue length counts requests, and requests are not equal. Take two itineraries waiting on one worker and six flight lookups waiting on another. The first queue is 16,384 tokens of writing and the second is 1,536. At about 328 tokens a second the first takes about 50 seconds to clear and the second under 5. The shortest queue is the slowest one.

Chapter 5 of 14

The prompt already says where it belongs

Blocks of the prompt, matched against what each GPU holds

The missing piece is in the request itself. Reading a prompt is the expensive part of a prompt-heavy request, and a worker that has read the same opening before can skip it, because the result is still in its KV cache. So the picker reads the prompt before choosing. It turns the text into tokens with a tokenizer of its own, cuts them into blocks of a fixed size, and gives each block a fingerprint that depends on everything before it. Two prompts share a fingerprint for block 40 only if their first 40 blocks are the same.

The picker keeps a map from fingerprints to the workers that hold them. The map is kept current by events the workers send whenever they store or drop a block. vLLM publishes them over ZeroMQ and NVIDIA Dynamo over NATS. For a new prompt the picker follows its blocks through the map from the first one and stops at the first block a worker does not hold. That gives, for every worker, how much of the opening is already there.

Take a prompt of 20,000 tokens and blocks of 16 tokens. That is 1,250 blocks. Suppose gpu-2 holds the first 1,200, which is 19,200 tokens and about 5 GB of cache. On gpu-2 only the last 50 blocks, 800 tokens, are left to read. On the other two workers all 20,000 are.

Chapter 6 of 14

Why not always follow the cache

Everyone with the same opening lands on one GPU

Now there is a tempting rule: send every request to the worker that holds its prefix. Try it on the travel planner. All five agents share the same opening, the retrieved documents, and so do the agents of every other user asking about that destination. Under a cache-only rule they all go to the one worker that read those documents first. That worker's queue grows to dozens of requests while the others sit idle. Each request saves a couple of seconds of reading and then waits far longer than that in line.

The rule also feeds itself. The busy worker is still the only one holding the prefix, so it still wins every comparison, and every new request makes it slower. F5's engineers call this a death spiral.

F5 measured it. Qwen3-32B ran on eight H100 GPUs under a workload with a shared prefix, and only the router was changed. With a router that follows the cache alone, the median time to first token was 29 seconds, with more than 100 requests queued on one warm GPU and seven GPUs idle. With the F5 endpoint picker it was 1.2 seconds, about 24 times sooner. The cache-only router had the better hit rate, 81.5% against 76.7%. A router that sees the cache and not the queue can do worse than one that sees neither.

Chapter 7 of 14

Three signals that each mislead

A short queue, a cache hit and a high hit rate

The failures so far have one cause. Each router trusted a single signal. F5's engineers list three beliefs that sound safe and are wrong.

The first is that the worker with the fewest requests waiting is the fastest. A queue length counts requests. A short queue of very large jobs finishes later than a long queue of small ones, as the two queues of 16,384 and 1,536 tokens showed. What matters is how long the line takes to clear.

The second is that a cache hit is always worth the same. Cached blocks can sit in GPU memory, in the host's memory, on a local SSD or in remote storage. A hit in GPU memory costs nothing to use. A hit lower down has to be fetched first. Fetching 5 GB from host memory over a PCIe link of about 64 GB a second takes about 80 milliseconds. From a current PCIe Gen4 NVMe drive at about 7 GB a second it takes about 0.7 seconds, still faster than the 2 seconds it takes to read the prompt again. From a slow tier, such as an older drive or a network volume at 1.6 GiB a second, it takes about 2.9 seconds, which is longer than reading the prompt again. Where the blocks live, and how fast that tier is, decides whether the hit is a gain at all.

The third is that the best router has the highest hit rate. Chasing hits pins traffic to one hot worker, which slows down and keeps winning. The 81.5% hit rate with a 29-second wait was that belief, measured.

Chapter 8 of 14

The signal no router has: how fast each card is

On a mixed pool, an idle tie can park a whole app on the slowest GPU

All three signals above assume that every GPU in the pool is the same card. So do most benchmarks, and so does the introductory course material on llm-d, which pictures a fleet of identical servers. Real pools are often mixed. A cluster grows over years, and newer cards join next to older or smaller ones. The same request takes a different time on each. Decode reads all of the model's weights from memory for every token it writes, so a card with half the memory bandwidth writes tokens at roughly half the speed.

The owner tested this in a lab. Three llm-d inference simulators stood in for a big, a mid-size and a small GPU. The simulator serves the same OpenAI-compatible API and the same metrics as vLLM without loading a model, and its settings fix how long each phase takes. The owner's lab set three of them on each simulator: --prefill-overhead, a fixed cost for every prompt, --prefill-time-per-token, a cost for each prompt token, and --inter-token-latency, the time for each token after the first. The same shared-context chat traffic went through four front doors: HAProxy and Envoy Gateway taking turns, and two endpoint pickers, llm-d's and F5's, each behind a Gateway API InferencePool. Neither picker knew the GPUs differed in speed. On an idle pool the ties went to the slowest GPU, and cache affinity then pinned whole apps there.

An idle pool ties because every signal reads zero. Nothing is waiting, nothing is running, no cache is in use and no prefix matches yet. Time to drain is work waiting divided by tokens per second, and zero work divided by any speed is zero. A fast card and a slow card score the same, and the picker's rule for ties decides. The open reference picker of the Gateway API Inference Extension shuffles the candidates before it sorts them by score, so a tie goes to a random one. That rule does not look at speed, so the slow card wins its share of first requests. F5's engineering deck names the same blind spot in other routers: a card can look least loaded and clear slowest. F5's answer is to rank by time to clear, measured from live tokens per second. That measure needs work flowing before it can see a difference, so it starts from the same tie.

Cache affinity turns one unlucky tie into a lasting cost. The first request of an app lands on the slow card and leaves the app's shared prefix in its cache. Every later request of that app now matches a prefix there and nowhere else, so the cache score favours the slow card. In the owner's lab that match did not come from the workers. The simulators cannot publish vLLM's KV-cache events, so F5's precise prefix-cache routing stayed off, and the picker fell back on remembering which worker it had sent each prefix to. The effect is the same: the picker's record says the slow card holds the app's prefix. The load score only pushes the app away once the slow card's line is long enough to outweigh the hit. With illustrative speeds of 40 milliseconds a token on the small card and 10 on the big one, a 256-token answer takes about 10.2 seconds on the small card and about 2.6 seconds on the big one. The app pays four times the wait while the big card sits idle.

An operator can keep ties from crossing card types. Put each kind of GPU in its own pool. NVIDIA's GPU feature discovery labels every node with its card, in nvidia.com/gpu.product. A Deployment per card type, with a nodeSelector on that label, and an InferencePool whose selector matches only that Deployment's Pods, makes every tie a tie between equal cards. Which pool a request goes to is then a rule above the picker, by model name, tenant or price. The three workers in this chapter's scene stand for the owner's mixed lab pool. In the cluster the site's other lessons share, northlight-eu, the Deployment qwen3 has two Pods, qwen3-6f7d9c8b4-x7k2p on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t on gpu-node-2. When both nodes carry the same kind of card, those two Pods are equals and this failure cannot happen there.

Chapter 9 of 14

Warm cache when there is room, another GPU when there is not

The picker weighs both for every request

The endpoint picker keeps both pictures and weighs them for each request. From the prompt it knows where the prefix is and, because it has counted the tokens, how big the job is. A prompt of 20,000 tokens and a lookup of 100 are different amounts of work and it treats them so. From the workers it knows how fast each one is producing tokens right now, which it turns into an estimate of how long that worker's line will take to clear.

Then it decides in a fixed order. Workers that are already saturated are set aside first, before any matching, so a full worker cannot attract more work by being warm. Among the rest, the warm one wins while it has room. When it fills, the overflow goes to an idle worker, which reads the prefix once and is then warm too. From then on two workers can take that destination's requests.

F5 describes four ideas behind the scoring. Load is counted in tokens. Capacity is a time to drain, taken from live tokens per second. A cache hit is priced by the tier it sits in. And the point where waiting for the warm worker costs more than reading the prefix again is worked out from what the hardware is doing, with no weight to tune by hand. In the example below that point is passed: 36 seconds of waiting against 2 seconds of reading.

Chapter 10 of 14

Inside the picker: five steps for every request

Admit, prepare, score, pick, then leave a note

F5 describes its picker as a pipeline that runs once for each request. The first step is admission. The picker checks whether the pool is saturated, and if no worker can take the request it refuses at once instead of adding to a line that is already too long. The second step prepares the data: the prompt is tokenized into token ids, which gives both the size of the job and the blocks to look up.

The third step scores. Thirteen scorers each give every worker a number between 0 and 1, and the numbers are combined into a weighted sum per worker. Ten of them measure load and pressure: KV cache use, queue, running requests, GPU utilization, memory utilization, framebuffer, power, temperature, token-weighted load and a classifier for hot workers. Three measure what can be reused: the prefix cache, a loaded LoRA adapter and blocks that are active right now. The second group is what a balancer working on pool members cannot see.

The fourth step picks. It uses a hot and cold ranking of the workers where it applies, and otherwise takes the highest score, or draws at random in proportion to the scores. The last step runs before the request leaves. The picker reserves the prefix blocks for the worker it chose, so the next request in the same burst already sees them, and it writes the worker's address into a header.

Chapter 11 of 14

What an operator can read

Fresh numbers from the workers, and a few from the picker

The picker reads the same three numbers the metric router did, far more often. In the F5 picker each worker's /metrics page is read about every 50 milliseconds, where a monitoring system reads it every 15 to 20 seconds. That is 300 to 400 times fresher. The numbers are vllm:num_requests_waiting, vllm:num_requests_running and vllm:kv_cache_usage_perc. A worker whose cache use crosses a threshold counts as saturated. The value F5 generates for that threshold is 0.99.

Two counters on each worker tell an operator whether routing is finding the cache. vllm:prefix_cache_queries counts the prompt tokens that were looked up and vllm:prefix_cache_hits counts those found. If a worker reports 20,000,000 queried and 14,400,000 hit, its hit rate is 72%. The histogram vllm:time_to_first_token_seconds shows what callers felt. Read the two together. A rising hit rate with a rising time to first token is the pile-up from the chapter Why not always follow the cache.

The picker has failure signs of its own. If the tokenizer named in its configuration does not match the model the pool serves, it cannot count tokens, and a counter of failed encodings rises with every request. Token-weighted scoring then runs blind while requests are still served. If the workers send no cache events, the picker falls back to remembering where it sent each prefix, which is a guess.

Chapter 12 of 14

When the worker is a NIM

The same load signals behind another path and, sometimes, other names

NVIDIA NIM packages a model and an inference engine into one container that serves an OpenAI-compatible API. Inside, the engine is vLLM or SGLang, depending on the image. To a picker a NIM is a worker like any other, with two differences that quietly break a picker set up for plain vLLM. NIM serves its metrics at /v1/metrics, where vLLM serves them at /metrics. And NIM passes the engine's own Prometheus metrics through without changing them. A vLLM-based NIM reports vllm:num_requests_waiting, vllm:num_requests_running and vllm:kv_cache_usage_perc. An SGLang-based NIM reports the same three ideas as sglang:num_queue_reqs, sglang:num_running_reqs and sglang:token_usage.

A picker reading the wrong path or the wrong names does not stop. It keeps routing with empty load scores. The open reference picker of the Gateway API Inference Extension, release v1.0.0, reads /metrics unless --model-server-metrics-path says otherwise. It looks for the queue in vllm:num_requests_waiting unless --total-queued-requests-metric names another metric, and for cache use in vllm:gpu_cache_usage_perc unless --kv-cache-usage-percentage-metric does. Current vLLM calls that last number vllm:kv_cache_usage_perc and no longer has the older name in its metrics code, so even a plain vLLM worker needs the flag checked. The owner's lab met the same class of problem with NVIDIA Dynamo's simulated workers. F5's picker needed an override to match their metric labels, and with the wrong KV event topic it received no cache events at all, so prefix routing quietly became load-only routing while every status stayed green.

NIM also answers two health checks. /v1/health/live returns 200 as soon as the container runs, before the model is loaded. /v1/health/ready answers only once the model is loaded and ready for inference, and NVIDIA's Helm chart points its startup probe at it. A Pod should join the pool on readiness. Joined on liveness, a worker still loading the 34.3 GB of the FP8 build, about three minutes of work, would be offered prompts it cannot answer.

F5's deck on BNK and NVIDIA lists routing across models on NIM statistics as part of the joint work, next to Dynamo's runtime signals and KV cache integration. Routing across models happens in two steps. The model a caller wants is in the model field of the JSON body. The Gateway API Inference Extension's body-based router reads that field and copies it into a header, X-Gateway-Model-Name, so ordinary route rules can match it and choose the model's InferencePool. That pool's own picker then reads its NIMs' statistics to choose the worker. F5's slide draws the loop the same way: telemetry from the inference cluster updates the routing rules, and the new rules are applied to the next requests. Its inputs are pending requests, KV cache, GPU metrics and VRAM utilization, and they add up to one routing decision, a warm KV cache where one exists and a cold one when it must.

Chapter 13 of 14

What the difference came to

The same eight GPUs, 3.2 times the work

F5 has shown the outcome in public. Eight workers served one model. The load was 200 requests at a time, each with a prompt of 20,000 tokens, and F5's slide says the load exceeded the fleet's KV cache by 24%, so something always had to give. The slide does not say how F5 counted that. A plain product of 200 × 20,000 tokens at about 260 kB a token would come to about 1 TB, far more than 1.24 times the cache, so F5's figure must count something narrower, such as the data the load kept coming back to. Two routers that both use cache and load served the same eight GPUs under that load. With the F5 endpoint picker the pool completed 5,623 requests. With the other router it completed 1,738. Once the caches were warm, the first token came back in 248 milliseconds against 3.56 seconds. The eight GPUs were the same. The slide names the two routers, F5 BIG-IP Next for Kubernetes with its endpoint picker and Envoy AI Gateway, and does not say where each one ran. What decided the outcome was where each request was sent.

The requests asked for 128 tokens each, so the test is heavy in prefill, the phase a warm cache removes. Each measured window lasted 240 seconds. Over that window 5,623 requests is about 23 a second and 1,738 is about 7.

F5 gives three reasons why its picker did better than another router that also uses cache and load. It has a tokenizer built in, so it knows that a prompt of 20,000 tokens is a different job from a lookup of 100. It tracks each GPU's live tokens per second to estimate the wait. And it skips saturated GPUs before it looks for a warm cache, with nothing to tune.

The slide also plots the 240 seconds as a time series. After warm-up the F5 line holds flat latency, and the Envoy AI Gateway line keeps swinging up and down, which F5 calls thrashing. The slide states no values for the swings, but its four panels have axes, and at full size rough values can be read off them. Neither router completes a request until about 45 seconds in. The mean time to first token, over a 10 second rolling window, climbs to about 38 seconds on both before the F5 line drops to near zero by about 55 seconds and stays at 248 ms. The Envoy AI Gateway line falls to about 5 to 10 seconds, rises again to about 17 seconds near 125 seconds and about 11 seconds near 155 seconds, and ends at 3.56 seconds. Its 99th percentile reaches about 90 seconds near the 95 second mark and ends at 11.3 seconds, against 326 ms for F5. Output tokens per second hold near 3,700 for F5 and wander between about 1,000 and 1,500 for Envoy AI Gateway, ending at 4,017 and 1,715. The shape fits what happens when the working set is bigger than the cache. A worker evicts blocks to make room, a later request needs them and pays a full prefill of 20,000 tokens, the line behind it grows, it drains, and the cycle starts again. A picker that keeps each prefix on the worker that still holds it, and keeps full workers out, avoids most of those refills, so its time to first token stops moving. That reading is this lesson's explanation of the chart. F5 states only the shapes and the end values.

F5 frames the result as a higher token revenue ceiling on the exact same 8 GPUs. An hour is 15 windows of 240 seconds. In tokens, 5,623 requests a window of 20,128 tokens each, 20,000 in and 128 out, is 84,345 requests, about 1.70 billion tokens an hour. 1,738 requests a window is 26,070 requests, about 525 million tokens an hour. A provider that bills by the token can sell at most what its GPUs push through, so the ceiling moves with throughput, 3.2 times here. Revenue moves less than that when cached input is billed lower. Anthropic's API, for example, bills a cache read at a tenth of the base input price for most models.

The owner's own lab points the same way on a smaller scale. On simulated GPUs, the two picker front doors, llm-d's and F5's, completed 3 to 5 times the requests of round robin on the same workers. A second test replayed 20,000 requests from a public production trace of prompt prefixes over four simulated GPUs. Round robin recomputed 39% of the prefill work, and prefix and load routing recomputed 10%, about a quarter. In that replay, prefix-aware placement with 24 GiB of KV cache per GPU beat round robin with 96 GiB, four times the memory. A third, separate run put F5's real endpoint picker in the path, with 1,000 prompts on simulated GPUs. There 95.5% of prefill was saved against 83.3% with round robin, so the picker left 4.5% to compute where round robin left 16.7%, again about a quarter, and no request failed open. The two runs used different prompts, so round robin's 39% in the replay and its 16.7% with the real picker are different workloads and do not contradict each other. These are simulators. They show where requests went and how much prompt had to be read again, and say nothing about real latency. The baseline also differs: round robin in the owner's runs, another cache and load router in F5's.

Chapter 14 of 14

The gain depends on how full the cache is

Close when everything fits, far apart when it does not

One headline number hides a slope. F5 ran the same comparison at three levels of pressure on the cache, with the same GPUs, the same model and the same 240-second window. Pressure is the cache memory the prompts in play need, divided by what the fleet has. At 0.46 times the fleet's cache everything fits, and the F5 path completed 13% more work than the open-source gateway it was tested against. At 0.93, near the edge, it completed 30% more. At 1.24, where blocks must be evicted, it completed 102% more. Over all twelve load points the total was 1.32 times.

At the highest pressure the mean time to first token was 61% lower and the mean inter-token latency 38% lower. The peak ratio of requests completed at a single load point, with no shared prefix, was 3.24. That is the ratio of 5,623 to 1,738 in the last chapter, and both are labelled 24% over the fleet's cache, so they are most likely the same run, though the deck does not say so. F5's own summary is that inside the cache the choice of gateway barely matters, and past it the choice decides how much of the fleet keeps working.

Earlier tests against plain round robin show what else moves the gain. It grows when answers are short, because prefill is then a larger share of each request. It grows with more requests at once and with a longer shared prefix. With no shared prefix the first token still comes sooner, and throughput hardly changes when the load is already even. That finding is against round robin at loads that fit in cache. The 3.24 peak above also had no shared prefix, and there the gain came from avoiding saturated workers and cache eviction. No shared prefix means the prompts did not open with common text. A warm cache can still matter there, because a working set that exceeds the cache by 24% implies the same prompts coming back, and a worker that still holds one serves it without a new prefill. The slide of 5,623 against 1,738 does not call its workload shared-prefix. The shared-prefix label in this lesson belongs to the other slide, the cache-only router against the picker. Reading the warm cache in the heavy run as repeated whole prompts is this lesson's inference.

F5's AI Gateway workflow deck adds one more figure: up to 40% reduction in cluster idle time. It sits under the heading Maximized GPU ROI and is credited to three things together, semantic cache offload, prefix-affinity placement and running prefill and decode on separate workers. The deck gives no method, no baseline and no workload, so it is a claim, and arithmetic is the way to weigh it. Idle time and work done are different measures. Suppose a pool's GPUs sit idle 30% of the time. 40% less idle leaves 18%, so busy time rises from 70% to 82%, which is 1.17 times, about 17% more. That is close to the 13% the picker added when everything fit in cache, and far from the 102% at 1.24 times the cache. The heavy run shows why. With 200 requests at once on eight GPUs, both pools were most likely busy nearly all the time, so neither had much idle time to cut, and still one completed 3.2 times the requests of the other. The difference was in what the GPUs were busy with. A prefill recomputed after an eviction counts as busy and produces nothing new. Less idle time helps a pool that is underused, with bursts and gaps. Less wasted work helps a pool that is full. The picker results in this lesson are mostly the second kind.

What to keep

Know the prompt, know the line, then choose

Choosing a GPU went through four stages. Round robin takes turns and cannot see that one request is thirty times another. Routing on the workers' own metrics sees queues, up to 20 seconds late, and still cannot see the prompt. Following the cache alone sees the prompt and ignores the queue, and sends a whole burst to one worker. The endpoint picker reads the prompt, tracks which worker holds which part of it, estimates how long each worker's line will take, and sets full workers aside before it looks for a warm one. On the same GPUs that was the difference between 1,738 and 5,623 requests.
