Kubernetes underneath

The same path in eBPF

How Cilium does with programs and maps what a bridge and iptables did before

The earlier lessons moved a packet with a bridge, a tunnel device and lists of iptables rules, and the last one dropped packets with rules written by a policy agent. Cilium does the same jobs with eBPF: small programs that the kernel checks and then runs at fixed points on a packet's way, reading shared tables called maps. This lesson puts Cilium into the same cluster and follows the same calls. The cluster of the last lesson is rebuilt with Cilium as its network plugin. Flannel and the kube-network-policies agent beside it are gone, and kube-proxy is removed as well, because Cilium takes over all three jobs. Read the scene with three changes. The box marked Kernel rules now holds eBPF programs and maps. cilium-agent sits where kube-proxy sat. The tunnel device is Cilium's own, cilium_vxlan. The Pods are the same three: client, web-1 and web-2, with the policy of the last lesson still in place. Along the way the lesson keeps apart what is plain Linux and what is Cilium, gives the limits and defaults that matter in operation, and ends with what eBPF leaves to a proxy and with netkit, the device that replaces the veth pair. Model servers behind a gateway work the same way.

Chapter 1 of 12

A program the kernel checks first

This part is plain Linux and has nothing to do with Cilium yet

eBPF is a part of the Linux kernel. It is older and wider than Cilium. An eBPF program is a small piece of code that a privileged process hands to the kernel with the bpf system call, as bytecode. Before the kernel accepts it, a verifier inspects it. First it checks the program's structure and rejects unreachable instructions and loops that might never end. Then it follows the paths through the program, simulating each instruction and tracking what every register and stack slot holds. Reading a register that was never written is rejected. So is a memory access outside its bounds. A program that passes is turned into machine code by a just-in-time compiler and attached to a hook. From then on the kernel runs it every time that hook is reached.

The program works with eleven registers, r0 to r10. r10 is read-only and holds the frame pointer, and a program has 512 bytes of stack below it. The verifier does not walk every possible path. When it reaches an instruction in a state that is contained in one it has already checked there, it prunes the branch. Its budget counts instructions explored during the check: 1 million, which the kernel's own Q&A says means a program of at most 1 million no-op instructions. Unprivileged programs are held to 4096 instructions. One program can hand over to another with a tail call, at most 33 in a row.

The Q&A is frank about one thing. The only way to know that a program will be accepted is to try to load it. In return, the kernel developers promise that a later kernel accepts every program an earlier one accepted.

Who may load at all is a setting. Without CAP_SYS_ADMIN or CAP_BPF, the bpf call returns EPERM unless the sysctl kernel.unprivileged_bpf_disabled is 0. Set to 1, it cannot be undone without a reboot. The JIT has a sysctl too, net.core.bpf_jit_enable, and Cilium's list of required kernel options includes CONFIG_BPF_JIT=y.

Chapter 2 of 12

Three places to attach

The network card, each Pod's cable and the socket call

The kernel offers many hooks, and Cilium's datapath uses a few on the network path. XDP sits in the driver of a network card and runs a program on a packet as it is received, before the kernel has done any other work on it. tc, short for traffic control, sits on any network interface in both directions, ingress and egress, and runs after the kernel has started to process the packet. Socket hooks are attached to a cgroup, the kernel's grouping of processes, and run when a process makes a socket call such as connect, before any packet exists. Cilium attaches a tc program to the node end of every Pod's veth pair, so everything a Pod sends meets a program first. It attaches tc programs to the node's network card, optionally with XDP, and socket programs to the root cgroup.

Cilium's own description places the tc hook before the layer 3 processing of the stack, with access to most of the packet's metadata. XDP is cheaper still. The 2018 paper that introduced it measured 24 million dropped packets per second on one core, which works out to about 42 nanoseconds a packet. An XDP program ends with one of five verdicts. XDP_ABORTED, value 0, is the error case. The others drop, pass, send back out of the same card, or redirect.

The hooks have kernel versions. Socket address hooks such as connect4 exist from 4.17. tc gained a newer way to attach, tcx, in kernel 6.6, and libbpf marks the old classifier section as legacy. Cilium itself needs Linux 5.10 or later, or an equivalent such as 4.18 on RHEL 8.10.

The kernel offers two more socket hooks, and older Cilium releases used them. A socket operations program on the root cgroup watched TCP connections reach the ESTABLISHED state, and for a peer on the same node a message program handed data straight to the other socket. That acceleration, switched on with sockops-enable, was deprecated in Cilium 1.13 and removed in 1.14, and the bpf/sockops directory is gone from the source since then. The page eBPF Datapath: Introduction on docs.cilium.io still describes it, so treat that part of the page as out of date. On top of the hooks Cilium creates its own interfaces on each node: cilium_host, cilium_net and, in tunnel mode, cilium_vxlan.

Chapter 3 of 12

Maps are the tables everyone shares

The agent writes them and the programs read them

A program that runs for one packet and then ends cannot remember anything by itself. State lives in eBPF maps. A map is a key and value store inside the kernel. Programs read and write it through helper calls, and processes outside the kernel reach the same map through a system call. Cilium is built around this split. cilium-agent, one on each node, watches the API server and writes what it learns into maps. The programs on the packet's path look things up. Cilium keeps a map of the endpoints on the node, a map from IP address to identity for the whole cluster, maps of Services and their backends, a policy map for each endpoint and a connection tracking table. Every map is created with a fixed upper size.

The kernel offers several kinds. A hash map, available since kernel 3.19, fills up to the max_entries given when it is created and then refuses new entries. An LRU hash, since 4.10, evicts the least recently used entry when it is full, so it never refuses and quietly forgets. A longest prefix match trie, since 4.11, finds the most specific prefix for a key, the way a routing table does. Cilium uses all three.

The defaults are numbers an operator should know. The agent's flags give connection tracking 524288 TCP entries and 262144 for other protocols. The Service map holds 65536 entries, and the documentation translates that into about 3000 Services of type ClusterIP or NodePort across all clusters. Each Service takes backends times ports entries: web takes 2 × 1 = 2. A policy map holds 16384 entries for each endpoint.

The connection tracking numbers are rarely what a node gets. The flag --bpf-map-dynamic-size-ratio sizes the large maps from the node's memory when the agent starts, and it is on by default: 0.0025 in the agent and in the Helm chart, which is 0.25 percent of memory. It covers the connection tracking maps, the NAT maps and a few others, with at least 131072 connection tracking entries. The documentation's table gives a node with 30 GiB 284560 entries, below the fixed 524288, a node with 60 GiB 569120, and one with 240 GiB 2276480. A GPU node with hundreds of GiB of memory therefore gets millions. The fixed numbers apply when the ratio is set to 0. The Service map is not among the dynamic maps and stays at 65536.

Chapter 4 of 12

A number for a set of labels

Cilium's own idea: policy follows identity, never the address

A kernel rule that matches addresses cannot match a label. The policy agent of the last lesson therefore had to track Pod addresses and update its view on the nodes whenever a matching Pod started or stopped. Cilium separates policy from addresses. Every Pod it manages is an endpoint, and every endpoint gets an identity: a number that stands for the Pod's set of labels. All Pods with the same labels share one number in the whole cluster, so web-1 and web-2 have one identity between them. The agents agree on the numbers through a shared store. The IP cache map records which address has which identity. When a packet travels to another node through the tunnel, the sender's identity rides in the tunnel header, so the receiving node knows who is calling.

The first numbers are reserved. 0 is unknown, 1 the node itself, 2 the world outside the cluster, 3 an unmanaged Pod started before Cilium, 4 health checks, 5 init, 6 remote nodes, 7 the kube-apiserver and 8 Cilium's ingress. Identity 0 also has a meaning in the datapath, where it stands for any identity in a policy map. Seen in Hubble output, it means an identity could not be found. Identity 5, init, belongs to an endpoint whose labels are not known yet, as during start-up. Until its labels arrive, a new Pod is nobody that a policy names.

The ranges are fixed. 1 to 255 are reserved, 256 to 65535 are the identities of this cluster, and the numbers up to 2^24 minus 1 belong to identities of other clusters. With ClusterMesh, 8 bits carry the cluster's id, which is why one cluster has 16 bits for its own. Numbers from 2^24 up are identities for CIDRs, such as those of an ipBlock. They are local to one node, never travel in a packet, and can differ between nodes. A changed label is not used at once. The agent waits --identity-change-grace-period, 5 seconds by default.

Chapter 5 of 12

The policy check is a few lookups

The same NetworkPolicy, kept in a map on the node of web-2

The NetworkPolicy from the last lesson is still in the API server, unchanged. Cilium implements the standard NetworkPolicy API, so nobody rewrites it. The agent on node-2 resolves the policy's selectors to identities and writes the result into the policy map of the endpoint web-2. The map gets an entry for each allowed identity and port. The entry for Pod client is identity 23701, TCP, port 8080. Now Pod client sends a request. The program on its veth pair looks up the destination, learns that it lives on node-2 and sends the packet into the tunnel with identity 23701 in the header. On node-2 the policy program of the endpoint builds a key from that identity, the protocol and the port, and finds it in the map. The packet is delivered, and replies pass on the connection tracking entry.

On current Cilium the policy map is a longest prefix match trie, named with the prefix cilium_policy_v3_. Its key holds a prefix length, the identity, the direction, the protocol and the destination port. The port can be a prefix, so a range of ports takes a few entries and port 0 stands for all ports. The protocol can be left open only when the port is too. The value holds flags, one of which marks a deny, and a proxy port for traffic that goes to a proxy.

The datapath does two lookups: one with the caller's own identity and one with an aggregated identity that stands for any caller. If several entries fit, a deny wins over an allow, then the longer prefix, then the entry for the specific identity. With no entry at all the verdict is DROP_POLICY, and a matching deny gives DROP_POLICY_DENY. The count of lookups is fixed, whatever the number of rules: two, plus a fallback when neither finds an entry. Where iptables walked a list, Cilium asks a map a small, fixed number of questions.

Chapter 6 of 12

Tunnel or native routing

The tunnel carries the identity, native routing leaves the packet as it is

Cilium's defaults in code are routing mode tunnel and tunnel protocol vxlan, on UDP port 8472. Geneve is the other choice, on UDP port 6081. The agent flag --tunnel-port changes either. In tunnel mode every Pod packet between nodes, with its own inner Ethernet header, is wrapped in an outer IP, UDP and VXLAN header. Counted against the MTU that adds 20 + 8 + 8 + 14 = 50 bytes, where the 14 is the inner Ethernet header. The outer Ethernet header, 14 more bytes on the wire, does not count against the MTU. The identity of the sender travels in the 24-bit network id of the VXLAN header, which is why cluster identities stay below 2^24.

The 50 bytes come out of the packet size the Pods can use. On a network with an MTU of 1500 bytes, the inner IP packet can be at most 1450 bytes. The routing page puts the trade-off this way: 50 bytes for each 1500 bytes, or 50 bytes for each 9000 bytes with jumbo frames. For model servers that move large answers or tensors between nodes, that is an argument for jumbo frames or for no tunnel at all.

Native routing is turned on with routing-mode: native. ipv4-native-routing-cidr names the range that is routed without masquerading, and auto-direct-node-routes: true lets each node install routes to the Pod ranges of the others when they share one layer 2 network. Otherwise the network itself must know the Pod ranges, for example from BGP, as the lesson on Pod networks without a tunnel shows. With no tunnel header, the receiving node finds the caller's identity by looking up the packet's source address in its own IP cache.

The nodes must also reach each other on a few ports. UDP 8472 for VXLAN, TCP 4240 for cilium-health, the agent's checks of node to node and endpoint reachability, TCP 4244 for the Hubble server on each node and TCP 4245 for Hubble Relay.

Chapter 7 of 12

A Service call is settled at the socket

The backend is chosen inside connect, before any packet exists

kube-proxy's iptables rules handle a Service on the packet's path. The first packet of a connection is matched against the Service rules and its destination is rewritten to a Pod. Connection tracking then rewrites every later packet, in both directions. Cilium moves the decision to the moment a program calls connect. A socket program attached to the root cgroup runs inside that call. It looks up the destination in the Service map, picks a backend and connects the kernel socket straight to the backend's address. The application still believes it is talking to the Service. No packet ever carries the Service address, so nothing has to be translated on the way out or on the way back. Here Pod client calls the Service web on port 80, and its first packet already names web-2 and port 8080.

The backend is chosen at random by default. The flag --bpf-lb-algorithm also offers maglev, a consistent hash that keeps a flow on the same backend across nodes. Its table size defaults to 16381, which the documentation calls suitable for at most about 160 backends. With sessionAffinity: ClientIP on the Service, the affinity lasts three hours by default and is renewed by each request.

Deciding inside connect has a price. A socket that stays open keeps its backend. If that backend is deleted, the socket would go on sending to it, so the agent forcefully closes sockets connected to deleted backends. That needs the kernel options CONFIG_INET_DIAG, CONFIG_INET_UDP_DIAG and CONFIG_INET_DIAG_DESTROY.

A terminating backend is used for new connections only if no active backend is left and it is still serving, and Cilium counts such events in k8s_terminating_endpoints_events_total. The socket programs need cgroup v2. Cilium mounts it itself, or is pointed at an existing mount with cgroup.hostRoot.

Chapter 8 of 12

kube-proxy leaves, and its chains with it

A lookup takes the same time whatever the number of Services

With Services handled in maps, kube-proxy has nothing left to do. Cilium is installed with kubeProxyReplacement=true and kube-proxy is never deployed. The agent must then be given the API server's real address, because the Service address it would normally use is one that kube-proxy used to provide. The gain is in how the cost grows. In iptables mode kube-proxy writes one top-level rule for every Service, and the kernel tests the first packet of each new connection against them in order. That time grows with the number of Services, and so does the time to rewrite the rules after a change. A lookup in a hash map takes about the same time for ten Services and for ten thousand. This cluster has a handful of Services and would never feel the difference. A platform with a Service for every model and every tenant does.

Traffic that comes from outside, to a NodePort or a LoadBalancer Service, is translated per packet at the network card. --bpf-lb-mode decides how: snat, the default, sends the request on with the node's address as source, so the answer comes back the same way. dsr, direct server return, lets the backend's node answer the client directly. hybrid uses dsr for TCP and snat for UDP. --bpf-lb-acceleration native moves this work into XDP, and it is disabled by default. Masquerading can be eBPF too. The agent's flag --enable-bpf-masquerade defaults to true, but a Helm install, as here, writes the chart's value into the agent's configuration: bpf.masquerade defaults to false in the 1.20 chart and earlier, so iptables still masquerades unless bpf.masquerade=true is set. The chart on the main branch, for 1.21, turns it on by default. The documentation recommends it with the eBPF NodePort, because eBPF and iptables address translation could otherwise choose the same ports.

The replacement has documented limits. SCTP is supported only in a few basic cases, and TCP and UDP are fully supported. NFS and SMB mounts to a Service address can break with socket LB on kernels without certain fixes. A hostPort that overlaps the NodePort range is ignored with a warning in the agent's log. cilium-dbg service list shows the Services the agent has programmed.

Chapter 9 of 12

Hubble shows the drop that was silent

The caller still times out, and now there is a record

In the last lesson a denied call left nothing in the Kubernetes API. The caller timed out, and only the policy agent's own log could say why. With eBPF every verdict is reached in a program that can report it. Now web-1 calls web-2 on port 8080 again. The drop also moves. The agent of the last lesson queued web-1's SYN on node-1, because web-1 is selected too, and dropped it there. Cilium checks egress at the source and ingress at the destination, and web-1 has no egress rule against it, so this time the SYN crosses the tunnel. Its SYN arrives on node-2 with identity 31544 in the tunnel header, the number web-1 shares with web-2. The policy program of web-2 looks for that identity with TCP and port 8080 in the policy map and finds no entry. The packet is dropped, and so is every copy web-1 sends after it. web-1 again gets only a timeout. This time the program also emits an event. Hubble, which runs inside cilium-agent on every node, turns such events into flow records with Pod names, identities and a verdict. Hubble Relay gathers the records of all nodes, and the hubble command or the Hubble UI reads them.

The events travel from the kernel to the agent through a shared buffer, which the monitor reports as 64x4096 of shared memory: 64 pages of 4096 bytes. Hubble keeps the flows in a ring buffer in user space. Its size is --hubble-event-buffer-capacity, one less than a power of two, 4095 by default and at most 65535, on each node. When it is full the oldest flows are overwritten, so on a busy node it holds a window of the last seconds or minutes. It is no archive.

The hubble command talks to the Observer API, a gRPC service with GetFlows, GetNodes, GetNamespaces and ServerStatus, served on a local socket or through Relay. In a flow line, Policy denied is the reason and DROPPED the verdict. The caller's retransmitted SYNs show up again as further lines, as the documentation's own example shows a second apart. Whether drops are reported at all is a setting, --bpf-events-drop-enabled, true by default.

Chapter 10 of 12

When maps fill and counters climb

Every drop has a numbered reason, and every map a pressure

A dropped packet in Cilium always carries a reason, and the reasons are numbered. Codes below 130 are not drops. 133 is Policy denied, the drop of the last chapter. 181 is a drop by a deny rule. 155 is CT: Map insertion failed. 158 means a Service has no backend. 169 means the routing lookup in the kernel's forwarding table failed. 171 is an invalid identity. 203 means the endpoint's policy program is not available.

Code 155 is the one that looks like a mystery. When the connection tracking table is full, new connections cannot get an entry and are dropped, though no policy forbids them. The troubleshooting guide names the sign: if connectivity fails and cilium-dbg monitor --type drop shows xx drop (CT: Map insertion failed), the table is likely filling up. A garbage collector removes stale entries on its own schedule. With --conntrack-gc-interval left at 0 the interval adapts: longer when few entries are collected, shorter when many are. Its starting value is 5 minutes. The lifetimes are defaults of the agent: 2 hours 13 minutes 20 seconds for an established TCP connection, 1 minute while it is being set up, 10 seconds after FIN and 1 minute for other protocols.

The metrics make this visible before it hurts. bpf_map_pressure gives each map's fill as a ratio of its configured size, and values near 1 are a warning. drop_count_total counts drops by reason and direction, so a rise in CT: Map insertion failed shows apart from Policy denied. policy_implementation_delay measures the seconds between a policy change and its arrival in the datapath, which is the number the NetworkPolicy API cannot give. For a lost path between nodes, cilium-health status --verbose comes first. For a whole report, cilium sysdump collects state from every node.

Chapter 11 of 12

Modes, deny rules and the proxy

What the agent can be told, and where eBPF hands over

Cilium follows the NetworkPolicy model by default: an endpoint has unrestricted access until a policy selects it, and from then on only what is allowed passes, separately for each direction. The agent setting enable-policy, Helm value policyEnforcementMode, can change that. default is the model just described. always enforces policy on every endpoint, even one that no rule selects, so a Pod with no policy can talk to nobody. never turns enforcement off, even for selected endpoints. There is also an audit mode, --policy-audit-mode, which evaluates policy without dropping, a way to try a policy before it bites.

Unlike the NetworkPolicy API, the policy map has a deny flag, and a deny entry wins over any allow. The standard NetworkPolicy has no deny, so these entries come from Cilium's own policy types or from ClusterNetworkPolicy, which Cilium supports from release 1.20. Cilium's page names the version v1alpha2. The network policy project's release v0.3.0 of November 2026 made v1beta1 the stored version and still serves v1alpha2 with the same schema.

An ipBlock behaves differently here. By default Cilium's ipBlock rules do not match addresses inside the cluster, such as Pod or node addresses. A policy that allowed a Pod range by CIDR under another plugin stops matching under Cilium unless --policy-cidr-match-mode is set to pods or nodes.

eBPF works on addresses, ports and identities. It does not hold HTTP/2 state, reassemble request bodies or read JSON, and it cannot see inside TLS. Cilium hands layer 7 rules to an Envoy proxy. The policy map's value has a proxy port for this, and an entry with a proxy port sends the connection to the proxy before it reaches the Pod. For model servers this is the same split the owner's research draws: limits on which identity may reach port 8000 belong in eBPF, and checks on prompts, tokens and tool calls belong in a proxy such as a gateway.

Chapter 12 of 12

netkit, a cable with a program inside

The veth pair can be replaced by a device built for eBPF

Every Pod in this lesson is joined to its node by a veth pair, and Cilium's program sits on the node end. A packet leaving the Pod crosses into the node, waits in the per-CPU backlog queue, and only then meets tc and the program. netkit is a Linux network device built to remove that wait. It was merged in kernel 6.7 and is plain Linux, though engineers from the Cilium project wrote it and Cilium was the first to use it. Like veth it is a pair, with a primary end on the node and a peer end in the Pod. The eBPF program runs inside the device's transmit path and can pass, drop or redirect the packet before the node's stack is involved. The Pod's side cannot change or detach the program, so a container with CAP_NET_ADMIN cannot remove its own policy.

libbpf names the attach points netkit/primary and netkit/peer. Cilium lists netkit among its features that need kernel 6.8 or later.

The owner tested netkit on a GPU server with kernel 7.0, in a throwaway container. A 40-line program dropped ICMP and passed the rest. Ping from the netkit Pod was blocked, and the program's counter showed exactly 3 drops for the 3 pings. TCP through the same device carried 117 Gbit/s while the program inspected each of 668 thousand packets. That figure comes from the demo, a single transfer with the program attached. A separate benchmark then compared the two devices, three runs each, and its numbers are the ones to use for netkit against veth. The owner's note does not say why the single demo run came out faster, so the gap between 117 and 107 is no measure of what the program costs. In the benchmark, measured from host to Pod, one TCP stream reached 103 Gbit/s over veth and 107 Gbit/s over netkit, about 4 percent more and steady across runs. Four streams gave 382 and 386 Gbit/s, within noise. Ping took 0.024 and 0.025 ms. The larger gain is expected when the program redirects straight to another Pod or the network card, which the test did not measure.

The test found practical traps. iproute2 6.1 cannot create netkit devices, 6.7 or later is needed. Even in layer 3 mode the program sees a 14-byte header of zeros before the IP header, so the protocol byte sits at offset 14 + 9 = 23.

What to keep

What is Linux and what is Cilium

Two things were at work in this lesson. eBPF is the kernel's part: programs that are verified before they run, within fixed limits, a compiler, maps of fixed size, and hooks at the network card, at every interface and at socket calls. netkit adds a device with the program inside. Any project can use these. Cilium is one way of using them for a Kubernetes cluster. Its agent on each node turns Pods, Services and policies into map entries. Its programs at each Pod's veth pair enforce policy by looking up a number that stands for the caller's labels, in a fixed small number of lookups. Its socket programs settle Service calls inside connect, which is why kube-proxy can go. Hubble reads the events the programs emit, so a dropped packet has a record and a numbered reason. Layer 7 checks go to Envoy. Put model servers behind a gateway and the same maps do the work: the gateway's identity is the one entry in each model server's policy map.
