BNK and gateways

What leaves the factory

Egress: giving each tenant's outbound traffic one address, one policy and one log

Most of this site is about traffic coming in. A model server and the agents around it also call out, all day: to object storage or a model registry for weights, to an image registry for images, to a commercial model, to a database, to a monitoring service. In a plain Kubernetes cluster that outbound traffic leaves wearing the address of whatever node the Pod happens to be on. To the firewall at the other end every tenant and every application look the same, and the address changes when a Pod moves. This lesson shows that problem with two tenants, then steers each tenant's outbound traffic through BNK so it leaves from one address of its own, under a policy of its own.

Chapter 1 of 14

A model server calls out

Tenant A's weights are in tenant A's storage

Tenant A runs its own model on GPU workers in this factory. The models the factory itself serves sit in the factory's own object storage, behind BIG-IP. Tenant A's weights are different: they are tenant A's property and they stay in an object store that tenant A runs elsewhere, behind tenant A's own firewall. Every time one of its workers starts, it has to fetch 34.3 GB from there, the size of Qwen3-32B in its official FP8 build, Qwen3-32B-FP8. That store is not open to the world. Its firewall lets in only the source addresses on its list, and today that list holds one address, 203.0.113.201.

The worker is not the only thing in the cluster that calls out. An inference server fetches models from a model registry and its image from an image registry. An agent that does retrieval reads an external database. A fine-tuning job pushes metrics to a monitoring service. An orchestrating agent calls a commercial model's API. Each of those destinations has an owner with a firewall, and each owner wants to write a rule that names who may come in.

So the question is simple and it decides everything that follows: when a Pod of tenant A connects out, what source address does the far firewall see? A Pod's own address, 10.244.1.21 here, comes from a private range that only this cluster knows. It cannot be the answer, because the store would have no route to send its reply to. Something has to replace it on the way out, and the rest of this lesson is about what does the replacing and which address it picks.

Chapter 2 of 14

By default it leaves as the node

Masquerading hides who is calling

A Pod's address means nothing outside the cluster, so the cluster's network replaces it on the way out. The usual replacement is the address of the node the Pod is running on. That is called masquerading. In Calico it is a setting on the IP pool, natOutgoing. With it on, a packet from a Pod in the pool to a destination outside every pool has its source rewritten by the node's kernel to the node's own address, and the kernel keeps a record of the connection so it can undo the change on the reply.

Now look at it from the store's firewall. The cluster has three nodes, 10.0.1.11, 10.0.1.12 and 10.0.1.13. The connection comes from 10.0.1.11. A worker of tenant B on the same node would come from the same address. To the firewall the question of which application this is has no answer.

To let tenant A's workers in, the firewall has to allow every node of the cluster, because a Pod can be scheduled on any of them. That is 10.0.1.0/24, and it lets in tenant B and everything else running there too. And when a Pod is rescheduled to another node its source address changes. A rule written for 10.0.1.11 no longer matches, and nothing in the cluster reports that as an error. The download simply stops working after a restart.

Chapter 3 of 14

Declare the way out

A pool of addresses, and an egress object that names it

The fix is to send the tenant's outbound traffic through one place that knows whose it is. With BNK that place is TMM, and it is set up with two objects. The first is a pool of source addresses. In the form the author's lab used, that is an F5SPKSnatpool: a name, a list of addresses and the VRF they belong to. The second is the egress object itself, an F5SPKEgress. It says how to translate, with snatType set to SRC_TRANS_SNATPOOL and egressSnatpool naming the pool. It lists the namespaces to steer under pseudoCNIConfig. And it can name the firewall policy to enforce.

There are three translation types. SRC_TRANS_AUTOMAP is the default and uses TMM's own address on the outside network, which is simple and gives every tenant the same source. SRC_TRANS_SNATPOOL uses the pool, which is what gives a tenant an address of its own. SRC_TRANS_NONE keeps the Pod's address.

Two rules come with it. A namespace gets exactly one egress object, and one pool is used by one egress object. Newer releases also describe the same intent with two newer objects, and the 2.4 releases carry both of them. A GatewaySettings object holds named egressConfigs, each with a SNAT pool and a VRF. An EgressGateway picks one of them by sectionName and selects Pods with a sourceSelector, by namespace, by Pod label or both.

Chapter 4 of 14

Steer the tenant's traffic to BNK

A tunnel from every node, and a rule for every Pod

Egress is the one feature of BNK that reaches into the nodes. A controller reads the egress object and works out which TMMs act as the way out for which namespaces. It sends those mappings over gRPC to an agent that runs on every node as a privileged DaemonSet, called CSRC. The agent does two things on its node. It builds a VXLAN tunnel from the node to TMM. And for each Pod of that namespace on its node it writes a policy routing rule that says: packets from this Pod's address use a routing table of their own, and that table's default route is the tunnel.

The Pod is not changed and knows nothing about it. It has no sidecar and no proxy setting. Its packets simply take a different way out of the node, still carrying the Pod's own address, wrapped in an outer packet from the node to TMM. Masquerading never sees them, because they no longer leave by the node's ordinary route.

The tunnel's defaults are UDP port 4789 and an MTU of 1,460 bytes. VXLAN over IPv4 adds 50 bytes to every inner IP packet: the inner Ethernet header of 14, the VXLAN header of 8, UDP 8 and the outer IPv4 header 20. A full 1,460-byte packet would become a 1,510-byte outer packet, which does not fit a network with the standard 1,500-byte IP MTU. So this lesson sets the tunnel's MTU to 1,430. A full packet then becomes an outer IP packet of 1,480 bytes, inside the 1,500, and a frame of 1,494 bytes on the wire once the outer Ethernet header is added. When TMM also runs on a DPU in the Pod's own server, that local TMM is preferred over the others as the way out.

Chapter 5 of 14

One address for the tenant

TMM translates, and routes out of the tenant's own VRF

TMM takes the packet out of the tunnel and now it knows two things the node's masquerading never did: which tenant this is, and which Pod. The egress object has given TMM a wildcard listener for this tenant, a virtual server on 0.0.0.0 port 0 that accepts traffic for any destination when it comes from the steered Pods. The listener replaces the source with an address from that tenant's own pool and sends the packet out through the tenant's VRF, onto the tenant's slice of the fabric.

Every worker of tenant A, on whichever node, now leaves as the same address. With one TMM carrying the traffic, the store's firewall rule is one line and stays true when Pods move, when nodes are added and when the cluster is rebuilt. This time the connection is accepted, and the weights start to flow.

One address is enough for a great deal of traffic. A TCP connection is told apart by four values: two addresses and two ports. Towards one store address and port, one source address can therefore hold about 64,000 connections at once, one for each source port above 1,023. A worker that downloads over 32 parallel connections uses 32 of them, so about 2,000 workers could download at the same moment before a second address is needed. The pool is a list for exactly that reason.

Chapter 6 of 14

The way back, and a second TMM

A reply has to find the TMM that holds the connection

The store's reply is addressed to 203.0.113.201, so the outside world must know that this address lives at TMM. In this lesson's picture TMM tells it the same way it announces a Gateway's address. On an EVPN fabric the pool address then goes out as a type 5 route, an IP prefix, tagged for tenant A's routing table and carrying tenant A's VNI, and the leaf holds 203.0.113.201/32 in tenant A's table, pointing at TMM's tunnel endpoint. Whether a given release announces SNAT pool addresses by itself, or the route has to be added to TMM's routing configuration or to the fabric by hand, is something to check on the leaf before the first download. The reply arrives in tenant A's VRF, TMM finds the connection it remembered, puts the Pod's address back and sends the packet down the tunnel to the right node.

That memory is per TMM, and a factory runs more than one. There are two ways to keep a reply and its connection together. By default each TMM gets its own address from the pool, which is why the address list is a list per TMM. The fabric then delivers a reply to the one TMM that owns the address. The cost is one more address per TMM in every tenant's allowlist. The pool has to hold that many addresses. In the author's lab a pool with a single address under the default mode gave it to one TMM only, and the second TMM fell back to another source address or dropped the traffic.

The other way is one shared address for all TMMs. Now the fabric may hand a reply to a TMM that never saw the connection. That TMM works out which one did and forwards the packet to it over a VLAN set aside for the purpose. This is flow forwarding. It saves addresses and has one restriction: a firewall ACL cannot be applied to an address that is being flow forwarded.

Chapter 7 of 14

Getting the second TMM running

One labelled node per TMM, one self IP per TMM on every VLAN

The chapter before assumed that a second TMM is simply there. Getting it there is the job of the F5 Lifecycle Operator, FLO. It reads the CNEInstance and builds TMM as a DaemonSet. A DaemonSet is the Kubernetes object that runs one copy of a Pod on every node that matches its selector. FLO's selector is the node label app=f5-tmm, so one labelled node gives one TMM and two labelled nodes give two. The label is set by hand before the install, with kubectl label node <node> app=f5-tmm, and a node that carries it hands TMM a large share of its resources. At the Small size on 2.4.0 the author measured f5-tmm requesting 4.6 vCPU, 8 GiB of memory and 4 GiB of 2 MiB hugepages per TMM. A second TMM asks for all of that again, on a node that may also be running the GPU workers.

The label is easy to forget and the failure gives no clue. With no node labelled, FLO panics with assignment to entry in nil map at f5tmm_daemonset.go:186, recovers, queues the work again and panics again, while every other component reports healthy. The message names neither TMM nor the label. The author's install script now checks for the label before it starts.

A second labelled node has its own history. The lifecycle operator in 2.3.0 panics while building the TMM DaemonSet when two nodes carry the label. The author's install script therefore refuses a second TMM node unless BNK_TMM_ALLOW_MULTI=true is set. On 2.4.1 and on 2.4.2 two TMMs were verified in two separate labs, both TMM Pods serving traffic, and the flag is needed only to get past the installer's own guard. One exception remains open. On the container lab running on kind, labelling a second node on a 2.4 release still sent the operator into a panic loop, and that lab runs one TMM. So after labelling the second node, read the operator's log for a panic and check that the DaemonSet wants two Pods and has two ready before sending traffic to the second.

A running second TMM still has to be given addresses. Every F5SPKVlan lists its self IPs in selfip_v4s and selfip_v6s, one per TMM, in order. The first address in each list goes to the first TMM, which gets the device name DP-0, and the second address to the second TMM, DP-1. The number of TMMs that carry traffic is the smaller of maxActiveReplicas and the shortest selfip list across all VLAN objects. The reference's own example: maxActiveReplicas 6, one VLAN with 6 self IPs and another with 4, gives 4 active TMMs. A TMM beyond that count is a standby. It gets no self IPs and no SNAT addresses, keeps receiving the configuration that is not tied to one TMM, and takes over when an active TMM fails or more self IPs are added. In this lesson that means each tenant leg needs two addresses now: int-a lists 10.249.1.250 and 10.249.1.251, int-b lists 10.249.2.250 and 10.249.2.251. Forget the second address on int-b and one TMM carries all the traffic while the other waits, with nothing reported as wrong. Calico's externalNodesList also grows, because each new self IP on a tenant leg is a new source of VXLAN packets.

The outside addresses grow too. Under the default UNIQUE_SNAT_ADDRESS mode each TMM needs its own SNAT address per tenant. Two tenants on two TMMs need 2 × 2 = 4 addresses, and each tenant's far firewall now allows 2 sources. Under SHARED_SNAT_ADDRESS_FLOW_FORWARD the same two tenants need 2 addresses, one each, and pay with the flow-forward VLAN and the loss of an ACL on that address.

Chapter 8 of 14

A policy on the way out

With the firewall on, nothing leaves without a rule

Now that all of a tenant's outbound traffic passes one point, that point can say no. In the author's lab on 2.4, with BNK's firewall switched on, an egress path forwarded nothing until a policy was enforced on it. F5's egress reference does not say this, so check it on your release. Each tenant gets a firewall policy attached to its egress, and only what the policy accepts gets out.

The policy is an F5BigFwPolicy, an ordered list of rules. A rule has a name, a protocol, a source and a destination, and an action. The destination can be addresses, ranges, ports, named lists or DNS names. The action is accept, accept-decisively, reject or drop. Reject answers the sender with a reset and drop says nothing. A rule can also set logging, so that every match is written down. Rules are read top to bottom and the first match decides. Before TMM uses a policy, the rules are sent to the firewall's management Pod and compiled into one binary large object, a BLOB, which is what keeps the per-packet check fast. TMM receives the compiled BLOB.

For a tenant this turns outbound access into a short list: the storage, the registry, the one model provider it has a contract with. It also changes what a compromised agent can do. Picture an agent whose every single call is permitted. It reads logs, queries a database and looks up records, and then it posts what it gathered to a webhook nobody approved. Each step looks like work. The last step needs a destination, and with a policy on the way out the destination is not on the list.

Chapter 9 of 14

Closing the door, and proving it is closed

Swap one policy and watch the far side stay silent

A claim that nothing leaves has to be shown, and the author's lab shows it with two captures. A Pod in a tenant's namespace calls a small receiver outside the factory. With the tenant's accept policy in place the receiver logs the request, and the source it logs is the tenant's SNAT address. Then the accept policy is swapped for one that rejects. The next connection from that Pod is reset at once, before translation and before routing. A packet capture on the border router, the last hop before the outside, stays empty. Applying the accept policy again opens the way, because TMM applies a changed policy to new connections in place.

Rules can be finer than open and closed. In the lab one tenant's policy starts with two rules in order. The first accepts TCP port 443 and logs it. The second allows the rest. Turning only the first to reject cuts that tenant off from a hosted model and leaves everything else as it was. A later version of the same policy has three rules: the first admits the hosted model by name, the second rejects every other TLS destination, and the last still allows the rest.

A rule can also name a destination by DNS name. For that TMM needs a resolver of its own, an object that BNK's lifecycle operator creates empty when BNK is installed. In the author's lab the installer then fills it with a zone and name servers, so it is a step the platform team owns. TMM then resolves the name, keeps the addresses fresh and matches packets against them. In one lab session its counters showed one name, eight refreshes and no failures, and a connection to any other TLS name was refused.

Chapter 10 of 14

What stays out of the tunnel

Traffic inside the cluster must not take the long way

There is one trap. Once a namespace is steered, everything its Pods send goes into the tunnel unless it is excluded. That would include a Pod talking to another Pod, to a Service, to its node, and to the factory's own Gateway address when it calls its own model. Sending those out to TMM's egress listener would break some and slow the rest. A call to a Service address, for instance, would arrive at TMM with a destination that only the node's own rules know how to turn into a Pod.

So the agent on the nodes carries a list of networks to leave alone, its EXCLUDE_CIDR setting: the Pod network, the Service network, the node network and the network the Gateways' addresses come from. A packet to any of those keeps taking the node's ordinary route. Only traffic to anywhere else is steered.

The last entry is the one people forget. A worker of tenant A that calls tenant A's own Gateway at 10.201.100.10 is making an inbound call from inside. It is meant to reach TMM by the node's route to TMM's internal address and to be handled by the Gateway's listener. If the Gateway range is missing from the list, the call goes into the egress tunnel, meets the egress policy, and is rejected or translated and sent out to the fabric. Getting that list right is part of the work of turning egress on in an existing cluster.

Chapter 11 of 14

Four assumptions that failed in a small lab

Each one left a different kind of silence

On servers with real network cards, egress tends to just work. The author rebuilt it on a lab where the nodes are containers, and four assumptions failed one behind the other. They are worth knowing because each can also bite on real hardware.

First, the node agent only reports physical, VLAN, macvlan and VXLAN interfaces. A container node has only virtual Ethernet pairs, so the controller found no interface in the tunnel's subnet and built nothing. The fix was a VLAN sub-interface per tenant on every node. Second, the controller places the tunnel's far ends, the nodes, in the VRF of the egress object. With the tunnel's underlay in the default routing table, TMM looked for the nodes inside the tenant's VRF, where the only route points at the fabric. Each tenant therefore got its own leg on TMM's internal side: a VLAN marked internal, in the tenant's VRF, with its own address.

Third, with the firewall on, the egress listener forwarded nothing until a policy was enforced. Fourth, and the hardest to find, checksums. A Pod's kernel leaves the TCP checksum for the network card to fill in, and on a virtual link nothing fills it. TMM checks the checksum of what it takes out of the tunnel and dropped the SYN after the listener had matched it. Fourteen connection attempts produced no server-side connection, no counter and no log line. Turning checksum offload off on the tunnel devices fixed it.

Each of the four has a mechanism behind it. Start with the node agent, CSRC. F5's egress reference says that when vxlan.nodeInterfaceName is left unset, the agent finds the node's interface by itself, and the one it picks is the interface that can reach the TMM VLAN named in vxlan.tmmInterfaceName. In the author's lab the agent reported only a node's physical, VLAN, macvlan and VXLAN devices and its loopback. A kind node is a container. Its eth0 is one end of a virtual Ethernet pair, a veth, and the agent does not report veths. So it offered the controller no candidate at all. F5's own lab for BNK on kind gives every node a macvlan leg for the same reason. The author used VLAN sub-interfaces instead: int-a with tag 201 and int-b with tag 202 on every node, with tenant A's node ends at 10.249.1.241, 10.249.1.242 and 10.249.1.243 on the three nodes. The names avoid the string eth0 on purpose. Calico chooses the interface for its own tunnel with the regular expression eth0, a sub-interface called eth0.201 matched it, and Calico moved its own VXLAN endpoint onto the tenant's leg.

The second fix leans on a field whose documented purpose is narrower than the way the lab used it. On an F5SPKVlan, internal is a boolean that defaults to false. The reference describes it as turning on routing annotations for internal Pods, to be set on the internal VLAN, and on one VLAN only. In the author's lab on 2.4 the same object also carried a vrf field that names the tenant the VLAN belongs to. The 2.1.0 reference does not list that field, so read your release's reference for its default and for whether it can be changed on a VLAN that already exists. The lab needed the tunnel's underlay inside the tenant's VRF, because the controller programs the far ends of the tunnel, the node addresses, in the VRF of the egress object. So it created one leg per tenant: F5SPKVlan int-a with tag 201, vrf tenant-a, internal: true and self IP 10.249.1.250, and int-b with tag 202, vrf tenant-b and 10.249.2.250. Each egress object names its own leg in vxlan.tmmInterfaceName, which the reference says must match the metadata.name of a VLAN object created beforehand. A leg made in the wrong table is a reason to stop and check that reference before editing its vrf in place.Calico also has to be told about each leg's self IP in the externalNodesList of its Felix configuration, next to TMM's main internal self IP, or it drops the VXLAN packets that come from those addresses.

Third, the firewall. BNK's firewall is switched on for the whole instance, in the author's labs with firewallACL enabled: true in the CNEInstance. From then on an egress listener forwards a connection only when its egress object names a policy in firewallEnforcedPolicy and that policy has been compiled and enforced. An egress without one looks healthy: the tunnel is up, the per-Pod rules are on the nodes, the listener matches, and nothing leaves. The lab's answer was an accept-all policy for every tenant at setup, egress-allow-a and egress-allow-b, each named by its own tenant's egress object. Narrower rules are then placed above the accept-all rule as the tenant's list of destinations takes shape, and closing the exit means applying a version whose rules reject. Enforcement was proven exactly that way: the Pod got a reset at once and a capture on the border router stayed empty. The firewall also costs memory. In another of the author's labs its rule-compiling sidecar needed more than 9 GiB of RAM, so the firewall ran only on nodes with 32 GiB.

Fourth, the checksum fix has to be kept in place. The agent recreates its VXLAN devices whenever an egress is declared again, and a new device comes up with checksum offload on. The tenant legs themselves report the setting as fixed, so it cannot be turned off one level lower. The lab therefore runs a small watcher container on each node, in the node's network namespace with the NET_ADMIN capability, that sets tx-checksum-ip-generic off on every egress VXLAN device it finds.

Chapter 12 of 14

Addresses TMM sees its own way

TMM has three kinds of address, and the wrong one breaks things quietly

TMM has more than one address, and which one a packet carries depends on where it goes. TMM has self IPs on its VLANs: the internal legs towards the nodes and the external legs towards the fabric. It owns the virtual addresses, the VIPs, of the Gateways, which it announces to the fabric. And TMM is itself a Pod, so it also has an ordinary Pod address on the cluster network. Four things in the author's labs came down to which of these was involved, and none of them showed up as an error on the object that was wrong.

The first is reaching a VIP from inside the cluster. A Pod's packets leave through the node's own routing table. A VIP such as tenant A's Gateway address 10.201.100.10 is reachable from a Pod only if the node has a route for the VIP range that points at TMM's internal self IP. In the container lab, the author's notes say a worker's call to its own Gateway is meant to reach TMM through the node's route to the internal self IP, and for that the VIP range also has to be in the agent's EXCLUDE_CIDR, or the call is steered into the egress tunnel. On the author's OpenShift lab nothing wrote it. Pods on the cluster network timed out on every VIP, and only the external network, where TMM's external self IPs live, routed to the pools. A controller there that had to call each VIP got a macvlan leg on the external network with a route to the VIP pool through TMM. In a real site the management network plays that part. Test this from a Pod with a timed connection before an in-cluster caller, such as a benchmark or an agent, is pointed at a VIP.

The second is the sideband. An iRule is a small Tcl program that TMM runs on traffic, and a sideband is a connection it opens on its own to ask another service a question, for example to check an API key or to record a request's tokens. The BIG-IP reference for connect gives the form connect -protocol TCP -timeout 100 -idle 30 -status conn_status followed by a destination of ip:port. It says that TCP is the default protocol, and that without -myaddr the system uses the self IP closest to the destination as the source. On BNK neither held for a Service. To reach a ClusterIP Service the lab had to write -protocol TCP explicitly. A capture in TMM's debug container then showed the sideband SYNs leaving from TMM's Pod address, 10.130.0.112 in that lab, and never from its internal self IP. That fits how a ClusterIP works: the node's kube-proxy rules turn it into a real Pod address, and TMM reaches those rules through its own Pod interface. So the service at the far end must admit TMM's Pods, labelled app=f5-tmm in BNK's namespace, and that address changes every time TMM is recreated. The lab's collectors accept a sender only if it is a current TMM Pod address, which they look up again every 10 seconds. Admitting the whole Pod network instead would let any Pod write usage records. Every connect is also wrapped in Tcl's catch. The reference says an unknown protocol triggers a Tcl error that tears down the client connection, and in the lab any failed sideband call without catch reset the client.

The third is where named lists live. An F5BigCneAddresslist holds addresses, subnets and ranges, and may include other lists by name. An F5BigCnePortlist does the same for ports. A firewall rule can point at them in place of writing addresses out. The reference's sample puts a list in a Gateway's namespace. On BNK 2.4.2 in the author's lab, lists created in a tenant's namespace never got a status, the firewall looked for them under the CNE namespace with names that start f5-bnk-lfw-al-, and the policy that named them waited for its dependent objects indefinitely. List references resolve only in the namespace of the CNE instance. That lab now writes each list's entries straight into the rules that use them, so a tenant's policy and everything it needs stay in the tenant's namespace.

The fourth is the log publisher. An F5BigLogHslpub, a high-speed logging publisher, tells TMM where to send log lines and in what form. Its pool.endpoint is, in the reference's words, an IPv4 or IPv6 address and the service port, such as 10.30.2.220:514 or [2002::10:30:2:220]:514. Syslog defaults to rfc5424 over udp. A Service name in that field is refused by the API with HTTP 422, so the lab resolves the collector's name to its address when it writes the object. A log profile, F5BigLogProfile, then names the publisher and says which events to send: firewall matches by action, and the source translation of each outbound connection. With both on, one log line holds the Pod's own address and the tenant's SNAT address together, which is the record the last chapter of this lesson relies on.

Chapter 13 of 14

Leave the egress object alone

Open and close the door with the policy, never by deleting the door

The obvious way to close a tenant's exit is to delete its egress object, and to open it again by applying the file once more. F5's reference recommends that you always delete and reapply the object, rather than change the running one with kubectl apply, and notes that each change to egress makes TMM redeploy. On a running system in the author's lab that cost two tenants their way out, and the controller's log showed why.

A recreated egress object does not relearn the Pods of its namespace. The controller's count of steered Pods for the new object starts at zero, although the Pods are all still running. Every Pod it then sees arrive is logged as an unexpected object, and every Pod that ends still counts down. At the next rollout of the tenant's Deployments the old Pods ended against a count that no longer matched them, and the controller arrived at zero for the object. At zero it sent the node agents a delete for the egress mapping, with an empty tunnel name. The agent's delete handler walked every routing table it had and removed the tunnel device of a different tenant, on all three nodes. Restarting the agent rebuilt the tunnels the controller still remembered and nothing for the tenant whose object had been recreated.

So the working rule in that lab is strict. Egress objects are created once, when the tenant is set up, and not touched while Pods are running. What changes is the firewall policy the egress names. And after a restart of TMM itself the tunnel has to be put back by applying the egress again and restarting the node agents.

Chapter 14 of 14

Two tenants, two addresses

Each one's traffic is its own, all the way out

Do the same for tenant B and the picture is complete. Tenant B's namespace has its own egress object, its own tunnel rules, its own address and its own policy, and its packets leave through its own VRF. Two workers side by side on one node now leave the factory as two different addresses, by two different routes, under two different sets of rules.

Follow one packet from each. Tenant A's worker at 10.244.1.21 and tenant B's at 10.244.1.23 both sit on node 10.0.1.11. The node holds one rule for each address, pointing into two different tunnels. The first tunnel ends on tenant A's leg of TMM and the second on tenant B's. TMM gives the first packet the source 203.0.113.201 and routes it out of VRF tenant-a with VNI 10001. It gives the second 203.0.113.202 and routes it out of VRF tenant-b with VNI 10002. Before this, both would have left as 10.0.1.11.

Tenant A's store sees only tenant A. If tenant B's policy forbids a destination, that says nothing about tenant A. If tenant B's worker tries tenant A's store, it arrives from 203.0.113.202, is on no allow rule, and is dropped by the store firewall's default, under an allowlist that tenant A's own security team wrote and can read. And when someone asks which tenant made a connection at three in the morning, the answer is in one log, by name.

What to keep

Outbound traffic gets an owner

Left to the cluster's defaults, a Pod leaves with the address of its node, and nothing outside can tell one tenant or application from another. Steering a namespace's outbound traffic through BNK changes that at one point. An agent on each node tunnels the namespace's packets to TMM. TMM gives them the tenant's own source address and sends them out of the tenant's VRF, under the tenant's firewall policy, and writes down what it saw wherever logging is set. The far end needs one stable rule per tenant, naming that tenant's addresses: one address with one TMM or in the shared SNAT mode, one per TMM in the default unique mode.
