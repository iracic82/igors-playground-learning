BNK and gateways

Two tenants, one factory

What keeps them apart, layer by layer

An AI factory rents the same GPUs, the same network and the same data plane to customers who must never see each other. Here there are two: tenant A, whose caller is an AI agent, and tenant B, whose caller is an app. They are kept apart five times over, at five different layers, because each layer only separates what it can see. An address range separates names. A routing table separates packets. A Gateway separates routes and policy. A pool separates GPUs, queues and cache. An egress address separates what the outside world sees. Follow one request from each tenant and watch where the lanes are drawn.

The lesson goes layer by layer and stops at each one long enough to read the real objects. It starts with the address and the IPAM record behind it, and what happens when a Gateway skips that record. It reads a BGP EVPN route byte by byte and times how long a new address takes to become reachable. It counts the 50 bytes of VXLAN on every packet and shows the MTU failure they cause when a fabric forgets them. Then it follows the request into TMM, through the Gateway API's namespace rules, into each tenant's own pool and the budgets and quotas in front of it. It ends with the Pod network inside the cluster, the way out, the KV cache, and what it takes to add a third tenant without touching the first two. After that come four chapters on a design the owner proposed and has not built: giving each tenant's Pods their own network with OVN-Kubernetes, announcing it with BGP and EVPN into the same tenant tables, and following fabric controllers such as Netris and NVIDIA's Cumulus and NetQ.

Chapter 1 of 20

A range each

Where a tenant's address comes from

Each tenant gets a Gateway, the Gateway API object that describes a way into the factory. A Gateway needs an address to be reached on, and nobody types one in. F5 IPAM holds a range for every tenant and hands out the next free address from the right one. Tenant A's Gateway gets 10.201.100.10. Tenant B's gets 10.202.100.10. From now on the address alone says whose service it is, and that makes every firewall rule and every route that follows easy to read.

The range is not typed into the Gateway either. It lives in a separate F5 object called F5BnkGateway. Its spec holds a list under ingressConfig.defaultListenerNetworks, and each entry has a name, a base CIDR and a first and last address. The platform team writes one F5BnkGateway per tenant. Tenant A's says ipv4BaseCidr 10.201.100.0/24, startAddress 10.201.100.10 and endAddress 10.201.100.29, which gives twenty addresses to hand out. Tenant B's says the same for 10.202.100.0/24. A second F5BnkGateway with its own range was accepted next to the first one in the owner's lab, and Gateways that pointed at it got addresses from it. That is how a per tenant pool is built today.

The Gateway points at its tenant's F5BnkGateway through spec.infrastructure.parametersRef, with group k8s.f5net.com and kind F5BnkGateway. The F5 IPAM controller sees the reference, takes the next free address from that range, writes an IPAM record for it, and the address appears in the Gateway's status.addresses. Once TMM has programmed the listener, the Gateway's Programmed condition turns True. Two points are worth knowing before day one. Changing the ranges of a running F5BnkGateway needs care: on versions 2.1.0 and 2.1.1, F5 bug 1987357 leaves a Gateway without an address when a block of a new IP family is added to an existing F5BnkGateway, as a later chapter describes. And a Gateway that names a static address should still reference the F5BnkGateway and pick an address inside its range, so that IPAM knows the address is taken.

Chapter 2 of 20

An address with no record

What happens when one Gateway skips IPAM

IPAM can only protect addresses it knows about. Suppose someone in tenant A writes a test Gateway by hand and gives it spec.addresses with the value 10.201.100.11, but leaves out the parametersRef. Kubernetes accepts the object. TMM programs a listener on 10.201.100.11. The Gateway works. Nothing about it looks wrong from the outside.

The problem is what IPAM did not see. Because the Gateway never referenced the F5BnkGateway, the IPAM controller wrote no record for 10.201.100.11. To IPAM that address is still free. The next Gateway in tenant A that asks for an address through the proper reference can be given 10.201.100.11, the address the test Gateway already holds. Two listeners now claim one address in one VRF, and which one answers a connection is no longer a question you can answer from the objects.

This is not a thought experiment. The owner's lab hit exactly this on 16 November 2026. A Gateway asked for a fixed address without the reference, got it, and IPAM later handed the same address to another Gateway that asked for any address. The fix was a rule: every Gateway carries the parametersRef, whether a person or a controller writes it. A policy engine or a review check that rejects Gateways without it turns the rule into something enforced.

There is a known bug in the same area worth recognising. F5 bug 1987357, listed against versions 2.1.0 and 2.1.1, describes what happens when an existing F5BnkGateway is updated in place to add a block of a new IP family, such as IPv6. The IPAM status does not show the new address, the Gateway never receives an address of that family, and TMM gets no new virtual server for it. The bug's own workaround is to delete the Gateway object and apply it again. On those versions, make a change of range in a quiet window, then check the IPAM status and every Gateway's status.addresses, and keep that workaround ready.

Chapter 3 of 20

Tell the fabric, one tenant at a time

BGP EVPN carries each address with its tenant's tag

An address nobody knows the way to is useless. TMM announces each new address to the data center fabric with BGP. It does not use ordinary BGP routes, because an ordinary route has no idea of tenants. It uses EVPN, a BGP address family built for this. Each route TMM announces here carries two extra things: a route target, which says which tenant's routing table may import it, and a VNI in the route's label field, the number that will mark this tenant's packets on the wire. The leaf switch reads the route target and puts tenant A's address into tenant A's table only. In a lab run that used plain BGP, the address was reachable about ten seconds after the Gateway was ready.

A route distinguisher sits in front of every route. It is eight bytes that make the route unique inside BGP. TMM uses 10.0.0.5:10001 for tenant A and 10.0.0.5:10002 for tenant B, its own address followed by the tenant's number. If both tenants ever announced the same prefix, the distinguisher would keep the two routes apart in every BGP table on the way. The route target, a BGP extended community, is the separate label that decides which VRF may import the route. Here it is 65000:10001 for tenant A and 65000:10002 for tenant B, written by hand. RFC 8365 describes how a route target can be derived automatically from the AS number and the VNI, and it says that automatic form only works with two byte AS numbers. Larger AS numbers need the targets set by hand. Each speaker also derives the target from its own AS number, so two sides in different AS numbers derive different targets and need the same one written by hand.

The next hop in every one of these routes is 10.0.0.5, the tunnel endpoint of TMM. That address lives in the fabric's own underlay table, which every leaf and spine knows. So the leaf ends up with a tenant route whose way to get there is: send it in a VXLAN tunnel to 10.0.0.5, with VNI 10001. Each Gateway address goes out as a /32, a route for exactly one host, which is how BNK announces its addresses.

Chapter 4 of 20

Reading one EVPN route

Thirty four bytes that carry a tenant

An EVPN route of type 5 is small, and every field in it has a job. RFC 9136 lays out the IPv4 version as seven fields. The route distinguisher takes 8 bytes. The Ethernet segment identifier takes 10. The Ethernet tag takes 4. The prefix length takes 1. The IPv4 prefix takes 4. The gateway IP address takes 4. The label takes 3. That adds up to 34 bytes for the route itself. In tenant A's route the prefix length is 32, the prefix is 10.201.100.10, and the segment identifier, the tag and the gateway IP are all zero. Zero in the gateway field means the route points straight at the tunnel endpoint, without an extra hop to resolve.

The label field is where the tenant's number travels. MPLS labels are 20 bits, but RFC 8365 says that for VXLAN the whole 24 bit field holds the VNI. So the three bytes read 10001 for tenant A. Three extended communities ride along with the route. The first is the route target from the previous chapter, 65000:10001, which picks the VRF. The second is the BGP encapsulation community with tunnel type 8, which says VXLAN. The third is the router's MAC community. RFC 9136 requires it when the tunnel carries Ethernet frames, as VXLAN does. It holds the MAC address of TMM's tunnel interface, here 02:00:00:00:00:05, and the leaf writes it as the inner destination MAC of every packet it wraps for this tenant.

Routes flow the other way too. The leaf announces tenant A's own network, 10.1.0.0/24, as a type 5 route with route target 65000:10001 and VNI 10001. TMM imports it into VRF tenant-a only. That is how a reply from Gateway A finds its way back to 10.1.0.20. Tenant B's 10.1.0.0/24 arrives with 65000:10002 and lands in VRF tenant-b. Both routes have the same prefix, and the different route distinguishers keep them from replacing each other.

Chapter 5 of 20

Ready is not reachable

The seconds between a Gateway and a working address

A Gateway whose Programmed condition is True has a listener inside TMM. That does not mean anyone outside can reach it yet. The route still has to be announced, received by the leaf, imported into the tenant's table and, in a larger fabric, passed on to every other leaf. In a lab run with plain BGP from TMM to an FRR router, the owner measured the address reachable 11.5 seconds after the Gateway was Ready. Another lab showed about ten seconds. Treat the gap as normal and design for it. A pipeline that creates a Gateway and immediately runs a smoke test from outside the factory will see failures that fix themselves.

Removing a tenant service has the same delay in the other direction, and it was longer. When the Gateway was deleted, the route was withdrawn 25.2 seconds later. For those seconds the fabric still sends traffic for that address to TMM, which no longer has a listener for it, so callers get resets or timeouts.

Two details from the owner's install notes explain where the routing lives. In BNK 2.4.2, enabling dynamic routing after install left TMM on the older ZebOS routing image, and the global routing object failed. Setting ZEBOS_STATE to ocnos in the TMM environment switched it to the OcNOS image and fixed it, at the cost of TMM memory rising from 8 to 9.5 GiB in that lab. And BNK announces each Gateway address as a /32, one route per address, so a tenant with twenty Gateways puts twenty routes into its VRF.

Chapter 6 of 20

The same address twice

Two callers, told apart by a 24-bit number

Tenant A's agent and tenant B's app both have the address 10.1.0.20. Each opens a connection to its own factory address. On the wire between the leaf and TMM their packets would be impossible to tell apart by source, so the leaf doesn't send them as they are. It looks at the port a packet came in on, which belongs to exactly one VRF, and wraps the whole packet in a new one: outer addresses of the two tunnel endpoints, a UDP header, and eight bytes of VXLAN that carry the tenant's VNI. That number is the only thing in the frame that says whose packet this is.

The VXLAN header itself is eight bytes, laid out by RFC 7348. The first byte holds flags, and only one of them is used: the I flag, which says a valid VNI follows, so the byte reads 0x08. Then come 24 reserved bits, the 24 bit VNI, and 8 more reserved bits. Around it sit an outer UDP header to port 4789, an outer IPv4 header from the leaf's tunnel endpoint 10.0.0.11 to TMM's 10.0.0.5, and an outer Ethernet header. The outer UDP source port is not fixed. RFC 7348 says it should come from a hash of the inner packet and recommends the range 49152 to 65535. Different tenant connections therefore get different source ports, and the fabric's switches, which spread traffic by hashing outer headers, put them on different links. One connection always hashes the same way, so its packets stay in order.

A 24 bit VNI allows 16,777,216 values. A VLAN ID is 12 bits, with 4,094 usable values. That difference is the reason fabrics that host many tenants carry tenancy in VXLAN rather than in VLAN tags.

Chapter 7 of 20

Fifty bytes on every packet

The tunnel needs room, and the fabric must give it

Wrapping costs space. VXLAN carries the tenant's whole Ethernet frame, so on an IPv4 fabric each tenant packet gains the inner Ethernet header of 14 bytes, the VXLAN header of 8, UDP 8 and the outer IPv4 header 20. That is 50 bytes added to every tenant IP packet, all of them counted against the fabric's IP MTU. The outer Ethernet header of 14 bytes, or 18 with a VLAN tag, comes on top and does not count against the IP MTU. Tenant A's machines send standard packets with a 1,500 byte IP MTU. A full one is a 1,514 byte Ethernet frame. Wrapped, the tenant's 1,500 bytes of IP packet, its 14-byte inner Ethernet header, the VXLAN header and UDP make 1,500 + 14 + 8 + 8 = 1,530 bytes. The outer IPv4 header brings the outer IP packet to 1,550. With the outer Ethernet header it is a 1,564 byte frame on the wire.

So every link between the leaf and TMM needs an IP MTU of at least 1,550. Fabrics that carry VXLAN usually run a much larger MTU end to end so that no one has to count. RFC 7348 is strict about the alternative: a tunnel endpoint must not fragment VXLAN packets, and a receiving endpoint may silently throw away fragments that a router in the middle created.

The failure this causes is easy to misread. The TCP SYN is 74 bytes and passes. The connection opens. Then the first large packet, often the TLS server certificate or a long prompt, is silently dropped somewhere in the fabric. The caller sees a handshake that hangs, or a request that never gets an answer, while ping works. For an agent sending a 6.3 kB prompt with tool results, every request hangs. When a tenant reports that small calls work and large ones stall, check the fabric MTU on every hop before anything else.

Chapter 8 of 20

One TMM, two routing tables

The number on the tunnel picks the table

Both packets arrive at the same TMM. It takes the outer headers off and keeps the one thing they told it: the VNI. Each VNI is tied to one VRF, and a VRF is a complete routing table of its own. The agent's packet is looked up in tenant A's table, where the only listener is tenant A's Gateway. From there on it is an ordinary request: TLS ends at TMM with tenant A's certificate, tenant A's firewall policy and iRules run, and tenant A's HTTPRoute names the backend. Keys and budgets per tenant sit one layer up, in the AI gateway.

The two tables really are separate. VRF tenant-a holds 10.1.0.0/24 through VNI 10001 and 10.201.100.10/32 as a local listener. VRF tenant-b holds its own 10.1.0.0/24 through VNI 10002 and 10.202.100.10/32. A reply from Gateway A to 10.1.0.20 is looked up in tenant A's table, finds the route the leaf announced with VNI 10001, and is wrapped with that number on the way back. It cannot reach tenant B's 10.1.0.20, because tenant A's table has no path to it.

In the owner's lab each tenant also has its own VLAN leg between the fabric and TMM, VLAN 101 for tenant A and 102 for tenant B, so even the interface a packet arrives on belongs to one tenant. The egress tunnels from the nodes use other legs on TMM's internal side, VLANs 201 and 202. The Gateway's listener sits in the tenant's VRF. TLS ends there with the certificate for chat.tenant-a.example. The F5 firewall policy and iRules that tenant A's team attached run only on that listener. Inside TMM the two tenants share one process and its CPUs, which is why per tenant limits higher up still matter.

Chapter 9 of 20

A route cannot cross a namespace

Gateway API draws the next line, in the objects

The network kept tenant B's packets out of tenant A's table. The Gateway API keeps tenant B's configuration out of tenant A's Gateway. Each tenant lives in its own namespace, tenant-a and tenant-b, and two rules from the Gateway API specification do the work.

The first rule is on the listener. Every listener has allowedRoutes.namespaces.from, and its default is Same. A Gateway in tenant-a therefore accepts HTTPRoutes only from tenant-a. If someone in tenant-b writes an HTTPRoute whose parentRefs names Gateway chat in namespace tenant-a, the route is not attached. Its status shows the condition Accepted with status False and the reason NotAllowedByListeners. No traffic is ever sent along it.

The second rule is on the backend. An HTTPRoute in tenant-a may name a backend in its own namespace freely. To name a backend in another namespace, the other namespace must hold a ReferenceGrant that allows it, listing the namespace and kind it trusts. Tenant B writes no ReferenceGrant. So if tenant A's route points at tenant B's InferencePool, by mistake or on purpose, the route's ResolvedRefs condition turns False with the reason RefNotPermitted, and the reference is not used.

Both refusals happen at configuration time, before a single request. They are also visible: kubectl get httproute -o yaml shows the condition and the reason. The platform team owns the GatewayClass and the F5BnkGateways. Tenants own their Gateways and routes. Kubernetes RBAC decides which people can write objects in which namespace.

Chapter 10 of 20

Own GPUs, own queue

A noisy neighbor stays next door

Each tenant's route ends at an InferencePool of its own: its own GPU workers, picked by its own endpoint picker, with its own queue in front of them. Now the agent does what agents do. It splits its task into forty parts and sends them all at once. Pool A fills up. Its GPU memory is taken by KV cache and the rest of the calls wait in line. Tenant B's app sends one request in the middle of this and notices nothing, because none of what just filled up is shared. The queue is the thing to isolate. It is where one caller's load turns into another caller's wait.

The pool is a Gateway API Inference Extension object. Its selector matches Pods by label, only in its own namespace, and targetPorts says they listen on 8000. Tenant A's selector finds qwen3-6f7d9c8b4-x7k2p at 10.244.1.21 and qwen3-6f7d9c8b4-m9q4t at 10.244.2.22. Its endpointPickerRef names tenant A's own endpoint picker, with failureMode FailClose, which means that if the picker is down requests fail instead of being spread blindly. The picker reads each worker's vLLM metrics: vllm:num_requests_running, vllm:num_requests_waiting and vllm:kv_cache_usage_perc. It sends a request to the worker that already holds the start of the conversation when it can, because that worker can skip recomputing the prefix.

During the flood, pool A reports 12 running, 28 waiting and 97 percent of its KV cache in use. Those numbers are illustrative. What matters is that 12 plus 28 is all 40 of the agent's calls, and none of them are in pool B. Tenant B's worker at 10.244.2.23, on its own GPU of gpu-node-2, shows one running, none waiting and 31 percent cache in use, so its time to first token is what it always was. F5's own deck shows the same idea as two figures on one slide: a time to first token of 800 ms under standard Kubernetes networking, and 45 ms with F5's service plane keeping the traffic apart. The slide compares the two set-ups and gives no before and after for one tenant. Those are figures from a vendor slide, shown as an example.

Chapter 11 of 20

Limits in front of the queue

Budgets stop the bill, quotas stop the grab

A separate pool keeps tenant A's flood away from tenant B. It does nothing to stop tenant A from hurting itself, or from asking for more GPUs than it pays for. Two more limits sit in front of the queue, and both are per tenant.

The first is in the AI gateway behind Gateway A. Each tenant has its own keys, and each key can carry a model scope and a budget. In the F5 AI gateway build the owner tested, a key asking for a model outside its scope was refused with 403 and model_not_allowed. Budgets were checked before the call ran: the gateway reserved the prompt plus max_tokens against the budget, and if that would pass the limit it answered 429 with budget_exceeded. For the agent's loop, that means the fortieth call can be refused before it ever reaches pool A. That protects tenant A's bill. The separate pool still protects tenant B.

The second limit is in Kubernetes. A ResourceQuota in namespace tenant-a can cap requests.nvidia.com/gpu, the GPU count all of the tenant's Pods may request together. With a cap of 2, tenant A's two vLLM workers fit. A third worker is refused when it is created, before the scheduler sees it. The error names the quota, what was requested, what is used and the limit. Extended resources such as GPUs can only be capped under the requests. prefix, because Kubernetes does not allow them to be overcommitted.

Pools, budgets and quotas are three different questions: who shares a queue, how much one tenant may spend, and how much hardware one tenant may hold. A factory needs answers to all three.

Chapter 12 of 20

No route across

The other tenant's address doesn't exist

Suppose the agent is told tenant B's address, by a careless config or by a prompt someone planted. It tries to connect. The packet reaches the leaf on tenant A's port and is looked up in tenant A's table. Tenant B's address was never imported there, so there is nothing to match. The leaf answers that the network is unreachable. No firewall rule fired and nobody had to remember to write one. Isolation by routing table fails closed: what was never connected stays unreachable.

The reply is an ICMP message of type 3, destination unreachable, with code 0, network unreachable. It comes from 10.1.0.1, the leaf's own address in tenant A's network, and it carries the IP header and the first 8 bytes of the packet that failed, which is the minimum a router returns. On the agent, that reads as a connection that fails at once, with an error such as network is unreachable. Some fabrics are set not to send ICMP at all, and then the connect simply times out. Either way, nothing from tenant A ever reached tenant B.

The same holds in the other direction and inside TMM. If a packet tagged VNI 10001 somehow carried a destination of 10.202.100.10, TMM would look it up in VRF tenant-a, where that address does not exist. There is no shared table to fall back on. This is the property F5's material on multi tenant factories asks for by name, isolation that fails closed: a missing entry means no path.

Chapter 13 of 20

Inside the cluster, a different wall

Pods of two tenants do not pass through a VRF

Everything so far was about traffic that crosses the fabric. Both tenants' Pods also run in one Kubernetes cluster, on a Pod network that the cluster's network plugin builds. On that network, 10.244.1.21 in tenant-a can reach 10.244.2.23 in tenant-b directly, without passing through TMM or any VRF. Kubernetes allows all Pod to Pod traffic by default. The tenant VRFs do not see these packets at all.

A NetworkPolicy closes that path. The usual first one in each tenant namespace selects every Pod, with podSelector set to empty, and lists Ingress under policyTypes with no ingress rules. That denies all incoming traffic to the tenant's Pods. Then small allow rules open exactly what is needed: the picker and TMM may reach port 8000 of the vLLM workers, and nothing from other tenant namespaces may. A NetworkPolicy only works if the network plugin enforces it. The owner's first lab, a Kubespray cluster in F5's UDF, used Calico, which enforces it. OVN-Kubernetes, the plugin on the owner's OpenShift lab, enforces it too. A plugin without policy support accepts the objects and ignores them.

The owner's install notes add one more trap. On OpenShift, a primary user defined network from OVN-Kubernetes was not reachable from BNK 2.4.2 in host mode, so tenant isolation there uses BNK's own VRFs and VLANs on TMM's interfaces. The general point holds everywhere: the fabric's VRF separates what enters the factory, and the cluster's policy separates Pods that already live inside it.

Chapter 14 of 20

The way out

Each tenant leaves from its own address

Traffic also leaves the factory. A worker in pool A needs model files from storage that tenant A runs elsewhere, behind tenant A's firewall. Pod addresses change with every restart and mean nothing outside the cluster, so that firewall could never keep a list of them. Instead the Pod's traffic is sent out through TMM, in tenant A's VRF, and TMM rewrites the source to an address from tenant A's SNAT pool. Tenant A's security team allows exactly that one address. A Pod of tenant B that tried the same thing would arrive from tenant B's address and be dropped.

The objects behind it are F5's. An F5SPKSnatpool holds tenant A's egress address 203.0.113.201 in its addressList. An F5SPKEgress for namespace tenant-a names that SNAT pool in egressSnatpool, sets snatType to SRC_TRANS_SNATPOOL and lists tenant-a under pseudoCNIConfig.namespaces, which is what steers the namespace's outbound traffic into TMM through a VXLAN tunnel. There is one F5SPKEgress per namespace. Tenant B has its own, with 203.0.113.202. The fabric must also route 203.0.113.201 to TMM in VRF tenant-a, so the reply from the store comes back to TMM in the right table. Whether TMM announces that address itself or the route is set up on the fabric depends on the release and the design.

TMM keeps a record of each translation. The connection from 10.244.1.21:38412 leaves as 203.0.113.201:20114, and when the store replies to that address and port, TMM rewrites it back and hands it to the Pod. The owner's notes carry one hard warning about these objects on a running system: deleting and recreating an F5SPKEgress once removed another tenant's tunnel. Change the firewall policy instead of the egress object. The lesson on what leaves the factory goes through that in detail.

Chapter 15 of 20

What a VRF does not split

Packets are not the only thing tenants can share

It is tempting to stop at the network: give every tenant a VRF and call it isolation. A VRF separates packets. It knows nothing about what happens once two requests are inside the same GPU. If both tenants' routes pointed at one pool, their requests would sit in one queue and their prompts would be kept in one KV cache. A prompt that starts like one already cached gets its first token sooner, whoever sent the first one, and that speed can be measured from outside. So the rule is one layer per thing to separate, and none of them stands in for another.

The timing leak works because of how vLLM's prefix cache finds blocks. It splits a prompt into blocks of tokens and hashes each block together with the hash of the block before it. A new request whose first blocks hash the same as blocks already in memory reuses them and skips that part of the prefill. A caller who sends a guess and sees a much faster first token learns that someone else sent the same beginning recently. On a shared pool, that someone could be another tenant.

vLLM has a per request answer for pools that must be shared. A request can carry a cache_salt field in its JSON body, and vLLM mixes the salt into the hash of the first block. Because every later block's hash includes the one before, requests with different salts can never reuse each other's blocks. vLLM's documentation names timing attacks as the reason the feature exists. A gateway that sets cache_salt to the tenant's name keeps the cache shared within a tenant and separate between tenants. Separate pools remain simpler, because they also separate the queue.

Chapter 16 of 20

A third tenant is a pull request

Adding a tenant must not move the others

Tenants arrive and leave all the time. F5's deck on multi tenant AI factories lists churn as a problem in itself: a new or departing tenant must not destabilise the shared fabric. With the layers in this lesson, adding tenant C is a set of new objects and nothing else. In the owner's lab, tenant C is Cobalt Labs, with VRF tenant-c, VNI 10003, TMM VLAN 103 and the range 10.203.100.0/24.

The order is the order of this lesson. Create the namespace tenant-c. Write an F5BnkGateway with tenant C's range and a VRF in TMM tied to VNI 10003, with route target 65000:10003. Configure the leaf with the same VRF and target. Then write tenant C's Gateway with its parametersRef, its HTTPRoute, its InferencePool and picker, its ResourceQuota, its NetworkPolicies, and its SNAT pool and egress object. The Gateway gets 10.203.100.10, TMM announces it about ten seconds after it is Programmed, and the leaf imports it into tenant C's table only.

Nothing in tenant A's or tenant B's objects changes, and their tables gain no routes. That is the test of a good tenant model: compare tenant A's routing table before and after, and it must be identical. It is also why the owner's notes warn against deleting and recreating shared egress objects on a running system, because that is the one place a change for one tenant once reached another. Removing tenant C is the same list in reverse, with the 25 second route withdraw in mind. A 24 bit VNI leaves room for about 16.7 million tenants on the wire, so the numbering never runs out first.

Chapter 17 of 20

The Pods' side of the same tenant

A proposal: give each tenant's Pods a network of their own

Everything up to here separates tenants where traffic crosses TMM. The Pods themselves still share one Pod network, and the only wall between them is the NetworkPolicy from the chapter on the Pod network. The owner's controller project, which connects BNK to the networking an OpenShift based AI factory already runs, wrote down a proposal for closing that gap with the cluster's own network plugin. It is a proposal. The owner's lab did not build it, and everything in the next four chapters that is not a quoted lab result is a design, with illustrative values.

On OpenShift the network plugin is OVN-Kubernetes. On OpenShift 4.22 it can give a group of namespaces a user defined network, a separate layer 2 or layer 3 segment that is isolated from every other network by default. The cluster scoped form is a ClusterUserDefinedNetwork, CUDN for short, in API group k8s.ovn.org/v1. With role Primary it becomes the main network of the Pods in the namespaces it selects. In the proposal each tenant gets one: CUDN tenant-a selects namespace tenant-a, CUDN tenant-b selects namespace tenant-b. OVN-Kubernetes also creates a Linux VRF on each node for the CUDN, and Red Hat's examples show it named after the CUDN, so tenant-a is a routing table on every node as well as on TMM and the leaf. Linux limits interface names, VRF devices included, to 15 characters, so keep CUDN names short and check the VRF's real name on a node with ip vrf show.

A Layer3 CUDN takes a cidr and a hostSubnet. With cidr 10.110.0.0/16 and hostSubnet 24, each node gets its own /24 out of the /16, so 256 nodes can each have a /24 of 256 addresses. A few addresses of each /24 cannot go to Pods, such as the network address and the node's own gateway address, so slightly fewer than 256 are left for them. Tenant A's worker qwen3-6f7d9c8b4-x7k2p on gpu-node-1 would get an address from that node's /24, for example 10.110.1.21, while it keeps an address on the cluster default network for infrastructure traffic. Tenant B gets 10.120.0.0/16 the same way.

The Red Hat documentation lists limits that change how a factory runs. A namespace used by a primary CUDN must carry the label k8s.ovn.org/primary-user-defined-network, and that label can only be added when the namespace is created. The network must exist before the Pods, and OVN-Kubernetes refuses a UDN for a namespace that already has Pods. So moving tenant A onto its own network means a new namespace and new Pods, and each vLLM Pod spends about three minutes loading the 34.3 GB Qwen3-32B-FP8 weights again. A NetworkPolicy that tries to allow traffic between namespaces on two different primary UDNs has no effect, because the networks are not connected at all. DNS still answers with the Pod's default network address. Kubelet health checks also run over the default network, so a Pod can look healthy while its primary interface is broken.

That last limit is what the owner hit with BNK. On OpenShift 4.22 with BNK 2.4.2 in host mode, a backend on a primary UDN got a programmed VIP and requests that timed out. BNK takes its backend addresses from the Service's ordinary EndpointSlice, which lists the Pods' default network addresses. Under a primary UDN those addresses are for infrastructure only: Pods on the default network cannot open connections to them unless the Pod opens specific ports with the annotation k8s.ovn.org/open-default-ports. The lab recorded the programmed VIP, the timeouts and where the backends came from, and nothing about probes. Red Hat's documented limit gives a likely reason the Pods still looked healthy: kubelet probes run over the default network, so a readiness probe can pass while TMM cannot reach the Pod. The lab's real namespace was tenant-b on 10.201.0.0/16, and the owner's controller now refuses such a namespace with the reason, instead of reporting a Ready exposure that cannot carry traffic. This is why the lab keeps tenant isolation in BNK's own VRFs and VLANs today, and why the proposal keeps BNK's side of each tenant in BNK's own objects.

Chapter 18 of 20

Advertising the Pods with BGP

RouteAdvertisements and FRR-K8s put each tenant's Pod routes into its own table

A tenant network that nothing outside the cluster can route to is only half useful. OVN-Kubernetes can announce Pod subnets to the data center with BGP, and on OpenShift this is called route advertisements. It is switched on in the cluster's Network operator configuration with two settings: spec.additionalRoutingCapabilities.providers set to [FRR], which deploys the FRR-K8s daemon on every node, and spec.defaultNetwork.ovnKubernetesConfig.routeAdvertisements set to Enabled. FRR-K8s is FRRouting, the open source routing suite, wrapped so that Kubernetes objects configure it. It runs in the namespace openshift-frr-k8s and is the same deployment that MetalLB uses when MetalLB is installed.

Two objects then do the work. An FRRConfiguration, in API group frrk8s.metallb.io/v1beta1, says who the nodes peer with: a router with the cluster's AS number and a list of neighbors, each an address and an AS number. A RouteAdvertisements object, in k8s.ovn.org/v1, says what to announce and where. Its advertisements list can hold PodNetwork and EgressIP. Its networkSelectors pick networks, here ClusterUserDefinedNetworks with a matching label. Its frrConfigurationSelector picks the FRRConfiguration by label. Its targetVRF decides which routing table the routes are announced in. Left out, it means the default VRF. Set to auto, it means the VRF named after each network, so CUDN tenant-a is announced in VRF tenant-a and CUDN tenant-b in VRF tenant-b. A healthy object shows STATUS Accepted in the output of oc get ra.

With targetVRF auto and no EVPN, the design is VRF-lite. Each tenant VRF needs its own link to the fabric, usually a VLAN interface placed in the VRF, and its own BGP session on that link. On this lesson's two GPU nodes with two tenants that is four VLAN interfaces and four BGP sessions. With 100 tenants it is 200 of each, all of them configured on the leaf too. That growth is the reason for the next chapter.

Some limits matter for a factory. Pod network advertisements must come from all nodes, so the nodeSelector has to select every node when PodNetwork is listed. Route advertisements announce Pod and CUDN subnets and egress IP addresses. They do not announce Services. On OpenShift, Service addresses of type LoadBalancer are announced by MetalLB, and BNK announces its own VIPs from TMM, as the earlier chapters showed. Red Hat supports BGP route advertisements only on bare metal infrastructure. The owner's lab is OpenShift 4.22.22 on virtual machines with platform None, so the proposal lists checking whether RouteAdvertisements work there at all as the first test, followed by how TMM's own BGP sessions share the same fabric router.

Chapter 19 of 20

One VTEP, at most 4,094 tables

EVPN on a primary CUDN, and the limit that comes from the Linux bridge

OpenShift 4.22 adds BGP EVPN for primary CUDNs, and it replaces the per tenant VLANs and sessions of VRF-lite with one multiprotocol BGP session from each node to the fabric. This is the same EVPN the earlier chapters read byte by byte on TMM. Each node becomes a VXLAN tunnel endpoint, a VTEP, and each tenant network becomes an EVPN instance. EVPN offers two kinds. A MAC-VRF stretches a layer 2 segment across the fabric, for traffic that must stay bridged, such as a virtual machine moving between nodes. An IP-VRF gives the network routed layer 3 reachability and uses type 5 routes like the ones TMM sends. A Layer3 CUDN uses an IP-VRF only. A Layer2 CUDN uses a MAC-VRF and can add an IP-VRF on top.

The setup has four objects and a gateway change. The Cluster Network Operator must run with gatewayConfig.routingViaHost true and gatewayConfig.ipForwarding Global, so packets leave through the host's routing stack where FRR and the VXLAN device live. An FRRConfiguration defines at least one BGP router in the default VRF, the underlay session. A VTEP object, kind VTEP in k8s.ovn.org/v1, sets mode Unmanaged and a list of IPv4 cidrs. In Unmanaged mode OVN-Kubernetes does not hand out addresses. Each node must already carry one address from that range as the primary address of an interface, and the documentation suggests a dummy interface set up with an NMState NodeNetworkConfigurationPolicy so the address does not depend on one cable. A healthy VTEP shows Accepted True with reason Allocated. Then a RouteAdvertisements object selects the CUDNs, and the CUDN itself is created with transport EVPN and an evpn block naming the VTEP and the VRF's VNI and route target. A healthy CUDN shows reason EVPNTransportAccepted. EVPN cannot be switched on for an existing CUDN, because its spec is immutable, so a tenant that started without it moves to a new network.

Here the proposal meets the rest of this lesson. If CUDN tenant-a uses ipVRF vni 10001 and routeTarget 65000:10001, the same values TMM uses for tenant A, the leaf imports the Pod subnet and Gateway A's address into the one VRF tenant-a. Tenant A's Pods and tenant A's VIP then sit in one routing table across the whole fabric, and tenant B's 10.120.0.0/16 with VNI 10002 stays in another. The route targets are written by hand here because the automatic form builds the target from the local AS number and the VNI. The cluster is in AS 65200, so it would derive 65200:10001, while TMM's routes for tenant A carry 65000:10001 and the two would never import each other's routes. Writing the same value on both sides makes them match.

The limits are hard numbers. VTEP addresses must be IPv4, because FRR, which runs the EVPN control plane, does not support IPv6 VTEPs here. The VXLAN destination port is 4789 and cannot be changed. Each VTEP holds at most 4,094 MAC-VRF and IP-VRF instances combined. The reason is in the data path: OVN-Kubernetes uses one shared VXLAN device per VTEP and maps a VLAN ID to each VNI on that device, and a Linux bridge has 4,094 usable VLAN IDs. So a node can carry 4,094 Layer3 tenants with an IP-VRF each, or 2,047 Layer2 tenants that use both a MAC-VRF and an IP-VRF. The 24 bit VNI field has room for 16,777,216 values, about 4,098 times more, so on these nodes the bridge runs out long before the numbering does. Only Pod subnets are announced over EVPN. EgressIP, IPsec, egress services and IP-VRF multicast are unsupported with EVPN, and Services of type NodePort, External IP and LoadBalancer work only where the fabric can already reach the node and Service addresses. Like route advertisements, EVPN on primary CUDNs is supported only on bare metal.

Chapter 20 of 20

Following the fabric's own controller

Netris and NVIDIA's fabric stack as sources to read, never to program

Many factories already run a fabric controller that knows which servers belong to which tenant. The proposal's second half reads that knowledge instead of asking anyone to type it twice. The controller in the owner's project has two modes. In push mode a portal or a custom resource tells it what to expose. In follow mode an adapter watches an infrastructure controller and derives exposures, the controller's word for a BNK Gateway, route and pool in front of a group of backends, from what that controller already knows. Follow adapters exist for OVN-Kubernetes, NVIDIA NICo, Netris and a static inventory. A rule in the design is that they only read: nothing is programmed on a switch by this controller.

Netris is a commercial fabric controller that models tenants as VPCs and drives the switches. Its REST API has no webhooks, so the adapter polls it. In phase 5 of the owner's project a real Netris 4.6.0.2 controller ran inside the OpenShift lab from Netris's public Helm chart, as one replica, with no switches behind it, so the test covers the controller's API only. Netris's production sizing is three nodes of 8 cores and 32 GB each, plus a licence. A seed script created a site, IPAM, three servers and a server cluster lab-gpu-a tagged role=inference, all through Netris's API. The adapter turned that cluster into an exposure named infer-lab-gpu-a in namespace fabric-netris, Ready on 10.210.100.14 with the three servers as backends and owner fabric:netris. That Ready came with one lab setting. With no switches and no licence, Netris never moves a server cluster out of Provisioning, so the lab set the adapter's readyStates to [active, provisioning] and counted Provisioning as ready. Production keeps the default, active only. Then the test deleted the cluster in Netris. The exposure was removed 12.5 seconds later and the VIP was withdrawn from the BGP fabric 17.2 seconds after that, 29.7 seconds from the change in Netris to the route leaving the fabric.

NVIDIA's fabric stack is the other proposed source, through two APIs. Cumulus Linux switches expose NVUE, their configuration model, as a REST API on port 8765 under /nvue_v1/. A change there is a revision: POST /nvue_v1/revision creates one, PATCH requests with ?rev= set values such as a VRF's BGP settings under /nvue_v1/vrf/, and a PATCH of the revision with state apply makes it live. NetQ, NVIDIA's monitoring and validation service for the fabric, has its own REST API for reading state across switches. An adapter for these two would read VRFs and routes and never write a revision. Without switches in the lab, the proposal points at NVIDIA's hosted simulation, DSX Air, which has a free trial.

The proposal also says why OVN-Kubernetes comes first and these second. OVN-Kubernetes is already in every OpenShift cluster and is driven by Kubernetes objects, so the controller can watch it with no new credentials and no polling. VMware NSX needs vCenter and an NSX Manager, which a standalone ESXi host does not have. Replacing OpenShift's network plugin with Cilium or Calico is not supported. The ownership split is plain. OVN-Kubernetes owns each tenant's workload network and its advertisement. BNK owns each tenant's VIPs through its Vrf, F5SPKVlan and RoutingConfig objects. The fabric, EVE-NG routers in the lab and Netris or Cumulus in production, is read and never written. What phase 6 did build is a BnkTenant with its own F5BnkGateway address pool, .40 to .49, announced over plain BGP to an FRR router in AS 65000. EVPN was not done there.

What to keep

Five lanes, none optional

A tenant in an AI factory is a stack of separations, each made of ordinary Kubernetes objects. An F5BnkGateway gives it an address range and IPAM keeps the record, as long as every Gateway carries the reference. BGP EVPN announces those addresses as 34 byte type 5 routes tagged for one routing table, and VXLAN carries the tenant's number on every packet at a cost of 50 bytes, so two tenants can even use the same addresses. One TMM holds a VRF and a Gateway per tenant, and the Gateway API keeps each tenant's routes and backends in its own namespace. Each Gateway routes to an InferencePool of its own, with budgets and a GPU quota in front, which is what keeps one tenant's flood out of another's queue and one tenant's prompts out of another's cache. Inside the cluster a default deny NetworkPolicy does the job the VRF cannot. On the way out, a SNAT pool gives each tenant one address the outside can trust. Leave any layer out and the others don't cover for it.
