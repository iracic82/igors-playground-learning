Running a GPU cloud

What turns GPU servers into a GPU cloud

The operations layer, self-service, the catalogue, build or buy, and the step from an AI factory to a cloud service

Northlight Compute owns three servers with four H100 GPUs each, twelve GPUs in all. They are racked, cabled, cooled and healthy. One of them can run vLLM serving Qwen3-32B from its FP8 build, whose 34.3 GB of weights fit on one 80 GB H100 with room left for the KV cache. None of that makes Northlight a cloud. A stranger cannot yet pick a product, pay for it, receive a server in a network of its own, see what it used and hand it back, all without someone at Northlight doing the work by hand. This lesson is about the software and the habits that sit between the hardware and the customer. It starts from the five tests in NIST's definition of cloud computing and the three readiness states that separate a working GPU from a sellable one. Then it separates hosting from cloud, untangles the words cloud GPU, GPUaaS and GPU cloud, and shows what self-service really demands. It shows how an inventory becomes a catalogue, how the same hardware, in an example data centre of twenty servers, can be sold two ways, why an AI factory is a different thing from a cloud service, how to weigh building the layer against buying it, and how to check readiness before the first customer orders. The other lessons in this track teach each step in depth. This one shows how they fit together, and what has to exist before any of them matters.

Chapter 1 of 16

Five tests from NIST

A 2011 definition that still decides whether GPU servers are a cloud

The definition most people quote is NIST Special Publication 800-145, written by Peter Mell and Timothy Grance and published in September 2011. It is seven pages long. It calls cloud computing a model for on-demand network access to a shared pool of configurable computing resources that can be rapidly provisioned and released with minimal management effort or service provider interaction. It then names five essential characteristics, three service models (SaaS, PaaS and IaaS) and four deployment models (private, community, public and hybrid).

The five characteristics work as five tests. On-demand self-service: a consumer can unilaterally provision computing capabilities, such as server time and network storage, as needed automatically without requiring human interaction with each service provider. Broad network access: the capabilities are reached over the network through standard mechanisms. Resource pooling: the provider's resources serve multiple consumers using a multi-tenant model, with physical and virtual resources dynamically assigned and reassigned according to demand, and the customer generally has no control over or knowledge of the exact location, but may be able to specify it at a higher level, such as a country, a state or a data centre. Rapid elasticity: capabilities can be provisioned and released quickly, and to the consumer they often appear unlimited. Measured service: the system meters use at a level that suits the service, so usage can be monitored, controlled and reported to both sides. A footnote adds that this is typically done on a pay-per-use or charge-per-use basis.

Apply them to Northlight's twelve GPUs. Broad network access is the easy one: an SSH login and an HTTPS API over the internet already pass it. Resource pooling does not require two tenants on one GPU. A whole server rented to tenant A this month and wiped and rented to tenant B next month is a physical resource reassigned according to demand. The hard tests are the first and the last. Self-service fails as long as a person at Northlight must act on every request. Measured service fails as long as nobody can say which tenant held which GPU for how long.

A second footnote in the same document gives this lesson its shape. It calls the cloud infrastructure the collection of hardware and software that enables the five characteristics, with a physical layer of servers, storage and network and an abstraction layer of software deployed across it, which manifests the essential characteristics. The three servers are the physical layer. The rest of this lesson is about the abstraction layer.

Chapter 2 of 16

Hardware-ready, AI-ready, service-ready

Three states that are easy to mistake for one another

A GPU server passes through three states of readiness, and each one answers a different question. Hardware-ready means the GPUs, servers, network and storage are installed and healthy. The questions are physical: does nvidia-smi list four H100 cards, does the fabric pass traffic at line rate, is the storage mounted, can the fleet be monitored. AI-ready, also called workload-ready, means training, fine-tuning and inference actually run. The driver, CUDA, the container runtime and a scheduler are in place, and a model answers. Service-ready means customers can select, order, receive, consume, measure and end a service through workflows that repeat the same way every time.

Northlight can show the first two today. Its engineers started vLLM on gpu-srv-3 with the official FP8 build of Qwen3-32B. The 34.3 GB of weights loaded in about three minutes (an illustrative figure), and the server answered a test prompt. That proves the infrastructure runs AI. It proves nothing about a stranger's ability to order it, because no step of that demo involved an order, a tenant, a bill or a return to the pool.

The gap between the second and the third state is a list of jobs that have nothing to do with the GPU itself. A commercial service still needs a definition of what is sold, a way to order it, a way to find and hold free capacity, provisioning, network and storage set up for the tenant, tenant and access policy, scheduling, usage metering, billing, monitoring, management of the service level, deprovisioning, and recovery and recycling of the hardware. That is thirteen jobs. None of them can be bought with a faster GPU.

The confusion is common because the first two states are visible in a demo and the third one is not. A model answering a prompt looks like a product. What makes it a product is everything that happens before the first prompt and after the last one.

Chapter 3 of 16

The layer between the servers and the customer

Infrastructure, operations, service, and a loop that never ends

The simplest picture has three layers. At the bottom is the GPU infrastructure: GPUs, servers, network, storage and the data centre. At the top is the GPU cloud service the customer sees: a web console, an API, self-service and GPUs on demand. In between sits the cloud operations layer. On Northlight's board it is the row of boxes on the control plane: identity, catalogue and orders, scheduler, provisioner, metering and billing, with the portal and API as its front.

Each box has one job. The catalogue defines what can be ordered. Ordering and fulfilment connect a request to a real workflow. Identity and access control decide who may do what. The scheduler decides which GPUs go to which customer or workload. The provisioner turns free hardware into a usable environment. Isolation keeps tenants apart in identity, network, storage and data. Metering records who used what, for how long. Billing turns those records and the contract into charges. Observability and SLA management track health and the promises made. Lifecycle automation handles creation, termination, recovery, reset and reuse.

The boxes run as a loop. A customer finds a product in the catalogue, orders it, the platform provisions it, isolates it in the tenant's segment, schedules work onto it, meters it, bills it, holds it to its service level, recovers it when the customer leaves and recycles it into the pool, where the catalogue can offer it again. That is ten steps: catalogue, order, provision, isolate, schedule, meter, bill, SLA, recover, recycle. The loop is the reason a cloud is harder than a demo. A demo runs the first half once. A cloud runs the whole loop thousands of times and must end each pass with a server that is clean, counted and free.

The other lessons in this track each open one step. From an order to a server and back follows provisioning and recovery through OpenStack Ironic. A tenant is a boundary covers isolation. Why a job waits while GPUs are free covers scheduling and quota. Metering is not billing covers the four records from GPU counter to invoice. This lesson stays at the level of the loop.

Chapter 4 of 16

Hosting and cloud are two operating models

Same servers, different promises, and both are legitimate

GPU hosting means a provider assigns a server to a customer, usually for a long period, and operates it on the customer's behalf. Remote access is part of hosting too. A customer who can SSH into a rented H100 server in someone else's data centre is using hosting, unless the steps around that login also pass the tests from the first chapter.

Hosting is not the lesser model. It fits well when a dedicated server goes to one customer for a long period, when configuration rarely changes, when the commercial terms are fixed, when the number of customers is small and when the workflows are simple. A research lab that rents eight servers for two years, with a custom network design negotiated once, gains little from a self-service portal. Its order happens once. A person on each side is cheaper than an automated workflow nobody will run again.

Cloud becomes the better fit when the list on the other side grows. Customers want to choose resources themselves. There is more than one product. Resources must be created and released quickly. Other systems need an API. There are many tenants. Usage must be measured. Capacity must be recycled again and again. Each of these multiplies the cost of doing the work by hand, because every order, change and return repeats the same steps.

The two models live side by side on one portfolio. A provider can sell long-term dedicated hosting, reserved capacity, GPUs on demand and managed AI services from the same building. What has to be explicit is the capacity policy: which servers belong to which model, and whether a hosting customer's server can ever be lent to the on-demand pool. On Northlight's board, tenant A's reservation on gpu-srv-1 behaves much like hosting: one customer, a long term, a fixed price of 4,000 units per GPU-hour. Tenant B on gpu-srv-2 orders on demand at the list price of 5,000 and may leave at any hour. Both run through the same operations layer.

Chapter 5 of 16

Cloud GPU, GPUaaS, GPU cloud and neocloud

Words that overlap, and the questions that matter more than the label

Four words get used as if they meant the same thing. There is no enforced taxonomy, so any definition is a working one. A useful split is this. A cloud GPU is one GPU resource or GPU instance obtained from a cloud. GPU as a Service, GPUaaS, is the service and consumption model: GPU compute obtained as a service instead of owned. A GPU cloud is the broader environment that delivers and operates those resources. A neocloud is a recent market term for providers built mainly around GPUs and AI workloads. None of them is a NIST service or deployment model.

GPUaaS is often mistaken for two other things. It is not a virtualization technology. The same operations layer, with its catalogue, provisioning, allocation and scheduling, metering, observability and lifecycle, can deliver GPU virtual machines, containers, whole dedicated GPUs, bare-metal servers, multi-node clusters, or an internal GPU service for a company's own teams. Bare metal can be GPUaaS. It is also not a billing method. GPUaaS is not always pay as you go. It can be reserved, a subscription, a contract, or internal chargeback, where teams are charged internally for what they used, or showback, where they are only shown it.

On demand carries the same confusion. On demand describes how capacity is requested and released. It does not mean shared GPUs, virtual machines or spot capacity. Spot capacity is spare capacity the provider may take back under stated terms. On demand also does not promise instant capacity. GPU availability depends on the model, the server shape, the site and existing reservations, so an on-demand request can still wait. Reserved and on-demand are not opposites either. Northlight can reserve gpu-srv-1 for tenant A and keep the other two servers for on-demand orders, and its capacity policy decides how the two pools interact. The form of the resource and the way it is consumed are separate decisions.

The label matters less than the scope. When comparing offers, ask what is delivered: a raw server, or drivers, containers, Kubernetes, frameworks, model serving and monitoring too. Ask how it is provisioned and how fast. Ask how it is operated, measured and released. Two services using the same GPU model can give different results, because interconnect, storage throughput, topology and the software stack all differ.

Chapter 6 of 16

A GPU cloud runs more than language models

Twelve kinds of work, and why each one asks for a different card or a different form

This site follows one workload, Qwen3-32B served by vLLM. A GPU cloud's catalogue has to answer for many more. The articles in Thaki Cloud's insights series list them again and again, and the lists agree. Foundation model training. Fine-tuning. Evaluation, the runs that score a model before it is released. Batch inference, where a large set of inputs is processed with no user waiting, and real-time inference, where a user waits for each answer. RAG, retrieval-augmented generation, and agents, which call models many times per task. Computer vision. Speech and language AI. HPC and simulation: scientific computing, engineering simulation, molecular modelling and weather models. Rendering and media: 3D rendering, visual effects, VFX, video processing and virtual production. GPU-accelerated analytics. And virtual desktops, VDI, which the series names as a reason to choose a virtualized GPU over bare metal.

They do not ask for the same thing. Training and HPC use the processors, memory, GPUs, network and storage as one tightly coupled system, so they want whole servers, fast links between GPUs and bare metal. Many HPC codes compute in double precision, FP64, with 64-bit numbers. NVIDIA's table for the H100 SXM gives 34 teraFLOPS of FP64 and 67 teraFLOPS of FP64 on its Tensor Cores. Language models run in BF16 or FP8 instead, where the same card is quoted at 1,979 teraFLOPS of BF16, a figure NVIDIA marks as with sparsity. A pool sized for one kind of arithmetic may be the wrong pool for the other.

Rendering, media and desktops ask for parts an H100 does not list. NVIDIA's H100 table lists video decoders, 7 NVDEC and 7 JPEG, and no video encoder and no RT Cores. The L40S page lists third-generation RT Cores for ray tracing, 3 NVENC encoders and 3 NVDEC decoders with AV1, four DisplayPort outputs and vGPU support, on 48 GB of memory. A render farm or a VDI service is therefore usually built on cards like the L40S, sold as GPU VMs. NVIDIA's vGPU guide lists Q-series vGPU types on the L40S, the workstation profiles, as supporting CUDA and OpenCL, so a designer's virtual workstation can also run compute. The L40S page lists MIG as not supported and NVLink as not supported, so an L40S service is split into vGPUs and grows by adding more cards.

Inference outside language models has its own toolkits. Computer vision on video streams uses NVIDIA DeepStream, which takes camera, file or RTSP streams and uses hardware plugins built on NVDEC and NVENC, so decoder count matters as much as compute. Speech runs on toolkits such as NVIDIA Riva, whose server performs streaming and batch speech recognition and speech synthesis. These services are latency bound like a chat model, and a voice request carries recognition and synthesis on top of the model's own time. GPU analytics can be as simple as RAPIDS cuDF's pandas accelerator mode, cudf.pandas, which runs supported pandas operations on the GPU and falls back to the CPU library for the rest, so a data team's existing scripts become GPU work.

The catalogue follows from this. Northlight's twelve H100 GPUs suit training, fine-tuning, LLM inference and FP64 work. The FP8 build of Qwen3-32B, 34.3 GB of weights, would also fit on one 48 GB L40S, with 13.7 GB left before the runtime's own memory and the KV cache are counted. The BF16 build, 65.5 GB, would not fit on one L40S at all. A provider that wants rendering, VDI and video analytics customers adds a second kind of server and a second set of products, sold mostly as VMs, and keeps the operations layer the same. Each product in the catalogue should say which of the twelve kinds of work it is meant for.

Chapter 7 of 16

Self-service is an operating model

A Request button with a ticket queue behind it is still manual

A portal can look self-service while people do the work behind it. The customer clicks Request for a GPU server. An operations engineer reads a ticket, checks a spreadsheet for a free machine, configures the switch port, creates an account and emails the login. That is a valid way to run a business. It fails NIST's first test, because a person acts on each request.

End-to-end self-service means the request flows through policy, capacity, provisioning, service state, usage and recovery without anyone rebuilding the workflow each time. Take one order: one 4 × H100 bare-metal server for seven days. The platform validates the customer and its entitlement, the right to order this product. It checks the organisation's policy and quota. It confirms capacity exists and reserves it. It provisions compute, network and storage. It creates credentials and access. It exposes the right state to the customer. It records usage. At the end it terminates the service, cleans the server and returns it to the pool. That is ten steps. The portal is only the entry to them. Seven days are 168 hours, so the order covers 4 × 168 = 672 GPU-hours, which at the on-demand list price of 5,000 units comes to 3,360,000 units.

Three misreadings follow from treating self-service as a screen. A portal is not required: an API is a self-service interface, and many orders come from pipelines, schedulers and developer platforms that never open a browser. Self-service does not mean every request is approved: quota, entitlement, approval policies and capacity still apply. Self-service and on demand are related but separate: self-service is how the customer asks and controls, on demand is whether capacity can be requested and released as needed. A reserved product can be ordered through self-service, and an on-demand request can still wait for approval.

Self-service also needs no virtualization and no shared GPUs. OpenStack Ironic provisions whole physical servers through an API. Its node multi-tenancy feature lets non-admin projects act on nodes through the API, limited by policy. A node's lessee field names a project that gets temporary, limited access, and Ironic can fill it in automatically at deploy time. A dedicated server becomes a self-service product once reservation, provisioning, access, state and recovery are connected.

The quality of self-service shows in failure. If the GPUs are reserved and the network step fails, the platform must decide whether to retry, whether to keep or release the reservation, whether to clean up what was built, what state the customer sees, and that billing does not start. The lesson From an order to a server and back follows exactly that case through order ord-1043.

Chapter 8 of 16

What the operations team does instead

Self-service moves people to the work machines cannot do

A common fear is that end-to-end self-service removes the operations team. It moves it. In the portal-only model engineers spend their day on the ordinary case: reading tickets, matching requests to servers, configuring ports, creating accounts. In the end-to-end model the platform handles the normal, repeatable flow, and people work on five things it cannot.

Policy: which products exist, which tenants may order which ones, what quotas and approval thresholds apply, and what the capacity policy between reserved and on-demand pools is. Exceptions: the order that hit a quota, the customer who needs a network design the catalogue does not offer, the order stuck in a state longer than it should be. Capacity: watching how much can actually be sold now, which is less than what is installed, and deciding when to buy, move or retire hardware. Incidents: a GPU throwing errors, a switch dropping a tenant's segment, a cleaning step that fails. Service quality: provisioning time, support response, failure recovery and maintenance notices, the things an SLA promises.

The difference shows in where the time goes. In a portal-only model, every order costs engineer time in proportion to the number of orders. In an end-to-end model, engineer time goes into designing and fixing the workflow, and each extra order costs almost none. The owner's AI Grid deck describes the state many GPU operators start from: fleet operations were artisanal, and provisioning, tenancy, configuration drift and fault remediation were all home grown and expensive to maintain.

The owner's same deck states the goal for providers that rent bare metal: tenants should not be over-privileged, the infrastructure should be tenant self-serviced and API driven, and the customer should get the look and feel of the public cloud with AI performance. Reaching that takes people who write policy and handle exceptions. Fulfilling tickets by hand stops being their job.

Chapter 9 of 16

Inventory, price list and catalogue

What exists, what it costs, and what a customer can order

Picture a data centre with one hundred GPU servers. Operations knows each server's GPU type, memory, network connection, rack position and status. That is an inventory. A customer still cannot order from it, because customers do not order asset IDs. They order products: a dedicated eight-GPU server, a GPU virtual machine, GPU capacity for a fixed period, a defined bundle of compute, storage and network.

Three records are easy to mix up. The inventory says what exists, what is free, what is in use and what is under maintenance. The price list says what things cost. The catalogue says what a customer may order and on what terms. A catalogue item references the inventory, through the kind of hardware it maps to, and references the price list, through the rate it is sold at. It is neither of them.

A catalogue item can hold many fields, and not every service needs all of them: a product code, GPU type and count, form (bare metal, VM or a workload), CPU and memory, network options, storage options, duration and reservation rules, site or region, eligibility and quota, price or contract mapping, a provisioning template, a termination and recovery policy, and the support or SLA scope. The provisioning template is what connects the product to the build. Ironic's own documentation gives the idea of a resource class: an order for the product becomes a request for any available node of that class.

Productization is the real work behind a catalogue. It changes the question from what do we own to what can the customer buy. A good catalogue does not expose every option or every GPU model. It offers a few products that customers understand and operators can fulfil the same way every time. Northlight offers two bare-metal products and hides the rest: the BMC addresses, the racks, the firmware levels and the serial numbers stay in the inventory.

One name causes confusion. OpenStack Keystone also has a service catalog. Keystone's documentation describes it as an endpoint registry used for endpoint discovery. It tells an API client where the compute, image or bare-metal APIs of a cloud are, and an operator fills it with openstack service create and openstack endpoint create. It has nothing to do with products, prices or terms. A cloud built on OpenStack has both, for different jobs.

Chapter 10 of 16

A product the pool cannot deliver today

The catalogue must not drift away from what the hardware can do

A catalogue item can exist while the capacity behind it does not. Northlight's on-demand product draws on gpu-srv-2 and gpu-srv-3. Tenant B holds gpu-srv-2. If gpu-srv-3 is in cleaning when a new order arrives, the product is listed and nothing can fulfil it this minute.

The platform must decide how an order maps to real supply, and there are five honest answers. Real-time availability shows the customer, before ordering, whether the product can be delivered now. A reservation holds a future slot, such as gpu-srv-3 from tomorrow 09:00. A wait state accepts the order and queues it with a visible status. An approval policy sends the order to a person when it is unusual. An alternative offer proposes a different product, site or start time. What fails is the silent case: an order accepted as if capacity existed, followed by a ticket and a delay nobody announced.

The catalogue must also connect to provisioning. If a customer orders bm-4xh100-od, the platform must know how to build it: which servers qualify, which image, which network segment, which storage, which credentials, and what completion means. In the order lesson completion means the customer can log in and see four GPUs.

The catalogue must agree with billing too. If the product says seven-day dedicated reservation, metering records GPU utilization and billing charges virtual machine runtime, the service has three definitions of the same thing, and the customer will find the gap on the invoice. The product definition, the state of the order, the usage record and the price rule have to describe one thing.

The opening question from Thaki Cloud's insights series makes this concrete. A first external customer asks for eight GPU servers for one week, when it can have them, what it will cost and what happens when the week ends. Northlight has three servers, so the honest answer is an alternative or a wait. A provider with twenty servers needs to know how many are free now, how many are reserved, how many are cleaning or broken, and which ones fit the product. The number that matters is how much can be provisioned to customers now. The installed count only sets its upper limit.

Chapter 11 of 16

From hosting to cloud on the same hardware

An operating-model change, done in six stages

Consider a data centre with twenty servers of eight GPUs each, 160 GPUs. In a hosting model a customer calls sales, negotiates a contract, and receives a dedicated server through a delivery that several teams coordinate. In a cloud model the same hardware is an orderable product, and a request flows through entitlement, capacity, reservation, provisioning, access, usage and termination. Nothing in the racks changes. The difference is the operating layer around the asset.

Before building anything, check what can be reused. Is there a reliable GPU and server inventory. Does every server have a BMC, the management controller that powers and boots it remotely, through Redfish or IPMI. Can the network be configured by software, and can storage be attached the same way. Can an image be deployed and the server reset without hands on it. Is there monitoring that reports resource state. Which servers are alike enough to become one product. OpenStack Ironic shows that physical servers can be provisioned and managed through an API, but each site still has to prove its own hardware, network and storage integration.

The move happens in six stages, and each one can be done incrementally. First, capacity and inventory. Second, the service catalogue and its product codes, called SKUs, stock-keeping units. Third, customers, tenants and policy. Fourth, standard provisioning. Fifth, metering joined to billing. Sixth, lifecycle, recovery and operations. Self-service does not have to replace enterprise sales. Large customers still negotiate reservations, network designs and service levels, and the self-service layer takes the repeatable requests.

The goal is repeatability and consistent state, and total automation is optional: every order passes through the same steps, and every server is always in a known state. Recovery time shows why. Suppose each rental lasts seven days. A manual turnaround of two days, 48 hours, and an automated one of one hour differ by 47 hours per rental. On an eight-GPU server that is 47 × 8 = 376 GPU-hours that cannot be sold, worth 1,880,000 units at the list price of 5,000. If each of the twenty servers is rented three times a month, that is 60 rentals, 22,560 GPU-hours and 112,800,000 units a month lost to waiting. The whole fleet holds 160 × 720 = 115,200 GPU-hours in a 30-day month, so manual turnaround alone costs about 19.6% of it.

Chapter 12 of 16

An AI factory is not yet a cloud service

Running AI well for your own people and selling it to others are two stages

An AI factory is the infrastructure and operating environment for producing and running AI at scale: GPU clusters, fabric, storage, data pipelines, and the platforms for training, fine-tuning and inference. On this scene the factory serves its callers through the BNK data plane, a key service, an endpoint picker and three GPU workers. It can be excellent at that and still not be a cloud service.

An internal factory has its own priorities: access, quota, provisioning, scheduling, observability, capacity planning, visibility of who used what, and lifecycle. Its users are the company's research, data science and product teams. Nobody needs a public price, an invoice or a self-service console for strangers. The step to a customer-facing service adds a different set: a catalogue, ordering, management of customer organisations and tenants, a self-service console, external APIs, metering that can be billed, billing or settlement, service levels, and support workflows. Infrastructure operations become service operations.

Not every factory should take that step. Internal research, restricted workloads, dedicated production inference and internal training are all good reasons to stay internal. Having the technical ability to serve others does not create a business reason to. The step makes sense when an owner wants to sell capacity, turn infrastructure into products, or give several organisations self-service access.

Telecom operators show why the step is hard. The owner's AI Grid deck describes telcos and CDN providers with distributed sites and power already in place, and lists what they lack as commercialization plumbing: hard multi-tenancy, role-based access control, token metering and a marketplace, the pieces a telco needs to sell inference and not only run it.

The beats follow one request twice. First an employee of the factory's owner calls Qwen3-32B with an internal key. Then a tenant's application calls the same model. The path through the data plane and the picker is the same. What changes is what the key service has to know and keep: whose key it is, which tenant pays, the budget, and a usage record per tenant built from the token counts the model server itself returns. The owner's BNK blog draft counts tokens from the model's own answer, so the bill matches what the client sees.

Chapter 13 of 16

A dashboard is not an operations platform

Monitoring reports what happened. Operating means running the workflow from request to reuse

Building a factory and operating it every day are two separate problems. The build is GPUs, servers, network, storage, Kubernetes or another container platform, frameworks and data platforms. Operating starts when people use it, and new questions arrive with the first users. Several teams ask for GPUs at once. One project could take the whole cluster. Production inference may need priority over experiments. A GPU goes bad. A large job waits while some GPUs are free. Someone has to decide when to buy more. Those are operating questions. Buying hardware answers none of them.

A GPU dashboard answers some of what an operator needs. Northlight's dashboard reads DCGM counters every 30 seconds and shows each card's utilization, memory, temperature and errors, and whether each node is healthy. It still leaves the important questions open: who is asking for resources, what each team's quota is, which workload runs first, how a server is prepared without a person, why a job is pending, how a server is taken back, and how much each team or project used. Monitoring provides information. It does not run the workflow. Observability goes one step further than monitoring, because it joins infrastructure metrics to workload state, usage and operational events. That join is what answers which team uses the most capacity, why a job is pending, which node keeps failing, why GPUs are allocated and still idle, whether a queue grows from too little capacity or from fragmentation, and whether a failed server can safely return to the pool.

The series gives the lifecycle an operations platform has to connect in seven steps. Request: users and teams ask for resources. Provision: compute, network and storage are prepared. Schedule: each workload is placed on a suitable GPU or node. Run: training, fine-tuning, inference. Observe: health, performance and usage are checked. Manage capacity: demand, quotas and available resources are adjusted. Recover and reuse: resources are cleaned up, repaired if needed, and recycled. Recover and reuse covers both endings. When work ends normally the platform reclaims the resources, removes credentials, detaches network and storage, resets the environment, runs health checks and returns the server. When something fails it isolates the bad resource, recovers the workload, repairs or validates the hardware, and only then returns capacity to the pool.

When each step lives in its own tool, or in a manual process, the operators become the integration layer. Picture Northlight before its platform. Requests arrive in a ticket queue. A spreadsheet says which server is free. A provisioning script runs from an engineer's laptop. The scheduler is Kubernetes on one cluster and a calendar for the bare-metal servers. The dashboard is Grafana. Capacity planning is a monthly meeting. Cleaning is a checklist. Seven steps, seven places, and a person carrying each fact from one to the next. Every copy is a chance to forget something: a reservation never released, a credential never removed, a server returned to the pool before its health check. The platform's job is to connect the steps through policy and workflow that repeat the same way for every order.

The scope depends on who the users are. An internal factory needs access, quota, provisioning, scheduling, observability, capacity, usage visibility and lifecycle. Usage visibility there means GPU-hours by team, consumption by project, reserved against actual use, and showback or chargeback. A customer-facing factory adds the service catalogue, ordering, organisation and tenant management, multi-tenancy, a self-service console, external APIs, metering, billing or settlement, SLA management and support workflows. Billing is not required for every internal factory. The operating scope grows as the factory becomes a service, which is the step the previous chapter described.

Chapter 14 of 16

Multi-customer is not the same as public

NIST's four deployment models and five design questions

When a factory starts serving more than one organisation it is tempting to call it a public cloud. NIST's wording is narrower. A public cloud is provisioned for open use by the general public, and it exists on the premises of the cloud provider. A private cloud is provisioned for exclusive use by a single organisation comprising multiple consumers, such as business units, and may be run by the organisation, a third party or both, on or off premises. A community cloud is provisioned for exclusive use by a specific community of consumers from organisations that have shared concerns, such as mission, security requirements, policy or compliance. A hybrid cloud is two or more of these that remain distinct but are bound together by technology that lets data and applications move between them.

A GPU service limited to a telco's enterprise customers, to the members of a research consortium or to the companies of one industry group is multi-customer and not public. In NIST's terms it is closer to a community cloud, or a set of dedicated clouds run by one operator. The phrase multi-customer cloud service is an operating description, not a formal category. Kubernetes uses a similar phrase. Its multi-tenancy page calls this pattern multi-customer tenancy and states that Kubernetes has no first-class concept of end users or tenants.

The design questions are the same whatever the label. The tenant model: is the tenant an organisation, a project, a team. The access model: who can reach the service, from where, through which identity. The resource pool: shared among all customers, split per community, or dedicated per customer. The service policy: quotas, priorities, data handling, residency. The commercial model: public price list, contracts, consortium settlement or internal chargeback. A multi-customer service also does not always need an invoice. A consortium can settle by contribution, and an internal service can use showback.

Dedicated hardware does not remove the need for tenant boundaries either. If tenant A has gpu-srv-1 and tenant B has gpu-srv-2, the platform still has to keep apart their identities, organisations, credentials, networks, storage, access policies, quotas, usage records and order states. Exclusive hardware covers only the compute.

Chapter 15 of 16

Build it or integrate a platform

Open source can build the parts. The question is who owns the workflow

Open source can build a real GPU cloud. OpenStack provides identity, networking, images and compute. Ironic provisions physical servers and manages their lifecycle. Kubernetes runs containers and schedules GPUs that a vendor device plugin advertises as resources such as nvidia.com/gpu. It offers namespaces, RBAC and ResourceQuota for multi-team use. NVIDIA's dcgm-exporter publishes GPU telemetry in Prometheus format, with counters such as DCGM_FI_DEV_GPU_UTIL_RATIO and DCGM_FI_DEV_FB_USED_BYTES. Prometheus stores and queries them and Grafana draws them. Each of these is substantial.

Each also stops at a line. Ironic is a bare-metal provisioning project and is not by itself a commercial GPU service. Kubernetes is not a product catalogue, a contract, a price, an invoice or a settlement system, and has no first-class concept of a tenant. Prometheus metrics are telemetry, and a utilization ratio is not a billable record. So the useful question is who will integrate and own the whole customer workflow, from order to resource recovery. Whether open source can build the parts is already settled.

Follow one order. The customer chooses a product, identity and entitlement are checked, an order or reservation is created, capacity is held, the server, network and storage are built, access is created, usage is measured, rated and billed, the service ends and the server is cleaned and returned. Each step may live in a different system. When capacity is reserved and the network step fails, someone has to retry the network, release or keep the GPUs, clean up the half-built pieces, show the customer the right state, stop billing from starting, return the server to the pool, and record the failure for audit. That is a problem of workflow ownership and state reconciliation, the work of making several systems agree on what is true. It has nothing to do with OpenStack against Kubernetes.

A fair comparison covers twelve factors: integration with existing hardware; the catalogue; the order-to-fulfilment workflow; identity and multi-tenancy; metering against pricing and billing; integration APIs; who owns failure and rollback; upgrades, security and support, counted as one; customisation; dependence on a vendor; the internal engineering required; and the total cost of ownership over three to five years. Neither side wins by default.

Building makes sense when the service is internal only, the organisation has strong cloud platform engineers, deep customisation is a strategic advantage, or the portal, identity, ordering and billing systems already exist. An integrated platform is worth evaluating when the service is external and multi-customer, self-service and on demand are required, platform engineering capacity is limited, products are multiplying, and standard workflows matter more each month. Licence cost is not total cost. Open source removes licence fees and leaves engineering, integration, testing, upgrades, security, incident response, billing integration, documentation and support. A platform adds a licence or subscription and may remove some of that work. Compare several years of ownership. One line of a quote says little. A vendor that says build your own cloud describes a category. It proves nothing until it shows integration depth, lifecycle automation, multi-site operation and measured results.

Chapter 16 of 16

Twelve checks before the first customer

A diagnostic, read with the critical controls first

A working diagnostic from Thaki Cloud's insights series puts the whole lesson into twelve questions in four groups. It is not an industry certification. Its value is that it asks about the parts a demo never shows.

Group A is the product. One: is the specification clear, so a customer knows the GPU type, count, form, network, storage and duration. Two: are price, commitment, reservation, cancellation and support rules the same in sales and in operations. Three: can an order be tracked through ordered, reserved, provisioning, ready, active, terminating, failed, cancelled and completed.

Group B is customers and resources. Four: can organisations, users, roles, credentials and quotas be managed separately per customer. Five: has tenant isolation across identity, network, storage and workload actually been tested after it was designed. Six: does the platform know whether compute, GPU, network, storage, image and access are each really ready.

Group C is commercial operation. Seven: is there a billable usage record tied to the contract, separate from raw telemetry. Eight: do rating, invoicing, cancellations and adjustments stay consistent with the real state of service. Nine: can the operator manage failures, maintenance, free capacity, reservations and service commitments.

Group D is lifecycle and growth. Ten: are ordering, provisioning, retry, rollback, support and termination repeatable processes instead of one engineer's knowledge. Eleven: can access, data, network, storage and server state be cleaned safely before capacity goes back to the pool. Twelve: can new GPU models, servers, sites and products be added without rebuilding the operating model.

The list is not a score. An operator can pass ten of twelve and still carry serious commercial or security risk, if the two gaps are among tenant isolation, customer data handling, billing correctness, revoking access, or recovery from failure. Northlight's own check shows it: it passes ten, but item five was designed and never tested, and item eleven has no proof that the disks are wiped. Those two decide whether it can launch. Test the critical controls first, then test the rest for repeatability. The closing question replaces how many GPUs do we have: if a customer orders tomorrow, can we create the service, isolate it, measure it, bill it, end it and return the resource to a sellable state.

What to keep

A cloud is what happens around the GPU

Northlight's twelve H100 GPUs were hardware-ready and AI-ready from the first week. They became a cloud only when a stranger could pick a product from a catalogue, order it through a portal or an API with nobody at Northlight acting on it, receive a server in a segment of its own, see its usage, pay a bill that matches the product, and hand the server back to be wiped and sold again. NIST's five tests describe that from the outside. The cloud operations layer is how it is built from the inside: catalogue, orders, identity, scheduling, provisioning, isolation, metering, billing, service levels and lifecycle, run as a loop that ends every pass with a known, clean, counted server. Hosting stays a sound business beside it. An AI factory can stay internal for good reasons. Whether the layer is built from open source or bought as a platform, the hard part is the same: someone has to own the workflow when a step fails, and someone has to prove the critical controls before the first customer arrives.
