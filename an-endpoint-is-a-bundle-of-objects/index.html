Inference

An endpoint is a bundle of objects

How a click in a provider's console becomes Kubernetes objects, then TMM configuration, and how deleting it removes exactly what it made

A GPU cloud sells an inference endpoint: one address, one model, a set of policies the customer switched on. The customer creates it in the provider's console or API. Behind that click there is no single "endpoint" object anywhere. There is a bundle of ordinary Kubernetes objects: a Gateway that holds the address, an HTTPRoute that sends /v1 to the model pool, an InferencePool with F5's endpoint picker in front of it, an iRule attached through a policy object that carries the per-request logic, and a firewall policy of its own. This lesson follows how that bundle is made and unmade. A small adapter turns the provider's API calls into objects. The BNK controller turns the objects into TMM configuration. Labels let an operator read the whole endpoint with kubectl. Owner references let Kubernetes delete exactly that endpoint's objects and nothing else. And the two paths, the one that changes configuration and the one that carries prompts, never share a hop, so the provider's console can be down while the model Pods qwen3-6f7d9c8b4-x7k2p and qwen3-6f7d9c8b4-m9q4t keep answering.

Chapter 1 of 14

Two paths that never share a hop

Configuration goes down one line, prompts go down another

The design rests on two lines. The control path is provider API, then adapter, then Kubernetes objects, then the BNK controller, then TMM. TMM is the Traffic Management Microkernel, the traffic engine BNK takes from BIG-IP. The request path is client, then the TMM address, then the GPU the endpoint picker chose. Creating, changing and deleting an endpoint goes down the first line. Every prompt and every streamed token goes down the second.

The two lines touch in one place only: TMM. The control path ends there as configuration, and the request path runs through it as traffic. Nothing on the control path sits between a client and a GPU. The provider's console and API are never in the request path. During a request TMM makes only two kinds of outside call that the provider owns: it checks the API key against the provider's key service, and it sends usage records. Both are plain sideband calls from the iRule.

The same split shows up much lower in the stack. In the owner's GPU from scratch series, setting up one CUDA context on an H100 took 361 resource manager ioctls, 87 UVM ioctls and 237 firmware RPCs. Twelve copies after that took zero of each, only twelve doorbell writes. Setup is slow and goes through the kernel. The hot path is a few stores. An inference endpoint behaves the same way. Creating it takes seconds and passes through several controllers. Serving a prompt passes through none of them.

Chapter 2 of 14

The provider keeps its own API

Customers keep calling the console they already use

A GPU cloud already has a portal, an API, customer accounts and a bill. It does not want its customers to learn Kubernetes, and it does not want to rewrite its portal for BNK. So the portal stays. A small adapter sits behind it and turns each API call into BNK objects. The owner's design says an adapter holds no state of its own and never writes to BNK directly. It writes Kubernetes objects and reports status back in the platform's own terms.

The owner built adapters for several platforms behind one core. A REST API serves a customer portal, reached through an OpenShift Route in the lab, with tokens that are hashed and scoped to one tenant. A gRPC API offers the same operations plus a watch stream. A custom resource serves GitOps and anyone with kubectl. Follow adapters read an infrastructure controller such as NVIDIA NICo or Netris and derive endpoints from what it already knows. In the Lambda profile the controller served the Lambda Inference Gateway and Network Firewall APIs, 34 operations, checked against the contracts in Lambda's adoption kit, with Lambda's portal unchanged in front.

In the lab, a portal request for an endpoint became Ready in 8 to 31 seconds. Another tenant's token got 403. A write to an endpoint owned by another source got 409. Those two refusals happen at the adapter and the API server, long before anything reaches TMM.

Chapter 3 of 14

One intent, with one owner

The endpoint is first written down as a single custom resource

The owner's controller stores every accepted intent as a custom resource in the BNK cluster: BnkInferenceEndpoint for a model endpoint, BnkExposure for a plain service, BnkTenant for a tenant with its own address pool. Storing intents as resources means the store survives a controller restart without a database to run. It also means GitOps and kubectl see the same thing the portal created.

Each intent has exactly one owner, the source that created it, such as api:console or fabric:netris. A write from any other source is refused, and the refusal is enforced at the API server by an admission policy that ships in the chart. In the lab, kubectl edits of an endpoint the portal owned were refused. The owner chose refusal over merging on purpose: two platforms writing the same endpoint is a configuration mistake, and merging their intents would hide it until traffic went somewhere unexpected. Ownership transfer, such as a portal endpoint adopted into GitOps, is meant to be an explicit operation.

The intent is the root of everything that follows. Every BNK object rendered for this endpoint will point back at it through an owner reference that carries its UID. That pointer is what later makes the delete exact. The controller that renders the objects is leader-elected, so when two replicas run only one writes.

The owner's design names the parts of that one program. An adapter faces one platform's API and turns its calls into intents. The reconciler checks ownership, stores each generation and reads status back. A driver renders one kind of intent into BNK objects and reads their conditions. This lesson calls the whole program, adapters, reconciler and drivers together, the integration controller, and says adapter when it means the part that faces the provider.

Chapter 4 of 14

What one endpoint is made of

Five jobs, each done by an ordinary object

The controller reads the intent and renders the bundle. The blog lists it as five parts. The Gateway is the endpoint's address and listeners. The HTTPRoute sends /v1 to the model pool. The InferencePool with its F5EPP is the pool of model servers and the cache-aware picker in front of it. The iRule and its policy carry the per-request logic. The F5BigFwPolicy is the endpoint's own network firewall.

In real kinds that is more than five objects, because BNK attaches extras through policy objects. An iRule lives in an F5BigCneIrule, and a NetPolicy attaches it to the Gateway. A NetPolicy takes one to eight extension references and exactly one target, and its target cannot be changed after creation. An F5BigFwPolicy is attached by a SecPolicy, which takes up to three extension references, each kind at most once, and one to sixteen targets. The owner's controller adds a Kubernetes NetworkPolicy that lets only the BNK namespace reach the picker on port 9002, because TMM speaks to the picker in plaintext.

The Gateway asks F5 IPAM for its address by naming an F5BnkGateway in infrastructure.parametersRef. The owner found that a Gateway that requests an address without that reference gets it but leaves no IPAM record, and IPAM later handed the same address to another Gateway. So the controller always renders the reference.

The Deployment qwen3 is not part of the bundle. The pool selects its Pods by label. The model servers, with 34.3 GB of FP8 weights each in GPU memory, belong to whoever runs the workload.

Chapter 5 of 14

Labels to read it, owner references to delete it

Two kinds of link, used for two different jobs

Each object in the bundle carries two kinds of link back to the endpoint. Kubernetes keeps them apart on purpose, and its documentation uses the same example: a Service finds its EndpointSlices by label, and each slice also carries an owner reference to the Service.

Labels are for reading and grouping. A label key has an optional prefix, a DNS subdomain of at most 253 characters, then a slash, then a name of at most 63 characters. Values are at most 63 characters. The documentation says automated components that add labels to end-user objects must use a prefix, and kubernetes.io/ and k8s.io/ are reserved. The owner's controller labels what it renders with keys under bnk-connector.io: site, tenant, source, and the name of the endpoint or exposure. With those, a platform team reads one endpoint across nine kinds with one selector, and finds every endpoint of a tenant with another.

Owner references are for deletion. metadata.ownerReferences on a dependent holds the owner's apiVersion, kind, name and UID, plus controller and blockOwnerDeletion flags. An owner reference is only valid inside one namespace. A namespaced dependent whose owner is in another namespace is treated as having no owner, and the garbage collector reports an OwnerRefInvalidNamespace warning event. The owner's security review found why the UID matters: a same-named object could have been taken over by a forced apply. Now an object counts as the controller's only if it carries an owner reference to the intent's UID.

Chapter 6 of 14

One namespace, or the delete leaks

Ownership, attachment and lists all stop at the namespace line

Three separate rules push the whole bundle into one namespace. Kubernetes owner references cannot cross namespaces, so an object in another namespace cannot be owned by the intent. Kubernetes treats such an owner reference as absent, so the object is not cleanly tied to the endpoint's delete and may even be collected on its own while the endpoint still exists. F5's SecPolicy must sit in the same namespace as the F5BigFwPolicy it references, and both must sit with the Gateway when the target is a Gateway. NetPolicy, its F5BigCneIrule and the Gateway must all share a namespace too.

The owner hit a fourth rule in the lab. The Lambda profile first rendered F5BigCneAddresslist and F5BigCnePortlist objects next to the endpoint. They never got a status. AFM, the firewall manager, looked for the lists by a name in BNK's own namespace, the one F5 calls the CNE namespace, because list references resolve there. The F5BigFwPolicy then waited for its dependent objects forever. The fix was to inline every list's entries into the rules that named them and render no list objects at all. The policy, its rules and its owner reference then all stayed with the endpoint.

A picker brings its own namespace needs. BNK creates the picker Deployment for an F5EPP, with a ServiceAccount per endpoint, named ie-<id>-main-epp in the Lambda profile. On OpenShift the picker runs as UID 2000, which the restricted-v2 policy refuses, so the namespace needs nonroot-v2. The picker image pulls with far-pull-secret, which BNK creates only in f5-bnk, so it must be copied to the endpoint's namespace. The namespace also has to be listed in the CNEInstance's eppNamespaces.

Chapter 7 of 14

From objects to TMM configuration

The BNK controller watches, programs and reports

The adapter's job ends at the API server. From there BNK's own controllers take over. The CNE controller watches Gateway API resources, the Inference Extension's InferencePool and the F5EPP, turns them into TMM configuration and creates one picker Deployment per pool. The owner's GRID deck describes it in three verbs: reconcile the resources, program TMM, manage the picker deployment.

Each part of the bundle travels its own way. The Gateway and its route become a virtual server in TMM. On the owner's other lab cluster, bnk-eve on BNK 2.4.1, a Gateway reached Programmed about 3 seconds after it was applied. With dynamic routing on, the address is advertised over BGP by both TMMs. On the BNK 2.4.2 lab the owner measured this for an exposure, the plain-service intent: a fabric router learned the new Gateway's address 11.5 seconds after the exposure was Ready. An endpoint's Gateway is advertised the same way. An F5BigFwPolicy goes first to the AFM Pod, F5's Advanced Firewall Manager, which compiles the rules into a binary blob, and the blob is then sent to TMM to filter packets. In the owner's lab the TMM Pods with AFM switched on carried a blobd sidecar for this. An F5BigCneIrule reports READY True with the message "CR config sent to all grpc endpoints" once every TMM has it. The F5EPP becomes a Deployment that the F5EPP owns.

That last point creates a second layer of ownership. BNK generates objects of its own beneath the bundle and keeps them as it wants them. Scaling the picker Deployment to zero was undone by BNK at once. So the owner's controller writes only the objects it renders and changes the picker only through F5EPP.spec. Otherwise two controllers would undo each other's changes forever.

Chapter 8 of 14

The iRule is built from the switches

One iRule per endpoint, made from the policies the provider turned on

The per-request logic of an endpoint is one iRule. It is built from whichever policies the provider switched on for that endpoint, so two endpoints on the same GPUs can carry different iRules. The policy names differ by layer: the customer asks for an API key, guardrails, a token budget and a firewall, and the intent records them as auth, guardrails, quota and firewall. In the blog the request meets seven decisions at one address. Step 0 is the network firewall, which runs first at the network layer, before any HTTP is parsed. Steps 1 to 6 are the iRule: the API key against the provider's key service, the F5 AI Guardrails prompt scan, the token budget per user, the model choice, the F5 Endpoint Picker, and metering. Steps 0 to 3 can stop the request, and anything they stop never reaches a GPU. The budget step has two outcomes in the blog: a caller past the budget is moved to a cheaper model, or refused with 429.

The iRule does its work with plain sideband calls. It sends an introspect request to the key service, a scan request to the guardrail scanner and usage records to the usage store. It asks the picker for a GPU over gRPC ext_proc. In the Lambda profile run on BNK 2.4.2, no key and a bad key got 401 at the gateway, a valid key got 200 and was metered as demo-admin, a benign prompt was served, a prompt about ransomware was blocked before any model, and past a 50-token quota requests were rewritten to a 1.5B model, the cheaper-model outcome. The 429 refusal was not part of that run.

The iRule is rendered, so a change of switch is a change of object. When the scanner disappeared under a live guardrail policy, the controller re-rendered the iRule with a black-hole sideband. Every request was then blocked, and the policy showed error. That is the safe direction: a missing check refuses instead of waving prompts through.

Chapter 9 of 14

A firewall of the endpoint's own

F5BigFwPolicy rules, attached to this endpoint's Gateway

Step 0 is the network firewall, and each endpoint gets its own. An F5BigFwPolicy holds an ordered list of rules. Each rule has a name and either an action or a reference to an F5BigFwRulelist, never both. The action is one of accept, accept-decisively, reject or drop. ipProtocol defaults to any. Source and destination can match addresses, CIDR ranges, ports and port ranges, VLANs, zones, geographic codes, fully qualified names and Kubernetes namespaces. logging defaults to false.

A SecPolicy attaches the firewall to its target. The scope depends on the target. Aimed at a GatewayClass, the policy applies cluster-wide on every TMM. Aimed at a Gateway with no sectionName, it applies to all of that Gateway's traffic. Aimed at one listener through sectionName, it applies to that listener's inbound traffic and overrides the Gateway-wide rules there. Only one SecPolicy may target each Gateway, listener or GatewayClass. When two do, the oldest by creation date wins, the rule from Gateway API's GEP-2648.

For the endpoint the controller renders a Gateway-wide policy. In the Lambda profile run, a client whose address matched a drop rule was dropped, eight drop events reached syslog, and the rule's hit count rose. The default for traffic that matches no rule is set globally, and a default-drop setup blocks the controller's own calls to the VIP too. So the owner's chart takes a list of platform addresses, firewallPlatformCidrs, and puts them in an accept rule.

Chapter 10 of 14

Status flows back up the control path

The endpoint is Ready when BNK says its parts are

The controller never infers what BNK is doing. It reads the status of BNK's resources. The owner's data flow is written for an exposure, the plain-service intent, and has six steps. The adapter authenticates and validates. The reconciler checks ownership, allocates or validates the address, stores generation N and emits accepted. The driver renders the objects with its field manager and labels and emits programming. BNK accepts the Gateway, programs TMM and sets Programmed. The reconciler sees Programmed on the Gateway and Accepted on the route, marks the exposure ready, records how many milliseconds programming took and emits ready. On every later pass it compares what should exist with what does. An inference endpoint goes through the same steps with one more condition to read. Its route goes through a picker, so the controller also reads Available on the F5EPP, and an endpoint whose picker is not Available is not Ready.

The status goes back in each platform's own terms. On the custom resource it is the status block, with the observed generation, a phase, the address and a message. Argo CD reads health from that status through a small Lua check the project ships. For the portal it is an HTTP answer, a server-sent event stream or a webhook. Every transition is also a CloudEvent with a trace id and a Kubernetes Event.

The times measured in the lab: Ready in 9 to 24 seconds through the custom resource, 8 to 31 seconds through the portal, and 2.1 seconds to Active for the Lambda profile, which counts Active differently. An endpoint is marked Degraded with reason PickerNotAvailable when its route goes through a picker that is not Available. On OpenShift that happened when the picker Pods could not start because of the UID rule from chapter six.

Chapter 11 of 14

Drift, repair and rollback

The bundle is kept the way the intent says

Once an endpoint is Ready the controller keeps comparing. It uses a subset compare: every field it rendered must still have the value it rendered. A missing object is created again and the event is repaired. A field someone changed by hand is set back. In the owner's lab drift was restored in 0.6 seconds. When BNK drops Programmed on a Gateway, the endpoint turns Degraded, and back to Ready with recovered true when it returns.

Server-side apply gives this a precise meaning. Every apply names a field manager, and the API server records in metadata.managedFields which manager set which field. Applying a different value to a field another manager owns is a conflict, and the request is rejected unless it is forced. Kubernetes recommends that a controller always force conflicts on objects it owns and manages, because it cannot resolve them by asking anyone. Forcing changes the value and removes the field from the other managers' entries. Fields the controller never applied stay as they are, so BNK's own status and generated fields are left alone.

Rollback covers the opposite case, a change that never works. If a new generation stays Failed past its deadline, set by rollbackAfterSeconds with 0 meaning off, the controller applies the last generation that reached Ready again. It records lastReady, failedSince and rolledBack in status and never rewrites the intent's spec. In the lab rollbackAfterSeconds was 60. Generation 1 was back on BNK 92.4 seconds after the bad change, a time that includes the 60-second deadline. The endpoint then showed phase Degraded with the condition RolledBack, not Ready, because the intent still asked for the generation that had failed. Traffic kept flowing on the old listener the whole time.

Chapter 12 of 14

Delete the endpoint, and exactly its objects go

One delete on the intent, then the garbage collector

The customer deletes the endpoint in the console. The adapter deletes one object, the intent. Kubernetes does the rest from the owner references.

A delete with finalizers present does not remove the object at once. The API server sets metadata.deletionTimestamp, keeps the object while metadata.finalizers is not empty and answers 202 Accepted. The owner's controller uses a finalizer to delete in a fixed order and only then lets the intent go. Its earlier connector deleted routes first, then the Gateway, then the backends, and retried until done. After a deletion timestamp is set, finalizers can be removed but no new one added, and the object cannot be brought back.

The cascade itself is the garbage collector's. By default Kubernetes uses background cascading deletion: the owner goes at once and the collector removes dependents afterwards. With foreground deletion, propagationPolicy Foreground or kubectl delete --cascade=foreground, the owner stays visible with the foregroundDeletion finalizer until every dependent with blockOwnerDeletion true is gone. Below the intent the chain can run further. The owner's lab records the picker Deployment BNK made as owned by the F5EPP. If that link is an owner reference, the collector removes the Deployment once the F5EPP is gone, then the Deployment's ReplicaSet, then its Pods, since a Deployment owns its ReplicaSets and a ReplicaSet owns its Pods. Whether the collector or BNK's own controller removes the picker was not checked. Labels act as a safety net. The connector looked for leftovers by label and removed them.

In the Lambda profile, the objects and the Pod membership labels were gone in about 1 second, and the route was withdrawn from the fabric 15 to 37 seconds later. The vLLM Pods were not deleted. They were never in the bundle, so the 34.3 GB of FP8 weights stay loaded and a new endpoint does not wait three minutes for them.

Chapter 13 of 14

When the control path is down

What breaks, and what keeps serving

Because the paths are separate, a failure on one should not take the other down. If the provider's console is down, nobody can create, change or delete endpoints through it, and no prompt passes through the console anyway. If the adapter or the integration controller is down, changes stop as well. The owner's design assumes that every endpoint already programmed keeps serving then, because TMM holds its configuration and the objects stay in the API server. That is how Kubernetes controllers generally behave, since nothing removes objects while their controller is away. The owner marks this assumption as not yet tested: a later phase is meant to stop the controller and check. What was measured is a controller failover. With a standby replica, the controller failed over in 2 seconds and 200 of 200 requests succeeded during it. A second assumption covers the BNK cluster's API: if it is unreachable, the controller stops writing and reports unavailable, and BNK keeps the last programmed state.

The request path has its own dependencies, and the key service is one of them. The iRule calls it for every request. A provider that runs the key service on the same footing as its console has put a control-plane-looking service on the request path, and must run it like the request path.

The picker is the other one. With failureMode FailClose, also the default in the Inference Extension's v1 InferencePool, a request fails when the picker is unreachable and never falls back to round robin. In the owner's lab on BNK 2.4.2 no request reached a worker, as intended. The reply was malformed, though. After 4 to 5 seconds TMM sent back the client's own request headers, then the body {"error":{"code":503,"message":"inference endpoint picker unavailable"}}, with no HTTP status line, and held the connection open. curl reports "Received HTTP/0.9 when not allowed". The owner reported it to F5. Until it is fixed, the controller probes picker health itself.

Chapter 14 of 14

The adapter is one Helm chart

What it installs, and what it needs from the cluster

The adapter needs nothing beyond the Kubernetes API of the BNK cluster and four sets of definitions: BNK's own resources, the Gateway API and the Inference Extension, plus its own intent kinds. It ships as one Helm chart. The owner's chart holds the custom resource definitions, the RBAC rules, the admission policy that enforces one owner per intent, and a NetworkPolicy for the sideband ports. CI tests it.

Helm treats definitions differently from everything else in a chart. Definitions in a chart's crds directory are installed by helm install, skipped with a warning when they already exist, and skipped entirely with --skip-crds. Helm does not upgrade or delete them. That was a deliberate decision, because deleting a definition deletes every object of that kind. For an endpoint controller that is the right default: uninstalling the adapter must not delete every tenant's endpoints.

The BNK side has to be prepared once, by the platform team. BNK is installed and licensed. The GAIE InferencePool definitions are installed separately, since BNK does not install them, and with eppNamespaces set the CNE controller exits at boot if they are missing. The VLANs, VRFs, IPAM ranges and the GatewayClass exist, and the controller references them by name and never creates them. Site values tune the rest: the controller's values for the Lambda profile added the platform addresses for the firewall and, in the lab, a leg on the external network, because Pods on the cluster network could not reach the VIPs.

What to keep

Objects say what the endpoint is, controllers make it so

An inference endpoint on BNK is not a product object hidden in an appliance. It is a labelled bundle of standard objects in one namespace: a Gateway with an IPAM reference, an HTTPRoute to an InferencePool, an F5EPP that BNK turns into a picker, an iRule attached by a NetPolicy and rendered from the policies the provider switched on, and an F5BigFwPolicy attached by a SecPolicy. A provider's own API reaches it through an adapter that holds no state and writes only objects. BNK's controller turns those objects into TMM configuration and reports conditions back. Labels let anyone read the endpoint with kubectl. An owner reference to the intent's UID on every object lets Kubernetes delete exactly that endpoint and nothing beside it, while the model Pods and their 34.3 GB of weights stay loaded for the next one. And because configuration and prompts never share a hop, a console outage stops changes and leaves traffic alone.
