GPU and hardware

Behind the Pod IP

How a CPU asks a GPU to do anything

To the network a model server is one address in a pool. Behind that address there are at least two computers: the host, with its CPU and DRAM, and the GPU, with its own processors, memory, page tables and firmware. They share no memory. Everything between them crosses a PCIe link, and that link has rules. This lesson follows one small job across it: a 4 MiB block of KV cache that sits in host DRAM and has to be in GPU memory before the model can use it. The CPU never copies a byte. It writes down what it wants, points at it, and rings a bell.

Chapter 1 of 14

One address

All the network can see

A request arrives and the endpoint picker sends it to gpu-2. The reason is something no load balancer can see in an address: the start of this prompt was processed before, and the result, its KV cache, is still on gpu-2. It is not in GPU memory any more. It was moved down into the server's ordinary memory to make room. So picking gpu-2 means choosing a particular price: a few copies across PCIe before the model can start answering.

The picker knows this from the model servers themselves. With prefix caching on, vLLM can publish events for the KV cache blocks it stores and removes, and the picker uses them to match the start of a new prompt against what each worker holds. A tool such as LMCache sits under the engine and keeps blocks that no longer fit in GPU memory in a pool of the server's own DRAM. That pool is its first tier, CPU memory on the same host. So a prefix can be cached on gpu-2 in two places. In GPU memory it is ready at once. In host DRAM it has to come back across PCIe first.

That trip is short next to recomputing the prefix, which means running the whole model over every one of its tokens again. In this lesson the block is 4 MiB, and the copy takes about 130 microseconds. That is the price the picker accepted.

To see what that price is made of, go below the Pod IP. The rest of this lesson takes the copy apart one write at a time, from the process that asks for it to the copy engine that does it.

Chapter 2 of 14

Two computers

The GPU is not part of the host

A GPU like the H100 is a separate machine at the far end of a PCIe link. It has its own processors, 80 GB of memory the host CPU cannot address as its own, its own memory management unit walking its own page tables, its own clocks, power states and interrupt sources, and a small RISC-V core running firmware. The host has its CPU, its DRAM and its own page tables. An address that means something on one side means nothing on the other until someone sets up a matching mapping.

The measurements this lesson draws on were taken on rented H100 PCIe machines. That card has 114 SMs, the GPU's processor blocks. The SXM version of the H100 has 132, and the full die 144. The CPU and the GPU share neither an instruction pointer nor a stack, so the host cannot call a function on the GPU. It can only send it messages across the link.

That link has three rules, and almost every design choice in this lesson follows from them. First, there is no passive sharing. Every transfer has an initiator: the CPU writes or reads a device address, or the device reads or writes host memory. Second, a round trip across the bus costs roughly a microsecond, against about a nanosecond for a hit in the CPU's closest cache. Third, the two sides order their memory independently. The CPU may still hold a write in a buffer while the device is already reading. "I wrote it" and "they can see it" are two separate events, and someone has to join them on purpose.

The block of KV cache the request needs is on the host side. The model runs on the GPU side.

Chapter 3 of 14

Five layers of software

Two in the process, two in the kernel, one on the GPU

vLLM calls PyTorch, and below PyTorch NVIDIA's driver stack has five pieces of software on two processors. PyTorch calls the CUDA runtime, libcudart.so. The runtime is a thin layer over the CUDA driver API in libcuda.so, NVIDIA's closed user-space driver, about 110 MB in version 610.43.02, the version traced in Maxime Peim's AI Infrastructure series on Medium. Both run in user space, inside the vLLM process. libcuda turns a copy into the exact bytes the copy engine reads, manages memory, and builds streams and events on top of queues, doorbells and semaphores.

Below them are two kernel modules. nvidia.ko holds the Resource Manager, which keeps a tree of allocated objects and passes requests that touch hardware on to the GPU. nvidia-uvm.ko owns GPU virtual address spaces and page faults. The fifth layer is not on the host at all. GSP-RM is firmware running on the GPU System Processor, a RISC-V core on the GPU die, and it does the actual programming of the hardware.

The process reaches the kernel modules through three device files: /dev/nvidiactl for control, /dev/nvidia0 for this GPU, and /dev/nvidia-uvm for address spaces. Every request is an ioctl, and every mapping is an ioctl followed by an mmap, each on a fresh file descriptor. The kernel module talks to GSP through a ring of messages in host DRAM and pokes one register, NV_PGSP_QUEUE_HEAD, to say there is mail. That is already the shape this lesson is about: a queue in memory and a doorbell.

Only the two user-space libraries run on the path of a copy. The kernel modules and the firmware are setup machinery. Moving work into GSP shrinks the host kernel's attack surface, lets each virtual machine run a thin driver that calls one shared GSP, and lets the firmware hold boundaries for confidential computing. It also left the kernel module thin enough for NVIDIA to publish its source in 2022.

Each of those three reasons has a concrete mechanism. Security comes first. Before Turing, one large closed kernel driver programmed the hardware itself, so every bug in it ran with full kernel rights on the host. With GSP, the host's Resource Manager keeps its object tree and forwards anything that touches hardware as a message. The code that writes the GPU's registers runs on the GPU's own processor. That firmware is signed by NVIDIA, and NVIDIA has authenticated the firmware that runs on its GPUs with AES since the V100, so the GPU can trust that its boot firmware was neither corrupted nor tampered with.

Virtualization is the second reason. A virtual machine that is given a GPU, or a share of one through NVIDIA vGPU, runs its own copy of the driver. That guest driver must not program hardware that other tenants share, so it forwards its requests out of the virtual machine. GSP gives the bare metal driver the same shape: a thin Resource Manager that sends RPC messages to one shared manager below it. The open source shows how close the two cases are. The RPC code that the host driver uses to call GSP lives in src/nvidia/src/kernel/vgpu/rpc.c, a directory named for virtual GPUs. The channel code tests both cases in one line, IS_VIRTUAL(pGpu) || IS_GSP_CLIENT(pGpu). When a channel is made runnable, that branch sends the request NVA06F_CTRL_CMD_GPFIFO_SCHEDULE onward as an RPC, under the comment that all real hardware management is done in the host. Inside a virtual machine the message goes to the host. On a bare metal H100 such as gpu-node-1 it goes to the firmware.

Confidential Computing is the third reason. An H100 has three modes. CC-Off is standard operation. CC-On turns on every protection and disables the performance counters, so they cannot be used for side-channel attacks. CC-DevTools follows the CC-On workflow with the protections off, so profilers such as Nsight Systems still work. In CC-On the CPU keeps the virtual machine's memory private from the hypervisor and the host, and the GPU is not allowed to read the guest's private pages directly. The CUDA driver and the GPU firmware encrypt and sign command buffers and CUDA kernels before they cross PCIe, and the unified memory module moves pages through an encrypted bounce buffer in shared system memory that the GPU can reach. Before the guest trusts the GPU, it asks for an attestation report, signed with a device-unique ECC-384 key, that covers the GPU hardware and its driver, firmware and microcode. Something has to hold the keys and enforce those rules where the host cannot reach. In the series' words, the firmware enforces a trust boundary the host cannot cross.

That changes the copy this lesson follows. With CC-Off the copy engine reads the pinned block straight out of host memory. With CC-On the plain block never crosses the link. It is encrypted into the bounce buffer, and the GPU reads the encrypted copy. NVIDIA measured the CPU to GPU path at roughly 4 GB/s in CC-On, limited by how fast the CPU encrypts, against tens of GB/s for a plain copy. Inside GPU memory nothing changes: the compute engines run plaintext code on plaintext data. So a model server pays the price on transfers. Loading the 34.3 GB FP8 build of Qwen3-32B through that path takes about 34.3 / 4 = 8.6 seconds for the transfer alone, against about 0.7 seconds at 50 GB/s. Moving KV cache blocks to host memory pays it again. Decoding tokens on weights that are already on the GPU does not.

An operator can see whether GSP is in use. nvidia-smi -q prints a line GSP Firmware Version with the driver's version, or N/A when GSP is off, and the same line appears in /proc/driver/nvidia/gpus/<PCI address>/information as GSP Firmware. The firmware files are gsp_*.bin under /lib/firmware/nvidia/<driver version>/, one per GPU architecture, for example gsp_tu10x.bin for Turing. The kernel module parameter NVreg_EnableGpuFirmware=0 forces the driver off GSP. The open kernel modules depend on GSP, which is why NVIDIA's README says they support Turing and later GPUs and nothing older. Since the 560 driver, GSP is the default on every Turing and later GPU.

Chapter 4 of 14

One address on both sides

The same number in the CPU's tables and the GPU's

The GPU walks its own page tables, so a source address in a copy command has to mean the same thing to the CPU that wrote it and to the GPU that reads it. The unified virtual memory module makes it mean the same to both. nvidia-uvm.ko builds the GPU's page tables so that a GPU virtual address equals the CPU virtual address of the same buffer. The CPU writes 0x2_0080_0000 into a command, and the GPU's MMU walks its own tables at that same number and finds the right physical pages in host DRAM. A buffer that lives only in GPU memory still gets its range carved out of the process's address space. The CPU keeps that range reserved and never touches it.

libcuda arranges this at startup. It reserves a window of about 4 GiB at 0x200000000 with no access rights, then places buffers that both sides use inside it with fixed mappings. In the traced run they started at 0x200600000, and maps them for the GPU at the same numbers. The host-side addresses in this lesson sit inside such a window.

This is more than tidiness. The engineer who rebuilt a copy from scratch first used different CPU and GPU addresses for the same buffers. Between 25 and 34 percent of 128 MiB round-trip copies then failed, some timing out on the semaphore and some returning wrong data. Copying libcuda's layout, one address for both sides, made 1,000 of 1,000 runs pass. The root cause was never isolated.

The block must also be pinned, held at fixed physical pages, because the copy engine reads physical memory. cudaHostRegister on a 4 MiB buffer from malloc showed up as three mappings. The buffer did not start on a page boundary, so it covered 1,025 pages of 4 KiB: a head page of 4 KiB, 4,190,208 bytes in the middle and a tail page of 4 KiB. That is 4,198,400 bytes mapped, 4 KiB more than the buffer itself, because the buffer starts partway into its first page and ends partway into its last.

The mode UVM uses for these buffers is called an external mapping. The memory belongs to the Resource Manager, which allocated it, and UVM only writes the GPU's page table entries for it, at a virtual address the caller picks. For a buffer the CPU also touches, the caller picks the buffer's own CPU address. Nothing migrates. The managed mode behind cudaMallocManaged works differently: UVM owns those pages and moves them between host and GPU when either side faults on them. An external mapping takes two ioctls on /dev/nvidia-uvm. UVM_CREATE_EXTERNAL_RANGE, number 73, claims a base and a length in the process's UVM address space. UVM_MAP_EXTERNAL_ALLOCATION, number 33, then maps one Resource Manager memory object into that range, named by rmCtrlFd, hClient and hMemory, at an offset, with mapping attributes for each GPU. The cudaHostRegister call above was one legacy memory allocation call followed by three such pairs, one for the head page, one for the middle and one for the tail. No GPU work was submitted inside the call. A mapping is only half of the setup. UVM also has to be told about the channel that will use the address space, and the chapter Two quiet failures in setup shows what happens when it is not.

Chapter 5 of 14

The slow way in

Why the CPU doesn't just copy it

The GPU shows the host a few windows into itself, called BARs, base address registers. Each is a range of physical address space with no RAM behind it. When the CPU touches an address in it, the chipset turns the access into a PCIe packet aimed at the device. Two matter here. BAR0 holds the control registers. A process never gets all of it. The driver hands it one 64 KiB window, the USERMODE aperture, with the doorbell at offset 0x90. BAR1 is a view of GPU memory. It was once only 256 MB, which forced copies to be staged in pieces. With Resizable BAR it can cover most or all of the 80 GB.

Through BAR1 the CPU can write GPU memory as if it were its own. This is memory-mapped I/O, MMIO, and it behaves nothing like ordinary memory. Stores can be reordered unless fenced, and a read can have side effects or return zero forever. The driver maps BAR1 write-combined. The CPU gathers its small stores in a buffer and sends them out together as PCIe writes of up to 64 bytes. Writing that way is fast. NVIDIA's GDRCopy library, which copies through BAR1 with the CPU, measures writes at about 22 GB/s on a B200, in a test that copies 131,072 bytes (128 KiB) at a time. Reading is the slow direction. Every load waits for its answer to cross the link, and the same test reads at about 0.9 GB/s.

If that rate held for the whole 4 MiB block, the block would take about 190 µs. GDRCopy's own latency table supports that: it puts a 1 MiB write at about 44 µs, close to the same rate. That is a little longer than the 130 µs the copy engine needs, but the two numbers come from different cards. The 22 GB/s is a B200, and the 130 µs is the H100 PCIe this lesson measures, so the comparison is a rough one. The cost that matters is the CPU. The copy is 1,048,576 stores of 4 bytes, or 65,536 of 64 bytes, and one core executes every one of them. That core is busy for the whole copy, where the copy engine needs 350 ns of asking. Copying the other way, out of GPU memory, would run near 0.9 GB/s and take about 4.7 ms. MMIO is fine for flipping a control bit or writing a ring entry. For a model's weights or a KV cache it spends a core the server needs for other work.

So the work splits by who starts it. MMIO is started by the CPU and is for control: write a pointer, ring a bell. DMA is started by the device and is for data.

Chapter 6 of 14

Write down the copy

Seven methods, sixty bytes

Bulk data goes the other way round. The GPU has copy engines, hardware built to reach into host memory and move data at tens of GB/s without using the SMs, so the model's kernels can keep running while a copy is in flight. The CPU's job is only to describe the copy. It writes a short list of commands, called methods, into a buffer in its own memory, the pushbuffer.

Each group of methods starts with a header dword that says how many dwords follow, which method they start at and which subchannel they are for. libcuda binds the copy engine class, HOPPER_DMA_COPY_A (0xC8B5), to subchannel 4 once, when it sets up the channel. After that a copy is source address, destination address, length and a launch. Then where to report, what value to report, and a second launch. Seven methods, 15 dwords, 60 bytes in all.

The first launch, 0x182, moves data and nothing else: run the copy as one unit, linear layout at both ends, no flush, no semaphore. The second launch moves no data. It turns on FLUSH_ENABLE and releases the semaphore. libcuda's value is 0x14, a four-word release that also writes a timestamp. A one-word release, 0x00c, works too, and the two jobs can be fused into a single launch, 0x18e.

A from-scratch rebuild uses 18 dwords, 72 bytes, because it binds the copy engine again on every submission and gives source and destination separate headers. Nothing has crossed PCIe yet. This was the CPU writing into its own memory, which costs it about 50 ns.

Two counts of this stream are both correct, and other lessons on this site use the second one. The decoder that printed the trace names seven methods, because it joins pairs of registers that together hold one address. In the copy engine's class header, clc8b5.h, an address of up to 57 bits takes two method registers. OFFSET_IN_UPPER at offset 0x400 holds bits 56 to 32, and OFFSET_IN_LOWER at 0x404 holds the low 32 bits. The destination is OFFSET_OUT_UPPER and OFFSET_OUT_LOWER at 0x408 and 0x40C. The semaphore address is SET_SEMAPHORE_A at 0x240, the upper bits, and SET_SEMAPHORE_B at 0x244, the lower 32. Count the registers written and there are ten method writes: four for the two addresses, one length, one launch, three for the semaphore address and payload, and the second launch.

A header covers a run of registers that sit next to each other, so libcuda writes the four address registers 0x400 to 0x40C under one header. Then come a header and LINE_LENGTH_IN at 0x418, a header and LAUNCH_DMA at 0x300, a header and the three semaphore registers 0x240, 0x244 and 0x248, and a last header and LAUNCH_DMA. That is 5 + 2 + 2 + 4 + 2 = 15 dwords: ten method writes and five headers, 60 bytes. Seven named methods and ten method writes describe the same 60 bytes. The rebuild's 18 dwords are the same ten writes with a sixth header, for the separate destination address, and two more dwords for SET_OBJECT.

The size of the copy does not change the size of the command. The series traced a 256 MiB cudaMemcpy, and its command was the same 60 bytes, with LINE_LENGTH_IN set to 0x10000000 and the semaphore payload 0x2. This lesson's 4 MiB block puts 0x400000 in the same field. Because the length field is 32 bits, a copy of more than 4 GiB minus one byte needs more than one launch. The 34.3 GB of the FP8 build would need at least 8 launches even if it sat in one buffer, since 34.3 GB divided by 4,294,967,295 bytes is 7.99.

Chapter 7 of 14

Point at it

Eight bytes in a ring

The GPU doesn't know the pushbuffer exists. It learns about work from a ring both sides agreed on at setup, the GPFIFO. Each entry is eight bytes: the address of a pushbuffer and its length in dwords. In the setup that was measured, the ring itself sits in GPU memory, and the CPU writes it through a BAR1 mapping. The pushbuffers stay in host DRAM. The scene draws the ring beside the process because the process is the only one that writes entries into it.

The entry packs the address in a particular way. The low dword holds address bits 31 to 2 in place, because commands are always 4-byte aligned. The high dword holds bits 39 to 32 in its low 8 bits and the length in dwords from bit 10 up. So an entry reaches 40 bits of address. A pushbuffer above that needs an extra entry first, SET_PB_SEGMENT_EXTENDED_BASE, which carries bits 56 to 40. Inside the 4 GiB window at 0x200000000 that never happens.

The CPU writes one entry, then moves its write index, GPPut, forward by one. The GPU has a read index of its own, GPGet. Both live in a small per-channel region called USERD, which on Hopper is also in GPU memory, with GPPut at offset 0x8c. Each index has exactly one writer, so no locks or atomic operations are needed. When the two are equal the ring is empty. Valid work lies from GPGet up to GPPut, wrapping at the ring's size.

Now they differ by one. The GPU still doesn't know, because it does not poll for work.

Chapter 8 of 14

Ring the doorbell

The only signal that crosses the link

The CPU now tells the GPU to look. It does that with one 32-bit store to a register on the GPU called the doorbell, at offset 0x90 of the 64 KiB USERMODE window. The value is the channel's work-submit token, an opaque number the driver handed out when it created the channel. Hundreds of channels can share the one register, and the token says which one has work. Its low 12 bits are a vector, and bits 16 to 22 name a runlist. Read the doorbell back and it returns zero.

This is MMIO, the slow kind of access from earlier, and that is fine: it is four bytes, once. It is also a write, so the CPU sends it and moves on without waiting. A doorbell is the opposite of an interrupt. An interrupt is the device poking the CPU. A doorbell is the CPU poking the device, so the GPU never has to burn power polling host memory for work.

The GPU's front end, the PBDMA, wakes up. It reads GPPut, finds one new entry and reads it. The ring is in the GPU's own memory, so that read stays on the card. Then it follows the entry to the pushbuffer and reads the sixty bytes from host DRAM. That read does cross PCIe, and the GPU starts it. Its read index catches up and the ring is empty again.

All four steps on the CPU side, the commands, the entry, the index and the doorbell, took about 350 ns together. There was no system call, and the kernel never learned that a copy was asked for.

Chapter 9 of 14

The copy engine does the work

Data moves with no CPU in the loop

The front end hands the methods to the copy engine bound to subchannel 4. Now the data moves, and the direction of control is the opposite of the slow way: the GPU is the initiator. The copy engine sends memory read requests to host DRAM in large transfers, and host memory answers with completions that carry the data. The engine writes the data into GPU memory at 0x2_1000_0000. This is direct memory access, DMA. The host CPU executes nothing while it happens, and neither do the SMs.

Nothing in the methods names a direction. The copy engine reads the source address and writes the destination address. Swap the two and the same 60 bytes copy from GPU memory to host DRAM. The GPU's MMU translates both addresses through the same page tables, and that is how it knows one is in host memory and the other is on the card.

The whole 4 MiB block takes about 130 microseconds. That is 4,194,304 bytes in 130 µs, about 32 GB/s, half of what a Gen5 x16 link carries. Asking for it took about 350 nanoseconds, roughly one part in 370. These figures were measured on copies from GPU memory to host memory. The command carries no direction, so this lesson uses the same figures for the copy back in and treats them as approximate.

The source must stay pinned until the copy finishes. Ordinary memory can be moved or paged out at any time, and the copy engine reads physical pages with no way to notice that they moved.

Chapter 10 of 14

Done, and provably so

The GPU writes back

The CPU must not use the block before it has really arrived, and it must not ask. Reading a GPU register across PCIe would cost up to a microsecond of waiting, on every copy. So the answer comes the cheap way: the GPU writes it. The last methods named a spot in host memory and a value. When the copy is finished the copy engine writes that value there. That is the semaphore.

Order is the subtle part. The copy's own writes into GPU memory and the semaphore write into host memory travel different paths. If the semaphore could land first, the CPU would see the value and read a block that is still in flight. FLUSH_ENABLE on the second launch forces every earlier write of the copy to land before the semaphore is written. It is a rule for correctness, and leaving it out gives wrong data, sometimes. libcuda's four-word release writes a 16-byte block, four 4-byte words, that holds the 4-byte payload and a timestamp of the moment of release.

There are two ways for the CPU to learn that the value changed. The GPU can raise an interrupt, which costs tens of microseconds to handle. Or a CPU thread can poll the spot in its own memory, which notices the change within about a microsecond and keeps one core busy while it waits. For short transfers polling wins, and CUDA's copy commands carry the semaphore for exactly that.

Either way the CPU only ever reads its own memory. Every crossing of the link in this whole copy was a write, or a read that the GPU started.

Chapter 11 of 14

Small copies pay more

A fixed cost per copy, and a clock that has to wake up

Copy engines are fast for big transfers and noticeably slower per byte for small ones. The measurements compared copies from GPU memory to host memory on an H100 PCIe, with the rebuilt library and with CUDA. At 4 MiB the rebuilt copy ran at 31.3 GB/s and CUDA at 35.7 GB/s. At 64 MiB both were near 54 GB/s. At 256 MiB the rebuilt copy ran at 55.1 GB/s and CUDA at 52.9, and at 1 GiB both reached about 55.5 GB/s, a plateau close to what the link allows.

The reason is a fixed cost per copy. About 15 µs of every copy is submission and completion: a few microseconds from the doorbell to the copy engine starting, and the rest for the flush, the semaphore becoming visible and the poll noticing it. On a 4 MiB copy that is about 11 percent. On a 64 MiB copy, which takes about 1,245 µs at 53.9 GB/s, it is about 1 percent. A KV cache moved in many small pieces pays that cost again for every piece.

There was a second, stranger cost. The first benchmarks of the rebuilt library ran at about two thirds of CUDA's rate, with timings clumped in a few discrete steps. The GPU's SM clock sat at its idle floor of 345 MHz, and the copy engine's rate followed that clock. CUDA sends one Resource Manager control at startup, NV2080_CTRL_CMD_PERF_BOOST, which asks for the highest performance state with no time limit. With it the clock ran at 1755 MHz. Adding that one call took a 256 MiB copy from about 38 GB/s to 54.8 GB/s, against 54.7 for CUDA in the same run. That was a separate run from the table above, which is why CUDA's 256 MiB figure differs between the two.

Two lessons for anyone who benchmarks a cache transfer. Use realistic sizes, because small chunks measure the fixed cost and say little about the link. And check the GPU's clocks before blaming PCIe.

Chapter 12 of 14

Leave out one fence

A bug that only shows under load

The CPU writes the pushbuffer, the ring entry and GPPut through write-combined mappings. The pushbuffer is ordinary host DRAM, and the ring entry and GPPut sit in GPU memory behind BAR1, but the driver maps all three write-combined for the CPU. Write-combining lets the CPU gather small stores in a buffer and send them out together, which is good for speed. The catch is that the buffer drains when the CPU decides, and not always in program order. So the submission carries four store fences, one after each step: after the commands, after the ring entry, after GPPut and after the doorbell. The x86 instruction is sfence. In C it is _mm_sfence(), which also stops the compiler from moving memory accesses across it.

Suppose the fence after the ring entry is missing. Most of the time nothing happens, because write-combining buffers often drain in order anyway. Now and then, under load, GPPut and the doorbell get out before the entry is complete. The front end wakes up, sees a new index, reads an entry that is only half written, and fetches garbage. The GPU reports it with an error code, an Xid, in the kernel log, where dmesg shows it.

Without a driver to explain, those codes are the debugger. Xid 32, invalid pushbuffer stream, means the front end could not make sense of the method stream: a missing fence, a missing SET_OBJECT, an unbound subchannel. Xid 31 is an MMU fault, a GPU client touching an address it cannot translate, and the report includes the faulting address. Xid 13 is an exception on the SMs. In production two more are worth an alert: Xid 79, a GPU that fell off the PCIe bus, and Xid 48, an uncorrectable double-bit memory error.

Chapter 13 of 14

Pay once

685 calls before the first copy, none during the copies

None of this works until someone has created the channel, built the ring, mapped the doorbell page into the process, pinned the memory and bound a copy engine. That is a lot of privileged work, done by the kernel modules and by the firmware on the GPU. The Resource Manager keeps it as a tree of objects, each with a class number: a root client, the device (0x80), the subdevice (0x2080), the USERMODE doorbell window (0xC661), GPU and host memory (0x40 and 0x3E), a GPU address space (0x90F1), a channel group (0xA06C), the channel with its GPFIFO and USERD (0xC86F), and under it the copy engine object (0xC8B5). Two ioctls drive nearly all of it: RM_ALLOC creates an object, and RM_CONTROL calls an operation on one.

Each call into GSP is a round trip between processors. The series puts each one at hundreds of microseconds to milliseconds, so setup takes hundreds of milliseconds. It was counted on an H100 for a program that sets up, copies twelve times and tears down. Setup made 361 Resource Manager ioctls, 87 unified memory ioctls and 237 firmware calls, 685 in all. The twelve copies made none. Twelve doorbells, and the kernel never learned the copies happened. Teardown made 3, 2 and 183. Setup also rang 193 doorbells, one for each pushbuffer submission libcuda made while it set up. Those are channel doorbells in the USERMODE window. The kick to GSP's queue register goes with each firmware call and is counted there.

A big, slow, careful control path, and a small, boring data path that never calls back into it. BNK is built the same way. Kubernetes objects configure TMM ahead of time, and TMM then handles each request on state that is already in place.

Chapter 14 of 14

Two quiet failures in setup

The wrong structure size, and a channel UVM was never told about

Setup can fail without leaving an error behind, and the series hit two such failures while rebuilding a copy without libcuda. Both look the same from outside. Every call returns, and the channel never does the work. Both sit on the slow path, so getting them right costs nothing per copy.

The first is the size of one structure. RM_ALLOC is escape 0x2B, sent as an ioctl to /dev/nvidiactl or /dev/nvidia0, and on Linux an ioctl's request number carries the size of the structure passed with it. For this one call the kernel accepts two sizes. NVOS21_PARAMETERS is the older form, 32 bytes: hRoot, hObjectParent, hObjectNew and hClass at 4 bytes each, an 8-byte pointer pAllocParms to the class's own parameters, then paramsSize and status. NVOS64_PARAMETERS is 48 bytes. It adds pRightsRequested, an 8-byte pointer to the access rights the caller asks for, which may be NULL, and a flags word whose one defined bit is NVOS64_FLAGS_FINN_SERIALIZED. Those fields come to 44 bytes, and 8-byte alignment pads them to 48. The first five fields sit at the same offsets in both forms, and escape.c checks that with five ct_assert lines, so a build in which they drift apart fails to compile. The kernel's escape.c chooses by size alone. 48 bytes goes to Nv04AllocWithAccessSecInfo, 32 bytes goes to Nv04AllocWithSecInfo, and any other size is refused with NVRM: invalid 43 structure size! in the kernel log, 43 being 0x2B in decimal. libcuda sends the 48-byte form for every object.

Creating the channel with NVOS21 failed silently in the series. No call reported an error, and the channel did not work. The open source shows both forms converging on the same allocator code, and the author never found out why. The fix was to send NVOS64 for every RM_ALLOC, exactly as libcuda does. That is the rule for anyone who drives a closed stack from the side: send the bytes the vendor's own library sends, down to the structure size, and check that the next step actually works. A call that returns only proves the kernel accepted the request.

The second is a registration step with UVM. The GPU address space here is built by UVM, which the Resource Manager calls an externally owned address space, so UVM has to know about every channel that runs in it. The order on /dev/nvidia-uvm is UVM_REGISTER_GPU, then UVM_REGISTER_GPU_VASPACE, which hands UVM the Resource Manager's address space object by rmCtrlFd, hClient and hVaSpace, then UVM_REGISTER_CHANNEL, UVM_IOCTL_BASE(27), with gpuUuid, rmCtrlFd, hClient, hChannel, base and length. Register a channel before its GPU address space and UVM answers NV_ERR_INVALID_DEVICE. Registration retains the Resource Manager's channel, reads where its instance block lives, in host memory or GPU memory, and places the channel's context buffers inside the range from base to base plus length in the process's address space. Then it binds them, which in the source's words tells RM the virtual address of each allocation so it can in turn tell the hardware where they are.

The Resource Manager enforces this when the channel is made runnable. NVA06F_CTRL_CMD_GPFIFO_SCHEDULE, command 0xa06f0103, sent with bEnable set, first asks whether the channel can be scheduled. If the channel's address space is externally owned, the channel runs on the graphics and compute engine, and its context is not bound, the driver logs Cannot schedule externally-owned <channel> with unbound allocations! and the call returns NV_ERR_INVALID_STATE. The comment above the check gives the reason: clients could allocate and schedule channels while skipping the UVM registration step. The check runs on bare metal, on the host and inside a guest. A copy engine channel can have no context buffers at all, and then UVM ignores base and length. In the current source the hard check covers graphics and compute channels only. The series registers its copy channel anyway, as libcuda does, and treats the step as required.

Both fixes cost a few calls at setup and nothing per copy. The twelve copies counted in the previous chapter made no kernel calls either way. A vLLM Pod such as qwen3-6f7d9c8b4-x7k2p goes through the same setup inside libcuda when it starts, before its three-minute weight load, so a mistake here stops the Pod long before any request reaches 10.244.1.21:8000.

What to keep

A queue, a doorbell, a completion

Behind a Pod IP there are two computers and a link with rules: someone has to start every transfer, writes are cheap, reads are expensive, and order is not guaranteed without a fence. So the CPU never copies data to a GPU and never asks whether it is done. It writes sixty bytes of commands into its own memory, adds eight bytes to a ring, and makes one four-byte write to a doorbell. The GPU fetches the work, a copy engine moves the data at tens of gigabytes per second, and the GPU writes a value into host memory to say so. All the expensive, privileged work happened once, at setup. That is why a cache hit in host DRAM is cheap and still not free, and why the endpoint picker has to know which tier a prefix is in. The Pod IP is where the network ends. It is not where the cost ends.
