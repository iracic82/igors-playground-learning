Kubernetes underneath

How the cluster hears of a change

List once, watch from there, and keep a copy

No part of Kubernetes calls another part to say that something happened. The kubelet does not ring the gateway when a model server is ready. Each component asks the API server for the objects it cares about, once, and then holds a connection open and receives every later change as it is stored. This is called list and watch. This lesson follows one change, the model server qwen3-6f7d9c8b4-x7k2p becoming ready, and shows who hears of it and what each one does. Then it takes the mechanism apart: the number that orders all changes, the cache inside the API server that answers the listeners, the stream, the local copy every listener keeps, the queue that decides when work is retried, and what happens when a listener is too slow or falls too far behind. It ends with the commands, logs and metrics an operator uses to see all of this on a live cluster.

Chapter 1 of 15

One write, and a new version number

Every stored change gets a resourceVersion

The model server qwen3-6f7d9c8b4-x7k2p has spent three minutes loading 34.3 GB of weights from the FP8 build Qwen3-32B-FP8. Its readiness check now passes, and the kubelet on gpu-node-1 writes that into the Pod's status. The API server stores the new Pod in etcd, the cluster's database. As it does, the Pod gets a new value in metadata.resourceVersion. This field is a string that names the version of an object as it is stored. Each stored change gives the object a new one. A client must pass it back exactly as it received it.

The number comes from etcd. etcd keeps one 64-bit counter for its whole key space, called the store revision, and adds one to it for every transaction that changes a key. Each key also remembers the revision of its last change, its mod_revision. When the API server reads a Pod back from etcd, it copies that mod_revision into metadata.resourceVersion. So the Pod's version jumps from 81102 to 81377, and the 274 numbers in between were used by other writes in the cluster, such as leases, events and other Pods.

For the kinds that kube-apiserver serves, the values can be ordered like growing whole numbers within one resource type. Two Pods can be compared, even in different namespaces. A Pod and a Deployment cannot. The documentation gives a rule that works without parsing into a fixed-size integer: both strings start with a digit from 1 to 9, the longer string is the greater, and two strings of equal length compare as text. Since Kubernetes 1.35 this ordering is part of the conformance requirements. For an extension API server a client should first check that the value is a decimal number, and otherwise only test for equality. The ordering is what lets a listener say where it stopped.

Chapter 2 of 15

The API server answers from its own cache

One watch on etcd for each resource type, shared by every listener

The listeners do not watch etcd. Only the API server talks to etcd, and for each resource type it keeps one watch of its own on etcd, feeding a structure called the watch cache. The flag --watch-cache turns it on and defaults to true. The watch cache holds the current state of every object of that type in memory and a history of the most recent changes. Every client watch on Pods, from the scheduler, the controllers and the two kubelets, is served from this cache. etcd sends the change once, and the API server copies it to every listener whose request matches it.

The history is a ring buffer of events per resource type. It starts at 100 events and can grow to 100 × 1024, which is 102,400. It doubles when it is full and all the events in it are younger than its fresh duration. It halves when it is full and even the newest quarter of its events began longer ago than that duration, which means about three quarters of the buffer is old. The fresh duration is 75 seconds, the default bookmark frequency of one minute plus 15 seconds. The 75 seconds is the target that decides when the buffer grows. It is no promise of history: at the upper bound of 102,400 events, a resource type that changes more than about 1,365 times a second (102,400 ÷ 75) keeps less than 75 seconds. The old flags --default-watch-cache-size and --watch-cache-sizes now do almost nothing. Caches are sized automatically, and the only useful value left for a resource is 0, which turns its cache off.

A request that wants the most recent data must wait until the cache is known to be up to date with etcd. When nothing changes for a resource type, no event arrives to prove that. So while at least one such request is waiting, the cache asks etcd for a progress notification every 100 milliseconds, and etcd answers with an empty response that carries the current revision. When no request is waiting, it sends none. Since Kubernetes 1.34 the gate ConsistentListFromCache is stable, so with etcd 3.4.31 or 3.5.13 and later even a request for the most recent data is answered from the cache, once the cache has caught up with the revision etcd reported.

Chapter 3 of 15

Three listeners get the same event

A watch is a request that the server keeps answering

Nobody polls for this change. Each listener opened a watch long ago: an ordinary GET with watch=1 that the API server does not finish. The server keeps the response open and writes one small JSON document into it for every change that matches. Each document has a type and the whole object as it is after the change. The Pod's new status goes out as MODIFIED on every watch that covers this Pod. The controllers receive it. The scheduler receives it, because it watches every Pod that has not finished. The kubelet on gpu-node-1 receives it too, even though it made the change, because its watch covers the Pods of its own node.

The filtering happens on the server. A watch names a label selector, a field selector or both, and the API server only sends objects that match. Field selectors work on a short fixed list of fields for each kind. For a Pod these include spec.nodeName, spec.restartPolicy, spec.schedulerName, spec.serviceAccountName, spec.hostNetwork, status.phase, status.podIP and status.podIPs. Any other field is refused with BadRequest and the message that it is not a known field selector. So the kubelet on gpu-node-2 never receives this event at all.

The documentation puts one Pod at roughly 2 KiB of encoded JSON. A Pod with a large status can be several times that, and the sizes on this page are illustrative. Each copy goes out separately, so the three listeners that match cost three sends. API priority and fairness, the API server's limit on concurrent work, also covers watches. It counts a watch against its seats only while the first burst of notifications is being sent, and then lets the seat go while the stream stays open.

Chapter 4 of 15

One change causes the next

A listener answers with a write of its own

One of the controllers keeps the EndpointSlice of the Service qwen3. An EndpointSlice is the object that lists the Pod addresses behind a Service, each with a ready flag. That controller watches Pods and Services. It sees that qwen3-6f7d9c8b4-x7k2p is Ready and writes the flag for 10.244.1.21. This is a second write, with a version number of its own, to a different kind of object. Its resourceVersion is one higher than the Pod's because nothing else was written in between. On a busy cluster the gap would be larger.

The gateway controller does not watch Pods at all. It watches EndpointSlices, so this is the event that reaches it. It adds the address to the gateway's list of backends, and requests start to arrive at the new model server. The kubelet and the gateway never exchanged a message. Each step waited for a write that came before it, and each component knows only the kind of object it watches.

The owner's lab shows the same pattern in F5 BIG-IP Next for Kubernetes. Its CNE controller watches the InferencePool objects of the Gateway API inference extension and its own F5EPPConfig objects. It programs the data plane's table of pools and endpoint pickers and manages one endpoint picker Deployment per pool. The picker learns its workers only from the Pods in its own cluster. In the lab a worker whose labels were changed so that it no longer matched the pool received no requests within 10 seconds. Nobody told the picker. It heard of the change the way every other listener does.

Chapter 5 of 15

A watch has to start somewhere

First the whole state, then every change after it

A watch only reports changes, so a listener first needs the state those changes apply to. A minute later the kubelet on gpu-node-2 is restarted after a driver update. It knows nothing. It sends one list request for the Pods of its node. The answer holds the Pods and, on the list itself, a resourceVersion. That number dates the whole answer. The kubelet then opens a watch and passes the number back. The server sends every change that came after it, so nothing is missed between the two requests.

The field means something different on the list than on each item. On an object, metadata.resourceVersion is the version at which that object last changed. On a collection it is the version at which the collection was put together. The Pod qwen3-6f7d9c8b4-m9q4t last changed at 80911, long ago. The PodList says 81402, which means: this is the state of every matching Pod as of 81402. Starting the watch from 80911 would replay changes the list already contains. Starting from 81402 replays exactly the ones it does not.

The watch request carries three more parameters. watch=1 turns the GET into a stream. resourceVersion=81402 says where to start. allowWatchBookmarks=true asks for the progress markers that a later chapter explains. The answer is 200 OK with no length given in advance. Over HTTP/1.1 the body uses chunked transfer encoding. Over HTTP/2, which client-go uses with kube-apiserver by default, HTTP/2 forbids chunked encoding and the events travel as DATA frames on one stream. Either way the server keeps the answer open until a timeout ends it. A newer way does both steps in one request, also covered later: a watch with sendInitialEvents=true first sends each existing object as ADDED, then a BOOKMARK, then the changes.

Chapter 6 of 15

Three ways to name a starting point

Unset, "0", or an exact number each mean something else

The resourceVersion parameter on a request is easy to misread, because the same value means different things on a get, a list and a watch. On a get or a list, leaving it unset asks for the most recent data, which must be consistent with etcd. The value "0" asks for any data, which is always served from the watch cache and may be older than something the client has already seen, for example right after the client switched to another API server. Any other value asks for data not older than that version. A list may add resourceVersionMatch=Exact or NotOlderThan to say which it wants, and sending resourceVersionMatch without a resourceVersion is invalid.

On a watch the same three cases read differently. Unset means: get the current state, send it as ADDED events, then follow from the most recent version. "0" means the same from any version the cache has, which again may be stale. Any other value means start exactly after that version, and in that case no ADDED events are sent for what already exists, because the client says it has that state already. The kubelet's watch from 81402 is of this third kind.

client-go's reflector, the part that does list and watch for most Go components, picks its starting point in one of two ways. In release 1.37 its gate WatchListClient is on, so it first tries a streaming list: one watch with sendInitialEvents=true and resourceVersionMatch=NotOlderThan, shown in a later chapter. On its first sync it leaves resourceVersion unset, so that initial state is a consistent read. Only when the server cannot stream does it fall back to a plain list. That first plain list sends resourceVersion=0 so that the watch cache can answer it without touching etcd, and a component on that path may begin from a picture that is slightly old and then catch up through the watch. A client can also name a number the server has not reached yet. For a get or a list, kube-apiserver waits up to 3 seconds for its cache to catch up and then answers 504 with the message Too large resource version and a Retry-After of 1 second. A watch with such a number waits until its request times out.

Chapter 7 of 15

Big lists come in pages

limit, continue, and a resourceVersion that stays the same

One node has five Pods. A list of all Pods in a large cluster can be tens of thousands of objects, and the documentation warns that such an answer may be 10 to 20 MB. To keep that manageable a client can ask for a page with limit, and the server returns at most that many items with a continue token in metadata.continue. The client sends the token back with the same query to get the next page, and stops when the token comes back empty. Every page carries the same resourceVersion, the moment the first page was taken, so the pages fit together as one consistent list.

kubectl get uses this by default. Its flag --chunk-size is 500, and 0 turns paging off. client-go's pager also asks for 500 at a time. Inside the API server the watch cache reads etcd in pages of 10,000. In this cluster you run kubectl get pods -A --chunk-size=20 to see paging happen. With 46 Pods across all namespaces, illustrative, that takes three requests: 20, then 20, then 6. The first answer says remainingItemCount: 26. The second says 6. The server leaves that field out when the list used a label or field selector, because it cannot count matches it has not looked at yet.

A continue token does not live long. It expires after about 5 minutes by default, and a client that comes back later gets 410 Gone, reason Expired, together with a new token. That token goes on from the next key, but from the latest snapshot, so its pages are inconsistent with the pages already received: objects created, changed or deleted in between may show up or be missing. A client that needs a consistent list must start again without continue. client-go's pager handles this by falling back to one full list. Responses to list and get are also compressed with gzip when the client sends Accept-Encoding: gzip, which has been on by default since Kubernetes 1.16.

Chapter 8 of 15

One request instead of two

A streaming list sends the state as events, then a marked bookmark

A list followed by a watch costs memory on both sides. The server has to build the whole list in one answer, and a controller that watches tens of thousands of objects pays for that at every restart. Streaming lists replace the two requests with one watch. The client sets sendInitialEvents=true, resourceVersionMatch=NotOlderThan and allowWatchBookmarks=true. The server first sends every existing object as an ADDED event, then one BOOKMARK that marks the end of that initial state, and then the changes as usual. The marker is the annotation k8s.io/initial-events-end: "true" on the bookmark's object. With resourceVersion unset, the initial state is a consistent read.

The feature has moved back and forth, so the version matters. On the server the gate WatchList was alpha from 1.27 to 1.31, beta and on in 1.32, turned off again in 1.33 because the ordinary JSON and protobuf list encoders had become good enough, and beta and on again from 1.34. On the client, client-go's gate WatchListClient was beta and off from 1.30 to 1.34 and beta and on from 1.35. When the server does not support it, the client falls back to a plain list without telling its user.

In this cluster the gateway controller is restarted after an upgrade, about thirty seconds after the kubelet's list. Its reflector opens one streaming watch on EndpointSlices. It receives the slice for qwen3 as ADDED, then the marked bookmark at 81460. Only after that bookmark does it treat its cache as filled. It then goes on reading changes from the same stream without a second request.

Chapter 9 of 15

Every listener keeps a copy

Decisions are read from a local cache

A component does not ask the API server each time it needs to know something. Go components use a library, client-go, that packs list and watch into a part called an informer. Inside it a reflector does the list and the watch. Each object that arrives is saved in a local store, under a key made of namespace and name. Then a handler is called, and the usual handler only puts that key on a work queue. A worker takes the key and reads the object from the store. So a controller asking which Pods belong to qwen3 reads its own memory. Without this, two model servers and their controllers would load the API server with the same questions all day.

Between the reflector and the store sits a queue of deltas. Each delta is named Added, Updated, Deleted, Replaced or Sync. Replaced is what a relist after a watch error produces, and Sync is the periodic resync. The handler contract in client-go says three things a controller author must know. An update handler is also called on a relist, even when nothing changed. Several changes may arrive combined as one, so a handler cannot count on seeing every step. A delete handler may receive an object of type DeletedFinalStateUnknown instead of the last state, when the delete happened while the watch was down and was only found by the relist. Handlers must never change the objects they receive.

A controller must not act on an empty cache. It calls WaitForCacheSync, which checks every 100 milliseconds and logs Waiting for caches to sync, then Caches are synced, with the controller's name. Resync is no relist. It replays the local store to the update handler on a timer, at least 1 second apart. In kube-controller-manager the flag --min-resync-period is 12 hours, and each reflector picks a period between that and twice that.

Chapter 10 of 15

The work queue decides when to try again

Keys are merged, failures wait longer each time, and stale writes are refused

The work queue between the handlers and the workers does more than hold keys. If the same key is added several times before a worker takes it, it is processed once. A key that a worker is processing is never handed to a second worker at the same time. A burst of ten changes to one EndpointSlice therefore costs one pass of the controller, which reads the newest copy from the store. This only works because the controller acts on the state and ignores how it got there.

When a worker fails, it puts the key back with a rate limit. client-go's default limiter combines two rules and uses the longer delay of the two. Per key, the delay starts at 5 milliseconds and doubles on every failure up to 1000 seconds: 5, 10, 20, 40 ms and so on. For the queue as a whole a token bucket allows 10 retries per second with a burst of 100. When the key finally succeeds, the controller tells the queue to forget it, and the next failure starts again at 5 milliseconds.

Not every controller uses that default. The EndpointSlice controller queues Service keys, and its limiter starts each key at 1 second instead of 5 milliseconds, doubling to at most 1000 seconds: 1, 2, 4, 8 seconds and so on. Its source says the higher start keeps the controller from overwhelming the API server, because one Service change can mean large slice changes. It combines that with the same bucket of 10 per second and burst 100. After 15 retries of one key it logs Retry budget exceeded, dropping service out of the queue, and forgets the key until the next change.

A common reason to retry is a conflict. Every update carries the resourceVersion the writer read. If the object changed in between, the API server refuses the write with 409 Conflict, reason Conflict. This is optimistic concurrency: nothing is locked, and the loser reads again and decides again. In the example on this page the EndpointSlice controller tries to write the slice from a copy that is one version behind, because the slice changed a moment earlier. It is refused. The worker logs Error syncing endpoint slices for service, retrying, and puts the Service key inference/qwen3 back on its queue with a delay of 1 second. Then it computes the slices for the Service again from the Pods and slices in its stores, which now hold the newer copy, and the write succeeds. The whole sequence is illustrative.

Chapter 11 of 15

A quiet stream still moves forward

Bookmarks, and watches that end on purpose

The kubelet on gpu-node-2 watches a handful of Pods, and one of them is the model server. Hours can pass with no event for them, while the rest of the cluster changes all the time. Its last known resourceVersion would grow old. The BOOKMARK event solves that. Its object holds only the kind, the apiVersion and a newer metadata.resourceVersion, and it means that everything up to this number has been sent. A client asks for bookmarks with allowWatchBookmarks=true. The documentation does not promise when the server sends them, or that it sends any.

The kube-apiserver source of release 1.37 does send them on a pattern. It aims for one roughly every minute, and one 2 seconds before the watch's deadline, so that a client reconnecting after a timeout starts from a number that is as recent as possible. The comment in the source says the second rule covers 99 percent of cases. That is the reason the cache's history window is the bookmark frequency plus 15 seconds.

Watches also end on purpose. A client sets timeoutSeconds, and client-go picks a random value between 5 and 10 minutes so that thousands of watches do not all reconnect at the same moment. When the client sends none, the server picks a random time between 1 and 2 times --min-request-timeout, which defaults to 1800 seconds, so 30 to 60 minutes. When the stream closes, the client opens a new one from the last number it holds, with no list. A connection that dies without closing is found separately. client-go sends an HTTP/2 ping when it has read nothing for 30 seconds and gives up if no answer comes within 15 seconds.

Chapter 12 of 15

A listener that cannot keep up is cut off

The server never waits for a slow client

The watch cache hands each event to every matching watcher through a small buffer per watcher. If a watcher's buffer is full because its client reads too slowly or its network has stopped, the server does not slow down every other listener to wait for it. It closes that watch. It counts the event in the metric apiserver_terminated_watchers_total, which sits outside the apiserver_watch_cache_ prefix, and logs, at verbosity 1, a line that begins Forcing … watcher close due to unresponsiveness. The client sees its stream end and has to reconnect. If the cache itself loses its watch on etcd, it ends every client watch on that resource type at once and logs Terminating all watchers from cacher as a warning.

At 600 seconds into this story the network path between the gateway controller and the API server fails. The server's buffer for that watch fills and the server closes it. On the controller's side no data arrives. After 30 seconds without a frame client-go sends an HTTP/2 ping, and after 15 more seconds without an answer it closes the connection, so the reflector knows 45 seconds after the failure. It tries again and fails, because the network is still down.

The reflector retries with a growing delay. It starts at 800 milliseconds, doubles each time, adds random jitter of up to the same amount again, and stops growing at 30 seconds. After 2 minutes without a failure the delay resets. The reflector logs Failed to watch with the error on each attempt. While a watch cache is starting up or rebuilding, the server refuses watches and unpaged or filtered lists with 429 Too Many Requests and a Retry-After header between 1 and 30 seconds, and clients are expected to honour it.

Chapter 13 of 15

Too old: 410 Gone

History is kept for minutes, and then it is gone

A watch from an old number only works while the server still has the changes that followed it. It does not keep them long. A cluster on etcd 3 keeps about the last five minutes of changes by default. The API server itself causes that: it asks etcd to compact, which throws away old revisions, at the interval set by --etcd-compaction-interval, 5 minutes by default, and 0 turns its compaction requests off. The API server's etcd layer learns where the last compaction was by watching the key compact_rev_key in etcd, which the compacting servers also use to agree on who compacts. With the gate ListFromCacheSnapshot on, beta and on since 1.34, the watch cache reads that point every 15 seconds and drops the list snapshots it kept from before it.

There are two windows. Most watches are served from the watch cache, and the cache aims for 75 seconds of history: more when its buffer has room, less on a resource type that changes so fast that 102,400 events fill up sooner. A watch that the cache cannot serve from its history is refused with the message too old resource version, followed by the requested number and, in brackets, the oldest number a watch may still start from. That is one less than the oldest change the cache can still deliver. A watch that reaches etcd behind a compaction gets etcd's error mvcc: required revision has been compacted, which the API server turns into the same refusal.

Now the gateway controller's network comes back at 1800 seconds, twenty minutes after it failed. It asks to continue from 82010, the last number it saw. The server no longer has that history. The request itself was valid, so the watch cache answers 200 OK, sends one event of type ERROR whose object is a Status with code 410 and reason Expired, and ends the stream. The source says so in a comment: once a watch has passed authentication, authorization and admission and its resourceVersion has been parsed, other errors must arrive as an ERROR event and never as a returned error, to match the watch that goes to etcd directly. Servers up to 1.17 used the reason Gone. A list or a continue token that is too old gets 410 Gone as the HTTP status of the answer itself.

The rule for a client is fixed: start over from the current state. In release 1.37 client-go's reflector does that with a streaming list again. It opens a watch with sendInitialEvents=true, resourceVersionMatch=NotOlderThan and resourceVersion=82010, which asks for a state not older than that number, so the watch cache can answer without etcd. Only if that also fails as too old does it try once more with resourceVersion unset, a consistent read. A client that cannot stream does the same with a plain list and then a watch from the list's number. Either way it receives every object once more and follows changes from a new number.

Chapter 14 of 15

It missed three events and needs none of them

Components act on the state, whatever the history was

During those twenty minutes the EndpointSlice changed three times. The container of qwen3-6f7d9c8b4-m9q4t restarted, so its address went to not ready. Three minutes later the weights were loaded and it was ready again. Then the container of qwen3-6f7d9c8b4-x7k2p restarted, and that Pod is still loading. The gateway controller saw none of this, and the server will not replay it. It does not need the replay. The fresh list says how things stand now, and the controller makes the gateway match that.

Kubernetes calls this level-based behaviour, as opposed to edge-based. An edge-based component reacts to each change as a signal: ready, then not ready, then ready. If it misses one, its picture is wrong for good. A level-based component reads the state as it is and makes the world match it. A missed step in between does no harm. Informers, the merged keys on the work queue, the periodic resync and the list after a 410 all exist to serve this one idea.

The owner's lab shows the same idea on a real product. F5's CNE controller manages the endpoint picker Deployment of each inference pool. When that Deployment was scaled to zero by hand, the controller saw that the state no longer matched what it wanted and scaled it back, while a standby picker carried on. It did not need to know who scaled it or when. Level-based behaviour has one limit, and the next beat shows it. It repairs the picture once a controller can listen again. While the gateway controller was cut off, the gateway kept its old instructions, including a backend that was not ready.

Chapter 15 of 15

Seeing the streams on a live cluster

kubectl watch flags, log lines and metrics

Everything in this lesson can be watched by hand. kubectl get with --watch, or -w, first lists the objects and then keeps printing changes. --watch-only skips the list. --output-watch-events adds the event type to each line and prints the objects that already exist as ADDED, and it fails with an error if used without --watch or --watch-only. With -o json each line is the event object itself, the same document a controller receives. Running kubectl get endpointslices -n inference -w --output-watch-events while qwen3-6f7d9c8b4-x7k2p finishes loading shows the slice go from ADDED to MODIFIED as the ready flag flips.

The components say what their reflectors do when their verbosity is raised. At verbosity 3 a reflector logs Starting reflector and Listing and watching. At 2 it logs Caches populated. At 4 it logs Watch closed for an expired watch, and at 1 Watch closed with unexpected EOF. Failed to watch is logged as an error. A watch that ends in under a second with no items logs very short watch, which usually points at a server or proxy that closes long requests. On the server, kube-apiserver logs Starting watch at verbosity 3 with the path, the resourceVersion, the selectors and the timeout it chose.

The API server's metrics give the totals. apiserver_longrunning_requests counts open watches by resource and component. apiserver_watch_events_total counts the events sent and apiserver_watch_events_sizes their sizes. The watch cache adds its own series under apiserver_watch_cache_, among them resource_version, capacity, events_received_total and events_dispatched_total. The watchers it closes for being slow are counted in apiserver_terminated_watchers_total, which carries no watch_cache_ in its name. A rising count of terminated watchers or a stream of 410 relists is the sign that some listener is too slow or too far away.

What to keep

List, watch, cache, and act on what is there

Every component learns of changes the same way. It lists the objects it cares about and gets a resourceVersion that dates the answer. It watches from that number and receives each later change as ADDED, MODIFIED or DELETED, with a BOOKMARK now and then to keep its position recent. The API server answers all of them from one watch cache per resource type, fed by a single watch on etcd, and closes any listener that cannot keep up. Each listener keeps the newest copy of each object in memory, puts keys on a work queue that merges repeats and retries with a growing delay, and decides from its copy. When its number is older than the history the server holds, it gets a 410 with reason Expired and fetches the whole state again, as a streaming list or a plain one. Because each component acts on the current state, a missed event costs nothing once it can listen again. That is how one Pod turning ready reached a gateway that the kubelet never spoke to.
