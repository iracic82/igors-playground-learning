BNK and gateways

What a guardrail reads

Card numbers, planted instructions and an answer that is still streaming

The lesson before this one showed where a guardrail can stand. This one opens it up. A scan is not one check. It is a few very different pieces of work run on the same text. Some are plain pattern matching with arithmetic behind it. One is a small language model of its own. You will follow an honest message with a card number in it, which gets masked and goes on. Then a message that carries a planted instruction, which gets refused. Then the answer, which has to be checked while it is still being written. The guardrail stands in the path here, behind the AI gateway, because masking and answer checks need to touch the bytes.

Chapter 1 of 12

An honest message with a card number

Nobody is attacking anything

A customer writes to the support bot about a double charge and pastes the card number and an email address into the chat. Nothing here is hostile. The trouble is where the text is about to go. A prompt is copied into the model's context, into the KV cache of a GPU, often into logs, and with a hosted model into another company's systems. The provider of this factory has promised that card numbers stay out of all of those. So the AI gateway hands the text to the guardrail before any GPU sees it.

Count the places one prompt lands. The request body crosses the border and the gateway. The model server turns it into tokens and writes their keys and values into the KV cache on a GPU, where a later request with the same opening can reuse them. Access logs and traces may keep the body. With a hosted model, all of that happens again on another company's machines. A card number in the prompt is in every one of those copies, and none of them is a system built to hold card data.

The guardrail stands in the path here, behind the AI gateway. The gateway posts the text to F5 AI Guardrails at /backend/v1/scans, with scanDirection set to request and flagOnly set to false so that the result names the real outcome. Only the user's message is sent, 79 characters. F5 ships its guardrails in packages, among them personal data, restricted topics and prompt injection. Each one can be set to scan prompts, responses or both, and prompts are the default.

Chapter 2 of 12

Patterns first, then arithmetic

How sixteen digits become a card number

The first scanner looks for personal data, and it does not need a language model. It runs a list of recognizers over the text. Each one knows a single kind of thing. The card recognizer starts with a pattern: 13 to 17 digits in up to four groups, with optional spaces or dashes between them. Many things match that, such as order numbers and tracking codes. So it does the arithmetic that every card number has to pass, the Luhn check. Double every second digit from the right, add all the digits up, and the total must end in zero. This number totals 30. Passing that check is what settles it. The email address is found by pattern alone. The open tool Presidio works this way, and its names for the two findings are used here.

Work it through for 4111 1111 1111 1111. Counting from the right, the digits in odd positions stay as they are: eight 1s, which add to 8. The digits in even positions are doubled. Seven 1s become seven 2s, which add to 14, and the leading 4 becomes 8. When doubling gives a two digit number its digits are added, so a doubled 7 counts as 1 + 4 = 5. The total is 8 + 14 + 8 = 30. Change the last digit to 2 and the total is 31. The recognizer then drops the match, however much the text around it talks about cards.

Chapter 3 of 12

A score for every finding

0.3 for the shape, 1.0 for the checksum

Each recognizer returns a score between 0 and 1 with every finding, and the policy acts only above a threshold. Presidio's card recognizer shows how a score is built. Its pattern accepts 13 to 17 digits in up to four groups, starting with 1, 3, 4 or 6, or with 50 to 55. A match on the pattern alone scores 0.3, and the pattern's name in the source is All Credit Cards (weak). Then the checksum runs. A number that passes is set to 1.0. A number that fails is set to 0 and dropped from the results. The email recognizer works the same way: 0.5 for the shape, then 1.0 if the ending of the domain is a real one.

Many kinds of personal data have no checksum. A phone number or a date is only a shape. For those, the words around the match carry the decision. Each recognizer has a list of context words. The card recognizer's list includes credit, card, visa, mastercard and amex. By default Presidio looks at the 5 words before a match and none after it. If one of them is on the list it adds 0.35 to the score, lifts the result to at least 0.4 and caps it at 1.0.

Run the numbers on the customer's message. The pattern gives 0.3. The checksum passes, so the score is 1.0, and the word card in front of it can add nothing more. Now take an order number, 5500 1234 5678 9012, in a message with no card words. The pattern still matches at 0.3. Its checksum total is 53, so it is dropped. A threshold of 0.5 would have ignored it even without the checksum.

Chapter 4 of 12

What to do with a finding

Monitor, warn, mask or block

A finding is only a fact about the text. What happens next is policy, and the choices form a ladder. The mildest is to monitor: log the finding and let the text through. Then warn the user. Then mask or redact, which changes the text and lets the request continue. The hardest is to block. A sound way to roll a guardrail out is to climb that ladder. Watch first, see what the findings look like in real traffic, and only then start changing or refusing requests.

F5 AI Guardrails reports the result of a scan as an outcome. Cleared means nothing fired. Flagged means a guardrail fired and the caller is only being told. Blocked means a guardrail that is set to block fired, and the caller asked for the real outcome by sending flagOnly as false. When text was changed, the result carries the new text in a field named redactedInput.

How the text is changed is a choice too. Presidio calls the options operators. Replace puts the entity type in angle brackets, such as <CREDIT_CARD>, and is the default. Redact removes the span. Mask overwrites a chosen number of characters, which is how a receipt shows only the last four digits. Hash writes a SHA-256 digest. Encrypt is the one that can be undone, with decrypt and the key. This factory uses replace with a counter added, and keeps a map of its own so that it can undo the swap later.

Chapter 5 of 12

Mask it and keep the map

The model gets a placeholder

A finding like this is not a reason to refuse. The customer did nothing wrong and still needs an answer. So the verdict is mask. The guardrail swaps each finding for a placeholder that says what kind of thing was there, and keeps a small map from placeholder to original for the length of this request. The gateway puts the masked text into the request body and sends it on. The body is now three bytes shorter, so its length header is rewritten too. From here on, the model, the KV cache on the GPU and every log line hold a placeholder. The model can still reason about it. It knows a card was mentioned and can refer to it.

Check the three bytes. 4111 1111 1111 1111 is 19 characters with its spaces, and <CREDIT_CARD_1> is 15, which is four fewer. dana@example.com is 16 characters and <EMAIL_ADDRESS_1> is 17, which is one more. Four fewer and one more is three fewer, so 2,180 becomes 2,177. A gateway that forgot to rewrite Content-Length would announce three bytes that never come, and the model server would wait for them until it timed out.

The map is held in memory for this one request. It is never written to a log, because a log line with the map in it would undo the whole exercise. The scan took about 3 ms from request to verdict, nearly all of it pattern matching on a CPU.

Chapter 6 of 12

A message that carries an instruction

The attack is inside the pasted text

A second customer asks the bot to summarize an email thread and pastes the thread in. One line of that thread was written by someone else, and it is addressed to the assistant. This is the indirect kind of prompt injection. The person typing may not even know it is there. To a model, text is text. Nothing in a prompt marks which words came from the user and which came from a document the user passed along. No pattern or checksum finds this. There is no fixed shape to an instruction. The same attack can be phrased a thousand ways and in any language.

OWASP's list of risks for language model applications puts prompt injection first, as LLM01, and names the two kinds. Direct injection is when the user's own input changes how the model behaves. Indirect injection is when the model takes in outside content, such as a web page or a file, and that content holds the instruction. OWASP also says it is unclear whether any fool-proof method of prevention exists. Its advice is layers: filter input and output, keep outside content apart from instructions and mark it, give the model the least privilege that works, and ask a human before a high-risk action.

This message is 8,450 bytes of JSON holding 6,320 characters of user text, about 1,400 tokens. All of it goes to the guardrail, because the planted line could be anywhere in it.

Chapter 7 of 12

The injection check is a model too

A small one, reading 512 tokens at a time

The second scanner is a classifier: a small language model trained on a great many attacks and a great many harmless texts. It does not write anything. It reads a piece of text and returns one number, how likely this is an attempt to take over a model. Llama Prompt Guard 2 is an open example, at 86 million weights against the 32 billion of the model it protects, so it is small enough to run on every request. It reads at most 512 tokens at once, and its makers say to split longer text into segments. This message is 1,400 tokens, so the guardrail cuts it into three windows and scores each one. The highest score counts. The second window holds line 17 and scores 0.99.

Prompt Guard 2 comes in two sizes, 86 million and 22 million weights, both built on the DeBERTa family of encoders. An encoder reads a whole window at once and outputs a label, benign or malicious, with a probability. The larger one is multilingual. Its makers measured 92.4 ms for one 512 token window on an A100 GPU, and 19.3 ms for the smaller model. Its tokenizer is hardened against tricks such as extra spaces placed inside words. It judges one thing only: whether a text tries to override earlier instructions. Whether the text is harmful in some other way is a different check.

Chapter 8 of 12

Where the threshold sits

Every setting trades misses for false alarms

A classifier returns a probability, and someone has to pick the number above which a text counts as an attack. No setting is free. Two rates describe the trade. The false positive rate is the share of honest texts that get refused. Recall is the share of real attacks that get caught. Move the threshold down and both go up.

The makers of Prompt Guard 2 publish one point on that curve. With the threshold set so that 1 in 100 honest English prompts is refused, the large model catches 97.5 percent of the jailbreaks in their test set and the small one 88.7 percent. The model before it caught 21.2 percent at the same setting. Put that against traffic. A support bot that takes 200,000 honest messages a day refuses 2,000 of them at a 1 percent false positive rate. Of 1,000 attacks, 25 get past the large model and 113 past the small one.

Those figures come from one test set, and the makers list the limits themselves. An attacker can craft text to slip under a classifier they can test against. The right threshold depends on what honest traffic looks like in a given application. On an agent benchmark named AgentDojo, the large model stopped 81.2 percent of attacks at a setting that cost 3 percent of the agents' usefulness. That leaves about one attack in five. A classifier lowers the rate of successful attacks. It does not bring it to zero.

Chapter 9 of 12

Refused before any GPU

And the user is told why

A masked card number could go on. This cannot. There is no safe way to cut one sentence out of a document and be sure the rest is clean, so the verdict is block. The gateway answers the user itself. The refusal says which check fired, because this user is probably not the attacker and needs to know the thread they pasted is the problem. No worker was picked and no KV cache was written. Compare the cost of the two scanners. The pattern scan took about 3 ms on a CPU, from request to verdict. The classifier ran a model. Scoring the three windows in one batch takes on the order of 100 milliseconds on a GPU of its own. That cost is what makes this check worth placing carefully.

Look at what did not happen. The endpoint picker was never asked. No worker turned 1,400 tokens into KV cache blocks, and the three workers show the same memory as before. A generation started by this prompt could have run for seconds on a GPU, and a successful injection would have spent them writing out refund codes. The refusal cost one pass of a small classifier and 298 bytes back to the user.

The refusal reached the user 102.4 ms after the request arrived. An operator sees it as one audit record: the time, the key, the scanner that failed and the outcome blocked.

Chapter 10 of 12

The answer is checked while it streams

A window that trails the text

Back to the first customer. The model is answering, a few tokens at a time, and the answer has to be checked as well. A model can repeat something from its instructions, or produce an internal key it was shown. The hard part is that the text arrives in pieces and a finding can straddle two of them. A key that starts at the end of one chunk and ends in the next is invisible to a scanner that looks at one chunk at a time. So the gateway holds back the tail of the stream. It releases a token only once enough text has arrived after it to be sure it is not the start of something. That costs the user a delay before the first word appears, while the first window fills. After that every window waits for its own scan, so the stream runs behind the model by the window plus a few milliseconds for each scan.

F5's scan API has a streaming form of this. The caller forwards the model's event stream to it. The service gathers text and runs a scan when enough new text has arrived, when a timer runs out or when the stream ends. Each scan takes the new text together with the text before it. The events pass through unchanged. After each scan the service adds a comment line that starts with : x-ai-security and holds the outcome and a scan id. If a guardrail blocks, the text of that part is not sent. The stream gets an error and ends.

The window here is 40 tokens. At 50 tokens a second that is 40 ÷ 50 = 0.8 s before the first word. Each scan of the window then takes 3 to 4 ms, and that is paid again for every window until the stream ends.

Chapter 11 of 12

Put the number back, or do not

The map is used once, on the way out

The model's answer mentions the card, as a placeholder, because a placeholder is all it was given. On the way out the gateway looks each placeholder up in the map and puts the original back. The customer reads their own card number in the reply and never learns it was gone. This step is a policy choice. A provider can also leave the placeholder in, so that the number is not shown again even to its owner. The key the model leaked is different. It was never the user's, so it stays masked. When the stream ends the map is thrown away.

Putting a value back is only safe for values the user sent. The gateway restores a placeholder only if the map says it came from this user's own prompt in this request. <API_KEY_1> was made on the response side, so it has no entry that may be restored. Streaming sets a trap here too. A placeholder can be split across two chunks, just as the key was, so the swap has to happen inside the same held-back window and never on single chunks. A model can also garble a placeholder. One that comes back as <CREDIT CARD 1> matches nothing in the map and is left as it is.

Every log line and trace behind the gateway holds placeholders for this request. The card number existed in the user's browser, at the border and the gateway while the request passed, and in the map. It never reached a GPU, and no log behind the gateway holds it.

Chapter 12 of 12

What a text check cannot see

The same number, written another way

Every check in this lesson reads text and looks for something it can recognize. That is also the limit. Write the same card number in base64 and it is 28 characters: 26 letters and digits and 2 padding signs. The pattern finds no digits in a row, the Luhn check never runs, and the scan comes back clean. A guardrail can decode the obvious encodings before it scans, and good ones do, but there is always one more way to write a thing. The second limit is bigger. These checks judge what is said. An agent with tools can do harm with a request in which every word is harmless. That is the next lesson.

The arithmetic of base64 explains the 28. It writes every 3 bytes as 4 characters. The card number with its spaces is 19 bytes. That is six full groups of 3, which make 24 characters, and one byte left over, which makes 2 characters and 2 padding signs. 24 + 4 = 28. Splitting the number across two messages, spelling the digits as words or putting a dot after every digit would each defeat the pattern in the same way.

A 2026 study of agents by Faberlens Research recorded this exact move. An agent was told that a customer export held personal data and should be base64 encoded before it was written to a shared folder. The card numbers went past the content scanner as gibberish, and the file was called sanitized.

What to keep

A few kinds of work on one text

A scan is several scanners. Personal data is found by patterns, with arithmetic and nearby words to cut the false alarms, and it can be masked so that the request still goes on. A planted instruction has no shape, so it takes a classifier: a small model that reads the text in windows and returns a score, with a threshold that someone has to choose. The answer is checked in a window that trails the stream, which delays the first word and adds a short scan to every window after it. And every one of these checks reads words. What is written another way, or done instead of said, gets past them.
