Kubernetes underneath

Who may talk to whom

How a NetworkPolicy leaves the web Pods reachable by the client alone

A Pod that listens on a port answers anyone who can reach it. In a new cluster that is every Pod, because Kubernetes puts no limits on traffic between Pods. A NetworkPolicy changes that for the Pods it selects. It picks Pods by label, names a direction and lists who is allowed. This lesson writes one policy for the Pods of the Service web, so that only Pod client may reach them on port 8080 and another Pod on the node may not. It follows the policy from the API server to the node that enforces it, opens up one agent to see how it decides about a packet, and reads the trace a refused packet leaves. Then it covers the timing, the egress side with its DNS trap, and the places where the API says nothing. The same rule is how a model server's Pods are restricted to their gateway: select the model servers by label and allow the gateway's namespace on the serving port.

Chapter 1 of 11

Every Pod accepts every caller

With no policy, nothing stands between any Pod and the web Pods

Three Pods run in the namespace inference. Pod client is on node-1. web-1 on node-1 and web-2 on node-2 are the Pods of the Service web, and each listens on port 8080. Kubernetes calls a Pod in this state non-isolated. It is non-isolated for ingress, which is traffic coming in, and for egress, which is traffic going out. Nobody wrote a rule to permit this. It is what having no rules means. The web Pods are meant to serve Pod client and nobody else, yet any Pod can call them. In this lesson web-1 plays the part of any other Pod on the node. It calls web-2 directly at its Pod address. The packet crosses the bridge, goes through the tunnel to node-2 and reaches the Pod, and web-2 answers.

The Service web does not change this. A Service gives the Pods a stable name and address, and the Pod addresses stay reachable all the same. Anyone who learns 10.244.2.17 can skip the Service and go straight to the Pod.

On a GPU cluster the same gap is wider. A model server such as vLLM listens on port 8000 and answers whoever sends it a prompt. The gateway in front of it may check keys, count tokens and refuse some requests. A Pod that calls the model server's address directly skips all of that. The endpoint picker of the AI gateway lessons is another example. In the owner's BNK lab it listened on port 9002 without TLS, and F5's own admission check refused to turn TLS on for it, because BIG-IP Next connects to the picker in plaintext. The lab closed that port to everything but BNK's own namespace with a NetworkPolicy. This lesson shows how such a policy works, using the web Pods because they are simpler.

Chapter 2 of 11

A policy selects Pods and names a direction

Two fields are enough to close a Pod

A NetworkPolicy is an object in a namespace. Its spec starts with two fields. podSelector picks the Pods the policy applies to, by label, inside the policy's own namespace. policyTypes lists the directions the policy covers: Ingress, Egress or both. These two fields alone change the selected Pods. A Pod selected by any policy that has Ingress in its policyTypes becomes isolated for ingress. From then on the only connections into it are those that some policy allows, and those from its own node. The policy here selects the label app: web and names Ingress. Both web Pods are now isolated for ingress, and their egress is untouched. Pods that no policy selects stay exactly as open as before.

The defaults of these two fields catch people out. podSelector is optional, and a policy that leaves it out gets an empty selector, which matches every Pod in the namespace. If policyTypes is left out, Ingress is always set, and Egress is added only when the policy has egress rules. A policy meant to restrict only outgoing traffic must therefore say policyTypes: [Egress] in so many words. The API refuses more than two entries in policyTypes. The policy's own name must be a valid DNS subdomain name, such as web-from-client.

kubectl describe networkpolicy shows how the API server understood the object, in plain words. For the policy here it prints PodSelector: app=web, then Allowing ingress traffic: with the rules, then Not affecting egress traffic, then Policy Types: Ingress. An empty selector is shown as <none> (Allowing the specific traffic to all pods in this namespace). The Kubernetes page on policies gives the same advice: when in doubt, use kubectl describe to see how the policy was interpreted.

Chapter 3 of 11

The rule says who is allowed in

from says who, ports says where, and one dash changes the meaning

The ingress field is a list of rules. A rule allows traffic that matches both its from part and its ports part. An entry under from can hold three things. A podSelector picks Pods in the policy's own namespace. A namespaceSelector picks whole namespaces by their labels. An ipBlock picks a range of addresses written as a CIDR, and can leave pieces out with except. Pod client runs in the same namespace as the web Pods, so this rule needs only a podSelector for the label app: client. A caller in another namespace takes a namespaceSelector and a podSelector in one entry. That means Pods with that label inside that namespace. Written as two entries, the same lines would allow every Pod in that namespace, and also every Pod with that label in inference. ports then narrows the rule to TCP port 8080.

Empty and missing mean different things here, and the API types spell it out. A rule with no ports, or an empty list, matches every port. A rule with no from matches every source. An empty podSelector inside from selects every Pod, and an empty namespaceSelector every namespace. So ingress: [{}] is one rule that allows everything, while ingress: [] or no ingress at all allows nothing.

A namespace cannot be named directly. The control plane puts the label kubernetes.io/metadata.name on every namespace, with the namespace's name as its value, and nobody can change it. Selecting on that label is how a rule names one namespace. matchExpressions also works, for example the operator In with a list of names.

A port can be a number or the name of a port the Pod declares, and the plugin then resolves the name Pod by Pod. endPort extends a numbered port into a range. An ipBlock takes IPv4 or IPv6, and except must lie strictly inside cidr. The documentation's example allows 172.17.0.0/16 except 172.17.1.0/24, which leaves 172.17.0.0 to 172.17.0.255 and 172.17.2.0 to 172.17.255.255. The API server checks all this and refuses an object that breaks the rules, with messages such as must specify a peer, may not specify both ipBlock and another peer, and must be a strict subset of `cidr`.

Chapter 4 of 11

The API server only stores the policy

The network plugin on each node does the enforcing

The API server has checked the object and stored it. It forwards no packets, so it can enforce nothing. Enforcement belongs to the cluster's network plugin, also called the CNI plugin, which runs an agent on every node. Each agent watches the policies, the Pods and the namespaces, and writes rules into its own node's kernel for the Pods that run there. node-2 gets the rules that guard web-2, and node-1 gets the rules that guard web-1. Each agent still reads every policy in the cluster, so it can also judge a packet bound for a Pod on another node. The chapter on a denied call shows when that happens. If the plugin does not implement NetworkPolicy, the object is stored all the same and nothing happens. kubectl shows the policy, and every Pod is as open as before. Flannel, which builds the tunnel on this scene, needs a policy controller beside it for this. This cluster runs one.

The NetworkPolicy type has no status at all. In the Go source of the API, the place where a status field would be holds only a comment saying that it is tombstoned, kept free so its protobuf number is never reused. No controller can write back that a policy was applied, and no condition can say it failed. kubectl get networkpolicy prints three columns, NAME, POD-SELECTOR and AGE, and none of them says whether anything enforces it.

The Kubernetes task page on declaring policies lists Antrea, Calico, Cilium and Kube-router as plugins that support NetworkPolicy. Flannel is not on that list. Its own documentation says that from version v0.25.5 it can be installed with the kube-network-policies controller, by setting the Helm value netpol.enabled=true. The Flannel Pod on each node then starts with an extra container, and that container is the agent this lesson calls the policy agent. The next chapter opens it up.

Chapter 5 of 11

Inside one policy agent

A kernel rule hands the packet up, and the agent gives the verdict

Plugins enforce policy in different ways, and kube-network-policies, the agent beside Flannel here, makes the mechanism easy to see. It writes an nftables table named kube-network-policies into the node's kernel. A rule in that table sends packets to NFQUEUE, a kernel facility that parks a packet and passes a copy to a program in user space. The agent reads the packet from queue number 100, checks it against the policies it has loaded, and returns a verdict: accept or drop. The kernel then carries out that verdict on the parked packet.

Sending every packet to user space would be slow, so the agent only captures packets for Pods that at least one policy selects. The agent keeps the addresses of its node's selected Pods in a set named podips-v4, and its rules queue a packet whose source or destination is in that set. Pod client is selected by no policy, so its own traffic never enters the queue on node-1. Packets towards web-2 enter it on node-2. web-1 carries the label app: web too, so on node-1 every packet that web-1 sends or receives enters the queue as well.

For each queued packet the agent runs two checks in a row. First it takes the policies that select the source Pod and asks whether they allow the packet out. Then it takes the policies that select the destination Pod and asks whether they let it in. The first deny ends the evaluation. The agent reads every policy in the cluster, so the second check works even when the destination Pod runs on another node. The queue holds at most 1024 packets. Once a connection has been accepted, its later packets are matched by connection tracking in the kernel and need no new verdict.

The agent can also stop. Its setting FailOpen decides what happens to traffic when the agent cannot give a verdict. With FailOpen true, a packet the agent cannot process is accepted, and while the agent is not running the queue rule lets packets bypass it. With FailOpen false, a packet the agent cannot process is dropped. On shutdown the agent logs which branch it took: FailOpen is true, skipping nftables cleanup on shutdown to avoid traffic disruption, or FailOpen is false, cleaning up nftables rules on shutdown.

kube-router shows a second design. It writes iptables chains and ipsets. Each Pod gets a chain with the prefix KUBE-POD-FW-, each policy a chain with the prefix KUBE-NWPLCY-, and the Pods that a rule allows become an ipset with the prefix KUBE-SRC-. Allowed traffic gets the mark 0x10000. Anything left unmarked is logged through NFLOG group 100, at most 10 a minute, and then rejected.

Chapter 6 of 11

A denied call ends in a timeout

The packet is dropped before it leaves node-1 and the caller is told nothing

web-1 repeats its call. Its first packet is a TCP SYN. The policy does not isolate web-1 for egress, yet the SYN never leaves node-1. web-1 carries the label app: web, so web-from-client selects it, and the agent on node-1 queues every packet that web-1 sends. The agent checks the egress side first and finds no Egress policy for web-1, so that check passes. It then looks up the policies that select the destination web-2, finds web-from-client, and sees that no rule allows web-1. It drops the SYN on node-1, before the packet is wrapped for the tunnel. node-2 never sees it. Nothing is sent back. The kernel under web-1 waits a second and sends the SYN again. On kernels with tcp_syn_linear_timeouts, which defaults to 4, the first retries come 1 second apart, and after that the gap doubles each time. Eventually curl gives up with a timeout.

Where the drop happens depends on the caller and on the plugin. A caller that no policy selects, such as a Pod in a namespace without policies, is not queued on its own node. Its SYN crosses the tunnel, and the agent on node-2 queues it there because web-2 is the destination and drops it just before the Pod. kube-network-policies judges a packet on the first node that queues it. Cilium, in a later lesson, checks ingress policy on the destination's node. The Kubernetes API records nothing about it: no event on either Pod, and no condition on the policy. A closed port would have answered at once with a reset, and curl would have said connection refused. The call from Pod client takes the same road, matches the rule and gets through.

The silence depends on the plugin. kube-network-policies and Cilium drop the packet by default, and the caller waits. kube-router ends its per-Pod chain with REJECT, so the kernel answers the caller at once and the call fails fast. Cilium has an option to answer an egress drop with an ICMP Destination Unreachable, and its documentation says that ingress drops like this one cannot be answered that way yet.

The test itself has to use a protocol the API covers. NetworkPolicy is defined for TCP, UDP and, where the plugin supports it, SCTP. For ICMP the documentation says the behaviour is undefined: some plugins let ping through and some do not. A ping that succeeds proves nothing about port 8080. curl with a time limit, or busybox wget with --timeout=1, tests the real port. The kubelet's health probes still reach web-2, because traffic from a Pod's own node is always allowed, and a Pod cannot block access to itself.

Chapter 7 of 11

Where a refused packet leaves a trace

Not in the API, but in the agent's log and its metrics

The Kubernetes API keeps no record of the drop. The documentation lists the ability to log network security events among the things NetworkPolicy cannot do. The agent that made the decision can, and kube-network-policies does so by default. Its flag --log-verdicts takes deny, all or none, and the default deny writes one line for every packet it drops. The verdict line is written at any verbosity. The shipped manifests run the agent at -v=2, and -v=4 adds a trace of how each packet was evaluated.

With JSON logging the line carries msg Packet verdict and verdict deny, the protocol TCP, the source and destination with their ports, the Pods by namespace and name, the direction ingress, the evaluator StandardNetworkPolicy and the TCP flags, here SYN. For web-1's call it names inference/web-1 and inference/web-2. Traffic from outside the cluster shows the Pod as external. The line sits in the log of the agent on node-1, the node that dropped the packet. Its direction says ingress, because web-2's ingress rules refused it, even though it was written on the caller's node. Looking on node-2, where the protected Pod runs, finds nothing. For a caller that no policy selects, the same line would be written on node-2 instead.

The agent also exports Prometheus metrics under the namespace kube_network_policies. packet_count counts packets, packet_process_duration_microseconds measures how long each verdict took. nfqueue_queue_total shows packets waiting right now. nfqueue_queue_dropped counts packets the kernel threw away because too many were already waiting for user space. A rising nfqueue_queue_dropped means packets are lost for lack of capacity, which looks like a policy drop to the caller and has nothing to do with any policy. verdict_log_dropped counts log lines lost when the log could not keep up.

kube-router leaves its trace in the kernel. Its NFLOG rule sends denied packets to log group 100, limited to 10 a minute with a burst of 10, before the REJECT.

Chapter 8 of 11

Policies add up and never take away

A second caller gets a second policy

A NetworkPolicy has no deny rule. A policy can only add to what is allowed. When several policies select the same Pod, the Pod accepts the union of what they allow, and the order in which they were created makes no difference. This matters the first time something else needs the web Pods. Prometheus collects their metrics from /metrics on the same port 8080, and with the first policy alone its requests are dropped like those of web-1. The fix is a second small policy for the same Pods that allows the namespace monitoring. Nobody has to edit the first one. Many teams start a namespace with a policy that has an empty podSelector and no rules. It isolates every Pod there, and each allowance is then added as its own policy.

The union also means that one broad policy overrides every narrow one. A policy that selects the web Pods and has the rule ingress: [{}] allows all incoming traffic. The documentation puts it plainly: with such a policy in place, no other policy can cause an incoming connection to those Pods to be denied. A single careless allow-all undoes the work of all the others.

The API also has no policy for the whole cluster. Every NetworkPolicy lives in one namespace, and a default deny has to be repeated in each. The successor developed in the Kubernetes network policy project is ClusterNetworkPolicy, in the group policy.networking.k8s.io. The project's release v0.3.0, of 6 November 2026, moved it to version v1beta1, which is now the version the API server stores. v1alpha2 is still served, with the same schema, and some plugins still name only v1alpha2 in their documentation. It is cluster-wide, has rule actions Accept, Deny and Pass, and sits in tiers. The Admin tier is evaluated first, then ordinary NetworkPolicies, then the Baseline tier. Within a tier a lower priority number wins, from 0 to 1000. A connection that the Admin tier passes on, or does not match, is decided by the v1 NetworkPolicies that select the Pod, and the Baseline tier is consulted only when none does. Unlike NetworkPolicy, ClusterNetworkPolicy has a status with conditions.

Chapter 9 of 11

When a change takes effect

New Pods start isolated, open connections are a matter of the plugin

Policies change while traffic flows, and the documentation is precise about what that means. A Pod created after the plugin has handled a policy is isolated before it starts. Its allow rules follow, and the documentation says they are applied eventually after the isolation rules. In the worst case a new Pod has no network at all for a moment after it starts. Different nodes can also be at different points: the documentation's own example is a new Pod that reaches Pod A at once and Pod B only a few seconds later. Its advice for an application that must talk to something at start-up is an init container that waits until the destination is reachable. Policies apply the same to init containers, sidecar containers and regular containers.

The other order is risky. If the Pod is created before the plugin has handled the policy that selects it, the Pod may start unprotected, and the isolation rules arrive later.

Connections that are already open are left to the implementation. When a policy or a label changes during a connection, it is implementation defined whether the change applies to that connection. The documentation recommends not changing policies, Pods or namespaces in ways that affect connections in use. For a model server this is concrete: a chat answer that streams for a minute may survive a new deny on one plugin and be cut on another.

kube-network-policies offers a clear line as an option. In its strict mode, which its code describes as enforcing network policies also on established connections, a background task reads the kernel's connection tracking table and judges each established connection again. When the agent accepts a connection it sets a connection tracking label on its entry, label 100 by default, and a rule lets packets of established connections that carry the label skip the queue. For a connection that the current policies no longer allow, the task clears that label. The entry itself stays in the table. The next packet of such a connection no longer matches the skip rule, goes back through the queue and gets a fresh verdict. The task runs no more often than every 30 seconds and at least once an hour, so an open connection can outlive the policy that allowed it for a while. Without strict mode, a connection already accepted by connection tracking keeps going.

Chapter 10 of 11

The egress policy that forgets DNS

Closing the way out also closes port 53

Egress works the same way from the other side, and a connection between two Pods needs both sides to agree: the source's egress policies and the destination's ingress policies. Suppose the namespace inference gets a default-deny egress policy, so that a web Pod can send nothing out, with one allowance for the object storage that holds its files. The next time web-2 restarts, it never gets them. Before it can open a connection to the storage it has to look up the name s3.northlight.internal. That question goes to the cluster's DNS Service on port 53, which no rule allows. It is dropped on node-2, the Pod's own node, and web-2 reports that it cannot resolve the host. The cure is one more egress rule.

The default deny has a second victim. Its empty podSelector selects every Pod in inference, and that includes Pod client. From now on client is isolated for egress, its packets enter the queue on node-1, and its own requests to web-2 on port 8080 are dropped there as egress. The ingress rule of web-from-client still allows them, but a connection needs both sides. One more policy, client-to-web, selects app: client and allows egress to the Pods with app: web on TCP 8080. The DNS policy below covers client's lookups as well.

One lookup is several questions. The kubelet writes the Pod's /etc/resolv.conf with the DNS Service as nameserver, a search list of inference.svc.cluster.local, svc.cluster.local and cluster.local, and the option ndots:5. A name with fewer than five dots, such as s3.northlight.internal with two, is first tried with each search suffix in turn before it is tried as written. Each of those questions goes to port 53, and each is dropped.

The wait adds up. The resolver's defaults, as the resolv.conf manual gives them, are a timeout of 5 seconds per try and 2 attempts. The application waits several seconds per name before it sees the error. The exact total depends on the C library in the image.

The rule should select the DNS Pods by label, as below, and not the Service address with an ipBlock. Whether a connection to a Service address is subject to ipBlock rules is undefined in the API. Cilium, for one, does not match Pod or node addresses with ipBlock rules unless its option policy-cidr-match-mode is set.

Chapter 11 of 11

What the API leaves open

Gateways on the host network, rewritten sources and everything above port numbers

The NetworkPolicy page ends with a list of what the API cannot do, and several items matter for a model server behind a gateway. It cannot force traffic through a common gateway. It knows nothing of TLS. It cannot target a Service by name. It has no node-specific policies, no default policies for all namespaces, no deny, no logging of security events and no way to block loopback or traffic from the node itself.

Gateways and load balancers often run with hostNetwork, sharing the node's own address. The documentation says policy behaviour for such Pods is undefined. The most common case is that the plugin cannot tell them apart and ignores them when it matches podSelector and namespaceSelector. Their traffic is treated as traffic from the node's address. A rule that allows the gateway by its Pod label may then match nothing. Such a Pod can be allowed with an ipBlock that covers the node addresses. Because traffic from a Pod's own node is always allowed, a gateway with hostNetwork on node-2 reaches web-2 whatever the policies say.

Traffic from outside the cluster brings the same question. A request from 198.51.100.7 that comes through the load balancer may reach node-2 with its source rewritten to the load balancer's or a node's address. The API leaves undefined whether ipBlock rules see the address before or after that rewrite.

The owner's BNK lab shows the pattern used for real. The endpoint picker on port 9002 speaks plaintext, so a NetworkPolicy in its namespace allowed port 9002 only from the namespace where BNK runs, f5-bnk. Requests still flowed through BNK, 20 of 20 in the test, and nothing else could reach the picker. For model servers the policy has the same shape: select app: qwen3, allow the gateway's namespace on port 8000, and check first whether the gateway uses the host network.

What to keep

An allow list in each node's kernel

A cluster starts with every Pod open to every other. A NetworkPolicy picks Pods by label and isolates them for the directions in its policyTypes. From then on they accept what the rules of all their policies allow, replies to connections that were allowed, and traffic from their own node. The API server keeps the object and has no status to report. The network plugin's agents enforce it in the nodes' kernels, and a plugin without policy support enforces nothing and says nothing. A refused caller gets silence and a timeout, or an immediate rejection with some plugins. The record of the drop, if there is one, is in the log of the agent that dropped it. With kube-network-policies that was node-1, because the caller web-1 is selected by the policy too. For the web Pods, two short policies mean that requests arrive only from Pod client and the metrics are read only by monitoring. Once the namespace also denies egress by default, client needs its own egress allowance to keep calling them. A model server's Pods, and the picker beside them, are closed to everything but their gateway in the same way.
