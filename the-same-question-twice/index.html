BNK and gateways

The same question twice

A semantic cache at the AI gateway, and the three ways it goes wrong

A support assistant gets the same question hundreds of times a day, each time in different words. Every one of those requests runs the full model on a GPU, although the answer was written an hour ago. A semantic cache at the AI gateway stops that. It compares the meaning of a new question with the questions it has seen, and when one is close enough it returns the stored answer in milliseconds, with no GPU involved.

This lesson follows one question through a hit and another through a miss at Northlight Compute, and works the similarity out by hand. It shows how BIG-IP Next for Kubernetes (BNK) switches the cache on with one annotation and hands each lookup to an external cache service called CodeFuse-ModelCache, what that service does inside, and how the connection to it is pooled and timed out. Then it spends most of its time on what can go wrong: a threshold set badly, an answer handed to the wrong user or the wrong conversation, an answer that is no longer true, a stream cut short, and a hit rate that was promised and never arrives.

Chapter 1 of 17

The same question, asked again

Different words, the same answer, the full price every time

Northlight's customers build assistants on Qwen3-32B. One of them, the tenant acme, runs a support assistant, and its users keep asking how to rotate an API key. One writes "How do I rotate my API key?" and the next writes "What is the way to rotate an API key?". An ordinary HTTP cache is no help. It builds its key from the method, the URL and sometimes a few headers, and it matches those byte for byte. Every chat request is a POST to the same URL, /v1/chat/completions, with the question inside the JSON body, and HTTP caches do not store POST responses by default. Even a cache that hashed the body would see two different strings here.

So each request travels to a GPU worker. The worker reads the prompt, which is the prefill step, and then writes about 160 tokens of answer over roughly two seconds, at about 12.4 ms a token, which is the decode step. Two seconds of a shared batch on a GPU that costs several dollars an hour is spent on text that already exists.

The AI gateway stage sits in front of the model and sees every prompt before a GPU does. In BNK that stage runs in TMM, the data plane, as the next chapter shows, and the board draws it as its own box. That makes it the place to notice that a question has been answered before. It asks the semantic cache first and sends on only what the cache cannot answer. F5's own deck draws the same order in five steps: the request arrives in the OpenAI format, the cache is queried, a hit returns the stored answer, a miss goes to the model, and the new answer is written back. A fifth arrow sends the counts to the operator's Prometheus and Grafana.

Chapter 2 of 17

How BNK switches the cache on

One annotation on the Gateway, and a cache that lives outside BNK

In BNK the semantic cache is a feature of the BNK data plane, the Traffic Management Microkernel (TMM), switched on per Gateway resource. The board draws the AI gateway stage as its own box. The cache is off by default. An operator turns it on with an annotation called k8s.f5.com/ai, placed under spec.infrastructure.annotations of the Gateway. Its value is a list of key=value pairs separated by commas.

Two keys are required. semantic_cache is enabled or disabled. semantic_cache_ip_port is the address and port of the cache service. BNK does not hold the cache itself. It sends each lookup to an external service called CodeFuse-ModelCache, an open source semantic cache, and F5's deck labels that box "F5 with partner solution". At Northlight the service listens on 10.96.40.30:5000, an illustrative cluster address, and 5000 is the port ModelCache's own service script uses.

Three keys are optional. semantic_cache_recv_timeout is how long, in milliseconds, BNK waits for the cache to answer, and it defaults to 500. semantic_cache_pool_max_size caps the pooled connections to the cache at 10000 by default. semantic_cache_pool_idle_timeout closes a pooled connection after 300 idle seconds by default. Both pool keys arrived in BNK 2.4.1.

The cache checks two endpoints, /v1/completions and /v1/chat/completions, both with or without streaming. F5 recommends turning on Server-Sent Events (SSE) as well, which is a separate annotation, k8s.f5.com/sse-enabled: "true", on the HTTPRoute that carries the traffic. The HTTPRoute also names the backend pool, which is where a miss goes.

Chapter 3 of 17

Every AI feature is an annotation on the Gateway

Three annotations, one format, and one feature that works another way

The cache annotation is one case of a general rule. BNK has no custom resource for its AI gateway features. Each one is switched on by an annotation under spec.infrastructure.annotations of the Gateway resource, and each takes the same kind of value: a string of key=value pairs separated by commas. BNK's controller reads the string and programs TMM. Three annotations cover the AI features. k8s.f5.com/ai switches on semantic caching, as the last chapter showed. k8s.f5.com/ai-token-counting counts the tokens each user spends and can enforce limits. k8s.f5.com/ai-llm-router hands requests to an external LLM router that picks a model. F5's token counting page says it in so many words: the feature is configured through infrastructure annotations on the Gateway, the same way as semantic caching. Because an annotation value is a plain string, the Kubernetes API server accepts any text in it and checks none of the keys. A misspelt key is applied without complaint, so read the Gateway back and test the feature after every change.

Token counting first has to know who the user is. user_id_source chooses how. api_key, the default, reads the header named in user_id_header, which defaults to Authorization. For Authorization it takes the bearer token out of "Authorization: Bearer <token>", and for any other header, such as x-api-key, it takes the raw value. ip uses the client address, and header uses the raw value of the named header. fallback_to_ip defaults to true, so a request with no key is counted against its source address. Set it to false and a request with no identity is rejected with a 401 and the error user_identity_missing. On the request path TMM asks a pod called the distributed Shared State Manager (dSSM) for the user's current count. dSSM holds the counters so that every TMM pod sees the same totals. If the user is over a limit and rate_limit_action is drop, the reply is 429 Too Many Requests. With log_only the violation is logged and the request goes on.

On the way back TMM reads usage.prompt_tokens, usage.completion_tokens and usage.total_tokens from the JSON answer, adds them to three counters in dSSM (the user's total, the user's count for that model, and the global count), and writes a High Speed Logging (HSL) record that a metering tool such as OpenMeter can bill from. For a stream it collects the SSE chunks, finds the last one by its finish_reason (stop, length, content_filter, tool_calls or function_call), and uses the usage numbers if the stream carried them. If not, it estimates. token_source defaults to auto, which uses the server's counts when they exist and the estimate when they do not. The estimate divides ASCII text by token_estimate_ratio, 4.0 characters per token by default, counts other scripts at about half as many characters per token, treats whitespace separately, and then takes 25% off. A 640 character English answer comes out at roughly 640 ÷ 4 = 160 tokens, then 160 × 0.75 = 120. vLLM puts a usage object on every non-streamed answer, so Northlight's non-streamed requests are counted from real numbers.

Northlight gives each API key 200,000 Qwen3 tokens an hour and 500,000 tokens a day on any other model, with five sessions at once. That is rate_limit_policy per_user_per_model and a rate_limits list in which "qwen3-*" is a wildcard on the model name and "*" catches the rest. The check happens before a request is forwarded and the count is updated after the answer, so a limit can be overshot by the request that crosses it. A key at 199,700 tokens is under the limit, its request is forwarded, and the answer reads 1,100 prompt tokens and writes 160. The count is now 199,700 + 1,260 = 200,960, and the next request from that key gets a 429. The other defaults are rate_limit_window 3600 seconds, and timeout and lifetime of 86400 seconds for the counters' idle time and total age.

The router annotation takes llm_router enabled, llm_router_type litellm, routellm or nvidia, a strategy of auto, cost, speed, quality or balanced (balanced by default), an optional max_tokens_cap per request, and peak_hours, off by default, with peak_hours_start 09:00 and peak_hours_end 17:00. BNK deploys one virtual address (VIP) in front of the router and a separate VIP for each model backend. A request goes from BNK to the router, the router picks a model, and the request goes to that model's VIP and on to its GPUs. With RouteLLM each strategy becomes a model name that carries a threshold: auto and balanced send router-mf-0.5, cost router-mf-0.9, speed router-mf-0.8 and quality router-mf-0.1. mf is RouteLLM's matrix factorization router, and RouteLLM's documentation says a higher threshold gives lower cost and possibly lower quality, because fewer requests go to the strong, expensive model. With peak hours on, BNK sends router-mf-0.4 inside the window and router-mf-0.8 outside it. F5 lists Dynamo deployments as not supported for this feature.

Intelligent load balancing is the exception, because it needs a process of its own. It is switched on in the CNEInstance resource with spec.intelligentLB.enabled: true. The controller then deploys an Analyzer pod. An F5BigAnalyzer resource tells the Analyzer which HTTPRoute to tune, which metrics to read (NIM by default, DCGM or vLLM, alone or as NIM with DCGM or vLLM with DCGM) and how often to run, with a schedule such as 1m and a minimum of 10s. The Analyzer writes its result as weights in an annotation on the HTTPRoute, k8s.f5.com/service-settings, and TMM sends traffic in those proportions. BNK 2.4.0 adds the F5 endpoint picker, which the F5 Analyzer hosts as an external processing server that TMM calls over gRPC. It is configured with an F5EPP resource and an InferencePool, and the release notes say the Gateway refers to it through an infrastructure annotation. So the switches are still annotations, while the work runs in a pod beside TMM.

Chapter 4 of 17

From a question to a vector to a score

An embedding, and the angle between two of them

An embedding is a list of numbers that a small model produces from a piece of text. Texts that mean similar things get lists that point in similar directions, even when they share few words. Such a list is called a vector. The model that makes it is far smaller than Qwen3-32B and runs in milliseconds, about 15 ms in this lesson. Two common sizes are 768 numbers, which all-mpnet-base-v2 produces and which ModelCache's service script loads, and 1,024 numbers, which BGE-M3 produces. Stored as 32-bit floats, that is 768 × 4 = 3,072 bytes or 1,024 × 4 = 4,096 bytes per question.

The cache compares two vectors by cosine similarity. Multiply them position by position and add the products up. Divide that sum by the lengths of the two vectors, where a length is the square root of the sum of the squares. The result is 1 when they point the same way, 0 when they are unrelated, and below 0 when they point apart. Dividing by the lengths means only the direction counts, so a long question and a short one can still score 1.

Real vectors have hundreds of positions. Three show the method. The stored question is (1, 2, 2), with length 3, because 1 + 4 + 4 = 9. The new one is (2, 10, 11), with length 15, because 4 + 100 + 121 = 225. The products add up to 2 + 20 + 22 = 44, and 44 divided by 3 × 15 = 45 is 0.978. A second stored question about invoices, (1, 2, -2), gives 2 + 20 - 22 = 0. It has nothing to do with keys, and the score says so.

A large store does not compare the new vector with every entry. A vector database such as Milvus keeps an index that finds the nearest few in a few milliseconds.

Chapter 5 of 17

The same vectors behind retrieval

384, 768, 1,024 or 1,536 numbers, for a cached question or a document chunk

The embedding and the nearest neighbour search in the cache are the same machinery that retrieval augmented generation (RAG) uses. RAG looks up passages in the operator's own documents and adds them to the prompt, so the model answers from them. F5's Distributed Inference deck draws it in seven steps. Clean the text, which removes noise and normalizes it. Chunk it into manageable pieces and add context and metadata. Embed each chunk into a vector. Store the vectors with their metadata in a vector database. Those four run ahead of time, as an indexing job. When a prompt arrives, embed it the same way and send it to the database over HTTP REST or gRPC, search for the closest vectors by cosine similarity, and retrieve the top K chunks. The deck's example indexes a list of hotels and asks "find the best hotels in Paris for next week". The slide adds that the method is not only used in RAG. The semantic cache runs the query half of it against stored questions.

The deck draws its vectors with three numbers, as this lesson does, and says that in real life a vector has 384, 768, 1,024 or 1,536. Each size comes from a family of embedding models. all-MiniLM-L6-v2 and bge-small-en-v1.5 make 384. all-mpnet-base-v2, ModelCache's default, makes 768. BGE-M3 makes 1,024. OpenAI's text-embedding-ada-002 makes 1,536, and so does text-embedding-3-small by default. text-embedding-3-large makes 3,072 and accepts a dimensions parameter that cuts the vector shorter, for a store that takes no more than 1,024. Stored as 32-bit floats at 4 bytes each, the four sizes take 1,536, 3,072, 4,096 and 6,144 bytes a vector. One number repeats: 384 numbers take 1,536 bytes, and 1,536 is also the largest of the deck's four counts of numbers. Say which one is meant.

Put sizes on Northlight's own case. It indexes its support documentation as 100,000 chunks (illustrative). The raw vectors take 100,000 × 1,536 B = 153.6 MB at 384 numbers, 307.2 MB at 768, 409.6 MB at 1,024 and 614.4 MB at 1,536. A corpus of 10 million chunks at 1,536 numbers takes 61.44 GB of vectors, close to the 65.5 GB of the BF16 Qwen3-32B build, and the search index adds memory on top. Comparing one question with every chunk at 1,536 numbers is 100,000 × 1,536 = 153.6 million multiplications, which is why the database keeps an index that visits only a small part of the store.

The two uses differ in what comes back. The cache returns one stored answer or nothing, and a hit skips the GPU. RAG returns the K closest chunks and adds them to the prompt, so the request still goes to a GPU and its prefill grows. Four chunks of 500 tokens add 2,000 tokens for the worker to read. A top K search always returns K results, the closest ones, even when none of them is close. The cache needs a threshold because it has to decide whether to answer at all.

One rule holds for both. A collection holds vectors of one size, made by one model. Questions must be embedded by the model that embedded the store, because the numbers in each position only mean something to the model that made them. Moving Northlight's documents from text-embedding-3-small at 1,536 numbers to text-embedding-3-large at 3,072 would mean embedding all 100,000 chunks again into a new collection. The cache and the document store choose their models separately, so the cache can use 768 numbers while RAG uses 1,536.

Chapter 6 of 17

Inside the cache service

ModelCache: four modules, two databases and one HTTP endpoint

CodeFuse-ModelCache is a Python service that grew out of the ideas of an earlier project, GPTCache. It is built from four modules. The adapter takes a request and runs the steps in order. The embedding module turns text into a vector. The similarity, or rank, module scores the vectors that come back from the search. The data manager talks to the databases. F5's slide draws the same parts: embedding, ranking, data manager, a vector database and a relational database.

In its standard setup the vectors go to Milvus, a vector database, and the questions and answers go to MySQL. A demo setup swaps those for FAISS and SQLite so it runs with no database at all. In front of the relational store sits a memory layer of 10,000 entries with an ARC eviction policy, which keeps the entries read most often in memory.

The service has one HTTP endpoint, POST /modelcache, on port 5000. The body carries a type, one of query, insert, remove or register, and a scope. The scope holds a model name, and ModelCache keeps a separate collection of vectors for each model name. That is its isolation: entries written under one model are never searched for another.

The default service script loads all-mpnet-base-v2, compares by cosine and sets the threshold at 0.9. Before it embeds, a function called query_with_role takes only the last message of the conversation and makes it "user: What is the way to rotate an API key?". The reply names whether it was a hit, how long the lookup took, which stored question matched and the answer.

Chapter 7 of 17

The threshold is the whole trade-off

Too low answers a different question, too high answers nothing

The cache returns a stored answer only when the best score reaches a threshold. Northlight has set it at 0.95. The rephrased rotate question scores 0.978 and is a hit.

Later a user asks how to revoke a key. That question sits at (2, 1, 2), length 3, and scores 2 + 2 + 4 = 8 divided by 3 × 3 = 9 against the stored rotate question, which is 0.889. It is a miss, and that is correct, because revoking a key is a different action with a different answer. Rotating issues a new key and retires the old one later. Revoking ends a key now.

Lower the threshold to 0.85 and this user gets the rotate instructions, stated with full confidence. Nothing in the reply shows that it answers a different question. Raise it to 0.99 and even the rephrased rotate question misses, so the cache costs a lookup on every request and saves nothing.

The defaults of two open source caches land close to each other. ModelCache uses a similarity of 0.9. RedisVL, Redis's library, states its threshold as a cosine distance, which is 1 minus the similarity and runs from 0 to 2, and defaults to 0.1, the same 0.9 in similarity. At 0.9 the revoke question misses by only 0.011. A slightly different wording could cross the line. No value suits every application. It has to be tuned on real pairs of questions from the application, counting the wrong answers as well as the hits.

Chapter 8 of 17

A miss goes to a GPU and is written back

Two caches meet on this path, and they save different things

The revoke question finds nothing close enough, so the gateway sends the request on as if there were no cache. ModelCache replies with cacheHit false and an empty answer. BNK asks the endpoint picker for a worker and gpu-1 gets it.

On that worker a second cache is at work. The KV cache keeps the result of reading a prompt, the keys and values each layer of the model computed for each token, and a request whose opening tokens match exactly can skip that reading. It lives in one GPU's memory. It needs an exact match of tokens from the first one on, and the model still writes every token of the answer. The semantic cache matches by meaning, lives outside the GPUs and skips the model entirely. The two stack. A miss here can still find its system prompt already read on the worker, so its prefill is shorter.

When the answer is complete the gateway writes the question and the answer to the store. In ModelCache that is a POST to /modelcache with type insert, the same scope, and a chat_info list that holds the query messages and the answer. The service embeds the question again on its side, stores the vector in the model's Milvus collection and the text in MySQL, and replies with writeStatus success. The next person who asks how to revoke a key gets a hit.

A miss is not free. It pays for the lookup, about 20 ms here, before generation starts, and it pays for the insert after. The insert happens after the user has the answer, so it adds load to the cache and no wait to the user.

Chapter 9 of 17

What belongs in the key

The question alone is never enough

A stored answer is valid only for the context it was written in. The model is part of that context, because two models answer differently. The system prompt is part of it, because the same question put to a legal assistant and to a support assistant has two answers. The tenant is part of it, because one customer's documents must never answer another customer's question. These values are stored beside each entry and applied as exact filters, so the similarity search looks only inside the matching scope.

Check what the cache in use actually separates. ModelCache's scope holds one value, model, and it keeps one collection per model name. Its default script embeds only the last message. So out of the box, two tenants on qwen3-32b share one collection, and two assistants with different system prompts share entries. The BNK page does not say what BNK puts in scope.model. F5 engineers have said that tenants' data is not shared for optimizations. Whether that covers the semantic cache has not been confirmed in writing, so test it with two tenants before promising it. RedisVL takes extra exact fields, declared as filterable_fields when the cache is created and passed with each store and check.

Personal questions need one more value: the user. Ana asks "What is my current balance?" and the answer is stored. Ben asks "What's my balance?". The two questions are almost the same sentence and score 0.97. Without the user in the key, Ben is shown Ana's balance.

A scope per user rarely hits, because one person seldom asks the same thing twice. The simpler rule for personal answers is to send them past the cache altogether.

Chapter 10 of 17

The connection to the cache

A pool of reused connections, a wait limit and a counter to read

Every request on a cached route makes at least one call to the cache, and a miss makes two. Opening a new TCP connection for each would add a handshake to every lookup and leave thousands of short connections behind. From BNK 2.4.1 the connections are pooled. For each Gateway, BNK builds a dedicated virtual server named after the Gateway with -sc-vs on the end, in front of the ModelCache address, and gives it a OneConnect profile. OneConnect is the BIG-IP feature that keeps server-side connections open and hands them to the next request. Earlier BNK versions opened a fresh connection every time.

The pool holds at most semantic_cache_pool_max_size connections, 10000 by default. A connection that sits idle for semantic_cache_pool_idle_timeout seconds, 300 by default, is closed. Two limits are fixed. A connection is retired after 86,400 seconds, which is 24 hours, or after 1,000 reuses, whichever comes first.

The operator checks the pool from the TMM pod with tmctl and the profile_connpool_stat table. In F5's sample output the cache virtual server shows cur_size 20 against max_size 35, 1,072 reuses and 78 connects. Of 1,150 requests, 1,072 went over an existing connection, which is 93.2%. In a healthy pool reuses climb faster than connects. If they do not, the documentation says to check the prerequisites and the annotation.

The wait limit matters as much. semantic_cache_recv_timeout defaults to 500 ms, 25 times the 20 ms lookup in this lesson. A slow cache can add up to that much to every request.

Chapter 11 of 17

The same pooling, pointed at storage

BNK AI Storage: OneConnect, TCP tuning, bandwidth control and a SNAT egress path

The -sc-vs pool is built from OneConnect, a BIG-IP feature much older than BNK, and F5 points the same feature at storage. Its "BNK and NVIDIA" deck has a slide called BNK AI Storage, under the line "Models need data, the GPUs most efficient path is through BNK". It lists four functions. Hardware acceleration runs the traffic at line speed off the DPU or network card. Bandwidth management distributes load by concurrent connections or by bandwidth needs, or applies a policy per request. Connection optimization uses OneConnect to cut the number of backend connections and raise what each storage node can carry. TCP optimization tunes the network for different kinds of connection. Under them the slide draws GPU nodes reaching storage and vector databases through BNK AI egress: an F5SPKEgress and a Gateway with its GatewayClass, storage specific optimized profiles, network isolation by SNAT at the egress point, and IPv4 or IPv6 to an external storage endpoint.

OneConnect keeps a server side TCP connection open in a reuse pool when a request on it finishes, and sends a later request over it. On BIG-IP the profile's defaults are max-size 10000 connections, max-age 86400 seconds and max-reuse 1000. Those are the numbers BNK gives the cache pool. The max-size counts idle connections per TMM. source-mask decides which clients may share a pooled connection. Its default, 0.0.0.0, lets any client use any connection. 255.255.255.255 shares only between requests from the same source address. When SNAT translates the source first, the mask applies to the translated address, so all GPU Pods behind one SNAT address share one pool.

Storage traffic is where this pays. S3 is HTTP, and each object read is a GET. Northlight's indexing job on gpu-1 fetches 100,000 document objects (illustrative). If every GET opened its own connection, the storage nodes would accept 100,000 TCP handshakes and, with TLS, 100,000 TLS handshakes. With each pooled connection carrying up to 1,000 requests, the same job needs at least 100,000 ÷ 1,000 = 100 server side connections, and at least as many as the job keeps in flight at once. That is the ratio the cache pool showed earlier, 1,072 reuses against 78 connects.

TCP tuning matters because a storage path is short and wide. The amount of data that must be in flight to fill a link is its bandwidth times its round trip time. At 100 Gb/s and a 100 µs round trip that is 100,000,000,000 × 0.0001 = 10,000,000 bits, which is 1.25 MB. A sender held to a 64 KB window can move only 65,536 bytes per round trip, 65,536 ÷ 0.0001 s = about 655 MB/s, which is about 5.2 Gb/s, a twentieth of the link. BIG-IP ships TCP profiles for different paths, such as f5-tcp-lan, f5-tcp-wan and f5-tcp-progressive. In BNK the TCP settings of a virtual server are an F5BigTcpSetting resource, which F5's deck shows on its own egress path to F5 AI Security. The "storage specific optimized profiles" on the slide are such settings tuned for storage.

The egress path is how Pods' outbound traffic enters TMM at all. In BNK 2.x that was an F5SPKEgress resource, one per namespace. The owner's lab notes carry a hard rule for it: never delete and recreate an F5SPKEgress on a running cluster. The new one counts Pods from zero, and in the lab its cleanup removed another tenant's VXLAN device. BNK 2.4.0 adds EgressGateway, a Gateway API style resource that F5 says is designed to replace F5SPKEgress. Each EgressGateway creates a wildcard virtual server on TMM, 0.0.0.0:0 for IPv4 and [::]:0 for IPv6, and takes its SNAT, network and VRF from an entry in a GatewaySettings resource, for example sourceNATConfig type Automap. sourceSelector picks the Pods by NamespaceSelector, PodSelector or Combined. A separate EgressGateway per tenant gives each tenant its own SNAT address and VRF, so a storage system can tell tenants apart by source address, and a SecPolicy can attach firewall rules to the egress virtual servers.

Chapter 12 of 17

Answers go stale

A time to live, and deleting on purpose

A cached answer was true when it was written. Northlight changes how key rotation works, and the cache keeps handing out the old steps. A semantic cache makes this worse than an ordinary cache, because one stale entry answers every rewording of the question.

The first defence is a time to live, a number of seconds after which an entry is removed. Short lives suit prices and status. Long lives suit definitions. Check whether a hit renews the life of an entry. In RedisVL, ttl has no default, so entries stay until deleted, and refresh_ttl_on_hit defaults to true, so every hit restarts the clock. A popular wrong answer then never expires. ModelCache's source has no time to live at all.

The second defence is invalidation, which means deleting entries on purpose when their source changes. That needs a handle. RedisVL deletes chosen entries with drop and everything with clear. ModelCache takes a request of type remove, with remove_type delete_by_id and a list of ids, or truncate_by_model, which empties the whole collection for one model. To delete only the entries about API keys, the ids have to be found first. The insert reply carries no id. Each entry is a row in ModelCache's MySQL table modelcache_llm_answer, with an id, the question, the answer, the model, a hit_count and gmt_create, the time it was written. Northlight's operators select the rows whose question mentions an API key and keep that list under the label docs/api-keys.

A change of model or system prompt needs no deletion when both are in the key, because the old entries stop matching and age out. ModelCache's README offers its one-step clearing for use after a model upgrade.

Chapter 13 of 17

Streams

Forward each event, keep a copy, store only a finished answer

Most chat clients ask for a stream. With stream set to true, the model server sends the answer as Server-Sent Events while it writes. Each event is a line that starts with data: and holds a chat.completion.chunk object. Its choices[0].delta.content carries the next few characters. The last chunk carries a finish_reason, and the stream ends with the line data: [DONE].

On a miss, BNK passes each chunk to the client as it arrives, so the user sees the first words after the prefill and not after the whole answer. At the same time it puts the pieces together into one complete response and stores that in ModelCache. The finish_reason tells the gateway whether the answer is whole. stop means the model ended on its own. length means it hit the max_tokens limit and the text is cut off. A client that disconnects halfway leaves a copy that is half an answer. Storing either of the last two would serve a broken answer to everyone who asks next, so only stop should be stored.

On a hit, the client still expects events. BNK fetches the complete stored answer and, when SSE is on for the route, sends it to the client in chunks. The user sees the same kind of stream as from a GPU, only much sooner. This is why F5 recommends turning on SSE with the cache: without it, a client that asked for a stream would get the two kinds of answer in two different shapes.

Chapter 14 of 17

Tool calls and conversations

When the last message is not the whole question

Two kinds of request make a stored answer unsafe even when the words match. The first is a tool call. A request can list tools, functions the model may ask the application to run. The model's reply is then a request to run one, with finish_reason tool_calls and a tool_calls list holding the function name and its arguments. The next prompt carries what the function returned in a message with role tool, such as a live order status. Replaying a stored reply would repeat an old decision or an old result. Requests that carry tools are usually sent past the cache.

The second is a conversation. In a chat, the meaning of the newest message depends on the ones before it. ModelCache's default embeds only the last message, as "user: " followed by its text. Two users in two conversations about different things both end with "Yes, please do that.". The text is identical, so the vectors are identical and the score is exactly 1.0, above any threshold. The second user gets the answer written for the first conversation.

There are three ways out. Cache only the first turn of a conversation, where the last message is the whole question. Embed the whole conversation, which is what ModelCache's other configuration does by joining every message with its role. Or send any request with more than one user message past the cache. Agents are the extreme case. They send long, changing histories and lists of tools, and almost none of their calls should be answered from a cache.

Chapter 15 of 17

What the cache saves

One hour of traffic, counted both ways

Put numbers on it, all of them illustrative. The assistant sends 10,000 requests in an hour. Each one that reaches a GPU takes 2 seconds of generation. The cache lookup takes 20 ms, and 30% of requests are hits.

Without the cache the workers spend 10,000 × 2 = 20,000 seconds generating. With it, 7,000 requests reach them and they spend 14,000 seconds, so 6,000 seconds of GPU time, 100 minutes, are free for other work. The average wait falls from 2,000 ms to 1,420 ms. 3,000 answers take 20 ms, which is 60,000 ms in all. 7,000 take 2,020 ms, the lookup plus generation, which is 14,140,000 ms. Together that is 14,200,000 ms over 10,000 requests.

Every request pays for the lookup and only the hits get it back. The average with the cache is 20 ms plus the miss share times 2,000 ms. That is below 2,000 ms once the hit share times 2,000 ms is more than 20 ms, which is a hit rate above 1%. The break-even is low. The risk sits elsewhere.

The number that a hit rate hides is wrong answers. If 1 hit in 100 is a false match, 1% of 3,000 hits is 30 confident wrong answers an hour. Nothing in a status code or a latency graph shows them. They have to be found by sampling hits and reading them: the stored question beside the new one, which ModelCache returns as hit_query and also writes to its query log, modelcache_query_log, with the new question and cache_hit for every lookup. The hit rate itself comes from the same log: rows with a hit divided by all rows.

Chapter 16 of 17

How many hits to expect

The workload sets the hit rate, and the claims vary widely

The saving depends on one number the operator does not choose: how often users really ask the same thing. F5's workflow deck says a semantic cache eliminates up to 60 to 80% of redundant token generation for common corporate prompts. The word redundant matters. It is a share of the repeated requests, and it says nothing about how many requests are repeated. One research paper on a semantic cache for GPT models, cited in Northlight's own research notes, measured hits of 61.6 to 68.8% on repetitive workloads. Write-ups of production systems describe much lower rates for general chat. Those are blog posts, so treat them as a rough direction only.

Run the same hour at three hit rates, keeping 10,000 requests, 2 s per generation and a 20 ms lookup. At 20% hits, 8,000 requests reach a GPU for 16,000 s, and the average wait is 2,000 × 20 ms plus 8,000 × 2,020 ms, which is 16,200,000 ms, or 1,620 ms each. At 30%, as before, 14,000 s and 1,420 ms. At 60%, 4,000 requests reach a GPU for 8,000 s, and the average is 6,000 × 20 ms plus 4,000 × 2,020 ms, which is 8,200,000 ms, or 820 ms.

The pattern is simple. A support desk or an FAQ bot answers a small set of questions many times, and hits often. A creative writing tool, an agent with tools and a long chat almost never repeat, and hit close to zero. Measure before promising. Run the cache for a week on real traffic, count hits, read a sample of them, and only then quote a saving.

Where the cache sits among F5's three roles

GSLB picks the site, BNK picks the GPU, BNK with AI Security guards, caches and routes

F5's "BNK and NVIDIA" deck maps its products onto what it calls the AI Grid control plane, and on its full service plane slide the GSLB box carries the AI Grid label. It splits the control plane into two tiers. Tier 1 is global site selection, done by F5's CNF DNS or GSLB. It answers which region, cluster or cloud serves a request, and it weighs policy (sovereignty, cost and tenancy), AI telemetry (GPU load, queue depth and time to first token) and the round trip time and health of each site. Tier 2 is local inference routing, done by BNK. It answers which GPU, model and Pod handles the request, and it weighs each Pod's GPU use, queue depth, KV cache locality, model affinity and priority class. Telemetry flows up from the GPUs and ratios and weights flow down. On top of the two tiers the deck names F5's three core roles.

Role 1 is the GSLB layer, global server load balancing, with BIG-IP DNS or the Next DNS CNF. Clients use a single name, api.northlight.example, and the DNS answer carries the address of the site that should serve them, chosen by topology (where the client is), latency and health. Today Northlight runs one site, northlight-eu, and the answer is always 203.0.113.80. If it added a second site (illustrative), a client nearer that site would be given its address, and a site that fails its health check would stop being handed out. Steering happens when the name is resolved, so a change reaches a client only after its cached DNS answer expires.

Role 2 is BNK itself: routing at layer 7 that knows the model and the tokens, run on the host or on a BlueField-3 or BlueField-4 DPU. The roles slide names its parts as iRules plus a NIM or Dynamo classifier, and does not say how the classifier decides. iRules read the request. A separate slide on KV cache and telemetry shows the serving stack's own numbers feeding the routing decision, under the heading NVIDIA NIM stats and Dynamo integration: pending requests, KV cache, GPU metrics and VRAM utilization. A third slide shows what it buys to classify requests by intent and cost. With every request in one queue, heavy reasoning jobs block urgent chat, and the deck shows an average wait of 250 ms. With chat sent to a low latency pool and reasoning to a high throughput pool, it shows 12 ms. Those are F5's figures. On this board, role 2 is the endpoint picker choosing gpu-1, gpu-2 or gpu-3.

Role 3 is BNK together with F5 AI Security. It covers the OWASP Top 10 risks for LLM applications, personal data (PII) and compliance, semantic caching, and routing between local and external models. The cache in this lesson lives in role 3. Local and external routing is the k8s.f5.com/ai-llm-router annotation from earlier: a router chooses between the qwen3-32b workers in the cluster and a hosted model outside it, and BNK gives the router and each model its own VIP.

Follow one request through all three. The user's resolver asks for api.northlight.example and gets 203.0.113.80 (role 1). TMM checks the API key, F5 AI Guardrails scans the prompt, and the cache is asked (role 3). Scanning before the cache is this lesson's assumption, so that a prompt is checked before any stored answer is served. The deck draws the cache first. On a hit the answer goes back and nothing below it runs. On a miss the router, with strategy cost, keeps the request on the local model (role 3), and the endpoint picker sends it to gpu-1 (role 2). The deck's full service plane slide draws the same parts on one plane: GSLB, the semantic cache for similar requests, AI Guardrails, the BNK inference traffic scheduler with its Gateway, HTTPRoute, decision engine and endpoint picker, and the prefill and decode workers. Its numbered markers label the parts and do not trace this request step by step.

What to keep

Fast, cheap, and only as right as its key

A semantic cache at the AI gateway turns a question into a vector, looks for a stored question that points the same way, and returns the stored answer when the score clears a threshold. In BNK it is switched on with the k8s.f5.com/ai annotation on a Gateway and served by an external CodeFuse-ModelCache over a pool of reused connections, with 500 ms as the default wait. A hit skips the model and every GPU. A miss costs about 20 ms more and ends with a new entry. That differs from the KV cache on a worker, which saves the reading of a prompt and still writes the answer. Everything hard about it is in the decisions around the lookup: a threshold that separates rotate from revoke, a key that holds the model, the system prompt, the tenant and for personal questions the user, an embedding that sees the whole conversation, a time to live and a way to delete, a rule that stores only finished streams, and a rule that keeps tool calls out. With those in place, three requests in ten here never touched a GPU.
