GPU and hardware

The far side of the motherboard

NUMA: why the same server is fast or slow depending on where a process lands

A big GPU server has two processors, and it is less one computer than two that share a case. Each processor has its own memory sticks and its own card slots. A single link joins the two halves. Each half is called a NUMA node, short for non-uniform memory access: how long a read takes depends on which half the bytes live in. Everything in the server can still reach everything else, so nothing ever fails because of this. It just gets slower, by a factor of two or three, when a byte has to come from the other half. A GPU sits in a slot of one half. This lesson follows a vLLM server feeding that GPU. It shows how Linux decides where memory goes, what happens when the process lands on the wrong half, why no gauge tells you, how to see it, and how the kubelet is told to keep a Pod's cores, memory and GPU together. It ends with the one thing no setting fixes: which slot each card was pushed into.

Chapter 1 of 14

Two halves in one case

Each processor owns the memory next to it

Look at the board. On the left is CPU 0 with its bank of memory. On the right is CPU 1 with its own. The memory sticks are wired to the processor beside them and to nothing else, because the memory controllers are inside the processor. When a program on CPU 0 reads memory from the left bank, the bytes come straight in.

The width of that road is simple arithmetic. Take a processor with eight memory channels of DDR5-4800 as an example. Each channel moves 4,800 million transfers a second, 8 bytes each, which is 38.4 GB a second. Eight channels make 307.2 GB a second, and that is the 307 on the board. The right bank has the same road to CPU 1.

When a program on CPU 0 reads from the right bank, CPU 0 has to ask CPU 1. CPU 1 reads its own memory and sends the bytes back across the link between the two processors. That link is much narrower than either memory road, and every request pays for two extra hops. The owner's notes on the talk this lesson follows put the cost at two to three times slower for cross-socket access.

Linux knows this layout and will tell you. It numbers the halves node 0 and node 1, lists the cores and memory of each, and prints a table of how far each node is from the other. The numbers come from the firmware and are relative: 10 means local by convention, and 21 means a little over twice as far.

Chapter 2 of 14

Linux puts memory where the thread is

Pages land on the node of the core that touches them first

A program never says which node it wants memory from. It asks for memory, and Linux decides. Once the system has booted, the default policy is local allocation: a page comes from the node of the core the thread is running on. The decision is made late. Asking for 64 GB only reserves addresses. A real page is found the first time the thread touches each 4 KiB piece, in the page fault that follows, and that is when the node is chosen. So whoever touches a buffer first decides where it lives.

If the local node has no free memory left, the kernel does not fail the allocation. It takes a page from the next node in order of distance. The program gets its memory and never learns that some of it is far.

Threads also move. The scheduler may run a thread on a core of the other processor when that is where there is room. The pages it already touched stay where they were. A kernel feature called automatic NUMA balancing watches which node's cores use a page and moves pages towards them over time. It is controlled by the sysctl kernel.numa_balancing and helps slowly. It cannot move pinned buffers, and it only sees reads made by the processor's cores, so it never learns about a copy engine's reads.

A program can override all of this. A memory policy can bind it to a set of nodes, prefer one node, or spread pages evenly across several, which is called interleave. The numactl command sets such a policy for a whole process before it starts.

Chapter 3 of 14

The GPU lives on one side

A card belongs to the processor its slot is wired to

Card slots are wired the same way as memory. The PCI Express lanes of each slot end at a root port inside one processor. So a card is local to one node and far from the other, and that includes the GPU. In this server the GPU's slot belongs to CPU 0. A slot here is PCIe Gen5 with 16 lanes: 32 gigatransfers a second on each lane, 16 lanes, which is about 64 GB a second in each direction before encoding overhead. That is the 64 on the road from the slots to the GPU.

Linux records which node every PCI device belongs to, and you can read it from one file in sysfs. The file numa_node under the device's directory holds the answer. For this GPU it is 0. Next to it, local_cpulist lists the cores of that node, here 0 to 31. That single digit decides which half of the server is the fast place to run anything that feeds this GPU.

The value -1 means the firmware did not say. It happens in some virtual machines and on some single-socket boards, and then nothing above it, neither the kubelet nor a scheduler, can make a good choice.

On a server with eight GPUs it is normal for four to hang off each processor, often behind PCIe switches. So the right half differs from one GPU to the next, and a process that serves GPU 5 should not sit on the same cores as one that serves GPU 1.

Chapter 4 of 14

Reading the topology matrix

One command shows every GPU, every network card and the path between them

Reading sysfs one device at a time gets tiring on a server with eight GPUs and eight network ports. NVIDIA's tool prints the whole picture at once. The command nvidia-smi topo -m draws a matrix with a row and a column for every GPU and every network card, and adds the CPU cores and the NUMA node each GPU is close to.

Each cell names the kind of path between two devices. The legend is short. X is the device itself. PIX means the path crosses a single PCIe switch, the best case for two cards. PXB means several PCIe switches, still without going through the processor. PHB means the path goes through a PCIe host bridge, which is usually the processor. NODE means it crosses between host bridges inside one NUMA node. SYS means it crosses the link between the two processors. NV followed by a number means a set of that many NVLink connections.

For this server the row for GPU 0 reads CPU affinity 0 to 31 and NUMA affinity 0, which agrees with sysfs. The cell between GPU 0 and the network card says SYS. That one word is the whole story of the chapter It is not only the GPU, later in this lesson: data from the network has to cross the link to reach this GPU.

The owner's post on networking for AI makes the point that this matrix shows what should be possible, and only a measurement shows what the system really does. Read the matrix when the server arrives, and measure a copy in each direction before trusting it.

Chapter 5 of 14

On the near side

Buffer, processor and GPU in one half

Start with the case that goes well. The model server's threads run on cores of CPU 0, so by local allocation the memory they touch comes from the bank of node 0. Now a conversation that was parked in host memory comes back, and its KV cache has to be copied into the GPU. The KV cache is the set of keys and values the model saved for every earlier token of the conversation.

The size follows from the model. Qwen3-32B has 64 layers, and each layer keeps 8 key heads and 8 value heads of 128 numbers, 2 bytes each. That is 64 × 8 × 128 × 2 × 2 = 262,144 bytes for every token. This conversation is 24,000 tokens long, so the cache is 24,000 × 262,144 = 6,291,456,000 bytes, about 6.3 GB.

The buffer is pinned, which means the kernel promised not to move its pages, so a device may read them directly. The GPU's copy engine, hardware on the GPU whose only job is moving data, pulls the bytes from the left bank, through CPU 0's root port and slot, into GPU memory. Nothing crosses the link. The copy runs at 55 GB a second, a little under the slot's 64 GB a second. That is the plateau measured on an H100 PCIe card for large copies from the card to the host, the figure used in the lesson Behind the Pod IP. This lesson assumes the copy into the card runs at about the same speed. It is done in 6.29 GB ÷ 55 GB/s = 114 milliseconds.

Then the GPU goes back to work from its own memory. The H100 PCIe card reads it at about 2,000 GB a second, about 31 times the slot's 64.

Chapter 6 of 14

On the far side

The same copy, with the link in the middle

Now the same server on a different day. The model server was restarted and the kernel happened to start its threads on cores of CPU 1. Nothing is wrong with that as far as Linux is concerned. All 64 cores are free to use, and the kernel picks the least busy ones. By local allocation, the memory those threads touch now comes from the right bank, and that includes the pinned buffers that hold parked KV cache.

The same 6.3 GB of KV cache now travels from the memory of node 1, through CPU 1, across the link, through CPU 0, and only then down the slot to the GPU. The copy engine does not know or care. It asks for addresses and the bytes arrive. The copy still works. It runs at well under half the speed, about 24 GB a second in this example, and takes 6.29 GB ÷ 24 GB/s = 262 milliseconds.

That is 148 milliseconds more for every conversation that is brought back, and the user sees it as a slower first word. Nothing else about the request changed. The same model, the same GPU, the same prompt.

The link is shared, too. Everything else that crosses it competes for the same lanes: other processes on the wrong side, the network card on node 1, the operating system. So the far-side speed is not even steady. It moves with whatever else the server is doing.

Chapter 7 of 14

No gauge moves

Why this goes unnoticed for months

The hard part is that nothing reports it. The copy succeeded, so there is no error and no line in the kernel log. GPU utilization looks the same, because that gauge counts the share of time a kernel was running on the GPU, not how fast its data arrived. Memory use is the same. No Xid error appears, because the GPU did nothing wrong.

The only thing that changes is latency, and only for the work that touches host memory: loading a model, bringing a parked conversation back, turning text into tokens on the CPU, copying sampled tokens back. On a dashboard it shows up as a slow tail on one server out of forty, the kind of thing that gets blamed on a noisy neighbour. The owner's notes on the talk put NUMA allocation and the mapping of Pods to GPUs on the list of things GPU observability should add, for this reason.

To see it you have to ask where a process's memory lives. The command numastat -p with the process id prints the memory of one process per node. Without arguments, numastat prints counters for the whole machine. numa_hit counts pages that came from the node they were meant to. numa_miss counts pages placed on a node because the intended one was full. local_node counts pages placed on a node for a process running on that node, and other_node counts pages placed on a node for a process running on another one. None of them knows where the GPU is. In this failure the process runs on node 1 and its pages come from node 1, so they count as numa_hit and local_node on node 1, exactly as on a healthy server. The machine-wide counters cannot show this mismatch. Only the per-process view can: numastat -p, or the file numa_maps under /proc for the process, which shows the split for every region of its memory, compared with the numa_node of the GPU it feeds.

Chapter 8 of 14

Pinning by hand

numactl binds a process to one half before it starts

Outside Kubernetes, the fix is one command in front of the program. numactl with --cpunodebind=0 runs the program only on cores of node 0. Adding --membind=0 sets a bind policy, so every page it touches comes from node 0. If node 0 runs out, an allocation under bind does not quietly go to node 1. That is the point: the program stays on the fast side, or it fails where you can see it. A softer choice is --preferred=0, which tries node 0 first and falls back by distance.

For a vLLM server feeding GPU 0 the line is numactl --cpunodebind=0 --membind=0 vllm serve Qwen/Qwen3-32B. The command taskset does only the first half: it limits the cores and leaves memory to the default policy, which works as long as the threads touch their buffers first on those cores.

The owner's notes on the LMCache adapter that spills KV cache to NVMe through SPDK make the same point for helper threads. The adapter lets you place its worker threads and SPDK's polling threads on chosen cores. Those must not overlap, and on a server with two NUMA nodes they belong on the side of the drive they serve.

Pinning by hand has a cost. It is a promise about one server's wiring, written in a start script. Move the script to a server where the GPU sits on node 1 and it pins the program to the wrong side on purpose. Kubernetes needs a way to do this from the facts the node reports, Pod by Pod.

Chapter 9 of 14

The CPU Manager gives a Pod its own cores

The static policy, and the Pods it applies to

Left alone, the kubelet does not care about any of this. Its CPU Manager starts with the policy none. A Pod gets a share of CPU time, enforced by the kernel's scheduler, and its threads run on any core the kernel likes, on either half.

The policy static changes that for some Pods. The kubelet keeps a shared pool of cores, which at first holds every core on the node. A container gets cores of its own only when two things are true: its Pod is in the Guaranteed class, meaning every container's requests equal its limits for both CPU and memory, and its CPU request is a whole number. Such a container is given that many cores, they leave the shared pool, and nothing else runs on them. Containers with half a CPU, or in Burstable and BestEffort Pods, stay in the shared pool and can drift to either side.

The static policy needs some cores held back, or the shared pool could be emptied. The kubelet refuses to start without a reservation, made through kubeReserved and systemReserved, or with an explicit list in reservedSystemCPUs. On this node the list is cores 0 to 3. Those cores stay in the shared pool for system work and other containers, but they are never handed to a container as its own, so exclusive cores start at core 4.

The kubelet writes its assignments to the file /var/lib/kubelet/cpu_manager_state. The policy only applies to new Pods, so changing it on a running node means draining the node, stopping the kubelet, deleting that file and starting again. If the file is left behind, the kubelet stops with an error that says the configured policy differs from the one in the checkpoint.

Chapter 10 of 14

The Topology Manager puts it together

Hints from cores, memory and GPU, and one policy that decides

Exclusive cores are not yet near cores. The CPU Manager could hand out cores 32 to 39 for a Pod whose GPU is on node 0. Lining things up is the job of the Topology Manager, another part of the kubelet.

It works with hints. Before a container starts, the kubelet asks each hint provider which NUMA nodes could satisfy the request. The CPU Manager answers for cores. The Memory Manager answers for memory and huge pages. The device manager answers for devices, using what each device plugin reported. A device plugin sends, with every device, a TopologyInfo that lists NUMA node IDs. For GPU 0 it lists node 0. A hint is a set of nodes and a flag that says whether the set is preferred. The narrowest preferred set wins.

The policy says what to do with the result. none does nothing. best-effort prefers aligned resources and admits the Pod anyway. restricted admits only if a preferred set was found. single-numa-node admits only if everything fits on one node. The scope says what is aligned together: container, the default, aligns each container on its own, and pod treats the whole Pod as one.

Memory needs its own manager. With memoryManagerPolicy set to Static, a Guaranteed Pod's memory is reserved on the chosen node and the kubelet writes the node into the cgroup setting cpuset.mems, so the kernel can only take pages from there. Static requires reservedMemory per node, and its total must equal kubeReserved plus systemReserved plus the hard eviction threshold, which is 100Mi by default.

Chapter 11 of 14

When the node cannot line it up

The kubelet refuses the Pod, and the scheduler never knew

Alignment can fail. Say gpu-node-2 has one free GPU, on node 0, but node 0 has only five free cores left because other Pods hold the rest, while node 1 has twenty. The Pod asks for eight cores and one GPU. Under single-numa-node there is no single node that can give both, so the Topology Manager rejects the Pod at admission.

The Pod never starts. The kubelet marks it failed with the reason TopologyAffinityError, which you see in kubectl get pods as the status and in kubectl describe as the reason. The Kubernetes documentation describes it as the Pod being terminated with an admission failure. The scheduler does not try that Pod again. A Deployment notices a missing replica and creates a new Pod, and that is how it is meant to recover.

The catch is in the documentation's list of limitations: the scheduler is not topology-aware. It saw a node with a free GPU and 25 free cores in total and picked it. It can pick the same node for the replacement, which fails the same way. Schedulers that know about NUMA close that gap. The owner's notes on the KAI scheduler list NUMA-aware GPU and CPU placement as one of its features, while Kueue, which only admits jobs, has to rely on another scheduler for it.

There is also a ceiling. By default the Topology Manager does not run on a node with more than 8 NUMA nodes, because the number of combinations explodes. The policy option max-allowable-numa-nodes raises it. The option prefer-closest-numa-nodes makes best-effort and restricted favour nodes that are close by distance.

Chapter 12 of 14

It is not only the GPU

The network card has a side too

Look at the other card. The network card sits in a slot of node 1. Data that arrives from the network and is headed for the GPU has to cross the link whatever you do, because its two ends are in different halves. The kubelet cannot fix it, numactl cannot fix it. It was decided by which slot each card was pushed into when the server was built.

It matters for the things that move real volume over the network. Loading the 34.3 GB of weights of the official FP8 build, Qwen3-32B-FP8, from storage: the port runs at 400 Gb/s, which is 50 GB a second, so on a good path the load takes 34.3 ÷ 50 = 0.69 seconds of network time. That is only the wire's share of a load, which takes about three minutes in all in this site's examples, and here the link sits in the middle of that path. A KV cache tier kept on another machine. And the traffic between GPUs on different servers, where NCCL, NVIDIA's library for collective operations, moves data straight between GPU memory and the network card with GPUDirect RDMA.

NVIDIA's documentation for GPUDirect RDMA is blunt about this. The two devices must share the same upstream PCIe root complex. A path through a single processor works with worse performance. A path that crosses the link between processors may be extremely performance-limited or not work reliably. The owner's post on networking for AI draws the same three cases: one PCIe switch with full peer bandwidth, through the root complex, and across sockets with reduced bandwidth. It adds that a poor match does not show as an error. NCCL quietly falls back to a slower path, and the GPUs wait at every synchronisation point.

So NUMA is a question to ask before the hardware is ordered. For each GPU, is there a network port on the same side, ideally under the same PCIe switch, so that nvidia-smi topo -m says PIX?

Chapter 13 of 14

Who gets to set all this

How a GPU is delivered decides how much of this lesson you can use

Look back at what this lesson changed. numactl bound a process to one half. The kernel.numa_balancing sysctl was turned on or off. The kubelet ran the static CPU Manager, the Static Memory Manager and the single-numa-node Topology Manager, with CPUs and memory reserved for the system. A NUMA-aware scheduler placed GPU and CPU together. Before all of them, someone chose which slot each card went into, and nvidia-smi topo -m reads the result. Every one of these is set by whoever runs the host. So the way a GPU reaches you, as a whole server, as a virtual machine or as a share of a card, decides which of these levers you hold. That is where topology meets the choice of delivery.

Bare metal means a dedicated physical server, used directly, with no hypervisor from the provider between the workload and the hardware. The tenant gets the GPUs, the processors, both memory banks, the local disks, the network cards and the device topology exactly as they are wired. The numa_node file in sysfs says 0 for the GPU because the firmware said so. topo -m shows the real PIX, PXB, NODE and SYS paths. The tenant chooses the operating system, the kernel and its settings, the NVIDIA driver and CUDA version, the container runtime, the kubelet configuration and the scheduler. Thaki Cloud's insights series (thakicloud.com/en/insights) names the two things this buys: a hardware topology that is easier to see and reason about, meaning PCIe and NVLink inside the server and the network fabric between servers, and control of the stack, meaning drivers, kernels, runtimes and schedulers.

A virtual machine with GPU passthrough sits in the middle. A hypervisor is present, and one whole physical GPU is assigned to one VM, so the GPU itself is not shared. The guest sees only the NUMA layout the hypervisor describes to it. QEMU's documentation of the PCI expander bridge, pxb, gives the reason that bridge exists: its bus can be associated with a NUMA node, "allowing the guest OS to recognize the proximity of a pass-through device to other resources as RAM and CPUs". Without such a description the guest can read -1 in numa_node, the case from the chapter The GPU lives on one side, and a kubelet inside the guest has nothing to line up. The host must also place the VM well. In OpenStack Nova the libvirt driver by default enforces strict NUMA affinity for PCI devices: a device must come from the same host NUMA node as at least one of the instance's CPUs. That default has a name, legacy, and it also accepts a device that reports no NUMA information at all. The flavor extra spec hw:pci_numa_affinity_policy changes it to required, socket or preferred, or sets legacy explicitly.

vGPU is the third form. Software exposes GPU resources to several VMs through a virtualization layer, and depending on the implementation they are shared or partitioned. Allocation units are smaller and utilization is higher. The tenant has the least view of the hardware: someone else owns the card, its slot and its path to the network. A Pod on a cluster run by someone else sits at the same end. It gets a GPU and whatever kubelet policy the operator chose, and it cannot turn on single-numa-node or move a card.

Two limits keep this honest. Bare metal is not automatically faster. Passthrough hands a VM a whole GPU, and the hypervisor's overhead is often not the largest cost. What bare metal adds for sure is that the topology is visible and the settings are yours. Bare metal is also a way of delivering a server, and it can still be cloud. NIST's definition of cloud computing, SP 800-145, rests on on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service. A bare metal server that is ordered through an API, deployed automatically, metered, and cleaned for the next tenant when it is released meets that definition.

Chapter 14 of 14

The work that wants the whole machine

Five kinds of workload, and the part of the topology each one leans on

Large training comes first. A model trained across many GPUs exchanges gradients and activations at every step. Inside a server that traffic runs over NVLink, which topo -m shows as NV# between two GPUs. Between servers it runs over the fabric, where NCCL uses GPUDirect RDMA, and the chapter It is not only the GPU showed that path needs the network card and the GPU under the same upstream root complex. Every GPU waits at each synchronisation point for the slowest path. So a single GPU whose port is on the other socket, SYS in the matrix, slows all of them, and no error reports it. The team that runs the job has to see the matrix, choose which GPU pairs with which port, and check the fabric between servers. Bare metal shows all of it.

HPC and simulation use the processors, memory, GPUs, network and storage as one tightly coupled system. This lesson's numbers show what is at stake. The example processor reads its own bank at 307 GB a second. A copy from the near bank into the GPU runs at 55 GB a second and from the far bank at about 24. A simulation that moves data between host and GPU on every step pays that difference on every step, and only an operator who can pin threads and memory can remove it.

Dedicated inference is the case this site keeps returning to. The Deployment qwen3 runs Pods qwen3-6f7d9c8b4-x7k2p on gpu-node-1 and qwen3-6f7d9c8b4-m9q4t on gpu-node-2, each holding one GPU for weeks. Each serves the official FP8 build, Qwen3-32B-FP8, whose 34.3 GB of weights take about three minutes to load, so these Pods are meant to stay put. A long-running service wants predictable capacity. On a dedicated server no neighbour competes for the cores, the memory bandwidth, the PCIe slots or the link between sockets. The chapters On the near side and On the far side showed why that matters: a parked 6.3 GB KV cache comes back in 114 milliseconds from the near side and 262 from the far side, and contention on the link moves the far figure further. The chapter No gauge moves showed that none of this raises an alarm.

Controlled or regulated environments want physical separation. On a dedicated server no other tenant's code runs on the same processors, memory or GPUs. Separation in time matters as much: the server must be wiped before the next tenant gets it. OpenStack Ironic, which runs physical machines as cloud resources, does this with automated cleaning. A node passes through cleaning when it moves from active to available, or from manageable to available, and the default steps include erasing all of the previous tenant's data. This is also why bare metal provisioning is more involved than starting a VM. It can go through the BMC, the board's remote management controller, then PXE or image deployment over a network boot, and then cleaning on the way out.

Custom system stacks need direct control of drivers, kernels, runtimes or schedulers. Examples from this lesson: a kernel with numa_balancing set the way you measured, a kubelet with the static CPU Manager and single-numa-node, a NUMA-aware scheduler such as the KAI scheduler, a particular NVIDIA driver and CUDA version. Each sits below the line that a VM or a shared cluster lets a tenant change.

Virtualization fits the other side of the list. Users who need less than a full GPU, short-lived development and test environments, cases where fast creation from a VM image matters, organizations with established VM security, image and backup operations, a priority on high utilization, and desktop or VDI work. A developer trying a small model for an afternoon gains nothing from owning the slots. A team serving Qwen3-32B-FP8 around the clock, or training across sixteen GPUs, does.

When buying, the label bare metal says little on its own. Check the GPU model, count, memory and interconnect. Check the processors, memory, local storage and PCIe topology. Check the network bandwidth, Ethernet or InfiniBand, RDMA support and the topology between servers. Check storage throughput, provisioning time, the API, metering and reservation, and the driver, CUDA, container and Kubernetes support with the scheduler. The question from the chapter It is not only the GPU, whether each GPU has a port on its own side, belongs on that list.

What to keep

Near is fast, far is slow, and nothing tells you

A two-socket server is two halves joined by one link. Memory and card slots belong to the processor beside them. Linux puts a page on the node of the core that first touches it, and moves threads by load, so where a process lands is luck unless someone decides it. A GPU is on one side, and the process that feeds it is fast when its cores and memory are on the same side and two to three times slower when they are not. Nothing fails either way, so it shows only as latency. Linux will tell you the layout if you ask, through numactl, sysfs, numastat and nvidia-smi topo -m. By hand, numactl binds a process to one half. In Kubernetes, the kubelet keeps a Pod's cores, memory and GPU on one node if it runs the static CPU and Memory Managers with the single-numa-node Topology Manager and the Pod asks for whole CPUs with requests equal to limits. What no setting can change is which slot a card is in. And every one of these levers belongs to whoever runs the host, which is why work that depends on topology, such as large training, HPC, long-running dedicated inference, regulated systems and custom stacks, so often runs on bare metal.
