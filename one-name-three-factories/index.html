BNK and gateways

One name, three factories

How GSLB sends a caller to one site

The other lessons happen inside one factory. A real service runs in several: here Frankfurt, Amsterdam and Madrid, each with its own GPUs and its own address. Callers still know a single name. Something has to decide which factory a caller reaches, before any packet of the request exists. That decision is made in DNS. The server that answers for the name does global server load balancing, GSLB for short: it knows every site, keeps checking them, and answers each lookup with the address of the one that should take this caller right now. Inside the chosen factory, BNK then picks the GPU. Two tiers, two different questions. This lesson follows one lookup from a browser in Lisbon, takes the decision apart, and then breaks a factory to show what DNS can fix, how fast, and what it cannot move. Along the way it shows what the GPUs must report for GSLB to judge room, the rules about where data may go that come before any score, and what happens when every site is full: overflow to a cloud tier, unless the caller or the data must stay.

Chapter 1 of 16

One name

The caller asks its resolver

A user in Lisbon opens the chat app. The same would be true of an agent or a backend service: all of them are configured with a name, not an address. The browser needs an IP address for api.northlight.example before it can open a connection, so it asks the operating system, and the operating system's stub resolver sends the question on. A stub resolver is the small DNS client built into every computer. It does no searching of its own. It forwards each question to one recursive resolver, here the resolver of the user's internet provider at 198.51.100.53.

The question is one UDP datagram to port 53. It starts with a 12-byte header holding a random 16-bit id, here 0x7c1e, so that the answer can be matched to the question, and the flag RD, recursion desired, which asks the resolver to do the whole search. The question section names the host and the record type A, an IPv4 address. On the wire each label of the name is a length byte followed by its letters, so api takes 4 bytes, northlight 11 and example 8, and a zero byte ends the name: 24 bytes. With 2 bytes of type and 2 of class the DNS message is 12 + 24 + 4 = 40 bytes, and the whole frame 82.

The resolver first looks in its cache. It answered the same question for another customer earlier, but that answer came with a lifetime of 30 seconds and has expired. So the resolver must ask the server that is responsible for the name. Everything that follows depends on that server, and on the fact that its answers are made to expire quickly.

Chapter 2 of 16

The resolver finds who answers for the name

A delegation hands one name to F5 DNS

DNS is a tree of zones, and each zone can hand part of itself to other servers. The handover is a delegation: NS records in the parent zone that name the servers of the child. A resolver with an empty cache would start at a root server, be referred to the servers of example, then to the servers of northlight.example, and finally to the server for the name itself. Each referral is an answer with no address for the name in it, only NS records and the addresses of those servers, called glue. A busy resolver rarely makes the whole walk, because the NS records higher up live for hours or days and stay in its cache.

Northlight's own zone, northlight.example, is ordinary DNS. It holds one record that matters here: api.northlight.example NS ns1.northlight.example, together with northlight.example's own A record for ns1, which gives its address as 203.0.113.5. Because ns1 sits in northlight.example itself, above the cut, that A record is ordinary authoritative data of the zone, not glue. That record hands this single name to F5 DNS. The rest of the zone, the web site and the mail servers, stays with the normal DNS servers. This is how GSLB is usually brought in: the company keeps its zone and delegates only the names that need a choice made for them.

The delegation itself can live long, an hour or a day, because ns1 does not move. Only the answers ns1 gives about the factories need a short life. The resolver now prepares its question for 203.0.113.5. It clears the RD flag, because it is asking an authoritative server, one that holds the data and gives a final answer. And it adds a detail about the user, which the next chapter takes apart.

Chapter 3 of 16

Where the caller really is

The resolver adds the client's subnet

F5 DNS sees the question arrive from 198.51.100.53, the resolver. Plain DNS says nothing about the user behind it. For GSLB that is a problem, because the point is to answer by where the caller is. Many people use public resolvers far from where they sit, and a large provider can serve a whole country from a few resolver sites. Placing a user by the resolver's address can be off by a country or more.

EDNS Client Subnet, ECS, defined in RFC 7871, closes that gap. EDNS is the extension mechanism of DNS: a pseudo-record of type OPT added at the end of a message, which carries options. ECS is option 8. It holds the address family, 1 for IPv4, a source prefix length, a scope prefix length and the leading bits of the client's address. The RFC recommends that a resolver send at most 24 bits of an IPv4 address and 56 bits of an IPv6 address, so here the option says 198.51.100.0/24. That places the user and keeps the exact host private. In a query the scope is 0. The OPT record adds 22 bytes: 11 for the record itself and 11 for the option, which makes this frame 104 bytes.

BIG-IP DNS supports ECS from version 14.0. When a query carries the option, topology load balancing uses that subnet in place of the resolver's address. F5 DNS looks the subnet up in its IP geolocation database, which places IPv4 addresses by continent, country, state and ISP. In this lesson 198.51.100.0/24 falls in a topology region named Iberia. If a resolver sends no ECS, the decision uses the resolver's own address.

Chapter 4 of 16

What GSLB knows

It has been checking the factories all along

F5 DNS does not start investigating when the question arrives. It already holds a picture of every factory, built by monitors. A monitor is a small test that F5 DNS runs against a site's address on a timer. In BIG-IP DNS terms each factory's address is a virtual server. Virtual servers are listed under a server object, servers belong to a data center, and the members of a wide IP's pool point at virtual servers. Monitoring these objects is what makes each one available or not.

Two settings drive a monitor. The interval is how often a check runs. The timeout is how long a target may go without a good answer before it is marked down. The http monitor of BIG-IP DNS ships with an interval of 30 seconds and a timeout of 120, and F5's usual advice is a timeout of three intervals plus one second. The default does not follow that advice: three intervals plus one would be 91 seconds. This lesson's monitors are tighter: an HTTPS check every 5 seconds with a timeout of 16, which is 3 × 5 + 1. A target is marked down once no check has succeeded for the whole timeout, whether it just went silent or refused the connection. This lesson counts the full 16 seconds.

When a site runs BIG-IP software, BIG-IP DNS can also learn the state of its virtual servers over iQuery, F5's own protocol on TCP port 4353, spoken between the gtmd process on the DNS system and the big3d agent on each BIG-IP. In this lesson the check goes to each factory's address, where TMM, BNK's data plane, answers. A healthy answer therefore proves two things: the factory is up, and the way into it works. The latest checks are in. Frankfurt answers and has room. Amsterdam answers but is almost full. Madrid, the factory closest to Lisbon, has not answered for 16 seconds and is down.

Chapter 5 of 16

Up is not the same as room

A healthy site can still make a caller wait

A plain health check would call Amsterdam perfectly fine. It answers quickly with 200 OK. Yet the KV cache on its GPUs, the memory that holds the requests in flight, is 96% full and 41 requests are waiting. A caller sent there would join that line. For web servers this gap rarely matters, because one more page costs little. For a model server it matters a great deal. One request can occupy a GPU for seconds and hold its memory for the whole length of the answer, so a site can be fully up and have no room at all.

BIG-IP DNS has tools for load beyond up and down. Limit settings make a resource unavailable when it crosses a threshold: bits per second, packets per second and current connections at the level of server, pool and virtual server, and CPU and memory for a server. Dynamic load balancing methods such as Virtual Server Capacity, Least Connections and CPU prefer the members with more headroom. None of these counts GPUs. A connection count says little about a server whose work is measured in tokens.

F5's own decks describe where this goes. The first tier, site selection, takes three kinds of input: policy (sovereignty, cost and tenancy), AI telemetry (GPU load, queue depth and time to first token) and round trip time with health. Telemetry flows up from each factory, and ratios or weights flow back down. In the factory-terminated design F5 draws for an AI grid, GSLB weighs health, capacity and a tenant's service level, down to millijoules per token, and even the local price of power and the carbon footprint. This lesson shows the capacity signal as a figure in the monitor's answer, with illustrative field names, and applies a policy of its own: a factory under 10% free capacity is used only when nothing else is left.

Chapter 6 of 16

What the GPUs report

Room is measured in KV cache and queues

The best known number for how busy a GPU is does not measure room. The utilization that nvidia-smi and NVIDIA's management library NVML report is the percent of time, over the last sample period, during which one or more kernels was executing on the GPU. A worker running a batch of 2 requests and a worker running a batch of 60 can both read close to 100%, because in both a kernel runs nearly all the time. The figure says that the GPU is working. It says nothing about whether one more conversation fits, and that is the question GSLB has to answer for the next caller.

The numbers that do answer it live inside the model server. vLLM publishes Prometheus metrics at /metrics on its serving port, here port 8000 of each Pod. Four of them describe room. vllm:kv_cache_usage_perc is the fraction of KV cache blocks in use, from 0 to 1. vllm:num_requests_waiting counts requests that have arrived and have no place in a batch yet. vllm:num_requests_running counts the requests in the batch. vllm:time_to_first_token_seconds is a histogram of how long callers waited for their first token. The KV cache figure is the most direct, because every running request keeps the keys and values of all its tokens in GPU memory until its answer is finished. When the blocks run out, new requests wait.

Here is how much that memory holds. Qwen3-32B keeps 64 layers × 8 KV heads × 128 values × 2 (a key and a value) × 2 bytes = 262,144 bytes, 256 KiB, for every token of context, with the cache in 16-bit values. On an 80 GB H100, vLLM by default plans to use 90% of the memory, 72 GB. The FP8 build's weights take 34.3 GB of that, which leaves 37.7 GB, and this lesson counts about 30 GB of it as KV cache once activations and CUDA graphs have their share. 30,000,000,000 ÷ 262,144 is about 114,400 tokens per worker, about 343,300 tokens for a factory of three workers.

A collector in each factory reads the three workers every 5 seconds and adds them up into one signal for the site. In Amsterdam the three workers report KV usage of 0.97, 0.95 and 0.96. Their free fractions are 0.03 + 0.05 + 0.04 = 0.12 of one worker, and 0.12 × 114,441 is about 13,700 tokens. Over three workers that is 4% free. Requests waiting: 14 + 13 + 14 = 41. Two conversations of 7,200 tokens would need 14,400, so Amsterdam has room for one, and not for two. Frankfurt reports 0.41, 0.36 and 0.37. Free is 0.59 + 0.64 + 0.63 = 1.86 workers, about 212,900 tokens, 62% free, with 0 + 1 + 0 = 1 request waiting. These are the figures the monitor answers carried in the chapters before. F5's diagram of the logical flow of the AI service plane draws this same path: a per-site GPU capacity signal from each on-prem site feeds one aggregated GPU metric, and GSLB selects the site on that metric.

In F5's AI Grid, GSLB reads that signal as an input next to health and topology. The two-tier deck draws the link as telemetry going up from the factories and a ratio or weight coming down. The signal reaches the decision in two forms. A threshold turns a site into a site with no room: in this lesson, under 10% free. A weight shares new callers between sites that are otherwise equal. The weight has a plain BIG-IP DNS object behind it. Every pool member has a ratio, an integer weight with a default of 1, used by the Ratio load balancing method, and it can be written through iControl REST whenever the signal changes. With a ratio of free tokens ÷ 1,000, Frankfurt gets 213 and Amsterdam 14, and Ratio sends 213 ÷ 227 = 93.8% of new lookups to Frankfurt and 6.2% to Amsterdam.

The signal changes every 5 seconds and each answer lives 30. Steering on the raw figure would swing whole subnets back and forth between sites. Two habits keep it calm. Smoothing: decide on the average of the last three reports, taken 5 seconds apart, so 10 seconds pass from the oldest to the newest. Hysteresis: a site leaves when its free capacity drops under 10% and comes back only when it climbs above 20%, so a site hovering between 9% and 11% does not flap. Both numbers are this lesson's own policy.

Chapter 7 of 16

Where the data may go

Regulation is a hard rule, and it runs first

F5's deck on placing inference names three hard constraints. The first two match the task to a size of model and the size of model to a tier of infrastructure, from cheap edge boxes for simple calls to the big factory for long reasoning. Governance is the third, and the deck lists the rules it stands for: GDPR, UK GDPR, national sovereignty, HIPAA, PCI-DSS and the FCA. Its example fixes the order of every routing decision: a request tagged EU-only cannot leave EU infrastructure, regardless of latency or cost. A hard constraint removes options before anything is scored. Distance and spare capacity are preferences, and they only rank what is left.

The rules ask for different things. GDPR, the EU's Regulation 2016/679, controls transfers of personal data to countries outside the EU in its Chapter V. A transfer needs an adequacy decision by the European Commission for that country, or appropriate safeguards such as standard contractual clauses, or binding corporate rules inside one group of companies, or one of a few narrow exceptions. GDPR does not itself forbid processing abroad. Many contracts still say EU-only, because that removes the transfer question altogether. A prompt that names a person is personal data. So is the KV cache that holds the prompt on the GPU while the answer is made, and so is the log line written afterwards. UK GDPR is the version of GDPR kept in UK law after Brexit, next to the Data Protection Act 2018, with its own rules for transfers out of the UK. National sovereignty rules go further and keep some data inside one country. The FCA, the UK's Financial Conduct Authority, expects a firm that outsources to the cloud to keep choice and control over the jurisdictions where its data is processed, stored and managed, in its guidance FG16/5.

Two of the rules are about assurance more than place. HIPAA, the US health privacy law, has no requirement specific to health data processed or stored outside the United States, as the US Department of Health and Human Services says in its guidance on cloud computing. It does require a business associate agreement with anyone who handles protected health information for a covered entity, and a risk analysis that takes the location into account. PCI DSS, the standard of the PCI Security Standards Council, applies to every system that stores, processes or transmits cardholder data. A site that receives a prompt holding a card number becomes part of the environment that is assessed. For routing, all six end in the same form: a list of sites that may take this traffic.

At DNS time there are only two facts to hang that list on: the name that was asked and the caller's subnet. No prompt exists yet. So the residency class is written into the name. api.northlight.example is Northlight's EU name, and its wide IP has only EU factories in its pools. Virginia, 198.18.0.80, is not a member at all, so no score, weight or failure can ever produce its address. The caller's country, looked up from the ECS subnet, is the second place a rule can live, and a later chapter uses it. Inside the factory the AI gateway knows the tenant from its key and applies the same tag to every request, and to every place a request could be forwarded.

Put numbers on it. For the caller in Lisbon, Virginia would have 80% of its GPU capacity free and a price per token 30% lower than Frankfurt's, both figures made up for the lesson. Neither number enters the decision. If Madrid, Frankfurt and Amsterdam were all down at once, the capacity floor would have nothing left to give way to. F5 DNS would return no address rather than one outside the EU: the pool's fallback, Return to DNS by default, gives none, and the wide IP can be set to answer with an RCODE such as REFUSED, which F5 describes as refusing for policy reasons. The caller sees an outage. The data stays in the EU. That is the price of a hard constraint, and the reason it is applied before anything else.

Chapter 8 of 16

The decision

Rules first, then the best site left

Now F5 DNS answers the question. In its configuration the name is a wide IP: a fully qualified name with one or more pools behind it. Here there is one pool, eu-factories, with one member for each factory's virtual server. Each pool has three load balancing methods, tried in order. The preferred method runs first. If it cannot return a valid answer, often because the metrics it needs are missing, the alternate runs, and the alternate must be a static method. The fallback runs last and ignores whether members are available, so that F5 DNS can still return an answer. A fallback of None or Return to DNS gives no address, so even the fallback does not guarantee one. A method set to None is skipped.

This pool's preferred method is Topology. A topology record maps a request source to a destination and gives the pair a weight. The source can be a subnet, a region, an ISP, a state, a country or a continent. The destination can be a pool, a data center, a region or a subnet among others. For each member F5 DNS takes the first record that matches both the caller and that member, and the record's weight becomes the member's score. A member that matches no record scores zero. The highest score wins, and members with equal scores share the traffic round robin. With Longest Match, the default, more specific sources sort first, so a record for one subnet beats a record for a whole continent.

The rules run in a fixed order. Data residency first: this customer's data must stay in the European Union, so the factory in Virginia is not in this pool at all. Health next: Madrid is down. Topology then ranks what is left for a caller in Iberia. Its records give Madrid 300, Frankfurt 200 and Amsterdam 100, and Madrid's 300 does not count while Madrid is down. Then the capacity floor sets Amsterdam aside. Frankfurt is what remains. It is not the closest factory. It is the closest one that can do the work.

Chapter 9 of 16

The answer, and how long it lives

Thirty seconds, for one /24

F5 DNS answers with one A record: api.northlight.example, 203.0.113.80, TTL 30. The TTL, time to live, is the number of seconds any cache may keep the answer. The flag AA, authoritative answer, says it comes from the server that owns the name. On the wire the answer adds 16 bytes to the question's 40: a 2-byte pointer back to the name already written in the question, 2 bytes of type, 2 of class, 4 of TTL, 2 of length and the 4 bytes of the address. The OPT record goes back too, 22 bytes, now with the scope prefix length filled in.

The scope tells the resolver who may reuse the answer. A scope of 24 means the answer holds for clients in 198.51.100.0/24 only. The resolver files it under that subnet. A user of the same resolver in another /24, in Paris for example, gets a lookup of their own and maybe a different factory. A scope of 0 would mean the answer suits everyone. Narrow scopes make answers more precise and caches less effective, because the resolver keeps one copy per subnet.

The TTL is the dial between agility and load. A TTL of a day would mean one lookup a day per subnet, and a failed site that callers feel for a day. Thirty seconds means a resolver with steady traffic asks up to twice a minute per subnet, 86,400 ÷ 30 = 2,880 times a day, and a failed site leaves its answers within 30 seconds of F5 DNS noticing. The resolver passes the address to the browser and keeps it until the 30 seconds are over. The browser and the operating system may keep it too, and that is the part F5 DNS controls least.

Chapter 10 of 16

To Frankfurt

DNS is done, the request begins

The browser now has an address and opens a connection to it. From here on DNS plays no part. TCP's handshake comes first, and this lesson's clock leaves it out. Then TLS 1.3. The browser's ClientHello carries the name api.northlight.example in the server_name extension, SNI, so the factory knows which certificate to present, and it offers h2 and http/1.1 through ALPN, the extension that agrees the application protocol. The ClientHello is 517 bytes, and with the Ethernet, IP and TCP headers the frame is 583. The factory answers with its ServerHello, its certificate and its Finished message, picks TLS 1.3 and h2, and after one round trip both sides hold the keys.

The packets reach Frankfurt because the internet's routers know the way to 203.0.113.80. The Frankfurt factory announces the address block it belongs to with BGP, the routing protocol between networks. Each factory announces its own block, so 192.0.2.80 leads to Amsterdam and 192.0.2.160 to Madrid. DNS picks the destination address and routing does the rest. That is why GSLB fits any network: it needs nothing from the routers.

This lesson puts the round trip from Lisbon to Frankfurt at 31 ms, so the factory's reply arrives 31 ms after the ClientHello left at 25 ms, at 56 ms. The lookup took about 24.7 ms of that, and the next lookup within 30 seconds costs nothing because the answer is cached. F5 DNS never sees the request, the prompt or the answer. It chose the site and stepped aside.

Chapter 11 of 16

Inside the factory

The second tier takes over

Zoom into Frankfurt. This is the factory of the other lessons, and the connection lands where every request does: on the BNK data plane at its border, TMM, on 203.0.113.80. The browser sends its request on the new connection: an HTTP/2 POST to /v1/chat/completions: a HEADERS frame of 148 bytes, then a DATA frame of 8,210 bytes, which is a 9-byte frame header and 8,201 bytes of JSON. Everything after this is the second tier of the decision.

The two tiers know different things at different speeds. GSLB chose among three sites on what it could learn from outside: a monitor answer every 5 seconds, and a decision that holds for 30 seconds for a whole /24 of callers. The second tier decides once per request, in milliseconds, on what it knows from inside. The AI gateway works out who is calling and which model answers, with their keys and budgets. The endpoint picker chooses a GPU from the live state of each worker: its queue and what its KV cache holds.

F5's deck on the two-tier control plane lists the inputs of the second tier as GPU use per Pod, queue depth, where the KV cache already holds the prompt, affinity to a model and priority class. It also shows the link between the tiers: telemetry flows up from the factory, and weights flow down. When the second tier sees its pool filling, that is exactly the signal the first tier needs to send the next callers elsewhere.

Chapter 12 of 16

A factory fails

What DNS can fix, and how fast

Zoom back out. At 60 seconds Frankfurt loses its uplink. Its last good answer to a monitor came at 59 seconds. F5 DNS cannot see a failure directly. It can only notice that checks stop succeeding. The checks at 64, 69 and 74 seconds go unanswered. A dead uplink sends no reset, so nothing shortens the wait. At 75 seconds, 16 seconds after the last good answer, the timeout runs out and Frankfurt is marked down.

F5 DNS cannot call anyone back. All it can do is answer the next question differently. Every answer it gave up to 75 seconds still said Frankfurt, and each lives 30 seconds in the resolver that holds it. Our resolver last asked at 48 seconds, so its copy expires at 78 seconds. The next caller after that makes it ask again, and this time the answer is Amsterdam. With Madrid and Frankfurt both down, Amsterdam is the only member left, and the capacity floor gives way. A full factory is better than none.

The worst case adds up simply. A resolver that asked just before 75 seconds keeps the old answer for 30 more seconds, so callers can be sent to a dead site for as long as the timeout plus the TTL, 16 + 30 = 46 seconds after the last good check. A request that was streaming from Frankfurt when it failed is lost, because its connection ran over the failed uplink, and the caller has to send it again. A shorter timeout notices sooner and risks marking a site down for one slow answer. A shorter TTL moves callers sooner and costs more lookups.

Chapter 13 of 16

What DNS cannot move

Caches and connections it does not control

The 46 seconds assume that every cache obeys the TTL. Not all do. Some resolvers raise very short TTLs to a minimum of their own to save lookups. Language runtimes and HTTP client libraries can keep their own copy of an answer with their own lifetime. Each of these stretches the time a caller keeps going to the old address, and F5 DNS has no say over any of them.

A bigger effect comes from connections. DNS is asked only when a connection is opened. An HTTP/2 connection carries many requests, one per stream, and a client keeps it open for minutes or hours. While Frankfurt was healthy that saved time: no lookup and no handshake per request. When Frankfurt fails, the client learns of it only through the connection, as requests that time out or a connection that is reset. Only then does it open a new connection, ask DNS again and land in Amsterdam. Agents and backend services that hold long connections move on their own schedule, whatever the TTL says.

The same is true when a site is healthy and overloaded. DNS can steer only new lookups away. Callers who already have connections stay. That is why the second tier matters. Inside Amsterdam the endpoint picker sees every request and can queue it, place it, or refuse it with a 429 when the pool is truly full. GSLB moves the next callers. The picker protects the GPUs from the callers already there.

A client built for several factories therefore does three things. It retries a failed request on a new connection. It looks the name up again when it does. And it treats a lost stream as something to send again.

Chapter 14 of 16

When Madrid comes back

Up again, and how the traffic returns

Ten minutes in, Madrid's network is repaired and its next check succeeds. Nothing is pushed to anyone. Like a failure, a recovery shows only in the next answers. Without any hold, F5 DNS would mark Madrid up at once. A lookup from Iberia would score Madrid 300 again, the highest, and get Madrid's address with a TTL of 30. Within 30 seconds every resolver serving Iberian users would move its new callers back, while existing connections stay where they are until they close. This lesson's pool holds Madrid back with the setting described below, so that move happens at 12 minutes.

That swing can hurt. A site that has just recovered gets a whole region's new traffic at once, and its GPUs hold none of the prompts that the other sites have cached, so the first requests of every conversation pay the full prefill. A site that comes up and fails again flaps, pulling callers back and forth every few seconds. BIG-IP DNS has a setting for this called Manual Resume. When it is enabled on a pool, a virtual server that comes back online receives no requests until an operator enables it again. That gives the operator time to check the site, and to warm it, before it takes traffic.

Without Manual Resume the return is automatic and quick, which suits a short blip. With it, Madrid stays out until someone decides. In this lesson the operator checks Madrid and enables it two minutes after it came back, at 12 minutes. The next lookup from Lisbon gets Madrid. Frankfurt, whose uplink failed at 60 seconds, was repaired a few minutes later and went through the same hold. The operator checks it and enables it at 12 minutes too, so from then on all three factories take new callers again. Either way the decision stays in one place, the wide IP, and callers only ever see an address that changed.

Chapter 15 of 16

When every site is full

Overflow to the cloud, unless the caller must stay

F5's slide on the logical flow of the AI service plane draws the whole decision in one picture. A user request reaches GSLB, which selects among the on-prem sites on an aggregated GPU metric built from each site's own capacity signal. Inside GSLB sits a Geo-DB, the geolocation lookup that gives the caller's country, its countryID. Each on-prem site runs an AI gateway, per tier and model, that throttles every tenant to a token limit, and AI Guardrails, AIGR, that look for personal data, PII. Off to one side is a cloud GPU tier: elastic capacity, and the ultimate overflow. A PII or countryID match forces local and skips the overflow logic. The customer goal written on the slide is continuity: staying online.

Fifteen minutes into the lesson, at an evening peak, all three factories are healthy and all three are full. Frankfurt has 6% free, Amsterdam 3% and Madrid 5%, each under the 10% floor. In the failure chapter the floor gave way because Amsterdam was the last place left. Here a fourth place exists. Northlight rents GPUs in a cloud region inside the EU, cloud-eu at 198.18.2.80, running the same Qwen3-32B-FP8 build, so an answer does not change with the site that made it. In BIG-IP DNS terms the wide IP now holds pools in order, first eu-factories, the pool of the earlier chapters, then cloud-eu, with the Global Availability method between them: the first pool in the list is used until it becomes unavailable, then the next. A wide IP can also name a last resort pool for when its other pools cannot answer, which fits a cloud tier just as well. F5's slide says that GSLB tries each on-prem site by its live capacity and overflows when no on-prem site has capacity. Its footer names site capacity, AIGR and the Geo-DB as extensions of this design, so none of the three is built-in product behaviour. What counts as no capacity is the operator's choice, and in this lesson it is the 10% floor. On plain BIG-IP DNS one way to build it is an automation that disables a member of eu-factories while its site is under the floor, the way the operator held Madrid out earlier. With all three members disabled, eu-factories has nothing to offer and Global Availability moves on to cloud-eu. Callers who must stay local then need a pool the automation never touches. So the wide IP holds a third pool, eu-local, with the same three sites and a Topology method of its own, listed after cloud-eu so that the normal order reaches it only when the cloud tier is down too.

The country rule comes before any overflow. F5 DNS takes the subnet from ECS and looks it up in its geolocation database. The iRule command whereis returns the country as a two-letter ISO 3166 code, and in this lesson 198.51.100.0/24 gives PT. Northlight's policy lists the countries whose callers must be served on its own sites: PT and ES, an illustrative list. A match forces local, and the iRule answers from eu-local, where Madrid is still enabled. The caller in Lisbon gets Madrid, topology score 300, at 5% free. Madrid's endpoint picker then decides whether the request waits in its queue or is shed with a 429. A caller in Paris, whose subnet 198.19.44.0/24 this lesson places in FR, is not on the list. Every member of eu-factories is under the floor and disabled, so the answer for Paris is cloud-eu. Both answers live 30 seconds.

The PII rule cannot be applied in DNS, because PII is found in the prompt and the prompt does not exist yet. It is applied at the site, where AI Guardrails scan the prompt before the gateway decides where the request runs, and it governs the second overflow path, the one the next chapter follows. A tenant whose every request may carry personal data is safer with a name of its own whose wide IP has no cloud pool, so that DNS cannot send its callers to the cloud tier either. That last step is this lesson's way of applying the slide.

Elastic capacity has to be warm to be any use. A cloud GPU that must be ordered, booted and then loaded is too slow for a peak that lasts minutes: loading this model alone takes about three minutes once the server is up. So the cloud tier keeps at least one worker running and adds more as its own queue grows. Rented GPUs cost more per token than owned GPUs that are already paid for, which is why the cloud tier is the last place tried, and the first released when the on-prem sites climb back above 20% free.

Chapter 16 of 16

One tenant over its limit

The second overflow path, and why the count may be approximate

The second overflow path starts inside a site. Each on-prem site's AI gateway throttles every tenant to a token limit, so that one tenant's burst cannot fill the site's GPUs for everyone else. On F5's slide a tenant that reaches its limit overflows to the cloud tier, per tenant. The site keeps serving its other tenants on its own GPUs, and only the heavy tenant's extra requests leave. This is Frankfurt again, with two tenants of Northlight, tenant A and tenant B, each limited to 120,000 tokens per minute at this site, a figure made up for the lesson.

Tenant A has used 118,500 tokens in the current minute when its next request arrives: a prompt of 1,900 tokens and max_tokens of 1,024. The gateway cannot know how long the answer will be until the model has written it, so it reserves the worst case, prompt plus max_tokens, as BNK's gateway did for a budget in the lab: 1,900 + 1,024 = 2,924. That would take tenant A to 118,500 + 2,924 = 121,424, over the 120,000 limit. Without overflow the answer would be a 429, Too Many Requests. In the lab that 429 came from a budget, a token allowance that resets hourly, daily, weekly or monthly, and its error was budget_exceeded. BNK's gateway lists rate limits as a feature separate from budgets. A limit per minute like this one would be a rate limit, because a budget resets hourly at the shortest, and this lesson does not show a rate limit's error body. AI Guardrails scan the prompt first and find no personal data, so overflow is allowed. The gateway sends the request to its cloud deployment of the same model, which it holds as a second provider of lower priority. The answer comes back with its usage, 1,900 prompt tokens and 640 completion tokens, 2,540 in all, and the 384 tokens reserved and not used are released.

Tenant B is over its limit at the same moment, but AI Guardrails find an email address and a bank account number in its prompt. A PII match forces local and skips both overflow paths. The request stays in Frankfurt and gets the 429, and the client retries once the minute rolls over. Guardrails run before the overflow decision for exactly this reason: the decision depends on what they find.

The customer goal on the slide is continuity, and it names the accounting that goes with it: some level of token accounting, not necessarily exact. The limit above is per site, so tenant A could take 120,000 tokens a minute at each of three sites, 360,000 in all. One exact limit across all sites would need every request, at every site, to check a single shared counter before it runs. That adds a round trip between sites to every request, 30 ms between Frankfurt and Madrid in this lesson. And when the link between sites breaks, every site would have to stop serving, or stop counting. Continuity takes the other road. Each site counts locally, the sites exchange their counts every 10 seconds, and the overshoot is accepted.

The overshoot has a simple bound. With a shared limit of 360,000 tokens a minute and the tenant drawing 2,000 tokens a second at each of three sites, the sites can admit at most 3 × 2,000 × 10 = 60,000 tokens between two exchanges, which is 16.7% of the minute's limit. Exchanging every 2 seconds cuts it to 12,000, 3.3%, at five times the messages. The reservation is approximate too: it held 1,024 tokens for an answer that used 640. Every figure in this chapter is illustrative. The shape is what the slide asks for: the service stays up, and the count is close enough to bill and to protect each site.

What to keep

Site chosen in DNS

One name can lead to many factories because the choice is made in DNS, before the request exists. A delegation hands the name to F5 DNS, the resolver says where the caller is with a client subnet, and monitors keep a picture of every site. F5 DNS answers each lookup with one address: the factory with the best topology score among those that are allowed to serve this caller, healthy, and have room. Then it is out of the way, and BNK inside the factory picks the model and the GPU. When a site fails, DNS can only change its next answer, so callers move over within the timeout plus the TTL, and long connections move only when they break. Both tiers need the same thing to decide well: live knowledge of how busy the GPUs are, beyond whether a server is up. What GSLB knows about room comes from the model servers themselves: KV cache in use and requests waiting, summed per site. Rules from regulation sit above all of it. An EU-only name never answers with a site outside the EU, and a countryID or PII match keeps a request on the owner's own sites. When every site is full, the cloud tier takes the overflow, and per-tenant limits keep one tenant from filling a site. The goal is continuity, so the token count only has to be close.
