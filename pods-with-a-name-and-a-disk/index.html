Kubernetes underneath

Pods with a name and a disk

What a StatefulSet promises a database, and what it refuses to do

The model servers on this cluster are interchangeable. Any qwen3 Pod can answer any request, and a replacement is as good as the one it replaced. A database is different. The chat application in front of the model servers keeps its users' conversations in a MySQL database with three members, one primary and two replicas. Each member has its own data and its own place in the group. Swap two of them and the database is confused. A StatefulSet is the controller for Pods like these. It gives each Pod a number, a name that never changes, a DNS name of its own and a disk of its own that outlives the Pod.

This lesson builds one, then watches it come up, deletes a member, updates it, shrinks it, grows its disks, loses a node under it and finally tears it down. Along the way it shows what the controller writes into events, logs and status fields, so that an operator can tell what it is waiting for at each step.

Chapter 1 of 13

A database beside the model servers

Two objects: a Service with no address, and the StatefulSet

The chat application needs a place for its users' conversations. It uses MySQL, a relational database, run as three Pods: one primary that takes the writes and two replicas that copy from it. You apply two objects. The first is a headless Service called db. Headless means clusterIP is set to None: the Service gets no virtual address and exists only to give its Pods DNS names. A StatefulSet requires one, and you create it yourself. The Go type marks serviceName as optional, and its comment still says the Service must exist before the StatefulSet. kubectl get service db shows None in the CLUSTER-IP column.

The second is the StatefulSet, also called db. Its name must be a valid DNS label, because it becomes the start of every Pod name and every DNS name. Its serviceName field points at the Service. Its replicas field says three. Leave replicas out and it defaults to 1. Its selector must match the labels in the Pod template, or the API server rejects the object when it is created. Its volumeClaimTemplates field holds a template for a PersistentVolumeClaim, a request for storage. With no storageClassName in that template, the cluster's default StorageClass is used. From these the controller will make Pods named db-0, db-1 and db-2, the StatefulSet's name followed by an ordinal.

The model servers themselves do not need any of this. A vLLM Pod loads its weights from a shared source and keeps nothing it would miss. Some pieces of an AI stack do keep state on disk. A semantic router that classifies prompts before they reach a model is one example. In a lab built for this site's material it runs as a StatefulSet with two replicas, and each replica downloads about 3.6 GB of classifier models into a volume of its own on first start, so a restart finds them in place. A model too large for one machine is a different case. Its shards form one server that must start and stop as a unit, and projects such as llm-d use a LeaderWorkerSet for that.

Chapter 2 of 13

One at a time, in order

db-1 is not created until db-0 is Ready

The StatefulSet controller does not create three Pods at once. With the default policy, OrderedReady, it creates them in order from 0 upward and waits for each to be Running and Ready before it creates the next. So it first creates a claim and a Pod for ordinal 0 and stops. db-0 is scheduled, its image is pulled, its volume is mounted and its readiness probe passes. Only then does db-1 appear, and db-2 after that. This database depends on it: db-0 starts empty as the primary, and each replica first copies its data from the member one ordinal below, which must be up.

The controller's source code spells out the gate. For each ordinal, in order, three things stop it. A Pod that is terminating blocks, which means a Pod with a deletion timestamp. A Pod that is not Running and Ready blocks, which means its phase must be Running and its Ready condition True. And when spec.minReadySeconds is above 0, a Pod that has not been Ready for that many seconds blocks. That last field is stable since 1.25 and defaults to 0. At log verbosity 4, kube-controller-manager writes one of three lines to say which gate holds it: StatefulSet is waiting for Pod to Terminate, StatefulSet is waiting for Pod to be Running and Ready, or StatefulSet is waiting for Pod to be Available.

Deletion runs the other way, from the highest ordinal down, and each Pod must be gone before the next is touched. The other policy, Parallel, creates or deletes Pods without waiting. It still creates them in batches that start at 1 and double, up to 500 at a time. Parallel changes scaling only. Updates still go one Pod at a time unless maxUnavailable says otherwise.

Chapter 3 of 13

Watching it come up

Events, status fields and log lines say what the controller is doing

A StatefulSet that stops halfway looks the same from the outside whatever the reason. Three places tell them apart. The first is events on the StatefulSet object. For every Pod it creates, updates or deletes, the controller records an event whose reason is Successful or Failed followed by the verb. A good one reads Create Pod db-0 in StatefulSet db successful. A failure reads Create Pod db-0 in StatefulSet db failed error, followed by the error itself. Claims get their own events: Create Claim storage-db-0 Pod db-0 in StatefulSet db success, or a Warning that names the claim and the error. Since 1.35 the verb at the start of the message is capitalised, as in the reason. Clusters on 1.34 and earlier write it in lower case, create Pod db-0, so a search for the exact text should ignore case. A missing StorageClass or a full quota shows up there first.

The second place is the status. kubectl get statefulset db prints only three columns, NAME, READY and AGE, and READY is readyReplicas over replicas. The object itself holds more. status.replicas counts the Pods the controller created. readyReplicas counts those with a Ready condition. availableReplicas counts those Ready for at least minReadySeconds. currentRevision and updateRevision name the template versions in use. observedGeneration says which edit of the spec the controller has seen.

The third place is the controller's own log at verbosity 4, which names the gate it is stuck on. Clusters that run kube-state-metrics turn the status into series such as kube_statefulset_status_replicas_ready and kube_statefulset_replicas. A rollout that stalls shows kube_statefulset_status_replicas_updated below kube_statefulset_replicas while the current and update revision series differ.

Chapter 4 of 13

A claim for each Pod

The disk belongs to the name, and it outlives the Pod

Each entry in volumeClaimTemplates gives every Pod one PersistentVolumeClaim of its own. The claim's name is the template's name, then the Pod's name. For the third Pod that is storage-db-2. In the source this is plain string formatting, the claim template name, the StatefulSet name and the ordinal joined by dashes, and a comment notes that the zone spreading heuristics for volumes rely on that format. The controller creates the claims before the Pod, in the same step. If a claim cannot be created, the Pod is not created either.

The storage system provisions a PersistentVolume for the claim, and the two are bound. When db-2 lands on gpu-node-1, the kubelet asks the storage driver there to make that volume appear, and the container sees it at /var/lib/mysql. The Pod's spec refers to the claim by name, and that is the whole link between them. The claim is a separate object with its own life. Deleting the Pod leaves it alone. Deleting the StatefulSet leaves it alone as well, by default. Three Pods therefore mean three claims and three volumes, each holding one member's full copy of the data.

Two details of that link catch people out. When a claim with the right name already exists, the controller uses it as it is. The code has only a to-do comment about checking its size and access modes, so a leftover claim of 10Gi is used without complaint. And when the claim with that name is being deleted, the controller will not create the Pod and reports pvc storage-db-2 is being deleted. While a Pod is Pending, the controller checks on every pass that its claims exist and creates any that are missing.

Chapter 5 of 13

A name that DNS answers

Each Pod gets its own record, through the headless Service

A normal Service hides its Pods behind one address. That is wrong for a database whose members must reach one particular peer. The headless Service gives each Pod a DNS name of its own: the Pod's name, then the Service's name, then the namespace. db-1 is db-1.db.inference.svc.cluster.local, and the answer is the Pod's own IP. The plain name db returns the addresses of all three. The application sends writes to db-0.db, the primary, and can read from any member. The replicas use the same names. Each one replicates from db-0.db, and db-1 cloned its data from there.

The record exists because of two Pod fields that the controller fills in. spec.hostname is db-1 and spec.subdomain is db, the name of the headless Service. A Pod with a subdomain and no hostname would get no record of its own. For a named port, the Service also answers SRV queries of the form _port-name._port-protocol followed by the Service's name, one answer for each Pod, each naming that Pod's hostname. The tutorial reads its own reads through a second, ordinary Service called mysql-read, with a cluster IP that spreads connections across all Ready members. Writes still need the primary's own name.

The name is the stable part. The IP belongs to the Pod of the moment and may differ after a restart, so clients should keep the name and look it up again. Two limits come with names. A lookup made before the Pod exists may be cached as a failure, and the StatefulSets page gives two remedies: watch the API instead of relying on DNS, or lower the cache time in the cluster's DNS server. And a Pod that sets setHostnameAsFQDN puts its full name into the kernel's hostname, which holds at most 64 characters. db-1.db.inference.svc.cluster.local is 35 characters, well inside the limit.

Chapter 6 of 13

Delete a Pod and it comes back as itself

Same name, same claim, same data, perhaps another node

Now delete db-1. The controller notices that ordinal 1 is missing and creates a Pod for it. A Deployment would make up a new name. The StatefulSet creates db-1 again, and the new Pod's spec names the same claim, storage-db-1. The scheduler is free to choose a node. Here it picks gpu-node-1, and the old Pod ran on gpu-node-2. The volume has to follow: it is detached from the old node and attached to the new one, which works when the storage is on the network. A volume that lives on one node's own disk pins the Pod to that node. The new db-1 has a new IP, the same DNS name and every byte the old one wrote. It skips the clone, reconnects to db-0 and catches up.

The same thing happens when a member stops by itself. A StatefulSet Pod whose phase becomes Failed is deleted and created again under the same name. So is one whose phase becomes Succeeded. The source explains why: a Pod that was evicted or stopped by a node reboot gets its final phase from the container's exit code, so a clean exit says nothing about whether the member should still be running. The replacement is created on the next pass after the old object is gone from etcd.

The wait for the old Pod to be gone is the reason the grace period matters. terminationGracePeriodSeconds gives MySQL time to flush and close its files after SIGTERM. Setting it to 0 turns every delete into a force delete, and the StatefulSets page calls that unsafe and strongly discouraged. Draining a node is the planned version of this chapter. The tutorial runs kubectl drain with --force, --delete-emptydir-data and --ignore-daemonsets, and the member reappears on another node passing through Init:1/2.

Chapter 7 of 13

Updates run from the highest number down

One Pod at a time, and a field that holds the rest back

You change the image in the Pod template. The default update strategy, RollingUpdate, replaces Pods one at a time in reverse order. db-2 is deleted and created again from the new template, with the same name and the same claim. The controller waits until it is Running and Ready, then moves to db-1, then db-0. In the source the loop starts at the highest ordinal and walks down to the partition. It deletes the first Pod whose revision label differs from the new revision and returns. If the Pod at the current position is not available, it stops and logs StatefulSet is waiting for Pod to update.

The partition field holds part of this back. With partition: 2, only Pods with an ordinal of 2 or more are updated. db-0 and db-1 keep the old version, even if one of them is deleted and recreated. That makes db-2 a trial: check it, then lower the partition to 0 and the rest follow. A partition equal to or larger than replicas freezes every Pod, because every ordinal is below it. On three replicas the ordinals are 0, 1 and 2, all below 3, so a partition of 3 stores the new template and changes no Pod. The tutorial stages a change that way and lowers the partition later.

Two more settings change the pace. maxUnavailable in rollingUpdate allows more than one Pod down at a time. It takes a number or a percentage that is rounded up, it cannot be 0, and it defaults to 1. It is behind the gate MaxUnavailableStatefulSet. The gate was alpha and off from 1.24 to 1.34. It turned beta and on by default in 1.35.0 to 1.35.3, was switched off by default again from 1.35.4 and for all of 1.36, and is on by default again from 1.37. On a cluster where the gate is off the field has no effect, the default of 1 is not filled in, and Pods are replaced one at a time. A third strategy, Recreate, deletes every Pod at once and waits for all of them to end before creating any. It is alpha and off by default from 1.37. The other established strategy, OnDelete, changes nothing until you delete a Pod yourself. Switching to it means setting rollingUpdate to null in the same patch.

Chapter 8 of 13

Revisions, and how a rollout is watched

Each template version is stored, and each Pod is labelled with the one it came from

The controller has to know which Pods are old. It does that with ControllerRevision objects. When the Pod template changes, the controller stores a snapshot of the new template in a ControllerRevision and gives it an increasing revision number. Each Pod carries the label controller-revision-hash, which names the revision it was built from. The update loop compares that label with status.updateRevision. A Pod whose label differs is old.

Two status fields describe the rollout. currentRevision is the revision used for Pods in the range from 0 up to currentReplicas. updateRevision is the revision used for the Pods at the top of the range, the last updatedReplicas of them. When the two are equal, the rollout is finished. Here currentRevision was db-7c9d5b8f6d before the change and updateRevision became db-58f4b7c9d2. Both names are illustrative. The real ones are the StatefulSet's name followed by a hash.

kubectl rollout status statefulset db reads these fields and prints a line from a fixed set, checking in a fixed order. If status.observedGeneration is behind the object's generation, it prints Waiting for statefulset spec update to be observed... If readyReplicas is below spec.replicas, it prints Waiting for N pods to be ready..., so this is the line you see while a replaced Pod is starting. Only when every Pod is Ready does it look at the strategy. When rollingUpdate.partition is set, it reports in partition terms: Waiting for partitioned roll out to finish, with a count out of replicas minus partition, then partitioned roll out complete. Defaulting fills in rollingUpdate with partition 0 whenever updateStrategy is left out, so almost every StatefulSet takes this branch, including db after its partition is lowered to 0. The other pair, waiting for statefulset rolling update to complete and statefulset rolling update complete, each with a count and a revision, appears only when a manifest writes type: RollingUpdate with no rollingUpdate block, because then no partition is filled in. With OnDelete the command returns an error, rollout status is only available for RollingUpdate strategy type.

Old revisions are kept for rollback. revisionHistoryLimit defaults to 10, and older ones are garbage collected. kubectl rollout history lists them, and kubectl rollout undo with --to-revision applies an old template as a new revision. Setting the limit to 0 removes the ability to roll back.

Chapter 9 of 13

Scaling down keeps the claim

The Pod goes. Its disk waits for it

The application is quiet, so you set replicas to 2. The controller removes the highest ordinal, db-2. Its claim, storage-db-2, stays, and so does the volume behind it. This is deliberate. Deleting data because a number in a spec went down is too easy a mistake, so the default is to keep it. Scale back to 3 and the new db-2 mounts the old claim and finds its data, which may be out of date by then. The cost is that kept volumes are still paid for, and their claims still show as Bound.

Scaling has the same gates as creation. The controller will not scale down while any member is unhealthy, because it cannot tell a permanent fault from a passing one. In the source the one exception is the Pod being removed when it is itself the first unhealthy one. If db-0 fails after db-2 is gone, db-1 is not removed until db-0 is Running and Ready again. Scaling also comes before updates: Pods marked for removal are handled before the rolling update step. One more trap: applying the manifest again after kubectl scale puts replicas back to what the file says, and a HorizontalPodAutoscaler that manages the set needs spec.replicas left out of the file.

The field persistentVolumeClaimRetentionPolicy changes the default. It has two settings, whenScaled and whenDeleted, and each is Retain or Delete. It is stable since 1.32. The controller does not delete claims itself. It puts owner references on them and lets the garbage collector remove them after the Pod has gone, so the volume is unmounted first. A claim that already has another controller as owner keeps it, and the StatefulSet records a ConflictingController warning. The policy applies only to scaling down and to deleting the StatefulSet. A Pod that is deleted or loses its node always keeps its claim.

Chapter 10 of 13

Growing a disk, and the fields that never change

volumeClaimTemplates is fixed. The claims themselves can grow

The conversations keep coming, and 50Gi per member will not last. The obvious move is to raise the size in volumeClaimTemplates. The API server refuses it. Four fields of a StatefulSet cannot be changed once it exists: selector, volumeClaimTemplates, serviceName and podManagementPolicy. Everything else, such as replicas, the Pod template, the update strategy, minReadySeconds, ordinals, the retention policy and revisionHistoryLimit, may be edited.

The claims are separate objects, so they can be changed one by one. A PersistentVolumeClaim can grow only when its StorageClass sets allowVolumeExpansion to true, and it can never shrink below its current size. You patch storage-db-0, storage-db-1 and storage-db-2 to 100Gi each. The storage driver grows each volume, and the claim's status shows the new capacity when the work is done. Some drivers can grow a volume while it is mounted. Others need the Pod restarted, which in a StatefulSet means deleting the member and letting it come back as itself.

The template still says 50Gi. That matters only for a claim that does not exist yet. If you later scale to four, storage-db-3 is created at 50Gi while the other three hold 100Gi. A claim that already exists is used as it is, whatever its size. The only way to give the template a new size is to create the StatefulSet again. Deleting it with --cascade=orphan removes the object and leaves the Pods and their claims running. In the StatefulSet tutorial, a StatefulSet created again over orphaned Pods adopts the ones it finds Running and Ready, one ordinal at a time.

Chapter 11 of 13

A silent node and a name that must stay unique

The Deployment replaces its Pod. The StatefulSet waits

Next, gpu-node-2 stops answering. On it are db-2 and the model server qwen3-6f7d9c8b4-m9q4t. The control plane marks the node unreachable and taints it. Every Pod carries an automatically added toleration for that taint with tolerationSeconds 300, unless the Pod sets its own. So after 300 seconds both Pods are marked for deletion. The kubelet that should confirm the deletion cannot be reached, so both stay in Terminating. A graceful kubectl delete pod against them would end in the same state.

For qwen3-6f7d9c8b4-m9q4t the ReplicaSet does not wait. A Pod marked for deletion no longer counts, and a replacement is created at once. It belongs to the same revision, so it keeps the hash 6f7d9c8b4 and gets new random characters: qwen3-6f7d9c8b4-r5v8n. The StatefulSet controller will not do that. It promises at most one Pod with a given identity, and the documentation names that at most one semantics. It cannot know whether the old db-2 is dead or still running and writing behind a broken network link. Two members with one identity would be a split brain, which in a quorum system can lose data. So db-2 stays Terminating and nothing replaces it until someone confirms the node is gone, by deleting the Node object, or the node returns.

The volume holds a second lock. The VolumeAttachment that ties storage-db-2's volume to gpu-node-2 is not removed while the node is shut down, so the volume cannot be attached anywhere else. The documentation adds that if a Pod's deletion has not succeeded after 6 minutes and the node is unhealthy, Kubernetes force detaches the volumes being unmounted. That timer does not free db-2's volume while the Pod object is still there. The attach/detach controller's source treats a Pod as finished only when its phase is Succeeded or Failed, or when it has a deletion timestamp and no container is reported running. db-2's last status, sent before the node went silent, still shows its containers running, so the controller still wants the volume attached to gpu-node-2. The 6-minute timer applies to a volume the controller has already decided to detach, which happens here only after the Pod object is removed. The forced detach skips the rule that a volume is detached only after the node has unmounted it, and the documentation warns that the data may be corrupted. An administrator can turn the forced detach off with disable-force-detach-on-timeout in kube-controller-manager's configuration.

Chapter 12 of 13

A quicker way out: the out-of-service taint

Tell the cluster the node is down, and it moves the Pods and their volumes

Deleting the Node object works, but it throws away the object along with any labels and taints someone added to it by hand. Kubernetes has a supported alternative for a node that is known to be off: the taint node.kubernetes.io/out-of-service, part of non-graceful node shutdown handling, stable since 1.28. Replay the failure of gpu-node-2 with it. You first check that the machine is shut down or powered off, and not in the middle of a restart. Then you add the taint with the effect NoExecute or NoSchedule.

The control plane then does two things at once. Pods on the node that do not tolerate the taint are force deleted, so db-2 and qwen3-6f7d9c8b4-m9q4t leave Terminating within moments. And the volume detach for those Pods happens immediately, without waiting for the 6 minute forced detach and without asking the dead kubelet. The StatefulSet controller sees ordinal 2 free, creates db-2 on gpu-node-1, and the volume storage-db-2 attaches there. The new member mounts its data, skips the clone and rejoins replication.

The taint is a statement you make on the cluster's behalf, with the same weight as a force delete. If the machine was only cut off from the network and is still running, the old db-2 may still write to its disk. The documentation is explicit about the order: confirm the node is down first, and remove the taint yourself after the Pods have moved. A node that comes back with the taint still in place gets no Pods scheduled onto it.

Chapter 13 of 13

Taking the whole StatefulSet away

No order is promised, and the Service and the claims stay

The chat application moves to a managed database, and db is no longer needed. Deleting a StatefulSet gives no promise about the order or the grace of its Pods' termination. The documentation's advice is to scale it to 0 first. Scaling down follows the usual rules, from the highest ordinal down, one at a time, each Pod gone before the next is touched. Only then delete the object.

Two things survive the delete. The headless Service db is a separate object and the StatefulSet does not own it, so it stays until you delete it. The claims stay too, unless whenDeleted is Delete. The documented teardown reads the Pods' terminationGracePeriodSeconds into a variable, deletes the StatefulSet, sleeps for that many seconds so the Pods can finish, and only then deletes the claims by label.

Deleting a claim is not always immediate. While a Pod still uses it, the claim shows Status Terminating and the finalizer kubernetes.io/pvc-protection in kubectl describe, and its removal waits until no Pod uses it. Once it goes, the reclaim policy of the PersistentVolume decides the data's fate. A dynamically provisioned volume takes the policy of its StorageClass, and that is Delete unless the StorageClass says otherwise. So deleting storage-db-0, storage-db-1 and storage-db-2 here destroys all 300Gi of conversations. Take a backup first. A volume with the policy Retain is kept, and an administrator has to clean it up by hand.

What to keep

An identity, kept by refusing shortcuts

A StatefulSet treats each Pod as an individual. The ordinal gives it a name, the headless Service turns the name into a DNS record, and the claim template gives the name a disk that stays when the Pod is gone. Everything else follows from protecting that identity. Pods are created in order and removed in reverse, and the controller's log and events say which gate holds it. Updates go from the highest ordinal down, each Pod labelled with the revision it came from, and a partition can stop them early. Scaling down keeps the claims unless a retention policy says to delete them, and growing a disk means editing each claim because the template is fixed. When a node goes silent, the controller leaves the Pod Terminating instead of risking two Pods with one name, until you delete the Node or mark it out of service. A Deployment would have replaced it within minutes, and for a database that speed would be the danger.
