Models

A model bigger than one GPU

Three ways to split the work, and what each asks of the link

Every GPU worker in the factory so far held a whole model. That stops working as models grow. A model of 72 billion weights takes 145 GB at two bytes per weight, and an H100 SXM has 80 GB. It has to be spread over several GPUs, and there is more than one way to cut it. Each way decides how often the GPUs have to talk and how much they say, and that decides whether they can sit in different servers or must share one. The same choice comes back in training, with one more option. This lesson cuts one model two ways on two servers, counts what crosses the link each time, shows the third way that training adds, and ends by putting the two cuts together.

Chapter 1 of 8

It does not fit

Weights first, and then room to work

Start with the arithmetic. This model has 72.7 billion weights. Stored as 16-bit numbers that is 145 GB, and they all have to be in GPU memory, because reading them from the server's own memory across the bus would be far too slow. One H100 SXM has 80 GB. Two have 160 GB, which holds the weights and leaves at most about 14.6 GB. That remainder is not spare. It is where the KV cache of every conversation lives, at 327,680 bytes per token for this model, so two GPUs leave room for at most about 44,500 tokens across everyone being served at once. That is an upper bound. vLLM by default lets itself use 90% of each GPU's memory (gpu_memory_utilization 0.9), and the working space for a pass and the CUDA graphs it records take a share too, so the real room is smaller, and two GPUs are a tight fit for this model. Storing the weights in 8 bits would halve them, and the lesson Prefill and decode shows that trade. Here the weights stay as they are and the model is split.

Chapter 2 of 8

The same code, a different file

The transformer is shared, and the model is in its weights

Before cutting the model, look at what there is to cut. A language model is two things. The first is the transformer, the formula that takes a list of tokens and works out a score for every possible next token. It is written once in code, and where makers publish their code, as Meta does for Llama and Alibaba does for Qwen, it is broadly the same from one model to the next. The second is the weights, the numbers that training produced and that the formula multiplies by. Most of what makes one model different from another lives in the weights, and so does everything a model knows. A few settings, such as how many layers there are and how wide each table is, decide the shape the weights fill. The formula is about a page of code. In the Hugging Face Transformers library the whole Llama model, with its attention, its feed-forward part, its normalisation and the loop over the layers, is one file of about 500 lines, comments included. The weights are a file of numbers on disk, and for the model in this lesson that file is 145,412,407,296 bytes.

Open-weight models let you check this, because their makers publish the settings next to the weights in a file called config.json. The model in this lesson is Qwen2.5-72B, from Alibaba's Qwen team. The files quoted here are from its chat build, Qwen2.5-72B-Instruct, which has the same shape and the same total size as the base build. Put its config.json next to that of Meta's Llama 3.1 70B. Both have 80 layers. Both pass a list of 8,192 numbers per token from layer to layer. Both have 64 query heads and 8 key and value heads of 128 numbers each, so both keep 327,680 bytes of KV cache per token. Both use the same activation, SiLU. The differences are small settings. Qwen's feed-forward part is 29,568 wide and Llama's 28,672. Qwen knows 152,064 different tokens and Llama 128,256. Qwen adds a bias, a small list of extra numbers, to three of its attention tables. Out of those settings come 72,706,203,648 weights for Qwen and 70,553,706,496 for Llama. In the Transformers library the Qwen2 code is written as a 207-line file, modular_qwen2.py. It takes its attention, its feed-forward part and its layer from the Llama code, its model class from the Mistral code and its rotary position code from the Gemma2 code. It adds the bias, and handling for a sliding window of attention that Qwen2.5-72B's config.json leaves switched off. A tool generates from it the file that actually runs, modeling_qwen2.py, which is 494 lines long.

For the closed models only the outline is public. OpenAI's GPT-4 technical report says that GPT-4 is a Transformer-based model pre-trained to predict the next token in a document, and gives no sizes. Meta's Llama 3 paper calls its largest model a dense Transformer with 405 billion parameters. Where a maker publishes the details, as with Llama and Qwen, the blocks are close enough to share code. Where it does not, broadly the same shape is as far as anyone outside can say.

The weights file is plain. Qwen2.5-72B ships as 37 files named model-00001-of-00037.safetensors to model-00037-of-00037.safetensors, and one more, model.safetensors.index.json, maps each of its 963 tensor names to the file that holds it and gives total_size 145,412,407,296. A tensor is one table of numbers. Each safetensors file starts with 8 bytes holding a number N, the size of the header. The next N bytes are JSON that lists every tensor in the file with its name, its number type, its shape and where its bytes start and end. The rest of the file is the numbers, back to back. In the first file N is 1,392, and the first tensor, model.embed_tokens.weight, is 152,064 rows of 8,192 BF16 numbers taking bytes 0 to 2,491,416,576. There is no code in it. config.json says which code to use: its architectures field reads Qwen2ForCausalLM, and vLLM looks that name up in its own list of supported models to pick the code it fills with these numbers.

This is what makes a model splittable. Every GPU runs the same code, and every tensor carries its layer number in its name, so splitting the model comes down to which numbers each GPU loads. For a cut between layers, GPU 0 loads model.embed_tokens.weight and every tensor from model.layers.0 to model.layers.39, which is 72,706,195,456 bytes. GPU 1 loads model.layers.40 to model.layers.79, model.norm.weight and lm_head.weight, which is 72,706,211,840 bytes. For a cut inside the layers, each GPU loads 4,096 of the 8,192 rows of every query table, which is 32 of the 64 query heads, and 4 of the 8 key and value heads. The model this site's cluster serves, Qwen3-32B, is the same kind of file. Its config.json names Qwen3ForCausalLM, with 64 layers, 5,120 numbers per token, 64 query heads and 8 key and value heads. Its BF16 build is 65.5 GB and its FP8 build Qwen3-32B-FP8 is 34.3 GB, so the FP8 build fits one 80 GB H100 and needs no cut at all.

Chapter 3 of 8

Cut it between layers

Pipeline parallelism: the first half here, the second half there

The simplest cut follows the model's own shape. A transformer is a stack of blocks, and each block only needs the output of the one below. So put layers 1 to 40 on GPU 0 and layers 41 to 80 on GPU 1. A token goes up through the first 40 layers on one GPU, and what comes out is handed to the other, which runs the rest. What comes out of a layer is one list of 8,192 numbers per token, 16,384 bytes. For a prompt of 1,248 tokens the whole hand-off is about 20 MB, once. During decode it is 16,384 bytes per token written. That is very little to send, so this cut works between servers, over the ordinary fabric.

Chapter 4 of 8

Cut it inside every layer

Tensor parallelism: both GPUs work on every layer

The other cut goes the other way. Each layer is mostly a few very large tables of weights, and a table can be sliced down the middle. Give each GPU half of every table in every layer. Now both work on the same layer at the same moment, neither waits for the other, and a pass takes about half as long. But half a table gives half an answer. Inside every layer the GPUs have to add their partial results together before the layer can finish, once after attention and once after feed-forward. With 80 layers that is 160 exchanges for every pass, which during decode means 160 exchanges for every single token written. Each one is small. What hurts is that the GPUs cannot go on until it has arrived.

Chapter 5 of 8

So chatter stays in the box

NVLink inside a server, the fabric between servers

A cut that talks 160 times per token needs the shortest and widest path there is. Inside one server, GPUs are joined by NVLink, direct links from GPU to GPU that skip the host and the network. An H100 SXM has 900 GB per second of it. A 400 gigabit network port carries 50 GB per second, and each trip through it adds a network card and a switch on the way. So the rule that falls out is simple. Cut inside the layers when the GPUs share a box. Cut between layers when they do not. Large deployments do both at once: tensor parallel across the eight GPUs of each server, and pipeline parallel from server to server.

Chapter 6 of 8

One server made of several Pods

Why a Deployment or a StatefulSet is the wrong shape

On Kubernetes a model split across two machines runs as two Pods, and the usual tools misread them. A Deployment thinks they are two copies of one service and will happily replace one while the other keeps running. But these Pods are halves of a single server. If one restarts it loses its half of the weights and its half of every KV cache, and the other half is useless until the pair is rebuilt together. Scaling out means adding a whole new pair, never one more half. A LeaderWorkerSet describes exactly that: a group with one leader Pod and its workers, created, restarted and scaled as one unit. Each worker is told the leader's address when it starts, and the pair joins up before it takes traffic.

Chapter 7 of 8

Training adds a third way

Data parallelism: whole copies, different text

Training has the same two cuts and one more that serving has no use for. If a model fits on one GPU, give every GPU a complete copy and a different slice of the batch. Each works out its own slopes for every weight from its own text. Then all the GPUs average their slopes, an exchange called all-reduce, and every copy takes the same step, so they stay identical. The run finishes sooner because each step sees more text. It saves time and no memory at all: every GPU still holds everything. And what is exchanged is no longer one list per token. It is a slope for every weight, on every step, between all the GPUs of the job.

Chapter 8 of 8

Both cuts at once

Tensor parallel inside each server, pipeline parallel between them

Real deployments use the two cuts together, each where it fits. Take two servers with eight H100 SXM GPUs each, joined by NVLink inside the server and by the fabric between them. Cut inside the layers across the eight GPUs of each server, and between layers from one server to the other. vLLM calls these two settings tensor parallel size 8 and pipeline parallel size 2. Server A runs layers 1 to 40 and server B runs layers 41 to 80, and inside each server every table of those layers is sliced eight ways. This model slices cleanly by eight. Its 64 query heads give 8 to each GPU, its 8 key and value heads give 1 to each, its feed-forward width of 29,568 gives 3,696 to each and its 152,064 tokens give 19,008 to each.

Now count what crosses where for one token of the answer. Inside server A, 40 layers with 2 exchanges each make 80 exchanges, all over NVLink. Then one hand-off of 16,384 bytes goes across the fabric to server B. Inside server B, another 80 exchanges stay on NVLink. The chatty cut never leaves a box, and the network carries one small hand-off per pass.

Memory changes even more. Each GPU holds one sixteenth of the weights, about 9.1 GB, which leaves at most about 70.9 GB. Each GPU keeps the keys and values of one head in each of its 40 layers, which is 40 × 2 × 1 × 128 × 2 = 20,480 bytes per token. So each GPU has room for at most about 3.46 million tokens, against at most about 44,500 when two GPUs held everything. Spreading the weights thinner leaves far more room for the conversations themselves.

What to keep

Where you cut decides what the link must do

A model that does not fit on one GPU has to be split, and the way it is split sets the demands on what joins the GPUs. Cut between layers and one small result crosses per pass, so the halves can sit in different servers. Cut inside the layers and both GPUs work at once, at the cost of two exchanges in every layer, which only a direct link inside one server can carry well. Training adds whole copies that exchange a slope for every weight on every step. Real systems nest all three. On Kubernetes the pieces of one model are one unit that must start, restart and scale together, which is what a LeaderWorkerSet is for.
