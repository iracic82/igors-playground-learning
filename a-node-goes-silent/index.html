Kubernetes underneath

A node goes silent

What the cluster does when a GPU node stops answering, and how long the capacity is really gone

A node that fails does not say so. It stops renewing a small object, and the control plane has to decide how long silence may last before it means something. Kubernetes answers with two timers. After 50 seconds the node is marked as unknown and traffic is steered away from its Pods. After 300 more seconds the Pods are deleted and replaced. For a web server the story ends there. A model server then has to find a free GPU on another node and load 34.3 GB of weights, the size of the FP8 build Qwen3-32B-FP8.

This lesson follows gpu-node-2 from its last heartbeat to its return, and adds up the time. On the way it opens each step: how the heartbeat is timed and retried, how the controller measures silence on its own clock, the four conditions and two taints written at the 50 second mark, the rate limits that slow everything down when many nodes fail at once, the tolerations that hold the Pods for five minutes, the Pod that stays Terminating, and how a network partition differs from a power cut.

Chapter 1 of 12

A small object says the node is alive

The kubelet renews a Lease every 10 seconds

Every node has a Lease object with the node's own name, kept in the namespace kube-node-lease. The kubelet, the agent on the node, updates it every 10 seconds. The update changes one field, spec.renewTime. That is the node's heartbeat. The 10 seconds is derived. The kubelet writes nodeLeaseDurationSeconds, 40 by default, into the Lease and renews at a quarter of it. Raising the duration to 80 would make it renew every 20 seconds. The renew loop also adds jitter of up to 4%, so consecutive renewals are 10 to 10.4 seconds apart.

There is a second, slower heartbeat. The kubelet works out the node's full status every 10 seconds, set by nodeStatusUpdateFrequency, and sends it only when something changed, or when nodeStatusReportFrequency, five minutes by default, has passed without a report. The Lease exists because the full status is large and a cluster may have thousands of nodes. A tiny write every 10 seconds costs far less than a full status every 10 seconds. One trap sits in the defaults. If nodeStatusUpdateFrequency is set explicitly, the default of nodeStatusReportFrequency follows it, and the full status is sent on every interval again.

If an update of the Lease fails, the kubelet's lease controller makes 5 update attempts in a row, with no wait between them. Each failure logs Failed to update lease. If all 5 fail, it stops trusting its cached copy and falls back to fetching the Lease again, or creating it if it is gone. Only that fetch or create backs off: after a failure it waits 200 milliseconds, then twice as long each time, capped at 7 seconds, and it keeps trying until one call succeeds. Then it makes 5 more update attempts. If those fail too, the next round comes at the next renew tick, 10 seconds later. The error of a failed round is failed 5 attempts to update lease, and it reaches the log inside the line failed to update lease using latest lease, fallback to ensure lease, or Will retry updating lease. Here gpu-node-2 renews its Lease at 09:00:00. It is the last time it will.

Chapter 2 of 12

The power goes and nobody is told

A dead node sends no message, so every record stays as it was

At 09:00:04 gpu-node-2 loses power. The kubelet, the container runtime and the model server in Pod qwen3-6f7d9c8b4-m9q4t all stop in the same instant. With them go the 34.3 GB of FP8 weights in GPU memory, the KV cache of every request in its batch, and every request that was being answered. Those callers see a connection that stops sending tokens.

None of the stopped programs had time to send anything, so nothing in the API server changes. The Node still says Ready. The Pod still says Running. The EndpointSlice, the list of Pod addresses behind the Service qwen3, still lists 10.244.2.22 as ready. The gateway reads that list, so it keeps sending every second request to an address where nothing answers. Those requests wait and then time out. How long they wait depends on the gateway's own connect and request timeouts, which Kubernetes does not set.

A power cut skips the kubelet's graceful node shutdown entirely. That feature relies on systemd inhibitor locks to delay a planned shutdown, and it is off by default. A cut cable has the same effect from the control plane's side as a power cut. The renewals due at 09:00:10, 09:00:20 and later never arrive. The control plane can only measure how long it has heard nothing, and it has no way to tell a dead machine from a lost link.

Chapter 3 of 12

How the controller measures silence

It times the gap on its own clock, every 5 seconds

The node controller is one of the loops inside kube-controller-manager. Every 5 seconds, set by --node-monitor-period, it looks at each node. It never compares the node's clock with its own. Instead it keeps a probe timestamp for each node, taken from its own clock at the moment it sees the Lease's renewTime move forward or the Ready condition's lastHeartbeatTime change. A node whose clock is wrong by a minute is judged exactly like any other.

Either heartbeat is enough. The source says so in a comment: if a kubelet never posted node status but keeps renewing its Lease, the controller assumes the node is healthy and takes no action. A node is declared unknown only when both have been quiet for longer than the grace period.

The grace period is the flag --node-monitor-grace-period. Its default is 50 seconds. Before Kubernetes v1.32 it was 40. The flag's description sets two rules for it. It must be several times the kubelet's nodeStatusUpdateFrequency, so a kubelet can retry a few times before the node is judged. And it should be longer than the time the HTTP/2 health check of the kubelet's connection to the API server can take, about 45 seconds, so a broken connection is replaced before the node is declared lost.

A node that never reported at all gets a different timer. --node-startup-grace-period, 1 minute by default, applies to a node that is starting. A freshly provisioned GPU node whose kubelet never comes up is marked with the reason NodeStatusNeverUpdated and the message Kubelet never posted node status.

Chapter 4 of 12

After 50 seconds, Unknown

The node controller marks the node and taints it

When the gap passes the grace period, the controller writes the node's conditions. It writes four of them, not only Ready. Ready, MemoryPressure, DiskPressure and PIDPressure all become Unknown, each with the reason NodeStatusUnknown and the message Kubelet stopped posting node status. NetworkUnavailable is left alone, because the control plane manages it. Unknown means the control plane has heard nothing. Had the kubelet itself reported a problem, Ready would be False.

What an operator sees differs by tool. kubectl get nodes prints NotReady for gpu-node-2. The printer adds the word Not in front of the condition type whenever Ready is anything but True, so Unknown and False look the same there. kubectl describe node shows the four rows with status Unknown. The controller records a Normal event on the Node with the reason NodeNotReady and the message Node gpu-node-2 status is now: NodeNotReady.

The controller then adds taints to the node. A taint is a mark on a node that repels Pods. The scheduler checks taints, not conditions, so every condition has a taint that mirrors it. For Ready Unknown that is node.kubernetes.io/unreachable with the effect NoSchedule, which keeps new Pods away. The same key is also added with the effect NoExecute, which applies to Pods already running there. For Ready False the key would be node.kubernetes.io/not-ready instead. Other conditions have their own keys, such as node.kubernetes.io/memory-pressure, and a cordoned node carries node.kubernetes.io/unschedulable.

Chapter 5 of 12

When many nodes fail at once

The NoExecute taint is rate limited, and sometimes held back entirely

One silent node is the easy case. When a switch fails and a whole rack goes quiet, removing every Pod at full speed could make things worse. So the control plane limits the rate at which it adds the NoExecute taint, separately for each zone. A cluster without zones counts as one zone.

The normal rate is --node-eviction-rate, 0.1 nodes per second by default, which means no more than one node every 10 seconds. Ten silent nodes are tainted over 90 seconds, the first at once and the last 90 seconds later, so the last one's 300 second timer starts late and its Pods are replaced a minute and a half after the first.

The controller also judges each zone. A zone where no node is Ready and at least one is not is in full disruption. A zone is partially disrupted when more than two nodes are not Ready and they make up at least --unhealthy-zone-threshold of it, 0.55 by default. In a partially disrupted zone the rate drops to --secondary-node-eviction-rate, 0.01 per second. In a zone of 50 nodes or fewer, set by --large-cluster-size-threshold, that secondary rate becomes 0, so evictions stop. The threshold is compared with the number of nodes in each zone, the flag's description says so, and the code counts the nodes of the zone. So a cluster of 300 nodes with a zone of 40 also stops evicting in that zone when it is partially disrupted.

The last case is every zone in full disruption. Then the controller assumes the fault is between itself and the nodes, logs Controller detected that all Nodes are not-Ready. Entering master disruption mode, and evicts nothing. If both GPU nodes and every other node of this cluster went silent together, no Pod would be replaced. Here only gpu-node-2 is silent, the zone stays normal, and its taint is added at once.

Chapter 6 of 12

Traffic leaves first

The Pod is marked not ready long before it is deleted

The Pod on the dead node cannot report its own state, so the node controller does it. As soon as the node is no longer Ready, the controller sets the Ready condition of every Pod on it to False. It does this one Pod at a time. If an update fails, it keeps the node in a retry list and tries again on its next pass, five seconds later. On a node with many Pods, traffic leaves Pod by Pod. Each Pod also gets a Warning event with the reason NodeNotReady and the message Node is not ready.

That one change is what moves traffic. The EndpointSlice controller watches Pods, and it rewrites the entry for 10.244.2.22. An endpoint has three conditions. serving follows the Pod's Ready condition. terminating says whether the Pod is being deleted. ready is a shortcut for serving and not terminating. All three are now false. A Service with spec.publishNotReadyAddresses would keep ready true, which a model server should not use. Each endpoint also carries nodeName and zone, so a gateway could act on a whole node at once.

The gateway's controller watches EndpointSlices and takes the address out of the data plane. From about 09:00:51 every request goes to qwen3-6f7d9c8b4-x7k2p. The Pod object still exists, it is still bound to gpu-node-2 and its phase is still Running. Requests failed for 47 seconds. The cluster now has half its capacity and no errors, and it will stay that way for a while.

Chapter 7 of 12

Five minutes of patience

Every Pod tolerates an unreachable node for 300 seconds

A NoExecute taint removes the Pods that do not tolerate it. A toleration is the matching entry on a Pod that lets it stay. When any Pod is created, the DefaultTolerationSeconds admission plugin in the API server adds two tolerations to it: one for not-ready and one for unreachable, each with tolerationSeconds: 300. It skips a key when the Pod already tolerates it with effect NoExecute or with no effect. The 300 comes from two API server flags, --default-not-ready-toleration-seconds and --default-unreachable-toleration-seconds, so an administrator can change it for every Pod at once.

So the taint starts a timer of five minutes. A node often goes quiet because of a reboot or a short network fault, and deleting everything on it at the first silence would be costly. Since v1.29 the timer is kept by its own component, the taint-eviction-controller, which an administrator can switch off with --controllers=-taint-eviction-controller. For each Pod it takes the smallest tolerationSeconds among the tolerations that match the node's NoExecute taints and counts from the moment it handles the change to the node or the Pod. Here that is the same second the taint was added. If a timer for the Pod is already queued, it keeps the earlier start. The taint's timeAdded field is not what it reads, so a restart of kube-controller-manager starts the timers again from the restart. A matching toleration without tolerationSeconds means forever. A Pod with no matching toleration at all is deleted at once.

If the node answers in time, the taint is removed and the timer is cancelled. Here it does not. At 09:05:50 the controller adds a DisruptionTarget condition to Pod qwen3-6f7d9c8b4-m9q4t and deletes it, with a Normal event TaintManagerEviction. A PodDisruptionBudget does not stop this. Budgets limit voluntary disruptions such as drains, and a dead node is involuntary.

Chapter 8 of 12

A new Pod needs a GPU and three minutes

Replacing the object is fast and loading the model is slow

The Deployment qwen3 owns a ReplicaSet, an object whose controller keeps a set number of Pods in existence. It wants two. A Pod with a deletion timestamp no longer counts, so the controller sees one and creates another at once, while the old one still shows Terminating. Nothing is moved. The new Pod, qwen3-6f7d9c8b4-r5n8w, starts from nothing: no node, no address, no model.

The scheduler filters the nodes before it scores them. gpu-node-2 fails the taint filter, because qwen3-6f7d9c8b4-r5n8w tolerates the unreachable taint only for NoExecute, and the NoSchedule copy of the taint has no matching toleration. That leaves gpu-node-1, and the Pod fits only if one of its four GPUs is free. The scheduler compares the Pod's request of nvidia.com/gpu: 1 with what the node can allocate minus what other Pods already requested. Here three are in use, one by qwen3-6f7d9c8b4-x7k2p and two by other GPU workloads on the node, which are illustrative. So one is free and it fits.

The kubelet on gpu-node-1 sees the binding and asks containerd to start the container. The image is already on the node because qwen3-6f7d9c8b4-x7k2p uses the same one, so there is no pull. Ten seconds after the delete, a span that covers creating qwen3-6f7d9c8b4-r5n8w, scheduling it, binding it and starting the container, the container is running, and then the model has to load: 34.3 GB of FP8 weights, about three minutes. During that time the Pod's phase is Running and its Ready condition is False, so it is not yet an endpoint of the Service. The readiness probe passes at 09:09:00.

Chapter 9 of 12

The Pod that stays Terminating

Only three things remove a Pod from a node that does not answer

The delete at 09:05:50 set a deletion timestamp on qwen3-6f7d9c8b4-m9q4t. The object stays, and kubectl get pods shows it as Terminating for as long as the node is silent. The documentation lists exactly three ways it can leave the API server. The Node object is deleted, by a person or by the node controller. The kubelet on the node starts answering, stops the Pod and removes the entry. Or a user force deletes the Pod.

Force deletion is kubectl delete pods qwen3-6f7d9c8b4-m9q4t --grace-period=0 --force. It does not wait for the kubelet to confirm that the containers have stopped. For a Deployment that is harmless once the node is truly dead. For a StatefulSet it can break the rule that at most one Pod runs with a given name, if the node was only cut off.

Deleting the Node is the clean choice when the machine is gone for good. The Pod garbage collector then finds Pods bound to a node that no longer exists. It runs every 20 seconds and waits 40 seconds in case the node reappears. It adds DisruptionTarget with the reason DeletionByPodGC and the message PodGC: node no longer exists, marks the Pod Failed and deletes it. In a cloud this can happen without a person. When a node is unhealthy, the cloud's node controller asks the provider whether the machine still exists, and deletes the Node if it does not.

A third route exists for a node known to be shut down. Adding the taint node.kubernetes.io/out-of-service force deletes Pods without a matching toleration and detaches their volumes at once. Check first that the machine is off, and remove the taint by hand afterwards. Without it, a volume stuck on an unhealthy node is force detached after 6 minutes.

Chapter 10 of 12

Add up the time

Four waits in a row, and the gateway only shortens the first

Now the sum. The node died at 09:00:04. For 46 seconds nobody knew. For 300 seconds the cluster knew and waited. Ten seconds went on creating, scheduling and starting a Pod. Then 180 seconds went on loading the model. The second model server was missing for 536 seconds, which is 8 minutes and 56 seconds. The gateway reacted in the first minute, so callers saw errors for 47 seconds and then a service at half its capacity for the other 489.

Two of the four waits can be changed. The toleration is a field on the Pod, and a shorter one means an earlier replacement. With 30 seconds the same failure costs 46 + 30 + 10 + 180 = 266 seconds, 4 minutes and 26 seconds. The grace period can be lowered too, but it is a flag for the whole cluster, and the rules in its description set a floor near 45 seconds.

The price of a short toleration is that a node which was only unreachable for a minute loses a loaded model for nothing. A reboot that takes 90 seconds would delete the Pod, start a replacement elsewhere and pay the three minutes, when waiting would have cost less. The right value depends on how a node usually fails in a given cluster.

The last wait is the model itself. With a 30 second toleration, loading is 180 of the 266 seconds, about two thirds, and no Kubernetes setting shortens it. A spare model server that is already loaded on another node is the only thing that removes it.

Chapter 11 of 12

The node comes back

It returns empty, and its old Pod is finally removed

At 09:15:00 the power is back and the kubelet on gpu-node-2 starts. It renews its Lease and sends its status with Ready set to True, the reason KubeletReady and the message kubelet is posting ready status. The node controller sees a fresh probe, records the change and removes both taints. The scheduler may use the node again, and the device plugin, a DaemonSet Pod that was never evicted, reports its four GPUs.

The kubelet also finds Pod qwen3-6f7d9c8b4-m9q4t in the API server, bound to this node and marked for deletion. After a power loss nothing of it is running, so the kubelet has nothing to stop. It confirms the deletion and the object is removed. The Pod was shown as Terminating for 9 minutes and 10 seconds.

Nothing is moved back. Kubernetes does not rebalance running Pods. qwen3-6f7d9c8b4-r5n8w stays on gpu-node-1 beside qwen3-6f7d9c8b4-x7k2p, and gpu-node-2 has four free GPUs. Both model servers now share one node, so a second failure of gpu-node-1 would take out all of the capacity. Spreading them again means deleting one Pod on purpose, which costs another three minutes of loading, or using a topology spread constraint for new Pods from the start.

Had the node returned before 09:05:50, the taint would have come off in time and the timer would have been cancelled with the event Cancelling deletion of Pod inference/qwen3-6f7d9c8b4-m9q4t. After a power loss the container would still have to start again and load the model again, but the Pod would keep its name and its node.

Chapter 12 of 12

A partition is not a power cut

The same timers, with a model server still running where nobody can see it

The control plane sees a partition exactly as it saw the power cut. The Lease stops, the node is Unknown after 50 seconds, the Pod is marked not ready, and after 300 more seconds it is deleted. The difference is on the node. The kubelet, containerd and vLLM keep running. qwen3-6f7d9c8b4-m9q4t still holds its GPU, its weights and its KV cache, and it may still be answering clients that reach it by another path.

The decision to delete cannot reach the node. The documentation says so directly: the kubelet learns of the deletion only when it can talk to the API server again, and until then the Pod may keep running. Meanwhile the scheduler has placed qwen3-6f7d9c8b4-r5n8w elsewhere. For a Deployment that means two copies for a while, which is harmless for a stateless model server. For a StatefulSet this is why the controller waits for the old Pod to be gone before it creates a new one with the same name.

When the link returns, the kubelet reads the deletion, stops the container gracefully and confirms. If the link returns within the 300 seconds, the node controller removes the taint, the taint eviction controller cancels the timer, and the model server simply stays. Nothing was lost but the traffic of those minutes, and the Pod was never deleted.

A planned shutdown is a third case. The kubelet's graceful node shutdown, when shutdownGracePeriod is set above zero, holds the shutdown with a systemd inhibitor lock and stops Pods first. Those Pods end with the reason Terminated and the message Pod was terminated in response to imminent node shutdown. Their replacements start without waiting for any timer.

What to keep

Two timers, then the model's own

A node fails silently, and Kubernetes turns that silence into action in fixed steps. The kubelet renews a Lease every 10 seconds. The node controller measures the gap on its own clock, and after 50 seconds it marks four conditions Unknown and taints the node. The Pods there are marked not ready at once, so traffic leaves within about a second. They are deleted only when their toleration runs out, 300 seconds later by default, and the rate of that is limited when many nodes fail together. The ReplicaSet controller then creates a new Pod, which needs a free GPU on a healthy node and three minutes to load its model. The old Pod stays Terminating until the node answers, the Node is deleted or someone forces it. The dead node returns empty. For model servers the sum is what matters: about nine minutes with the defaults, of which Kubernetes can give back five.
